1부

코드를 어디서 돌리고, 어떻게 잇는가

10장이 VPC, EC2, ALB, RDS 같은 부품을 하나씩 보았다면, 이 장은 그 부품들을 조립합니다. 먼저 애플리케이션을 올릴 컴퓨팅과, 서비스끼리 비동기로 잇는 메시징 선택지를 고릅니다.

오른쪽으로 갈수록 AWS가 더 많이 맡는다

같은 애플리케이션도 어디에 올리느냐에 따라 내가 관리할 층이 달라집니다. 오른쪽으로 갈수록 OS 패치나 서버 수 관리를 AWS가 대신하지만, 그만큼 실행 시간과 환경에 대한 제어권은 줄어듭니다.

판단 순서는 단순합니다. 트래픽이 들쭉날쭉하고 작업이 짧으면 Lambda, 상시 트래픽을 받는 API라면 컨테이너, OS 수준 제어가 필요하면 EC2입니다. 상시 고부하에서는 Lambda의 호출당 과금이 오히려 비싸질 수 있습니다.

Lambda는 이벤트가 올 때만 실행 환경을 빌린다

  1. 이벤트 발생HTTP, S3 업로드, SQS
  2. 실행 환경 확보microVM 하나 배정
  3. 핸들러 실행이벤트 1건 처리
  4. 결과 반환환경은 잠시 대기

서버리스는 서버가 없다는 뜻이 아니라, 서버를 내가 보지 않는다는 뜻입니다. Lambda는 이벤트가 오면 격리된 실행 환경(Firecracker microVM)을 배정하고 그 안에서 핸들러 함수를 부릅니다.

핵심 규칙은 실행 환경 하나는 한 번에 요청 하나만 처리한다는 것입니다. 요청 100건이 동시에 오면 환경 100개가 뜹니다. 이 규칙에서 콜드 스타트와 DB 커넥션 문제가 모두 나옵니다(2부).

작업을 SQS 메시지 단위로 쪼개 여러 함수가 나눠 처리하거나, Step Functions로 단계를 잇거나, ECS 태스크로 옮깁니다.

API Gateway가 함수 앞에서 문지기를 맡는다

  1. 클라이언트HTTPS 요청
  2. API Gateway인증, 스로틀링, 검증
  3. Lambda비즈니스 로직
  4. DynamoDB/RDS데이터 저장

Lambda는 HTTP를 직접 받지 않으므로 앞에 API Gateway를 둡니다. API Gateway는 경로별 라우팅, Cognito나 Lambda Authorizer를 이용한 인증, 토큰 버킷 방식의 스로틀링(8장 Rate Limiting)을 함수 바깥에서 처리합니다.

API는 29초 안에 끝나야 합니다

Lambda는 15분까지 돌 수 있지만, REST API의 통합 타임아웃 기본 최대값은 29초(HTTP API는 30초)입니다. 긴 작업은 접수만 하고 비동기로 넘깁니다.

8장에서 본 메시지 큐와 로그 기반 브로커(Kafka)의 차이가 그대로 이어집니다. 큐는 처리한 메시지를 지우고, 로그는 보존 기간 동안 남겨 여러 컨슈머가 각자 위치에서 읽습니다. MSK는 관리형 Kafka입니다.

2부

관리형 서비스 안에서 실제로 일어나는 일

콜드 스타트는 왜 생기는지, SQS는 어떻게 메시지를 잃지 않는지, 3-티어 구조의 각 부품은 어떤 장애를 흡수하는지 메커니즘으로 봅니다.

기초 원리 여기부터는 서비스 내부 동작과 장애 흡수 메커니즘을 다룹니다.

콜드 스타트는 실행 환경을 처음 만드는 비용이다

  1. 환경 생성

    새 microVM을 배정합니다.

  2. 코드 내려받기

    zip 패키지나 컨테이너 이미지를 가져옵니다.

  3. 런타임 시작

    JVM이나 Node.js 프로세스를 띄웁니다.

  4. 초기화 코드

    핸들러 밖 코드: SDK 클라이언트, DI 컨테이너 생성.

  5. 핸들러 실행

    여기부터가 요청 처리(Invoke) 시간입니다.

1~4단계가 콜드 스타트(Init 단계)입니다. 처리를 마친 환경은 한동안 살아 있다가 다음 요청에 재사용되는데, 이때는 5단계만 실행됩니다(웜 스타트).

그래서 무거운 초기화는 핸들러 밖에 두어 한 번만 치르게 합니다. Java는 JVM 기동과 클래스 로딩, Spring 컨텍스트 생성 때문에 4단계가 특히 깁니다. 실제 값은 로그 REPORT 줄의 Init Duration으로 확인합니다.

동시성은 요청률과 실행 시간의 곱이다

콜드 스타트를 줄이는 방법은 세 가지입니다. 미리 초기화된 환경을 유지하는 Provisioned Concurrency(대기 비용 발생), 초기화가 끝난 상태의 스냅샷에서 복원하는 SnapStart(Java 등), 그리고 의존성과 패키지를 줄이는 것입니다.

필요한 환경 수는 초당 요청 × 평균 실행 시간입니다. 초당 500건 × 0.2초면 환경 100개가 동시에 떠 있습니다.

환경마다 DB 커넥션을 연다면

트래픽이 튀는 순간 환경 수만큼 커넥션이 몰려 RDS의 최대 연결 수를 넘깁니다. Lambda와 RDS 사이에는 커넥션을 모아 주는 RDS Proxy(10장)를 둡니다.

VPC 안의 Lambda는 NAT 없이 밖으로 못 나간다

Lambda는 기본적으로 AWS가 관리하는 VPC에서 돌며 인터넷에 나갈 수 있습니다. Private Subnet의 RDS에 접근하려고 내 VPC에 연결하면, 함수는 그 서브넷의 Hyperplane ENI를 통해 통신합니다.

이 ENI에는 공인 IP가 없습니다. 그래서 Public Subnet에 붙여도 인터넷이 안 되고, Private Subnet → NAT Gateway 경로를 만들어야 외부 API를 부를 수 있습니다.

SQS는 꺼낸 메시지를 지우지 않고 숨긴다

컨슈머SQS 큐
ReceiveMessage
처리 시작 메시지 + 수신 핸들Visibility Timeout 시작 숨김
처리 완료 DeleteMessage 수신 핸들 영구 삭제
실패: 삭제 전에 컨슈머가 죽으면
중복 수신 같은 메시지 재전달다른 컨슈머가 받을 수도 있음 다시 보임

메시지를 받으면 SQS는 그것을 지우지 않고 가시성 제한 시간 동안 다른 컨슈머에게 숨깁니다. 기본 30초, 최대 12시간입니다.

처리를 끝낸 컨슈머가 직접 삭제해야 사라집니다. 그래서 컨슈머가 처리 도중 죽어도 메시지는 잃지 않습니다. 대가는 중복입니다.

잃지 않는 대가로 중복을 받아들인다

제한 시간을 처리 시간보다 짧게 잡으면 처리 중인 메시지가 다시 보여 두 번 처리됩니다. 반대로 너무 길게 잡으면 컨슈머가 죽었을 때 재시도가 그만큼 늦어집니다.

기준은 처리 시간 p99보다 넉넉하게 잡고, 긴 작업은 ChangeMessageVisibility로 중간에 연장하는 것입니다. Lambda가 SQS를 읽는다면 AWS는 함수 타임아웃의 6배 이상을 권장합니다.

중복은 반드시 온다고 가정합니다

Standard 큐는 최소 한 번(at-least-once) 전달입니다. 설정을 잘해도 중복은 생기므로, 메시지 ID나 비즈니스 키로 처리 이력을 확인하는 멱등 컨슈머(8장)를 만듭니다.

DLQ는 독이 든 메시지를 격리한다

  1. 소스 큐메시지 수신
  2. 처리 실패 반복수신 횟수 증가
  3. 임계 초과maxReceiveCount
  4. DLQ로 이동알람, 원인 조사
  5. Redrive고친 뒤 소스로 복귀

형식이 깨진 메시지처럼 몇 번을 다시 받아도 실패하는 메시지가 있습니다. 그대로 두면 끝없이 재전달되며 컨슈머 용량을 갉아먹습니다. DLQ는 수신 횟수가 maxReceiveCount를 넘은 메시지를 따로 빼 두는 큐입니다.

DLQ 메시지 수가 0보다 커지면 알람을 겁니다. Standard 큐에서는 만료가 원래 메시지의 등록 시각 기준이므로 DLQ 보존 기간을 소스 큐보다 길게 잡습니다.

롱 폴링을 켜 두세요

WaitTimeSeconds를 최대 20초로 주면 메시지가 올 때까지 응답을 미룹니다. 빈 응답과 API 호출 비용이 크게 줄어듭니다.

SNS 앞, SQS 뒤: 팬아웃의 기본 형태

주문 완료 이벤트 하나를 결제, 재고, 알림이 모두 받아야 할 때 SNS 토픽에 한 번 발행하고 각 서비스가 구독합니다.

SNS는 메시지를 저장하지 않고 밀어 넣기만 합니다. 그래서 구독자마다 SQS 큐를 하나씩 붙여 버퍼로 씁니다. 재고 서비스가 잠시 죽어도 메시지는 큐에 남고, 각 서비스는 자기 속도로 따로 확장합니다.

  2. ALB 우회

    헬스 체크에 실패한 대상을 빼고 AZ b로만 보냅니다.

  3. RDS 장애 조치

    대기가 기본이 되고 엔드포인트 DNS가 바뀝니다(보통 1~2분).

  4. 용량 회복

    Auto Scaling이 AZ b에 인스턴스를 더 띄웁니다.

  5. 재균형

    AZ a가 돌아오면 다시 두 곳에 나눠 배치합니다.

인프라가 자동으로 넘어가도 애플리케이션이 따라오지 못하면 장애는 계속됩니다. 10장에서 본 JVM DNS 캐시와 풀에 남은 죽은 커넥션이 대표적이므로, 장애 조치 훈련 때 앱이 실제로 다시 붙는지까지 확인합니다.

이 구조가 막지 못하는 것

리전 전체 장애, 잘못된 배포, 실수로 지운 데이터, DB 과부하는 Multi-AZ로 막을 수 없습니다. 그래서 관측성, 배포 전략, DR이 필요합니다.

3부

운영: 보고, 고치고, 대비하고, 아낀다

구조가 장애를 흡수해도 무엇이 일어나는지 볼 수 없으면 운영할 수 없습니다. 관측성에서 시작해 트러블슈팅, 보안, 용량, DR, 비용까지 실제 운영 판단을 다룹니다.

원리 실무 CloudWatch 지표, 알람 설계, 장애 사례와 대응 수치를 다룹니다.

메트릭, 로그, 트레이스는 다른 질문에 답한다

항목메트릭로그트레이스

모니터링이 미리 정한 지표를 지켜보는 것이라면, 관측성은 예상하지 못한 문제도 밖으로 드러난 데이터만으로 원인을 좁혀 갈 수 있는 성질입니다. 메트릭으로 이상을 알아채고, 트레이스로 구간을 찾고, 로그로 이유를 읽습니다.

CloudWatch는 지표, 로그, 알람을 한곳에 모은다

지표는 네임스페이스와 차원(인스턴스 ID 등)으로 구분된 시계열입니다. EC2 기본 모니터링은 5분, 세부 모니터링은 1분 간격입니다. 로그는 로그 그룹에 모이고 Logs Insights로 질의합니다.

로그 그룹의 기본 보존 기간은 무기한입니다. 보존 기간을 정하지 않으면 로그 저장 비용이 계속 쌓입니다.

EC2 메모리 지표는 기본으로 없습니다

CloudWatch는 하이퍼바이저에서 VM을 밖에서 봅니다. CPU, 네트워크, 디스크 I/O는 보이지만 게스트 OS 안의 메모리 사용량은 모릅니다. CloudWatch 에이전트를 설치해야 mem_used_percent가 생깁니다.

trace id 하나로 요청의 전 구간을 꿴다

요청이 들어올 때 추적 ID를 만들고, 서비스가 다른 서비스를 부를 때마다 헤더(W3C traceparent)로 넘깁니다. 각 구간은 시작과 끝 시각을 가진 span이 됩니다.

로그에도 같은 trace id를 찍으면 느린 span에서 바로 그 요청의 로그로 넘어갈 수 있습니다. 계측은 OpenTelemetry 표준으로 하고, 수집 백엔드로 X-Ray 등을 고르는 방식이 이식성이 좋습니다.

지연 시간은 평균이 아니라 백분위로 봅니다

요청 99건이 50ms, 1건이 5초면 평균은 약 100ms로 멀쩡해 보입니다. 그 1%의 사용자가 겪는 고통은 p99에서만 보입니다.

SLO는 얼마나 실패해도 되는지를 정한다

SLI는 측정값(성공 요청 비율), SLO는 내부 목표(30일간 99.9%), SLA는 어기면 보상하는 고객과의 계약입니다. SLO는 SLA보다 엄격하게 잡아 계약을 어기기 전에 알아챕니다.

100%에서 SLO를 뺀 나머지가 에러 예산입니다. 예산이 남으면 과감히 배포하고, 다 쓰면 기능 배포를 멈추고 안정화에 집중합니다.

가용성 SLO30일 허용 중단

 9가 하나 늘 때마다 허용 시간이 10분의 1로 줄고, 비용은 크게 늡니다.

알람은 사람을 깨울 가치가 있을 때만 울린다

알람은 사용자가 겪는 증상(에러율, p99 지연, SLO 소진 속도)에 겁니다. CPU나 GC 같은 원인 지표는 대시보드에 두고 조사할 때 봅니다.

모든 알람에는 받은 사람이 할 행동, 즉 런북 링크가 있어야 합니다. CloudWatch에서는 "5개 데이터 포인트 중 3개"처럼 조건을 걸어 순간적인 튐을 거르고, 여러 알람은 복합 알람으로 묶습니다.

"CPU 80%" 알람이 나쁜 이유

CPU가 높아도 사용자는 멀쩡할 수 있고, 매번 확인만 하고 닫다 보면 진짜 알람도 무시하게 됩니다(알람 피로). 울리면 반드시 행동하는 알람만 남깁니다.

"서버가 느려요"에 답하는 순서

  1. 범위 좁히기

    전체인가, 특정 API나 인스턴스인가. 언제부터, 배포와 겹치나.

  2. 지표

    골든 시그널, CPU, 메모리, GC 시간, DB 연결 수.

  3. 트레이스와 로그

    느린 span과 그 요청의 에러 로그.

  4. 스레드·힙 덤프

    스레드가 어디서 기다리는지, 무엇이 힙을 채우는지(5장).

  5. DB

    슬로 쿼리, 실행 계획, 락 대기(4장).

바깥에서 안으로, 싼 정보에서 비싼 정보로 내려갑니다. 서버 명령어는 9장에서 다뤘습니다.

장애 중에는 원인보다 완화가 먼저입니다. 배포 직후라면 롤백하고, 부하라면 스케일 아웃합니다. 단, 재시작 전에 스레드 덤프를 떠 두어야 증거가 남습니다.

장애 대응의 네 단계

탐지, 완화, 원인 분석, 포스트모템. 포스트모템은 사람이 아니라 시스템의 빈틈을 찾는 문서입니다.

지표 조합이 원인의 방향을 가리킨다

"CPU는 한가한데 느리다"는 가장 흔하고 헷갈리는 패턴입니다. 스레드가 일하지 않고 커넥션, 락, 외부 API 응답을 기다리고 있다는 뜻입니다.

커넥션 풀 고갈은 로그와 덤프로 확정한다

평소에는 HikariCP가 내보내는 대기 스레드 수(pending)와 대여 대기 시간을 지표로 걸어, 타임아웃 예외가 나기 전에 알람을 받습니다.

두 OOM은 흔적이 남는 곳이 다르다

JVM OutOfMemoryError(5장)와 컨테이너 OOM(9장)은 흔적이 남는 곳이 다릅니다. 앞의 것은 앱 로그와 힙 덤프를 남기지만, 뒤의 것은 커널이 SIGKILL로 끝내 앱 로그가 조용합니다.

그래서 힙 덤프 경로는 태스크가 사라져도 남는 볼륨(EFS 등)에 두고, 메모리 알람은 태스크 한도 기준으로 겁니다. 주기적인 p99 튐이 GC 정지와 겹치면 GC 튜닝(5장) 대상입니다.

# JVM OOM: 앱 로그와 덤프 파일
java.lang.OutOfMemoryError: Java heap space
Dumping heap to /dumps/java_pid1.hprof

# 컨테이너 OOM: 태스크 중지 사유에만
$ aws ecs describe-tasks --cluster prod \
    --tasks <id> \
    --query 'tasks[].containers[].reason'

 due to memory usage"   # exit 137

CloudTrail은 누가 무엇을 했는지 남긴다

AWS의 모든 조작은 API 호출입니다. CloudTrail은 콘솔 클릭까지 포함해 누가, 언제, 어디서, 어떤 API를 불렀는지 기록합니다. 관리 이벤트는 기본으로 90일간 조회할 수 있습니다.

장기 보관과 사후 감사를 위해서는 모든 리전을 대상으로 트레일을 만들어 별도 계정의 S3로 보내고, 로그 파일 무결성 검증을 켭니다. IAM 최소 권한(10장)이 예방이라면 CloudTrail은 탐지와 증거입니다.

Access Key가 유출됐다면

먼저 키를 비활성화하고, CloudTrail에서 그 키가 호출한 API를 확인해 만들어진 자원과 바뀐 권한을 되돌린 뒤, 새 키로 교체합니다. 애초에 장기 키 대신 Role을 씁니다.

비밀은 코드가 아니라 비밀 저장소에 둔다

애플리케이션은 기동할 때 IAM Role 권한으로 값을 읽어 캐시합니다. ECS는 Task Definition의 secrets 항목으로 환경 변수에 주입할 수 있습니다. 교체가 필요한 DB 자격 증명은 Secrets Manager, 나머지 설정은 Parameter Store가 일반적인 분담입니다.

봉투 암호화: 큰 데이터는 데이터 키로 잠근다

  1. 데이터 키 요청

    KMS가 평문 키와 KMS 키로 암호화한 키를 함께 줍니다.

  2. 데이터 암호화

    평문 데이터 키로 실제 데이터를 암호화합니다.

  3. 평문 키 폐기

    암호화된 키만 데이터 옆에 저장합니다.

  4. 복호화

    암호화된 키를 KMS에 보내 평문 키를 돌려받습니다.

KMS 키 자체는 KMS 밖으로 나오지 않습니다. 그래서 키 정책으로 누가 복호화할 수 있는지 통제하고, 모든 사용 기록이 CloudTrail에 남습니다. EBS, RDS, S3의 저장 시 암호화가 모두 이 구조입니다.

전송 시 암호화는 TLS입니다(2장, 7장). ALB에서 TLS를 종료하더라도 규정상 필요하면 ALB와 앱 사이, 앱과 RDS 사이도 TLS로 둡니다.

스케일 지표는 병목을 따라 고른다

스케일 기준잘 맞는 경우함정

기본은 목표값을 정하면 알아서 맞추는 Target Tracking입니다. 늘릴 때는 빠르게, 줄일 때는 천천히 해야 늘었다 줄었다를 반복하는 플래핑을 피합니다. JVM은 JIT 워밍업이 끝나야 제 성능이 나오므로 인스턴스 워밍업 시간을 설정합니다.

용량은 AZ 하나를 잃어도 버티게 잡는다

  1. 피크 동시 요청

    2,000 RPS × 0.1초 = 200건(리틀의 법칙).

  2. 인스턴스당 처리량

    부하 테스트로 측정: 안정적으로 50건.

  3. 필요 대수

    200 ÷ 50 = 4대. 이것은 정상일 때의 숫자입니다.

  4. AZ 장애 대비

    2 AZ면 각 AZ 4대, 총 8대. 3 AZ면 각 2대, 총 6대.

AZ 하나가 사라지는 순간 남은 AZ가 피크 전체를 받아야 합니다. AZ가 셋이면 하나를 잃어도 남는 비율이 2/3라 여유 용량이 줄어 더 쌉니다.

새 인스턴스가 준비되기까지 수 분이 걸리므로 갑작스런 폭증은 Auto Scaling이 따라가지 못합니다. 예측 가능한 피크는 예약(Scheduled) 스케일링으로 미리 늘립니다.

DR의 두 숫자: 잃어도 되는 데이터와 시간

RPO(Recovery Point Objective)는 장애 시점에서 거꾸로 얼마만큼의 데이터를 잃어도 되는가, RTO(Recovery Time Objective)는 얼마 만에 복구해야 하는가입니다.

Multi-AZ는 DR이 아닙니다. 리전 장애에는 무력하고, 실수로 실행한 DELETE나 랜섬웨어 암호화는 대기 인스턴스에도 그대로 복제됩니다. 그래서 별도의 백업과 다른 리전 복사본이 필요합니다.

서비스마다 RPO·RTO 요구가 다르므로 전부 멀티 사이트로 만들 필요는 없습니다. 결제는 웜 스탠바이, 사내 도구는 백업·복원처럼 나눕니다. 그리고 복구 훈련을 해 보지 않은 DR은 없는 것과 같습니다.

AWS의 Well-Architected Framework는 좋은 아키텍처를 여섯 관점으로 점검하는 틀입니다. 기둥은 서로 당깁니다. 멀티 사이트는 안정성을 높이지만 비용을 키웁니다. 그 균형을 고르는 근거가 1장부터 쌓아 온 원리입니다.

정리

  • 컴퓨팅은 실행 시간, 상태, 트래픽 모양으로 고릅니다. 짧고 간헐적이면 Lambda, 상시 API는 컨테이너, OS 제어가 필요하면 EC2입니다.
  • SQS는 지우지 않고 숨겨서 유실을 막습니다. 그 대가로 중복이 생기므로 멱등 컨슈머와 DLQ가 짝으로 따라옵니다.
  • 고가용성은 계층마다 SPOF를 없애는 일입니다. 여러 AZ에 걸친 ALB, Auto Scaling, RDS Multi-AZ가 각자 다른 장애를 흡수합니다.
  • 알람은 증상에, 조사는 원인 지표로 합니다. 지표에서 트레이스, 로그, 덤프, 슬로 쿼리로 좁혀 들어갑니다.
  • Multi-AZ는 DR이 아닙니다. RPO·RTO에 맞춰 백업부터 멀티 사이트까지 전략을 고르고, 복구를 연습합니다.

스스로 점검

  1. VPC에 연결한 Lambda를 Public Subnet에 두면 외부 API를 부를 수 있을까요?

    아닙니다. Lambda의 ENI에는 공인 IP가 붙지 않으므로, Private Subnet에 두고 NAT Gateway로 가는 라우트를 만들어야 합니다.

  2. 처리에 평균 40초 걸리는 작업에서 SQS 가시성 제한 시간을 기본 30초로 두면?

    처리 중인 메시지가 다시 보여 다른 컨슈머가 같은 작업을 또 시작합니다. 제한 시간을 처리 시간보다 넉넉히 늘리거나 처리 중에 연장해야 합니다.

  3. Lambda 트래픽이 갑자기 10배가 되면 RDS에는 어떤 일이 생길 수 있나요?

    동시 실행 환경 수만큼 커넥션이 열려 DB 최대 연결 수를 넘길 수 있습니다. RDS Proxy로 커넥션을 모으거나 예약 동시성으로 상한을 둡니다.

  4. 모든 계층을 Multi-AZ로 구성해도 막지 못하는 장애는 무엇인가요?

    리전 전체 장애, 잘못된 배포, 실수로 지운 데이터, DB 과부하입니다. 그래서 DR, 배포 전략, 백업과 관측성이 따로 필요합니다.

스스로 점검 (계속)

  1. CPU는 20%인데 응답이 느립니다. 다음으로 무엇을 보나요?

    스레드가 무언가를 기다리고 있을 가능성이 큽니다. 스레드 덤프로 커넥션 풀, 락, 외부 호출 대기를 확인합니다.

  2. ECS 태스크가 종료 코드 137로 죽는데 Java 로그에는 OutOfMemoryError가 없습니다. 왜일까요?

    힙이 아니라 프로세스 전체 메모리가 컨테이너 한도를 넘어 커널이 SIGKILL한 것입니다. 힙 비율을 낮춰 힙 밖 메모리 여유를 남깁니다.

  3. 2개 AZ에 피크 기준 4대가 필요한 서비스라면 최소 몇 대를 둬야 할까요?

    AZ 하나를 잃어도 버티려면 각 AZ에 4대씩 8대입니다. 3개 AZ로 나누면 각 2대씩 6대로 줄어듭니다.

  4. RDS Multi-AZ가 있는데도 백업이 필요한 이유는?

    Multi-AZ는 잘못된 DELETE까지 그대로 복제합니다. 논리적 오류와 리전 장애에서 되돌아갈 시점은 백업과 PITR만 줍니다.

맨 아래층에서 클라우드 운영까지

CPU와 메모리에서 출발해 네트워크, 데이터베이스, JVM, 프레임워크, 분산 시스템, 컨테이너를 거쳐 클라우드 운영까지 올라왔습니다. 장애가 났을 때 어느 층을 의심해야 하는지 아는 것, 그것이 이 시리즈가 쌓은 힘입니다.
