8장에서 그린 무상태 서버, 캐시, 큐는 모두 Linux 서버 위의 프로세스입니다. 서버 한 대를 다루는 기본기를 먼저 쌓고, 커널의 집계 방식, 컨테이너의 원리, Docker 실전 순서로 올라갑니다.

커널은 자원을, 셸은 사람의 말을 맡는다

커널은 CPU, 메모리, 디스크, 네트워크를 관리하는 OS의 핵심이고, 프로그램은 시스템 콜로만 커널에 부탁할 수 있습니다(1장).

셸은 사람이 입력한 명령을 해석해 프로그램을 실행해 주는 평범한 프로그램입니다. 서버에서는 보통 bash를 씁니다.

Linux라는 이름은 엄밀히 커널만 가리킵니다. 커널에 셸, 기본 도구, 패키지 관리자를 묶어 배포하는 것이 배포판입니다.

디렉터리마다 맡은 역할이 정해져 있다

파일 위치는 FHS(Filesystem Hierarchy Standard)라는 관례를 따릅니다. 처음 들어간 서버에서도 어디를 볼지 알 수 있는 이유입니다.

경로담는 것운영에서 보는 이유
/etc시스템과 서비스 설정nginx, systemd, sysctl 설정
/var로그, 캐시 등 자주 바뀌는 것/var/log가 차면 쓰기 실패
/proc, /sys커널이 만든 가상 파일프로세스와 커널 상태 조회
/usr, /opt설치 프로그램, 직접 배포한 앱앱은 보통 /opt/앱이름
/home, /root사용자, root의 홈SSH 키(~/.ssh) 위치
/tmp임시 파일재부팅 때 지워질 수 있음

경로는 루트에서 쓰거나 지금 위치에서 쓴다

$ pwd
/opt/api
$ cat /etc/hostname     # 절대 경로
$ cat ./conf/app.yml    # 상대 경로
$ cd ../logs            # 한 단계 위
$ cd ~                  # 내 홈
$ cd -                  # 직전 위치

절대 경로는 /로 시작해 어디서 실행해도 같은 파일을 가리킵니다. 상대 경로는 현재 디렉터리를 기준으로 해석되며 .은 여기, ..은 한 단계 위입니다.

cron이나 systemd가 실행하는 스크립트는 현재 디렉터리가 예상과 다를 수 있습니다. 그래서 자동 실행되는 설정에는 절대 경로를 씁니다.

하드 링크는 inode를, 심볼릭 링크는 경로를

파일 이름은 inode 번호를 가리키는 디렉터리 항목일 뿐입니다(1장). 하드 링크는 같은 inode에 이름을 하나 더 붙인 것이라, 원본 이름을 지워도 데이터가 남습니다. 다른 파일 시스템이나 디렉터리에는 걸 수 없습니다.

심볼릭 링크는 경로 문자열을 담은 작은 파일입니다. 대상이 사라지면 끊어진 링크가 됩니다. 배포에서 current → releases/v42처럼 버전을 바꿔 끼울 때 씁니다.

앱은 전용 계정으로, 관리는 sudo로

$ grep app /etc/passwd

Linux는 사용자를 숫자 UID로, 묶음을 그룹으로 구분합니다. UID 0인 root는 권한 검사를 건너뜁니다.

그래서 앱은 로그인 셸이 없는 전용 계정(nologin)으로 돌리고, 사람은 일반 계정으로 들어와 필요할 때만 sudo로 권한을 빌립니다. 누가 무엇을 했는지 로그에도 남습니다.

권한은 소유자, 그룹, 나머지의 rwx다

$ ls -l /opt/api
-rw-r----- 1 app app  51M app.jar
-rw------- 1 app app  812 db.env
drwxr-x--- 2 app app 4.0K logs
-rwxr-xr-x 1 app app  1.2K start.sh

맨 앞 글자는 종류(- 파일, d 디렉터리, l 링크)이고, 뒤 아홉 글자가 소유자, 그룹, 나머지 순서의 읽기 r, 쓰기 w, 실행 x입니다.

디렉터리에서는 의미가 조금 다릅니다. r은 목록 보기, w는 안에 파일 만들기와 지우기, x는 안으로 들어가기입니다. 그래서 파일 권한이 넉넉해도 상위 디렉터리에 x가 없으면 열 수 없습니다.

권한은 숫자로 더하고, 기본값은 umask가 뺀다

$ chmod 600 db.env      # rw- --- ---
$ chmod 750 logs        # rwx r-x ---
$ chmod u+x start.sh    # 기호 방식
$ chown -R app:app /opt/api
$ umask
0022
$ touch a; mkdir b; ls -ld a b
-rw-r--r-- … a
drwxr-xr-x … b

r=4, w=2, x=1을 더하면 세 자리 8진수가 됩니다. 640은 소유자 rw-, 그룹 r--, 나머지 ---입니다. chown은 소유자와 그룹을 바꿉니다.

새 파일은 666, 디렉터리는 777에서 umask만큼 뺀 권한으로 만들어집니다. umask 022면 파일 644, 디렉터리 755입니다. 비밀 파일을 다루는 서비스는 077로 둡니다.

setuid는 실행하는 동안 소유자의 권한을 빌린다

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root … /usr/bin/passwd
$ ls -ld /tmp
drwxrwxrwt … /tmp
$ find / -perm -4000 -type f 2>/dev/null

소유자 x 자리의 s가 setuid입니다. 일반 사용자가 passwd를 실행해도 root 권한으로 돌아 /etc/shadow를 고칠 수 있습니다. 그룹 자리면 setgid입니다.

/tmp의 t는 sticky bit로, 누구나 쓰되 자기 파일만 지우게 합니다. setuid 파일은 권한 상승 통로가 되므로 함부로 만들지 않고, 4부의 컨테이너 보안 설정도 이를 막습니다.

패키지는 프로그램과 설정, 그리고 의존성 목록을 묶은 파일이고, 패키지 관리자는 저장소에서 의존성까지 함께 받아 설치하고 지웁니다. apt update는 목록만 새로 받고 upgrade가 실제로 올립니다. 운영 서버는 장기 지원(LTS) 버전을 골라 버전을 고정하고 보안 업데이트를 계획적으로 적용합니다.

모든 프로세스는 fd 0, 1, 2를 갖고 태어난다

$ java -jar app.jar > out.log        # 1번만
$ java -jar app.jar >> out.log       # 이어 쓰기
$ java -jar app.jar 2> err.log       # 2번만
$ java -jar app.jar > all.log 2>&1
$ java -jar app.jar 2>&1 > all.log    # 다름!
$ cmd < input.txt                    # 0번
$ cmd > /dev/null 2>&1               # 버림

표준 입력(0), 표준 출력(1), 표준 오류(2)는 미리 열린 fd입니다. 리다이렉션은 셸이 프로그램을 띄우기 전에 이 fd를 파일로 바꿔 끼우는 일입니다.

2>&1은 "2번을 지금 1번이 가리키는 곳으로"라는 뜻이라 왼쪽부터 순서대로 적용됩니다. 그래서 다섯째 줄은 오류가 여전히 화면으로 나갑니다.

파이프는 작은 도구를 이어 붙인다

  1. cat access.log파일을 흘려보냄
  2. grep " 500 "500 응답만 남김
  3. awk '{print $7}'URL 열만 뽑음
  4. sort | uniq -cURL별 개수
  5. sort -rn | head많은 순 상위 10

파이프 |는 앞 프로세스의 표준 출력을 뒤 프로세스의 표준 입력에 커널 버퍼로 연결합니다(1장 IPC). 각 단계가 동시에 돌기 때문에 수 GB 로그도 메모리에 다 올리지 않고 처리합니다.

"한 가지 일을 잘하는 도구를 조합한다"는 Unix 철학이 여기서 나옵니다. 장애 중에 대시보드가 없어도 로그 몇 줄로 "어떤 URL이 500을 내는가"에 바로 답할 수 있습니다.

환경 변수는 부모에서 자식으로만 흐른다

$ PROFILE=prod          # 셸 변수
$ export PROFILE        # 자식에게 전달
$ SPRING_PROFILES_ACTIVE=prod java -jar app.jar
$ echo $PATH

환경 변수는 프로세스가 시작할 때 부모에게서 복사받는 이름=값 목록입니다. export한 변수만 자식에게 넘어가고, 자식이 바꾼 값은 부모에게 돌아오지 않습니다.

PATH는 명령 이름을 찾을 디렉터리 목록으로 앞에서부터 찾습니다. cron과 systemd는 로그인 셸의 PATH를 쓰지 않아 "터미널에선 되는데"가 생깁니다.

grep으로 찾고, awk로 세고, sed로 고친다

$ grep -i -C 3 timeout app.log        # 앞뒤 3줄 문맥
$ grep -v healthcheck access.log      # 반대로 거르기
$ grep -rl "jdbc:" /etc/api/          # 파일 이름만
$ less +F app.log                     # 큰 파일 열기
$ tail -F app.log | grep --line-buffered ERROR
$ awk '{c[$9]++} END {for(k in c) print k, c[k]}' access.log
$ awk '{s+=$NF; n++} END {print s/n}' access.log  # 평균
$ sed -i.bak 's/^port=.*/port=8081/' app.conf
$ sed -n '10,20p' app.log

grep은 패턴에 맞는 줄을 찾습니다. 큰 파일은 편집기 대신 less로 열어야 GB 단위도 바로 열리고, tail -F는 logrotate로 파일이 바뀌어도 새 파일을 따라갑니다. awk는 줄을 공백으로 나눠 $1, $2로 열을 다루며 합계와 그룹별 개수를 한 줄로 냅니다. sed -i는 파일을 직접 고치므로 .bak 백업을 남기는 습관을 들입니다.

프로세스는 fork로 태어나 exec로 바뀐다

$ ps -ef | grep java
app  4211     1  … java -jar app.jar
$ ps -eo pid,ppid,stat,rss,cmd --sort=-rss \
    | head -5
$ pstree -p 1 | head
systemd(1)─┬─sshd(812)───bash(990)
           └─java(4211)─┬─{java}(4212)
$ top -H -p 4211   # 스레드별 CPU

새 프로세스는 부모가 자신을 복제(fork)한 뒤 그 자식이 다른 프로그램으로 갈아타는(exec) 방식으로 생깁니다. 그래서 모든 프로세스에는 부모(PPID)가 있고, 맨 위에는 PID 1이 있습니다.

ps의 STAT 열은 상태입니다. R은 실행 중이거나 실행 대기, S는 잠듦, D는 디스크 I/O 등을 기다리는 중단 불가 잠듦, Z는 좀비입니다.

좀비는 못 거둔 자식, 고아는 부모 잃은 자식

  1. 자식 종료

    자식이 끝나면 커널은 종료 코드를 담은 작은 기록만 남깁니다.

  2. 좀비(Z)

    부모가 wait()로 읽어 가기 전까지 이 기록이 남은 상태입니다.

  3. 회수

    부모가 wait를 부르면 기록이 지워지고 PID가 반납됩니다.

  4. 고아

    부모가 먼저 죽으면 자식은 PID 1에 입양되고, PID 1이 대신 거둡니다.

좀비는 메모리를 거의 쓰지 않지만 PID 번호를 차지합니다. 부모 코드가 wait를 빠뜨리면 좀비가 쌓여 결국 새 프로세스를 못 만듭니다. 좀비는 kill로 지울 수 없고 부모를 고치거나 끝내야 합니다.

고아를 거두는 PID 1의 역할은 컨테이너에서 다시 중요해집니다. 컨테이너 안에서는 우리 앱이 PID 1이기 때문입니다(4부).

터미널을 닫아도 살아남게 하려면

$ ./batch.sh &        # 백그라운드 실행
[1] 5120
$ jobs; fg %1         # 다시 앞으로
$ Ctrl+Z; bg          # 멈추고 뒤로 보냄
$ nohup ./batch.sh > batch.log 2>&1 &
$ disown %1           # 셸 작업 목록에서 뺌
$ tmux new -s deploy  # 세션 유지

&를 붙이면 셸이 기다리지 않고 프롬프트를 돌려줍니다. 하지만 SSH가 끊기면 셸이 자식들에게 SIGHUP을 보내 대부분 함께 죽습니다.

nohup은 SIGHUP을 무시하게 하고 출력을 파일로 돌립니다. 잠깐 도는 작업이면 충분하지만, 죽으면 아무도 다시 살리지 않으므로 서비스는 systemd에 맡깁니다.

시그널은 프로세스에 보내는 짧은 통지다

시그널번호보내는 상황프로세스가 잡을 수 있나
SIGTERM15kill 기본값, 정상 종료 요청잡아서 정리 후 종료
SIGKILL9kill -9, 유예 시간 초과불가, 커널이 즉시 제거
SIGINT2터미널에서 Ctrl+C가능
SIGHUP1터미널 끊김, 설정 재로드 관례가능

시그널은 커널이 프로세스에 전달하는 번호 하나짜리 통지로, kill -신호 PID로 보냅니다. SIGTERM을 받은 앱은 새 요청을 멈추고 처리 중인 일을 마친 뒤 스스로 끝날 수 있지만(Spring의 Graceful Shutdown, 11장), SIGKILL은 커널이 바로 제거해 정리할 기회가 없습니다. 그래서 모든 도구가 TERM을 보내고 기다린 뒤 KILL합니다. 시그널로 죽으면 종료 코드는 128+번호(143, 137)입니다.

systemd가 서버의 프로세스를 지킨다

systemd는 부팅 때 커널이 처음 띄우는 PID 1입니다. 서비스를 순서대로 띄우고, 죽으면 다시 살리고, 출력을 journald로 모으고, 각 서비스를 cgroup에 넣어 자원을 묶어 관리합니다.

관리 대상 하나하나를 유닛이라 하고, 종류는 파일 확장자로 구분합니다. 서비스는 .service, 주기 작업은 .timer, 마운트는 .mount, 묶음 목표는 .target입니다.

service 파일 하나가 실행 방법의 전부다

[Unit]
Description=Order API
After=network-online.target

[Service]
User=app
WorkingDirectory=/opt/api
EnvironmentFile=/etc/api/env
ExecStart=/usr/bin/java -jar /opt/api/app.jar
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target

[Unit]은 순서와 의존 관계, [Service]는 실행 방법, [Install]은 부팅 때 어느 목표에 붙일지입니다.

User로 전용 계정을, EnvironmentFile로 비밀 값을 코드 밖에 둡니다. TimeoutStopSec은 SIGTERM 뒤 SIGKILL까지 기다릴 시간(기본 90초)이고, LimitNOFILE이 이 서비스의 fd 한도입니다.

enable은 부팅, Restart=는 죽었을 때

$ sudo systemctl enable --now api       # 부팅 등록 + 지금 시작
$ systemctl status api; systemctl list-units --failed
$ journalctl -u api -f --since "10 min ago" -p err
Restart= 값다시 시작하는 경우어울리는 곳
no (기본)다시 시작하지 않음한 번 돌고 끝나는 작업
on-failure0이 아닌 종료 코드, 시그널, 타임아웃대부분의 앱 서버
always정상 종료여도 항상멈추면 안 되는 에이전트

enable은 부팅 목표에 링크만 걸고 start는 지금만 띄우므로 둘 다 하려면 enable --now입니다. 유닛을 고친 뒤 daemon-reload를 빠뜨리면 옛 설정으로 돕니다. 기본값으로 10초 안에 5번 시작하면 systemd가 포기하고 failed가 되니, RestartSec으로 간격을 두고 실패 알림을 겁니다.

cron은 다섯 칸으로 시각을 적는다

# 분 시 일 월 요일  명령
30 3 * * *   /opt/api/bin/cleanup.sh
*/5 * * * *  /opt/api/bin/health.sh
0 9 * * 1-5 /opt/api/bin/report.sh

# 환경과 겹침 실행 대비
PATH=/usr/local/bin:/usr/bin:/bin
*/10 * * * * flock -n /tmp/sync.lock \
  /opt/api/bin/sync.sh >> /var/log/sync.log 2>&1

cron은 정해진 시각에 명령을 실행하는 데몬입니다. 다섯 칸은 분, 시, 일, 월, 요일이고 */5는 5분마다입니다.

함정은 세 가지입니다. 최소한의 PATH로 돌고, 출력을 버리면 실패를 모르며, 이전 실행이 안 끝났는데 다음이 겹칩니다. flock으로 겹침을 막습니다. 서버가 여러 대면 모든 서버에서 돌므로 분산 스케줄링은 8장의 분산 락이나 관리형 스케줄러를 씁니다.

SSH 키 인증은 비밀키를 보내지 않는다

내 PC서버 sshd
접속 요청 키 교환 시작
known_hosts 확인 호스트 키 서명 서버가 자신을 증명
사용자 인증 비밀키로 만든 서명비밀키 자체는 PC를 떠나지 않음 authorized_keys로 검증
셸 세션 암호화된 채널

SSH는 두 방향으로 신원을 확인합니다. 먼저 서버가 호스트 키로 "내가 그 서버가 맞다"를 증명하고, 그다음 사용자가 비밀키로 서명해 "내가 이 공개키의 주인"임을 증명합니다.

비밀번호와 달리 서버에 비밀이 저장되지 않아 서버가 털려도 키가 새지 않습니다. 운영 서버는 PasswordAuthentication no로 비밀번호 로그인을 끕니다.

호스트 키 경고는 무시하지 않는다

$ ssh-keygen -t ed25519 && ssh-copy-id ubuntu@10.0.1.12
$ chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
$ ssh-keygen -R 10.0.1.12        # 서버 재생성이 확실할 때만
$ scp app.jar api1:/opt/api/
$ rsync -avz --delete --dry-run dist/ api1:/srv/web/
# ~/.ssh/config의 ProxyJump로 배스천 자동 경유

처음 접속한 서버의 호스트 키는 known_hosts에 저장되고 다음부터 비교됩니다. 키가 바뀌었다는 경고는 중간자 공격일 수도 있습니다. sshd는 ~/.ssh가 남에게 쓰기 가능하면 키 인증을 거부하니, 키를 넣었는데 비밀번호를 묻는다면 권한부터 봅니다.

scp는 매번 전체를 복사하고 rsync는 바뀐 부분만 보냅니다. --delete는 원본에 없는 파일을 지우므로 --dry-run으로 먼저 확인합니다.

포트 포워딩은 SSH 안으로 다른 연결을 통과시킨다

Private Subnet의 DB는 인터넷에서 직접 닿지 않습니다. 접속 가능한 중계 서버(배스천)에 SSH로 들어가 그 안에서 DB로 연결을 이어 주는 것이 로컬 포트 포워딩입니다.

-L은 내 포트를 원격 목적지로, -R은 원격 포트를 내 쪽으로 엽니다. -D는 SOCKS 프록시를 만듭니다. AWS에서는 SSM Session Manager로 배스천 자체를 없애는 방법도 씁니다(14장).

2부

숫자 뒤에 있는 커널의 사정

명령어가 내놓는 숫자는 커널이 집계한 값입니다. 그 숫자가 무엇을 세는지 알아야 "느리다", "꽉 찼다"를 정확히 읽습니다.

기초 원리 여기부터는 네트워크, 메모리, 디스크, 커널 파라미터가 내부에서 어떻게 집계되는지 봅니다.

/proc은 커널이 열어 둔 상태 창이다

$ cat /proc/loadavg
3.12 2.80 2.41 4/812 5120
$ grep -E 'MemTotal|MemAvail' /proc/meminfo
$ cat /proc/4211/status | grep -E 'State|VmRSS'
$ ls -l /proc/4211/fd | wc -l
$ cat /proc/4211/limits
$ cat /proc/sys/net/core/somaxconn
$ cat /sys/fs/cgroup/…/memory.current

/proc은 디스크에 없는 가상 파일 시스템입니다. 파일을 읽는 순간 커널이 내부 상태를 글자로 만들어 돌려줍니다. top, free, ps도 결국 여기를 읽습니다.

/proc/PID/에는 프로세스별 정보가, /proc/sys/에는 바꿀 수 있는 커널 파라미터가, /sys/fs/cgroup에는 cgroup별 사용량이 있습니다.

ip로 주소와 경로를, ss로 소켓을 본다

$ ip -br addr
eth0   UP   10.0.2.15/24
$ ip route
default via 10.0.2.1 dev eth0
$ ip route get 10.0.9.20   # 어느 길로?
$ ss -ltnp
LISTEN 0 4096  127.0.0.1:8080  … java
$ ss -tn state established '( dport = :3306 )'
$ ss -s

ip는 예전 ifconfig, route를 대신합니다. 주소, 기본 게이트웨이, 특정 목적지로 가는 경로를 확인합니다(서브넷과 게이트웨이는 2장).

ss -ltnp는 듣고 있는 TCP 포트와 프로세스를 보여 줍니다. 위 예처럼 127.0.0.1에만 묶여 있으면 외부에서 닿지 않습니다. "포트는 열렸는데 접속이 안 된다"의 흔한 원인입니다.

연결 문제는 계층 순서로 잘라 본다

  1. dig이름이 맞는 IP로 풀리나
  2. nc -zv포트까지 TCP가 닿나
  3. curl -vTLS와 HTTP 응답은
  4. curl -w어느 단계가 느린가
$ dig +short api.internal.example.com
$ nc -zv 10.0.3.21 5432     # succeeded / timed out / refused
$ curl -sv https://api.example.com/health -o /dev/null
$ curl -so /dev/null \
    -w '%{time_connect} %{time_appconnect} %{time_total}\n' URL

계층별로 잘라야 원인이 보입니다. refused는 호스트에 닿았지만 듣는 프로세스가 없다는 뜻이고, timed out은 중간에서 패킷이 버려진다는 뜻이라 방화벽이나 보안 그룹을 의심합니다.

경로는 traceroute, 패킷은 tcpdump

$ traceroute -n 8.8.8.8
$ mtr -rwc 50 api.example.com
$ sudo tcpdump -i any -nn port 8080
$ sudo tcpdump -i eth0 -nn \
    'tcp[tcpflags] & tcp-syn != 0'
$ sudo tcpdump -i eth0 -w cap.pcap \
    host 10.0.3.21   # Wireshark로 분석

traceroute는 TTL을 1씩 늘려 보내며 중간 라우터의 응답으로 경로를 그립니다. 응답하지 않는 구간 * * *은 ICMP를 막았을 뿐 끊긴 것이 아닐 수 있습니다.

tcpdump는 NIC를 지나는 패킷을 그대로 봅니다. SYN만 오고 SYN+ACK가 안 나간다면 앱이 아니라 커널이나 방화벽 단계에서 막힌 것입니다. 추측을 사실로 바꾸는 마지막 도구입니다.

방화벽은 커널 안의 체인에서 패킷을 거른다

Linux 방화벽은 커널의 netfilter에 걸린 규칙입니다. 패킷은 도착하면 PREROUTING을 지나, 내 프로세스로 가면 INPUT, 다른 곳으로 넘기면 FORWARD를 거칩니다. 내가 보내는 패킷은 OUTPUT과 POSTROUTING을 지납니다.

규칙은 표(table)로 나뉩니다. filter는 허용과 차단, nat은 주소 변환입니다. Docker의 포트 매핑도 바로 이 nat 표에 규칙을 넣는 방식입니다(4부).

iptables는 앞 규칙부터 맞춰 보고 멈춘다

$ sudo iptables -L INPUT -n -v --line-numbers
$ sudo iptables -A INPUT -m conntrack \
    --ctstate ESTABLISHED,RELATED -j ACCEPT
$ sudo iptables -A INPUT -p tcp --dport 22 \
    -s 10.0.0.0/16 -j ACCEPT
$ sudo iptables -P INPUT DROP
$ sudo nft list ruleset    # nftables
$ sudo ufw allow 443/tcp   # 쉬운 앞단

규칙은 위에서부터 비교해 처음 맞은 규칙의 동작(ACCEPT, DROP, REJECT)을 따르고, 아무것도 맞지 않으면 체인의 기본 정책을 씁니다. conntrack은 연결 상태를 기억해 응답 패킷을 자동으로 허용합니다.

nftables는 iptables의 후속으로 최신 배포판의 기본 백엔드입니다. 클라우드에서는 보안 그룹이 앞에서 먼저 거릅니다(13장). 원격에서 DROP 정책을 걸 때는 SSH 허용 규칙을 먼저 넣습니다.

로드 애버리지는 CPU 사용률이 아니라 줄의 길이다

$ uptime; nproc
load average: 7.92, 6.10, 3.05
4
$ top -bn1 | head -3
%Cpu(s): 31.0 us, 4.2 sy, 0.0 id, 63.5 wa
$ ps -eo stat,pid,cmd | awk '$1 ~ /^D/'

로드 애버리지는 실행 중이거나 실행을 기다리는(R) 작업 수의 1, 5, 15분 지수 이동 평균입니다. Linux는 여기에 D 상태(I/O를 기다리며 깨울 수 없는 잠)도 더합니다.

그래서 코어 4개에 7.92는 "CPU가 바쁘다"가 아닐 수 있습니다. 위 예처럼 wa(I/O 대기)가 높다면 디스크나 NFS를 기다리는 줄입니다. 숫자를 코어 수와 비교하고, 세 값의 추세로 악화 중인지 봅니다.

메모리는 free가 아니라 available을 본다

$ free -h
       total   used   free  buff/cache  available
Mem:    15Gi    9Gi  320Mi       5.9Gi      5.6Gi
$ vmstat 1 3          # si/so가 계속 0이 아니면 스왑 중
 r b  swpd  free  si  so   bi  bo  wa
 6 3  812k  102k 420 980 1500 220  41
$ sysctl vm.swappiness   # 기본 60

Linux는 남는 메모리를 디스크 파일을 담아 두는 페이지 캐시로 써서 free 열은 늘 작습니다. 캐시는 앱이 요구하면 즉시 비워 줄 수 있으므로, 이를 감안한 available이 실제로 쓸 수 있는 양입니다.

swap은 덜 쓰는 페이지를 디스크로 내보내 죽음을 늦추지만, 수천 배 느려 스래싱(1장)을 부릅니다. vm.swappiness는 그 적극성이고, 지연이 중요한 서버와 Kubernetes 노드는 전통적으로 swap을 끕니다.

메모리가 바닥나면 OOM Killer가 고른다

$ dmesg -T | grep -i -A2 'killed process'
Out of memory: Killed process 4211 (java)
  total-vm:9.1G, anon-rss:7.4G …
$ cat /proc/4211/oom_score
812
$ echo -500 | sudo tee /proc/4211/oom_score_adj
# systemd: OOMScoreAdjust=-500

페이지 캐시를 비우고 swap까지 써도 메모리를 못 구하면, 커널의 OOM Killer가 프로세스 하나를 SIGKILL로 죽여 메모리를 확보합니다. 대상은 oom_score가 가장 높은 프로세스이고, 주로 메모리를 가장 많이 쓰는 것입니다.

oom_score_adj(-1000~1000)로 우선순위를 조정합니다. 앱 로그에는 흔적이 없고 커널 로그(dmesg)에만 남는다는 점이 함정입니다.

디스크는 용량과 inode 둘 다 바닥난다

$ df -h /
/dev/nvme0n1p1  50G  31G  19G  62% /
$ df -i /
/dev/nvme0n1p1  3.2M 3.2M  0  100% /
$ du -xh /var --max-depth=1 | sort -h | tail
$ find /var/spool -xdev -type f | wc -l
$ ncdu -x /     # 대화형 탐색

df는 파일 시스템 단위 사용량, du는 디렉터리 단위 사용량입니다. du를 큰 순으로 정렬해 내려가면 범인을 찾습니다.

파일 하나에 inode 하나가 필요하고, ext4는 포맷할 때 inode 개수가 정해집니다. 작은 세션 파일이나 메일 큐가 수백만 개 쌓이면 용량이 남아도 "No space left on device"가 납니다. df -i로 구분합니다.

로그를 지웠는데 디스크가 그대로인 이유

$ rm /var/log/api/app.log
$ df -h /     # 그대로 100%
$ sudo lsof +L1
COMMAND PID  FD  SIZE/OFF NLINK NAME
java   4211  7w 21474836480 0 app.log (deleted)
# 재시작 없이 비우기
$ : > /proc/4211/fd/7

rm은 디렉터리에서 이름만 지웁니다. 프로세스가 그 파일을 fd로 열고 있으면 inode와 데이터는 마지막 fd가 닫힐 때까지 남습니다. 20GB 로그를 지웠는데 공간이 돌아오지 않는 이유입니다.

lsof +L1로 링크 수 0인 열린 파일을 찾아 앱을 재시작하거나 fd를 비웁니다. 애초에 지우지 말고 : > app.log로 비우고, logrotate의 copytruncate나 앱의 로그 롤링을 씁니다.

I/O 대기는 vmstat와 iostat로 본다

$ vmstat 1
 r  b   si so   bi    bo   us sy id wa st
 1 7    0  0  120 88000  5  3 30 62  0
$ iostat -xz 1
Device  r/s  w/s r_await w_await aqu-sz %util
nvme1n1 12 3400   0.9    48.2    160   100
$ pidstat -d 1   # 프로세스별 I/O

vmstat의 b는 I/O를 기다리며 막힌 프로세스 수, wa는 CPU가 I/O를 기다리며 논 시간 비율입니다. st는 하이퍼바이저가 다른 VM에 CPU를 빼앗긴 시간입니다.

iostat에서는 await(요청당 대기 ms)와 aqu-sz(큐 길이)를 봅니다. SSD는 병렬 처리라 %util 100%가 곧 한계는 아닙니다. 지연이 함께 뛰는지가 기준입니다.

층설정적용 범위확인

프로세스 상한의 상한fs.nr_openhard 한도로 줄 수 있는 최대sysctl fs.nr_open

프로세스 한도를 정하는 곳은 띄운 주체마다 다릅니다. 로그인 셸은 ulimit -n과 /etc/security/limits.conf를, systemd 서비스는 유닛의 LimitNOFILE을, Docker 컨테이너는 --ulimit nofile=65535:65535를 따릅니다. limits.conf를 고쳐도 systemd 서비스에는 적용되지 않는 것이 흔한 실수입니다. 한도를 올리기 전에 누수인지부터 가르는 방법은 1장에서 다뤘습니다.

sysctl로 커널의 기본값을 서버에 맞춘다

파라미터의미기본값언제 손대나
net.core.somaxconnaccept 큐 길이 상한4096 (5.4+)순간 연결 폭주, 큐 넘침
net.ipv4.ip_local_port_range나가는 연결의 포트 범위32768–60999외부 호출 많은 서버
net.ipv4.tcp_tw_reuseTIME_WAIT 포트 재사용2 (루프백만)풀 도입이 먼저
fs.file-max시스템 전체 fd 상한메모리 비례대량 연결 서버
vm.swappinessswap 적극성60지연 민감 서버

accept 큐는 listen()의 backlog와 somaxconn 중 작은 값이라, 커널만 올리고 앱 설정(Tomcat accept-count 등)을 그대로 두면 효과가 없습니다. 포트와 TIME_WAIT 원리는 2장에서 다뤘습니다.

sysctl 변경은 파일에 남겨야 재부팅을 견딘다

$ sysctl net.core.somaxconn
$ sudo sysctl -w net.core.somaxconn=8192
# 영구 적용
$ cat /etc/sysctl.d/90-api.conf
net.core.somaxconn = 8192
net.ipv4.ip_local_port_range = 10240 65000
$ sudo sysctl --system
# 컨테이너별 (net namespace 단위)
$ docker run --sysctl net.core.somaxconn=8192 …

sysctl -w는 지금 커널 메모리의 값만 바꿔 재부팅하면 사라집니다. /etc/sysctl.d/에 파일로 두고 --system으로 다시 읽어야 영구 적용되고 코드처럼 관리됩니다.

net.* 파라미터 상당수는 네트워크 namespace마다 따로 있어서, 컨테이너 안에서는 호스트 값이 아니라 자기 값이 적용됩니다. 다음 부의 namespace가 바로 그 이유입니다.

3부

컨테이너는 커널 기능의 조합이다

커널 안에 "컨테이너"라는 객체는 없습니다. 2부에서 본 프로세스, 파일 시스템, 네트워크를 namespace로 나눠 보이고, cgroup으로 양을 제한하고, 레이어 파일 시스템을 씌운 평범한 프로세스입니다.

VM은 하드웨어를, 컨테이너는 OS를 나눈다

"내 PC에선 되는데 서버에선 안 된다"는 문제는 실행 환경 차이에서 옵니다. 두 기술 모두 환경을 통째로 묶어 옮기지만, 어디를 나누는지가 다릅니다.

VM은 하이퍼바이저가 가상 하드웨어를 만들고 그 위에 게스트 OS를 통째로 올립니다. 컨테이너는 호스트 커널을 공유하고 프로세스만 격리합니다.

커널을 공유하면 가볍지만 경계는 얇아진다

항목VM컨테이너
격리 단위가상 하드웨어 + 게스트 OS프로세스 (namespace, cgroup)
시작 시간OS 부팅, 수십 초 이상프로세스 시작, 보통 1초 안팎
이미지 크기GB 단위수십~수백 MB
다른 OS 실행가능 (Linux 위 Windows)호스트 커널과 같은 계열만
보안 경계하이퍼바이저, 두꺼움커널 취약점이 곧 탈출 경로

그래서 실무에서는 둘을 겹쳐 씁니다. 클라우드 VM(EC2) 위에 컨테이너 여러 개를 올리는 구성이 가장 흔하고, macOS에서 Docker를 쓸 때도 내부에서 작은 Linux VM이 돕니다. Fargate나 Lambda처럼 남과 섞이는 환경은 Firecracker 같은 경량 VM으로 컨테이너를 한 겹 더 감쌉니다.

namespace는 프로세스가 보는 세상을 나눈다

namespace나누는 것컨테이너 안에서 보이는 모습
pid프로세스 번호내 앱이 PID 1, 남의 프로세스 안 보임
netNIC, IP, 라우팅, 포트, iptables자기만의 eth0, 8080을 따로 씀
mnt마운트 목록이미지가 루트(/)로 보임
uts / ipc호스트 이름 / 공유 메모리호스트 이름이 컨테이너 ID
userUID 매핑안의 root가 밖에선 일반 UID
cgroup / timecgroup 경로 / 시계 오프셋자기 cgroup이 루트로 보임

프로세스는 namespace 종류마다 하나씩에 속합니다. ls -l /proc/PID/ns로 어느 namespace에 속했는지 확인합니다.

같은 프로세스가 안과 밖에서 다른 번호를 갖는다

pid namespace 안에서 처음 뜬 프로세스는 PID 1을 받지만, 호스트에서 보면 평범한 PID 4211입니다. 두 컨테이너는 서로를 보지 못해도 호스트의 ps에는 모두 보입니다.

Docker 없이도 sudo unshare --pid --fork --mount-proc bash로 새 pid namespace에서 셸을 띄우면 ps에 프로세스가 둘만 보입니다. 컨테이너의 정체는 커널 기능을 조합한 프로세스라는 것을 직접 확인하는 방법입니다.

cgroup은 프로세스 묶음이 쓰는 양을 제한한다

$ stat -fc %T /sys/fs/cgroup
cgroup2fs          # v2
$ cd /sys/fs/cgroup/system.slice/\
docker-<id>.scope
$ cat cpu.max
50000 100000
$ cat memory.max memory.current
536870912
402653184
$ cat memory.events | grep oom_kill

cgroup은 프로세스를 묶어 CPU, 메모리, I/O, PID 수를 세고 제한하는 커널 기능입니다. 설정은 /sys/fs/cgroup 아래 파일을 쓰는 것으로 끝납니다.

v1은 자원마다 계층이 따로라 관리가 복잡했고, v2는 하나의 계층으로 통합했습니다. 최신 배포판(Ubuntu 22.04, Amazon Linux 2023 등)은 v2가 기본이며, 오래된 JVM은 v2를 못 읽는 문제가 있었습니다.

CPU 상한은 죽이지 않고 멈춰 세운다

cpu.max = 50000 100000은 100ms 주기마다 CPU 시간 50ms, 즉 0.5코어를 쓸 수 있다는 뜻입니다. 다 쓰면 남은 주기 동안 스로틀링되어 아예 실행되지 않습니다.

함정은 스레드가 여럿일 때입니다. 스레드 4개가 동시에 돌면 50ms를 12.5ms 만에 소진하고 87.5ms를 멈춥니다. 평균 CPU 사용률은 낮은데 p99 지연이 100ms씩 튀는 이유입니다. cpu.stat의 nr_throttled로 확인합니다.

메모리 상한을 넘으면 그 cgroup 안에서 죽인다

메모리는 빌려 쓰고 나중에 갚을 수 없는 자원이라 CPU처럼 멈춰 세울 수 없습니다. cgroup이 memory.max에 닿으면 커널은 먼저 그 cgroup의 페이지 캐시를 회수하고, 그래도 모자라면 cgroup 안의 프로세스를 OOM Killer로 죽입니다.

호스트에는 메모리가 남아 있어도 일어납니다. 종료 코드는 137, docker inspect에 OOMKilled: true, Kubernetes에서는 OOMKilled로 보입니다(10장).

상한에는 힙 밖 메모리도 들어간다

JVM이면 힙에 메타스페이스, 스레드 스택, 다이렉트 버퍼, GC 자료구조가 더해집니다. 힙을 상한 가까이 잡으면 GC 로그는 멀쩡한데 컨테이너가 죽습니다.

페이지 캐시도 사용량에 잡힌다

파일을 많이 읽는 컨테이너는 사용량이 상한 근처에 붙어 보입니다. 회수 가능한 캐시이므로 working set(사용량 − 비활성 캐시)을 기준으로 봅니다.

이미지는 읽기 전용 레이어의 겹침이다

이미지는 파일 변경분을 담은 레이어를 차례로 쌓은 것입니다. OverlayFS는 아래 레이어들(lowerdir)과 맨 위 쓰기 레이어(upperdir)를 겹쳐 하나의 디렉터리(merged)로 보여 줍니다. Docker의 기본 저장 드라이버 overlay2가 이것입니다.

같은 경로의 파일이 여러 층에 있으면 위층이 이깁니다. 파일 삭제는 위층에 "지워졌음" 표시(whiteout)를 남기는 방식이라 아래 레이어의 용량은 줄지 않습니다.

쓰기 레이어는 복사 후 쓰기라서 무겁고 사라진다

  1. 읽기

    위층부터 찾아 내려가 처음 발견한 파일을 그대로 읽습니다.

  2. 첫 수정

    아래층 파일을 통째로 쓰기 레이어에 복사한 뒤 고칩니다(copy-up).

  3. 이후 수정

    쓰기 레이어의 사본만 고칩니다.

  4. 컨테이너 삭제

    쓰기 레이어가 함께 지워지고 변경 내용도 사라집니다.

이 방식을 CoW라 합니다. 덕분에 컨테이너 100개가 이미지 하나를 공유하고 1초 만에 뜹니다.

대가도 있습니다. 1GB 파일의 한 바이트만 고쳐도 1GB가 복사되고, 쓰기 레이어는 느리며 컨테이너와 운명을 같이합니다. 그래서 DB 데이터나 업로드 파일처럼 남아야 하거나 많이 쓰는 것은 볼륨에 둡니다(4부).

OCI 표준 덕분에 어떤 도구로 만들어도 돌아간다

OCI 명세정하는 것덕분에 가능한 일
Image Spec매니페스트, 레이어 tar, 설정 JSON 형식Docker로 빌드, containerd로 실행
Runtime Spec풀어 놓은 파일 묶음을 실행하는 방법runc, crun, gVisor 교체
Distribution Spec레지스트리 HTTP APIDocker Hub, ECR, GHCR 호환

OCI는 Docker가 만든 형식을 업계 공통 표준으로 정리한 것입니다. 그래서 "Docker 이미지"라는 말은 사실 OCI 이미지를 뜻하고, Jib처럼 Docker 없이 만든 이미지도 Kubernetes에서 그대로 돕니다. 이미지의 각 레이어와 매니페스트는 sha256 해시로 주소가 정해지는 내용 주소 방식입니다.

docker run은 네 단계를 거쳐 runc로

  1. docker CLIREST API로 요청
  2. dockerd빌드, 네트워크, 볼륨
  3. containerd이미지와 생명주기
  4. shim컨테이너마다 하나
  5. runcnamespace, cgroup 생성

CLI는 /var/run/docker.sock으로 데몬 dockerd에 부탁만 합니다. dockerd는 이미지 관리와 실행을 containerd에 맡기고, containerd는 컨테이너마다 containerd-shim을 띄워 runc를 부릅니다.

runc는 namespace와 cgroup을 만들고 앱을 실행한 뒤 바로 빠집니다. 그 뒤로는 shim이 부모로 남아 있어서 dockerd를 재시작해도 컨테이너가 죽지 않습니다(live-restore 설정 시).

K8s 노드는 containerd로 돌린다

도구위치특징
Docker Engine개발자 PC, 단일 서버빌드, Compose, 네트워크까지 다 갖춤
containerdEKS 등 대부분의 K8s 노드실행에 필요한 것만, CRI 지원
CRI-OOpenShift 등Kubernetes 전용으로 만든 런타임
Podman개발자 PC, RHEL 서버데몬 없음, rootless 기본, docker 명령 호환

Kubernetes의 kubelet은 CRI라는 규격으로 런타임과 말합니다. Docker는 CRI를 직접 지원하지 않아 중간 어댑터(dockershim)가 필요했고, 1.24에서 제거되었습니다. 이미지는 OCI 표준이라 Docker로 빌드한 이미지는 그대로 돕니다. 노드에서 디버깅할 때 docker 대신 crictl을 쓰는 이유입니다(10장).

4부

좋은 이미지를 만들고 안전하게 띄우기

원리를 알았으니 손에 쥘 차례입니다. Dockerfile 한 줄 한 줄이 레이어와 PID 1, 보안에 어떤 결과를 남기는지 따져 가며 씁니다.

원리 실무 Dockerfile, 이미지 선택, 네트워크와 저장소, 보안, 디버깅과 장애 사례를 다룹니다.

태그는 바뀔 수 있고, digest는 바뀌지 않는다

# 저장소/이름:태그
docker.io/library/eclipse-temurin:21-jre
123456789012.dkr.ecr.ap-northeast-2…
  …/order-api:3f9c2e1
$ docker images --digests
# 내용 해시로 고정
eclipse-temurin@sha256:5f1c…a9
$ docker buildx imagetools inspect \
    eclipse-temurin:21-jre

태그는 이미지를 가리키는 이름표라 누군가 같은 태그로 다시 push하면 가리키는 대상이 바뀝니다. latest는 "가장 최신"이 아니라 태그를 안 붙였을 때의 기본 이름일 뿐입니다.

digest는 매니페스트 내용의 sha256 해시라 절대 바뀌지 않습니다. 운영 배포는 커밋 SHA 태그나 digest로 고정해야 어떤 코드가 도는지 추적되고, 롤백도 정확합니다(11장).

Docker Hub pull에는 한도가 있다

사용자pull 한도 (6시간당)실무 영향
로그인 안 함IP(IPv4)당 100회NAT 뒤 노드 전체가 한 IP로 셈
무료 계정 (Personal)200회CI는 로그인해서 pull
유료 (Pro, Team, Business)무제한 (공정 사용 조건)조직 단위 운영

사설 서브넷의 노드들은 NAT Gateway 하나의 공인 IP로 나가므로, 로그인 없이 pull하면 클러스터 전체가 한도를 나눠 씁니다. 대규모 배포나 노드 교체 중에 toomanyrequests로 이미지가 안 받아지는 사고가 여기서 납니다. 운영에서는 자주 쓰는 베이스 이미지를 사설 레지스트리로 미러링하거나 pull-through cache를 씁니다. AWS의 ECR과 그 캐시 기능은 14장에서 다룹니다.

Dockerfile 한 장을 위에서부터 읽는다

FROM eclipse-temurin:21-jre
ARG APP_VERSION=dev
ENV TZ=Asia/Seoul \
    JAVA_OPTS="-XX:MaxRAMPercentage=75"
WORKDIR /app
RUN useradd -r -u 10001 app
COPY --chown=app build/libs/app.jar app.jar
USER app
EXPOSE 8080
HEALTHCHECK CMD curl -fs localhost:8080/health \
  || exit 1
LABEL version=$APP_VERSION
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS \
  -jar app.jar"]

docker build가 이 파일로 읽기 전용 이미지를 만들고, docker run이 쓰기 레이어를 얹어 컨테이너로 띄웁니다. 클래스와 인스턴스 관계입니다. 파일 시스템을 바꾸는 RUN, COPY, ADD만 레이어를 만들고 나머지는 설정만 바꿉니다.

이 짧은 파일에 베이스 선택, 비 root 실행, 헬스 체크, PID 1까지 결정이 담겨 있습니다. 명령 하나씩 왜 이렇게 쓰는지 봅니다.

설치와 청소는 한 RUN에서, 복사는 COPY로

# 나쁜 예: 레이어 3개, 지운 캐시가 앞 레이어에 그대로
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
# 좋은 예: 한 레이어에서 설치와 청소
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*
COPY --chown=app:app build/libs/app.jar /app/app.jar
ADD vendor.tar.gz /opt/vendor/                # 자동 압축 해제
ADD --checksum=sha256:<hash> https://example.com/agent.jar /opt/

FROM은 출발점이 될 베이스 이미지를, RUN은 빌드 중 명령을 실행해 결과를 레이어로 남깁니다. 레이어는 겹치기만 하므로 다음 RUN에서 지워도 앞 레이어 용량은 그대로라서, 설치와 정리는 한 RUN에서 합니다. ADD는 COPY에 tar 자동 해제와 URL 다운로드가 더해진 것이라, 기본은 COPY를 쓰고 URL은 --checksum으로 고정합니다.

ENTRYPOINT는 실행 파일, CMD는 인자

Dockerfiledocker run imgdocker run img --debug
CMD만 ["java","-jar","app.jar"]java -jar app.jar--debug (CMD 통째 교체)
ENTRYPOINT만 ["java","-jar","app.jar"]java -jar app.jarjava -jar app.jar --debug
ENTRYPOINT ["java","-jar","app.jar"] + CMD ["--port=8080"]… app.jar --port=8080… app.jar --debug

최종 실행 명령은 ENTRYPOINT + CMD입니다. docker run 뒤에 붙인 인자는 CMD를 대체하고, ENTRYPOINT는 --entrypoint로만 바꿉니다. 그래서 "무엇을 실행하나"는 ENTRYPOINT에, "기본 옵션"은 CMD에 두면 사용자가 옵션만 바꿔 실행할 수 있습니다. Kubernetes에서는 command가 ENTRYPOINT를, args가 CMD를 덮어씁니다.

shell form은 셸을 PID 1로 만든다

# shell form: /bin/sh -c "java …" 로 실행
ENTRYPOINT java -jar app.jar
# PID 1 = sh, java는 자식

# exec form: JSON 배열, 셸 없음
ENTRYPOINT ["java", "-jar", "app.jar"]
# PID 1 = java

# 변수 확장이 필요하면 exec로 넘김
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS \
  -jar app.jar"]

명령을 문자열로 쓰는 shell form은 /bin/sh -c로 감싸 실행되어 셸이 PID 1이 됩니다. sh는 받은 SIGTERM을 자식에게 넘겨주지 않을 수 있습니다.

JSON 배열로 쓰는 exec form은 앱이 곧바로 PID 1입니다. 환경 변수 확장이 필요해 셸을 거친다면 마지막에 exec로 셸을 앱으로 갈아 끼웁니다. 왜 이것이 중요한지는 PID 1 슬라이드에서 이어집니다.

ARG는 빌드에서 끝나고, ENV는 실행까지 남는다

명령하는 일꼭 알아 둘 점
ARG빌드 중에만 쓰는 변수 (--build-arg)이미지 이력에 값이 남음, 비밀 금지
ENV이미지와 컨테이너의 환경 변수실행 시 -e로 덮어씀
WORKDIR이후 명령의 작업 디렉터리, 없으면 생성RUN cd는 다음 줄에 안 이어짐
EXPOSE쓰는 포트를 문서로 남김실제 공개는 -p가 함
USER이후 명령과 실행 계정 지정숫자 UID가 K8s 검사에 유리
HEALTHCHECK주기적으로 상태 확인 명령 실행기본 30초 간격, 3회 실패 시 unhealthy

FROM 앞의 ARG는 베이스 태그를 고를 때만 쓰이고 FROM 뒤에서는 다시 선언해야 합니다. HEALTHCHECK 상태는 Docker와 Compose가 쓰고, Kubernetes는 무시하고 자체 probe를 씁니다(10장).

COPY src ./src
RUN ./gradlew bootJar --no-daemon

Docker는 명령 문자열과 복사할 파일 내용이 이전 빌드와 같으면 레이어를 재사용합니다. 하지만 한 레이어가 바뀌면 그 아래 모든 명령이 다시 실행됩니다.

그래서 빌드 설정만 먼저 복사해 의존성을 받고, 자주 바뀌는 소스는 나중에 복사합니다. 코드만 고친 빌드는 의존성 다운로드를 건너뛰어 수 분이 수십 초로 줄어듭니다. BuildKit의 RUN --mount=type=cache로 Gradle 캐시를 빌드 간에 유지하는 방법도 있습니다.

.dockerignore가 없으면 수백 MB의 .git이 전송되어 빌드가 느려지고, 무관한 파일 변경이 캐시를 깨뜨리며, .env나 키 파일이 이미지에 섞여 레지스트리로 새어 나갑니다. !로 예외를 둡니다.

빌드에는 JDK와 Gradle, 소스가 필요하지만 실행에는 JRE와 JAR만 있으면 됩니다. 멀티 스테이지 빌드는 앞 단계의 결과물만 마지막 단계로 복사하고 나머지를 버립니다.

최종 이미지가 수백 MB 줄어 배포와 스케일 아웃이 빨라지고, 컴파일러나 소스 같은 공격 표면도 사라집니다. 빌드 환경이 이미지 안에 고정되어 "내 PC의 JDK 버전" 문제도 없어집니다.

bridge 네트워크는 veth 한 쌍으로 시작한다

기본 bridge 모드에서 Docker는 호스트에 가상 스위치 docker0을 만들고, 컨테이너마다 veth 쌍을 만듭니다. 한쪽 끝은 컨테이너의 net namespace에 eth0으로, 다른 끝은 브리지에 꽂힙니다.

컨테이너는 172.17.0.0/16 같은 사설 IP를 받고, 밖으로 나갈 때는 호스트 IP로 주소가 바뀝니다(SNAT, 2장의 NAT). 들어오는 쪽은 다음 슬라이드의 포트 매핑이 맡습니다.

컨테이너끼리는 사용자 정의 네트워크로 잇는다

모드동작쓰는 곳
bridge (기본)자기 net ns + veth + NAT, 이름 조회 없음단독 컨테이너
사용자 정의 bridge위와 같고 내장 DNS로 이름 조회여러 컨테이너 연결
host호스트 net ns를 그대로 씀, 포트 충돌은 직접 관리NAT 비용이 아까운 프록시
none루프백만외부 통신 없는 일괄 작업
 
$ docker network create app-net
$ docker run -d --name db --network app-net postgres:16
$ docker run -d --name api --network app-net -e DB_HOST=db api
$ docker exec api getent hosts db      # 172.18.0.2 db

컨테이너 IP는 재시작마다 바뀔 수 있으므로, 사용자 정의 네트워크의 내장 DNS(127.0.0.11)로 이름을 풀어 잇습니다.

-p는 iptables 규칙이고, 방화벽보다 앞선다

$ docker run -d -p 8080:8080 api
$ sudo iptables -t nat -L DOCKER -n
DNAT tcp dpt:8080 to:172.17.0.2:8080
# 0.0.0.0에 열림: 외부에서도 접근
$ docker run -d -p 127.0.0.1:5432:5432 db
$ docker port api

-p 호스트:컨테이너는 nat 표에 DNAT 규칙을 넣어 호스트 포트로 온 패킷의 목적지를 컨테이너 IP로 바꿉니다. 주소를 생략하면 모든 인터페이스(0.0.0.0)에 열립니다.

이 패킷은 INPUT이 아니라 FORWARD 체인을 지나므로, ufw로 막은 포트도 Docker가 열어 버립니다. 개발용 DB를 -p 5432:5432로 띄운 서버가 인터넷에 노출되는 사고가 여기서 납니다. 로컬 전용이면 127.0.0.1에 묶습니다.

재시작 정책은 Docker판 Restart=다

정책다시 시작하는 경우손으로 멈춘 뒤 데몬 재시작
no (기본)하지 않음멈춘 채
on-failure[:5]0이 아닌 종료 코드, 최대 횟수 지정 가능멈춘 채
always항상다시 뜸
unless-stopped항상멈춘 채

단일 서버에서 Compose로 운영한다면 unless-stopped가 무난합니다. 재시작 간격은 Docker가 100ms부터 두 배씩 늘리며 조절합니다. 다만 재시작은 같은 호스트 안에서만 일어나므로, 서버 자체가 죽었을 때 다른 서버에서 띄워 주는 일은 오케스트레이터의 몫입니다(10장).

PID 1은 시그널도 받고 좀비도 거둬야 한다

$ time docker stop api
real  0m10.4s     # 매번 10초면 의심
$ docker inspect -f '{{.State.ExitCode}}' api
137
# 해결 1: exec form으로 앱을 PID 1에
# 해결 2: 작은 init을 PID 1에
$ docker run --init api
# Dockerfile: ENTRYPOINT ["tini","--","java",…]

docker stop은 PID 1에 SIGTERM을 보내고 기본 10초 뒤 SIGKILL을 보냅니다. 커널은 PID 1이 핸들러를 등록하지 않은 시그널을 무시하므로, 셸이나 시그널을 처리하지 않는 앱이 PID 1이면 매번 10초 뒤 강제 종료(137)됩니다.

또 PID 1은 고아를 거둘 책임이 있습니다. 자식을 여럿 띄우는 앱이면 tini 같은 작은 init을 PID 1에 두어 시그널 전달과 좀비 회수를 맡깁니다.

Compose는 여러 컨테이너를 한 파일로 띄운다

services:
  api:
    build: .
    ports: ["127.0.0.1:8080:8080"]
    environment:
      DB_URL: jdbc:postgresql://db:5432/app
    depends_on:
      db: { condition: service_healthy }
    restart: unless-stopped
  db:
    image: postgres:16
    environment: [POSTGRES_PASSWORD=dev]
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: pg_isready -U postgres
volumes: { pgdata: {} }

Docker Compose는 앱과 DB, Redis 묶음을 YAML 하나로 선언하고 docker compose up -d로 띄웁니다. 프로젝트 네트워크를 만들어 모든 서비스를 붙입니다.

서비스 이름 db가 곧 호스트 이름입니다. depends_on만 쓰면 시작 순서만 보장하므로, service_healthy로 DB가 준비될 때까지 기다립니다. 그래도 앱 스스로 재시도해야 하고, Compose는 서버 한 대용이라 여러 서버 운영은 10장의 몫입니다.

컨테이너 안의 root는 호스트의 root다

$ docker run -d --name api \
    --user 10001:10001 \
    --read-only --tmpfs /tmp \
    --cap-drop ALL \
    --cap-add NET_BIND_SERVICE \
    --security-opt no-new-privileges \
    --memory 1g --cpus 1 --pids-limit 512 \
    order-api:3f9c2e1

user namespace를 켜지 않은 기본 설정에서 컨테이너의 root는 UID 0 그대로입니다. 커널 취약점이나 잘못된 마운트 하나로 호스트 전체가 넘어갑니다. 그래서 USER로 일반 계정을 씁니다.

--read-only는 루트 파일 시스템을 읽기 전용으로 만들어 침입자가 도구를 내려받지 못하게 하고, no-new-privileges는 setuid로 권한을 올리는 길을 막습니다. 자원 상한은 한 컨테이너가 호스트를 잠식하는 것을 막습니다.

capabilities는 root 권한의 조각이다

capability허용하는 일Docker 기본
NET_BIND_SERVICE1024 미만 포트 바인딩허용
CHOWN, SETUID소유자 변경, UID 전환허용
NET_ADMIN네트워크 설정, iptables 변경제외
SYS_ADMIN마운트 등 사실상 root 전부제외, 절대 주지 말 것

Linux는 root의 힘을 40여 개의 capabilities로 쪼개 둡니다. Docker는 기본으로 그중 십여 개만 남기고 나머지를 뺍니다. 가장 안전한 방법은 --cap-drop ALL 후 꼭 필요한 것만 더하는 것입니다. --privileged는 모든 capability와 장치 접근을 주어 격리를 사실상 없애므로, 운영 앱에는 쓰지 않습니다.

# 이미지 취약점 검사

이미지는 레지스트리를 통해 여러 사람과 서버로 퍼집니다. ENV, ARG, 복사한 파일은 docker history나 레이어 tar에서 누구나 꺼낼 수 있고, 뒤에서 지워도 앞 레이어에 남습니다.

실행용 비밀은 환경 변수나 마운트로 실행 시 주입하고(K8s Secret은 10장, AWS Secrets Manager는 16장), 빌드용 비밀은 레이어에 남지 않는 BuildKit secret으로 씁니다. 이미지는 Trivy 같은 스캐너로 CVE를 검사합니다.

디버깅은 logs와 inspect에서 시작한다

$ docker ps -a       # 죽은 것까지
$ docker logs --tail 100 -f api
$ docker exec -it api sh
$ docker inspect -f \
  '{{.State.ExitCode}} {{.State.OOMKilled}}' api
$ docker stats --no-stream
$ docker events --since 10m
# 셸 없는 이미지: 옆에 붙어서 보기
$ docker run --rm -it --network container:api \

logs로 앱이 남긴 말을, inspect로 종료 코드와 OOM 여부, 설정된 환경 변수와 마운트를, stats로 실시간 CPU와 메모리 사용량을 봅니다. events는 언제 죽고 재시작됐는지를 보여 줍니다.

distroless처럼 셸이 없으면 exec가 막힙니다. 대상 컨테이너의 네트워크 namespace를 공유하는 도구 컨테이너를 붙이면 그 안에서 curl, tcpdump를 쓸 수 있습니다.

137은 두 경우로 갈립니다. OOMKilled: true면 메모리 상한 문제이고, false면 SIGTERM에 반응하지 않아 유예 시간 뒤 강제 종료된 것이라 PID 1과 종료 처리를 봅니다. Alpine 이미지에서 127이 나면 glibc 바이너리를 찾지 못한 경우도 있습니다.

장애 사례: 로그 없이 사라지는 컨테이너

  1. 증상

    API 컨테이너가 하루 몇 번 재시작되는데 앱 로그는 정상 요청 기록에서 뚝 끊깁니다.

  2. 확인

    inspect 결과 종료 코드 137, OOMKilled: true입니다.

  3. 원인

    상한 1GB에 -Xmx900m. 힙 밖 메모리를 더하면 상한을 넘습니다.

  4. 조치

    힙을 상한의 70% 안팎으로, 스레드 수와 다이렉트 버퍼도 함께 점검합니다.

이 장애가 까다로운 이유는 GC 로그도 힙 사용량도 멀쩡하다는 데 있습니다. JVM 입장에서는 힙에 여유가 있었지만, 커널은 cgroup 전체 사용량만 보고 프로세스를 죽였습니다.

3부의 원리(memory.max, OOM Killer)와 4부의 도구(inspect, 종료 코드)를 함께 알아야 "앱 버그"가 아니라 자원 설정 문제로 바로 좁힐 수 있습니다.

정리

  • 서버 운영의 기본은 파일, 권한, 프로세스, 시그널입니다. 앱은 전용 계정과 systemd로 돌리고, 종료는 SIGTERM 후 SIGKILL 두 단계로 이뤄집니다.
  • 명령어의 숫자는 커널 집계입니다. load는 줄의 길이, 메모리는 available, 디스크는 용량과 inode, fd는 띄운 주체의 한도를 봅니다.
  • 컨테이너는 namespace로 격리하고 cgroup으로 제한한 프로세스입니다. CPU 상한은 스로틀링, 메모리 상한은 OOM으로 나타납니다.
  • 이미지는 OverlayFS 레이어의 겹침입니다. 명령 순서, 멀티 스테이지, 레이어드 JAR로 작고 캐시가 잘 맞는 이미지를 만듭니다.
  • 안전한 컨테이너는 비 root, 최소 capability, 비밀 주입, exec form PID 1입니다. 문제는 종료 코드와 inspect에서 시작해 좁힙니다.

스스로 점검 (1)

  1. chmod 644인 파일을 다른 사용자가 못 읽는다면 어디를 봐야 하나요?

    상위 디렉터리들의 x 권한입니다. 디렉터리에 들어갈 권한이 없으면 파일 권한과 관계없이 경로를 따라갈 수 없습니다.

  2. /etc/security/limits.conf에서 nofile을 올렸는데 systemd로 띄운 앱의 한도가 그대로입니다. 왜일까요?

    limits.conf는 로그인 세션(PAM)에 적용되고 systemd 서비스는 유닛의 LimitNOFILE을 따릅니다. 유닛 파일을 고치고 daemon-reload 후 재시작합니다.

  3. 코어 8개 서버의 load가 20인데 CPU idle이 70%입니다. 무엇을 의심하나요?

    Linux load에는 D 상태 작업이 포함되므로 디스크나 NFS I/O 대기입니다. vmstat의 b와 wa, iostat의 await를 확인합니다.

  4. 로그 파일을 지웠는데 df 사용량이 줄지 않습니다. 이유와 확인 방법은?

    프로세스가 그 파일을 열고 있어 inode가 해제되지 않았습니다. lsof +L1로 찾아 프로세스를 재시작하거나 fd를 비웁니다.

스스로 점검 (2)

  1. CPU 상한 1코어 컨테이너의 평균 CPU가 40%인데 p99 지연이 튑니다. 원인 후보는?

    여러 스레드가 주기 초반에 할당량을 다 써서 스로틀링되는 경우입니다. cpu.stat의 nr_throttled를 보고 상한을 올리거나 스레드 수를 맞춥니다.

  2. Dockerfile에서 RUN rm으로 큰 파일을 지웠는데 이미지가 줄지 않는 이유는?

    레이어는 겹치기만 해서 삭제는 위층의 whiteout 표시일 뿐입니다. 파일을 만든 같은 RUN에서 지우거나 멀티 스테이지로 결과물만 옮깁니다.

  3. docker stop이 매번 10초 걸리고 종료 코드가 137입니다. 무엇을 고치나요?

    PID 1이 SIGTERM을 처리하지 않는 것입니다. shell form을 exec form으로 바꾸거나 스크립트 끝에 exec를 쓰고, 필요하면 tini를 PID 1에 둡니다.

  4. ufw로 5432를 막았는데 -p 5432:5432로 띄운 DB가 외부에서 접속됩니다. 왜일까요?

    Docker의 포트 매핑은 nat 표의 DNAT와 FORWARD 체인으로 처리되어 ufw의 INPUT 규칙을 지나지 않습니다. 127.0.0.1에 바인딩하거나 DOCKER-USER 체인에서 막습니다.

  5. Kubernetes 노드에 Docker가 없어도 Docker로 빌드한 이미지가 도는 이유는?

    이미지는 OCI 표준 형식이고 kubelet은 CRI로 containerd 같은 런타임과 말하기 때문입니다. 빌드 도구와 실행 런타임이 표준으로 분리되어 있습니다.
