이 장은 주문 API 서버 한 대에서 시작한다

커널은 자원을, 셸은 사람의 말을 맡는다

서버에서는 주문 API, 웹 서버, 로그 수집기가 CPU와 메모리, 디스크를 함께 씁니다. 각자 하드웨어를 직접 만지면 서로 덮어쓰고 망가뜨리므로, 하드웨어는 커널만 만지고 프로그램은 시스템 콜, 즉 커널에 일을 부탁하는 정해진 함수로만 요청합니다(1장).

커널 바깥에서 도는 프로그램이 모인 영역을 사용자 공간이라 합니다. 우리가 명령을 치는 셸도 여기 있는 평범한 프로그램으로, 입력한 글자를 해석해 해당 프로그램을 실행해 줍니다.

Linux는 커널이고, 배포판은 그 위의 묶음이다

엄밀히 말해 Linux라는 이름은 커널만 가리킵니다. 커널만으로는 명령을 칠 수도, 프로그램을 설치할 수도 없으므로, 커널에 셸(보통 bash), 기본 명령어, 패키지 관리자, 서비스 관리자를 묶어 내놓은 것이 배포판입니다. Ubuntu, Debian, Red Hat Enterprise Linux(RHEL), Amazon Linux가 모두 배포판입니다.

배포판끼리 커널은 거의 같지만 프로그램을 설치하는 방법과 기본 설정 위치가 조금씩 다릅니다. 그래서 서버에 처음 들어가면 cat /etc/os-release로 어떤 배포판인지부터 확인합니다. 이 장의 예제는 Ubuntu 서버를 기준으로 하고, 차이가 나는 곳은 그때마다 짚습니다.

셸에 명령을 치면 무슨 일이 일어날까요? 셸은 이름에 맞는 실행 파일을 찾아 새 프로세스로 띄웁니다. 그 실행 파일을 어디서 찾는지가 다음 주제인 파일 시스템의 배치 규칙입니다.

디렉터리마다 맡은 역할이 정해져 있다

Linux의 파일은 모두 /(루트) 하나에서 갈라져 나온 나무 모양 디렉터리에 있습니다. 어떤 파일을 어디에 둘지는 FHS라는 관례로 정해져 있어서, 처음 들어간 서버에서도 설정과 로그가 어디 있을지 짐작할 수 있습니다.

/etc에는 시스템과 각 서비스의 설정 파일이 있습니다. 웹 서버 nginx의 설정도, 뒤에서 볼 서비스 정의 파일도 여기 있습니다. /var는 로그(/var/log)처럼 운영 중에 계속 바뀌고 자라는 데이터를 담습니다. 이곳이 가득 차면 로그를 쓰지 못하는 앱이 멈추므로 운영에서 가장 자주 보는 디렉터리입니다.

/usr에는 패키지로 설치한 프로그램이, /opt에는 패키지 관리자 밖에서 직접 배포한 앱이 들어갑니다. 주문 API처럼 우리가 만든 JAR는 보통 /opt/앱이름에 둡니다. 사용자의 개인 파일은 /home/이름, 관리자 root의 것은 /root에 있고, /tmp는 재부팅 때 지워질 수 있는 임시 공간입니다.

/proc과 /sys는 특별합니다. 디스크에 실제로 있는 파일이 아니라, 읽는 순간 커널이 자기 상태를 글자로 만들어 보여 주는 가상 파일입니다. 지금은 "커널의 상태 창"으로만 알아 두면 되고, 2부에서 이 창을 열어 서버의 숫자를 읽습니다.

주문 API의 파일은 이렇게 나눠 둔다

FHS를 따르면 실행 파일, 설정, 비밀, 로그가 각자 다른 곳에 놓입니다. 이렇게 나누면 앱을 새 버전으로 바꿔도 설정과 로그는 건드리지 않습니다.

무엇경로이렇게 두는 이유
실행 파일/opt/api/app.jar직접 배포한 앱의 자리
설정, 비밀 값/etc/api/env코드와 분리, 권한을 따로 잠금
로그/var/log/api/자라는 데이터, 용량 감시 대상
서비스 정의/etc/systemd/system/부팅 때 자동 실행(1부 뒤쪽)
임시 파일/tmp잃어도 되는 것만

서비스 정의 파일이 무엇인지는 이 부의 뒤쪽 systemd에서 자세히 봅니다.

경로는 루트에서 쓰거나 지금 위치에서 쓴다

$ pwd
/opt/api
$ cat /etc/hostname     # 절대 경로
$ cat ./conf/app.yml    # 상대 경로
$ cd ../logs            # 한 단계 위
$ cd ~                  # 내 홈
$ cd -                  # 직전 위치

파일을 가리키는 방법은 둘입니다. 절대 경로는 /로 시작해 어디서 실행해도 같은 파일입니다. 상대 경로는 지금 있는 디렉터리(pwd로 확인)에서 출발하며, .은 여기, ..은 한 단계 위, ~는 내 홈입니다.

뒤에서 볼 자동 실행 도구(cron, systemd)는 우리가 서 있던 디렉터리를 모릅니다. 그래서 자동 실행 설정에는 절대 경로를 씁니다.

하드 링크는 inode를, 심볼릭 링크는 경로를

1장에서 본 inode는 파일의 실체(권한, 크기, 데이터 위치)를 담은 기록이고, 파일 이름은 "이 이름은 inode 812번"이라고 적어 둔 디렉터리 항목일 뿐입니다. 하드 링크는 같은 inode에 이름을 하나 더 붙이는 것이라, 원래 이름을 지워도 데이터가 남습니다.

심볼릭 링크는 "저 경로로 가라"는 문자열을 담은 작은 파일입니다. 따라가 보고 대상이 없으면 끊어진 링크가 됩니다.

심볼릭 링크 하나로 배포 버전을 바꿔 끼운다

$ ls -l /opt/api
releases/
current -> releases/v42
$ ls /opt/api/releases
v41  v42
# 새 버전 배포: 링크만 바꿔 끼움
$ ln -sfn releases/v43 /opt/api/current
# 문제가 생기면 되돌리기
$ ln -sfn releases/v42 /opt/api/current

주문 API를 배포할 때 버전마다 디렉터리를 두고, 서비스는 늘 current 링크를 실행하게 하면 링크를 바꾸는 순간 새 버전을 가리킵니다. 되돌릴 때도 링크만 다시 바꾸면 됩니다.

하드 링크로는 이렇게 못 합니다. inode 번호는 파일 시스템(디스크 파티션)마다 따로 매기므로 다른 파일 시스템에는 걸 수 없고, 디렉터리에 걸면 순환이 생겨 금지돼 있습니다.

계정을 나누는 이유는 사고의 범위를 줄이기 위해서다

$ id
uid=1000(ubuntu) gid=1000(ubuntu)
groups=1000(ubuntu),27(sudo)
$ grep app /etc/passwd
app:x:998:998::/opt/api:/usr/sbin/nologin
# 이름:암호자리:UID:GID:설명:홈:로그인 셸

주문 API에 원격 코드 실행 취약점이 있다고 해 봅시다. 앱이 관리자 권한으로 돌았다면 공격자는 서버 전체를 갖습니다. 앱 전용 계정으로 돌았다면 그 계정이 만질 수 있는 파일까지만 피해가 납니다.

Linux는 사용자를 숫자 UID로, 사용자 묶음을 그룹(GID)으로 구분합니다. 계정 목록은 /etc/passwd에 한 줄씩 있습니다. UID 0인 root는 권한 검사를 모두 건너뜁니다.

앱은 전용 계정으로, 관리는 sudo로

$ sudo useradd -r -s /usr/sbin/nologin \
    -d /opt/api app
$ sudo -u app ls /opt/api
$ sudo visudo   # sudoers 안전 편집
$ sudo usermod -aG docker ubuntu

첫 줄은 시스템 계정(-r)을 만들되 로그인 셸을 nologin으로 두어, 이 계정으로는 사람이 들어올 수 없게 합니다.

사람은 일반 계정으로 들어와 필요할 때만 sudo로 root 권한을 빌립니다. 누가 무엇을 했는지 로그에 남고, 허용 범위는 /etc/sudoers에 적어 visudo로 문법 검사와 함께 고칩니다. 마지막 줄의 docker 그룹은 사실상 root와 같은 힘을 주는데, 이유는 4부 보안에서 봅니다.

권한은 소유자, 그룹, 나머지의 rwx다

$ ls -l /opt/api
-rw-r----- 1 app app  51M app.jar
-rw------- 1 app app  812 db.env
drwxr-x--- 2 app app 4.0K logs
-rwxr-xr-x 1 app app  1.2K start.sh

계정을 나눴으면 "누가 이 파일을 무엇까지 할 수 있나"를 정해야 합니다. ls -l의 맨 앞 글자는 종류(- 파일, d 디렉터리, l 링크)이고, 뒤 아홉 글자가 소유자, 그룹, 나머지 순서의 읽기 r, 쓰기 w, 실행 x입니다. DB 비밀번호가 든 db.env는 소유자 app만 읽고 씁니다.

디렉터리에서는 r이 목록 보기, w가 안에 파일 만들기와 지우기, x가 안으로 들어가기입니다. 파일 권한이 넉넉해도 상위 디렉터리에 x가 없으면 열 수 없습니다.

권한은 숫자로 더하고, 기본값은 umask가 뺀다

$ chmod 600 db.env      # rw- --- ---
$ chmod 750 logs        # rwx r-x ---
$ chmod u+x start.sh    # 기호 방식
$ chown -R app:app /opt/api
$ umask
0022
$ touch a; mkdir b; ls -ld a b
-rw-r--r-- … a
drwxr-xr-x … b

r, w, x는 켜짐과 꺼짐 세 비트라 r=4, w=2, x=1로 더하면 0~7 한 자리, 즉 8진수 한 자리가 됩니다. 640은 소유자 rw-, 그룹 r--, 나머지 ---입니다. chown은 소유자와 그룹을 바꿉니다.

새로 만드는 파일은 666, 디렉터리는 777에서 umask에 켜진 비트를 뺀 권한을 받습니다. umask 022면 파일 644, 디렉터리 755입니다. 비밀 파일을 다루는 서비스는 077로 둬 남이 아예 못 읽게 합니다.

setuid는 실행하는 동안 소유자의 권한을 빌린다

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root … /usr/bin/passwd
$ ls -ld /tmp
drwxrwxrwt … /tmp
$ find / -perm -4000 -type f 2>/dev/null

일반 사용자도 자기 비밀번호는 바꿀 수 있어야 하지만, 비밀번호 해시가 든 /etc/shadow는 root만 쓸 수 있습니다. 이 모순을 푸는 것이 소유자 x 자리의 s, setuid입니다. 이 표시가 있으면 누가 실행하든 파일 소유자(root)의 권한으로 돕니다.

/tmp의 t는 sticky bit로, 누구나 쓰되 자기 파일만 지우게 합니다. setuid 파일은 권한 상승 통로라, 4부에서 컨테이너가 이를 막는 옵션을 씁니다.

패키지 관리자는 의존성까지 챙겨 설치한다

주문 API를 돌리려면 Java 런타임이 필요하고, Java는 다시 여러 시스템 라이브러리가 필요합니다. 이것을 손으로 받아 맞추다 보면 버전이 꼬입니다. 그래서 배포판은 프로그램과 설정, "이것이 필요로 하는 것" 목록(의존성)을 하나로 묶은 패키지를 저장소라는 서버에 모아 두고, 패키지 관리자가 의존성까지 찾아 함께 설치하고 지웁니다.

계열대표 배포판패키지 관리자주로 보는 곳
Debian 계열Ubuntu, Debianapt (.deb)범용 서버, 개발 PC
Red Hat 계열RHEL, Rocky, Amazon Linux 2023dnf (.rpm)기업 서버, AWS 기본 서버 이미지
경량Alpineapk컨테이너 베이스 이미지(4부)

운영 서버는 버전을 고정하고 패치를 계획한다

$ sudo apt update        # 목록만 갱신
$ sudo apt install -y \
    openjdk-21-jre-headless
$ apt list --upgradable
$ sudo apt upgrade       # 실제로 올림
# Red Hat 계열
$ sudo dnf install -y java-21-amazon-corretto
$ sudo dnf upgrade --security

apt update는 저장소의 최신 목록만 받아 오고, 실제로 설치된 것을 올리는 일은 upgrade가 합니다. 둘을 혼동해 "업데이트했는데 그대로"인 경우가 흔합니다.

운영 서버는 지원 기간이 긴 LTS 버전을 고르고, 갑작스런 버전 변화를 막으려 주요 패키지 버전을 고정합니다. 보안 패치는 그대로 두지 않고 정해진 주기에 적용합니다.

모든 프로세스는 fd 0, 1, 2를 갖고 태어난다

$ ls -l /proc/self/fd
0 -> /dev/pts/0     # 표준 입력
1 -> /dev/pts/0     # 표준 출력
2 -> /dev/pts/0     # 표준 오류
$ java -jar app.jar > out.log
$ java -jar app.jar >> out.log  # 이어 쓰기
$ java -jar app.jar 2> err.log
$ cmd < input.txt

이제 앱을 실행해 볼 차례인데, 실행한 앱의 출력은 어디로 갈까요? 1장에서 본 fd, 즉 커널이 열린 파일마다 붙여 주는 번호 중 0, 1, 2는 미리 열려 있습니다. 0은 표준 입력, 1은 표준 출력, 2는 표준 오류이고 기본으로 터미널을 가리킵니다.

리다이렉션은 셸이 프로그램을 띄우기 전에 이 번호를 파일로 바꿔 끼우는 일입니다. 프로그램은 바뀐 줄 모르고 1번에 씁니다.

2>&1은 왼쪽부터 순서대로 적용된다

$ java -jar app.jar > all.log 2>&1
# 1 → all.log, 그다음 2 → (1이 가리키는) all.log

$ java -jar app.jar 2>&1 > all.log
# 2 → (지금 1이 가리키는) 터미널
# 그다음 1 → all.log. 오류는 화면으로

$ cmd > /dev/null 2>&1   # 모두 버림

정상 로그와 오류를 한 파일에 모으려면 2>&1을 씁니다. 뜻은 "2번을 지금 1번이 가리키는 곳으로"입니다. 그래서 순서가 바뀌면 결과가 달라집니다. 두 번째 예는 2번이 아직 터미널을 가리키던 1번을 따라간 뒤에 1번만 파일로 바뀝니다.

/dev/null은 쓰면 그대로 사라지는 특수 파일입니다. 출력을 버릴 때 쓰지만, 실패 흔적까지 버린다는 점을 기억해야 합니다.

다섯 프로세스가 동시에 돌며 조금씩 넘겨받으므로 수 GB 로그도 메모리에 다 올리지 않습니다. 한 가지 일을 잘하는 도구를 조합한다는 Unix의 설계 철학 덕분에, 대시보드가 없어도 장애 중에 바로 답을 얻습니다.

환경 변수는 부모에서 자식으로만 흐른다

$ PROFILE=prod          # 셸 변수
$ export PROFILE        # 자식에게 전달
$ SPRING_PROFILES_ACTIVE=prod \
    java -jar app.jar     # 이 실행에만
$ env | grep SPRING
$ tr '\0' '\n' < /proc/4211/environ

주문 API는 운영과 개발에서 다른 DB에 붙어야 합니다. 이런 값을 코드에 넣지 않고 실행 환경에서 주입하는 통로가 환경 변수입니다. 프로세스는 시작할 때 부모의 환경 변수를 복사받습니다.

셸에서 만든 변수는 export해야 자식에게 넘어가고, 자식이 바꾼 값은 부모에게 돌아오지 않습니다. 이미 떠 있는 프로세스가 받은 값은 마지막 줄처럼 /proc에서 확인합니다.

PATH가 다르면 "터미널에선 되는데"가 생긴다

$ echo $PATH
/usr/local/bin:/usr/bin:/bin
$ which java
/usr/bin/java
$ type ll       # 별칭인지 확인
# 자동 실행 스크립트 안에서는
/usr/bin/java -jar /opt/api/app.jar

셸이 java라는 이름만 보고 실행 파일을 찾을 수 있는 것은 환경 변수 PATH 덕분입니다. 콜론으로 나눈 디렉터리를 앞에서부터 뒤져 처음 찾은 것을 실행합니다.

로그인할 때 읽는 설정 파일(~/.bashrc 등)이 PATH를 늘려 두는데, 뒤에서 볼 cron과 systemd는 이 파일을 읽지 않아 PATH가 훨씬 짧습니다. 그래서 수동으로는 되던 스크립트가 자동 실행에서 "명령을 찾을 수 없음"으로 실패합니다. 실행 파일도 절대 경로로 씁니다.

로그는 grep으로 찾고, less와 tail로 읽는다

$ grep -i -C 3 timeout app.log
$ grep -v healthcheck access.log
$ grep -rl "jdbc:" /etc/api/
$ less +F app.log
$ tail -F app.log | \
    grep --line-buffered ERROR

grep은 패턴에 맞는 줄만 골라냅니다. -i는 대소문자 무시, -C 3은 앞뒤 3줄 문맥, -v는 반대로 거르기, -rl은 디렉터리를 뒤져 파일 이름만 보여 줍니다.

GB 단위 로그를 편집기로 열면 통째로 메모리에 올리느라 멈춥니다. less는 보이는 만큼만 읽습니다. tail -F는 새로 붙는 줄을 따라가며, 로그 파일을 주기적으로 잘라 새 파일로 바꾸는 도구인 logrotate가 파일을 바꿔도 새 파일을 이어서 따라갑니다.

awk는 열을 세고, sed는 줄을 고친다

# 상태 코드($9)별 개수
$ awk '{c[$9]++} END \
    {for(k in c) print k, c[k]}' access.log
# 마지막 열(응답 시간) 평균
$ awk '{s+=$NF; n++} END {print s/n}' \
    access.log
$ sed -i.bak 's/^port=.*/port=8081/' \
    app.conf
$ sed -n '10,20p' app.log

awk는 각 줄을 공백으로 잘라 $1, $2…로 부르고, 마지막 열은 $NF입니다. 첫 예는 상태 코드별 개수를, 둘째는 응답 시간 평균을 한 줄로 냅니다.

sed는 줄 단위로 찾아 바꿉니다. -i는 파일을 그 자리에서 고치므로 .bak처럼 백업 확장자를 붙이는 습관을 들입니다. -n '10,20p'는 10~20번째 줄만 출력합니다.

프로세스는 fork로 태어나 exec로 바뀐다

  1. 셸이 입력을 받음

    java -jar app.jar를 읽고 PATH에서 java를 찾습니다.

  2. fork

    셸이 자신을 복제해 자식 프로세스를 만듭니다. 자식은 새 PID를 받습니다.

  3. exec

    자식이 자기 몸을 java 프로그램으로 갈아 끼웁니다. PID와 열린 fd는 그대로입니다.

  4. wait

    셸은 자식이 끝나기를 기다렸다가 종료 코드를 받습니다.

앱이 "실행된다"는 것은 프로세스가 생긴다는 뜻입니다(1장). Linux는 새 프로세스를 빈손으로 만들지 않고, 부모가 자신을 복제(fork)한 뒤 그 자식이 다른 프로그램으로 바뀌는(exec) 두 단계를 거칩니다.

exec 뒤에도 fd가 그대로라서, 셸이 fork와 exec 사이에 바꿔 둔 리다이렉션이 java에 그대로 적용됩니다. 그래서 모든 프로세스에는 부모(PPID)가 있고, 맨 위에는 PID 1이 있습니다.

ps로 부모와 상태를, top으로 스레드를 본다

$ ps -ef | grep java
app  4211     1  … java -jar app.jar
$ ps -eo pid,ppid,stat,rss,cmd \
    --sort=-rss | head -5
$ pstree -p 1 | head
systemd(1)─┬─sshd(812)───bash(990)
           └─java(4211)─┬─{java}(4212)
$ top -H -p 4211   # 스레드별 CPU

ps -ef의 둘째, 셋째 열이 PID와 PPID입니다. 둘째 명령은 실제 메모리 사용량(RSS) 순으로 정렬하고, pstree는 부모 자식 관계를 나무로 그립니다. java 아래 중괄호는 스레드입니다.

STAT 열은 상태입니다. R은 실행 중이거나 차례를 기다림, S는 잠듦, D는 디스크 I/O 등을 기다리며 깨울 수 없는 잠듦, Z는 좀비입니다. D는 2부의 로드 애버리지에서 다시 만납니다.

좀비는 못 거둔 자식, 고아는 부모 잃은 자식

  1. 자식 종료

    자식이 끝나면 커널은 종료 코드를 담은 작은 기록만 남깁니다.

  2. 좀비(Z)

    부모가 wait()로 읽어 가기 전까지 이 기록이 남은 상태입니다.

  3. 회수

    부모가 wait를 부르면 기록이 지워지고 PID가 반납됩니다.

  4. 고아

    부모가 먼저 죽으면 자식은 PID 1에 입양되고, PID 1이 대신 거둡니다.

앞에서 셸이 자식의 종료 코드를 wait로 받는다고 했습니다. 받아 가기 전까지 남은 기록이 좀비입니다. 메모리는 거의 안 쓰지만 PID 번호를 차지하므로, wait를 빠뜨린 부모 밑에 좀비가 쌓이면 결국 새 프로세스를 못 만듭니다. 이미 죽은 것이라 kill로 지울 수 없고 부모를 고쳐야 합니다.

고아를 거두는 PID 1의 역할은 4부에서 다시 중요해집니다. 컨테이너 안에서는 우리 앱이 PID 1이 되기 때문입니다.

터미널을 닫으면 그 안의 프로세스도 죽는다

$ ./batch.sh &        # 백그라운드 실행
[1] 5120
$ jobs; fg %1         # 다시 앞으로
$ Ctrl+Z; bg          # 멈추고 뒤로 보냄
$ nohup ./batch.sh > batch.log 2>&1 &
$ tmux new -s deploy  # 세션 유지

셸은 보통 자식이 끝날 때까지 기다립니다. 끝에 &를 붙이면 기다리지 않고 프롬프트를 돌려주는 백그라운드 실행이 됩니다. 하지만 SSH 연결이 끊기면 셸이 자식들에게 "터미널이 끊겼다"는 통지 SIGHUP을 보내고, 대부분은 이 통지를 받으면 종료합니다.

nohup은 SIGHUP을 무시하게 하고 출력을 파일로 돌립니다. tmux는 서버 쪽에 셸 세션을 붙잡아 둬 다시 접속해 이어 갑니다.

시그널은 커널이 프로세스에 보내는 짧은 통지다

방금 본 SIGHUP처럼 "끊겼다", "멈춰라" 같은 사건을 프로세스에 알리는 장치가 시그널입니다. 내용 없이 번호 하나만 전달되고, kill -신호 PID로 보냅니다. 이름이 kill이지만 죽이는 시그널만 보내는 것은 아닙니다.

시그널을 받은 프로세스는 셋 중 하나를 합니다. 미리 등록해 둔 함수, 즉 시그널 핸들러를 실행하거나, 무시하거나, 아무 준비도 없으면 시그널마다 정해진 기본 동작(대개 종료)을 따릅니다. Java는 JVM이 SIGTERM 핸들러를 등록해 두므로 Spring 앱은 이 시그널을 받으면 종료 절차를 밟습니다.

그런데 예외가 둘 있습니다. SIGKILL과 SIGSTOP은 핸들러를 등록할 수도, 무시할 수도 없습니다. 커널이 직접 처리하기 때문입니다. 이 차이가 다음 슬라이드에서 보는 "부드러운 종료"와 "강제 종료"를 가릅니다.

TERM은 부탁이고, KILL은 강제다

시그널번호보내는 상황프로세스가 잡을 수 있나
SIGTERM15kill 기본값, 정상 종료 요청잡아서 정리 후 종료
SIGKILL9kill -9, 유예 시간 초과불가, 커널이 즉시 제거
SIGINT2터미널에서 Ctrl+C가능
SIGHUP1터미널 끊김, 설정 재로드 관례가능

프로세스가 끝나면 0~255 사이의 종료 코드를 남기고, 0은 성공, 그 밖은 실패를 뜻합니다. 시그널로 죽으면 셸과 Docker는 128 + 시그널 번호로 보여 주므로 SIGTERM은 143, SIGKILL은 137입니다. 이 두 숫자는 4부의 컨테이너 디버깅에서 그대로 다시 나옵니다.

모든 도구는 TERM을 보내고 기다린 뒤 KILL한다

  1. SIGTERM 전송

    "이제 끝내 달라"고 부탁합니다.

  2. 앱의 정리

    새 요청을 멈추고, 처리 중인 주문을 마치고, DB 연결을 닫습니다.

  3. 유예 시간 대기

    정해진 시간(systemd 90초, Docker 10초) 동안 기다립니다.

  4. SIGKILL

    그래도 남아 있으면 강제로 제거합니다. 정리는 없습니다.

주문 API가 결제 처리 도중 SIGKILL로 죽으면 그 요청은 중간에서 끊깁니다. 그래서 앱을 내릴 때는 SIGTERM으로 정리할 기회를 먼저 주고, 응답이 없을 때만 SIGKILL을 씁니다.

SIGTERM을 받고 하던 일을 마친 뒤 끝내는 것을 Graceful Shutdown이라 합니다. 지금은 이 순서만 기억하면 되고, Spring의 설정과 무중단 배포의 조건은 11장에서 봅니다.

systemd가 서버의 프로세스를 지킨다

nohup으로 띄운 주문 API는 죽으면 아무도 다시 살리지 않고, 서버가 재부팅되면 사라집니다. 이 일을 맡는 것이 systemd입니다. 커널이 부팅 끝에 처음 띄우는 PID 1로, 사용자와 상관없이 뒤에서 계속 도는 프로그램인 데몬들을 관리합니다.

systemd는 서비스를 순서대로 띄우고, 죽으면 되살리고, 출력을 로그 저장소 journald로 모읍니다. 또 서비스마다 프로세스 묶음(cgroup)을 만들어 자식까지 한꺼번에 세고 멈춥니다. cgroup은 3부의 주인공입니다.

service 파일 하나가 실행 방법의 전부다

[Unit]
Description=Order API
After=network-online.target

[Service]
User=app
WorkingDirectory=/opt/api
EnvironmentFile=/etc/api/env
ExecStart=/usr/bin/java -jar /opt/api/app.jar
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target

systemd가 관리하는 대상 하나를 유닛이라 하고, 서비스 유닛은 .service 파일로 정의합니다. 세 구역으로 나뉩니다.

[Unit]은 순서입니다. 네트워크가 준비된 뒤에 띄우라는 뜻입니다. [Install]은 부팅 때 어느 단계에 붙일지인데, multi-user.target은 "네트워크까지 갖춘 일반 서버 상태"라는 목표 지점입니다. 실행 방법인 [Service]는 다음 슬라이드에서 한 줄씩 봅니다.

[Service]의 각 줄은 앞에서 배운 것을 적용한다

User=app은 앞서 만든 전용 계정으로 앱을 돌립니다. WorkingDirectory는 상대 경로의 기준이 될 디렉터리입니다. systemd는 로그인 셸을 거치지 않으므로 이 값을 직접 정해 줘야 합니다.

EnvironmentFile은 환경 변수를 파일에서 읽어 옵니다. DB 비밀번호 같은 값을 권한 600으로 잠근 /etc/api/env에 두면, 유닛 파일이나 코드에 비밀이 드러나지 않습니다. ExecStart는 실행 명령이며 PATH에 기대지 않도록 절대 경로로 씁니다.

Restart=on-failure는 비정상 종료 때 다시 띄우라는 뜻이고, RestartSec=5는 그 전에 5초 쉬라는 뜻입니다. 쉬지 않으면 설정 오류로 바로 죽는 앱이 초당 수십 번 재시작을 반복합니다.

TimeoutStopSec=30은 앞에서 본 SIGTERM 후 SIGKILL까지의 유예 시간입니다(기본 90초). 주문 처리가 끝나기에 충분하되 배포가 늘어지지 않을 만큼 잡습니다. LimitNOFILE은 이 서비스가 열 수 있는 fd 개수 한도로, 연결 하나가 fd 하나이므로 동시 연결이 많은 서버는 기본값(보통 1024)보다 크게 둡니다. 한도가 왜 여러 겹인지는 2부에서 봅니다.

enable은 부팅 때, Restart=는 죽었을 때

$ sudo systemctl daemon-reload          # 유닛 파일 다시 읽기
$ sudo systemctl enable --now api       # 부팅 등록 + 지금 시작
$ systemctl status api; systemctl list-units --failed
$ journalctl -u api -f --since "10 min ago" -p err
Restart= 값다시 시작하는 경우어울리는 곳
no (기본)다시 시작하지 않음한 번 돌고 끝나는 작업
on-failure0이 아닌 종료 코드, 시그널, 타임아웃대부분의 앱 서버
always정상 종료여도 항상멈추면 안 되는 에이전트

enable은 부팅 목표에 등록만, start는 지금 시작만 하므로 둘 다 하려면 --now를 붙입니다. 유닛을 고친 뒤 daemon-reload를 빠뜨리면 옛 설정으로 돕니다. journalctl은 서비스(-u)의 로그를 실시간(-f), 시간, 심각도(-p err)로 거릅니다. 10초 안에 5번 넘게 시작하면 systemd는 포기하고 failed로 두므로, 실패 알림을 함께 겁니다.

cron은 다섯 칸으로 시각을 적는다

# 분 시 일 월 요일  명령
30 3 * * *   /opt/api/bin/cleanup.sh
*/5 * * * *  /opt/api/bin/health.sh
0 9 * * 1-5 /opt/api/bin/report.sh

systemd가 계속 떠 있어야 하는 앱을 맡는다면, "매일 새벽 3시 반에 오래된 주문 임시 파일 정리"처럼 정해진 시각에 한 번 도는 일은 cron이 맡습니다. cron은 1분마다 일정표를 확인해 시각이 맞는 명령을 실행하는 데몬입니다.

일정은 다섯 칸으로 적습니다. 분, 시, 일, 월, 요일 순이고 *는 "모두", */5는 "5마다", 1-5는 월~금입니다. 위 셋은 매일 03:30, 5분마다, 평일 09:00입니다.

cron 작업은 환경, 실패, 겹침을 챙겨야 한다

PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""

*/10 * * * * flock -n /tmp/sync.lock \
  /opt/api/bin/sync.sh \
  >> /var/log/api/sync.log 2>&1

cron 작업은 세 가지로 조용히 실패합니다. 짧은 PATH 때문에 명령을 못 찾고, 출력을 어디에도 남기지 않아 실패를 모르고, 10분 걸리던 작업이 어느 날 12분 걸리면 다음 실행과 겹칩니다.

그래서 PATH를 적고, 출력을 로그로 돌리고, flock으로 겹침을 막습니다. flock은 파일 잠금을 잡은 채 명령을 실행하며, -n은 잠금이 이미 잡혀 있으면 기다리지 않고 건너뜁니다. 서버가 여러 대면 모든 서버에서 돌므로 8장의 분산 락, 즉 여러 서버가 공유하는 잠금이 필요합니다.

SSH 키 인증은 비밀키를 보내지 않는다

내 PC서버 sshd
접속 요청 키 교환 시작
known_hosts 확인 호스트 키 서명 서버가 자신을 증명
사용자 인증 비밀키로 만든 서명비밀키 자체는 PC를 떠나지 않음 authorized_keys로 검증
셸 세션 암호화된 채널

지금까지의 일은 모두 서버에 원격으로 들어가 합니다. 그 통로가 암호화된 원격 셸 SSH이고, 서버에서는 sshd 데몬이 받습니다.

SSH는 양쪽을 다 확인합니다. 서버는 호스트 키로 서명해 "내가 그 서버"임을 증명하고, 사용자는 비밀키로 서명해 "이 공개키의 주인"임을 증명합니다. 서명 원리는 7장의 전자 서명 그대로입니다.

키를 등록하고, 호스트 키 경고는 무시하지 않는다

$ ssh-keygen -t ed25519
$ ssh-copy-id ubuntu@10.0.1.12
$ chmod 700 ~/.ssh
$ chmod 600 ~/.ssh/authorized_keys
WARNING: REMOTE HOST IDENTIFICATION
HAS CHANGED!
$ ssh-keygen -R 10.0.1.12

ssh-keygen이 키 쌍을 만들고, ssh-copy-id가 공개키를 서버의 ~/.ssh/authorized_keys에 붙입니다. 서버에는 공개키만 있으니 서버가 털려도 내 비밀키는 안전하고, 그래서 운영 서버는 비밀번호 로그인을 끕니다.

처음 접속한 서버의 호스트 키는 내 PC의 known_hosts에 저장되어 다음부터 비교됩니다. 키가 바뀌었다는 경고는 누군가 중간에서 서버인 척하는 중간자 공격일 수 있으므로, 서버를 새로 만든 게 확실할 때만 -R로 지웁니다.

파일은 scp로 옮기고, 동기화는 rsync로 한다

$ scp app.jar api1:/opt/api/releases/v43/
$ rsync -avz --delete --dry-run \
    dist/ api1:/srv/web/
# ~/.ssh/config
Host api1
  HostName 10.0.1.12
  User ubuntu
  ProxyJump bastion

새 JAR를 서버에 올릴 때 scp는 SSH 위에서 파일을 통째로 복사합니다. rsync는 양쪽을 비교해 바뀐 부분만 보내므로 큰 디렉터리 동기화에 맞습니다. --delete는 원본에 없는 파일을 대상에서 지우므로 --dry-run으로 무엇이 지워질지 먼저 봅니다.

키를 넣었는데도 비밀번호를 묻는다면 권한부터 봅니다. sshd는 ~/.ssh를 남이 쓸 수 있으면 키를 믿지 않습니다. 설정 파일의 ProxyJump는 다음 슬라이드의 중계 서버를 자동으로 거치게 합니다.

포트 포워딩은 SSH 안으로 다른 연결을 통과시킨다

운영 DB는 인터넷에서 직접 닿지 않는 사설 구역(13장의 Private Subnet)에 둡니다. 들어가는 문은 외부 SSH만 받는 중계 서버 하나로 좁히는데, 이것을 배스천이라 합니다.

DB 툴로 운영 DB를 봐야 할 때는 로컬 포트 포워딩(-L)으로 내 PC의 포트를 SSH 터널 너머 DB에 잇습니다. AWS에서는 배스천 없이 접속하는 방법도 있습니다(14장).

2부

숫자 뒤에 있는 커널의 사정

1부에서 주문 API를 서비스로 올렸습니다. 이제 "느려졌다", "접속이 안 된다", "죽었다"는 신고를 받았을 때 볼 숫자들을 다룹니다. 명령어가 내놓는 숫자는 모두 커널이 센 값이라, 무엇을 세는지 알아야 바르게 읽습니다.

기초 원리 여기부터는 네트워크, CPU, 메모리, 디스크, 커널 파라미터가 내부에서 어떻게 집계되는지 봅니다.

"주문 API가 느려요"를 받으면 자원부터 나눈다

월요일 아침, 주문 API 응답이 평소 100ms에서 2초로 늘었다는 신고가 들어왔다고 합시다. 가장 흔한 실수는 원인을 모른 채 재시작하는 것입니다. 잠깐 나아지더라도 증거가 사라지고, 같은 장애가 다시 옵니다.

느림은 결국 무언가를 기다린다는 뜻입니다. 네트워크 너머의 상대를, CPU 차례를, 메모리를, 디스크를, 아니면 커널이 정한 한도를 기다립니다. 그래서 이 부는 이 순서로 자원을 하나씩 엽니다. 먼저 모든 숫자의 출처인 /proc을 보고, 연결과 방화벽, CPU와 로드, 메모리와 OOM, 디스크와 I/O, fd 한도와 커널 파라미터 순으로 내려갑니다.

각 자원마다 "얼마나 쓰고 있나", "줄을 서서 기다리는 게 있나", "오류가 나나"를 묻는 것이 기본 틀입니다. 이 틀은 부의 마지막에 표 하나로 다시 정리합니다.

/proc은 커널이 열어 둔 상태 창이다

$ cat /proc/loadavg
3.12 2.80 2.41 4/812 5120
$ grep -E 'MemTotal|MemAvail' /proc/meminfo
$ grep -E 'State|VmRSS' /proc/4211/status
$ ls /proc/4211/fd | wc -l
$ cat /proc/4211/limits
$ cat /proc/sys/net/core/somaxconn

1부에서 "커널의 상태 창"이라고만 한 /proc을 열어 봅니다. 디스크에 없는 가상 파일 시스템이라, 파일을 읽는 순간 커널이 내부 상태를 글자로 만들어 돌려줍니다. 이 부에서 쓸 top, free, ps도 결국 여기를 읽어 보기 좋게 바꿀 뿐입니다.

/proc/PID/에는 주문 API(PID 4211)의 상태, 열린 fd, 한도가 있고, /proc/sys/에는 읽고 쓸 수 있는 커널 설정값이 있습니다. 설정값은 이 부의 끝에서 바꿔 봅니다.

ip로 내 주소와 나가는 길을 본다

$ ip -br addr
lo     UNKNOWN 127.0.0.1/8
eth0   UP      10.0.1.12/24
$ ip route
default via 10.0.1.1 dev eth0
10.0.1.0/24 dev eth0 scope link
$ ip route get 10.0.9.20

"DB에 연결이 안 된다"면 내 서버가 네트워크에 어떻게 붙어 있는지부터 봅니다. ip는 예전 ifconfig와 route를 대신하는 명령입니다. lo는 자기 자신만 가리키는 루프백, eth0은 실제 네트워크 카드입니다.

2장에서 본 것처럼 같은 서브넷(10.0.1.0/24)이면 바로 보내고, 그 밖은 기본 게이트웨이(10.0.1.1)로 보냅니다. ip route get은 특정 목적지로 실제로 어느 길을 쓰는지 알려 줍니다.

ss로 누가 어느 주소에서 듣고 있는지 본다

$ ss -ltnp
State  Recv-Q Send-Q Local:Port
LISTEN 0      4096   127.0.0.1:8080
  users:(("java",pid=4211…))
$ ss -tn state established \
    '( dport = :5432 )' | wc -l
$ ss -s

ss는 커널의 소켓 목록을 보여 줍니다. -l 듣는 소켓, -t TCP, -n 숫자 그대로, -p 프로세스 표시입니다. 둘째 명령은 DB(5432)로 맺은 연결 수, -s는 상태별 합계입니다.

주목할 것은 듣는 주소입니다. 위 예처럼 127.0.0.1에만 묶여 있으면 같은 서버 안에서만 닿고 밖에서는 닿지 않습니다. 모든 주소에서 받으려면 0.0.0.0에 묶어야 합니다. "프로세스는 떠 있는데 접속이 안 된다"의 흔한 원인입니다.

연결 문제는 계층 순서로 잘라 본다

  1. dig이름이 맞는 IP로 풀리나
  2. nc -zv포트까지 TCP가 닿나
  3. curl -vTLS와 HTTP 응답은
  4. curl -w어느 단계가 느린가
$ dig +short db.internal.example.com
$ nc -zv 10.0.3.21 5432     # succeeded / refused / timed out

주문 API가 DB에 붙지 못한다면 2장의 계층을 아래에서 위로 하나씩 확인합니다. dig로 DNS가 맞는 IP를 주는지 보고, nc -zv로 그 IP의 포트까지 TCP 연결이 맺어지는지 봅니다. nc의 답이 원인을 가릅니다. refused는 서버가 "그 포트에는 듣는 프로세스가 없다"며 연결 거부(RST) 패킷을 돌려준 것이니 서버까지는 닿았습니다. timed out은 아무 답도 없었다는 뜻이라, 중간의 방화벽이 패킷을 말없이 버렸을 가능성이 큽니다. 클라우드라면 서버 앞의 방화벽인 보안 그룹(13장)부터 의심합니다.

curl -w는 느린 구간을 숫자로 보여 준다

$ curl -sv https://api.example.com/health \
    -o /dev/null
$ curl -so /dev/null -w \
  '%{time_namelookup} %{time_connect}\
 %{time_appconnect} %{time_starttransfer}\
 %{time_total}\n' URL
0.004 0.012 0.041 1.930 1.931

TCP까지 닿는데 느리다면 HTTP 단계를 봅니다. curl -v는 TLS 인증서 교환과 요청·응답 헤더를 그대로 보여 줍니다.

-w는 각 단계가 끝난 누적 시각을 찍습니다. 위 예는 DNS 4ms, TCP 연결 12ms, TLS 41ms까지는 정상인데 첫 바이트가 1.93초에 왔습니다. 네트워크가 아니라 서버가 응답을 만드는 데 2초 가까이 걸린 것이므로, 이제 서버 안의 CPU, 메모리, 디스크를 봐야 합니다.

경로는 traceroute로, 패킷은 tcpdump로 본다

$ traceroute -n 8.8.8.8
 1  10.0.1.1   0.4 ms
 2  * * *
 3  72.14.215.85  2.1 ms
$ mtr -rwc 50 api.example.com

밖으로 나가는 길이 의심스러울 때는 경로를 그립니다. IP 패킷에는 TTL이라는 남은 홉 수가 있어 라우터를 지날 때마다 1씩 줄고, 0이 되면 그 라우터가 버리면서 오류 알림용 프로토콜 ICMP로 "여기서 만료됐다"고 알려 줍니다(2장의 DNS TTL과는 다른 것입니다).

traceroute는 TTL을 1, 2, 3으로 늘려 보내며 각 라우터의 알림으로 경로를 그립니다. * * *은 그 라우터가 ICMP를 막았을 뿐 끊긴 게 아닐 수 있습니다. mtr은 이를 반복해 구간별 손실률을 냅니다.

tcpdump는 추측을 사실로 바꾸는 마지막 도구다

$ sudo tcpdump -i any -nn port 8080
$ sudo tcpdump -i eth0 -nn \
    'tcp[tcpflags] & tcp-syn != 0'
$ sudo tcpdump -i eth0 -w cap.pcap \
    host 10.0.3.21
# cap.pcap을 Wireshark로 열어 분석

지금까지의 도구는 결과만 보여 줍니다. tcpdump는 네트워크 카드를 지나는 패킷 자체를 보여 주므로 "정말 요청이 왔나"를 확인할 수 있습니다. 둘째 줄은 연결 시작 패킷인 SYN만 걸러 봅니다.

2장의 3-way handshake를 떠올리면, SYN은 들어오는데 SYN+ACK가 나가지 않는다면 앱이 아니라 커널이나 방화벽 단계에서 막힌 것입니다. -w로 파일에 담아 그래픽 분석 도구 Wireshark로 자세히 볼 수도 있습니다.

방화벽은 커널 안의 체인에서 패킷을 거른다

패킷이 막혔다면 어디서 막혔을까요? Linux 방화벽은 커널 안의 netfilter라는 검문소 체계입니다. 패킷은 들어오자마자 PREROUTING을 지나고, 내 프로세스로 가면 INPUT, 다른 곳으로 넘길 패킷이면 FORWARD를 거칩니다. 내가 보내는 패킷은 OUTPUT과 POSTROUTING을 지납니다.

각 검문소(체인)에는 규칙 목록이 걸립니다. 그림의 DNAT와 SNAT는 다음 슬라이드에서 설명합니다.

규칙은 표로 나뉘고, nat 표는 주소를 바꾼다

규칙은 하는 일에 따라 표로 나뉩니다. filter 표는 통과시킬지 막을지를, nat 표는 패킷의 주소를 바꾸는 일을 맡습니다.

주소 변환은 2장의 NAT와 같은 일입니다. 목적지 주소를 바꾸는 것이 DNAT로, "이 서버 8080으로 온 패킷을 안쪽 172.17.0.2:8080으로 보내라"처럼 들어오는 패킷을 안쪽으로 넘길 때 씁니다. 라우팅 전에 목적지가 정해져야 하므로 PREROUTING에서 일어납니다. 출발지 주소를 바꾸는 것이 SNAT로, 안쪽 주소를 서버 주소로 감춰 밖으로 내보낼 때 쓰며 나가기 직전인 POSTROUTING에서 일어납니다.

이 두 가지를 기억해 두면 4부의 Docker 포트 매핑이 그대로 이해됩니다. Docker는 컨테이너를 띄울 때 바로 이 nat 표에 DNAT 규칙을 넣고, 패킷은 INPUT이 아니라 FORWARD를 지나 컨테이너로 갑니다.

iptables는 위 규칙부터 맞춰 보고 멈춘다

$ sudo iptables -L INPUT -n -v \
    --line-numbers
$ sudo iptables -A INPUT -m conntrack \
    --ctstate ESTABLISHED,RELATED -j ACCEPT
$ sudo iptables -A INPUT -p tcp \
    --dport 22 -s 10.0.0.0/16 -j ACCEPT
$ sudo iptables -P INPUT DROP
$ sudo nft list ruleset
$ sudo ufw allow 443/tcp

iptables는 netfilter 규칙을 다루는 명령입니다. 규칙은 위에서부터 비교해 처음 맞은 규칙의 동작을 따르고, 아무것도 안 맞으면 체인의 기본 정책(-P)을 씁니다. DROP은 말없이 버려 상대가 timeout을, REJECT는 거부를 알려 refused를 봅니다. conntrack은 연결 상태를 기억해 응답 패킷을 자동 허용합니다.

후속인 nftables가 최신 배포판의 기본이고, ufw는 Ubuntu의 쉬운 앞단입니다. 원격에서 DROP 정책을 걸 땐 SSH 허용 규칙을 먼저 넣습니다.

로드 애버리지는 CPU 사용률이 아니라 줄의 길이다

$ uptime
load average: 7.92, 6.10, 3.05
$ nproc
4
$ ps -eo stat,pid,cmd | awk '$1 ~ /^D/'

네트워크가 멀쩡하다면 서버 안을 봅니다. 가장 먼저 보는 숫자가 로드 애버리지입니다. 실행 중이거나 CPU 차례를 기다리는(R) 작업 수를 1분, 5분, 15분 동안 평균 낸 값인데, 최근 값에 더 큰 무게를 두는 방식이라 급변이 먼저 1분 값에 드러납니다.

Linux는 여기에 D 상태(I/O를 기다리는 깨울 수 없는 잠)도 더합니다. 그래서 4코어에 7.92는 "CPU가 바쁘다"가 아닐 수 있습니다. 세 값이 1분 쪽으로 커지면 악화 중입니다. 무엇을 기다리는 줄인지는 다음 숫자가 알려 줍니다.

CPU 시간은 어디에 썼는지로 나눠 읽는다

$ top -bn1 | head -3
%Cpu(s): 31.0 us,  4.2 sy,  0.0 id,
         63.5 wa,  0.0 st
$ mpstat -P ALL 1    # 코어별
$ pidstat 1          # 프로세스별

top의 CPU 줄은 시간을 쓴 곳별로 나눕니다. us는 앱 코드 실행, sy는 커널 일(시스템 콜 처리), id는 놀기, wa는 할 일이 I/O 완료만 기다리며 논 시간입니다. st(steal)는 가상 서버에서 같은 물리 서버의 다른 가상 서버에 빼앗긴 시간으로, 가상 서버의 구조는 3부에서 봅니다.

위 예는 wa 63.5%입니다. 앞의 높은 로드는 CPU가 아니라 디스크를 기다리는 줄이었습니다. 한 코어만 100%인 경우도 평균에 묻히니 mpstat로 코어별로 봅니다.

남는 메모리는 페이지 캐시가 쓴다

$ free -h
     total used  free buff/cache available
Mem:  15Gi  9Gi 320Mi    5.9Gi     5.6Gi
Swap: 2.0Gi 812Mi 1.2Gi

다음은 메모리입니다. free의 free가 320MB뿐이라 놀라기 쉽지만 정상입니다. 디스크는 메모리보다 수만 배 느리므로, Linux는 한번 읽은 파일 내용을 남는 메모리에 담아 둡니다. 이것이 페이지 캐시(buff/cache)입니다.

캐시는 앱이 메모리를 요구하면 바로 비워 줄 수 있습니다. 그래서 캐시 중 비울 수 있는 몫을 더한 available이 앱이 실제로 더 쓸 수 있는 양입니다. 경보도 free가 아니라 available에 겁니다.

swap은 죽음을 늦추지만 지연을 부른다

$ vmstat 1 3
 r b  swpd  free  si  so   bi  bo wa
 6 3  812k  102k 420 980 1500 220 41
$ sysctl vm.swappiness
vm.swappiness = 60

available마저 바닥나면 커널은 한동안 안 쓴 메모리 페이지를 디스크의 swap 영역으로 내보내 자리를 만듭니다. 덕분에 당장 죽지는 않지만, 그 페이지가 다시 필요하면 디스크에서 읽어 와야 하니 수천 배 느립니다. 이것이 심해지면 1장의 스래싱, 즉 페이지를 들이고 내보내기만 하며 일을 못 하는 상태가 됩니다.

vmstat의 si/so(초당 swap 입출력)가 계속 0이 아니면 이 상태입니다. vm.swappiness는 swap을 쓰는 적극성으로, 지연이 중요한 서버와 Kubernetes 노드는 전통적으로 swap을 끕니다.

커널은 메모리를 실제보다 많이 약속한다

swap까지 다 쓰면 어떻게 될까요? 그 전에 왜 메모리가 "갑자기" 바닥나는지부터 봐야 합니다. 프로세스가 메모리를 달라고 하면 커널은 실제 메모리를 바로 주지 않고 "이 주소 범위를 써도 된다"는 약속만 합니다. 실제 물리 메모리는 그 주소에 처음 쓰는 순간, 즉 1장의 페이지 폴트가 일어날 때 줍니다.

대부분 프로그램은 받은 만큼 다 쓰지 않으므로, 커널은 물리 메모리보다 많은 양을 약속해도 대개 문제가 없습니다. 이것을 오버커밋이라 합니다. 메모리를 효율적으로 쓰게 해 주지만, 여러 프로세스가 약속받은 메모리를 한꺼번에 실제로 쓰기 시작하면 줄 것이 없는 순간이 옵니다.

그 순간 커널은 이미 약속한 것을 거둘 방법이 없습니다. 남은 선택은 누군가를 죽여 메모리를 되찾는 것뿐이고, 그 일을 하는 것이 다음 슬라이드의 OOM Killer입니다.

메모리가 바닥나면 OOM Killer가 하나를 고른다

$ dmesg -T | grep -i -A2 'killed process'
Out of memory: Killed process 4211 (java)
  total-vm:9.1G, anon-rss:7.4G …
$ cat /proc/4211/oom_score
812
$ echo -500 | \
    sudo tee /proc/4211/oom_score_adj
# systemd 유닛: OOMScoreAdjust=-500

페이지 캐시를 비우고 swap까지 써도 모자라면 커널의 OOM Killer가 프로세스 하나를 SIGKILL로 죽입니다. 대상은 oom_score가 가장 높은 것, 대개 메모리를 가장 많이 쓰는 프로세스이고, 서버에서는 주문 API의 JVM이 되기 쉽습니다.

SIGKILL이라 앱은 아무 말도 남기지 못합니다. 흔적은 커널 로그(dmesg)에만 있습니다. 꼭 살려야 할 프로세스는 oom_score_adj(-1000~1000)를 낮춥니다.

디스크는 용량과 inode 둘 다 바닥난다

$ df -h /
/dev/nvme0n1p1  50G  31G  19G  62% /
$ df -i /
/dev/nvme0n1p1  3.2M 3.2M  0  100% /
$ du -xh /var --max-depth=1 | \
    sort -h | tail
$ ncdu -x /     # 대화형 탐색

"No space left on device"가 났다면 df(파일 시스템 단위 사용량)와 du(디렉터리 단위 사용량)로 범인을 찾습니다. du를 큰 순으로 정렬해 한 단계씩 내려갑니다.

그런데 위 예는 용량이 19GB나 남았습니다. 파일 하나마다 inode가 하나 필요한데, Linux의 대표 파일 시스템 ext4는 포맷할 때 inode 개수를 정해 둡니다. 작은 세션 파일 수백만 개가 쌓이면 용량이 남아도 inode가 바닥납니다. df -i로 구분합니다.

로그를 지웠는데 디스크가 그대로인 이유

$ rm /var/log/api/app.log
$ df -h /     # 그대로 100%
$ sudo lsof +L1
COMMAND PID  FD SIZE/OFF    NLINK NAME
java   4211  7w 21474836480 0 app.log
                            (deleted)
# 재시작 없이 비우기
$ : > /proc/4211/fd/7

급한 마음에 20GB 로그를 rm했는데 공간이 돌아오지 않습니다. 1부의 하드 링크에서 봤듯 rm은 이름만 지웁니다. inode와 데이터는 이름이 0개이고 그 파일을 연 fd도 모두 닫혔을 때 비로소 풀립니다. 주문 API가 아직 쓰고 있으니 그대로입니다.

lsof +L1은 이름이 0개인 열린 파일을 찾습니다. 앱을 재시작하거나 fd를 비웁니다. 애초에 지우지 말고 : > app.log로 내용만 비우고, logrotate나 앱의 로그 롤링으로 크기를 관리합니다.

I/O 대기는 vmstat와 iostat로 좁힌다

$ vmstat 1
 r  b  si so  bi    bo   us sy id wa st
 1 7   0  0 120 88000  5  3 30 62  0
$ iostat -xz 1
Device  w/s w_await aqu-sz %util
nvme1n1 3400  48.2    160   100
$ pidstat -d 1   # 누가 쓰나

앞에서 wa가 높았던 이유를 찾아갑니다. vmstat의 b는 I/O를 기다리며 막힌 프로세스 수(D 상태), bo는 초당 디스크 쓰기 블록 수입니다. 막힌 7개가 로드를 키웠습니다.

iostat에서는 요청 하나가 끝나기까지 기다린 시간 await(ms)와 대기 줄 길이 aqu-sz를 봅니다. SSD는 요청을 병렬로 처리하므로 %util 100%가 곧 한계는 아닙니다. 지연이 함께 뛰는지가 기준이고, pidstat -d로 쓰는 프로세스를 찾습니다.

fd 한도는 세 겹으로 걸려 있다

1장에서 본 "Too many open files"는 fd 한도에 닿았다는 뜻입니다. 이 한도는 한 곳이 아니라 세 겹입니다. 커널 전체가 열 수 있는 총량이 있고, 프로세스 하나가 가질 수 있는 한도가 있으며, 그 프로세스 한도에도 지금 적용 중인 soft 값과, soft를 그 이상 올릴 수 없는 천장 hard 값이 따로 있습니다.

층설정적용 범위확인
시스템 전체fs.file-max커널 전체가 여는 파일 수/proc/sys/fs/file-nr
hard의 상한fs.nr_openhard 한도로 줄 수 있는 최대sysctl fs.nr_open
프로세스soft / hard 한도프로세스마다, 자식에게 상속/proc/PID/limits

프로세스 한도는 띄운 주체가 정한다

$ grep 'open files' /proc/4211/limits
Max open files  1024  524288
# 로그인 셸에서 띄운 경우
$ ulimit -n 65535
# /etc/security/limits.conf
# systemd 서비스
LimitNOFILE=65535
# Docker 컨테이너
$ docker run --ulimit nofile=65535:65535 …

프로세스 한도는 부모에게서 상속되므로, 결국 누가 띄웠느냐가 정합니다. 로그인 셸은 ulimit과 로그인 인증 모듈(PAM)이 읽는 limits.conf를, systemd 서비스는 유닛의 LimitNOFILE을, Docker 컨테이너는 --ulimit을 따릅니다.

그래서 limits.conf를 고쳐도 systemd로 띄운 주문 API는 그대로입니다. 한도를 올리기 전에 누수인지부터 가르는 법은 1장에서 다뤘습니다.

sysctl로 커널의 기본값을 서버에 맞춘다

커널의 기본값은 범용으로 정해져 있어, 연결이 많은 API 서버에는 좁을 때가 있습니다. /proc/sys/ 아래의 이 값들을 읽고 쓰는 명령이 sysctl입니다. 아래 표의 값들은 2장에서 원리를 본 것들입니다. accept 큐는 handshake를 마친 연결이 앱의 accept()를 기다리는 줄이고, TIME_WAIT은 먼저 닫은 쪽이 60초간 포트를 붙잡는 상태입니다.

파라미터의미기본값언제 손대나
net.core.somaxconnaccept 큐 길이 상한4096 (커널 5.4+)순간 연결 폭주
net.ipv4.ip_local_port_range나가는 연결의 포트 범위32768–60999외부 호출 많은 서버
net.ipv4.tcp_tw_reuseTIME_WAIT 포트 재사용2 (루프백만)커넥션 풀이 먼저
fs.file-max시스템 전체 fd 상한메모리 비례대량 연결 서버
vm.swappinessswap 적극성60지연 민감 서버

커널 값만 올리면 소용없는 경우가 있다

앞 표의 값들은 짝이 되는 앱 설정과 함께 움직입니다. 실제 accept 큐 길이는 앱이 listen()할 때 요청한 길이(backlog)와 somaxconn 중 작은 값입니다. 그래서 커널 값만 8192로 올리고 Tomcat의 accept-count(기본 100)를 그대로 두면 줄은 여전히 100입니다.

나가는 포트가 바닥나는 문제도 마찬가지입니다. 주문 API가 결제 서버를 부를 때마다 새 연결을 열고 닫으면, 닫힌 포트가 TIME_WAIT 60초 동안 묶여 포트 범위(약 2만 8천 개)가 금세 찹니다. ip_local_port_range를 넓히거나 tcp_tw_reuse를 켜는 것은 시간을 버는 일일 뿐이고, 근본 해결은 연결을 열어 둔 채 재사용하는 것, 즉 4장의 커넥션 풀과 2장의 HTTP keep-alive입니다.

원칙은 하나입니다. 증상을 확인한 값만, 이유를 적어 두고 바꿉니다. 다음 슬라이드는 그 기록을 남기는 방법입니다.

sysctl 변경은 파일에 남겨야 재부팅을 견딘다

$ sysctl net.core.somaxconn
$ sudo sysctl -w net.core.somaxconn=8192
# 영구 적용
$ cat /etc/sysctl.d/90-api.conf
net.core.somaxconn = 8192
net.ipv4.ip_local_port_range = 10240 65000
$ sudo sysctl --system

sysctl -w는 지금 커널 메모리의 값만 바꿔 재부팅하면 사라집니다. /etc/sysctl.d/에 파일로 두고 --system으로 다시 읽어야 영구 적용되고, 파일이므로 코드처럼 리뷰하고 이력을 남길 수 있습니다.

한 가지 예외가 3부의 복선입니다. net.* 파라미터 상당수는 서버 전체가 아니라 "네트워크 namespace"마다 따로 있어서, 컨테이너 안에서는 호스트 값이 아닌 자기 값이 적용됩니다.

"서버가 느리다"는 자원별 세 질문으로 좁힌다

2부의 도구를 한 틀로 묶습니다. 자원마다 사용률(Utilization), 줄 서서 기다리는 포화(Saturation), 오류(Errors)를 차례로 묻는 것을 USE 관점이라 합니다. 월요일 아침의 주문 API는 디스크 줄에서 포화가 보였습니다.

자원보는 명령이상 신호
CPUuptime, mpstat -P ALL 1, pidstat 1load가 코어 수 초과, 한 코어만 100%
메모리free -h, vmstat 1, dmesg -Tavailable 감소, si/so, OOM 기록
디스크df -h, df -i, iostat -xz 1await 급증, 100%, inode 고갈
네트워크ss -s, sar -n DEV,TCP,ETCP 1재전송, TIME_WAIT·CLOSE_WAIT 폭증

sar는 네트워크 장치별 처리량과 TCP 재전송을 초 단위로 보여 줍니다. 지표·로그·덤프를 엮은 전체 장애 대응 절차는 18장에서 다룹니다.

3부

컨테이너는 커널 기능의 조합이다

서버 한 대에 앱이 하나일 때는 2부까지로 충분합니다. 앱이 여럿 올라가면 서로의 라이브러리, 포트, 메모리를 침범합니다. 이 부는 "이 충돌을 VM보다 가볍게 막는 방법은 무엇이고, 커널의 어떤 기능으로 만드는가"에 답합니다. 재료는 1·2부에서 본 프로세스, 네트워크, cgroup, 파일 시스템입니다.

한 서버에 앱 둘을 올리면 서로 부딪힌다

주문 API 서버에 여유가 있어 결제 결과를 처리하는 워커를 같이 올리기로 했다고 합시다. 곧바로 문제가 생깁니다. 워커는 JDK 17에서만 검증됐는데 서버에는 주문 API용 JDK 21이 설치돼 있습니다. 패키지 관리자는 보통 한 버전을 시스템 전체에 깔기 때문에, 한쪽에 맞추면 다른 쪽이 깨집니다.

포트도 부딪힙니다. 둘 다 기본 설정이 8080이라 나중에 뜬 쪽이 "이미 사용 중"으로 죽습니다. 설정 파일 위치(/etc)나 임시 파일 이름이 겹칠 수도 있습니다.

자원은 더 위험합니다. 워커에 메모리 누수가 있으면 2부의 OOM Killer가 메모리를 가장 많이 쓰는 프로세스, 즉 멀쩡한 주문 API를 죽일 수 있습니다. 한 앱의 문제가 이웃에게 번지는 것입니다.

개발자 PC에서는 되는데 서버에서 안 되는 문제도 같은 뿌리입니다. 앱은 코드만이 아니라 런타임, 라이브러리, 설정 파일이라는 "환경" 위에서 돌고, 그 환경이 장소마다 다릅니다. 필요한 것은 두 가지입니다. 앱마다 환경을 통째로 묶어 옮길 수 있어야 하고, 한 서버 안에서 서로 보이지 않고 서로의 자원을 넘보지 못하게 해야 합니다.

첫째 해법은 하드웨어를 흉내 내는 VM이다

오래된 해법은 서버 한 대를 여러 대인 것처럼 쪼개는 것입니다. 하이퍼바이저는 실제 하드웨어 위에서 가상의 CPU, 메모리, 디스크, 네트워크 카드를 만들어 주는 소프트웨어이고, 그 위에서 각자 완전한 OS를 돌리는 가상 컴퓨터가 VM입니다. VM 안에서 도는 OS를 게스트 OS라 합니다.

게스트 OS의 커널은 자기가 진짜 하드웨어를 다룬다고 믿습니다. 하이퍼바이저는 게스트가 하드웨어를 직접 건드리는 특권 명령을 실행하려 하면 CPU의 가상화 기능으로 가로채, 대신 처리하고 결과만 돌려줍니다. 디스크나 네트워크 카드도 흉내 낸 장치를 보여 줍니다.

이렇게 하면 VM마다 커널부터 라이브러리까지 따로라서 충돌은 완전히 사라집니다. 대가는 무게입니다. 앱 하나를 위해 OS 전체를 부팅하고, OS마다 메모리를 따로 씁니다. 클라우드의 가상 서버(14장의 EC2)가 바로 이 VM입니다.

VM은 하드웨어를, 컨테이너는 OS를 나눈다

둘째 해법은 커널은 하나만 두고, 그 위의 프로세스들이 서로를 못 보게 칸막이만 치는 것입니다. 이렇게 격리된 프로세스와 그 환경 묶음이 컨테이너입니다.

그림의 점선 상자가 격리 단위입니다. VM은 상자 안에 게스트 OS(커널)까지 들어 있고, 컨테이너는 상자 안에 앱과 라이브러리만 있고 호스트 커널을 함께 씁니다.

커널을 공유하면 가볍지만 경계는 얇아진다

커널을 공유하니 OS 부팅이 없어 빠르고 작지만, 커널에 구멍이 하나 나면 모든 컨테이너가 위험합니다. 그래서 실무는 둘을 겹쳐 씁니다. 클라우드 VM 위에 컨테이너 여러 개를 올리는 구성이 가장 흔하고, macOS의 Docker도 안에서 작은 Linux VM을 돌립니다. 여러 고객의 코드가 한 서버에 섞이는 AWS Fargate와 Lambda(14·17장)는 커널 공유가 곤란하므로 고객마다 VM 경계를 한 겹 더 둡니다. 이때 쓰는 Firecracker는 AWS가 공개한 하이퍼바이저로, 네트워크와 디스크 같은 꼭 필요한 가상 장치만 흉내 내어 VM 하나를 수 MB 메모리와 1초도 안 되는 시간에 띄웁니다. 이렇게 작게 만든 VM을 microVM이라 부릅니다. VM 수준의 격리를 컨테이너에 가까운 속도로 얻는 셈입니다.

칸막이는 세 가지 커널 기능으로 만든다

Linux 커널 안에는 "컨테이너"라는 객체가 없습니다. 컨테이너는 따로 존재하던 세 가지 기능을 한 프로세스에 함께 건 결과입니다. 앞에서 정리한 두 요구를 하나씩 맞춰 보면 이렇습니다.

"서로 보이지 않게"는 namespace가 맡습니다. 프로세스가 보는 프로세스 목록, 네트워크, 파일 시스템을 따로 갖게 합니다. "서로의 자원을 넘보지 못하게"는 1부 systemd에서 이름만 나온 cgroup이 맡습니다. 프로세스 묶음이 쓰는 CPU와 메모리의 양을 제한합니다. "환경을 통째로 묶어 옮기게"는 레이어 파일 시스템과 그것을 담는 이미지 형식이 맡습니다.

이 부는 이 순서대로 하나씩 열어 보고, 마지막에 Docker가 이 세 가지를 어떤 프로그램들로 엮는지 봅니다. 4부의 Dockerfile과 실행 옵션은 모두 이 세 기능 중 하나를 설정하는 일입니다.

namespace는 프로세스가 보는 세상을 나눈다

namespace는 커널의 전역 자원 하나(프로세스 번호, 네트워크 등)를 여러 벌로 나눠, 각 프로세스가 자기 몫만 보게 하는 기능입니다. 종류마다 따로 나눌 수 있고, 프로세스는 종류마다 정확히 하나에 속합니다.

namespace나누는 것컨테이너 안에서 보이는 모습
pid프로세스 번호내 앱이 PID 1, 남의 프로세스 안 보임
net네트워크 카드, IP, 라우팅, 방화벽자기만의 eth0, 8080을 따로 씀
mnt마운트(붙은 파일 시스템) 목록이미지가 루트(/)로 보임
uts / ipc호스트 이름 / 공유 메모리호스트 이름이 컨테이너 ID
userUID 번호 대응안의 root가 밖에선 일반 UID

이 밖에 cgroup, time namespace도 있습니다. ls -l /proc/PID/ns로 프로세스가 어느 namespace에 속했는지 봅니다.

namespace가 앞의 충돌을 하나씩 지운다

결제 워커와 주문 API의 충돌로 돌아가 봅시다. net namespace를 나누면 두 앱이 각자 자기 네트워크 카드와 포트 공간을 가지므로 둘 다 8080에서 들어도 부딪히지 않습니다. 2부 끝에서 sysctl의 net.* 값이 컨테이너마다 따로라고 한 이유가 이것입니다. 대신 바깥에서 들어오려면 둘을 잇는 장치가 필요한데, 4부의 bridge 네트워크와 포트 매핑이 그 일을 합니다.

mnt namespace를 나누면 각자 다른 디렉터리를 루트(/)로 봅니다. 워커의 /usr/lib/jvm에는 JDK 17이, 주문 API의 같은 경로에는 JDK 21이 있을 수 있습니다. 그 디렉터리 내용이 바로 뒤에서 볼 이미지입니다.

pid namespace는 서로의 프로세스를 못 보게 하고, 각 컨테이너의 첫 프로세스를 PID 1로 만듭니다. 1부에서 PID 1은 고아를 거두는 특별한 역할이 있다고 했는데, 이제 그 역할이 우리 앱에 떨어집니다(4부).

user namespace는 컨테이너 안의 UID 0(root)을 밖에서는 권한 없는 UID로 대응시킵니다. 탈출하더라도 일반 사용자에 머물게 하는 강력한 방어지만, Docker는 기본으로 켜지 않습니다. 이 점이 4부 보안의 출발점입니다.

같은 프로세스가 안과 밖에서 다른 번호를 갖는다

pid namespace 안에서 처음 뜬 프로세스는 PID 1을 받지만, 호스트에서 보면 평범한 PID 4211입니다. 두 컨테이너는 서로를 못 봐도 호스트의 ps에는 모두 보입니다.

Docker 없이도 sudo unshare --pid --fork --mount-proc bash로 새 pid namespace에서 셸을 띄우면 ps에 프로세스가 둘만 보입니다. 컨테이너의 정체는 커널 기능을 건 프로세스라는 것을 직접 확인하는 방법입니다.

cgroup은 프로세스 묶음이 쓰는 양을 제한한다

$ stat -fc %T /sys/fs/cgroup
cgroup2fs          # v2
$ cd /sys/fs/cgroup/system.slice/\
docker-<id>.scope
$ cat cpu.max
50000 100000
$ cat memory.max memory.current
536870912
402653184
$ grep oom_kill memory.events

namespace가 "보이는 것"을 나눈다면, 워커가 메모리를 다 먹는 문제는 막지 못합니다. cgroup은 프로세스를 묶어 CPU, 메모리, 디스크 I/O, 프로세스 개수를 세고 제한하는 기능입니다. 설정은 /sys/fs/cgroup 아래 파일에 값을 쓰는 것으로 끝납니다.

예전 v1은 자원마다 계층이 따로라 복잡했고, v2는 하나로 통합했습니다. Ubuntu 22.04, Amazon Linux 2023 같은 최신 배포판은 v2가 기본입니다.

docker run의 자원 옵션은 cgroup 파일이 된다

$ docker run -d --name worker \
    --cpus 0.5 --memory 512m \
    --pids-limit 256 payment-worker
# 호스트의 해당 cgroup 디렉터리에서
cpu.max      50000 100000
memory.max   536870912
pids.max     256

4부에서 쓸 Docker 옵션은 사람이 읽기 좋은 표현일 뿐입니다. --cpus 0.5는 cpu.max에, --memory 512m은 memory.max(바이트)에, --pids-limit은 프로세스 개수 상한에 그대로 적힙니다. 1부의 systemd도 서비스마다 같은 파일을 씁니다.

CPU와 메모리는 상한에 닿았을 때 반응이 전혀 다릅니다. CPU는 기다리게 하고, 메모리는 죽입니다. 두 반응을 차례로 봅니다.

CPU 상한은 죽이지 않고 멈춰 세운다

cpu.max = 50000 100000은 100ms 주기마다 CPU 시간 50ms, 즉 0.5코어를 쓸 수 있다는 뜻입니다. 다 쓰면 그 주기가 끝날 때까지 스로틀링되어 아예 실행되지 않습니다.

스레드가 여럿이면 함정이 됩니다. 4개가 동시에 돌면 50ms를 12.5ms 만에 다 쓰고 87.5ms를 멈춥니다. 평균 CPU 사용률은 낮은데, 가장 느린 1% 요청의 응답 시간인 p99 지연이 100ms씩 튀는 이유입니다.

스로틀링은 cpu.stat에서 확인하고 스레드 수로 다룬다

$ cat cpu.stat
usage_usec      912345678
nr_periods      86400
nr_throttled    21600
throttled_usec  1843000000

nr_periods는 지나간 주기 수, nr_throttled는 그중 할당량을 다 써서 멈춘 주기 수입니다. 위 예는 주기의 25%에서 멈췄습니다. 이 비율이 의미 있게 크면 평균 사용률과 관계없이 지연의 원인입니다.

대응은 상한을 실제 순간 사용량에 맞춰 올리거나, 동시에 도는 스레드 수를 줄이는 것입니다. JVM은 GC 스레드와 요청 처리 스레드를 코어 수에 맞춰 만드는데, 컨테이너의 CPU 상한을 코어 수로 읽으므로 상한이 작으면 스레드도 줄어듭니다. 이 연결은 4부의 Java 이미지에서 다시 봅니다.

메모리 상한을 넘으면 그 cgroup 안에서 죽인다

메모리는 빌려 쓰고 나중에 갚을 수 없어 CPU처럼 멈춰 세울 수 없습니다. cgroup이 memory.max에 닿으면 커널은 먼저 그 cgroup의 페이지 캐시를 비우고, 그래도 모자라면 2부의 OOM Killer를 그 cgroup 안에서만 돌립니다. 워커가 넘쳐도 주문 API는 무사합니다.

호스트에 메모리가 남아 있어도 일어납니다. 종료 코드는 137, docker inspect에 OOMKilled: true, Kubernetes에서는 OOMKilled로 보입니다(10장).

상한에는 힙 밖 메모리도 들어간다

JVM은 힙(5장)에 Metaspace, 스레드 스택, 다이렉트 버퍼가 더해집니다. 힙을 상한 가까이 잡으면 GC 로그는 멀쩡한데 컨테이너가 죽습니다.

페이지 캐시도 사용량에 잡힌다

파일을 많이 읽으면 사용량이 상한 근처에 붙어 보입니다. 비울 수 있는 캐시를 뺀 실사용량(working set)을 기준으로 봅니다.

환경을 옮기려면 파일 시스템을 통째로 묶는다

이제 세 번째 요구, "환경을 통째로 묶어 옮기기"입니다. 앱이 도는 환경이란 결국 파일들입니다. JDK 바이너리, 시스템 라이브러리, 설정 파일, 그리고 app.jar입니다. 이것을 디렉터리 하나에 담아 mnt namespace의 루트로 보여 주면, 어느 서버에서든 같은 환경이 됩니다.

이 디렉터리 묶음과 "무엇을 어떻게 실행하라"는 설정을 함께 포장한 것이 이미지입니다. 이미지를 만든 곳에서 올려 두고 다른 서버들이 내려받는 저장소 서버를 레지스트리라 합니다. Docker Hub가 공개 레지스트리이고, AWS의 ECR(14장)도 레지스트리입니다.

문제는 크기입니다. 주문 API 이미지가 300MB인데 코드 한 줄을 고칠 때마다 300MB를 새로 올리고 내려받아야 할까요? 서버 한 대에 컨테이너 열 개를 띄우면 300MB짜리 복사본이 열 개 필요할까요? 이 낭비를 없애는 것이 다음 슬라이드의 레이어 구조입니다.

이미지는 읽기 전용 레이어의 겹침이다

이미지는 파일 변경분을 담은 레이어를 차례로 쌓은 것입니다. 베이스 OS와 JRE, 의존성, 앱 JAR가 각각 한 층입니다. OverlayFS는 아래 층들(lowerdir)과 맨 위 쓰기 층(upperdir)을 겹쳐 하나의 디렉터리(merged)로 보여 주는 커널 기능으로, Docker의 기본 저장 방식 overlay2가 이것입니다.

같은 경로가 여러 층에 있으면 위층이 이깁니다. 삭제는 위층에 "지워졌음" 표시(whiteout)를 남길 뿐이라 아래 층의 용량은 줄지 않습니다.

쓰기 레이어는 복사 후 쓰기라서 무겁고 사라진다

  1. 읽기

    위층부터 찾아 내려가 처음 발견한 파일을 그대로 읽습니다.

  2. 첫 수정

    아래층 파일을 통째로 쓰기 레이어에 복사한 뒤 고칩니다(copy-up).

  3. 이후 수정

    쓰기 레이어의 사본만 고칩니다.

  4. 컨테이너 삭제

    쓰기 레이어가 함께 지워지고 변경 내용도 사라집니다.

이미지 층은 모두 읽기 전용이고, 컨테이너가 쓰는 것은 컨테이너마다 붙는 얇은 쓰기 층에만 갑니다. 고칠 때 비로소 복사하는 이 방식을 CoW라 합니다. 덕분에 컨테이너 100개가 이미지 하나를 공유하고 1초 만에 뜹니다.

대가도 있습니다. 1GB 파일의 한 바이트만 고쳐도 1GB가 복사되고, 쓰기 층은 느리며 컨테이너와 운명을 같이합니다. 그래서 DB 데이터나 업로드 파일처럼 남아야 하거나 많이 쓰는 것은 볼륨에 둡니다(4부).

OCI 표준 덕분에 어떤 도구로 만들어도 돌아간다

이미지를 Docker로 만들고 다른 도구로 실행하려면 형식이 약속돼 있어야 합니다. Docker가 만든 형식을 업계 공통 표준으로 정리한 단체와 그 규격이 OCI입니다. 이미지는 레이어 파일들과, 어떤 레이어를 어떤 순서로 쌓는지 적은 목록인 매니페스트로 이뤄지고, 각각은 내용의 sha256 해시로 이름이 정해집니다. 내용이 같으면 이름도 같아 한 번만 저장됩니다.

  4. shim컨테이너마다 하나
  5. runcnamespace, cgroup 생성

우리가 치는 docker는 요청만 보내는 클라이언트입니다. 유닉스 소켓 파일 /var/run/docker.sock을 통해 데몬 dockerd에 부탁하고, dockerd는 네트워크와 볼륨을 준비한 뒤 이미지 관리와 실행을 containerd에 맡깁니다. containerd는 컨테이너마다 작은 감시 프로세스 containerd-shim을 띄우고, shim이 OCI Runtime Spec의 표준 실행기 runc를 부릅니다.

runc는 지금까지 본 namespace와 cgroup을 만들고, 레이어를 겹친 루트를 붙인 뒤 앱을 exec하고 바로 빠집니다. 이후 shim이 앱의 부모로 남으므로, live-restore를 켜 두면 dockerd를 재시작해도 컨테이너가 죽지 않습니다.

Kubernetes 노드는 containerd로 돌린다

앞의 계층에서 실제 실행에 꼭 필요한 것은 containerd와 runc뿐입니다. 10장의 Kubernetes는 서버마다 kubelet이라는 관리 프로그램을 두는데, kubelet은 CRI라는 규격으로 런타임에 "이 컨테이너를 띄워라"고 말합니다. Docker는 CRI를 직접 지원하지 않아 중간 어댑터(dockershim)가 필요했고, 이 어댑터는 Kubernetes 1.24에서 제거됐습니다.

이미지는 OCI 표준이라 Docker로 빌드한 이미지가 그대로 돕니다. 대신 노드에는 docker 명령이 없으므로, 노드에 들어가 컨테이너를 살펴볼 때는 CRI 런타임에 직접 말을 거는 명령줄 도구 crictl을 씁니다.

4부

주문 API를 좋은 이미지로 만들고 안전하게 띄우기

3부에서 컨테이너가 namespace, cgroup, 레이어로 만들어진다는 것을 봤습니다. 이 부는 1부에서 systemd로 돌리던 주문 API를 이미지로 옮깁니다. Dockerfile 한 줄이 레이어, PID 1, 보안에 어떤 결과를 남기는지 따지며 쓰고, 띄우고, 고칩니다.

원리 실무 이미지 이름, Dockerfile, 베이스와 Java, 네트워크와 저장소, Compose, 보안, 디버깅과 장애 사례를 다룹니다.

Dockerfile은 이미지를 만드는 조리법이다

FROM eclipse-temurin:21-jre
ARG APP_VERSION=dev
ENV TZ=Asia/Seoul \
    JAVA_OPTS="-XX:MaxRAMPercentage=75"
WORKDIR /app
RUN useradd -r -u 10001 app
COPY --chown=app build/libs/app.jar app.jar
USER app
EXPOSE 8080
HEALTHCHECK CMD curl -fs localhost:8080/health \
  || exit 1
LABEL version=$APP_VERSION
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS \
  -jar app.jar"]

이미지는 Dockerfile이라는 텍스트 파일로 만듭니다. docker build가 위에서부터 한 줄씩 실행해 읽기 전용 이미지를 만들고, docker run이 그 위에 쓰기 층을 얹어 컨테이너로 띄웁니다. 이미지와 컨테이너는 클래스와 인스턴스 관계입니다.

파일 시스템을 바꾸는 RUN, COPY, ADD만 레이어를 만들고 나머지는 실행 설정만 바꿉니다. 이 짧은 파일에 1부의 전용 계정, 2부의 메모리, PID 1이 모두 담겨 있습니다. 다음 슬라이드부터 한 줄씩 봅니다.

설치와 청소는 한 RUN 안에서 끝낸다

# 나쁜 예: 레이어 3개
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
# 좋은 예: 레이어 1개
RUN apt-get update \
 && apt-get install -y \
    --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

FROM은 출발점이 될 베이스 이미지를 고르고, RUN은 빌드 중에 명령을 실행해 그 결과를 새 레이어로 남깁니다. 헬스 체크용 curl을 설치하는 위 두 예는 결과 파일이 같아 보여도 크기가 다릅니다.

3부에서 봤듯 레이어는 겹치기만 하므로, 다음 RUN에서 지워도 앞 레이어 용량은 그대로입니다. 나쁜 예는 패키지 목록 수십 MB가 둘째 층에 남습니다. 그래서 설치와 정리는 한 RUN에서 &&로 잇고, 추천 패키지는 빼고 설치합니다.

파일은 COPY로 넣고, ADD는 이유가 있을 때만 쓴다

COPY --chown=app:app \
    build/libs/app.jar /app/app.jar
# tar를 풀어서 넣음
ADD vendor.tar.gz /opt/vendor/
# URL에서 받되 해시로 고정
ADD --checksum=sha256:<hash> \
    https://example.com/agent.jar /opt/

COPY는 빌드하는 PC의 파일을 이미지 안으로 그대로 복사합니다. --chown으로 소유자를 바로 정하면 따로 chown을 RUN할 필요가 없고, 그만큼 레이어가 줄어듭니다.

ADD는 COPY에 두 기능이 더해진 것입니다. 로컬 tar 파일은 자동으로 풀고, URL을 주면 내려받습니다. 의도치 않게 풀리거나 받은 파일이 바뀔 수 있어 기본은 COPY를 쓰고, URL을 받을 때는 --checksum으로 내용을 고정합니다.

ENTRYPOINT는 실행 파일, CMD는 기본 인자다

이미지에는 "컨테이너가 시작하면 무엇을 실행할지"가 적혀 있어야 합니다. 두 명령이 이 일을 나눠 맡습니다. ENTRYPOINT는 실행할 프로그램을, CMD는 거기에 붙일 기본 인자를 적고, 최종 실행 명령은 ENTRYPOINT + CMD입니다. docker run 이미지 뒤에 붙인 인자는 CMD를 통째로 바꾸고, ENTRYPOINT는 --entrypoint로만 바뀝니다.

Dockerfiledocker run imgdocker run img --debug
CMD만 ["java","-jar","app.jar"]java -jar app.jar--debug (CMD 통째 교체)
ENTRYPOINT만 ["java","-jar","app.jar"]java -jar app.jarjava -jar app.jar --debug
ENTRYPOINT + CMD ["--port=8080"]… app.jar --port=8080… app.jar --debug

Kubernetes에서도 같은 구분이 이어집니다. Pod 명세의 컨테이너 항목에 적는 command가 ENTRYPOINT를, args가 CMD를 덮어씁니다.

shell form은 셸을 PID 1로 만든다

# shell form: /bin/sh -c "java …"
ENTRYPOINT java -jar app.jar
# PID 1 = sh, java는 자식

# exec form: JSON 배열, 셸 없음
ENTRYPOINT ["java", "-jar", "app.jar"]
# PID 1 = java

# 변수 확장이 필요하면 exec로 넘김
ENTRYPOINT ["sh","-c","exec java \
  $JAVA_OPTS -jar app.jar"]

ENTRYPOINT와 CMD는 두 가지 꼴로 쓸 수 있습니다. 문자열로 쓰는 shell form은 /bin/sh -c로 감싸 실행되므로 셸이 PID 1, java는 그 자식이 됩니다. 셸은 받은 SIGTERM을 자식에게 넘기지 않을 수 있습니다.

JSON 배열로 쓰는 exec form은 셸 없이 java가 곧바로 PID 1입니다. 다만 셸이 없으니 $JAVA_OPTS 같은 변수가 풀리지 않습니다. 그럴 때는 셸을 거치되 1부의 exec로 셸을 java로 갈아 끼웁니다. 왜 PID 1이 중요한지는 실행 편에서 봅니다.

ARG는 빌드에서 끝나고, ENV는 실행까지 남는다

ARG JRE_TAG=21-jre
FROM eclipse-temurin:${JRE_TAG}
ARG APP_VERSION=dev     # FROM 뒤 재선언
LABEL version=$APP_VERSION
ENV TZ=Asia/Seoul
$ docker build \
    --build-arg APP_VERSION=3f9c2e1 .
$ docker run -e TZ=UTC order-api

빌드할 때마다 값을 바꾸고 싶으면 ARG를 씁니다. --build-arg로 넘기며 빌드 중에만 존재합니다. FROM 앞의 ARG는 베이스 태그를 고를 때만 쓰이고, FROM 뒤에서 쓰려면 다시 선언해야 합니다.

ENV는 이미지에 박혀 컨테이너 안의 환경 변수가 되고, 1부에서 본 대로 앱이 읽습니다. 실행 때 -e로 덮어씁니다. 둘 다 이미지 이력에 값이 남으므로 비밀번호를 넣으면 안 됩니다(보안 편).

나머지 명령은 실행 환경을 설명한다

남은 네 명령은 레이어를 만들지 않고 실행 설정만 정합니다. 1부에서 systemd 유닛에 적었던 작업 디렉터리, 실행 계정, 그리고 2부의 연결 확인이 여기서는 이미지 안에 들어갑니다.

명령하는 일꼭 알아 둘 점
WORKDIR이후 명령의 작업 디렉터리, 없으면 생성RUN cd는 다음 줄에 안 이어짐
USER이후 명령과 실행 계정 지정숫자 UID가 K8s 검사에 유리
EXPOSE쓰는 포트를 문서로 남김실제 공개는 -p가 함
HEALTHCHECK주기적으로 상태 확인 명령 실행기본 30초 간격, 3회 실패 시 unhealthy

HEALTHCHECK 결과는 Docker와 Compose가 씁니다. Kubernetes는 이를 무시하고 자체 probe를 씁니다(10장). 각 RUN은 새 셸에서 돌기 때문에 cd가 다음 줄로 이어지지 않습니다.

레이어 캐시는 명령 순서가 결정한다

# 나쁜 순서: 코드 한 줄에도 재다운로드
COPY . .
RUN ./gradlew bootJar

# 좋은 순서: 잘 안 바뀌는 것부터
COPY gradlew settings.gradle build.gradle ./
COPY gradle ./gradle
RUN ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew bootJar --no-daemon

빌드를 다시 하면 Docker는 각 줄의 명령 문자열과 복사할 파일 내용이 지난번과 같은지 봐서, 같으면 만들어 둔 레이어를 재사용합니다. 하지만 한 레이어가 바뀌면 그 아래 모든 줄이 다시 실행됩니다.

그래서 빌드 설정만 먼저 복사해 의존성을 받고, 자주 바뀌는 소스는 나중에 복사합니다. 코드만 고친 빌드는 의존성 다운로드를 건너뛰어 수 분이 수십 초가 됩니다. 현재 Docker의 빌드 엔진 BuildKit은 RUN --mount=type=cache로 Gradle 캐시를 빌드 사이에 유지하는 기능도 줍니다.

.dockerignore로 빌드 컨텍스트를 줄인다

.git

!build/libs/*.jar

docker build .의 마지막 점은 빌드 컨텍스트, 즉 빌더에 보낼 디렉터리입니다. 이 디렉터리 전체가 빌더로 전송되고, COPY . .은 그 전부를 이미지에 넣습니다.

.dockerignore가 없으면 수백 MB의 .git이 매번 전송되어 느리고, 무관한 파일이 바뀌어 캐시가 깨지며, .env나 키 파일이 이미지에 섞여 레지스트리로 새어 나갑니다. 형식은 .gitignore와 비슷하고 !로 예외를 둡니다.

멀티 스테이지로 빌드 도구를 버린다

# 1단계: 빌드 (JDK, Gradle 포함)
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY gradlew settings.gradle build.gradle ./
COPY gradle ./gradle
RUN ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew bootJar --no-daemon

# 2단계: 실행 (JRE만)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/build/libs/*.jar app.jar
USER 10001
ENTRYPOINT ["java", "-jar", "app.jar"]

앞의 캐시 예제처럼 이미지 안에서 빌드하면 JDK와 Gradle, 소스가 최종 이미지에 남습니다. 실행에는 JRE와 JAR만 있으면 됩니다. 멀티 스테이지 빌드는 FROM을 여러 번 써서 단계를 나누고, 앞 단계의 결과물만 --from으로 마지막 단계에 복사합니다.

최종 이미지가 수백 MB 줄어 배포가 빨라지고, 컴파일러 같은 공격 도구도 사라집니다. 빌드 환경이 고정되어 "내 PC의 JDK 버전" 문제도 없어집니다.

베이스 이미지는 무엇을 담느냐로 갈린다

2단계의 FROM에 무엇을 고르느냐가 최종 이미지의 크기와 보안, 디버깅 편의를 정합니다. 고르기 전에 알아야 할 부품이 하나 있습니다. Linux의 거의 모든 프로그램은 파일 열기, 메모리 할당, DNS 조회 같은 기본 기능을 C 표준 라이브러리에 기대는데, 대부분 배포판은 glibc를, 초경량 배포판 Alpine은 작게 다시 만든 musl을 씁니다. glibc를 전제로 컴파일된 프로그램은 musl 위에서 실행되지 않거나 미묘하게 다르게 동작합니다.

베이스는 크게 다섯 갈래입니다. 셸과 패키지 관리자까지 갖춘 일반 배포판, 꼭 필요한 패키지만 남긴 slim, musl 기반의 alpine, 런타임만 넣고 셸조차 뺀 distroless, 아예 빈 scratch입니다. 담은 것이 적을수록 작고, 알려진 보안 취약점(CVE라는 번호로 관리됩니다)이 줄지만, 문제가 생겼을 때 안에 들어가 쓸 도구도 줄어듭니다.

  Effective CPU Count: 2
  Memory Limit: 2.00G
# 기본 최대 힙 = 2GB × 25% = 512MB
JAVA_OPTS="-XX:MaxRAMPercentage=75"

JVM은 시작할 때 메모리와 CPU 수를 보고 힙 크기와 GC 스레드 수를 정합니다(5장). 최신 JDK(10 이상, 8u191 이상)는 호스트 전체가 아니라 3부의 cgroup 상한을 읽습니다. cgroup v2 인식은 JDK 15, 11.0.16, 8u372부터라 오래된 JDK는 v2 서버에서 상한을 못 봅니다.

읽더라도 기본 최대 힙은 상한의 25%뿐이라 2GB 컨테이너가 512MB만 씁니다. 3부에서 봤듯 힙 밖 메모리 몫을 남겨야 하므로 MaxRAMPercentage를 70~75로 둡니다.

레이어드 JAR는 의존성과 내 코드를 나눈다

FROM eclipse-temurin:21-jre AS builder
WORKDIR /builder
COPY build/libs/*.jar application.jar
RUN java -Djarmode=tools \
  -jar application.jar extract \
  --layers --destination extracted
FROM eclipse-temurin:21-jre
WORKDIR /application
COPY --from=builder \
  /builder/extracted/dependencies/ ./
# spring-boot-loader, snapshot-…도 같은 식
COPY --from=builder \
  /builder/extracted/application/ ./
ENTRYPOINT ["java","-jar","application.jar"]

Spring Boot의 app.jar는 의존성 라이브러리까지 한 파일에 담은 fat JAR입니다. 의존성 수십 MB와 내 코드 수백 KB가 한 레이어라, 코드 한 줄만 고쳐도 통째로 올리고 받습니다.

Boot 3.3부터는 jarmode=tools로 JAR를 잘 안 바뀌는 순서의 디렉터리로 풀 수 있습니다. 순서대로 COPY하면 배포마다 바뀐 application 레이어만 전송됩니다.

bridge 네트워크는 veth 한 쌍으로 시작한다

이미지를 만들었으니 띄울 차례입니다. 3부에서 컨테이너는 자기 net namespace를 가진다고 했으니, 바깥과 이을 선이 필요합니다. 기본 bridge 모드에서 Docker는 호스트에 소프트웨어 스위치 docker0을 만들고, 컨테이너마다 양 끝이 이어진 가상 랜선 veth 쌍을 만들어 한쪽은 컨테이너 안 eth0으로, 다른 쪽은 스위치에 꽂습니다.

같은 스위치에 꽂힌 컨테이너끼리는 2장의 같은 네트워크(L2) 통신처럼 바로 통하고, 밖으로 나갈 때는 2부의 SNAT로 출발지가 호스트 IP로 바뀝니다.

네트워크 모드는 격리를 얼마나 할지의 선택이다

bridge는 기본값일 뿐이고, Docker는 컨테이너에 net namespace를 어떻게 줄지 몇 가지 모드를 제공합니다. 자기 namespace를 받되 이름으로 서로 찾을 수 있게 하는 사용자 정의 bridge, 아예 namespace를 나누지 않고 호스트의 네트워크를 그대로 쓰는 host, 루프백만 남기는 none입니다.

모드동작쓰는 곳
bridge (기본)자기 net ns + veth + NAT, 이름 조회 없음단독 컨테이너
사용자 정의 bridge위와 같고 내장 DNS로 이름 조회여러 컨테이너 연결
host호스트 net ns를 그대로 씀NAT 비용이 아까운 프록시
none루프백만외부 통신 없는 일괄 작업

host 모드는 격리를 포기하므로 1부의 포트 충돌이 그대로 돌아옵니다. 포트는 직접 관리해야 합니다.

컨테이너끼리는 사용자 정의 네트워크로 잇는다

$ docker network create app-net
$ docker run -d --name db \
    --network app-net postgres:16
$ docker run -d --name api \
    --network app-net -e DB_HOST=db \
    order-api
$ docker exec api getent hosts db
172.18.0.2      db

주문 API가 같은 서버의 Postgres 컨테이너에 붙으려면 주소가 필요한데, 컨테이너 IP는 재시작마다 바뀔 수 있습니다. 그래서 IP 대신 이름으로 잇습니다.

직접 만든 네트워크(app-net)에서는 Docker의 내장 DNS(127.0.0.11)가 컨테이너 이름을 지금의 IP로 풀어 줍니다. 주문 API는 DB_HOST=db만 알면 됩니다. 기본 bridge에는 이 기능이 없어 사용자 정의 네트워크를 씁니다.

-p는 DNAT 규칙이고, 방화벽보다 앞선다

$ docker run -d -p 8080:8080 order-api
$ sudo iptables -t nat -L DOCKER -n
DNAT tcp dpt:8080 to:172.17.0.2:8080
# 주소 생략 = 0.0.0.0, 외부에도 열림
$ docker run -d -p 127.0.0.1:5432:5432 \
    postgres:16
$ sudo iptables -I DOCKER-USER \
    -p tcp --dport 5432 -j DROP

바깥에서 들어오는 길은 -p 호스트포트:컨테이너포트가 엽니다. 2부에서 예고한 대로 Docker는 nat 표에 DNAT 규칙을 넣어, 호스트 8080으로 온 패킷의 목적지를 컨테이너 IP로 바꿉니다.

이 패킷은 INPUT이 아니라 FORWARD를 지나므로 ufw로 막은 포트도 Docker가 열어 버립니다. 개발용 DB를 -p 5432:5432로 띄운 서버가 인터넷에 노출되는 사고가 여기서 납니다. 127.0.0.1에 묶거나, Docker가 비워 둔 사용자용 체인 DOCKER-USER에 막는 규칙을 넣습니다.

남겨야 할 데이터는 컨테이너 밖에 둔다

3부에서 쓰기 레이어는 느리고 컨테이너와 함께 사라진다고 했습니다. Postgres 컨테이너를 새 버전으로 바꾸는 순간 주문 데이터가 사라지면 안 되므로, 데이터 디렉터리에는 컨테이너 밖의 저장소를 붙여(마운트) 씁니다. 붙이는 방법은 세 가지입니다.

방식실체어울리는 것주의점
volumeDocker가 관리하는 디렉터리DB 데이터, 영속 파일백업은 직접
bind mount호스트의 특정 경로개발 중 소스, 설정 파일UID와 권한 불일치
tmpfs메모리임시 파일, 민감한 캐시메모리 상한에 포함

volume은 남고, bind mount는 권한을 탄다

$ docker run -d \
    -v pgdata:/var/lib/postgresql/data \
    postgres:16
$ docker volume inspect pgdata
$ docker run -d \
    -v "$PWD/conf:/app/conf:ro" \
    order-api
$ docker run -d \
    --tmpfs /tmp:size=64m order-api

첫 줄의 pgdata는 이름 붙인 volume으로, /var/lib/docker/volumes 아래에 생기고 컨테이너를 지워도 남습니다. 새 Postgres 컨테이너에 같은 이름을 붙이면 데이터를 이어받습니다.

bind mount는 호스트 경로를 그대로 보여 주고 :ro로 읽기 전용을 겁니다. 컨테이너 안의 UID로 호스트 파일을 다루므로, 1부의 권한 규칙 때문에 "Permission denied"가 흔합니다. tmpfs는 메모리라 빠르지만 3부의 메모리 상한에 함께 잡힙니다.

로그는 stdout으로, 보관은 드라이버에 맡긴다

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "5"
  }
}

1부에서는 주문 API가 /var/log/api에 파일로 로그를 썼습니다. 컨테이너에서는 파일 대신 표준 출력에 씁니다. 쓰기 층의 파일은 컨테이너와 함께 사라지기 때문입니다. Docker의 로깅 드라이버가 출력을 받아 저장하거나(json-file, local) 외부로 보냅니다(AWS CloudWatch용 awslogs, 수집기 fluentd).

기본 json-file은 회전 설정이 없어 디스크를 끝없이 채웁니다. 2부의 "디스크 100%"가 컨테이너 서버에서 가장 흔히 나는 경로라, 위처럼 크기와 개수를 제한합니다.

재시작 정책은 Docker판 Restart=다

systemd의 Restart=가 맡던 "죽으면 다시 띄우기"는 Docker에서는 --restart 정책이 맡습니다. 차이는 사람이 손으로 멈춘 컨테이너를 서버(데몬) 재시작 뒤에 다시 띄우느냐에 있습니다.

정책다시 시작하는 경우손으로 멈춘 뒤 데몬 재시작
no (기본)하지 않음멈춘 채
on-failure[:5]0이 아닌 종료 코드, 최대 횟수 지정 가능멈춘 채
always항상다시 뜸
unless-stopped항상멈춘 채

재시작 간격은 100ms부터 두 배씩 늘어납니다. 재시작은 같은 서버 안에서만 일어나므로, 서버 자체가 죽었을 때 다른 서버에 띄우는 일은 오케스트레이터의 몫입니다(10장).

PID 1은 시그널도 받고 좀비도 거둬야 한다

$ time docker stop api
real  0m10.4s     # 매번 10초면 의심
$ docker inspect \
    -f '{{.State.ExitCode}}' api
137
# 해결 1: exec form으로 앱을 PID 1에
# 해결 2: 작은 init을 PID 1에
$ docker run --init order-api

docker stop은 1부의 순서대로 PID 1에 SIGTERM, 10초 뒤 SIGKILL을 보냅니다. 그런데 커널은 PID 1이 핸들러를 등록하지 않은 시그널은 기본 동작 없이 무시합니다. shell form의 셸처럼 시그널을 처리하지 않는 프로그램이 PID 1이면 매번 10초 뒤 137로 강제 종료됩니다.

또 PID 1은 고아를 거둘 책임이 있습니다. 자식을 여럿 띄우는 앱이라면 tini 같은 작은 init을 PID 1에 두어 시그널 전달과 좀비 회수를 맡깁니다. --init이 그것입니다.

Compose는 여러 컨테이너를 한 파일로 띄운다

services:
  api:
    build: .
    ports: ["127.0.0.1:8080:8080"]
    environment:
      DB_URL: jdbc:postgresql://db:5432/app
    depends_on:
      db: { condition: service_healthy }
    restart: unless-stopped
  db:
    image: postgres:16
    environment: [POSTGRES_PASSWORD=dev]
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: pg_isready -U postgres
volumes: { pgdata: {} }

지금까지 네트워크 생성, DB 실행, 볼륨, 포트, 재시작 정책을 명령 여러 줄로 쳤습니다. Docker Compose는 이것을 YAML 파일 하나에 선언하고 한 번에 띄우는 도구입니다. 왼쪽 파일은 앞 슬라이드들의 설정을 그대로 옮긴 것입니다.

Compose는 프로젝트 전용 네트워크를 만들어 모든 서비스를 붙이므로, 서비스 이름 db가 곧 호스트 이름입니다. healthcheck는 Dockerfile의 HEALTHCHECK와 같은 일을 합니다.

depends_on은 순서만 정하므로 준비 상태를 기다린다

$ docker compose up -d --build
$ docker compose ps
NAME   STATUS
db     Up 12s (healthy)
api    Up 3s
$ docker compose logs -f api
$ docker compose down     # 볼륨은 남음
$ docker compose down -v  # 볼륨까지

depends_on만 쓰면 db 컨테이너를 먼저 "시작"할 뿐, Postgres가 연결을 받을 준비가 될 때까지 기다리지 않습니다. 그래서 주문 API가 먼저 붙으려다 실패합니다. condition: service_healthy는 db의 헬스 체크가 통과할 때까지 api 시작을 미룹니다.

그래도 DB가 운영 중에 재시작될 수 있으니 앱 스스로 재연결해야 합니다. down -v는 데이터 볼륨까지 지우므로 조심합니다. Compose는 서버 한 대용이고, 여러 서버 운영은 10장의 몫입니다.

컨테이너 안의 root는 호스트의 root다

이제 띄운 컨테이너를 안전하게 만들 차례입니다. 3부에서 Docker는 user namespace를 기본으로 켜지 않는다고 했습니다. 그래서 컨테이너 안에서 root로 돈 프로세스는 호스트에서도 UID 0입니다. namespace와 cgroup이 칸막이를 쳐 주지만, 커널 취약점 하나나 호스트 디렉터리를 잘못 마운트한 설정 하나로 칸막이를 넘으면 호스트 전체가 넘어갑니다.

같은 이유로 1부에서 경고한 docker 그룹이 위험합니다. 이 그룹은 /var/run/docker.sock에 말할 수 있는데, dockerd는 root로 돌므로 docker run -v /:/host처럼 호스트 루트를 마운트한 컨테이너를 띄울 수 있습니다. docker 그룹 가입은 root 권한을 주는 것과 같습니다.

방어의 기본은 칸막이를 넘더라도 얻는 게 없게 하는 것입니다. 앱을 일반 계정으로 돌리고, root의 힘을 잘게 빼고, 파일 시스템을 읽기 전용으로 만듭니다. 다음 슬라이드가 그 옵션들입니다.

실행 옵션으로 칸막이 너머의 이득을 없앤다

$ docker run -d --name api \
    --user 10001:10001 \
    --read-only --tmpfs /tmp \
    --cap-drop ALL \
    --cap-add NET_BIND_SERVICE \
    --security-opt no-new-privileges \
    --memory 1g --cpus 1 \
    --pids-limit 512 \
    order-api:3f9c2e1

--user는 Dockerfile의 USER처럼 일반 UID로 돌립니다. --read-only는 루트 파일 시스템을 읽기 전용으로 만들어 침입자가 도구를 내려받지 못하게 하고, 꼭 써야 하는 /tmp만 tmpfs로 엽니다.

no-new-privileges는 1부의 setuid로 권한을 올리는 길을 막습니다. 자원 상한은 3부의 cgroup 값으로, 한 컨테이너가 서버를 잠식하거나 프로세스를 무한히 만드는 것을 막습니다. --cap-*는 다음 슬라이드입니다.

capabilities는 root 권한의 조각이다

root의 힘은 한 덩어리가 아닙니다. Linux는 이를 40여 개의 capabilities로 쪼개, 프로세스마다 필요한 조각만 줄 수 있게 합니다. 예를 들어 1024 미만 포트에서 듣는 권한만 따로 줄 수 있습니다. Docker는 기본으로 그중 십여 개만 남기고 나머지를 뺍니다.

capability허용하는 일Docker 기본
NET_BIND_SERVICE1024 미만 포트 바인딩허용
CHOWN, SETUID소유자 변경, UID 전환허용
NET_ADMIN네트워크 설정, iptables 변경제외
SYS_ADMIN마운트 등 사실상 root 전부제외, 절대 주지 말 것

가장 안전한 방법은 --cap-drop ALL 후 꼭 필요한 것만 더하는 것입니다. --privileged는 모든 capability와 장치 접근을 주어 격리를 사실상 없애므로 운영 앱에는 쓰지 않습니다.

비밀은 이미지에 굽지 말고 실행할 때 주입한다

# 나쁜 예: 이미지 이력에 영원히 남음
ENV DB_PASSWORD=s3cret
COPY .npmrc /root/.npmrc

# 빌드에만 필요한 비밀: BuildKit secret
RUN --mount=type=secret,id=npmrc,\
target=/root/.npmrc npm ci
$ docker build \
    --secret id=npmrc,src=.npmrc .
$ docker history --no-trunc order-api

이미지는 레지스트리를 거쳐 여러 사람과 서버로 퍼집니다. ENV, ARG, 복사한 파일은 docker history나 레이어 파일에서 누구나 꺼낼 수 있고, 뒤에서 지워도 앞 레이어에 남습니다.

실행용 비밀은 1부의 EnvironmentFile처럼 실행 시 환경 변수나 파일 마운트로 넣습니다(K8s Secret은 10장, AWS Secrets Manager는 16장). 빌드에만 필요한 비밀은 레이어에 남지 않게 잠깐 붙였다 떼는 BuildKit secret을 씁니다.

비밀을 지켜도, 베이스 이미지 안의 오래된 라이브러리에 알려진 취약점이 있으면 뚫립니다. 공개된 취약점에는 CVE라는 "CVE-연도-일련번호" 형식의 공통 번호가 붙습니다(왼쪽 출력은 형식만 보인 예시라 번호를 비워 두었습니다). Trivy 같은 스캐너는 이미지의 패키지 목록을 취약점 데이터베이스와 대조해 심각도별로 보여 줍니다.

대응은 앞에서 고른 베이스로 돌아갑니다. 담은 것이 적은 slim이나 distroless로 바꾸면 검사 대상 자체가 줄고, 베이스 태그를 주기적으로 새로 받아 다시 빌드하면 패치가 들어옵니다. CI에서 CRITICAL이 있으면 배포를 막는 단계는 11장에서 다룹니다.

디버깅은 logs와 inspect에서 시작한다

$ docker ps -a       # 죽은 것까지
$ docker logs --tail 100 -f api
$ docker exec -it api sh
$ docker inspect -f \
  '{{.State.ExitCode}} {{.State.OOMKilled}}' api
$ docker stats --no-stream
$ docker events --since 10m
# 셸 없는 이미지: 옆에 붙어서 보기
$ docker run --rm -it \
    --network container:api nicolaka/netshoot

컨테이너가 이상하면 logs로 앱이 남긴 말을, inspect로 종료 코드와 OOM 여부, 환경 변수와 마운트를, stats로 실시간 CPU와 메모리를, events로 언제 죽고 재시작됐는지를 봅니다. exec는 떠 있는 컨테이너 안에서 명령을 실행합니다.

distroless처럼 셸이 없으면 exec가 막힙니다. 이때는 2부의 도구(curl, tcpdump)를 담은 이미지 netshoot을 대상의 net namespace에 붙여 띄웁니다.

장애 사례: 로그 없이 사라지는 주문 API

  1. 증상

    주문 API 컨테이너가 하루 몇 번 재시작되는데, 앱 로그는 정상 요청 기록에서 뚝 끊깁니다.

  2. 확인

    inspect 결과 종료 코드 137, OOMKilled: true입니다.

  3. 원인

    상한 1GB에 -Xmx900m. 힙 밖 메모리를 더하면 상한을 넘습니다.

  4. 조치

    힙을 상한의 70% 안팎으로 낮추고, 스레드 수와 다이렉트 버퍼도 함께 점검합니다.

이 장애가 까다로운 이유는 GC 로그도 힙 사용량도 멀쩡하다는 데 있습니다. JVM은 힙에 여유가 있었지만, 커널은 cgroup 전체 사용량만 보고 SIGKILL을 보냈으니 앱은 마지막 말을 남길 틈이 없었습니다.

2부의 OOM Killer, 3부의 memory.max, 4부의 종료 코드와 inspect를 함께 알아야 "앱 버그"가 아니라 자원 설정 문제로 바로 좁힐 수 있습니다.

정리

  • 서버 운영의 기본은 파일, 권한, 프로세스, 시그널입니다. 주문 API는 전용 계정과 systemd로 돌리고, 종료는 SIGTERM 후 SIGKILL 두 단계로 이뤄집니다.
  • 명령어의 숫자는 커널이 센 값입니다. load는 줄의 길이, 메모리는 available, 디스크는 용량과 inode, fd는 띄운 주체의 한도를 봅니다.
  • 컨테이너는 namespace로 격리하고 cgroup으로 제한한 프로세스입니다. 커널을 공유해 VM보다 가볍고, CPU 상한은 스로틀링, 메모리 상한은 OOM으로 나타납니다.
  • 이미지는 OverlayFS 레이어의 겹침입니다. 명령 순서, 멀티 스테이지, 레이어드 JAR로 작고 캐시가 잘 맞는 이미지를 만듭니다.
  • 안전한 컨테이너는 비 root, 최소 capability, 비밀 주입, exec form PID 1입니다. 문제는 종료 코드와 inspect에서 시작해 좁힙니다.

스스로 점검 (1)

  1. chmod 644인 파일을 다른 사용자가 못 읽는다면 어디를 봐야 하나요?

    상위 디렉터리들의 x 권한입니다. 디렉터리에 들어갈 권한이 없으면 파일 권한과 관계없이 경로를 따라갈 수 없습니다.

  2. /etc/security/limits.conf에서 nofile을 올렸는데 systemd로 띄운 앱의 한도가 그대로입니다. 왜일까요?

    limits.conf는 로그인 세션(PAM)에 적용되고 systemd 서비스는 유닛의 LimitNOFILE을 따릅니다. 유닛 파일을 고치고 daemon-reload 후 재시작합니다.

  3. 코어 8개 서버의 load가 20인데 CPU idle이 70%입니다. 무엇을 의심하나요?

    Linux load에는 D 상태 작업이 포함되므로 디스크나 네트워크 파일 시스템의 I/O 대기입니다. vmstat의 b와 wa, iostat의 await를 확인합니다.

  4. 로그 파일을 지웠는데 df 사용량이 줄지 않습니다. 이유와 확인 방법은?

    프로세스가 그 파일을 열고 있어 inode가 해제되지 않았습니다. lsof +L1로 찾아 프로세스를 재시작하거나 fd를 비웁니다.

스스로 점검 (2)

  1. nc -zv의 결과가 refused일 때와 timed out일 때 의심할 곳은 어떻게 다른가요?

    refused는 서버까지 닿았지만 그 포트에서 듣는 프로세스가 없는 것이라 앱과 바인드 주소를 봅니다. timed out은 중간에서 패킷이 버려진 것이라 방화벽과 보안 그룹을 봅니다.

  2. CPU 상한 1코어 컨테이너의 평균 CPU가 40%인데 p99 지연이 튑니다. 원인 후보는?

    여러 스레드가 주기 초반에 할당량을 다 써서 스로틀링되는 경우입니다. cpu.stat의 nr_throttled를 보고 상한을 올리거나 스레드 수를 맞춥니다.

  3. Dockerfile에서 RUN rm으로 큰 파일을 지웠는데 이미지가 줄지 않는 이유는?

    레이어는 겹치기만 해서 삭제는 위층의 whiteout 표시일 뿐입니다. 파일을 만든 같은 RUN에서 지우거나 멀티 스테이지로 결과물만 옮깁니다.

  4. docker stop이 매번 10초 걸리고 종료 코드가 137입니다. 무엇을 고치나요?

    PID 1이 SIGTERM을 처리하지 않는 것입니다. shell form을 exec form으로 바꾸거나 스크립트 끝에 exec를 쓰고, 필요하면 tini를 PID 1에 둡니다.

스스로 점검 (3)

  1. ufw로 5432를 막았는데 -p 5432:5432로 띄운 DB가 외부에서 접속됩니다. 왜일까요?

    Docker의 포트 매핑은 nat 표의 DNAT와 FORWARD 체인으로 처리되어 ufw의 INPUT 규칙을 지나지 않습니다. 127.0.0.1에 바인딩하거나 DOCKER-USER 체인에서 막습니다.

  2. Kubernetes 노드에 Docker가 없어도 Docker로 빌드한 이미지가 도는 이유는?

    이미지는 OCI 표준 형식이고 kubelet은 CRI로 containerd 같은 런타임과 말하기 때문입니다. 빌드 도구와 실행 런타임이 표준으로 분리되어 있습니다.
