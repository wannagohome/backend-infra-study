1부

코드가 운영에 닿기까지

10장에서 Kubernetes는 원하는 상태를 받으면 그대로 맞춰 준다고 했습니다. 이 장은 그 원하는 상태를 누가, 어떤 검증을 거쳐, 어떻게 바꾸는지를 다룹니다.

커밋은 다섯 관문을 지나 운영에 닿는다

  1. 커밋, PR작은 단위로 리뷰
  2. CI빌드, 테스트, 스캔
  3. 아티팩트이미지 한 번만 빌드
  4. 환경 승격dev, stage, prod
  5. 무중단 교체배포 전략, 롤백

개발자가 코드를 고친 순간부터 사용자가 그 코드를 쓰는 순간까지 사이에는 사람이 손으로 하면 반드시 실수가 나는 일이 줄지어 있습니다. 빌드 명령을 빠뜨리거나, 테스트하지 않은 파일을 올리거나, 서버 한 대만 옛 버전으로 남기는 식입니다.

CI/CD는 이 길 전체를 매번 같은 방식으로 자동 실행되는 파이프라인으로 바꾸는 일입니다. 1부는 각 관문이 무엇이고 왜 필요한지, 2부는 그 도구와 배포 전략, IaC의 동작 원리, 3부는 운영에서 자주 터지는 문제를 봅니다.

merge, rebase, squash는 기록의 모양이 다르다

방식무엇을 하나남는 기록주의점
merge두 줄기를 합치는 병합 커밋 생성분기와 합류가 그대로기록이 갈라져 복잡
rebase내 커밋을 최신 main 뒤로 다시 쌓음한 줄로 곧은 기록공유 브랜치에선 금지
squashPR의 커밋을 하나로 압축PR당 커밋 하나중간 커밋 정보 사라짐

rebase는 커밋을 새로 만들어 해시가 바뀝니다. 이미 남이 받아 간 브랜치를 rebase하고 강제로 push하면 동료의 기록과 어긋나므로, 혼자 쓰는 브랜치에서만 씁니다. 많은 팀이 PR은 squash 병합으로 main을 깔끔하게 유지하고, 작업 중에는 rebase로 main을 따라갑니다.

PR은 합치기 전에 사람과 기계가 함께 본다

PR은 "이 브랜치를 main에 합쳐 달라"는 요청이자 리뷰의 단위입니다. 기계는 CI로 빌드와 테스트, 정적 분석 결과를 PR에 붙이고, 사람은 설계와 의도, 놓친 경우를 봅니다.

리뷰 품질은 PR 크기에 크게 좌우됩니다. 수천 줄짜리 PR은 대충 승인되기 쉽고, 문제가 생겨도 원인을 좁히기 어렵습니다. 작게 자주 올리는 습관이 뒤에 나올 브랜치 전략과 배포 주기의 바탕입니다.

main을 지키는 장치는 브랜치 보호 규칙입니다. 이 규칙으로 다음을 강제합니다.

  • CI 검사(status check)가 통과해야만 병합할 수 있게 합니다.
  • 지정한 인원 이상의 승인과, 코드 소유자(CODEOWNERS)의 리뷰를 요구합니다.
  • main에 직접 push와 강제 push를 막아 모든 변경이 PR을 거치게 합니다.

브랜치 전략은 배포 주기에 맞춘다

전략구조브랜치 수명맞는 팀
Git Flowmain, develop, feature, release, hotfix며칠~몇 주정해진 주기로 릴리스
GitHub Flowmain + 짧은 feature 브랜치, PR하루~며칠수시 배포하는 웹 서비스
Trunk-Basedmain(trunk)에 하루 여러 번 병합몇 시간 이내CI 성숙, Feature Flag 사용

Git Flow는 모바일 앱이나 설치형 소프트웨어처럼 버전을 묶어 내보내고 여러 버전을 동시에 유지보수할 때 잘 맞습니다. 하루에도 여러 번 배포하는 웹 서비스에서는 develop과 release 브랜치가 오히려 병합 대기열이 되어, 대부분 GitHub Flow나 Trunk-Based로 갑니다.

브랜치가 오래 살수록 병합은 비싸진다

브랜치가 갈라져 있는 동안 main도 계속 바뀝니다. 2주 동안 따로 작업한 브랜치는 2주 치 차이를 한꺼번에 맞춰야 하고, 충돌을 푸는 사람은 양쪽 의도를 모두 이해해야 합니다. 이것을 흔히 "병합 지옥"이라 부릅니다.

Trunk-Based는 이 비용을 작은 변경을 자주 합쳐서 매번 조금씩 치르는 방식입니다. 그런데 아직 완성되지 않은 기능도 main에 들어가게 됩니다.

그래서 Trunk-Based는 두 장치와 함께 씁니다.

  • Feature Flag: 미완성 코드는 main에 합치되 플래그로 꺼 둡니다. 배포는 됐지만 사용자에게는 보이지 않습니다(2부에서 자세히).
  • 빠르고 믿을 만한 CI: 하루 수십 번 병합하려면 검증이 10분 안팎으로 끝나야 하고, 실패하면 바로 고칩니다.

CI는 자주 합치고 매번 검증하는 습관이다

지속적 통합(CI)은 원래 도구가 아니라 습관의 이름입니다. 모든 개발자가 하루에도 여러 번 main에 코드를 합치고, 합칠 때마다 자동으로 빌드와 테스트를 돌려 "main은 언제나 동작한다"는 상태를 지킵니다.

핵심은 피드백 시간입니다. 충돌이나 버그를 방금 짠 코드에서 찾으면 몇 분이면 고치지만, 2주 뒤에 찾으면 원인을 찾는 데만 반나절이 걸립니다.

그래서 CI가 제대로 돌아가는 팀에는 공통 규칙이 있습니다.

  • main이 빨갛게 깨지면 새 기능보다 복구가 먼저입니다.
  • 로컬에서 돌린 결과가 아니라 깨끗한 CI 환경의 결과를 믿습니다.
  • CI가 느리면 사람들이 기다리지 않고 합치므로, 속도도 품질의 일부로 관리합니다.

Delivery는 버튼을 남기고 Deployment는 없앤다

구분지속적 전달(Delivery)지속적 배포(Deployment)
운영 반영사람이 승인 버튼을 누름테스트 통과 시 자동
보장하는 것언제든 배포 가능한 상태모든 변경이 곧바로 운영에
필요한 전제자동화된 빌드와 테스트강한 테스트, 자동 롤백
어울리는 곳규제, 출시 시점 조율 필요작은 변경을 수시 배포

CD라는 약어는 두 가지를 모두 가리킵니다. 지속적 전달은 운영 배포 직전까지 자동화하고 마지막 결정을 사람이 내립니다. 지속적 배포는 그 결정까지 파이프라인에 맡깁니다. 차이는 기술보다 테스트와 관측을 얼마나 믿을 수 있느냐에 있습니다.

파이프라인은 싼 검사부터 비싼 검사 순으로

  1. 빌드컴파일, 의존성 해석
  2. 테스트단위, 통합
  3. 분석, 스캔린트, SAST, 의존성
  4. 아티팩트이미지 빌드, 스캔, 푸시
  5. 배포, 확인스모크 테스트

단계는 빨리 실패할 수 있는 것부터 배치합니다. 컴파일 오류는 몇십 초 안에 드러나지만 통합 테스트는 몇 분이 걸립니다. 앞 단계가 실패하면 뒤 단계는 돌지 않으므로, 싼 검사를 앞에 둘수록 평균 피드백 시간이 짧아집니다.

서로 의존하지 않는 단계(예: 린트와 단위 테스트)는 병렬로 돌립니다. 이어지는 슬라이드에서 각 단계가 무엇을 잡는지 봅니다.

테스트는 아래가 넓은 피라미드로 쌓는다

단위 테스트는 클래스나 함수 하나를 외부 의존 없이 검사합니다. 밀리초 단위로 끝나므로 수천 개를 매 커밋마다 돌릴 수 있습니다.

통합 테스트는 실제 DB나 메시지 브로커와 함께 돌립니다. CI에서는 Testcontainers로 MySQL 컨테이너를 띄워 실제 SQL을 검증하는 방식이 흔합니다. E2E 테스트는 배포된 시스템 전체를 사용자처럼 호출합니다.

위로 갈수록 실제와 가깝지만 느리고 잘 깨집니다. 그래서 단위가 가장 많고, 통합은 적당히, E2E는 핵심 흐름 몇 개만 두는 테스트 피라미드가 권장됩니다.

E2E가 잔뜩 쌓인 역삼각형 구조가 되면 CI가 30분을 넘기고, 원인이 불분명한 실패가 늘어 결국 아무도 결과를 믿지 않게 됩니다. 이 문제는 3부의 flaky 테스트에서 다시 봅니다.

정적 분석과 보안 스캔은 실행 없이 잡는다

검사무엇을 보나대표 도구
린트, 정적 분석코드 스타일, 버그 패턴, 복잡도Checkstyle, SpotBugs, SonarQube
SASTSQL Injection 같은 취약 코드 패턴CodeQL, Semgrep
의존성 스캔(SCA)라이브러리의 알려진 CVEDependabot, OWASP Dependency-Check
이미지 스캔베이스 이미지 OS 패키지 CVETrivy, Grype, ECR 스캔
시크릿 스캔커밋에 섞인 키, 토큰gitleaks, GitHub secret scanning

SAST는 내 코드를, SCA는 내가 가져다 쓴 코드를 봅니다. 실제 애플리케이션은 코드의 대부분이 라이브러리라서, Log4Shell 같은 사고는 SCA가 잡습니다.

스캔 결과는 차단 기준을 정해야 쓸모 있다

스캐너를 처음 붙이면 경고가 수백 개 쏟아집니다. 전부 빌드 실패로 만들면 아무도 배포하지 못하고, 전부 경고로만 두면 아무도 보지 않습니다.

그래서 보통 심각도로 차단선을 긋습니다. 예를 들어 "고칠 수 있는 버전이 있는 Critical, High CVE가 있으면 실패, 나머지는 리포트만"처럼 정하고, 기존 경고는 기준선으로 묶어 새로 생긴 것만 막습니다.

스캔은 한 번으로 끝나지 않습니다. 어제 깨끗했던 이미지도 오늘 새 CVE가 공개되면 취약해집니다. 그래서 레지스트리에 올라간 이미지를 주기적으로 다시 스캔하고, 의존성 업데이트 PR을 자동으로 만드는 봇(Dependabot, Renovate)을 함께 씁니다.

취약점 개념 자체(SQL Injection, XSS 등)는 7장에서 다뤘습니다.

이미지는 한 번만 빌드하고 환경마다 승격한다

아티팩트는 빌드의 결과물입니다. JAR 파일이나 컨테이너 이미지가 여기에 해당하고, 레지스트리나 저장소에 버전을 붙여 보관합니다.

핵심 원칙은 stage에서 검증한 바로 그 이미지를 prod에 내보내는 것입니다. 환경마다 다시 빌드하면 그사이 의존성이나 베이스 이미지가 바뀌어, 테스트한 것과 다른 바이너리가 나갈 수 있습니다.

환경 차이는 이미지 밖에서 주입하는 설정으로만 만듭니다.

스모크 테스트는 배포 직후의 첫 숨 확인

배포가 "성공"했다는 것은 새 Pod가 떴다는 뜻일 뿐, 서비스가 제대로 동작한다는 뜻은 아닙니다. 설정이 잘못되어 결제 API만 500을 낼 수도 있습니다.

스모크 테스트는 배포 직후 핵심 경로 몇 개만 실제로 호출해 보는 짧은 검사입니다. 이름은 전자 기기에 전원을 넣었을 때 연기가 나는지부터 본다는 데서 왔습니다.

좋은 스모크 테스트는 다음 조건을 갖춥니다.

  • 1~2분 안에 끝나고, 실패하면 파이프라인이 롤백이나 알림으로 이어집니다.
  • 헬스 체크만이 아니라 로그인, 주요 조회처럼 DB와 외부 연동을 실제로 거치는 경로를 봅니다.
  • 운영 데이터를 오염시키지 않도록 읽기 위주이거나 테스트 계정을 씁니다.

태그는 사람용 SemVer와 기계용 SHA

SemVer는 MAJOR.MINOR.PATCH 형식입니다. 하위 호환이 깨지면 MAJOR, 기능이 추가되면 MINOR, 버그만 고치면 PATCH를 올립니다. 라이브러리나 외부에 공개하는 API처럼 사용자가 버전을 보고 판단해야 할 때 씁니다.

서비스 배포용 이미지에는 git 커밋 SHA를 태그로 붙이는 방식이 흔합니다. 태그만 보고 어떤 코드인지 바로 추적할 수 있기 때문입니다.

latest 태그로 배포하면 안 되는 이유는 셋입니다.

  • 같은 이름이 계속 다른 이미지를 가리켜, 지금 운영에 무엇이 떠 있는지 알 수 없습니다.
  • 노드마다 받은 시점이 달라 같은 Deployment 안에 서로 다른 버전이 섞입니다.
  • 롤백할 "이전 버전"의 이름이 없습니다.

태그도 덮어쓸 수 있으므로 가장 엄격하게는 digest(@sha256:…)로 고정합니다(9장).

환경은 나누고, 차이는 설정으로만 둔다

환경목적데이터배포 방식
dev개발 중 기능 통합 확인가짜 데이터main 병합 시 자동
stage운영과 같은 구성으로 최종 검증익명화한 운영 유사 데이터자동 또는 버튼
prod실제 사용자실데이터, 접근 통제승인 후 배포

stage가 운영과 다르게 생기면(DB 버전, 인스턴스 크기, 네트워크 경로) stage에서 통과한 것이 운영에서 깨집니다. 환경 사이의 차이를 줄이는 것이 12-Factor의 "개발/운영 일치" 원칙이고, 그 차이를 코드로 고정하는 도구가 2부의 IaC입니다.

#  일반 설정  → 환경 변수, ConfigMap

코드에는 설정의 이름과 기본값만 두고, 실제 값은 실행 환경이 주입합니다. Spring은 환경 변수, 프로필별 파일, 외부 설정 순으로 값을 덮어쓰므로 같은 JAR가 어디서든 뜹니다.

비밀번호와 API 키는 이미지나 Git에 넣지 않습니다. Kubernetes Secret(10장), AWS Secrets Manager나 Parameter Store 같은 외부 저장소에서 실행 시점에 받습니다.

2부

파이프라인 도구는 어떻게 동작하나

가장 널리 쓰이는 GitHub Actions를 기준으로 워크플로가 어떤 단위로 나뉘고, 어디서 실행되고, 어떻게 비밀과 권한을 다루는지 봅니다.

기초 원리 여기부터는 도구의 실행 구조, 배포 전략의 동작, IaC의 상태 관리를 다룹니다.

워크플로는 job으로, job은 step으로 나뉜다

워크플로는 .github/workflows/ 아래 YAML 파일 하나이고, 트리거(push, PR 등)가 일어나면 실행됩니다.

워크플로는 여러 job으로 나뉘고, job마다 새 러너(가상 머신) 하나를 받습니다. 그래서 job끼리는 기본적으로 병렬로 돌고 파일 시스템을 공유하지 않습니다. 순서가 필요하면 needs로 잇습니다.

job 안의 step은 같은 러너에서 위에서 아래로 차례로 실행됩니다.

트리거가 워크플로를 언제 돌릴지 정한다

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
    paths-ignore: ['docs/**', '**.md']
  workflow_dispatch:        # 수동 실행 버튼
  schedule:
    - cron: '0 18 * * *'      # UTC 기준

concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true

pull_request는 PR이 열리거나 커밋이 추가될 때, push는 브랜치에 커밋이 들어올 때 돕니다. paths 필터로 문서만 바뀐 커밋은 건너뛸 수 있습니다.

schedule의 cron은 UTC 기준이라 한국 시간 새벽 3시는 18시로 씁니다. concurrency는 같은 그룹의 실행이 겹치지 않게 해서, 배포 두 개가 동시에 도는 사고를 막습니다.

러너는 매번 새로 받는 깨끗한 머신이다

러너는 job을 실제로 실행하는 머신입니다. runs-on: ubuntu-latest처럼 쓰면 GitHub이 관리하는 가상 머신을 job마다 새로 받고, 끝나면 버립니다. 이전 실행의 찌꺼기가 없으니 결과가 재현 가능하지만, 매번 의존성을 처음부터 받아야 합니다.

job에는 timeout-minutes를 꼭 둡니다. 기본값은 360분이라 멈춘 테스트 하나가 6시간 동안 러너를 붙잡습니다.

상태job마다 새 VM재사용될 수 있음

matrix는 job 하나를 조합 수만큼 복제한다

jobs:
  test:
    runs-on: ${{ matrix.os }}
    timeout-minutes: 20
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        java: ['17', '21']
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: ${{ matrix.java }}
      - run: ./gradlew test

운영체제 2개와 Java 2개를 곱해 job 4개가 병렬로 생깁니다. 라이브러리를 여러 런타임에서 검증하거나, 큰 테스트 묶음을 조각으로 나눠 동시에 돌릴 때 씁니다.

fail-fast의 기본값은 true라 하나가 실패하면 나머지를 취소합니다. 어떤 조합에서만 깨지는지 보고 싶으면 false로 둡니다. uses는 남이 만든 액션을 가져다 쓰는 step입니다.

cache는 속도용, artifact는 결과 전달용

- uses: actions/cache@v6
  with:
    path: ~/.gradle/caches
    key: gradle-${{ hashFiles('**/*.gradle*') }}
    restore-keys: gradle-

- run: ./gradlew bootJar

- uses: actions/upload-artifact@v7
  with:
    name: app-jar
    path: build/libs/*.jar
    retention-days: 7

캐시는 다음 실행을 빠르게 하려고 의존성 같은 재생성 가능한 파일을 보관합니다. 키가 정확히 맞으면 복원하고, 없으면 restore-keys의 접두어로 가장 가까운 것을 찾습니다. 빌드 파일이 바뀌면 해시가 달라져 새 캐시가 생깁니다.

아티팩트는 빌드 결과물을 job 사이에 넘기거나 사람이 내려받게 남깁니다. 캐시는 없어도 빌드가 되고, 아티팩트는 없으면 다음 단계가 못 돕니다.

secrets는 가려지고 environment는 문을 단다

deploy:
  needs: build
  runs-on: ubuntu-latest
  environment: production
  steps:
    - run: ./deploy.sh
      env:
        SLACK_URL: ${{ secrets.SLACK_WEBHOOK }}

시크릿은 저장소, 조직, environment 단위로 암호화해 저장하고, 로그에 값이 찍히면 ***로 가립니다. 포크에서 온 PR 워크플로에는 시크릿이 전달되지 않습니다.

environment는 배포 대상에 보호 규칙을 붙입니다. 지정한 리뷰어(최대 6명 중 1명)의 승인, 대기 시간, 배포 가능한 브랜치 제한을 걸 수 있고, 승인 전에는 그 환경의 시크릿을 읽을 수 없습니다. 지속적 전달의 "버튼"이 바로 이것입니다.

장기 Access Key 대신 OIDC로 빌려 쓴다

CI가 AWS에 배포하려면 자격 증명이 필요합니다. 예전에는 IAM 사용자의 Access Key를 시크릿에 넣었지만, 이 키는 만료되지 않아 유출되면 누군가 지울 때까지 계속 쓸 수 있습니다.

OIDC 방식에서는 GitHub이 실행마다 "이 실행은 어느 저장소, 어느 브랜치의 워크플로다"라고 서명한 토큰(JWT)을 발급합니다. AWS는 이 서명을 확인하고 몇십 분~1시간짜리 임시 자격 증명을 내줍니다.

그래서 저장소에 보관할 키 자체가 사라집니다. 유출될 것이 없고, 탈취돼도 짧은 시간이 지나면 쓸모가 없습니다.

AWS 쪽에서는 IAM 역할의 신뢰 정책에 "GitHub OIDC 공급자가 발급했고, 특정 저장소와 브랜치의 토큰일 때만 이 역할을 맡게 허용"이라고 적습니다. 신뢰 정책과 AssumeRole의 원리는 12장에서 다룹니다.

OIDC 토큰은 STS에서 임시 키로 바뀐다

러너GitHub, AWS
id-token: write 토큰 요청 GitHub OIDC 공급자
JWT sub=repo:org/api:ref:… 서명됨
AssumeRoleWithWebIdentity JWT AWS STS
서명, aud, sub를 신뢰 정책과 대조
임시 키 자격 증명만료 시각이 있는 키 세 개

워크플로에는 permissions: id-token: write가 있어야 토큰을 요청할 수 있습니다. 이 권한은 토큰을 받을 권한일 뿐 저장소를 수정할 권한이 아닙니다.

신뢰 정책의 sub 조건을 repo:org/*처럼 넓게 쓰면 조직의 아무 저장소나 운영 역할을 맡을 수 있으니, 저장소와 브랜치(또는 environment)까지 좁힙니다.

빌드부터 ECR 푸시까지 한 워크플로로

permissions: { id-token: write, contents: read }
jobs:
  image:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v7
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci
          aws-region: ap-northeast-2
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - run: |
          REG=${{ steps.ecr.outputs.registry }}
          IMG=$REG/api:${{ github.sha }}
          docker build -t $IMG . && docker push $IMG

체크아웃 다음 step이 OIDC로 역할을 맡고, 그다음 step이 그 임시 자격 증명으로 ECR에 로그인합니다. 이미지 태그는 커밋 SHA입니다.

워크플로 맨 위의 permissions는 이 실행이 받는 GITHUB_TOKEN 권한을 필요한 만큼만 남깁니다. ECR 자체의 설정은 14장, 배포를 AWS 도구로 이어가는 방법은 18장에서 다룹니다.

남이 만든 액션은 커밋 SHA로 고정한다

uses: 누군가/액션@v4의 v4는 Git 태그라서 작성자가 언제든 다른 커밋으로 옮길 수 있습니다. 액션 저장소가 탈취되면 태그가 악성 코드로 바뀌고, 그 액션을 쓰는 모든 워크플로가 다음 실행 때 그 코드를 돌립니다.

실제로 2025년 3월 널리 쓰이던 tj-actions/changed-files의 태그가 바뀌어, 수많은 저장소의 CI 로그에 시크릿이 찍혀 나간 사고가 있었습니다.

그래서 외부 액션은 @<40자리 커밋 SHA>로 고정하고, 업데이트는 Dependabot이 만든 PR로 리뷰합니다.

또 하나 위험한 트리거가 pull_request_target입니다. 포크 PR에도 시크릿과 쓰기 권한을 주는 기본 브랜치 맥락에서 돌기 때문에, 여기서 PR의 코드를 체크아웃해 실행하면 외부인이 시크릿을 빼 갈 수 있습니다.

Jenkins는 직접 운영하는 범용 자동화 서버

pipeline {
  agent { label 'docker' }
  stages {
    stage('Test')  { steps { sh './gradlew test' } }
    stage('Image') {
      steps { sh "docker build -t api:${GIT_COMMIT} ." }
    }
    stage('Deploy') {
      input { message '운영에 배포할까요?' }
      steps { sh './deploy.sh prod' }
    }
  }
}

Jenkins는 컨트롤러가 작업을 계획하고 에이전트(빌드 머신)가 실행하는 구조의 오픈소스 서버입니다. 파이프라인을 Jenkinsfile로 저장소에 함께 둡니다.

사내망 안에서 자유롭게 확장할 수 있는 대신, 서버와 수많은 플러그인의 업그레이드, 보안 패치, 백업을 팀이 직접 떠안습니다. 새로 시작한다면 관리형 CI를 먼저 검토하는 경우가 많습니다.

파이프라인 시간은 캐시와 병렬화로 줄인다

먼저 각 step의 소요 시간을 보고 가장 긴 것부터 줄입니다. Dockerfile의 명령 순서가 레이어 캐시 적중률을 정한다는 점(9장)은 CI에서도 그대로 적용됩니다. 의존성 설치를 소스 복사보다 앞에 두면 코드만 바뀐 커밋은 의존성 레이어를 재사용합니다.

2부

멈추지 않고 새 버전으로 바꾸는 법

이미지가 준비됐다면 남은 일은 실행 중인 옛 버전을 새 버전으로 교체하는 것입니다. 교체 방식마다 비용, 롤백 속도, 위험이 다릅니다.

무중단 배포가 어려운 건 두 버전이 겹쳐서다

서버 한 대를 끄고 새 버전을 켜면 그사이 요청은 모두 실패합니다. 이것을 피하려면 옛 버전이 요청을 받는 동안 새 버전을 띄워야 하고, 그러면 잠시라도 두 버전이 동시에 운영됩니다.

두 버전이 겹치는 동안에는 같은 DB, 같은 캐시, 같은 메시지 큐를 함께 씁니다. 요청 하나가 v1으로, 바로 다음 요청이 v2로 갈 수도 있습니다.

그래서 배포 전략은 결국 세 질문에 대한 선택입니다.

  • 공존 시간을 얼마나 짧게, 혹은 얼마나 통제하며 가져갈 것인가.
  • 문제가 생겼을 때 몇 명의 사용자가 영향을 받는가.
  • 되돌리는 데 얼마나 걸리고, 그동안 자원을 얼마나 더 쓰는가.

어느 전략을 고르든 공존 자체를 견디는 장치(호환되는 스키마, 우아한 종료)는 따로 필요합니다.

Recreate: 모두 내리고 새로 올린다

  1. v1 전부 종료

    모든 인스턴스를 내립니다. 이때부터 서비스 중단.

  2. 공백

    새 버전이 뜰 때까지 요청이 실패합니다.

  3. v2 전부 기동

    준비가 끝나면 서비스가 재개됩니다.

Recreate는 가장 단순한 방식입니다. 다운타임이 생기지만 두 버전이 절대 겹치지 않는다는 장점이 있습니다.

그래서 두 버전이 동시에 떠 있으면 안 되는 경우에 씁니다. 예를 들어 한 번에 하나의 프로세스만 써야 하는 볼륨을 쓰거나, 호환되지 않는 스키마 변경을 점검 시간에 한꺼번에 할 때입니다. Kubernetes Deployment에서는 strategy.type: Recreate로 지정합니다.

Rolling: 조금씩 바꿔 끼운다

  1. 새 인스턴스 추가

    허용된 여유분만큼 v2를 먼저 띄웁니다.

  2. 준비 확인

    헬스 체크를 통과한 v2만 트래픽을 받습니다.

  3. 옛 인스턴스 제거

    허용된 범위 안에서 v1을 하나씩 내립니다.

  4. 반복

    모두 v2가 될 때까지 되풀이합니다.

Rolling은 인스턴스를 몇 개씩 차례로 교체합니다. 추가 자원이 적게 들어 가장 널리 쓰이고, Kubernetes Deployment의 기본 전략입니다. 교체 속도를 정하는 maxSurge와 maxUnavailable의 동작은 10장에서 봤습니다.

약점은 롤백입니다. 되돌리려면 반대 방향으로 다시 굴려야 해서 느리고, 배포 내내 두 버전이 섞여 있으며, 이미 교체된 비율만큼 사용자가 영향을 받습니다.

Blue-Green: 통째로 준비하고 한 번에 전환

운영 중인 Blue 옆에 같은 규모의 Green(v2)을 띄워 검증한 뒤, 로드 밸런서나 Service가 가리키는 대상을 한 번에 Green으로 돌립니다.

Blue를 남겨 두면 롤백은 대상을 되돌리는 것 한 번입니다. 대신 전환 동안 자원이 두 배 들고, 두 환경이 같은 DB를 쓰므로 스키마 호환은 여전히 필요합니다.

Blue-Green의 함정은 전환 순간에 있다

전환은 한 번이지만 전환 순간 모든 사용자가 새 버전을 만납니다. Green이 검증 환경에서 멀쩡했어도 실제 부하에서 처음 문제가 드러나면 영향은 전체에 미칩니다.

또 Green은 막 뜬 상태라 JVM 워밍업, 커넥션 풀, 로컬 캐시가 비어 있습니다. 전체 트래픽을 한꺼번에 받으면 첫 몇 분간 지연이 튑니다.

운영에서는 다음을 함께 챙깁니다.

  • 전환 전에 Green에 내부 테스트 트래픽이나 스모크 테스트를 흘려 예열합니다.
  • Blue에 진행 중인 요청과 장기 연결(WebSocket)이 끝나도록 드레이닝 시간을 둡니다.
  • Blue는 롤백이 필요 없다고 확신할 때까지(보통 수십 분~하루) 지우지 않습니다.

Canary: 일부에게 먼저 내보내고 지표로 판단

  1. 5%v2로 일부 트래픽
  2. 지표 비교에러율, p99 지연
  3. 25%, 50%이상 없으면 확대
  4. 100%v1 정리

탄광의 카나리아처럼 소수 사용자에게 먼저 v2를 보내고, v1과 지표를 비교해 단계적으로 늘립니다. 나쁘면 그 5%만 되돌리면 되므로 영향 범위가 가장 작습니다.

대신 비율 단위 라우팅(Ingress 가중치, 서비스 메시, ALB 가중치)과 버전별로 나눠 보는 관측성이 갖춰져야 합니다. 지표를 보지 않는 Canary는 느린 Rolling일 뿐입니다. 이 판정을 자동화한 것이 뒤에서 볼 Progressive Delivery입니다.

Canary 비율은 인스턴스 수로도 흉내 낸다

가장 단순한 Canary는 같은 Service 뒤에 v1 Pod 9개와 v2 Pod 1개를 두는 것입니다. 요청이 Pod에 고르게 나뉘면 약 10%가 v2로 갑니다.

하지만 이 방식은 비율이 Pod 수에 묶입니다. 1%를 보내려면 Pod 100개가 필요하고, HPA가 Pod 수를 바꾸면 비율도 흔들립니다.

정밀한 Canary는 트래픽 계층에서 가중치를 나눕니다. Ingress Controller나 서비스 메시(Istio), AWS ALB의 가중치 대상 그룹은 Pod 수와 상관없이 "v2에 3%"를 정확히 보냅니다.

특정 사용자만 보내는 것도 가능합니다. 헤더나 쿠키로 사내 직원 요청만 v2로 보내면, 실제 사용자 영향 없이 운영 환경에서 먼저 확인할 수 있습니다.

Shadow는 복사한 트래픽으로 몰래 시험한다

Shadow 배포는 운영 요청을 그대로 복제해 v2에도 보냅니다. 사용자에게는 v1의 응답만 돌아가고, v2의 응답은 비교용으로 기록한 뒤 버립니다.

실제 트래픽 패턴과 부하로 새 버전을 시험하면서도 사용자 영향이 0이라는 점이 장점입니다. 검색 엔진 교체나 성능 검증에 잘 맞습니다.

함정은 쓰기 요청입니다. 복제된 결제 요청을 v2가 실제로 처리하면 결제가 두 번 일어납니다.

A/B 테스트는 위험이 아니라 효과를 잰다

Canary와 A/B 테스트는 둘 다 사용자를 나눠 다른 버전을 보여 주지만 목적이 다릅니다. Canary는 새 버전이 안전한가를 에러율과 지연으로 판정하고, 확인되면 100%로 갑니다.

A/B 테스트는 어느 쪽이 더 나은가를 전환율이나 클릭률로 비교하는 실험입니다. 두 버전 모두 정상이고, 통계적으로 유의한 차이가 날 때까지 며칠~몇 주 유지합니다.

Feature Flag는 배포와 출시를 분리한다

if (flags.isEnabled("new-checkout", user)) {
    return newCheckout(order);  // 새 흐름
}
return legacyCheckout(order);   // 기존 흐름

// 플래그 규칙 (관리 화면이나 설정 저장소)
// new-checkout: 사내 직원 100%, 일반 사용자 5%

배포는 코드를 운영 서버에 올리는 기술적 사건이고, 출시는 사용자가 기능을 쓰기 시작하는 비즈니스 사건입니다. Feature Flag는 코드 안의 조건문으로 이 둘을 떼어 놓습니다.

새 결제 흐름을 꺼 둔 채 배포하고, 나중에 재배포 없이 설정만 바꿔 직원, 5%, 전체 순으로 켭니다. 문제가 생기면 플래그를 끄는 것이 곧 롤백입니다.

플래그는 켜는 것보다 지우는 것이 어렵다

플래그는 용도에 따라 수명이 다릅니다. 출시용 플래그는 기능이 100% 켜지면 지워야 하는 임시 장치입니다. 운영용 플래그(kill switch)는 외부 결제사가 느려질 때 추천 기능을 끄는 식으로 계속 남겨 둡니다.

출시용 플래그를 지우지 않으면 조건 분기가 쌓여, 어떤 조합이 실제로 운영에서 돌고 있는지 아무도 모르게 됩니다.

운영에서 지키는 규칙은 다음과 같습니다.

  • 플래그를 만들 때 담당자와 제거 예정일을 함께 등록합니다.
  • 플래그 저장소가 응답하지 않을 때의 기본값을 안전한 쪽(대개 끔)으로 정합니다.
  • 켜짐과 꺼짐 두 경로를 모두 테스트합니다. 꺼진 경로가 썩어 있으면 kill switch가 동작하지 않습니다.

도구는 LaunchDarkly, Unleash, AWS AppConfig 등이 있습니다.

무중단의 조건: 앱이 우아하게 떠나야 한다

어떤 전략이든 옛 인스턴스는 결국 종료됩니다. 이때 앱이 진행 중인 요청을 버리고 즉시 죽으면, 배포할 때마다 몇 건씩 502가 납니다. 사용자는 전략이 무엇이었는지 모르고 "배포 때마다 에러가 난다"고만 느낍니다.

무중단 배포는 그래서 세 가지가 맞물려야 성립합니다.

  1. readiness

    새 인스턴스는 준비가 끝난 뒤에만 트래픽을 받습니다.

  2. 트래픽 차단 먼저

    옛 인스턴스는 라우팅 대상에서 빠진 뒤에 종료를 시작합니다.

  3. Graceful Shutdown

    종료 신호를 받으면 새 요청은 거절하고 진행 중인 요청은 끝냅니다.

  4. 커넥션 드레이닝

    로드 밸런서는 빠지는 대상의 기존 연결이 끝나길 기다립니다.

Spring Boot는 SIGTERM에 요청을 마무리한다

server:
  shutdown: graceful   # Boot 3.4부터 기본값
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s  # 기본 30s
management:
  endpoint:
    health:
      probes:
        enabled: true  # /actuator/health/readiness

SIGTERM을 받으면 Spring Boot는 웹 서버가 새 요청을 받지 않게 하고, 진행 중인 요청이 끝나기를 설정한 시간만큼 기다린 뒤 애플리케이션 컨텍스트를 닫습니다. 그 사이 readiness 상태도 거부로 바뀝니다.

Spring Boot 3.4부터는 내장 Tomcat, Jetty, Netty 모두 graceful이 기본입니다. 그 이전 버전은 명시적으로 켜야 합니다. 대기 시간을 넘긴 요청은 강제로 끊깁니다.

종료 예산은 플랫폼 유예 시간 안에 맞춘다

앱이 아무리 우아하게 끝내려 해도 플랫폼이 먼저 강제 종료하면 소용없습니다. Kubernetes는 유예 시간(terminationGracePeriodSeconds, 기본 30초)이 지나면 SIGKILL을 보냅니다.

그래서 규칙은 preStop 대기 + 앱 종료 시간 < 플랫폼 유예 시간입니다. 예를 들어 preStop 10초, Spring 대기 20초라면 유예 시간은 40초 정도로 둡니다.

preStop에서 몇 초 기다리는 이유, 엔드포인트 제거와 SIGTERM이 동시에 시작되는 경합은 10장 Pod 종료 절차에서 다뤘습니다.

로드 밸런서 쪽의 커넥션 드레이닝 시간(AWS에서는 대상 그룹의 등록 취소 지연, 18장)도 같은 예산 안에서 맞춥니다. 긴 배치 작업이나 메시지 컨슈머는 처리 중인 메시지를 끝내거나 다시 큐에 돌려놓는 코드가 따로 필요합니다(8장 멱등 컨슈머).

스키마 변경도 코드처럼 버전으로 관리한다

V1__create_orders.sql
V2__add_orders_status_index.sql
V3__add_customer_full_name.sql

-- flyway_schema_history (Flyway가 관리)
-- version | description          | checksum | success
-- 1       | create orders        | 91c2…    | 1
-- 2       | add orders status …  | 5ab0…    | 1

DB 스키마를 사람이 직접 ALTER하면 환경마다 상태가 어긋납니다. Flyway는 번호가 붙은 SQL 파일을 순서대로 적용하고, 적용 이력을 이력 테이블에 남깁니다. 다음 실행 때는 아직 적용되지 않은 번호만 실행합니다.

이미 적용된 파일을 고치면 체크섬이 달라져 검증에서 실패합니다. 수정은 항상 새 번호의 파일로 합니다. Liquibase는 같은 일을 XML, YAML 변경 단위(changeset)로 하며 DB 종류에 덜 묶입니다.

마이그레이션은 언제, 누가 실행하는가

Spring Boot는 Flyway가 클래스패스에 있으면 앱이 뜰 때 마이그레이션을 실행합니다. 간단하지만 인스턴스 10개가 동시에 뜨면 10개가 동시에 시도합니다. Flyway와 Liquibase는 DB 락으로 하나만 실행하게 하지만, 오래 걸리는 변경이면 나머지 인스턴스의 기동이 그만큼 늦어집니다.

그래서 운영에서는 마이그레이션을 배포 파이프라인의 별도 단계로 떼어 내는 경우가 많습니다.

  • CI/CD에서 앱 배포 직전에 마이그레이션 job을 한 번 실행합니다.
  • Kubernetes에서는 Job으로 돌리거나, Argo CD의 PreSync 훅으로 동기화 전에 실행합니다.

어느 쪽이든 새 스키마에서 옛 앱이 계속 동작해야 합니다. 앱보다 스키마가 먼저 바뀌기 때문입니다.

스키마는 두 버전이 함께 견뎌야 한다

배포 중에는 v1과 v2가 같은 DB를 씁니다. v2 배포와 함께 컬럼 이름을 바꾸면 아직 남은 v1이 즉시 에러를 냅니다. 롤백해도 v1은 바뀐 스키마를 모릅니다.

해법은 변경을 여러 배포로 쪼개는 Expand-Contract입니다. 먼저 넓히고, 모두 옮긴 뒤, 나중에 좁힙니다.

  1. Expand

    새 컬럼 full_name을 NULL 허용으로 추가합니다. v1은 영향이 없습니다.

  2. 이중 쓰기

    v2는 두 컬럼에 모두 쓰고, 읽을 때는 새 컬럼을 우선합니다.

  3. 백필

    기존 행의 값을 배치로 나눠 새 컬럼에 복사합니다.

  4. 전환

    v1이 모두 사라진 뒤 새 컬럼만 읽고 씁니다.

  5. Contract

    다음 릴리스에서 옛 컬럼 name을 삭제합니다.

위험한 스키마 변경은 따로 있다

큰 테이블 인덱스 추가락, 복제 지연온라인 DDL, 한가한 시간

JPA 엔티티에서 필드를 지울 때도 같습니다. 옛 버전이 그 컬럼을 SELECT하는 동안에는 컬럼을 지우면 안 됩니다. 큰 테이블의 ALTER가 운영을 멈추는 이유는 3부에서 봅니다.

롤백보다 롤포워드가 나을 때가 있다

롤백은 직전 버전의 이미지로 되돌리는 것입니다. 이미지가 그대로 남아 있으니 가장 빠르고 확실한 첫 대응입니다. 장애 중에는 원인을 찾기 전에 먼저 롤백하는 것이 원칙입니다.

그런데 되돌릴 수 없는 변화가 섞이면 롤백이 통하지 않습니다. 이미 지운 컬럼, 새 형식으로 저장된 데이터, 새 스키마로 발행된 메시지는 이미지를 바꿔도 돌아오지 않습니다.

이때는 롤포워드, 즉 문제를 고친 새 버전을 빠르게 내보냅니다. 롤포워드가 가능하려면 파이프라인이 빨라야 합니다. 수정 하나를 운영에 반영하는 데 2시간이 걸리면 그 2시간이 장애 시간입니다.

가장 좋은 상태는 모든 배포가 롤백 가능하도록 설계하는 것입니다. Expand-Contract, Feature Flag, 하위 호환 메시지 형식이 모두 이를 위한 장치입니다.

GitOps: 클러스터가 Git을 끌어와 맞춘다

지금까지의 파이프라인은 CI가 클러스터에 kubectl apply를 밀어 넣는 push 방식입니다. CI가 운영 클러스터의 강한 권한을 쥐어야 하고, 누가 손으로 바꾼 상태는 아무도 모릅니다.

GitOps는 방향을 뒤집습니다. 클러스터 안의 에이전트가 Git 저장소를 주기적으로 읽어 실제 상태를 그에 맞춥니다. Git이 원하는 상태의 유일한 원본이 되고, 배포는 곧 Git 커밋입니다. 10장의 조정 루프를 Git까지 넓힌 셈입니다.

Argo CD Application은 어디를 어디에 맞출지다

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: api-prod, namespace: argocd }
spec:
  source:
    repoURL: https://github.com/acme/deploy-config
    path: apps/api/overlays/prod
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: api
  syncPolicy:
    automated:
      prune: true     # Git에서 지운 리소스도 삭제
      selfHeal: true  # 손으로 바꾼 것을 되돌림

Argo CD는 Kubernetes용 GitOps 도구입니다. Application 리소스 하나가 "이 저장소의 이 경로를, 이 클러스터의 이 네임스페이스에 맞춰라"를 선언합니다. 경로에는 일반 YAML, Helm 차트, Kustomize 오버레이(10장)를 둘 수 있습니다.

자동 동기화를 켜도 prune은 안전을 위해 기본이 꺼져 있습니다. Git에서 사라진 리소스를 실제로 지우려면 명시적으로 켜야 합니다.

drift는 감지되고 selfHeal이 되돌린다

drift는 실제 상태가 선언된 상태와 어긋난 것입니다. 누군가 장애 중에 kubectl scale로 Pod 수를 바꿨다면 Git과 클러스터가 달라집니다. Argo CD는 이를 OutOfSync로 표시합니다.

selfHeal을 켜면 이런 수동 변경을 몇 초 안에 Git 상태로 되돌립니다. Git 변경은 기본적으로 약 3분 주기(120초 + 최대 60초 지연)로 확인하며, 저장소 웹훅을 걸면 즉시 반영됩니다.

그래서 GitOps에서 장애 대응도 Git으로 합니다. 급하게 손으로 고쳐도 곧 되돌려지므로, 수정 사항을 커밋하거나 해당 앱의 자동 동기화를 잠시 멈춥니다.

CI와는 설정 저장소로 연결합니다. CI는 이미지를 푸시한 뒤 설정 저장소의 이미지 태그를 바꾸는 커밋(또는 PR)만 만들고, 나머지는 Argo CD가 합니다. 롤백은 그 커밋을 revert하는 것입니다.

앱이 많으면 다른 Application들을 만드는 상위 Application 하나를 두는 App of Apps 패턴(또는 ApplicationSet)으로 묶습니다. Flux도 같은 pull 모델의 GitOps 도구입니다.

Progressive Delivery는 Canary 판정을 자동화한다

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: api }
spec:
  replicas: 10
  strategy:
    canary:
      analysis:
        templates: [{ templateName: success-rate }]
      steps:
        - setWeight: 10
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
  # selector, template은 Deployment와 같음

사람이 대시보드를 보며 Canary 비율을 올리는 방식은 느리고, 새벽 배포에서는 아무도 안 보고 있습니다. Progressive Delivery는 단계적 노출과 지표 판정을 함께 자동화합니다.

Argo Rollouts의 Rollout은 Deployment를 대체하는 리소스로, 단계를 직접 적습니다. 10%를 보내고 10분 관찰, 50%로 올리고 10분 관찰, 마지막 단계가 끝나면 100%가 됩니다. 기간 없는 pause: {}는 사람이 승격할 때까지 멈춥니다.

지표가 나빠지면 Rollout이 스스로 멈춘다

kind: AnalysisTemplate
metadata: { name: success-rate }
spec:
  metrics:
  - name: success-rate
    interval: 5m
    successCondition: result[0] >= 0.95
    failureLimit: 3
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{app="api",
            code!~"5.."}[5m])) /
          sum(rate(http_requests_total{app="api"}[5m]))

분석 템플릿은 "무엇을, 얼마나 자주 재고, 어떤 값이면 성공인가"를 적습니다. 이 예는 5분마다 성공률을 재서 95% 미만이 세 번 나오면 분석을 실패로 판정합니다.

분석이 실패하면 Rollout은 Canary 가중치를 0으로 되돌리고 중단합니다. 사람이 깨어나기 전에 롤백이 끝나 있습니다. 지표는 Prometheus 외에 CloudWatch, Datadog 등에서도 가져올 수 있습니다.

2부

인프라도 코드로 선언하고 리뷰한다

애플리케이션은 파이프라인으로 배포되는데, 그 아래 네트워크, 서버, DB는 누가 어떻게 만들까요. 같은 원칙을 인프라에 적용하는 방법을 봅니다.

손으로 만든 인프라는 기억 속에만 있다

콘솔에서 클릭으로 만든 인프라에는 세 가지 문제가 있습니다. 누가 언제 왜 바꿨는지 기록이 없고, 같은 구성을 다른 리전이나 환경에 똑같이 다시 만들기 어렵고, stage와 prod가 조금씩 달라져도 아무도 모릅니다.

이런 서버를 흔히 눈송이 서버라 부릅니다. 하나하나 모양이 달라서 다시 만들 수 없다는 뜻입니다.

IaC는 인프라의 원하는 모습을 코드 파일로 적고, 도구가 그 코드대로 만들게 합니다. 그러면 애플리케이션 코드가 누리던 것을 인프라도 누립니다.

  • Git 기록이 곧 변경 이력이고, PR 리뷰가 곧 변경 승인입니다.
  • 같은 코드로 dev, stage, prod를 같은 모양으로 찍어 냅니다.
  • 적용 전에 무엇이 바뀔지 미리 보고, 사고가 나면 이전 커밋으로 되돌립니다.

선언형은 결과를, 명령형은 절차를 적는다

명령형은 "서버를 하나 만들어라, 보안 그룹을 붙여라"처럼 할 일을 순서대로 적습니다. 셸 스크립트나 AWS CLI 호출이 그렇습니다. 두 번 실행하면 서버가 두 대 생깁니다.

선언형은 "서버가 하나 있고 이 보안 그룹이 붙어 있어야 한다"는 결과만 적습니다. 도구가 현재 상태와 비교해 필요한 작업을 계산합니다. 몇 번을 실행해도 결과가 같습니다(멱등).

구분명령형선언형
적는 것절차원하는 결과
재실행중복 생성 위험변화 없음
변경 계산사람이 함도구가 함

불변 인프라는 고치지 않고 갈아 끼운다

가변 인프라는 서버를 한 번 만들고 그 위에서 패키지를 업데이트하고 설정을 고치며 계속 씁니다. 시간이 지나면 서버마다 적용된 패치와 수동 변경이 달라져 구성 표류(configuration drift)가 생깁니다.

불변 인프라는 실행 중인 서버를 고치지 않습니다. 변경이 필요하면 새 이미지(컨테이너 이미지, AMI)를 만들어 새 서버로 교체하고 옛 서버는 버립니다.

컨테이너와 Kubernetes가 바로 이 모델입니다. 실행 중인 Pod에 들어가 파일을 고치지 않고, 이미지를 바꿔 새 Pod로 교체합니다. 그래서 어떤 서버든 이미지 버전만 보면 정확한 상태를 알 수 있습니다.

Terraform은 provider로 어디든 만든다

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}
provider "aws" { region = "ap-northeast-2" }

data "aws_vpc" "main" { tags = { Name = "main" } }

resource "aws_security_group" "api" {
  name   = "api-sg"
  vpc_id = data.aws_vpc.main.id
}

Terraform은 HCL이라는 선언형 언어로 인프라를 적습니다. provider는 AWS, Kubernetes, GitHub 같은 대상 API를 다루는 플러그인입니다.

resource는 Terraform이 만들고 관리하는 대상이고, data는 이미 있는 것을 읽기만 합니다. 다른 블록의 속성을 참조하면(data.aws_vpc.main.id) Terraform이 그 의존 관계로 생성 순서를 정합니다.

variable은 입력, output은 출력이다

variable "instance_type" {
  type    = string
  default = "t3.small"
}
locals {
  name = "api-${terraform.workspace}"
}
output "sg_id" {
  value = aws_security_group.api.id
}

# prod.tfvars
instance_type = "m7g.large"

variable은 코드를 함수처럼 만드는 입력입니다. 같은 코드에 환경별 .tfvars 파일을 넣어 크기만 다른 인프라를 만듭니다. locals는 코드 안에서 반복되는 값에 이름을 붙인 것입니다.

output은 만든 결과(ID, 주소)를 밖으로 내보냅니다. 다른 모듈이나 다른 Terraform 프로젝트가 이 값을 받아 씁니다.

state는 코드와 실제 리소스를 잇는 장부다

코드에 aws_security_group.api라고 적었을 때, 이것이 AWS의 어느 보안 그룹(sg-0a1b…)인지는 코드만 봐서는 모릅니다. Terraform은 이 대응 관계와 마지막으로 알던 속성을 state 파일에 기록합니다.

plan은 세 가지를 비교합니다. 코드(원하는 상태), state(지난번 기록), 실제 API 응답(현재 상태)입니다. state가 없으면 Terraform은 이미 만든 리소스를 모르는 것으로 보고 새로 만들려 합니다.

plan으로 보고, 리뷰하고, apply로 적용한다

  1. init

    provider 플러그인과 모듈을 받고 state 저장소에 연결합니다.

  2. plan

    새로 고친 실제 상태와 코드를 비교해 바뀔 목록을 출력합니다.

  3. 리뷰

    PR에 plan 결과를 붙여 삭제, 교체 항목을 사람이 확인합니다.

  4. apply

    저장해 둔 plan 그대로 API를 호출하고 state를 갱신합니다.

plan 출력에서 가장 주의해서 볼 기호는 -/+(삭제 후 재생성)입니다. DB 인스턴스 이름처럼 바꿀 수 없는 속성을 고치면 Terraform은 지우고 새로 만들려 하고, 데이터가 사라집니다.

CI에서는 plan -out=tfplan으로 저장한 plan 파일을 리뷰한 뒤 apply tfplan으로 적용합니다. 그사이 상태가 바뀌었다면 저장된 plan은 거부됩니다.

DB처럼 지워지면 안 되는 리소스에는 lifecycle { prevent_destroy = true }를 둡니다.

state는 원격에 두고 락으로 순서를 지킨다

terraform {
  backend "s3" {
    bucket       = "acme-tfstate"
    key          = "prod/network/terraform.tfstate"
    region       = "ap-northeast-2"
    encrypt      = true
    use_lockfile = true  # S3 네이티브 락
  }
}

state를 노트북에 두면 팀원끼리 공유할 수 없고, 노트북을 잃으면 장부가 사라집니다. 그래서 S3 같은 원격 백엔드에 두고 버전 관리를 켭니다.

두 사람이 동시에 apply하면 state가 서로를 덮어씁니다. 락은 이를 막습니다. Terraform 1.11부터 use_lockfile로 S3에 .tflock 파일을 만들어 잠그는 방식이 정식 기능이 되었고, 예전의 DynamoDB 락 테이블 방식은 deprecated입니다.

module은 인프라 부품을 재사용하게 한다

module "vpc" {
  source   = "../../modules/vpc"
  cidr     = "10.0.0.0/16"
  az_count = 3
}

module "api" {
  source = "../../modules/ecs-service"
  subnet_ids = module.vpc.private_subnet_ids
  cpu        = 1024
}

모듈은 리소스 묶음에 입력(variable)과 출력(output)을 붙인 부품입니다. VPC 하나에 서브넷, 라우팅 테이블, NAT Gateway 등 수십 개 리소스가 필요한데, 모듈로 감싸면 환경마다 몇 줄로 찍어 냅니다.

공용 레지스트리의 모듈이나 Git 저장소 모듈을 쓸 때는 버전(version, ?ref=)을 고정합니다. 모듈을 너무 잘게 쪼개거나 너무 많은 옵션을 넣으면 오히려 읽기 어려워집니다.

환경 분리는 workspace보다 디렉터리가 흔하다

CLI workspace는 같은 백엔드 안에 state를 여러 벌 두는 기능이라, prod를 dev로 착각하고 apply하는 사고가 쉽게 납니다. 그래서 운영에서는 환경별 디렉터리에 공통 모듈을 불러 쓰고, prod state는 별도 AWS 계정의 버킷에 두는 구성이 흔합니다. 큰 시스템은 네트워크, DB, 앱처럼 state를 층별로도 나눠 한 번의 실수가 미치는 범위를 줄입니다.

import로 들이고, drift는 plan이 알려 준다

import {
  to = aws_s3_bucket.logs
  id = "acme-legacy-logs"
}
# resource 블록이 없으면 초안을 생성
$ terraform plan -generate-config-out=gen.tf
$ terraform apply              # state에 편입
$ terraform plan -refresh-only  # drift 확인

콘솔로 이미 만든 리소스를 Terraform 관리로 들이는 것이 import입니다. import 블록에 대상과 실제 ID를 적으면 plan이 state에 편입할 계획을 보여 주고, 설정 코드 초안도 생성해 줍니다.

누군가 콘솔에서 값을 바꿨다면 다음 plan에서 그 차이가 "변경 예정"으로 드러납니다. 그대로 apply하면 수동 변경이 코드대로 되돌아갑니다. -refresh-only는 실제 상태를 state에만 반영하고 리소스는 건드리지 않습니다.

민감 값은 가려도 state에는 평문으로 남는다

변수나 출력에 sensitive = true를 붙이면 plan과 apply 화면에서 값이 (sensitive value)로 가려집니다. 하지만 이것은 화면 표시만 가리는 것입니다.

DB 비밀번호를 Terraform 리소스 인자로 넘기면 그 값은 state 파일에 평문으로 저장됩니다. state를 읽을 수 있는 사람은 비밀번호도 읽습니다.

그래서 다음을 함께 지킵니다.

  • state 버킷은 암호화하고, 읽기 권한을 배포 역할과 소수의 관리자로 제한합니다.
  • 비밀번호는 Terraform이 직접 만들지 않고 Secrets Manager가 생성, 관리하게 하거나(RDS의 관리형 마스터 암호 등), 1.11부터 지원되는 write-only 인자처럼 state에 남지 않는 방식을 씁니다.
  • *.tfvars에 비밀을 적어 Git에 올리지 않습니다.

CloudFormation은 AWS의 IaC 서비스입니다. 템플릿을 올리면 리소스 묶음인 스택이 생기고, state를 AWS가 서비스 안에서 관리하므로 백엔드와 락을 따로 챙길 필요가 없습니다.

생성이나 변경 중 하나라도 실패하면 스택 전체를 이전 상태로 자동 롤백합니다. DeletionPolicy: Retain은 스택을 지워도 버킷은 남기라는 뜻입니다.

change set으로 미리 보고 drift를 검사한다

change set은 Terraform plan에 해당합니다. 템플릿을 바로 적용하지 않고 변경 세트를 만들면, 어떤 리소스가 추가, 수정, 교체(Replacement)되는지 보여 줍니다. 확인 후 실행합니다.

drift detection은 스택의 리소스가 콘솔 등에서 수동으로 바뀌었는지 검사해 속성별 차이를 보여 줍니다. 단, 감지만 하고 자동으로 되돌리지는 않습니다.

AWS CDK는 TypeScript, Python, Java 같은 언어로 인프라를 적고, 실행하면 CloudFormation 템플릿을 생성(synth)해 배포합니다. 몇 줄의 고수준 구성 요소가 VPC, ALB, 보안 그룹, IAM 역할 수십 개로 펼쳐집니다.

Pulumi도 범용 언어를 쓰지만 CloudFormation을 거치지 않고 Terraform처럼 자체 state로 여러 클라우드를 다룹니다. 반복문, 테스트, IDE 지원이 장점이고, 코드가 너무 똑똑해지면 실제로 무엇이 만들어지는지 읽기 어려워집니다.

3부

배포는 자주, 사고는 작게

파이프라인을 갖추는 것과 그것으로 안전하게 자주 배포하는 것은 다른 문제입니다. 측정, 흔한 장애, 사고 예방을 봅니다.

원리 실무 배포 성과 지표, 배포 직후 장애 사례, 시크릿과 state 사고, 접근 통제를 다룹니다.

DORA 지표는 속도와 안정성을 함께 잰다

DORA(DevOps Research and Assessment) 연구는 이 네 지표로 소프트웨어 전달 성과를 잽니다. 핵심 발견은 잘하는 팀은 빠르면서 동시에 안정적이라는 것입니다. 작게 자주 배포하면 변경 하나의 위험이 작고, 문제가 나도 원인이 좁습니다. 최근 모델은 계획에 없던 장애 대응 배포의 비율(배포 재작업률)을 다섯 번째 지표로 더합니다.

지표는 개선 방향을 알려 줄 뿐 목표가 아니다

네 지표는 서로 견제하도록 묶여 있습니다. 배포 빈도만 목표로 삼으면 의미 없는 배포가 늘고, 실패율만 보면 배포를 미루게 됩니다. 한 지표가 좋아질 때 다른 지표가 나빠지지 않는지 함께 봅니다.

측정은 도구에서 자동으로 뽑습니다. 리드 타임은 Git 커밋 시각과 배포 기록, 실패율은 롤백과 핫픽스 기록에서 계산합니다.

지표가 나쁠 때 흔한 원인과 처방은 이렇습니다.

  • 리드 타임이 길면 대개 리뷰 대기나 느린 CI, 수동 승인 단계가 병목입니다.
  • 실패율이 높으면 테스트 공백, stage와 운영의 차이, 큰 배포 단위를 의심합니다.
  • 복구가 느리면 롤백이 자동화되어 있지 않거나, 배포와 장애를 연결해 볼 관측성이 없습니다.

flaky 테스트는 CI의 신뢰를 갉아먹는다

flaky 테스트는 코드가 그대로인데 때로는 통과하고 때로는 실패하는 테스트입니다. 처음에는 "다시 돌리면 되지"로 넘어가지만, 실패가 흔해지면 사람들은 빨간 결과를 무시하기 시작하고, 진짜 버그도 그 사이에 묻힙니다.

흔한 원인은 시간 의존(현재 시각, 고정 sleep), 테스트 간 공유 상태(같은 DB 행, 정적 변수), 실행 순서 의존, 외부 네트워크 호출, 비동기 처리 대기 부족입니다.

다루는 방법은 다음과 같습니다.

  • 재시도 후 통과한 테스트를 기록해 flaky 목록을 자동으로 만듭니다.
  • 발견하면 격리(quarantine)해 병합을 막지 않게 하되, 담당자와 기한을 붙여 고칩니다.
  • 고정 sleep 대신 조건이 만족될 때까지 기다리고(Awaitility), 시각은 주입한 Clock으로 고정합니다.
  • 테스트마다 자기 데이터를 만들고 지워서 실행 순서에 의존하지 않게 합니다.

배포 직후 자주 터지는 장애 네 가지

유형증상예방
설정 누락새 환경 변수가 prod에만 없음, 기동 실패기동 시 필수 설정 검증
마이그레이션 락ALTER 하나에 테이블 전체가 멈춤락 대기 시간 제한, 온라인 DDL
캐시 콜드 스타트새 인스턴스의 지연 급증, DB 부하 폭증예열, 점진적 트래픽
하위 호환 깨짐옛 버전, 옛 클라이언트가 에러Expand-Contract, 계약 테스트

설정 누락은 앱이 뜬 뒤 그 기능이 처음 호출될 때 터지면 가장 고약합니다. Spring의 @ConfigurationProperties에 @Validated를 붙여 필수 값이 없으면 기동 자체가 실패하게 만들면, readiness를 통과하지 못해 Rolling이 그 자리에서 멈추고 옛 버전이 계속 서비스합니다.

ALTER 하나가 테이블 전체를 세우는 이유

  1. 긴 트랜잭션

    배치 작업이 orders를 읽는 트랜잭션을 열어 둡니다.

  2. ALTER 대기

    마이그레이션의 ALTER가 메타데이터 락을 얻지 못해 기다립니다.

  3. 뒤따르는 쿼리 정체

    그 뒤에 온 일반 SELECT, INSERT도 ALTER 뒤에 줄을 섭니다.

  4. 커넥션 풀 고갈

    요청 스레드가 모두 대기에 묶여 서비스 전체가 응답하지 않습니다.

MySQL에서 테이블 구조를 바꾸려면 메타데이터 락이 필요합니다. 온라인 DDL이라도 시작과 끝에 잠깐 이 락을 잡아야 합니다. 그런데 대기 중인 ALTER가 뒤에 오는 모든 쿼리를 막아, 몇 초짜리 변경이 몇 분짜리 장애가 됩니다.

마이그레이션 세션에는 lock_wait_timeout(PostgreSQL은 lock_timeout)을 몇 초로 짧게 걸어, 락을 못 얻으면 실패하고 나중에 다시 시도하게 합니다. 큰 테이블은 gh-ost, pt-online-schema-change를 씁니다. DB 락 자체는 4장에서 다뤘습니다.

콜드 스타트와 직렬화 호환도 배포의 일부다

새로 뜬 JVM은 JIT 컴파일 전이라 느리고, 커넥션 풀과 로컬 캐시도 비어 있습니다. 한꺼번에 전부 교체하면 모든 인스턴스가 동시에 DB로 몰려 캐시 미스 폭풍이 납니다. 배포 직후 Redis 키 구조를 바꾼 경우도 같은 일이 생깁니다.

처방은 readiness 전에 주요 경로를 호출해 예열하고, Rolling이나 Canary로 천천히 교체하는 것입니다.

하위 호환은 DB 스키마만의 문제가 아닙니다.

  • 캐시: v2가 필드를 바꾼 객체를 캐시에 쓰면, 아직 남은 v1이 역직렬화에 실패합니다.
  • 메시지: v2 프로듀서가 새 형식으로 발행하면 v1 컨슈머가 처리하지 못합니다. 필드는 추가만 하고 지우지 않습니다.
  • API: 모바일 앱처럼 업데이트를 강제할 수 없는 클라이언트는 옛 응답 형식을 오래 기대합니다(7장 버저닝).

시크릿은 들어가는 길과 새는 길을 모두 막는다

시크릿이 새는 경로는 대부분 평범합니다. 커밋에 섞인 .env 파일, 디버깅하려고 찍은 환경 변수 로그, 이미지 레이어에 남은 설정 파일, 너무 넓은 권한의 CI 토큰입니다. Git 기록에 한 번 들어간 키는 다음 커밋에서 지워도 기록에 남아 있습니다.

예방은 세 겹으로 합니다. 커밋 전 훅과 저장소 push 보호로 키 패턴을 차단하고, 시크릿 저장소에서만 값을 읽게 하고, OIDC로 장기 키 자체를 없앱니다.

유출되면 기록 삭제보다 폐기가 먼저입니다

공개 저장소에 올라간 키는 몇 분 안에 자동 수집됩니다. 즉시 키를 폐기, 교체하고, 그 키로 무슨 일이 있었는지 감사 로그로 확인한 뒤 기록을 정리합니다. AWS 키 사고 대응 절차는 12장에서 봅니다.

Terraform 사고는 대개 state와 수동 변경에서

사고무슨 일이 일어나나대응과 예방
락이 남음apply 중 CI가 죽어 락이 풀리지 않음실행 중인 작업이 없는지 확인 후 force-unlock
수동 변경 덮어쓰기장애 중 콘솔로 늘린 용량이 다음 apply에 원복수동 변경은 바로 코드에 반영
의도치 않은 재생성이름 변경이 삭제 후 생성으로plan의 -/+ 확인, moved 블록
state 손상, 분실모든 리소스를 모르는 상태버킷 버전 관리로 이전 state 복구

가장 흔한 것은 수동 변경입니다. 새벽 장애 때 콘솔로 고친 설정을 아무도 코드에 옮기지 않으면, 한참 뒤 전혀 상관없는 PR의 apply가 그 설정을 되돌려 같은 장애가 다시 납니다. 리소스 주소를 바꿀 때는 moved 블록으로 "같은 리소스의 이름만 바뀌었다"고 알려 재생성을 막습니다.

운영 접근은 사람이 아니라 파이프라인이 한다

운영 환경에 사람이 직접 kubectl apply나 terraform apply를 할 수 있으면, 리뷰와 기록을 우회하는 길이 열려 있는 셈입니다. 목표는 평소의 모든 운영 변경이 PR과 파이프라인을 거치는 것입니다.

그래서 사람에게는 운영 읽기 권한만 주고, 쓰기 권한은 배포 파이프라인의 역할에만 줍니다. 파이프라인 역할도 environment 승인과 브랜치 제한으로 묶습니다.

장애 때는 예외 경로가 필요합니다. 이것을 미리 설계해 둡니다.

  • 긴급 접근(break-glass): 평소 잠긴 고권한 역할을 승인 후 짧게 받아 쓰고, 사용 사실을 자동으로 알립니다.
  • 감사 기록: 누가 언제 어떤 권한으로 무엇을 했는지 남깁니다(AWS는 CloudTrail, 16장).
  • 사후 반영: 긴급 변경은 사후에 반드시 코드로 옮겨 drift를 없앱니다.

정리

  • CI/CD는 커밋에서 운영까지를 매번 같은 자동 경로로 만듭니다. 이미지는 한 번 빌드해 SHA 태그로 승격하고, 환경 차이는 설정으로만 둡니다.
  • 배포 전략은 비용, 롤백 속도, 영향 범위의 교환입니다. Rolling은 싸고, Blue-Green은 즉시 되돌리고, Canary는 영향을 가장 작게 묶습니다.
  • 무중단은 전략보다 공존을 견디는 장치에 달려 있습니다. Graceful Shutdown, readiness, Expand-Contract가 없으면 어떤 전략도 502와 스키마 오류를 냅니다.
  • GitOps와 IaC는 Git을 원하는 상태의 원본으로 삼습니다. 도구가 실제 상태와 비교해 맞추고, 수동 변경은 drift로 드러납니다.
  • Terraform state는 장부이자 비밀 저장소입니다. 원격에 두고 S3 네이티브 락으로 잠그며, 접근을 좁힙니다.

스스로 점검 (1)

  1. stage와 prod에서 각각 이미지를 다시 빌드하면 어떤 위험이 있나요?

    그사이 의존성이나 베이스 이미지가 바뀌어 stage에서 검증한 것과 다른 바이너리가 운영에 나갈 수 있습니다. 한 번 빌드한 이미지를 태그로 승격해야 검증이 의미를 가집니다.

  2. 지속적 전달과 지속적 배포의 차이를 GitHub Actions 설정으로 표현하면?

    운영 배포 job에 required reviewers가 걸린 environment를 붙이면 지속적 전달, 승인 없이 테스트 통과 후 자동 실행되면 지속적 배포입니다.

  3. OIDC 신뢰 정책의 sub 조건을 repo:org/*로 두면 무엇이 문제인가요?

    조직의 아무 저장소, 아무 브랜치의 워크플로나 그 역할을 맡을 수 있습니다. 저장소와 브랜치 또는 environment까지 좁혀야 합니다.

  4. Pod 수로 Canary 비율을 정하면 어떤 한계가 있나요?

    비율이 Pod 수의 배수로만 정해져 1% 같은 작은 비율이 어렵고, HPA가 Pod 수를 바꾸면 비율도 흔들립니다. 트래픽 계층의 가중치 라우팅이 필요합니다.

  5. 컬럼 이름을 바꾸는 마이그레이션을 v2 배포와 함께 하면 무슨 일이 생기나요?

    배포 중 남아 있는 v1이 옛 컬럼을 찾다가 즉시 에러를 내고, 롤백해도 v1은 새 스키마를 모릅니다. 새 컬럼 추가, 이중 쓰기, 백필, 전환, 삭제로 나눠야 합니다.

스스로 점검 (2)

  1. Spring 대기 25초, preStop 10초인데 유예 시간이 30초면 어떻게 되나요?

    합이 35초라 앱이 진행 중 요청을 끝내기 전에 SIGKILL을 받습니다. 유예 시간을 40초 이상으로 늘리거나 앱 대기 시간을 줄여야 합니다.

  2. selfHeal이 켜진 앱을 장애 중에 kubectl로 스케일하면 어떻게 되나요?

    Argo CD가 drift로 보고 몇 초 안에 Git의 값으로 되돌립니다. 변경을 Git에 커밋하거나 자동 동기화를 잠시 꺼야 합니다.

  3. Terraform state를 잃어버리면 다음 apply에서 무슨 일이 생기나요?

    Terraform은 기존 리소스를 모르므로 전부 새로 만들려 하고, 이름 충돌로 실패하거나 중복 리소스가 생깁니다. 버킷 버전 관리로 이전 state를 복구하거나 import로 다시 들여야 합니다.

  4. 몇 초면 끝나는 ALTER가 왜 서비스 전체 장애가 되나요?

    긴 트랜잭션 때문에 메타데이터 락을 기다리는 ALTER 뒤에 일반 쿼리가 모두 줄을 서고, 커넥션 풀이 고갈됩니다. 마이그레이션에 짧은 락 대기 제한을 둡니다.

  5. 배포 빈도만 KPI로 삼으면 어떤 부작용이 있나요?

    의미 없는 작은 배포가 늘거나 검증을 건너뛰어 실패율이 올라갈 수 있습니다. 속도 지표와 안정성 지표를 함께 봐야 합니다.
