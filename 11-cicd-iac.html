1부

코드가 운영에 닿기까지

10장에서 Kubernetes는 원하는 상태를 적어 주면 그대로 맞춰 준다고 했습니다. 남은 질문은 그 원하는 상태를 누가, 어떤 검증을 거쳐 바꾸느냐입니다. 1부는 고친 코드 한 줄이 사용자에게 닿기까지 거치는 관문과, 그 일을 왜 사람이 아니라 기계에 맡기는지를 봅니다.

이 장의 예제: 손으로 배포하는 주문 API 팀

이 장은 한 팀의 이야기를 따라갑니다. 여섯 명이 주문 API(이하 order-api)를 만듭니다. Spring Boot 애플리케이션이고, 9장에서 본 방식으로 컨테이너 이미지로 만들어 10장의 Kubernetes Deployment로 띄웁니다. 소스 코드는 GitHub 저장소 acme/order-api에 있습니다.

지금 이 팀의 배포는 이렇습니다. 기능을 다 만든 개발자가 자기 노트북에서 테스트를 돌리고, 이미지를 빌드해 레지스트리에 올리고, deploy.sh라는 스크립트로 운영 클러스터의 이미지 태그를 바꿉니다. 그 아래의 네트워크, DB, 파일 저장 공간(S3 버킷)은 몇 해 전 누군가 AWS 콘솔에서 클릭으로 만들었습니다.

이 방식은 사람이 바뀔 때마다 결과가 달라집니다. 누구는 테스트를 건너뛰고, 누구는 커밋하지 않은 파일이 섞인 채 빌드하고, 누구는 운영 DB 주소가 박힌 설정으로 이미지를 만듭니다. 배포 중에 서버가 잠깐 끊기는 것도 "원래 그렇다"고 여깁니다.

이번 분기에 팀은 새 결제 흐름을 내보내야 하고, 이를 위해 주문 테이블의 주소 컬럼 이름도 바꿔야 합니다. 이 장은 이 변경 하나를 사고 없이 운영에 내보내기 위해 팀이 무엇을 자동화하고 무엇을 코드로 바꾸는지를 차례로 봅니다.

커밋은 다섯 관문을 지나 운영에 닿는다

  1. 커밋, PR작은 단위로 리뷰
  2. CI빌드, 테스트, 스캔
  3. 아티팩트이미지 한 번만 빌드
  4. 환경 승격dev, stage, prod
  5. 무중단 교체배포 전략, 롤백

앞 슬라이드의 손 배포를 단계로 나누면 이 다섯 관문이 됩니다. 변경을 기록하고 동료에게 검토받는 단계, 그 변경이 망가뜨린 것이 없는지 기계가 검사하는 단계(CI), 검사를 통과한 결과물 하나를 만드는 단계(아티팩트, 실행 가능한 빌드 결과물), 그 결과물을 시험 환경에서 운영 환경으로 차례로 올리는 단계(승격), 마지막으로 사용자를 멈추지 않고 옛 버전을 새 버전으로 바꾸는 단계입니다.

이 다섯 단계를 매번 같은 순서와 같은 조건으로 자동 실행하도록 묶은 것을 파이프라인이라 부르고, CI/CD는 이 길 전체를 파이프라인으로 바꾸는 일입니다. 첫 관문은 변경을 기록하는 도구인 Git에서 시작합니다.

Git의 커밋은 스냅숏, 브랜치는 이름표다

CI/CD의 모든 단계는 Git이라는 버전 관리 도구 위에서 움직이므로, 이 장에서 쓰는 Git 용어 몇 개를 먼저 정리합니다.

커밋은 어느 순간의 프로젝트 파일 전체를 찍어 둔 스냅숏입니다. 각 커밋에는 내용과 바로 앞 커밋을 가리키는 정보가 들어 있고, 이것을 SHA-1 해시로 계산한 40자리 16진수가 커밋의 이름이 됩니다(3f9c2ab…). 내용이 한 글자만 달라도 해시가 바뀌므로, 커밋 해시 하나가 정확히 하나의 코드 상태를 가리킵니다. 이 성질 덕분에 뒤에서 이미지에 커밋 해시를 붙여 "운영에 도는 코드가 정확히 무엇인가"를 추적합니다.

브랜치는 특정 커밋을 가리키는 움직이는 이름표입니다. 새 커밋을 만들면 이름표가 그 커밋으로 옮겨 갑니다. 팀이 공유하는 기준 브랜치를 보통 main이라 부르고, 각자는 main에서 갈라져 나온 작업 브랜치(feature/new-checkout)에서 일합니다.

작업 브랜치의 커밋을 다시 main에 합치는 것을 병합이라 합니다. 합치는 방법에 따라 main에 남는 기록의 모양이 달라지는데, 그 차이를 다음 슬라이드에서 봅니다.

merge, rebase, squash는 기록의 모양이 다르다

merge는 두 줄기의 끝을 잇는 병합 커밋을 하나 새로 만들어, 갈라졌다 합쳐진 모양을 그대로 남깁니다. rebase는 내 커밋들을 최신 main 끝에 하나씩 다시 적용해 한 줄로 곧게 만듭니다. 다시 적용하므로 커밋 내용은 같아도 해시는 모두 새것이 됩니다. squash는 PR 안의 커밋 여러 개를 하나로 눌러 main에 올립니다.

방식무엇을 하나남는 기록주의점
merge병합 커밋을 새로 만듦분기와 합류가 그대로기록이 갈라져 복잡
rebase내 커밋을 main 끝에 다시 쌓음한 줄로 곧은 기록공유 브랜치에선 금지
squashPR의 커밋을 하나로 압축PR당 커밋 하나중간 커밋 정보 사라짐

rebase가 공유 브랜치에서 금지인 이유는 해시가 바뀌기 때문입니다. 동료가 이미 받아 간 커밋을 rebase한 뒤 서버의 기록을 덮어쓰는 강제 push를 하면, 동료의 기록과 서버의 기록이 어긋납니다. 그래서 많은 팀이 작업 중에는 자기 브랜치를 rebase로 main에 맞추고, 합칠 때는 squash로 PR당 커밋 하나를 남깁니다.

PR은 합치기 전에 사람과 기계가 함께 본다

작업 브랜치를 main에 합치기 전에 검토를 받는 절차가 PR입니다. "이 브랜치를 main에 합쳐 달라"는 요청이자 리뷰의 단위로, 바뀐 줄과 토론, 검사 결과가 한 화면에 모입니다. 기계는 빌드와 테스트, 정적 분석 결과를 PR에 붙이고, 사람은 설계와 의도, 놓친 경우를 봅니다.

리뷰 품질은 PR 크기에 크게 좌우됩니다. 수천 줄짜리 PR은 꼼꼼히 읽을 수 없어 대충 승인되기 쉽고, 문제가 생겨도 원인을 좁히기 어렵습니다.

order-api 팀도 처음에는 새 결제 흐름 전체를 PR 하나로 올리려 했습니다. 3,000줄짜리 PR은 이틀 동안 아무도 열어 보지 않았고, 그사이 main은 계속 바뀌었습니다.

팀은 이것을 화면 단위, API 단위의 작은 PR 여러 개로 나눴습니다. 그러자 리뷰가 몇 시간 안에 끝났습니다. 그런데 미완성 기능이 조각조각 main에 들어가도 괜찮은가라는 질문이 남습니다. 이 질문은 브랜치 전략을 본 뒤에 답합니다.

브랜치 보호 규칙이 main을 지킨다

PR이라는 절차가 있어도, 누군가 main에 직접 커밋을 올리면 리뷰와 검사를 모두 건너뜁니다. 그래서 저장소 설정에서 브랜치 보호 규칙으로 절차를 강제합니다. 규칙은 사람의 선의가 아니라 시스템이 지키게 하는 장치입니다.

GitHub에서는 같은 일을 하는 더 새로운 기능으로 저장소 규칙(ruleset)도 있지만, 강제하는 내용은 같습니다.

  • 필수 상태 검사(status check): CI 같은 자동 검사가 PR에 "성공"을 보고해야만 병합 버튼이 열립니다. 빨간 PR은 아무도 합칠 수 없습니다.
  • 필수 승인: 정한 인원 이상의 승인을 요구합니다. CODEOWNERS 파일에 "결제 패키지는 결제 담당자가 본다"처럼 경로별 책임자를 적으면, 그 경로를 건드린 PR은 책임자 승인이 있어야 합니다.
  • 직접 push, 강제 push 금지: 모든 변경이 PR을 거치게 하고, 기록을 덮어쓰지 못하게 합니다.

Git Flow는 릴리스를 묶어 내는 팀의 방식

브랜치를 어떻게 나누고 언제 합칠지 정한 팀의 약속을 브랜치 전략이라 합니다. 가장 오래되고 구조가 복잡한 것이 Git Flow입니다.

Git Flow는 브랜치 다섯 종류를 둡니다. main은 실제로 출시된 버전만 담습니다. develop은 다음 출시를 위해 기능이 모이는 통합 브랜치입니다. feature는 기능 하나를 만드는 브랜치로 develop에서 갈라져 develop으로 돌아갑니다. 출시 시점이 되면 develop에서 release 브랜치를 떼어 버그만 고치며 안정화하고, 끝나면 main과 develop 양쪽에 합칩니다. 운영에서 급한 버그가 나면 main에서 hotfix를 떼어 고칩니다.

이 구조는 "버전 3.2를 다음 달에 출시하고, 그동안 3.1의 버그도 고친다"처럼 버전을 묶어 정해진 주기로 내보내는 소프트웨어에 맞습니다. 앱 스토어 심사를 거치는 모바일 앱이나 고객이 설치해 쓰는 제품이 그렇습니다.

반대로 하루에도 여러 번 배포하는 웹 서비스에는 무겁습니다. 기능이 develop과 release를 거치며 며칠씩 대기하고, 양쪽에 합치는 과정에서 충돌이 자주 납니다. 그래서 웹 서비스는 더 단순한 전략을 씁니다.

웹 서비스는 짧은 브랜치로 자주 합친다

GitHub Flow는 main 하나와 짧게 사는 기능 브랜치만 둡니다. main은 언제나 배포할 수 있는 상태이고, PR이 병합되면 곧 배포됩니다. Trunk-Based는 여기서 더 나아가, 모두가 기준 브랜치(trunk, 곧 main)에 몇 시간 단위로 작은 변경을 합칩니다.

전략구조브랜치 수명맞는 팀
Git Flowmain, develop, feature, release, hotfix며칠~몇 주정해진 주기로 릴리스
GitHub Flowmain + 짧은 기능 브랜치, PR하루~며칠수시 배포하는 웹 서비스
Trunk-Basedmain에 하루 여러 번 병합몇 시간 이내CI 성숙, Feature Flag 사용

표의 마지막 열이 보여 주듯, 브랜치 수명이 짧을수록 받쳐 줄 장치가 더 필요합니다. 왜 그런 장치까지 써 가며 브랜치를 짧게 가져가려 하는지 다음 슬라이드에서 봅니다.

브랜치가 오래 살수록 병합은 비싸진다

브랜치가 갈라져 있는 동안 main도 계속 바뀝니다. 2주 동안 따로 작업한 브랜치는 2주 치 차이를 한꺼번에 맞춰야 하고, 충돌을 푸는 사람은 양쪽 의도를 모두 이해해야 합니다. 이것을 흔히 "병합 지옥"이라 부릅니다.

Trunk-Based는 이 비용을 작은 변경을 자주 합쳐서 매번 조금씩 치르는 방식입니다. 그 대가로 앞에서 남긴 질문, 즉 아직 완성되지 않은 기능도 main에 들어간다는 문제가 생깁니다.

그래서 Trunk-Based는 두 장치와 함께 씁니다.

  • Feature Flag: 코드 안에 "이 기능을 켤까"를 묻는 조건문을 두고, 미완성 기능은 꺼 둔 채 합칩니다. 코드는 배포됐지만 사용자에게는 보이지 않습니다. 동작 원리는 3부에서 봅니다.
  • 빠르고 믿을 만한 CI: 하루 수십 번 합치려면 매 병합의 검증이 10분 안팎에 끝나야 하고, 실패하면 바로 고쳐야 합니다.

두 번째 장치가 바로 CI입니다.

CI는 자주 합치고 매번 검증하는 습관이다

지속적 통합(CI)은 원래 도구가 아니라 습관의 이름입니다. 모든 개발자가 하루에도 여러 번 main에 코드를 합치고, 합칠 때마다 자동으로 빌드와 테스트를 돌려 "main은 언제나 동작한다"는 상태를 지킵니다.

핵심은 피드백 시간입니다. 버그를 방금 짠 코드에서 찾으면 무엇을 바꿨는지 머릿속에 남아 있어 몇 분이면 고칩니다. 2주 뒤에 찾으면 어느 변경이 원인인지 찾는 데만 반나절이 걸립니다.

그래서 CI가 제대로 돌아가는 팀에는 공통 규칙이 있습니다.

  • main이 깨지면 새 기능보다 복구가 먼저입니다. 깨진 위에 쌓은 변경은 검증이 의미가 없기 때문입니다.
  • 로컬 결과가 아니라 깨끗한 CI 환경의 결과를 믿습니다. 내 노트북에만 있는 파일과 설정이 결과를 바꾸기 때문입니다.
  • CI가 느리면 사람들이 기다리지 않고 합치므로, 속도도 품질의 일부로 관리합니다.

CI 서버는 이벤트를 받아 검사를 돌리고 보고한다

  1. 이벤트PR 생성, push
  2. 실행 머신 배정깨끗한 빌드 환경
  3. 정의된 단계 실행저장소의 설정 파일대로
  4. 결과 보고PR에 성공, 실패 표시

습관을 기계가 강제하려면 "합치려는 순간"을 기계가 알아채야 합니다. CI 서버는 저장소에서 PR이 열리거나 커밋이 올라오는 이벤트를 받아, 빌드용 머신 하나를 깨끗한 상태로 준비하고, 저장소 안의 설정 파일에 적힌 단계를 차례로 실행한 뒤, 결과를 PR에 성공 또는 실패로 표시합니다. 이 표시가 앞에서 본 필수 상태 검사의 입력이 됩니다.

이 일을 하는 제품으로 GitHub Actions, GitLab CI, Jenkins 등이 있고, 2부에서 GitHub Actions를 기준으로 실행 구조를 자세히 봅니다. 그 전에 CI 다음 단계, 즉 검증된 코드를 운영에 내보내는 쪽의 용어를 정리합니다.

Delivery는 버튼을 남기고 Deployment는 없앤다

CI/CD의 CD는 두 가지를 가리킵니다. 지속적 전달은 운영 배포 직전까지 모든 것을 자동화해 main을 언제든 내보낼 수 있는 상태로 두고, 마지막 "지금 내보낸다"는 결정만 사람이 버튼으로 내립니다. 지속적 배포는 그 결정까지 파이프라인에 맡겨, 검사를 통과한 모든 변경이 곧바로 운영에 나갑니다.

구분지속적 전달(Delivery)지속적 배포(Deployment)
운영 반영사람이 승인 버튼을 누름검사 통과 시 자동
보장하는 것언제든 배포 가능한 상태모든 변경이 곧바로 운영에
필요한 전제자동화된 빌드와 테스트강한 테스트, 자동 롤백
어울리는 곳규제, 출시 시점 조율 필요작은 변경을 수시 배포

둘의 차이는 기술보다 신뢰의 문제입니다. 테스트와 운영 지표를 사람의 눈보다 믿을 수 있어야 버튼을 없앨 수 있습니다. order-api 팀은 우선 지속적 전달을 목표로 잡았습니다.

파이프라인은 싼 검사부터 비싼 검사 순으로

  1. 빌드컴파일, 의존성 해석
  2. 테스트단위, 통합
  3. 분석, 스캔린트, 보안 검사
  4. 아티팩트이미지 빌드, 푸시
  5. 배포, 확인스모크 테스트

order-api의 파이프라인은 이 다섯 단계입니다. 빌드는 소스를 컴파일하고 Java 빌드 도구인 Gradle이 필요한 라이브러리를 내려받아 맞추는 단계, 테스트는 코드가 의도대로 동작하는지 확인하는 단계, 분석과 스캔은 코드를 실행하지 않고 읽기만 해서 문제를 찾는 단계, 아티팩트는 배포할 이미지를 만드는 단계, 마지막은 배포 직후 핵심 기능을 실제로 호출해 보는 단계입니다.

순서에는 이유가 있습니다. 컴파일 오류는 몇십 초 만에 드러나지만 통합 테스트는 몇 분이 걸립니다. 앞 단계가 실패하면 뒤 단계는 돌지 않으므로, 싸고 빨리 실패하는 검사를 앞에 둘수록 평균 피드백 시간이 짧아집니다. 서로 의존하지 않는 단계는 병렬로 돌립니다. 이제 각 단계가 무엇을 잡는지 하나씩 봅니다.

테스트는 아래가 넓은 피라미드로 쌓는다

테스트는 무엇을 진짜로 쓰고 무엇을 가짜로 바꾸느냐에 따라 세 층으로 나눕니다.

단위 테스트는 클래스나 함수 하나만 검사합니다. DB나 외부 API처럼 느리거나 통제할 수 없는 의존 대상은 미리 정한 값을 돌려주는 가짜 객체(목)로 바꿉니다. 밀리초 단위로 끝나므로 수천 개를 매 커밋마다 돌릴 수 있습니다.

통합 테스트는 실제 DB나 메시지 브로커와 함께 돌립니다. 목은 SQL 문법 오류나 인덱스 누락을 잡지 못하기 때문입니다. 대신 준비할 것이 많고 몇 초에서 몇 분이 걸립니다.

E2E 테스트는 배포된 시스템 전체를 사용자처럼 호출합니다. 로그인부터 주문 완료까지 화면이나 API를 실제로 거칩니다. 가장 실제와 가깝지만 가장 느리고, 네트워크나 타이밍 때문에 이유 없이 깨지기도 합니다.

그래서 단위를 가장 많이, 통합은 적당히, E2E는 핵심 흐름 몇 개만 두는 테스트 피라미드가 권장됩니다. E2E가 잔뜩 쌓인 역삼각형이 되면 CI가 30분을 넘기고, 원인 모를 실패가 늘어 결국 아무도 결과를 믿지 않게 됩니다. 이 문제는 5부의 flaky 테스트에서 다시 봅니다.

통합 테스트는 컨테이너로 진짜 DB를 띄운다

@SpringBootTest
@Testcontainers
class OrderRepositoryTest {

  @Container @ServiceConnection
  static MySQLContainer<?> mysql =
      new MySQLContainer<>("mysql:8.4");

  @Autowired OrderRepository orders;

  @Test
  void findsPendingOrders() {
    orders.save(Order.pending("A-1"));
    assertThat(orders.findPending())
        .hasSize(1);
  }
}

통합 테스트에 진짜 DB가 필요하다면, CI 머신마다 MySQL을 설치해 둘 수는 없습니다. Testcontainers는 테스트 코드가 시작될 때 Docker로 DB 컨테이너를 띄우고 끝나면 지우는 라이브러리입니다.

강조한 두 줄이 MySQL 8.4 컨테이너를 선언합니다. @ServiceConnection은 그 컨테이너의 접속 주소를 Spring의 데이터소스 설정에 자동으로 넣어 줍니다(Spring Boot 3.1부터). 그래서 테스트는 운영과 같은 종류의 DB에 실제 SQL을 보냅니다.

정적 분석은 코드를 실행하지 않고 읽는다

테스트는 코드를 실행해서 결과를 봅니다. 그런데 어떤 문제는 실행해 보지 않아도 코드만 읽으면 보입니다. 닫지 않은 자원, 사용자 입력을 그대로 이어 붙인 SQL 같은 패턴입니다. 이렇게 실행 없이 소스를 분석하는 것을 정적 분석이라 하고, 코드 스타일까지 검사하는 가벼운 도구를 흔히 린터라 부릅니다.

보안 쪽에서는 대상을 둘로 나눕니다. SAST는 내가 짠 코드에서 SQL Injection처럼 공격에 쓰일 수 있는 패턴을 찾습니다(취약점 자체는 7장에서 봤습니다). SCA는 내가 가져다 쓴 라이브러리 목록을 공개 취약점 데이터베이스와 대조합니다.

이때 기준이 되는 것이 CVE입니다. 공개된 보안 취약점마다 붙이는 전 세계 공통 번호로, CVE-2021-44228처럼 씁니다. 각 CVE에는 영향받는 버전과 심각도(Critical, High, Medium, Low)가 함께 기록됩니다.

SCA가 중요한 이유는 현대 애플리케이션 코드의 대부분이 라이브러리이기 때문입니다. 방금 든 번호가 2021년의 Log4Shell입니다. 널리 쓰이던 로깅 라이브러리 Log4j의 취약점으로, 로그에 찍힌 문자열 하나로 서버에서 임의 코드를 실행할 수 있었습니다. 내 코드는 한 줄도 틀리지 않았지만 서비스가 위험해진 사고였고, 이런 것은 SCA만 잡을 수 있습니다.

검사 대상마다 맡는 스캐너가 다르다

앞에서 본 두 가지 외에, 컨테이너 시대에는 대상이 둘 더 늘었습니다. 이미지 안의 운영체제 패키지(9장의 베이스 이미지에 깔린 openssl 같은 것)와, 실수로 커밋에 섞여 들어간 비밀 값입니다. 다섯 대상을 표로 정리하면 이렇습니다.

검사무엇을 보나대표 도구
린트, 정적 분석스타일, 버그 패턴, 복잡도Checkstyle, SpotBugs, SonarQube
SAST내 코드의 취약 패턴CodeQL, Semgrep
SCA라이브러리의 알려진 CVEDependabot, OWASP Dependency-Check
이미지 스캔베이스 이미지 OS 패키지 CVETrivy, Grype, ECR 스캔
시크릿 스캔커밋에 섞인 키, 토큰gitleaks, GitHub secret scanning

도구를 붙이는 것은 쉽습니다. 어려운 것은 그 결과로 무엇을 막을지 정하는 일이고, 그 기준이 없으면 스캐너는 금방 무시당합니다.

스캔 결과는 차단 기준을 정해야 쓸모 있다

order-api에 스캐너를 처음 붙이자 경고가 400개 넘게 쏟아졌습니다. 전부 빌드 실패로 만들면 아무도 배포하지 못하고, 전부 경고로만 두면 아무도 보지 않습니다.

그래서 심각도로 차단선을 긋습니다. 예를 들어 "고칠 수 있는 버전이 이미 나온 Critical, High CVE가 있으면 실패, 나머지는 리포트만"처럼 정합니다. 기존 경고 400개는 기준선으로 묶어 두고 새로 생긴 것만 막은 뒤, 기준선은 따로 일정을 잡아 줄여 갑니다.

스캔은 한 번으로 끝나지 않습니다. 어제 깨끗했던 이미지도 오늘 새 CVE가 공개되면 취약해집니다. 코드는 그대로인데 세상의 지식이 바뀐 것입니다.

그래서 레지스트리에 올라간 이미지를 주기적으로 다시 스캔하고, 의존성에 새 버전이 나오면 버전을 올리는 PR을 자동으로 만들어 주는 봇(Dependabot, Renovate)을 함께 씁니다. 그 PR도 CI를 거치므로, 업데이트가 무언가를 깨뜨리면 병합 전에 드러납니다.

아티팩트는 검증을 통과한 실행 단위다

검사를 모두 통과했다면 배포할 물건을 만듭니다. 빌드의 결과물 중 실제로 배포하는 단위를 아티팩트라 합니다. Java라면 JAR 파일, 컨테이너 환경이라면 그 JAR와 JRE, 운영체제 파일을 함께 담은 컨테이너 이미지입니다.

아티팩트는 버전 이름을 붙여 저장소에 보관합니다. 이미지라면 9장에서 본 레지스트리, 즉 이미지를 이름과 태그로 올리고 내려받는 서버에 둡니다.

order-api 팀의 예전 방식에서는 개발자 노트북이 아티팩트를 만들었습니다. 그 노트북에 있던 커밋 안 된 파일, 그 노트북의 Gradle 캐시, 그 노트북의 JDK 버전이 모두 결과물에 섞였습니다.

파이프라인에서는 깨끗한 CI 머신이 정해진 커밋으로만 아티팩트를 만듭니다. 그래서 같은 커밋이면 누가 언제 눌러도 같은 결과물이 나옵니다. 남은 질문은 이 결과물을 여러 환경에 어떻게 내보내느냐입니다.

이미지는 한 번만 빌드하고 환경마다 승격한다

운영에 내보내기 전에는 보통 시험용 환경을 거칩니다(환경은 다음 슬라이드들에서 자세히 봅니다). 이때 핵심 원칙은 stage에서 검증한 바로 그 이미지를 prod에 내보내는 것입니다. 이렇게 같은 아티팩트를 다음 환경으로 올리는 것을 승격이라 합니다.

환경마다 다시 빌드하면 그사이 라이브러리나 베이스 이미지가 바뀌어, 테스트한 것과 다른 바이너리가 나갈 수 있습니다. 환경 차이는 이미지 밖에서 주입하는 설정으로만 만듭니다.

태그는 사람용 SemVer와 기계용 커밋 SHA

같은 이미지를 여러 환경에 승격하려면, 그 이미지를 정확히 가리킬 이름이 필요합니다. 이미지 이름 뒤의 태그가 그 역할을 합니다.

SemVer는 MAJOR.MINOR.PATCH 형식입니다. 하위 호환이 깨지면 MAJOR, 기능이 추가되면 MINOR, 버그만 고치면 PATCH를 올립니다. 라이브러리나 외부 공개 API처럼 사용자가 버전 번호를 보고 업그레이드를 판단해야 할 때 씁니다.

서비스 배포용 이미지에는 Git 커밋 해시(SHA)를 태그로 붙이는 방식이 흔합니다. 앞에서 봤듯 해시 하나가 코드 상태 하나를 가리키므로, order-api:3f9c2ab만 보고 어떤 코드인지 바로 찾아갈 수 있습니다.

latest 태그로 배포하면 안 되는 이유는 셋입니다.

  • 같은 이름이 계속 다른 이미지를 가리켜, 지금 운영에 무엇이 떠 있는지 알 수 없습니다.
  • 노드마다 받은 시점이 달라 같은 Deployment 안에 서로 다른 버전이 섞입니다.
  • 롤백할 "이전 버전"의 이름이 없습니다.

태그도 누군가 덮어쓸 수 있으므로, 가장 엄격하게는 9장에서 본 digest, 즉 이미지 내용의 해시(@sha256:…)로 고정합니다.

환경은 목적에 따라 dev, stage, prod로 나눈다

승격이 거치는 단계를 환경이라 합니다. 같은 애플리케이션을 서로 다른 목적으로 띄워 둔, 서로 격리된 실행 공간입니다. dev는 개발자들이 합친 기능이 함께 동작하는지 보는 곳, stage는 운영과 같은 구성으로 최종 확인하는 리허설 무대, prod는 실제 사용자가 쓰는 운영 환경입니다.

환경목적데이터배포 방식
dev개발 중 기능 통합 확인가짜 데이터main 병합 시 자동
stage운영과 같은 구성으로 최종 검증익명화한 운영 유사 데이터자동 또는 버튼
prod실제 사용자실데이터, 접근 통제승인 후 배포

stage가 운영과 다르게 생기면(DB 버전, 인스턴스 크기, 네트워크 경로) stage에서 통과한 것이 운영에서 깨집니다. 환경 사이의 차이를 줄이라는 이 원칙은 4부 끝에서 볼 12-Factor App(클라우드에서 잘 도는 앱의 12개 원칙)의 한 항목이고, 그 차이를 코드로 고정하는 도구가 4부의 IaC입니다.

설정은 밖에서 주입하고 비밀은 따로 둔다

# 기본값과 자리만 정의
spring:
  datasource:
    url: ${DB_URL}
    password: ${DB_PASSWORD}
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:local}

# 값은 실행 환경이 채운다
# 일반 설정 → 환경 변수, ConfigMap
# 비밀 값  → Secret, 외부 비밀 저장소

같은 이미지가 dev에서는 dev DB에, prod에서는 prod DB에 붙으려면 설정이 이미지 밖에 있어야 합니다. ${DB_URL}은 "실행할 때 같은 이름의 환경 변수 값으로 채워라"는 자리표시자입니다. ${이름:기본값}처럼 쓰면 값이 없을 때 기본값을 씁니다.

프로필은 Spring이 환경별 설정 묶음을 고르는 이름입니다. prod로 실행하면 application-prod.yml이 기본 파일 위에 덮입니다. Kubernetes에서는 10장의 ConfigMap과 Secret이 이 환경 변수를 넣어 줍니다.

비밀번호는 이미지에도 Git에도 넣지 않는다

설정 중에서도 DB 비밀번호와 외부 API 키 같은 시크릿은 따로 다룹니다. 이미지에 넣으면 이미지를 받을 수 있는 모든 사람이 비밀번호를 갖게 되고, Git에 넣으면 저장소를 볼 수 있는 모든 사람과 그 기록이 남는 모든 곳에 퍼집니다.

10장에서 봤듯 Kubernetes Secret은 기본적으로 base64로 적어 둘 뿐 암호화가 아닙니다. 그래서 원본은 별도 비밀 저장소에 두고, 실행 시점에 받아 오는 구성이 흔합니다.

AWS에서는 비밀 값을 암호화해 보관하고 접근 기록을 남기는 Secrets Manager와 Parameter Store가 이 역할을 합니다(16장). 앱은 시작할 때 자기 권한으로 값을 읽고, 사람은 저장소의 값을 직접 볼 필요가 없습니다.

정리하면 order-api 이미지에는 코드와 설정의 자리만 들어 있고, 일반 설정은 환경 변수로, 비밀은 비밀 저장소에서 들어옵니다. 이제 그 이미지가 운영에 배포된 직후를 봅니다.

스모크 테스트는 배포 직후의 첫 숨 확인

배포가 "성공"했다는 것은 새 Pod가 떴다는 뜻일 뿐, 서비스가 제대로 동작한다는 뜻은 아닙니다. 설정이 잘못되어 결제 API만 500을 낼 수도 있습니다.

스모크 테스트는 배포 직후 핵심 경로 몇 개만 실제로 호출해 보는 짧은 검사입니다. 이름은 전자 기기에 처음 전원을 넣을 때 연기가 나는지부터 본다는 데서 왔습니다.

좋은 스모크 테스트는 다음 조건을 갖춥니다.

  • 1~2분 안에 끝나고, 실패하면 파이프라인이 롤백이나 알림으로 이어집니다. 오래 걸리면 그동안 사용자가 문제를 먼저 겪습니다.
  • 서버가 살아 있는지만 묻는 헬스 체크가 아니라 로그인, 주문 조회처럼 DB와 외부 연동을 실제로 거치는 경로를 봅니다.
  • 운영 데이터를 오염시키지 않도록 읽기 위주이거나 테스트 계정을 씁니다.

1부의 길을 order-api에 그려 보면

지금까지 본 관문을 order-api 팀의 하루로 다시 이어 보겠습니다. 개발자가 feature/checkout-api 브랜치에서 결제 API 하나를 만들고 PR을 엽니다. 브랜치 보호 규칙 때문에 CI가 통과하고 결제 담당자가 승인해야만 병합할 수 있습니다.

CI는 컴파일, 단위 테스트, Testcontainers 통합 테스트, 정적 분석과 스캔을 싼 것부터 차례로 돌립니다. 모두 통과해 병합되면 커밋 해시를 태그로 단 이미지 order-api:3f9c2ab가 레지스트리에 한 번 올라가고, dev에 자동으로 배포됩니다.

같은 이미지가 stage로 승격되고, 담당자가 승인 버튼을 누르면 prod로 갑니다. 각 환경은 환경 변수와 비밀 저장소로 자기 설정만 넣고, 배포 직후 스모크 테스트가 주문 조회와 결제 준비 API를 호출해 봅니다.

여기에는 아직 답하지 않은 질문이 셋 남아 있습니다. 이 파이프라인을 실제로 무엇이 어떻게 돌리는가(2부), 운영의 옛 버전을 사용자 모르게 새 버전으로 어떻게 바꾸는가(3부), 그리고 그 아래의 네트워크와 DB는 누가 어떻게 만드는가(4부)입니다.

2부

파이프라인은 무엇이 어떻게 돌리나

1부에서 그린 길을 실제로 실행하는 도구를 봅니다. 가장 널리 쓰이는 GitHub Actions를 기준으로, 파이프라인이 어떤 단위로 나뉘고, 어느 머신에서 돌고, 운영 클라우드에 배포할 권한을 어떻게 얻는지 따라갑니다.

기초 원리 여기부터는 도구의 실행 구조와 권한 위임의 동작을 다룹니다.

GitHub Actions는 저장소 안의 YAML로 움직인다

order-api 팀은 코드가 이미 GitHub에 있으므로 별도 서버 없이 쓸 수 있는 GitHub Actions를 골랐습니다. 1부에서 본 CI 서버의 네 가지 일, 즉 이벤트를 받고, 머신을 배정하고, 단계를 실행하고, 결과를 보고하는 일을 GitHub이 직접 합니다.

무엇을 할지는 저장소 안의 .github/workflows/ 폴더에 둔 YAML 파일로 적습니다. 파일 하나가 워크플로 하나입니다. 파이프라인 정의가 코드와 같은 저장소에 있으므로, 파이프라인을 바꾸는 일도 PR로 리뷰받고 기록으로 남습니다.

워크플로는 세 겹으로 이루어집니다. 맨 위에는 언제 실행할지 정하는 트리거가 있습니다. 그 아래에 독립된 작업 단위인 job이 하나 이상 있고, 각 job 안에 차례로 실행할 명령인 step이 줄지어 있습니다.

그리고 job을 실제로 실행하는 머신을 러너라 부릅니다. 이 네 단어(트리거, job, step, 러너)가 어떻게 맞물리는지가 GitHub Actions 구조의 전부이고, 다음 슬라이드에서 그림으로 봅니다.

워크플로는 job으로, job은 step으로 나뉜다

트리거(push, PR 등)가 일어나면 워크플로가 시작됩니다. 워크플로 안의 job마다 새 러너 하나가 배정됩니다. 그래서 job끼리는 기본적으로 병렬로 돌고 파일 시스템을 공유하지 않습니다. 순서가 필요하면 needs로 "이 job은 저 job이 성공한 뒤에"라고 잇습니다.

job 안의 step은 같은 러너에서 위에서 아래로 차례로 실행되므로, 앞 step이 만든 파일을 뒤 step이 그대로 씁니다.

첫 워크플로: PR마다 테스트를 돌린다

name: ci
on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '21'
      - run: ./gradlew test

order-api 팀의 첫 워크플로입니다. on은 트리거로, main을 향한 PR이 열리거나 커밋이 추가될 때 실행합니다. jobs 아래 test라는 job 하나가 있고, runs-on으로 러너 종류를 고릅니다.

step은 두 종류입니다. run은 셸 명령을 그대로 실행합니다. uses는 남이 만들어 공개한 재사용 부품인 액션을 불러옵니다. checkout은 저장소 코드를 러너에 내려받고, setup-java는 JDK 21을 설치합니다. with는 액션에 넘기는 입력값입니다.

트리거가 워크플로를 언제 돌릴지 정한다

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
    paths-ignore: ['docs/**', '**.md']
  workflow_dispatch:        # 수동 실행 버튼
  schedule:
    - cron: '0 18 * * *'      # UTC 기준

concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true

첫 워크플로는 PR에만 반응했습니다. 병합 뒤 main에서도 돌리려면 push를 더합니다. paths-ignore는 문서만 바뀐 커밋을 건너뜁니다. workflow_dispatch는 웹 화면에 수동 실행 버튼을 만듭니다.

schedule의 cron은 분, 시, 일, 월, 요일 다섯 칸으로 시각을 적는데 UTC 기준이라 한국 새벽 3시는 18시입니다. ${{ }}는 실행 시점에 값을 채우는 표현식이고, github.ref는 실행된 브랜치 이름입니다. concurrency는 같은 그룹의 실행이 겹치지 않게 해 배포 두 개가 동시에 도는 사고를 막습니다.

러너는 매번 새로 받는 깨끗한 머신이다

앞의 runs-on: ubuntu-latest는 GitHub이 관리하는 가상 머신(9장의 VM)을 job마다 새로 받아 쓰고, job이 끝나면 버린다는 뜻입니다. 이전 실행의 찌꺼기가 없으니 1부에서 말한 "깨끗한 CI 환경"이 저절로 보장되지만, 매번 의존성을 처음부터 받아야 하는 비용이 있습니다.

job에는 timeout-minutes를 꼭 둡니다. 기본값이 360분이라, 멈춘 테스트 하나가 6시간 동안 러너를 붙잡고 사용 시간 요금을 씁니다.

러너를 회사 서버에 직접 띄우는 셀프 호스팅도 있습니다. 사내망 DB에 접근해야 할 때 씁니다.

공개 저장소에서는 누구나 PR로 코드를 보내 그 러너에서 실행시킬 수 있어, 재사용되는 셀프 호스팅 러너가 공격 발판이 됩니다.

matrix는 job 하나를 조합 수만큼 복제한다

jobs:
  test:
    runs-on: ${{ matrix.os }}
    timeout-minutes: 20
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        java: ['17', '21']
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: ${{ matrix.java }}
      - run: ./gradlew test

job이 러너마다 따로 돈다는 성질을 이용하면 같은 job을 조건만 바꿔 여러 벌 돌릴 수 있습니다. matrix에 운영체제 2개와 Java 2개를 적으면 곱해서 job 4개가 병렬로 생기고, 각 job 안에서 ${{ matrix.java }}가 자기 값으로 채워집니다.

라이브러리를 여러 런타임에서 검증하거나, 큰 테스트 묶음을 조각으로 나눠 동시에 돌릴 때 씁니다. fail-fast의 기본값은 true라 하나가 실패하면 나머지를 취소합니다. 어느 조합에서만 깨지는지 보려면 false로 둡니다.

cache는 속도용, artifact는 결과 전달용

- uses: actions/cache@v6
  with:
    path: ~/.gradle/caches
    key: gradle-${{ hashFiles('**/*.gradle*') }}
    restore-keys: gradle-

- run: ./gradlew bootJar

- uses: actions/upload-artifact@v7
  with:
    name: app-jar
    path: build/libs/*.jar
    retention-days: 7

러너가 매번 새것이라는 비용을 줄이는 장치가 캐시입니다. Gradle이 내려받은 라이브러리(~/.gradle/caches)를 GitHub 쪽 저장소에 보관했다가 다음 실행에 복원합니다. key는 빌드 파일 내용의 해시라, 의존성이 바뀌면 키가 달라져 새 캐시가 생깁니다. 정확한 키가 없으면 restore-keys 접두어로 가장 가까운 것을 씁니다.

아티팩트는 빌드 결과물을 다른 job에 넘기거나 사람이 내려받게 남깁니다. 캐시는 없어도 빌드가 되고, 아티팩트는 없으면 다음 job이 못 돕니다.

secrets는 가려지고 environment는 문을 단다

deploy:
  needs: build
  runs-on: ubuntu-latest
  environment: production
  steps:
    - run: ./deploy.sh
      env:
        SLACK_URL: ${{ secrets.SLACK_WEBHOOK }}

배포 job에는 비밀 값이 필요합니다. 시크릿은 저장소, 조직, environment 단위로 암호화해 저장하고 secrets.이름으로 꺼내며, 로그에 그 값이 찍히면 ***로 가립니다. 포크, 즉 외부인이 저장소를 복제해 보낸 PR의 워크플로에는 시크릿이 전달되지 않습니다. 누구나 PR을 보낼 수 있으니 그 코드에 비밀을 줄 수 없기 때문입니다.

environment는 배포 대상에 보호 규칙을 붙입니다. 지정한 리뷰어(최대 6명 중 1명)의 승인, 대기 시간, 배포 가능한 브랜치를 걸 수 있고, 승인 전에는 그 환경의 시크릿을 읽을 수 없습니다. 지속적 전달의 "버튼"이 바로 이것입니다.

GITHUB_TOKEN은 필요한 권한만 남긴다

# 워크플로 전체의 기본값
permissions:
  contents: read

jobs:
  label:
    runs-on: ubuntu-latest
    # 이 job만 PR에 쓰기 허용
    permissions:
      pull-requests: write
    steps:
      - run: gh pr edit "$PR" --add-label tested
        env:
          PR: ${{ github.event.number }}
          GH_TOKEN: ${{ github.token }}

워크플로는 우리가 넣은 시크릿 말고도 자격 증명 하나를 자동으로 받습니다. GitHub이 실행마다 발급하고 job이 끝나면 만료되는 GITHUB_TOKEN으로, 코드를 읽거나 PR에 댓글을 다는 데 씁니다.

문제는 이 토큰이 저장소 설정에 따라 넓은 쓰기 권한을 가질 수 있다는 점입니다. 액션 하나가 오염되면 그 권한으로 코드를 고칠 수 있습니다. 그래서 permissions로 기본값을 읽기 전용으로 내리고, 꼭 필요한 job에서만 필요한 권한을 더합니다. 예제의 job은 GitHub 명령줄 도구 gh로 PR에 라벨만 붙이므로 PR 쓰기 권한 하나만 받습니다.

장기 Access Key는 유출되면 끝이 없다

이제 order-api의 배포 job이 AWS의 레지스트리에 이미지를 올리고 운영 클러스터를 바꿀 차례입니다. 그러려면 AWS에 "나는 이 일을 해도 되는 주체다"라고 증명할 자격 증명이 필요합니다.

AWS의 권한 체계는 12장에서 자세히 보지만, 여기서는 세 가지만 알면 됩니다. IAM 사용자는 AWS 안의 사람이나 프로그램 계정이고, Access Key는 그 사용자가 프로그램에서 쓰는 아이디와 비밀번호 한 쌍입니다. 역할은 특정 사용자에게 묶이지 않은 권한 묶음으로, 허락받은 주체가 잠시 "맡아서" 쓰고 내려놓습니다.

예전에는 배포용 IAM 사용자를 만들고 그 Access Key를 GitHub 시크릿에 넣었습니다. 이 키는 누가 지우기 전까지 만료되지 않습니다. 시크릿이 로그에 찍히거나, 오염된 액션이 키를 빼 가거나, 퇴사자의 노트북에 복사본이 남으면, 그 키는 몇 달 뒤에도 운영 계정을 열 수 있습니다.

그래서 질문을 바꿉니다. 저장해 둘 키를 잘 지키는 대신, 저장해 둘 키 자체를 없앨 수는 없을까. 실행할 때마다 GitHub이 "이 실행은 누구다"라고 보증하고, AWS가 그 보증을 믿고 짧게 쓸 키를 내주면 됩니다. 이 보증에 쓰는 표준이 OIDC입니다.

OIDC는 실행마다 서명된 신분증을 발급한다

7장에서 OIDC를 "구글로 로그인"의 표준으로 봤습니다. 로그인 서비스가 "이 사용자는 누구다"를 담은 JWT, 즉 서명된 JSON 토큰을 발급하고, 받는 쪽은 서명을 확인해 그 내용을 믿습니다. GitHub Actions도 같은 표준으로 워크플로 실행에 신분증을 발급합니다.

이 토큰에는 어느 저장소의, 어느 브랜치나 environment에서 실행된 워크플로인지가 sub(주체) 필드에 적힙니다. 예를 들면 repo:acme/order-api:environment:production입니다.

AWS 쪽에는 토큰을 키로 바꿔 주는 STS가 있습니다. STS는 받은 토큰의 서명이 GitHub 것이 맞는지, 그리고 맡으려는 역할의 신뢰 정책(이 역할을 누가 맡을 수 있는지 적은 규칙)과 sub가 맞는지 확인합니다.

통과하면 몇십 분에서 한 시간 뒤 만료되는 임시 자격 증명을 내줍니다. 저장소에 보관할 키가 없으니 유출될 것이 없고, 실행 중에 탈취되더라도 곧 쓸모가 없어집니다. 실제 주고받는 순서를 다음 슬라이드에서 봅니다.

OIDC 토큰은 STS에서 임시 키로 바뀐다

러너GitHub, AWS
id-token: write 토큰 요청 GitHub OIDC 공급자
JWT sub=repo:acme/order-api:… 서명됨
AssumeRoleWithWebIdentity JWT AWS STS
서명, aud, sub를 신뢰 정책과 대조
임시 키 자격 증명만료 시각이 있는 키 세 개

러너는 먼저 GitHub의 OIDC 공급자에게 토큰을 요청합니다. 워크플로에 permissions: id-token: write가 있어야 요청할 수 있는데, 이것은 토큰을 받을 권한일 뿐 저장소를 고칠 권한이 아닙니다.

받은 JWT를 STS의 AssumeRoleWithWebIdentity API(웹 신원 토큰으로 역할을 맡는 요청)에 내면, STS가 대조를 마친 뒤 접근 키, 비밀 키, 세션 토큰 세 개로 된 임시 자격 증명을 돌려줍니다.

신뢰 정책이 어느 실행만 믿을지 정한다

{
  "Effect": "Allow",
  "Principal": {
    "Federated": "<GitHub OIDC 공급자 ARN>" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": { "StringEquals": {
    "token.actions.githubusercontent.com:aud":
      "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub":
      "repo:acme/order-api:environment:production"
  } }
}

AWS 쪽 설정은 배포 역할의 신뢰 정책입니다. 계정에 GitHub을 OIDC 공급자로 미리 등록해 두고, Principal에 그 공급자의 ARN(AWS 리소스의 고유 이름)을 적어 "이 공급자가 발급한 토큰"을, Action은 그 토큰으로 역할을 맡는 요청을 허용한다는 뜻입니다.

핵심은 Condition입니다. aud는 토큰의 수신자가 STS인지, sub는 order-api 저장소의 production environment에서 돈 실행인지 확인합니다. 이 조건을 repo:acme/*처럼 넓히면 조직의 아무 저장소나 운영 역할을 맡을 수 있으니, 저장소와 environment까지 좁힙니다. 정책 문법은 12장에서 봅니다.

빌드부터 ECR 푸시까지 한 워크플로로

permissions: { id-token: write, contents: read }
jobs:
  image:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    environment: production
    steps:
      - uses: actions/checkout@v7
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci
          aws-region: ap-northeast-2
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - run: |
          REG=${{ steps.ecr.outputs.registry }}
          IMG=$REG/order-api:${{ github.sha }}
          docker build -t $IMG . && docker push $IMG

지금까지의 조각을 합친 워크플로입니다. 맨 위 permissions가 OIDC 토큰 요청을 허용하고, 첫 강조 줄의 액션이 앞에서 본 토큰 교환을 대신 해 임시 키를 환경 변수로 깔아 둡니다.

다음 step은 그 키로 ECR, 즉 AWS의 컨테이너 레지스트리(14장)에 로그인하고, id: ecr로 이름 붙인 결과에서 레지스트리 주소를 꺼냅니다. 마지막 step은 9장의 docker build와 push로 커밋 SHA(github.sha)를 태그로 단 이미지를 올립니다.

남이 만든 액션은 커밋 SHA로 고정한다

방금 워크플로에는 남이 만든 액션이 네 개 있습니다. 그 코드는 우리 러너에서, 우리 시크릿과 임시 키를 쥔 채 실행됩니다. 그래서 액션의 출처가 곧 파이프라인의 보안입니다.

uses: 누군가/액션@v4의 v4는 Git 태그라서 작성자가 언제든 다른 커밋으로 옮길 수 있습니다. 액션 저장소가 탈취되면 태그가 악성 코드를 가리키고, 그 액션을 쓰는 모든 워크플로가 다음 실행 때 그 코드를 돌립니다.

실제로 2025년 3월 널리 쓰이던 tj-actions/changed-files의 태그가 바뀌어, 수많은 저장소의 CI 로그에 시크릿이 찍혀 나간 사고가 있었습니다.

그래서 외부 액션은 @<40자리 커밋 SHA>로 고정합니다. 커밋 해시는 내용이 바뀌면 달라지므로 누구도 같은 이름 뒤의 코드를 바꿀 수 없습니다. 업데이트는 Dependabot이 만든 PR로 리뷰합니다.

또 하나 위험한 트리거가 pull_request_target입니다. 포크 PR에 반응하면서도 기본 브랜치의 맥락, 즉 시크릿과 쓰기 권한이 있는 상태로 돕니다. 여기서 PR의 코드를 체크아웃해 실행하면, 앞에서 포크에 시크릿을 주지 않던 보호가 무너져 외부인이 시크릿을 빼 갈 수 있습니다.

Jenkins는 직접 운영하는 범용 자동화 서버

pipeline {
  agent { label 'docker' }
  stages {
    stage('Test')  { steps { sh './gradlew test' } }
    stage('Image') {
      steps {
        sh "docker build -t order-api:${GIT_COMMIT} ."
      }
    }
    stage('Deploy') {
      input { message '운영에 배포할까요?' }
      steps { sh './deploy.sh prod' }
    }
  }
}

GitHub Actions 이전부터 널리 쓰인 도구가 오픈소스 Jenkins입니다. 작업을 계획하는 컨트롤러 서버와 실제로 실행하는 에이전트(빌드 머신)로 나뉩니다. 파이프라인은 Groovy 언어 기반의 Jenkinsfile로 저장소에 둡니다.

agent는 docker 라벨이 붙은 에이전트에서 돌라는 뜻이고, 각 stage가 GitHub Actions의 step 묶음에 해당합니다. 강조한 input은 사람이 누를 때까지 멈추는 승인 버튼입니다.

사내망 안에서 자유롭게 확장할 수 있는 대신, 서버와 수많은 플러그인의 업그레이드, 보안 패치, 백업을 팀이 떠안습니다.

파이프라인 시간은 캐시와 병렬화로 줄인다

파이프라인을 다 갖추자 order-api의 CI는 18분이 걸렸습니다. 1부에서 봤듯 느린 CI는 사람들이 기다리지 않게 만듭니다. 줄이는 방법은 다섯 가지입니다. 라이브러리를 다시 받지 않기, 9장에서 본 Docker 레이어 캐시를 CI에서도 살리기(buildx는 Docker의 확장 빌드 도구로, 캐시를 GitHub 캐시 저장소에 둘 수 있습니다), 바뀌지 않은 모듈의 컴파일과 테스트 결과를 재사용하는 Gradle 빌드 캐시, 테스트를 조각내 동시에 돌리는 샤딩, 그리고 아예 돌릴 필요가 없는 실행을 건너뛰기입니다.

방법무엇을 아끼나예
의존성 캐시라이브러리 다운로드setup-java의 cache: gradle
Docker 레이어 캐시바뀌지 않은 레이어 재빌드buildx cache-to: type=gha
빌드 도구 캐시바뀌지 않은 모듈의 작업Gradle 빌드 캐시
병렬, 분할벽시계 시간matrix로 테스트 샤딩
변경 범위 필터불필요한 실행 자체paths, 영향받은 모듈만

먼저 각 step의 소요 시간을 보고 가장 긴 것부터 줄입니다. 짐작으로 고르면 2분짜리 step을 30초로 줄이느라 10분짜리를 놓칩니다.

3부

멈추지 않고 새 버전으로 바꾸는 법

2부의 파이프라인이 order-api:3f9c2ab 이미지를 레지스트리에 올렸습니다. 남은 일은 운영에서 돌고 있는 옛 버전을 사용자가 눈치채지 못하게 새 버전으로 바꾸는 것입니다. 교체 방식마다 비용, 되돌리는 속도, 위험이 어떻게 다른지, 그리고 어떤 전략을 고르든 앱과 DB가 갖춰야 할 조건이 무엇인지 봅니다.

무중단 배포가 어려운 건 두 버전이 겹쳐서다

사용자가 끊김을 느끼지 않게 새 버전으로 바꾸는 것을 무중단 배포라 합니다. 서버를 끄고 새 버전을 켜면 그사이 요청은 모두 실패하므로, 옛 버전이 요청을 받는 동안 새 버전을 띄워야 합니다. 그러면 잠시라도 두 버전이 동시에 운영됩니다.

겹치는 동안 두 버전은 같은 DB, 같은 캐시, 같은 메시지 큐를 함께 씁니다. 한 사용자의 요청 하나가 v1으로, 바로 다음 요청이 v2로 갈 수도 있습니다.

그래서 배포 전략은 결국 세 질문에 대한 선택입니다.

  • 두 버전의 공존 시간을 얼마나 짧게, 혹은 얼마나 통제하며 가져갈 것인가.
  • 문제가 생겼을 때 몇 명의 사용자가 영향을 받는가.
  • 되돌리는 데 얼마나 걸리고, 그동안 자원을 얼마나 더 쓰는가.

어느 전략을 고르든 공존 자체를 견디는 장치(호환되는 스키마, 우아한 종료)는 따로 필요하며, 이는 3부 뒤쪽에서 봅니다.

교체는 로드 밸런서가 어디로 보내느냐다

모든 배포 전략은 같은 부품 위에서 움직이므로 먼저 그 부품을 상기합니다. 8장에서 봤듯 로드 밸런서는 요청을 여러 서버(대상)에 나눠 보내는 앞단이고, 헬스 체크로 대상이 살아 있는지 주기적으로 물어 죽은 대상을 목록에서 뺍니다. Kubernetes에서는 10장의 Service가 이 역할을 하고, Pod의 readiness 검사를 통과한 Pod만 요청 목록(엔드포인트)에 올립니다.

이렇게 보면 배포란 결국 두 가지 조작의 조합입니다. 하나는 새 버전 인스턴스를 띄워 요청 목록에 넣는 것, 다른 하나는 옛 버전 인스턴스를 목록에서 빼고 종료하는 것입니다. 목록에서 뺀 뒤에도 이미 맺어진 연결과 처리 중인 요청이 끝나길 잠시 기다려 주는 것을 커넥션 드레이닝이라 합니다.

전략의 차이는 이 조작을 얼마만큼씩, 어떤 순서로, 무엇을 보고 하느냐에 있습니다. 한꺼번에 빼고 넣으면 Recreate, 몇 개씩 번갈아 하면 Rolling, 새 묶음을 통째로 준비했다가 한 번에 바꾸면 Blue-Green, 일부 비율만 먼저 보내면 Canary입니다.

가장 단순한 것부터 봅니다.

Recreate: 모두 내리고 새로 올린다

  1. v1 전부 종료

    모든 인스턴스를 내립니다. 이때부터 서비스 중단.

  2. 공백

    새 버전이 뜰 때까지 요청이 실패합니다.

  3. v2 전부 기동

    준비가 끝나면 서비스가 재개됩니다.

Recreate는 옛 인스턴스를 모두 목록에서 빼고 종료한 뒤 새 인스턴스를 띄웁니다. 다운타임이 생기지만 두 버전이 절대 겹치지 않는다는 장점이 있습니다.

그래서 두 버전이 동시에 떠 있으면 안 되는 경우에 씁니다. 한 번에 한 프로세스만 붙을 수 있는 볼륨을 쓰거나, 호환되지 않는 스키마 변경을 공지한 점검 시간에 한꺼번에 할 때입니다. Kubernetes Deployment에서는 strategy.type: Recreate로 지정합니다.

Rolling: 조금씩 바꿔 끼운다

  1. 새 인스턴스 추가

    허용된 여유분만큼 v2를 먼저 띄웁니다.

  2. 준비 확인

    readiness를 통과한 v2만 트래픽을 받습니다.

  3. 옛 인스턴스 제거

    허용된 범위 안에서 v1을 하나씩 내립니다.

  4. 반복

    모두 v2가 될 때까지 되풀이합니다.

Rolling은 인스턴스를 몇 개씩 차례로 교체합니다. 10장에서 본 maxSurge(정원보다 더 띄울 수 있는 수)와 maxUnavailable(정원보다 모자라도 되는 수)이 속도를 정합니다. order-api처럼 Pod 4개에 1과 0이면, 다섯 번째 Pod로 v2를 띄우고 준비되면 v1 하나를 내리는 일을 네 번 반복합니다.

추가 자원이 적어 가장 널리 쓰이고 Deployment의 기본 전략입니다. 약점은 되돌리려면 반대로 다시 굴려야 해 느리고, 배포 내내 두 버전이 섞여 있다는 점입니다.

Blue-Green: 통째로 준비하고 한 번에 전환

Rolling의 느린 롤백을 해결하려면 옛 버전을 지우지 않고 남겨 두면 됩니다. 운영 중인 Blue(v1) 옆에 같은 규모의 Green(v2)을 띄워 검증한 뒤, 로드 밸런서나 Service가 가리키는 대상을 한 번에 Green으로 돌립니다.

Blue를 남겨 두면 롤백은 대상을 되돌리는 것 한 번입니다. 대신 전환 동안 자원이 두 배 들고, 두 환경이 같은 DB를 쓰므로 스키마 호환은 여전히 필요합니다.

Blue-Green의 함정은 전환 순간에 있다

전환은 한 번이지만, 전환 순간 모든 사용자가 새 버전을 만납니다. Green이 검증에서 멀쩡했어도 실제 부하에서 처음 문제가 드러나면 영향은 전체에 미칩니다.

또 Green은 막 뜬 상태입니다. 5장에서 봤듯 JVM은 자주 쓰는 코드를 실행 중에 기계어로 바꾸는 JIT 컴파일 전이라 느리고, 커넥션 풀과 로컬 캐시도 비어 있습니다. 전체 트래픽을 한꺼번에 받으면 첫 몇 분간 지연이 튑니다.

운영에서는 다음을 함께 챙깁니다.

  • 전환 전에 Green에 내부 테스트 트래픽이나 스모크 테스트를 흘려 예열합니다.
  • Blue에서 진행 중인 요청과 오래 유지되는 연결(WebSocket 같은)이 끝나도록 드레이닝 시간을 둡니다.
  • Blue는 롤백이 필요 없다고 확신할 때까지(보통 수십 분~하루) 지우지 않습니다.

전환 순간의 "전체 영향"을 줄이려면, 한 번에 바꾸지 말고 일부에게 먼저 보내야 합니다.

Canary: 일부에게 먼저 내보내고 지표로 판단

  1. 5%v2로 일부 트래픽
  2. 지표 비교에러율, p99 지연
  3. 25%, 50%이상 없으면 확대
  4. 100%v1 정리

이름은 광부들이 유독가스에 먼저 반응하는 카나리아를 탄광에 데려간 데서 왔습니다. 소수 사용자에게 먼저 v2를 보내고, v1과 지표를 비교해 단계적으로 늘립니다. 지표는 요청 중 실패 비율인 에러율과, 느린 쪽 1% 요청의 응답 시간인 p99 지연(5장)이 기본입니다. 나쁘면 그 5%만 되돌리면 되므로 영향 범위가 가장 작습니다.

대신 두 가지가 갖춰져야 합니다. 트래픽을 비율로 나누는 라우팅, 그리고 지표를 버전별로 나눠 보는 관측성(시스템 내부 상태를 지표, 로그, 추적으로 들여다보는 능력, 18장)입니다. 지표를 보지 않는 Canary는 느린 Rolling일 뿐입니다. 비율을 나누는 방법부터 봅니다.

Canary 비율은 인스턴스 수로도 흉내 낸다

가장 단순한 Canary는 같은 Service 뒤에 v1 Pod 9개와 v2 Pod 1개를 두는 것입니다. Service는 요청을 Pod에 고르게 나누므로 약 10%가 v2로 갑니다. 별도 장비 없이 바로 할 수 있습니다.

하지만 이 방식은 비율이 Pod 수에 묶입니다. 1%를 보내려면 Pod 100개가 필요하고, 10장의 HPA가 부하에 따라 Pod 수를 바꾸면 비율도 함께 흔들립니다.

정밀한 Canary는 트래픽 계층에서 가중치를 나눕니다. 10장의 Ingress Controller나 서비스 메시(Istio), AWS의 L7 로드 밸런서인 ALB의 가중치 대상 그룹(13장)은 Pod 수와 상관없이 "v2에 3%"를 정확히 보냅니다. Pod 수는 부하에 맞추고, 비율은 라우팅에 맡기는 것입니다.

특정 사용자만 보내는 것도 가능합니다. 요청 헤더나 쿠키를 보고 사내 직원 요청만 v2로 보내면, 실제 사용자 영향 없이 운영 환경에서 먼저 확인할 수 있습니다. 그렇다면 사용자 영향이 아예 없게 시험하는 방법은 없을까요.

Shadow는 복사한 트래픽으로 몰래 시험한다

Shadow 배포는 운영 요청을 그대로 복제해 v2에도 보냅니다(트래픽 미러링). 사용자에게는 v1의 응답만 돌아가고, v2의 응답은 비교용으로 기록한 뒤 버립니다. 실제 트래픽 패턴과 부하로 시험하면서도 사용자 영향이 0입니다. 검색 엔진 교체나 성능 검증에 잘 맞습니다.

함정은 쓰기 요청입니다. 복제된 결제 요청을 v2가 실제로 처리하면 결제가 두 번 일어납니다. 그래서 읽기 요청만 복제하거나, v2의 외부 호출을 가짜로 막아 둡니다.

A/B 테스트는 위험이 아니라 효과를 잰다

사용자를 나눠 다른 버전을 보여 준다는 점에서 Canary와 비슷해 보이는 것이 A/B 테스트입니다. 하지만 목적이 다릅니다.

Canary는 새 버전이 안전한가를 에러율과 지연으로 판정하고, 확인되면 100%로 갑니다. A/B 테스트는 어느 쪽이 더 나은가를 구매 전환율이나 클릭률로 비교하는 실험입니다. 두 버전 모두 정상이고, 통계적으로 의미 있는 차이가 날 때까지 며칠~몇 주 유지합니다.

기준CanaryA/B 테스트
질문고장 나지 않았나더 효과적인가
지표에러율, 지연전환율, 매출
기간몇 분~몇 시간며칠~몇 주

A/B에서 배정을 고정하는 이유는, 같은 사람이 새로고침마다 다른 화면을 보면 실험 결과가 섞이기 때문입니다.

전략은 비용, 롤백 속도, 위험의 교환이다

3부 첫머리의 세 질문(공존 시간, 영향 범위, 되돌리는 비용)으로 주요 전략 셋을 나란히 놓으면 이렇습니다.

기준RollingBlue-GreenCanary

롤백 속도다시 롤링, 느림전환 한 번, 즉시비율을 0으로, 빠름

필요한 것헬스 체크두 벌의 환경가중치 라우팅, 지표

Recreate는 다운타임을 받아들이는 대신 공존이 없고, Shadow는 사용자 영향이 없는 대신 쓰기 요청을 다루기 어렵습니다. 많은 팀이 기본은 Rolling, 위험한 변경은 Canary, 즉시 롤백이 중요한 핵심 시스템은 Blue-Green으로 섞어 씁니다. AWS 서비스로 구현하는 방법은 18장에서 봅니다.

Feature Flag는 배포와 출시를 분리한다

if (flags.isEnabled("new-checkout", user)) {
    return newCheckout(order);  // 새 흐름
}
return legacyCheckout(order);   // 기존 흐름

// 플래그 규칙 (관리 화면이나 설정 저장소)
// new-checkout: 사내 직원 100%, 일반 사용자 5%

지금까지의 전략은 모두 코드 버전을 교체했습니다. 1부에서 미뤄 둔 Feature Flag는 다른 축에서 위험을 나눕니다. 배포는 코드를 운영 서버에 올리는 기술적 사건이고, 출시는 사용자가 기능을 쓰기 시작하는 비즈니스 사건입니다. Feature Flag는 코드 안의 조건문으로 이 둘을 떼어 놓습니다.

order-api 팀은 새 결제 흐름을 꺼 둔 채 배포하고, 재배포 없이 설정만 바꿔 직원, 5%, 전체 순으로 켭니다. 문제가 생기면 플래그를 끄는 것이 곧 롤백입니다.

플래그는 사용자마다 같은 답을 내야 한다

앞 코드의 flags.isEnabled("new-checkout", user)는 매 요청마다 불립니다. 그때마다 원격 서버에 물으면 요청이 느려지고, 그 서버가 죽으면 결제가 멈춥니다. 그래서 플래그 도구의 SDK(앱에 넣는 클라이언트 라이브러리)는 규칙 전체를 앱 메모리에 내려받아 두고, 판정은 로컬에서 합니다. 규칙이 바뀌면 몇 초 안에 스트리밍이나 주기적 조회로 갱신합니다.

"일반 사용자 5%"를 판정하는 방법도 중요합니다. 요청마다 난수를 뽑으면 같은 사용자가 새로고침할 때마다 옛 화면과 새 화면을 오갑니다. 그래서 사용자 ID와 플래그 이름을 해시해 0~99 사이의 고정 번호를 만들고, 번호가 5 미만이면 켭니다. 같은 사용자는 늘 같은 번호를 받으므로 같은 답을 듣습니다.

비율을 5%에서 25%로 올리면 기준만 25 미만으로 바뀌므로, 이미 켜져 있던 5%는 그대로 켜진 채 20%가 더해집니다. 켜졌다 꺼지는 사용자가 생기지 않습니다.

규칙에는 비율 말고도 사용자 속성(직원 여부, 국가, 앱 버전)을 조건으로 걸 수 있습니다. 대표 도구로 LaunchDarkly, Unleash, AWS AppConfig 등이 있습니다. 편리한 만큼 대가도 있는데, 그것은 플래그가 쌓인다는 것입니다.

플래그는 켜는 것보다 지우는 것이 어렵다

플래그는 용도에 따라 수명이 다릅니다. 출시용 플래그는 기능이 100% 켜지면 지워야 하는 임시 장치입니다. 운영용 플래그는 외부 결제사가 느려질 때 추천 기능을 끄는 식의 비상 차단기(kill switch)로, 계속 남겨 둡니다.

출시용 플래그를 지우지 않으면 조건 분기가 쌓여, 어떤 조합이 실제로 운영에서 돌고 있는지 아무도 모르게 됩니다. 플래그 10개면 조합은 1,024가지입니다.

운영에서 지키는 규칙은 다음과 같습니다.

  • 플래그를 만들 때 담당자와 제거 예정일을 함께 등록합니다.
  • 플래그 서버에 닿지 못할 때의 기본값을 안전한 쪽(대개 끔)으로 정합니다.
  • 켜짐과 꺼짐 두 경로를 모두 테스트합니다. 꺼진 경로가 썩어 있으면 kill switch를 당겨도 동작하지 않습니다.

여기까지가 "무엇을 어떤 순서로 바꿀까"였습니다. 이제 어떤 전략이든 공통으로 필요한 조건으로 갑니다.

무중단의 조건: 앱이 우아하게 떠나야 한다

어떤 전략이든 옛 인스턴스는 결국 종료됩니다. 이때 앱이 진행 중인 요청을 버리고 즉시 죽으면, 배포할 때마다 몇 건씩 로드 밸런서가 502(뒤쪽 서버의 응답 실패)를 돌려줍니다. 사용자는 전략이 무엇이었는지 모르고 "배포 때마다 에러가 난다"고만 느낍니다.

무중단 배포는 그래서 네 장치가 맞물려야 성립합니다. 앞 둘은 플랫폼이, 셋째는 앱이, 넷째는 로드 밸런서가 맡습니다.

  1. readiness

    새 인스턴스는 준비가 끝난 뒤에만 트래픽을 받습니다.

  2. 트래픽 차단 먼저

    옛 인스턴스는 라우팅 대상에서 빠진 뒤에 종료를 시작합니다.

  3. Graceful Shutdown

    종료 신호를 받으면 새 요청은 거절하고 진행 중인 요청은 끝냅니다.

  4. 커넥션 드레이닝

    로드 밸런서는 빠지는 대상의 기존 연결이 끝나길 기다립니다.

Spring Boot는 SIGTERM에 요청을 마무리한다

server:
  shutdown: graceful   # Boot 3.4부터 기본값
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s  # 기본 30s
management:
  endpoint:
    health:
      probes:
        enabled: true  # /actuator/health/readiness

9장에서 봤듯 컨테이너를 멈출 때 플랫폼은 먼저 SIGTERM(정리하고 끝내라는 신호)을 보내고, 기다려도 안 끝나면 SIGKILL(즉시 강제 종료)을 보냅니다. Graceful Shutdown은 첫 신호를 받았을 때의 행동입니다.

shutdown: graceful이면 웹 서버가 새 요청을 받지 않고, 진행 중인 요청을 timeout-per-shutdown-phase만큼 기다린 뒤 앱을 닫습니다. 넘긴 요청은 끊깁니다. 마지막 블록은 Spring Actuator(운영용 관리 엔드포인트 모음)의 readiness 경로를 켜, 종료 중에는 "준비 안 됨"을 알립니다.

종료 예산은 플랫폼 유예 시간 안에 맞춘다

앱이 아무리 우아하게 끝내려 해도 플랫폼이 먼저 강제 종료하면 소용없습니다. Kubernetes는 유예 시간(terminationGracePeriodSeconds, 기본 30초)이 지나면 SIGKILL을 보냅니다.

그래서 규칙은 preStop 대기 + 앱 종료 시간 < 플랫폼 유예 시간입니다. 10장에서 봤듯 Pod를 지우면 엔드포인트 제거와 종료 절차가 동시에 시작되므로, preStop에서 몇 초 기다려 라우팅 갱신이 먼저 퍼지게 합니다.

order-api에 숫자를 넣어 보면, preStop 10초 동안 라우팅에서 빠지고, 그다음 SIGTERM을 받아 최대 20초 동안 요청을 마무리합니다. 합이 30초라 기본 유예 시간과 딱 맞으므로 여유를 두어 40초로 늘립니다.

로드 밸런서 쪽 드레이닝 시간(AWS에서는 대상 그룹의 등록 취소 지연, 18장)도 같은 예산 안에서 맞춥니다. 긴 배치나 메시지 컨슈머는 처리 중인 메시지를 끝내거나 큐에 돌려놓는 코드가 따로 필요합니다(8장 멱등 컨슈머).

스키마를 손으로 바꾸면 환경마다 어긋난다

앱이 우아하게 떠나도, 두 버전이 공유하는 DB가 남아 있습니다. order-api 팀은 새 결제 흐름을 위해 orders 테이블의 addr 컬럼을 shipping_address로 바꿔야 합니다.

예전 팀은 DB 접속 도구로 각 환경에 ALTER TABLE을 직접 실행했습니다. 그러자 dev에는 적용했는데 stage에는 깜빡하고, prod에는 오타가 섞인 채 적용되는 일이 생겼습니다. 어느 DB가 어느 상태인지 아무도 확신하지 못했습니다.

해법은 코드에 했던 일을 스키마에도 하는 것입니다. 스키마 변경을 번호 붙은 파일로 저장소에 두고, 도구가 각 DB에 "어디까지 적용됐는지"를 기록하며 빠진 것만 순서대로 적용하게 합니다. 이것을 스키마 마이그레이션이라 합니다.

그러면 스키마도 PR로 리뷰받고, 모든 환경이 같은 순서로 같은 변경을 받습니다. Java 진영의 대표 도구가 Flyway와 Liquibase입니다.

Flyway는 번호 순서대로 한 번씩만 적용한다

V1__create_orders.sql
V2__add_orders_status_index.sql
V3__add_shipping_address.sql

-- flyway_schema_history (Flyway가 관리)
-- version | description      | checksum | success
-- 1       | create orders    | 91c2…    | 1
-- 2       | add orders st…   | 5ab0…    | 1

Flyway는 V번호__설명.sql 형식의 파일을 번호 순으로 적용하고, 각 DB 안의 이력 테이블에 적용한 번호와 파일 내용의 체크섬(내용으로 계산한 짧은 지문)을 남깁니다. 다음 실행 때는 이력에 없는 번호만 실행합니다. 위 예에서 이 DB에는 V3만 새로 적용됩니다.

이미 적용된 파일을 고치면 체크섬이 달라져 검증에서 실패합니다. 수정은 항상 새 번호의 파일로 합니다. Liquibase는 같은 일을 XML, YAML로 쓴 변경 단위(changeset)로 하며, DB 종류에 덜 묶입니다.

마이그레이션은 언제, 누가 실행하는가

Spring Boot는 Flyway가 클래스패스에 있으면 앱이 뜰 때 마이그레이션을 실행합니다. 간단하지만 인스턴스 10개가 동시에 뜨면 10개가 동시에 시도합니다.

Flyway는 DB 락으로 하나만 실행하게 하지만, 오래 걸리는 변경이면 나머지 인스턴스의 기동이 그만큼 늦어지고, readiness를 통과하지 못해 배포 전체가 멈춥니다.

그래서 운영에서는 마이그레이션을 배포 파이프라인의 별도 단계로 떼어 내는 경우가 많습니다. 앱 배포 직전에 마이그레이션만 하는 일을 한 번 실행합니다. Kubernetes에서는 한 번 실행하고 끝나는 Pod인 10장의 Job으로 돌리거나, 뒤에서 볼 Argo CD의 PreSync 훅(동기화 직전에 먼저 실행하는 작업)으로 돌립니다.

어느 쪽이든 순서는 같습니다. 스키마가 앱보다 먼저 바뀝니다. 그러니 새 스키마 위에서 아직 남은 옛 앱이 계속 동작해야 합니다.

스키마는 두 버전이 함께 견뎌야 한다

V3를 단순히 RENAME COLUMN addr TO shipping_address로 쓰면, 마이그레이션 직후 아직 남은 v1이 addr를 찾다가 즉시 에러를 냅니다. 롤백해도 v1은 바뀐 스키마를 모릅니다.

해법은 변경을 여러 배포로 쪼개는 Expand-Contract입니다. 먼저 넓히고, 모두 옮긴 뒤, 나중에 좁힙니다. 매 단계에서 직전 버전과 다음 버전이 모두 동작하게 만드는 것이 핵심입니다.

  1. Expand

    새 컬럼 shipping_address를 NULL 허용으로 추가합니다. v1은 영향이 없습니다.

  2. 이중 쓰기

    v2는 두 컬럼에 모두 쓰고, 읽을 때는 새 컬럼을 우선합니다.

  3. 백필

    기존 행의 값을 배치로 나눠 새 컬럼에 복사합니다.

  4. 전환

    v1이 모두 사라진 뒤 새 컬럼만 읽고 씁니다.

  5. Contract

    다음 릴리스에서 옛 컬럼 addr를 삭제합니다.

릴리스마다 직전 버전으로 되돌릴 수 있다

다섯 단계를 실제 릴리스에 놓아 보면, 이름 변경 하나가 세 번의 배포에 걸칩니다. 백필(이미 있는 행을 새 컬럼에 채우는 작업)은 v2 배포 뒤 별도 배치로 돌립니다. 마지막 열이 이 방식의 대가이자 보상입니다.

릴리스스키마앱이 쓰는 곳직전 버전으로 롤백
v2addr + shipping_address두 컬럼 모두가능(v1은 addr만 씀)
v3addr + shipping_addressshipping_address만가능(v2도 새 컬럼 읽음)
v4shipping_address만shipping_address만가능(v3는 addr 안 씀)

한 번에 하던 일을 몇 주에 걸쳐 나누는 대신, 어느 시점에 문제가 생겨도 바로 앞 버전으로 안전하게 돌아갈 수 있습니다. 모든 변경이 이렇게 위험한 것은 아니므로, 어떤 변경에 이 절차가 필요한지 다음 표로 가립니다.

위험한 스키마 변경은 따로 있다

판단 기준은 하나입니다. "이 변경 뒤에도 옛 버전의 SQL이 그대로 성공하는가."

변경옛 버전에 미치는 영향안전한 방법
NULL 허용 컬럼 추가없음그대로 진행
NOT NULL 컬럼 추가옛 INSERT가 실패기본값 지정 또는 단계적 전환
컬럼 이름 변경옛 쿼리 즉시 실패Expand-Contract
컬럼 삭제옛 코드가 읽으면 실패코드에서 먼저 제거, 다음에 삭제
큰 테이블 인덱스 추가락, 복제 지연온라인 DDL, 한가한 시간

NOT NULL 컬럼이 위험한 이유는, 그 컬럼을 모르는 옛 버전의 INSERT가 값을 넣지 않아 제약 위반이 나기 때문입니다. JPA 엔티티에서 필드를 지울 때도 같아서, 옛 버전이 그 컬럼을 SELECT하는 동안에는 컬럼을 지우면 안 됩니다. 마지막 행의 "락"이 왜 서비스 전체를 세우는지는 5부에서 봅니다.

롤백보다 롤포워드가 나을 때가 있다

롤백은 직전 버전의 이미지로 되돌리는 것입니다. 이미지가 레지스트리에 그대로 남아 있으니 가장 빠르고 확실한 첫 대응입니다. 장애 중에는 원인을 찾기 전에 먼저 롤백하는 것이 원칙입니다. 원인 분석은 사용자를 기다리게 할 이유가 아니기 때문입니다.

그런데 되돌릴 수 없는 변화가 섞이면 롤백이 통하지 않습니다. 이미 지운 컬럼, 새 형식으로 저장된 데이터, 새 형식으로 발행된 메시지는 이미지를 바꿔도 돌아오지 않습니다.

이때는 롤포워드, 즉 문제를 고친 새 버전을 빠르게 내보냅니다. 롤포워드가 가능하려면 파이프라인이 빨라야 합니다. 수정 하나를 운영에 반영하는 데 2시간이 걸리면 그 2시간이 장애 시간입니다.

가장 좋은 상태는 모든 배포가 롤백 가능하도록 설계하는 것입니다. Expand-Contract, Feature Flag, 하위 호환 메시지 형식이 모두 이를 위한 장치입니다.

GitOps: 클러스터가 Git을 끌어와 맞춘다

지금까지의 파이프라인은 CI가 클러스터에 kubectl apply를 밀어 넣는 push 방식입니다. 그러려면 CI가 운영 클러스터의 강한 권한을 쥐어야 하고, 누가 손으로 바꾼 상태는 아무도 모릅니다.

GitOps는 방향을 뒤집습니다. 클러스터 안의 에이전트가 Git 저장소를 주기적으로 읽어 실제 상태를 그에 맞춥니다(pull 방식). Git이 원하는 상태의 유일한 원본이 되고, 배포는 곧 Git 커밋입니다. 10장의 조정 루프(원하는 상태와 실제 상태의 차이를 계속 메우는 루프)를 Git까지 넓힌 셈입니다.

코드 저장소와 설정 저장소를 나눈다

그림에서 CI가 커밋하는 곳은 코드 저장소가 아니라 설정 저장소였습니다. order-api 팀은 저장소를 둘로 나눴습니다. acme/order-api에는 애플리케이션 소스가, acme/deploy-config에는 Kubernetes 매니페스트가 들어 있습니다.

설정 저장소는 10장의 Kustomize로 구성합니다. 공통 매니페스트(base) 위에 환경별 차이만 덮어쓰는 오버레이(overlays/dev, overlays/prod)를 두는 방식입니다.

나누는 이유는 둘입니다. 코드 커밋마다 배포 기록이 섞이지 않고, 운영에 무엇이 어떤 버전으로 떠 있는지가 설정 저장소 하나에 모입니다. 또 운영 매니페스트를 고칠 권한을 코드 저장소와 따로 줄 수 있습니다.

CI의 마지막 단계는 이렇게 바뀝니다. 이미지를 푸시한 뒤 설정 저장소의 overlays/prod에 적힌 이미지 태그를 새 SHA로 바꾸는 커밋이나 PR을 만듭니다. 나머지는 클러스터 안의 에이전트가 합니다. 그 에이전트가 Argo CD입니다.

Argo CD Application은 어디를 어디에 맞출지다

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: order-api-prod, namespace: argocd }
spec:
  source:
    repoURL: https://github.com/acme/deploy-config
    path: apps/order-api/overlays/prod
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: order-api
  syncPolicy:
    automated:
      prune: true     # Git에서 지운 리소스도 삭제
      selfHeal: true  # 손으로 바꾼 것을 되돌림

Argo CD는 Kubernetes용 GitOps 도구로, 10장의 CRD(사용자 정의 리소스 종류)로 Application이라는 리소스를 추가합니다. Application 하나가 "source의 이 저장소, 이 경로를 destination의 이 클러스터, 이 네임스페이스에 맞춰라"를 선언합니다. 경로에는 일반 YAML, Helm 차트, Kustomize 오버레이를 둘 수 있습니다.

automated는 차이가 보이면 자동으로 맞추라는 뜻입니다. 이때도 prune은 안전을 위해 기본이 꺼져 있어, Git에서 사라진 리소스를 실제로 지우려면 명시적으로 켜야 합니다.

drift는 감지되고 selfHeal이 되돌린다

drift는 실제 상태가 선언된 상태와 어긋난 것입니다. 누군가 장애 중에 kubectl scale로 Pod 수를 바꿨다면 Git과 클러스터가 달라집니다. Argo CD는 이를 OutOfSync로 표시하고, selfHeal을 켜 두면 수동 변경을 몇 초 안에 Git 상태로 되돌립니다.

Git의 새 커밋은 기본적으로 약 3분 주기(120초 + 최대 60초 지연)로 확인하며, 저장소 웹훅을 걸면 커밋 즉시 반영됩니다.

그래서 GitOps에서는 장애 대응도 Git으로 합니다. 급하게 손으로 고쳐도 곧 되돌려지므로, 수정 사항을 커밋하거나 해당 앱의 자동 동기화를 잠시 멈춥니다.

롤백도 Git으로 합니다. 이미지 태그를 바꾼 커밋을 git revert(그 커밋을 거꾸로 적용하는 새 커밋)하면 Argo CD가 옛 태그로 되돌립니다. 누가 언제 왜 되돌렸는지가 커밋 기록에 남습니다.

앱이 늘면 Application을 만드는 Application을 둔다

order-api 하나에 환경이 셋이면 Application이 셋입니다. 회사 전체에 서비스가 서른 개면 아흔 개가 되고, 이것을 손으로 만들면 다시 수동 관리 문제가 생깁니다.

App of Apps 패턴은 다른 Application들의 YAML을 담은 디렉터리를 가리키는 상위 Application 하나를 둡니다. 상위 Application이 동기화되면 하위 Application들이 생기고, 각자 자기 서비스를 맞춥니다. 새 서비스는 그 디렉터리에 파일 하나를 더하는 PR로 추가됩니다.

ApplicationSet은 같은 일을 템플릿으로 합니다. "apps/ 아래 폴더마다, 그리고 클러스터 목록마다 Application을 하나씩 만들어라"처럼 생성 규칙을 적으면, 폴더나 클러스터가 늘 때 자동으로 따라 늘어납니다.

앞에서 미뤄 둔 PreSync 훅도 여기서 씁니다. 매니페스트의 Job에 PreSync 표시를 달면, Argo CD가 동기화 직전에 그 Job(예: Flyway 마이그레이션)을 먼저 실행하고 성공해야 앱을 바꿉니다. 같은 pull 모델의 다른 도구로 Flux가 있으며, 개념은 거의 같습니다. 이제 GitOps 위에서 Canary 판정까지 자동화해 봅니다.

Progressive Delivery는 Canary 판정을 자동화한다

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: order-api }
spec:
  replicas: 10
  strategy:
    canary:
      analysis:
        templates: [{ templateName: success-rate }]
      steps:
        - setWeight: 10
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
  # selector, template은 Deployment와 같음

사람이 대시보드를 보며 Canary 비율을 올리는 방식은 느리고, 새벽 배포에서는 아무도 보고 있지 않습니다. Progressive Delivery는 단계적 노출과 지표 판정을 함께 자동화합니다.

Argo CD의 자매 프로젝트인 Argo Rollouts는 Deployment를 대신하는 Rollout 리소스를 추가합니다. 단계를 직접 적어, 10%를 보내고 10분 관찰, 50%로 올리고 10분 관찰한 뒤 100%로 갑니다. 기간 없는 pause: {}는 사람이 승격할 때까지 멈춥니다. 가중치는 Ingress나 메시가 연결돼 있으면 그쪽으로, 아니면 Pod 수 비율로 맞춥니다.

지표가 나빠지면 Rollout이 스스로 멈춘다

kind: AnalysisTemplate
metadata: { name: success-rate }
spec:
  metrics:
  - name: success-rate
    interval: 5m
    successCondition: result[0] >= 0.95
    failureLimit: 3
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{app="order-api",
            code!~"5.."}[5m])) /
          sum(rate(http_requests_total{app="order-api"}[5m]))

판정에 쓰는 지표는 Prometheus에서 가져옵니다. 앱들이 내보내는 숫자를 주기적으로 모아 시간순으로 저장하고 질의하게 해 주는 지표 저장소입니다. 쿼리는 최근 5분간 초당 요청 수 중 5xx(서버 오류 응답)가 아닌 비율, 즉 성공률을 계산합니다.

템플릿은 5분마다 이 값을 재서 0.95 이상이면 성공으로 칩니다. 실패한 측정이 failureLimit인 3번을 넘으면 분석이 실패하고, Rollout은 Canary 가중치를 0으로 되돌린 뒤 멈춥니다. 사람이 깨어나기 전에 롤백이 끝나 있습니다.

4부

인프라도 코드로 선언하고 리뷰한다

이제 order-api의 코드와 매니페스트는 Git에 있고, 모든 변경이 리뷰와 파이프라인을 거칩니다. 그런데 그 아래의 네트워크, DB, 저장소 버킷은 여전히 콘솔 클릭으로 만든 그대로입니다. 4부는 같은 원칙을 인프라에 적용하는 방법, 즉 인프라를 코드로 적고 도구가 그 코드대로 만들게 하는 방법을 봅니다.

손으로 만든 인프라는 기억 속에만 있다

order-api의 운영 인프라는 몇 해 전 퇴사한 동료가 AWS 콘솔에서 만들었습니다. 사설 네트워크, 방화벽 규칙, DB 인스턴스, 로그 버킷이 있다는 것은 알지만, 각 설정값이 왜 그렇게 되어 있는지는 아무도 모릅니다.

이번에 stage 환경을 운영과 똑같이 새로 만들려고 하자 문제가 드러났습니다. 콘솔 화면을 한 장씩 비교하며 따라 만들었지만, 결과물은 운영과 미묘하게 달랐습니다.

클릭으로 만든 인프라에는 세 가지 문제가 있습니다.

  • 누가 언제 왜 바꿨는지 기록이 없습니다.
  • 같은 구성을 다른 환경이나 다른 지역(리전)에 똑같이 다시 만들기 어렵습니다.
  • stage와 prod가 조금씩 달라져도 아무도 모릅니다.

이렇게 하나하나 모양이 달라 다시 만들 수 없는 서버를 눈송이 서버라 부릅니다. 같은 눈송이가 둘 없다는 뜻입니다.

IaC는 인프라에 코드의 습관을 입힌다

IaC는 인프라의 원하는 모습을 텍스트 파일로 적고, 도구가 그 파일대로 클라우드 API를 호출해 만들게 하는 방식입니다. 파일은 애플리케이션 코드처럼 Git에 둡니다.

그러면 1부에서 코드가 누리던 것을 인프라도 누립니다. 2부의 파이프라인이 그대로 인프라 변경에도 쓰입니다.

  • 기록: Git 기록이 곧 변경 이력이고, 커밋 메시지가 변경 이유입니다.
  • 리뷰: PR 리뷰가 곧 변경 승인입니다. 방화벽을 여는 변경도 동료가 봅니다.
  • 재현: 같은 코드로 dev, stage, prod를 같은 모양으로 찍어 냅니다.
  • 미리 보기와 되돌리기: 적용 전에 무엇이 바뀔지 보고, 사고가 나면 이전 커밋으로 돌아갑니다.

도구를 보기 전에, 그 도구들이 공유하는 두 가지 설계 원칙부터 봅니다.

선언형은 결과를, 명령형은 절차를 적는다

10장에서 Kubernetes가 "컨테이너 3개를 띄워라"가 아니라 "3개가 떠 있어야 한다"를 받는다고 했습니다. 인프라 도구도 같은 갈림길에 있습니다.

명령형은 "서버를 하나 만들어라, 방화벽 규칙을 붙여라"처럼 할 일을 순서대로 적습니다. 셸 스크립트나 AWS CLI 호출이 그렇습니다. 두 번 실행하면 서버가 두 대 생깁니다. 선언형은 "서버가 하나 있고 이 규칙이 붙어 있어야 한다"는 결과만 적습니다. 도구가 현재 상태와 비교해 필요한 작업을 계산하므로 몇 번을 실행해도 결과가 같습니다(2장의 멱등).

구분명령형선언형
적는 것절차원하는 결과
재실행중복 생성 위험변화 없음
변경 계산사람이 함도구가 함
예셸, AWS CLITerraform, CloudFormation

선언형이 "현재 상태와 비교"하려면 현재 상태를 알아야 합니다. 이 문제는 Terraform의 state에서 다시 만납니다.

불변 인프라는 고치지 않고 갈아 끼운다

두 번째 원칙은 이미 만든 것을 어떻게 바꾸느냐입니다. 가변 인프라는 서버를 한 번 만들고 그 위에서 패키지를 업데이트하고 설정을 고치며 계속 씁니다. 시간이 지나면 서버마다 적용된 패치와 수동 변경이 달라져 구성 표류가 생기고, 결국 눈송이 서버가 됩니다.

불변 인프라는 실행 중인 서버를 고치지 않습니다. 변경이 필요하면 새 이미지(컨테이너 이미지, 또는 가상 머신 디스크 이미지인 AMI, 14장)를 만들어 새 서버로 교체하고 옛 서버는 버립니다.

컨테이너와 Kubernetes가 바로 이 모델입니다. 실행 중인 Pod에 들어가 파일을 고치지 않고, 이미지를 바꿔 새 Pod로 교체합니다. 그래서 어떤 서버든 이미지 버전만 보면 정확한 상태를 압니다. 3부의 배포 전략이 모두 "교체"였던 것도 이 때문입니다.

IaC 도구는 두 축으로 나뉜다

IaC 도구는 무엇을 하느냐와 어떻게 적느냐로 나뉩니다. 첫째 축은 프로비저닝(서버, 네트워크, DB 같은 자원 자체를 만드는 일)과 구성 관리(이미 있는 서버 안에 패키지를 깔고 설정 파일을 놓는 일)입니다. 둘째 축은 전용 설정 언어로 적느냐, TypeScript 같은 범용 프로그래밍 언어로 적느냐입니다.

가장 널리 쓰이는 Terraform으로 원리를 자세히 보고, 나머지는 Terraform과의 차이 위주로 짧게 봅니다.

Terraform은 provider로 어디든 만든다

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}
provider "aws" { region = "ap-northeast-2" }

data "aws_vpc" "main" { tags = { Name = "main" } }

resource "aws_security_group" "order_api" {
  name   = "order-api-sg"
  vpc_id = data.aws_vpc.main.id
}

Terraform은 HCL이라는 선언형 언어로 인프라를 적습니다. 파일은 종류 "이름" { 설정 } 모양의 블록으로 이루어집니다. provider는 AWS, Kubernetes, GitHub 같은 대상의 API를 다루는 플러그인이고, ~> 6.0은 6.x 안에서만 올리라는 버전 제약입니다.

resource는 Terraform이 만들고 관리하는 대상, data는 이미 있는 것을 읽기만 하는 대상입니다. 여기서는 기존 사설 네트워크(VPC, 13장)를 찾아, 그 안에 방화벽 규칙 묶음인 보안 그룹(13장)을 만듭니다.

참조가 곧 의존 관계이고 생성 순서다

  1. .tf 파일원하는 상태
  2. Terraform 코어의존 그래프 계산
  3. providerAPI 호출로 번역
  4. AWS API실제 리소스 생성

앞 코드의 보안 그룹은 vpc_id = data.aws_vpc.main.id로 VPC의 속성을 참조했습니다. Terraform 코어는 이런 참조를 모두 모아 "무엇이 무엇에 기대는가"를 나타내는 그래프를 만들고, 기대는 쪽을 나중에 만듭니다. 그래서 파일 안 블록의 순서는 상관이 없고, 서로 기대지 않는 리소스는 동시에 만듭니다.

코어는 AWS를 직접 알지 못합니다. "보안 그룹 하나를 이 설정으로"라는 요청을 AWS provider에 넘기면, provider가 그것을 AWS API 호출로 바꿉니다. provider만 바꾸면 같은 방식으로 Kubernetes 리소스나 GitHub 저장소 설정도 관리할 수 있는 이유가 이 분리에 있습니다. 다음은 같은 코드를 환경마다 다르게 쓰는 방법입니다.

variable은 입력, output은 출력이다

variable "instance_type" {
  type    = string
  default = "t3.small"
}
locals {
  name = "order-api-${var.env}"
}
output "sg_id" {
  value = aws_security_group.order_api.id
}

# prod.tfvars
instance_type = "m7g.large"

variable은 코드를 함수처럼 만드는 입력입니다. 같은 코드에 환경별 .tfvars 파일을 넣어, dev는 작은 인스턴스로, prod는 큰 인스턴스로 만듭니다. 코드 안에서는 var.이름으로 꺼냅니다.

locals는 코드 안에서 반복되는 값에 이름을 붙인 것입니다. output은 만든 결과(ID, 주소)를 밖으로 내보내, 다른 모듈이나 다른 Terraform 프로젝트가 받아 씁니다.

state는 코드와 실제 리소스를 잇는 장부다

선언형 도구는 현재 상태와 비교해야 한다고 했습니다. 그런데 코드에 aws_security_group.order_api라고 적었을 때, 이것이 AWS의 어느 보안 그룹(sg-0a1b…)인지는 코드만 봐서는 모릅니다.

Terraform은 이 대응 관계와 마지막으로 알던 속성을 state 파일에 기록합니다. plan은 코드(원하는 상태), state(지난번 기록), 실제 API 응답(현재 상태)을 비교합니다. state가 없으면 Terraform은 이미 만든 리소스를 모르는 것으로 보고 새로 만들려 합니다.

state 파일 안에는 실제 ID와 속성이 있다

{
  "version": 4,
  "serial": 42,
  "resources": [{
    "mode": "managed",
    "type": "aws_security_group",
    "name": "order_api",
    "instances": [{
      "attributes": {
        "id": "sg-0a1b2c3d4e5f",
        "name": "order-api-sg",
        "vpc_id": "vpc-0123abcd"
      }
    }]
  }]
}

state는 JSON 파일입니다. type과 name이 코드의 resource "aws_security_group" "order_api"를, attributes.id가 AWS의 실제 ID를 가리킵니다. 이 한 줄이 장부의 핵심 기록입니다.

serial은 state가 바뀔 때마다 오르는 번호로, 더 오래된 state가 새것을 덮어쓰는 일을 막는 데 씁니다. 눈여겨볼 점은 attributes에 리소스의 속성이 있는 그대로 담긴다는 것입니다. DB 비밀번호 같은 값도 예외가 아니며, 이 문제는 뒤에서 다시 봅니다.

plan으로 보고, 리뷰하고, apply로 적용한다

  1. init

    provider 플러그인과 모듈을 받고 state 저장소에 연결합니다.

  2. plan

    실제 상태를 새로 읽어 코드와 비교하고, 바뀔 목록을 출력합니다.

  3. 리뷰

    PR에 plan 결과를 붙여 삭제, 교체 항목을 사람이 확인합니다.

  4. apply

    저장해 둔 plan 그대로 API를 호출하고 state를 갱신합니다.

Terraform 작업은 이 네 단계로 돕니다. order-api 팀은 인프라 저장소의 PR마다 CI가 plan을 돌려 결과를 PR 댓글로 붙이게 했습니다. 리뷰어는 코드가 아니라 "그래서 실제로 무엇이 바뀌는가"를 봅니다.

CI에서는 plan -out=tfplan으로 계획을 파일로 저장하고, 승인 뒤 apply tfplan으로 그 파일을 그대로 적용합니다. 그사이 state가 바뀌었다면 저장된 plan은 거부됩니다. 리뷰한 것과 다른 변경이 적용되는 일을 막는 장치입니다. plan 출력을 어떻게 읽는지 봅니다.

plan 출력에서 -/+ 기호를 먼저 찾는다

  # aws_security_group.order_api will be updated in-place
  ~ resource "aws_security_group" "order_api" {
      ~ tags = {
          ~ "Team" = "order" -> "payments"
        }
    }

  # aws_db_instance.orders must be replaced
-/+ resource "aws_db_instance" "orders" {
      ~ storage_encrypted = false -> true # forces replacement
    }

Plan: 1 to add, 1 to change, 1 to destroy.

plan은 리소스마다 기호를 붙입니다. +는 새로 생성, -는 삭제, ~는 그 자리에서 속성만 변경, -/+는 삭제 후 재생성입니다.

어떤 속성은 클라우드 API가 수정을 허락하지 않아, 바꾸려면 리소스를 새로 만들어야 합니다. DB의 저장 암호화 여부가 그렇습니다. RDS는 암호화를 DB를 만들 때만 정할 수 있어서, 켜려면 새 DB가 필요합니다. 위 plan을 그대로 적용하면 주문 DB가 지워지고 빈 DB가 생깁니다. 그래서 지워지면 안 되는 리소스에는 lifecycle { prevent_destroy = true }를 둬, 삭제가 포함된 plan 자체를 오류로 만듭니다.

state는 원격에 두고 락으로 순서를 지킨다

terraform {
  backend "s3" {
    bucket       = "acme-tfstate"
    key          = "prod/network/terraform.tfstate"
    region       = "ap-northeast-2"
    encrypt      = true
    use_lockfile = true  # S3 네이티브 락
  }
}

state를 노트북에 두면 팀원끼리 공유할 수 없고, 노트북을 잃으면 장부가 사라집니다. 그래서 state를 둘 곳을 정하는 backend를 S3 같은 원격 저장소로 지정하고, 버킷의 버전 관리를 켜 이전 state를 되살릴 수 있게 합니다.

두 사람이 동시에 apply하면 서로의 state를 덮어씁니다. 락은 먼저 시작한 쪽이 끝날 때까지 다른 쪽을 기다리게 합니다. Terraform 1.11부터 use_lockfile로 S3에 .tflock 파일을 만들어 잠그는 방식이 정식 기능이 되었고, 예전의 DynamoDB 락 테이블 방식은 더 이상 권장되지 않습니다(deprecated).

module은 인프라 부품을 재사용하게 한다

module "vpc" {
  source   = "../../modules/vpc"
  cidr     = "10.0.0.0/16"
  az_count = 3
}

module "order_api" {
  source = "../../modules/ecs-service"
  subnet_ids = module.vpc.private_subnet_ids
  cpu        = 1024
}

모듈은 리소스 묶음에 입력(variable)과 출력(output)을 붙인 부품입니다. VPC 하나에는 서브넷, 라우팅 테이블, NAT Gateway 등 수십 개 리소스가 필요한데(13장), 모듈로 감싸면 환경마다 몇 줄로 찍어 냅니다. 강조한 줄처럼 한 모듈의 출력을 다른 모듈의 입력으로 이어, 앞에서 본 의존 그래프가 모듈 단위로도 만들어집니다.

공용 레지스트리나 Git 저장소의 모듈은 버전을 고정합니다. 모듈을 너무 잘게 쪼개거나 옵션을 너무 많이 넣으면 오히려 읽기 어려워집니다.

환경 분리는 workspace보다 디렉터리가 흔하다

모듈이 생기면 dev와 prod를 어떻게 나눌지 정해야 합니다. 방법은 둘입니다. workspace는 같은 코드와 같은 backend 안에 state만 여러 벌 두고 terraform workspace select prod로 바꿔 가며 쓰는 기능이고, 환경별 디렉터리는 envs/dev, envs/prod처럼 폴더를 나눠 각자 공통 모듈을 불러 쓰는 방식입니다.

기준workspace환경별 디렉터리
구조같은 코드, state만 여러 벌envs/dev, envs/prod 각자 state
환경 차이 표현코드 안 조건문각 디렉터리의 입력값
사고 위험현재 workspace 착각디렉터리 위치로 명확
권한 분리같은 backend라 어려움환경별 계정, 역할 가능

workspace는 prod를 dev로 착각하고 apply하는 사고가 쉽게 납니다. 그래서 운영에서는 디렉터리로 나누고, prod state는 별도 AWS 계정의 버킷에 둡니다. 큰 시스템은 네트워크, DB, 앱처럼 state를 층별로도 나눠 한 번의 실수가 미치는 범위를 줄입니다.

import로 들이고, drift는 plan이 알려 준다

import {
  to = aws_s3_bucket.logs
  id = "acme-legacy-logs"
}
# resource 블록이 없으면 초안을 생성
$ terraform plan -generate-config-out=gen.tf
$ terraform apply              # state에 편입
$ terraform plan -refresh-only  # drift 확인

order-api 팀의 출발점은 콘솔로 이미 만든 인프라였습니다. 이것을 지우고 다시 만들 수는 없으므로, 있는 리소스를 Terraform 관리로 들입니다. 이것이 import입니다. 블록에 대상 주소와 실제 ID를 적으면 plan이 state에 편입할 계획을 보여 주고, 설정 코드 초안도 생성해 줍니다.

들인 뒤 누군가 콘솔에서 값을 바꾸면, 다음 plan에서 그 차이가 "변경 예정"으로 드러납니다. Terraform의 drift 감지입니다. 그대로 apply하면 수동 변경이 코드대로 되돌아갑니다. -refresh-only는 실제 상태를 state에만 반영하고 리소스는 건드리지 않습니다.

민감 값은 가려도 state에는 평문으로 남는다

앞에서 state의 attributes에 속성이 있는 그대로 담긴다고 했습니다. 변수나 출력에 sensitive = true를 붙이면 plan과 apply 화면에서 값이 (sensitive value)로 가려지지만, 이것은 화면 표시만 가리는 것입니다.

DB 비밀번호를 Terraform 리소스 인자로 넘기면 그 값은 state 파일에 평문으로 저장됩니다. state를 읽을 수 있는 사람은 비밀번호도 읽습니다.

그래서 다음을 함께 지킵니다.

  • state 버킷은 암호화하고, 읽기 권한을 배포 역할과 소수의 관리자로 제한합니다.
  • 비밀번호는 Terraform이 직접 만들지 않습니다. 비밀 보관 서비스인 Secrets Manager(16장)가 생성, 관리하게 하거나(AWS의 관리형 DB인 RDS는 마스터 암호를 Secrets Manager에 맡기는 옵션이 있습니다, 15장), Terraform 1.11부터 지원되는 write-only 인자처럼 state에 남지 않는 방식을 씁니다.
  • *.tfvars에 비밀을 적어 Git에 올리지 않습니다.

CloudFormation은 AWS가 state를 대신 든다

AWSTemplateFormatVersion: '2010-09-09'
Parameters:
  Env: { Type: String, AllowedValues: [dev, prod] }
Resources:
  LogsBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    Properties:
      BucketName: !Sub 'acme-logs-${Env}'
Outputs:
  BucketArn:
    Value: !GetAtt LogsBucket.Arn

Terraform에서 state 보관과 락을 직접 챙기는 것이 부담이라면, AWS가 그것을 대신 해 주는 CloudFormation이 있습니다. YAML 템플릿을 올리면 리소스 묶음인 스택이 생기고, 무엇을 만들었는지는 AWS가 서비스 안에 기록합니다.

Parameters는 Terraform의 variable, Outputs는 output입니다. !Sub는 문자열에 값을 끼워 넣는 내장 함수, !GetAtt는 리소스의 속성을 읽는 함수입니다. 변경 중 하나라도 실패하면 스택 전체를 이전 상태로 자동 롤백합니다. DeletionPolicy: Retain은 스택을 지워도 버킷은 남기라는 뜻입니다.

change set으로 미리 보고 drift를 검사한다

CloudFormation에서 Terraform plan에 해당하는 것이 change set입니다. 템플릿을 바로 적용하지 않고 변경 세트를 만들면, 어떤 리소스가 추가, 수정, 교체(Replacement)되는지 보여 줍니다. 확인한 뒤 실행합니다.

drift detection은 스택의 리소스가 콘솔 등에서 수동으로 바뀌었는지 검사해 속성별 차이를 보여 줍니다. 단, 감지만 하고 자동으로 되돌리지는 않습니다. 같은 스택을 여러 계정과 리전에 한꺼번에 배포하는 StackSets도 있습니다.

5부

배포는 자주, 사고는 작게

order-api 팀은 이제 파이프라인, 배포 전략, GitOps, IaC를 모두 갖췄습니다. 하지만 도구를 갖추는 것과 그것으로 안전하게 자주 배포하는 것은 다른 문제입니다. 5부는 잘하고 있는지 재는 법, 배포 직후 실제로 자주 터지는 장애의 원리, 비밀과 state와 운영 권한에서 나는 사고를 봅니다.

원리 실무 배포 성과 지표, 배포 직후 장애 사례, 시크릿과 state 사고, 접근 통제를 다룹니다.

DORA 지표는 속도와 안정성을 함께 잰다

"우리 배포가 나아지고 있는가"를 감이 아니라 숫자로 보려면 무엇을 재야 할까요. 구글 클라우드 산하의 DORA(DevOps Research and Assessment) 연구팀은 해마다 수만 명의 실무자를 조사해 다음 네 지표를 제시했습니다.

지표무엇을 재나축

핵심 발견은 잘하는 팀은 빠르면서 동시에 안정적이라는 것입니다. 작게 자주 배포하면 변경 하나의 위험이 작고, 문제가 나도 원인이 좁기 때문입니다. 최근 모델은 계획에 없던 장애 대응 배포의 비율(배포 재작업률)을 다섯 번째 지표로 더합니다.

지표는 개선 방향을 알려 줄 뿐 목표가 아니다

네 지표는 서로 견제하도록 묶여 있습니다. 배포 빈도만 목표로 삼으면 의미 없는 배포가 늘고, 실패율만 보면 배포를 미루게 됩니다. 한 지표가 좋아질 때 다른 지표가 나빠지지 않는지 함께 봅니다.

측정은 사람의 보고가 아니라 도구 기록에서 자동으로 뽑습니다. 리드 타임은 Git 커밋 시각과 배포 기록에서, 실패율은 롤백과 긴급 수정 기록에서 계산합니다.

지표가 나쁠 때 흔한 원인과 처방은 이렇습니다.

  • 리드 타임이 길면 대개 리뷰 대기, 느린 CI, 수동 승인 단계가 병목입니다.
  • 실패율이 높으면 테스트 공백, stage와 운영의 차이, 큰 배포 단위를 의심합니다.
  • 복구가 느리면 롤백이 자동화되어 있지 않거나, 배포와 장애를 연결해 볼 관측성이 없습니다.

order-api 팀의 첫 측정에서 가장 나쁜 것은 리드 타임이었고, 원인은 CI 결과를 믿지 못해 생기는 재실행이었습니다.

flaky 테스트는 CI의 신뢰를 갉아먹는다

flaky 테스트는 코드가 그대로인데 때로는 통과하고 때로는 실패하는 테스트입니다. 처음에는 "다시 돌리면 되지"로 넘어가지만, 실패가 흔해지면 사람들은 빨간 결과를 무시하기 시작하고, 진짜 버그도 그 사이에 묻힙니다.

흔한 원인은 시간 의존(현재 시각, 고정 sleep), 테스트끼리 공유하는 상태(같은 DB 행, 정적 변수), 실행 순서 의존, 외부 네트워크 호출, 비동기 처리를 충분히 기다리지 않는 것입니다.

다루는 방법은 다음과 같습니다.

  • 재시도 끝에 통과한 테스트를 기록해 flaky 목록을 자동으로 만듭니다.
  • 발견하면 격리(quarantine)해 병합을 막지 않게 하되, 담당자와 기한을 붙여 고칩니다.
  • 고정 sleep 대신 조건이 만족될 때까지 기다리는 Awaitility 같은 도구를 쓰고, 현재 시각은 테스트가 주입한 Clock으로 고정합니다.
  • 테스트마다 자기 데이터를 만들고 지워 실행 순서에 의존하지 않게 합니다.

배포 직후 자주 터지는 장애 네 가지

CI를 믿을 수 있게 되어도, 배포 직후에만 드러나는 장애가 있습니다. 테스트 환경에서는 재현되지 않고 운영의 데이터 양, 설정, 동시 실행 버전 때문에 터지는 것들입니다. 자주 보는 네 가지를 표로 정리하고, 이어지는 슬라이드에서 하나씩 원리를 봅니다.

유형증상예방
설정 누락새 환경 변수가 prod에만 없음기동 시 필수 설정 검증
마이그레이션 락ALTER 하나에 테이블 전체가 멈춤락 대기 시간 제한, 온라인 DDL
캐시 콜드 스타트새 인스턴스 지연 급증, DB 부하 폭증예열, 점진적 트래픽
하위 호환 깨짐옛 버전, 옛 클라이언트가 에러Expand-Contract, 계약 테스트

필수 설정이 없으면 아예 뜨지 않게 한다

@Validated
@ConfigurationProperties("payment")
public record PaymentProperties(
    @NotBlank String apiUrl,
    @NotNull Duration timeout
) {}

# application-prod.yml
payment:
  api-url: ${PAYMENT_API_URL}
  timeout: 3s

새 결제 흐름은 결제사 주소를 담은 환경 변수 PAYMENT_API_URL이 필요했는데, stage에만 넣고 prod에는 빠뜨렸습니다. 앱은 정상으로 떴고, 첫 결제 요청에서야 터졌습니다. 설정 누락은 기능이 처음 호출될 때 터지면 가장 고약합니다.

@ConfigurationProperties는 payment.* 설정을 이 객체에 묶고, @Validated와 제약 어노테이션은 그 값을 기동 시점에 검사합니다. 값이 없으면 기동 자체가 실패하므로 readiness를 통과하지 못하고, Rolling은 그 자리에서 멈춰 옛 버전이 계속 서비스합니다.

메타데이터 락은 테이블 구조를 지키는 락이다

두 번째 장애인 마이그레이션 락을 이해하려면, 행이 아니라 테이블 구조를 지키는 락을 알아야 합니다. 4장에서 본 락은 행이나 행 사이 간격을 잠가 데이터 충돌을 막는 것이었습니다. 그런데 어떤 트랜잭션이 orders를 읽는 도중 다른 세션이 컬럼을 지워 버리면, 트랜잭션은 존재하지 않는 구조를 보게 됩니다.

MySQL은 이것을 메타데이터 락(MDL)으로 막습니다. 평범한 SELECT, INSERT도 테이블을 쓰는 동안 공유 MDL을 잡고, 이 락은 문장이 아니라 트랜잭션이 끝날 때 풀립니다. 공유 락끼리는 서로 막지 않으므로 평소에는 존재를 느낄 일이 없습니다.

ALTER TABLE은 구조를 바꾸므로 배타적 MDL이 필요합니다. 데이터 복사를 다른 쿼리와 동시에 진행하는 온라인 DDL이라도, 시작과 끝의 짧은 순간에는 배타적 MDL을 잡아야 합니다. 그리고 배타 락을 기다리는 요청이 하나 생기면, 그 뒤에 오는 공유 락 요청도 줄을 섭니다. 대기 중인 ALTER가 영원히 밀리지 않게 하려는 규칙입니다.

문제는 그 대기 시간의 상한인 lock_wait_timeout의 기본값이 31,536,000초, 즉 1년이라는 점입니다. 사실상 무한히 기다립니다. 다음 슬라이드에서 이것이 어떻게 장애로 이어지는지 봅니다.

ALTER 하나가 테이블 전체를 세우는 순서

  1. 긴 트랜잭션

    정산 배치가 orders를 읽는 트랜잭션을 30분째 열어 두고 있습니다.

  2. ALTER 대기

    V3 마이그레이션의 ALTER가 배타적 MDL을 얻지 못하고 기다립니다.

  3. 뒤따르는 쿼리 정체

    그 뒤 일반 SELECT, INSERT도 ALTER 뒤에 줄을 섭니다.

  4. 커넥션 풀 고갈

    요청 스레드가 모두 대기에 묶여 서비스 전체가 응답하지 않습니다.

몇 초면 끝날 ALTER가 몇 분짜리 전체 장애가 되는 순서입니다. 앱의 커넥션 풀(DB 연결을 미리 만들어 돌려 쓰는 묶음)이 바닥나면 DB와 상관없는 API까지 멈춥니다.

예방은 마이그레이션 세션에 lock_wait_timeout(PostgreSQL은 lock_timeout)을 몇 초로 짧게 거는 것입니다. 락을 못 얻으면 줄을 막는 대신 실패하고, 한가할 때 다시 시도합니다. 큰 테이블은 gh-ost나 pt-online-schema-change를 씁니다. 빈 사본 테이블에 구조를 먼저 바꾸고 데이터를 조금씩 옮긴 뒤, 마지막에 이름만 맞바꾸는 도구입니다.

콜드 스타트와 직렬화 호환도 배포의 일부다

세 번째는 콜드 스타트입니다. 3부에서 봤듯 새로 뜬 JVM은 JIT 컴파일 전이라 느리고, 커넥션 풀과 로컬 캐시도 비어 있습니다. 한꺼번에 전부 교체하면 모든 인스턴스가 동시에 DB로 몰려 캐시 미스 폭풍이 납니다. 배포와 함께 Redis 키 구조를 바꾼 경우도 같습니다.

처방은 readiness를 통과하기 전에 주요 경로를 미리 호출해 예열하고, Rolling이나 Canary로 천천히 교체하는 것입니다.

네 번째, 하위 호환은 DB 스키마만의 문제가 아닙니다. 두 버전이 공존하는 모든 공유 자원에서 같은 일이 생깁니다.

  • 캐시: v2가 필드를 바꾼 객체를 캐시에 쓰면, 아직 남은 v1이 역직렬화에 실패합니다.
  • 메시지: v2 프로듀서가 새 형식으로 발행하면 v1 컨슈머가 처리하지 못합니다. 필드는 추가만 하고 지우지 않습니다.
  • API: 모바일 앱처럼 업데이트를 강제할 수 없는 클라이언트는 옛 응답 형식을 오래 기대합니다(7장 버저닝). 양쪽이 기대하는 형식을 테스트로 고정해 두는 계약 테스트가 이런 깨짐을 CI에서 잡습니다.

시크릿은 들어가는 길과 새는 길을 모두 막는다

장애만큼 자주 나는 사고가 비밀 유출입니다. 새는 경로는 대부분 평범합니다. 커밋에 섞인 .env 파일, 디버깅하려고 찍은 환경 변수 로그, 이미지 레이어에 남은 설정 파일, 너무 넓은 권한의 CI 토큰입니다. Git 기록에 한 번 들어간 키는 다음 커밋에서 지워도 기록에 남아 있습니다.

예방은 세 겹으로 합니다.

  • 들어가는 길 막기: 커밋 직전에 도는 pre-commit 훅과 GitHub의 push 보호로 키 모양의 문자열을 차단합니다.
  • 한 곳에 두기: 비밀은 1부의 비밀 저장소에서만 읽고, 코드와 이미지에는 자리만 둡니다.
  • 없애기: 2부의 OIDC로 장기 키 자체를 없앱니다. 없는 키는 새지 않습니다.

그래도 새는 일은 생깁니다. 그때의 순서가 중요합니다.

유출되면 기록 삭제보다 폐기가 먼저다

  1. 즉시 폐기, 교체

    키를 무효로 만들고 새 키로 바꿉니다. 이것이 피해를 멈춥니다.

  2. 사용 기록 확인

    감사 로그로 그 키가 언제 무엇에 쓰였는지 봅니다.

  3. 피해 복구

    만들어진 리소스, 바뀐 권한, 빠져나간 데이터를 처리합니다.

  4. 기록 정리

    Git 기록에서 지우고, 새게 된 경로를 막습니다.

많은 사람이 유출을 알면 먼저 Git 기록부터 지우려 합니다. 하지만 공개 저장소에 올라간 키는 몇 분 안에 자동 수집기에 수집됩니다. 기록을 지워도 이미 복사된 키는 살아 있습니다.

그래서 첫 단계는 언제나 폐기입니다. AWS 키라면 이후 감사 로그인 CloudTrail로 사용 내역을 확인합니다(16장). 기록 정리는 피해를 멈춘 다음에 해도 늦지 않습니다.

Terraform 사고는 대개 state와 수동 변경에서

4부에서 state를 장부라고 했습니다. Terraform 사고의 대부분은 이 장부가 실제와 어긋나거나, 장부 자체가 잠기거나 사라지는 데서 옵니다.

사고무슨 일이 일어나나대응과 예방
락이 남음apply 중 CI가 죽어 락이 안 풀림실행 중 작업 확인 후 force-unlock
수동 변경 덮어쓰기콘솔로 늘린 용량이 다음 apply에 원복수동 변경은 바로 코드에 반영
의도치 않은 재생성이름 변경이 삭제 후 생성으로plan의 -/+ 확인, moved
state 손상, 분실모든 리소스를 모르는 상태버킷 버전 관리로 복구

가장 흔한 것은 수동 변경입니다. 새벽 장애 때 콘솔로 DB 크기를 키우고 아무도 코드에 옮기지 않으면, 한참 뒤 상관없는 PR의 apply가 그 크기를 되돌려 같은 장애가 다시 납니다. 나머지 둘의 도구는 다음 슬라이드에서 봅니다.

moved는 이름만 바꾸고, force-unlock은 신중히

# 리소스 이름을 바꿨다고 알려 재생성을 막음
moved {
  from = aws_security_group.api
  to   = aws_security_group.order_api
}

# 남은 락 해제: 락 ID는 오류 메시지에 나옴
$ terraform force-unlock 6f1c2e…

Terraform은 리소스를 코드 속 주소(종류.이름)로 state와 연결합니다. 그래서 이름만 api에서 order_api로 바꿔도, 옛 주소는 코드에서 사라졌으니 삭제, 새 주소는 state에 없으니 생성으로 계산합니다. moved 블록은 "같은 리소스의 주소만 바뀌었다"고 알려, plan이 삭제와 생성 대신 state 기록만 옮기게 합니다.

force-unlock은 남은 락을 강제로 풉니다. 다른 apply가 정말 돌고 있는데 풀면 두 작업이 state를 동시에 덮어써 장부가 망가지므로, 실행 중인 작업이 없는지 먼저 확인합니다.

운영 접근은 사람이 아니라 파이프라인이 한다

지금까지 본 사고의 상당수는 누군가 운영에 직접 손을 댄 데서 시작했습니다. 운영 환경에 사람이 직접 kubectl apply나 terraform apply를 할 수 있으면, 리뷰와 기록을 우회하는 길이 열려 있는 셈입니다.

그래서 목표는 평소의 모든 운영 변경이 PR과 파이프라인을 거치는 것입니다. 사람에게는 운영 읽기 권한만 주고, 쓰기 권한은 배포 파이프라인의 역할에만 줍니다. 그 역할도 environment 승인과 브랜치 제한, OIDC 신뢰 정책으로 묶습니다.

장애 때는 예외 경로가 필요하므로, 이것을 미리 설계해 둡니다.

  • 긴급 접근(break-glass): 평소 잠긴 고권한 역할을 승인 후 짧게 받아 쓰고, 사용 사실을 자동으로 알립니다.
  • 감사 기록: 누가 언제 어떤 권한으로 무엇을 했는지 남깁니다(AWS는 CloudTrail, 16장).
  • 사후 반영: 긴급 변경은 반드시 코드로 옮겨, GitOps와 Terraform의 drift를 없앱니다.

정리

  • CI/CD는 커밋에서 운영까지를 매번 같은 자동 경로로 만듭니다. 작은 PR, 보호된 main, 싼 검사부터 도는 CI가 그 입구이고, 이미지는 한 번 빌드해 커밋 SHA 태그로 승격하며, 환경 차이는 설정으로만 둡니다.
  • 파이프라인의 권한은 저장하지 않고 빌려 씁니다. GitHub Actions는 OIDC 토큰을 STS에서 임시 키로 바꾸고, 신뢰 정책의 sub 조건으로 어느 저장소의 어느 환경만 믿을지 좁힙니다.
  • 배포 전략은 비용, 롤백 속도, 영향 범위의 교환입니다. Rolling은 싸고, Blue-Green은 즉시 되돌리고, Canary는 영향을 가장 작게 묶으며, Feature Flag는 배포와 출시를 떼어 놓습니다.
  • 무중단은 전략보다 공존을 견디는 장치에 달려 있습니다. readiness, Graceful Shutdown과 종료 예산, Expand-Contract가 없으면 어떤 전략도 502와 스키마 오류를 냅니다.
  • GitOps와 IaC는 Git을 원하는 상태의 원본으로 삼습니다. 도구가 실제 상태와 비교해 맞추고 수동 변경은 drift로 드러나며, Terraform state는 장부이자 비밀 저장소라 원격에 두고 잠그고 접근을 좁힙니다.

스스로 점검 (1)

  1. 공유 브랜치를 rebase하고 강제 push하면 왜 동료가 곤란해지나요?

    rebase는 커밋을 다시 적용해 해시가 모두 새것이 됩니다. 동료가 가진 옛 해시의 커밋과 서버의 새 기록이 어긋나, 동료의 다음 병합에서 같은 변경이 중복되거나 충돌합니다.

  2. stage와 prod에서 각각 이미지를 다시 빌드하면 어떤 위험이 있나요?

    그사이 의존성이나 베이스 이미지가 바뀌어 stage에서 검증한 것과 다른 바이너리가 운영에 나갈 수 있습니다. 한 번 빌드한 이미지를 태그로 승격해야 검증이 의미를 가집니다.

  3. 지속적 전달과 지속적 배포의 차이를 GitHub Actions 설정으로 표현하면?

    운영 배포 job에 필수 리뷰어가 걸린 environment를 붙이면 지속적 전달, 승인 없이 검사 통과 후 자동 실행되면 지속적 배포입니다.

  4. OIDC 신뢰 정책의 sub 조건을 repo:acme/*로 두면 무엇이 문제인가요?

    조직의 아무 저장소, 아무 브랜치의 워크플로나 그 역할을 맡을 수 있습니다. 저장소와 브랜치 또는 environment까지 좁혀야 합니다.

스스로 점검 (2)

  1. 외부 액션을 @v4 대신 커밋 SHA로 고정하는 이유는?

    태그는 작성자나 탈취자가 다른 커밋으로 옮길 수 있지만, 커밋 해시는 내용이 바뀌면 달라지므로 같은 이름 뒤의 코드를 바꿀 수 없습니다.

  2. Pod 수로 Canary 비율을 정하면 어떤 한계가 있나요?

    비율이 Pod 수에 묶여 1% 같은 작은 비율이 어렵고, HPA가 Pod 수를 바꾸면 비율도 흔들립니다. 트래픽 계층의 가중치 라우팅이 필요합니다.

  3. Feature Flag의 5% 판정에 요청마다 난수를 쓰면 무슨 일이 생기나요?

    같은 사용자가 요청마다 옛 흐름과 새 흐름을 오갑니다. 사용자 ID를 해시해 고정 번호로 판정해야 같은 사용자에게 늘 같은 답을 줍니다.

  4. Spring 대기 25초, preStop 10초인데 유예 시간이 30초면 어떻게 되나요?

    합이 35초라 앱이 진행 중 요청을 끝내기 전에 SIGKILL을 받습니다. 유예 시간을 40초 이상으로 늘리거나 앱 대기 시간을 줄여야 합니다.

스스로 점검 (3)

  1. 컬럼 이름을 바꾸는 마이그레이션을 v2 배포와 함께 하면 무슨 일이 생기나요?

    스키마가 먼저 바뀌므로 남아 있는 v1이 옛 컬럼을 찾다가 즉시 에러를 내고, 롤백해도 v1은 새 스키마를 모릅니다. 추가, 이중 쓰기, 백필, 전환, 삭제로 나눠야 합니다.

  2. selfHeal이 켜진 앱을 장애 중에 kubectl로 스케일하면 어떻게 되나요?

    Argo CD가 drift로 보고 몇 초 안에 Git의 값으로 되돌립니다. 변경을 Git에 커밋하거나 자동 동기화를 잠시 꺼야 합니다.

  3. Terraform state를 잃어버리면 다음 apply에서 무슨 일이 생기나요?

    Terraform은 기존 리소스를 모르므로 전부 새로 만들려 하고, 이름 충돌로 실패하거나 중복 리소스가 생깁니다. 버킷 버전 관리로 이전 state를 복구하거나 import로 다시 들여야 합니다.

  4. plan에서 DB 인스턴스에 -/+가 보이면 무엇을 의심해야 하나요?

    수정할 수 없는 속성을 바꿔 삭제 후 재생성이 계획된 것입니다. 적용하면 데이터가 사라지므로 변경을 되돌리거나 다른 방법을 찾고, prevent_destroy로 미리 막아 둡니다.

스스로 점검 (4)

  1. sensitive = true를 붙인 DB 비밀번호는 안전하게 숨겨지나요?

    화면 출력만 가려질 뿐 state 파일에는 평문으로 남습니다. state 접근을 좁히고, 비밀은 Secrets Manager나 write-only 인자로 state 밖에 둡니다.

  2. 몇 초면 끝나는 ALTER가 왜 서비스 전체 장애가 되나요?

    긴 트랜잭션 때문에 배타적 메타데이터 락을 기다리는 ALTER 뒤에 일반 쿼리가 모두 줄을 서고, 커넥션 풀이 고갈됩니다. 마이그레이션에 짧은 락 대기 제한을 둡니다.

  3. 배포 빈도만 KPI로 삼으면 어떤 부작용이 있나요?

    의미 없는 작은 배포가 늘거나 검증을 건너뛰어 실패율이 올라갈 수 있습니다. 속도 지표와 안정성 지표를 함께 봐야 합니다.
