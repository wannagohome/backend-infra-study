1부

클라우드의 지도부터 그립니다

9장에서 컨테이너로 배포할 준비를 마쳤습니다. 이제 그 컨테이너와 서버가 올라갈 땅, 즉 AWS의 책임 경계와 물리적 구조를 먼저 봅니다.

AWS 서비스는 앞 장 개념의 관리형 구현이다

클라우드는 데이터센터의 서버, 네트워크, 디스크를 API 호출로 빌리고 쓴 만큼 내는 방식입니다. 새로운 원리가 아니라, 익숙한 원리를 남이 운영해 주는 것입니다.

어느 서비스든 마지막 두 줄은 항상 고객 몫입니다. 공개된 버킷이나 과한 권한은 AWS가 막아 주지 않습니다.

리전은 지역, 가용 영역은 장애 격리 단위다

리전은 서울(ap-northeast-2)처럼 지리적으로 떨어진 독립 지역이고, 각 리전에는 보통 세 개 이상의 가용 영역(AZ)이 있습니다. AZ는 전원, 냉각, 네트워크가 분리된 하나 이상의 데이터센터 묶음이며, AZ끼리는 저지연 전용망으로 이어집니다.

그래서 설계의 기본 단위는 AZ 하나를 통째로 잃어도 버티는 구조입니다. 리전은 사용자와의 지연, 데이터 국외 이전 규정, 비용, 필요한 서비스 제공 여부로 고릅니다.

2부

누가 무엇을, 어떤 패킷이 어디로

모든 AWS 호출은 IAM을 통과하고, 모든 패킷은 VPC의 라우팅과 방화벽을 통과합니다. 이 두 관문이 나머지 서비스 전부의 바탕입니다.

기초 원리 여기부터는 정책 평가, 라우팅, 연결 추적이 실제로 어떻게 동작하는지 봅니다.

IAM은 주체에게 정책을 붙여 권한을 준다

IAM은 AWS API를 호출하는 주체가 누구인지 확인(인증)하고, 그 호출을 허락할지 판단(인가)합니다. 7장의 인증과 인가를 AWS 리소스에 적용한 것입니다.

구성 요소정체자격 증명
사용자(User)사람 또는 외부 프로그램 한 명비밀번호, 장기 Access Key
그룹(Group)사용자 묶음. 정책을 한 번에 부여없음(주체가 아님)
역할(Role)누군가 잠시 맡는 권한 모자임시 자격 증명(자동 만료)
정책(Policy)허용·거부를 적은 JSON 문서주체나 리소스에 붙임

역할은 EC2, Lambda 같은 AWS 서비스나 다른 계정, 외부 IdP 사용자가 맡을 수 있습니다. 실무에서는 사람도 역할로 들어오는 방식이 기본이 되었습니다.

정책 한 줄은 누가, 무엇을, 어디에, 언제다

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::app-uploads/*",
    "Condition": {
      "Bool": {"aws:SecureTransport": "true"}
    }
  }]
}

문장(Statement)마다 Effect(허용/거부), Action(API 이름), Resource(대상 ARN), 선택적인 Condition이 있습니다.

이 정책은 특정 버킷의 객체 읽기·쓰기만, 그것도 HTTPS 요청일 때만 허용합니다. "Action": "*"나 "Resource": "*"는 편하지만 사고 범위를 계정 전체로 넓힙니다.

정책 평가: 명시적 Deny가 모든 Allow를 이긴다

  1. 기본은 거부

    어떤 정책도 허용하지 않은 요청은 암묵적으로 거부됩니다.

  2. 명시적 Deny 확인

    적용되는 정책 중 하나라도 Deny면 그 자리에서 거부합니다.

  3. 상한선 확인

    SCP나 권한 경계가 있으면 그 안에서도 허용되어야 합니다.

  4. Allow 찾기

    신원 기반 또는 리소스 기반 정책에 Allow가 있으면 허용합니다.

왜 Deny가 이기게 만들었을까요? 권한은 여러 정책이 겹쳐 쌓이기 때문에, 누가 어디선가 Allow를 추가해도 절대 넘으면 안 되는 선을 지킬 수단이 필요합니다.

같은 계정 안에서 신원 기반 정책과 리소스 기반 정책(예: 버킷 정책)은 합집합으로, SCP와 권한 경계는 교집합으로 작동합니다.

EC2에는 Access Key 대신 역할을 붙인다

EC2 안의 SDK인스턴스 메타데이터(IMDS)
PUT /latest/api/tokenIMDSv2 세션 토큰 요청
토큰 TTL 지정
GET …/security-credentials/역할명
키 보관 없음 임시 키 + 세션 토큰 만료 시각 포함
만료 전에 SDK가 스스로 다시 받음

Access Key는 만료되지 않는 장기 비밀이라 코드, AMI, Git에 섞여 들어가 유출되기 쉽습니다.

역할을 담는 그릇인 인스턴스 프로파일을 EC2에 붙이면, 애플리케이션은 몇 시간짜리 임시 자격 증명을 받아 쓰고 SDK가 알아서 교체합니다. 서버에 비밀을 둘 일이 사라집니다.

최소 권한으로 시작하고, 루트는 잠가 둔다

최소 권한은 지금 하는 일에 필요한 Action과 Resource만 허용하는 원칙입니다. 처음에 넓게 주고 나중에 줄이려 하면, 무엇이 쓰이는지 몰라 결국 줄이지 못합니다.

IAM의 마지막 접근 정보와 Access Analyzer의 정책 생성 기능으로 실제로 호출된 API만 남기는 방식이 현실적입니다.

루트 사용자는 일상 작업에 쓰지 않습니다

루트는 어떤 IAM 정책으로도 제한되지 않습니다. MFA를 걸고, Access Key는 만들지 말고, 관리자 역할을 따로 만들어 씁니다.

키가 유출되었다면

즉시 키를 비활성화하고, 그 키로 무엇을 했는지 CloudTrail(11장)에서 확인한 뒤 새 키로 교체합니다. 가능하면 역할로 옮깁니다.

VPC는 리전 안에 긋는 나만의 사설망이다

VPC는 리전 하나에 걸치는 논리적 네트워크이고, 2장의 사설 IP 대역을 CIDR로 정해 만듭니다(예: 10.0.0.0/16). 서브넷은 그 대역을 잘라 AZ 하나에 놓은 것입니다. 그래서 다중 AZ 구성은 곧 AZ마다 서브넷을 하나씩 두는 일입니다.

서브넷 크기는 /16에서 /28 사이이고, 각 서브넷의 앞 4개와 마지막 1개 주소는 AWS가 예약합니다(네트워크 주소, VPC 라우터, DNS, 예비, 브로드캐스트). /24 서브넷이면 쓸 수 있는 주소는 251개입니다.

CIDR은 나중에 바꾸기 어렵습니다. 다른 VPC나 사내망과 겹치지 않게, 컨테이너가 IP를 많이 쓰는 경우까지 넉넉히 잡습니다.

두 AZ에 걸친 VPC의 기본 모양

Public과 Private은 라우팅 테이블 한 줄 차이다

# Public 서브넷용
대상             타깃
10.0.0.0/16      local
0.0.0.0/0        igw-0a1b2c

# Private 서브넷용 (AZ a)
10.0.0.0/16      local
0.0.0.0/0        nat-0d4e5f  (AZ a)

# DB 서브넷용
10.0.0.0/16      local

서브넷에는 이름표가 아니라 라우팅 테이블이 붙습니다. 기본 경로(0.0.0.0/0)가 IGW로 가면 Public Subnet, 그렇지 않으면 Private Subnet입니다.

목적지에 맞는 경로 중 가장 긴 프리픽스가 이기므로 VPC 내부 통신은 항상 local로 갑니다. 인스턴스가 인터넷과 통신하려면 퍼블릭 IP도 함께 있어야 합니다.

NAT Gateway는 나가는 문만 연다

Private 서버도 패키지 설치나 외부 API 호출처럼 밖으로 나갈 일이 있습니다. NAT Gateway는 2장의 NAT를 관리형으로 만든 것으로, 출발지 주소를 자신의 Elastic IP로 바꿔 내보내고 응답만 되돌려 줍니다.

밖에서 먼저 시작한 연결은 들어올 수 없습니다. DB와 앱을 Private에 두는 이유가 바로 이 비대칭입니다. 대역폭은 5 Gbps에서 시작해 100 Gbps까지 자동으로 늘어납니다.

기본 NAT Gateway는 AZ 하나에 산다

NAT 하나를 여러 AZ가 같이 쓰면 그 AZ 장애 때 나머지 AZ도 외부로 나가지 못합니다. AZ마다 두고 라우팅도 같은 AZ로 맞춥니다.

리전 모드 NAT Gateway

최근에는 워크로드가 있는 AZ로 자동 확장되는 리전 모드도 있어, AZ별 NAT와 라우팅을 직접 관리하는 수고를 줄일 수 있습니다.

보안 그룹과 NACL은 서는 자리가 다르다

항목보안 그룹(Security Group)NACL(Network ACL)
적용 단위ENI(인스턴스의 네트워크 카드)서브넷 경계
상태Stateful: 응답은 자동 허용Stateless: 응답도 규칙 필요
규칙 종류허용만허용과 거부
평가 방식모든 규칙을 합쳐 판단번호 낮은 순, 첫 일치로 결정
기본값인바운드 거부, 아웃바운드 허용기본 NACL은 모두 허용
소스 지정CIDR 또는 다른 보안 그룹CIDR만

실무의 주 방어선은 보안 그룹입니다. NACL은 특정 IP 대역을 서브넷 단위로 차단하는 보조 수단으로 씁니다.

Stateful은 응답 패킷을 기억한다는 뜻이다

클라이언트EC2 :443
SYN 52344 → 443 인바운드 443 허용
SYN + ACK 443 → 52344 연결 추적으로 통과
HTTP 요청 52344 → 443
NACL이라면 아웃바운드 1024–65535 규칙이 따로 필요

응답 패킷의 목적지는 클라이언트가 고른 임시 포트입니다. 보안 그룹은 2장의 TCP 연결 상태를 추적하므로, 허용된 요청의 응답이면 규칙 없이 통과시킵니다.

NACL은 패킷 하나하나를 독립적으로 봅니다. 그래서 인바운드 443만 열고 아웃바운드 임시 포트 범위를 잊으면 요청은 들어오는데 응답이 나가지 못합니다.

보안 그룹은 IP 대신 다른 보안 그룹을 가리킨다

DB 보안 그룹의 소스를 IP 대역 대신 sg-app으로 지정하면, 그 보안 그룹이 붙은 인스턴스만 접근할 수 있습니다.

Auto Scaling으로 서버 IP가 계속 바뀌어도 규칙을 고칠 필요가 없고, 같은 서브넷에 있는 엉뚱한 인스턴스는 IP가 맞아도 막힙니다. 계층마다 바로 앞 계층만 믿는 사슬이 됩니다.

3부

서버를 빌리고, 트래픽을 나누고, 수를 조절한다

EC2는 1장의 컴퓨터를, ELB는 8장의 로드 밸런서를, Auto Scaling은 8장의 스케일 아웃을 API 하나로 다룰 수 있게 만든 것입니다.

EC2 인스턴스 이름에는 성격이 적혀 있다

m7g.large는 계열(m, 범용), 세대(7), 속성(g, Graviton ARM 프로세서), 크기(large)로 읽습니다. 크기가 한 단계 오르면 vCPU와 메모리가 대략 두 배가 됩니다. 인스턴스는 AMI라는 부팅 이미지(OS와 미리 설치한 소프트웨어)로 시작합니다.

계열성격어울리는 워크로드
t (버스트)CPU 크레딧을 쌓았다 씀개발 서버, 한가한 관리 도구
m (범용)CPU와 메모리 균형대부분의 웹·API 서버
c (컴퓨팅 최적화)vCPU당 메모리 적음인코딩, 연산 위주 배치
r (메모리 최적화)vCPU당 메모리 많음큰 힙의 JVM, 인메모리 캐시

같은 서버라도 사는 방법에 따라 값이 다르다

구매 옵션약정할인맞는 용도

Savings Plans, 예약 인스턴스1년 또는 3년 사용량 약정최대 약 72%항상 켜 두는 기준 용량
스팟(Spot)없음, 2분 전 회수 통보최대 90%중단돼도 되는 작업만

스팟은 AWS의 남는 용량이라 언제든 회수될 수 있습니다. 그래서 상태 없는 서버, 재시도 가능한 배치에만 씁니다. 실무에서는 기준 용량은 Savings Plans로, 그 위의 변동분은 온디맨드와 스팟을 섞어 채웁니다.

ALB는 요청을 읽고, NLB는 연결을 넘긴다

2장의 L7/L4 구분과 8장의 로드 밸런싱을 그대로 옮긴 두 제품입니다. 둘 다 여러 AZ에 노드를 두는 관리형 서비스입니다.

항목ALB(Application LB)NLB(Network LB)
계층L7: HTTP, HTTPS, gRPCL4: TCP, UDP, TLS

IP 주소노드 IP가 바뀜, DNS 이름으로 접근AZ별 고정 IP, EIP 지정 가능
Cross-Zone 기본값항상 켜짐꺼짐
어울리는 곳웹, REST API, 경로별 서비스 분기비 HTTP 프로토콜, 고정 IP 요구

요청은 리스너, 규칙, 대상 그룹 순으로 흐른다

  1. 클라이언트DNS로 ALB 노드 IP 획득
  2. 리스너:443, 인증서로 TLS 종료
  3. 규칙/api/* 이면 api 대상 그룹
  4. 대상 그룹건강한 대상만 후보
  5. 대상EC2, IP, Lambda

대상 그룹마다 헬스 체크를 따로 설정합니다. ALB 기본값은 30초 간격, 5초 타임아웃이고, 연속 2번 실패하면 제외, 연속 5번 성공해야 복귀합니다. 즉 죽은 서버는 약 1분 안에 빠지지만 살아난 서버가 돌아오는 데는 2분 넘게 걸립니다.

Cross-Zone과 TLS 종료가 기본 동작을 바꾼다

클라이언트 트래픽은 먼저 AZ별 노드에 반씩 나뉩니다. Cross-Zone이 꺼져 있으면 노드는 자기 AZ의 대상에만 보냅니다. AZ a에 2대, AZ b에 8대라면 a의 서버는 각각 25%, b의 서버는 6.25%를 받습니다.

켜면 열 대가 똑같이 10%씩 받습니다. ALB는 항상 켜져 있고, NLB는 꺼져 있는 것이 기본이라 대상 수를 AZ마다 고르게 맞추는 것이 중요합니다.

HTTPS 리스너에 ACM 인증서를 붙이면 ALB가 TLS 종료를 맡고, 뒤쪽 서버는 평문 HTTP로 받을 수 있습니다. 2장의 TLS 핸드셰이크 비용과 인증서 갱신을 ALB가 대신 지는 셈입니다.

대신 서버가 보는 원래 클라이언트 IP와 프로토콜은 X-Forwarded-For, X-Forwarded-Proto 헤더로 읽어야 합니다.

Auto Scaling은 희망 용량을 계속 맞춰 준다

시작 템플릿에는 AMI, 인스턴스 유형, 보안 그룹, IAM 역할, 사용자 데이터처럼 "서버 한 대를 만드는 법"을 적습니다.

Auto Scaling 그룹은 최소, 희망, 최대 용량을 갖고, 실제 대수가 희망 용량과 다르면 맞을 때까지 인스턴스를 띄우거나 내립니다. 스케일링 정책은 결국 희망 용량을 바꾸는 장치입니다.

  1. 희망 용량 결정

    정책이나 사람이 desired 값을 바꿉니다(min ≤ desired ≤ max).

  2. AZ에 고르게 배치

    지정한 서브넷의 AZ들에 균형 있게 인스턴스를 띄웁니다.

  3. 대상 그룹 등록

    새 인스턴스를 ALB 대상 그룹에 자동으로 붙입니다.

  4. 비정상 교체

    헬스 체크에 실패한 인스턴스를 종료하고 새로 띄웁니다.

스케일링 정책은 언제 몇 대를 바꿀지 정한다

정책동작어울리는 상황
대상 추적(Target Tracking)지표를 목표값에 맞춤(CPU 50% 등)기본 선택, 대부분의 웹 서비스
단계 조정(Step)경보 초과 폭에 따라 단계별 증감급증 폭에 따라 다르게 대응

예측(Predictive)과거 패턴으로 미리 증설주기가 뚜렷한 트래픽

새 인스턴스는 부팅과 JVM 워밍업이 끝나야 제 몫을 합니다. 그래서 단순 정책에는 기본 300초의 쿨다운이, 대상 추적에는 인스턴스 워밍업 시간이 있어 같은 신호로 과하게 늘어나는 것을 막습니다. 어떤 지표로 스케일할지는 11장에서 다룹니다.

4부

데이터는 어디에, 어떤 모양으로 두는가

객체 저장소 S3, 블록 디스크 EBS, 그리고 4장의 복제와 백업을 관리형으로 만든 RDS와 Aurora를 봅니다.

S3는 파일 시스템이 아니라 키-값 객체 저장소다

S3는 버킷 안에 키와 객체를 저장합니다. images/2026/a.png의 슬래시는 폴더가 아니라 키 문자열의 일부(접두사)일 뿐입니다. 그래서 이름 바꾸기는 복사 후 삭제이고, 파일 중간만 고쳐 쓰는 일은 없습니다. 객체는 통째로 교체됩니다.

객체는 기본적으로 세 개 이상의 AZ에 나뉘어 저장되어 99.999999999%(11 nines) 내구성을 목표로 설계되었습니다. 그리고 쓰기나 삭제 직후의 읽기에 강한 일관성(strong read-after-write)을 보장하므로, 방금 올린 객체가 안 보이는 일은 없습니다.

스토리지 클래스는 접근 빈도로 고른다

버저닝을 켜면 덮어쓰거나 지워도 이전 버전이 남고, 삭제는 삭제 마커가 됩니다. 수명 주기 규칙으로 오래된 객체를 싼 클래스로 옮기고 이전 버전을 만료시켜 비용이 끝없이 늘지 않게 합니다.

S3 접근은 세 겹의 장치가 함께 결정한다

IAM 정책은 주체 쪽에 붙어 "이 역할은 무엇을 할 수 있나"를, 버킷 정책은 리소스 쪽에 붙어 "이 버킷에 누가 접근할 수 있나"를 적습니다. 버킷 정책에는 Principal 필드가 있습니다.

평가는 앞에서 본 규칙 그대로입니다. 같은 계정이면 둘 중 하나만 허용해도 되고, 다른 계정이 접근하려면 양쪽 모두 허용해야 합니다.

퍼블릭 액세스 차단이 맨 위에 있다

Block Public Access는 정책이나 ACL이 공개를 허용해도 덮어씁니다. 새 버킷은 기본으로 켜져 있으니, 계정 수준에서도 켜 둡니다.

공개해야 하는 정적 파일은

버킷을 열지 말고 CloudFront 뒤에 두고 OAC로 CloudFront만 읽게 합니다(이 장 5부).

Presigned URL은 서버가 자기 자격 증명으로 특정 객체, 특정 동작, 만료 시각에 서명해 준 URL입니다. 받은 사람은 자격 증명 없이 그 일 하나만 할 수 있습니다.

서명한 주체의 권한을 넘지 못하고, 역할로 서명했다면 역할 세션이 끝날 때 URL도 함께 만료됩니다. 최대 기간은 7일입니다.

블록, 파일, 객체는 붙는 방식이 다르다

EBS는 네트워크로 붙는 디스크라 인스턴스를 멈춰도 데이터가 남습니다. gp3는 용량과 무관하게 3,000 IOPS와 125 MiB/s를 기본으로 줍니다. 다른 AZ로 옮기려면 S3에 증분 저장되는 스냅샷을 거칩니다.

Multi-AZ는 가용성용, 읽기 전용 복제본은 확장용

RDS는 OS와 엔진 패치, 백업, 장애 조치를 AWS가 맡는 관리형 DB입니다. 4장의 복제를 목적에 따라 두 제품으로 나눴습니다.

항목Multi-AZ(대기 인스턴스)읽기 전용 복제본(Read Replica)

대기 인스턴스 두 개가 읽기도 받는 Multi-AZ DB 클러스터 배포도 있습니다. 둘은 함께 쓸 수 있습니다.

Multi-AZ 장애 조치는 DNS를 바꿔서 끝난다

  1. 장애 감지

    기본 인스턴스, 스토리지, 네트워크, AZ의 이상을 RDS가 감지합니다.

  2. 대기 승격

    동기 복제본이므로 커밋된 데이터는 이미 대기 쪽에 있습니다.

  3. DNS 전환

    엔드포인트의 CNAME이 새 기본 인스턴스 IP를 가리킵니다.

  4. 재연결

    기존 커넥션은 끊깁니다. 애플리케이션이 다시 연결해야 합니다.

보통 60~120초가 걸리고, 큰 트랜잭션이 복구 중이면 더 길어집니다. 엔드포인트 이름이 같으니 설정은 그대로지만, 앱이 옛 IP를 캐시하거나 죽은 커넥션을 붙잡고 있으면 장애가 길어집니다.

이 절차는 장애뿐 아니라 패치나 인스턴스 유형 변경 때도 쓰여 중단 시간을 줄입니다. 앱 쪽 대응은 6부에서 봅니다.

자동 백업은 스냅샷과 로그로 PITR을 만든다

RDS는 매일 백업 창에 스냅샷을 찍고, 그 사이의 트랜잭션 로그를 S3에 계속 올립니다. 스냅샷에 로그를 재생하면 보관 기간 안의 특정 시점으로 복원할 수 있습니다. 4장의 WAL 재생과 같은 원리이고, 보통 현재 시각 5분 전까지 복원됩니다.

보관 기간은 0~35일입니다. 콘솔로 만들면 기본 7일, API는 기본 1일이며 0으로 두면 자동 백업이 꺼집니다.

복원하면 새 인스턴스가 생긴다

기존 DB를 되돌리는 것이 아닙니다. 새 엔드포인트로 앱을 돌리고, 보안 그룹과 파라미터 그룹도 다시 확인해야 합니다.

수동 스냅샷은 보관 기간과 상관없이, DB를 지워도 남습니다. 큰 변경 전에는 수동 스냅샷을 찍어 둡니다.

Aurora는 DB 엔진과 스토리지를 떼어 냈다

RDS는 인스턴스마다 자기 디스크가 있고 복제로 맞춥니다. Aurora는 모든 인스턴스가 3개 AZ에 걸친 하나의 클러스터 볼륨을 공유하고, 데이터를 6개 스토리지 노드에 씁니다.

6개 중 4개가 확인하면 쓰기가 끝나므로 AZ 하나(사본 2개)를 잃어도 쓰기가 계속됩니다. 복제본은 같은 볼륨을 읽기만 해서 지연이 짧고, 최대 15개까지 두며, 장애 시 보통 30초 안팎에 승격됩니다.

ElastiCache와 DynamoDB는 짧게 짚는다

ElastiCache는 8장의 Redis(현재는 Valkey, Redis OSS)와 Memcached를 관리형으로 제공합니다. 노드 교체, 패치, 복제본 자동 장애 조치를 AWS가 맡고, 클러스터 모드로 데이터를 여러 샤드에 나눕니다.

캐시 전략, 스탬피드, 세션 외부화 같은 설계 판단은 여전히 우리 몫입니다. 보통 Private Subnet에 두고 앱 보안 그룹만 허용합니다.

DynamoDB는 서버를 고르지 않는 키-값/문서형 NoSQL입니다. 파티션 키로 데이터를 나누고, 정렬 키로 같은 파티션 안의 범위 조회를 합니다.

요청 수대로 내는 온디맨드와 처리량을 미리 정하는 프로비저닝 모드가 있습니다. 항목 하나는 400KB까지이고, 접근 패턴을 먼저 정한 뒤 키를 설계합니다(4장 NoSQL 비교 참고).

5부

사용자는 이름으로 찾아오고, 엣지에서 받는다

2장의 DNS는 Route 53으로, 8장의 CDN은 CloudFront로 구현됩니다. 둘 다 리전이 아니라 전 세계 엣지에서 동작합니다.

Route 53: Alias와 라우팅 정책

2장에서 본 대로 CNAME은 존 최상위(example.com 자체)에 둘 수 없습니다. Route 53의 Alias 레코드는 ALB, CloudFront, S3 같은 AWS 리소스를 가리키되 A 레코드처럼 IP로 바로 답하므로 최상위에도 쓸 수 있습니다.

대상의 IP가 바뀌면 자동으로 따라가고, TTL은 대상의 기본값을 씁니다.

라우팅 정책답하는 방식
단순정해진 값 그대로
가중치비율대로 분배(Canary 배포)
지연 시간지연이 가장 낮은 리전
장애 조치헬스 체크 실패 시 보조로
지리적 위치사용자의 국가, 대륙별
다중 값 응답건강한 IP 여러 개

CloudFront는 엣지에서 캐시로 먼저 답한다

  1. 사용자가장 가까운 엣지로 연결
  2. 엣지 로케이션캐시 적중이면 즉시 응답
  3. 리전별 엣지 캐시엣지들이 공유하는 중간층
  4. 오리진S3 버킷 또는 ALB

캐시는 캐시 키(기본은 URL 경로, 필요하면 쿼리·헤더·쿠키 일부)로 구분하고, TTL 동안 오리진에 묻지 않습니다. 캐시 키에 넣는 값이 많을수록 적중률이 떨어지므로 꼭 필요한 것만 넣습니다.

정적 자산뿐 아니라 API 앞에 두어도 TLS 연결이 사용자 가까이에서 끝나고 AWS 백본을 타므로 지연이 줄어듭니다.

OAC로 S3를 잠그고, 무효화 대신 버전을 바꾼다

OAC를 쓰면 CloudFront가 서명한 요청으로 S3를 읽고, 버킷 정책은 그 배포만 허용합니다. 버킷은 계속 비공개이고 S3 URL로 직접 들어오는 길은 막힙니다. 예전 방식인 OAI는 레거시로 분류되었습니다.

배포 후 옛 파일이 보이면 무효화로 엣지 캐시를 지웁니다. 매달 1,000개 경로까지 무료이고, /images/* 같은 와일드카드는 한 경로로 셉니다.

파일 이름에 버전을 넣으면 무효화가 필요 없다

app.3f9c2a.js처럼 내용 해시를 붙여 배포하면 새 파일은 새 URL이라 바로 반영됩니다. 긴 TTL을 걸 수 있고, 무효화는 HTML 같은 진입 파일에만 씁니다.

6부

설정은 맞는데 운영에서 터지는 지점들

서비스 하나하나의 기본값이 실제 운영에서 어떤 사고로 이어지는지, 그리고 무엇으로 막는지 봅니다.

원리 실무 접속 경로, 비용, 헬스 체크, 장애 조치 후 재연결 문제를 다룹니다.

Private 서버 접속은 Bastion 대신 SSM으로

Session Manager는 인스턴스의 SSM 에이전트가 AWS로 먼저 연결을 여는 구조라, 보안 그룹에 SSH를 열 필요가 없습니다. 대신 인스턴스 역할에 SSM 권한이 있어야 하고, NAT가 없는 서브넷이라면 SSM용 인터페이스 엔드포인트가 필요합니다.

NAT 요금이 이상하게 크다면 VPC 엔드포인트

NAT Gateway는 시간당 요금에 더해 처리한 데이터 GB당 요금이 붙습니다. Private 서버가 S3로 백업을 올리거나 ECR에서 큰 이미지를 받는 트래픽이 모두 NAT를 지나면 청구서가 커집니다.

S3와 DynamoDB는 게이트웨이 엔드포인트를 만들어 라우팅 테이블에 경로를 추가하면 NAT를 우회하며, 추가 요금이 없습니다. 다른 서비스는 시간당 과금되는 인터페이스 엔드포인트(PrivateLink)를 씁니다.

다른 AZ의 NAT를 쓰면 이중으로 낸다

AZ 간 데이터 전송 요금이 NAT 처리 요금에 더해집니다. 앞에서 본 AZ별 NAT 배치는 가용성과 비용 양쪽의 문제입니다.

VPC끼리 연결할 때

VPC Peering은 CIDR이 겹치면 만들 수 없고 전이되지 않습니다. 연결할 VPC가 많아지면 Transit Gateway로 허브를 둡니다.

헬스 체크와 등록 해제 지연을 앱에 맞춘다

Auto Scaling 그룹의 헬스 체크 유형 기본값은 EC2 상태만 봅니다. 프로세스가 죽어도 인스턴스가 켜져 있으면 교체되지 않으므로, ALB 뒤라면 ELB 헬스 체크를 함께 켭니다. 부팅 시간만큼 유예 기간도 줍니다.

스케일 인이나 배포로 대상이 빠질 때 ALB는 기본 300초 동안 진행 중인 요청을 기다립니다. 9장의 Graceful Shutdown 시간과 맞추고, 요청이 짧은 API라면 30~60초로 줄여 배포를 빠르게 합니다.

헬스 체크에서 DB까지 확인하지 마세요

8장의 원칙이 여기서는 더 비싸게 돌아옵니다. 모든 대상이 동시에 비정상이 되면 Auto Scaling이 멀쩡한 서버를 전부 갈아엎습니다.

장애 조치 뒤에 앱이 다시 붙지 않는 이유

RDS 장애 조치는 DNS를 바꿔서 끝나는데, JVM이 DNS 결과를 오래 캐시하면 앱은 계속 옛 IP로 갑니다. AWS는 JVM의 DNS TTL(networkaddress.cache.ttl)을 60초 이하로 두라고 권장합니다.

커넥션 풀(4장)에는 끊긴 연결이 남아 있을 수 있으므로 검증과 최대 수명을 설정해 빨리 버리게 합니다.

RDS Proxy는 앱과 DB 사이의 관리형 커넥션 풀입니다. 장애 조치 동안 앱의 연결을 붙잡고 있다가 새 기본 인스턴스로 이어 주고, Lambda처럼 연결을 마구 여는 클라이언트로부터 DB를 보호합니다.

다만 세션 변수나 임시 테이블을 쓰면 연결을 공유할 수 없어 한 클라이언트에 고정되는 피닝이 생겨 효과가 줄어듭니다.

복제 지연은 지표로 보고 구조로 줄인다

4장에서 본 read-after-write 문제는 RDS 읽기 전용 복제본에서도 그대로 생기고, 대응도 같습니다. 쓴 직후 본인이 다시 읽는 화면과 정확해야 하는 조회는 기본 인스턴스로 보냅니다.

AWS에서 새로 생기는 선택지는 Aurora입니다. 모든 인스턴스가 같은 스토리지를 읽으므로 복제 지연이 보통 100ms 미만이라, 이 문제가 훨씬 작아집니다.

지연을 숫자로 본다

CloudWatch의 ReplicaLag 지표에 알람을 겁니다. 복제본에서 긴 분석 쿼리가 돌면 지연이 몇 분까지 늘어나므로, 분석용 복제본은 서비스용과 분리합니다.

정리

  • AWS 서비스는 앞 장 개념의 관리형 구현입니다. 원리는 같고, 운영 책임의 경계만 공유 책임 모델에 따라 옮겨 갑니다.
  • IAM은 기본 거부, 명시적 Deny 우선입니다. 서버에는 장기 키 대신 역할을 붙이고, 루트는 MFA로 잠급니다.
  • Public과 Private은 라우팅 테이블이 정합니다. NAT Gateway는 나가는 길만 열고, 보안 그룹은 연결을 추적하며 다른 보안 그룹을 소스로 삼습니다.
  • 가용성은 AZ 단위로 설계합니다. ALB, Auto Scaling, RDS Multi-AZ, Aurora 모두 AZ 하나를 잃어도 버티도록 만들어졌습니다.
  • 기본값이 사고를 만듭니다. 헬스 체크 유형, 등록 해제 지연, DNS 캐시, 복제 지연을 앱과 맞춰야 장애 조치가 실제로 작동합니다.

스스로 점검 (1)

  1. RDS를 쓰면 보안 사고 책임이 모두 AWS로 넘어가나요?

    아닙니다. OS와 엔진 패치는 AWS가 맡지만 보안 그룹, IAM 권한, 데이터 암호화 선택은 여전히 고객 몫입니다.

  2. IAM 정책에서 Allow를 줬는데도 거부된다면 어디를 봐야 하나요?

    다른 정책의 명시적 Deny, 그리고 SCP나 권한 경계 같은 상한선입니다. 그중 하나라도 막으면 Allow는 의미가 없습니다.

  3. 서브넷 이름이 public-a인데 인터넷에서 접속이 안 됩니다. 무엇을 확인하나요?

    라우팅 테이블에 0.0.0.0/0 → IGW 경로가 있는지, 인스턴스에 퍼블릭 IP가 있는지, 보안 그룹이 허용하는지입니다. 이름은 아무것도 결정하지 않습니다.

  4. NACL에 인바운드 443만 허용했더니 응답이 안 옵니다. 왜인가요?

    NACL은 Stateless라 응답 패킷도 규칙으로 평가합니다. 아웃바운드에 클라이언트 임시 포트 범위(1024–65535)를 허용해야 합니다.

  5. Multi-AZ 대기 인스턴스로 읽기 부하를 나눌 수 있나요?

    단일 대기 인스턴스 방식은 읽기를 받지 않습니다. 읽기 분산은 읽기 전용 복제본이나 Aurora Reader, Multi-AZ DB 클러스터로 합니다.

스스로 점검 (2)

  1. NLB 뒤에서 AZ a에 2대, AZ b에 8대를 두었더니 a의 서버만 과부하입니다. 왜인가요?

    NLB는 Cross-Zone이 기본으로 꺼져 있어 노드가 자기 AZ 대상에만 보냅니다. Cross-Zone을 켜거나 AZ별 대수를 맞춥니다.

  2. 역할로 만든 Presigned URL이 7일로 지정했는데 몇 시간 만에 만료됐습니다. 왜인가요?

    임시 자격 증명으로 서명한 URL은 그 자격 증명이 만료되면 함께 만료됩니다. 지정한 기간보다 세션 만료가 먼저 옵니다.

  3. Aurora는 왜 AZ 하나를 잃어도 쓰기를 계속할 수 있나요?

    데이터를 3개 AZ에 2개씩 6개로 쓰고 4개만 확인되면 쓰기를 완료합니다. AZ 하나가 사라져도 4개가 남습니다.

  4. 프로세스가 죽은 서버가 Auto Scaling에서 교체되지 않습니다. 무엇을 바꾸나요?

    헬스 체크 유형에 ELB를 추가합니다. EC2 유형만으로는 인스턴스가 켜져 있으면 정상으로 봅니다.

  5. RDS 장애 조치가 끝났는데 앱은 몇 분째 DB 오류를 냅니다. 원인 후보는?

    JVM이 옛 IP를 DNS 캐시로 들고 있거나 커넥션 풀에 끊긴 연결이 남아 있는 경우입니다. DNS TTL을 줄이고 풀 검증을 켜거나 RDS Proxy를 씁니다.
