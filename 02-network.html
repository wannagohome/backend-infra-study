패킷은 어떻게 상대를 찾아가는가

계층과 캡슐화, IP 주소와 서브넷, NAT, 포트, DNS, 그리고 HTTP 메시지의 생김새까지. 네트워크를 읽기 위한 기본 어휘를 갖춥니다.

소켓 너머에는 다른 컴퓨터가 있다

1장에서 프로세스는 파일, 파이프, 소켓을 모두 파일 디스크립터 하나로 다룬다는 것을 봤습니다. 그중 소켓은 같은 컴퓨터를 넘어 바다 건너 다른 컴퓨터의 프로세스와도 이어지는 통로입니다.

애플리케이션은 write(fd, buf) 한 줄만 호출합니다. 그 아래에서 커널은 데이터를 잘게 나누고, 주소를 붙이고, 수많은 장비를 거쳐 보냅니다. 이 장은 그 여정을 아래에서 위로 따라갑니다.

  1. 프로세스write(fd) 호출
  2. 소켓커널의 연결 끝점
  3. TCP/IP 스택나누고 주소를 붙임
  4. 네트워크 카드전기 신호로 송출
  5. 라우터들목적지까지 중계

와이파이가 유선으로 바뀌어도 브라우저 코드는 그대로입니다. 통신을 계층으로 나누고 각 계층이 바로 아래 계층의 기능만 쓰게 했기 때문입니다. 실무에서 쓰는 모델은 TCP/IP 4계층이지만, "L4", "L7" 같은 번호는 OSI 7계층에서 왔습니다.

아래층은 위층 데이터를 봉투에 넣는다

보내는 쪽에서 데이터는 계층을 내려갈 때마다 그 계층의 헤더로 한 겹씩 감싸집니다. 이것을 캡슐화라고 합니다.

헤더에는 그 계층에 필요한 정보만 있습니다. TCP는 포트와 순서 번호, IP는 출발지와 목적지 IP, 이더넷은 바로 다음 장비의 MAC 주소입니다.

중간 라우터는 IP 헤더까지만 열어 보고 안쪽은 보지 않습니다. 받는 쪽은 역순으로 헤더를 벗겨 냅니다.

IP 주소는 네트워크와 호스트로 나뉜다

IPv4 주소는 32비트 숫자를 8비트씩 끊어 192.168.10.37처럼 씁니다. 앞부분은 어느 네트워크인지, 뒷부분은 그 안의 어느 호스트인지를 뜻하고, 경계는 서브넷 마스크가 정합니다.

주소와 마스크를 비트 AND 하면 네트워크 주소가 나옵니다. 두 주소의 네트워크 주소가 같으면 라우터 없이 직접 전달할 수 있는 같은 네트워크입니다.

IP 주소     192.168.10.37    11000000.10101000.00001010.00100101
마스크      255.255.255.0    11111111.11111111.11111111.00000000
네트워크    192.168.10.0     11000000.10101000.00001010.00000000
            앞 24비트 = 네트워크 부분, 뒤 8비트 = 호스트 부분

CIDR은 네트워크 크기를 비트 수로 말한다

CIDR 표기 10.0.1.0/24의 /24는 앞 24비트가 네트워크라는 뜻입니다. 호스트에 남는 비트가 8개이므로 주소는 2⁸ = 256개이고, 숫자가 클수록 작은 네트워크입니다. 맨 앞(네트워크 주소)과 맨 뒤(브로드캐스트) 주소는 호스트에 쓰지 않습니다.

CIDR서브넷 마스크주소 개수쓰임
10.0.0.0/8255.0.0.016,777,216사설 대역(가장 큼)
172.16.0.0/12255.240.0.01,048,576사설 대역
192.168.0.0/16255.255.0.065,536사설 대역(가정용 공유기)

 위 세 개는 RFC 1918이 정한 사설 대역으로, 인터넷에서 라우팅되지 않습니다. 13장의 VPC 설계는 큰 대역(/16)을 잡고 겹치지 않는 서브넷(/24)으로 쪼개는 일입니다.

같은 네트워크면 ARP, 밖이면 게이트웨이

  1. 목적지 판정

    목적지 IP에 내 마스크를 AND 해서 같은 네트워크인지 봅니다.

  2. 같은 네트워크

    ARP 브로드캐스트로 "이 IP의 MAC 주소는?"을 묻고 직접 보냅니다.

  3. 다른 네트워크

    기본 게이트웨이(라우터)의 MAC을 알아내 그쪽으로 프레임을 보냅니다.

  4. 라우터 중계

    라우팅 테이블로 다음 홉을 고르고 새 이더넷 헤더로 다시 감쌉니다.

IP 주소는 최종 목적지, MAC 주소는 바로 다음 장비를 가리킵니다. 그래서 라우터를 지날 때마다 IP 헤더는 그대로이고 이더넷 헤더만 바뀝니다.

라우팅 테이블은 "이 대역은 저쪽으로"라는 규칙 목록입니다. 13장의 VPC 라우팅 테이블이 바로 이것입니다.

IP, 마스크, 게이트웨이, DNS 서버 주소는 부팅 때 DHCP로 받습니다. 아직 내 IP가 없으므로 UDP 브로드캐스트로 요청합니다.

NAT는 사설 주소를 공인 주소로 바꿔 내보낸다

사설 IP는 인터넷에서 길을 찾을 수 없습니다. NAT 장비는 나가는 패킷의 출발지 주소와 포트를 자신의 공인 주소와 새 포트로 바꾸고, 그 짝을 변환 표에 적어 둡니다.

응답이 돌아오면 표를 보고 원래 주소로 되돌립니다. 표에 없는 연결, 즉 밖에서 먼저 시작한 연결은 들어올 수 없습니다. 13장의 Private Subnet과 NAT Gateway가 이 원리입니다.

IP는 컴퓨터까지, 포트는 프로세스까지

16비트 포트는 한 컴퓨터 안에서 어느 프로세스인지를 가립니다. 서버는 정해진 포트(443, 5432)에서 기다리고, 클라이언트는 OS가 고른 임시 포트를 씁니다. 리눅스 기본 범위는 32768~60999입니다.

TCP 연결은 프로토콜, 출발지 IP·포트, 목적지 IP·포트의 5-tuple로 구별됩니다. 그래서 서버 443 포트 하나에 수만 개의 연결이 붙을 수 있고, 각 연결은 프로세스에게 fd 하나입니다.

TCP는 보장을 사고, UDP는 속도를 산다

전송 계층에는 두 선택지가 있습니다. TCP는 연결을 맺고 도착과 순서를 보장하는 대신 왕복과 상태를 치르고, UDP는 IP 위에 포트만 얹어 바로 보냅니다.

DNS는 이름을 단계적으로 물어 찾는다

브라우저는 먼저 자기 캐시, OS 캐시와 hosts 파일을 봅니다. 없으면 재귀 리졸버에게 "답을 끝까지 찾아 달라"고 재귀 질의를 보냅니다.

리졸버는 루트, TLD, 권한 서버 순으로 반복 질의하며 "다음엔 어디로"를 따라가고 결과를 캐시합니다. 보통 UDP 53번을 쓰고, 응답이 크면 TCP로 다시 묻습니다.

레코드는 답의 종류, TTL은 답의 유효기간

레코드의미예
A이름 → IPv4 주소api.example.com → 203.0.113.10
AAAA이름 → IPv6 주소api.example.com → 2001:db8::10
CNAME이름 → 다른 이름(별칭)www → shop.cdn.example.net
NS이 영역의 권한 서버example.com → ns1.example.net
MX메일을 받을 서버example.com → mail.example.com

모든 레코드에는 TTL(초)이 붙고, 리졸버와 브라우저는 그동안 답을 재사용합니다. TTL이 길면 조회가 줄지만 바뀐 주소가 늦게 퍼집니다.

IP를 옮기기 전에 TTL부터 낮추세요

HTTP는 무상태입니다. 요청 하나하나가 독립적이고 서버는 이전 요청을 기억하지 않습니다. 확장은 쉽지만 "로그인 상태"는 따로 만들어야 하며, 그것이 2부의 쿠키입니다.

2부

연결과 신뢰와 보안은 어떻게 만들어지나

TCP가 연결을 맺고 끊는 과정, 유실과 혼잡을 견디는 방법, HTTP의 진화, TLS와 쿠키, 그리고 요청이 지나는 프록시와 서버의 역할까지 내부를 봅니다.

기초 원리 여기부터는 프로토콜 상태와 커널 동작을 다룹니다.

연결이란 서로의 시작 번호를 아는 상태다

클라이언트서버
SYN_SENT SYN seq=x (내 ISN) LISTEN
SYN + ACK seq=y, ack=x+1 SYN_RCVD
ESTABLISHED ACK ack=y+1서버의 ISN이 닿았음을 확인 ESTABLISHED
데이터를 보내기 전 1 RTT

TCP는 바이트마다 번호를 매기므로, 양쪽이 서로의 시작 번호(ISN)를 알고 상대가 그것을 받았는지 확인해야 합니다. 두 번만 주고받으면 서버는 자기 ISN이 도착했는지 모른 채 연결을 열게 됩니다.

ISN을 0이 아닌 난수로 고르는 이유는 이전 연결의 늦은 패킷과 섞이지 않게 하고, 공격자가 번호를 맞혀 끼어들지 못하게 하기 위해서입니다.

핸드셰이크는 커널의 두 큐에서 일어난다

  1. listen()

    소켓을 LISTEN으로 바꾸고 SYN 큐와 accept 큐를 만듭니다.

  2. SYN 도착

    반쯤 열린 연결을 SYN 큐에 두고 SYN+ACK를 보냅니다.

  3. ACK 도착

    완성된 연결을 accept 큐로 옮깁니다.

  4. accept()

    애플리케이션이 꺼내 갈 때 새 fd가 생깁니다.

SYN 플러딩은 위조한 출발지로 SYN만 대량으로 보내 SYN 큐를 채우는 공격입니다. 마지막 ACK는 오지 않으니 정상 사용자가 들어올 자리가 사라집니다.

방어책인 SYN 쿠키는 큐에 상태를 저장하지 않고, 그 정보를 서버의 ISN 안에 암호학적으로 담아 보냅니다. ACK가 돌아오면 그 번호로 검증해 연결을 복원합니다.

종료가 네 번인 이유는 반쪽씩 닫기 때문이다

먼저 닫는 쪽상대
FIN_WAIT_1 FIN 더 보낼 것 없음 CLOSE_WAIT
FIN_WAIT_2 ACK
남은 데이터이 방향은 아직 열려 있음
FIN 나도 끝 LAST_ACK
TIME_WAIT ACK CLOSED

TCP 연결은 두 방향의 통로가 따로 닫힙니다. FIN은 "나는 더 보낼 게 없다"는 뜻일 뿐이고, 상대는 아직 보낼 데이터가 남았을 수 있습니다(half-close).

그래서 상대는 ACK는 바로 보내되 자기 FIN은 일을 마친 뒤 따로 보냅니다. 수립 때처럼 SYN과 ACK를 합쳐 한 번에 보낼 수 없는 이유입니다.

TIME_WAIT는 마지막을 책임지는 대기다

마지막 ACK를 보낸 쪽은 바로 사라지지 않고 TIME_WAIT로 기다립니다. 이유는 두 가지입니다.

첫째, 마지막 ACK가 유실되면 상대가 FIN을 다시 보내는데, 그때 응답할 주체가 남아 있어야 합니다. 둘째, 네트워크를 떠돌던 옛 연결의 패킷이 같은 주소와 포트를 쓰는 새 연결에 섞이지 않도록 패킷 수명의 두 배(2MSL)만큼 기다립니다.

리눅스는 TIME_WAIT를 60초로 고정해 둡니다. 이 값은 sysctl로 바꿀 수 없습니다.

TIME_WAIT는 먼저 닫은 쪽에 생깁니다

클라이언트냐 서버냐가 아니라 누가 먼저 FIN을 보냈느냐로 정해집니다. 3부의 포트 고갈이 여기서 시작됩니다.

신뢰성은 번호, 확인, 재전송으로 만든다

IP는 패킷을 잃고, 늦추고, 순서를 바꾸고, 가끔 망가뜨립니다. TCP는 네 가지 장치로 이것을 연속된 바이트 흐름으로 바꿔 애플리케이션에 건넵니다.

장치동작막는 문제
순서 번호보낸 바이트마다 번호를 매김순서 뒤바뀜, 중복
누적 ACK"다음에 받을 번호"를 알림도착 여부 불명
재전송타임아웃 또는 중복 ACK 3개유실
체크섬손상된 세그먼트를 버림비트 오류(재전송으로 복구)

재전송 타임아웃(RTO)은 고정값이 아니라 측정한 RTT로 계속 다시 계산합니다. 같은 ACK가 세 번 겹쳐 오면 타임아웃을 기다리지 않고 바로 다시 보냅니다(빠른 재전송).

흐름 제어는 받는 쪽 버퍼를 지킨다

받는 쪽은 ACK마다 남은 버퍼 크기 rwnd를 알려 줍니다. 보내는 쪽은 확인받지 못한 데이터를 이 크기까지만 내보내므로 수신 버퍼가 넘치지 않습니다. 애플리케이션이 read()를 늦게 하면 rwnd가 0이 되어 보내는 쪽이 멈춥니다.

혼잡 제어는 네트워크 전체를 지킨다

흐름 제어가 상대를 보호한다면, 혼잡 제어는 중간 네트워크를 보호합니다. 보내는 쪽은 스스로 혼잡 윈도우(cwnd)를 정합니다.

새 연결은 작게 시작해 RTT마다 두 배로 늘리고(Slow Start), 임계값을 넘으면 1씩 늘립니다. 유실을 감지하면 크게 줄입니다. 더할 때는 조금, 뺄 때는 크게 하는 AIMD 방식입니다.

HTTP/1.1은 연결을 재사용하지만 줄을 선다

HTTP/1.0은 요청마다 TCP 연결을 새로 열었습니다. 매번 핸드셰이크 왕복을 치르는 셈입니다. HTTP/1.1은 응답 뒤에도 연결을 열어 두는 지속 연결(keep-alive)이 기본입니다.

하지만 한 연결에서는 응답이 순서대로 하나씩 옵니다. 앞 응답이 느리면 뒤 요청이 모두 기다리는 HOL 블로킹(Head-of-Line)입니다. 그래서 브라우저는 도메인마다 연결을 여러 개 엽니다.

이름만 같은 두 keep-alive

HTTP keep-alive는 연결을 재사용하는 것이고, TCP keepalive는 유휴 연결에 탐침을 보내 살아 있는지 보는 커널 기능입니다. 리눅스 기본값은 2시간 유휴 후 탐침입니다.

HTTP/2는 다중화하고, HTTP/3는 TCP를 떠났다

항목HTTP/1.1HTTP/2HTTP/3
전송 계층TCPTCPUDP 위의 QUIC
형식텍스트바이너리 프레임바이너리 프레임

HTTP/2는 요청과 응답을 프레임으로 잘라 스트림 번호를 붙이고, 한 연결 위에 섞어 보냅니다. 느린 응답 하나가 다른 응답을 막지 않습니다. 적어도 HTTP 수준에서는 그렇습니다.

HTTP/3가 UDP 위에 TCP를 다시 지은 이유

HTTP/2의 스트림도 결국 TCP라는 하나의 바이트 흐름에 실립니다. 패킷 하나가 유실되면 TCP는 재전송이 올 때까지 뒤의 모든 바이트를 붙잡으므로 모든 스트림이 같이 멈춥니다.

TCP는 커널과 수많은 중간 장비에 박혀 있어 고치기 어렵습니다. 그래서 QUIC은 UDP 위에서 순서와 재전송을 스트림별로 직접 구현하고, TLS 1.3을 합쳐 연결 수립을 1 RTT로 줄였습니다.

네트워크가 바뀌어도 연결이 이어집니다

QUIC은 연결을 IP와 포트가 아닌 연결 ID로 구별합니다. 와이파이에서 LTE로 바뀌어도 다시 연결하지 않습니다.

0-RTT 데이터는 재전송 공격에 열려 있습니다

재연결 때 첫 패킷에 싣는 요청은 공격자가 복사해 다시 보낼 수 있습니다. 멱등한 요청에만 허용합니다.

HTTPS는 두 종류의 암호를 섞어 쓴다

평문 HTTP는 경로 위의 누구든 읽고(도청), 고치고(변조), 서버인 척할(사칭) 수 있습니다. TLS는 TCP와 HTTP 사이에서 기밀성, 무결성, 서버 인증을 제공합니다. SSL은 TLS의 전신으로 모든 버전이 폐기되었고, 지금은 TLS 1.2와 1.3을 씁니다.

공개키 방식은 미리 비밀을 나누지 않아도 되지만 느리고, 대칭키 방식은 빠르지만 키를 안전하게 나눌 방법이 없습니다. 그래서 핸드셰이크에서 공개키 기법으로 대칭 세션 키를 합의하고, 데이터는 대칭키로 암호화합니다. 각 기법의 원리는 7장에서 다룹니다.

  1. TCP 연결3-way handshake
  2. TLS 핸드셰이크키 합의, 인증서 검증
  3. 암호화된 HTTP대칭키로 빠르게

TLS 1.3은 첫 왕복에 키 재료를 싣는다

클라이언트서버
ClientHello 암호 목록, key_share
ServerHello key_share여기서 양쪽이 같은 세션 키를 계산
인증서, 서명, Finished이미 암호화되어 전송
1 RTT Finished + HTTP 요청
HTTP 응답

TLS 1.2는 키 교환까지 2 RTT가 걸렸습니다. 1.3은 클라이언트가 서버가 고를 법한 방식의 키 재료(key_share)를 첫 메시지에 미리 담아 1 RTT로 줄였습니다.

키 교환은 매번 새 임시 키를 쓰는 ECDHE만 남았습니다. 서버 개인키가 나중에 유출되어도 지난 대화는 풀 수 없는 전방 비밀성이 기본입니다.

인증서는 "이 키가 이 도메인 것"이라는 보증이다

키 합의만으로는 상대가 진짜 서버인지 모릅니다. 중간자가 양쪽과 각각 키를 합의하면 그만입니다. 그래서 서버는 신뢰받는 CA가 서명한 인증서를 내밉니다.

브라우저는 되는데 서버 간 호출만 실패한다면

서버가 중간 인증서를 빠뜨린 경우가 흔합니다. 브라우저는 스스로 보충하지만 curl이나 Java 클라이언트는 검증에 실패합니다.

  1. 체인 전송

    서버가 자기 인증서와 중간 CA 인증서를 보냅니다.

  2. 내용 확인

    도메인 이름 일치, 유효기간, 폐기 여부를 봅니다.

  3. 서명 따라 올라가기

    각 인증서의 서명을 윗단계 공개키로 검증합니다.

  4. 루트 대조

    OS나 브라우저에 미리 심어진 루트 CA와 맞춰 봅니다.

  5. 소유 증명

    서버가 개인키로 핸드셰이크에 서명해 키 주인임을 증명합니다.

쿠키는 상태를 요청마다 다시 실어 보낸다

브라우저서버
POST /login 아이디, 비밀번호
Set-Cookie SESSION=8f3a2c; HttpOnly
브라우저가 도메인별 저장소에 보관
GET /orders Cookie: SESSION=8f3a2c
200 OK 내 주문 목록

무상태인 HTTP에서 "아까 그 사용자"를 알아보려면 클라이언트가 매 요청에 단서를 실어 와야 합니다. 서버는 Set-Cookie 헤더로 단서를 맡기고, 브라우저는 도메인, 경로, 만료 조건이 맞는 요청마다 자동으로 Cookie 헤더에 붙입니다.

이 "자동"이 편리함이자 CSRF 공격의 뿌리입니다(7장).

쿠키 속성은 언제, 어디로 보낼지를 정한다

속성의미빠뜨리면
Domain, Path보낼 대상 호스트와 경로설정한 호스트에만 전송
Expires, Max-Age만료 시점브라우저 종료 시 삭제

세션 ID를 담는 쿠키라면 HttpOnly; Secure; SameSite=Lax가 출발점입니다. SameSite는 Strict, Lax, None 세 값이 있고, None을 쓰려면 Secure가 반드시 함께 있어야 합니다. 속성이 없을 때 Chrome, Edge 같은 Chromium 계열은 Lax로 취급하지만 Firefox와 Safari는 기본으로 그렇게 하지 않으므로, 항상 명시합니다.

세션은 쿠키에 열쇠만 두고 상태는 서버에 둔다

쿠키에 사용자 정보를 직접 담으면 노출과 변조 위험이 있고 크기도 4KB 남짓으로 작습니다. 그래서 쿠키에는 추측할 수 없는 무작위 세션 ID만 넣고, 실제 데이터는 서버의 세션 저장소에 둡니다.

무상태 프로토콜 위에 상태를 얹는 것은 모순이 아닙니다. HTTP는 여전히 무상태이고 상태는 애플리케이션이 서버에 보관할 뿐입니다. 대신 서버가 여러 대면 다른 서버는 그 세션을 모릅니다. 이 문제는 8장, 토큰 방식과의 비교는 7장에서 다룹니다.

  1. 브라우저SESSION=8f3a2c
  2. 서버세션 ID로 조회
  3. 세션 저장소8f3a2c → 사용자 7

프록시는 누구 편에 서느냐로 나뉜다

포워드 프록시는 클라이언트 편입니다. 사내망의 요청을 모아 대신 보내며 접근 통제와 캐시를 맡고, 외부 서버는 프록시만 봅니다.

리버스 프록시는 서버 편입니다. 서비스의 단일 입구로서 TLS 종료, 부하 분산, 캐시, 압축을 맡고, 클라이언트는 뒤의 실제 서버를 모릅니다. Nginx가 대표적이며 원래 클라이언트 IP는 X-Forwarded-For로 넘깁니다.

웹 서버는 연결을, WAS는 로직을 맡는다

WAS 앞에 웹 서버를 두면 느린 클라이언트의 업로드나 응답 전송을 웹 서버가 버퍼링해 줍니다. 1장에서 본 이벤트 루프가 값싼 연결 관리를 맡고, 비싼 WAS 스레드는 실제 로직을 도는 동안만 쓰입니다. Tomcat 스레드 풀은 6장에서 다룹니다.

L4는 주소를 보고, L7은 내용을 본다

로드 밸런서는 패킷 봉투를 어디까지 열어 보느냐로 나뉩니다. 앞서 본 캡슐화에서 L4는 TCP 헤더까지, L7은 HTTP 메시지까지 엽니다. 분배 알고리즘은 8장, AWS 구현체는 13장에서 다룹니다.

서버가 먼저 말하려면 연결을 열어 둬야 한다

HTTP는 클라이언트가 묻고 서버가 답하는 구조라, 서버가 먼저 알릴 방법이 없습니다. 채팅이나 알림처럼 실시간이 필요하면 네 가지 방법 중에서 고릅니다.

방식동작방향어울리는 곳
폴링주기적으로 다시 요청클라이언트 → 서버변화가 드문 상태 확인
롱 폴링새 소식이 생길 때까지 응답 보류클라이언트 → 서버단순한 알림
SSE응답을 끝내지 않고 이벤트를 흘림서버 → 클라이언트피드, 진행률, 토큰 스트리밍
WebSocket101 응답 후 양방향 프레임양방향채팅, 게임, 협업 편집

WebSocket은 Upgrade: websocket 헤더를 단 HTTP 요청으로 시작해 같은 TCP 연결을 넘겨받습니다. 연결을 오래 붙잡으므로 프록시의 Upgrade 헤더 전달과 유휴 타임아웃 설정이 함께 필요합니다.

브라우저에 URL을 입력하면 생기는 일

지금까지 본 모든 계층이 요청 하나에 다 등장합니다. https://shop.example.com/orders를 입력했을 때 요청이 거치는 길을 먼저 지도로 보고, 다음 두 슬라이드에서 단계별로 따라갑니다.

연결이 열리기까지: 이름, 주소, 핸드셰이크

  1. URL 해석과 캐시

    스킴, 호스트, 경로를 나누고 캐시에 쓸 만한 응답이 있는지 봅니다.

  2. DNS 조회

    브라우저, OS 캐시를 거쳐 리졸버가 반복 질의로 IP를 찾습니다.

  3. 패킷 경로

    게이트웨이로 나가 공유기에서 NAT되고, 라우터를 거쳐 갑니다.

  4. TCP 3-way

    임시 포트에서 443으로 연결을 맺습니다. 1 RTT.

  5. TLS 1.3

    키를 합의하고 인증서 체인을 검증합니다. 1 RTT.

첫 요청을 보내기도 전에 DNS, TCP, TLS 왕복이 쌓입니다. 서울에서 미국 동부까지 RTT가 약 180ms라면 왕복 비용만 수백 ms입니다.

그래서 두 번째 요청부터는 빠릅니다. DNS 결과는 캐시되고, keep-alive로 연결과 TLS 세션을 재사용합니다. 서버 간 호출에서 커넥션 풀을 쓰는 이유도 같습니다.

요청이 서버 안을 지나 화면이 되기까지

  1. 로드 밸런서

    TLS를 종료하고 경로를 보고 건강한 대상 하나를 고릅니다.

  2. 웹 서버

    정적 파일이면 바로 답하고, 아니면 WAS로 프록시합니다.

  3. WAS

    스레드가 세션 쿠키로 사용자를 찾고 로직을 돌려 DB를 조회합니다.

  4. 응답 귀환

    응답이 역순으로 돌아오고 브라우저가 HTML을 파싱합니다.

  5. 추가 리소스

    CSS, JS, 이미지를 같은 연결의 스트림으로 받아 그립니다.

이 경로는 이후 장의 지도이기도 합니다. DB 안쪽은 4장, WAS 내부는 5장과 6장, 인증은 7장, 서버를 늘리는 법은 8장입니다.

이 구성을 AWS의 ALB, EC2, RDS로 옮긴 모습은 13~15장과 18장에서 봅니다. 3부에서는 이 경로가 실제로 어디서 끊기는지를 봅니다.

3부

운영 서버에서 연결이 무너질 때

TIME_WAIT가 쌓이고, 포트가 바닥나고, 로드 밸런서가 502와 504를 돌려주는 순간. 원인은 대개 2부에서 본 상태 전이와 타임아웃의 어긋남입니다.

원리 실무 관측 명령어, 커널 파라미터, 프록시 설정, 장애 사례를 다룹니다.

TIME_WAIT는 상대별로 묶어 봐야 보인다

$ ss -tan state time-wait | wc -l
28412
$ ss -tan state time-wait \
    | awk '{print $4}' | sort \
    | uniq -c | sort -rn | head -3
  27950 10.0.2.31:8080
    310 10.0.3.12:5432
    152 203.0.113.50:443
$ ss -tan state close-wait | wc -l
   214

상대 주소별로 세면 범인이 드러납니다. 이 서버가 내부 API 10.0.2.31:8080을 부를 때마다 연결을 열고 먼저 닫고 있습니다.

TIME_WAIT 소켓 하나는 메모리를 거의 쓰지 않습니다. 진짜 위험은 같은 목적지로 나갈 포트가 묶이는 것입니다. 반면 CLOSE_WAIT가 늘면 우리 코드가 소켓을 닫지 않는 누수입니다.

임시 포트는 목적지 하나당 약 2만 8천 개다

나가는 연결은 (내 IP, 내 포트, 상대 IP, 상대 포트)가 유일해야 합니다. 상대가 하나로 고정되면 바꿀 수 있는 것은 내 포트뿐이고, 닫힌 포트는 TIME_WAIT 60초 동안 다시 쓸 수 없습니다.

항목값계산
기본 포트 범위32768 ~ 6099928,232개
포트 묶임 시간TIME_WAIT60초
지속 가능한 새 연결같은 목적지 기준초당 약 470개
넘으면connect() 실패Cannot assign requested address

목적지가 소수로 몰리는 곳에서 잘 터집니다. Nginx에서 WAS로, 앱에서 Redis나 내부 API로, 그리고 NAT 장비를 통과하는 서버 간 호출입니다.

포트 고갈은 연결 재사용으로 푼다

  1. 연결 재사용

    HTTP 클라이언트에 커넥션 풀과 keep-alive를 켭니다. 근본 해결입니다.

  2. 프록시 업스트림 keepalive

    Nginx가 WAS 연결을 재사용하게 합니다(뒤 슬라이드).

  3. 포트 범위 확장

    ip_local_port_range를 넓힙니다. 리스닝 포트와는 겹치지 않게 합니다.

  4. tcp_tw_reuse

    1이면 나가는 연결에 TIME_WAIT 포트를 안전할 때 재사용합니다.

아래쪽 조치일수록 증상만 미룹니다. tcp_tw_reuse의 커널 기본값은 2로, 루프백 연결에서만 재사용합니다. 커널 문서도 함부로 바꾸지 말라고 적어 둡니다.

오래된 글의 tcp_tw_recycle은 따라 하지 마세요

NAT 뒤에서 들어오는 연결을 거부하는 부작용 때문에 리눅스 4.12에서 아예 삭제된 옵션입니다.

유휴 타임아웃은 뒤로 갈수록 길게 둔다

재사용하는 연결의 양 끝은 각자 유휴 타임아웃을 갖고, 먼저 다 된 쪽이 연결을 닫습니다. 닫는 쪽이 요청을 보내는 쪽이어야 경쟁이 생기지 않습니다.

그래서 규칙은 하나입니다. 앞단 타임아웃 < 뒷단 타임아웃. ALB 유휴 타임아웃 기본값이 60초이므로 뒤의 Nginx나 WAS의 keep-alive는 그보다 길게 둡니다. Nginx 클라이언트 쪽 기본값은 75초입니다.

Nginx는 기본 설정으로 업스트림 연결을 버린다

upstream app {
    server 10.0.2.31:8080;
    keepalive 32;
    keepalive_timeout 60s;
}
server {
    keepalive_timeout 75s;
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 60s;
    }
}

Nginx는 기본적으로 업스트림에 HTTP/1.0으로 말하고 요청마다 연결을 닫습니다. 먼저 닫는 쪽이 Nginx이므로 TIME_WAIT가 Nginx 서버에 쌓입니다.

강조한 세 줄이 함께 있어야 재사용됩니다. keepalive 32는 워커마다 보관할 유휴 연결 수이지 연결 상한이 아닙니다. WAS의 keep-alive는 업스트림 keepalive_timeout보다 길게 둡니다.

502는 이상한 대답, 504는 대답 없음이다

세 코드 모두 앱이 아니라 프록시가 만든 응답입니다. 그래서 앱 로그에는 흔적이 없을 수 있고, 프록시나 로드 밸런서의 로그부터 봐야 합니다.

코드프록시가 본 상황흔한 원인Nginx 에러 로그 단서
502 Bad Gateway연결 거부, 끊김, 깨진 응답앱 다운·재시작, keep-alive 경쟁Connection refused, upstream prematurely closed
503 Service Unavailable보낼 대상이 없음헬스 체크 실패로 대상 0개no live upstreams
504 Gateway Timeout시간 안에 응답이 안 옴느린 쿼리, 스레드 풀 고갈upstream timed out

502는 빨리 실패하고, 504는 프록시 타임아웃(Nginx proxy_read_timeout 기본 60초, ALB는 유휴 타임아웃)만큼 기다린 뒤 실패합니다. 응답 시간 분포만 봐도 둘을 가를 수 있습니다.

한가할 때만 튀는 502는 keep-alive 경쟁이다

로드 밸런서백엔드
요청 A 응답 후 연결 보관
5초 유휴, 백엔드 keep-alive 만료
FIN 백엔드가 연결 정리
요청 B FIN 도착 직전 같은 연결로
502 반환 RST 이미 닫은 연결

백엔드의 keep-alive가 로드 밸런서의 유휴 타임아웃보다 짧으면, 백엔드가 닫는 순간과 로드 밸런서가 그 연결을 재사용하는 순간이 엇갈립니다. 트래픽이 뜸해 유휴 연결이 많을 때 드물게 튀는 502의 전형입니다.

Node.js HTTP 서버의 keep-alive 기본값은 5초라 ALB 60초 뒤에서 자주 겪습니다. AWS 문서도 백엔드 타임아웃을 더 길게 두라고 권합니다.

정리

  • 계층마다 헤더 한 겹, 일 하나입니다. IP는 컴퓨터까지, 포트는 프로세스까지, MAC은 바로 다음 장비까지만 책임집니다.
  • CIDR, 게이트웨이, NAT는 VPC의 언어입니다. 사설 대역을 쪼개고, 밖으로는 게이트웨이와 NAT로 나갑니다.
  • TCP의 신뢰는 상태로 만듭니다. 핸드셰이크로 번호를 맞추고, ACK와 윈도우로 유실과 혼잡을 견디며, TIME_WAIT로 마무리합니다.
  • HTTP는 무상태이고, 상태는 쿠키와 세션이 얹습니다. TLS는 공개키로 대칭키를 합의하고, 인증서로 상대를 확인합니다.
  • 장애는 연결 재사용과 타임아웃 순서에서 납니다. 연결을 재사용하고, 앞단 타임아웃을 뒷단보다 짧게 둡니다.

스스로 점검 (1)

  1. 10.0.1.20/24와 10.0.2.20/24는 라우터 없이 통신할 수 있나요?

    아닙니다. 마스크를 적용한 네트워크 주소가 10.0.1.0과 10.0.2.0으로 다르므로, 각자 게이트웨이를 거쳐야 합니다.

  2. Private Subnet의 서버가 NAT를 통해 외부 API는 부를 수 있는데, 외부에서는 왜 그 서버에 접속할 수 없나요?

    NAT는 안에서 시작한 연결만 변환 표에 기록합니다. 밖에서 먼저 온 패킷은 표에 짝이 없어 어디로 보낼지 알 수 없습니다.

  3. 핸드셰이크를 두 번으로 줄이면 어떤 일이 생길 수 있나요?

    서버는 자기 ISN이 클라이언트에 도착했는지 확인할 수 없습니다. 네트워크에 떠돌던 옛 SYN 하나로도 서버가 유령 연결을 열게 됩니다.

  4. HTTP/2로 바꿨는데도 패킷 손실이 잦은 모바일 망에서 느린 이유는 무엇인가요?

    스트림을 다중화해도 모두 하나의 TCP 바이트 흐름에 실리므로, 패킷 하나가 유실되면 모든 스트림이 재전송을 기다립니다. HTTP/3는 스트림별로 재전송해 이를 피합니다.

  5. 세션 ID 쿠키에서 HttpOnly를 빼면 어떤 공격이 쉬워지나요?

    페이지에 주입된 스크립트가 document.cookie로 세션 ID를 읽어 갈 수 있습니다. XSS 한 번이 곧 세션 탈취가 됩니다.

스스로 점검 (2)

  1. TLS 핸드셰이크에서 공개키로 데이터를 직접 암호화하지 않는 이유는 무엇인가요?

    공개키 연산은 대칭키보다 훨씬 느리기 때문입니다. 공개키 기법은 세션 키 합의와 인증에만 쓰고, 데이터는 빠른 대칭키로 암호화합니다.

  2. API 서버에 TIME_WAIT가 3만 개 쌓였고 대부분 상대가 같은 내부 서비스입니다. 무엇부터 고치나요?

    그 서비스를 부르는 HTTP 클라이언트가 요청마다 연결을 새로 열고 닫는지 확인하고, 커넥션 풀과 keep-alive를 켭니다. 커널 파라미터는 그다음입니다.

  3. CLOSE_WAIT가 계속 늘어나는 것은 누구의 문제인가요?

    상대는 FIN을 보냈는데 우리 애플리케이션이 소켓을 닫지 않은 것입니다. 응답 본문을 다 읽지 않았거나 커넥션 반환을 빠뜨린 코드를 찾습니다.

  4. ALB 뒤에서 504가 정확히 60초 걸려 난다면 무엇을 의심하나요?

    ALB 유휴 타임아웃 기본값 60초 안에 백엔드가 응답하지 못한 것입니다. 느린 쿼리나 고갈된 스레드 풀처럼 백엔드가 느려진 원인을 먼저 찾습니다.

  5. 백엔드 keep-alive를 ALB 유휴 타임아웃보다 길게 두라는 이유는 무엇인가요?

    연결은 항상 요청을 보내는 ALB 쪽이 먼저 닫아야 합니다. 백엔드가 먼저 닫으면 그 순간 재사용된 요청이 RST를 받아 502가 됩니다.
