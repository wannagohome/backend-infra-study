1부

설계는 어딘가에서 돌아가야 한다

8장에서 그린 무상태 서버와 캐시, 큐는 결국 리눅스 위의 프로세스입니다. 서버 한 대를 다루는 법에서 시작해 컨테이너라는 포장 단위까지 올라갑니다.

코드에서 운영까지는 다섯 층을 지난다

  1. Linux 서버프로세스, 권한, 로그
  2. 컨테이너실행 환경째 포장
  3. Kubernetes여러 대를 선언적으로 운영
  4. CI/CD빌드부터 배포까지 자동화
  5. 배포 전략멈추지 않고 교체

각 층은 아래층의 불편을 해결하려고 생겼습니다. 서버마다 설치 환경이 달라서 컨테이너가, 컨테이너가 수백 개로 늘어서 오케스트레이션이, 사람이 배포하다 실수해서 CI/CD가 등장했습니다.

마지막 층인 무중단 배포는 앞의 모든 층이 협력해야 가능합니다. 이 장의 실무 파트가 그 협력을 다룹니다.

디렉터리마다 맡은 역할이 정해져 있다

리눅스는 FHS(Filesystem Hierarchy Standard)라는 관례로 파일 위치를 정합니다. 처음 들어간 서버에서도 어디를 볼지 알 수 있는 이유입니다.

경로담는 것운영에서 보는 이유
/etc시스템과 서비스 설정 파일nginx, systemd 설정 확인
/var/log로그 같은 자주 바뀌는 데이터가득 차면 쓰기 실패 장애
/proc커널이 만든 가상 파일프로세스와 커널 상태 조회
/usr, /opt설치된 프로그램직접 배포한 앱은 보통 /opt
/tmp임시 파일재부팅 때 지워질 수 있음

/proc은 디스크에 없는 파일입니다. 1장의 "모든 것은 파일" 원칙이 커널 상태 조회에까지 적용된 예입니다.

권한은 소유자, 그룹, 나머지의 rwx다

$ ls -lh /opt/api
-rw-r----- 1 app app  51M Nov 14 10:02 app.jar
-rw------- 1 app app  812 Nov 14 10:02 db.env
drwxr-x--- 2 app app 4.0K Nov 14 10:05 logs

$ chmod 600 db.env    # rw- --- ---
$ chown -R app:app /opt/api

맨 앞 글자는 종류(d는 디렉터리)이고, 뒤 아홉 글자가 소유자, 그룹, 나머지 순서의 읽기(r=4), 쓰기(w=2), 실행(x=1) 권한입니다. 숫자는 이를 더한 값이라 640은 rw-, r--, ---입니다.

디렉터리의 x는 "안으로 들어갈 수 있음"을 뜻합니다. 앱은 전용 계정으로 실행하고 비밀 파일은 600으로 두는 것이 기본입니다.

시그널은 프로세스에 보내는 짧은 통지다

프로세스 자체는 1장에서 다뤘습니다. 여기서는 운영자가 프로세스에 말을 거는 방법인 시그널을 봅니다.

시그널번호보내는 상황프로세스가 잡을 수 있나
SIGTERM15kill 기본값, 정상 종료 요청잡아서 정리 후 종료
SIGKILL9kill -9, 유예 시간 초과불가, 커널이 즉시 제거
SIGINT2터미널에서 Ctrl+C가능
SIGHUP1설정 다시 읽기 관례(nginx)가능

SIGTERM은 "정리하고 나가 달라"는 부탁이고 SIGKILL은 강제 철거입니다. 이 차이가 3부의 Graceful Shutdown 전체를 떠받칩니다. 시그널로 죽은 프로세스의 종료 코드는 128 + 번호라서 SIGKILL이면 137입니다.

systemd가 서버의 프로세스를 지킨다

[Unit]
Description=Order API
After=network.target

[Service]
User=app
ExecStart=/usr/bin/java -jar /opt/api/app.jar
Restart=on-failure
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target

$ sudo systemctl enable --now api
$ journalctl -u api -f

nohup java -jar &로 띄운 프로세스는 죽어도 아무도 다시 살리지 않습니다. systemd는 부팅 때 PID 1로 시작해 서비스를 띄우고, 죽으면 재시작하고, 로그를 journald로 모읍니다.

systemctl stop은 SIGTERM을 보내고 TimeoutStopSec이 지나면 SIGKILL을 보냅니다. 뒤에 나올 Docker와 Kubernetes도 같은 2단계 종료를 씁니다.

VM은 하드웨어를, 컨테이너는 OS를 나눈다

"내 PC에선 되는데 서버에선 안 된다"는 문제는 실행 환경 차이에서 옵니다. 두 기술 모두 환경을 통째로 묶어 옮기지만, 어디를 나누는지가 다릅니다.

VM은 하이퍼바이저가 가상 하드웨어를 만들고 그 위에 게스트 OS를 통째로 올립니다. 컨테이너는 호스트 커널을 공유하고 프로세스만 격리합니다.

커널을 공유하면 가볍지만 경계는 얇아진다

항목VM컨테이너
격리 단위가상 하드웨어 + 게스트 OS프로세스 (namespace, cgroup)
시작 시간OS 부팅, 수십 초 이상프로세스 시작, 보통 1초 안팎
이미지 크기GB 단위수십~수백 MB
다른 OS 실행가능 (리눅스 위 윈도우)호스트 커널과 같은 계열만
보안 경계하이퍼바이저, 두꺼움커널 취약점이 곧 탈출 경로

그래서 실무에서는 둘을 겹쳐 씁니다. 클라우드의 VM(EC2) 위에 컨테이너 여러 개를 올리는 구성이 가장 흔합니다. macOS에서 Docker를 쓸 때도 내부적으로 작은 리눅스 VM이 돌고 있습니다.

이미지는 설계도, 컨테이너는 실행 중인 사본

  1. Dockerfile환경을 코드로 기술
  2. 이미지docker build
  3. 레지스트리docker push
  4. 컨테이너docker run

이미지는 앱과 런타임, 라이브러리를 묶은 읽기 전용 파일 묶음이고, 컨테이너는 그 이미지로 띄운 프로세스입니다. 클래스와 인스턴스의 관계와 비슷해서 이미지 하나로 컨테이너를 여러 개 띄웁니다.

이미지는 Docker Hub, GHCR, ECR 같은 레지스트리에 올려 공유합니다. 태그는 latest 대신 커밋 SHA처럼 바뀌지 않는 값을 써야 어떤 코드가 돌고 있는지 추적됩니다.

Compose는 여러 컨테이너를 한 파일로 띄운다

services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_URL: jdbc:mysql://db:3306/app
    depends_on:
      db: { condition: service_healthy }
  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: app
      MYSQL_ROOT_PASSWORD: local-only
    healthcheck:
      test: ["CMD", "mysqladmin", "ping"]

앱 하나에도 DB, Redis가 따라붙습니다. Docker Compose는 이 묶음을 YAML 하나로 선언하고 docker compose up 한 번으로 띄웁니다.

Compose는 서비스끼리 같은 네트워크에 두고 서비스 이름을 DNS로 풀어 줍니다. 그래서 주소가 db:3306입니다. 다만 한 호스트용이라 운영의 여러 서버 관리는 Kubernetes가 맡습니다.

2부

컨테이너는 커널 기능의 조합이다

컨테이너라는 커널 객체는 따로 없습니다. namespace, cgroup, 계층형 파일 시스템을 조합한 결과이고, Kubernetes는 그 위에서 "원하는 상태"를 유지하는 제어 루프입니다.

기초 원리 여기부터는 커널 격리 기능과 Kubernetes 내부 동작을 다룹니다.

namespace는 보이는 범위를, cgroup은 쓰는 양을

namespace는 프로세스가 볼 수 있는 자원의 범위를 나눕니다. PID, 네트워크, 마운트, 호스트 이름(UTS), IPC, 사용자 namespace가 대표적입니다. 그래서 컨테이너 안의 java는 자신을 PID 1로 봅니다.

cgroup은 프로세스 묶음이 쓸 CPU와 메모리의 상한을 정합니다. 격리는 namespace, 제한은 cgroup입니다.

메모리 상한을 넘으면 커널이 프로세스를 죽인다

cgroup의 메모리 상한에 닿으면 커널의 OOM Killer가 그 cgroup 안의 프로세스를 SIGKILL로 제거합니다. 종료 코드 137, Kubernetes에서는 OOMKilled로 보입니다. 앱 로그에는 아무것도 남지 않는다는 점이 함정입니다.

CPU 상한은 다르게 동작합니다. 넘는다고 죽지 않고 스로틀링되어 다음 주기까지 멈춥니다. 응답 지연이 들쭉날쭉한데 CPU 사용률이 낮아 보인다면 이것을 의심합니다.

JVM 힙 + 그 밖의 메모리 < 상한

컨테이너 메모리는 힙만이 아닙니다. 메타스페이스, 스레드 스택, 다이렉트 버퍼까지 더해야 하므로 힙을 상한의 50~75% 정도로 둡니다(JVM 메모리 구조는 5장).

JVM은 컨테이너 상한을 인식합니다

최신 JVM은 cgroup 상한을 읽어 힙 기본값을 정합니다. 기본 최대 힙은 상한의 25%라 -XX:MaxRAMPercentage로 조정합니다.

이미지는 읽기 전용 레이어의 겹침이다

Dockerfile의 FROM, COPY, RUN 같은 명령 하나하나가 파일 변경분을 담은 레이어가 됩니다. overlay2 같은 유니언 파일 시스템이 이를 겹쳐 하나의 디렉터리처럼 보여 줍니다.

컨테이너를 띄우면 맨 위에 얇은 쓰기 레이어만 추가됩니다. 아래 파일을 고치면 그때 위로 복사해 수정하는 Copy-on-Write라서, 같은 이미지의 컨테이너 100개가 아래 레이어를 공유합니다.

레이어 캐시는 명령 순서가 결정한다

# 나쁜 순서: 코드 한 줄에도 의존성 재설치
COPY . .
RUN ./gradlew bootJar

# 좋은 순서: 잘 안 바뀌는 것부터
COPY build.gradle settings.gradle ./
RUN ./gradlew dependencies
COPY src ./src
RUN ./gradlew bootJar

Docker는 명령과 입력 파일이 이전 빌드와 같으면 그 레이어를 재사용합니다. 하지만 한 레이어가 바뀌면 그 아래 모든 명령이 다시 실행됩니다.

그래서 빌드 설정만 먼저 복사해 의존성을 받고, 자주 바뀌는 소스는 나중에 복사합니다. 코드만 고친 빌드는 의존성 다운로드를 건너뛰어 수 분이 수십 초로 줄어듭니다.

멀티 스테이지로 빌드 도구를 버린다

# 1단계: 빌드 (JDK, Gradle 포함)
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY gradlew settings.gradle build.gradle ./
COPY gradle ./gradle
RUN ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew bootJar --no-daemon

# 2단계: 실행 (JRE만)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/build/libs/*.jar app.jar
USER 1000
ENTRYPOINT ["java", "-jar", "app.jar"]

빌드에는 JDK와 Gradle, 소스가 필요하지만 실행에는 JRE와 JAR만 있으면 됩니다. 멀티 스테이지 빌드는 앞 단계에서 만든 결과물만 마지막 단계로 복사합니다.

최종 이미지가 작아져 배포가 빨라지고, 컴파일러나 소스 같은 공격 표면도 사라집니다. USER로 root가 아닌 계정을 지정하는 것도 같은 이유입니다.

PID 1이 시그널을 받아야 정상 종료된다

# shell form: /bin/sh -c 가 PID 1이 되어
# SIGTERM이 java까지 가지 않을 수 있음
CMD java -jar app.jar

# exec form: java가 직접 PID 1
ENTRYPOINT ["java", "-jar", "app.jar"]

# 스크립트로 시작해야 한다면 마지막에 exec
exec java $JAVA_OPTS -jar app.jar

docker stop은 컨테이너의 PID 1에 SIGTERM을 보내고, 기본 10초 뒤 SIGKILL을 보냅니다. 셸이 PID 1이면 시그널이 자식인 java에 전달되지 않을 수 있어 매번 10초를 기다렸다가 강제 종료됩니다.

exec form으로 앱을 직접 PID 1로 두거나, 좀비 프로세스 정리까지 필요하면 tini 같은 작은 init(docker run --init)을 씁니다.

컨테이너가 수백 개면 사람이 관리할 수 없다

서버 20대에 컨테이너 300개가 돈다고 해 봅시다. 어느 서버에 여유가 있는지, 죽은 컨테이너를 어디서 다시 띄울지, 새 컨테이너의 IP를 로드 밸런서에 어떻게 알릴지 매번 사람이 판단할 수는 없습니다.

오케스트레이션은 이 일을 자동화합니다. 핵심은 명령형("3개 띄워")이 아니라 선언형("항상 3개가 떠 있어야 한다")이라는 점입니다.

  • 배치(스케줄링) 자원이 남는 노드를 골라 컨테이너를 놓습니다.
  • 자가 치유 죽거나 응답 없는 컨테이너를 교체합니다.
  • 서비스 발견 계속 바뀌는 IP 앞에 고정 주소를 둡니다.
  • 확장과 배포 개수를 늘리고 새 버전으로 점진 교체합니다.

Kubernetes는 두뇌와 손발로 나뉜다

apply 한 번이 Pod가 되기까지

  1. kubectl apply

    YAML을 API Server에 보내고, API Server는 검증 후 etcd에 저장합니다.

  2. Deployment 컨트롤러

    "3개 필요, 0개 있음"을 보고 ReplicaSet과 Pod 객체를 만듭니다.

  3. Scheduler

    노드가 정해지지 않은 Pod에 자원이 맞는 노드를 기록합니다.

  4. kubelet

    자기 노드에 배정된 Pod를 보고 런타임에 컨테이너 실행을 지시합니다.

누구도 다음 단계를 직접 호출하지 않습니다. 각 구성 요소가 API Server를 지켜보다가 자기 몫의 차이를 발견하면 움직입니다. 이것을 조정 루프라고 합니다.

노드가 죽어 Pod가 2개로 줄면 같은 루프가 차이를 보고 하나를 새로 만듭니다. 자가 치유는 별도 기능이 아니라 이 루프의 결과입니다.

Pod는 버려지고 Deployment가 개수를 지킨다

오브젝트무엇인가왜 필요한가
Pod컨테이너 묶음, 배포의 최소 단위같은 IP와 볼륨을 공유
ReplicaSet같은 Pod N개를 유지개수 보장 (직접 쓰지 않음)
DeploymentReplicaSet의 버전 관리롤링 업데이트와 롤백
ServicePod 묶음의 고정 주소Pod IP는 재시작마다 바뀜

Pod는 언제든 죽고 새 IP로 다시 태어나는 일회용입니다. 그래서 Pod를 직접 만들지 않고 Deployment에 원하는 상태를 맡깁니다. Service는 라벨 셀렉터로 대상 Pod를 고르므로 Pod가 바뀌어도 주소는 그대로입니다. 8장의 무상태 서버 원칙이 여기서 전제가 됩니다.

Deployment YAML은 원하는 상태의 기록이다

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: ghcr.io/acme/api:3f9c2e1
        resources: { requests: { cpu: 500m } }

selector와 template의 라벨이 같아야 Deployment가 자기 Pod를 알아봅니다. Service도 같은 app: api 라벨로 이 Pod들을 찾습니다.

requests는 Scheduler가 노드를 고르는 기준이자 뒤에 나올 HPA 사용률의 분모입니다. 비워 두면 배치와 확장이 모두 부정확해집니다.

요청은 Ingress, Service를 거쳐 Pod에 닿는다

  1. 클라이언트api.example.com
  2. Ingress호스트, 경로로 L7 라우팅
  3. Service고정 가상 IP, 부하 분산
  4. PodReady인 Pod만 대상

Service의 기본형(ClusterIP)은 클러스터 안에서만 닿는 가상 IP입니다. 각 노드의 kube-proxy가 이 IP로 오는 패킷을 실제 Pod로 보내는 규칙을 깔아 둡니다. 밖에서 들어오는 HTTP는 Ingress가 받아 2장의 L7 라우팅처럼 경로별로 Service에 나눠 줍니다.

Kubernetes 프로젝트는 Ingress API를 동결하고 후속인 Gateway API를 권장합니다. Ingress는 계속 지원되므로 개념은 그대로 유효합니다.

같은 이미지를 개발과 운영에 그대로 쓰려면 환경별 값은 밖으로 빼야 합니다. ConfigMap은 일반 설정을, Secret은 비밀번호와 키를 담아 환경 변수나 파일로 Pod에 주입합니다.

Secret의 base64는 암호화가 아니라 인코딩입니다. etcd 저장 암호화와 RBAC 접근 제한을 켜거나 외부 비밀 저장소(11장)를 연동해야 합니다.

살아 있음과 받을 준비는 다른 질문이다

프로브묻는 것실패하면
liveness프로세스가 고장 났나 (데드락 등)컨테이너 재시작
readiness지금 트래픽을 받아도 되나Service 대상에서 제외만
startup느린 시작이 끝났나끝날 때까지 위 둘을 보류

kubelet은 기본 10초마다 프로브를 보내고, 연속 3번 실패하면 실패로 판단합니다. readiness는 기동 직후 캐시를 데우는 동안이나 종료 중에 "잠시 빼 달라"는 신호이고, liveness는 "나를 다시 시작해 달라"는 신호입니다.

liveness에 DB 연결 검사를 넣지 마세요

8장에서 본 헬스 체크 원칙 그대로입니다. DB가 잠깐 느려지면 모든 Pod가 동시에 재시작되므로, liveness는 프로세스 자체만 봅니다.

HPA는 사용률 비율만큼 Pod 수를 바꾼다

HPA는 metrics-server에서 Pod의 CPU 사용량을 주기적으로 읽어 Deployment의 replicas를 조정합니다. 계산은 단순한 비례식입니다.

Pod 4개의 평균 CPU가 목표 50%에 대해 80%라면 ceil(4 × 80/50) = 7개로 늘립니다. 사용률은 requests 대비이므로 requests가 없으면 계산할 수 없습니다.

desired = ceil(current × cur / target)

출렁임을 막는 두 장치

비율이 목표와 10% 이내면 움직이지 않습니다(tolerance 0.1). 줄일 때는 기본 5분 동안의 추천값 중 최댓값을 써서 급감을 막습니다.

원리 실무 진단 명령어, 파이프라인, 배포 전략, 종료 순서와 장애 사례를 다룹니다.

load average는 1, 5, 15분 평균 대기열 길이입니다. 코어 4개에 7.92이면 늘 두 배의 작업이 줄을 서 있고, 오르는 추세입니다. 메모리는 free가 아니라 available을 보며, si/so가 0이 아니면 스왑이 일어나는 중입니다. wa가 높으면 CPU가 아니라 디스크를 기다리는 것입니다.

디스크와 네트워크: 공간, 대기, 연결

$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p1   50G   50G     0 100% /
$ df -i /var              # inode 고갈도 "디스크 꽉 참"
$ du -xh /var --max-depth=1 | sort -h | tail -3
$ iostat -x 1             # %util, await
$ ss -s                   # 상태별 소켓 개수
$ ss -tanp '( dport = :3306 )'   # DB로 나간 연결
$ lsof -p 4211 | wc -l    # 프로세스가 연 fd 수

디스크는 용량과 inode(1장) 두 가지가 모두 바닥날 수 있습니다. 작은 파일이 수백만 개 쌓이면 용량이 남아도 파일을 못 만듭니다. 네트워크는 2장의 소켓 상태를, fd 수는 1장의 fd 고갈을 여기서 실제로 확인합니다.

로그를 지웠는데 디스크가 그대로인 이유

$ grep -c " 500 " access.log
$ journalctl -u api --since "10 min ago"
$ kubectl logs api-7d9f --previous

$ rm /var/log/api/app.log

파일을 rm해도 프로세스가 fd로 열고 있으면 inode는 남아 계속 공간을 차지합니다. 20GB 로그를 지웠는데 df가 그대로라면 이 경우입니다.

lsof +L1로 찾아 프로세스를 재시작하거나 파일을 비웁니다(: > app.log). 근본 대책은 logrotate나 stdout 로그입니다. --previous는 재시작 직전 컨테이너의 로그입니다.

CI는 자주 합치고, CD는 언제든 내보낸다

  1. 커밋, PR작은 단위로 자주
  2. 빌드, 테스트CI: 깨지면 즉시 알림
  3. 이미지 빌드태그는 커밋 SHA
  4. 스테이징같은 이미지로 검증
  5. 운영 배포수동 승인 또는 자동

CI는 모두의 코드를 하루에도 여러 번 main에 합치고 그때마다 빌드와 테스트를 돌려 충돌을 일찍 잡는 습관입니다. 지속적 전달은 언제든 운영에 내보낼 수 있는 상태를 유지하되 마지막 버튼은 사람이 누르고, 지속적 배포는 그 버튼까지 자동입니다.

핵심 원칙은 이미지를 한 번만 빌드하고 같은 이미지를 환경별로 승격하는 것입니다. 환경마다 다시 빌드하면 테스트한 것과 다른 것이 나갑니다.

배포는 이 이미지 태그를 Deployment에 반영하는 단계입니다. 클러스터가 Git 저장소의 매니페스트를 끌어와 맞추는 GitOps(Argo CD 등) 방식도 많이 씁니다.

Rolling: 조금씩 바꿔 끼운다

  1. 새 Pod 추가

    maxSurge만큼 v2 Pod를 먼저 띄웁니다.

  2. readiness 통과 대기

    준비된 v2만 Service 대상에 들어갑니다.

  3. 옛 Pod 제거

    maxUnavailable 범위 안에서 v1을 종료합니다.

  4. 반복

    모든 Pod가 v2가 될 때까지 되풀이합니다.

무중단 배포가 어려운 이유는 교체하는 동안 두 버전이 동시에 요청을 받기 때문입니다. Rolling은 그 공존을 받아들이고 조금씩 바꿉니다. Deployment의 기본 전략이며 maxSurge와 maxUnavailable의 기본값은 각각 25%입니다.

추가 자원이 적게 들지만, 롤백도 다시 굴려야 해서 느립니다. 문제가 생겨도 이미 일부 사용자가 영향을 받습니다.

Blue-Green: 통째로 준비하고 한 번에 전환

운영 중인 Blue 옆에 같은 규모의 Green(v2)을 띄워 검증한 뒤, 로드 밸런서나 Service의 대상을 한 번에 Green으로 돌립니다.

Blue를 남겨 두면 롤백은 대상을 되돌리는 것 한 번입니다. 대신 전환 동안 자원이 두 배 들고, 두 환경이 같은 DB를 쓰므로 스키마 호환은 여전히 필요합니다.

Canary: 일부에게 먼저 내보내고 지표로 판단

  1. 5%v2로 일부 트래픽
  2. 지표 비교에러율, p99 지연
  3. 25%이상 없으면 확대
  4. 100%v1 정리

탄광의 카나리아처럼 소수 사용자에게 먼저 v2를 보내고, v1과 지표를 비교해 단계적으로 늘립니다. 나쁘면 그 5%만 되돌리면 되므로 영향 범위가 가장 작습니다.

대신 비율 단위 라우팅(Ingress 가중치, 서비스 메시, Argo Rollouts 등)과 버전별로 나눠 보는 관측성이 갖춰져야 합니다. 지표를 보지 않는 Canary는 느린 Rolling일 뿐입니다.

세 전략은 비용, 롤백 속도, 위험의 교환이다

기준RollingBlue-GreenCanary

어느 전략이든 공통 전제가 두 가지 있습니다. 내려가는 인스턴스가 진행 중 요청을 끝내야 하고(Graceful Shutdown), 두 버전이 같은 DB를 견뎌야 합니다(스키마 하위 호환). AWS에서는 ECS, CodeDeploy가 이 전략을 구현합니다(11장).

Pod 종료는 두 갈래로 동시에 진행된다

Kubernetes앱 컨테이너
Pod Terminating, 엔드포인트 제거 전파 시작
preStop sleep 10그동안 라우팅 규칙이 갱신됨
SIGTERM 종료 시작
새 요청 거절, 진행 중 요청 마무리
exit 0 정상 종료
30초 초과 SIGKILL진행 중 요청 유실

Pod가 삭제되면 엔드포인트에서 빠지는 일과 컨테이너에 종료를 알리는 일이 동시에 시작됩니다. 라우팅 규칙이 모든 노드에 퍼지기 전에 앱이 먼저 죽으면 그 사이 요청이 502로 실패합니다.

그래서 preStop에서 몇 초 기다려 트래픽이 끊긴 뒤에 종료를 시작합니다. 전체 유예 시간은 기본 30초이고, preStop 시간도 여기에 포함됩니다.

종료 예산을 앱과 Pod 설정에 나눠 쓴다

# application.yml (Spring Boot)
server:
  shutdown: graceful   # Boot 3.4부터 기본값
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s

# Pod spec
terminationGracePeriodSeconds: 40
containers:
- name: api
  lifecycle:
    preStop:
      exec: { command: ["sleep", "10"] }

SIGTERM을 받은 Spring Boot는 새 요청을 거절하고 진행 중 요청을 최대 20초 기다립니다. preStop 10초와 합쳐 30초이므로 유예 시간을 40초로 넉넉히 둡니다.

규칙은 preStop + 앱 종료 시간 < 유예 시간입니다. 긴 배치 작업이나 메시지 컨슈머는 처리 중인 일을 마치거나 다시 큐에 돌려놓는 코드가 따로 필요합니다(8장 멱등 컨슈머).

스키마는 두 버전이 함께 견뎌야 한다

배포 중에는 v1과 v2가 같은 DB를 씁니다. v2 배포와 함께 컬럼 이름을 바꾸면 아직 남은 v1이 즉시 에러를 냅니다. 롤백해도 v1은 바뀐 스키마를 모릅니다.

해법은 변경을 여러 배포로 쪼개는 Expand-Contract입니다. 먼저 넓히고, 모두 옮긴 뒤, 나중에 좁힙니다.

큰 테이블의 ALTER는 락과 복제 지연을 부를 수 있어 MySQL 온라인 DDL이나 gh-ost 같은 도구를 씁니다.

  1. Expand

    새 컬럼 full_name을 NULL 허용으로 추가합니다. v1은 영향이 없습니다.

  2. 이중 쓰기

    v2는 두 컬럼에 모두 쓰고, 읽을 때는 새 컬럼을 우선합니다.

  3. 백필

    기존 행의 값을 배치로 나눠 새 컬럼에 복사합니다.

  4. 전환

    v1이 모두 사라진 뒤 새 컬럼만 읽고 씁니다.

  5. Contract

    다음 릴리스에서 옛 컬럼 name을 삭제합니다.

콘솔에서 손으로 만든 인프라는 누가 왜 바꿨는지 남지 않고 똑같이 다시 만들기도 어렵습니다. IaC는 원하는 인프라를 코드로 선언하고 Git으로 리뷰합니다.

Terraform은 state 파일에 기록된 현재 상태와 코드를 비교해 차이(plan)를 보여 준 뒤 적용합니다. Kubernetes의 선언형 모델과 같은 발상입니다. 운영 관행은 11장에서 다룹니다.

브랜치 전략은 배포 주기에 맞춘다

전략구조맞는 팀
Git Flowmain, develop, feature, release, hotfix정해진 주기로 릴리스
GitHub Flowmain + 짧은 feature 브랜치, PR수시 배포하는 웹 서비스
트렁크 기반main에 하루 여러 번 병합CI 성숙, 기능 플래그 사용

브랜치가 오래 살수록 병합 충돌과 통합 위험이 커집니다. CI의 취지인 "자주 합치기"와 맞는 쪽은 짧은 브랜치입니다. 미완성 기능은 브랜치에 숨기는 대신 기능 플래그로 꺼 둔 채 main에 합칠 수 있습니다.

12-Factor는 이 장의 원칙을 요약한다

12-Factor App은 클라우드에서 잘 도는 앱의 조건 12가지입니다. 그중 이 장과 직접 맞닿은 것만 추립니다.

요소내용이 장의 연결
설정설정은 환경 변수로 분리ConfigMap, Secret
프로세스무상태, 상태는 외부 저장소일회용 Pod (8장)
폐기 가능성빠른 시작, 우아한 종료SIGTERM, Graceful Shutdown
개발/운영 일치환경 차이를 최소화같은 이미지 승격
로그파일 대신 stdout 이벤트 스트림수집은 플랫폼이 담당

정리

  • SIGTERM은 부탁, SIGKILL은 철거입니다. systemd, Docker, Kubernetes 모두 SIGTERM 후 유예 시간이 지나면 SIGKILL을 보냅니다.
  • 컨테이너는 격리된 프로세스입니다. namespace가 보이는 범위를, cgroup이 쓰는 양을 나누고 커널은 공유합니다.
  • Kubernetes는 조정 루프의 집합입니다. 원하는 상태를 etcd에 적으면 컨트롤러가 차이를 메우고, 그 결과가 자가 치유입니다.
  • 배포 전략은 비용, 롤백 속도, 위험의 교환입니다. Rolling은 싸고, Blue-Green은 롤백이 빠르고, Canary는 영향이 작습니다.
  • 무중단은 종료 순서와 스키마 호환이 완성합니다. preStop으로 트래픽을 먼저 끊고, Expand-Contract로 두 버전이 공존하게 합니다.

스스로 점검 (1)

  1. docker stop을 할 때마다 정확히 10초씩 걸린다면 무엇을 의심하나요?

    PID 1이 SIGTERM을 처리하지 않아 SIGKILL을 기다리는 것입니다. shell form CMD로 셸이 PID 1이 된 경우가 흔하며 exec form으로 바꿉니다.

  2. VM 위에서도 컨테이너를 돌리는데, 왜 컨테이너가 더 가볍다고 하나요?

    컨테이너 하나마다 게스트 OS와 커널을 부팅하지 않기 때문입니다. 비교 대상은 "VM 하나 대 컨테이너 하나"이고, 컨테이너는 프로세스 하나를 띄우는 비용에 가깝습니다.

  3. 소스 한 줄만 고쳤는데 이미지 빌드가 매번 의존성을 다시 받습니다. 왜인가요?

    소스 복사가 의존성 설치보다 앞에 있어 그 레이어가 바뀌면 아래 명령의 캐시가 모두 무효가 됩니다. 빌드 설정을 먼저 복사해 의존성을 받고 소스는 나중에 복사합니다.

  4. 노드 하나가 죽었는데 아무도 명령하지 않았는데 Pod가 다른 노드에 다시 생겼습니다. 어떤 구성 요소들이 움직였나요?

    ReplicaSet 컨트롤러가 실제 개수가 원하는 개수보다 적은 것을 보고 Pod를 만들고, Scheduler가 노드를 정하고, 그 노드의 kubelet이 컨테이너를 띄웠습니다.

  5. readiness가 실패한 Pod와 liveness가 실패한 Pod는 각각 어떻게 되나요?

    readiness 실패는 Service 대상에서만 빠지고 컨테이너는 그대로 둡니다. liveness 실패는 kubelet이 컨테이너를 재시작합니다.

스스로 점검 (2)

  1. 배포 때마다 몇 초간 502가 납니다. 앱은 graceful 설정이 되어 있다면 무엇이 빠졌을까요?

    엔드포인트 제거가 퍼지기 전에 SIGTERM으로 종료가 시작된 것입니다. preStop에서 몇 초 기다려 트래픽이 끊긴 뒤 종료하게 합니다.

  2. 롤백이 가장 빨라야 하는 서비스와 실패 영향 범위를 최소로 해야 하는 서비스에는 각각 어떤 전략이 맞나요?

    롤백 속도는 Blue-Green으로 대상 전환 한 번이면 됩니다. 영향 범위는 Canary로 소수에게만 먼저 노출해 줄입니다.

  3. 컬럼을 삭제하는 마이그레이션을 새 버전 배포와 같이 내보내면 어떤 일이 생기나요?

    아직 남은 이전 버전이 그 컬럼을 읽다가 에러를 내고, 롤백해도 컬럼이 없어 복구되지 않습니다. 이전 버전이 모두 사라진 다음 릴리스에서 삭제합니다.

  4. 로그 파일을 지웠는데 df 사용률이 줄지 않습니다. 어떻게 확인하나요?

    lsof +L1로 삭제됐지만 열려 있는 파일을 찾습니다. 프로세스가 fd를 놓아야 공간이 반환되므로 재시작하거나 파일을 비웁니다.

  5. CPU 사용률은 낮은데 응답 지연이 주기적으로 튑니다. 컨테이너 환경이라면 무엇을 보나요?

    CPU limit에 의한 스로틀링입니다. 짧은 순간 상한을 다 써서 다음 주기까지 멈추는 것이며, cgroup의 스로틀링 통계를 확인하고 limit을 조정합니다.
