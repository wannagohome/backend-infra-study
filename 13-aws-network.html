1부

주문 API 서버를 놓을 사설망을 긋는다

12장에서 계정과 권한을 만들었습니다. 이 부에서는 그 계정 안에 서버들이 살 네트워크를 만듭니다. 주소를 얼마나 잡을지, 어디에 나눠 놓을지, 어떤 문으로 드나들게 할지, 누구를 막을지를 차례로 정합니다.

이 장 내내 쓸 예제: shop 주문 API

개념을 매번 새 예로 설명하면 머릿속에 그림이 쌓이지 않습니다. 그래서 이 장은 하나의 서비스를 끝까지 붙들고 갑니다. 쇼핑몰 shop의 주문 API를 AWS 서울 리전(ap-northeast-2)에 올리는 일입니다.

구성은 단순합니다. Spring Boot로 만든 주문 API 서버 여러 대가 8080 포트로 요청을 받고, 뒤에 MySQL DB가 있습니다. 사용자는 api.example.com으로 접속합니다.

이 서비스가 해야 하는 통신을 미리 적어 두면 이 장의 지도가 됩니다. 사용자의 요청을 인터넷에서 받아야 하고(들어오기), 결제 대행사(PG)의 외부 API를 호출해야 하며(나가기), 상품 이미지와 백업을 AWS의 저장 서비스에 올려야 합니다(AWS 서비스로 가기).

또 다른 팀이 운영하는 회원 서비스를 불러야 하고(다른 네트워크로 가기), 회사 데이터 센터에 있는 정산 시스템과도 주고받아야 합니다(사내망으로 가기). 그러면서 DB는 아무도 바깥에서 건드리지 못해야 합니다.

1부는 들어오기와 나가기, 그리고 막기를 다룹니다. 2부는 AWS 서비스·다른 네트워크·사내망과 잇는 길을, 3부는 서버 여러 대 앞에서 요청을 나누는 장치를, 4부는 이름으로 찾아오게 하는 DNS를 봅니다.

물리망은 하나인데 고객은 수백만이다

AWS 데이터 센터에는 수많은 고객의 서버가 같은 물리 스위치와 케이블을 나눠 씁니다. 이것을 그대로 하나의 평평한 네트워크로 두면 두 가지가 곤란합니다. 남의 서버로 패킷을 보낼 수 있고, 모두가 10.0.0.0/8 같은 사설 대역을 쓰고 싶어 하니 주소가 겹칩니다.

AWS의 해법은 2장의 캡슐화를 한 번 더 쓰는 것입니다. 고객 서버가 보낸 패킷을 물리망 전용 헤더로 한 번 더 감싸고, 그 헤더에 "이 패킷은 어느 고객의 어느 가상 네트워크 소속인가"를 적어 둡니다. 물리 호스트는 이 표식을 보고 같은 가상 네트워크 안으로만 배달합니다.

그래서 고객마다 자기만의 네트워크를 가진 것처럼 보이고, 다른 고객과 같은 사설 대역을 써도 충돌하지 않습니다. 이렇게 소프트웨어로 나눈 가상 네트워크 하나가 다음 슬라이드의 VPC입니다.

VPC는 리전 하나에 걸친 나만의 사설망이다

VPC는 AWS 리전 하나 안에 만드는, 다른 계정과 격리된 가상 네트워크입니다. 사용자에게는 2장에서 본 사무실 사설 네트워크 하나처럼 보입니다. 그 안에 서버, 로드 밸런서, DB를 놓고 사설 IP로 서로 통신합니다.

범위를 정확히 알아 두어야 합니다. 12장에서 리전은 서울 같은 지리적 지역이고, 그 안의 가용 영역(AZ)은 전원과 네트워크가 분리된 데이터 센터 묶음이라고 했습니다. VPC는 리전 전체에 걸치므로 서울의 모든 AZ를 품을 수 있습니다. 반면 다음에 볼 서브넷은 AZ 하나에만 놓입니다.

VPC를 만들 때 반드시 정해야 하는 것은 주소 대역 하나입니다. shop은 10.10.0.0/16을 고릅니다. 왜 이 값인지가 다음 두 슬라이드의 주제입니다.

VPC 대역은 CIDR 하나로 정한다

2장에서 본 CIDR 표기를 상기해 봅니다. 10.10.0.0/16의 /16은 앞 16비트가 네트워크 부분이라는 뜻이고, 남은 16비트로 216 = 65,536개 주소를 쓸 수 있습니다. 숫자가 하나 커질 때마다 크기는 절반이 됩니다.

VPC의 IPv4 대역은 /16(65,536개)부터 /28(16개) 사이에서 고릅니다. 2장의 RFC 1918 사설 대역(10/8, 172.16/12, 192.168/16) 안에서 고르는 것이 원칙입니다.

중요한 제약이 있습니다. 처음 정한 대역은 나중에 줄이거나 바꿀 수 없습니다. 부족하면 보조 CIDR, 즉 VPC에 덧붙이는 두 번째 대역을 추가할 수는 있지만, 주소가 여러 조각으로 흩어져 관리가 번거로워집니다.

그래서 처음 설계가 중요합니다. shop이 VPC 하나에 쓸 수 있는 가장 큰 크기인 /16을 고른 것도 이 때문입니다.

대역은 넉넉하게, 그리고 겹치지 않게

가장 흔한 실수는 너무 작게 잡는 것입니다. 서버 수만 세면 /24(256개)도 넉넉해 보입니다. 그러나 10장에서 본 Kubernetes의 Pod를 AWS에서 돌리면(EKS, 14장) Pod 하나하나가 VPC IP를 하나씩 받습니다. 서버 10대에 Pod가 수백 개면 IP가 서버 수보다 훨씬 빨리 바닥납니다.

두 번째 실수는 겹치는 대역입니다. 나중에 VPC를 사내망이나 다른 VPC와 사설 IP로 잇게 되는데(2부), 양쪽에 똑같은 10.10.1.5가 있으면 라우터는 그 주소가 어느 쪽인지 정할 수 없습니다. 그래서 겹치는 네트워크끼리는 잇지 못합니다.

그래서 회사 단위로 대역 계획표를 둡니다. shop 운영은 10.10.0.0/16, 개발은 10.20.0.0/16, 사내망은 192.168.0.0/16처럼 서로 겹치지 않게 배정합니다.

서브넷은 VPC 대역을 AZ 하나에 놓은 조각이다

서브넷은 VPC 대역을 잘라 가용 영역 하나에 놓은 조각입니다. 서버를 만들 때는 VPC가 아니라 서브넷을 고르고, 서버는 그 서브넷의 AZ에 놓입니다.

서브넷은 AZ를 넘지 못합니다. 그래서 AZ 하나가 통째로 멈춰도 서비스가 살아 있으려면 같은 역할의 서브넷을 AZ마다 하나씩 만들어 서버를 나눠 둡니다.

서브넷마다 주소 5개는 AWS 몫이다

각 서브넷의 앞 4개와 마지막 1개 주소는 AWS가 예약해 서버에 줄 수 없습니다. 맨 앞(네트워크 주소)과 맨 뒤(브로드캐스트 주소)를 쓰지 않는 것은 2장에서 본 일반 규칙이고, 나머지 셋은 AWS가 가상 네트워크를 돌리는 데 씁니다.

.1은 VPC 라우터, 즉 모든 서브넷에 보이지 않게 들어 있는 가상 라우터입니다. 2장의 기본 게이트웨이가 바로 이 주소입니다. .2는 DNS 용도의 예약(실제 DNS 서버는 VPC 대역의 +2, 1부 끝에서 봅니다), .3은 향후 용도입니다.

라우팅 테이블이 서브넷의 출구를 정한다

서브넷을 만들었다고 패킷이 어디로든 가는 것은 아닙니다. 2장에서 라우팅 테이블을 "이 대역은 저쪽으로"라는 규칙 목록이라고 했습니다. VPC에서도 같습니다. 서버가 보낸 패킷은 서브넷의 VPC 라우터(.1)에 닿고, 라우터는 그 서브넷에 연결된 라우팅 테이블을 보고 다음 행선지를 고릅니다.

규칙 한 줄은 대상(destination)과 타깃(target)으로 이루어집니다. 대상은 목적지 대역, 타깃은 그 대역으로 가는 패킷을 넘길 장치입니다. "0.0.0.0/0은 인터넷 게이트웨이로"처럼 읽습니다.

서브넷 하나에는 라우팅 테이블이 정확히 하나 연결됩니다. 반대로 테이블 하나는 여러 서브넷이 같이 쓸 수 있습니다. shop처럼 역할이 같은 서브넷은 같은 테이블을 쓰고, 역할이 다르면 테이블을 나눕니다. 즉 서브넷의 성격은 연결된 라우팅 테이블이 정합니다.

모든 테이블에는 지울 수 없는 local 규칙이 들어 있습니다. VPC 대역(10.10.0.0/16) 전체를 VPC 안에서 직접 배달하라는 뜻이라, 같은 VPC의 서브넷끼리는 언제나 길이 통합니다. 막는 일은 길이 아니라 뒤에서 볼 방화벽의 몫입니다.

테이블을 따로 연결하지 않은 서브넷은 VPC의 메인 라우팅 테이블을 따릅니다. 그러니 메인 테이블에는 인터넷 경로를 넣지 않는 편이 안전합니다. 새로 만든 서브넷이 실수로 인터넷에 열리지 않습니다.

규칙이 여럿 맞으면 가장 구체적인 것이 이긴다

대상              타깃
10.10.0.0/16      local
0.0.0.0/0         nat-0d4e5f    # 뒤에서 설명

# 패킷 목적지 → 맞는 규칙 → 선택
10.10.21.5     /16, /0 둘 다  → local
52.95.0.10     /0만          → nat-0d4e5f

목적지 10.10.21.5는 10.10.0.0/16에도, 모든 주소를 뜻하는 0.0.0.0/0에도 맞습니다. 이때 VPC 라우터는 최장 일치, 즉 고정된 앞자리(프리픽스)가 가장 긴 규칙을 고릅니다.

프리픽스가 길수록 가리키는 범위가 좁아 더 구체적인 규칙이기 때문입니다. /0은 고정한 비트가 하나도 없어 "나머지 전부"를 뜻하는 기본 경로가 됩니다. 이 원리 덕분에 2부에서 S3로 가는 길만 따로 빼낼 수 있습니다.

인터넷 게이트웨이는 VPC의 인터넷 출입문이다

지금까지의 VPC는 local 규칙만 있어 바깥과 완전히 끊겨 있습니다. 사용자의 요청을 받으려면 인터넷과 이어진 문이 필요합니다.

인터넷 게이트웨이(IGW)가 그 문입니다. VPC에 하나만 붙이고, 라우팅 테이블에 0.0.0.0/0 → igw-… 규칙을 넣은 서브넷만 이 문을 씁니다.

IGW는 장비 한 대가 아니라 AWS가 여러 곳에 나눠 운영하는 논리적 장치입니다. 그래서 대역폭 한도나 단일 장애점을 신경 쓸 필요가 없고, IGW 자체에는 요금도 붙지 않습니다.

그런데 문을 달았다고 바로 통하지는 않습니다. VPC 안의 서버에는 사설 IP뿐인데, 인터넷은 사설 IP로 길을 찾지 못하기 때문입니다(2장). 이 간극을 IGW가 어떻게 메우는지 다음 슬라이드에서 봅니다.

IGW는 사설 IP를 퍼블릭 IP로 1:1 바꾼다

AWS의 가상 서버를 EC2 인스턴스라고 합니다(자세한 것은 14장). 인스턴스에 퍼블릭 IP를 붙여도 운영체제의 네트워크 카드에는 사설 IP만 보입니다. 퍼블릭 IP는 IGW가 따로 기억해 둡니다.

패킷이 IGW를 나갈 때 IGW가 출발지 사설 IP를 짝지어진 퍼블릭 IP로 바꾸고, 들어올 때는 반대로 바꿉니다. 2장의 NAT와 비슷하지만 포트를 섞지 않고 주소 하나에 하나를 대응시키는 1:1 변환입니다.

그래서 서버가 인터넷과 직접 통신하려면 세 가지가 모두 있어야 합니다. IGW로 가는 경로, 인스턴스의 퍼블릭 IP, 그리고 그 트래픽을 허용하는 보안 그룹입니다. 보안 그룹은 인스턴스 앞에 붙는 방화벽으로, 1부 뒤쪽에서 자세히 봅니다. 하나라도 빠지면 연결되지 않습니다.

퍼블릭 IPv4 주소는 2024년부터 쓰든 안 쓰든 개당 시간당 0.005 USD(한 달 약 3.6 USD)가 붙습니다.

IGW로 가는 길이 있으면 Public 서브넷이다

콘솔에 "Public"이라는 체크 상자는 없습니다. 연결된 라우팅 테이블에 IGW로 가는 기본 경로가 있으면 그 서브넷을 Public 서브넷이라고 부를 뿐입니다. shop의 10.10.1.0/24와 10.10.2.0/24가 여기에 해당합니다.

그렇다면 주문 API 서버도 Public 서브넷에 두고 퍼블릭 IP를 주면 간단하지 않을까요? 그러면 서버 하나하나가 인터넷에 직접 노출되어 공격받을 지점이 서버 수만큼 늘고, 퍼블릭 IP 요금도 서버마다 붙습니다.

그래서 Public 서브넷에는 바깥과 직접 마주해야 하는 장치만 둡니다. 사용자의 요청을 대표로 받아 뒤의 서버들에 나눠 주는 로드 밸런서(3부)와, 곧 볼 NAT Gateway입니다. 서버는 그 뒤에 숨깁니다.

바뀌면 안 되는 주소에는 Elastic IP를 쓴다

인스턴스에 자동으로 붙는 퍼블릭 IP는 인스턴스를 중지했다 다시 시작하면 새 주소로 바뀝니다. 결제 대행사가 "호출하는 쪽 IP를 알려 주면 방화벽에 등록하겠다"고 할 때 이 주소를 알려 주면 곤란합니다. 이때 쓰는 것이 Elastic IP(EIP), 계정이 보유하고 원하는 장치에 붙였다 떼는 고정 퍼블릭 IP입니다.

항목자동 할당 퍼블릭 IPElastic IP(EIP)
소유인스턴스에 딸림계정이 보유, 떼었다 붙임
중지 후 시작새 주소로 바뀜그대로 유지
요금시간당 0.005 USD연결 여부와 관계없이 동일
쓰는 곳임시 서버NAT Gateway, 고정 IP가 필요한 곳

서버 한 대의 IP를 외부에 알리면 그 서버를 교체할 때마다 EIP를 옮겨야 합니다. 그래서 서버 대신 앞단 장치(NAT Gateway나 3부의 NLB)의 고정 IP를 알리는 쪽이 교체에 강합니다. 쓰지 않는 EIP도 요금이 나가니 바로 반납합니다.

Private 서브넷의 서버도 밖으로는 나가야 한다

주문 API 서버는 Public 서브넷 뒤, 10.10.11.0/24와 10.10.12.0/24에 둡니다. 퍼블릭 IP가 없으니 인터넷에서 들어올 수 없어 안전합니다. 그런데 이 서버도 밖으로 나갈 일이 있습니다. 결제 시 PG사의 외부 API를 호출하고, 운영체제 보안 패치를 내려받아야 합니다.

IGW로 바로 보내면 될까요? 안 됩니다. IGW의 1:1 변환은 퍼블릭 IP가 짝지어진 주소만 바꿀 수 있어서, 퍼블릭 IP 없는 서버의 패킷은 IGW를 지나도 돌아올 주소가 없습니다.

필요한 것은 2장의 NAT입니다. 여러 사설 주소의 연결을 공인 주소 하나로 모아 내보내고, 출발지 포트까지 바꿔 연결을 구분하는 방식이었습니다. 포트까지 바꾸는 이 방식을 정확히는 NAPT라고 부릅니다.

NAT Gateway는 이 NAPT를 AWS가 관리형으로 운영해 주는 장치입니다. Public 서브넷에 만들고 EIP를 하나 붙인 뒤, 주문 API 서브넷의 라우팅 테이블에 0.0.0.0/0 → nat-…을 넣습니다. 그러면 서버의 패킷은 NAT로 가고, NAT가 출발지를 자기 EIP로 바꿔 IGW로 내보냅니다.

이렇게 기본 경로가 NAT를 향하는 서브넷을 Private 서브넷이라고 부릅니다. 이름이 그렇다는 것이지, 실제 성질은 이 경로 한 줄이 만듭니다.

NAT는 안에서 시작한 연결만 통과시킨다

주문 API 10.10.11.5PG사 API
요청 10.10.11.5:41000 → PG:443
NAT: 출발지를 EIP:1024로 바꾸고 짝을 기록
응답 PG:443 → EIP:1024기록을 보고 10.10.11.5:41000으로
차단 새 연결 외부 → EIP:22

NAT는 안에서 나간 연결마다 "원래 주소:포트 ↔ EIP:새 포트" 짝을 표에 적어 둡니다. 응답이 돌아오면 그 표를 보고 원래 서버로 되돌립니다.

밖에서 먼저 보낸 패킷은 표에 짝이 없어 어디로 보낼지 알 수 없으니 버려집니다. 그래서 나갈 수는 있지만 밖에서 먼저 말을 걸 수는 없는 비대칭이 생기고, 이것이 Private 서브넷이 안전한 이유입니다.

NAT Gateway는 AZ마다 두고 경로도 맞춘다

NAT Gateway는 만든 서브넷의 AZ 하나에 사는 장치입니다. 그 AZ 안에서는 AWS가 이중화해 주지만, AZ 자체가 멈추면 함께 멈춥니다.

shop의 두 AZ가 AZ a의 NAT 하나를 같이 쓴다고 해 봅시다. AZ a가 멈추면 AZ c의 서버는 멀쩡한데도 PG사를 부르지 못해 결제가 멈춥니다. 그래서 AZ마다 NAT를 두고, 각 AZ의 라우팅 테이블이 같은 AZ의 NAT를 가리키게 합니다. 라우팅 테이블도 AZ별로 나뉘는 이유입니다.

다른 AZ의 NAT로 가면 요금도 두 번

12장에서 본 대로 데이터 전송 요금은 경로마다 다르고, AZ 경계를 넘으면 GB당 요금이 붙습니다. AZ를 건너 NAT로 가면 NAT 처리 요금에 이 요금이 더해집니다.

리전 모드 NAT Gateway

NAT 하나가 워크로드가 있는 AZ로 자동 확장되고 Public 서브넷도 필요 없는 방식도 있습니다. 새 AZ로 확장되는 데 최대 60분이 걸리고 Private NAT 용도는 지원하지 않습니다.

NAT 하나가 같은 목적지에 여는 연결은 5만 5천 개다

NAT Gateway의 대역폭은 5 Gbps에서 시작해 100 Gbps까지 자동으로 늘어나고, 초당 처리 패킷 수도 100만에서 1,000만까지 늘어납니다. 이 한도를 넘으면 패킷을 버리므로, 그 정도 트래픽이면 서브넷을 나눠 NAT를 더 둡니다.

더 자주 부딪히는 것은 포트 한도입니다. 2장에서 TCP 연결 하나는 출발지 IP·포트, 목적지 IP·포트, 프로토콜의 다섯 값(5-튜플)으로 구분된다고 했습니다.

shop의 모든 서버가 PG사 API 한 곳을 부르면 NAT 쪽 IP, 목적지 IP·포트, 프로토콜이 모두 같고 NAT의 출발지 포트만 달라질 수 있습니다. 포트는 16비트라 한계가 있고, AWS는 이를 IP 하나당 같은 목적지로 동시 연결 55,000개로 정해 두었습니다.

넘으면 새 연결이 실패하고 CloudWatch 지표 ErrorPortAllocation이 올라갑니다. NAT에 IP를 최대 8개까지 붙이거나, 커넥션 재사용(keep-alive)으로 연결 수 자체를 줄입니다.

NAT 요금은 켜 둔 시간과 지나간 양으로 쌓인다

NAT Gateway 요금은 두 가지입니다. us-east-1 기준으로 존재하는 것만으로 시간당 0.045 USD, 처리한 데이터 GB당 0.045 USD입니다. 인터넷으로 나가는 전송 요금은 여기에 별도로 더해집니다. 서울 리전은 단가가 조금 다르지만 구조는 같습니다.

계산해 보면 감이 옵니다. AZ 세 곳에 NAT를 하나씩 두면 시간 요금만 한 달(730시간) 약 100 USD입니다. 하루 1TB를 NAT로 보내면 처리 요금만 한 달 약 1,380 USD입니다. 시간 요금보다 처리 요금이 훨씬 커지기 쉽습니다.

처리 요금이 큰 경우를 살펴보면 대개 S3 업로드나 컨테이너 이미지 내려받기처럼 AWS 서비스로 가는 트래픽입니다. 이것을 NAT를 거치지 않게 돌리는 방법이 2부의 VPC 엔드포인트입니다.

NAT 인스턴스는 싸지만 운영을 떠안는다

NAT Gateway가 나오기 전에는 EC2 인스턴스에 2장의 NAT를 직접 설정해 썼습니다. 9장의 iptables로 주소 변환 규칙을 넣는 방식입니다. 이때 꼭 꺼야 하는 설정이 소스/대상 확인입니다. EC2는 기본적으로 자기 IP가 출발지나 목적지가 아닌 패킷을 버리는데(위조 방지), NAT는 남의 패킷을 중계하는 장치라 이 확인을 꺼야 동작합니다.

NAT 인스턴스는 트래픽이 아주 적은 개발 환경에서 비용을 아끼려고 쓰는 정도입니다. 운영 환경의 기본은 NAT Gateway입니다.

DB 서브넷에는 나가는 길도 두지 않는다

shop의 MySQL은 주문 API 서버만 접속하면 됩니다. DB가 먼저 인터넷으로 나갈 이유는 없습니다. 그래서 DB 서브넷(10.10.21.0/24, 10.10.22.0/24)의 라우팅 테이블에는 local 규칙 하나만 둡니다. 이렇게 VPC 밖으로 가는 경로가 아예 없는 서브넷을 Isolated 서브넷이라고 부릅니다.

나가는 길이 없으면 DB가 해킹당하더라도 데이터를 인터넷으로 빼낼 길이 막힙니다. 공격을 막는 마지막 방어선이 하나 더 생기는 셈입니다.

대가도 있습니다. 백업 파일을 S3에 올리거나 AWS 서비스를 부르는 것도 막힙니다. AWS 서비스도 결국 VPC 밖에 있기 때문입니다. VPC 안에서 AWS 서비스로만 이어지는 사설 통로를 따로 뚫어야 하는데, 그것이 2부 첫머리의 VPC 엔드포인트입니다.

두 AZ에 펼친 shop VPC의 모양

ENI는 인스턴스에 꽂는 가상 네트워크 카드다

그림의 상자 하나하나는 어떻게 서브넷에 "놓이는" 걸까요? 실제로 서브넷에 속하는 것은 서버가 아니라 ENI, 서브넷 하나에 속한 가상 네트워크 카드입니다. 사설 IP, 퍼블릭 IP, 2장의 MAC 주소, 그리고 뒤에서 볼 보안 그룹이 모두 인스턴스가 아니라 ENI에 붙습니다.

인스턴스는 기본 ENI 하나를 갖고, 유형에 따라 보조 ENI를 더 꽂거나 ENI마다 보조 사설 IP를 여러 개 둘 수 있습니다.

더 중요한 사실은 VPC에 들어오는 거의 모든 관리형 서비스가 ENI를 만든다는 점입니다. 로드 밸런서 노드, NAT Gateway, 2부의 인터페이스 엔드포인트, AWS의 관리형 DB인 RDS(15장), VPC에 연결한 Lambda 함수(17장)가 모두 서브넷의 IP를 하나 이상 차지합니다.

그래서 서브넷 크기를 정할 때 서버 수만 세면 모자랍니다. 이런 관리형 서비스의 몫과 확장 여유까지 셉니다.

기본 VPC는 연습용 지름길이다

shop처럼 VPC를 직접 설계하지 않아도 계정에는 리전마다 기본 VPC가 하나씩 있습니다. 대역은 172.31.0.0/16이고, AZ마다 /20 서브넷이 하나씩 있으며, 모든 서브넷이 IGW로 가는 경로를 가진 Public 서브넷입니다. 인스턴스에는 퍼블릭 IP가 자동으로 붙습니다.

덕분에 아무 설정 없이 인스턴스를 띄워 바로 접속해 볼 수 있지만, 지금까지 본 원칙과 정반대입니다. 모든 것이 인터넷에 노출되고, 모든 계정의 기본 VPC 대역이 같아서 나중에 서로 이을 수도 없습니다.

운영 계정에서는 목적에 맞는 VPC를 11장의 IaC로 새로 만들고, 기본 VPC는 지우거나 쓰지 않습니다. 지운 기본 VPC는 필요하면 콘솔에서 다시 만들 수 있습니다.

길이 열려 있어도 문은 따로 잠근다

라우팅의 local 규칙 때문에 VPC 안의 서브넷끼리는 언제나 길이 통한다고 했습니다. 그렇다면 Public 서브넷에 놓인 로드 밸런서가 해킹당했을 때 DB 3306 포트까지 바로 갈 수 있다는 뜻입니다. 길(라우팅)과 출입 허가(방화벽)는 따로 정해야 합니다.

그 출입 허가를 맡는 첫 번째 장치가 보안 그룹입니다. ENI 하나하나에 붙는 가상 방화벽으로, "어디서 오는 어느 포트의 트래픽을 받을지"를 규칙으로 적습니다. 인스턴스가 아니라 ENI 단위라서, 같은 서브넷에 있는 서버라도 보안 그룹이 다르면 다르게 막힙니다.

규칙은 허용만 적을 수 있습니다. 거부 규칙은 없고, 적힌 허용에 하나도 맞지 않으면 거부됩니다. 규칙이 여러 개면 순서와 관계없이 모두 합쳐서 하나라도 맞으면 통과합니다.

새로 만든 보안 그룹은 들어오는 것은 모두 막고, 나가는 것은 모두 허용하는 상태로 시작합니다. 그래서 shop의 주문 API 서버에 보안 그룹을 붙이면 처음에는 아무 요청도 받지 못하고, "로드 밸런서에서 오는 8080"을 직접 허용해야 비로소 동작합니다.

그런데 서버가 받은 요청에 응답을 돌려보낼 때, 그 응답 패킷은 무슨 규칙으로 나갈까요? 다음 슬라이드의 주제입니다.

보안 그룹은 오간 연결을 기억한다

클라이언트서버 :443
SYN 52344 → 443 인바운드 443 허용
SYN + ACK 443 → 52344 기억한 연결이라 통과
HTTP 요청 52344 → 443
상태를 안 보는 방화벽이면 52344로 나가는 규칙이 따로 필요

응답의 목적지 포트는 클라이언트가 고른 2장의 임시 포트(ephemeral port)라서 매번 다릅니다. 이걸 규칙으로 일일이 열 수는 없습니다.

보안 그룹은 9장의 conntrack처럼 연결 상태를 추적합니다. 허용된 요청으로 시작된 연결이면 응답은 규칙과 관계없이 통과시킵니다. 이렇게 상태를 기억하는 방화벽을 Stateful이라고 부릅니다.

보안 그룹은 IP 대신 다른 보안 그룹을 가리킨다

보안 그룹 규칙의 출발지에는 IP 대역뿐 아니라 다른 보안 그룹을 적을 수 있습니다. DB 보안 그룹의 출발지를 sg-app으로 적으면, 그 보안 그룹이 붙은 ENI에서 온 트래픽만 받습니다.

서버 수를 부하에 따라 자동으로 늘리고 줄이는 Auto Scaling(14장)을 쓰면 서버 IP가 계속 바뀌는데, 이 방식이면 규칙을 고칠 필요가 없습니다. 같은 서브넷의 엉뚱한 서버는 IP가 맞아도 막힙니다. 각 계층이 바로 앞 계층만 믿는 사슬이 됩니다.

보안 그룹에도 한도가 있고 지킬 습관이 있다

보안 그룹 하나에는 인바운드와 아웃바운드 각각 기본 60개 규칙을 둘 수 있고, ENI 하나에는 기본 5개(최대 16개)의 보안 그룹을 붙입니다. 두 값의 곱은 1,000을 넘지 못합니다. ENI마다 평가할 규칙 수를 제한해 성능을 지키려는 한도입니다.

Stateful에는 부작용도 있습니다. 허용 규칙을 지워도 이미 추적 중인 연결은 끊기지 않습니다. 공격 중인 연결을 즉시 끊어야 한다면 다음에 볼 NACL의 거부 규칙을 씁니다.

운영에서 지키는 습관은 셋입니다. 출발지를 0.0.0.0/0으로 여는 것은 공개 로드 밸런서의 443뿐으로 제한합니다. 서버 접속용 22번 포트는 열지 않고, 인바운드 포트 없이 IAM 권한으로 접속하는 SSM Session Manager(14장)를 씁니다.

마지막으로 보안 그룹과 규칙마다 "왜 열었는가"를 설명으로 남깁니다. 이유가 없는 규칙은 아무도 지우지 못해 계속 늘어납니다.

NACL은 서브넷 경계에 선 두 번째 방화벽이다

보안 그룹은 허용만 적을 수 있어서 "이 대역은 무조건 막아라"를 표현하지 못합니다. 특정 공격 대역을 서브넷 전체에서 한 번에 막고 싶을 때 쓰는 것이 NACL(네트워크 ACL)입니다. ACL은 접근 제어 목록(Access Control List)의 줄임말입니다.

NACL은 ENI가 아니라 서브넷 경계에 붙습니다. 서브넷으로 들어오고 나가는 모든 패킷이 검사를 받고, 같은 서브넷 안의 서버끼리 주고받는 패킷은 검사하지 않습니다.

규칙에는 허용(ALLOW)과 거부(DENY)를 모두 적을 수 있고, 각 규칙에 번호가 붙습니다. 9장의 iptables처럼 번호가 낮은 규칙부터 맞춰 보다가 처음 맞은 규칙의 동작으로 결정하고 멈춥니다. 보안 그룹처럼 모두 합쳐 보지 않습니다.

가장 큰 차이는 상태를 기억하지 않는다(Stateless)는 점입니다. 패킷 하나하나를 앞뒤 연결과 무관하게 판단하므로, 들어오는 요청을 허용했더라도 나가는 응답은 별도 규칙으로 허용해야 합니다.

VPC를 만들면 생기는 기본 NACL은 모든 트래픽을 허용합니다. 반면 새로 만든 사용자 지정 NACL은 모든 트래픽을 거부하는 상태로 시작하므로, 붙이는 순간 서브넷이 먹통이 되지 않게 규칙을 먼저 채웁니다.

NACL은 번호 순으로 읽다가 첫 일치에서 멈춘다

번호  유형    포트          소스             동작

100   TCP     443           0.0.0.0/0        ALLOW
110   TCP     1024-65535    0.0.0.0/0        ALLOW
*     전체    전체          0.0.0.0/0        DENY

# 아웃바운드
100   TCP     443           0.0.0.0/0        ALLOW

90번은 공격 대역을 막는 규칙입니다. 100번보다 작은 번호라야 먼저 평가되어 효과가 있습니다. 번호를 10 단위로 띄워 두면 사이에 끼워 넣기 쉽습니다. *는 아무것도 맞지 않을 때의 마지막 거부입니다.

아웃바운드 110번은 사용자에게 가는 응답(목적지가 임시 포트)을, 인바운드 110번은 NAT 등을 통해 밖으로 연 연결의 응답을 받기 위한 규칙입니다. 이걸 잊으면 요청은 들어오는데 응답이 나가지 못합니다.

보안 그룹은 보안 그룹 참조와 Stateful 덕분에 실수할 여지가 적어 주 방어선이 됩니다. NACL은 특정 대역을 서브넷 단위로 막거나 이미 맺어진 연결을 끊을 때만 씁니다. 수천 개 IP를 막는 일은 규칙 한도 때문에 맞지 않고, 웹 요청을 내용까지 보고 거르는 방화벽인 WAF(16장)가 맡습니다.

VPC 안의 DNS는 대역 +2 주소가 답한다

주문 API 서버는 PG사 API를 IP가 아니라 이름(api.pg-example.com)으로 부릅니다. 2장에서 이름은 재귀 리졸버에게 물어 IP로 바꾼다고 했습니다. VPC 안에서는 누가 그 리졸버일까요?

VPC마다 Route 53 Resolver(최근 문서 표기는 VPC Resolver)가 들어 있습니다. 주소는 VPC 기본 대역의 +2(10.10.0.2)입니다. 서브넷마다 .2를 비워 두는 것도 이 DNS 용도의 예약입니다.

또 하나의 주소는 169.254.169.253입니다. 169.254.0.0/16은 링크 로컬 대역, 즉 라우터를 넘지 않고 바로 붙은 장치끼리만 쓰는 주소라서 어느 VPC 대역에서든 똑같이 쓸 수 있습니다.

인스턴스는 부팅 때 2장의 DHCP로 이 리졸버 주소를 받습니다. 리졸버는 인터넷 도메인은 재귀 조회로 찾고, VPC 내부 이름과 4부에서 볼 프라이빗 호스팅 영역(VPC 안에서만 보이는 DNS 레코드 묶음)은 직접 답합니다.

DNS 동작은 VPC 속성 두 개가 켠다

enableDnsSupport(기본 true)는 VPC 리졸버를 쓸지 여부입니다. 끄면 위의 .2 주소가 답하지 않습니다.

enableDnsHostnames(직접 만든 VPC는 기본 false)는 퍼블릭 IP를 가진 인스턴스에 ec2-3-35-…amazonaws.com 같은 DNS 이름을 붙일지입니다. 이름만 보면 사소해 보이지만, 프라이빗 호스팅 영역과 2부 인터페이스 엔드포인트의 프라이빗 DNS는 둘 다 true여야 동작합니다. shop은 둘 다 켭니다.

리졸버에는 잘 알려지지 않은 한도가 있습니다. DNS, 그리고 링크 로컬 주소로 제공되는 다른 서비스를 합쳐 ENI당 초당 1,024패킷입니다.

함께 묶이는 서비스는 인스턴스가 자기 정보와 임시 자격 증명을 가져오는 IMDS(인스턴스 메타데이터 서비스, 12장의 역할 자격 증명이 여기서 옵니다)와 시각을 맞추는 NTP입니다. DNS 결과를 캐시하지 않는 앱이 초당 수천 번 조회하면 이 한도에 걸려 조회가 간헐적으로 실패합니다.

IPv6는 Egress-only IGW로 나간다

퍼블릭 IPv4 요금과 주소 고갈 때문에 IPv6를 함께 쓰는 VPC가 늘고 있습니다. VPC에 IPv6 대역(/56)을 붙이면 서브넷마다 /64가 배정됩니다. IPv6 주소는 128비트라 주소가 넉넉해서 모두 인터넷에서 유일한 전역 주소이고, 그래서 NAT가 없습니다.

그러면 "나가기만 되는 서브넷"을 어떻게 만들까요? 그 장치가 Egress-only 인터넷 게이트웨이입니다. 라우팅 테이블에 ::/0 → eigw-…를 넣으면 안에서 시작한 연결과 그 응답만 통과시키고 밖에서 시작한 연결은 막습니다. NAT처럼 상태를 기억하지만 주소는 바꾸지 않습니다.

주의할 점은 보안 그룹과 NACL 규칙을 IPv4와 IPv6에 각각 적어야 한다는 것입니다. 0.0.0.0/0만 열고 ::/0을 잊는 실수가 흔합니다. 여기까지가 VPC 하나의 안쪽 설계입니다.

2부

격리된 VPC를 바깥과 잇는 길

1부의 VPC는 인터넷 말고는 아무 데도 닿지 않습니다. 그런데 shop은 AWS 저장 서비스에 파일을 올리고, 다른 팀 VPC의 회원 API를 부르고, 회사 데이터 센터와도 주고받아야 합니다. 상대가 누구냐에 따라 길이 다르고, 길마다 패킷이 지나는 곳과 요금이 다릅니다.

기초 원리 여기부터는 연결 장치마다 패킷이 라우팅 테이블의 어느 줄을 타고 어디를 지나는지 봅니다.

S3로 가는 트래픽이 NAT를 지날 이유는 없다

shop은 상품 이미지와 DB 백업을 S3, AWS의 파일 저장 서비스(15장)에 올립니다. S3의 주소는 퍼블릭 IP이므로, Private 서브넷의 주문 API 서버가 보낸 패킷은 기본 경로를 따라 NAT Gateway와 IGW를 지납니다. 같은 서울 리전 안의 통신인데도 1부에서 본 NAT 처리 요금이 GB마다 붙고, Isolated 서브넷의 DB 서버는 아예 갈 수 없습니다.

VPC 엔드포인트는 VPC 안에서 AWS 서비스로 바로 이어지는 사설 지름길입니다. NAT도 IGW도 거치지 않으므로 Isolated 서브넷에서도 동작합니다. 라우팅 테이블에 경로를 넣는 게이트웨이형과 서브넷에 ENI를 만드는 인터페이스형 두 가지가 있습니다.

  1. 주문 APIPrivate 서브넷
  2. NAT GatewayGB당 처리 요금
  3. IGW퍼블릭 경로
  4. S3같은 리전
  1. 주문 APIPrivate 서브넷
  2. 엔드포인트AWS 망 안에서 직접
  3. S3NAT 요금 없음

게이트웨이 엔드포인트는 라우팅 경로 한 줄이다

대상              타깃
10.10.0.0/16      local
0.0.0.0/0         nat-0d4e5f
pl-78a54011       vpce-0s3gw   # 자동 추가

게이트웨이 엔드포인트는 S3와 DynamoDB(AWS의 키-값 DB, 15장) 두 서비스만 지원합니다. 만들 때 고른 라우팅 테이블에 경로 한 줄이 자동으로 들어갑니다.

대상의 pl-…은 프리픽스 목록, 즉 "서울 리전 S3가 쓰는 IP 대역 전부"를 AWS가 관리하는 이름 하나로 묶은 것입니다. 이 대역들은 0.0.0.0/0보다 프리픽스가 기므로 1부의 최장 일치에 따라 S3로 가는 패킷만 엔드포인트로 빠집니다. 앱 코드는 바꿀 것이 없습니다.

게이트웨이 엔드포인트는 공짜지만 VPC 안에서만 쓴다

게이트웨이 엔드포인트에는 시간 요금도 데이터 처리 요금도 없습니다. NAT를 지날 때 GB당 붙던 요금이 그대로 사라지므로, S3를 쓰는 VPC라면 만들지 않을 이유가 거의 없습니다. shop은 주문 API 서브넷과 DB 서브넷의 라우팅 테이블 모두에 연결합니다.

DB 서브넷은 이제 local과 S3 경로 두 줄만 가집니다. 인터넷으로는 여전히 나갈 수 없지만 백업은 올릴 수 있습니다.

같은 리전, 같은 VPC 안에서만

라우팅 테이블에 적힌 경로라서 그 VPC의 서브넷만 탈 수 있습니다. 다른 리전의 S3에는 쓸 수 없고, 뒤에서 볼 VPN이나 Peering 너머의 네트워크가 이 경로를 빌려 쓸 수도 없습니다. 그런 경우에는 다음의 인터페이스 엔드포인트를 씁니다.

나머지 서비스는 인터페이스 엔드포인트로 간다

shop이 부르는 AWS 서비스는 S3만이 아닙니다. DB 비밀번호를 꺼내 오는 Secrets Manager(16장), 로그를 보내는 CloudWatch Logs(18장), 12장의 임시 자격 증명을 발급하는 STS, 컨테이너 이미지를 내려받는 ECR(14장)도 부릅니다. 이들에는 게이트웨이형이 없습니다.

인터페이스 엔드포인트는 고른 서브넷마다 사설 IP를 가진 ENI를 만들고, 그 ENI를 서비스로 가는 입구로 씁니다. ENI로 보낸 패킷은 AWS 망 안에서 서비스까지 전달됩니다. 이 전달 기술의 이름이 PrivateLink입니다.

ENI이므로 1부의 보안 그룹이 붙습니다. shop은 엔드포인트 보안 그룹에 "sg-app에서 오는 443"만 허용합니다.

프라이빗 DNS가 SDK 설정을 그대로 두게 한다

  1. 이름 조회

    SDK가 secretsmanager.ap-northeast-2.amazonaws.com을 VPC 리졸버에 묻습니다.

  2. 프라이빗 DNS 켬

    리졸버가 공인 IP 대신 엔드포인트 ENI의 사설 IP(예: 10.10.11.40)를 답합니다.

  3. 연결

    패킷이 local 경로로 같은 VPC의 ENI에 닿습니다. NAT를 지나지 않습니다.

  4. 전달

    PrivateLink가 AWS 망 안에서 Secrets Manager까지 요청을 넘깁니다.

엔드포인트를 만들어도 앱이 공인 주소로 가면 소용이 없습니다. 프라이빗 DNS를 켜면 VPC 안에서 서비스의 원래 이름이 ENI의 사설 IP로 풀리므로, 앱과 SDK 설정을 하나도 바꾸지 않아도 됩니다. 1부의 DNS 속성 두 개가 켜져 있어야 동작합니다.

요금은 AZ마다 시간당 요금 + GB당 처리 요금(us-east-1 기준 각 0.01 USD)입니다. 서비스 10개를 3 AZ에 만들면 시간 요금만 한 달 약 216 USD이므로, 실제로 쓰는 서비스만 만듭니다.

엔드포인트 정책으로 지름길에 문지기를 둔다

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::shop-prod-*/*"
  }]
}

엔드포인트 정책은 12장의 리소스 기반 정책과 같은 문법으로, 이 엔드포인트를 지나는 요청에 조건을 하나 더 겁니다. 기본값은 모두 허용입니다.

위 정책은 Principal이 누구든(*) 이 길로는 shop-prod-로 시작하는 버킷에만 읽고 쓰게 합니다. 서버 자격 증명이 털려도 공격자 버킷으로 데이터를 빼돌리는 경로가 막힙니다. 권한을 새로 주지는 않고, IAM 정책과 함께 평가되어 범위를 좁힐 뿐입니다.

다른 팀의 API 하나만 부르고 싶을 때

이번에는 상대가 AWS 서비스가 아니라 사내 다른 팀입니다. 회원 팀은 자기 VPC에서 회원 조회 API를 운영하고, shop의 주문 API가 이걸 불러야 합니다. 방법은 셋입니다.

첫째, 회원 API를 인터넷에 공개하고 shop이 NAT로 나가서 부르는 방법입니다. 사내용 API를 인터넷에 내놓아야 하고 NAT 요금도 붙습니다. 둘째, 두 VPC의 네트워크를 통째로 잇는 방법입니다(곧 볼 Peering). 서로의 모든 서브넷이 이어지므로 필요 이상으로 열립니다. 게다가 두 팀 모두 10.10.0.0/16을 쓰고 있다면 1부에서 본 대로 대역이 겹쳐 이을 수 없습니다.

셋째가 앞에서 본 PrivateLink를 내 서비스에 쓰는 방법입니다. AWS 서비스 대신 회원 API 하나만 shop VPC 안의 ENI로 끌어옵니다. 다음 슬라이드에서 구조를 봅니다.

PrivateLink로 내 서비스를 다른 VPC에 내놓는다

회원 팀은 API 앞에 NLB(연결을 내용 확인 없이 그대로 넘기는 로드 밸런서, 3부)를 두고 이를 엔드포인트 서비스로 등록합니다. shop은 자기 서브넷에 인터페이스 엔드포인트를 만들어 접속합니다.

연결은 shop에서 회원 쪽으로만 열리고, 두 VPC의 라우팅은 섞이지 않습니다. 패킷이 ENI에서 NLB로 넘어갈 때 주소가 바뀌기 때문에 CIDR이 겹쳐도 됩니다. 외부 업체가 고객 VPC에 API를 사설로 제공할 때도 이 방식을 씁니다.

VPC Peering은 두 VPC를 통째로 잇는다

서비스 하나가 아니라 두 네트워크 전체가 서로 통해야 할 때도 있습니다. 운영 VPC와, 배치 작업과 모니터링 도구가 모인 공용 VPC처럼요. VPC Peering은 두 VPC를 사설 IP로 직접 잇는 연결입니다. 다른 계정, 다른 리전과도 맺을 수 있습니다.

만들면 pcx-…라는 연결이 생기고, 양쪽 라우팅 테이블에 "상대 CIDR → pcx-…" 경로를 직접 넣어야 통합니다. 보안 그룹에 상대 VPC의 보안 그룹을 출발지로 적을 수도 있습니다(같은 리전일 때).

# shop VPC 10.10.0.0/16 쪽
10.10.0.0/16   local
10.30.0.0/16   pcx-0ab12c

# 공용 VPC 10.30.0.0/16 쪽
10.30.0.0/16   local
10.10.0.0/16   pcx-0ab12c

Peering은 전이되지 않는다

Peering에는 중간 장비가 없습니다. 두 VPC의 가상 라우터가 직접 패킷을 주고받으므로 대역폭 병목이나 단일 장애점이 없고, 연결 자체도 무료입니다(데이터 전송 요금만 붙음).

대신 제약이 둘입니다. 두 VPC의 CIDR이 하나라도 겹치면 만들 수 없고, 전이되지 않습니다. Peering은 "A와 B 사이" 패킷만 나르므로, B에서 출발해 A를 거쳐 C로 가는 패킷은 버립니다. VPC n개를 모두 이으려면 n(n−1)/2개, 10개면 45개 연결과 그만큼의 라우팅 규칙이 필요합니다.

Transit Gateway는 연결을 허브 하나로 모은다

VPC가 열 개를 넘고 사내망까지 붙으면 Peering 그물은 관리할 수 없게 됩니다. Transit Gateway(TGW)는 리전 안에 두는 관리형 가상 라우터입니다. VPC, 사내망 VPN, 전용선을 각각 TGW에 연결(attachment)로 붙이면, 모두가 TGW를 거쳐 서로 통신합니다.

바큇살이 모두 바퀴 축 하나로 모이는 모양이라 허브 앤 스포크라고 부릅니다. VPC가 10개여도 연결은 10개면 되고, 사내망 VPN도 TGW에 한 번만 붙이면 모든 VPC에 닿습니다. Peering과 달리 TGW는 전이 라우팅을 합니다.

TGW 라우팅 테이블로 누가 누구와 통할지 정한다

# rt-prod: 운영 VPC가 연결(association)됨
10.10.0.0/16   tgw-attach-prod      (전파)
10.90.0.0/16   tgw-attach-shared    (전파)
192.168.0.0/16 tgw-attach-vpn       (전파)

# rt-dev: 개발 VPC가 연결됨
10.20.0.0/16   tgw-attach-dev       (전파)
10.90.0.0/16   tgw-attach-shared    (전파)
# 운영 대역 경로가 없으므로 개발 → 운영 불가

TGW 안에도 라우팅 테이블이 여러 개 있습니다. 각 연결은 테이블 하나에 연결(association)되어, 그 연결에서 들어온 패킷의 목적지를 그 표로 찾습니다. 또 각 연결은 자기 대역을 여러 표에 전파(propagation)해 "이 대역은 나에게로"를 자동으로 적어 넣습니다.

운영과 개발이 공용 VPC에는 닿되 서로는 닿지 못하게 하려면 위처럼 표를 나눕니다. 각 VPC의 서브넷 라우팅 테이블에도 "다른 대역 → tgw-…" 경로를 넣어야 패킷이 TGW까지 옵니다.

Peering과 TGW는 규모와 비용으로 고른다

항목VPC PeeringTransit Gateway
구조1:1 그물망허브 앤 스포크
전이 라우팅불가가능(VPN, 전용선 포함)
요금연결 무료, 전송 요금만연결당 시간 + GB당 처리
지연추가 홉 없음TGW 홉 하나 추가

둘을 섞어 쓰기도 합니다. 대부분은 TGW로 묶고, 트래픽이 아주 많은 VPC 한 쌍만 Peering으로 직접 이어 TGW 처리 요금을 피합니다. 이제 남은 상대는 회사 데이터 센터입니다.

사내망과 잇는 첫 길은 인터넷 위의 암호 터널이다

shop의 정산 시스템은 회사 데이터 센터(192.168.0.0/16)에 있습니다. 주문 데이터를 넘기려면 VPC와 데이터 센터가 사설 IP로 통해야 합니다. 가장 빨리 만들 수 있는 길은 이미 양쪽에 깔린 인터넷을 쓰는 것입니다. 다만 사설 주소의 패킷을 인터넷에 그대로 내보낼 수 없고, 내용이 노출되어서도 안 됩니다.

해법은 터널입니다. 사설 IP 패킷을 통째로 암호화한 뒤, 공인 IP 헤더를 가진 새 패킷 안에 넣어 인터넷으로 보냅니다. 반대편 끝에서 겉 헤더를 벗기고 복호화하면 원래의 사설 패킷이 나옵니다. 인터넷에서 보면 두 공인 IP 사이에 암호문이 오갈 뿐입니다. 이 방식의 표준 규약이 IPsec입니다.

Site-to-Site VPN은 AWS가 관리하는 IPsec VPN입니다. 터널의 한쪽 끝은 데이터 센터의 라우터나 방화벽 장비이고, AWS는 이를 고객 게이트웨이(Customer Gateway)라는 이름으로 등록합니다.

다른 쪽 끝은 AWS 쪽 장치입니다. VPC 하나에만 붙인다면 VPC에 붙는 VPN 접속점인 가상 프라이빗 게이트웨이(VGW)를, 여러 VPC가 함께 쓴다면 앞에서 본 TGW를 씁니다. shop은 TGW에 붙여 운영·공용 VPC가 모두 정산 시스템에 닿게 합니다.

VPN 터널은 둘이고, 경로는 BGP가 알려 준다

VPN 연결 하나를 만들면 터널이 항상 두 개 생기고, 서로 다른 AWS 장비에 맺힙니다. AWS 쪽 유지 보수로 한 터널이 내려가도 다른 쪽으로 통하도록 고객 게이트웨이에 두 터널을 모두 구성해야 합니다.

"어느 대역이 터널 너머에 있는가"는 정적 경로로 직접 적거나 BGP로 주고받습니다. BGP는 라우터끼리 "나는 이 대역들에 닿을 수 있다"를 서로 알려 주는 프로토콜이라, 한 터널이 죽으면 그 경로가 자동으로 빠집니다.

표준 터널 하나의 대역폭은 최대 1.25 Gbps입니다(대역폭 확장 터널은 5 Gbps). TGW에 붙이고 BGP를 쓰면 ECMP, 즉 같은 비용의 경로 여러 개에 흐름을 나눠 싣는 방식으로 여러 터널을 묶어 더 키울 수 있습니다.

VPN의 장점은 몇 분이면 만든다는 것, 단점은 인터넷을 지나므로 지연과 대역폭이 그날의 인터넷 사정에 따라 흔들린다는 것입니다. 그래서 초기 연결이나 다음에 볼 전용선의 백업으로 많이 씁니다.

Direct Connect는 인터넷 대신 전용선을 깐다

정산 데이터가 늘어 VPN의 흔들림을 견딜 수 없게 되면 Direct Connect(DX)를 씁니다. 데이터 센터에서 DX 로케이션(AWS 라우터가 들어와 있는 통신사 건물)까지 물리 회선을 끌어와 AWS와 직접 잇습니다. 인터넷을 거치지 않으니 지연과 대역폭이 일정합니다.

전용 연결은 1, 10, 100, 400 Gbps이고, 파트너가 나눠 주는 호스팅 연결은 더 작은 단위로 받습니다. 개통에 몇 주가 걸리고, 회선 자체는 암호화되지 않으므로 필요하면 위에 VPN을 얹거나 이더넷 구간 암호화 표준인 MACsec을 켭니다.

회선 하나 위에 논리적인 연결을 여러 개 나눠 만드는데, 이를 가상 인터페이스(VIF)라고 합니다. 어디에 닿느냐로 세 종류입니다.

가상 인터페이스닿는 곳
Private VIFVPC(VGW 또는 DX 게이트웨이 경유)
Transit VIFDX 게이트웨이 → TGW
Public VIFS3 등 AWS 퍼블릭 서비스

DX 게이트웨이는 회선 하나를 여러 리전의 VGW나 TGW에 잇게 해 주는 중계 장치입니다.

전용선 하나는 단일 장애점이라 VPN을 뒤에 둔다

회선은 굴착 공사 한 번에 끊깁니다. DX 하나만 쓰면 사내망과 AWS의 연결 전체가 그 회선에 달려 있습니다. 중요도에 따라 서로 다른 DX 로케이션에 회선을 두 개 이상 두거나, 최소한 Site-to-Site VPN을 백업 경로로 둡니다.

두 경로가 BGP로 같은 대역을 알리면 AWS는 경로를 고를 때 DX를 VPN보다 우선합니다. 그래서 평소에는 전용선으로 흐르고, DX의 BGP 세션이 끊기면 그 경로가 빠지면서 자동으로 VPN으로 넘어갑니다.

장애 조치는 실제로 회선을 내려 시험해 봐야 믿을 수 있습니다. 백업 VPN의 대역폭(터널당 1.25 Gbps)이 평소 트래픽을 감당하지 못하면, 넘어간 뒤에 혼잡으로 다시 장애가 납니다.

IP가 통해도 이름은 따로 이어야 한다

VPN이 열려도 주문 API가 settle.corp.internal을 부르면 실패합니다. VPC 리졸버는 사내 DNS 영역을 모르고, 사내 DNS는 VPC의 프라이빗 호스팅 영역을 모르기 때문입니다.

Route 53 Resolver의 아웃바운드 엔드포인트와 전달 규칙("corp.internal은 사내 DNS로 넘겨라")이 VPC → 사내 방향을, 인바운드 엔드포인트(사내 DNS가 물어 올 VPC 안의 사설 IP)가 반대 방향을 잇습니다.

사람 한 명, 서비스 하나를 잇는 길도 있다

지금까지는 네트워크와 네트워크를 이었습니다. 재택 근무 중인 운영자가 노트북에서 shop의 관리 도구에 접근해야 한다면 단위가 다릅니다. Client VPN은 개인 단말이 VPC에 붙는 관리형 VPN으로, 오픈소스 OpenVPN 클라이언트로 접속합니다.

인증은 회사 계정 디렉터리(Active Directory), 12장에서 본 사내 로그인 연동 표준 SAML, 인증서 중에서 고르고, 연결된 서브넷 시간과 접속 수로 과금됩니다.

VPC Lattice는 반대로 IP 라우팅을 맞추는 대신 서비스 이름으로 VPC와 계정을 가로질러 잇는 L7 서비스 네트워크입니다. 접근 허용을 IAM 정책으로 적고, HTTP 경로별 라우팅도 함께 제공합니다.

서비스마다 옆에 프록시를 붙여 서비스 사이의 통신과 인증을 맡기는 구조를 서비스 메시라고 하는데, Lattice는 같은 문제를 프록시 없이 AWS 관리형으로 푸는 쪽입니다. MSA에서 서비스가 많고 VPC 구조와 서비스 연결을 분리하고 싶을 때 검토합니다.

무엇과 잇느냐가 장치를 정한다

2부에서 놓은 길을 상대별로 정리합니다. 각 장치는 결국 1부의 라우팅 테이블에 줄 하나를 더하거나(게이트웨이 엔드포인트, Peering, TGW, VPN), 서브넷에 ENI를 꽂는(인터페이스 엔드포인트, PrivateLink) 두 방식 중 하나입니다.

3부

서버 여러 대 앞에서 요청을 나누는 문지기

1부에서 Public 서브넷에 "로드 밸런서"를 두겠다고만 했습니다. 이 부는 그 자리에 무엇이 서는지, 요청 하나가 그 안에서 어떤 단계를 거쳐 서버에 닿는지, 그리고 설정 숫자 하나하나가 배포와 장애 때 무엇을 바꾸는지를 봅니다.

서버가 여러 대면 앞에 문지기가 필요하다

shop의 주문 API는 AZ a와 c에 두 대씩, 모두 네 대입니다. 사용자는 이 네 대의 사설 IP를 알 수도 없고 알아서도 안 됩니다. 서버는 배포 때마다 바뀌고, 죽기도 하고, 트래픽에 따라 늘었다 줄기 때문입니다. 사용자에게는 변하지 않는 입구 하나가 필요합니다.

2장에서 이 역할을 하는 장치를 봤습니다. 서비스의 단일 입구가 되어 요청을 뒤의 서버들에 나눠 주는 리버스 프록시이자 로드 밸런서입니다. 봉투를 TCP 헤더까지만 열면 L4, HTTP 메시지까지 열면 L7 로드 밸런서라고 했습니다. 8장에서는 요청을 나누는 알고리즘(라운드 로빈, 최소 연결)을 봤습니다.

이걸 서버에 Nginx를 깔아 직접 운영할 수도 있습니다. 그러면 Nginx 서버 자체의 이중화, 트래픽 증가에 맞춘 확장, 인증서 갱신이 모두 우리 일이 됩니다.

ELB는 이 로드 밸런서를 AWS가 관리형으로 운영해 주는 서비스입니다. 우리는 "어느 서브넷에서, 어느 포트로 받아서, 어느 서버들에 나눌지"만 정하고, 장비의 이중화와 확장은 AWS가 맡습니다. 요금은 켜 둔 시간과 처리량으로 붙습니다.

ELB에는 종류가 여럿 있고, 가장 큰 갈림길은 2장의 L4와 L7 구분 그대로입니다. 다음 슬라이드에서 두 대표 제품의 동작 차이부터 봅니다.

ALB는 요청을 읽고, NLB는 연결을 넘긴다

ALB는 L7 로드 밸런서입니다. 클라이언트와 TCP 연결을 끝내고 HTTP 요청을 읽은 뒤, 경로나 도메인을 보고 대상을 골라 대상과 새 연결을 맺습니다.

NLB는 L4입니다. 요청을 읽지 않고, 프로토콜과 출발지·목적지 IP·포트(1부의 5-튜플)를 해시해 대상을 고른 뒤 그 연결의 패킷을 계속 같은 대상으로 넘깁니다. 이를 흐름 해시라고 합니다.

ELB는 계층과 용도에 따라 네 종류다

여기에 L3 장치인 GWLB가 더해집니다. 요청이나 연결이 아니라 IP 패킷 자체를 받아 방화벽 같은 보안 장비로 돌려보내는 로드 밸런서로, 3부 뒤쪽에서 봅니다.

항목ALBNLBGWLB
계층L7: HTTP, HTTPS, gRPCL4: TCP, UDP, TLSL3: 모든 IP 패킷
대상 고르는 기준호스트, 경로, 헤더 등흐름 해시흐름 해시
IP 주소바뀜, DNS 이름으로 접근AZ별 고정, EIP 가능사설 엔드포인트
대표 용도웹, REST API비 HTTP, 고정 IP, PrivateLink보안 장비 삽입

네 번째인 CLB(Classic Load Balancer)는 L4와 L7을 어설프게 겸하던 1세대 제품으로, 새로 만들 이유가 없는 레거시입니다. 남아 있다면 ALB나 NLB로 옮깁니다. shop의 주문 API는 HTTP API이므로 ALB를 씁니다.

로드 밸런서는 AZ마다 노드를 둔다

ALB는 장비 한 대가 아닙니다. 만들 때 AZ마다 Public 서브넷을 하나씩 고르면, 그 서브넷마다 로드 밸런서 노드가 생깁니다. 1부 그림의 "ALB 노드" 두 개가 이것이고, 노드마다 서브넷의 IP를 차지하는 ENI를 가집니다.

클라이언트는 노드 IP를 직접 알지 못합니다. ALB에 붙는 DNS 이름(shop-alb-123.ap-northeast-2.elb.amazonaws.com)을 조회하면 노드들의 IP 목록이 돌아오고, 그중 하나로 접속합니다.

트래픽이 늘면 AWS가 노드를 더 큰 것으로 바꾸거나 수를 늘리고, DNS 응답을 새 IP로 바꿉니다. 그래서 로드 밸런서 서브넷에는 확장용 여유 IP가 최소 8개 필요하고, AWS는 /27 이상의 서브넷을 권합니다.

이 구조에서 바로 다음 슬라이드의 결론이 나옵니다. ALB의 IP는 언제든 바뀐다는 것입니다.

ALB의 IP는 바뀌므로 이름으로 찾는다

ALB DNS 레코드의 TTL(2장: 리졸버가 답을 캐시해도 되는 시간)은 60초입니다. 노드가 바뀌면 1분 안에 새 IP가 퍼지도록 짧게 둔 것입니다. 거꾸로 말하면 오늘의 ALB IP가 내일도 같다는 보장이 없습니다.

그래서 두 가지를 하면 안 됩니다. 사내 방화벽이나 파트너사 허용 목록에 ALB IP를 고정 등록하는 것, 그리고 앱이 DNS 결과를 영원히 캐시하는 것입니다. 둘 다 어느 날 갑자기 멀쩡하던 연결이 실패하는 장애로 돌아옵니다(5부에서 JVM 사례를 봅니다).

고정 IP가 꼭 필요하면 AZ마다 고정 IP를 갖는 NLB를 쓰거나, 전 세계에 고정 IP 두 개를 내주고 AWS 망으로 트래픽을 끌어오는 Global Accelerator(16장)를 앞에 둡니다. 이제 ALB 안으로 들어가 요청이 어떻게 처리되는지 봅니다.

요청은 리스너, 규칙, 대상 그룹 순으로 흐른다

  1. 클라이언트DNS로 노드 IP 획득
  2. 리스너:443, TLS 종료
  3. 규칙우선순위 순으로 평가
  4. 대상 그룹건강한 대상만 후보
  5. 대상주문 API 서버

리스너는 "어느 포트, 어느 프로토콜로 받는가"입니다. shop은 443(HTTPS)과 80(HTTP) 리스너를 둡니다. 리스너마다 규칙 목록이 있어 우선순위 번호가 낮은 것부터 조건을 맞춰 보고, 처음 맞은 규칙의 동작(액션)을 실행합니다. 아무것도 맞지 않으면 지울 수 없는 기본 규칙이 처리합니다.

대상 그룹은 같은 일을 하는 서버 묶음입니다. shop의 주문 API 네 대가 tg-order 하나를 이룹니다. 다음 슬라이드부터 이 세 부품을 하나씩 들여다봅니다.

대상 그룹은 서버 묶음이자 분배 단위다

대상 그룹에는 서버 목록만 있는 것이 아니라, 그 서버들에 요청을 보내는 방식이 함께 담깁니다. 대상이 받는 포트와 프로토콜(HTTP:8080), 뒤에서 볼 헬스 체크, 그리고 분배 알고리즘이 모두 대상 그룹마다 따로 정해집니다.

그래서 서비스가 여럿이면 대상 그룹도 여럿입니다. shop이 주문 API 외에 상품 API를 같은 ALB 뒤에 둔다면 tg-order와 tg-product를 만들고, 규칙이 요청을 둘 중 하나로 보냅니다.

분배 알고리즘의 기본은 8장의 라운드 로빈, 순서대로 한 대씩입니다. 요청마다 처리 시간이 크게 다르면 8장에서 본 대로 느린 요청이 운 나쁜 서버에 쌓입니다. 이때 고르는 것이 최소 미처리 요청입니다. 8장의 최소 연결과 같은 발상으로, 아직 응답하지 않은 요청이 가장 적은 서버에 보냅니다.

shop의 주문 API는 대부분 수십 ms지만 결제 승인 요청은 PG사 응답을 기다리느라 수 초가 걸립니다. 이런 편차가 있으면 최소 미처리 요청이 더 고르게 나눕니다. 다만 뒤에서 볼 slow start와는 함께 쓸 수 없다는 제약이 있습니다.

ALB 규칙은 여섯 가지 조건으로 요청을 고른다

규칙의 조건은 HTTP 요청의 어느 부분을 볼지 정합니다. ALB가 요청을 읽는 L7이기에 가능한 일입니다.

조건shop 예시쓰임
host-headeradmin.example.com도메인별 서비스 분리
path-pattern/orders/*경로별 서비스 라우팅
http-headerX-Canary: true테스트 트래픽 분리
http-request-methodGET읽기/쓰기 분리
query-stringversion=v2버전 분기
source-ip192.168.0.0/16사내망만 관리자 경로

한 규칙에 조건을 여럿 넣으면 모두 맞아야 하고(AND), 조건 하나에 값을 여럿 넣으면 하나만 맞아도 됩니다(OR). 와일드카드 *, ?를 쓸 수 있습니다. source-ip는 헤더가 아니라 ALB에 실제로 접속한 IP를 봅니다. ALB 하나당 규칙은 기본 100개입니다.

액션은 전달, 리다이렉트, 고정 응답, 인증이다

$ aws elbv2 create-rule --listener-arn $L443 \
  --priority 10 \
  --conditions Field=path-pattern,Values='/orders/*' \
  --actions Type=forward,TargetGroupArn=$TG_ORDER

$ aws elbv2 create-listener --load-balancer-arn $ALB \
  --protocol HTTP --port 80 \
  --default-actions 'Type=redirect,RedirectConfig='\
'{Protocol=HTTPS,Port=443,StatusCode=HTTP_301}'

첫 명령은 443 리스너에 우선순위 10번 규칙을 넣습니다. 경로가 /orders/로 시작하면(--conditions) forward, 즉 tg-order로 보냅니다(--actions).

둘째 명령은 80 리스너를 만들면서 기본 동작을 redirect로 둡니다. ALB가 "HTTPS 443으로 가라"는 301을 직접 답해 모든 HTTP 요청을 HTTPS로 돌립니다.

fixed-response는 서버를 거치지 않고 ALB가 정해진 응답을 줍니다. 점검 중 503 페이지에 씁니다. authenticate는 뒤에서 봅니다.

가중치 대상 그룹으로 트래픽을 비율대로 나눈다

{
  "Type": "forward",
  "ForwardConfig": {
    "TargetGroups": [
      { "TargetGroupArn": "...tg-order-v1", "Weight": 90 },
      { "TargetGroupArn": "...tg-order-v2", "Weight": 10 }
    ],
    "TargetGroupStickinessConfig": {
      "Enabled": true, "DurationSeconds": 3600
    }
  }
}

forward 액션에는 대상 그룹을 여러 개 넣고 가중치를 줄 수 있습니다. 위 설정은 주문 API v1에 90%, 새 버전 v2에 10%를 보냅니다. 11장의 Canary, 즉 새 버전을 일부에게 먼저 내보내는 배포를 서버 대수와 상관없이 정확한 비율로 할 수 있습니다.

아래의 대상 그룹 단위 고정을 켜면 한 사용자는 1시간(3600초) 동안 같은 버전에만 머뭅니다. 화면을 넘길 때마다 버전이 바뀌는 혼란을 막습니다.

대상은 인스턴스, IP, 함수 중 하나로 등록한다

대상 유형등록하는 것어울리는 곳
instance인스턴스 ID(기본 ENI로 전달)EC2와 Auto Scaling
ip사설 IP와 포트컨테이너, 사내 서버
lambda함수 하나가벼운 HTTP 엔드포인트

shop의 주문 API가 EC2 위에서 돈다면 instance 유형이 자연스럽습니다. 컨테이너로 옮기면 사정이 달라집니다. AWS의 컨테이너 서비스 ECS와 EKS(14장)에서는 컨테이너 묶음(ECS의 태스크, Kubernetes의 Pod)마다 자기 VPC IP를 받으므로, ip 유형으로 그 IP를 직접 등록해 ALB가 서버를 거치지 않고 컨테이너로 바로 보냅니다.

ip 유형은 Peering이나 VPN 너머의 사설 IP도 등록할 수 있어, 데이터 센터의 서버를 같은 ALB 뒤에 섞어 두고 옮기는 이전 작업에도 씁니다. lambda 유형은 ALB가 HTTP 요청을 JSON 이벤트로 바꿔 함수를 호출합니다(17장).

헬스 체크는 다섯 숫자로 동작이 정해진다

대상 그룹은 대상마다 주기적으로 요청을 보내 살아 있는지 확인하고, 정상인 대상에만 요청을 보냅니다. 이것이 헬스 체크입니다.

설정ALB 기본값범위
간격30초5~300초
타임아웃5초2~120초
정상 임계값연속 5회2~10
비정상 임계값연속 2회2~10
성공 코드200200~499

기본값으로 계산하면 죽은 서버는 30초 × 2회, 약 1분 안에 빠지지만 살아난 서버는 30초 × 5회, 2분 30초가 지나야 돌아옵니다. 빼는 것은 빠르게, 넣는 것은 신중하게 한 설계입니다.

빨리 빼고 싶으면 간격을 10초로 줄입니다. 다만 대상이 많으면 헬스 체크 요청 자체가 부하가 되므로, 경로는 DB를 건드리지 않는 가벼운 /health로 둡니다. 왜 DB를 건드리면 안 되는지가 다음 슬라이드입니다.

모든 대상이 비정상이면 ALB는 전부에 보낸다

대상 그룹의 모든 대상이 비정상으로 판정되면, ALB는 요청을 버리는 대신 비정상 대상 전부에게 계속 보냅니다. 이를 페일 오픈이라고 합니다.

모두가 동시에 죽는 것보다 헬스 체크가 틀렸을 가능성, 예를 들어 헬스 체크 경로만 고장 난 경우가 더 흔하다고 보는 설계입니다. 서비스가 실제로는 살아 있다면 사용자는 계속 응답을 받습니다.

헬스 체크에 DB 확인을 넣지 마세요

shop의 MySQL이 잠깐 느려지면 주문 API 네 대가 동시에 비정상이 됩니다. Auto Scaling이 이 판정을 쓰고 있다면 멀쩡한 서버를 전부 교체하기 시작합니다. DB 상태는 별도 지표로 봅니다.

등록 해제 지연은 진행 중인 요청을 기다린다

배포로 주문 API 한 대가 빠질 때, 그 순간 처리 중이던 결제 요청이 끊기면 안 됩니다. 그래서 ALB는 빠지는 대상에 새 요청은 보내지 않고 진행 중인 요청이 끝나기를 기다립니다. 이 상태를 draining이라 하고, 기본 대기 시간(등록 해제 지연)은 300초입니다.

진행 중인 요청이 없으면 더 기다리지 않고 바로 끝냅니다. 반대로 대기 중에 서버가 먼저 연결을 끊으면 사용자는 5xx를 받습니다.

값은 앱의 가장 긴 요청에 맞춥니다. 요청이 수 초인 API라면 30~60초로 줄여 배포를 빠르게 하고, 큰 파일 업로드가 있다면 늘립니다.

앱 쪽 종료 대기는 이 값보다 길게 둡니다. 10장에서 Pod가 종료 신호(SIGTERM)를 받기 전에 preStop으로 기다리게 한 것, 11장에서 Spring Boot가 SIGTERM을 받으면 진행 중인 요청을 마무리하고 떠나게(graceful shutdown) 한 것과 같은 이유입니다. ALB가 손을 뗀 뒤에 앱이 닫혀야 끊기는 요청이 없습니다.

slow start는 막 뜬 서버를 천천히 데운다

반대 방향의 문제도 있습니다. 새 대상이 헬스 체크를 통과하면 기본적으로 즉시 자기 몫의 요청을 다 받습니다. 그런데 막 뜬 JVM은 5장에서 본 대로 아직 JIT 컴파일 전이라 느리고, 커넥션 풀과 로컬 캐시도 비어 있습니다. 이때 몰린 요청이 타임아웃을 만듭니다.

slow start를 30~900초로 켜면, 그 시간 동안 ALB가 새 대상에 보내는 요청량을 0에서 선형으로 늘립니다. JIT 워밍업 시간을 로드 밸런서가 벌어 주는 셈입니다.

제약도 있습니다. 대상 그룹에 이미 정상 대상이 하나는 있어야 적용되고(모두 새 대상이면 나눌 곳이 없으니까), 앞에서 본 최소 미처리 요청 알고리즘과는 함께 쓸 수 없습니다.

스티키 세션은 쿠키로 같은 서버에 묶는다

8장에서 본 Sticky Session, 즉 같은 사용자를 계속 같은 서버로 보내는 기능을 ALB는 쿠키로 구현합니다. 기간 기반은 ALB가 직접 만든 AWSALB 쿠키를 보고, 애플리케이션 기반은 앱이 정한 쿠키 이름을 보고 같은 대상으로 보냅니다.

유지 시간은 1초에서 7일까지, 기본 1일입니다. 기능 자체는 기본으로 꺼져 있습니다.

고정은 부하 불균형을 낳는다

새로 추가된 서버는 기존 사용자를 받지 못해 놀고, 서버가 죽으면 그 사용자 세션은 사라집니다. 8장처럼 세션을 Redis로 꺼내 두고 고정은 끄는 것이 기본입니다.

원래 요청은 X-Forwarded 헤더로 읽는다

GET /orders/42 HTTP/1.1
Host: api.example.com
X-Forwarded-For: 203.0.113.7
X-Forwarded-Proto: https
X-Forwarded-Port: 443
X-Amzn-Trace-Id: Root=1-67a1b2c3-...

ALB는 클라이언트와의 연결을 끝내고 서버와 새 연결을 맺으므로, 주문 API가 보는 출발지 IP는 ALB 노드의 사설 IP입니다. 그래서 2장의 리버스 프록시처럼 원래 IP를 X-Forwarded-For에, HTTPS였는지를 -Proto에 담아 줍니다. X-Amzn-Trace-Id는 요청마다 붙는 추적 ID입니다.

Spring에서는 server.forward-headers-strategy로 이 헤더를 믿게 해야 리다이렉트 URL이 http로 잘못 만들어지지 않습니다. 헤더는 클라이언트가 위조할 수 있으니 ALB 뒤에서만 믿습니다.

shop의 사내 관리 도구처럼 로그인 기능이 없는 앱을 회사 SSO 뒤에 둘 때 유용합니다. 앱은 헤더에 담긴 서명된 사용자 정보를 검증해 씁니다.

NLB는 고정 IP와 낮은 지연이 필요할 때 쓴다

이제 L4 쪽을 봅니다. NLB는 요청을 읽지 않으므로 경로별 라우팅 같은 똑똑한 일은 못 합니다. 대신 ALB가 못 하는 것을 합니다.

첫째, AZ마다 고정 IP를 갖고, 원하면 그 자리에 내 EIP를 지정합니다. 파트너사가 방화벽에 등록할 고정 IP를 요구하면 NLB가 답입니다. 둘째, HTTP가 아닌 프로토콜(DB 프로토콜, 게임 서버의 UDP, MQTT 같은 메시지 프로토콜)을 나눌 수 있습니다.

셋째, 연결을 끊고 다시 맺지 않으므로 지연이 매우 낮고, 초당 수백만 연결까지 확장됩니다. 넷째, 2부에서 본 대로 PrivateLink 엔드포인트 서비스는 NLB(또는 GWLB) 뒤에만 만들 수 있습니다. 회원 팀이 NLB를 둔 이유입니다.

대상 그룹, 헬스 체크, 등록 해제 지연 같은 부품은 ALB와 같습니다. 달라지는 지점은 셋입니다. 서버가 보는 출발지 IP, TLS를 어디서 푸는가, 그리고 쉬는 연결을 언제 잊는가입니다. 차례로 봅니다.

NLB는 클라이언트 IP를 그대로 전달할 수 있다

ALB와 달리 NLB는 패킷의 출발지 IP를 클라이언트 IP 그대로 둘 수 있습니다. 이 클라이언트 IP 보존은 instance 유형 대상에서 기본으로 켜져 있고, ip 유형의 TCP·TLS 대상에서는 기본으로 꺼져 있습니다.

꺼져 있을 때 원래 IP가 필요하면 Proxy Protocol v2를 켭니다. NLB가 연결 맨 앞에 "원래 출발지는 이 IP:포트"라는 작은 이진 헤더를 붙여 보내고, 앱(또는 Nginx)이 그걸 읽습니다.

보존이 켜져 있으면 대상의 보안 그룹은 클라이언트 IP 기준으로 열려 있어야 합니다. NLB의 IP만 열어 두면 막힙니다.

NLB도 2023년부터 보안 그룹을 지원합니다. 대상 보안 그룹의 출발지를 NLB 보안 그룹으로 지정하면 클라이언트 IP 보존과 관계없이 NLB를 거친 트래픽만 받습니다. 단, 보안 그룹은 NLB를 만들 때 붙여야 하고 나중에 처음 붙일 수는 없습니다.

NLB의 TLS는 넘기거나 풀거나 둘 중 하나다

443으로 오는 HTTPS를 NLB로 받는 방법은 둘입니다. TCP 리스너(패스스루)로 받으면 NLB는 암호문을 그대로 대상에 넘기고, 대상이 직접 TLS를 처리합니다. 인증서 관리는 서버 몫이지만 종단 간 암호화가 유지됩니다.

클라이언트도 인증서를 내밀어 서로를 확인하는 mTLS를 서버가 직접 검증해야 할 때 이 방식을 씁니다. 클라이언트 인증서가 서버까지 그대로 닿기 때문입니다.

TLS 리스너(종료)로 받으면 NLB가 인증서로 TLS를 풀고 대상에 평문이나 새 TLS로 보냅니다. 인증서는 AWS의 인증서 발급·관리 서비스인 ACM(16장)에서 받아 붙입니다. 서버는 TLS 연산과 인증서 갱신에서 벗어납니다.

어느 쪽이든 NLB는 HTTP를 읽지 않으므로 경로 라우팅이나 X-Forwarded-For는 없습니다.

NLB는 350초 쉬는 연결을 잊는다

NLB는 흐름마다 "이 연결은 이 대상으로"를 기억해야 같은 대상으로 계속 보낼 수 있습니다. 그런데 기억을 무한히 들고 있을 수는 없어서, 일정 시간 아무 데이터도 오가지 않은 흐름은 지웁니다. 이 시간이 유휴 타임아웃입니다.

TCP 흐름은 기본 350초(60~6,000초로 변경 가능), TLS 리스너는 350초 고정, UDP는 120초입니다. 흐름이 지워진 뒤에 보낸 패킷은 NLB가 어느 대상의 것인지 모르므로 2장의 RST(연결 강제 종료)가 돌아옵니다.

그래서 NLB 뒤에서 오래 쉬는 DB 커넥션 풀이 갑자기 끊깁니다. 앱은 연결이 살아 있다고 믿고 쿼리를 보냈다가 RST를 받습니다. TCP keepalive(빈 패킷을 주기적으로 보내 연결이 살아 있음을 알리는 기능)를 350초보다 짧게 두거나, 4장의 커넥션 풀 maxLifetime을 그보다 짧게 둡니다.

GWLB는 보안 장비를 트래픽 경로에 끼워 넣는다

회사 정책상 모든 트래픽이 방화벽이나 침입 탐지 시스템(IDS) 같은 다른 회사의 보안 장비를 지나야 할 때가 있습니다. 장비를 한 대만 두면 단일 장애점이 되고, 여러 대를 두면 한 연결의 가는 패킷과 오는 패킷이 같은 장비를 지나도록 맞추기 어렵습니다. 연결 상태를 보는 방화벽은 한쪽만 보면 오작동합니다.

GWLB는 L3에서 모든 IP 패킷을 받아, 원래 패킷을 통째로 감싸는 터널 형식인 GENEVE(포트 6081)에 담아 장비로 보내고, 흐름마다 같은 장비를 유지합니다. 장비는 검사한 패킷을 GWLB로 돌려보내고, 패킷은 원래 목적지로 갑니다.

다른 VPC에서는 GWLB 엔드포인트를 라우팅 테이블의 타깃으로 지정해 트래픽을 끌어옵니다. 1부의 라우팅으로 "지나가는 길에 검문소를 세우는" 구조입니다. 직접 운영하기보다 보안 팀의 검사 전용 VPC 설계에서 만나는 경우가 많습니다.

Cross-Zone은 AZ 간 불균형을 지운다

앞에서 클라이언트는 DNS로 노드 IP 중 하나를 받는다고 했습니다. 그래서 트래픽은 먼저 AZ별 노드에 대략 반씩 나뉩니다. Cross-Zone이 꺼져 있으면 각 노드는 자기 AZ의 대상에만 보냅니다.

AZ a에 2대, c에 8대라면 a의 서버는 각각 25%, c의 서버는 6.25%를 받습니다. 켜면 노드가 AZ를 넘어 보내므로 열 대가 10%씩입니다. ALB는 항상 켜져 있고(대상 그룹에서 끌 수 있음), NLB와 GWLB는 꺼진 것이 기본입니다.

NLB Cross-Zone은 요금과 격리의 문제다

NLB가 Cross-Zone을 기본으로 끄는 데는 이유가 있습니다. 켜면 노드가 다른 AZ의 대상으로 패킷을 보내고, NLB에서는 이 AZ 간 데이터 전송에 요금이 붙습니다(ALB는 붙지 않습니다). 또 끈 상태에서는 한 AZ의 문제가 다른 AZ로 번지지 않는 격리 효과가 있습니다.

끈 채로 쓴다면 AZ마다 대상 수를 같게 유지하는 것이 핵심입니다. Auto Scaling의 AZ 균형 기능(14장)이 이 일을 돕습니다. 반대로 대상 수가 적거나 AZ별로 들쭉날쭉한 환경이라면 켜서 균등 분배를 얻는 편이 낫습니다.

어느 쪽이든 "한 AZ의 대상이 모두 빠지면 그 AZ의 노드는 어디로 보내는가"를 확인해 둡니다. Cross-Zone이 꺼진 NLB는 그 경우 DNS 응답에서 해당 AZ의 노드 IP를 뺍니다.

TLS는 로드 밸런서에서 끝낸다

shop의 443 리스너에 ACM 인증서를 붙이면 ALB가 TLS 종료, 즉 암호를 풀어 평문 HTTP로 바꾸는 일을 맡고, 주문 API는 VPC 안에서 8080 HTTP로 받습니다. 2장의 TLS 핸드셰이크 비용과 인증서 갱신을 로드 밸런서가 대신 집니다. ACM 공개 인증서는 무료이고, DNS 검증을 해 두면 자동 갱신됩니다.

규정상 VPC 안 구간도 암호화해야 하면 대상 그룹 프로토콜을 HTTPS로 둡니다. ALB는 대상의 인증서를 검증하지 않으므로 서버에는 자체 서명 인증서를 써도 됩니다.

shop은 api.example.com과 admin.example.com을 ALB 하나로 받습니다. 그런데 TLS는 HTTP보다 먼저 맺어지니 Host 헤더로는 어느 인증서를 줄지 모릅니다. 그래서 클라이언트가 TLS 첫 메시지에 접속할 도메인을 적어 보내는 SNI를 쓰고, ALB는 이를 보고 인증서를 고릅니다.

리스너의 보안 정책은 허용할 TLS 버전과 암호 스위트(키 교환·암호화 알고리즘 조합)를 정합니다. 최신 권장 정책은 TLS 1.2 이상만 받습니다.

4부

사용자는 IP가 아니라 이름으로 찾아온다

3부의 ALB에는 길고 바뀌는 DNS 이름만 있습니다. 사용자가 api.example.com을 입력했을 때 그 이름이 어떻게 ALB까지 이어지는지, 그리고 서버가 죽거나 리전을 옮길 때 DNS의 답을 어떻게 바꾸는지를 봅니다.

도메인을 사는 일과 답을 주는 일은 다르다

  1. 리졸버재귀 조회 시작
  2. 루트 서버.com 담당을 알려 줌
  3. .com 서버등록된 NS를 알려 줌
  4. Route 53호스팅 영역이 답함

2장에서 리졸버가 루트, TLD(.com), 권한 네임서버 순으로 물어 내려간다고 했습니다. Route 53은 이 중 권한 네임서버를 AWS가 대신 운영해 주는 서비스입니다(이름의 53은 DNS 포트 번호입니다).

여기서 두 가지 일이 구별됩니다. 도메인 등록은 example.com이라는 이름의 소유권을 등록 대행 업체(레지스트라)에서 사는 일입니다. 호스팅 영역은 그 도메인의 레코드를 담고 질의에 답하는 권한 네임서버 묶음입니다(영역당 월 0.50 USD). 다른 곳에서 산 도메인도 Route 53 영역을 쓸 수 있습니다.

NS 위임이 두 일을 잇는다

shop이 Route 53에 example.com 영역을 만들면 AWS가 이름 서버 4개(ns-123.awsdns-15.com처럼 awsdns-가 붙고 .com, .net, .org, .co.uk에 하나씩)를 배정합니다. 최상위 도메인 하나에 문제가 생겨도 나머지로 답하도록 나눠 둔 것입니다. 이 4개를 레지스트라에 등록하면, .com 서버가 "example.com은 이 4개에게 물어라"라고 답하게 됩니다. 이것이 NS 위임입니다.

위임이 없으면 Route 53에 레코드를 아무리 만들어도 인터넷의 리졸버는 그 영역까지 오지 않습니다.

이름 서버 4개가 서로 다른 최상위 도메인(.com, .net, .org, .co.uk)에 나뉘어 있는 것은, 한 최상위 도메인의 장애가 조회 전체를 막지 않게 하려는 설계입니다.

주의할 점이 하나 있습니다. 영역을 지우고 다시 만들면 배정되는 NS가 바뀌므로 레지스트라 설정도 고쳐야 합니다. 그 사이 도메인 전체가 조회되지 않습니다.

프라이빗 호스팅 영역은 VPC 안에서만 보인다

위의 영역은 인터넷 어디서나 조회되는 퍼블릭 호스팅 영역입니다. 프라이빗 호스팅 영역은 연결한 VPC의 리졸버에게만 답합니다. shop은 db.shop.internal을 만들어 주문 API가 DB를 IP 대신 이름으로 찾게 합니다. DB를 교체해도 레코드만 고치면 됩니다.

프라이빗 영역은 여러 VPC, 다른 계정의 VPC에도 연결할 수 있습니다. 1부의 DNS 속성 두 개가 켜져 있어야 동작합니다.

같은 이름으로 퍼블릭과 프라이빗 영역을 동시에 두는 split-horizon 구성도 가능합니다. VPC 안에서 api.example.com을 물으면 내부용 ALB 주소를, 밖에서 물으면 공개 ALB 주소를 받습니다.

이때 VPC 안에서는 프라이빗 영역이 우선하고, 프라이빗 영역에 없는 레코드는 퍼블릭 영역으로 넘어가지 않고 "없음"으로 실패합니다. 내부에서 필요한 레코드는 프라이빗 쪽에도 모두 만들어야 합니다.

SOA는 영역의 대표 정보로, "없는 이름"이라는 답을 얼마나 캐시할지(부정 응답 TTL)도 여기서 정합니다. NS와 SOA는 영역을 만들 때 자동으로 생깁니다. CAA에 Amazon을 빼먹으면 ACM 인증서 발급이 실패합니다.

영역 꼭대기에는 CNAME을 둘 수 없다

shop은 example.com 자체(www 없이)로 접속해도 ALB로 가게 하고 싶습니다. ALB는 IP가 바뀌므로 A 레코드에 IP를 적을 수 없고, 자연스러운 답은 "example.com은 shop-alb-123…elb.amazonaws.com의 별칭"이라는 CNAME입니다.

그런데 DNS 표준은 CNAME이 있는 이름에는 다른 레코드를 둘 수 없다고 정합니다. CNAME은 "이 이름에 대해서는 저쪽에 다시 물어라"라는 뜻이라, 같은 이름에 다른 답이 함께 있으면 모순이기 때문입니다. 그리고 영역의 꼭대기 이름(zone apex), 즉 example.com에는 앞에서 본 NS와 SOA가 반드시 있습니다.

그래서 www.example.com에는 CNAME을 쓸 수 있어도 example.com에는 쓸 수 없습니다. 이 막힌 자리를 푸는 Route 53만의 장치가 다음 슬라이드의 Alias입니다.

Alias는 AWS 리소스를 가리키는 A 레코드다

Alias는 겉으로는 A(또는 AAAA) 레코드지만, 값으로 IP 대신 ALB 같은 AWS 리소스를 지정합니다. 질의가 오면 Route 53이 내부에서 그 리소스의 현재 IP를 찾아 IP로 바로 답합니다. A 레코드이므로 꼭대기에도 둘 수 있고, ALB의 IP가 바뀌어도 자동으로 따라갑니다.

TTL은 바꿀 일을 앞두고 미리 줄인다

2장에서 TTL은 리졸버가 답을 캐시해도 되는 시간이라고 했습니다. 길면 조회가 줄어 빠르고 Route 53 요금도 줄지만, 레코드를 바꿨을 때 옛 답이 TTL만큼 남아 일부 사용자는 계속 옛 서버로 갑니다.

실무 규칙은 이렇습니다. 평소 자주 안 바뀌는 레코드는 3600초 이상, 뒤에서 볼 장애 조치나 가중치 이동에 쓰는 레코드는 60초 안팎으로 둡니다. 서버 이전처럼 계획된 변경은 며칠 전에 TTL을 60초로 낮추고, 기존 TTL이 다 지난 뒤에 값을 바꾸고, 안정되면 다시 올립니다.

ELB를 가리키는 Alias는 TTL을 정할 수 없고 ELB의 60초를 그대로 씁니다. 또 클라이언트 쪽 캐시는 TTL을 지키지 않을 수 있습니다. 이 함정은 5부 마지막에서 JVM 사례로 봅니다.

라우팅 정책은 같은 이름에 다른 답을 준다

지금까지 이름 하나에는 답 하나였습니다. 그런데 Route 53은 권한 네임서버라서 질의가 올 때마다 무엇을 답할지 직접 고를 수 있습니다. 같은 api.example.com에 레코드를 여러 개 만들어 두고, 규칙에 따라 그중 하나를 답하게 하는 것이 라우팅 정책입니다. 아무 정책도 고르지 않으면 정해진 값을 그대로 답하는 단순 정책입니다.

가중치 정책은 레코드마다 0~255의 가중치를 주고 그 비율로 답합니다. shop이 주문 API를 새 인프라로 옮길 때 새 ALB에 5%만 보내 보는 데 씁니다. 3부의 ALB 가중치와 달리 DNS 캐시 때문에 비율이 즉시, 정확히 맞지는 않습니다.

지연 시간 정책은 AWS가 측정한 "사용자 네트워크에서 각 리전까지의 지연"으로 가장 가까운 리전을 답합니다. shop이 서울과 도쿄에 같은 서비스를 띄운다면 일본 사용자는 도쿄로 갑니다.

장애 조치 정책은 기본(primary)과 보조(secondary) 레코드를 두고, 기본에 연결된 헬스 체크가 실패하면 보조를 답합니다. 보조는 다른 리전의 대기 환경이나 S3에 올린 점검 안내 페이지가 됩니다. 멀티 리전 재해 복구(DR) 전략 전체는 18장에서 봅니다.

이 세 가지가 가장 많이 쓰입니다. 나머지 정책은 다음 슬라이드에서 봅니다.

지리 위치는 규정에, 지리 근접은 분산에 쓴다

지리 위치 정책은 사용자가 어느 국가·대륙에 있는지로 답합니다. 위치는 질의한 리졸버의 IP로 추정하고, 리졸버가 사용자 대역 일부를 함께 보내 주는 확장(EDNS Client Subnet)이 있으면 그걸 씁니다. "EU 사용자는 EU 리전으로"처럼 데이터 규정이나 언어별 콘텐츠에 씁니다.

어디에도 해당하지 않는 위치를 위한 기본(Default) 레코드를 꼭 둡니다. 없으면 그 사용자는 답을 못 받습니다.

지리 근접은 리소스 위치까지의 거리로 고르고, 편향(bias) 값으로 한 리전이 맡는 영역을 넓히거나 줄입니다. IP 기반은 "이 통신사 대역은 이 엔드포인트로"를 CIDR로 직접 지정합니다.

다중 값 응답은 헬스 체크를 통과한 IP를 최대 8개 돌려줘, 클라이언트가 하나에 실패하면 다른 IP를 시도하게 합니다. 로드 밸런서를 대신하지는 못하는 보조 수단입니다.

여덟 정책은 답을 고르는 기준만 다르다

헬스 체크는 세계 여러 곳에서 함께 판정한다

3부의 ALB 헬스 체크는 VPC 안에서 서버를 봤습니다. Route 53의 엔드포인트 헬스 체크는 전 세계에 흩어진 Route 53 검사기가 인터넷 너머의 IP나 도메인에 HTTP, HTTPS, TCP로 요청합니다. 간격은 30초(표준) 또는 10초(빠른), 연속 실패 기준은 기본 3회입니다.

검사기 중 18%를 넘는 곳이 정상이라고 보면 정상입니다. 일부 지역의 네트워크 문제만으로 비정상 판정이 나지 않게 한 설계입니다.

계산된 헬스 체크는 다른 헬스 체크 여러 개를 묶어 "3개 중 2개 이상 정상이면 정상"처럼 판정합니다.

검사기는 인터넷에서 오므로 사설 IP를 직접 검사할 수 없습니다. 이때는 AWS의 지표가 기준을 넘으면 울리는 경보인 CloudWatch 알람(18장)을 만들고, 알람 기반 헬스 체크로 그 상태를 가져옵니다. 공개 엔드포인트라면 앞단 방화벽이 Route 53 검사기의 IP 대역을 허용해야 합니다.

DNS 장애 조치는 TTL과 캐시만큼 늦다

  1. 장애 발생

    서울 리전의 shop ALB가 응답하지 않습니다.

  2. 판정

    30초 간격 × 3회 실패, 약 1분 반 뒤 비정상.

  3. 응답 전환

    Route 53이 보조 레코드로 답하기 시작합니다.

  4. 캐시 만료

    리졸버와 클라이언트가 TTL 동안 옛 답을 씁니다.

  5. 복구

    새로 조회한 사용자부터 보조로 연결됩니다.

전체 전환 시간은 판정 시간 + TTL + 클라이언트 캐시입니다. 10초 간격과 TTL 60초로 줄이면 2분 안팎까지 당길 수 있습니다.

더 빨라야 하면 DNS를 바꾸지 않고 앞단의 고정 IP가 뒤의 목적지를 바꾸는 방식, 즉 3부에서 언급한 Global Accelerator(16장)를 검토합니다. 그리고 보조 쪽이 실제로 트래픽을 받을 준비가 됐는지를 평소에 시험해 둡니다.

DNSSEC은 DNS 응답에 서명을 붙인다

2장의 DNS 질의는 대개 UDP 한 번 오가는 것이라, 리졸버는 돌아온 답을 그대로 믿습니다. 공격자가 진짜 답보다 먼저 가짜 답을 끼워 넣으면 리졸버가 그 가짜를 캐시해 모든 사용자에게 퍼뜨립니다. 이를 캐시 포이즈닝이라고 합니다.

DNSSEC은 영역의 레코드에 디지털 서명을 붙이고, 상위 영역이 하위 영역의 공개 키를 보증하는 사슬로 검증하게 합니다. Route 53은 퍼블릭 호스팅 영역의 DNSSEC 서명을 지원합니다. 서명 키는 us-east-1에 있는 AWS 키 관리 서비스 KMS(16장)의 키로 만들고, 레지스트라에 그 키의 요약값인 DS 레코드를 등록해 상위 영역과 사슬을 잇습니다.

잘못 운영하면 도메인 전체가 조회 불능이 됩니다. KMS 키를 지우거나 비활성화하면 서명이 깨져 검증하는 리졸버가 모든 답을 거부하므로, 켜기 전에 키 관리와 되돌리는 절차를 먼저 정합니다.

5부

연결이 안 될 때, 5xx가 튈 때, 청구서가 클 때

1~4부에서 shop의 길을 다 깔았습니다. 이제 운영 중에 실제로 부딪히는 일을 봅니다. 설정은 맞는 것 같은데 통하지 않는 순간, 이유 없이 튀는 502와 504, 예상보다 큰 네트워크 요금, 조용히 바닥나는 IP, 그리고 장애 조치가 끝났는데도 복구되지 않는 앱입니다.

원리 실무 디버깅 순서, 로그 읽기, 비용 계산, 장애 사례를 다룹니다.

먼저 거부인지 타임아웃인지 가른다

$ nc -zv 10.10.21.9 3306
nc: connect to 10.10.21.9 port 3306
    (tcp) failed: Connection refused

$ nc -zv -w 5 10.10.21.9 3306
nc: connect to 10.10.21.9 port 3306
    (tcp) timed out

"주문 API가 DB에 붙지 못한다"는 신고가 왔습니다. 9장에서 본 nc -zv로 포트까지 TCP가 닿는지부터 봅니다. 결과는 둘 중 하나입니다.

거부(refused)는 2장의 RST가 돌아왔다는 뜻입니다. 패킷이 DB 서버까지 갔는데 그 포트에서 기다리는 프로세스가 없으니 네트워크는 정상이고, DB 프로세스를 봅니다.

타임아웃은 중간 어딘가에서 패킷이 아무 말 없이 버려진 것입니다. 보안 그룹과 NACL은 막을 때 응답을 보내지 않으므로, 이때 AWS 쪽 설정을 의심합니다.

타임아웃이면 패킷이 지나는 순서대로 본다

  1. 보안 그룹

    목적지 인바운드에 출발지(보안 그룹이나 CIDR)와 포트가 있나.

  2. NACL

    양쪽 서브넷에서 요청과 응답(임시 포트) 둘 다 허용되나.

  3. 라우팅

    출발 서브넷에 목적지 경로가, 돌아올 경로도 있나.

  4. 중계 장치

    IGW, NAT, 엔드포인트, TGW 연결이 살아 있나.

  5. DNS

    이름이 기대한 IP로 풀리나(dig로 확인).

순서는 실수 빈도와 확인 비용으로 정했습니다. 보안 그룹이 가장 흔한 원인이고 확인도 쉽습니다. NACL은 1부에서 본 대로 응답 방향을 잊는 실수가 잦습니다.

라우팅은 돌아오는 길을 놓치기 쉽습니다. Peering이나 TGW에서 한쪽 라우팅 테이블에만 경로를 넣으면 요청은 가는데 응답이 돌아오지 못해 역시 타임아웃이 됩니다. 마지막으로 이름이 엉뚱한 IP로 풀리는지 9장의 dig로 봅니다.

Reachability Analyzer는 설정을 읽는다

보안 그룹 수십 개와 TGW 라우팅을 사람이 눈으로 따라가기는 어렵습니다. Reachability Analyzer는 출발지와 목적지(인스턴스, ENI, IGW, TGW 등)와 포트를 주면, 실제 패킷을 보내지 않고 설정만 분석해 도달 가능 여부를 알려 줍니다.

도달 불가라면 "sg-db의 인바운드 규칙이 3306을 허용하지 않음"처럼 막힌 지점을 짚어 줍니다. 앞 슬라이드의 다섯 단계를 자동으로 따라가는 셈입니다.

설정을 보는 도구이므로 앱이 죽었거나 서버 운영체제의 방화벽(9장의 iptables)이 막은 경우는 잡지 못합니다. 그때는 다음 슬라이드의 Flow Logs로 실제 패킷의 흔적을 봅니다.

분석 한 번마다 요금이 붙지만 사람의 시간보다 훨씬 쌉니다. 보안 그룹이나 라우팅을 바꾼 뒤 "주문 API → DB 3306" 같은 핵심 경로를 검증하는 단계로 넣어 두기도 합니다.

Flow Logs는 허용과 거부를 한 줄씩 남긴다

ver acct     eni          src         dst
    sport dport proto pkts bytes start end 동작

2 1234... eni-0a1b 10.10.11.5 10.10.21.9
  41822 3306 6 12 1840 1731... 1731... ACCEPT OK
2 1234... eni-0a1b 10.10.12.7 10.10.21.9
  51210 3306 6 3 180 1731... 1731... REJECT OK

Flow Logs는 VPC, 서브넷, ENI 단위로 켜고 CloudWatch Logs나 S3에 쌓습니다. 패킷 내용은 없고 흐름마다 5-튜플(출발지·목적지 IP와 포트, 프로토콜 번호 6=TCP), 패킷 수, 바이트, 그리고 ACCEPT/REJECT가 남습니다.

둘째 줄은 AZ c의 주문 API(10.10.12.7)에서 DB로 가는 연결이 거부된 것입니다. 보안 그룹이 원인이면 요청이 거부되고, NACL이 원인이면 요청은 ACCEPT인데 응답이 REJECT로 남는 비대칭이 보입니다.

ELB의 5xx는 누가 만들었는지부터 가른다

이번에는 연결은 되는데 사용자가 5xx를 받는 경우입니다. 2장에서 본 대로 502, 503, 504는 앱이 아니라 앞단 프록시가 만든 응답입니다. 앱이 직접 500을 돌려준 것과는 원인을 찾을 곳이 다릅니다.

코드ALB가 본 상황먼저 볼 곳
502대상이 연결을 끊거나 깨진 응답앱 재시작, keep-alive 불일치
503보낼 정상 대상이 없음대상 그룹 비어 있음, 등록 누락
504유휴 타임아웃 안에 응답 없음느린 쿼리, 스레드 풀 고갈
대상 5xx앱이 직접 5xx를 반환앱 로그, 예외

CloudWatch 지표에서 HTTPCode_ELB_5XX_Count(ALB가 만든 것)와 HTTPCode_Target_5XX_Count(앱이 만든 것)를 나눠 보면 찾을 곳이 절반으로 줄어듭니다.

한가한 새벽에 튀는 502는 타임아웃 순서 문제다

shop에서 트래픽이 적은 새벽에만 502가 드문드문 생깁니다. 2장에서 본 keep-alive 경쟁이 ALB 뒤에서 그대로 일어난 것입니다. ALB는 주문 API와의 연결을 재사용하고, 그 연결의 유휴 타임아웃은 기본 60초(1~4,000초)입니다.

Tomcat의 keep-alive가 이보다 짧으면 Tomcat이 연결을 닫는 순간과 ALB가 그 연결을 재사용하는 순간이 엇갈려 502가 납니다. 한가할수록 쉬는 연결이 많아 더 자주 엇갈립니다. 그래서 AWS 문서도 앱의 유휴 타임아웃을 ALB보다 길게 두라고 권합니다.

server:
  tomcat:
    keep-alive-timeout: 75s
    connection-timeout: 20s
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 60s

keep-alive를 ALB의 60초보다 긴 75초로 둡니다. 아래 두 줄은 3부의 등록 해제 지연과 맞춘 종료 대기입니다.

504는 타임아웃을 늘리기 전에 원인을 본다

ALB에는 "응답 대기 시간"이라는 설정이 따로 없습니다. 요청을 보낸 뒤 대상이 유휴 타임아웃 동안 아무 바이트도 보내지 않으면 ALB는 504를 반환합니다. 그래서 shop의 매출 리포트 생성 API가 정확히 60초에 실패합니다.

유휴 타임아웃을 늘리면 증상은 사라지지만, 느린 요청이 연결과 스레드를 오래 붙잡아 다른 요청까지 밀리게 됩니다. 먼저 원인이 4장의 슬로 쿼리인지, 4장의 커넥션 풀 고갈인지, 6장의 Tomcat 스레드 풀 포화인지 봅니다.

정말 긴 작업이라면 동기 응답 대신 작업 ID를 바로 돌려주고 결과는 나중에 조회하게 바꿉니다. 작업은 메시지 큐(17장의 SQS)에 넣어 따로 처리합니다. 대용량 파일 업로드는 앱이 서명해 준 URL로 S3에 직접 올리게 해(15장의 Presigned URL) ALB를 아예 거치지 않게 합니다.

액세스 로그는 시간을 구간별로 쪼개 준다

https 2026-11-17T05:12:03.412Z app/shop-alb/...
203.0.113.7:51234 10.10.11.5:8080
0.001 59.998 -1 504 - 412 0
"POST https://api.example.com:443/reports HTTP/1.1"
... targetgroup/tg-order/... "Root=1-67a1..."

504가 어느 요청에서 났는지는 액세스 로그로 봅니다. 기본으로 꺼져 있고, 켜면 S3 버킷에 5분 단위로 쌓입니다. 강조한 줄의 세 숫자가 요청 처리, 대상 처리, 응답 처리 시간(초)이고, 대상이 응답하지 않으면 -1입니다.

위 줄은 주문 API가 60초 가까이 답하지 않아 504가 된 경우입니다. S3에 쌓인 로그 파일에 SQL로 질의하는 서비스 Athena로 대상 처리 시간이 긴 요청을 모으면 느린 경로가 드러나고, 끝의 추적 ID로 앱 로그와 연결합니다.

네트워크 요금은 경계를 넘을 때 붙는다

이번에는 청구서입니다. 12장에서 데이터 전송 요금은 방향과 경로에 따라 다르다고 했습니다. 이 장에서 본 장치들을 그 경로에 올려 보면 규칙이 하나로 모입니다.

경로요금(us-east-1 기준 예)
같은 AZ, 사설 IP무료
AZ 간방향마다 GB당 0.01 USD
NAT Gateway 경유GB당 0.045 USD 처리 요금 추가
인터넷으로 나감GB당 0.09 USD부터(구간별 할인)
인터넷에서 들어옴무료

단가는 리전마다 다르니 숫자보다 구조를 기억합니다. 트래픽이 AZ, NAT, 리전, 인터넷이라는 경계를 하나 넘을 때마다 요금이 붙습니다. 들어오는 것은 대부분 무료이고, 나가는 것과 중간 장치를 지나는 것이 비쌉니다.

NAT와 AZ 간 전송 비용은 이 순서로 줄인다

12장의 Cost Explorer에서 사용 유형 NatGateway-Bytes와 DataTransfer-Regional-Bytes(AZ 간 전송)가 크다면 이 두 경계가 문제입니다. Flow Logs로 NAT의 ENI를 지나는 상위 목적지를 뽑으면 대개 S3, ECR, 외부 SaaS 몇 곳이 대부분을 차지합니다.

그다음 2부의 엔드포인트로 돌립니다. S3·DynamoDB는 무료 게이트웨이 엔드포인트로, ECR·CloudWatch처럼 큰 트래픽은 인터페이스 엔드포인트(GB당 0.01 USD로 NAT보다 쌈)로 보냅니다.

AZ 간 전송은 구조로 줄입니다. 1부에서 본 대로 각 AZ가 같은 AZ의 NAT와 엔드포인트를 쓰게 하고, 읽기 트래픽이 많은 DB 복제본이나 캐시는 같은 AZ의 노드를 우선하게 합니다.

다만 AZ 간 전송을 없애려고 한 AZ로 몰면 고가용성을 잃습니다. 이 비용은 여러 AZ에 나눠 둔 대가로 받아들이고, 불필요하게 AZ를 오가는 부분만 걷어 냅니다.

IP 고갈은 서브넷이 조용히 꽉 차며 시작된다

서브넷의 남은 IP가 0이 되면 새 인스턴스, VPC에 연결된 Lambda의 ENI, 로드 밸런서 노드 확장이 모두 실패합니다. 오류는 InsufficientFreeAddressesInSubnet처럼 나오지만, 사람이 보는 증상은 "배포가 안 된다", "서버가 늘지 않는다"입니다.

1부에서 예고한 EKS가 대표적입니다. Pod마다 VPC IP를 주고, Pod를 빨리 띄우려고 노드마다 여분 IP를 미리 확보해 둡니다. Pod 수보다 훨씬 많은 IP가 묶입니다.

대응은 세 단계입니다. 서브넷별 남은 IP를 지표로 감시합니다. VPC의 주소 사용 현황을 모아 보여 주는 IPAM(IP 주소 관리) 기능을 쓰면 여러 VPC를 한눈에 봅니다.

부족하면 VPC에 1부의 보조 CIDR을 붙여 Pod 전용 서브넷을 만듭니다. 이때 흔히 100.64.0.0/10 안의 대역을 씁니다. 통신사 NAT용으로 따로 정해 둔 대역이라 사내망의 RFC 1918 대역과 겹칠 일이 적기 때문입니다. EKS 쪽 설정은 14장에서 다룹니다.

대규모 이벤트 전에는 로드 밸런서도 데워 둔다

shop이 블랙 프라이데이 특가를 0시에 연다고 합시다. ALB는 트래픽에 맞춰 자동 확장되지만 확장에는 시간이 걸립니다. 평소 초당 1,000 요청(RPS)인 서비스에 판매 시작 순간 수십 배가 몰리면, 확장이 따라오기 전 몇 분 동안 503이나 지연이 생길 수 있습니다.

AWS는 ALB의 사용량을 LCU(로드 밸런서 용량 단위)로 셉니다. 초당 새 연결 수, 분당 활성 연결 수, 처리 바이트, 규칙 평가 수 네 차원을 각각 LCU로 환산해 가장 큰 값으로 과금합니다. LCU 예약은 이 용량의 최소치를 미리 잡아 두는 기능으로, 그 아래로는 줄어들지 않습니다.

예약은 최소 100 LCU부터이고, 필요량은 지난 이벤트의 PeakLCUs 지표나 부하 테스트로 정합니다. 예약한 만큼은 쓰지 않아도 과금되니 이벤트가 끝나면 해제합니다.

로드 밸런서만 데우면 소용없습니다. 뒤의 Auto Scaling 최소 서버 수, DB 커넥션, PG사 API 호출 한도, 1부의 NAT 포트 한도까지 경로 전체를 같은 기준으로 미리 올려 둡니다.

장애 조치 뒤에도 앱이 옛 IP를 붙잡고 있다면

4부에서 Route 53이 장애 조치로 답을 바꿔도, 앱이 옛 IP를 계속 쓰면 복구되지 않는다고 했습니다. 대표 원인이 JVM의 DNS 캐시입니다. JVM은 조회 결과를 자체적으로 캐시하는데, 보안 관리자(Security Manager, JVM 안에서 코드 권한을 제한하는 오래된 장치)가 켜진 환경에서는 성공한 조회를 영원히 캐시합니다.

또 커넥션 풀이 이미 맺어 둔 연결은 DNS와 관계없이 옛 서버를 향합니다.

그래서 JVM에는 DNS 캐시 시간을 정하는 보안 속성 networkaddress.cache.ttl을 60초 이하로 명시합니다. AWS SDK 문서도 이 설정을 권합니다.

커넥션 풀은 4장의 연결 최대 수명(maxLifetime)과 검증으로 옛 연결을 주기적으로 버리게 합니다. 이 패턴이 DB 장애 조치에서 어떻게 나타나는지는 15장 RDS에서 이어 봅니다.

정리

  • VPC는 리전, 서브넷은 AZ에 묶입니다. Public, Private, Isolated는 기본 경로 한 줄로 갈리고, NAT도 AZ별로 둡니다.
  • 보안 그룹은 상태를 기억하고, NACL은 기억하지 않습니다. 길과 허가는 따로 정하며, 보안 그룹 참조 사슬이 주 방어선입니다.
  • VPC 밖과 잇는 길은 상대마다 다릅니다. AWS 서비스는 엔드포인트, 서비스 하나는 PrivateLink, 여러 VPC와 사내망은 TGW입니다.
  • ALB는 요청을 읽고, NLB는 흐름을 넘깁니다. 헬스 체크와 타임아웃 숫자를 앱의 동작에 맞춰야 5xx가 사라집니다.
  • Route 53은 같은 이름에 상황별로 다른 답을 줍니다. 헬스 체크, TTL, 클라이언트 캐시가 DNS 장애 조치의 속도를 정합니다.
  • 요금은 경계를 넘을 때 붙습니다. AZ, NAT, 인터넷을 넘는 트래픽을 찾아 엔드포인트로 돌립니다.

스스로 점검 (1)

  1. Private 서브넷의 서버에 퍼블릭 IP를 붙이면 인터넷에서 접속할 수 있나요?

    아닙니다. 그 서브넷의 기본 경로가 NAT로 가므로 응답이 IGW로 돌아가지 못합니다. 들어오는 연결에는 IGW로 가는 경로가 필요합니다.

  2. AZ 두 곳이 NAT Gateway 하나를 같이 쓰면 무엇이 문제인가요?

    NAT가 있는 AZ가 장애 나면 다른 AZ의 서버도 밖으로 나가지 못하고, 평소에도 AZ 간 전송 요금이 붙습니다.

  3. NACL에 인바운드 443만 허용했더니 웹 요청이 타임아웃됩니다. 왜일까요?

    NACL은 상태를 기억하지 않으므로, 클라이언트 임시 포트로 나가는 응답이 아웃바운드에서 막힙니다. 아웃바운드 1024–65535 허용이 필요합니다.

스스로 점검 (2)

  1. VPC A–B, B–C가 Peering으로 이어져 있을 때 A에서 C로 갈 수 있나요?

    갈 수 없습니다. Peering은 두 VPC 사이 패킷만 나르고 전이되지 않으므로 A–C를 직접 잇거나 Transit Gateway로 묶어야 합니다.

  2. Isolated 서브넷의 서버가 Secrets Manager를 쓰려면 무엇이 필요한가요?

    Secrets Manager 인터페이스 엔드포인트와 프라이빗 DNS, 엔드포인트 보안 그룹의 443 허용입니다. VPC의 DNS 속성 두 개도 켜져 있어야 합니다.

  3. 모든 서버가 외부 API 한 곳만 세게 부르자 NAT에서 새 연결이 실패합니다. 왜일까요?

    목적지가 같으면 바뀔 수 있는 것은 NAT의 출발지 포트뿐이라 IP 하나당 동시 연결 55,000개에서 막힙니다. NAT에 IP를 추가하거나 keep-alive로 연결 수를 줄입니다.

스스로 점검 (3)

  1. 트래픽이 적은 새벽에만 ALB 502가 간헐적으로 생깁니다. 무엇을 의심하나요?

    앱의 keep-alive 타임아웃이 ALB 유휴 타임아웃(60초)보다 짧은 경우입니다. 앱 쪽을 ALB보다 길게 둡니다.

  2. 파트너사가 방화벽에 등록할 고정 IP를 요구합니다. ALB만으로 될까요?

    ALB 노드 IP는 확장 때마다 바뀌므로 안 됩니다. EIP를 붙인 NLB를 앞에 두거나 Global Accelerator의 고정 IP를 씁니다.

  3. example.com 자체를 ALB로 보내려면 CNAME과 Alias 중 무엇을 쓰나요?

    Alias입니다. 영역 꼭대기에는 NS와 SOA가 있어 CNAME을 둘 수 없고, Alias는 A 레코드로 답하며 AWS 리소스 대상 조회는 무료입니다.

  4. Route 53 장애 조치를 설정했는데 전환에 10분 넘게 걸렸습니다. 어디를 보나요?

    헬스 체크 간격과 실패 횟수, 레코드 TTL, 그리고 JVM DNS 캐시처럼 TTL을 무시하는 클라이언트 캐시와 오래된 커넥션을 차례로 봅니다.
