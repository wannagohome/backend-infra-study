1부

서버 한 대를 API로 빌린다

EC2는 1장에서 본 컴퓨터를 가상 머신으로 잘라 빌려주는 서비스입니다. 이름 읽는 법부터 부팅, 접속, 정지와 종료까지 한 대의 일생을 따라갑니다.

컴퓨팅은 맡기는 범위로 고른다

13장에서 VPC와 ELB로 길을 깔았습니다. 이제 그 길 끝에서 실제로 코드를 실행할 자리가 필요합니다.

  1. EC2OS부터 내가 관리
  2. ECS/EKS on EC2노드는 내가, 배치는 AWS
  3. Fargate노드도 AWS가 관리
  4. Lambda함수만 올림(17장)

오른쪽으로 갈수록 AWS가 더 많은 층을 맡고 우리는 덜 신경 씁니다. 대신 제어권과 단가에서 대가를 치릅니다. 이 장은 가장 왼쪽의 EC2를 바닥부터 이해한 다음, 그 위에 컨테이너 서비스를 쌓습니다. 다섯 가지를 한 표로 놓고 고르는 종합 비교는 18장에서 합니다.

Nitro는 가상화 부담을 카드로 옮겼다

EC2 인스턴스는 물리 서버 한 대를 하이퍼바이저로 나눈 가상 머신입니다(9장의 VM). 예전 Xen 기반에서는 네트워크와 디스크 I/O도 호스트 CPU가 소프트웨어로 처리해서 그만큼 성능이 깎였습니다.

Nitro는 이 일을 전용 하드웨어 카드로 떼어 냈습니다. 하이퍼바이저는 CPU와 메모리 분배만 맡아 가볍고, VPC 네트워킹과 EBS는 Nitro 카드가 처리합니다. 그래서 가상 머신인데도 성능이 베어메탈과 거의 같습니다.

인스턴스 이름은 네 조각으로 읽는다

예시계열(시리즈)세대 + 옵션크기
m7g.largem: 범용7세대, g: Gravitonlarge(2 vCPU)
c7i.2xlargec: 컴퓨팅 최적화7세대, i: Intel2xlarge(8 vCPU)
r6id.xlarger: 메모리 최적화i: Intel, d: 로컬 NVMexlarge(4 vCPU)
m7a.metalm: 범용7세대, a: AMDmetal(베어메탈)

점 앞은 패밀리, 점 뒤는 크기입니다. 옵션 문자는 프로세서(a AMD, g Graviton, i Intel)와 추가 능력(d 인스턴스 스토어, n 네트워크 강화, e 추가 메모리나 스토리지, z 고클럭, flex)을 뜻합니다. 같은 패밀리에서 크기가 한 단계 오르면 vCPU, 메모리, 시간당 요금이 대략 두 배가 됩니다.

가속기 패밀리는 칩 종류로 나뉜다

GPU나 전용 칩이 붙은 패밀리입니다. P는 NVIDIA 고성능 GPU로 모델 학습과 HPC에, G는 그래픽과 가벼운 추론에 씁니다. Inf는 AWS가 만든 추론 칩 Inferentia, Trn은 학습 칩 Trainium을 답니다.

이 밖에 FPGA를 붙인 F, macOS 빌드용 Mac, HPC 전용 Hpc 패밀리가 있습니다.

패밀리를 고를 때는 프로파일링으로 병목 자원을 먼저 찾습니다. CPU 사용률은 낮은데 GC가 잦으면 R, 메모리는 남는데 CPU가 꽉 차면 C가 맞습니다.

가속기 패밀리는 용량이 귀해서 원하는 AZ에 자리가 없을 수 있습니다. 그래서 3부에서 볼 용량 예약과 함께 계획합니다.

Graviton은 싸지만 ARM 빌드가 필요하다

Graviton은 AWS가 설계한 ARM64 프로세서입니다. 같은 크기의 x86 인스턴스보다 시간당 요금이 낮게 책정되고, 전력 효율이 좋아 같은 일을 더 적은 비용으로 처리하는 경우가 많습니다.

x86 vCPU는 물리 코어 하나를 하이퍼스레드 둘로 나눈 것이지만, Graviton의 vCPU는 물리 코어 하나입니다. 그래서 CPU 사용률이 높을 때도 성능이 덜 흔들립니다.

대가는 아키텍처가 다르다는 점입니다. 컨테이너 이미지는 linux/arm64로 빌드해야 하고, JNI나 네이티브 라이브러리가 섞인 의존성은 ARM 빌드가 있는지 확인해야 합니다.

Java는 JVM이 ARM을 지원하므로 대개 그대로 돌아갑니다. 전환 체크리스트는 6부에서 다룹니다.

T 계열은 CPU 크레딧을 모았다 쓴다

T 계열은 기준 사용률만큼의 CPU를 늘 보장하고, 그 위는 CPU 크레딧으로 빌려 씁니다. 크레딧 1개는 vCPU 하나를 1분 동안 100% 쓰는 양입니다.

예를 들어 t3.nano는 vCPU 2개, 기준 5%라서 시간당 5% × 2 × 60분 = 6크레딧을 법니다. 기준보다 덜 쓰면 남은 크레딧이 쌓이고, 더 쓰면 쌓인 크레딧을 꺼내 씁니다.

  1. 한가할 때

    기준보다 덜 써서 크레딧이 쌓입니다(상한 있음).

  2. 잠깐 바쁠 때

    쌓인 크레딧으로 기준 이상, 최대 100%까지 씁니다.

  3. 크레딧 바닥

    standard 모드면 기준 사용률로 묶입니다.

  4. unlimited 모드

    바닥나도 계속 쓰고, 넘친 만큼 추가 요금을 냅니다.

unlimited는 느려지는 대신 돈을 낸다

항목standardunlimited
크레딧이 바닥나면기준 사용률로 강제 제한계속 버스트, 잉여 크레딧 사용
추가 요금없음24시간 평균이 기준 초과 시 과금
기본값T2T3, T3a, T4g

standard 모드의 함정은 장애가 서서히 온다는 점입니다. 트래픽이 조금씩 늘어 크레딧이 매일 조금씩 줄다가, 0이 되는 순간 CPU가 기준(크기에 따라 5~40%)으로 묶여 응답이 몇 배 느려집니다. 리눅스 기준 잉여 크레딧은 vCPU 시간당 0.05달러이므로, 늘 기준을 넘는 서버라면 M 계열이 더 쌉니다. CPUCreditBalance 지표에 알람을 거는 것이 첫 대책입니다.

AMI는 부팅 디스크의 설계도다

AMI는 인스턴스를 시작할 때 쓰는 이미지로, 루트 볼륨의 EBS 스냅샷, 아키텍처(x86_64/arm64), 블록 디바이스 매핑, 누가 이 AMI로 시작할 수 있는지 정하는 시작 권한으로 이루어집니다.

AMI는 리전 단위 리소스입니다. 다른 리전에서 쓰려면 copy-image로 복사하며, 이때 뒤의 스냅샷도 함께 복사됩니다.

OS 패치, 에이전트, 런타임까지 미리 구운 AMI를 골든 이미지라고 합니다. 부팅 때 설치할 것이 줄어 Auto Scaling의 새 인스턴스가 빨리 준비됩니다.

대신 바뀔 때마다 AMI를 다시 구워야 합니다. 그래서 자주 안 바뀌는 것은 AMI에, 자주 바뀌는 앱과 설정은 부팅 시점에 넣는 것이 보통입니다. EC2 Image Builder가 굽는 과정을 파이프라인으로 자동화합니다.

user data는 첫 부팅 때 한 번 실행된다

#!/bin/bash

aws s3 cp s3://my-artifacts/api.jar \
  /opt/api/api.jar

인스턴스 안의 cloud-init이 부팅 때 메타데이터에서 user data를 읽어 실행합니다. 셸 스크립트는 기본적으로 첫 부팅 한 번만 실행되고, 출력은 /var/log/cloud-init-output.log에 남습니다.

S3 권한은 키가 아니라 인스턴스 프로파일로 받습니다(12장). user data는 메타데이터로 읽히니 비밀 값을 넣지 않습니다.

IMDS는 인스턴스가 자기를 묻는 창구다

IMDS는 인스턴스 안에서만 닿는 169.254.169.254 주소입니다. 인스턴스 ID, AZ, user data, 그리고 인스턴스 역할의 임시 자격 증명을 돌려줍니다. SDK가 키 없이 AWS를 호출하는 비밀이 여기 있습니다(12장).

IMDSv1은 GET 한 번이면 답을 줬습니다. 그래서 앱에 SSRF 취약점이 있으면 공격자가 서버를 시켜 자격 증명을 읽어 갈 수 있었습니다.

배치 그룹은 물리적 거리를 고른다

전략배치 방식얻는 것어울리는 곳
cluster한 AZ 안에 가깝게 모음낮은 지연, 흐름당 10GbpsHPC, 노드 간 통신 많은 일
spread인스턴스마다 다른 랙동시 장애 최소화AZ당 최대 7대
partition파티션마다 별도 랙 묶음파티션 단위 장애 격리HDFS, Cassandra, Kafka

cluster는 같은 네트워크 구간에 모아 속도를 얻는 대신, 한 AZ에 몰려 있어 AZ 장애에 함께 쓰러집니다. spread는 반대로 소수의 핵심 인스턴스를 떼어 놓습니다. partition은 AZ당 최대 7개 파티션을 만들고 인스턴스가 어느 파티션에 있는지 알려 줘서, 복제본을 다른 파티션에 두는 토폴로지 인식 시스템에 맞습니다. 자리가 없으면 시작이 실패하므로 cluster는 한 번에 띄우는 것이 좋습니다.

네트워크 대역폭에도 기준과 최대가 있다

현행 인스턴스는 ENA라는 가상 NIC으로 Nitro 카드와 통신합니다. 대역폭은 vCPU 수에 비례하고, 사양표에 "최대 10Gbps"처럼 적힌 작은 크기(대개 4xlarge 이하)는 기준 대역폭이 따로 있어 네트워크 I/O 크레딧으로 잠깐 그 위까지 올라갑니다.

T 계열의 CPU 크레딧과 같은 구조라서, 크레딧이 떨어지면 기준 대역폭으로 내려옵니다.

흐름 하나(5-튜플이 같은 TCP 연결 하나)는 cluster 배치 그룹 밖에서 최대 5Gbps, 안에서 최대 10Gbps로 제한됩니다. 대용량 복사가 느리면 연결을 여러 개로 나누는 것이 답입니다.

한도 초과는 ENA 드라이버 통계 bw_out_allowance_exceeded, pps_allowance_exceeded로 확인합니다(ethtool -S eth0).

상태 확인 실패는 누가 고칠지로 나뉜다

EC2는 1분마다 상태를 확인합니다. 시스템 상태 확인이 실패하면 자동 복구가 인스턴스를 건강한 호스트로 옮깁니다. 지원 인스턴스는 단순 자동 복구가 기본으로 켜져 있고, 인스턴스 ID, 사설 IP, EIP, EBS는 그대로지만 RAM 내용은 사라집니다. 인스턴스 상태 확인 실패는 OS 문제라 복구 대상이 아니므로, Auto Scaling 그룹에 넣어 교체하게 합니다.

2부

디스크는 네트워크 너머에 있다

EC2의 루트 디스크는 대부분 서버 안이 아니라 네트워크로 붙은 EBS 볼륨입니다. 이 사실 하나가 성능, 가용성, 백업 방식을 모두 결정합니다.

기초 원리 여기부터는 볼륨 성능 모델, 스냅샷, 구매 방식, 스케일링 동작 원리를 다룹니다.

EBS 볼륨은 AZ 하나에 묶여 있다

EBS는 네트워크로 붙는 블록 디바이스입니다. 인스턴스가 사라져도 볼륨은 남고, 다른 인스턴스로 떼어 붙일 수 있습니다. 데이터는 같은 AZ 안 여러 서버에 자동으로 복제됩니다.

대신 볼륨은 만든 AZ에서만 붙일 수 있습니다. 다른 AZ로 옮기려면 리전 단위인 스냅샷을 거쳐 새 볼륨을 만들어야 합니다. 블록, 파일, 객체 저장소의 비교는 15장에서 합니다.

볼륨 유형은 IOPS형과 처리량형으로 나뉜다

유형최대 IOPS최대 처리량쓰임

HDD 유형(st1, sc1)은 부트 볼륨이 될 수 없습니다. gp3, io2는 최대 64TiB, gp2, st1, sc1은 16TiB입니다. 2026년 AWS EBS 사용 설명서 기준.

gp2는 크기에 묶였고, gp3는 풀려났다

gp2는 성능이 크기에 비례합니다. 100GiB면 기준 300 IOPS이고, 1TiB 미만 볼륨은 I/O 크레딧으로 3,000 IOPS까지 버스트합니다. 크레딧 통은 540만 개라서 3,000 IOPS를 최소 30분 버틸 수 있습니다.

그래서 IOPS가 필요하면 쓰지도 않을 용량을 늘려 사야 했습니다. 3,000 IOPS를 늘 쓰려면 1TiB가 필요합니다.

gp3는 크기와 무관하게 3,000 IOPS, 125MiB/s를 기본으로 주고 버스트가 없습니다. 더 필요하면 IOPS(GiB당 최대 500)와 처리량(IOPS당 0.25MiB/s)을 따로 사서 올립니다. 가격도 gp2보다 최대 20% 낮습니다.

gp2에서 gp3로는 Elastic Volumes로 무중단 전환됩니다. 신규 볼륨은 gp3가 기본 선택입니다.

IOPS와 처리량은 I/O 크기로 이어진다

처리량 = IOPS × I/O 크기입니다. 16KiB 페이지를 읽는 DB가 3,000 IOPS를 쓰면 약 47MiB/s라서 gp3 기본 처리량 125MiB/s 안에 들어옵니다. 반면 256KiB 단위로 읽는 순차 작업은 500 IOPS만 써도 125MiB/s 천장에 닿습니다. 어느 쪽이 먼저 막히는지 보고 IOPS나 처리량 중 하나를 올립니다.

io2 Block Express는 16KiB I/O 평균 지연 0.5ms 미만, 연 고장률 0.001%를 내세웁니다. gp3로 버티다 꼬리 지연(p99)이 문제 되거나 80,000 IOPS를 넘길 때 고릅니다. HDD 유형은 1MiB 같은 큰 순차 I/O에서만 제 성능이 나오고, 작은 무작위 I/O에서는 매우 느립니다.

지표로 확인하는 법

CloudWatch의 VolumeReadOps, VolumeThroughputPercentage, 그리고 대기열 길이 VolumeQueueLength가 계속 높으면 볼륨이 병목입니다.

볼륨이 빨라도 인스턴스가 막을 수 있다

EBS는 네트워크 너머에 있으므로 인스턴스에서 EBS로 가는 길에도 대역폭이 있습니다. EBS 최적화 인스턴스는 EBS 전용 대역폭을 따로 받아 앱 네트워크 트래픽과 다투지 않고, 현행 Nitro 인스턴스는 모두 기본으로 EBS 최적화입니다.

이 전용 대역폭에도 인스턴스 크기별 한도가 있습니다.

예를 들어 작은 인스턴스에 io2 볼륨 50,000 IOPS를 붙여도, 그 인스턴스의 EBS 최대 IOPS가 그보다 낮으면 거기서 막힙니다. 작은 크기는 "최대" 값까지 30분 정도만 버스트하고 그 뒤 기준 값으로 내려옵니다.

그래서 볼륨 성능을 올렸는데 숫자가 안 나오면 인스턴스 사양표의 EBS 기준, 최대 IOPS와 처리량부터 확인합니다.

스냅샷은 바뀐 블록만 저장한다

첫 스냅샷은 사용 중인 블록 전체를, 다음 스냅샷부터는 증분으로 바뀐 블록만 저장합니다. 각 스냅샷은 앞 스냅샷의 블록을 참조해서 그 시점의 볼륨 전체를 복원할 수 있습니다.

그래서 오래된 스냅샷을 지워도 뒤 스냅샷이 참조하는 블록은 남고, 지운 만큼 비용이 줄지 않을 수 있습니다. 스냅샷은 사용자가 직접 볼 수 없는 S3에 저장됩니다.

스냅샷에서 만든 볼륨은 처음에 느리다

스냅샷으로 만든 볼륨은 바로 붙일 수 있지만, 블록은 처음 읽힐 때 S3에서 가져오는 지연 로딩 방식입니다. 그래서 복원 직후 DB를 띄우면 첫 읽기마다 지연이 붙습니다. fio나 dd로 모든 블록을 한 번 읽어 미리 데우거나, 비용을 내고 FSR을 켜서 처음부터 완전히 초기화된 볼륨을 받습니다.

스냅샷은 리전과 계정을 넘어 복사할 수 있어 DR 백업의 기본 재료가 됩니다(18장). 주기적인 생성과 보관 기간은 Data Lifecycle Manager나 AWS Backup으로 자동화합니다.

실수로 지운 스냅샷을 되살리는 휴지통(Recycle Bin) 규칙과, 90일 이상 둘 스냅샷을 싸게 보관하는 스냅샷 아카이브도 있습니다.

암호화는 켜 두면 신경 쓸 일이 없다

EBS 암호화는 KMS 키로 볼륨, 스냅샷, 인스턴스와 볼륨 사이 전송 구간을 함께 암호화합니다. 암호화는 인스턴스를 호스팅하는 서버에서 일어나서 성능 차이는 거의 없습니다. 키와 봉투 암호화 원리는 16장에서 다룹니다.

리전별 기본 암호화 설정을 켜면 그 뒤로 만드는 모든 볼륨이 자동으로 암호화됩니다. 기존 볼륨에는 영향이 없습니다.

  1. 스냅샷 생성

    암호화되지 않은 볼륨의 스냅샷을 만듭니다.

  2. 암호화 복사

    스냅샷을 복사하면서 KMS 키로 암호화합니다.

  3. 새 볼륨

    암호화된 스냅샷에서 볼륨을 만들어 교체합니다.

  4. 주의

    다른 계정과 공유할 스냅샷은 고객 관리형 키로 암호화해야 합니다.

Elastic Volumes는 무중단으로 키운다

크기를 늘리고, 유형을 바꾸고, IOPS와 처리량을 조정하는 일을 분리 없이 합니다. 다만 크기는 줄일 수 없고, 디스크가 커져도 파티션과 파일 시스템은 직접 늘려야 합니다.

한 볼륨은 24시간 안에 최대 네 번까지, 앞 변경이 끝난 뒤에 다시 바꿀 수 있습니다.

인스턴스 스토어는 빠르지만 휘발된다

인스턴스 스토어는 호스트에 물리적으로 꽂힌 로컬 NVMe 디스크입니다. 이름에 d가 붙은 유형(m7gd, i4i)에 딸려 오고, 네트워크를 거치지 않아 EBS보다 지연이 훨씬 낮습니다.

대신 정지, 최대 절전, 종료, 호스트 고장 때 데이터가 사라집니다. 재부팅은 견딥니다. 캐시, 임시 정렬 파일, 다른 노드에 복제본이 있는 분산 DB에만 씁니다.

Multi-Attach는 반대 방향의 특수 기능입니다. io1, io2 볼륨 하나를 같은 AZ의 Nitro 인스턴스 최대 16대에 동시에 붙입니다.

여러 노드가 같은 블록에 쓰므로 ext4, XFS 같은 일반 파일 시스템을 올리면 데이터가 깨집니다. 쓰기 순서를 조율하는 클러스터 인식 파일 시스템이나 애플리케이션이 있을 때만 씁니다. 여러 서버가 파일을 함께 쓰는 일이라면 EFS(15장)가 맞습니다.

EC2 비용의 대부분은 어떤 인스턴스를 쓰느냐보다 어떻게 사느냐에서 갈립니다. 약정, 경매가 아닌 여유 용량, 전용 하드웨어의 원리를 봅니다.

RI는 속성에, SP는 금액에 약정한다

예약 인스턴스(RI)는 Savings Plans 이전의 방식으로, 인스턴스 유형, 플랫폼, 리전 같은 속성을 약정합니다. 표준 RI는 할인이 더 크지만 다른 패밀리로 바꿀 수 없고, 전환형 RI는 할인이 작은 대신 기간 중 다른 속성의 전환형 RI로 교환할 수 있습니다.

EC2만 놓고 보면 같은 할인 폭에 관리가 쉬운 Savings Plans를 먼저 고릅니다. RI는 SP가 적용되지 않는 서비스(RDS, ElastiCache, OpenSearch 등의 예약 노드)나, AZ를 지정해서 용량 예약까지 함께 얻고 싶을 때 의미가 남습니다.

세 방식 모두 결제는 전체 선결제, 부분 선결제, 선결제 없음 중에 고르며 선결제가 클수록 할인이 큽니다.

Spot은 2분 전에 회수를 통보한다

Spot은 AWS에 남는 용량을 싸게 빌리는 것입니다. 입찰 경쟁은 2017년에 없어졌고, 가격은 용량 풀(인스턴스 유형 × AZ)마다 수요와 공급에 따라 천천히 움직입니다.

AWS가 용량을 되찾을 때는 2분 전에 중단 알림을 보냅니다. 그 전에 위험이 커졌다는 리밸런스 권고가 먼저 올 수 있습니다.

4부

서버 수를 사람 대신 맞춘다

8장의 스케일 아웃을 AWS가 구현한 것이 EC2 Auto Scaling입니다. 몇 대를 유지할지, 언제 늘리고 줄일지, 교체를 어떻게 안전하게 할지 차례로 봅니다.

그룹은 희망 용량을 계속 맞춘다

Auto Scaling 그룹(ASG)은 시작 템플릿, 서브넷 목록, 그리고 최소, 희망, 최대 용량을 가집니다. 실제 대수가 희망 용량과 다르면 맞을 때까지 인스턴스를 띄우거나 내립니다.

10장의 조정 루프와 같은 원리입니다. 스케일링 정책은 결국 희망 용량 숫자를 바꾸는 장치이고, 실제 증감은 이 루프가 합니다.

  1. 희망 용량 결정

    정책, 예약, 사람이 desired를 바꿉니다(min ≤ desired ≤ max).

  2. AZ에 고르게 배치

    지정한 서브넷의 AZ들에 균형을 맞춰 띄웁니다.

  3. 대상 그룹 등록

    ELB 대상 그룹에 자동으로 등록합니다.

  4. 비정상 교체

    헬스 체크에 실패하면 종료하고 새로 띄웁니다.

스케일링 정책은 다섯 가지다

정책동작어울리는 상황
대상 추적지표를 목표값에 맞춤(CPU 50% 등)기본 선택, 대부분의 웹
단계알람 초과 폭에 따라 다른 증감급증 폭별로 다르게 대응
단순알람 한 번에 정해진 증감 후 쿨다운권장하지 않음(레거시)
예약정한 시각에 min/max/desired 변경출근 시간, 행사 오픈
예측과거 패턴으로 미리 증설일, 주 단위 주기가 뚜렷함

여러 정책을 함께 걸 수 있고, 둘 이상이 동시에 신호를 내면 더 큰 용량을 요구하는 쪽이 이깁니다. 그래서 늘리는 쪽은 빠르고 줄이는 쪽은 보수적으로 움직입니다.

대상 추적은 비례 계산으로 대수를 정한다

대상 추적 정책을 만들면 AWS가 CloudWatch 알람 두 개(늘리기, 줄이기)를 대신 만들고 관리합니다. 지표가 목표를 넘으면 지표가 목표에 가까워지도록 비례해서 대수를 늘립니다.

예: 현재 4대, 평균 CPU 90%, 목표 60%면 4 × 90 / 60 = 6, 2대를 추가합니다. 10장 HPA의 계산식과 같은 생각입니다.

지표는 인스턴스 수에 반비례해야 제대로 동작합니다. 평균 CPU, 대상당 ALB 요청 수(ALBRequestCountPerTarget)가 대표적입니다. 큐 길이처럼 그룹 전체 합계인 지표는 "인스턴스당 백로그"로 나눠서 써야 합니다.

무엇을 기준 지표로 삼을지는 병목 자원을 따라 고릅니다(18장).

워밍업이 끝나야 지표에 넣는다

새 인스턴스는 부팅하고 JVM이 데워져야 제 몫을 합니다. 그 사이의 높은 CPU를 지표에 섞으면 정책이 "아직 부족하다"고 오판해 과하게 늘립니다.

기본 인스턴스 워밍업은 InService가 된 뒤 정한 시간 동안 그 인스턴스를 집계 지표에서 빼 줍니다. 기본으로 꺼져 있으므로 대상 추적, 단계 정책을 쓰면 꼭 설정합니다.

쿨다운(기본 300초)은 단순 정책 전용 장치로, 한 번 조정하고 나면 정한 시간 동안 다음 단순 정책 조정을 멈춥니다. 대상 추적과 단계 정책에는 적용되지 않고 워밍업이 그 역할을 합니다.

워밍업 시간은 "인스턴스 시작부터 트래픽을 감당할 때까지"를 실제로 재서 정합니다. 너무 짧으면 과증설, 너무 길면 대응이 늦습니다.

ELB 헬스 체크를 켜야 앱 장애를 잡는다

ASG의 기본 헬스 체크는 EC2 상태 확인뿐입니다. OS는 살아 있는데 앱이 500을 내거나 멈춰 있어도 정상으로 보고 교체하지 않습니다.

ELB 헬스 체크를 추가로 켜면 대상 그룹에서 비정상 판정을 받은 인스턴스도 교체합니다. 13장의 헬스 체크 경로가 여기서 교체 기준이 됩니다.

유예 기간은 새 인스턴스가 부팅하는 동안 헬스 체크 실패를 무시하는 시간입니다. 콘솔로 만들면 300초, CLI와 SDK로 만들면 0초가 기본입니다.

앱 기동이 3분 걸리는데 유예 기간이 0이면, ELB가 비정상으로 판정하는 순간 ASG가 지우고 다시 띄우기를 끝없이 반복합니다. IaC로 만들 때 특히 놓치기 쉽습니다.

수명 주기 후크로 시작과 종료 사이에 끼어든다

수명 주기 후크는 인스턴스를 Pending:Wait나 Terminating:Wait 상태에 붙잡아 두고 내 작업을 끝낼 시간을 줍니다. 기본 대기 시간은 1시간이고, 작업이 끝나면 complete-lifecycle-action으로 놓아 줍니다.

시작 쪽에서는 설정 적용, 캐시 예열을, 종료 쪽에서는 로그 업로드, 큐 작업 마무리, 클러스터 탈퇴를 합니다.

  1. 축소 결정

    ASG가 종료할 인스턴스를 고릅니다.

  2. Terminating:Wait

    후크가 인스턴스를 붙잡고 EventBridge로 알립니다.

  3. 내 작업

    Lambda나 에이전트가 로그 전송, 작업 마무리를 합니다.

  4. CONTINUE

    완료 신호를 보내면 실제 종료로 넘어갑니다.

웜 풀은 미리 데운 인스턴스를 세워 둔다

부팅과 초기화에 몇 분씩 걸리는 앱은 급증 때 스케일 아웃이 늦습니다. 웜 풀은 초기화까지 끝낸 인스턴스를 그룹 옆에 대기시켜 두고, 늘릴 때 새로 만드는 대신 여기서 꺼내 씁니다.

대기 상태는 Stopped, Hibernated, Running 중에 고릅니다.

Stopped는 EBS와 EIP 요금만 내서 가장 경제적이고, Hibernated는 메모리까지 보존해 더 빨리 돌아옵니다. Running 대기는 요금이 그대로 나가 권장하지 않습니다.

초기화가 끝나기 전에 Stopped로 들어가면 안 되므로, 시작 쪽 수명 주기 후크와 함께 씁니다. 축소할 때 종료 대신 웜 풀로 돌려보내는 재사용 정책도 있습니다.

인스턴스 새로 고침은 그룹의 롤링 교체다

시작 템플릿에 새 AMI를 넣어도 이미 떠 있는 인스턴스는 바뀌지 않습니다. 인스턴스 새로 고침은 그룹을 묶음 단위로 교체하는 롤링 배포입니다. 배포 전략 일반론은 11장에서 봤습니다.

최소 정상 비율이 90%면 한 번에 10%씩 갈아 끼웁니다. 최소와 최대를 모두 100%로 두면 새 인스턴스를 먼저 띄우고 옛것을 지워 용량이 줄지 않습니다.

체크포인트는 정한 비율만큼 교체한 뒤 멈춰서 지표를 볼 시간을 주고, bake 시간은 끝난 뒤 한동안 지켜봅니다. skip matching은 이미 새 설정인 인스턴스를 건너뜁니다.

자동 롤백을 켜면 실패 시 이전 템플릿으로 되돌리고, CloudWatch 알람을 걸어 두면 알람이 울릴 때 자동으로 멈추고 롤백합니다.

바닥은 On-Demand, 위는 Spot으로

"MixedInstancesPolicy": {
  "LaunchTemplate": {
    "LaunchTemplateSpecification": {
      "LaunchTemplateName": "api",
      "Version": "$Latest" },
    "Overrides": [
      { "InstanceType": "m7g.large" },
      { "InstanceType": "m6g.large" },
      { "InstanceType": "c7g.xlarge" } ] },
  "InstancesDistribution": {

처음 2대는 무조건 On-Demand로, 그 위는 20%만 On-Demand이고 나머지 80%는 Spot으로 띄웁니다. 비율 계산이 소수면 On-Demand 쪽으로 올림합니다.

세 유형 모두 Graviton이라 같은 arm64 AMI를 씁니다. Capacity Rebalancing을 켜면 리밸런스 권고를 받은 Spot을 미리 교체합니다.

줄일 때는 AZ 균형부터 맞춘다

ASG는 AZ 사이 대수를 고르게 유지하려 하고, 이 균형이 종료 정책보다 우선합니다. AZ 하나에 자리가 없어 실패하면 다른 AZ에 띄웠다가, 자리가 나면 AZ 재조정으로 새로 띄운 뒤 넘치는 쪽을 지웁니다.

정족수가 필요한 시스템처럼 불균형을 견딜 수 없다면 AZ 분산 전략을 "균형만(balanced only)"으로 바꿀 수 있습니다.

  1. AZ 선택

    인스턴스가 가장 많은 AZ를 고릅니다.

  2. 구매 옵션 맞춤

    혼합 그룹이면 On-Demand와 Spot 비율에 맞는 쪽을 고릅니다.

  3. 오래된 설정

    시작 구성, 다른 템플릿, 가장 오래된 버전 순으로 고릅니다.

  4. 과금 시간

    다음 과금 시간에 가장 가까운 것, 같으면 무작위입니다.

5부

컨테이너를 AWS에서 돌리는 세 갈래

9장에서 만든 이미지를 어디에 두고, 누가 띄우고, 어떤 기계 위에서 돌릴지 정합니다. 저장소 ECR, AWS 자체 오케스트레이터 ECS, 서버를 숨기는 Fargate, 관리형 Kubernetes EKS 순서로 봅니다.

ECR은 IAM으로 잠긴 이미지 저장소다

ECR은 리전마다 있는 프라이빗 레지스트리입니다. 리포지토리 하나에 이미지 하나(api, worker)를 두고, 푸시와 풀은 IAM 권한으로 통제합니다. 같은 리전의 ECS, EKS가 풀하면 Docker Hub 같은 외부 레지스트리의 횟수 제한을 피하고 전송도 빠릅니다.

태그 불변성을 켜면 이미 있는 태그로 다시 푸시할 때 ImageTagAlreadyExistsException이 납니다. 1.4.2가 어제와 오늘 다른 이미지를 가리키는 사고를 막으므로, 11장에서 본 git SHA나 SemVer 태그 전략과 함께 켭니다.

Private 서브넷에서 풀하려면 NAT, 또는 ECR API, ECR DKR 인터페이스 엔드포인트와 S3 게이트웨이 엔드포인트가 필요합니다(13장). 이미지 레이어는 S3에서 내려오기 때문입니다.

수명 주기 정책이 이미지 쓰레기를 치운다

{ "rules": [
  { "rulePriority": 1,
    "description": "untagged 7일 뒤 삭제",
    "selection": {
      "tagStatus": "untagged",
      "countType": "sinceImagePushed",
      "countUnit": "days", "countNumber": 7 },
    "action": { "type": "expire" } },
  { "rulePriority": 2,
    "description": "release 태그는 최근 30개만",

CI가 커밋마다 이미지를 밀어 넣으면 저장 비용이 계속 쌓입니다. 수명 주기 정책은 나이나 개수 기준으로 오래된 이미지를 자동으로 지웁니다.

규칙은 우선순위 숫자가 작은 것부터 평가합니다. 운영 중인 태그까지 지우지 않도록, 롤백에 쓸 만큼의 개수는 남겨 둡니다.

스캔, 복제, 캐시로 공급망을 다룬다

기능동작쓰는 이유
기본 스캔푸시 시 또는 수동으로 OS 패키지 CVE 검사무료로 시작하는 취약점 확인
향상된 스캔Amazon Inspector가 OS와 언어 패키지를 지속 스캔새 CVE가 나오면 기존 이미지도 재평가
복제레지스트리 단위로 다른 리전, 계정에 자동 복사멀티 리전 배포, DR
pull-through cacheDocker Hub, Quay, GHCR 등을 ECR에 캐시외부 한도 회피, 외부 장애 격리

pull-through cache는 계정.dkr.ecr.리전.amazonaws.com/docker-hub/library/nginx처럼 ECR 주소로 풀하면 처음 한 번 원본에서 가져와 저장하고, 이후에는 ECR에서 줍니다. Docker Hub처럼 인증이 필요한 원본은 자격 증명을 Secrets Manager에 둡니다.

ECS는 태스크 정의를 서비스가 유지한다

태스크 정의는 10장의 Pod 명세에, 태스크는 Pod에, 서비스는 Deployment에 해당합니다. 서비스는 희망 개수만큼 태스크를 유지하고, 죽은 태스크를 다시 띄우고, 대상 그룹에 등록합니다.

태스크 정의는 컨테이너 묶음의 명세다

{ "family": "api",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024", "memory": "2048",
  "executionRoleArn": "arn:aws:iam::111122223333:role/apiExec",
  "taskRoleArn": "arn:aws:iam::111122223333:role/apiTask",
  "containerDefinitions": [{ "name": "app",
    "image": "111122223333.dkr.ecr.us-east-1.amazonaws.com/api:1.4",
    "portMappings": [{ "containerPort": 8080 }],
    "logConfiguration": { "logDriver": "awslogs", "options": {
      "awslogs-group": "/ecs/api", "awslogs-region": "us-east-1",
      "awslogs-stream-prefix": "app" } } }] }

태스크 수준 cpu, memory는 태스크 전체의 크기이고(1024 = 1 vCPU), 컨테이너마다 다시 나눌 수 있습니다. 정의는 수정할 수 없고 바꿀 때마다 api:7, api:8처럼 새 리비전이 생깁니다.

awsvpc는 태스크마다 ENI를 준다

네트워크 모드동작특징
awsvpc태스크마다 자기 ENI와 사설 IP태스크 단위 보안 그룹, Fargate 필수
bridge호스트 안 Docker 브리지(9장)동적 포트 매핑, EC2 리눅스 기본값
host호스트 네트워크를 그대로 사용같은 포트 태스크는 호스트당 하나
none외부 네트워크 없음격리된 배치 작업

AWS 권장값은 awsvpc입니다. 태스크가 VPC의 일급 시민이 되어 보안 그룹, Flow Logs, ALB의 ip 대상 유형을 태스크 단위로 씁니다. 대가는 ENI 수 한도입니다. EC2 인스턴스는 붙일 수 있는 ENI 개수가 정해져 있어서, c5.large는 태스크를 2개만 올릴 수 있습니다. awsvpcTrunking 계정 설정을 켜면 트렁크 ENI로 한도가 12개(태스크 10개)까지 늘어납니다.

실행 역할은 ECS가, 작업 역할은 앱이 쓴다

12장에서 역할을 주는 원리를 봤습니다. ECS에는 역할이 두 개 붙고 쓰는 주체가 다릅니다.

태스크 실행 역할은 태스크를 띄우는 ECS 에이전트가 씁니다. ECR에서 이미지를 풀하고, awslogs로 로그를 보내고, Secrets Manager나 Parameter Store의 비밀을 환경 변수로 주입할 때 필요합니다.

태스크 역할은 컨테이너 안의 앱 코드가 씁니다. 앱이 S3에 쓰거나 SQS를 읽을 권한은 여기에 줍니다. SDK는 컨테이너 자격 증명 엔드포인트에서 자동으로 임시 키를 받습니다.

두 역할을 섞으면 앱에 필요 없는 ECR, 비밀 읽기 권한까지 앱에 주게 됩니다. 이미지 풀 실패는 실행 역할을, 앱의 AccessDenied는 태스크 역할을 먼저 봅니다.

용량 공급자 전략으로 "base 2개는 Fargate, 그 위는 Fargate와 Fargate Spot을 1:3"처럼 섞습니다. EC2 공급자의 관리형 스케일링을 켜면 띄울 태스크가 자리를 못 찾을 때 ECS가 ASG 희망 용량을 대신 늘립니다.

롤링 배포는 두 퍼센트로 속도를 정한다

minimumHealthyPercent는 배포 중 유지할 정상 태스크의 하한(올림), maximumPercent는 동시에 떠 있을 수 있는 태스크의 상한(내림)입니다. 10장 Deployment의 maxUnavailable, maxSurge와 같은 생각입니다.

희망 개수 4일 때 100/200이면 새 태스크 4개를 먼저 띄우고 옛것을 내립니다. 50/100이면 2개를 먼저 내리고 그 자리에 새것을 띄웁니다.

앞쪽은 빠르고 안전하지만 순간적으로 용량이 두 배 필요합니다. 뒤쪽은 추가 용량 없이 가지만 배포 중 처리 능력이 절반으로 줄어듭니다.

함정: 희망 개수 2에 최소 75%면 2개 모두 유지해야 해서 하나도 내릴 수 없고, 최대가 100%라 하나도 더 띄울 수 없으면 배포가 영원히 멈춥니다. 둘 중 하나는 반드시 여유를 둡니다.

서킷 브레이커가 실패한 배포를 되돌린다

$ aws ecs update-service \
  --cluster prod --service api \
  --task-definition api:8 \
  --deployment-configuration \
"minimumHealthyPercent=100,maximumPercent=200,\
deploymentCircuitBreaker={enable=true,\
rollback=true}"

새 태스크가 RUNNING에 오르지 못하거나 헬스 체크로 교체되는 횟수가 임계값을 넘으면 배포를 실패로 판정하고, 롤백을 켰다면 마지막 완료 배포로 되돌립니다.

기본 임계값은 희망 개수의 50%이고 최소 3, 최대 200으로 묶입니다. 서킷 브레이커가 없으면 이미지 오타 하나에 ECS가 태스크를 끝없이 다시 띄웁니다.

Blue/Green은 ECS가 직접 하게 됐다

롤링 대신 새 버전(green) 전체를 옆에 띄우고 트래픽을 한 번에 또는 단계적으로 넘기는 방식입니다. 예전에는 CodeDeploy와 연동해야 했지만, 지금은 ECS 서비스 배포 유형으로 blue/green, linear, canary를 바로 고를 수 있습니다.

ALB 리스너 규칙의 대상 그룹 두 개를 바꿔 끼우는 방식으로 동작합니다.

테스트 리스너로 green에 먼저 요청을 보내 검증하고, 단계마다 Lambda로 확인하는 수명 주기 후크를 걸 수 있습니다. 전환 뒤 두 버전을 함께 띄워 두는 bake 시간 동안 문제가 생기면 즉시 blue로 돌아갑니다.

배포 전략의 비교와 선택 기준은 11장, AWS 배포 도구 전체 흐름은 18장에서 다룹니다.

밖은 ALB로, 안은 Service Connect로

외부 트래픽은 서비스에 ALB 대상 그룹을 연결해서 받습니다. awsvpc 모드면 대상 유형을 ip로 하고 태스크 IP가 바로 등록됩니다. bridge 모드에서는 호스트 포트를 0으로 두는 동적 포트 매핑으로 한 인스턴스에 같은 컨테이너를 여러 개 띄웁니다.

배포 중 내려가는 태스크는 대상 그룹 등록 해제 지연(13장)만큼 연결을 비운 뒤 SIGTERM을 받습니다.

서비스끼리의 내부 호출은 Service Connect를 씁니다. 태스크마다 Envoy 기반 프록시를 사이드카로 넣고 http://orders:8080 같은 짧은 이름으로 부르게 해 주며, 재시도와 요청 지표도 붙여 줍니다.

이름 등록부는 Cloud Map 네임스페이스입니다. 프록시 없이 DNS 이름만 필요하면 Cloud Map 서비스 디스커버리를 직접 씁니다.

로그와 오토스케일링도 서비스에 붙인다

컨테이너의 stdout은 awslogs 드라이버로 CloudWatch Logs에 바로 보냅니다. 여러 목적지(OpenSearch, S3, 외부 SaaS)로 거르고 나눠 보내려면 Fluent Bit 사이드카를 쓰는 FireLens를 씁니다.

로그 전달 mode가 blocking이면 CloudWatch 쪽이 막힐 때 앱의 stdout 쓰기까지 멈춥니다. 지금 기본값인 non-blocking은 버퍼(max-buffer-size)가 넘치면 로그를 버리는 대신 앱을 지킵니다.

태스크 개수 조절은 Application Auto Scaling이 맡습니다. 정책은 EC2와 같은 대상 추적, 단계, 예약, 예측입니다. 평균 CPU(ECSServiceAverageCPUUtilization)나 대상당 ALB 요청 수가 흔한 지표입니다.

태스크가 늘어 EC2 자리가 모자라면 용량 공급자가 ASG를 늘리는 두 단계 스케일링이 일어납니다. 배포 중에는 축소가 자동으로 멈춥니다.

5부(계속)

서버를 숨기거나, Kubernetes를 빌리거나

Fargate는 노드를 아예 보이지 않게 하고, EKS는 10장의 Kubernetes 컨트롤 플레인을 AWS가 대신 운영합니다. Kubernetes 자체의 원리는 10장에 두고, 여기서는 AWS가 붙이는 부분만 봅니다.

Fargate는 태스크마다 VM을 따로 준다

Fargate에서는 태스크(또는 EKS Pod) 하나가 전용 경량 VM에서 돕니다. 노드 AMI 패치, 용량 계획, 빈 자리 맞추기(빈 패킹)가 사라지고, 태스크에 할당한 vCPU와 메모리만큼 초 단위로 과금됩니다.

격리 단위가 VM이라 다른 고객이나 다른 태스크와 커널을 공유하지 않습니다.

대신 할 수 없는 일이 생깁니다. privileged 컨테이너, 호스트 네트워크, DaemonSet이 안 되고, EKS의 Fargate Pod에는 EBS를 붙일 수 없으며 GPU도 없습니다. 노드 에이전트형 도구는 사이드카로 바꿔야 합니다.

임시 스토리지는 기본 20GiB이고 ephemeralStorage로 200GiB까지 늘립니다. 네트워크 모드는 awsvpc만 됩니다.

EKS는 컨트롤 플레인을 AWS VPC에 둔다

EKS는 10장의 kube-apiserver와 etcd를 AWS 소유 VPC에서 여러 AZ에 걸쳐 운영합니다. 우리는 API 엔드포인트만 받고, 컨트롤 플레인의 패치, 백업, 확장은 AWS가 합니다.

요금은 클러스터당 시간당 0.10달러이고, 노드와 로드 밸런서 등은 따로 냅니다. 워커 노드는 내 VPC에 있고, EKS가 내 서브넷에 만든 ENI로 API 서버와 통신합니다.

데이터 플레인은 다섯 가지 중에 고른다

Karpenter는 그룹 없이 노드를 바로 만든다

10장의 Cluster Autoscaler는 미리 만든 노드 그룹(ASG)의 개수만 조절합니다. 그래서 유형마다 그룹을 따로 만들어야 했습니다. Karpenter는 Pending Pod의 요청량과 제약을 읽고, 거기에 맞는 인스턴스 유형을 골라 EC2 Fleet API로 바로 띄웁니다.

허용할 유형, 아키텍처, Spot 여부는 NodePool에, 서브넷, 보안 그룹, AMI는 EC2NodeClass에 적습니다.

통합(consolidation)은 노드가 비거나 더 싼 조합으로 옮길 수 있으면 Pod를 옮기고 노드를 지웁니다. PodDisruptionBudget(10장)을 지키며 진행합니다.

EKS Auto Mode는 이 Karpenter 방식을 AWS가 운영하고, VPC CNI, 로드 밸런서 컨트롤러, EBS CSI까지 내장해 관리합니다. 노드는 불변 AMI에 최대 21일 수명이라 저절로 교체되며, EC2 요금 위에 관리 요금이 붙습니다.

VPC CNI는 Pod에 VPC IP를 준다

10장에서 Pod마다 IP가 있다고 했습니다. EKS의 기본 CNI인 VPC CNI는 그 IP를 오버레이가 아닌 VPC 서브넷의 실제 사설 IP로 줍니다. 노드에 ENI를 붙이고 각 ENI의 보조 IP를 Pod에 나눠 줍니다.

그래서 Pod가 VPC 안에서 바로 라우팅되고 보안 그룹과 Flow Logs가 그대로 통하지만, Pod 수만큼 서브넷 IP를 씁니다.

프리픽스 위임으로 노드당 Pod를 늘린다

프리픽스 위임은 ENI 슬롯 하나에 IP 하나 대신 /28 프리픽스(IP 16개)를 붙입니다. 같은 ENI 수로 훨씬 많은 Pod IP를 얻고, IP를 하나씩 받느라 EC2 API를 부르는 횟수도 줄어 Pod 시작이 빨라집니다.

관리형 노드 그룹은 그래도 maxPods를 vCPU 30개 미만이면 110, 이상이면 250으로 묶습니다.

대가는 서브넷 조각화입니다. 연속된 /28 블록이 있어야 해서, IP가 흩어져 남은 서브넷에서는 "IP는 남는데 프리픽스를 못 받는" 일이 생깁니다. 노드 전용 서브넷을 크게 잡는 것이 안전합니다.

VPC 대역 자체가 모자라면 100.64.0.0/10 같은 보조 CIDR를 VPC에 붙이고 사용자 지정 네트워킹으로 Pod만 그 대역에서 IP를 받게 합니다. IPv6 클러스터도 근본 해법입니다.

Ingress를 만들면 ALB가 생긴다

ip 대상은 Pod IP로 바로 보내 NodePort를 거치는 한 홉이 없고, Fargate Pod에서는 이것만 됩니다.

10장의 PV와 StorageClass는 CSI 드라이버로 AWS에 닿습니다. EBS CSI는 Pod가 뜬 AZ에 볼륨을 만들어 붙이고(한 AZ에 묶임), EFS CSI는 여러 AZ에서 함께 쓰는 볼륨을 줍니다.

Pod의 AWS 권한은 12장의 원리대로 Pod Identity나 IRSA로 줍니다. Pod Identity는 OIDC 공급자 없이 노드의 에이전트가 자격 증명을 나눠 줍니다.

EKS는 버전을 미루면 비용이 여섯 배다

Kubernetes 마이너 버전은 EKS 출시 후 14개월 표준 지원, 이어서 12개월 연장 지원을 받습니다. 연장 지원 기간에는 클러스터 요금이 시간당 0.10달러에서 0.60달러로 오르고, 연장 지원도 끝나면 AWS가 자동으로 업그레이드합니다.

업그레이드는 컨트롤 플레인 먼저, 노드와 애드온 나중 순서로 한 마이너씩 올립니다.

EKS 애드온은 VPC CNI, CoreDNS, kube-proxy, EBS/EFS CSI, Pod Identity Agent 같은 핵심 구성 요소를 AWS가 검증한 버전으로 설치, 갱신해 줍니다. 클러스터 버전을 올릴 때 애드온 버전 호환표도 함께 확인합니다.

누가 kubectl을 쓸 수 있는지는 액세스 항목으로 IAM 역할과 Kubernetes 권한을 EKS API에서 연결합니다. 예전의 aws-auth ConfigMap은 잘못 고치면 클러스터 접근을 잃어 레거시가 됐습니다.

크기를 고르고, 아키텍처를 바꾸고, Spot을 굴리고, 컨테이너가 안 뜰 때 원인을 좁히는 법을 봅니다.

크기는 지표로 깎는다

처음 고른 인스턴스는 대개 넉넉합니다. Compute Optimizer는 최근 14일(유료 옵션으로 93일)의 CloudWatch 지표를 보고 EC2, ASG, EBS, Lambda, Fargate 위 ECS 서비스에 대해 과다, 부족, 적정 판정과 추천 유형을 줍니다.

단, 기본 EC2 지표에는 메모리가 없습니다. CloudWatch 에이전트로 메모리를 보내야 추천이 메모리까지 반영합니다.

  1. 지표 수집

    CPU, 메모리, 네트워크, EBS의 p99와 최대값을 2주 이상 봅니다.

  2. 병목 자원 찾기

    여유가 큰 자원에 맞춰 패밀리나 크기를 내립니다.

  3. 여유 남기기

    AZ 하나를 잃어도 버틸 만큼(18장) 남깁니다.

  4. 약정은 마지막

    크기를 맞춘 뒤에 Savings Plans를 삽니다.

Graviton 전환은 빌드에서 시작한다

  1. 의존성 점검

    네이티브 라이브러리, 에이전트, 사이드카 이미지의 arm64 빌드 여부를 확인합니다.

  2. 멀티 아키텍처 이미지

    docker buildx --platform linux/amd64,linux/arm64로 한 태그에 둘 다 넣습니다.

  3. 성능 비교

    같은 부하로 지연 p99, 처리량, GC를 비교합니다. JDK는 최신 LTS가 유리합니다.

  4. 일부만 먼저

    노드 그룹이나 ASG 일부를 Graviton으로 바꿔 canary로 봅니다.

Spot은 회수가 일상이라는 전제로 굴린다

Spot을 쓰는 서비스는 아무 때나 서버 하나가 2분 안에 사라져도 괜찮아야 합니다. 상태는 밖(DB, S3, ElastiCache)에 두고, 요청은 짧게 끝나며, 배치는 체크포인트로 다시 시작할 수 있어야 합니다.

회수는 같은 용량 풀에 몰리므로 유형 여러 개 × AZ 여러 개로 풀을 넓히는 것이 가장 효과가 큰 대책입니다.

ASG는 Capacity Rebalancing, EKS는 Karpenter나 관리형 노드 그룹의 Spot 처리, 또는 AWS Node Termination Handler로 알림을 받아 노드를 cordon, drain 합니다. ALB 등록 해제 지연은 2분보다 짧게 둡니다.

On-Demand 바닥 용량(base)을 남겨 Spot이 한꺼번에 빠져도 서비스가 서 있게 합니다. 전체를 Spot으로 두는 것은 배치나 개발 환경에서만 합니다.

크레딧 고갈은 서서히 느려지는 장애다

오류는 없는데 응답 시간이 며칠에 걸쳐 조금씩 늘다가 어느 순간 급격히 나빠지는 패턴이 있습니다. 대개 크레딧 기반 자원이 바닥난 것입니다. T 계열 CPU 크레딧, gp2 I/O 크레딧, 작은 인스턴스의 네트워크와 EBS 버스트가 모두 같은 모양입니다.

헬스 체크와 기동 시간을 맞춰야 한다

흔한 사고 하나: Spring Boot 앱이 기동에 90초 걸리는데, 서비스의 healthCheckGracePeriodSeconds가 0이고 ALB 헬스 체크는 30초 간격에 2번 실패로 비정상 판정입니다. 태스크가 준비되기도 전에 비정상으로 찍혀 교체되고, 새 태스크도 같은 길을 갑니다.

배포 서킷 브레이커가 이 반복을 실패로 판정해 롤백하지만, 원인은 설정입니다.

  1. 기동 시간 측정

    컨테이너 시작부터 첫 200 응답까지 실제로 잽니다.

  2. 유예 기간 설정

    측정값보다 넉넉하게 서비스 유예 기간을 둡니다.

  3. 헬스 경로 분리

    DB까지 확인하는 무거운 경로 대신 가벼운 readiness 경로를 씁니다.

  4. 기동 단축

    지연 초기화, CDS, 이미지 크기 축소로 근본 시간을 줄입니다.

업그레이드와 노드 교체를 일상으로 만든다

EKS 버전, 노드 AMI, ECS 최적화 AMI, 골든 이미지는 모두 몇 달 단위로 낡습니다. 미루면 여러 버전을 한꺼번에 건너야 하고, EKS는 연장 지원 요금까지 붙습니다.

그래서 인스턴스 새로 고침, 관리형 노드 그룹 업데이트, Karpenter의 drift 교체처럼 노드를 자주 갈아 끼워도 서비스가 흔들리지 않는 구조를 먼저 만듭니다.

그 구조의 조건은 앞 장들에서 본 것들입니다. 앱의 Graceful Shutdown(11장), PodDisruptionBudget과 readiness probe(10장), ELB 등록 해제 지연(13장), 그리고 여러 AZ에 걸친 여유 용량입니다.

관리형 노드 그룹은 드레인이 15분을 넘으면 Pod가 남아 있어도 노드를 지웁니다. 종료가 오래 걸리는 Pod는 이 시간을 고려해 설계합니다.

정리

  • EC2는 Nitro 위의 가상 머신이고, 이름에 성격이 적혀 있다. 패밀리는 vCPU당 메모리 비율, 옵션 문자는 프로세서와 로컬 디스크, 크기는 두 배씩 오릅니다.
  • EBS는 AZ에 묶인 네트워크 디스크다. gp3는 크기와 무관하게 3,000 IOPS를 주고, 스냅샷은 증분이며 AZ와 리전을 넘는 다리입니다.
  • 바닥은 약정으로, 출렁임은 On-Demand와 Spot으로 산다. Spot은 여러 유형과 AZ에 나눠 2분 회수를 견디게 설계합니다.
  • Auto Scaling은 희망 용량을 맞추는 루프다. 대상 추적, 워밍업, ELB 헬스 체크와 유예 기간, 인스턴스 새로 고침이 핵심 설정입니다.
  • ECS는 단순하게, EKS는 Kubernetes 생태계로 컨테이너를 돌린다. awsvpc와 VPC CNI 모두 태스크와 Pod에 VPC IP를 주므로 IP 계획이 중요합니다.

스스로 점검 (1)

  1. r7gd.2xlarge를 이름만 보고 설명하면?

    메모리 최적화(r) 7세대 Graviton(g)에 로컬 NVMe 인스턴스 스토어(d)가 붙은 8 vCPU 크기입니다. 로컬 디스크는 정지하면 사라집니다.

  2. t3 서버가 며칠째 조금씩 느려지다 갑자기 크게 느려졌다면 무엇부터 보나요?

    CPUCreditBalance입니다. standard 모드에서 크레딧이 0이 되면 기준 사용률로 묶입니다.

  3. IMDSv2가 SSRF를 막는 원리는?

    먼저 PUT과 TTL 헤더로 토큰을 받아야 하는데, 대부분의 SSRF는 임의 메서드와 헤더를 못 보냅니다. 홉 제한은 토큰이 인스턴스 밖으로 나가지 못하게 합니다.

  4. 100GiB gp2 볼륨이 평소엔 빠르다가 배치 30분 뒤 느려지는 이유는?

    기준 300 IOPS인데 I/O 크레딧으로 3,000까지 버스트하다 크레딧이 바닥났기 때문입니다. gp3로 바꾸면 크기와 무관하게 3,000 IOPS가 기본입니다.

  5. AZ a의 EBS 볼륨을 AZ b의 인스턴스에서 쓰려면?

    스냅샷을 만들고 AZ b에서 그 스냅샷으로 새 볼륨을 만듭니다. 복원 직후는 지연 로딩으로 첫 읽기가 느립니다.

스스로 점검 (2)

  1. CLI로 만든 ASG에서 새 인스턴스가 계속 교체만 반복된다면?

    CLI 기본 유예 기간이 0초라 앱이 뜨기 전에 ELB 헬스 체크 실패로 교체됩니다. 기동 시간보다 긴 유예 기간을 둡니다.

  2. 현재 5대, 평균 CPU 80%, 목표 50%면 대상 추적은 몇 대로 맞추나요?

    5 × 80 / 50 = 8, 3대를 늘려 8대로 맞춥니다.

  3. 앱이 S3에서 AccessDenied를 받으면 실행 역할과 태스크 역할 중 무엇을 고치나요?

    태스크 역할입니다. 실행 역할은 이미지 풀, 로그 전송, 비밀 주입처럼 ECS 에이전트가 하는 일에만 씁니다.

  4. m5.large 노드에 Pod가 29개 넘게 안 뜨는 이유는?

    VPC CNI가 ENI 보조 IP를 Pod에 주는데, ENI 3개 × (10 − 1) + 2 = 29가 한도입니다. 프리픽스 위임이나 큰 노드로 늘립니다.

  5. 희망 개수 2, minimumHealthyPercent 100, maximumPercent 100이면 배포가 어떻게 되나요?

    하나도 내릴 수 없고 하나도 더 띄울 수 없어 배포가 진행되지 않습니다. 최대를 200으로 올리거나 최소를 낮춥니다.
