1부

AWS라는 땅의 지도부터 그린다

11장에서 파이프라인과 Terraform으로 인프라를 코드로 배포하는 법을 익혔습니다. 이제 그 코드가 실제로 무엇을 만드는지, 그 무대인 AWS의 구조와 규칙부터 봅니다.

AWS 파트는 일곱 장으로 한 시스템을 쌓는다

클라우드는 남의 데이터센터를 API로 빌린다

클라우드 컴퓨팅은 서버, 저장 장치, 네트워크 같은 IT 자원을 인터넷으로 필요할 때 빌려 쓰고 쓴 만큼 내는 방식입니다. 서버를 사서 랙에 꽂고 회선을 까는 일을 API 호출 한 번이 대신합니다.

새로운 원리가 생긴 것은 아닙니다. 앞 장에서 배운 가상화, 로드 밸런싱, 복제를 다른 회사가 대규모로 운영해 주고 우리는 API로 쓰는 것입니다.

  • 온디맨드 셀프 서비스: 사람을 거치지 않고 몇 분 안에 자원을 만듭니다. 구매 품의와 납기가 사라집니다.
  • 탄력성: 트래픽이 늘면 늘리고 줄면 줄입니다. 최대 부하에 맞춰 미리 사 둘 필요가 없습니다.
  • 종량제: 초, 시간, GB, 요청 수 단위로 씁니다. 초기 투자가 운영비로 바뀝니다.

위로 갈수록 운영 부담은 줄고 제어권도 줄어듭니다. 실무에서 AWS 서비스를 고른다는 것은 결국 "이 층을 우리가 직접 다룰 이유가 있는가"를 묻는 일입니다.

AWS는 클라우드를, 고객은 그 안을 지킨다

공유 책임 모델은 보안과 운영 책임을 AWS와 고객이 나눠 지는 기준입니다. AWS는 클라우드 자체의 보안(데이터센터, 하드웨어, 하이퍼바이저, 글로벌 네트워크)을, 고객은 클라우드 안의 보안(데이터, 권한, 설정)을 맡습니다.

경계선은 고정되어 있지 않습니다. 관리형 서비스일수록 선이 위로 올라가 AWS 몫이 커집니다. 하지만 데이터와 IAM 권한은 어떤 서비스에서도 고객 몫으로 남습니다.

리전은 지역, AZ는 장애를 가두는 칸이다

리전은 서울(ap-northeast-2)처럼 지리적으로 떨어진 독립 지역입니다. 리전끼리는 장애도 데이터도 서로 넘어가지 않게 격리되어 있습니다.

리전마다 세 개 이상의 가용 영역(AZ)이 있습니다. AZ는 전원, 냉각, 네트워크가 분리된 데이터 센터 묶음이고, AZ끼리는 고대역폭·저지연 전용망으로 이어집니다. 그래서 설계의 기본 단위는 AZ 하나를 통째로 잃어도 버티는 구조입니다.

AZ 이름은 계정마다 다른 곳일 수 있다

콘솔에 보이는 us-east-1a 같은 AZ 이름은 리전 코드 뒤에 글자를 붙인 별칭입니다. 오래된 일부 리전에서는 2025년 11월 이전에 만든 계정마다 이 글자를 물리 AZ에 따로 섞어 배정했습니다. 모두가 a로 몰리지 않게 하려는 장치였습니다.

그래서 내 계정의 us-east-1a와 다른 계정의 us-east-1a는 다른 건물일 수 있습니다. 모든 계정에서 같은 물리 위치를 가리키는 값은 AZ ID(use1-az1)입니다.

$ aws ec2 describe-availability-zones \
  --region ap-northeast-2 --output text \
  --query 'AvailabilityZones[].[ZoneName,ZoneId]'
ap-northeast-2a  apne2-az1
ap-northeast-2b  apne2-az2
ap-northeast-2c  apne2-az3
ap-northeast-2d  apne2-az4

여러 계정이 AZ를 맞출 때는 ID로

다른 계정과 PrivateLink를 잇거나 AZ 장애 영향을 비교할 때는 이름이 아니라 AZ ID로 대조합니다.

네 가지 모두 "리전까지 가기엔 멀거나 갈 수 없을 때" AWS를 사용자 쪽으로 가져온 것입니다. 일반적인 웹 백엔드는 리전과 엣지 로케이션만으로 충분하며, 나머지는 이름과 용도만 알아 두면 됩니다.

리전은 지연, 규정, 서비스, 비용으로 고른다

  • 지연 시간: 사용자와 가까울수록 RTT가 줄어듭니다. 한국 사용자라면 서울 리전이 출발점입니다.
  • 규정과 데이터 주권: 개인정보나 금융 데이터의 국외 이전 제한이 있으면 리전이 사실상 정해집니다.
  • 서비스 제공 여부: 새 서비스나 인스턴스 유형은 버지니아(us-east-1) 같은 큰 리전에 먼저 나옵니다.
  • 비용: 같은 인스턴스도 리전마다 단가가 다릅니다.

us-east-1에는 리전 이상의 역할이 있습니다

CloudFront용 ACM 인증서, Organizations와 IAM 같은 글로벌 서비스의 제어 기능이 이곳에 묶여 있습니다. 서울만 쓰는 팀도 us-east-1을 막아 버리면 일부 기능이 멈춥니다.

2019년 이후 생긴 리전은 기본 비활성

옵트인 리전은 계정 설정에서 켜야 쓸 수 있습니다. 반대로 쓰지 않는 리전은 SCP로 막는 것이 좋습니다(3부).

서비스는 글로벌, 리전, AZ 범위 중 하나에 산다

범위대표 서비스·리소스의미
글로벌IAM, Organizations, Route 53, CloudFront어느 리전에서 봐도 같은 대상
리전VPC, S3 버킷, Lambda, DynamoDB, SQS만든 리전 안에만 존재
AZ서브넷, EC2 인스턴스, EBS 볼륨그 AZ가 죽으면 함께 멈춤

범위를 알면 장애의 크기가 보입니다. EBS 볼륨은 AZ에 묶여 있어 다른 AZ의 인스턴스에 붙일 수 없고, S3 버킷은 리전 안에서 여러 AZ에 자동으로 복제됩니다. S3 버킷 이름은 전 세계에서 유일해야 하지만 데이터는 고른 리전에만 저장됩니다.

"어제 만든 서버가 사라졌다"는 문의의 상당수는 콘솔 오른쪽 위의 리전 선택이 바뀐 것입니다.

ARN은 AWS 안의 모든 것을 가리키는 주소다

# arn:파티션:서비스:리전:계정ID:리소스
arn:aws:ec2:ap-northeast-2:111122223333:instance/i-0abc

# IAM은 글로벌이라 리전 칸이 비어 있음
arn:aws:iam::111122223333:role/app-server

# S3 버킷은 이름이 전역 유일이라 리전·계정도 비움
arn:aws:s3:::app-uploads
arn:aws:s3:::app-uploads/images/*

# 역할을 맡은 세션(누가 호출했는지 CloudTrail에 찍힘)
arn:aws:sts::111122223333:assumed-role/app-server/i-0abc

ARN은 리소스를 전 세계에서 하나로 식별하는 문자열입니다. IAM 정책의 Resource와 Principal이 모두 ARN으로 대상을 적기 때문에, ARN을 읽을 줄 알아야 정책을 읽을 수 있습니다.

파티션은 보통 aws이고, 중국(aws-cn)과 미국 정부(aws-us-gov) 리전만 다릅니다. 빈 칸은 그 서비스의 범위를 그대로 드러냅니다.

계정은 결제와 권한, 장애가 갇히는 상자다

AWS 계정은 12자리 ID로 식별되는 리소스의 컨테이너입니다. 계정 안의 리소스는 기본적으로 계정 밖과 완전히 분리되어, 다른 계정에서 접근하려면 양쪽이 명시적으로 허용해야 합니다.

그래서 계정은 권한 사고와 비용 사고의 폭발 반경을 자르는 가장 강한 경계입니다. 3부에서 prod와 dev를 계정 단위로 나누는 이유가 여기에 있습니다.

계정을 만들 때 쓴 이메일과 비밀번호가 루트 사용자입니다. 루트는 계정의 모든 리소스에 무조건 접근하며, 계정 해지나 지원 플랜 변경처럼 루트만 할 수 있는 일도 있습니다.

사용자나 역할에 붙이는 IAM 정책으로는 루트를 제한할 수 없습니다. 루트에 상한을 씌우는 수단은 Organizations의 SCP(멤버 계정에 한해)입니다. 그래서 루트는 MFA로 잠그고 평소에는 쓰지 않습니다(4부 체크리스트).

콘솔도 CLI도 같은 API를 서명해 부른다

콘솔 클릭도, aws s3 ls도, Spring 앱의 SDK 호출도 결국 같은 HTTPS API 요청이 됩니다. 차이는 자격 증명을 어디서 얻느냐뿐입니다.

요청은 비밀번호를 그대로 보내지 않습니다. SigV4는 비밀 키로 요청 내용과 시각의 HMAC 서명을 만들어 붙이고, AWS는 같은 계산으로 검증합니다. 비밀 키가 네트워크로 나가지 않고, 서명이 변조와 재전송을 막습니다(서명 원리는 7장).

  1. 콘솔·CLI·SDK자격 증명 확보
  2. SigV4 서명Authorization 헤더
  3. 서비스 엔드포인트서명 검증 = 인증
  4. IAM 평가허용 또는 거부 = 인가

SDK는 정해진 순서로 자격 증명을 찾는다

  1. JVM 시스템 속성

    aws.accessKeyId 등

  2. 환경 변수

    AWS_ACCESS_KEY_ID, AWS_SESSION_TOKEN

  3. 웹 ID 토큰

    AWS_WEB_IDENTITY_TOKEN_FILE + AWS_ROLE_ARN(EKS IRSA)

  4. ~/.aws 프로필

    SSO, 역할 전환, 정적 키 순으로 해석

  5. 컨테이너, 그다음 EC2 IMDS

    ECS 작업 역할·Pod Identity, 그다음 인스턴스 프로파일

AWS SDK for Java 2.x의 DefaultCredentialsProvider는 이 순서로 찾다가 처음 찾은 것에서 멈춥니다. 코드에 키를 적지 않아도 실행 환경에 따라 알맞은 자격 증명이 잡히는 이유입니다.

CLI와 다른 언어 SDK도 순서의 세부만 다를 뿐 "명시적 설정 → 환경 변수 → 파일 → 실행 환경" 흐름은 같습니다.

데이터는 들어올 땐 공짜, 나갈 땐 돈이다

인터넷에서 AWS로 들어오는 전송은 무료이고, AWS에서 인터넷으로 나가는 전송에 GB당 요금이 붙습니다. 인터넷 송신은 모든 서비스와 리전을 합쳐 매달 100GB까지 무료입니다.

내부 전송도 공짜가 아닙니다. 같은 AZ 안에서 사설 IP로 오가면 무료지만, AZ를 넘으면 양방향 모두 과금되고 리전을 넘으면 더 비쌉니다. Multi-AZ 설계는 가용성을 얻는 대신 이 비용을 냅니다(줄이는 법은 13장, 18장).

프리 티어는 크레딧이고, Budgets는 첫날 켠다

2025년 7월부터 새 계정은 무료 플랜과 유료 플랜 중 하나를 고릅니다. 신규 계정은 100달러 크레딧을 받고, 안내된 활동을 마치면 최대 100달러를 더 받습니다. 무료 플랜은 6개월이 지나거나 크레딧이 바닥나면 끝나며, 그 전에는 요금이 청구되지 않습니다.

여기에 Lambda 요청 수처럼 매달 주어지는 상시 무료 한도가 더해집니다. 이전 방식(12개월 무료)의 글은 이제 맞지 않습니다.

AWS Budgets의 알림은 무료입니다. 임계값을 넘으면 권한을 막는 예산 액션은 예산 두 개까지 무료입니다.

모든 서비스에는 할당량이 있고, 미리 늘린다

서비스 할당량은 계정과 리전마다 정해진 리소스 수와 API 호출 속도의 상한입니다. 예를 들어 실행 중인 온디맨드 인스턴스는 개수가 아니라 vCPU 합계로 제한되고, STS 호출은 계정·리전마다 초당 600회가 기본입니다.

할당량에는 요청하면 늘려 주는 조정 가능한 값과 설계상 고정된 하드 한도가 있습니다. Service Quotas 콘솔에서 현재 사용량과 적용된 값을 보고 증가를 요청합니다.

할당량은 트래픽 폭증 순간에 발견됩니다

Auto Scaling이 인스턴스를 늘리려는데 vCPU 할당량에 막혀 실패하는 일이 흔합니다. 출시나 이벤트 전에 최대 규모 기준으로 미리 증가를 요청합니다.

사용률에 알람을 겁니다

Service Quotas는 주요 할당량의 사용률을 CloudWatch 지표로 내보냅니다. 80% 알람을 걸어 두면 막히기 전에 압니다.

2부

모든 API 호출은 IAM을 통과한다

누가 호출했는지 확인하고, 그 호출에 걸린 모든 정책을 모아 허용할지 판단합니다. 이 판단 과정을 이해하면 AccessDenied는 더 이상 수수께끼가 아닙니다.

기초 원리 여기부터는 정책 문서, 평가 로직, 임시 자격 증명이 실제로 어떻게 동작하는지 봅니다.

IAM은 요청 하나를 문맥으로 바꿔 판정한다

7장에서 본 인증(누구인가)과 인가(해도 되는가)를 AWS는 이렇게 나눕니다. 서명 검증으로 호출자를 확인한 뒤, 요청을 요청 문맥으로 정리합니다.

문맥에는 Principal(호출자), Action(s3:GetObject 같은 API), Resource(대상 ARN), 그리고 출발 IP, 시각, MFA 여부, 태그 같은 조건 값이 담깁니다. 정책은 결국 이 네 가지를 맞춰 보는 규칙입니다.

호출하는 주체 Principal은 여섯 종류다

그룹은 Principal이 아닙니다. 정책을 묶어 붙이는 그릇일 뿐이라 정책의 Principal로 지정할 수 없습니다.

사용자는 사람, 그룹은 묶음, 역할은 모자다

IAM 사용자는 비밀번호와 Access Key라는 만료되지 않는 자격 증명을 가집니다. 그룹은 사용자를 모아 정책을 한 번에 붙이는 용도입니다.

역할에는 비밀번호도 키도 없습니다. 허락받은 누군가가 잠시 "쓰는" 모자이고, 쓰는 순간 STS가 몇 시간 뒤 만료되는 임시 키를 발급합니다.

왜 역할이 기본이 되었을까요? 유출 사고 대부분은 Git, 이미지, 로그에 섞여 든 장기 Access Key에서 시작합니다. 임시 키는 새어 나가도 곧 쓸모가 없어집니다.

그래서 오늘날의 기본형은 서버는 역할, 사람은 Identity Center(SSO)를 통한 역할, CI는 OIDC를 통한 역할입니다. IAM 사용자는 이 방식들을 쓸 수 없는 예외에만 남깁니다.

정책 문서는 문장들의 목록이다

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadWriteUploads",
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::app-uploads/*",
    "Condition": {
      "Bool": {"aws:SecureTransport": "true"}
    }
  }]
}

Version은 날짜처럼 보이지만 정책 언어의 판입니다. 항상 "2012-10-17"을 씁니다. 이것을 빼면 ${aws:username} 같은 변수가 동작하지 않습니다.

Statement마다 "어떤 Effect로, 어떤 Action을, 어떤 Resource에, 어떤 Condition일 때"를 적습니다. 이 정책은 한 버킷의 객체 읽기·쓰기를 HTTPS 요청일 때만 허용합니다.

흔한 실수: s3:ListBucket은 버킷 ARN(arn:aws:s3:::app-uploads)에, s3:GetObject는 객체 ARN(…/app-uploads/*)에 걸어야 합니다. 둘을 섞으면 조용히 거부됩니다.

서로 다른 조건 키는 모두 참이어야 하고(AND), 한 키에 값을 여러 개 주면 그중 하나만 맞으면 됩니다(OR). 위 예는 "서울 또는 도쿄, 그리고 MFA, 그리고 사내 IP"입니다.

aws:로 시작하는 전역 키는 모든 서비스에서, s3:prefix처럼 서비스 접두사가 붙은 키는 그 서비스에서만 씁니다. 키가 요청 문맥에 없을 때도 통과시키려면 StringEqualsIfExists처럼 IfExists를 붙입니다.

정책은 '주는 것'과 '상한을 긋는 것'으로 나뉜다

위 세 가지만 권한을 부여합니다. 아래 세 가지는 아무것도 주지 않고 "이 이상은 안 된다"는 천장만 긋습니다. 천장만 있고 부여가 없으면 결과는 거부입니다.

권한 경계는 '줄 수 있는 최대치'를 고정한다

권한 경계는 사용자나 역할에 지정하는 관리형 정책 하나로, 그 주체의 자격 증명 기반 정책이 줄 수 있는 권한의 최대치를 정합니다. 실제 권한은 두 정책이 모두 허용한 교집합입니다.

왜 필요할까요? 개발자에게 "역할을 만들 권한"을 주면, 그 개발자가 관리자 역할을 만들어 스스로 맡을 수 있습니다. 경계를 걸면 새로 만드는 역할도 경계 안에 갇힙니다(4부 위임 패턴).

세션 정책은 AssumeRole 호출에 함께 넘기는 정책으로, 그 세션 하나에만 상한을 씌웁니다. 하나의 넓은 역할을 요청마다 좁혀 쓰는 용도입니다.

예를 들어 멀티테넌트 서비스가 고객 A의 요청을 처리할 때 tenants/A/*만 허용하는 세션 정책으로 역할을 맡으면, 코드 버그가 있어도 다른 고객 데이터에 닿지 않습니다. 인라인 JSON과 관리형 정책 ARN을 합쳐 2,048자까지 넘길 수 있습니다.

AWS 관리형은 편하고, 고객 관리형은 정확하다

시작은 AWS 관리형(ReadOnlyAccess 등)으로 빠르게 하고, 운영 역할은 고객 관리형으로 좁혀 갑니다. 인라인은 "이 역할과 함께 태어나 함께 사라져야 하는" 예외 권한에만 씁니다. 역할 하나에는 관리형 정책을 기본 20개까지 붙일 수 있습니다.

평가는 Deny부터 찾고 천장을 차례로 본다

  1. 명시적 Deny 탐색

    모든 유형의 정책에서 Deny를 찾고, 하나라도 맞으면 즉시 거부합니다.

  2. RCP, 그다음 SCP

    조직 정책이 이 리소스·주체에 Allow하지 않으면 거부합니다.

  3. 리소스 기반 정책

    호출자를 직접 지정해 Allow했다면 여기서 허용될 수 있습니다.

  4. 자격 증명 기반 정책

    Allow가 없으면 암묵적 거부입니다.

  5. 권한 경계, 세션 정책

    있다면 이 천장들도 Allow해야 최종 허용입니다.

출발점은 암묵적 거부입니다. 아무도 허용하지 않은 요청은 거부되고, 허용은 반드시 누군가 명시해야 합니다.

왜 Deny가 무조건 이기게 했을까요? 권한은 여러 팀이 여러 정책으로 겹겹이 붙입니다. 누가 어디선가 Allow를 추가해도 절대 넘으면 안 되는 선을 지키려면, Deny가 순서와 상관없이 이겨야 합니다.

같은 계정 안에서는 천장의 교집합이 권한이다

자격 증명 기반 정책이 허용한 영역에 SCP, 권한 경계, 세션 정책이 각각 천장을 씌우면 실제 권한은 모두 겹치는 부분만 남습니다.

예외는 리소스 기반 정책입니다. 같은 계정에서 버킷 정책이 호출한 IAM 사용자나 역할 세션 ARN을 직접 지정해 허용하면, 자격 증명 기반 정책에 Allow가 없어도 허용됩니다. 역할 ARN으로 지정한 경우에는 권한 경계와 세션 정책의 제한을 받습니다.

같은 요청을 버지니아 리전 버킷에 보내면 SCP의 명시적 Deny에 걸려 첫 단계에서 끝납니다. 거부 메시지에는 어느 유형이 막았는지가 적히므로(because no permissions boundary allows…), 4부의 디버깅은 이 표를 거꾸로 짚어 가는 일입니다.

계정을 넘는 요청은 양쪽이 모두 허용해야 한다

계정 A의 역할이 계정 B의 버킷을 읽으려면, AWS는 두 번 평가합니다. A 쪽에서는 호출자의 자격 증명 기반 정책(과 A의 SCP, 경계)이 허용하는지, B 쪽에서는 버킷 정책(과 B의 RCP)이 A의 주체를 허용하는지 봅니다.

둘 다 Allow일 때만 통과합니다. 같은 계정에서는 한쪽만 허용해도 됐던 것과 다른 점입니다. B의 관리자는 버킷 정책으로, A의 관리자는 자기 정책으로 각자 문을 엽니다.

STS는 몇 시간짜리 열쇠를 찍어 내는 곳이다

STS는 역할을 맡겠다는 요청을 받아 임시 자격 증명(Access Key ID, Secret Access Key, Session Token, 만료 시각)을 발급합니다. 역할이 키 없이 동작하는 비밀이 바로 이 서비스입니다.

이후 호출은 원래 신원이 아니라 assumed-role/역할명/세션명으로 기록됩니다. 세션 이름에 사람이나 작업 ID를 넣어 두면 CloudTrail에서 누가 했는지 추적됩니다.

신뢰 정책은 역할에 붙는 리소스 기반 정책이라 Principal이 있고, 권한 정책은 자격 증명 기반 정책이라 Principal이 없습니다. 신뢰 정책은 KMS 키 정책과 함께, 같은 계정이라도 반드시 명시적으로 허용해야 하는 예외입니다.

세션은 기본 1시간, 역할 체인은 최대 1시간

AssumeRole의 DurationSeconds를 생략하면 세션은 1시간입니다. 15분부터 역할에 설정한 최대 세션 시간(1~12시간)까지 요청할 수 있습니다.

역할 세션으로 다시 다른 역할을 맡는 역할 체인에서는 최대 1시간으로 고정됩니다. 긴 배치 작업이 정확히 한 시간 뒤 실패한다면 이것부터 의심합니다.

  • 세션 태그: 세션에 키-값을 붙여 ABAC 조건으로 씁니다(최대 50개).
  • 소스 ID: SourceIdentity는 체인을 거쳐도 유지되어 원래 사람을 끝까지 추적합니다.
  • SDK 자동 갱신: SDK는 만료 전에 스스로 다시 맡으므로 앱은 만료를 신경 쓰지 않아도 됩니다.

임시 키로 서명한 Presigned URL은 지정한 기간보다 세션이 먼저 끝나면 그때 함께 만료됩니다.

IMDS가 열려 있으면 SSRF가 역할을 훔친다

IMDS는 인스턴스 안에서 HTTP로 누구나 부를 수 있습니다. 그래서 앱에 SSRF(서버가 공격자 대신 임의 URL을 요청하는 취약점) 하나만 있으면, 공격자가 169.254.169.254를 대신 불러 역할의 임시 키를 가져갈 수 있습니다.

IMDSv2는 먼저 PUT으로 세션 토큰을 받아야 하고, 응답 패킷의 홉 수를 제한합니다. 단순 GET만 되는 SSRF와 컨테이너 밖으로 새는 요청을 막는 장치입니다.

IMDSv2만 허용하도록 강제합니다

인스턴스 설정 HttpTokens=required로 v1을 끄고, SCP나 조건 키 ec2:MetadataHttpTokens로 v1 인스턴스 생성을 막습니다. 홉 제한 같은 세부 설정은 14장에서 다룹니다.

왜일까요? 이 확인이 없으면 EC2 생성 권한만 있는 사람이 관리자 역할을 붙인 인스턴스를 띄워 그 안에서 관리자가 되는 권한 상승이 가능합니다. 그래서 PassRole은 넘길 수 있는 역할 범위를 꼭 좁혀서 줍니다.

ECS는 실행 역할과 작업 역할을 나눈다

실행 역할은 ECS 에이전트가 태스크를 띄우는 동안 씁니다. ECR에서 이미지를 받고, CloudWatch Logs로 로그를 보내고, Secrets Manager에서 비밀을 꺼내 환경 변수로 넣는 일입니다.

작업 역할은 컨테이너 안의 앱 코드가 씁니다. 앱이 S3나 SQS를 부를 때의 권한입니다. 둘을 섞으면 앱이 비밀 전체를 읽을 수 있게 되거나, 반대로 태스크가 이미지를 못 받아 시작조차 못 합니다(설정은 14장).

교차 계정 역할에는 External ID를 건다

비용 분석 SaaS가 고객 계정의 역할을 맡아 데이터를 읽는다고 합시다. 악의적인 고객 B가 SaaS 설정 화면에 우리 계정의 역할 ARN을 적으면, SaaS는 B를 위해 일한다고 믿고 우리 역할을 맡게 됩니다. 이것이 혼동된 대리인 문제입니다.

해결은 SaaS가 고객마다 발급한 고유 값을 신뢰 정책 조건 sts:ExternalId로 요구하는 것입니다. B는 SaaS가 우리 계정용으로 보낼 External ID를 조작할 수 없으므로 우리 역할을 맡게 만들 수 없습니다.

AWS 서비스도 대리인이 될 수 있다

{
  "Effect": "Allow",
  "Principal": {"Service": "sns.amazonaws.com"},
  "Action": "sqs:SendMessage",
  "Resource":
    "arn:aws:sqs:ap-northeast-2:111122223333:orders",
  "Condition": {
    "ArnEquals": {"aws:SourceArn":
    "arn:aws:sns:ap-northeast-2:111122223333:order-events"}
  }
}

리소스 정책에서 "Service": "sns.amazonaws.com"만 허용하면, 다른 계정의 SNS 토픽도 우리 큐에 메시지를 넣을 수 있습니다. SNS라는 서비스 자체는 모든 고객이 공유하기 때문입니다.

그래서 서비스 Principal을 허용할 때는 aws:SourceArn(어느 리소스를 위해)이나 aws:SourceAccount(어느 계정을 위해)를 함께 겁니다. 서비스 간 혼동된 대리인을 막는 External ID 역할입니다.

MFA는 피싱에 강한 것부터 고른다

MFA는 비밀번호 외에 "가진 것"을 하나 더 요구합니다. AWS가 지원하는 방식은 패스키·보안 키(FIDO), 가상 인증 앱(TOTP), 하드웨어 TOTP 토큰입니다. 루트와 IAM 사용자는 종류를 섞어 최대 8개까지 등록할 수 있습니다.

AWS는 FIDO 방식을 권장합니다. 공개 키 서명이 도메인에 묶여 있어 가짜 로그인 페이지에 6자리 코드를 넘겨주는 식의 피싱이 통하지 않기 때문입니다.

{
  "Effect": "Deny",
  "Action": ["iam:*", "ec2:TerminateInstances"],
  "Resource": "*",
  "Condition": {"BoolIfExists": {
    "aws:MultiFactorAuthPresent": "false"
  }}
}

BoolIfExists를 쓰는 이유: 장기 Access Key 요청에는 이 키가 아예 없어서, Bool만 쓰면 Deny가 걸리지 않고 빠져나갑니다.

Access Key는 만들지 않는 것이 최선이다

장기 키가 필요한 곳은 생각보다 적습니다. 서버는 역할, 사람은 SSO, CI는 OIDC, 온프레미스 서버는 IAM Roles Anywhere(X.509 인증서로 역할을 맡음)로 대신할 수 있습니다.

그래도 써야 한다면 사용자당 키는 최대 2개입니다. 이 두 칸이 무중단 교체를 위해 존재합니다. 그리고 키 사용 정책에 출발 IP나 VPC 조건을 걸어 새어 나가도 쓸 수 없게 합니다.

  1. 새 키 생성

    두 번째 칸에 새 키를 만듭니다.

  2. 앱 교체 배포

    모든 사용처를 새 키로 바꿉니다.

  3. 옛 키 비활성화

    바로 삭제하지 않고 꺼서 문제를 봅니다.

  4. 마지막 사용 확인

    get-access-key-last-used로 끊겼는지 봅니다.

  5. 옛 키 삭제

    이상이 없으면 지웁니다.

사람은 Identity Center로 역할을 맡는다

IAM Identity Center(옛 AWS SSO)는 여러 계정의 사람 접근을 한곳에서 관리합니다. 사용자는 자체 디렉터리나 Okta, Entra ID 같은 외부 IdP에서 가져옵니다.

관리자는 권한 세트(정책 묶음)를 정의하고 "사용자·그룹 × 계정 × 권한 세트"로 할당합니다. 그러면 각 계정에 AWSReservedSSO_로 시작하는 역할이 생기고, 사용자는 포털에서 계정과 역할을 골라 임시 자격 증명으로 들어갑니다.

  1. IdP 로그인SAML 또는 OIDC, MFA
  2. 접근 포털계정·권한 세트 선택
  3. 역할 세션계정의 SSO 역할
  4. 콘솔·CLI몇 시간짜리 임시 키

SAML은 브라우저용, OIDC는 워크로드용이다

페더레이션은 "외부에서 인증한 신원을 AWS 역할로 바꾸는 것"입니다. SAML 2.0은 XML 어설션을 브라우저가 실어 나르는 사내 SSO 표준이고, OIDC는 JWT를 쓰는 OAuth 2.0 위의 인증 계층으로 앱과 워크로드에 맞습니다(원리는 7장).

어느 쪽이든 IAM에 IdP를 등록하고, 역할의 신뢰 정책이 그 IdP의 특정 주장(그룹, sub)을 조건으로 허용하는 구조는 같습니다.

[sso-session corp]
sso_start_url = https://corp.awsapps.com/start
sso_region = ap-northeast-2

[profile prod-readonly]
sso_session = corp
sso_account_id = 444455556666
sso_role_name = ReadOnly
region = ap-northeast-2

$ aws sso login --sso-session corp
$ aws s3 ls --profile prod-readonly

ABAC는 태그가 같으면 허용하는 규칙 하나다

{
  "Effect": "Allow",
  "Action": ["ec2:StartInstances",
             "ec2:StopInstances"],
  "Resource": "*",
  "Condition": {"StringEquals": {
    "aws:ResourceTag/project":
      "${aws:PrincipalTag/project}"
  }}
}

역할 이름이나 ARN 목록으로 권한을 주는 방식을 RBAC라 하면, ABAC는 속성(태그)을 비교해 권한을 줍니다.

이 정책 하나로 "project=pay 태그를 가진 사람은 같은 태그의 인스턴스만" 켜고 끌 수 있습니다. 새 프로젝트가 생겨도 정책을 고치지 않고 태그만 붙이면 됩니다. 태그는 SSO 속성이나 세션 태그로 주체에 실립니다.

ABAC는 태그를 지키는 규칙과 짝이어야 한다

ABAC의 약점은 태그 자체가 권한이 된다는 점입니다. 누군가 리소스의 project 태그를 자기 값으로 바꿀 수 있다면, 남의 리소스를 가져가는 셈입니다.

그래서 리소스를 만들 때 태그를 강제하는 aws:RequestTag, 바꿀 수 있는 태그 키를 제한하는 aws:TagKeys 조건과, 태그 변경 API(ec2:CreateTags 등)를 막는 Deny를 함께 둡니다.

외부 접근 분석은 정책을 실행해 보는 것이 아니라 논리 추론으로 "가능한 모든 요청 중 외부가 통과하는 것이 있는가"를 증명합니다. 외부 접근 분석기는 리전마다 켜야 하고, 사용자 지정 검사는 CI에서 정책 변경을 막는 관문으로 쓰기 좋습니다.

마지막 접근 정보는 줄일 권한을 알려 준다

$ JOB=$(aws iam generate-service-last-accessed-details \
    --arn arn:aws:iam::111122223333:role/app-server \
    --granularity ACTION_LEVEL --query JobId --output text)
$ aws iam get-service-last-accessed-details \
    --job-id "$JOB" \
    --query 'ServicesLastAccessed[].[ServiceNamespace,
             LastAuthenticated]' --output text
s3        2026-11-16T09:12:44Z
sqs       2026-11-17T01:03:10Z
dynamodb  None

IAM은 주체나 정책이 허용한 서비스(일부 서비스는 액션 단위까지)를 마지막으로 언제 썼는지 기록합니다. 서비스 단위 기록은 최소 400일치가 남습니다.

위 결과에서 dynamodb는 한 번도 쓰이지 않았습니다. 정책에서 빼도 되는 후보입니다. 단, iam:PassRole은 추적되지 않으므로 이 기록만 보고 지우면 안 됩니다.

3부

계정을 나누고, 조직으로 묶고, 천장을 씌운다

계정이 가장 강한 경계라면, 경계를 여러 개 두는 것이 가장 강한 격리입니다. 그 많은 계정을 한 몸처럼 다스리는 Organizations, SCP, RCP, Control Tower를 봅니다.

계정 하나에 모든 것을 두면 경계가 사라진다

계정 하나에 prod와 dev를 같이 두면, dev에서 실험하던 사람의 실수 한 번(terraform destroy, 과한 정책)이 곧 prod 장애가 됩니다. IAM으로 막을 수는 있지만 정책이 복잡해질수록 구멍도 늘어납니다.

계정을 나누면 기본값이 "서로 아무것도 못 함"이 됩니다. 필요한 접근만 교차 계정 역할로 엽니다.

  • 보안: 침해나 키 유출이 한 계정 안에 갇힙니다.
  • 할당량: 서비스 할당량이 계정마다 따로라 dev 부하가 prod 한도를 먹지 않습니다.
  • 비용: 계정별 청구서가 곧 팀·환경별 비용입니다.
  • 규정: 감사 대상 시스템만 별도 계정으로 떼어 범위를 줄입니다.

Organizations는 계정을 나무로 묶는다

AWS Organizations는 여러 계정을 하나의 조직으로 묶습니다. 조직을 만든 계정이 관리 계정이 되고, 나머지는 멤버 계정입니다.

계정은 OU라는 폴더에 넣고, 정책은 루트·OU·계정에 붙여 아래로 상속됩니다. OU는 루트 아래 5단계까지 중첩할 수 있습니다. 통합 결제로 청구서가 하나로 모이고, 사용량이 합산되어 볼륨 할인과 Savings Plans가 조직 전체에 적용됩니다.

SCP는 계정 안 모든 주체의 천장이다

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOtherRegions",
    "Effect": "Deny",
    "NotAction": ["iam:*", "organizations:*",
      "sts:*", "cloudfront:*", "route53:*",
      "support:*", "budgets:*"],
    "Resource": "*",
    "Condition": {"StringNotEquals": {
      "aws:RequestedRegion": ["ap-northeast-2",
                              "ap-northeast-1"]
    }}
  }]
}

SCP는 멤버 계정의 IAM 사용자, 역할, 루트까지 할 수 있는 최대치를 정합니다. 권한을 주지는 않습니다. 계정 관리자가 AdministratorAccess를 붙여도 SCP 밖의 일은 못 합니다.

이 예는 쓰지 않는 리전을 막습니다. NotAction으로 글로벌 서비스를 뺀 이유는, 이들의 API가 us-east-1 등 고정 리전으로 들어오기 때문입니다. 빼지 않으면 IAM 작업조차 막힙니다.

SCP는 거부 목록으로 쓰고, 예외를 기억한다

SCP를 켜면 모든 대상에 FullAWSAccess(모두 허용)가 붙습니다. 그 위에 막을 것만 Deny로 추가하는 거부 목록 방식이 운영하기 쉽습니다. 허용 목록 방식은 상속 경로의 모든 단계에 Allow가 있어야 해서, 하나만 빠져도 계정 전체가 멈춥니다.

정책 하나는 10,240자, 루트·OU·계정마다 직접 붙일 수 있는 SCP는 10개까지입니다.

SCP가 닿지 않는 곳

관리 계정의 주체, 서비스 연결 역할, 조직 밖 계정의 주체에는 적용되지 않습니다. 그래서 관리 계정에는 워크로드를 두지 않습니다.

자주 쓰는 가드레일

조직 탈퇴 금지, CloudTrail·GuardDuty 끄기 금지, 루트 사용 금지, 미사용 리전 차단, IMDSv1 인스턴스 생성 금지.

RCP는 리소스 쪽에서 조직 밖을 막는다

{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": "*",
  "Condition": {
    "StringNotEqualsIfExists": {
      "aws:PrincipalOrgID": "o-a1b2c3d4e5"
    },
    "BoolIfExists": {
      "aws:PrincipalIsAWSService": "false"
    }
  }
}

SCP는 "우리 주체가 무엇을 할 수 있나"를 제한할 뿐, 외부 주체가 우리 버킷에 들어오는 것은 막지 못합니다. 누군가 버킷 정책에 외부 계정을 열어 버리면 그대로 뚫립니다.

RCP는 멤버 계정의 리소스에 천장을 씌웁니다. 위 정책은 버킷 정책이 무엇을 허용하든 조직 밖 주체를 거부합니다(AWS 서비스 호출은 예외). S3, STS, KMS, SQS, Secrets Manager 등 지원 서비스에만 적용됩니다.

SCP와 RCP를 함께 써야 데이터 경계가 닫힌다

항목SCPRCP
제한 대상멤버 계정의 주체(루트 포함)멤버 계정의 리소스

예외관리 계정, 서비스 연결 역할에는 둘 다 적용 안 됨

AWS는 "신뢰하는 신원만, 신뢰하는 리소스에, 예상한 네트워크에서"를 데이터 경계라 부릅니다. SCP는 신원 쪽, RCP는 리소스 쪽, VPC 엔드포인트 정책(13장)은 네트워크 쪽 문을 맡습니다.

Control Tower가 모범 구성을 깔아 준다

계정 나누기, SCP, 로그 중앙화, SSO를 손으로 다 엮으려면 몇 주가 걸립니다. Control Tower는 이 묶음을 랜딩 존으로 자동 구성합니다. Security OU 아래 Log Archive와 Audit 계정, 조직 CloudTrail, Identity Center가 기본으로 깔립니다.

Account Factory로 새 계정을 찍어 내면 처음부터 기준선이 적용된 상태로 태어납니다.

태그는 비용과 권한의 공통 언어다

계정으로 나눠도 한 계정 안의 비용은 섞입니다. 리소스에 service, env, owner, cost-center 같은 필수 태그를 정해 붙이면 Cost Explorer에서 서비스별 비용이 보이고, 주인 없는 리소스를 찾을 수 있습니다.

태그가 청구서에 나타나려면 결제 콘솔에서 비용 할당 태그로 활성화해야 하고, 활성화한 시점 이후 비용부터 반영됩니다.

  • 대소문자 통일: Env와 env는 다른 태그입니다. 키 표기를 정해 둡니다.
  • 강제: Organizations의 태그 정책으로 허용 값을 정하고, SCP의 aws:RequestTag 조건으로 태그 없는 생성을 막습니다.
  • IaC 기본 태그: Terraform AWS provider의 default_tags로 모든 리소스에 자동으로 붙입니다(Terraform 자체는 11장).

4부

거부를 읽고, 사고를 막고, 권한을 줄인다

IAM 문제는 대개 "왜 안 되지"와 "왜 됐지" 둘 중 하나입니다. 앞의 평가 로직을 손에 쥐고 실제 장애와 사고를 다루는 절차를 봅니다.

원리 실무 디버깅 순서, 사고 대응 절차, 체크리스트, 최소 권한을 만드는 실제 과정을 다룹니다.

AccessDenied는 다섯 단계로 좁힌다

  1. 누구인가

    sts get-caller-identity로 실제 호출 주체를 확인합니다.

  2. 메시지 읽기

    어느 정책 유형이 막았는지 문구에 적혀 있습니다.

  3. CloudTrail 확인

    실패 이벤트의 Action, Resource, 조건 값을 봅니다.

  4. 시뮬레이터

    정책 시뮬레이터로 고친 정책을 미리 판정합니다.

  5. 숨은 문 확인

    리소스 정책, KMS 키 정책, 엔드포인트 정책.

가장 흔한 실패는 1단계에서 이미 갈립니다. 기대한 역할이 아니라 옛 키나 다른 프로필로 호출하고 있는 경우가 의외로 많습니다.

정책을 "일단 *로 열어 보기"는 금물입니다. 원인을 모른 채 넓힌 권한은 다시 줄어들지 않습니다. 평가 로직의 어느 단계에서 막혔는지 짚어 내는 것이 목표입니다.

거부 메시지에 범인의 유형이 적혀 있다

User: arn:aws:sts::111122223333:assumed-role/
  app-server/i-0abc is not authorized to perform:
  s3:DeleteObject on resource:
  arn:aws:s3:::app-uploads/a.png
  because no permissions boundary allows the
  s3:DeleteObject action

User: … is not authorized to perform: ec2:RunInstances
  with an explicit deny in a service control policy

because no … allows는 암묵적 거부입니다. 그 유형의 정책에 Allow를 추가해야 합니다. with an explicit deny in …는 명시적 Deny입니다. Allow를 아무리 더해도 소용없고 그 Deny를 고치거나 조건을 맞춰야 합니다.

SCP처럼 계정 밖에서 온 거부라면 계정 안에서는 고칠 수 없습니다. 플랫폼팀에 정책 ARN과 함께 요청합니다. 일부 서비스는 인코딩된 메시지를 주며, sts decode-authorization-message로 풉니다.

CloudTrail과 시뮬레이터로 판정을 재현한다

# 최근 거부 이벤트 찾기(관리 이벤트, 90일)
$ aws cloudtrail lookup-events --max-results 50 \
    --lookup-attributes \
    AttributeKey=Username,AttributeValue=i-0abc \
  | jq '.Events[].CloudTrailEvent | fromjson
        | select(.errorCode=="AccessDenied")
        | {eventName, errorMessage}'

# 고친 정책으로 미리 판정
$ aws iam simulate-principal-policy \
    --policy-source-arn \
      arn:aws:iam::111122223333:role/app-server \
    --action-names s3:DeleteObject \
    --resource-arns 'arn:aws:s3:::app-uploads/*'

CloudTrail 이벤트에는 실패한 API 이름, 대상, 출발 IP, 사용된 세션까지 남습니다. 조건 키 때문에 막혔다면 여기서 실제 값(예: 다른 리전)이 보입니다. CloudTrail의 구조는 16장에서 다룹니다.

정책 시뮬레이터는 자격 증명 기반 정책과 경계, SCP를 함께 평가해 줍니다. 단, 리소스 정책이나 KMS 키 정책 같은 다른 계정의 문은 전부 재현하지 못합니다.

자주 만나는 거부 원인은 정해져 있다

증상숨은 원인확인할 곳
S3는 되는데 객체만 거부SSE-KMS 키 정책에 주체 없음KMS 키 정책, kms:Decrypt
EC2·ECS 생성 실패iam:PassRole 누락호출자 정책의 PassRole 범위
교차 계정만 실패한쪽만 허용상대 계정의 리소스 정책
어제 된 것이 오늘 거부SCP·경계 변경, 태그 변경CloudTrail의 정책 변경 이벤트
방금 만든 역할로 실패IAM 최종 일관성잠시 뒤 재시도
VPC 안에서만 실패VPC 엔드포인트 정책엔드포인트 정책(13장)

IAM 변경은 전 세계에 복제되며 반영까지 시간이 걸립니다. 그래서 역할을 만들고 같은 스크립트에서 바로 쓰는 코드는 간헐적으로 실패합니다. IAM 변경은 배포 준비 단계로 떼어 둡니다.

키가 새면 몇 분 안에 채굴기가 뜬다

공개 GitHub 저장소에 올라간 Access Key는 자동 수집기가 매우 빨리 찾아냅니다. 공격자는 보통 권한을 확인한 뒤 모든 리전에 큰 GPU 인스턴스를 띄우고, 새 IAM 사용자와 키를 만들어 발판을 남깁니다.

AWS도 공개 저장소를 감시하다 노출된 키를 찾으면 계정에 알리고, 비용이 큰 작업을 막는 격리 정책 AWSCompromisedKeyQuarantine(V2, V3 등)을 해당 사용자에게 붙입니다. 이 정책을 떼지 말고 아래 절차를 먼저 끝냅니다.

  1. 키 비활성화

    삭제가 아니라 비활성화. 영향 확인 후 지웁니다.

  2. 세션 무효화

    그 키로 맡은 역할 세션도 끊습니다(다음 슬라이드).

  3. CloudTrail 조사

    새 사용자·키·역할·정책 생성을 찾습니다.

  4. 모든 리전 정리

    안 쓰던 리전까지 인스턴스를 찾아 지웁니다.

  5. 원인 제거

    역할·OIDC로 옮기고 Support에 회신합니다.

새어 나간 임시 세션은 발급 시각으로 끊는다

{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {"DateLessThan": {
    "aws:TokenIssueTime": "2026-11-17T03:20:00Z"
  }}
}

임시 자격 증명은 만료 전까지 스스로 취소되지 않습니다. 대신 역할에 "이 시각 이전에 발급된 토큰은 모두 거부"하는 Deny를 붙이는 방식으로 끊습니다. 콘솔의 활성 세션 취소 버튼이 바로 이 정책을 넣습니다.

정상 앱도 함께 끊기지만, SDK가 곧바로 새 세션을 받으므로 잠깐의 오류로 끝납니다. EC2 인스턴스 키가 의심되면 인스턴스 자체도 격리합니다.

루트 계정 보호는 체크리스트로 끝낸다

  • MFA 등록: AWS는 루트 MFA를 기본으로 강제합니다. 패스키나 보안 키를 두 개 이상 등록해 분실에 대비합니다.
  • Access Key 없음: 루트 키는 만들지 않고, 있다면 지웁니다.
  • 복구 수단 잠금: 루트 이메일은 개인 메일이 아닌 팀 메일 그룹으로, 전화번호는 회사 번호로 둡니다.
  • 대체 연락처: 결제·운영·보안 연락처를 등록해 AWS 알림을 놓치지 않습니다.

멤버 계정은 루트 자격 증명을 없앤다

Organizations의 루트 접근 중앙 관리를 켜면 멤버 계정의 루트 비밀번호, 키, MFA를 지울 수 있고, 새 계정은 루트 자격 증명 없이 태어납니다. 루트 작업은 관리 계정에서 대신 수행합니다.

루트 로그인은 그 자체가 경보입니다

CloudTrail의 루트 ConsoleLogin 이벤트에 알람을 걸어 둡니다. 계획에 없던 루트 로그인은 사고로 다룹니다.

최소 권한은 관찰해서 깎아 만든다

  1. 좁은 출발필요해 보이는 AWS 관리형
  2. 관찰stage에서 실제 호출 수집
  3. 정책 생성Access Analyzer 초안
  4. 검증·배포정책 검사, IaC 반영
  5. 주기적 정리마지막 접근·미사용 분석

처음부터 완벽한 정책을 손으로 쓰기는 어렵습니다. stage 환경에서 앱을 돌려 CloudTrail에 쌓인 호출로 Access Analyzer가 정책 초안을 만들게 하고, Resource를 실제 ARN으로 좁혀 IaC에 넣습니다. 이후 분기마다 마지막 접근 정보로 쓰이지 않는 권한을 걷어 냅니다.

권한 경계로 역할 생성을 안전하게 위임한다

{
  "Effect": "Allow",
  "Action": ["iam:CreateRole",
             "iam:PutRolePermissionsBoundary"],
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": {"StringEquals": {
    "iam:PermissionsBoundary":
      "arn:aws:iam::111122223333:policy/app-boundary"
  }}
}

모든 역할 요청이 플랫폼팀을 거치면 병목이 됩니다. 그렇다고 개발자에게 역할 생성 권한을 그냥 주면 관리자 역할을 만들 수 있습니다.

해법은 "app-boundary를 경계로 붙인 역할만 만들 수 있다"는 조건입니다. 여기에 경계 정책 자체를 수정·삭제하는 것과 경계를 떼는 것(iam:DeleteRolePermissionsBoundary)을 Deny하면, 개발자가 만든 역할은 무엇을 붙여도 경계 밖으로 나갈 수 없습니다.

운영 권한은 평소엔 닫고 필요할 때 연다

prod 계정에 사람이 관리자 권한으로 상시 접근하면, 실수와 탈취의 위험이 늘 열려 있습니다. 기본은 읽기 전용 권한 세트이고, 변경은 파이프라인 역할만 합니다.

장애 대응처럼 쓰기 권한이 꼭 필요할 때는 승인을 받아 정해진 시간만 관리자 권한 세트를 할당하는 방식(Identity Center와 연동하는 임시 상승 접근, 예: AWS 오픈소스 TEAM)을 씁니다. 세션 이름과 SourceIdentity로 누가 무엇을 했는지 남깁니다.

비상용 접근 경로를 따로 둡니다

IdP 장애로 SSO가 멈추면 아무도 못 들어갑니다. MFA를 건 비상용(break-glass) 역할이나 사용자를 금고에 보관하고, 사용 시 알람이 울리게 합니다.

사람 대신 파이프라인이 바꾼다

11장의 OIDC 배포 역할이 prod 변경의 유일한 통로가 되면, 모든 변경이 PR 리뷰와 기록을 거칩니다.

정리

  • AWS는 클라우드를, 고객은 그 안을 책임집니다. 관리형일수록 경계가 올라가지만 데이터와 IAM 권한은 언제나 고객 몫입니다.
  • 설계 단위는 AZ, 격리 단위는 계정입니다. AZ 하나를 잃어도 버티게 만들고, 환경과 기능은 계정으로 나눠 폭발 반경을 자릅니다.
  • IAM은 기본 거부, 명시적 Deny 우선, 천장의 교집합입니다. 계정을 넘으면 양쪽 모두의 허용이 필요합니다.
  • 장기 키 대신 역할과 임시 자격 증명을 씁니다. EC2는 인스턴스 프로파일, ECS는 작업 역할, EKS는 IRSA·Pod Identity, 사람은 Identity Center, CI는 OIDC입니다.
  • SCP와 RCP는 조직의 천장이고, 최소 권한은 관찰로 깎아 만듭니다. 거부 메시지와 CloudTrail이 어느 문에서 막혔는지 알려 줍니다.

스스로 점검 (1)

  1. RDS를 쓰면 데이터 유출 책임도 AWS로 넘어가나요?

    아닙니다. OS와 엔진 패치는 AWS 몫이지만 보안 그룹, IAM 권한, 암호화 선택, 데이터 자체는 고객 책임으로 남습니다.

  2. 다른 팀과 "us-east-1a에 두자"고 맞췄는데 지연이 다릅니다. 왜일까요?

    오래된 리전에서는 계정마다 AZ 이름이 다른 물리 AZ에 배정될 수 있습니다. 계정 간에는 AZ ID(use1-az1 등)로 맞춰야 합니다.

  3. ECS 태스크에 작업 역할을 붙였는데 앱이 옛 IAM 사용자로 호출합니다. 원인 후보는?

    이미지나 태스크 정의에 AWS_ACCESS_KEY_ID 환경 변수가 남아 있는 경우입니다. SDK 체인에서 환경 변수가 컨테이너 자격 증명보다 먼저 잡힙니다.

  4. 자격 증명 기반 정책이 s3:*를 허용하는데 DeleteObject만 거부됩니다. 어디를 보나요?

    권한 경계, 세션 정책, SCP 같은 천장과 어딘가의 명시적 Deny입니다. 거부 메시지가 어느 유형인지 알려 줍니다.

  5. 교차 계정 S3 읽기에서 버킷 정책만 열면 왜 부족한가요?

    교차 계정 요청은 호출자 계정과 리소스 계정을 따로 평가하고 둘 다 허용해야 합니다. 호출자 쪽 자격 증명 기반 정책에도 Allow가 필요합니다.

스스로 점검 (2)

  1. EC2 생성 권한만 있는 사람에게 iam:PassRole을 *로 주면 어떤 일이 가능해지나요?

    관리자 역할을 붙인 인스턴스를 띄워 그 안에서 관리자 권한을 얻는 권한 상승이 가능합니다. PassRole은 넘길 역할 ARN과 서비스를 좁혀서 줍니다.

  2. IRSA 신뢰 정책에서 sub 조건을 빼면 무엇이 문제인가요?

    그 클러스터의 모든 서비스 어카운트 토큰이 역할을 맡을 수 있게 됩니다. 사실상 클러스터의 모든 Pod가 같은 권한을 갖습니다.

  3. 외부 SaaS 연동 역할에 External ID가 없으면 어떤 공격이 가능한가요?

    다른 고객이 우리 역할 ARN을 자기 설정에 넣어 SaaS가 우리 역할을 맡게 만드는 혼동된 대리인 공격입니다. External ID로 요청이 누구를 위한 것인지 묶습니다.

  4. SCP로 막았는데 외부 계정이 우리 버킷을 여전히 읽습니다. 왜인가요?

    SCP는 우리 계정의 주체만 제한하고, 버킷 정책이 연 외부 주체는 제한하지 않습니다. 리소스 쪽 천장인 RCP나 버킷 정책 수정이 필요합니다.

  5. 노출된 키를 바로 삭제하지 않고 비활성화부터 하는 이유는?

    정상 시스템이 그 키를 쓰고 있었다면 즉시 장애가 나고 되돌릴 수 없습니다. 비활성화는 공격을 끊으면서도 영향 확인 뒤 되살릴 여지를 남깁니다.
