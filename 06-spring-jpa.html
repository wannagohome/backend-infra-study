1부

객체는 누가 만들고 누가 이어 주는가

5장에서 DIP를 다루며 "구현 객체는 누가 만들어 넣어 줄까"라는 질문이 남았습니다. 이 부는 그 질문에서 출발해, Spring이 객체를 대신 만들고 연결하는 방식과 그 객체를 쓸 때 지켜야 할 규칙을 봅니다.

이 장의 예제: 쇼핑몰 주문 API 서버

장 전체에서 주문 API 서버 하나를 따라갑니다. 클라이언트가 POST /orders를 보내면 서버는 재고를 줄이고, 결제사 API로 결제를 승인받고, 주문을 DB에 저장합니다. 테이블은 4장에서 본 member, orders와 같은 모양입니다.

백엔드 코드는 보통 세 계층으로 나눕니다. 컨트롤러는 HTTP 요청을 받아 해석하고, 서비스는 "재고 확인 후 결제 후 저장" 같은 업무 규칙을 담고, 리포지토리는 DB 읽기와 쓰기만 맡습니다. 바뀌는 이유가 다른 코드를 떼어 두는 것으로, 5장의 단일 책임 원칙을 계층 단위로 적용한 것입니다.

  1. 클라이언트POST /orders
  2. OrderController요청 해석, 응답 작성
  3. OrderService재고, 결제, 저장 순서
  4. OrderRepositorySQL 실행
  5. MySQLmember, orders

new를 직접 쓰면 구현에 묶인다

public class OrderService {
  private final PaymentClient pay =
      new KakaoPayClient("api-key");
  private final OrderRepository repo =
      new JdbcOrderRepository();

  public void order(Order o) {
    pay.approve(o.amount());
    repo.save(o);
  }
}

서비스가 결제사 인터페이스 PaymentClient를 쓰는 점은 좋습니다. 그런데 어떤 구현을 쓸지까지 스스로 new로 정합니다. 결제사를 토스로 바꾸려면 이 클래스를 고쳐야 하고, 테스트에서 가짜 결제 객체로 바꿔 끼울 수도 없습니다.

5장의 DIP(의존 역전 원칙)는 "구현 말고 추상에 의존하라"였습니다. 구현을 고르는 코드가 클래스 안에 있는 한 이 원칙은 반쪽만 지켜집니다.

조립하는 코드를 한곳으로 모은다

public class AppConfig {
  DataSource dataSource() { return new DataSource(…); }
  OrderRepository orderRepository() {
    return new OrderRepository(dataSource());
  }
  PaymentClient paymentClient() {
    return new KakaoPayClient("api-key");
  }
  OrderService orderService() {
    return new OrderService(
        paymentClient(), orderRepository());
  }
}

해법은 단순합니다. 서비스는 생성자로 필요한 것을 받기만 하고, "무엇을 만들어 누구에게 넣을지"는 AppConfig 같은 조립 전용 클래스가 정합니다. 결제사를 바꿀 때는 강조한 두 줄만 고치면 됩니다. 맨 위 DataSource는 DB 커넥션을 빌려주는 객체로, 4장의 커넥션 풀이 이 모양입니다.

하지만 객체가 수백 개가 되면 이 조립 코드도 거대해집니다. 같은 객체를 한 번만 만들기, 종료 때 자원 닫기, 모든 서비스에 트랜잭션 끼워 넣기까지 손으로 하게 됩니다. 이 반복을 통째로 떠맡는 것이 Spring입니다.

제어의 역전: 내가 부르지 않고 불려진다

제어의 역전(IoC)은 객체를 만들고 연결하고 호출하는 흐름의 주도권을 내 코드가 아니라 외부에 넘기는 것입니다. 라이브러리는 내가 필요할 때 호출하지만, 프레임워크는 정해진 흐름을 쥐고 있다가 적절한 때 내 코드를 호출합니다. 앞 슬라이드의 AppConfig도 작은 IoC입니다. 서비스는 자기 의존 객체를 고르지 않고 받기만 하니까요.

Spring에서는 IoC 컨테이너가 그 조립 담당입니다. 5장에서 본 리플렉션으로 클래스와 어노테이션을 읽어, 객체를 만들고 필요한 의존 객체를 넣어 주고, 애플리케이션이 끝날 때 정리합니다. 이렇게 필요한 객체를 밖에서 넣어 주는 방식을 의존성 주입(DI)이라고 합니다.

DI 덕분에 OrderService는 "PaymentClient 하나가 필요하다"고 선언만 하면 됩니다. 운영에서는 카카오페이 구현이, 테스트에서는 가짜 구현이 들어갑니다.

Spring은 세 장치로 코드를 평범하게 둔다

Spring이 지향하는 것은 비즈니스 코드를 POJO, 즉 특정 프레임워크 클래스를 상속하거나 구현하지 않는 평범한 자바 객체로 두는 것입니다. 그래야 프레임워크 없이 테스트하고, 기술을 바꿔도 업무 코드는 그대로 남습니다. 이를 위해 장치 세 개를 씁니다. DI는 방금 봤습니다.

AOP는 트랜잭션, 로깅처럼 여러 클래스에 반복되는 기능을 따로 떼어 내는 기법입니다. 지금은 이 정도로 알아 두고, 동작은 2부에서 봅니다. PSA는 기술마다 다른 API를 공통 인터페이스 뒤에 숨기는 것입니다. 예를 들어 SQL을 직접 보내는 Java 표준 API인 JDBC와, 객체를 테이블에 자동으로 저장해 주는 JPA(4부)는 트랜잭션을 여는 코드가 다르지만, Spring에서는 둘 다 @Transactional 하나로 씁니다.

장치하는 일없으면 생기는 일
IoC/DI객체 생성과 연결을 컨테이너가 맡음클래스마다 new와 조립 코드
AOP반복되는 공통 기능을 분리모든 메서드에 같은 코드 반복
PSA기술을 공통 인터페이스 뒤에 숨김DB 기술마다 다른 트랜잭션 코드

Spring과 Spring Boot는 맡은 일이 다르다

이 장에는 두 이름이 섞여 나오므로 먼저 구분합니다. Spring Framework는 IoC 컨테이너, AOP, 트랜잭션, 웹 MVC 같은 핵심 기능을 담은 본체입니다. 예전에는 이 본체를 쓰려면 XML이나 설정 클래스로 DB 연결, 웹 서버, 요청 데이터 변환기를 하나하나 등록해야 했습니다.

Spring Boot는 그 설정을 대신해 주는 도구입니다. 필요한 라이브러리를 묶은 starter 의존성(예: spring-boot-starter-web)을 추가하면, 흔히 쓰는 설정을 자동으로 등록하고 2장에서 본 WAS인 Tomcat을 애플리케이션 안에 넣어 java -jar 하나로 실행되게 합니다. 자동 설정이 어떻게 동작하는지는 3부에서 봅니다.

그래서 "Spring Boot 2.6부터 기본값이 바뀌었다"는 말은 본체가 아니라 Boot가 깔아 주는 설정이 바뀌었다는 뜻입니다. 이 장의 기본값은 Spring Boot 3.x 기준입니다.

컨테이너가 관리하는 객체가 Bean이다

// 1. 내 클래스: 표시만 하면 스캔이 찾음
@Service
public class OrderService { … }

// 2. 남의 클래스: 만드는 메서드를 등록
@Configuration
public class PaymentConfig {
  @Bean
  PaymentClient paymentClient() {
    return new KakaoPayClient("api-key");
  }
}

컨테이너가 만들고 관리하는 객체를 빈(Bean)이라 합니다. 컨테이너는 두 경로로 Bean을 압니다. 하나는 컴포넌트 스캔으로, 기동할 때 지정한 패키지의 클래스를 훑어 @Component가 붙은 것을 찾아 등록합니다. @Service, @Repository, @Controller는 계층 이름을 붙인 @Component입니다.

다른 하나는 앞의 AppConfig와 같은 모양입니다. @Configuration 클래스의 @Bean 메서드가 돌려준 객체를 등록합니다.

내 클래스는 스캔으로, 남의 클래스는 @Bean으로

두 방법은 쓰는 자리가 갈립니다. 외부 라이브러리의 KakaoPayClient에는 내가 어노테이션을 붙일 수 없으므로 @Bean 메서드로 만들어 등록합니다. 생성자 인자에 API 키를 넣는 것처럼 만드는 과정을 세밀하게 정해야 할 때도 @Bean이 맞습니다.

이렇게 등록된 Bean을 모두 담고 있는 컨테이너의 실체가 ApplicationContext입니다. Bean을 만들고 꺼내 주는 기본 기능(BeanFactory)에 이벤트 발행, 설정값 읽기 같은 기능을 더한 것입니다.

기준@Component 계열@Configuration + @Bean
붙이는 곳내가 만든 클래스설정 클래스 안의 메서드
발견 방식컴포넌트 스캔이 자동 등록메서드 반환값을 등록
주된 용도서비스, 리포지토리, 컨트롤러외부 라이브러리 객체, 세밀한 생성

의존성을 넣는 세 가지 방법

// 1. 생성자 주입 (권장)
private final PaymentClient pay;
OrderService(PaymentClient p) { this.pay = p; }

// 2. 수정자(setter) 주입
@Autowired
void setPay(PaymentClient p) { this.pay = p; }

// 3. 필드 주입
@Autowired private PaymentClient pay;

Bean이 등록됐으면 서로 넣어 줘야 합니다. @Autowired는 "여기에 맞는 타입의 Bean을 넣어 달라"는 표시입니다. 생성자가 하나뿐이면 Spring 4.3부터 이 표시를 생략할 수 있습니다.

생성자를 손으로 쓰는 대신 Lombok(컴파일 때 반복 코드를 생성해 주는 라이브러리)의 @RequiredArgsConstructor로 final 필드용 생성자를 만드는 경우가 많습니다.

생성자 주입을 권장하는 네 가지 이유

  • 불변: 필드를 final로 선언할 수 있어, 생성된 뒤에는 누구도 의존 객체를 바꾸지 못합니다. 실행 중에 결제 클라이언트가 바뀌는 일을 컴파일러가 막아 줍니다.
  • 누락 방지: 의존 객체 없이는 객체 자체를 만들 수 없으므로, 빠뜨리면 컴파일이나 기동 단계에서 바로 드러납니다. 필드 주입은 빠뜨려도 실행 중 NullPointerException으로 늦게 터집니다.
  • 순환 참조 조기 발견: A가 B를, B가 A를 필요로 하는 것을 순환 참조라 합니다. 둘 다 생성자로 요구하면 어느 쪽도 먼저 만들 수 없어 기동이 실패하고, 설계 문제가 그 자리에서 드러납니다. Spring Boot 2.6부터는 순환 참조를 기본으로 금지합니다.
  • 테스트 용이: 컨테이너 없이 new OrderService(fakePay, fakeRepo)로 바로 테스트할 수 있습니다. 필드 주입은 리플렉션으로 private 필드를 채우므로 컨테이너 밖에서는 채울 방법이 없습니다.

수정자 주입은 선택적이거나 실행 중 바뀌어야 하는 드문 의존성에만, 필드 주입은 테스트 코드 정도에만 씁니다.

같은 타입의 Bean이 여럿이면 골라 줘야 한다

@Component @Primary
class KakaoPay implements PaymentClient {}

@Component
class TossPay implements PaymentClient {}

// 이름으로 지정
OrderService(@Qualifier("tossPay")
             PaymentClient pay)

// 전부 받기: Bean 이름 → 객체
PayRouter(Map<String, PaymentClient> all)

결제사가 두 곳이 되면 PaymentClient 타입 후보가 둘입니다. 컨테이너는 무엇을 넣을지 몰라 기동에 실패합니다. @Primary는 기본으로 쓸 쪽을, @Qualifier는 Bean 이름으로 특정 쪽을 지정합니다.

마지막 줄처럼 Map으로 모두 받으면 요청마다 결제사를 골라 쓸 수 있습니다. 바꿔 끼울 수 있는 알고리즘을 인터페이스 뒤에 두는 이 구조를 전략 패턴이라 하며, 2부에서 다른 패턴과 함께 다시 봅니다.

Bean은 생성, 주입, 초기화 순으로 준비된다

  1. 객체 생성

    생성자를 호출합니다. 생성자 주입이면 의존 객체가 이때 함께 들어옵니다.

  2. 나머지 주입

    수정자 주입과 필드 주입 대상을 채웁니다.

  3. 초기화 콜백

    @PostConstruct 메서드가 실행됩니다. 모든 의존 객체가 채워진 첫 시점입니다.

  4. 사용

    애플리케이션이 Bean을 씁니다. 이 직전에 다른 객체로 감싸 바꿔치기하기도 합니다(2부).

  5. 소멸 콜백

    컨테이너가 닫힐 때 @PreDestroy 메서드가 자원을 정리합니다.

이 순서를 Bean의 생명주기라 합니다. 생성자에서 다른 Bean을 써서 캐시를 채우면 위험합니다. 수정자 주입 대상은 2단계에서야 채워지므로 아직 비어 있을 수 있습니다.

그래서 준비 작업은 @PostConstruct에, 커넥션이나 스레드 풀 닫기는 @PreDestroy에 둡니다. 서버를 내릴 때 처리 중인 요청을 마무리하고 자원을 닫는 절차가 이 5단계와 이어지며, 10장과 11장에서 배포 관점으로 다시 봅니다.

스코프: Bean을 몇 개, 언제까지 만들까

Bean의 스코프는 인스턴스를 몇 개 만들고 언제까지 살려 둘지에 대한 규칙입니다. 아무것도 지정하지 않으면 컨테이너 전체에서 하나만 만드는 singleton입니다. 1부 예제의 서비스와 리포지토리는 모두 이 기본값을 씁니다.

스코프인스턴스 수소멸 관리
singleton (기본)컨테이너당 하나컨테이너가 끝까지 관리
prototype꺼낼 때마다 새로만들어 준 뒤 손을 뗌
requestHTTP 요청마다 하나요청이 끝나면 소멸

함정이 하나 있습니다. 싱글톤 Bean에 prototype Bean을 주입하면 주입은 싱글톤이 만들어질 때 한 번뿐이라, 사실상 싱글톤처럼 쓰입니다. 매번 새 객체가 필요하면 ObjectProvider(필요할 때 컨테이너에서 Bean을 꺼내 주는 도우미)를 주입받아 쓸 때마다 꺼냅니다.

싱글톤 Bean은 상태를 가지면 안 된다

기본이 싱글톤인 이유는 요청마다 서비스 객체를 만들고 5장의 GC가 치우는 비용을 없애기 위해서입니다. 대신 객체 하나를 모든 요청 스레드가 동시에 씁니다.

서비스에 lastOrder 같은 변경 가능한 필드를 두면, 1장의 경쟁 상태(여러 스레드가 같은 값을 동시에 고쳐 결과가 꼬이는 현상)가 그대로 생깁니다. 요청별 값은 지역 변수나 파라미터로 다루면 5장에서 본 대로 스레드마다 따로 있는 스택에 놓이므로 안전합니다.

2부

트랜잭션 코드는 어디로 사라졌나

1부의 OrderService에는 커밋도 롤백도 없습니다. 그런데 @Transactional 한 줄이면 트랜잭션이 걸립니다. 컨테이너가 Bean을 넘겨주는 순간 무엇을 끼워 넣는지, 그 장치가 어떤 설계 패턴에서 왔는지 따라갑니다.

기초 원리 여기부터는 프레임워크 내부 동작을 다룹니다.

디자인 패턴은 되풀이되는 해법의 이름이다

디자인 패턴은 객체지향 설계에서 자꾸 마주치는 문제와 그 해법에 이름을 붙여 둔 것입니다. 1994년 네 명의 저자(흔히 GoF)가 23개를 정리한 책이 출발점입니다. 이름이 있으면 "여기는 전략 패턴으로"처럼 설계를 한마디로 주고받을 수 있습니다.

Spring 내부는 이 패턴들로 짜여 있어서, 패턴을 알면 Spring의 동작이 예측됩니다. 1부에서 이미 셋을 만났습니다.

싱글톤은 인스턴스를 하나만 두는 패턴입니다. GoF 방식은 생성자를 private으로 막고 static 필드에 하나를 보관해 클래스 스스로 유일함을 지킵니다. 그러면 테스트에서 바꿔 끼울 수 없습니다. Spring은 평범한 클래스를 컨테이너가 하나만 만들어 나눠 주는 방식이라, 클래스는 POJO로 남습니다.

팩토리는 객체를 만드는 방법을 한곳에 숨기는 패턴입니다. 쓰는 쪽은 "PaymentClient를 달라"고만 하고 어떤 구현을 어떻게 만드는지 모릅니다. BeanFactory와 @Bean 메서드가 이 역할입니다.

전략은 바꿔 끼울 알고리즘을 인터페이스 뒤에 두는 패턴으로, DI로 주입되는 모든 인터페이스가 그 예입니다. 이어서 나머지 셋인 템플릿 메서드, 옵저버, 프록시를 봅니다.

템플릿 메서드: 뼈대는 고정, 빈칸만 채운다

// 커넥션 획득, 실행, 예외 변환, 반납은
// JdbcTemplate 안에 고정되어 있다
List<Member> all = jdbc.query(
    "select id, name from member",
    (rs, rowNum) -> new Member(
        rs.getLong("id"), rs.getString("name")));

템플릿 메서드는 작업의 순서(뼈대)는 고정하고, 달라지는 단계만 바꿔 끼우게 하는 패턴입니다.

Java 프로그램이 DB와 대화하는 표준 API인 JDBC로 조회하면, 커넥션 얻기, SQL 실행, 예외 처리, 커넥션 반납을 매번 똑같이 씁니다. JdbcTemplate은 그 뼈대를 품고, 결과 한 행을 객체로 바꾸는 부분만 강조한 람다로 받습니다. 나중에 불려지도록 넘기는 이런 코드를 콜백이라 합니다.

옵저버: 주문 코드는 메일 코드를 모른다

// 발행: OrderService 안
events.publishEvent(new OrderPlaced(orderId));

// 구독: 별도 Bean
@Component
class OrderMailer {
  @TransactionalEventListener
  void on(OrderPlaced e) { mail.send(e); }
}

옵저버는 어떤 일이 일어났다는 사실(이벤트)을 발행하면, 관심 있는 구독자들이 알아서 반응하게 하는 패턴입니다. 주문 서비스는 메일, 알림, 포인트 적립 코드를 몰라도 되고, 구독자를 추가해도 주문 코드는 그대로입니다.

@TransactionalEventListener는 기본적으로 주문 트랜잭션이 커밋된 뒤에 실행됩니다. 주문이 롤백됐는데 "주문 완료" 메일이 나가는 일을 막기 위해서입니다.

프록시는 진짜 객체 앞에 선 대리인이다

마지막이자 이 부의 주인공인 프록시는 실제 객체와 같은 타입을 가진 대리 객체입니다. 호출을 먼저 받아 부가 기능을 실행하고, 진짜 일은 실제 객체에 맡깁니다(위임).

컨테이너가 다른 Bean에 넣어 주는 것이 실제 객체가 아니라 프록시라면, 호출하는 쪽은 코드 한 줄 바꾸지 않고도 모든 호출 앞뒤에 기능이 끼어듭니다. 사라진 트랜잭션 코드가 바로 여기에 있습니다.

여섯 패턴이 Spring에서 쓰이는 자리

지금까지 본 패턴을 Spring 안의 위치로 정리합니다. 프록시 행이 이 부의 나머지와 4부의 지연 로딩까지 이어집니다.

패턴핵심 아이디어Spring에서 쓰는 곳
싱글톤인스턴스를 하나만 유지기본 Bean 스코프
팩토리생성 방법을 한곳에 숨김BeanFactory, @Bean 메서드
전략알고리즘을 갈아 끼움DI로 주입되는 인터페이스
템플릿 메서드뼈대는 고정, 일부만 바꿈JdbcTemplate
옵저버이벤트를 구독자에게 통지publishEvent, 이벤트 리스너
프록시대리 객체가 호출을 가로챔AOP, @Transactional, 지연 로딩

같은 코드가 모든 서비스 메서드에 반복된다

public Order place(OrderReq r) {
  long t = System.nanoTime();
  try {
    return doPlace(r);   // 진짜 업무
  } finally {
    log.info("place {}ns", System.nanoTime() - t);
  }
}
// cancel(), refund(), MemberService.join() …
// 수십 개 메서드에 같은 다섯 줄

프록시를 어디에 쓰는지 예로 봅니다. 서비스 메서드마다 실행 시간을 로그로 남기고 싶다면, 강조한 측정 코드를 모든 메서드에 복사해야 합니다. 업무 코드보다 측정 코드가 길어지고, 로그 형식을 바꾸려면 수십 곳을 고쳐야 합니다.

트랜잭션, 권한 확인, 로깅처럼 여러 클래스에 가로로 걸친 기능을 횡단 관심사라 합니다. 이것을 한 모듈로 뽑아내는 것이 AOP입니다.

AOP: 무엇을, 어디에 끼울지 따로 적는다

@Aspect @Component
class TimingAspect {
  @Around("execution(* com.shop..*Service.*(..))")
  Object time(ProceedingJoinPoint jp)
      throws Throwable {
    long t = System.nanoTime();
    try { return jp.proceed(); }
    finally { log(jp, System.nanoTime() - t); }
  }
}

앞의 다섯 줄이 이 클래스 하나로 옮겨졌습니다. Aspect는 부가 기능 모듈입니다. 실행할 코드 time()이 Advice이고, @Around는 대상 메서드의 앞과 뒤를 모두 감싼다는 뜻입니다.

괄호 안 표현식이 Pointcut으로, "com.shop 아래 이름이 Service로 끝나는 클래스의 모든 메서드"를 고릅니다. 고른 실행 지점 하나하나가 JoinPoint이며, jp.proceed()가 실제 메서드를 호출합니다. Spring AOP의 JoinPoint는 메서드 실행뿐입니다.

프록시는 Bean 등록 순간에 바꿔치기된다

  1. Bean 생성과 주입

    컨테이너가 원본 OrderService를 만들고 의존 객체를 채웁니다.

  2. 후처리기 검사

    BeanPostProcessor가 Pointcut에 걸리는 메서드가 있는지 봅니다.

  3. 프록시 생성

    걸리면 원본을 감싼 프록시를 만들어 원본 대신 컨테이너에 등록합니다.

  4. 주입

    OrderController는 원본이 아니라 이 프록시를 주입받습니다.

1부 생명주기의 "사용" 직전 단계를 확대한 그림입니다. BeanPostProcessor는 초기화가 끝난 Bean을 받아 다른 객체로 바꿔 돌려줄 수 있는 확장 지점으로, AOP가 여기서 동작합니다.

부가 기능을 대상 코드에 엮는 일을 위빙이라 합니다. AOP 전용 도구인 AspectJ는 컴파일이나 클래스 로딩 때 바이트코드를 직접 고치지만, Spring AOP는 실행 중에 프록시를 덧씌웁니다. 설정이 단순한 대신 프록시를 거치는 호출에만 적용되며, 이 한계가 곧 @Transactional의 함정이 됩니다.

프록시 클래스를 실행 중에 만드는 두 방법

프록시는 실제 객체와 같은 타입이어야 합니다. 그런데 Spring은 우리 서비스 클래스를 미리 알 수 없으니, 기동 중에 프록시 클래스를 즉석에서 만들어야 합니다. 방법은 두 가지입니다.

JDK 동적 프록시는 Java 표준 기능입니다. java.lang.reflect.Proxy에 "이 인터페이스들을 구현한 객체를 만들어 달라"고 하면, 모든 메서드 호출을 하나의 처리기(InvocationHandler)로 보내는 클래스를 실행 중에 생성합니다. 5장의 리플렉션 위에 있는 기능이라 인터페이스가 반드시 있어야 하고, 만들어진 프록시는 그 인터페이스 타입일 뿐 OrderService 클래스 타입은 아닙니다.

CGLIB은 바이트코드를 생성하는 라이브러리로, 대상 클래스를 상속한 하위 클래스를 만들고 메서드를 오버라이드해 호출을 가로챕니다. 인터페이스가 없어도 되고 구체 클래스 타입으로 주입할 수 있습니다. 대신 상속과 오버라이드에 기대므로 final 클래스와 final 메서드는 가로챌 수 없습니다. 지금은 Spring에 포함되어 함께 배포됩니다.

Spring Boot는 기본으로 CGLIB을 쓴다

항목JDK 동적 프록시CGLIB
만드는 방법인터페이스 구현 클래스 생성대상 클래스의 하위 클래스 생성
조건인터페이스 필수클래스만 있어도 됨
구체 타입 주입불가 (인터페이스로만)가능
가로채지 못하는 것인터페이스에 없는 메서드final 클래스와 메서드

JDK 프록시를 쓰면, 컨트롤러가 OrderService 클래스 타입으로 주입받으려 할 때 프록시가 그 타입이 아니어서 기동이 실패합니다. 이런 혼란을 없애려고 Spring Boot는 2.0부터 spring.aop.proxy-target-class=true를 기본으로 두어, 인터페이스가 있어도 CGLIB을 씁니다.

프록시가 없다면 트랜잭션은 이렇게 쓴다

Connection con = dataSource.getConnection();
try {
  con.setAutoCommit(false);  // 트랜잭션 시작
  stockDao.decrease(con, itemId);
  orderDao.insert(con, order);
  con.commit();
} catch (Exception e) {
  con.rollback();
  throw e;
} finally {
  con.close();   // 풀에 반납
}

4장에서 트랜잭션은 "전부 되거나 전혀 안 되는" 작업 단위였고, DB 커넥션 하나 위에서 열립니다. JDBC 커넥션은 기본이 자동 커밋, 즉 SQL 한 문장마다 바로 커밋하는 모드라서, 여러 문장을 묶으려면 이를 끄고 직접 커밋해야 합니다.

문제는 둘입니다. 이 뼈대가 모든 서비스 메서드에 반복되고, 같은 커넥션을 DAO(리포지토리처럼 DB 접근만 맡는 객체)마다 인자로 넘겨야 합니다. JPA로 바꾸면 트랜잭션 API 자체가 달라져 전부 다시 써야 합니다.

트랜잭션 매니저가 기술 차이를 감춘다

두 번째 문제, 기술마다 API가 다른 문제는 1부에서 예고한 PSA로 풉니다. Spring은 트랜잭션을 시작, 커밋, 롤백하는 공통 인터페이스 PlatformTransactionManager를 두고, 기술별 구현을 Bean으로 등록합니다. JDBC나 MyBatis(4부에서 소개할 SQL 매퍼)에는 DataSourceTransactionManager가, JPA에는 JpaTransactionManager가 쓰이며, Spring Boot는 클래스패스에 있는 라이브러리를 보고 알맞은 것을 자동으로 등록합니다.

첫 번째 문제, 반복되는 뼈대는 프록시로 풉니다. 앞 슬라이드의 try, commit, rollback, close 뼈대가 TransactionInterceptor라는 Advice 안에 한 번만 들어 있고, @Transactional은 "이 메서드를 그 Advice로 감싸라"는 Pointcut 표시입니다.

마지막 남은 질문은 커넥션을 인자로 넘기지 않고도 서비스 안의 여러 리포지토리가 어떻게 같은 커넥션을 쓰느냐입니다. 다음 슬라이드에서 단계별로 봅니다.

@Transactional은 프록시가 여는 트랜잭션이다

  1. 프록시가 호출을 받음

    TransactionInterceptor가 메서드의 트랜잭션 속성을 읽습니다.

  2. 커넥션 획득, 자동 커밋 끔

    트랜잭션 매니저가 풀에서 커넥션을 받아 현재 스레드에 묶습니다.

  3. 실제 메서드 실행

    안의 리포지토리는 스레드에 묶인 같은 커넥션을 찾아 씁니다.

  4. 커밋 또는 롤백

    정상 반환이면 커밋, 롤백 대상 예외면 롤백합니다.

  5. 커넥션 반납

    스레드와의 연결을 풀고 커넥션을 풀에 돌려줍니다.

비밀은 2단계입니다. 5장의 ThreadLocal, 즉 스레드마다 따로 값을 두는 저장소에 커넥션을 보관합니다(TransactionSynchronizationManager). 요청 하나는 스레드 하나가 처리하므로, 같은 스레드의 코드는 인자 없이도 같은 커넥션을 찾습니다.

이 그림에서 운영에 중요한 사실이 하나 나옵니다. 트랜잭션이 열려 있는 동안 4장의 커넥션 풀에서 커넥션 하나를 점유합니다. 5부의 장애 이야기는 모두 여기서 출발합니다.

내부 호출은 프록시를 거치지 않는다

@Service
public class OrderService {
  public void placeAll(List<Req> rs) {
    for (Req r : rs) place(r);
  }

  @Transactional
  public void place(Req r) { … }
}

자기 호출과 private 메서드에는 걸리지 않는다

같은 클래스 안에서 this.place()처럼 자기 메서드를 부르는 것을 자기 호출이라 합니다. this는 프록시가 아니라 실제 객체를 가리키므로, 프록시에 있는 트랜잭션 시작 코드를 건너뜁니다. 가장 깔끔한 해결은 트랜잭션 메서드를 다른 Bean으로 분리해 호출이 프록시를 거치게 하는 것입니다. 자기 자신을 주입받는 우회법도 있지만 구조를 흐립니다.

private 메서드에도 걸리지 않습니다. CGLIB은 하위 클래스에서 오버라이드해 가로채는데, private과 final 메서드는 오버라이드할 수 없기 때문입니다. Spring 6.0부터 CGLIB 프록시에서는 protected와 package-private 메서드까지 트랜잭션이 적용됩니다.

내부 호출까지 정말 필요하면 바이트코드를 직접 고치는 AspectJ 위빙을 켤 수 있지만, 빌드 설정이 복잡해지므로 대부분은 클래스 구조를 고치는 편이 낫습니다.

전파: 이미 트랜잭션이 있으면 어떻게 할까

주문 서비스가 트랜잭션 안에서 감사 로그(누가 언제 무엇을 했는지 남기는 기록) 서비스의 트랜잭션 메서드를 부르면, 둘을 하나로 묶을지 따로 둘지 정해야 합니다. 이 규칙이 전파 속성입니다. 기본값 REQUIRED는 바깥 트랜잭션이 있으면 참여하고 없으면 새로 엽니다. 물리적으로 트랜잭션 하나이므로 함께 커밋되고 함께 롤백됩니다.

REQUIRES_NEW는 바깥을 잠시 멈추고 커넥션을 하나 더 받아 독립 트랜잭션을 엽니다. 주문이 실패해도 남겨야 하는 감사 로그에 씁니다. 그 밖에 MANDATORY, NESTED 등이 있지만 실무는 이 둘이 대부분입니다.

Checked 예외는 기본으로 롤백되지 않는다

@Transactional
void a() { throw new IllegalStateException(); }
// RuntimeException: 롤백

@Transactional
void b() throws IOException {
  throw new IOException(); }
// Checked 예외: 커밋된다

@Transactional(rollbackFor = Exception.class)
void c() throws IOException { … }
// 모든 예외에서 롤백

프록시는 메서드가 예외로 끝나면 롤백할지 따져 봅니다. 기본 규칙은 RuntimeException과 Error에서만 롤백하는 것입니다.

5장에서 Checked 예외는 "호출자가 대응할 수 있는 상황", Unchecked는 "코드를 고쳐야 하는 상황"이었습니다. Spring은 대응 가능한 상황이면 작업 결과를 살릴 수도 있다고 보고 커밋합니다. 의도와 다르면 rollbackFor로 대상을 넓힙니다.

안쪽 예외는 잡아도 롤백 표시가 남는다

@Transactional
public void place(OrderReq r) {
  orderRepo.save(r.toOrder());
  try {
    pointService.add(r.memberId()); // REQUIRED
  } catch (RuntimeException e) {
    log.warn("포인트 실패, 주문은 진행");
  }
}
// 커밋 시점:
// UnexpectedRollbackException

포인트 적립이 실패해도 주문은 살리려고 예외를 잡았습니다. 그런데 커밋 시점에 UnexpectedRollbackException이 나고 주문까지 롤백됩니다.

이유는 REQUIRED의 정의에 있습니다. 안쪽과 바깥이 물리적으로 한 트랜잭션이라 안쪽만 따로 롤백할 수 없습니다. 그래서 안쪽 프록시는 예외가 지나갈 때 트랜잭션에 롤백 전용(rollback-only) 표시만 남기고, 바깥이 커밋하려 할 때 이 표시를 보고 롤백합니다. 정말 분리하려면 포인트 쪽을 REQUIRES_NEW로 두거나 트랜잭션 밖에서 호출합니다.

3부

요청은 어떤 길로 컨트롤러에 닿는가

2부까지는 서비스 Bean 안을 들여다봤습니다. 이제 바깥으로 나가, POST /orders 요청이 2장의 WAS에 도착해서 OrderController 메서드가 불리기까지 어떤 스레드가 어떤 객체를 거치는지 따라갑니다.

서블릿은 Java 웹 요청 처리의 표준 계약이다

2장에서 웹 서버는 연결을, WAS는 로직을 맡는다고 했습니다. Java 진영에서 WAS와 애플리케이션 사이의 약속이 서블릿입니다. 서블릿은 "HTTP 요청 객체를 받아 응답 객체에 결과를 쓰는" 메서드(service(request, response))를 가진 인터페이스이고, 이 계약을 지키면 어느 WAS에서든 돌아갑니다.

서블릿을 실행해 주는 쪽이 서블릿 컨테이너이며, Tomcat이 대표입니다. 소켓에서 바이트를 읽어 HTTP를 해석하고, 요청 객체를 만들고, 스레드를 배정해 서블릿을 호출하는 일을 Tomcat이 합니다.

Spring MVC 입장에서 보면 Tomcat에 등록된 서블릿은 DispatcherServlet 하나뿐입니다. 모든 요청이 이 서블릿으로 들어오고, 거기서 Spring이 컨트롤러를 고릅니다. Spring Boot는 이 Tomcat을 애플리케이션 안에 넣어(내장 Tomcat) 함께 띄웁니다.

요청 하나에 스레드 하나: Tomcat 스레드 풀

  1. OS 대기열

    커널이 2장의 3-way handshake를 마친 연결을 Tomcat이 꺼내 갈 때까지 쌓아 둡니다.

  2. 연결 수락

    Tomcat이 연결을 받아 관리 목록에 올립니다. 이 목록에도 상한이 있습니다.

  3. 워커 스레드 배정

    요청 데이터가 도착하면 풀에서 스레드 하나를 꺼내 이 요청에 붙입니다.

  4. 응답 후 반납

    응답을 다 쓰면 스레드를 풀로 돌려보냅니다.

Tomcat은 요청마다 스레드를 새로 만들지 않고 미리 만든 워커 스레드 풀에서 빌려줍니다. 스레드 생성 비용을 아끼고, 동시에 도는 스레드 수에 상한을 두기 위해서입니다.

중요한 점은 3단계의 스레드가 응답이 끝날 때까지 이 요청에 붙어 있다는 것입니다. DB나 결제 API를 기다리는 동안에도 스레드는 놀면서 점유됩니다. 2부에서 ThreadLocal로 커넥션을 찾을 수 있었던 것도 요청과 스레드가 1:1이기 때문입니다.

세 단계마다 상한이 하나씩 있다

앞 슬라이드의 단계마다 Spring Boot 설정이 하나씩 대응합니다.

Spring Boot 설정기본값의미
server.tomcat.accept-count1001단계 OS 대기열 길이
server.tomcat.max-connections81922단계 동시에 붙잡는 연결 수
server.tomcat.threads.max2003단계 동시 처리 요청 수

스레드 200개가 모두 바쁘면 새 요청은 연결만 된 채 기다리고, 연결 8192개와 대기열 100개까지 차면 새 연결이 거절됩니다. 200이라는 값은 1장에서 본 원리대로, 대부분의 시간을 I/O 대기로 보내는 웹 요청에 맞춘 큰 숫자입니다. 다만 4장의 HikariCP 커넥션 풀 기본값은 10개라서, 스레드 200개가 DB를 동시에 원하면 190개는 커넥션을 기다리게 됩니다. 5부에서 이 차이가 장애가 되는 모습을 봅니다.

Java 21 이상에서 spring.threads.virtual.enabled=true로 5장의 Virtual Thread를 켜면 요청마다 가벼운 스레드를 쓰므로 threads.max는 효과가 없어집니다. 그래도 커넥션 풀 10개라는 한계는 그대로입니다.

DispatcherServlet은 모든 요청의 정문이다

워커 스레드는 DispatcherServlet을 호출합니다. 모든 요청을 진입점 하나가 받아 알맞은 처리기로 나눠 주는 구조를 프런트 컨트롤러 패턴이라 합니다. 컨트롤러마다 서블릿을 따로 두면 인코딩, 예외 처리, JSON 변환 같은 공통 일을 컨트롤러마다 반복해야 하지만, 정문이 하나면 그 일을 한곳에서 처리할 수 있습니다.

정문 안에서 일어나는 일을 크게 나누면 아래와 같습니다. 각 단계의 이름은 다음 슬라이드에서 하나씩 풉니다.

  1. 핸들러 찾기URL과 메서드로
  2. 인자 만들기JSON을 객체로
  3. 컨트롤러 호출OrderController
  4. 반환값 쓰기객체를 JSON으로
  5. 예외 변환오류 응답으로

정문 안에서 다섯 부품이 차례로 일한다

  1. HandlerMapping

    URL과 HTTP 메서드로 처리할 컨트롤러 메서드(핸들러)를 찾습니다.

  2. HandlerAdapter

    ArgumentResolver로 메서드 인자를 하나씩 만들어 호출합니다.

  3. HttpMessageConverter

    요청 본문 JSON을 객체로, 반환 객체를 JSON으로 바꿉니다.

  4. HandlerExceptionResolver

    예외가 나면 공통 예외 처리기(@ControllerAdvice, 곧 봄)로 응답을 만듭니다.

  5. ViewResolver

    HTML 화면이 필요한 경우에만 뷰 이름을 템플릿으로 바꿉니다.

핸들러는 요청을 처리할 대상, 대개 컨트롤러 메서드입니다. HandlerAdapter가 따로 있는 이유는 핸들러 모양이 여럿이어도 정문 코드를 바꾸지 않기 위해서입니다.

ArgumentResolver는 인자 하나를 채우는 부품으로, 경로 변수, 쿼리 파라미터, 요청 본문 등 종류마다 하나씩 있습니다. 본문을 읽는 리졸버가 3단계의 컨버터를 부릅니다. API 서버는 HTML을 만들지 않으므로 5단계는 대개 건너뜁니다.

JSON과 객체 사이는 메시지 컨버터가 바꾼다

@RestController
@RequiredArgsConstructor
class OrderController {
  private final OrderService orderService;

  @PostMapping("/orders")
  OrderRes place(@RequestBody OrderReq req) {
    return orderService.place(req);
  }
}
// 요청 본문: {"itemId":7,"qty":2}
// 응답 본문: {"orderId":101,"status":"PAID"}

JSON은 {"itemId":7}처럼 이름과 값을 글자로 적는 데이터 형식으로, 웹 API의 사실상 표준입니다. @PostMapping은 1단계가 찾을 주소를, @RequestBody는 "본문을 이 타입으로 바꿔 달라"를 뜻합니다.

HttpMessageConverter는 본문 형식을 알리는 Content-Type 헤더를 보고 맞는 변환기를 고릅니다. JSON이면 Java의 대표 JSON 라이브러리 Jackson이 맡습니다. @RestController는 반환값을 뷰 이름이 아니라 응답 본문으로 보고 같은 컨버터로 JSON을 씁니다.

예외를 HTTP 응답으로 바꾸는 곳은 한 군데다

@RestControllerAdvice
class ApiExceptionHandler {
  @ExceptionHandler(OutOfStockException.class)
  @ResponseStatus(HttpStatus.CONFLICT)
  ErrorRes outOfStock(OutOfStockException e) {
    return new ErrorRes("OUT_OF_STOCK",
                        e.getMessage());
  }
}

서비스가 재고 부족으로 OutOfStockException을 던지면, 컨트롤러마다 try-catch를 쓰는 대신 정문의 4단계가 받아 처리합니다. @ControllerAdvice는 모든 컨트롤러에 공통으로 적용되는 예외 처리 모음이고, @RestControllerAdvice는 반환값을 JSON 본문으로 쓰는 판입니다.

예외 종류마다 @ExceptionHandler 메서드를 두어 상태 코드와 오류 본문을 정합니다. 어떤 상태 코드와 오류 형식을 고를지는 7장에서 다룹니다.

세 가로채기 지점은 서는 위치가 다르다

요청 앞뒤에 공통 처리를 끼우는 자리는 세 곳입니다. Filter는 서블릿 스펙의 부품으로, Tomcat이 DispatcherServlet을 부르기 전에 실행해 모든 요청을 봅니다. Interceptor는 Spring MVC의 부품으로, 정문이 핸들러를 고른 뒤 컨트롤러 호출 전후(preHandle, postHandle)에 실행됩니다. 2부의 AOP는 가장 안쪽에서 웹과 무관하게 Bean 메서드를 감쌉니다.

무엇을 어디에 둘지 고르는 기준

위치가 다르면 아는 정보와 할 수 있는 일이 다릅니다. Filter는 가장 바깥이라 요청 객체를 감싼 다른 객체로 바꿔 넘길 수 있고, Interceptor는 어떤 컨트롤러 메서드가 선택됐는지 압니다.

기준FilterInterceptorAOP
소속서블릿 스펙Spring MVCSpring 컨테이너
아는 정보요청과 응답 원본선택된 핸들러메서드와 인자
요청 교체요청 객체 감싸기 가능불가불가
예외 처리@ControllerAdvice 밖@ControllerAdvice 안@ControllerAdvice 안
대표 용도보안, 인코딩, 요청 로깅로그인 확인, 로깅트랜잭션, 실행 시간

Filter에서 난 예외는 DispatcherServlet 밖이라 @ControllerAdvice가 잡지 못하고 Boot의 기본 오류 처리로 넘어갑니다. 원하는 오류 형식이 필요하면 Filter 안에서 직접 응답을 씁니다. 인증과 인가를 맡는 Spring Security가 Filter 묶음으로 만들어진 이유는 7장에서 봅니다.

Spring Boot 자동 설정은 조건부 Bean이다

@AutoConfiguration
@ConditionalOnClass(DataSource.class)
class DataSourceAutoConfig {

  @Bean
  @ConditionalOnMissingBean
  DataSource dataSource(DataSourceProps p) {
    return new HikariDataSource(p.toConfig());
  }
}

지금까지 쓴 Tomcat, DispatcherServlet, 커넥션 풀, 트랜잭션 매니저를 우리는 등록한 적이 없습니다. Boot는 jar 안의 AutoConfiguration.imports 파일에서 자동 설정 클래스 목록을 읽고, 조건이 맞는 것만 Bean으로 등록합니다.

@ConditionalOnClass는 그 클래스가 클래스패스(JVM이 클래스를 찾는 경로, 곧 추가한 라이브러리)에 있을 때만 켜집니다. @ConditionalOnMissingBean은 내가 같은 타입을 직접 등록하지 않았을 때만 켜집니다. 그래서 내 설정이 늘 자동 설정을 이깁니다.

WebFlux는 스레드 대신 이벤트 루프를 쓴다

앞에서 본 스레드 풀 모델은 결제 API를 기다리는 동안에도 스레드를 붙잡습니다. 동시 요청이 수만 개면 스레드 수와 스택 메모리가 버티지 못합니다. 1장에서 본 C10K 문제(동시 연결 1만 개를 연결당 스레드로 감당하지 못하는 문제)와 같은 구조입니다.

WebFlux는 Spring의 또 다른 웹 스택으로, Tomcat 대신 Netty라는 네트워크 서버 위에서 1장의 이벤트 루프 방식으로 동작합니다. 기다리는 일을 커널에 맡기고 준비된 일만 처리하므로 적은 스레드로 많은 연결을 다룹니다. 결과는 "나중에 값이 올 것"을 나타내는 Mono(값 하나)와 Flux(값 여러 개) 타입으로 돌려줍니다.

대신 호출 경로 전체가 논블로킹이어야 효과가 있습니다. JDBC와 JPA는 결과가 올 때까지 스레드를 멈추는 블로킹 API라, 그대로 쓰면 몇 개 안 되는 이벤트 루프 스레드가 멈춥니다. 그래서 DB 중심 서비스는 MVC를 유지하고, 외부 호출을 대량으로 묶는 게이트웨이 같은 곳에 WebFlux를 고르는 경우가 많습니다. 5장의 Virtual Thread가 그 사이의 선택지로 떠오르고 있습니다.

4부

SQL은 누가, 언제 만드는가

요청이 OrderService에 닿았고 트랜잭션도 열렸습니다. 이제 주문 객체를 4장의 테이블에 저장하고 읽어 오는 마지막 구간입니다. JPA가 SQL을 대신 만드는 원리와, 그 원리를 모를 때 쿼리가 폭증하는 이유를 봅니다.

JDBC로 직접 하면 변환 코드가 반복된다

PreparedStatement ps = con.prepareStatement(
  "insert into orders(member_id, status)"
  + " values (?, ?)");
ps.setLong(1, order.getMember().getId());
ps.setString(2, order.getStatus().name());
ps.executeUpdate();

ResultSet rs = …("select * from orders where id=?");
Order o = new Order(rs.getLong("id"), …);
// member는? member_id 숫자만 왔다

2부의 JDBC로 주문을 저장하면, 객체의 필드를 꺼내 SQL의 물음표 자리에 하나씩 넣습니다(PreparedStatement). 읽을 때는 결과 행(ResultSet)에서 열을 하나씩 꺼내 객체를 조립합니다.

필드 하나를 추가하면 INSERT, SELECT, 조립 코드를 모두 고쳐야 합니다. 더 곤란한 것은 마지막 주석입니다. 객체는 Member를 원하는데 테이블은 member_id 숫자만 줍니다.

객체와 테이블은 생각하는 방식이 다르다

앞 슬라이드의 어색함은 우연이 아닙니다. 객체 모델과 관계형 모델은 같은 데이터를 다른 규칙으로 표현하며, 이 차이를 패러다임 불일치라 합니다. 네 가지가 대표적입니다.

연관: 객체는 참조(order.member)로 다른 객체를 가리키고, 테이블은 4장의 외래 키(orders.member_id)로 다른 행을 가리킵니다. 참조는 한 방향이지만 외래 키는 JOIN으로 양쪽에서 쓸 수 있습니다.

그래프 탐색: 객체는 order.getMember().getAddress()처럼 점을 찍어 끝없이 따라가지만, SQL은 처음에 JOIN한 테이블까지만 가져옵니다. 어디까지 읽어 둘지 미리 정해야 합니다.

상속: 객체에는 상속이 있지만 테이블에는 없습니다. 카드 결제와 포인트 결제를 한 테이블에 둘지, 나눌지 매핑 규칙이 필요합니다.

동일성: 같은 주문 행을 두 번 읽으면 JDBC는 서로 다른 객체 두 개를 만듭니다. 객체 세계에서는 ==가 거짓이 되어, "같은 주문"이라는 사실이 흐려집니다.

이 변환을 매번 손으로 하지 않도록 도구가 대신 맡는 기법을 ORM(객체 관계 매핑)이라 합니다.

JPA는 명세, Hibernate는 구현이다

JPA는 Java ORM의 표준 명세로, 어노테이션과 인터페이스만 정합니다(원래 Java Persistence API였고 지금은 Jakarta Persistence로 이름이 바뀌었습니다). 실제로 SQL을 만들고 JDBC를 부르는 구현체가 Hibernate이며 Spring Boot의 기본값입니다.

그 위에 Spring Data JPA가 한 층 더 있습니다. 리포지토리 인터페이스만 선언하면 구현 클래스를 실행 중에 만들어 주는 Spring 모듈입니다. 우리 코드는 맨 왼쪽만 보고, 나머지 층이 차례로 일을 넘깁니다.

  1. OrderRepository내가 쓴 인터페이스
  2. Spring Data JPA구현을 자동 생성
  3. JPA 인터페이스EntityManager
  4. HibernateSQL 생성
  5. JDBCDB로 전송

JPA와 MyBatis는 SQL을 누가 쓰느냐가 다르다

한국 실무에서 JPA와 자주 비교되는 MyBatis는 ORM이 아니라 SQL 매퍼입니다. SQL은 개발자가 XML이나 어노테이션에 직접 쓰고, MyBatis는 그 결과를 객체 필드에 옮겨 주기만 합니다. JPA는 반대로 객체 변경을 보고 SQL을 대부분 스스로 만듭니다.

항목JPAMyBatis
SQL 작성대부분 자동 생성직접 작성해 매핑
강점CRUD 생산성, 변경 감지복잡한 통계 SQL 통제
약점동작을 모르면 쿼리 폭증반복 SQL, 객체 그래프 수동

"쿼리 폭증"이 무엇인지가 이 부의 후반부 주제입니다. 둘을 함께 쓰는 팀도 많습니다.

엔티티는 테이블과 짝지은 클래스다

@Entity @Table(name = "orders")
public class Order {
  @Id
  @GeneratedValue(strategy = IDENTITY)
  private Long id;

  @ManyToOne(fetch = FetchType.LAZY)
  @JoinColumn(name = "member_id")
  private Member member;

  @OneToMany(mappedBy = "order")
  private List<OrderItem> items;
}

@Entity가 붙은 클래스가 엔티티로, 객체 하나가 테이블 행 하나에 대응합니다. @Id는 PK이고, IDENTITY는 4장의 AUTO_INCREMENT로 DB가 번호를 매긴다는 뜻입니다.

강조한 두 줄이 연관 불일치의 해법입니다. "주문 여럿이 회원 하나에 속한다"(@ManyToOne)와 외래 키 열 이름을 적으면, JPA가 참조와 member_id를 오갑니다. 반대쪽 items의 mappedBy는 "외래 키는 OrderItem 쪽에 있으니 거기서 관리한다"는 표시입니다. fetch는 뒤에서 봅니다.

리포지토리는 인터페이스만 쓰면 된다

public interface OrderRepository
    extends JpaRepository<Order, Long> {

  List<Order> findByStatus(OrderStatus s);

  @Query("select o from Order o"
       + " where o.member.id = :memberId")
  List<Order> findOfMember(Long memberId);
}
// save, findById, findAll, delete는 상속

JpaRepository를 상속하면 저장, ID 조회, 전체 조회, 삭제를 공짜로 얻습니다. 강조한 줄처럼 메서드 이름을 규칙대로 지으면 이름을 해석해 쿼리를 만들어 주는데, 이를 메서드 이름 쿼리라 합니다.

@Query 안의 문장은 SQL이 아니라 JPQL입니다. 테이블과 열 대신 엔티티와 필드(Order, o.member.id)를 대상으로 쓰는 쿼리 언어이고, Hibernate가 실행 직전에 SQL로 번역합니다. 구현 클래스는 Spring Data가 2부의 프록시로 만들어 Bean으로 등록합니다.

영속성 컨텍스트는 엔티티를 담아 두는 작업 공간이다

리포지토리 아래에서 실제로 일하는 JPA 객체가 EntityManager이고, 그 안에 엔티티를 보관하는 메모리 공간이 영속성 컨텍스트입니다. Spring에서는 기본적으로 트랜잭션 하나와 수명이 같습니다.

JPA가 SQL을 바로 날리지 않고 이 공간을 거치는 덕분에, 앞에서 본 동일성 불일치가 풀리고 SQL을 모아 보낼 수 있습니다. 그림의 세 칸을 다음 슬라이드들에서 하나씩 봅니다.

1차 캐시: 같은 ID는 같은 객체로 돌려준다

// em: EntityManager
Order a = em.find(Order.class, 101L);
// select ... from orders where id=101

Order b = em.find(Order.class, 101L);
// SQL 없음: 1차 캐시에서 꺼냄

a == b   // true

find()는 먼저 1차 캐시, 즉 영속성 컨텍스트 안의 "ID → 엔티티" 지도를 봅니다. 없을 때만 SELECT하고, 읽은 엔티티를 지도에 넣어 둡니다.

그래서 같은 트랜잭션에서 같은 ID를 두 번 찾으면 같은 인스턴스가 나와 ==가 참입니다. 패러다임 불일치의 동일성 문제가 이렇게 풀립니다. 다만 트랜잭션이 끝나면 함께 사라지므로, 여러 요청이 공유하는 캐시는 아닙니다.

쓰기 지연: SQL은 flush 때 모아서 나간다

persist()로 저장해도 INSERT는 바로 나가지 않고 쓰기 지연 저장소에 쌓입니다. 모아 두면 여러 INSERT를 한 번에 보내는 JDBC 배치로 DB 왕복을 줄일 수 있습니다.

쌓인 변경을 SQL로 DB에 보내는 일이 flush입니다. flush는 커밋이 아닙니다. flush 후에도 롤백하면 모두 취소됩니다.

예외가 하나 있습니다. ID가 IDENTITY면 DB가 INSERT해야 번호가 생기므로, 1차 캐시에 넣을 ID를 얻으려고 persist 즉시 INSERT하고 배치도 쓸 수 없습니다.

  1. 트랜잭션 커밋 직전

    커밋하기 전에 자동으로 flush합니다.

  2. JPQL 쿼리 실행 직전

    JPQL은 DB에서 바로 읽으므로, 쌓인 변경이 결과에 반영되도록 먼저 flush합니다.

  3. 직접 호출

    em.flush()나 saveAndFlush()로 즉시 보냅니다.

변경 감지: save를 부르지 않아도 UPDATE된다

@Transactional
public void cancel(Long orderId) {
  Order o = orderRepo.findById(orderId)
                     .orElseThrow();
  o.cancel();   // status = CANCELED, save() 없음
}
// 커밋 직전 flush:
// 스냅샷과 비교 → 달라진 엔티티 발견
// update orders set status=? where id=?

영속성 컨텍스트는 엔티티를 처음 읽을 때 상태를 스냅샷으로 복사해 둡니다. flush 시점에 현재 값과 스냅샷을 비교해, 달라진 엔티티의 UPDATE를 만듭니다. 이것이 변경 감지입니다.

그래서 주문 취소는 "꺼내서 바꾸면 끝"입니다. 컬렉션의 객체를 고치듯 쓰면 되도록 만든 설계입니다. 반대로 트랜잭션 밖에서 바꾸면 비교할 영속성 컨텍스트가 없어 아무 일도 일어나지 않습니다.

save()는 persist 아니면 merge다

@Transactional(readOnly = true)
public class SimpleJpaRepository<T, ID> … {

  @Transactional
  public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
      em.persist(entity);
      return entity;
    }
    return em.merge(entity);
  }
}

Spring Data가 만들어 주는 리포지토리 구현의 실제 모양입니다. save()는 ID가 비어 있으면 새 엔티티로 보고 persist()를, 아니면 merge()를 부릅니다. 이미 영속 상태인 엔티티라면 변경 감지가 처리하므로 save는 필요 없습니다.

첫 줄도 눈여겨볼 만합니다. 리포지토리 자체에 @Transactional이 붙어 있어, 서비스 트랜잭션이 있으면 2부의 REQUIRED로 참여하고, 없으면 메서드 하나만큼의 짧은 트랜잭션을 엽니다.

엔티티는 네 가지 상태를 오간다

앞의 merge를 이해하려면 상태를 알아야 합니다. new로 막 만든 객체는 비영속, 영속성 컨텍스트가 관리하면 영속, 트랜잭션이 끝나 컨텍스트가 닫히면 준영속입니다. 1차 캐시, 변경 감지, 지연 로딩은 영속 상태에서만 동작합니다.

준영속 객체를 merge()하면 DB에서 다시 읽은 영속 엔티티에 값을 통째로 복사합니다. 비어 있는 필드도 그대로 덮어 null이 저장될 수 있으므로, 수정은 다시 조회해 변경 감지로 하는 편이 안전합니다.

readOnly=true는 변경 감지를 끈다

변경 감지에는 비용이 있습니다. 읽은 엔티티마다 스냅샷을 복사해 두고, flush 때 모든 필드를 비교해야 합니다. 주문 목록 1만 건을 읽기만 하는 조회에서는 낭비입니다.

@Transactional(readOnly = true)를 붙이면 Hibernate는 flush 모드를 수동으로 바꾸고 엔티티를 읽기 전용으로 다뤄, 스냅샷과 flush를 건너뜁니다. 대량 조회에서 메모리와 CPU를 아낍니다. JDBC 커넥션에도 읽기 전용 힌트가 전달되어 DB나 드라이버가 최적화에 쓸 수 있고, 4장의 읽기/쓰기 분리 구조에서는 이 속성을 보고 조회 트랜잭션을 Replica로 보내도록 구성하는 경우가 많습니다.

앞에서 본 SimpleJpaRepository처럼, 서비스 클래스에 readOnly = true를 기본으로 두고 쓰기 메서드에만 @Transactional을 다시 붙이는 방식을 흔히 씁니다.

지연 로딩은 프록시가 대신 서 있는 것이다

Order o = orderRepo.findById(101L).get();
// select ... from orders where id=101

Member m = o.getMember();
// m은 Hibernate 프록시, SQL 없음

m.getName();
// 이때 select ... from member where id=?

// 트랜잭션 밖에서 getName()을 부르면
// LazyInitializationException

엔티티 매핑에서 미뤄 둔 fetch입니다. 그래프 탐색 불일치 때문에 JPA는 주문을 읽을 때 회원까지 읽을지 정해야 합니다. 지연 로딩(LAZY)은 회원 자리에 Hibernate가 만든 프록시를 넣어 두고, 실제 값을 쓰는 순간 조회합니다. 즉시 로딩(EAGER)은 처음부터 함께 읽습니다.

프록시를 초기화하려면 열린 영속성 컨텍스트가 필요합니다. 트랜잭션이 끝난 뒤 건드리면 LazyInitializationException이 납니다. @ManyToOne과 @OneToOne은 기본이 EAGER라 직접 LAZY로 바꿔야 하며, 실무 원칙은 전부 LAZY입니다.

N+1: 쿼리 한 번이 N번을 부른다

List<Order> orders = orderRepo.findAll();
for (Order o : orders)
  o.getMember().getName();

-- 실제 SQL 로그
select * from orders                  -- 1번
select * from member where id=?       -- N번
select * from member where id=?
select * from member where id=?
…

주문 목록 화면에 주문자 이름을 함께 보여 준다고 합시다. 주문 100건을 읽으면, 반복문에서 주문마다 회원 프록시가 초기화되어 SELECT가 100번 더 나갑니다. 쿼리 1번이 N번을 부르는 이 현상이 N+1 문제입니다.

EAGER로 바꾸면 해결될까요? findAll()의 JPQL은 그대로 SQL로 번역되어 주문만 읽고, 그다음 EAGER를 채우려 다시 N번 조회합니다. 로딩 시점만 앞당겨질 뿐 N+1은 그대로입니다.

fetch join은 JOIN 한 번으로 함께 읽는다

@Query("select o from Order o"
     + " join fetch o.member")
List<Order> findAllWithMember();

@EntityGraph(attributePaths = "member")
List<Order> findByStatus(OrderStatus s);

-- 두 메서드 모두 SQL 한 번
select o.*, m.* from orders o
  join member m on m.id = o.member_id

N+1의 원인은 "회원이 필요하다"는 사실을 첫 쿼리가 몰랐다는 데 있습니다. fetch join은 JPQL에 join fetch로 그 사실을 알려, 4장의 JOIN 한 번으로 주문과 회원을 함께 읽고 회원 자리에 프록시 대신 실제 엔티티를 채웁니다.

@EntityGraph는 같은 일을 어노테이션으로 하는 방법입니다. JPQL을 쓰지 않는 메서드 이름 쿼리에도 붙일 수 있습니다.

배치 크기는 N번을 IN 절 몇 번으로 묶는다

spring.jpa.properties.hibernate:
  default_batch_fetch_size: 100

-- 주문 100건 + 회원 조회
select * from orders
select * from member
 where id in (?, ?, ?, … 100개)

세 번째 방법은 쿼리를 하나로 합치지 않고, 프록시를 초기화하는 쿼리를 모아 보내는 것입니다. 프록시 하나를 초기화할 때, 같은 영속성 컨텍스트에 아직 초기화되지 않은 회원 프록시가 더 있으면 최대 100개의 ID를 SQL의 IN 조건에 담아 한 번에 읽습니다.

주문 N건이면 쿼리는 1 + N/100번입니다. JOIN이 아니므로 행이 불어나지 않아, 다음 슬라이드에서 볼 fetch join의 한계에 걸리지 않습니다.

세 해법은 쿼리 수와 쓰는 자리가 다르다

방법쿼리 수적합한 경우
fetch join1ToOne 관계, 화면에 꼭 필요한 연관
@EntityGraph1메서드 이름 쿼리에 붙일 때
배치 크기1 + N/100컬렉션, 페이징이 필요한 조회

표의 "ToOne"은 @ManyToOne과 @OneToOne처럼 상대가 하나인 연관을, "컬렉션"은 @OneToMany처럼 상대가 여럿인 연관을 말합니다. 이 구분이 왜 중요한지는 fetch join이 컬렉션을 만났을 때 생기는 일에서 드러납니다.

fetch join은 컬렉션에서 두 가지 한계를 만난다

컬렉션 fetch join과 페이징: 주문 하나에 상품이 3개면 주문과 주문 상품을 JOIN한 결과는 3행이 됩니다. 이 상태에서 "주문 20건씩"을 SQL의 LIMIT으로 자르면 행 기준으로 잘려 어떤 주문은 상품 일부만 남습니다. 그래서 Hibernate는 LIMIT을 SQL에 넣지 않고 전체를 메모리로 읽은 뒤 페이징하며 경고 로그만 남깁니다. 주문이 수십만 건이면 메모리가 바닥납니다.

둘 이상의 컬렉션 fetch join: 주문 상품과 쿠폰 목록을 동시에 fetch join하면 행 수가 곱으로 불어납니다(상품 3 × 쿠폰 2 = 6행). 순서도 중복 구분도 없는 List 컬렉션, Hibernate 용어로 Bag은 어느 행이 어느 컬렉션 것인지 가려낼 수 없어 MultipleBagFetchException으로 막힙니다.

정석은 ToOne 관계만 fetch join으로 가져와 페이징하고, 컬렉션은 배치 크기에 맡겨 IN 절로 읽는 것입니다. 조회 전용 화면이라면 엔티티 대신 화면에 필요한 열만 담은 전달용 객체, 즉 DTO로 직접 조회하는 방법도 있습니다. DTO는 5부에서 다시 봅니다.

5부

커넥션은 생각보다 빨리 바닥난다

2부에서 "트랜잭션 동안 커넥션 하나를 점유한다"는 사실을 봤습니다. 이 부는 그 한 문장이 주문 서버에서 어떤 장애로 번지는지, 그리고 앞의 원리로 생기는 실수를 배포 전에 잡아내는 테스트 구성을 봅니다.

원리 실무 설정 기본값, 장애 사례, 테스트 구성을 다룹니다.

커넥션을 쥐는 시간이 처리량을 정한다

4장에서 본 HikariCP 커넥션 풀은 기본 10개이고, 빌리려는 요청은 connectionTimeout(기본 30초)까지 기다리다 실패합니다. 여기에 간단한 계산을 해 봅니다.

주문 트랜잭션 하나가 커넥션을 50밀리초 쥔다면, 커넥션 하나가 1초에 20건을 처리하므로 풀 전체로 초당 200건입니다. 같은 트랜잭션이 3초를 쥐면 초당 약 3건으로 떨어집니다. 3부에서 본 Tomcat 스레드 200개는 그 사이 커넥션을 기다리며 쌓이고, 커넥션과 무관한 조회 API까지 같은 풀을 기다리다 함께 느려집니다.

즉 처리량은 풀 크기를 커넥션 점유 시간으로 나눈 값입니다. 풀을 키우는 것은 DB 쪽 한계(4장) 때문에 오래 못 가고, 실무에서 고칠 수 있는 것은 점유 시간입니다. 이어지는 네 사례가 모두 이 시간을 늘리는 원인입니다.

트랜잭션 안의 외부 호출이 풀을 말린다

// 문제: 결제 API 3초 동안 커넥션 점유
@Transactional
public void pay(Long id) {
  Order o = orderRepo.findById(id).orElseThrow();
  pg.approve(o);  // 외부 결제 API
  o.markPaid();
}

// 개선: 외부 호출은 트랜잭션 밖에서
public void pay(Long id) {
  Approval a = pg.approve(orderQuery.get(id));
  orderTx.markPaid(id, a); // 별도 Bean
}

4장의 풀 고갈 사례가 Spring에서는 대개 이 모양입니다. 프록시가 메서드 전체를 트랜잭션으로 감싸므로, 안에서 결제 API를 기다리는 시간이 그대로 커넥션 점유 시간이 됩니다. 결제사가 평소 0.2초에서 3초로 느려지는 순간 앞 슬라이드의 계산이 현실이 됩니다.

해법은 경계를 쪼개는 것입니다. DB 갱신만 다른 Bean의 @Transactional 메서드로 옮깁니다. 같은 클래스에서 부르면 2부의 자기 호출이라 트랜잭션이 걸리지 않습니다.

OSIV는 커넥션을 응답 끝까지 붙잡는다

4부의 LazyInitializationException을 피하려고 만든 장치가 OSIV입니다. 영속성 컨텍스트를 요청 끝까지 열어 두어 컨트롤러와 JSON 변환 중에도 지연 로딩이 되게 합니다. Spring Boot는 spring.jpa.open-in-view=true가 기본이고 기동 시 경고 로그를 남깁니다.

편한 대신 커넥션을 응답이 끝날 때까지 놓지 않습니다. 느린 모바일 회선으로 응답을 보내는 시간까지 점유 시간에 들어갑니다.

OSIV를 끄면 응답은 트랜잭션 안에서 완성한다

@Transactional(readOnly = true)
public List<OrderRes> myOrders(Long memberId) {
  return orderRepo.findOfMemberWithItems(memberId)
    .stream()
    .map(OrderRes::from)  // 지연 로딩도 여기서
    .toList();
}
// 컨트롤러는 완성된 OrderRes만 받는다

트래픽이 많은 API 서버는 open-in-view=false로 끄는 쪽을 권장합니다. 끄면 컨트롤러에서 지연 로딩하던 코드가 예외를 내므로, 응답에 필요한 데이터를 서비스의 트랜잭션 안에서 모두 읽어 DTO로 바꿔 내보내야 합니다.

강조한 줄의 변환이 트랜잭션 안에서 실행되므로 지연 로딩이 안전합니다. 다만 변환 중 N+1이 생기지 않도록 4부의 fetch join이나 배치 크기를 함께 씁니다.

REQUIRES_NEW는 풀 전체를 멈출 수 있다

  1. 요청 10개 동시 도착

    주문 요청 10개가 각자 바깥 트랜잭션을 열어 커넥션 10개를 모두 가져갑니다.

  2. 감사 로그 호출

    각 요청이 REQUIRES_NEW 메서드를 불러 두 번째 커넥션을 요청합니다.

  3. 아무도 못 받음

    풀은 비었고, 반납할 수 있는 요청은 모두 두 번째를 기다리는 중입니다.

  4. 30초 뒤 일제히 실패

    connectionTimeout이 지나 10개 요청이 모두 예외로 끝납니다.

2부의 전파 그림에서 REQUIRES_NEW는 한 요청이 커넥션 두 개를 쥔다고 했습니다. 동시 요청 수가 풀 크기에 닿으면, 모두가 하나씩 쥔 채 서로의 반납을 기다리는 풀 데드락이 됩니다. 1장과 4장의 데드락 조건(점유한 채 대기, 순환 대기)이 커넥션 풀에서 그대로 성립합니다.

대응은 REQUIRES_NEW를 꼭 필요한 곳에만 쓰고, 쓴다면 풀 크기를 "동시 요청 수 × 2"를 견딜 만큼 잡거나 감사 로그를 이벤트로 빼는 것입니다.

네 원인은 모두 점유 시간을 늘린다

이 부의 사례에 4부의 N+1을 더해, 커넥션 점유 시간을 늘리는 원인을 정리합니다.

원인증상대응
트랜잭션 안 외부 호출외부가 느려지면 풀 고갈외부 호출을 트랜잭션 밖으로
OSIV 켬느린 응답 전송까지 점유OSIV 끄고 DTO로 반환
REQUIRES_NEW 남용모두 1개 쥔 채 2번째 대기사용 최소화, 풀 크기 여유
N+1쿼리 수백 개로 점유 연장fetch join, 배치 크기

풀 크기를 정하는 원칙은 4장에서 다뤘고, 운영 중 풀 고갈을 지표와 스레드 덤프로 확정하는 절차는 18장에서 다룹니다.

@Version은 4장의 낙관적 락을 자동으로 건다

@Entity
class Stock {
  @Id Long itemId;
  int quantity;
  @Version Long version;
}

-- 변경 감지가 만드는 UPDATE
update stock set quantity=?, version=6
 where item_id=? and version=5
-- 0행 갱신 → OptimisticLockException

두 요청이 같은 상품 재고를 동시에 읽고 각자 1을 빼면, 하나의 차감이 사라집니다. 4장에서 이를 막는 방법으로 낙관적 락(버전 열로 충돌 감지)과 비관적 락(SELECT ... FOR UPDATE로 미리 잠금)을 봤습니다.

JPA에서는 버전 필드에 @Version만 붙이면 변경 감지가 만드는 UPDATE에 버전 조건이 들어갑니다. 그사이 다른 트랜잭션이 바꿨다면 0행이 갱신되고 예외가 납니다. 충돌이 드물 때 맞고, 잡은 예외는 다시 읽어 재시도합니다.

충돌이 잦으면 비관적 락으로 줄을 세운다

interface StockRepository
    extends JpaRepository<Stock, Long> {
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("select s from Stock s"
       + " where s.itemId = :id")
  Optional<Stock> findForUpdate(Long id);
}
-- select ... from stock where item_id=?
--   for update

인기 상품 선착순 판매처럼 충돌이 잦으면 낙관적 락은 재시도만 폭증합니다. 이때는 PESSIMISTIC_WRITE로 4장의 SELECT ... FOR UPDATE를 내서, 먼저 온 트랜잭션이 커밋할 때까지 나머지를 줄 세웁니다.

대가는 이 부의 주제 그대로입니다. 락을 기다리는 시간도 커넥션 점유 시간에 더해집니다. 락 구간을 짧게 두고, 여러 행을 잠글 때는 4장에서 본 대로 순서를 통일해 데드락을 줄입니다. 서버 여러 대가 DB 밖에서 함께 쓰는 분산 락은 8장에서 봅니다.

엔티티를 API 응답으로 내보내지 않는다

OSIV를 끄며 만든 DTO에는 그 자체로 이유가 있습니다. 엔티티를 컨트롤러에서 그대로 JSON으로 반환하면 문제가 한꺼번에 생깁니다. 주문과 회원이 서로를 참조하면 Jackson이 둘을 끝없이 따라가고, 지연 로딩 프록시를 건드려 숨은 쿼리가 나가며, 비밀번호 같은 내부 필드가 노출됩니다.

더 큰 문제는 결합입니다. 테이블 열 이름 하나를 바꾸면 API 응답 형식이 따라 바뀌어 앱이 깨집니다. 엔티티는 DB 모델, DTO는 API 계약으로 나누고, 변환은 트랜잭션 안의 서비스 계층에서 합니다.

요청 쪽도 같습니다. 3부의 @RequestBody OrderReq처럼 요청 DTO로 받아야, 클라이언트가 보낸 JSON이 엔티티의 ID나 상태 필드를 마음대로 덮어쓰는 일을 막을 수 있습니다.

테스트 피라미드: 빠른 테스트를 많이

지금까지의 함정은 대부분 실행해 봐야 드러납니다. 테스트는 범위에 따라 나뉩니다. 단위 테스트는 클래스 하나를 컨테이너 없이, 슬라이스 테스트는 웹이나 JPA 같은 한 계층만 띄워서, 통합 테스트는 전체 컨텍스트와 실제 DB로, E2E 테스트는 배포된 시스템에 실제 요청을 보내 확인합니다.

아래층일수록 빠르고 실패 원인이 좁으므로 많이 두고, 위층은 핵심 흐름만 둡니다. 이 모양을 테스트 피라미드라 합니다.

층대상속도
단위도메인 로직, 서비스밀리초
슬라이스웹 계층, JPA 계층수 초
통합전체 컨텍스트, 실제 DB수십 초
E2E배포된 시스템 전체분 단위

단위 테스트는 협력 객체를 가짜로 바꾼다

@Test
void 재고가_없으면_결제하지_않는다() {
  PaymentClient pay = mock(PaymentClient.class);
  StockRepository stock = mock(StockRepository.class);
  when(stock.findForUpdate(7L))
      .thenReturn(Optional.of(new Stock(7L, 0)));

  var svc = new OrderService(pay, stock, …);

  assertThrows(OutOfStockException.class,
      () -> svc.place(new OrderReq(7L, 1)));
  verify(pay, never()).approve(any());
}

Mock은 정해 둔 값을 돌려주고 자신이 어떻게 불렸는지 기록하는 가짜 객체로, Mockito 라이브러리가 만들어 줍니다. 결제사 API를 실제로 부르지 않고도 "재고가 0이면 결제를 시도하지 않는다"를 밀리초 안에 확인합니다.

두 번째 강조 줄이 1부의 보답입니다. 생성자 주입을 썼기 때문에 컨테이너 없이 new로 가짜를 넣을 수 있습니다.

슬라이스 테스트는 필요한 계층만 띄운다

컨트롤러의 JSON 변환이나 JPA의 쿼리는 Spring이 있어야 확인됩니다. 그렇다고 매번 전체를 띄우면 느리므로, Spring Boot는 계층별로 필요한 Bean만 등록하는 테스트 어노테이션을 줍니다. 슬라이스 테스트에서 빠진 Bean은 @MockitoBean으로 가짜를 등록합니다(Spring Boot 3.4부터 @MockBean을 대신합니다).

도구띄우는 범위확인하는 것
@WebMvcTestMVC 계층 Bean만요청 매핑, 검증, 응답 JSON
@DataJpaTestJPA 계층, 테스트마다 롤백매핑, 쿼리, N+1 여부
@SpringBootTest전체 컨텍스트여러 계층에 걸친 흐름

DB까지 Mock으로 바꾸면 쿼리 문제는 운영에서야 드러납니다. JPA 테스트는 Testcontainers(테스트 중에 컨테이너 도구 Docker로 실제 MySQL을 띄워 주는 라이브러리, Docker는 9장)로 운영과 같은 DB에서 돌리는 편이 안전합니다.

테스트의 @Transactional이 버그를 숨긴다

테스트 메서드에 @Transactional을 붙이면 테스트 전체가 한 트랜잭션이 되어 끝에 롤백됩니다(@DataJpaTest는 기본으로 그렇습니다). 데이터 정리가 편한 대신, 4부의 원리 때문에 운영과 다른 조건이 생깁니다.

  • 지연 로딩 예외가 안 난다: 영속성 컨텍스트가 테스트 끝까지 열려 있어, OSIV를 끈 운영에서 날 LazyInitializationException을 놓칩니다.
  • flush가 안 일어난다: 커밋 없이 롤백으로 끝나므로 쌓인 UPDATE가 DB에 가지 않아, 제약 조건 위반을 놓칠 수 있습니다.
  • 1차 캐시가 결과를 돌려준다: 저장 직후 조회가 DB가 아니라 캐시를 읽어, 매핑 오류가 가려집니다.

중요한 흐름은 em.flush()로 SQL을 실제로 보내고 em.clear()로 1차 캐시를 비운 뒤 다시 조회하거나, 트랜잭션 없이 실행하고 직접 정리합니다.

정리

  • IoC 컨테이너가 객체를 만들고 연결합니다. 생성자 주입은 불변, 누락 방지, 순환 참조 조기 발견, 컨테이너 없는 테스트를 줍니다.
  • 싱글톤 Bean은 무상태여야 합니다. 모든 요청 스레드가 하나의 인스턴스를 동시에 쓰기 때문입니다.
  • AOP와 @Transactional은 프록시로 동작합니다. 그래서 자기 호출과 private 메서드에는 걸리지 않고, 트랜잭션 동안 커넥션을 점유합니다.
  • 요청은 Tomcat 스레드 하나가 끝까지 맡습니다. DispatcherServlet이 핸들러를 찾고, 메시지 컨버터가 JSON과 객체를 바꿉니다.
  • 영속성 컨텍스트가 SQL을 만듭니다. 1차 캐시, 스냅샷 비교, flush가 SQL을 만들고, 지연 로딩 프록시가 N+1의 원인이 됩니다.
  • 운영의 핵심은 커넥션 점유 시간입니다. 외부 호출, OSIV, REQUIRES_NEW, N+1이 모두 풀 고갈로 이어집니다.

스스로 점검 (1)

  1. 필드 주입을 쓴 서비스는 왜 단위 테스트하기 어려운가요?

    private 필드에 리플렉션으로 값을 넣으므로 컨테이너 없이는 의존성을 채울 방법이 없습니다. 생성자 주입이면 new로 가짜 객체를 바로 넣을 수 있습니다.

  2. 싱글톤 컨트롤러가 요청 200개를 동시에 처리해도 괜찮은 이유는?

    요청마다 Tomcat 스레드가 따로 있고, 요청별 값은 각 스레드 스택의 지역 변수에 놓이기 때문입니다. 컨트롤러가 변경 가능한 필드를 갖지 않는 한 공유되는 상태가 없습니다.

  3. 인터페이스가 없는 서비스 클래스에도 @Transactional이 동작하는 이유는?

    Spring Boot는 기본으로 CGLIB을 써서 클래스를 상속한 프록시를 만들기 때문입니다. 대신 final 클래스나 final 메서드면 가로챌 수 없습니다.

스스로 점검 (2)

  1. 같은 클래스의 @Transactional 메서드를 this로 부르면 왜 트랜잭션이 없나요?

    트랜잭션 시작 코드는 프록시에 있는데 this는 프록시가 아닌 실제 객체를 가리키기 때문입니다. 메서드를 다른 Bean으로 분리해 프록시를 거치게 합니다.

  2. 안쪽 메서드의 예외를 바깥에서 잡았는데도 주문이 롤백됐습니다. 왜일까요?

    REQUIRED로 참여한 안쪽은 바깥과 같은 물리 트랜잭션이라, 예외가 지나갈 때 롤백 전용 표시가 남습니다. 바깥이 커밋하려 할 때 이 표시를 보고 롤백하며 UnexpectedRollbackException을 냅니다.

  3. save()를 부르지 않았는데 UPDATE가 나간 이유는?

    영속 상태 엔티티는 커밋 직전 flush에서 스냅샷과 비교되어, 달라진 값의 UPDATE가 자동으로 만들어지기 때문입니다.

스스로 점검 (3)

  1. 연관을 EAGER로 바꾸면 N+1이 사라지나요?

    아닙니다. JPQL은 먼저 주 엔티티만 조회하고 EAGER를 채우려 다시 N번 조회합니다. fetch join이나 배치 크기로 해결합니다.

  2. 주문과 주문 상품 목록을 fetch join하고 페이징하면 무슨 일이 생기나요?

    JOIN 행 단위로는 주문을 정확히 자를 수 없어 Hibernate가 전체를 메모리로 읽은 뒤 페이징합니다. 데이터가 많으면 메모리 부족이 납니다.

  3. 결제 API가 느려지자 관계없는 조회 API까지 타임아웃이 났습니다. 원인은?

    트랜잭션 안에서 결제 API를 기다리며 커넥션을 붙잡아 풀이 고갈된 것입니다. 같은 풀을 쓰는 모든 요청이 connectionTimeout까지 기다리다 실패합니다.

  4. OSIV를 끄면 어떤 코드가 깨지고, 어떻게 고치나요?

    컨트롤러나 JSON 변환 중에 지연 로딩하던 코드가 LazyInitializationException을 냅니다. 필요한 데이터를 트랜잭션 안에서 조회해 DTO로 만들어 반환합니다.
