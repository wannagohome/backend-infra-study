프레임워크는 객체를 어떻게 대신 관리하는가

아래층부터 위로 쌓아 올라가는 순서입니다. 지금은 6단계입니다.

1부

객체를 만드는 일을 넘겨준다

5장에서 본 객체지향 설계 원칙을 실제 코드에서 지키려면 누군가 객체를 조립해 줘야 합니다. Spring은 5장 끝에서 본 리플렉션과 어노테이션으로 그 조립을 대신 맡는 컨테이너입니다.

new를 직접 쓰면 구현에 묶인다

public class OrderService {
  private final PaymentClient pay =
      new KakaoPayClient("api-key");

  public void order(Order o) {
    pay.approve(o.amount());
  }
}

OrderService는 인터페이스 PaymentClient를 쓰지만, 어떤 구현을 쓸지까지 스스로 정합니다. 결제사를 바꾸려면 이 클래스를 고쳐야 하고, 테스트에서 가짜 결제 객체로 바꿔 끼울 수도 없습니다.

5장의 DIP(의존 역전 원칙)는 "추상에 의존하라"고 말하지만, 구현을 고르는 코드가 안에 있는 한 원칙은 반쪽만 지켜집니다.

제어의 역전: 내가 부르지 않고 불려진다

제어의 역전(IoC)은 객체를 만들고 연결하고 호출하는 흐름의 주도권을 내 코드가 아니라 외부에 넘기는 것입니다. 라이브러리는 내가 호출하지만, 프레임워크는 내 코드를 호출합니다.

Spring에서는 IoC 컨테이너가 이 역할을 합니다. 컨테이너는 설정을 읽어 객체를 만들고, 필요한 의존 객체를 넣어 주고, 생명이 끝날 때 정리합니다.

앞 슬라이드의 OrderService는 이제 "PaymentClient 하나가 필요하다"고 선언만 하고, 무엇을 넣을지는 컨테이너가 정합니다. 이렇게 밖에서 넣어 주는 방식을 의존성 주입(DI)이라고 합니다.

Spring의 세 기둥은 POJO를 지키는 장치다

요소하는 일없으면 생기는 일
IoC/DI객체 생성과 연결을 컨테이너가 맡음클래스마다 new와 팩토리 코드
AOP트랜잭션, 로깅 같은 공통 기능 분리모든 메서드에 같은 코드 반복
PSA기술을 추상 인터페이스 뒤에 숨김JDBC, JPA마다 다른 트랜잭션 코드

POJO는 특정 프레임워크 클래스를 상속하지 않는 평범한 자바 객체입니다. 세 기둥 덕분에 비즈니스 코드는 POJO로 남고, PSA 예로 @Transactional은 JDBC든 JPA든 같은 방식으로 씁니다.

의존성을 넣는 세 가지 방법

// 1. 생성자 주입 (권장)
private final PaymentClient pay;
OrderService(PaymentClient p) { this.pay = p; }

// 2. 수정자(setter) 주입
@Autowired
void setPay(PaymentClient p) { this.pay = p; }

// 3. 필드 주입
@Autowired private PaymentClient pay;

생성자가 하나뿐이면 Spring 4.3부터 @Autowired를 생략할 수 있습니다. Lombok의 @RequiredArgsConstructor로 생성자를 자동 생성하는 경우가 많습니다.

수정자 주입은 선택적이거나 실행 중 바뀌는 의존성에, 필드 주입은 테스트 코드 정도에만 씁니다.

생성자 주입을 권장하는 네 가지 이유

  • 불변: 필드를 final로 선언할 수 있어 생성 후 누구도 의존성을 바꾸지 못합니다.
  • 누락 방지: 의존성 없이는 객체 자체를 만들 수 없어, 빠뜨리면 컴파일이나 기동 단계에서 바로 드러납니다.
  • 순환 참조 조기 발견: A와 B가 서로를 생성자로 요구하면 둘 다 먼저 만들 수 없으므로 기동 시점에 실패합니다.
  • 테스트 용이: 컨테이너 없이 new OrderService(fakePay)로 바로 테스트할 수 있습니다.

필드 주입은 리플렉션으로 private 필드에 값을 넣기 때문에 컨테이너 밖에서는 채울 방법이 없습니다. Spring Boot 2.6부터는 순환 참조 자체를 기본으로 금지합니다.

같은 타입의 Bean이 여럿이면 골라 줘야 한다

@Component @Primary
class KakaoPay implements PaymentClient {}

@Component
class TossPay implements PaymentClient {}

// 이름으로 지정
OrderService(@Qualifier("tossPay")
             PaymentClient pay)

// 전부 받기
Router(Map<String, PaymentClient> all)

후보가 둘 이상이면 컨테이너는 무엇을 넣을지 몰라 기동에 실패합니다. @Primary는 기본값을, @Qualifier는 특정 Bean을 지정합니다.

마지막 줄처럼 List나 Map으로 모두 받으면 요청마다 결제사를 고르는 전략 패턴이 됩니다. 새 결제사를 추가해도 Router는 바뀌지 않습니다.

컨테이너가 관리하는 객체가 Bean이다

컨테이너가 만들고 관리하는 객체를 빈(Bean)이라고 합니다. 컨테이너의 실체는 ApplicationContext로, 기본 기능인 BeanFactory에 이벤트 발행, 메시지, 환경 설정 같은 기능을 더한 것입니다.

등록 방법@Component@Bean
붙이는 곳내가 만든 클래스@Configuration 안의 메서드
발견 방식컴포넌트 스캔이 자동 등록메서드 반환값을 등록
주된 용도서비스, 리포지토리, 컨트롤러외부 라이브러리 객체, 세밀한 설정

Bean의 생명주기와 초기화 콜백

  1. 객체 생성

    생성자를 호출합니다. 생성자 주입이면 이때 의존성이 함께 들어옵니다.

  2. 의존성 주입

    수정자, 필드 주입 대상을 채웁니다.

  3. 초기화 콜백

    @PostConstruct가 실행됩니다. 의존성이 모두 준비된 첫 시점입니다.

  4. 사용

    애플리케이션이 Bean을 씁니다. 필요하면 이 앞에서 프록시로 감쌉니다.

  5. 소멸 콜백

    컨텍스트 종료 시 @PreDestroy로 자원을 정리합니다.

생성자 안에서 다른 Bean을 써서 캐시를 채우거나 연결을 여는 코드는 위험합니다. 수정자 주입 대상은 아직 비어 있을 수 있기 때문입니다.

그래서 초기화 작업은 @PostConstruct에, 커넥션이나 스레드 풀 정리는 @PreDestroy에 둡니다. 9장의 Graceful Shutdown이 이 소멸 단계와 이어집니다.

스코프: Bean을 몇 개, 언제까지 만들까

스코프인스턴스 수소멸 관리
singleton (기본)컨테이너당 하나컨테이너가 끝까지 관리
prototype요청할 때마다 새로생성 후 손을 뗌
requestHTTP 요청마다 하나요청이 끝나면 소멸

싱글톤 Bean에 prototype Bean을 주입하면 주입이 한 번만 일어나므로 사실상 싱글톤처럼 동작합니다. 매번 새 객체가 필요하면 ObjectProvider로 필요할 때 꺼내 씁니다.

싱글톤 Bean은 상태를 가지면 안 된다

기본 스코프가 싱글톤인 이유는 요청마다 객체를 만들고 GC하는 비용을 없애기 위해서입니다. 대신 하나의 객체를 모든 요청 스레드가 동시에 씁니다.

Bean에 변경 가능한 필드를 두면 1장의 경쟁 상태가 그대로 생깁니다. 요청별 값은 지역 변수나 파라미터로 다루면 각 스레드 스택에 따로 놓이므로 안전합니다.

2부

Spring 내부는 패턴과 프록시로 짜여 있다

Spring이 쓰는 디자인 패턴을 살펴본 뒤, 그중 프록시가 AOP와 @Transactional을 어떻게 가능하게 하는지, 요청 하나가 어떤 길을 지나는지 따라갑니다.

기초 원리 여기부터는 프레임워크 내부 동작을 다룹니다.

Spring 곳곳에 디자인 패턴이 있다

패턴핵심 아이디어Spring에서 쓰는 곳
싱글톤인스턴스를 하나만 유지기본 Bean 스코프
팩토리생성 로직을 한곳에 숨김BeanFactory, @Bean 메서드
템플릿 메서드뼈대는 고정, 일부만 바꿈JdbcTemplate, TransactionTemplate
전략알고리즘을 갈아 끼움DI로 주입되는 인터페이스
프록시대리 객체가 호출을 가로챔AOP, @Transactional, 지연 로딩
옵저버이벤트를 구독자에게 통지ApplicationEvent, @EventListener

Spring 싱글톤은 GoF 싱글톤과 다릅니다. private 생성자와 static 필드로 클래스가 스스로 유일함을 지키는 대신, 평범한 클래스를 컨테이너가 하나만 만들어 나눠 주므로 POJO로 남고 테스트에서 교체할 수 있습니다.

템플릿 콜백과 옵저버: 반복은 프레임워크로

// 템플릿: 연결, 예외, 반납은 고정
jdbc.query("select * from member",
    (rs, i) -> new Member(rs.getLong(1)));

// 옵저버: 발행자는 구독자를 모름
events.publishEvent(new Ordered(id));

@TransactionalEventListener
void on(Ordered e) { mail.send(e); }

JdbcTemplate은 커넥션 획득, 예외 변환, 자원 반납이라는 뼈대를 고정하고, 결과를 객체로 바꾸는 부분만 콜백으로 받습니다.

이벤트는 주문 코드와 메일 코드를 떼어 놓습니다. @TransactionalEventListener는 기본적으로 커밋 후에 실행되어, 롤백된 주문에 메일이 나가는 일을 막습니다.

프록시는 진짜 객체 앞에 선 대리인이다

프록시는 실제 객체와 같은 타입을 가진 대리 객체입니다. 호출을 먼저 받아 부가 기능을 실행하고 실제 객체에 위임합니다.

컨테이너가 다른 Bean에 넣어 주는 것이 실제 객체가 아니라 프록시라면, 호출하는 쪽은 코드 한 줄 바꾸지 않고 모든 호출 앞뒤에 기능이 끼어듭니다. 이것이 AOP의 토대입니다.

AOP: 흩어진 공통 관심사를 한곳에

@Aspect @Component
class TimingAspect {
  @Around("execution(* *..*Service.*(..))")
  Object time(ProceedingJoinPoint jp)
      throws Throwable {
    long t = System.nanoTime();
    try { return jp.proceed(); }
    finally { log(jp, System.nanoTime() - t); }
  }
}

로깅, 실행 시간 측정, 트랜잭션처럼 여러 클래스에 걸친 기능을 횡단 관심사라고 합니다. AOP는 이를 모듈 하나로 뽑아냅니다.

Aspect는 무엇을(Advice) 어디에(Pointcut) 적용할지 묶은 것이고, 적용되는 실행 지점을 JoinPoint라 합니다. Spring AOP의 JoinPoint는 메서드 실행뿐입니다.

프록시는 Bean 등록 순간에 바꿔치기된다

  1. Bean 생성과 주입

    컨테이너가 원본 객체를 만들고 의존성을 채웁니다.

  2. 후처리기 검사

    BeanPostProcessor가 Pointcut에 맞는 메서드가 있는지 봅니다.

  3. 프록시 생성

    맞으면 원본을 감싼 프록시를 만들어 원본 대신 등록합니다.

  4. 주입

    다른 Bean은 이 프록시를 주입받습니다.

바이트코드를 바꾸는 시점을 위빙이라 합니다. AspectJ는 컴파일이나 클래스 로딩 때 코드를 직접 바꾸지만, Spring AOP는 런타임에 프록시를 덧씌우는 방식입니다.

그래서 Spring AOP는 설정이 단순한 대신, 프록시를 거치는 외부 호출에만 적용됩니다. 이 한계가 곧 @Transactional의 함정이 됩니다.

JDK 동적 프록시와 CGLIB

항목JDK 동적 프록시CGLIB
만드는 방법인터페이스를 구현한 클래스 생성대상 클래스를 상속한 하위 클래스 생성
조건인터페이스 필수클래스만 있어도 됨
주입 타입구체 클래스 타입으로 주입 불가구체 클래스 타입도 가능
제약인터페이스 메서드만 가로챔final 클래스와 메서드는 불가

JDK 프록시는 5장의 리플렉션 API로 인터페이스 구현체를 실행 중에 만들고, CGLIB은 바이트코드로 하위 클래스를 만듭니다. Spring Boot는 spring.aop.proxy-target-class=true가 기본이라 CGLIB을 씁니다. 구체 타입 주입에서 생기는 오류를 없애기 위해서입니다.

@Transactional은 프록시가 여는 트랜잭션이다

  1. 프록시가 호출을 받음

    TransactionInterceptor가 트랜잭션 속성을 읽습니다.

  2. 커넥션 획득, 자동 커밋 끔

    트랜잭션 매니저가 풀에서 커넥션을 받아 현재 스레드에 묶습니다.

  3. 실제 메서드 실행

    안의 리포지토리는 스레드에 묶인 같은 커넥션을 씁니다.

  4. 커밋 또는 롤백

    정상 반환이면 커밋, 롤백 대상 예외면 롤백합니다.

  5. 커넥션 반납

    스레드 바인딩을 풀고 커넥션을 풀에 돌려줍니다.

여러 리포지토리가 같은 트랜잭션에 묶이는 비밀은 2단계입니다. 커넥션을 5장의 ThreadLocal에 보관하므로, 같은 스레드의 코드는 파라미터 없이도 같은 커넥션을 찾습니다.

4장의 트랜잭션이 DB 커넥션 단위라는 사실이 여기서 그대로 드러납니다. 트랜잭션이 열려 있는 동안 커넥션 하나를 점유합니다.

내부 호출은 프록시를 거치지 않는다

@Service
public class OrderService {
  public void placeAll(List<Req> rs) {
    for (Req r : rs) place(r);
  }

  @Transactional
  public void place(Req r) { … }
}

self-invocation과 private 메서드의 해법

같은 클래스 안에서 this.place()를 부르는 것을 자기 호출이라 합니다. 가장 깔끔한 해결은 트랜잭션 메서드를 다른 Bean으로 분리해 프록시를 거치게 하는 것입니다. 자기 자신을 주입받는 방법도 있지만 구조를 흐립니다.

private 메서드에도 적용되지 않습니다. CGLIB은 하위 클래스에서 오버라이드로 가로채는데, private과 final 메서드는 오버라이드할 수 없기 때문입니다. Spring 6.0부터 CGLIB 프록시는 protected와 package-private 메서드까지 지원합니다.

정말 내부 호출까지 트랜잭션이 필요하면 바이트코드를 직접 바꾸는 AspectJ 모드를 쓸 수 있지만, 대부분은 구조를 고치는 편이 낫습니다.

전파: 이미 트랜잭션이 있으면 어떻게 할까

트랜잭션 메서드가 다른 트랜잭션 메서드를 부를 때의 규칙이 전파 속성입니다. 기본값 REQUIRED는 있으면 참여하고 없으면 새로 엽니다. 안쪽에서 롤백이 나면 바깥까지 함께 롤백됩니다.

REQUIRES_NEW는 바깥을 잠시 멈추고 커넥션을 하나 더 받아 독립 트랜잭션을 엽니다. 실패해도 남겨야 하는 감사 로그 같은 곳에 씁니다.

Checked 예외는 기본으로 롤백되지 않는다

@Transactional
void a() { throw new IllegalStateException(); }
// RuntimeException: 롤백

@Transactional
void b() throws IOException {
  throw new IOException(); }
// Checked 예외: 커밋된다

@Transactional(rollbackFor = Exception.class)
void c() throws IOException { … }
// 모든 예외에서 롤백

Spring은 RuntimeException과 Error에서만 롤백합니다. 5장에서 본 대로 Checked 예외는 호출자가 복구할 수 있는 상황이라는 전제를 따른 설계입니다.

안쪽 REQUIRED 메서드의 예외를 바깥에서 catch해도 트랜잭션은 이미 롤백 전용으로 표시되어, 커밋 시점에 UnexpectedRollbackException이 납니다.

readOnly=true는 힌트 이상의 일을 한다

@Transactional(readOnly = true)를 붙이면 JPA(Hibernate) 환경에서 flush 모드가 수동으로 바뀌어 변경 감지와 flush를 건너뜁니다. 엔티티 스냅샷을 유지할 필요도 줄어 대량 조회에서 메모리와 CPU를 아낍니다.

JDBC 커넥션에도 읽기 전용 힌트가 전달되어, DB나 드라이버가 최적화에 쓸 수 있습니다. 4장의 읽기/쓰기 분리 구조에서는 이 속성을 보고 조회 트랜잭션을 Replica로 라우팅하도록 구성하는 경우가 많습니다.

그래서 서비스 클래스에 readOnly = true를 기본으로 두고, 쓰기 메서드에만 @Transactional을 다시 붙이는 패턴을 흔히 씁니다.

요청 하나에 스레드 하나: Tomcat 스레드 풀

Spring MVC는 서블릿 컨테이너인 Tomcat 위에서 돕니다. Tomcat은 연결을 받으면 워커 스레드 풀에서 스레드 하나를 꺼내, 응답이 끝날 때까지 그 요청에 붙여 둡니다. 1장의 I/O 바운드 풀 크기 원리가 여기에 적용됩니다.

Spring Boot 설정기본값의미
server.tomcat.threads.max200동시에 처리하는 요청 수 상한
server.tomcat.max-connections8192동시에 붙잡는 연결 수
server.tomcat.accept-count100그 너머 OS 대기열 길이

Java 21 이상에서 spring.threads.virtual.enabled=true로 5장의 Virtual Thread를 쓰면 threads.max 설정은 효과가 없습니다.

DispatcherServlet은 모든 요청의 정문이다

  1. HandlerMapping

    URL과 메서드로 처리할 컨트롤러 메서드를 찾습니다.

  2. HandlerAdapter

    ArgumentResolver로 파라미터를 만들고 메서드를 호출합니다.

  3. HttpMessageConverter

    @RequestBody JSON을 객체로, 반환 객체를 JSON으로 바꿉니다.

  4. 예외 처리

    예외가 나면 @ControllerAdvice가 응답으로 바꿉니다.

  5. 응답

    뷰가 필요하면 ViewResolver를 거쳐 응답을 씁니다.

모든 요청을 하나의 진입점이 받아 나눠 주는 구조를 프런트 컨트롤러 패턴이라 합니다. 인증, 인코딩, 예외 처리처럼 공통인 일을 한곳에서 처리할 수 있습니다.

@RestController는 반환값을 뷰 이름이 아니라 응답 본문으로 보고, 3단계의 컨버터(보통 Jackson)로 바로 JSON을 씁니다.

Filter, Interceptor, AOP는 서는 위치가 다르다

Filter는 서블릿 컨테이너 단계에서 동작해 DispatcherServlet에 닿기 전 요청 전체를 봅니다. 정적 파일 요청까지 모두 지나가므로 보안이나 인코딩처럼 예외 없이 적용할 일에 맞습니다.

Interceptor는 DispatcherServlet이 컨트롤러를 고른 뒤에 실행되어 어떤 핸들러가 선택됐는지 압니다. AOP는 더 안쪽에서 웹과 무관하게 Bean 메서드 단위로 끼어듭니다.

무엇을 어디에 둘지 고르는 기준

기준FilterInterceptorAOP
소속서블릿 스펙Spring MVCSpring 컨테이너
아는 정보요청과 응답 원본선택된 핸들러메서드와 인자
요청 교체요청 객체 감싸기 가능불가불가
예외 처리@ControllerAdvice 밖@ControllerAdvice 안@ControllerAdvice 안
대표 용도보안, 인코딩, CORS로그인 확인, 로깅트랜잭션, 실행 시간

Filter에서 난 예외는 DispatcherServlet 밖이라 @ControllerAdvice가 잡지 못하므로 Filter 안에서 직접 응답을 써야 합니다. Spring Security가 Filter 체인으로 만들어진 이유는 7장에서 봅니다.

Spring Boot 자동 설정은 조건부 Bean이다

@AutoConfiguration
@ConditionalOnClass(DataSource.class)
class DataSourceAutoConfig {

  @Bean
  @ConditionalOnMissingBean
  DataSource dataSource(Props p) {
    return new HikariDataSource(p.toConfig());
  }
}

Boot는 starter 의존성과 함께 자동 설정 클래스 목록을 읽어, 조건이 맞는 것만 Bean으로 등록합니다. 클래스패스에 라이브러리가 있는지, 설정값이 있는지 같은 조건입니다.

핵심은 @ConditionalOnMissingBean입니다. 내가 같은 타입 Bean을 직접 등록하면 자동 설정은 물러납니다. 내장 Tomcat도 같은 방식으로 뜹니다.

WebFlux는 스레드 대신 이벤트 루프를 쓴다

스레드 풀 모델은 I/O를 기다리는 동안에도 스레드를 붙잡습니다. 동시 요청이 수만 개면 스레드 수와 메모리가 버티지 못합니다.

WebFlux는 Netty 위에서 1장의 이벤트 루프 방식으로 동작해, 적은 스레드로 많은 연결을 처리합니다. 대신 호출 경로 전체가 논블로킹이어야 효과가 있습니다. JDBC와 JPA는 블로킹이라 그대로 쓰면 이벤트 루프가 멈춥니다.

그래서 DB 중심의 일반적인 서비스는 MVC를 유지하고, 외부 호출을 대량으로 묶는 게이트웨이 같은 곳에 WebFlux를 고르는 경우가 많습니다. Virtual Thread(5장)가 그 사이의 선택지로 떠오르고 있습니다.

3부

객체와 테이블 사이의 통역사

JPA가 왜 필요한지에서 출발해, 영속성 컨텍스트가 SQL을 언제 어떻게 만드는지, N+1 문제가 왜 생기는지 봅니다.

객체와 테이블은 생각하는 방식이 다르다

객체는 참조로 연결되고 상속이 있으며 order.getMember()처럼 그래프를 따라갑니다. 테이블은 외래 키로 연결되고 JOIN으로 묶습니다. 이 차이를 패러다임 불일치라 합니다.

JPA는 이 변환을 맡는 표준 명세이고, Spring Boot는 구현체로 Hibernate를 씁니다.

항목JPAMyBatis
SQL 작성대부분 자동 생성직접 작성해 매핑
강점CRUD 생산성, 변경 감지복잡한 SQL 통제
약점동작을 모르면 쿼리 폭증반복 SQL, 객체 그래프 수동

영속성 컨텍스트는 트랜잭션 안의 캐시다

영속성 컨텍스트는 엔티티를 담아 두는 메모리 공간으로, Spring에서는 기본적으로 트랜잭션 하나와 수명이 같습니다.

find()는 먼저 1차 캐시를 보고 없을 때만 SELECT합니다. 같은 트랜잭션에서 같은 ID로 두 번 찾으면 같은 인스턴스가 나와 == 비교가 참입니다.

쓰기 지연과 flush가 일어나는 시점

persist()를 불러도 INSERT는 바로 나가지 않고 쓰기 지연 저장소에 쌓입니다. 모아 보내면 JDBC 배치로 왕복을 줄일 수 있습니다.

flush는 쌓인 변경을 DB에 SQL로 보내는 일이지 커밋이 아닙니다. flush 후에도 롤백하면 모두 취소됩니다.

예외: ID 생성이 IDENTITY(AUTO_INCREMENT)면 ID를 알려면 INSERT해야 하므로 persist 즉시 나가고, INSERT 배치도 쓸 수 없습니다.

  1. 트랜잭션 커밋 직전

    커밋하기 전에 자동으로 flush합니다.

  2. JPQL 쿼리 실행 직전

    쌓인 변경이 조회 결과에 반영되도록 먼저 flush합니다.

  3. 직접 호출

    em.flush()나 saveAndFlush()로 즉시 보냅니다.

변경 감지: save를 부르지 않아도 UPDATE된다

@Transactional
public void rename(Long id, String name) {
  Member m = repo.findById(id).orElseThrow();
  m.changeName(name);   // save() 없음
}
// 커밋 직전 flush:
// 스냅샷과 비교 → 달라진 엔티티 발견
// update member set name=? where id=?

영속성 컨텍스트는 엔티티를 처음 읽을 때 상태를 스냅샷으로 복사해 둡니다. flush 시점에 현재 값과 비교해 달라진 엔티티의 UPDATE를 만듭니다. 이것이 변경 감지입니다.

그래서 엔티티 수정은 "꺼내서 바꾸면 끝"입니다. 반대로 트랜잭션 밖에서 바꾸면 아무 일도 일어나지 않습니다.

엔티티의 네 가지 상태

변경 감지는 영속 상태의 엔티티에만 일어납니다. new로 막 만든 객체는 비영속, 트랜잭션이 끝나 컨텍스트가 닫히면 준영속이 됩니다.

준영속 객체를 merge()하면 새 영속 엔티티에 값을 통째로 복사합니다. 빈 필드도 그대로 덮으므로, 수정은 다시 조회해 변경 감지로 하는 편이 안전합니다.

지연 로딩은 프록시가 대신 서 있는 것이다

@Entity
class Order {
  @ManyToOne(fetch = FetchType.LAZY)
  Member member;

  @OneToMany(mappedBy = "order")
  List<OrderItem> items; // 기본 LAZY
}
// order.getMember()    → 프록시, SQL 없음
// member.getName()     → 이때 SELECT

지연 로딩이면 Order를 읽을 때 Member 자리에 Hibernate가 만든 프록시를 넣고, 실제 값을 쓰는 순간 조회합니다. 2부의 프록시가 여기서도 쓰입니다.

@ManyToOne과 @OneToOne은 기본값이 EAGER라 직접 LAZY로 바꿔야 합니다. 실무 원칙은 전부 LAZY, 필요할 때만 함께 조회입니다.

N+1: 쿼리 한 번이 N번을 부른다

List<Order> orders = repo.findAll();
for (Order o : orders)
  o.getMember().getName();

-- 실제 로그
select * from orders                  -- 1번
select * from member where id=?       -- N번
select * from member where id=?
select * from member where id=?
…

주문 100건을 조회하면 주문마다 회원 프록시가 초기화되어 SELECT가 100번 더 나갑니다. 이것이 N+1 문제입니다.

EAGER로 바꾸면 해결될까요? JPQL은 먼저 SQL로 번역되어 주문만 읽고, 그다음 EAGER를 채우려 다시 N번 조회합니다. 로딩 시점만 바뀔 뿐 N+1은 그대로입니다.

N+1을 푸는 세 가지 방법

// 1. fetch join: JOIN 한 번으로 함께 조회
@Query("select o from Order o join fetch o.member")
// 2. @EntityGraph: 어노테이션으로 같은 효과
@EntityGraph(attributePaths = "member")
// 3. 배치 크기: 프록시 초기화를 IN 절로 묶음
spring.jpa.properties.hibernate.default_batch_fetch_size: 100
방법쿼리 수적합한 경우
fetch join1ToOne 관계, 화면에 꼭 필요한 연관
@EntityGraph1메서드 이름 쿼리에 붙일 때
배치 크기1 + N/100컬렉션, 페이징이 필요한 조회

fetch join에는 두 가지 한계가 있다

컬렉션 fetch join과 페이징: 주문 하나에 상품이 3개면 JOIN 결과는 3행이 됩니다. 행 기준으로 LIMIT을 걸면 주문이 잘리므로, Hibernate는 전체를 메모리로 읽은 뒤 페이징하고 경고만 남깁니다. 데이터가 많으면 메모리가 터집니다.

둘 이상의 컬렉션 fetch join: List 컬렉션 두 개를 동시에 fetch join하면 행이 곱으로 불어나고 어느 행이 어느 컬렉션 것인지 구분할 수 없어 MultipleBagFetchException이 납니다.

정석은 ToOne 관계만 fetch join으로 가져와 페이징하고, 컬렉션은 default_batch_fetch_size로 IN 절 조회에 맡기는 것입니다. 조회 전용 화면이라면 DTO로 필요한 열만 직접 조회하는 방법도 있습니다.

4부

커넥션은 생각보다 빨리 바닥난다

앞에서 본 원리들이 운영에서 어떤 장애로 나타나는지, 그리고 그것을 미리 잡아내는 테스트 전략을 봅니다.

원리 실무 설정 기본값, 장애 사례, 테스트 구성을 다룹니다.

OSIV는 커넥션을 응답 끝까지 붙잡는다

OSIV는 영속성 컨텍스트를 요청 끝까지 열어 두어 컨트롤러에서도 지연 로딩이 되게 합니다. Spring Boot는 spring.jpa.open-in-view=true가 기본이고 기동 시 경고를 남깁니다.

편한 대가로 DB 커넥션을 응답이 끝날 때까지 놓지 않습니다. 끄면 서비스 밖 지연 로딩이 LazyInitializationException을 내므로, 필요한 데이터는 트랜잭션 안에서 DTO로 만들어 나와야 합니다.

JPA 락: 4장의 락을 어노테이션으로

@Entity
class Stock {
  @Version Long version;   // 낙관적 락
  int quantity;
}

interface StockRepo extends JpaRepository<…> {
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("select s from Stock s where s.id=:id")
  Optional<Stock> findForUpdate(Long id);
}

@Version은 UPDATE에 where version=?를 붙여, 그사이 누가 바꿨으면 0행이 갱신되고 예외가 납니다. 충돌이 드물 때 재시도와 함께 씁니다.

PESSIMISTIC_WRITE는 4장의 SELECT ... FOR UPDATE를 냅니다. 충돌이 잦은 재고 차감에 맞지만, 락 대기 시간이 커넥션 점유 시간에 그대로 더해집니다.

엔티티를 API 응답으로 내보내지 않는다

엔티티를 컨트롤러에서 그대로 JSON으로 반환하면 여러 문제가 한꺼번에 생깁니다. 양방향 연관이 있으면 직렬화가 서로를 끝없이 따라가고, 지연 로딩 프록시를 건드려 숨은 쿼리가 나가며, 비밀번호 같은 내부 필드가 노출됩니다.

더 큰 문제는 결합입니다. 테이블 열 이름 하나를 바꾸면 API 응답 형식이 바뀌어 클라이언트가 깨집니다. 엔티티는 DB 모델, DTO는 API 계약으로 나누고, 변환은 트랜잭션 안의 서비스 계층에서 합니다.

요청 쪽도 같습니다. 요청 DTO로 받아야 클라이언트가 보낸 값이 엔티티의 ID나 권한 필드를 덮어쓰는 일을 막을 수 있습니다.

트랜잭션 범위가 곧 커넥션 점유 시간이다

// 문제: 외부 호출 3초 동안 커넥션 점유
@Transactional
public void pay(Long id) {
  Order o = repo.findById(id).orElseThrow();
  pg.approve(o);  // 외부 결제 API
  o.markPaid();
}

// 개선: 외부 호출은 트랜잭션 밖에서
public void pay(Long id) {
  Approval a = pg.approve(orderQuery.get(id));
  orderTx.markPaid(id, a); // 별도 Bean
}

4장에서 본 풀 고갈 사례가 Spring에서는 대개 이 모양으로 생깁니다. 프록시가 메서드 전체를 트랜잭션으로 감싸므로, 메서드 안의 외부 호출 시간이 그대로 커넥션 점유 시간이 됩니다.

해법은 경계를 쪼개는 것입니다. DB 갱신만 다른 Bean의 @Transactional 메서드로 옮깁니다. 같은 클래스에서 부르면 앞서 본 self-invocation 때문에 트랜잭션이 걸리지 않습니다.

생성자 주입을 쓴 서비스는 컨테이너 없이 가짜 객체를 넣어 단위 테스트할 수 있습니다. 1부의 설계 선택이 테스트 속도로 돌아오는 셈입니다.

슬라이스 테스트와 Mock을 쓰는 기준

Mock은 협력 객체를 가짜로 바꿔 대상만 검증하게 합니다. Spring Boot 3.4부터 @MockBean 대신 @MockitoBean을 씁니다. 다만 DB까지 Mock으로 바꾸면 쿼리 문제는 운영에서야 드러나므로, JPA 테스트는 Testcontainers로 실제 DB를 띄우는 편이 안전합니다.

테스트의 @Transactional이 버그를 숨긴다

테스트 메서드에 @Transactional을 붙이면 테스트 전체가 한 트랜잭션이 되어 끝에 롤백됩니다. 정리가 편한 대신, 운영과 다른 조건이 생깁니다.

  • 지연 로딩 예외가 안 난다: 영속성 컨텍스트가 테스트 끝까지 열려 있어 운영의 LazyInitializationException을 놓칩니다.
  • flush가 안 일어난다: 롤백으로 끝나므로 UPDATE가 실행되지 않아 제약 조건 위반을 놓칠 수 있습니다.
  • 1차 캐시가 결과를 돌려준다: 저장 후 조회가 DB가 아니라 캐시를 읽습니다.

중요한 흐름은 em.flush()와 em.clear()를 넣어 DB를 실제로 거치게 하거나, 트랜잭션 없이 실행하고 직접 정리합니다.

정리

  • IoC 컨테이너가 객체를 만들고 연결합니다. 생성자 주입은 불변, 누락 방지, 순환 참조 조기 발견, 테스트 용이성을 줍니다.
  • 싱글톤 Bean은 무상태여야 합니다. 모든 요청 스레드가 하나의 인스턴스를 동시에 쓰기 때문입니다.
  • AOP와 @Transactional은 프록시로 동작합니다. 그래서 내부 호출과 private 메서드에는 적용되지 않고, 트랜잭션 동안 커넥션을 점유합니다.
  • 영속성 컨텍스트는 쓰기 지연 캐시입니다. 1차 캐시, 스냅샷 비교, flush가 SQL을 만들고, 지연 로딩 프록시가 N+1의 원인이 됩니다.
  • 운영의 핵심은 커넥션 점유 시간입니다. 외부 호출, OSIV, REQUIRES_NEW, N+1이 모두 풀 고갈로 이어집니다.

스스로 점검 (1)

  1. 필드 주입을 쓴 서비스는 왜 단위 테스트하기 어려운가요?

    private 필드에 리플렉션으로 값을 넣으므로 컨테이너 없이는 의존성을 채울 방법이 없습니다. 생성자 주입이면 new로 가짜 객체를 바로 넣을 수 있습니다.

  2. 싱글톤 컨트롤러가 요청 200개를 동시에 처리해도 괜찮은 이유는?

    요청마다 Tomcat 스레드가 따로 있고, 요청별 값은 각 스레드 스택의 지역 변수에 놓이기 때문입니다. 컨트롤러가 변경 가능한 필드를 갖지 않는 한 공유되는 상태가 없습니다.

  3. 인터페이스가 없는 서비스 클래스에도 @Transactional이 동작하는 이유는?

    Spring Boot는 기본으로 CGLIB을 써서 클래스를 상속한 프록시를 만들기 때문입니다. 대신 final 클래스나 final 메서드면 가로챌 수 없습니다.

  4. 같은 클래스의 @Transactional 메서드를 this로 부르면 왜 트랜잭션이 없나요?

    트랜잭션 시작 코드는 프록시에 있는데 this는 프록시가 아닌 실제 객체를 가리키기 때문입니다. 메서드를 다른 Bean으로 분리해 프록시를 거치게 합니다.

  5. 메서드가 IOException을 던졌는데 데이터가 커밋됐습니다. 왜일까요?

    기본 롤백 규칙은 RuntimeException과 Error만 대상입니다. Checked 예외도 롤백하려면 rollbackFor를 지정합니다.

스스로 점검 (2)

  1. save()를 부르지 않았는데 UPDATE가 나간 이유는?

    영속 상태 엔티티는 커밋 직전 flush에서 스냅샷과 비교되어, 달라진 값의 UPDATE가 자동으로 만들어지기 때문입니다.

  2. 연관을 EAGER로 바꾸면 N+1이 사라지나요?

    아닙니다. JPQL은 먼저 주 엔티티만 조회하고 EAGER를 채우려 다시 N번 조회합니다. fetch join이나 배치 크기로 해결합니다.

  3. 주문과 상품 목록을 fetch join하고 페이징하면 무슨 일이 생기나요?

    JOIN 행 단위로는 정확히 자를 수 없어 Hibernate가 전체를 메모리로 읽은 뒤 페이징합니다. 데이터가 많으면 메모리 부족이 납니다.

  4. 외부 API가 느려지자 관계없는 조회 API까지 타임아웃이 났습니다. 원인은?

    트랜잭션 안에서 외부 API를 기다리며 커넥션을 붙잡아 풀이 고갈된 것입니다. 같은 풀을 쓰는 모든 요청이 connectionTimeout까지 기다리다 실패합니다.

  5. OSIV를 끄면 어떤 코드가 깨지고, 어떻게 고치나요?

    컨트롤러나 뷰에서 지연 로딩하던 코드가 LazyInitializationException을 냅니다. 필요한 데이터를 트랜잭션 안에서 조회해 DTO로 만들어 반환합니다.
