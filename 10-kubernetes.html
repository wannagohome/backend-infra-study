1부

서버 한 대의 Docker에서 클러스터로

9장의 Docker와 Compose는 서버 한 대 안의 일입니다. 서버 20대에 컨테이너 300개라면 빈자리에 배치하기, 죽은 것 되살리기, 바뀌는 IP 앞에 고정 주소 두기, 개수 늘리기와 새 버전 교체를 사람이 할 수 없습니다. 이 일을 자동화하는 컨테이너 오케스트레이션의 사실상 표준이 Kubernetes(K8s)입니다.

명령 대신 원하는 상태를 적어 둔다

"컨테이너 3개를 띄워라"는 명령형입니다. 한 번 실행되고 끝나므로, 나중에 하나가 죽어도 아무도 다시 띄우지 않습니다.

Kubernetes는 "이 이미지가 항상 3개 떠 있어야 한다"는 선언형 기록을 받습니다. 그리고 조정 루프가 실제 상태를 관찰해 원하는 상태와의 차이를 계속 메웁니다.

그래서 자가 치유는 별도 기능이 아니라 이 루프가 끝없이 도는 결과입니다.

클러스터는 두뇌와 손발로 나뉜다

Control Plane 구성 요소는 각자 한 가지만 한다

구성 요소하는 일멈추면
kube-apiserver인증, 인가, 검증 후 etcd에 기록클러스터 조작 불가
etcd모든 오브젝트를 키-값으로 저장상태 유실 위험, 백업 필수
kube-scheduler노드 없는 Pod에 노드 지정새 Pod가 Pending
controller-managerDeployment, Node 등 루프 실행자가 치유와 확장 정지
cloud-controllerLB 생성, 노드 정보를 클라우드와 동기화LoadBalancer 생성 불가

Control Plane이 잠시 멈춰도 이미 떠 있는 Pod는 계속 돕니다. 노드의 kubelet과 커널 규칙은 그대로이기 때문입니다. etcd는 Raft 합의로 과반수가 동의해야 기록하므로 3대나 5대처럼 홀수로 둡니다. 3대면 1대, 5대면 2대까지 고장을 견딥니다.

노드에서는 kubelet이 런타임에 일을 시킨다

  1. kubelet배정된 Pod 감시
  2. CRI (gRPC)런타임 표준 인터페이스
  3. containerd또는 CRI-O
  4. runcnamespace, cgroup 생성
  5. 컨테이너프로세스 실행

kubelet은 각 노드의 에이전트로, 자기 노드에 배정된 Pod를 보고 컨테이너를 띄우고 프로브로 상태를 확인해 API Server에 보고합니다. 런타임과는 CRI라는 표준 gRPC 인터페이스로만 대화하므로 런타임을 바꿔 끼울 수 있습니다.

Docker 전용 연결 코드(dockershim)는 1.24에서 제거되었지만, Docker로 빌드한 이미지는 OCI 표준(9장)이라 그대로 실행됩니다. kube-proxy는 4부에서 볼 Service 라우팅 규칙을 노드 커널에 깔아 둡니다.

kubectl은 API Server의 HTTP 클라이언트다

$ kubectl get pods -n prod -o wide
$ kubectl describe pod api-7d9f-x2k   # 이벤트 포함
$ kubectl logs api-7d9f-x2k -c api -f
$ kubectl logs api-7d9f-x2k --previous # 직전 컨테이너
$ kubectl exec -it api-7d9f-x2k -- sh
$ kubectl apply -f deployment.yaml
$ kubectl explain deployment.spec.strategy
$ kubectl get deploy api -o yaml   # 저장된 원본

kubectl은 ~/.kube/config의 주소와 자격 증명으로 API Server에 REST 요청을 보낼 뿐입니다. 어떤 클러스터를 보는지는 컨텍스트가 정하므로, 운영 클러스터에서 실수하지 않게 늘 확인합니다.

apply는 파일의 원하는 상태를 서버에 맞추는 선언형 명령입니다. explain은 필드 설명서를 바로 보여 줍니다.

모든 오브젝트는 같은 다섯 칸으로 생겼다

apiVersion: v1          # API 그룹/버전
kind: Pod                # 오브젝트 종류
metadata:                # 이름, 네임스페이스, 라벨
  name: api
  namespace: prod
  labels: { app: api }
spec:                    # 원하는 상태 (사람이 씀)
  containers:
  - name: api
    image: ghcr.io/acme/api:1.4.2
status:                  # 실제 상태 (시스템이 씀)
  phase: Running
  podIP: 10.0.3.17

apiVersion과 kind는 어떤 API로 무엇을 만드는지, metadata는 이름표입니다. 핵심은 마지막 둘입니다.

spec은 사람이 적는 원하는 상태, status는 컨트롤러와 kubelet이 채우는 관찰 결과입니다. 조정 루프는 이 두 칸의 차이를 메우는 일이고, 그래서 YAML에 status를 직접 쓰지 않습니다.

라벨로 고르고, 어노테이션으로 메모한다

metadata:
  labels:
    app: api
    tier: backend
    env: prod
  annotations:
    team: payments
    kubernetes.io/change-cause: "v1.4.2 배포"

$ kubectl get pods -l app=api,env!=dev
$ kubectl get pods -l 'tier in (backend,batch)'

라벨은 오브젝트에 붙이는 짧은 키-값 꼬리표이고, 셀렉터는 라벨로 대상을 고르는 조건입니다. Deployment가 자기 Pod를, Service가 트래픽 보낼 Pod를 찾는 방법이 전부 셀렉터입니다.

어노테이션은 고르는 데 쓰지 않는 메모입니다. 배포 사유, 도구 설정처럼 길거나 기계가 읽는 정보를 담습니다.

Namespace는 이름, 권한, 할당량의 경계다

Namespace는 한 클러스터를 논리적으로 나누는 칸입니다. 같은 이름의 api Service가 dev와 prod에 따로 있을 수 있고, 뒤에서 볼 RBAC 권한과 ResourceQuota도 네임스페이스 단위로 겁니다.

처음부터 default, 시스템 구성 요소가 사는 kube-system, 노드 생존 신호를 담는 kube-node-lease, 공개 정보용 kube-public이 있습니다.

네임스페이스는 네트워크 벽이 아닙니다

다른 네임스페이스의 Pod에도 기본으로 그대로 접속됩니다. 통신을 막으려면 4부의 NetworkPolicy가 필요합니다.

네임스페이스에 속하지 않는 오브젝트

Node, PersistentVolume, StorageClass, ClusterRole, Namespace 자신은 클러스터 전체에 하나씩 존재합니다.

apply 한 번이 Pod가 되기까지

  1. kubectl apply

    API Server가 인증, 인가, 검증을 거쳐 Deployment를 etcd에 저장합니다.

  2. Deployment 컨트롤러

    "ReplicaSet이 없다"를 보고 ReplicaSet을 만듭니다.

  3. ReplicaSet 컨트롤러

    "3개 필요, 0개 있음"을 보고 노드 없는 Pod 3개를 만듭니다.

  4. kube-scheduler

    각 Pod에 자원이 맞는 노드 이름을 기록합니다.

  5. kubelet

    자기 노드에 배정된 Pod를 보고 런타임에 실행을 지시합니다.

누구도 다음 단계를 직접 호출하지 않습니다. 각 구성 요소가 API Server를 지켜보다가 자기 몫의 차이를 발견하면 움직이고, 결과를 다시 API Server에 적을 뿐입니다.

이 느슨한 연결 덕분에 노드가 죽어 Pod가 2개로 줄면 3단계 루프가 다시 돌아 하나를 새로 만듭니다. 여기서부터는 이 흐름의 각 단계를 하나씩 깊이 들어갑니다.

2부

Pod: 가장 작은 실행 단위

Kubernetes는 컨테이너가 아니라 Pod를 배치합니다. Pod 안에서 컨테이너가 무엇을 공유하는지, 어떻게 태어나고 끝나는지, 특히 끝나는 순간에 요청이 왜 실패하는지를 봅니다.

기초 원리 여기부터는 오브젝트별 내부 동작과 설정의 의미를 다룹니다.

Pod는 네트워크와 볼륨을 함께 쓰는 묶음

Pod는 같은 노드에 함께 놓이는 컨테이너 묶음입니다. 묶음 안의 컨테이너는 하나의 network namespace를 공유하므로 IP가 하나이고, 서로 localhost로 통신하며, 같은 볼륨을 마운트할 수 있습니다.

이 공유 namespace를 붙잡는 것이 pause 컨테이너입니다. 아무 일도 하지 않고 잠들어 있지만, 앱 컨테이너가 재시작되어도 Pod의 IP가 유지되는 이유가 이것입니다.

init은 끝나야 넘어가고, 사이드카는 끝까지 산다

spec:
  initContainers:
  - name: wait-db               # 끝나야 다음으로
    image: busybox:1.36
    command:
    - sh
    - -c
    - until nc -z db 5432; do sleep 2; done
  - name: log-agent             # 네이티브 사이드카
    restartPolicy: Always
    image: fluent/fluent-bit:3.1
  containers:
  - name: api
    image: ghcr.io/acme/api:1.4.2

init 컨테이너는 적힌 순서대로 하나씩 실행되고, 각자 성공적으로 끝나야 다음이 시작됩니다. 실패하면 Pod는 Init:CrashLoopBackOff에 머뭅니다.

init 자리에 restartPolicy: Always를 주면 네이티브 사이드카가 됩니다. 앱보다 먼저 떠서 끝까지 살아 있고, 1.33에서 정식(GA) 기능이 되었습니다.

네이티브 사이드카가 해결한 세 가지 문제

상황일반 컨테이너로 둔 사이드카네이티브 사이드카
시작 순서앱과 동시에 시작, 프록시보다 앱이 먼저 통신할 수 있음앱보다 먼저 시작이 보장됨
Job 완료사이드카가 안 끝나 Job도 안 끝남주 컨테이너가 끝나면 Job 완료
종료 순서앱과 동시에 SIGTERM, 순서 없음앱이 끝난 뒤 정의 역순으로 종료

Pod의 컨테이너는 함께 배치되고 함께 확장되므로, 앱과 DB를 한 Pod에 넣으면 앱을 늘릴 때 DB도 늘어납니다. 그래서 주 컨테이너 하나에 로그 수집기, 프록시처럼 돕는 컨테이너만 곁에 둡니다. 이렇게 "앱보다 먼저 뜨고 늦게 죽어야 하는" 보조 컨테이너는 이제 네이티브 사이드카로 두고, preStop으로 순서를 맞추던 우회는 필요 없습니다.

Pod 단계는 다섯, 재시작은 같은 자리에서

Pod 단계의미
Pending노드 배정 전이거나 이미지 받는 중
Running컨테이너 하나 이상이 실행 중
Succeeded모든 컨테이너가 성공 종료
Failed하나 이상이 실패로 종료
Unknown노드와 통신이 끊김

컨테이너마다 Waiting, Running, Terminated 상태와 이유가 따로 있어, CrashLoopBackOff는 단계가 아니라 Waiting의 이유입니다.

restartPolicy는 Always(Deployment), OnFailure, Never(Job)입니다. kubelet은 같은 노드에서 10초, 20초, 40초로 간격을 늘려 최대 5분까지 재시작하고, 10분 정상 동작하면 초기화합니다.

Pod 종료는 두 갈래로 동시에 진행된다

kubelet앱 컨테이너
삭제 요청, 엔드포인트 제거도 동시 시작
Terminating preStop sleep 10그동안 라우팅 규칙이 갱신됨
SIGTERM 종료 시작
새 요청 거절, 진행 중 요청 마무리
exit 0 정상 종료
유예 시간 초과 SIGKILL진행 중 요청 유실, 종료 코드 137

Pod를 지우면 API Server는 삭제 예정 시각을 적고, 두 일이 따로 시작됩니다. kubelet은 컨테이너를 끄고, Control Plane은 이 Pod를 Service의 대상 목록에서 뺍니다.

kubelet은 preStop 훅을 먼저 실행한 뒤 SIGTERM을 보내고, terminationGracePeriodSeconds(기본 30초)가 지나면 SIGKILL로 강제 종료합니다.

엔드포인트가 빠지기 전에 앱이 죽으면 502

종료 예산은 preStop과 앱 종료를 합친 값

spec:
  terminationGracePeriodSeconds: 45
  containers:
  - name: api
    image: ghcr.io/acme/api:1.4.2
    lifecycle:
      preStop:
        sleep: { seconds: 10 }
    # 앱은 SIGTERM 후 최대 25초 안에
    # 진행 중 요청을 끝내도록 설정 (11장)

유예 시간은 preStop이 시작될 때부터 세므로 preStop + 앱 종료 시간 < 유예 시간이어야 합니다. 위 예는 10초 + 25초에 여유를 두어 45초입니다.

sleep 액션은 kubelet이 직접 기다리므로 sleep 명령이 없는 distroless 이미지에서도 됩니다. 앱이 SIGTERM에 반응하게 만드는 설정은 11장에서 다룹니다.

종료가 깨지는 흔한 이유

  • SIGTERM이 앱에 닿지 않음: 셸 형식 ENTRYPOINT라 PID 1이 셸이면 신호가 전달되지 않아, 결국 유예 시간 뒤 SIGKILL(종료 코드 137)로 끝납니다(9장 PID 1 문제).
  • preStop이 유예 시간을 다 씀: preStop이 끝나지 않으면 kubelet은 2초를 한 번만 더 준 뒤 강제 종료합니다.
  • 긴 작업을 처리하는 컨슈머: 처리 중 메시지를 끝내거나 큐에 돌려놓는 코드가 없으면 강제 종료 때 유실되므로 멱등 처리(8장)가 전제입니다.
  • 강제 삭제: --force --grace-period=0은 노드의 실제 종료를 기다리지 않습니다. StatefulSet에서는 같은 이름 Pod가 두 개 뜰 수 있어 위험합니다.

3부

Pod를 대신 관리하는 컨트롤러

Pod는 일회용이라 직접 만들지 않습니다. 무상태 서버, 상태를 가진 서버, 노드마다 하나씩 도는 에이전트, 끝나는 일마다 Pod를 관리하는 방식이 다르고, 그래서 컨트롤러도 다릅니다.

ReplicaSet은 개수를, Deployment는 버전을

ReplicaSet은 셀렉터에 맞는 Pod가 정확히 N개가 되도록 만들고 지웁니다. 하지만 Pod 템플릿이 바뀌어도 기존 Pod는 그대로 둡니다. 개수만 볼 뿐 버전을 모릅니다.

Deployment는 템플릿이 바뀔 때마다 새 ReplicaSet을 만들고, 새것은 늘리고 옛것은 줄여 버전을 바꿉니다. 옛 ReplicaSet을 0개로 남겨 두므로 그대로 되돌릴 수 있습니다. 그래서 ReplicaSet은 직접 쓰지 않습니다.

Deployment YAML은 원하는 상태의 기록이다

kind: Deployment
metadata: { name: api, namespace: prod }
spec:
  replicas: 3
  selector: { matchLabels: { app: api } }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: ghcr.io/acme/api:1.4.2
        resources:
          requests: { cpu: 500m, memory: 1Gi }

selector와 template의 라벨이 맞아야 Deployment가 자기 Pod를 알아봅니다. 셀렉터는 만든 뒤 바꿀 수 없습니다.

template 안이 바뀔 때만 새 리비전이 생깁니다. replicas만 바꾸면 기존 ReplicaSet의 개수만 조정됩니다. requests는 6부의 스케줄링과 7부의 HPA가 쓰는 기준입니다.

롤링 업데이트는 두 숫자 사이를 걷는다

  1. 시작: v1 4개

    replicas 4, maxSurge 25%(올림 1), maxUnavailable 25%(내림 1).

  2. v2 1개 추가, v1 1개 제거

    총 5개까지 허용, 가용 3개 이상 유지.

  3. v2가 Ready가 되면

    그만큼 v1을 더 줄이고 v2를 더 늘립니다.

  4. v2가 Ready가 안 되면

    진행이 멈춥니다. v1 3개가 계속 트래픽을 받습니다.

  5. 완료: v2 4개

    v1 ReplicaSet은 0개로 남습니다.

maxSurge는 원하는 개수보다 더 띄울 수 있는 수, maxUnavailable은 동시에 빠져도 되는 수입니다. 기본값은 둘 다 25%입니다.

용량을 한 순간도 줄이면 안 되면 maxUnavailable: 0, maxSurge: 1로 둡니다. 느리지만 가장 안전합니다. 진행의 기준이 readiness라서, readiness probe가 없으면 뜨기만 해도 준비된 것으로 보고 넘어갑니다.

Job은 끝나는 일을 끝까지 시킨다

4부

바뀌는 Pod 앞에 고정된 길을 낸다

Pod는 생길 때마다 새 IP를 받습니다. Pod끼리 어떻게 통신하는지, Service가 어떻게 고정 주소를 만드는지, 이름 조회와 외부 트래픽 유입, 통신 차단까지 차례로 봅니다.

모든 Pod는 NAT 없이 서로 닿는 IP를 받는다

Kubernetes 네트워크 모델의 약속은 셋입니다. 모든 Pod는 고유 IP를 갖고, 어느 노드에 있든 NAT 없이 서로 통신하며, 노드의 에이전트도 Pod에 직접 닿습니다.

이 약속을 실제로 구현하는 것이 CNI 플러그인입니다. Pod가 생기면 veth 쌍을 만들어 Pod의 namespace와 노드를 잇고, IP를 할당하고, 다른 노드로 가는 경로를 깝니다. 오버레이(VXLAN 캡슐화)나 직접 라우팅을 씁니다.

Service는 Pod 묶음에 고정 주소를 준다

kind: Service
metadata: { name: api, namespace: prod }
spec:
  type: ClusterIP           # 기본값
  selector: { app: api }    # 이 라벨의 Pod로
  ports:
  - port: 80                # Service가 받는 포트
    targetPort: 8080        # Pod의 포트

$ kubectl get svc api
NAME  TYPE       CLUSTER-IP     PORT(S)
api   ClusterIP  10.96.142.18   80/TCP

Service는 셀렉터에 맞는 Pod들 앞에 변하지 않는 가상 IP(ClusterIP)와 DNS 이름을 둡니다. Pod가 몇 번을 다시 태어나도 클라이언트는 api:80만 알면 됩니다.

2장의 L4 로드 밸런서를 클러스터 안에 둔 것과 같습니다. 연결 단위로 대상 Pod 하나를 고르며, Ready 상태인 Pod만 대상이 됩니다.

ClusterIP는 어디에도 없는 IP다

ClusterIP를 가진 인터페이스는 어느 노드에도 없습니다. 각 노드의 kube-proxy가 "이 IP:포트로 가는 패킷은 이 Pod들 중 하나로 목적지를 바꿔라"라는 DNAT 규칙을 커널에 깔아 둘 뿐입니다.

그래서 패킷은 보내는 Pod의 노드에서 바로 실제 Pod IP로 바뀌어 나가고, 응답은 conntrack이 되돌려 줍니다. ClusterIP에 ping이 안 되는 이유도 규칙이 TCP/UDP 포트에만 걸리기 때문입니다.

Cilium처럼 eBPF로 kube-proxy 자체를 대체하는 CNI도 많이 씁니다. 업그레이드 때 기본값이 바뀌어도 놀라지 않게 모드를 설정에 명시해 둡니다.

Ingress는 규칙이고, 실행은 컨트롤러가 한다

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: web }
spec:
  ingressClassName: public   # 어느 컨트롤러가 맡나
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service: { name: api, port: { number: 80 } }

LoadBalancer Service는 Service마다 LB를 하나씩 만들어 비쌉니다. Ingress는 LB 하나로 들어온 HTTP를 호스트와 경로에 따라 여러 Service로 나누는 L7 규칙입니다(2장 L7 라우팅).

Ingress 오브젝트는 규칙일 뿐이고, 그것을 읽어 실제 프록시를 구성하는 Ingress 컨트롤러를 따로 설치해야 동작합니다. AWS에서는 AWS Load Balancer Controller가 ALB를 만듭니다(14장).

Ingress는 동결됐고, 다음은 Gateway API

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api }
spec:
  parentRefs: [{ name: public-gw }]
  hostnames: [shop.example.com]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs:
    - { name: api-v1, port: 80, weight: 90 }
    - { name: api-v2, port: 80, weight: 10 }

Ingress API는 더 이상 기능이 추가되지 않고, 프로젝트는 Gateway API를 권장합니다. 가장 널리 쓰이던 Ingress NGINX 컨트롤러도 2026년 3월 은퇴해 보안 패치가 끊겼습니다.

Gateway API는 역할을 나눕니다. 인프라 제공자가 GatewayClass를, 운영자가 Gateway(리스너, TLS)를, 개발자가 HTTPRoute를 씁니다. 가중치 분할과 헤더 매칭이 표준이라 어노테이션 의존이 줄어듭니다.

NetworkPolicy가 없으면 모든 Pod가 열려 있다

# 1) prod의 모든 Pod: 들어오는 트래픽 기본 차단
kind: NetworkPolicy
metadata: { name: default-deny, namespace: prod }
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# 2) api Pod: web Pod에서 8080만 허용
kind: NetworkPolicy
metadata: { name: api-from-web, namespace: prod }
spec:
  podSelector: { matchLabels: { app: api } }
  ingress:
  - from: [{ podSelector: { matchLabels: { app: web } } }]
    ports: [{ port: 8080 }]

기본은 전부 허용입니다. 어떤 Pod를 고르는 정책이 하나라도 생기면 그 Pod는 그 방향으로 격리되고, 정책들이 허용한 것만 통과합니다. 정책은 허용 목록의 합집합입니다.

정책을 실제로 집행하는 것은 CNI입니다. 지원하지 않는 CNI에서는 오브젝트만 생기고 아무것도 막지 않습니다. Egress를 막을 때는 DNS(53번) 허용을 잊기 쉽습니다.

서비스 메시는 프록시로 통신을 가로챈다

서비스 메시는 모든 Pod 곁에 Envoy 같은 프록시를 두고 서비스 간 통신을 그 프록시로 지나가게 합니다. 앱 코드를 바꾸지 않고 서비스 사이 mTLS 암호화와 상호 인증, 재시도와 타임아웃, 가중치 트래픽 분할, 호출 단위 메트릭과 트레이스를 얻습니다.

대표가 Istio와 Linkerd입니다. Istio는 Pod마다 사이드카를 두는 대신 노드 단위 프록시를 쓰는 ambient 모드도 제공합니다.

메시는 공짜가 아닙니다

호출마다 프록시를 두 번 거치는 지연, Pod마다 늘어나는 메모리, 새로 익혀야 할 장애 지점이 생깁니다. 서비스 수가 적으면 라이브러리와 NetworkPolicy로 충분한 경우가 많습니다.

설정과 저장소: 이미지 밖에 두는 것들

ConfigMap은 설정을 이미지 밖으로 뺀다

- name: cfg
  configMap: { name: api-config }

ConfigMap은 설정 값을 키-값으로 담는 오브젝트입니다. Pod는 이것을 두 방식으로 받습니다. 환경 변수로 넣거나, 볼륨으로 마운트해 키마다 파일 하나로 봅니다.

이미지는 환경과 무관하게 한 번만 빌드하고, 환경별 차이는 ConfigMap만 바꿔 줍니다. 크기는 1MiB까지라 큰 파일에는 맞지 않습니다.

환경 변수는 재시작해야, 볼륨은 잠시 뒤 바뀐다

주입 방식ConfigMap을 고치면주의
환경 변수Pod를 다시 만들어야 반영프로세스 시작 때 한 번 읽음
볼륨 마운트kubelet 동기화 후 파일 교체앱이 파일을 다시 읽어야 함
subPath 마운트영영 반영 안 됨파일 하나만 꽂을 때 함정
immutable: true수정 자체가 금지새 이름으로 만들어 교체

볼륨 반영은 kubelet의 주기적 동기화와 캐시 전파를 거치므로 수십 초에서 1분 넘게 걸릴 수 있습니다. 그래서 실무에서는 설정 내용의 해시를 Pod 템플릿 어노테이션에 넣어, 설정이 바뀌면 롤링 업데이트가 일어나게 합니다. Helm의 checksum 어노테이션, Kustomize의 이름 접미사가 이 방법입니다.

Secret의 base64는 암호화가 아니다

kind: Secret
metadata: { name: db }
type: Opaque
data:
  password: c3VwZXItc2VjcmV0   # base64

$ kubectl get secret db \
    -o jsonpath='{.data.password}' | base64 -d
super-secret

Secret은 비밀번호와 키를 담는 ConfigMap의 사촌입니다. 값이 base64인 이유는 바이너리를 담기 위해서일 뿐, 누구나 되돌릴 수 있습니다.

기본 설정에서 Secret은 etcd에 암호화되지 않은 채 저장됩니다. 또 네임스페이스에서 Pod를 만들 수 있는 사람은 그 Pod에 Secret을 마운트해 읽을 수 있으니, Pod 생성 권한이 곧 Secret 읽기 권한입니다.

Secret을 실제로 지키는 세 겹

  • 저장 시 암호화: API Server의 EncryptionConfiguration으로 etcd에 쓰기 전에 암호화하고, 키는 KMS(AWS라면 KMS, 16장)에 맡깁니다. 관리형 클러스터는 대개 설정 하나로 켭니다.
  • RBAC 최소화: Secret의 get, list와 Pod 생성 권한을 꼭 필요한 주체에게만 줍니다(8부).
  • 외부 저장소 연동: 원본은 AWS Secrets Manager 같은 곳에 두고 External Secrets Operator가 Secret으로 동기화하거나, Secrets Store CSI 드라이버로 파일로 마운트합니다.

Secret YAML을 Git에 커밋하지 마세요

base64라 평문과 같습니다. GitOps로 관리하려면 External Secrets처럼 참조만 커밋하거나, Sealed Secrets와 SOPS처럼 암호화한 파일을 씁니다(GitOps 자체는 11장).

볼륨은 수명이 Pod와 같은지로 나뉜다

볼륨데이터 수명쓰임과 주의
emptyDirPod와 함께 삭제컨테이너 간 공유, 임시 파일
emptyDir (Memory)Pod와 함께 삭제tmpfs, 메모리 한도에 포함
hostPath노드에 남음노드 파일 노출, 보안 위험
configMap, secret원본 오브젝트를 따름설정 파일 주입
persistentVolumeClaimPod와 무관하게 유지DB, 업로드 파일

컨테이너의 쓰기 레이어(9장)는 컨테이너가 재시작되면 사라집니다. emptyDir은 그보다 길게 Pod 수명 동안 남고, PVC는 Pod가 어느 노드로 옮겨 가도 따라옵니다. hostPath는 노드 파일 시스템을 그대로 열어 주므로 DaemonSet 같은 시스템 용도 외에는 쓰지 않습니다.

PVC로 주문하면 StorageClass가 디스크를 만든다

PV는 실제 디스크 한 개를 나타내는 클러스터 오브젝트이고, PVC는 "50Gi, 한 노드에서 쓰기" 같은 사용자의 주문서입니다. 둘이 짝지어지면(바인딩) Pod는 PVC 이름만으로 디스크를 씁니다.

PV를 미리 만들어 두지 않아도 StorageClass가 주문을 보고 디스크를 새로 만듭니다. 이것이 동적 프로비저닝이고, 실제 생성은 스토리지별 CSI 드라이버가 합니다.

접근 모드와 회수 정책이 데이터 운명을 정한다

kind: StorageClass
metadata: { name: gp3 }
provisioner: ebs.csi.aws.com
parameters: { type: gp3 }
reclaimPolicy: Retain          # 기본 Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true

접근 모드는 ReadWriteOnce(한 노드에서 읽기·쓰기), ReadOnlyMany, ReadWriteMany(여러 노드, EFS 같은 파일 스토리지), ReadWriteOncePod(Pod 하나만)입니다. 블록 디스크는 대개 RWO만 됩니다.

동적 생성 PV의 회수 정책은 기본 Delete라 PVC를 지우면 디스크도 지워집니다. 중요한 데이터는 Retain으로 둡니다. AZ에 묶인 디스크는 WaitForFirstConsumer로 Pod 배치 뒤에 만들어야 다른 AZ에 생기지 않습니다.

6부

자원과 스케줄링: 어디에, 얼마나

Pod가 얼마나 쓸지 적는 두 숫자가 배치, 성능, 생존 순서를 모두 정합니다. 그 위에 노드를 고르고 밀어내는 규칙들이 얹힙니다.

requests는 예약이고, limits는 상한이다

containers:
- name: api
  resources:
    requests: { cpu: 500m, memory: 1Gi }
    limits:   { memory: 1Gi }

$ kubectl describe node ip-10-0-1-23
Allocatable:  cpu: 3920m   memory: 14.8Gi
Allocated resources:
  cpu       3500m (89%)   memory  12Gi (81%)

requests는 스케줄러가 보는 예약량입니다. 노드에 놓인 Pod들의 requests 합이 노드의 Allocatable을 넘지 않게 배치합니다. 실제 사용량과는 무관합니다.

limits는 실행 중 커널 cgroup(9장)이 집행하는 상한입니다. 500m은 0.5코어, 1Gi는 1024MiB입니다. Allocatable은 노드 용량에서 시스템 예약분과 eviction 여유를 뺀 값입니다.

CPU는 느려지고, 메모리는 죽는다

CPU limit은 9장에서 본 cgroup의 CFS 할당량(cpu.max)으로 집행되므로, 같은 스로틀링이 그대로 일어납니다. limit 500m은 100ms 주기당 50ms라, 스레드 4개가 함께 쓰면 12.5ms 만에 소진하고 87.5ms를 기다립니다.

메모리는 빌려 쓸 수 없어, limit을 넘으면 커널이 프로세스를 죽입니다. 상태는 OOMKilled, 종료 코드는 137입니다.

QoS 클래스는 requests와 limits의 모양이다

QoS 클래스조건자원이 모자랄 때
Guaranteed모든 컨테이너 CPU·메모리 requests = limits가장 마지막에 희생
Burstablerequests가 하나라도 있으나 위는 아님requests 초과분 기준으로 희생
BestEffortrequests, limits 모두 없음가장 먼저 희생

QoS 클래스는 직접 고르지 않고 Kubernetes가 붙입니다. 노드 메모리가 바닥나면 커널 OOM Killer가 고르는 순서(oom_score_adj)와 kubelet이 Pod를 쫓아내는 순서에 영향을 줍니다. 운영 서비스에 BestEffort Pod를 두지 않는 것이 첫 원칙이고, 중요한 서비스는 메모리를 Guaranteed에 가깝게 맞춥니다.

LimitRange는 기본값을, ResourceQuota는 총량을

kind: LimitRange
metadata: { name: defaults, namespace: team-a }
spec:
  limits:
  - type: Container
    defaultRequest: { cpu: 100m, memory: 256Mi }
    default:        { memory: 512Mi }
    max:            { memory: 4Gi }
---
kind: ResourceQuota
metadata: { name: quota, namespace: team-a }
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 64Gi
    pods: "100"

LimitRange는 requests나 limits를 빠뜨린 컨테이너에 기본값을 채우고, 한 컨테이너가 가질 수 있는 최소·최대를 정합니다.

ResourceQuota는 네임스페이스 전체의 합계 한도입니다. CPU requests 쿼터를 걸면 requests 없는 Pod는 생성이 거부되므로 LimitRange와 함께 씁니다. 여러 팀이 클러스터를 나눠 쓸 때의 기본 장치입니다.

스케줄러는 걸러 내고 점수를 매긴다

nodeSelector와 node affinity로 노드를 고른다

nodeSelector:
  kubernetes.io/arch: arm64        # 단순 일치
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node.kubernetes.io/instance-type
          operator: In
          values: [m7g.large, m7g.xlarge]
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 50
      preference:
        matchExpressions:
        - { key: capacity, operator: In, values: [spot] }

nodeSelector는 노드 라벨 완전 일치만 됩니다. node affinity는 In, NotIn, Exists 같은 연산자와 필수(required), 선호(preferred) 구분을 줍니다.

긴 이름 끝의 IgnoredDuringExecution은 "배치할 때만 본다"는 뜻입니다. 나중에 노드 라벨이 바뀌어도 이미 떠 있는 Pod는 쫓겨나지 않습니다.

Pod affinity는 붙이고, anti-affinity는 뗀다

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels: { app: api }
        topologyKey: kubernetes.io/hostname

Pod affinity는 "이 라벨의 Pod가 있는 곳 근처에", anti-affinity는 "그런 Pod가 없는 곳에" 놓으라는 규칙입니다. 근처의 범위는 topologyKey가 정해, hostname이면 같은 노드, zone이면 같은 AZ입니다.

위 예는 api 복제본을 서로 다른 노드에 흩어 노드 하나가 죽어도 전부 죽지 않게 합니다. 필수(required)로 걸면 복제본이 노드 수보다 많을 때 남는 Pod가 Pending에 갇히므로, 흔히 선호로 씁니다.

topologySpreadConstraints로 AZ에 고르게

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels: { app: api }
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels: { app: api }

maxSkew: 1은 가장 많은 영역과 가장 적은 영역의 Pod 수 차이를 1 이하로 지키라는 뜻입니다. 복제본 6개, AZ 3개면 2, 2, 2가 되어 AZ 하나가 장애 나도 4개가 남습니다.

DoNotSchedule은 필터, ScheduleAnyway는 점수로 작동합니다. 분산은 배치 순간에만 맞추므로, 노드가 바뀐 뒤 쏠린 Pod를 다시 펴려면 descheduler 같은 도구가 필요합니다.

taint는 노드가 밀어내고, toleration은 견딘다

$ kubectl taint nodes gpu-1 \
    dedicated=gpu:NoSchedule

# GPU 작업 Pod
tolerations:
- key: dedicated
  value: gpu
  effect: NoSchedule
nodeSelector:
  dedicated: gpu   # 끌어오는 건 별도

taint는 노드에 거는 "들어오지 마시오" 표시이고, toleration은 그것을 견디는 Pod 쪽 허가입니다. 효과는 NoSchedule(새 배치 금지), PreferNoSchedule(가급적 금지), NoExecute(이미 있는 Pod도 쫓아냄) 셋입니다.

toleration은 들어갈 수 있게 할 뿐 끌어오지 않으므로 전용 노드에는 affinity를 함께 씁니다. 노드 장애 때 Control Plane이 거는 unreachable taint도 NoExecute인데, 모든 Pod에 기본 300초 toleration이 붙어 있어 죽은 노드의 Pod는 약 5분 뒤에 옮겨 갑니다.

PriorityClass가 높으면 자리를 빼앗는다

kind: PriorityClass
metadata: { name: critical-api }
value: 100000
description: "결제 API"
---
kind: PriorityClass
metadata: { name: batch-low }
value: -10
preemptionPolicy: Never
---
# Pod spec
priorityClassName: critical-api

자리가 없어 Pending인 Pod의 우선순위가 높으면, 스케줄러는 낮은 우선순위 Pod를 쫓아내(선점) 자리를 만듭니다. 쫓겨나는 Pod도 정상 종료 절차를 밟습니다.

preemptionPolicy: Never는 줄은 앞에 서되 남을 쫓아내지는 않습니다. 사용자 값은 10억 이하만 허용되어, 약 20억인 system-cluster-critical 같은 시스템 클래스보다 항상 낮습니다.

노드가 버거우면 kubelet이 Pod를 쫓아낸다

kubelet은 노드 자원을 감시하다가 문턱을 넘으면 Pod를 골라 축출합니다. 리눅스 기본 하드 문턱은 memory.available<100Mi, nodefs.available<10%, imagefs.available<15%, nodefs.inodesFree<5%입니다.

먼저 사용량이 requests를 넘은 Pod를 우선순위와 초과량 순으로, 그다음 requests 안에서 쓰는 Pod를 고릅니다. 하드 문턱 축출은 유예 시간 없이 즉시 끝내고 PDB도 보지 않습니다.

7부

헬스 체크, 확장, 가용성

여기부터는 운영입니다. 프로브를 잘못 걸어 멀쩡한 서비스를 죽이는 사고, 오토스케일러의 계산과 출렁임, 노드를 비울 때 서비스를 지키는 장치를 다룹니다.

원리 실무 설정 수치, 장애 사례, 판단 기준을 다룹니다.

세 프로브는 서로 다른 질문을 한다

프로브묻는 것실패하면
startup느린 시작이 끝났나끝날 때까지 나머지 둘을 보류
liveness프로세스가 고장 났나 (데드락 등)컨테이너 재시작
readiness지금 트래픽을 받아도 되나Service 대상에서 빼기만

프로브는 kubelet이 실행합니다. HTTP GET(200~399면 성공), TCP 연결, 컨테이너 안 명령, gRPC 헬스 체크 중 하나를 고릅니다. 기본값은 periodSeconds 10초, timeoutSeconds 1초, failureThreshold 3회입니다.

readiness는 "잠시 빼 달라", liveness는 "나를 다시 시작해 달라"는 신호입니다. 8장에서 본 로드 밸런서 헬스 체크를 두 질문으로 쪼갠 것입니다.

startup probe가 느린 JVM 기동을 지켜 준다

startupProbe:
  httpGet: { path: /livez, port: 8080 }
  periodSeconds: 10
  failureThreshold: 30   # 최대 300초 대기
livenessProbe:
  httpGet: { path: /livez, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /readyz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2

기동에 1분이 걸리는 앱에 liveness만 걸면 준비가 끝나기 전에 실패로 판정되어 재시작되고, 다시 처음부터 기동하다 또 죽는 무한 반복에 빠집니다.

startup probe는 failureThreshold × periodSeconds(여기서는 300초)까지 기다려 주고, 한 번 성공하면 그때부터 liveness와 readiness가 시작됩니다. Spring Boot라면 /actuator/health/liveness와 /readiness를 각각 연결합니다.

프로브를 잘못 걸면 멀쩡한 서비스가 죽는다

잘못된 설정일어나는 일고치는 법
liveness에 DB 검사DB가 느려지면 전 Pod 동시 재시작liveness는 프로세스 자체만
liveness timeout 1초부하나 GC 정지 때 재시작, 부하 가중timeout과 실패 횟수 넉넉히
startup 없이 짧은 지연기동 중 죽어 무한 재시작startup probe 추가
readiness에 외부 의존외부 장애 때 모든 Pod 제외, 503자기 준비 상태만 확인
readiness 없음롤링 중 준비 안 된 Pod로 요청readiness 반드시 설정

공통 원리는 하나입니다. 공유 의존성을 프로브에 넣으면 장애가 한 Pod가 아니라 전체로 번집니다. 의존성 상태는 프로브가 아니라 메트릭과 서킷 브레이커(8장)로 다룹니다.

HPA는 사용률 비율만큼 Pod 수를 바꾼다

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 60 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300

HPA는 15초마다 metrics-server(별도 설치 애드온)에서 CPU를 읽어 ceil(현재 개수 × 현재값 / 목표값)으로 개수를 정합니다. 4개, 평균 90%, 목표 60%면 ceil(4 × 90 / 60) = 6개입니다.

사용률은 requests 대비이고, 비율이 1에서 10% 이내면 움직이지 않습니다. 늘릴 때는 즉시, 줄일 때는 최근 5분 추천값 중 최댓값으로 천천히 줄입니다. HPA를 쓰면 GitOps 매니페스트에서 replicas를 빼야 덮어쓰기 싸움이 없습니다.

CPU가 아닌 지표로 늘리기: 커스텀 메트릭과 KEDA

I/O를 기다리는 서비스나 큐 컨슈머는 CPU가 부하를 잘 보여 주지 않습니다. HPA는 Prometheus Adapter 같은 구현을 통해 초당 요청 수 같은 커스텀 메트릭이나 큐 길이 같은 외부 메트릭으로도 계산할 수 있습니다.

KEDA는 SQS, Kafka, Prometheus 등 수십 가지 이벤트 소스를 읽어 HPA를 대신 만들어 주는 애드온으로, 일이 없을 때 0개까지 줄이는 데 많이 씁니다.

0개까지 줄이기

CPU 같은 자원 메트릭은 떠 있는 Pod에서만 잴 수 있어 0개가 불가능합니다. 1.37에서는 외부·오브젝트 메트릭을 쓰는 HPA의 minReplicas: 0이 기본 활성(베타)입니다.

VPA와 in-place 리사이즈는 Pod 크기를 바꾼다

HPA가 개수를 바꾼다면 VPA는 requests를 바꿉니다. 별도 설치하는 애드온으로, 과거 사용량에서 적정 requests를 추천하고, 설정에 따라 Pod를 다시 만들거나 그대로 고쳐 적용합니다. 추천만 받는 모드로 시작해 requests를 맞추는 데 특히 유용합니다.

예전에는 requests를 바꾸려면 Pod를 다시 만들어야 했습니다. 1.35에서 정식이 된 in-place 리사이즈는 실행 중인 Pod의 CPU·메모리를 재시작 없이 바꿀 수 있게 했습니다.

HPA와 VPA를 같은 CPU 지표에 걸지 마세요

VPA가 requests를 올리면 사용률이 내려가 HPA가 Pod를 줄이고, 그러면 다시 사용률이 올라갑니다. 서로의 입력을 바꾸므로 출렁입니다. 함께 쓰려면 HPA는 커스텀 메트릭을 씁니다.

정리

  • Kubernetes는 조정 루프의 집합입니다. 원하는 상태를 적으면 컨트롤러들이 실제 상태와의 차이를 끝없이 메우고, 자가 치유와 롤링 업데이트가 그 결과입니다.
  • Pod는 일회용이고, 정체성은 컨트롤러가 줍니다. 무상태는 Deployment, 순번과 디스크가 필요하면 StatefulSet, 노드마다는 DaemonSet, 끝나는 일은 Job입니다.
  • Service는 라벨과 readiness로 대상을 고르는 가상 IP입니다. kube-proxy의 커널 규칙과 CoreDNS가 그것을 실현하고, 외부 유입은 Ingress에서 Gateway API로 옮겨 가고 있습니다.
  • requests는 배치를, limits는 집행을 정합니다. CPU 초과는 스로틀링, 메모리 초과는 OOMKilled이며, QoS와 축출 순서도 이 두 숫자에서 나옵니다.
  • 운영 사고의 상당수는 설정 하나에서 옵니다. 종료 절차와 preStop, 프로브의 의존성, PDB 한도, HPA의 requests 기준을 먼저 점검합니다.

스스로 점검 (1)

  1. 노드 하나가 꺼졌을 때 그 위의 Pod가 다른 노드에서 다시 뜨기까지 무슨 일이 일어나나요?

    노드에 unreachable taint가 걸리고, 기본 toleration 300초가 지나면 Pod가 축출됩니다. ReplicaSet 컨트롤러가 개수 부족을 보고 새 Pod를 만들고 스케줄러가 다른 노드에 배정합니다.

  2. preStop 없이 배포할 때마다 502가 몇 건씩 나는 이유는 무엇인가요?

    엔드포인트 제거가 각 노드와 LB에 퍼지기 전에 앱이 SIGTERM을 받고 먼저 닫히기 때문입니다. preStop으로 몇 초 기다린 뒤 종료를 시작하게 합니다.

  3. maxSurge 0, maxUnavailable 0으로 두면 어떻게 되나요?

    새 Pod를 더 띄울 수도, 옛 Pod를 뺄 수도 없어 업데이트가 불가능하므로 API가 거부합니다. 둘 중 하나는 0보다 커야 합니다.

  4. CPU 사용률 평균이 30%인데 응답 지연이 튀는 Pod가 있습니다. 무엇을 의심하나요?

    CPU limit에 의한 CFS 스로틀링입니다. 짧은 순간 여러 스레드가 할당량을 소진하면 평균은 낮아도 주기 대부분을 멈춰 있게 됩니다.

  5. Service의 ClusterIP로 ping이 안 되는 것은 장애인가요?

    아닙니다. ClusterIP는 인터페이스가 없는 가상 IP이고 kube-proxy 규칙이 Service 포트의 TCP/UDP에만 걸리므로 ICMP는 응답하지 않습니다.

스스로 점검 (2)

  1. liveness probe에서 DB 연결을 검사하면 어떤 장애가 생기나요?

    DB가 잠깐 느려지면 모든 Pod의 liveness가 동시에 실패해 일제히 재시작됩니다. 재시작 중 연결 폭증으로 DB가 더 느려지는 악순환이 생깁니다.

  2. Pod 4개, 평균 CPU 120%, 목표 80%면 HPA는 몇 개로 늘리나요? requests를 두 배로 올리면요?

    ceil(4 × 120 / 80) = 6개입니다. requests가 두 배면 사용률이 60%로 계산되어 ceil(4 × 60 / 80) = 3개로 오히려 줄이려 합니다(최소 개수 안에서).

  3. replicas 2인 Deployment에 minAvailable 2인 PDB를 걸면 노드 drain은 어떻게 되나요?

    허용 중단이 0이라 Eviction API가 계속 거절해 drain이 끝나지 않습니다. maxUnavailable 1로 두거나 복제본을 늘립니다.

  4. Secret을 볼륨으로 마운트했는데 값을 바꿔도 앱이 옛 값을 씁니다. 가능한 원인 두 가지는?

    subPath로 마운트해 갱신이 반영되지 않거나, 파일은 바뀌었지만 앱이 시작할 때 한 번만 읽은 경우입니다. 설정 해시 어노테이션으로 롤링 재시작을 일으키는 것이 확실합니다.

  5. EBS를 쓰는 StatefulSet Pod가 재생성 후 Pending에 머뭅니다. 무엇을 확인하나요?

    PV가 특정 AZ에 묶여 있어 그 AZ에 자리가 있는 노드가 없는지 봅니다. 해당 AZ에 노드를 늘리거나 WaitForFirstConsumer와 AZ 분산 설계를 점검합니다.
