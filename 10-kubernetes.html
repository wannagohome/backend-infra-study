1부

서버 여러 대의 컨테이너를 누가 돌보나

9장에서는 서버 한 대 위에서 컨테이너를 띄우고, 죽으면 다시 띄우고, Compose로 여러 개를 묶었습니다. 이 부에서는 서버가 수십 대로 늘 때 무엇이 무너지는지 보고, Kubernetes가 그 일을 어떤 구조로 떠맡는지 전체 지도를 그립니다.

서버 한 대일 때는 사람이 돌볼 수 있었다

9장 끝에서 우리는 쇼핑몰의 주문 API(order-api)를 이미지로 만들어 서버 한 대에서 docker run으로 띄웠습니다. 프로세스가 죽으면 재시작 정책이 다시 띄웠고, DB까지 함께 띄울 때는 Compose 파일 하나로 충분했습니다. 서버가 한 대라서 모든 결정을 그 서버 안에서 내릴 수 있었기 때문입니다.

이제 서비스가 커져 주문 API를 평소 3개, 행사 때 30개까지 띄워야 하고, 서버도 20대로 늘었다고 해 봅시다. 먼저 배치가 문제입니다. 새 컨테이너를 어느 서버에 놓아야 메모리가 넘치지 않는지 누군가 서버 20대의 남은 자원을 보고 골라야 합니다.

다음은 복구입니다. Docker의 재시작 정책은 같은 서버 안에서만 동작하므로, 서버 자체가 꺼지면 그 위의 컨테이너는 아무도 다른 서버에 다시 띄워 주지 않습니다. 새벽 세 시에 사람이 일어나야 합니다.

세 번째는 주소입니다. 컨테이너는 다시 뜰 때마다 다른 서버, 다른 IP에 놓이므로 이 API를 부르는 쪽은 매번 바뀌는 주소를 따라가야 합니다. 마지막으로 확장과 교체입니다. 트래픽에 맞춰 개수를 늘리고 줄이는 일, 새 버전을 한 대씩 바꾸며 문제가 생기면 되돌리는 일을 서버 20대에 손으로 하면 실수가 나지 않을 수 없습니다.

오케스트레이터가 다섯 가지 일을 떠맡는다

앞의 배치, 복구, 주소, 확장, 교체를 자동으로 해 주는 소프트웨어를 컨테이너 오케스트레이션 도구라고 부릅니다. 지휘자가 연주자 여럿을 맞추듯 컨테이너 여럿을 맞춘다는 뜻입니다. 그 사실상 표준이 Kubernetes로, 구글이 사내 시스템 Borg를 운영한 경험을 바탕으로 2014년에 공개했고 지금은 CNCF 재단이 관리합니다. K와 s 사이 여덟 글자를 줄여 K8s라고도 씁니다.

일사람이 하면Kubernetes에서 맡는 곳
배치서버별 남은 자원을 보고 고름스케줄러가 노드를 고름 (6부)
복구서버가 죽으면 새벽 호출개수를 지키는 루프가 다시 띄움 (3부)
주소바뀐 IP를 설정에 반영고정 이름과 가상 IP (4부)

교체한 대씩 바꾸고 되돌림롤링 업데이트와 롤백 (3부)

명령은 한 번 실행되고 잊힌다

# 명령형: 서버 세 대에 하나씩 띄운다
$ for h in node1 node2 node3; do

      ghcr.io/acme/order-api:1.4.2
  done

# 선언형: 원하는 상태만 적는다
kind: Deployment
metadata: { name: order-api }
spec:
  replicas: 3
  template: …   # 이미지 order-api:1.4.2

Kubernetes가 이 일을 어떻게 떠맡는지는 일하는 방식에서 시작합니다. 위쪽 스크립트는 명령형입니다. "세 대에 하나씩 띄워라"를 실행하고 끝나므로, 다음 날 node2가 꺼져 2개만 남아도 스크립트는 그 사실을 모릅니다.

아래쪽은 선언형입니다. 무엇을 할지가 아니라 "주문 API가 항상 3개 떠 있어야 한다"는 결과만 적어 Kubernetes에 맡깁니다. 그러면 지금 몇 개가 떠 있든, 어느 서버가 꺼졌든 3개를 맞추는 일은 시스템의 책임이 됩니다.

조정 루프가 차이를 끝없이 메운다

선언을 받은 쪽은 조정 루프를 돕니다. 실제 상태를 관찰하고, 원하는 상태와 비교하고, 차이가 있으면 메우는 행동을 한 뒤 다시 관찰합니다. 온도 조절기가 설정 온도와 실내 온도를 계속 비교하며 보일러를 켜고 끄는 것과 같습니다.

그림의 "Pod"는 Kubernetes가 컨테이너를 띄우는 단위입니다. 지금은 컨테이너 하나로 생각하고, 정확한 정의는 2부에서 봅니다. 자가 치유는 별도 기능이 아니라 이 루프가 끝없이 도는 결과입니다.

클러스터는 결정하는 쪽과 실행하는 쪽으로 나뉜다

그렇다면 이 루프들은 어디서 돌까요? Kubernetes가 관리하는 서버 묶음 전체를 클러스터라 하고, 그 안의 서버 한 대(물리 서버든 가상 머신이든)를 노드라고 합니다. 노드는 맡은 일에 따라 두 부류로 나뉩니다.

한쪽은 Control Plane입니다. 원하는 상태를 저장하고, 새 Pod를 어느 노드에 놓을지 정하고, 앞에서 본 조정 루프들을 돌립니다. 즉 "무엇이 어디에 있어야 하는가"를 결정하는 두뇌입니다. 운영 환경에서는 이 구성 요소들을 보통 서버 3대에 나눠 띄워 한 대가 죽어도 결정이 멈추지 않게 합니다.

다른 쪽은 워커 노드입니다. 우리 주문 API 컨테이너가 실제로 도는 곳이고, 각 노드에는 Control Plane의 결정을 받아 컨테이너를 띄우는 에이전트가 하나씩 있습니다. 노드가 20대면 에이전트도 20개입니다.

이렇게 나누면 결정과 실행의 장애가 분리됩니다. 워커 노드 하나가 죽으면 Control Plane이 그 일을 다른 노드에 다시 맡기고, Control Plane이 잠시 멈춰도 이미 떠 있는 컨테이너는 노드 위에서 계속 돕니다. 다음 그림에서 양쪽의 구성 요소를 한 번에 보고, 그 뒤로 하나씩 들어갑니다.

모든 구성 요소는 API Server를 거친다

API Server는 유일한 입구, etcd는 유일한 기억

그림 한가운데의 kube-apiserver(줄여서 API Server)는 클러스터의 유일한 입구입니다. 사람이 보내는 명령도, 컨트롤러와 노드 에이전트가 보내는 조회와 보고도 전부 이곳에 HTTP 요청으로 들어옵니다. 입구가 하나이므로 검사도 한곳에서 끝납니다.

요청이 들어오면 API Server는 세 관문을 거칩니다. 먼저 7장에서 본 인증(너는 누구인가)과 인가(그 일을 해도 되는가)를 확인하고, 이어서 어드미션 단계에서 요청 내용을 정책에 맞게 고치거나 거부합니다. 예를 들어 "팀 라벨이 없으면 기본 라벨을 붙인다"나 "root로 도는 컨테이너는 거부한다" 같은 규칙이 여기서 걸립니다. 마지막으로 형식이 올바른지 검증한 뒤 저장합니다.

저장하는 곳이 etcd입니다. etcd는 여러 서버에 같은 데이터를 복제해 두는 분산 키-값 저장소로, 클러스터의 모든 오브젝트(원하는 상태와 관찰된 상태)가 여기에 들어 있습니다. 다른 구성 요소는 etcd를 직접 만지지 않고 반드시 API Server를 통해 읽고 씁니다.

그래서 etcd가 사라지면 클러스터는 자기가 무엇을 해야 하는지 잊습니다. 노드 위의 컨테이너는 남아 있어도, 몇 개가 떠 있어야 하는지, 어떤 설정이었는지는 etcd에만 있기 때문입니다. 직접 운영하는 클러스터에서 etcd 백업이 필수인 이유입니다. 그러면 etcd는 서버 한 대가 죽는 상황을 어떻게 견딜까요?

etcd는 과반수가 동의해야 기록한다

etcd는 보통 3대나 5대로 띄웁니다. 여러 대가 같은 데이터를 갖되 서로 다른 값을 기억하면 안 되므로, Raft라는 합의 알고리즘을 씁니다. 한 대가 리더가 되어 쓰기를 받고, 과반수가 그 기록을 받았다고 답해야 확정합니다.

과반수를 요구하는 이유는 네트워크가 둘로 갈라져도 양쪽이 동시에 과반수일 수는 없어서, 서로 다른 기록이 확정되는 일이 원천적으로 막히기 때문입니다. 대가로 과반수가 살아 있어야만 쓸 수 있습니다.

etcd 대수과반수견디는 고장
1대10대
3대21대
4대31대
5대32대

4대는 3대와 견디는 고장 수가 같으면서 동의할 서버만 늘어 느려집니다. 그래서 홀수로 둡니다.

스케줄러와 컨트롤러는 차이를 보고 움직인다

나머지 셋은 API Server를 지켜보는 일꾼입니다. kube-scheduler는 아직 노드가 정해지지 않은 Pod를 발견하면 자원이 맞는 노드를 골라 그 이름을 Pod에 적습니다. kube-controller-manager는 앞에서 본 조정 루프(컨트롤러) 수십 개를 한 프로세스에 모아 돌립니다. cloud-controller-manager는 클라우드 위에서만 필요한 루프로, 로드 밸런서를 만들거나 사라진 가상 머신을 노드 목록에서 지우는 일을 클라우드 API로 합니다.

구성 요소하는 일멈추면
kube-apiserver인증, 인가, 검증 후 etcd에 기록클러스터 조작 불가
etcd모든 오브젝트를 키-값으로 저장과반수 잃으면 쓰기 불가
kube-scheduler노드 없는 Pod에 노드 지정새 Pod가 대기 상태로 남음
controller-manager개수 유지, 노드 감시 등 루프자가 치유와 확장 정지
cloud-controllerLB 생성, 노드를 클라우드와 동기화외부 LB 생성 불가

표의 오른쪽 열이 모두 "새로운 일"에 관한 것임에 주목하세요. 이미 떠 있는 Pod는 Control Plane이 멈춰도 계속 돕니다.

노드에서는 kubelet이 런타임에 일을 시킨다

  1. kubelet배정된 Pod 감시
  2. CRI (gRPC)런타임 표준 인터페이스
  3. containerd또는 CRI-O
  4. runcnamespace, cgroup 생성
  5. 컨테이너프로세스 실행

이제 오른쪽 워커 노드입니다. 노드마다 하나씩 도는 에이전트가 kubelet입니다. kubelet은 API Server를 지켜보다가 자기 노드 이름이 적힌 Pod를 발견하면 컨테이너를 띄우고, 상태를 주기적으로 확인해 API Server에 보고합니다. 앞의 스케줄러가 노드 이름을 "적기만" 해도 실제로 컨테이너가 뜨는 이유가 이것입니다.

kubelet은 컨테이너를 직접 만들지 않고 CRI라는 표준 규격으로 런타임에 요청합니다. CRI는 7장에서 본 gRPC로 정의되어 있어, 이 규격만 지키면 어떤 런타임이든 끼울 수 있습니다. 그 뒤는 9장에서 본 그대로 containerd가 이미지를 받고 runc가 namespace와 cgroup을 만들어 프로세스를 띄웁니다.

노드에는 하나가 더 있습니다. kube-proxy는 4부에서 볼 Service(여러 Pod 앞에 두는 고정 주소)로 가는 패킷을 실제 Pod로 돌려 보내는 규칙을 노드 커널에 깔아 둡니다. 지금은 "노드의 교통 규칙 담당" 정도로 기억해 두면 됩니다.

kubectl은 API Server의 HTTP 클라이언트다

$ kubectl config get-contexts
CURRENT  NAME      CLUSTER  NAMESPACE
*        prod-ctx  prod     prod
         dev-ctx   dev      dev
$ kubectl config use-context dev-ctx

$ kubectl get pods -v=6   # 요청 출력
GET https://10.0.0.1:6443/api/v1/
  namespaces/dev/pods?limit=500  200 OK

사람은 kubectl이라는 명령줄 도구로 클러스터를 다룹니다. kubectl은 특별한 통로가 아니라, 명령을 7장의 REST 요청으로 바꿔 API Server에 보내는 클라이언트일 뿐입니다. 마지막 명령처럼 -v=6을 붙이면 실제 HTTP 요청이 보입니다.

어디로 보낼지는 ~/.kube/config 파일(kubeconfig)이 정합니다. 이 파일에는 클러스터 주소, 사용자 자격 증명, 그리고 둘을 짝지은 컨텍스트가 들어 있습니다. 운영 클러스터에 실수로 명령하지 않도록 지금 컨텍스트를 늘 확인합니다.

처음 익힐 kubectl 명령은 여섯 개다

$ kubectl get pods -n prod -o wide
$ kubectl describe pod order-api-7d9f5-x2k4q
$ kubectl logs order-api-7d9f5-x2k4q -f
$ kubectl logs order-api-7d9f5-x2k4q --previous
$ kubectl exec -it order-api-7d9f5-x2k4q -- sh
$ kubectl apply -f deployment.yaml
$ kubectl explain deployment.spec.replicas

get은 목록을 보고(-n은 아래에서 볼 네임스페이스, -o wide는 IP와 노드까지), describe는 한 오브젝트의 상세와 최근 이벤트를 봅니다. logs는 컨테이너의 표준 출력을 보여 주며 -f는 계속 따라가기, --previous는 재시작 직전 컨테이너의 로그입니다.

exec는 9장의 docker exec처럼 컨테이너 안에서 명령을 실행합니다. apply는 파일에 적은 원하는 상태를 클러스터에 맞추는 선언형 명령이고, explain은 필드 설명서를 바로 보여 줍니다.

원하는 상태는 YAML 매니페스트로 적는다

name: order-api          # 키: 값
replicas: 3              # 숫자
labels:                  # 들여쓰기 = 안쪽
  app: order-api
ports:                   # - 는 목록 항목
- 8080
- 8443
selector: { app: web }   # 한 줄 표기
script: |                # 여러 줄 문자열
  echo start
  java -jar app.jar
---                      # 문서 구분선

apply에 넘기는 파일, 즉 원하는 상태를 적은 문서를 매니페스트라고 합니다. JSON도 되지만 사람이 읽고 쓰기 쉬운 YAML을 주로 씁니다.

YAML은 들여쓰기(공백, 탭 금지)로 포함 관계를 나타내고, -로 목록을, { }로 한 줄 묶음을 씁니다. | 뒤는 줄바꿈을 살린 문자열이고, ---로 한 파일에 여러 오브젝트를 담습니다. 들여쓰기 한 칸 차이로 뜻이 바뀌므로 오류의 흔한 원인입니다.

모든 오브젝트는 같은 다섯 칸으로 생겼다

apiVersion: v1          # API 그룹/버전
kind: Pod                # 오브젝트 종류
metadata:                # 이름표
  name: order-api
  namespace: prod
  labels: { app: order-api }
spec:                    # 원하는 상태
  containers:
  - name: api
    image: ghcr.io/acme/order-api:1.4.2
status:                  # 관찰된 상태
  phase: Running
  podIP: 10.0.3.17

Kubernetes가 저장하는 모든 것(Pod, 설정, 디스크 요청까지)을 오브젝트라 부르고, 모두 같은 틀을 씁니다. apiVersion은 어느 API 묶음의 몇 번째 버전인지(v1은 핵심 묶음, apps/v1은 apps 묶음), kind는 종류, metadata는 이름과 꼬리표입니다.

spec은 사람이 쓰는 원하는 상태, status는 시스템이 채우는 관찰 결과입니다. 조정 루프는 이 두 칸의 차이를 메우는 일이라 YAML에 status는 쓰지 않습니다.

라벨로 고르고, 어노테이션으로 메모한다

metadata:
  labels:
    app: order-api
    tier: backend
    env: prod
  annotations:
    team: payments
    kubernetes.io/change-cause: "1.4.2 배포"

$ kubectl get pods -l app=order-api,env!=dev
$ kubectl get pods -l 'tier in (backend,batch)'

오브젝트끼리는 서로를 이름으로 묶지 않습니다. 라벨이라는 짧은 키-값 꼬리표를 붙이고, 셀렉터라는 조건으로 "이 라벨을 가진 것 전부"를 고릅니다. Pod가 사라지고 새로 생겨도 라벨만 같으면 자동으로 묶이므로, 대상이 계속 바뀌는 환경에 맞는 방식입니다.

어노테이션은 고르는 데 쓰지 않는 메모로, 배포 사유나 도구 설정처럼 길거나 기계가 읽는 정보를 담습니다.

Namespace는 이름, 권한, 할당량의 경계다

한 클러스터를 여러 팀과 환경이 나눠 쓰려면 칸막이가 필요합니다. Namespace는 클러스터 안의 논리적인 칸으로, 같은 이름의 order-api가 dev와 prod에 따로 있을 수 있습니다. 9장의 리눅스 namespace와 이름만 같고 전혀 다른 개념입니다.

권한(누가 무엇을 할 수 있나, 8부 RBAC)과 자원 총량 한도(6부 ResourceQuota)도 이 칸 단위로 겁니다. 처음부터 default, 시스템 구성 요소가 사는 kube-system, 노드 생존 신호용 kube-node-lease, 공개 정보용 kube-public이 있습니다.

네임스페이스는 네트워크 벽이 아닙니다

다른 네임스페이스의 Pod에도 기본으로 그대로 접속됩니다. 통신을 막으려면 4부의 NetworkPolicy(Pod 간 방화벽 규칙)가 필요합니다.

네임스페이스에 속하지 않는 오브젝트

노드, 디스크(PersistentVolume), Namespace 자신처럼 클러스터 전체에 하나뿐인 것은 칸 밖에 있습니다.

Pod를 직접 만들지 않고 컨트롤러에 맡긴다

지금까지의 재료로 주문 API를 띄우는 길을 따라가 봅시다. 그 전에 오브젝트 세 개를 미리 짧게 알아 둡니다. 모두 뒤에서 자세히 다룹니다.

Pod는 컨테이너를 띄우는 최소 단위입니다(2부). 그런데 Pod 하나를 직접 만들면, 그 Pod가 있는 노드가 꺼질 때 아무도 다시 만들어 주지 않습니다. Pod 자체에는 "몇 개를 유지하라"는 뜻이 없기 때문입니다.

그래서 개수를 지키는 ReplicaSet을 둡니다. "이 라벨의 Pod가 3개여야 한다"는 조정 루프를 가진 오브젝트입니다. 다시 그 위에 Deployment를 둡니다. 새 버전 이미지로 바꿀 때 새 ReplicaSet을 만들어 Pod를 조금씩 갈아 끼우는 오브젝트입니다(3부).

정리하면 사람은 Deployment 하나만 적고, Deployment가 ReplicaSet을, ReplicaSet이 Pod를 만듭니다. 각 층이 자기 아래층의 원하는 상태를 적어 주는 셈입니다. 다음 슬라이드에서 kubectl apply 한 번이 이 층을 따라 내려가 노드 위의 컨테이너가 되기까지를 단계별로 봅니다.

apply 한 번이 Pod가 되기까지

  1. kubectl apply

    API Server가 인증, 인가, 어드미션, 검증을 거쳐 Deployment를 etcd에 저장합니다.

  2. Deployment 컨트롤러

    "이 Deployment의 ReplicaSet이 없다"를 보고 ReplicaSet을 만듭니다.

  3. ReplicaSet 컨트롤러

    "3개 필요, 0개 있음"을 보고 노드가 비어 있는 Pod 3개를 만듭니다.

  4. kube-scheduler

    노드 없는 Pod마다 자원이 맞는 노드를 골라 이름을 적습니다.

  5. kubelet

    자기 노드 이름이 적힌 Pod를 보고 런타임에 컨테이너 실행을 지시합니다.

누구도 다음 단계를 직접 호출하지 않습니다. 각 구성 요소가 API Server를 지켜보다가 자기 몫의 차이를 발견하면 움직이고, 결과를 다시 API Server에 적을 뿐입니다.

이 느슨한 연결 덕분에 노드가 꺼져 Pod가 2개로 줄면 3단계 루프가 혼자 다시 돌아 하나를 새로 만듭니다. 다음 부부터 이 흐름의 맨 끝, 실제로 실행되는 Pod부터 깊이 들어갑니다.

2부

Pod: 실제로 실행되는 가장 작은 단위

1부의 흐름은 kubelet이 Pod를 띄우는 데서 끝났습니다. 이 부에서는 그 Pod를 들여다봅니다. 왜 컨테이너가 아니라 Pod라는 묶음을 두는지, Pod가 어떤 순서로 시작하고 재시작하는지, 그리고 Pod가 끝나는 순간 요청이 왜 실패하는지를 차례로 봅니다.

기초 원리 여기부터는 오브젝트별 내부 동작과 설정의 의미를 다룹니다.

어떤 컨테이너는 늘 함께 있어야 한다

Kubernetes가 컨테이너 하나하나를 따로 배치한다고 상상해 봅시다. 주문 API 곁에는 API가 파일로 남기는 로그를 읽어 중앙 저장소로 보내는 로그 수집 컨테이너가 있다고 합시다. 둘은 같은 디렉터리를 봐야 하므로 같은 서버에 있어야 합니다.

그런데 스케줄러가 둘을 따로 보고 서로 다른 노드에 놓으면 로그 수집기는 읽을 파일이 없습니다. 둘 중 하나만 재시작되거나 하나만 다른 노드로 옮겨 가도 마찬가지입니다. 서로 localhost로 통신해야 하는 컨테이너 쌍(예: 앱과 그 앞의 프록시)도 같은 문제를 겪습니다.

그래서 Kubernetes는 배치의 단위를 컨테이너가 아니라 Pod로 정했습니다. Pod는 항상 같은 노드에 함께 놓이고, 함께 시작하고, 함께 사라지는 컨테이너 묶음입니다. 묶음 안의 컨테이너는 네트워크와 디스크 일부를 공유하므로, 같은 서버의 프로세스 여러 개처럼 협력할 수 있습니다.

대부분의 Pod에는 컨테이너가 하나뿐입니다. 그래도 단위를 Pod로 두면 "함께 있어야 하는 것"을 표현할 수 있는 자리가 생깁니다. 다음 슬라이드에서 이 공유가 9장의 리눅스 namespace로 어떻게 구현되는지 봅니다.

Pod는 네트워크와 볼륨을 함께 쓰는 묶음

Pod 안의 컨테이너들은 9장에서 본 network namespace 하나를 함께 씁니다. 그래서 IP가 하나이고, 서로 localhost로 통신하며, 같은 포트를 둘이 쓸 수는 없습니다. 파일 시스템과 프로세스는 컨테이너마다 따로입니다.

공유 namespace를 붙잡는 것은 pause 컨테이너입니다. 아무 일도 하지 않고 잠들어 있지만, 앱 컨테이너가 재시작되어도 Pod의 IP가 유지되는 이유가 이것입니다. 파일 공유는 emptyDir이라는 Pod 수명 동안만 있는 빈 디렉터리(5부)로 합니다.

한 Pod에는 주 컨테이너 하나와 도우미만

그렇다면 주문 API와 DB를 한 Pod에 넣으면 어떨까요? 함께 배치되니 편해 보이지만, Pod는 함께 확장됩니다. API를 30개로 늘리면 DB도 30개가 되고, API를 새 버전으로 바꾸면 DB도 함께 재시작됩니다. 수명과 확장 단위가 다른 것은 다른 Pod여야 합니다.

그래서 원칙은 주 컨테이너 하나, 그리고 그것만 돕는 컨테이너입니다. 주 컨테이너 곁에서 보조 역할을 하는 컨테이너를 오토바이 옆 좌석에 빗대 사이드카라고 부릅니다.

사이드카 예하는 일
로그 수집기공유 볼륨의 로그 파일을 전송
프록시들고 나는 통신 암호화, 재시도
설정 동기화외부 설정을 주기적으로 받아 파일로
DB, 다른 API사이드카가 아님, 따로 Pod로

init 컨테이너는 준비 작업을 먼저 끝낸다

spec:
  initContainers:
  - name: wait-db
    image: busybox:1.36
    command:
    - sh
    - -c
    - |
      until nc -z orders-db 5432
      do sleep 2; done
  containers:
  - name: api
    image: ghcr.io/acme/order-api:1.4.2

주문 API는 DB에 연결되지 않으면 기동하자마자 예외로 죽습니다. 이런 "앱이 뜨기 전에 끝나 있어야 할 일"을 앱 코드 밖으로 빼는 자리가 init 컨테이너입니다. 적힌 순서대로 하나씩 실행되고, 각자 성공으로 끝나야 다음이, 모두 끝나야 주 컨테이너가 시작됩니다.

예시는 작은 도구 모음 이미지(busybox)로 nc -z(포트에 연결만 해 보기)를 2초마다 반복해 DB 5432번 포트가 열릴 때까지 기다립니다. 실패해 끝나면 init을 처음부터 다시 시도합니다.

보통 컨테이너로 둔 사이드카는 순서가 없다

init 컨테이너는 끝나야 하므로 계속 도는 사이드카에는 쓸 수 없습니다. 그래서 오랫동안 사이드카는 주 컨테이너와 나란히 containers 목록에 두었는데, 이 목록의 컨테이너들은 시작과 종료 순서가 정해져 있지 않아 세 가지 문제가 생겼습니다. 표의 Job은 끝나는 일을 실행하는 오브젝트로 3부에서 봅니다.

상황일반 컨테이너로 둔 사이드카네이티브 사이드카
시작 순서앱과 동시에 시작, 프록시보다 앱이 먼저 통신할 수 있음앱보다 먼저 시작이 보장됨
Job 완료사이드카가 안 끝나 Job도 안 끝남주 컨테이너가 끝나면 Job 완료
종료 순서앱과 동시에 종료 신호, 순서 없음앱이 끝난 뒤 정의 역순으로 종료

오른쪽 열의 네이티브 사이드카는 이 세 문제를 풀려고 생긴 방식입니다. 다음 슬라이드에서 만드는 법을 봅니다.

네이티브 사이드카는 먼저 뜨고 늦게 죽는다

spec:
  initContainers:
  - name: wait-db
    image: busybox:1.36
    command: [sh, -c, "until nc -z …"]
  - name: log-agent
    restartPolicy: Always    # 사이드카 표시
    image: fluent/fluent-bit:3.1
  containers:
  - name: api
    image: ghcr.io/acme/order-api:1.4.2

방법은 init 컨테이너 목록에 사이드카를 두되 restartPolicy: Always를 붙이는 것입니다. 그러면 init 순서대로 시작되지만 끝나기를 기다리지 않고, 시작되자마자 다음으로 넘어가 주 컨테이너와 함께 끝까지 살아 있습니다. 죽으면 다시 띄웁니다.

이 네이티브 사이드카는 1.33에서 정식(GA) 기능이 되었습니다. Kubernetes 기능은 알파(기본 꺼짐), 베타, GA(안정) 순으로 성숙하므로, 운영에는 GA 기능을 쓰는 것이 원칙입니다.

Pod는 다섯 단계를 거치고, 옮겨 가지 않는다

Pod 단계의미
Pending노드 배정 전이거나 이미지 받는 중
Running노드에 놓였고 컨테이너 하나 이상 실행 중
Succeeded모든 컨테이너가 성공 종료, 재시작 안 함
Failed모두 끝났고 하나 이상이 실패
Unknown노드와 통신이 끊겨 알 수 없음

Pod의 status.phase는 Pod가 일생에서 어디쯤 있는지를 다섯 단계로 요약합니다. 1부의 흐름에 대면 스케줄러와 이미지 다운로드를 기다리는 동안이 Pending, kubelet이 컨테이너를 띄운 뒤가 Running입니다.

중요한 성질이 하나 있습니다. Pod는 한 번 노드에 놓이면 다른 노드로 옮겨 가지 않습니다. 노드가 죽으면 그 Pod도 끝이고, 컨트롤러가 이름과 IP가 다른 새 Pod를 만듭니다. Pod는 일회용입니다.

컨테이너는 같은 자리에서 간격을 늘리며 재시작한다

$ kubectl get pod order-api-7d9f5-x2k4q
NAME                   READY  STATUS
order-api-7d9f5-x2k4q  0/1    CrashLoopBackOff
  RESTARTS  6 (2m ago)

$ kubectl describe pod order-api-7d9f5-x2k4q
State:       Waiting
  Reason:    CrashLoopBackOff
Last State:  Terminated
  Reason:    Error
  Exit Code: 1

Pod 단계와 별개로 컨테이너마다 Waiting, Running, Terminated 상태와 그 이유가 있습니다. 컨테이너가 죽으면 kubelet은 Pod의 restartPolicy(Always, OnFailure, Never)에 따라 같은 노드, 같은 Pod 안에서 다시 띄웁니다.

계속 죽으면 8장의 지수 백오프처럼 10초, 20초, 40초로 간격을 늘려 최대 5분까지 기다립니다. 그 기다리는 상태가 CrashLoopBackOff입니다. 즉 단계가 아니라 Waiting의 이유이고, 진짜 원인은 Last State에 있습니다.

Pod 종료는 두 갈래로 동시에 진행된다

kubelet앱 컨테이너
삭제 요청, 엔드포인트 제거도 동시 시작
Terminating preStop 훅 실행있다면 먼저, 끝날 때까지
SIGTERM 종료 시작
새 요청 거절, 진행 중 요청 마무리
exit 0 정상 종료
유예 시간 초과 SIGKILL진행 중 요청 유실, 종료 코드 137

Pod는 새 버전 배포, 개수 축소, 노드 비우기 때마다 지워집니다. 삭제 요청이 오면 두 일이 따로 시작됩니다. 하나는 kubelet의 컨테이너 종료이고, 다른 하나는 이 Pod를 엔드포인트, 즉 트래픽을 받을 Pod 주소 목록(4부)에서 빼는 일입니다.

kubelet은 preStop 훅이 있으면 먼저 실행하고, 9장의 SIGTERM을 보냅니다. terminationGracePeriodSeconds(기본 30초)가 지나도 살아 있으면 SIGKILL로 끝냅니다.

엔드포인트가 빠지기 전에 앱이 죽으면 502

종료 예산은 preStop과 앱 종료를 합친 값

spec:
  terminationGracePeriodSeconds: 45
  containers:
  - name: api
    image: ghcr.io/acme/order-api:1.4.2
    lifecycle:
      preStop:
        sleep: { seconds: 10 }
    # 앱은 SIGTERM 후 최대 25초 안에
    # 진행 중 요청을 끝내도록 설정 (11장)

해결은 앱이 종료를 시작하기 전에 소식이 다 퍼질 시간을 버는 것입니다. preStop에서 10초를 기다리면 그동안 앱은 정상적으로 요청을 받고, 10초 뒤 SIGTERM을 받을 때는 새 요청이 거의 오지 않습니다.

유예 시간은 preStop 시작부터 세므로 preStop + 앱 종료 시간 < 유예 시간이어야 합니다. 위 예는 10초 + 25초에 여유를 두어 45초입니다. sleep 액션은 kubelet이 직접 기다리므로 sleep 명령이 없는 이미지에서도 됩니다.

종료가 깨지는 흔한 이유

preStop을 넣어도 종료가 깔끔하지 않다면 대개 다음 넷 중 하나입니다.

  • SIGTERM이 앱에 닿지 않음: 9장에서 본 셸 형식 ENTRYPOINT라 PID 1이 셸이면 신호가 앱까지 전달되지 않습니다. 결국 유예 시간 뒤 SIGKILL(종료 코드 137)로 끝나 진행 중 요청이 끊깁니다.
  • preStop이 유예 시간을 다 씀: preStop이 유예 시간 안에 끝나지 않으면 kubelet은 2초를 한 번만 더 준 뒤 강제 종료하므로, 앱은 정리할 기회를 잃습니다.
  • 오래 걸리는 메시지 처리: 큐에서 꺼낸 메시지를 처리하는 중에 강제 종료되면 그 메시지는 다시 처리됩니다. 8장의 멱등 처리가 전제여야 하는 이유입니다.
  • 강제 삭제: --force --grace-period=0은 API에서 기록만 지우고 노드의 실제 종료를 기다리지 않습니다. DB처럼 Pod마다 고정 이름을 쓰는 3부의 StatefulSet에서는 같은 이름의 Pod가 잠시 둘이 될 수 있어 위험합니다.

3부

일회용 Pod를 누가 대신 돌보나

2부에서 Pod는 노드가 죽으면 함께 사라지고 옮겨 가지 않는다는 것을 봤습니다. 그래서 Pod는 직접 만들지 않고, Pod를 대신 만들고 지우는 컨트롤러에 맡깁니다. 무상태 API, DB처럼 정체성이 필요한 서버, 노드마다 하나씩 도는 에이전트, 끝나는 배치는 돌보는 방식이 달라 컨트롤러도 다릅니다.

ReplicaSet은 개수를 지킨다

apiVersion: apps/v1
kind: ReplicaSet
metadata: { name: order-api-7d9f5 }
spec:
  replicas: 3
  selector: { matchLabels: { app: order-api } }
  template:                  # 찍어 낼 Pod 틀
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: api
        image: ghcr.io/acme/order-api:1.4.2

가장 단순한 돌봄은 개수 유지입니다. ReplicaSet은 셀렉터에 맞는 Pod를 세어 replicas보다 적으면 template(Pod를 찍어 내는 틀)으로 새로 만들고, 많으면 지웁니다. 노드가 죽어 2개가 되면 1개를 만들고, 누가 같은 라벨의 Pod를 손으로 띄워 4개가 되면 1개를 지웁니다.

한계는 버전을 모른다는 것입니다. 틀의 이미지를 1.5.0으로 바꿔도 이미 있는 Pod는 개수가 맞으니 그대로 둡니다.

Deployment는 ReplicaSet을 바꿔 끼운다

Deployment는 Pod 틀이 바뀔 때마다 새 ReplicaSet을 만들고, 새것은 늘리고 옛것은 줄여 버전을 바꿉니다. 이 한 번의 틀을 리비전이라 합니다. 옛 ReplicaSet은 0개로 남겨 두어 언제든 되돌릴 수 있습니다.

ReplicaSet과 Pod 이름 가운데의 7d9f5는 틀의 해시로, pod-template-hash 라벨로도 붙어 두 리비전의 Pod가 섞이지 않게 합니다. 그래서 ReplicaSet은 직접 쓰지 않고 늘 Deployment를 통해 씁니다.

Deployment YAML은 원하는 상태의 기록이다

kind: Deployment
metadata: { name: order-api, namespace: prod }
spec:
  replicas: 3
  selector: { matchLabels: { app: order-api } }
  strategy:
    rollingUpdate:          # 기본 전략
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: api
        image: ghcr.io/acme/order-api:1.4.2
        resources:
          requests: { cpu: 500m, memory: 1Gi }

앞 슬라이드의 ReplicaSet 내용에 strategy만 더한 모양입니다. selector와 template 라벨이 맞아야 Deployment가 자기 Pod를 알아보며, 셀렉터는 만든 뒤 바꿀 수 없습니다.

template 안이 바뀔 때만 새 리비전이 생기고, replicas만 바꾸면 기존 ReplicaSet의 개수만 조정됩니다. strategy는 다음 슬라이드에서, requests(Pod가 쓸 자원 예약량)는 6부에서 봅니다.

롤링 업데이트는 두 숫자 사이를 걷는다

  1. 시작: 1.4.2 4개

    replicas 4, maxSurge 25%(올림 1), maxUnavailable 25%(내림 1).

  2. 1.5.0 1개 추가, 1.4.2 1개 제거

    총 5개까지 허용, 준비된 Pod 3개 이상 유지.

  3. 1.5.0이 준비되면

    그만큼 1.4.2를 더 줄이고 1.5.0을 더 늘립니다.

  4. 1.5.0이 준비되지 않으면

    진행이 멈춥니다. 1.4.2 3개가 계속 트래픽을 받습니다.

  5. 완료: 1.5.0 4개

    1.4.2의 ReplicaSet은 0개로 남습니다.

기본 전략 RollingUpdate는 Pod를 조금씩 갈아 끼웁니다. 속도는 두 숫자로 정합니다. maxSurge는 원하는 개수보다 더 띄울 수 있는 수, maxUnavailable은 동시에 빠져도 되는 수이며, 기본값은 둘 다 25%입니다.

"준비됐다"의 기준은 readiness probe, 즉 트래픽을 받을 준비가 됐는지 묻는 검사입니다(7부). 이 검사가 없으면 뜨기만 해도 준비된 것으로 보고 넘어갑니다. 용량을 한 순간도 줄이면 안 되면 앞 슬라이드처럼 maxUnavailable: 0, maxSurge: 1로 둡니다.

rollout 명령으로 지켜보고 되돌린다

$ kubectl set image deploy/order-api \
    api=ghcr.io/acme/order-api:1.5.0
$ kubectl rollout status deploy/order-api
Waiting for rollout: 2 of 4 updated replicas…
$ kubectl rollout history deploy/order-api
REVISION  CHANGE-CAUSE
3         1.4.2 배포
4         1.5.0 배포
$ kubectl rollout undo deploy/order-api \
    --to-revision=3

set image는 틀의 이미지를 바꿔 새 리비전을 일으킵니다(실무에서는 YAML을 고쳐 apply). status는 끝날 때까지 진행을 보여 주고, history의 CHANGE-CAUSE는 1부의 change-cause 어노테이션입니다. undo는 옛 ReplicaSet을 다시 늘리는 롤링 업데이트라 빠릅니다.

progressDeadlineSeconds(기본 600초) 동안 진척이 없으면 실패로 기록될 뿐 자동 롤백은 없습니다. 배포 파이프라인이 실패를 보고 되돌립니다(11장).

DB는 "아무 Pod나 같다"가 성립하지 않는다

Deployment의 Pod는 서로 똑같아서, 어느 것이 죽어도 아무 이름의 새 Pod로 바꾸면 됩니다. 주문 데이터를 담는 PostgreSQL(orders-db)은 다릅니다. 각 서버가 자기 디스크에 자기 데이터를 갖고, 복제본은 "0번이 주 서버"처럼 서로를 이름으로 찾습니다.

Deployment로 띄우면 재생성된 Pod가 새 이름과 빈 디스크로 돌아와 자기 데이터를 잃고, 셋이 동시에 떠서 누가 주 서버인지 다툽니다. StatefulSet은 이 세 가지, 즉 고정 이름, 전용 디스크, 순서를 지켜 주는 컨트롤러입니다.

항목DeploymentStatefulSet
Pod 이름무작위 해시orders-db-0, -1, -2 고정
디스크모두 공유하거나 없음Pod마다 전용
생성 순서동시0, 1, 2 순서
DNS 이름묶음 이름 하나Pod마다 고정 이름

StatefulSet은 이름과 디스크를 짝지어 기억한다

kind: StatefulSet
metadata: { name: orders-db }
spec:
  serviceName: orders-db   # Headless Service
  replicas: 3
  selector: { matchLabels: { app: orders-db } }
  template: …
  volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: [ReadWriteOnce]
      resources: { requests: { storage: 50Gi } }
# PVC: data-orders-db-0, data-orders-db-1 …
# DNS: orders-db-0.orders-db.prod.svc…

volumeClaimTemplates는 Pod마다 PVC(디스크 요청서, 5부)를 하나씩 찍어 냅니다. orders-db-1이 어느 노드에서 다시 태어나든 같은 이름의 data-orders-db-1 디스크에 다시 붙습니다.

serviceName은 Headless Service를 가리킵니다. 여러 Pod 앞에 주소 하나를 두는 대신 Pod마다 고정 DNS 이름을 주는 Service로(4부), 복제본이 서로를 orders-db-0.orders-db로 찾게 합니다.

StatefulSet은 순서대로 만들고 하나씩 바꾼다

StatefulSet은 기본으로 0번부터 하나씩 만들고, 앞 번호가 준비되어야 다음 번호를 만듭니다. 지울 때는 큰 번호부터 역순입니다. DB 클러스터는 보통 0번이 먼저 떠서 주 서버가 되고 뒤 번호가 그것에 붙어 복제를 시작하므로, 이 순서가 초기화를 단순하게 해 줍니다. 순서가 필요 없다면 podManagementPolicy: Parallel로 동시에 만들 수 있습니다.

새 버전으로 바꿀 때도 큰 번호부터 하나씩, 앞의 것이 준비된 뒤 다음으로 갑니다. partition: 2처럼 값을 주면 2번 이상만 먼저 바꾸고 0, 1번은 그대로 두므로, 복제본 하나에서 새 버전을 시험해 볼 수 있습니다.

디스크는 오래 삽니다. StatefulSet을 지우거나 개수를 줄여도 PVC는 기본으로 남아, 실수로 지워도 데이터가 살아 있습니다. 대신 쓰지 않는 디스크 비용이 계속 나가므로 정리는 사람이 해야 합니다.

마지막으로 StatefulSet이 해 주지 않는 것을 알아야 합니다. 이름과 디스크와 순서만 지킬 뿐, 데이터 복제 설정, 주 서버 장애 시 승격, 백업은 하지 않습니다. 그 운영 지식은 Operator라는 DB 전용 컨트롤러(8부)가 코드로 대신하거나, 클라우드의 관리형 DB(15장)에 맡깁니다. 실무에서 주문 DB를 클러스터 안에 직접 두는 경우가 드문 이유입니다.

DaemonSet은 노드마다 정확히 하나씩

kind: DaemonSet
metadata: { name: log-agent }
spec:
  selector: { matchLabels: { app: log-agent } }
  updateStrategy:
    rollingUpdate: { maxUnavailable: 1 }
  template:
    spec:
      tolerations:
      - operator: Exists   # 모든 taint 허용
      containers:
      - name: agent
        image: fluent/fluent-bit:3.1
        resources:
          requests: { cpu: 50m, memory: 64Mi }

노드마다 하나씩 있어야 하는 일도 있습니다. 노드의 모든 컨테이너 로그를 모아 보내는 수집기, 노드의 CPU·디스크 지표를 내보내는 수집기, 1부의 kube-proxy가 그렇습니다. DaemonSet은 노드가 생기면 그 노드에 Pod를 하나 띄우고, 노드가 빠지면 함께 지웁니다.

모든 노드에 떠야 하므로 taint(일반 Pod를 거부하는 노드 표시)를 견디는 toleration을 넓게 줍니다(6부). 노드마다 자원을 먹으니 requests를 꼭 적습니다.

Job은 끝나는 일을 성공할 때까지 시킨다

kind: Job
metadata: { name: settle-2026-11-17 }
spec:
  completions: 10      # 성공 10번이면 완료
  parallelism: 3       # 동시에 3개
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: settle
        image: ghcr.io/acme/settle:2.0.1
        args: ["--date=2026-11-17"]

지금까지의 컨트롤러는 Pod가 끝나면 다시 띄웠습니다. 매일 밤 판매 대금을 정산하는 배치는 반대로 끝나야 성공입니다. Job은 Pod가 성공으로 끝날 때까지 다시 만들고, 성공 횟수가 completions에 닿으면 완료로 표시합니다.

예시는 정산을 10조각으로 나눠 3개씩 동시에 돌립니다. 성공한 Pod는 다시 띄우지 않으므로 Pod의 restartPolicy는 Never나 OnFailure만 허용됩니다.

Job의 재시도는 횟수와 시간으로 묶는다

spec:
  backoffLimit: 4                # 기본 6
  activeDeadlineSeconds: 3600    # 1시간
  ttlSecondsAfterFinished: 86400 # 하루 뒤 삭제
  template:
    spec:
      restartPolicy: Never

계속 실패하는 Job을 영원히 재시도하면 자원만 먹습니다. 실패한 Pod 수가 backoffLimit을 넘거나, 시작부터 activeDeadlineSeconds가 지나면 Job을 실패로 표시하고 남은 Pod를 정리합니다. 재시도 간격은 2부의 재시작처럼 점점 늘어납니다.

끝난 Job은 기록을 보도록 남아 있다가 ttlSecondsAfterFinished 뒤 자동으로 지워집니다. 재시도 때문에 같은 조각이 두 번 실행될 수 있으므로 정산 작업은 8장의 멱등성을 지켜야 합니다.

CronJob은 정해진 시각마다 Job을 만든다

kind: CronJob
metadata: { name: nightly-settle }
spec:
  schedule: "0 3 * * *"       # 매일 03:00
  timeZone: "Asia/Seoul"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 600
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec: { backoffLimit: 2, template: … }
concurrencyPolicy이전 실행이 안 끝났으면
Allow (기본)겹쳐서 또 실행
Forbid이번 실행을 건너뜀
Replace이전 것을 지우고 새로 실행
 CronJob은 9장 cron의 다섯 칸 표기로 시각마다 Job을 찍어 냅니다. timeZone이 없으면 Control Plane의 시간대(대개 UTC)라 한국 시각과 9시간 어긋납니다. 정산처럼 겹치면 안 되는 일은 Forbid로 두고, 놓친 실행은 startingDeadlineSeconds 안에서만 따라잡습니다.

워크로드는 Pod의 수명과 정체성으로 고른다

이 부에서 본 다섯 컨트롤러를 우리 쇼핑몰 예제에 대어 정리하면 다음과 같습니다. 고르는 기준은 두 질문입니다. Pod가 끝나는 일인가, 그리고 Pod마다 정체성이 필요한가.

어떤 컨트롤러가 만들었든 Pod는 생길 때마다 새 IP를 받습니다. 그렇다면 웹 서버는 계속 바뀌는 주문 API Pod들을 어떻게 찾아갈까요? 다음 부의 질문입니다.

4부

바뀌는 Pod 앞에 고정된 길을 낸다

3부의 컨트롤러들은 Pod를 수시로 지우고 새로 만들며, 새 Pod는 매번 새 IP를 받습니다. 이 부에서는 Pod끼리 어떻게 패킷을 주고받는지에서 시작해, 바뀌는 IP 앞에 고정 주소와 이름을 두는 방법, 클러스터 밖의 사용자를 들이는 방법, 그리고 통신을 막는 방법까지 차례로 봅니다.

모든 Pod는 NAT 없이 서로 닿는 IP를 받는다

9장에서 Docker 컨테이너를 밖에 열 때는 -p 8080:8080처럼 호스트 포트를 컨테이너 포트에 이어 주었습니다. 컨테이너가 호스트 안쪽의 사설 IP를 갖고, 밖으로 나갈 때와 들어올 때 주소를 바꿔(NAT, 2장) 주었기 때문입니다. 서버 한 대라면 괜찮지만, 노드 20대에 Pod 수백 개라면 포트 번호를 겹치지 않게 나눠 주는 일 자체가 큰 짐이 됩니다.

Kubernetes는 이 문제를 처음부터 피하려고 네트워크 모델에 세 가지를 약속했습니다. 첫째, 모든 Pod는 클러스터 안에서 고유한 IP를 갖는다. 둘째, 어느 노드에 있든 Pod끼리는 NAT 없이 그 IP로 직접 통신한다. 셋째, 노드의 에이전트(kubelet 등)도 그 노드의 Pod에 직접 닿는다.

NAT가 없다는 것은 받는 쪽이 보는 출발지 주소가 보낸 Pod의 실제 IP라는 뜻입니다. 그래서 주문 API의 로그에 찍힌 IP로 호출한 Pod를 찾을 수 있고, 모든 Pod가 같은 8080 포트를 써도 IP가 다르니 충돌하지 않습니다. 서버 여러 대가 마치 하나의 평평한 네트워크에 붙어 있는 것처럼 보이는 셈입니다.

이 약속은 규격일 뿐이고, Kubernetes 자신은 구현하지 않습니다. 실제로 IP를 나눠 주고 노드 사이에 길을 까는 일은 다음 슬라이드의 플러그인이 맡습니다.

CNI 플러그인이 그 약속을 실제로 깐다

kubelet은 Pod를 만들 때 CNI라는 규격으로 네트워크 플러그인을 부릅니다. 플러그인은 9장의 veth 쌍으로 Pod의 namespace와 노드를 잇고, IP를 할당하고, 다른 노드의 Pod로 가는 경로를 깝니다.

노드 사이를 건너는 방법은 둘입니다. 오버레이는 Pod 간 패킷을 노드 간 패킷 안에 통째로 싸서 보내는 방식(대표적으로 VXLAN)이고, 직접 라우팅은 노드 네트워크가 Pod IP 대역을 알게 해 그대로 보내는 방식입니다.

Pod IP를 직접 부르면 세 가지가 곤란하다

이제 웹 서버(web) Pod가 주문 API를 호출한다고 합시다. CNI 덕분에 주문 API Pod 3개의 IP로 바로 갈 수는 있습니다. 하지만 그 IP를 웹 서버 설정에 적어 두는 순간 문제가 시작됩니다.

첫째, IP가 바뀝니다. 3부에서 봤듯 배포할 때마다, 노드가 죽을 때마다 Pod는 새 IP로 다시 태어납니다. 적어 둔 주소는 몇 시간 만에 낡습니다.

둘째, 고르는 일이 남습니다. 대상이 3개, 행사 때는 30개인데 매 요청을 어느 Pod로 보낼지 호출하는 쪽이 정해야 합니다. 8장의 로드 밸런서가 하던 일을 모든 클라이언트가 직접 해야 하는 셈입니다.

셋째, 준비되지 않은 Pod를 피해야 합니다. 막 떠서 아직 기동 중인 Pod, 2부에서 본 종료 중인 Pod로는 요청을 보내면 안 됩니다. 이 상태 역시 계속 바뀝니다.

세 문제의 공통점은 "대상 목록이 계속 바뀐다"는 것입니다. 그래서 목록을 따라가는 일을 클러스터가 맡고, 클라이언트에게는 변하지 않는 주소 하나만 주면 됩니다. 그것이 다음 슬라이드의 Service입니다.

Service는 Pod 묶음에 고정 주소를 준다

apiVersion: v1
kind: Service
metadata: { name: order-api, namespace: prod }
spec:
  type: ClusterIP              # 기본값
  selector: { app: order-api } # 이 라벨의 Pod
  ports:
  - port: 80                   # 받는 포트
    targetPort: 8080           # Pod의 포트

$ kubectl get svc order-api -n prod
NAME       TYPE       CLUSTER-IP    PORT(S)
order-api  ClusterIP  10.96.142.18  80/TCP

Service는 셀렉터에 맞는 Pod들 앞에 변하지 않는 가상 IP(ClusterIP)와 이름을 둡니다. 웹 서버는 order-api:80만 알면 되고, 뒤의 Pod가 몇 번 바뀌어도 주소는 같습니다.

2장과 8장의 L4 로드 밸런서를 클러스터 안에 둔 것과 같습니다. TCP 연결 단위로 대상 Pod 하나를 고르며, 준비(Ready) 상태인 Pod만 대상이 됩니다. port는 Service가 받는 번호, targetPort는 Pod에서 앱이 듣는 번호입니다.

Service 타입은 어디서 닿게 할지를 정한다

앞의 ClusterIP는 클러스터 안에서만 닿는 주소입니다. 웹 서버가 주문 API를 부르는 것처럼 서비스끼리 호출할 때는 이것으로 충분합니다. 하지만 클러스터 밖의 사용자를 들이려면 바깥에서 닿는 입구가 필요하고, 그 정도에 따라 타입이 나뉩니다.

NodePort는 모든 노드의 같은 포트(30000~32767 중 하나)를 열어, 어느 노드의 IP로 들어와도 Service로 보내 줍니다. 노드 IP를 직접 외부에 알리기는 불편해서 주로 외부 로드 밸런서의 대상으로 씁니다.

LoadBalancer는 한 단계 더 나아가 1부의 cloud-controller-manager가 클라우드에 진짜 로드 밸런서를 만들고 그 대상을 NodePort로 연결합니다. 그래서 세 타입은 겹쳐 쌓입니다. LoadBalancer는 NodePort를 포함하고, NodePort는 ClusterIP를 포함합니다.

나머지 둘은 성격이 다릅니다. ExternalName은 Pod를 고르지 않고, 이름을 조회하면 클러스터 밖의 다른 이름(예: 관리형 DB 주소)을 돌려주는 별칭입니다. Headless는 clusterIP: None으로 가상 IP를 만들지 않고, 이름을 조회하면 Pod IP 목록을 그대로 돌려줍니다. 3부의 orders-db처럼 클라이언트가 특정 Pod를 골라야 할 때 씁니다.

다섯 타입을 한 표로 보면

타입어디서 닿나동작예제에서
ClusterIP클러스터 안가상 IP로 Pod에 분산web → order-api

실무에서 대부분의 Service는 ClusterIP입니다. 외부 입구는 LoadBalancer를 서비스마다 하나씩 만들기보다, 뒤에서 볼 HTTP 입구 규칙(Ingress, Gateway) 하나로 모읍니다. 그 전에 가장 흔한 ClusterIP가 실제로 어떻게 동작하는지부터 봅니다.

ClusterIP는 어디에도 없는 IP다

ClusterIP를 가진 네트워크 인터페이스는 어느 노드에도 없습니다. 각 노드의 kube-proxy가 "이 IP:포트로 가는 패킷은 이 Pod들 중 하나로 목적지를 바꿔라"라는 규칙을 커널에 깔아 둘 뿐입니다. 9장에서 본 iptables의 DNAT(목적지 주소 바꾸기)입니다.

그래서 패킷은 보내는 Pod의 노드에서 바로 실제 Pod IP로 바뀌어 나가고, 응답은 9장의 conntrack이 기억해 둔 연결 정보로 되돌려집니다. ClusterIP에 ping이 안 되는 것도 규칙이 TCP/UDP 포트에만 걸려 있기 때문입니다.

kube-proxy의 규칙 방식은 세 가지다

kube-proxy가 커널에 규칙을 까는 방식을 모드라고 합니다. iptables 모드는 Service마다 규칙 체인을 만들고 확률로 Pod를 고릅니다. IPVS 모드는 커널의 L4 로드 밸런서 기능에 해시 테이블로 대상을 등록합니다. nftables 모드는 9장에서 본 iptables의 후속 API로 규칙을 갱신합니다.

모드규칙 구조현재 상태 (1.37 기준)
iptablesService마다 규칙 체인, 확률로 분산기본값

iptables 모드는 Service가 수천 개로 늘면 규칙 갱신이 느려졌고, IPVS가 그 대안이었습니다. 하지만 IPVS는 Service 기능의 일부 경계 사례를 끝내 맞추지 못해 폐기 예정이 되었고 nftables가 권장됩니다. 한편 Cilium처럼 eBPF(커널 안에서 안전하게 실행되는 작은 프로그램)로 kube-proxy 자체를 대체하는 CNI도 많이 씁니다.

kube-proxy는 "지금 대상이 누구인가"를 어디서 알까요? EndpointSlice 컨트롤러가 Service 셀렉터에 맞는 Pod를 지켜보며 IP와 상태를 EndpointSlice 오브젝트에 적고, kube-proxy와 뒤에서 볼 HTTP 입구 프록시(Ingress 컨트롤러)는 이것을 읽어 규칙을 만듭니다. 2부에서 "엔드포인트"라 부른 목록이 이것입니다.

아래쪽은 2부의 종료 중인 Pod입니다. ready: false라 새 연결은 받지 않습니다. 한 조각에 100개까지 담아 바뀐 조각만 퍼뜨립니다. ENDPOINTS가 비어 있으면 Service 문제의 절반은 여기서 풀립니다.

Service 이름은 CoreDNS가 IP로 바꿔 준다

nameserver 10.96.0.10      # CoreDNS
search prod.svc.cluster.local
       svc.cluster.local cluster.local
options ndots:5

# 전체 이름 (FQDN)
order-api.prod.svc.cluster.local
# 같은 네임스페이스라면 이것만으로
order-api

웹 서버가 order-api라는 이름만 써도 되는 이유는 DNS 덕분입니다. 클러스터 안에는 CoreDNS라는 DNS 서버가 Pod로 돌며, Service마다 이름.네임스페이스.svc.cluster.local 레코드를 ClusterIP로 답합니다.

kubelet은 Pod마다 /etc/resolv.conf를 만들어 줍니다. nameserver는 물어볼 DNS 서버, search는 짧은 이름 뒤에 차례로 붙여 볼 꼬리입니다. 그래서 order-api는 첫 꼬리를 붙인 전체 이름으로 바로 풀립니다(2장 DNS).

ndots:5는 외부 이름 조회를 몇 배로 늘린다

# 점 2개 < ndots 5 → search 먼저
pay.example.com.prod.svc.cluster.local  # 없음
pay.example.com.svc.cluster.local       # 없음
pay.example.com.cluster.local           # 없음
pay.example.com                         # 성공

# 끝에 점을 붙이면 바로 조회
pay.example.com.

앞 슬라이드의 ndots:5는 "점이 5개 미만인 이름은 search 꼬리부터 붙여 보라"는 뜻입니다. 짧은 Service 이름에는 편리하지만, 주문 API가 외부 결제사 pay.example.com을 부를 때는 없는 이름 셋을 먼저 물은 뒤에야 성공합니다. IPv4(A)와 IPv6(AAAA)를 따로 물으면 질의가 8번입니다.

줄이는 법은 셋입니다. 이름 끝에 점을 붙여 완전한 이름임을 밝히거나, Pod의 dnsConfig로 ndots를 낮추거나, 노드마다 DNS 캐시를 두는 NodeLocal DNSCache를 씁니다.

밖의 사용자는 Ingress 규칙으로 들인다

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop, namespace: prod }
spec:
  ingressClassName: public  # 맡을 컨트롤러
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls    # 인증서 (5부)
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api/orders
        pathType: Prefix
        backend:
          service:
            name: order-api
            port: { number: 80 }

이제 사용자가 shop.example.com으로 들어옵니다. LoadBalancer Service로 열면 서비스마다 클라우드 로드 밸런서가 하나씩 생겨 비싸고, URL 경로로 나누거나 HTTPS를 끝내는 L7 기능(2장)도 없습니다.

Ingress는 입구 하나로 들어온 HTTP 요청을 호스트와 경로에 따라 여러 Service로 나누는 규칙입니다. 예시는 /api/orders로 시작하는 요청을 주문 API로 보내고, tls로 HTTPS를 처리합니다. /를 웹 서버로 보내는 규칙도 같은 모양으로 이어 적습니다.

Ingress는 규칙이고, 실행은 컨트롤러가 한다

  1. 사용자shop.example.com
  2. 클라우드 LB입구 하나
  3. Ingress 컨트롤러규칙대로 경로 분기
  4. Serviceorder-api, web
  5. Pod준비된 것만

앞의 Ingress 오브젝트는 etcd에 저장된 규칙일 뿐, 그 자체로는 패킷 하나도 나르지 않습니다. 규칙을 읽어 실제 리버스 프록시(NGINX, Envoy 등)를 구성하는 Ingress 컨트롤러를 따로 설치해야 동작합니다. 이 역시 1부의 조정 루프로, Ingress가 바뀌면 프록시 설정을 다시 맞춥니다.

ingressClassName은 클러스터에 컨트롤러가 여럿일 때 어느 것이 이 규칙을 맡을지 고르는 칸입니다. 컨트롤러는 대개 앞의 EndpointSlice를 읽어 Service를 거치지 않고 Pod IP로 바로 보냅니다. AWS에서는 AWS Load Balancer Controller가 Ingress를 보고 AWS의 L7 로드 밸런서(ALB)를 직접 만듭니다(13장, 14장).

Ingress는 동결됐고, 다음은 Gateway API

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: order-api, namespace: prod }
spec:
  parentRefs: [{ name: public-gw }]
  hostnames: [shop.example.com]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api/orders
    backendRefs:
    - { name: api-v1, port: 80, weight: 90 }
    - { name: api-v2, port: 80, weight: 10 }

Ingress는 규격이 작아서 가중치 분할이나 헤더 조건 같은 기능을 컨트롤러마다 다른 어노테이션으로 덧붙여 왔습니다. 그래서 Ingress API는 기능 추가가 멈췄고, 후속인 Gateway API가 권장됩니다. 가장 널리 쓰이던 Ingress NGINX 컨트롤러도 2026년 3월 은퇴해 보안 패치가 끊겼습니다.

Gateway API는 역할을 나눕니다. 인프라 담당이 GatewayClass를, 운영자가 Gateway(입구, 인증서)를, 개발자가 HTTPRoute를 씁니다. 예시는 주문 API의 두 버전 Service 중 새 버전(api-v2)에 10%만 보냅니다.

NetworkPolicy가 없으면 모든 Pod가 열려 있다

# 1) prod의 모든 Pod: 들어오는 트래픽 차단
kind: NetworkPolicy
metadata: { name: deny-all, namespace: prod }
spec:
  podSelector: {}           # 전부 고름
  policyTypes: [Ingress]
---
# 2) order-api: web에서 오는 8080만 허용
kind: NetworkPolicy
metadata: { name: allow-web, namespace: prod }
spec:
  podSelector:
    matchLabels: { app: order-api }
  ingress:
  - from:
    - podSelector:
        matchLabels: { app: web }
    ports: [{ port: 8080 }]

네트워크 모델은 "모든 Pod가 서로 닿는다"였습니다. 편하지만, 웹 서버 하나가 뚫리면 공격자가 orders-db까지 바로 접속할 수 있다는 뜻이기도 합니다. NetworkPolicy는 Pod 사이의 방화벽 규칙입니다.

규칙은 이렇습니다. 어떤 Pod를 고르는 정책이 하나라도 생기면 그 Pod는 그 방향으로 격리되고, 정책들이 허용한 것의 합집합만 통과합니다. 실제 차단은 CNI가 하므로 지원하지 않는 CNI에서는 아무것도 막지 않습니다. 나가는 쪽(Egress)을 막을 때는 DNS(53번) 허용을 잊기 쉽습니다.

서비스 메시는 프록시로 통신을 가로챈다

서비스가 수십 개로 늘면 서비스 사이 통신마다 암호화, 재시도, 타임아웃, 호출 지표를 각자 코드로 넣기 어려워집니다. 서비스 메시는 모든 Pod 곁에 Envoy 같은 프록시를 2부의 사이드카로 두고, 들고 나는 통신을 전부 그 프록시로 지나가게 합니다.

그러면 앱 코드를 바꾸지 않고 양쪽이 서로 인증서를 확인하는 mTLS 암호화, 재시도와 타임아웃, 가중치 분할, 호출 단위 지표를 얻습니다. 대표가 Istio와 Linkerd이며, Istio는 노드 단위 프록시를 쓰는 ambient 모드도 제공합니다.

메시는 공짜가 아닙니다

호출마다 프록시를 두 번 거치는 지연, Pod마다 늘어나는 메모리, 새로 익혀야 할 장애 지점이 생깁니다. 서비스 수가 적으면 라이브러리와 NetworkPolicy로 충분한 경우가 많습니다.

5부

이미지 밖에 두어야 하는 것들

4부의 Ingress는 인증서를 shop-tls라는 이름으로만 가리켰고, 3부의 orders-db는 Pod마다 디스크를 요청했습니다. 이 부에서는 이미지에 넣으면 안 되는 두 가지, 즉 환경마다 다른 설정과 비밀, 그리고 Pod가 사라져도 남아야 하는 데이터를 Kubernetes가 어떻게 다루는지 봅니다.

ConfigMap은 설정을 이미지 밖으로 뺀다

apiVersion: v1
kind: ConfigMap
metadata: { name: order-api-config }

  LOG_LEVEL: info
  PAYMENT_URL: https://pay.example.com.
  application.yaml: |
    payment:

주문 API는 개발 환경에서는 결제사의 테스트 주소를, 운영에서는 실제 주소를 써야 합니다. 이 값을 이미지에 넣으면 환경마다 이미지를 따로 빌드해야 하고, 그러면 "개발에서 검증한 그 이미지"를 운영에 올린다는 보장이 깨집니다. 그래서 이미지는 한 번만 빌드하고 설정은 밖에서 넣습니다(11장).

ConfigMap은 그 설정을 담는 키-값 오브젝트입니다. 값은 짧은 문자열일 수도, |로 쓴 파일 내용 전체일 수도 있습니다. 크기는 1MiB까지입니다.

Pod는 ConfigMap을 환경 변수나 파일로 받는다

containers:
- name: api
  image: ghcr.io/acme/order-api:1.4.2
  envFrom:                    # 방식 1
  - configMapRef: { name: order-api-config }
  volumeMounts:               # 방식 2
  - name: cfg
    mountPath: /config
volumes:
- name: cfg
  configMap: { name: order-api-config }
# 결과: 환경 변수 LOG_LEVEL=info …
#       파일 /config/application.yaml …

첫째 방식 envFrom은 ConfigMap의 키를 모두 환경 변수로 넣습니다. 9장에서 봤듯 환경 변수는 프로세스가 시작될 때 부모에게서 받는 값이라, 앱은 LOG_LEVEL을 그냥 읽으면 됩니다.

둘째 방식은 볼륨입니다. volumes에 ConfigMap을 디스크처럼 선언하고 volumeMounts로 /config에 붙이면, 키 하나가 파일 하나가 됩니다. Spring Boot는 이 위치의 application.yaml을 설정 파일로 읽을 수 있습니다. 두 방식은 값을 바꿀 때 큰 차이가 납니다.

환경 변수는 재시작해야, 볼륨은 잠시 뒤 바뀐다

운영 중에 결제 타임아웃을 3초에서 5초로 바꾸려고 ConfigMap을 고쳤다고 합시다. 환경 변수는 프로세스 시작 때 한 번 복사된 값이라 이미 떠 있는 Pod에는 영향이 없습니다. 볼륨은 kubelet이 주기적으로 원본을 확인해 파일을 바꿔 주지만, 앱이 그 파일을 다시 읽어야 의미가 있습니다. 파일 하나만 꽂는 subPath 마운트는 아예 갱신되지 않습니다.

그래서 실무에서는 설정 내용의 해시를 Pod 틀의 어노테이션에 넣어, 설정이 바뀌면 틀이 바뀌어 롤링 업데이트가 일어나게 합니다. 8부에서 볼 매니페스트 관리 도구(Helm, Kustomize)가 이 일을 자동으로 해 줍니다.

Secret의 base64는 암호화가 아니다

apiVersion: v1
kind: Secret
metadata: { name: orders-db-cred }
type: Opaque
data:
  password: c3VwZXItc2VjcmV0   # base64

$ kubectl get secret orders-db-cred -n prod \
    -o jsonpath='{.data.password}' | base64 -d
super-secret

DB 비밀번호, 결제사 API 키, 4부의 TLS 인증서처럼 노출되면 안 되는 값은 Secret에 담습니다. 넣는 방법은 ConfigMap과 같고, 다른 점은 다루는 방식입니다. kubelet은 Secret을 디스크가 아닌 메모리(tmpfs)에 마운트하고, 권한을 따로 줄 수 있습니다.

값이 base64인 것은 7장에서 본 대로 바이너리를 글자로 옮기기 위해서일 뿐, 위처럼 누구나 되돌립니다. 게다가 기본 설정에서 Secret은 etcd에 암호화되지 않은 채 저장됩니다.

Secret을 실제로 지키는 세 겹

  • 저장 시 암호화: API Server가 etcd에 쓰기 전에 암호화하도록 설정합니다(EncryptionConfiguration). 암호화 키는 클러스터 밖의 키 관리 서비스(KMS, AWS라면 16장의 KMS)에 맡겨, etcd 백업이 새어도 읽히지 않게 합니다.
  • 권한 최소화: Secret 읽기 권한과 Pod 생성 권한을 꼭 필요한 주체에게만 줍니다(8부). Pod를 만들 수 있으면 그 Pod에 아무 Secret이나 마운트해 읽을 수 있기 때문입니다.
  • 원본은 밖에: 값의 원본은 AWS Secrets Manager 같은 전용 저장소에 두고, External Secrets Operator가 Secret으로 동기화하거나 Secrets Store CSI 드라이버가 파일로 바로 마운트합니다.

Secret YAML을 Git에 커밋하지 마세요

base64라 평문과 같습니다. 매니페스트를 Git으로 관리하려면 외부 저장소의 참조만 커밋하거나, Sealed Secrets나 SOPS처럼 암호화된 파일을 씁니다(Git 기반 배포는 11장).

볼륨은 데이터가 얼마나 오래 사는지로 나뉜다

이제 데이터입니다. 9장에서 본 컨테이너의 쓰기 레이어는 컨테이너가 재시작되면 사라집니다. 2부의 emptyDir은 그보다 길게 Pod가 사는 동안 남고, Pod가 지워지면 함께 사라집니다. hostPath는 노드의 디렉터리를 그대로 열어 주므로 노드에 남지만, Pod가 다른 노드로 가면 볼 수 없고 노드 파일을 노출합니다. Pod가 어느 노드로 옮겨 가도 따라와야 하는 데이터는 persistentVolumeClaim으로 노드 밖 디스크를 붙입니다.

볼륨데이터 수명쓰임과 주의
emptyDirPod와 함께 삭제컨테이너 간 공유, 임시 파일
emptyDir (Memory)Pod와 함께 삭제tmpfs, 메모리 한도에 포함
hostPath노드에 남음노드 파일 노출, 시스템 용도만
configMap, secret원본 오브젝트를 따름설정 파일 주입
persistentVolumeClaimPod와 무관하게 유지DB 데이터, 업로드 파일

PV는 디스크 자체, PVC는 디스크 주문서

orders-db는 "50Gi 디스크가 필요하다"만 알면 되고, 그것이 어느 클라우드의 어떤 디스크인지는 몰라야 이식성이 생깁니다. 그래서 둘을 나눕니다. PV는 실제 디스크 한 개를 나타내는 클러스터 오브젝트, PVC는 "50Gi, 한 노드에서 쓰기" 같은 사용자의 주문서입니다.

Kubernetes가 조건에 맞는 PV를 PVC에 짝지으면(바인딩) Pod는 PVC 이름만으로 디스크를 씁니다. 3부의 data-orders-db-0이 이 PVC입니다.

StorageClass가 주문을 보고 디스크를 만든다

  1. PVC 생성

    orders-db-0의 50Gi PVC가 StorageClass gp3(AWS EBS 디스크 유형)를 지정합니다.

  2. Pod 배치 대기

    지연 바인딩이면 Pod의 노드가 정해질 때까지 기다립니다.

  3. CSI 드라이버

    그 노드의 AZ에 클라우드 디스크를 만들라고 클라우드 API를 부릅니다.

  4. PV 등록, 바인딩

    만든 디스크를 PV로 등록하고 PVC와 짝짓습니다.

  5. 마운트

    kubelet이 디스크를 노드에 붙이고 Pod 안에 마운트합니다.

예전에는 운영자가 PV를 미리 만들어 두어야 했습니다. StorageClass는 "이런 종류의 디스크를 이렇게 만든다"는 조리법으로, PVC가 이것을 지정하면 디스크가 그때그때 생깁니다. 이것이 동적 프로비저닝입니다.

실제로 디스크를 만들고 붙이는 일은 CSI 드라이버가 합니다. CNI, CRI처럼 스토리지 업체가 Kubernetes와 별개로 드라이버를 배포하게 해 주는 규격입니다(EBS CSI는 14장).

접근 모드와 회수 정책이 데이터 운명을 정한다

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3 }
provisioner: ebs.csi.aws.com   # CSI 드라이버
parameters: { type: gp3 }
reclaimPolicy: Retain          # 기본 Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true

접근 모드는 디스크를 몇 곳에서 동시에 쓸지입니다. ReadWriteOnce(한 노드), ReadWriteMany(여러 노드, 네트워크 파일 시스템), ReadWriteOncePod(Pod 하나)가 대표적이고, 블록 디스크는 대개 RWO만 됩니다.

회수 정책 기본값 Delete는 PVC를 지우면 디스크도 지웁니다. 주문 데이터는 Retain으로 둡니다. 클라우드 디스크는 데이터센터 묶음인 가용 영역(AZ, 12장) 하나에 묶이므로, WaitForFirstConsumer로 Pod 배치 뒤에 만들어야 다른 AZ에 생기지 않습니다.

6부

얼마나 쓰고, 어디에 놓일 것인가

1부에서 스케줄러는 "자원이 맞는 노드"를 고른다고만 했고, 3부의 Deployment에는 설명 없이 requests가 있었습니다. 이 부에서는 Pod가 쓸 자원을 적는 두 숫자가 배치, 성능, 생존 순서를 어떻게 정하는지 보고, 그 위에 노드를 고르거나 밀어내는 규칙들을 하나씩 얹습니다.

자원을 적지 않으면 스케줄러는 눈을 감고 놓는다

노드 한 대에 메모리 16GiB가 있고, 주문 API Pod는 보통 1GiB를 쓴다고 합시다. 스케줄러가 이 Pod를 놓을 노드를 고르려면 "이 Pod가 얼마나 필요한가"를 알아야 합니다. 그런데 컨테이너가 실제로 얼마나 쓸지는 띄워 보기 전에는 모릅니다. 그래서 Kubernetes는 사람이 미리 적은 숫자를 믿습니다.

숫자를 적지 않으면 스케줄러에게 이 Pod는 "0을 쓰는 Pod"입니다. 한 노드에 수십 개를 몰아 놓아도 계산상 문제가 없으니, 실제로는 메모리가 바닥나 서로를 죽이는 일이 벌어집니다. 반대 문제도 있습니다. 정산 배치 하나가 CPU를 독차지하면 같은 노드의 주문 API가 느려지는데, 상한이 없으면 막을 방법이 없습니다.

그래서 컨테이너마다 숫자 두 개를 적습니다. 하나는 배치를 위한 예약량으로 "최소한 이만큼은 보장해 달라"는 뜻이고, 다른 하나는 실행 중 상한으로 "이 이상은 쓰지 못하게 막아 달라"는 뜻입니다. 앞의 것을 requests, 뒤의 것을 limits라고 부릅니다.

두 숫자는 쓰이는 시점과 쓰는 주체가 다릅니다. requests는 Pod를 놓는 순간 스케줄러가 계산에 쓰고, limits는 Pod가 도는 동안 9장의 cgroup이 커널에서 집행합니다. 이 차이가 이 부 전체를 이해하는 열쇠입니다.

requests는 예약이고, limits는 상한이다

containers:
- name: api
  resources:
    requests: { cpu: 500m, memory: 1Gi }
    limits:   { memory: 1Gi }

$ kubectl describe node ip-10-0-1-23
Capacity:     cpu: 4      memory: 15.6Gi
Allocatable:  cpu: 3920m  memory: 14.8Gi
Allocated resources:
  cpu     3500m (89%)   memory  12Gi (81%)

CPU는 코어 단위이고 m은 천분의 일이라 500m은 0.5코어입니다. 메모리의 Gi는 1024MiB입니다. requests는 스케줄러만 보는 예약량으로, 한 노드에 놓인 Pod들의 requests 합이 노드의 Allocatable을 넘지 않게 배치합니다. 실제 사용량은 보지 않습니다.

Allocatable은 노드 용량(Capacity)에서 운영체제와 kubelet 몫, 비상 여유를 뺀 값입니다. 위 노드는 CPU 예약이 89%라 0.5코어 Pod 하나도 더 들어가지 못합니다. limits는 다음 슬라이드처럼 커널이 집행합니다.

CPU는 느려지고, 메모리는 죽는다

CPU limit은 9장에서 본 cgroup의 CPU 할당량(cpu.max)으로 집행되므로, 넘으면 멈춰 섭니다. limit 500m은 100ms 주기마다 50ms까지만 CPU를 쓰라는 뜻이라, 스레드 4개가 함께 일하면 12.5ms 만에 할당량을 다 쓰고 나머지 87.5ms를 기다립니다.

메모리는 빌려 쓰거나 기다릴 수 없어서, limit을 넘으면 커널이 그 컨테이너의 프로세스를 죽입니다. 상태는 OOMKilled, 종료 코드는 137(SIGKILL)이고 kubelet이 같은 자리에서 재시작합니다.

QoS 클래스는 requests와 limits의 모양이다

노드 전체의 메모리가 모자라면 누군가는 희생되어야 합니다. Kubernetes는 두 숫자를 어떻게 적었는지를 보고 Pod마다 QoS 클래스를 붙여 그 순서를 정합니다. 직접 고르는 값이 아니라 결과로 붙는 이름입니다.

QoS 클래스조건자원이 모자랄 때
Guaranteed모든 컨테이너 CPU·메모리 requests = limits가장 마지막에 희생
Burstablerequests가 하나라도 있으나 위는 아님requests 초과분이 큰 것부터
BestEffortrequests, limits 모두 없음가장 먼저 희생

이 클래스는 9장에서 본 커널 OOM Killer가 고르는 순서(oom_score_adj 값)와, 뒤에서 볼 kubelet의 Pod 축출 순서에 반영됩니다. 앞 슬라이드의 주문 API는 CPU limit이 없으니 Burstable입니다. 운영 서비스에는 BestEffort Pod를 두지 않는 것이 첫 원칙입니다.

숫자는 측정해서 정하고, JVM은 힙을 맞춘다

그러면 주문 API의 숫자는 얼마로 적어야 할까요? 출발점은 측정입니다. 부하가 있는 시간대의 실제 사용량을 보고, requests는 평소 사용량보다 조금 높게 잡습니다. 너무 낮으면 노드에 Pod가 과하게 몰려 서로 자원을 다투고, 너무 높으면 비어 있는 예약 때문에 노드를 더 사야 합니다. 7부의 VPA가 이 추천값을 계산해 줍니다.

메모리는 limit을 requests와 같게 두는 경우가 많습니다. 메모리 초과는 곧 죽음이므로 "예약보다 더 쓰다가 노드가 모자라면 죽는" 애매한 상태를 만들지 않으려는 것입니다.

CPU limit은 앞에서 본 스로틀링 때문에 지연에 민감한 API에는 두지 않거나 넉넉히 둡니다. requests가 있으면 CPU가 모자랄 때 그 비율대로 나눠 받으므로, 최소 몫은 이미 보장되기 때문입니다. 대신 한 Pod가 노드의 남는 CPU를 다 가져갈 수 있다는 점은 받아들여야 합니다.

JVM 앱은 하나를 더 챙깁니다. 5장과 9장에서 본 대로 JVM은 힙 외에 메타스페이스, 스레드 스택, 다이렉트 버퍼도 쓰므로 힙을 limit에 꽉 채우면 OOMKilled가 납니다. -XX:MaxRAMPercentage로 힙을 메모리 limit의 70~75% 정도로 둡니다.

LimitRange는 기본값을, ResourceQuota는 총량을

kind: LimitRange
metadata: { name: defaults, namespace: team-a }
spec:
  limits:
  - type: Container
    defaultRequest: { cpu: 100m, memory: 256Mi }
    default:        { memory: 512Mi }
    max:            { memory: 4Gi }
---
kind: ResourceQuota
metadata: { name: quota, namespace: team-a }
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 64Gi
    pods: "100"

여러 팀이 한 클러스터를 쓰면 누군가는 숫자를 빼먹고, 누군가는 너무 크게 적습니다. 1부의 Namespace 단위로 이것을 막는 장치가 둘 있습니다. LimitRange는 숫자를 빠뜨린 컨테이너에 1부의 어드미션 단계에서 기본값을 채우고, 컨테이너 하나의 최소·최대를 정합니다.

ResourceQuota는 네임스페이스 전체의 합계 한도입니다. CPU requests 쿼터를 걸면 requests 없는 Pod는 생성이 거부되므로 둘을 함께 씁니다.

스케줄러는 걸러 내고 점수를 매긴다

이제 숫자를 들고 스케줄러로 돌아갑니다. 스케줄러는 두 단계로 노드를 고릅니다. 그림의 requests 외 조건들, 즉 노드 라벨로 고르는 조건(nodeSelector, affinity), 노드가 거부하는 표시(taint), AZ 분산은 이어지는 슬라이드에서 하나씩 봅니다.

nodeSelector와 node affinity로 노드를 고른다

nodeSelector:
  kubernetes.io/arch: arm64        # 단순 일치
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node.kubernetes.io/instance-type
          operator: In
          values: [m7g.large, m7g.xlarge]
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 50
      preference:
        matchExpressions:
        - key: capacity
          operator: In
          values: [spot]

노드에도 1부의 라벨이 붙어 있습니다. CPU 종류(kubernetes.io/arch), 가상 머신 유형, AZ 같은 라벨은 자동으로, 나머지는 운영자가 붙입니다. ARM용으로만 빌드한 이미지라면 ARM 노드에만 놓여야 하듯, 노드를 골라야 할 때 이 라벨을 씁니다.

nodeSelector는 완전 일치만 됩니다. node affinity는 In, NotIn 같은 연산자와 필수(required)·선호(preferred) 구분을 줍니다. 이름 끝의 IgnoredDuringExecution은 배치할 때만 본다는 뜻이라, 나중에 라벨이 바뀌어도 떠 있는 Pod는 쫓겨나지 않습니다.

Pod affinity는 붙이고, anti-affinity는 뗀다

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels: { app: order-api }
        topologyKey: kubernetes.io/hostname

앞의 규칙이 노드의 라벨을 봤다면, 이번에는 이미 놓인 다른 Pod를 봅니다. Pod affinity는 "이 라벨의 Pod가 있는 곳 근처에", anti-affinity는 "그런 Pod가 없는 곳에" 놓으라는 규칙입니다. 근처의 범위는 topologyKey가 정해, hostname이면 같은 노드, zone이면 같은 AZ입니다.

위 예는 주문 API 복제본을 서로 다른 노드에 흩어, 노드 하나가 죽어도 전부 죽지 않게 합니다. 필수로 걸면 복제본이 노드 수보다 많을 때 남는 Pod가 Pending에 갇히므로 흔히 선호로 씁니다.

topologySpreadConstraints로 AZ에 고르게

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels: { app: order-api }
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels: { app: order-api }

anti-affinity는 "떨어뜨려라"만 말할 뿐 얼마나 고르게인지는 말하지 않습니다. 이 규칙은 분산의 정도를 숫자로 적습니다. maxSkew: 1은 가장 많은 영역과 가장 적은 영역의 Pod 수 차이를 1 이하로 지키라는 뜻입니다. 복제본 6개, AZ 3개면 2, 2, 2가 되어 AZ 하나가 장애 나도 4개가 남습니다.

DoNotSchedule은 필터, ScheduleAnyway는 점수로 작동합니다. 분산은 배치 순간에만 맞추므로, 쏠린 Pod를 다시 펴려면 descheduler(재배치 도구)가 필요합니다.

taint는 노드가 밀어내고, toleration은 견딘다

$ kubectl taint nodes gpu-1 \
    dedicated=gpu:NoSchedule

# GPU 작업 Pod의 틀
tolerations:
- key: dedicated
  value: gpu
  effect: NoSchedule
nodeSelector:
  dedicated: gpu   # 끌어오는 건 별도

지금까지는 Pod가 노드를 골랐습니다. 반대로 비싼 GPU 노드처럼 노드가 아무 Pod나 받지 않게 하고 싶을 때 taint("들어오지 마시오" 표시)를 겁니다. Pod 쪽의 toleration은 그 표시를 견디는 허가입니다. 효과는 NoSchedule(새 배치 금지), PreferNoSchedule(가급적 금지), NoExecute(있던 Pod도 쫓아냄)입니다.

노드가 응답하지 않으면 Control Plane이 NoExecute taint를 거는데, 모든 Pod에 기본 300초 toleration이 붙어 있어 죽은 노드의 Pod는 약 5분 뒤에 옮겨 갑니다.

PriorityClass가 높으면 자리를 빼앗는다

kind: PriorityClass
metadata: { name: critical-api }
value: 100000
description: "주문, 결제 API"
---
kind: PriorityClass
metadata: { name: batch-low }
value: -10
preemptionPolicy: Never
---
# 주문 API Pod 틀
priorityClassName: critical-api

모든 필터를 통과하는 노드가 없어 Pending인 Pod가 주문 API라면, 기다리게 두기보다 덜 중요한 Pod를 비키게 하고 싶습니다. Pod의 우선순위가 높으면 스케줄러는 낮은 우선순위 Pod를 쫓아내(선점) 자리를 만듭니다. 쫓겨나는 Pod도 2부의 정상 종료 절차를 밟습니다.

preemptionPolicy: Never는 줄은 앞에 서되 남을 쫓아내지는 않습니다. 사용자 값은 10억 이하라, 약 20억인 시스템 구성 요소용 클래스보다 항상 낮습니다.

노드가 버거우면 kubelet이 Pod를 쫓아낸다

requests는 배치 때 계산일 뿐이라, Burstable Pod들이 예약보다 많이 쓰면 노드 전체가 바닥날 수 있습니다. kubelet은 노드 자원이 문턱을 넘으면 Pod를 골라 축출합니다. 리눅스 기본 문턱은 가용 메모리 100Mi 미만, 노드 디스크(nodefs) 10% 미만, 이미지 디스크(imagefs) 15% 미만, inode 5% 미만입니다.

먼저 사용량이 requests를 넘은 Pod를 우선순위와 초과량 순으로 고릅니다. 이 축출은 유예 시간 없이 즉시이고, 노드를 비울 때 지키는 7부의 중단 한도(PDB)도 보지 않습니다.

세 프로브는 서로 다른 질문을 한다

8장에서 로드 밸런서는 헬스 체크 경로를 주기적으로 불러 실패한 서버를 뺐습니다. Kubernetes에서는 각 노드의 kubelet이 이 검사, 즉 프로브를 실행합니다. 차이는 질문을 셋으로 나눴다는 점입니다. "빼 달라"와 "다시 띄워 달라"는 전혀 다른 조치이기 때문입니다.

프로브묻는 것실패하면
startup느린 시작이 끝났나끝날 때까지 나머지 둘을 보류
liveness프로세스가 고장 났나 (데드락 등)컨테이너 재시작
readiness지금 트래픽을 받아도 되나EndpointSlice에서 빼기만

검사 방법은 HTTP GET(응답 코드 200~399면 성공), TCP 연결, 컨테이너 안 명령 실행, gRPC 헬스 체크 중 하나입니다. 기본값은 10초마다(periodSeconds), 1초 안에 답이 없으면 실패(timeoutSeconds), 3번 연속 실패하면 판정(failureThreshold)입니다.

startup probe가 느린 JVM 기동을 지켜 준다

startupProbe:
  httpGet: { path: /actuator/health/liveness,
             port: 8080 }
  periodSeconds: 10
  failureThreshold: 30   # 최대 300초 대기
livenessProbe:
  httpGet: { path: /actuator/health/liveness,
             port: 8080 }
  timeoutSeconds: 3
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness,
             port: 8080 }
  periodSeconds: 5
  failureThreshold: 2

주문 API는 Spring 컨텍스트를 올리느라 기동에 1분이 걸립니다. liveness만 걸면 준비 중인 앱이 30초 만에 고장으로 판정되어 재시작되고, 다시 처음부터 기동하다 또 죽는 무한 반복에 빠집니다.

startup probe는 failureThreshold × periodSeconds, 여기서는 300초까지 기다려 주고, 한 번 성공하면 그때부터 나머지 둘이 시작됩니다. 경로는 Spring Boot의 운영용 엔드포인트 모음인 Actuator가 liveness와 readiness를 따로 제공하는 것을 연결했습니다.

프로브를 잘못 걸면 멀쩡한 서비스가 죽는다

프로브는 실패에 대한 조치가 자동이라, 잘못 설계하면 장애를 막는 대신 키웁니다. 실제로 자주 일어나는 다섯 경우입니다.

잘못된 설정일어나는 일고치는 법
liveness에 DB 검사DB가 느려지면 전 Pod 동시 재시작liveness는 프로세스 자체만
liveness timeout 1초부하나 GC 정지 때 재시작, 부하 가중timeout과 실패 횟수 넉넉히
startup 없이 짧은 지연기동 중 죽어 무한 재시작startup probe 추가
readiness에 외부 의존외부 장애 때 모든 Pod 제외, 503자기 준비 상태만 확인
readiness 없음롤링 중 준비 안 된 Pod로 요청readiness 반드시 설정

공통 원리는 하나입니다. 공유 의존성을 프로브에 넣으면 장애가 한 Pod가 아니라 전체로 번집니다. DB 상태는 프로브가 아니라 지표와 8장의 서킷 브레이커로 다룹니다.

HPA는 사용률 비율만큼 Pod 수를 바꾼다

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-api, namespace: prod }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60

이제 행사 날입니다. HPA는 Deployment의 replicas를 자동으로 바꾸는 컨트롤러입니다. 15초마다 metrics-server(노드에서 사용량을 모으는 별도 설치 애드온)에서 CPU를 읽어 ceil(현재 개수 × 현재값 / 목표값)으로 개수를 정합니다.

4개, 평균 90%, 목표 60%면 ceil(4 × 90 / 60) = 6개입니다. 여기서 사용률은 requests 대비입니다. requests 500m에 450m을 쓰면 90%입니다. 그래서 6부의 requests가 틀리면 확장도 틀립니다.

늘릴 때는 빠르게, 줄일 때는 천천히

spec:
  behavior:
    scaleUp:
      policies:
      - { type: Percent, value: 100,
          periodSeconds: 15 }
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - { type: Pods, value: 2,
          periodSeconds: 60 }

사용률은 순간마다 출렁이므로 계산 결과를 그대로 따르면 Pod 수가 오르내리기를 반복합니다. 그래서 HPA는 비율이 1에서 10% 이내면 움직이지 않고, 줄일 때는 최근 5분(stabilizationWindowSeconds) 동안의 추천값 중 가장 큰 값을 씁니다. 잠깐 한가해졌다고 바로 줄였다가 다시 늘리는 낭비를 막는 것입니다.

behavior로 속도도 정합니다. 예시는 15초마다 최대 두 배로 늘리고, 1분에 2개씩만 줄입니다. HPA를 쓰면 매니페스트에서 replicas를 빼야 배포 때 HPA의 값을 덮어쓰지 않습니다.

CPU가 아닌 지표로 늘리기: 커스텀 메트릭과 KEDA

CPU가 부하를 잘 보여 주지 않는 서비스도 있습니다. 주문이 들어오면 큐에 넣고 따로 처리하는 컨슈머는 큐가 쌓여도 CPU는 한가할 수 있습니다. HPA는 지표 수집 시스템(대표적으로 Prometheus)과 잇는 어댑터를 통해 초당 요청 수 같은 커스텀 메트릭이나 큐 길이 같은 외부 메트릭으로도 계산합니다.

KEDA는 SQS, Kafka 등 수십 가지 이벤트 소스를 읽어 HPA를 대신 만들어 주는 애드온으로, 일이 없을 때 0개까지 줄이는 데 많이 씁니다.

0개까지 줄이기

CPU 같은 자원 지표는 떠 있는 Pod에서만 잴 수 있어 0개가 불가능합니다. 1.37에서는 외부·오브젝트 지표를 쓰는 HPA의 minReplicas: 0이 기본 활성(베타)입니다.

VPA와 in-place 리사이즈는 Pod 크기를 바꾼다

HPA가 개수를 바꾼다면 VPA는 6부의 requests를 바꿉니다. 별도 설치하는 애드온으로, 과거 사용량에서 적정 requests를 추천하고 설정에 따라 직접 적용합니다. 추천만 받는 모드로 시작해 숫자를 맞추는 데 특히 유용합니다.

예전에는 requests를 바꾸려면 Pod를 다시 만들어야 했습니다. 1.35에서 정식이 된 in-place 리사이즈는 실행 중인 Pod의 CPU·메모리를 재시작 없이 바꿉니다. 다만 JVM처럼 시작 때 힙 크기를 정하는 앱은 메모리가 늘어도 바로 쓰지 못합니다.

HPA와 VPA를 같은 CPU 지표에 걸지 마세요

VPA가 requests를 올리면 사용률이 내려가 HPA가 Pod를 줄이고, 그러면 다시 사용률이 올라갑니다. 서로의 입력을 바꾸므로 출렁입니다. 함께 쓰려면 HPA는 커스텀 지표를 씁니다.

Pod가 넘치면 노드를 늘린다

HPA가 주문 API를 30개로 늘렸는데 노드에 requests를 받아 줄 자리가 없으면, 새 Pod는 6부에서 본 대로 Pending에 머뭅니다. 노드 오토스케일러는 이 Pending을 보고 노드(가상 머신)를 늘리고, 한가해진 노드는 Pod를 옮긴 뒤 지웁니다. 두 가지 구현이 널리 쓰입니다. 표의 Spot은 클라우드의 남는 서버를 싸게 빌리되 회수될 수 있는 구매 방식입니다(14장).

새 노드가 뜨는 데 수십 초에서 몇 분이 걸리므로 급증에 대비해 여유 노드나 HPA 목표치에 여유를 둡니다. EKS에서의 구성은 14장에서 봅니다.

노드를 비울 때는 cordon하고 drain한다

노드 오토스케일러가 노드를 지울 때, 혹은 운영자가 노드의 운영체제나 Kubernetes 버전을 올릴 때 그 노드의 Pod들은 다른 곳으로 옮겨야 합니다. 순서는 둘입니다. 먼저 kubectl cordon으로 노드에 "새 Pod 배치 금지" 표시를 해 더 이상 Pod가 들어오지 않게 합니다.

다음으로 kubectl drain이 노드의 Pod를 하나씩 내보냅니다. 이때 Pod를 그냥 지우지 않고 Eviction API라는 "내보내도 되는지 묻고 내보내기" 요청을 씁니다. 내보낸 Pod는 2부의 종료 절차를 밟고, 3부의 컨트롤러가 다른 노드에 새로 만듭니다. DaemonSet Pod는 노드마다 하나라 옮길 수 없으므로 건너뛰고(--ignore-daemonsets), emptyDir을 쓰는 Pod는 그 임시 데이터가 사라지는 데 동의해야 내보냅니다(--delete-emptydir-data).

이처럼 사람이나 자동화가 계획해서 일으키는 중단을 자발적 중단이라 합니다. 노드 하드웨어 고장, 커널 패닉, 6부의 kubelet 축출처럼 예고 없이 오는 비자발적 중단과 구분됩니다.

자발적 중단은 속도를 조절할 수 있다는 점이 중요합니다. 주문 API 3개가 모두 같은 노드에 있었다면 drain이 셋을 한꺼번에 내보내 잠시 0개가 될 수도 있습니다. 그래서 "동시에 몇 개까지만 내보내라"는 한도를 선언해 둡니다. 다음 슬라이드의 PDB입니다.

PDB는 자발적 중단의 한도다

kind: PodDisruptionBudget
metadata: { name: order-api, namespace: prod }
spec:
  maxUnavailable: 1     # 또는 minAvailable
  selector: { matchLabels: { app: order-api } }

$ kubectl cordon ip-10-0-1-23
$ kubectl drain ip-10-0-1-23 \
    --ignore-daemonsets --delete-emptydir-data
evicting pod prod/order-api-7d9f5-x2k4q
error when evicting … would violate the
  pod's disruption budget. Will retry…

PDB는 셀렉터로 고른 Pod 중 동시에 빠져도 되는 수를 선언합니다. drain은 Eviction API로 묻고, 한도를 넘는 요청은 거절되어 앞의 Pod가 다른 노드에서 준비될 때까지 기다렸다 다시 시도합니다.

복제본 2개에 minAvailable: 2처럼 허용 중단이 0이면 drain이 영원히 멈춥니다. 복제본을 여유 있게 두고 maxUnavailable: 1처럼 겁니다. PDB는 비자발적 중단은 막지 못합니다.

8부

권한을 줄이고, 매니페스트를 다루고, 클러스터를 올린다

1부에서 API Server는 요청마다 인증과 인가를 거친다고 했고, 5부에서는 Pod 생성 권한이 곧 Secret 읽기 권한이라고 했습니다. 이 부에서는 그 권한을 설계하는 법, Pod가 노드에서 갖는 권한을 깎는 법, 늘어나는 YAML을 환경별로 관리하는 도구, Kubernetes를 확장하는 방법과 클러스터 업그레이드를 다룹니다.

ServiceAccount는 Pod의 신원이다

apiVersion: v1
kind: ServiceAccount
metadata: { name: order-api, namespace: prod }
automountServiceAccountToken: false
---
# 주문 API Pod 틀
serviceAccountName: order-api

# 마운트될 때의 토큰 위치
/var/run/secrets/kubernetes.io/
  serviceaccount/token

권한을 주려면 먼저 "누구"가 있어야 합니다. 사람은 회사 로그인이나 클라우드 계정 같은 외부 인증으로 API Server에 자신을 증명합니다. Pod 안의 프로세스는 ServiceAccount라는 Kubernetes 안의 신원을 씁니다. 네임스페이스마다 default가 있고, 지정하지 않으면 이것을 씁니다.

kubelet은 짧은 수명의 토큰을 발급받아 위 경로에 마운트하고 자동으로 교체합니다. API를 부를 일이 없는 주문 API는 마운트를 끕니다. 이 신원을 AWS 권한에 잇는 원리는 12장, 설정은 14장입니다.

RBAC: 누가, 어떤 리소스에, 무슨 동사를

kind: Role
metadata: { name: pod-reader, namespace: prod }
rules:
- apiGroups: [""]          # 핵심 묶음 (v1)
  resources: [pods, pods/log]
  verbs: [get, list, watch]
---
kind: RoleBinding
metadata: { name: ci-pods, namespace: prod }
subjects:
- kind: ServiceAccount
  name: ci
  namespace: ci
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

7장에서 본 인가를 Kubernetes는 RBAC으로 합니다. API 요청은 결국 "어떤 리소스에 어떤 동사를"이므로, 허용할 조합의 목록을 만들어 주체에 연결합니다. 동사는 HTTP 메서드에 대응해 get(하나 읽기), list, watch, create, update, patch, delete입니다.

Role은 그 목록이고, RoleBinding은 목록을 주체(사람, 그룹, ServiceAccount)에 묶습니다. 위 예는 CI가 prod의 Pod와 로그를 읽게만 합니다. 네임스페이스를 넘는 권한은 ClusterRole과 ClusterRoleBinding으로 줍니다.

겉보기보다 큰 권한을 조심한다

$ kubectl auth can-i delete pods -n prod \
    --as system:serviceaccount:ci:ci
no
$ kubectl auth can-i --list -n prod \
    --as system:serviceaccount:ci:ci

RBAC 규칙은 허용만 있고 거부는 없습니다. 아무 규칙에도 없으면 거부이고, 하나라도 허용하면 허용입니다. 그래서 무엇을 허용했는지 정확히 알아야 하는데, 이름만 보면 작아 보이는 권한이 실제로는 큽니다.

  • secrets의 list는 목록만이 아니라 값까지 읽습니다.
  • pods의 create는 아무 Secret이나 마운트한 Pod를 만들어 우회로 읽게 합니다.
  • pods/exec는 컨테이너 안에서 명령을 실행하는 권한입니다.

CI에 전권(cluster-admin)을 묶는 것이 가장 흔한 과잉 권한입니다. auth can-i로 확인합니다.

Pod Security Standards는 세 단계 기준이다

apiVersion: v1
kind: Namespace
metadata:
  name: prod
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted

RBAC는 API를 누가 쓰는지를 막지만, 허락받은 사람이 만든 Pod가 노드에서 얼마나 강한지는 막지 않습니다. 9장에서 봤듯 컨테이너 안의 root는 호스트의 root이고, 특권 컨테이너나 노드 디렉터리 마운트는 노드 장악으로 이어집니다.

PSS는 Pod 설정의 안전 수준을 셋으로 정의합니다. Privileged는 제한 없음, Baseline은 알려진 탈출 경로 차단, Restricted는 root 금지와 권한 최소화까지 요구합니다. 내장 어드미션이 네임스페이스 라벨을 보고 위반 Pod를 거부(enforce)하거나 경고(warn), 기록(audit)합니다.

securityContext로 컨테이너 권한을 깎는다

securityContext:                 # Pod 수준
  runAsNonRoot: true
  runAsUser: 10001
  fsGroup: 10001
  seccompProfile: { type: RuntimeDefault }
containers:
- name: api
  securityContext:               # 컨테이너
    allowPrivilegeEscalation: false
    readOnlyRootFilesystem: true
    capabilities: { drop: [ALL] }
  volumeMounts: [{ name: tmp, mountPath: /tmp }]
volumes: [{ name: tmp, emptyDir: {} }]

Restricted를 통과하려면 Pod 명세에 이렇게 적습니다. root가 아닌 사용자 10001로 실행하고, 9장의 setuid 같은 권한 상승을 막고, root 권한 조각인 capability를 모두 버립니다. seccomp는 프로세스가 부를 수 있는 시스템 콜을 커널이 걸러 주는 기능으로, 런타임 기본 목록이 위험한 호출을 막습니다.

루트 파일 시스템을 읽기 전용으로 두면 공격자가 도구를 내려받아 둘 곳이 없어집니다. 대신 앱이 쓰는 /tmp는 emptyDir로 따로 열어 줍니다.

환경이 늘면 YAML 복사본이 문제가 된다

지금까지 주문 API 하나를 위해 쓴 오브젝트를 세어 봅시다. Deployment, Service, ConfigMap, Secret 참조, HPA, PDB, ServiceAccount, Ingress 경로까지 여덟 개 남짓입니다. 이것이 개발, 스테이징, 운영 세 환경에 필요하고, 환경마다 다른 것은 복제본 수, 이미지 태그, 설정 값 몇 줄뿐입니다.

가장 쉬운 방법은 폴더를 세 개 만들어 복사하는 것입니다. 하지만 프로브 경로를 고칠 때 세 곳을 다 고쳐야 하고, 하나를 빠뜨리면 환경마다 다르게 동작합니다. "운영에서만 나는 장애"의 흔한 원인입니다. 필요한 것은 공통 부분은 한 번만 쓰고 차이만 따로 적는 방법입니다.

널리 쓰이는 해법은 두 갈래입니다. Helm은 YAML을 빈칸이 있는 템플릿으로 만들고, 환경마다 빈칸에 넣을 값 파일을 따로 둡니다. 서식 편지에 이름만 바꿔 넣는 방식입니다.

Kustomize는 템플릿 문법 없이 평범한 YAML을 원본(base)으로 두고, 환경마다 "이 필드만 이렇게 바꿔라"라는 덧칠(overlay)을 겹칩니다. 원본 위에 투명 필름을 얹는 방식입니다. 두 도구를 차례로 보고 쓰임을 비교합니다.

Helm은 템플릿의 빈칸을 값으로 채운다

# templates/deployment.yaml
spec:
  replicas: {{ .Values.replicas }}
  template:
    spec:
      containers:
      - name: api
        image: {{ .Values.image }}
# values-prod.yaml
replicas: 3
image: ghcr.io/acme/order-api:1.4.2

$ helm upgrade --install order-api ./chart \
    -n prod -f values-prod.yaml --atomic
$ helm rollback order-api 4 -n prod

템플릿과 기본 값을 묶은 꾸러미를 차트라 합니다. {{ .Values.replicas }} 자리가 값 파일의 replicas로 채워져 완성된 YAML이 클러스터에 들어갑니다.

설치 한 번을 릴리스라 하며, Helm은 매 설치의 기록을 리비전으로 Secret에 남겨 rollback으로 되돌립니다. --atomic은 실패하면 자동으로 되돌립니다. 남이 만든 소프트웨어(Ingress 컨트롤러, 모니터링)도 대개 차트로 배포됩니다.

Kustomize는 원본 위에 덧칠한다

# base/kustomization.yaml
resources: [deployment.yaml, service.yaml]

# overlays/prod/kustomization.yaml
resources: [../../base]
namespace: prod
images:
- name: ghcr.io/acme/order-api
  newTag: 1.4.2
patches:
- path: replicas.yaml    # replicas만 바꿈
configMapGenerator:
- name: order-api-config
  envs: [config.env]

$ kubectl apply -k overlays/prod

base에는 그대로 적용해도 되는 평범한 YAML이 있고, prod 덧칠은 네임스페이스, 이미지 태그, 복제본 수만 바꿉니다. 템플릿 문법이 없어 base가 그 자체로 유효한 YAML이라는 점이 장점입니다. kubectl에 내장되어 apply -k로 씁니다.

configMapGenerator는 ConfigMap 이름 뒤에 내용 해시를 붙여 만듭니다. 설정이 바뀌면 이름이 바뀌고, 그 이름을 참조하는 Pod 틀도 바뀌어 5부에서 말한 설정 변경이 롤링 업데이트로 이어집니다.

Helm은 남의 것, Kustomize는 우리 것에 맞는다

항목HelmKustomize
방식템플릿 차트에 값 주입평범한 YAML에 덧칠 패치
설치 단위릴리스 (리비전 기록 보관)그냥 매니페스트 묶음
롤백helm rollbackGit의 이전 커밋을 다시 적용
배우는 비용템플릿 문법, 차트 구조낮음, kubectl 내장
잘 맞는 곳남이 만든 소프트웨어 설치우리 서비스의 환경별 관리

Helm 차트는 수많은 사용자의 다양한 설정을 받아야 하는 공개 소프트웨어에 강하고, 그만큼 템플릿이 복잡해집니다. 우리 주문 API처럼 환경 차이가 몇 줄뿐인 서비스는 Kustomize가 더 읽기 쉽습니다. 실무에서는 둘을 함께 쓰는 경우가 많고, 어느 쪽이든 결과물을 Git에 두고 자동으로 적용하는 흐름은 11장에서 봅니다.

CRD와 Operator로 새 오브젝트를 가르친다

# cert-manager가 추가한 종류
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: { name: shop-tls, namespace: prod }
spec:
  secretName: shop-tls       # Ingress가 참조
  dnsNames: [shop.example.com]
  issuerRef:
    name: letsencrypt
    kind: ClusterIssuer

4부의 Ingress가 가리킨 shop-tls 인증서는 90일마다 갱신해야 합니다. 이 일을 Kubernetes답게 하려면 "이런 인증서가 있어야 한다"를 오브젝트로 적고 루프가 맞추게 하면 됩니다. CRD는 API Server에 Certificate 같은 새 오브젝트 종류를 등록합니다.

등록만으로는 저장될 뿐이고, 지켜보며 조정 루프를 도는 컨트롤러가 있어야 일이 일어납니다. 운영 지식을 그 컨트롤러에 담은 것이 Operator 패턴입니다. cert-manager는 인증서 발급과 갱신을, DB Operator는 3부에서 말한 복제와 장애 조치를 맡습니다.

클러스터 업그레이드는 한 단계씩, 위에서부터

Kubernetes는 1년에 세 번 정도 마이너 버전(1.36, 1.37처럼 가운데 숫자)을 내고, 최근 세 버전(지금은 1.37, 1.36, 1.35)만 약 1년간 보안 패치를 받습니다. 그래서 1년에 몇 번은 반드시 올려야 합니다.

순서는 Control Plane을 한 마이너씩 먼저 올리고, 그다음 노드를 7부의 cordon과 drain으로 비우며 교체합니다. 구성 요소 간 허용되는 버전 차이(skew)가 있기 때문입니다. kubelet은 API Server보다 새로우면 안 되고 최대 세 마이너까지 오래될 수 있으며, kubectl은 위아래 한 마이너 안에서 씁니다.

제거된 API 버전부터 확인합니다

업그레이드 사고의 대부분은 새 버전에서 사라진 apiVersion을 쓰는 매니페스트와 차트입니다. 올리기 전에 폐기 API 사용 여부를 점검하고, 노드 교체는 PDB를 지키며 천천히 진행합니다. EKS 버전 정책은 14장입니다.

9부

상태 이름이 원인을 가리킨다

지금까지 본 구성 요소는 각자 맡은 단계에서 실패하면 그 이유를 Pod 상태와 이벤트에 적어 둡니다. 이 부에서는 상태 이름을 1부의 "apply부터 Pod까지" 흐름에 대어 어디서 멈췄는지 찾고, 상태별로 증상, 확인 명령, 원인, 조치를 정리합니다. 클러스터 밖까지 포함한 장애 대응 전체는 18장에서 다룹니다.

진단은 get, describe, logs 순서로 좁힌다

$ kubectl get pods -n prod -o wide
NAME                   READY  STATUS
order-api-7d9f5-x2k4q  0/1    CrashLoopBackOff
$ kubectl describe pod order-api-7d9f5-x2k4q
$ kubectl logs order-api-7d9f5-x2k4q --previous
$ kubectl get events -n prod \
    --sort-by=.lastTimestamp
$ kubectl debug -it order-api-7d9f5-x2k4q \
    --image=busybox:1.36 --target=api

순서는 넓게 보고 좁히는 것입니다. get으로 상태 이름을, describe 맨 아래 Events와 Last State로 이유와 종료 코드를, logs --previous로 죽기 직전 컨테이너의 마지막 말을 봅니다. 이벤트는 기본 1시간만 보관되니 일찍 봅니다.

9장의 distroless처럼 셸이 없는 이미지는 exec가 안 됩니다. kubectl debug는 도구가 든 임시 컨테이너를 같은 Pod에 붙여, 같은 네트워크와 프로세스를 들여다보게 합니다.

상태 이름은 멈춘 단계를 알려 준다

  1. Pending스케줄러가 못 놓음
  2. ImagePullBackOff노드가 이미지 못 받음
  3. CrashLoopBackOff앱이 떴다가 죽음
  4. 0/1 Running준비 검사 실패
  5. 1/1 Running트래픽을 받음

1부에서 Pod는 스케줄러가 노드를 정하고, kubelet이 이미지를 받아 컨테이너를 띄우고, 프로브가 준비를 확인해야 트래픽을 받았습니다. 위의 상태 이름은 이 길의 어디에서 멈췄는지를 그대로 말해 줍니다. 그래서 상태 이름만 보고도 어느 구성 요소의 이야기를 들어야 할지 정해집니다.

Pending이면 스케줄러의 사정(6부의 자원과 규칙)을, ImagePullBackOff이면 노드와 레지스트리 사이를, CrashLoopBackOff이면 앱 자신의 로그를, Running인데 준비가 안 됐다면 7부의 프로브를 봅니다. 여기에 길 밖의 두 경우, 노드가 Pod를 쫓아낸 Evicted와 Pod는 멀쩡한데 Service가 닿지 않는 경우를 더해 차례로 봅니다.

CrashLoopBackOff와 OOMKilled: 떴다가 죽는다

단계CrashLoopBackOffOOMKilled
증상재시작 횟수가 계속 증가Last State Terminated, 137
확인logs --previous, 종료 코드describe의 Reason: OOMKilled

종료 코드가 첫 단서입니다(9장). 1은 앱이 스스로 실패한 것이라 로그에 이유가 있고, 137은 SIGKILL로 OOM이거나 2부의 유예 시간 초과이며, 143은 SIGTERM을 받고 정상 종료한 것입니다. 로그가 비어 있는데 137이 반복되면 메모리를 보고, 6부에서 본 대로 JVM 힙을 limit의 70~75%로 맞췄는지 확인합니다.

단계Evictedreadiness 실패로 트래픽 0

조치requests 현실화, 로그·임시 파일 정리프로브 대상과 timeout 재설계

축출(6부)된 Pod는 Failed 상태로 남아 목록을 어지럽힙니다. 같은 노드에서 반복되면 그 노드에 놓인 Pod들의 requests 합과 실제 사용량의 차이를 봅니다. readiness가 모든 Pod에서 동시에 실패하면 Pod 하나의 문제가 아니라 7부에서 본 공통 의존성이나 프로브 설계를 의심합니다.

4부의 순서를 거꾸로 짚습니다. Service의 셀렉터와 Pod 라벨이 맞는지, EndpointSlice에 IP가 있는지, 이름이 풀리는지 차례로 봅니다.

정리

  • Kubernetes는 조정 루프의 집합입니다. 원하는 상태를 적으면 컨트롤러들이 실제 상태와의 차이를 끝없이 메웁니다. 자가 치유와 롤링 업데이트가 그 결과입니다.
  • Pod는 일회용이고, 정체성은 컨트롤러가 줍니다. 주문 API는 Deployment, DB는 StatefulSet, 노드 에이전트는 DaemonSet, 정산은 Job과 CronJob입니다.
  • Service는 라벨과 준비 상태로 대상을 고르는 가상 IP입니다. kube-proxy 규칙, EndpointSlice, CoreDNS가 이를 실현하고, 외부 입구는 Gateway API로 옮겨 갑니다.
  • requests는 배치를, limits는 집행을 정합니다. CPU 초과는 스로틀링, 메모리 초과는 OOMKilled이고, QoS와 HPA 사용률도 여기서 나옵니다.
  • 운영 사고의 상당수는 설정 하나에서 옵니다. 종료와 주소 목록 갱신의 경합(preStop), 프로브의 공유 의존성, PDB 한도, 과한 RBAC 권한을 먼저 점검합니다.

스스로 점검 (1)

  1. 노드 하나가 꺼졌을 때 그 위의 주문 API Pod가 다른 노드에서 다시 뜨기까지 무슨 일이 일어나나요?

    노드에 응답 없음 taint가 걸리고, 기본 toleration 300초가 지나면 Pod가 축출됩니다. ReplicaSet 컨트롤러가 개수 부족을 보고 새 Pod를 만들고 스케줄러가 다른 노드에 배정합니다.

  2. preStop 없이 배포할 때마다 502가 몇 건씩 나는 이유는 무엇인가요?

    엔드포인트 제거가 각 노드와 외부 LB에 퍼지기 전에 앱이 SIGTERM을 받고 먼저 닫히기 때문입니다. preStop으로 몇 초 기다린 뒤 종료를 시작하게 합니다.

  3. maxSurge 0, maxUnavailable 0으로 두면 어떻게 되나요?

    새 Pod를 더 띄울 수도, 옛 Pod를 뺄 수도 없어 업데이트가 불가능하므로 API가 거부합니다. 둘 중 하나는 0보다 커야 합니다.

  4. CPU 사용률 평균이 30%인데 응답 지연이 튀는 Pod가 있습니다. 무엇을 의심하나요?

    CPU limit, 즉 cgroup CPU 할당량에 의한 스로틀링입니다. 짧은 순간 여러 스레드가 할당량을 소진하면 평균은 낮아도 주기 대부분을 멈춰 있게 됩니다.

스스로 점검 (2)

  1. Service의 ClusterIP로 ping이 안 되는 것은 장애인가요?

    아닙니다. ClusterIP는 인터페이스가 없는 가상 IP이고 kube-proxy 규칙이 Service 포트의 TCP/UDP에만 걸리므로 ICMP는 응답하지 않습니다.

  2. liveness probe에서 DB 연결을 검사하면 어떤 장애가 생기나요?

    DB가 잠깐 느려지면 모든 Pod의 liveness가 동시에 실패해 일제히 재시작됩니다. 재시작 중 연결 폭증으로 DB가 더 느려지는 악순환이 생깁니다.

  3. Pod 4개, 평균 CPU 120%, 목표 80%면 HPA는 몇 개로 늘리나요? requests를 두 배로 올리면요?

    ceil(4 × 120 / 80) = 6개입니다. requests가 두 배면 사용률이 60%로 계산되어 ceil(4 × 60 / 80) = 3개로 오히려 줄이려 합니다(최소 개수 안에서).

  4. replicas 2인 Deployment에 minAvailable 2인 PDB를 걸면 노드 drain은 어떻게 되나요?

    허용 중단이 0이라 Eviction API가 계속 거절해 drain이 끝나지 않습니다. maxUnavailable 1로 두거나 복제본을 늘립니다.

스스로 점검 (3)

  1. ConfigMap을 볼륨으로 마운트했는데 값을 바꿔도 앱이 옛 값을 씁니다. 가능한 원인 두 가지는?

    subPath로 마운트해 갱신이 반영되지 않거나, 파일은 바뀌었지만 앱이 시작할 때 한 번만 읽은 경우입니다. 설정 해시로 Pod 틀을 바꿔 롤링 재시작을 일으키는 것이 확실합니다.

  2. EBS를 쓰는 orders-db Pod가 재생성 후 Pending에 머뭅니다. 무엇을 확인하나요?

    PV가 특정 AZ에 묶여 있어 그 AZ에 자리가 있는 노드가 없는지 봅니다. 해당 AZ에 노드를 늘리거나 WaitForFirstConsumer와 AZ 분산 설계를 점검합니다.
