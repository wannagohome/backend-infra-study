1부

서비스 바깥쪽 경계를 그린다

15장까지는 데이터가 사는 곳을 만들었습니다. 이제 그 앞에서 요청을 받아 주고, 걸러 내고, 기록하는 바깥 경계를 세웁니다.

데이터를 만들었으니 이제 앞과 둘레를 지킨다

15장에서 S3, RDS, DynamoDB에 데이터를 두었습니다. 그런데 이 자원들은 모두 한 리전에 있습니다. 서울 리전의 서비스에 상파울루 사용자가 접속하면 왕복 지연만 수백 밀리초가 붙고, 공격 트래픽도 그대로 리전까지 밀려옵니다.

그래서 AWS는 리전 바깥, 사용자 가까이에 엣지(edge)라는 층을 둡니다. 엣지에서 캐시로 답하고, TLS를 끝내고, 공격을 걸러 냅니다.

동시에 리전 안쪽에서는 데이터를 키로 암호화하고, 비밀번호를 코드 밖에 두고, 모든 조작을 기록해야 합니다. 이 장은 이 두 방향, 바깥 경계와 안쪽 보호를 함께 다룹니다.

CloudFront는 캐시를 세 겹으로 쌓았다

층마다 맡는 역할이 다르다

엣지 로케이션은 사용자에게 가장 가까운 지점입니다. DNS가 사용자를 지연 시간이 가장 짧은 엣지로 보내고, 인기 있는 객체가 이곳 캐시에 남습니다.

리전 엣지 캐시는 엣지보다 캐시가 커서, 엣지에서 밀려난 덜 인기 있는 객체도 오래 붙잡아 둡니다. 여러 엣지의 미스를 모아 오리진으로 가는 요청을 줄입니다.

Origin Shield는 오리진과 가장 가까운 리전에 켜는 추가 캐시 층입니다. 모든 리전 엣지 캐시의 요청이 이곳을 거치므로, 같은 객체에 대한 동시 요청이 오리진에 하나만 가도록 합쳐집니다. 요청 수에 따라 추가 요금이 붙습니다.

배포 하나가 경로별로 오리진을 고른다

CloudFront 설정의 단위는 배포입니다. 배포는 d111abc.cloudfront.net 같은 도메인을 받고, 여기에 내 도메인을 대체 도메인 이름(CNAME)으로 붙입니다.

배포 안에는 여러 오리진과 캐시 동작이 있습니다. 캐시 동작은 경로 패턴마다 어느 오리진으로 보낼지, 어떻게 캐시할지를 정합니다.

2부

무엇을 같은 요청으로 볼 것인가

캐시 적중률은 캐시 키 설계가 거의 전부를 결정합니다. 캐시 키, TTL, 접근 제어, 엣지에서 도는 코드까지 CloudFront 내부 동작을 봅니다.

기초 원리 여기부터는 캐시 키, 정책, 서명, 엣지 함수의 동작을 다룹니다.

캐시 키가 같으면 같은 객체로 본다

엣지는 요청에서 캐시 키를 만들어 저장된 객체를 찾습니다. 기본 캐시 키는 도메인과 URL 경로뿐입니다.

쿼리 문자열, 헤더, 쿠키를 캐시 키에 넣으면 값마다 다른 객체로 저장됩니다. 넣을수록 정확해지지만 같은 파일이 여러 벌로 쪼개져 적중률이 떨어집니다.

요청키에 쿼리 제외키에 쿼리 전체
/a.js객체 A객체 A
/a.js?v=1객체 A객체 B
/a.js?utm=x객체 A객체 C

캐시 키, 오리진 전달, 응답 헤더는 따로 정한다

정책정하는 것관리형 예
캐시 정책캐시 키 구성, TTL, 압축 허용CachingOptimized, CachingDisabled
오리진 요청 정책키와 무관하게 오리진에 넘길 값AllViewerExceptHostHeader
응답 헤더 정책뷰어에게 붙일 CORS·보안 헤더SecurityHeadersPolicy, CORS-*

예전에는 "오리진에 넘기는 값은 곧 캐시 키"였습니다. 그래서 오리진이 User-Agent를 필요로 하면 캐시가 브라우저 종류만큼 쪼개졌습니다. 정책이 분리된 뒤에는 캐시 키는 좁게 두고, 오리진에는 필요한 값을 따로 넘길 수 있습니다.

캐시 정책은 키 구성과 TTL 세 값을 묶는다

resource "aws_cloudfront_cache_policy" "static" {
  name        = "static-assets"
  min_ttl     = 0
  default_ttl = 86400
  max_ttl     = 31536000
  parameters_in_cache_key_and_forwarded_to_origin {
    enable_accept_encoding_gzip   = true
    enable_accept_encoding_brotli = true
    query_strings_config { query_string_behavior = "none" }
    headers_config { header_behavior = "none" }
    cookies_config { cookie_behavior = "none" }
  }
}

쿼리, 헤더, 쿠키를 모두 none으로 두어 정적 파일을 경로 하나당 한 벌만 캐시합니다.

gzip과 Brotli를 켜면 Accept-Encoding을 정규화한 값이 키에 들어가, 압축본과 원본이 섞이지 않습니다.

Host 헤더를 넘기면 오리진이 길을 잃는다

오리진 요청 정책 AllViewer는 뷰어의 모든 헤더를 넘기는데, 여기에는 Host: www.example.com도 포함됩니다.

S3는 Host 헤더로 버킷을 찾으므로 엉뚱한 Host가 오면 요청을 처리하지 못합니다. ALB 오리진이라면 오리진 인증서 이름과 Host가 맞지 않아 502가 납니다. 그래서 S3와 대부분의 ALB 앞에는 AllViewerExceptHostHeader를 씁니다.

모든 헤더를 키에 넣으면 적중률은 0에 가깝다

레거시 설정에서 "모든 헤더 전달"을 고르면 사실상 캐시가 꺼집니다. 헤더는 오리진 요청 정책으로 넘기고, 캐시 키에는 꼭 필요한 것만 넣습니다.

TTL은 오리진 헤더와 정책 범위가 함께 정한다

오리진 응답 헤더CloudFront 캐시 시간브라우저 캐시 시간
max-age만max-age를 최소~최대 TTL 범위로 자름max-age
max-age + s-maxages-maxage를 범위로 자름max-age
Expires만Expires 시각을 범위로 자름Expires
헤더 없음기본 TTL브라우저 판단
no-cache, private최소 TTL(0이 아니면 캐시됨)헤더대로

정책에서 최소·기본·최대 TTL을 정하고, 오리진은 Cache-Control로 객체마다 값을 줍니다. 캐시 정책 없이 쓰면 기본 TTL은 24시간입니다.

s-maxage로 엣지와 브라우저를 따로 조절한다

Cache-Control: max-age=60, s-maxage=86400을 보내면 브라우저는 1분만, CloudFront는 하루를 캐시합니다. 배포 직후 무효화 한 번으로 엣지는 새 파일을 받고, 브라우저는 1분 안에 따라옵니다.

stale-while-revalidate와 stale-if-error도 지원합니다. 오리진이 죽어도 오래된 객체를 최대 TTL 범위 안에서 계속 내줄 수 있습니다.

최소 TTL이 0보다 크면 private도 캐시된다

관리형 CachingOptimized의 최소 TTL은 1초입니다. 사용자별 응답에 이 정책을 붙이면 no-store를 보내도 다른 사용자에게 섞여 나갈 수 있습니다.

압축은 엣지가 대신 해 준다

캐시 동작에서 압축을 켜면, 뷰어가 Accept-Encoding에 gzip이나 br을 보낼 때 CloudFront가 객체를 압축해서 내줍니다. 둘 다 받는 뷰어에게는 Brotli를 고릅니다.

압축 대상은 1,000바이트에서 10,000,000바이트 사이 객체입니다. 오리진이 이미 압축해서 보냈다면 그대로 캐시합니다. Chrome과 Firefox는 HTTPS에서만 Brotli를 요청합니다.

압축 설정은 캐시 정책에 들어 있습니다. 정책에서 Brotli를 켜지 않으면 br 요청도 gzip이나 무압축으로 처리됩니다.

무효화보다 파일명에 버전을 넣는다

무효화는 TTL이 끝나기 전에 엣지와 리전 엣지 캐시에서 객체를 지웁니다. 매달 경로 1,000개까지 무료이고, /images/* 같은 와일드카드는 파일 수와 상관없이 경로 하나로 셉니다.

하지만 무효화는 브라우저와 회사 프록시 캐시까지 지우지 못합니다. 그래서 자주 바뀌는 파일은 app.3f9c2a.js처럼 내용 해시를 이름에 넣고 긴 TTL을 겁니다.

무효화는 진입 파일에만

새 해시 파일을 가리키는 index.html만 짧은 TTL이나 무효화로 갱신합니다. 처리 속도 할당량은 초당 경로 150개, 와일드카드는 초당 1개입니다.

응답 헤더 정책으로 보안 헤더를 한곳에서 붙인다

strict-transport-security: max-age=63072000
x-content-type-options: nosniff
x-frame-options: DENY
referrer-policy: strict-origin-when-cross-origin
content-security-policy: default-src 'self'
access-control-allow-origin: https://app.example.com

응답 헤더 정책은 오리진 응답에 HSTS, CSP 같은 보안 헤더와 CORS 헤더(7장)를 덧붙이거나 오리진 값을 덮어씁니다.

S3처럼 헤더를 마음대로 붙이기 어려운 오리진도 엣지에서 일관되게 처리됩니다.

오리진 그룹은 읽기 요청만 보조로 넘긴다

  1. 주 오리진에 요청

    캐시 미스면 언제나 주 오리진부터 시도합니다.

  2. 실패 판정

    지정한 상태 코드(500, 502, 503, 504, 403, 404 등)나 연결 실패, 시간 초과.

  3. 보조 오리진에 재요청

    그 요청만 보조로 보냅니다. 다음 요청은 다시 주 오리진부터.

장애 조치는 뷰어 요청이 GET, HEAD, OPTIONS일 때만 일어납니다. POST 같은 쓰기는 넘기지 않습니다.

기본값으로는 연결 시도 3번 × 10초, 최대 30초를 기다린 뒤 넘어갑니다. 빠른 전환이 필요하면 연결 제한 시간과 시도 횟수를 줄입니다.

OAC: 버킷은 닫고 서명한 요청만 읽힌다

CloudFrontS3 버킷
캐시 미스 GET /logo.png SigV4 서명서비스 주체 cloudfront.amazonaws.com 정책 확인
200 OK SourceArn 일치
누군가 S3 URL로 직접 요청하면
403 서명 없음 버킷 정책에 허용 없음 퍼블릭 차단

OAC는 CloudFront가 S3로 가는 요청에 SigV4 서명을 붙이게 합니다. 버킷 정책은 그 서명 주체 중 내 배포 ARN만 허용합니다.

예전 방식인 OAI는 레거시입니다. 2022년 12월 이후 리전과 SSE-KMS를 지원하지 않습니다.

버킷 정책은 배포 ARN 하나만 허용한다

{
  "Effect": "Allow",
  "Principal": { "Service": "cloudfront.amazonaws.com" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-static-bucket/*",
  "Condition": { "StringEquals": {
    "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E1AB2"
  } }
}

Principal이 CloudFront 서비스 전체라서 Condition이 없으면 남의 배포도 이 버킷을 읽을 수 있습니다. SourceArn 조건이 핵심입니다. 객체가 SSE-KMS로 암호화되어 있다면 KMS 키 정책에도 같은 조건으로 kms:Decrypt를 허용해야 합니다.

VPC 오리진이면 ALB를 공개할 필요가 없다

예전에는 ALB가 퍼블릭 서브넷에 있어야 CloudFront가 닿았습니다. 그러면 누군가 ALB 주소로 CloudFront와 WAF를 우회할 수 있습니다.

VPC 오리진을 쓰면 프라이빗 서브넷의 ALB, NLB, EC2를 그대로 오리진으로 씁니다. CloudFront가 서브넷에 관리형 ENI를 만들어 사설 경로로 들어오고, 인터넷 쪽 입구는 아예 없습니다.

퍼블릭 ALB를 써야 한다면

보안 그룹에 관리형 접두사 목록 com.amazonaws.global.cloudfront.origin-facing만 허용하고, CloudFront가 붙인 비밀 헤더를 ALB 규칙에서 검사해 우회를 막습니다.

공개 키는 CloudFront 키 그룹에 올리고 캐시 동작에 신뢰 대상으로 지정합니다. 키는 RSA 2048이나 ECDSA 256입니다.

루트 사용자로 만드는 옛 CloudFront 키 페어 대신 키 그룹을 씁니다. API로 키 교체를 자동화할 수 있습니다.

지역 제한은 배포 전체에 국가 단위로 건다

지역 제한은 허용 목록이나 차단 목록으로 국가를 고르고, 막힌 요청에는 403을 돌려줍니다. 위치는 서드파티 IP 데이터베이스로 판단하며 AWS가 밝힌 정확도는 약 99.8%입니다.

제한은 배포 전체에 적용됩니다. 경로마다 다른 국가 규칙이 필요하면 WAF의 지리 매치 규칙이나 엣지 함수의 지역 정보를 씁니다.

규정 대응이라면 로그를 남긴다

표준 로그의 403만으로는 지역 차단과 다른 403을 구분하기 어렵습니다. WAF 지리 규칙을 쓰면 어떤 규칙이 막았는지 로그에 남습니다.

HTTPS는 뷰어 쪽과 오리진 쪽을 따로 정한다

구간설정인증서
뷰어 ↔ CloudFront뷰어 프로토콜 정책: HTTP를 HTTPS로 리다이렉트, HTTPS만ACM, 반드시 us-east-1
CloudFront ↔ 오리진오리진 프로토콜 정책: HTTPS만, 뷰어와 일치ALB 인증서는 ALB 리전

인증서는 us-east-1 ACM에서 가져옵니다. ALB 오리진은 CloudFront가 오리진 도메인 이름으로 TLS를 검증하므로 ALB 인증서가 그 이름을 포함해야 합니다. 뷰어 쪽 HTTP/2와 HTTP/3(QUIC, 2장)는 배포 설정 스위치로 켜며, 오리진은 지원하지 않아도 됩니다.

엣지 코드는 네 지점에 끼어든다

뷰어 쪽 함수는 캐시 적중 여부와 상관없이 매 요청 실행되므로 가벼워야 합니다. 오리진 쪽 함수는 캐시 미스일 때만 돌아 무거운 작업을 맡길 수 있습니다.

SPA 경로를 index.html로 돌리는 함수 하나

function handler(event) {
  var req = event.request;
  var uri = req.uri;
  // 확장자가 없는 경로는 앱 라우트로 본다

    req.uri = '/index.html';

  req.headers['x-edge-ts'] = { value: Date.now() + '' };
  return req;
}

뷰어 요청 이벤트에 붙이면 /orders/42 같은 앱 라우트가 S3의 index.html로 바뀝니다.

S3 오류 응답을 200으로 바꾸는 사용자 지정 오류 페이지보다 깔끔합니다. 진짜 없는 파일은 여전히 404입니다.

캐시하지 않아도 엣지를 거치면 빨라진다

API처럼 매번 다른 응답도 CloudFront 뒤에 두는 이유가 있습니다. TCP와 TLS 핸드셰이크가 사용자 가까운 엣지에서 끝나고, 엣지에서 오리진까지는 미리 열어 둔 연결과 AWS 백본망을 씁니다.

이런 경로에는 CachingDisabled 캐시 정책과 AllViewerExceptHostHeader 오리진 요청 정책을 붙입니다. POST 같은 메서드는 리전 엣지 캐시를 건너뛰고 오리진으로 바로 갑니다.

오리진 응답 시간 제한

오리진 응답 대기 시간은 기본 30초, 1~120초로 바꿀 수 있습니다. 긴 리포트 API가 30초를 넘기면 504가 나므로 비동기로 바꾸거나 값을 늘립니다.

3부

요청을 읽고 걸러 내는 방화벽

보안 그룹은 IP와 포트만 봅니다. SQL Injection이나 봇의 폭주는 HTTP 요청의 내용을 읽어야 막을 수 있습니다.

WAF는 L7 요청 내용을 보고 판정한다

WAF는 HTTP 요청의 URI, 쿼리, 헤더, 쿠키, 본문을 규칙과 비교해 통과나 차단을 정합니다. XSS와 SQL Injection의 원리와 코드 수준 방어는 7장에서 봤고, WAF는 그 앞단에 두는 추가 그물입니다.

WAF는 단독 장비가 아니라 다른 서비스에 붙여 씁니다. 보호 대상과 연결된 규칙 묶음을 웹 ACL이라 부르며, 새 콘솔에서는 보호 팩(protection pack)이라고도 표기합니다.

연결 대상웹 ACL 리전
CloudFront, Amplifyus-east-1(글로벌)
ALB, API Gateway REST대상과 같은 리전
AppSync, Cognito대상과 같은 리전
App Runner, Verified Access대상과 같은 리전

규칙은 우선순위 순서로, 첫 판정에서 멈춘다

  1. 우선순위 0 규칙

    일치하고 Block이면 여기서 403으로 끝납니다.

  2. Count 규칙

    일치해도 세기만 하고 다음 규칙으로 넘어갑니다.

  3. 규칙 그룹

    관리형 규칙 묶음 안에서도 같은 방식으로 평가합니다.

  4. 기본 동작

    아무 규칙에도 걸리지 않으면 기본 동작(Allow 또는 Block)을 따릅니다.

Allow와 Block은 종료 동작이라 평가를 멈춥니다. Count는 평가를 이어 가면서 레이블을 붙일 수 있어, 뒤 규칙이 그 레이블을 조건으로 쓸 수 있습니다.

그래서 순서가 곧 정책입니다. 신뢰하는 IP 허용 규칙을 위에, 무거운 검사를 아래에 둡니다.

동작은 다섯 가지, 둘은 사람인지 묻는다

동작결과평가 계속 여부
Allow보호 대상에 전달, 헤더 삽입 가능멈춤
Block기본 403, 사용자 지정 응답 가능멈춤

Challenge브라우저에서 조용히 검증유효 토큰이면 계속

CAPTCHA와 Challenge는 통과한 클라이언트에게 토큰을 주고, 면제 시간 동안 다시 묻지 않습니다. HTTPS 엔드포인트의 브라우저에서만 동작하고 추가 요금이 붙습니다. 모바일 앱이나 서버 간 호출에 걸면 그대로 막힙니다.

규칙은 일치 조건을 논리식으로 엮는다

And, Or, Not으로 엮고, 비교 전에 소문자화나 URL 디코딩 같은 텍스트 변환을 걸어 우회 표기를 정규화합니다.

AWS가 규칙을 계속 갱신하므로 직접 시그니처를 관리하지 않아도 됩니다. 그룹 안의 개별 규칙은 동작을 Count로 재정의(override)해서 끌 수 있습니다. 버전을 고정하면 갱신으로 생기는 예기치 않은 차단을 피할 수 있습니다.

WCU는 규칙이 쓰는 연산 예산이다

WCU는 규칙 평가에 드는 처리량을 수치로 나타낸 것입니다. 단순한 IP 일치는 적게, 정규식이나 JSON 본문 검사는 많이 듭니다.

웹 ACL 기본 요금에는 1,500 WCU까지 포함되고, 넘으면 단계별 추가 요금이 붙으며 최대 5,000입니다. 규칙 그룹의 용량은 만들 때 정하고 바꿀 수 없으므로 여유 있게 잡습니다.

예산 계산 예

Core 700 + Known bad 200 + SQL 200 + IP reputation 25 + Anonymous IP 50 = 1,175 WCU. 남은 325로 rate-based 규칙과 직접 만든 규칙 몇 개를 더할 수 있습니다.

rate-based 규칙은 키별로 요청 수를 센다

{
  "Name": "login-rate-limit",
  "Priority": 5,
  "Statement": { "RateBasedStatement": {
    "Limit": 100, "EvaluationWindowSec": 300,
    "AggregateKeyType": "FORWARDED_IP",
    "ForwardedIPConfig": {
      "HeaderName": "X-Forwarded-For",
      "FallbackBehavior": "MATCH" },
    "ScopeDownStatement": { "ByteMatchStatement": {
      … UriPath STARTS_WITH /login … } }
  } },
  "Action": { "Block": {} }
}

최근 300초 동안 같은 IP에서 /login 요청이 100번을 넘으면 그 IP의 추가 요청을 막습니다.

창은 60, 120, 300, 600초 중 고르고, 한도는 최소 10입니다. 한도는 근사치로 적용되며 동작으로 Allow는 쓸 수 없습니다.

무엇을 기준으로 셀지가 rate 규칙의 성패다

집계 키로 IP, 전달된 IP 헤더, 그리고 헤더·쿠키·쿼리·레이블·URI 경로를 조합한 사용자 지정 키를 쓸 수 있습니다. 예를 들어 Authorization 헤더를 키로 삼으면 사용자 계정 단위 제한이 됩니다.

WAF가 ALB에 붙어 있고 앞에 CloudFront가 있다면, ALB가 보는 출발지 IP는 사용자 IP가 아니라 CloudFront 엣지 서버의 IP입니다. 이때 IP 기준으로 세면 수많은 사용자가 한 엣지 IP로 묶여 한꺼번에 차단됩니다. WAF를 CloudFront에 붙이거나, 위 예처럼 X-Forwarded-For를 키로 씁니다.

토큰 버킷 같은 알고리즘의 원리는 8장, API Gateway의 스로틀링은 17장에서 다룹니다.

Bot Control은 밝힌 봇과 숨은 봇을 나눈다

Common 수준은 검색 엔진, 스크래핑 프레임워크처럼 스스로 정체를 밝히는 봇을 요청 정보로 식별하고 레이블을 붙입니다. 검증된 검색 엔진 봇은 막지 않습니다.

Targeted 수준은 정체를 숨기는 봇을 브라우저 검사, 지문, 행동 휴리스틱, 머신러닝으로 잡고 Challenge와 CAPTCHA로 대응합니다. 수준이 높을수록 요금도 올라갑니다.

범위를 좁혀 비용을 줄인다

Bot Control은 검사한 요청 수로 과금됩니다. scope-down 문으로 로그인, 장바구니처럼 봇이 노리는 경로에만 적용하고 정적 파일은 뺍니다.

WAF는 본문을 앞부분까지만 읽는다

본문 검사 한도는 연결 대상마다 다릅니다. ALB와 AppSync는 8KB 고정이고, CloudFront, API Gateway, Cognito, App Runner, Verified Access는 기본 16KB에서 64KB까지 16KB 단위로 늘릴 수 있습니다(16KB 초과분은 추가 요금).

한도를 넘는 부분은 검사하지 않습니다. 넘친 요청을 어떻게 다룰지(계속, 일치로 간주, 불일치로 간주)는 규칙마다 정합니다.

Core rule set은 8KB 넘는 본문을 막는다

규칙 SizeRestrictions_BODY가 8,192바이트를 넘는 본문을 차단합니다. 파일 업로드나 큰 JSON을 받는 API는 이 규칙만 Count로 돌리고 경로를 좁혀 다시 막습니다.

로그와 레이블이 있어야 규칙을 고칠 수 있다

WAF 로그는 CloudWatch Logs, S3, Data Firehose로 보냅니다. 대상 이름은 aws-waf-logs-로 시작해야 합니다. 로그에는 어느 규칙이 최종 판정을 냈는지(terminatingRuleId), 어떤 레이블이 붙었는지, Count로 일치한 규칙 목록이 남습니다.

로그를 켜지 않아도 콘솔에서 최근 3시간 동안의 샘플 요청과 규칙별 CloudWatch 지표(AllowedRequests, BlockedRequests, CountedRequests)를 볼 수 있습니다. Authorization이나 쿠키처럼 민감한 필드는 로그에서 가리도록(redaction) 설정합니다.

공격은 엣지에서 흡수하고 오리진은 숨긴다

공격 트래픽이 수백 개 엣지로 분산되어 각 위치에서 흡수되고, 오리진에는 공개 주소가 없어 우회 경로가 없습니다. CloudFront 정액 요금제(flat-rate plan)는 차단된 공격 요청을 사용량에 넣지 않습니다.

VPC 안쪽 방화벽과 조직 단위 관리는 따로 있다

AWS Network Firewall은 VPC에 두는 관리형 방화벽입니다. 서브넷 사이나 인터넷 출구에 끼워, 도메인 이름 기반 아웃바운드 허용 목록, Suricata 호환 IPS 규칙처럼 보안 그룹이 못 하는 L3~L7 검사를 합니다. 탈취된 서버가 외부 C&C 서버로 나가는 것을 막을 때 씁니다.

AWS Firewall Manager는 Organizations(12장)의 여러 계정에 WAF 규칙, Shield Advanced 보호, 보안 그룹 정책, Network Firewall 정책을 중앙에서 일괄 적용합니다. 새 계정이나 새 ALB가 생기면 정책이 자동으로 붙어, 보호 누락을 막습니다.

4부

암호는 쉽고, 키 관리가 어렵다

대칭키, 서명, 해시의 원리는 7장에서 봤습니다. 여기서는 인증서를 누가 갱신하고, 키를 어디에 두고, 비밀번호를 어떻게 바꾸는지 AWS의 구현을 봅니다.

ACM은 인증서 발급과 갱신을 떠맡는다

ACM은 TLS 인증서를 발급하고 ALB, CloudFront, API Gateway에 배포합니다. 통합 서비스에 붙이는 퍼블릭 인증서는 무료이고, 개인 키는 ACM 밖으로 나오지 않습니다.

퍼블릭 인증서의 유효 기간은 현재 198일입니다. CA/Browser Forum의 인증서 수명 단축에 맞춘 값이라, 수동 갱신으로는 감당하기 어렵고 자동 갱신이 전제가 됩니다.

DNS 검증 레코드가 남아 있으면 갱신은 자동이다

ACM은 도메인 소유를 확인하려고 _a79865eb….example.com 같은 CNAME 레코드를 줍니다. 이 레코드를 DNS에 넣으면 검증이 끝나고, 레코드가 남아 있는 한 ACM이 만료 전에 알아서 재검증하고 갱신합니다. 갱신해도 인증서 ARN은 그대로입니다.

이메일 검증은 갱신 때마다 사람이 메일을 눌러야 하므로 피합니다. 72시간 안에 검증하지 못하면 요청은 시간 초과로 끝납니다.

갱신이 멈추는 흔한 원인

DNS 정리 중 CNAME 삭제, 어떤 서비스에도 연결되지 않은 인증서, WAF가 /.well-known/pki-validation/ 경로를 막는 경우입니다.

KMS는 키를 꺼내 주지 않고 대신 써 준다

암호화의 약점은 키를 어디 두느냐입니다. 설정 파일에 키를 두면 서버 하나만 털려도 데이터가 다 열립니다.

KMS의 키는 FIPS 검증 HSM 안에 있고 평문으로 밖에 나오지 않습니다. 앱은 키를 받는 대신 "이것을 암호화해 줘", "이것을 풀어 줘"라는 API를 호출합니다. 그래서 IAM과 키 정책으로 호출을 통제할 수 있고, 모든 호출이 CloudTrail에 남습니다.

키를 쓸 권한 = 데이터를 읽을 권한

S3 객체 읽기 권한이 있어도 그 객체를 암호화한 KMS 키의 Decrypt 권한이 없으면 읽지 못합니다. 권한 경계가 하나 더 생기는 셈입니다.

AWS 관리형 키는 2021년 이후 새 서비스에서 더 만들지 않는 레거시 유형입니다. 교차 계정 공유, 세밀한 접근 통제, 감사가 필요하면 고객 관리형 키를 씁니다. 그 외에는 서비스 기본값(AWS 소유 키)으로도 저장 시 암호화는 됩니다.

KMS가 직접 암호화하는 데이터는 4KB까지다

KMS 키에는 용도가 있습니다. 가장 흔한 대칭 키(AES-256-GCM)는 Encrypt, Decrypt, 데이터 키 생성에 씁니다. 비대칭 키(RSA, ECC)는 공개 키를 밖으로 내보내 서명 검증이나 암호화를 KMS 없이도 하게 할 때, HMAC 키는 토큰 무결성 검사에 씁니다.

그런데 Encrypt API로 보낼 수 있는 평문은 최대 4,096바이트입니다. 모든 데이터를 네트워크로 KMS에 보내 암호화하는 것은 느리고 비싸며, 애초에 크기 제한으로 불가능합니다.

그렇다면 수 GB짜리 EBS 볼륨이나 S3 객체는 어떻게 KMS로 암호화할까요? 답이 봉투 암호화입니다.

봉투 암호화: 데이터 키로 잠그고 그 키를 잠근다

GenerateDataKey를 호출하면 KMS가 데이터 키를 만들어 평문과 KMS 키로 암호화한 사본을 함께 줍니다.

앱은 평문 키로 데이터를 로컬에서 암호화하고, 평문 키는 바로 메모리에서 지웁니다. 암호화된 데이터 키는 데이터 옆에 같이 저장합니다.

복호화는 작은 키 하나만 KMS에 다녀온다

  1. 암호화된 키 꺼내기

    데이터 옆에 저장한 암호화된 데이터 키를 읽습니다.

  2. Decrypt 호출

    그 작은 키만 KMS로 보냅니다. 여기서 권한 검사와 기록이 일어납니다.

  3. 평문 키 수신

    KMS가 KMS 키로 풀어 평문 데이터 키를 돌려줍니다.

  4. 로컬 복호화

    데이터 본체는 네트워크를 타지 않고 앱에서 풉니다.

데이터가 1GB든 1TB든 KMS가 다루는 것은 수십 바이트 키뿐입니다. 키 정책이 데이터 전체의 열쇠 구멍 역할을 합니다.

EBS, RDS, S3 SSE-KMS가 모두 이 구조입니다. S3 버킷 키(15장)는 데이터 키를 버킷 단위로 재사용해 KMS 호출 수를 줄입니다.

키 정책이 허락해야 IAM 정책도 효력이 있다

{ "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": { "AWS":
    "arn:aws:iam::111122223333:root" },
  "Action": "kms:*", "Resource": "*" },
{ "Sid": "AllowAppDecrypt",
  "Effect": "Allow",
  "Principal": { "AWS":
    "arn:aws:iam::111122223333:role/app" },

  "Resource": "*",
  "Condition": { "StringEquals": {
    "kms:ViaService":
      "s3.ap-northeast-2.amazonaws.com" } } }

모든 KMS 키에는 키 정책이 정확히 하나 있고, 이것이 1차 관문입니다(12장의 리소스 기반 정책).

첫 문장은 계정에게 "IAM 정책으로 위임해도 된다"고 허락합니다. 이 문장이 없으면 IAM의 Allow는 무시됩니다.

그랜트와 암호화 컨텍스트로 범위를 더 좁힌다

그랜트는 키 정책을 고치지 않고 특정 주체에게 특정 작업을 임시로 위임하는 장치입니다. EBS가 암호화된 볼륨을 인스턴스에 붙일 때, 서비스가 내부적으로 그랜트를 만들어 그 볼륨에 필요한 Decrypt만 허용하고 작업이 끝나면 회수합니다.

암호화 컨텍스트는 암호화할 때 함께 넘기는 키-값 쌍입니다. 복호화할 때 같은 값을 넘기지 않으면 실패하고, 값은 CloudTrail에 평문으로 남습니다. {"tenant": "a-corp"}를 붙여 두면 다른 테넌트 데이터의 암호문을 바꿔치기해도 풀리지 않고, 키 정책 조건으로 테넌트별 권한을 줄 수도 있습니다.

앞 슬라이드의 kms:ViaService 조건은 "S3를 거칠 때만" 쓰게 해서, 역할이 키를 직접 호출해 다른 용도로 쓰는 것을 막습니다.

키 회전은 옛 데이터를 다시 잠그지 않는다

자동 회전을 켜면 KMS가 기본 365일(90~2,560일로 조정 가능)마다 새 키 재료를 만듭니다. 키 ID와 ARN은 그대로이고, 옛 재료도 보관해 예전 암호문을 계속 풀 수 있습니다. 그래서 회전해도 기존 데이터를 다시 암호화할 필요가 없습니다.

자동 회전은 KMS가 만든 대칭 키에서만 됩니다. 고객 관리형 키는 자동 회전과 별개로 즉시 회전(on-demand)도 할 수 있고, AWS 관리형 키는 매년 자동 회전되며 설정을 바꿀 수 없습니다.

키 삭제는 데이터 삭제다

KMS 키는 7~30일(기본 30일) 대기 후 삭제되며, 그 뒤 그 키로 암호화한 데이터는 영원히 풀 수 없습니다. 먼저 비활성화해 영향을 확인하고, 대기 중 사용 시도를 CloudTrail 알람으로 잡습니다.

리전 간 복제와 호출량 한도도 설계 대상이다

KMS 키는 리전 자원입니다. 다중 리전 키는 같은 키 ID와 키 재료를 가진 복제본을 다른 리전에 만들어, 서울에서 암호화한 데이터를 도쿄에서 KMS 호출 없이 리전을 건너지 않고 풀게 합니다. DR(18장)이나 글로벌 테이블에서 씁니다.

대칭 키 암호 연산은 계정·리전별로 초당 1만~10만 건(리전에 따라 다름)을 공유합니다. S3 SSE-KMS 객체를 초당 수만 건 읽으면 S3가 대신 부르는 Decrypt가 이 한도를 먹어 ThrottlingException이 납니다. 버킷 키와 데이터 키 캐싱이 해법입니다.

규정상 HSM을 단독으로 써야 하면 전용 HSM 클러스터인 CloudHSM을 쓰거나, KMS 사용자 지정 키 저장소로 연결합니다.

교체는 스테이징 레이블을 옮기는 네 단계다

  1. createSecret

    새 비밀번호를 만들어 새 버전에 AWSPENDING 레이블로 저장합니다.

  2. setSecret

    DB에 접속해 실제 사용자 비밀번호를 새 값으로 바꿉니다.

  3. testSecret

    AWSPENDING 값으로 로그인이 되는지 확인합니다.

  4. finishSecret

    AWSCURRENT를 새 버전으로 옮기고, 옛 버전은 AWSPREVIOUS가 됩니다.

앱은 언제나 AWSCURRENT 버전을 읽습니다. 레이블 이동은 원자적이라 읽는 쪽에서 반쯤 바뀐 상태는 보이지 않습니다.

RDS, Aurora, Redshift 같은 관리형 비밀은 Lambda 없이 관리형 교체로 처리되고, 교체 주기는 최소 4시간까지 줄일 수 있습니다.

두 사용자를 번갈아 바꾸면 끊기지 않는다

단일 사용자 전략은 한 계정의 비밀번호를 그대로 바꿉니다. 단순하지만 setSecret과 앱이 새 값을 읽는 사이에, 옛 비밀번호로 새 연결을 여는 인스턴스는 로그인에 실패합니다.

교대 사용자 전략은 app_user와 복제한 app_user_clone 두 계정을 두고, 교체할 때마다 쓰지 않는 쪽만 바꿉니다. 옛 자격 증명도 다음 교체까지 유효하므로 교체 중 로그인 실패가 없습니다.

교대 전략의 준비물

복제 사용자를 만들 권한이 있는 별도 관리자 비밀이 필요하고, 원래 사용자 권한을 바꾸면 복제 사용자에도 똑같이 반영해야 합니다.

앱은 비밀을 캐시하고, 인증 실패 때 다시 읽는다

private final SecretCache cache = new SecretCache();

DbCredential current() {
  String json = cache.getSecretString("prod/orders/db");
  return mapper.readValue(json, DbCredential.class);
}

// 커넥션 풀이 새 연결에서 인증 실패를 받으면
void onAuthFailure() {
  cache.refreshNow("prod/orders/db");
  pool.softEvictConnections();
}

요청마다 API를 부르면 비용과 지연이 쌓입니다. Java 캐싱 라이브러리는 기본 1시간마다 새로 읽습니다.

교체 직후 캐시에 옛 값이 남을 수 있으므로, 인증 실패를 신호로 즉시 다시 읽는 경로를 둡니다.

호스티드 UI는 현재 관리형 로그인(managed login)이라는 이름으로 제공됩니다.

ID·Access 토큰은 기본 1시간, Refresh 토큰은 기본 30일이며 앱 클라이언트마다 바꿉니다. API Gateway의 Cognito 권한 부여자(17장)와 ALB 인증 연동(13장)이 이 검증을 대신해 줍니다.

5부

막지 못한 것은 기록하고 찾아낸다

예방은 언젠가 뚫립니다. 누가 무엇을 했는지 남기는 감사 기록과, 그 기록에서 이상을 찾아내는 탐지 서비스가 마지막 방어선입니다.

AWS의 모든 조작은 API 호출로 남는다

콘솔 클릭도, CLI도, Terraform도 결국 AWS API 호출입니다. CloudTrail은 그 호출을 누가, 언제, 어디서, 무엇을 대상으로, 성공했는지까지 기록합니다.

계정을 만들면 CloudTrail은 이미 켜져 있고, 관리 이벤트 90일을 리전별 이벤트 기록(Event history)에서 무료로 조회할 수 있습니다. 그 이상 보관하거나 데이터 이벤트를 남기려면 트레일을 만듭니다.

트레일은 조직 전체를 한 버킷에 모은다

멀티 리전 트레일은 켜져 있는 모든 리전의 이벤트를 S3 버킷 하나로 보냅니다. 쓰지 않는 리전에서 몰래 만든 채굴 인스턴스도 잡히므로 기본으로 씁니다. 로그 파일은 평균 5분 안팎으로 전달되고, CloudWatch Logs와 EventBridge로도 흘려 실시간 알람을 겁니다.

조직 트레일은 Organizations 관리 계정에서 만들어 모든 멤버 계정의 이벤트를 로그 아카이브 계정 버킷(12장 계정 분리)에 모읍니다. 멤버 계정 관리자는 이 트레일을 끄거나 지울 수 없습니다.

관리 이벤트의 첫 번째 사본은 트레일로 받아도 요금이 없고, 데이터 이벤트와 추가 사본은 과금됩니다. 데이터 이벤트는 민감한 버킷처럼 필요한 곳만 고급 이벤트 선택기로 좁혀 켭니다.

로그가 지워지거나 고쳐졌는지 증명할 수 있다

공격자는 들어온 뒤 흔적부터 지웁니다. 로그 파일 무결성 검증을 켜면 CloudTrail이 로그 파일마다 SHA-256 해시를 만들고, 매시간 그 해시들을 담은 다이제스트 파일을 RSA 서명과 함께 남깁니다. 다이제스트는 이전 다이제스트의 서명도 담아 사슬을 이룹니다.

aws cloudtrail validate-logs로 어느 파일이 수정·삭제됐는지 확인합니다. 버킷에는 S3 Object Lock(15장)이나 MFA Delete를 겁니다.

SQL로 조회하려면

CloudTrail Lake는 2026년 5월 31일부터 신규 고객을 받지 않습니다. 새로 시작한다면 S3의 트레일 로그를 Athena로 조회하는 구성이 일반적입니다.

CloudTrail은 행위를, Config는 상태를

CloudTrail이 "누가 보안 그룹 규칙을 바꿨나"에 답한다면, AWS Config는 "지난 화요일 오후 3시에 이 보안 그룹은 어떤 모양이었나"에 답합니다. 리소스가 바뀔 때마다 구성 항목을 남겨 시점별 상태와 관계를 보여 줍니다.

Config 규칙은 그 상태를 기준과 비교해 위반을 표시합니다. 변경이 생길 때나 주기적으로 평가합니다.

  1. 기록

    구성 기록기가 지정한 리소스 유형의 변경을 남깁니다.

  2. 평가

    예: s3-bucket-public-read-prohibited 규칙이 위반을 표시합니다.

  3. 교정

    SSM Automation 문서로 수동 또는 자동 교정을 실행합니다.

  4. 집계

    애그리게이터와 적합성 팩으로 여러 계정·리전을 한 화면에 모읍니다.

탐지 서비스는 각자 다른 원천을 본다

탐지 서비스는 각자 결과(finding)를 만들고, Security Hub가 한곳에 모아 우선순위를 매깁니다. 결과 이벤트를 EventBridge로 받아 격리 같은 대응을 자동화합니다.

GuardDuty는 켜기만 하면 로그를 읽는다

GuardDuty는 위협 탐지 서비스입니다. 활성화하면 CloudTrail 관리 이벤트, VPC 흐름 로그, DNS 로그를 내가 따로 켜지 않아도 AWS 내부 경로로 받아 분석합니다. 위협 정보(악성 IP·도메인)와 머신러닝으로 이상 행동을 찾습니다.

탐지 예: 탈취된 자격 증명을 다른 나라에서 사용, EC2가 암호화폐 채굴 풀과 통신, 루트 사용자의 이례적 API 호출.

6부

설정은 맞는데 운영에서 터지는 지점들

기본선 체크리스트, 암호화 지점 정리, 노출과 유출 대응, WAF 오탐과 캐시 사고를 차례로 봅니다.

원리 실무 체크리스트, 대응 절차, 실제 장애 사례를 다룹니다.

계정을 열면 첫날 깔아 둘 보안 기본선

  • 기록부터 켭니다. 조직 트레일(멀티 리전, 무결성 검증)과 Config 기록기를 로그 아카이브 계정으로 보냅니다.
  • 탐지를 켭니다. 모든 계정·리전에 GuardDuty와 Security Hub를 위임 관리자로 켜고, 높음 등급 결과를 알림 채널로 보냅니다.
  • 공개를 막습니다. 계정 수준 S3 퍼블릭 액세스 차단, EBS 기본 암호화, IMDSv2 필수(14장)를 기본값으로 겁니다.
  • 엣지를 세웁니다. 공개 엔드포인트는 CloudFront + WAF 관리형 규칙 뒤에 두고, 오리진은 VPC 오리진이나 헤더 검증으로 잠급니다.
  • 비밀을 뺍니다. 코드와 이미지의 비밀을 Secrets Manager로 옮기고, 장기 Access Key는 역할로 대체합니다(12장).

S3 버킷이 공개된 걸 알았을 때의 순서

  1. 즉시 차단

    버킷 퍼블릭 액세스 차단을 켜고 공개 정책과 ACL을 제거합니다.

  2. 노출 범위 확인

    Config 이력으로 언제부터 공개였는지, Macie로 무엇이 들어 있었는지 봅니다.

  3. 접근 기록 확인

    S3 데이터 이벤트나 서버 액세스 로그로 외부 GetObject를 찾습니다.

  4. 원인 제거

    누가 바꿨는지 CloudTrail PutBucketPolicy를 찾고 SCP로 재발을 막습니다.

  5. 통지와 기록

    개인정보가 있었다면 법적 통지 절차와 사후 분석을 진행합니다.

데이터 이벤트를 꺼 두었다면 3단계에서 누가 읽어 갔는지 알 수 없습니다. 그래서 민감 버킷은 평소에 데이터 이벤트를 켭니다.

정적 웹 호스팅을 위해 버킷을 공개하는 일 자체를 없애는 것이 근본 대책입니다. CloudFront와 OAC를 쓰면 공개할 필요가 없습니다.

키 유출은 대개 GuardDuty 알림으로 시작된다

GitHub에 올라간 Access Key는 몇 분 안에 자동화된 공격자가 가져갑니다. 흔한 첫 신호는 GuardDuty의 UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration이나 처음 보는 리전의 대량 RunInstances, 그리고 요금 알림입니다.

탐지 다음은 12장의 대응 절차입니다. 키를 비활성화하고, CloudTrail에서 그 accessKeyId로 필터해 공격자가 만든 사용자·역할·인스턴스·Lambda를 찾아 지웁니다.

공격자가 남긴 뒷문을 찾는다

새 IAM 사용자, 새 Access Key, 신뢰 정책에 외부 계정을 넣은 역할, 꺼진 트레일을 확인합니다. 키 하나 끄는 것으로 끝나지 않습니다.

사례: WAF를 켠 날 업로드와 결제가 막혔다

ALB 앞 웹 ACL에 Core rule set을 Block으로 바로 붙였습니다. 30분 뒤 이미지 업로드와 결제 콜백이 403으로 실패하기 시작했습니다.

WAF 로그의 terminatingRuleId는 SizeRestrictions_BODY였습니다. 8KB가 넘는 multipart 본문이 모두 막혔고, 결제사 콜백의 긴 서명 문자열은 다른 규칙에 걸렸습니다.

교훈: 새 규칙은 Count로 들어간다

관리형 규칙도 내 트래픽에서는 오탐이 납니다. 처음엔 Count로 붙여 실제 트래픽에서 무엇이 걸리는지 본 뒤 Block으로 바꿉니다.

오탐 튜닝은 관찰, 예외, 차단 순서다

  1. Count로 배포

    규칙 그룹 전체를 Count로 재정의해 붙입니다.

  2. 1~2주 관찰

    로그에서 규칙별 Count 일치를 경로, IP, UA로 집계합니다.

  3. 예외 설계

    오탐 규칙만 Count로 남기고 레이블 + scope-down 규칙으로 다시 막습니다.

  4. Block 전환

    나머지는 Block으로 바꾸고 BlockedRequests 알람을 겁니다.

예: SizeRestrictions_BODY는 Count로 두고, "이 레이블이 붙었고 경로가 /upload가 아니면 Block"인 규칙을 뒤에 추가합니다.

결제사 콜백처럼 신뢰하는 출발지는 IP 집합 Allow 규칙을 맨 위에 둡니다. 관리형 그룹 버전은 고정해 두고, 새 버전은 Count로 먼저 검증합니다.

사례: 로그인 사용자 페이지가 남에게 보였다

마이페이지 HTML을 기본 동작(*)으로 서빙했고, 기본 동작에는 CachingOptimized가 붙어 있었습니다. 오리진은 Cache-Control: private를 보냈지만 최소 TTL이 1초라 캐시되었고, 그 1초 사이 같은 URL을 요청한 다른 사용자에게 앞사람의 페이지가 나갔습니다.

쿠키를 캐시 키에 넣지 않았으니 엣지에게 두 요청은 같은 객체였습니다.

개인화 응답은 CachingDisabled

사용자별 경로는 명시적인 캐시 동작에 CachingDisabled를 붙입니다. "오리진이 private을 보내니 괜찮다"는 최소 TTL이 0일 때만 맞습니다.

적중률은 지표로 보고, 원인은 로그로 찾는다

기본 CloudWatch 지표(요청 수, 전송 바이트, 4xx·5xx 오류율)는 무료입니다. 캐시 적중률, 오리진 지연, 상태 코드별 오류율은 배포마다 추가 지표를 켜야 하고 지표당 월 요금이 붙습니다. 지표는 us-east-1 CloudWatch에 있습니다.

왜 미스가 났는지는 표준 로그에서 x-edge-result-type(Hit, Miss, RefreshHit, Error)과 x-edge-detailed-result-type으로 봅니다. 표준 로그 v2는 S3, CloudWatch Logs, Firehose로 보내고, 초 단위로 봐야 하면 유료 실시간 로그를 씁니다.

정적 자산 배포라면 적중률 90% 이상이 흔한 목표입니다. 낮다면 미스 요청의 URL을 모아 캐시 키에 들어간 쿼리나 헤더를 의심합니다.

KMS와 비밀이 장애 원인이 되는 순간들

  • KMS 스로틀링: 트래픽이 몰린 날 S3 SSE-KMS 읽기가 503과 지연으로 번집니다. 버킷 키를 켜고, 할당량 사용률 지표에 알람을 겁니다.
  • 교차 계정 복호화 실패: 다른 계정 역할에 IAM으로 허용해도 키 정책이 그 계정을 허용하지 않으면 AccessDenied입니다. 양쪽 모두 열어야 합니다.
  • 키 비활성화 사고: 정리 중 끈 키가 RDS 키였다면 DB가 접근 불가 상태가 됩니다. 키에 태그와 설명을 달고 삭제는 대기 기간 동안 사용 시도를 지켜봅니다.
  • 교체 직후 로그인 실패: ECS secrets나 External Secrets(10장)로 넣은 환경 변수는 시작 때 한 번만 읽힙니다. 단일 사용자 교체와 만나면 다음 배포까지 새 연결이 실패하므로, 교대 사용자 전략이나 SDK 재조회, 교체 이벤트 기반 재배포로 바꿉니다.

정리

  • CloudFront의 성능은 캐시 키가 정합니다. 키는 좁게 두고 오리진에 필요한 값은 요청 정책으로 따로 넘기며, 파일명 버전으로 무효화를 줄입니다.
  • 오리진은 엣지 뒤에 숨깁니다. S3는 OAC, ALB는 VPC 오리진으로 직접 접근을 없애야 WAF와 Shield가 의미를 가집니다.
  • WAF는 Count로 들어가 Block으로 바꿉니다. 규칙은 우선순위대로 평가되고, 관리형 규칙도 내 트래픽에서는 오탐이 납니다.
  • KMS는 키를 내주지 않고 대신 씁니다. 봉투 암호화로 큰 데이터를 다루고, 키 정책이 IAM보다 먼저 열려 있어야 합니다.
  • 막지 못한 것은 기록과 탐지로 잡습니다. CloudTrail은 행위, Config는 상태, GuardDuty 등은 이상을 보고 Security Hub가 모읍니다.

스스로 점검 (1)

  1. 오리진이 User-Agent별로 다른 응답을 주지 않는데 User-Agent를 캐시 키에 넣으면 어떻게 되나요?

    브라우저 종류·버전마다 같은 파일이 따로 캐시되어 적중률이 크게 떨어집니다. 오리진이 그 값을 참고만 한다면 오리진 요청 정책으로 넘기고 캐시 키에서는 뺍니다.

  2. OAC 버킷 정책에서 AWS:SourceArn 조건을 빼면 무엇이 위험한가요?

    Principal이 CloudFront 서비스 전체이므로 다른 사람이 만든 배포도 내 버킷을 오리진으로 읽을 수 있습니다. 조건으로 내 배포 ARN만 허용해야 합니다.

  3. ALB에 붙은 WAF의 IP 기준 rate 규칙이 CloudFront 뒤에서 정상 사용자를 대량 차단했습니다. 왜일까요?

    ALB가 보는 출발지 IP가 CloudFront 엣지 서버라 많은 사용자가 한 IP로 집계되었기 때문입니다. WAF를 CloudFront에 붙이거나 X-Forwarded-For를 집계 키로 씁니다.

  4. CloudFront에 붙일 인증서를 서울 리전 ACM에서 발급하면 왜 목록에 보이지 않나요?

    CloudFront는 us-east-1의 ACM 인증서만 쓸 수 있기 때문입니다. 같은 도메인으로 us-east-1에서 따로 발급해야 합니다.

  5. 오리진 그룹을 설정했는데 주문 생성 POST가 주 오리진 장애 때 실패했습니다. 왜일까요?

    오리진 장애 조치는 GET, HEAD, OPTIONS 요청에만 일어납니다. 쓰기 요청의 리전 장애 조치는 Route 53이나 Global Accelerator 수준에서 설계합니다.

스스로 점검 (2)

  1. KMS 자동 회전을 켜면 1년 전에 암호화한 데이터는 다시 암호화해야 하나요?

    아닙니다. KMS가 옛 키 재료를 보관하고 암호문에 맞는 재료로 자동 복호화합니다. 새로 암호화하는 데이터만 새 재료를 씁니다.

  2. IAM 정책에 kms:Decrypt를 허용했는데 AccessDenied가 납니다. 무엇을 먼저 보나요?

    키 정책입니다. 키 정책이 계정의 IAM 위임(계정 루트 주체 문장)이나 그 역할을 허용하지 않으면 IAM의 Allow는 효력이 없습니다.

  3. Secrets Manager로 DB 비밀번호를 단일 사용자 방식으로 교체한 직후 ECS 서비스가 DB 연결에 실패했습니다. 이유와 대책은?

    태스크 정의의 secrets로 시작 시 주입한 옛 비밀번호가 무효가 되었기 때문입니다. 교대 사용자 전략을 쓰거나, 앱이 SDK로 읽고 인증 실패 시 다시 읽게 하거나, 교체 후 재배포합니다.

  4. 누가 보안 그룹을 열었는지와, 지난주 그 보안 그룹의 규칙 모양은 각각 어디서 보나요?

    누가 바꿨는지는 CloudTrail의 AuthorizeSecurityGroupIngress 이벤트, 특정 시점의 모양은 AWS Config 구성 이력에서 봅니다.

  5. Shield Standard만 있어도 CloudFront를 앞에 두면 왜 DDoS에 더 강해지나요?

    공격 트래픽이 수백 개 엣지로 분산되어 각자 흡수되고, L7 공격은 엣지의 WAF가 거르며, 오리진은 공개 주소가 없어 직접 노려지지 않기 때문입니다.
