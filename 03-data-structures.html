Big-O는 데이터가 늘 때의 비용 증가율이다

Big-O 표기는 입력 크기 n이 커질 때 연산 횟수가 어떤 속도로 늘어나는지를 나타냅니다. 상수와 작은 항은 버리고 가장 빨리 자라는 항만 봅니다.

개발 환경의 데이터 1천 건에서는 모든 알고리즘이 빠릅니다. 문제는 운영 데이터가 100만 건이 될 때입니다. O(n²)은 데이터가 1천 배 늘면 비용이 100만 배 늡니다.

복잡도n = 100만일 때예
O(1)1해시 조회
O(log n)약 20균형 트리, 이분 탐색
O(n)100만풀 스캔
O(n log n)약 2천만좋은 정렬
O(n²)1조이중 반복문 비교

가끔 비싼 연산은 나눠 내면 싸다

동적 배열은 칸이 차면 두 배 크기의 배열을 새로 잡아 전부 복사합니다. 그 순간의 추가는 O(n)입니다.

하지만 n개를 넣는 동안 복사한 총량은 n + n/2 + n/4 + … < 2n입니다. 한 번에 평균 2칸 미만이므로 추가는 분할 상환 O(1)입니다.

두 배가 아니라 고정 10칸씩 늘리면 총 복사량이 O(n²)이 됩니다. 비율로 키우는 것이 핵심입니다.

배열은 위치로, 연결 리스트는 포인터로 찾는다

연산배열(동적 배열)연결 리스트
i번째 읽기O(1), 주소 계산O(n), 처음부터 따라감
끝에 추가분할 상환 O(1)O(1), 꼬리 포인터
중간 삽입/삭제O(n), 뒤쪽을 밀기위치를 알면 O(1)
메모리 배치연속, 캐시에 유리흩어짐, 노드마다 포인터

배열은 시작 주소 + i × 원소 크기로 바로 접근합니다. 연결 리스트는 각 노드가 다음 노드의 주소를 들고 있어 순서대로 따라가야 합니다. 그렇다면 중간 삽입이 잦으면 항상 연결 리스트가 나을까요? 실제로는 그렇지 않은 경우가 많습니다.

같은 O(n)이라도 캐시 지역성이 속도를 가른다

1장에서 본 것처럼 CPU는 메모리를 64바이트 캐시 라인 단위로 가져옵니다. 배열을 순회하면 한 번 가져온 라인에 다음 원소들이 함께 들어 있어 대부분 캐시에서 읽힙니다.

연결 리스트는 노드가 힙 곳곳에 흩어져 있어 노드마다 캐시 미스가 나기 쉽습니다. 중간 삽입을 하려 해도 그 위치를 찾는 순회가 먼저라서, 실측에서는 배열이 이기는 경우가 흔합니다.

스택과 큐는 꺼내는 순서에 대한 약속이다

스택은 마지막에 넣은 것을 먼저 꺼내고(LIFO), 큐는 먼저 넣은 것을 먼저 꺼냅니다(FIFO). 덱은 양쪽 끝 모두에서 넣고 뺄 수 있습니다.

세 가지 모두 배열 기반 원형 버퍼로 만들면 양 끝 연산이 O(1)이고 캐시에도 유리합니다. 스택 두 개로 큐를 만들 수도 있는데, 꺼낼 때 한쪽을 뒤집어 옮기는 비용이 분할 상환 O(1)입니다.

2부

찾기를 빠르게 만드는 구조

순회 없이 원하는 데이터에 닿는 방법은 크게 두 갈래입니다. 키를 주소로 계산하거나, 데이터를 정렬된 모양으로 유지하는 것입니다.

기초 원리 여기부터는 각 구조가 내부에서 어떻게 동작하고 왜 그렇게 설계됐는지 봅니다.

해시 테이블은 키를 배열 위치로 계산한다

해시 함수는 키를 정수로 바꾸고, 그 값을 배열 크기로 나눈 나머지가 저장 위치(버킷)가 됩니다. 계산 한 번으로 위치가 정해지니 평균 O(1)입니다.

좋은 해시 함수는 같은 키에 항상 같은 값을 내고, 값을 버킷 전체에 고르게 퍼뜨립니다. 그래도 버킷 수보다 키가 많으면 충돌은 반드시 일어납니다(비둘기집 원리).

충돌은 체인으로 묶거나 빈칸을 찾아 피한다

항목체이닝(Separate Chaining)개방 주소법(Open Addressing)
충돌 처리버킷마다 리스트로 매달기규칙에 따라 다른 빈칸 탐사
메모리노드마다 포인터 추가배열 하나, 캐시에 유리
꽉 찰수록체인이 길어지며 완만히 느려짐탐사가 급격히 길어짐
삭제노드만 떼면 됨표시(tombstone)가 필요
구현 예Java HashMap, Redis dictPython dict, Go map(1.24~)

개방 주소법은 같은 배열 안에서 다음 칸을 찾아가므로, 테이블이 꽉 찰수록 빈칸을 찾는 거리가 빠르게 늘어납니다. 그래서 두 방식 모두 "얼마나 찼는가"를 감시해야 합니다. Java HashMap이 체인을 트리로 바꾸는 최적화는 5장에서 다룹니다.

load factor가 넘으면 통째로 다시 배치한다

load factor는 저장된 키 수 ÷ 버킷 수입니다. 이 값이 높아지면 충돌이 늘어 O(1)이 무너지므로, 임계값(Java HashMap 기본 0.75, Python dict 약 2/3)을 넘으면 버킷 배열을 보통 두 배로 키웁니다.

버킷 수가 바뀌면 hash mod 버킷 수도 바뀌므로 모든 키를 새 위치로 옮기는 재해싱이 필요합니다. 동적 배열과 같은 논리로 분할 상환 O(1)이지만, 그 한 번은 O(n)입니다.

  1. 임계값 초과

    키 수가 버킷 수 × load factor를 넘습니다.

  2. 새 배열 할당

    보통 두 배 크기의 버킷 배열을 잡습니다.

  3. 전체 재배치

    모든 키의 위치를 다시 계산해 옮깁니다. 이 순간만 O(n)입니다.

저장할 개수를 미리 알면 초기 용량을 넉넉히 주어 재해싱을 아예 피할 수 있습니다.

이진 탐색 트리는 모양이 무너지면 리스트가 된다

해시는 범위 검색과 정렬 순회를 못 합니다. "10 이상 20 미만"을 찾으려면 데이터를 정렬된 모양으로 두어야 합니다. 이진 탐색 트리(BST)는 왼쪽에 작은 값, 오른쪽에 큰 값을 둬서 한 번 비교할 때마다 후보를 절반으로 줄입니다.

그런데 이미 정렬된 순서로 넣으면 한쪽으로만 자라 높이가 n인 편향 트리가 되고, 탐색이 O(n)으로 떨어집니다.

균형 트리는 회전으로 높이를 log n에 묶는다

균형 트리는 삽입과 삭제 때마다 규칙이 깨졌는지 확인하고, 노드를 회전해 높이를 O(log n)으로 유지합니다. 어떤 순서로 넣어도 탐색, 삽입, 삭제가 모두 O(log n)으로 보장됩니다.

항목AVL 트리Red-Black 트리
균형 규칙좌우 높이 차 1 이하색 규칙으로 최장 경로 ≤ 최단 × 2
탐색더 낮아서 조금 빠름약간 더 높음
삽입/삭제회전이 잦음회전이 적어 쓰기에 유리
서버에서읽기 위주 메모리 인덱스Java TreeMap, Linux epoll, Nginx 타이머

힙은 가장 급한 하나만 빠르게 꺼낸다

힙은 부모가 항상 자식보다 작은(최소 힙) 완전 이진 트리입니다. 전체 정렬은 하지 않고 맨 위만 최솟값임을 보장합니다. 완전 이진 트리라서 포인터 없이 배열에 담기고, i번 노드의 자식은 2i+1, 2i+2입니다.

꺼낼 때는 마지막 원소를 루트로 올린 뒤 아래로 내려 보내고, 넣을 때는 끝에 넣고 위로 올립니다. 둘 다 O(log n)입니다. 그래서 다음에 만료될 타이머를 찾는 우선순위 큐에 씁니다.

디스크에서는 넓고 얕은 트리가 이긴다

디스크는 바이트가 아니라 페이지(InnoDB 기본 16KB) 단위로 읽고, 한 번 읽는 비용이 메모리 접근보다 수천 배 큽니다. 이진 트리로 1억 건을 담으면 높이가 약 27이라 최대 27번 읽어야 합니다.

B-Tree는 노드 하나를 페이지 하나로 만들고 그 안에 키를 수백 개 넣습니다. 자식이 500개면 높이 3으로 1억 2500만 건에 닿습니다. 실제 인덱스 구조인 B+Tree는 4장에서 봅니다.

Skip List와 트라이는 특정 일에 특화된 구조다

Skip List는 정렬된 연결 리스트 위에 듬성듬성한 "급행 차선"을 여러 층 얹습니다. 노드마다 몇 층까지 올라갈지를 확률로 정하므로 회전 없이도 평균 O(log n) 탐색과 삽입이 됩니다. Redis Sorted Set은 Skip List와 해시 테이블을 함께 써서 점수 순 범위 조회와 멤버 조회를 모두 빠르게 합니다.

트라이는 문자열을 한 글자(또는 한 구간)씩 나눠 경로로 저장합니다. 탐색 비용이 데이터 개수가 아니라 키 길이에 비례하고, 공통 접두사를 공유합니다.

Gin 같은 웹 프레임워크의 URL 라우터가 공통 접두사를 압축한 radix tree를 쓰고, 라우터의 IP 최장 접두사 일치도 같은 원리입니다.

정렬은 최악의 경우와 안정성으로 고른다

정렬평균 / 최악안정 정렬특징
퀵 정렬n log n / n²아니오제자리, 실측 가장 빠른 편
병합 정렬n log n / n log n예추가 메모리 O(n)
힙 정렬n log n / n log n아니오제자리, 캐시에 불리
TimSortn log n / n log n예이미 정렬된 구간이면 O(n)

퀵 정렬은 피벗이 매번 최솟값이면 O(n²)이 되므로 무작위나 중앙값 피벗을 씁니다. 안정 정렬은 같은 값끼리 원래 순서를 지킵니다. 그래서 Java는 기본형 배열에 Dual-Pivot Quicksort를, 순서가 의미 있는 객체에 TimSort를 씁니다.

의존 관계는 그래프이고, 탐색은 DFS와 BFS다

그래프는 정점과 간선으로 관계를 나타냅니다. 간선이 적은 그래프가 대부분이라 정점마다 이웃 목록을 두는 인접 리스트(O(V+E) 공간)를 주로 쓰고, 연결 여부를 O(1)로 물어야 할 때만 인접 행렬(O(V²))을 씁니다.

DFS는 스택으로 끝까지 파고들어 순환을 찾기 좋고, BFS는 큐로 가까운 것부터 넓혀 가므로 가중치 없는 최단 경로를 줍니다.

문제를 쪼개는 세 가지 방식과 이분 탐색

분할 정복은 문제를 독립된 부분으로 나눠 풀고 합칩니다(병합 정렬). 동적 계획법(DP)은 부분 문제가 겹칠 때 답을 저장해 재사용합니다. 재귀 피보나치는 O(2ⁿ)이지만 메모해 두면 O(n)입니다. 그리디는 매 순간 최선만 고르며, 다익스트라처럼 그것이 전체 최적임이 증명될 때만 씁니다.

이분 탐색은 정렬된 배열의 가운데와 비교해 절반씩 버리는 O(log n) 탐색입니다. B-Tree 페이지 안의 키 찾기, git bisect가 같은 원리입니다.

가운데를 (lo + hi) / 2로 구하면 큰 배열에서 정수 오버플로가 납니다. lo + (hi - lo) / 2가 안전하며, JDK도 이 버그를 2006년에 고쳤습니다.

3부

운영에서 만나는 자료구조

교과서 구조를 조합해 캐시를 만들고, 실제 시스템이 그 구조를 어떻게 변형해 쓰는지, 어디서 장애가 나는지 봅니다.

원리 실무 LRU 캐시 구현, Redis와 InnoDB의 근사 LRU, 해시 테이블 장애 사례를 다룹니다.

LRU 캐시는 해시와 이중 연결 리스트의 조합이다

1장의 페이지 교체에서 본 LRU는 "가장 오래 안 쓴 것을 버린다"는 정책입니다. 구현하려면 조회, 사용 순서 갱신, 가장 오래된 항목 제거가 모두 O(1)이어야 합니다.

해시만으로는 순서를 모르고, 리스트만으로는 찾는 데 O(n)입니다. 그래서 해시가 노드 위치를, 이중 연결 리스트가 순서를 맡깁니다. 이전 포인터가 있어야 중간 노드를 O(1)에 떼어 낼 수 있습니다.

Java에서는 LinkedHashMap 하나로 LRU가 된다

class LruCache<K,V> extends LinkedHashMap<K,V> {
  private final int capacity;

  LruCache(int capacity) {
    super(16, 0.75f, true); // 접근 순서로 정렬
    this.capacity = capacity;
  }

  @Override
  protected boolean removeEldestEntry(
      Map.Entry<K, V> eldest) {
    return size() > capacity; // 오래된 것 제거
  }
}

LinkedHashMap은 해시 테이블의 각 항목을 이중 연결 리스트로도 엮어 둔 구조로, 앞 슬라이드의 그림 그대로입니다. 세 번째 생성자 인자 true가 순서를 "넣은 순"에서 "접근 순"으로 바꿉니다.

다만 스레드 안전하지 않습니다. 운영 코드의 로컬 캐시는 보통 Caffeine 같은 라이브러리를 씁니다.

실제 시스템은 정확한 LRU 대신 근사치를 쓴다

시스템방식이유
Redis키 몇 개를 무작위로 뽑아 가장 오래된 것 제거키마다 포인터 두 개는 메모리 낭비
InnoDB 버퍼 풀새 페이지를 리스트 중간(뒤 3/8 지점)에 삽입풀 스캔이 캐시를 쓸어내는 것 방지
CaffeineW-TinyLFU: 사용 빈도까지 반영한 번 쓰고 버리는 데이터 걸러내기

순수 LRU의 약점은 한 번 훑고 지나가는 대량 접근입니다. 배치 작업이 테이블을 한 번 읽기만 해도 자주 쓰던 페이지가 모두 밀려납니다. Redis는 maxmemory-samples(기본 5)로 근사 정확도를 조절합니다.

해시 테이블의 O(1)이 깨지는 두 순간

재해싱 정지. 수백만 키를 가진 테이블이 한 번에 재해싱하면 그동안 요청이 멈춥니다. 싱글 스레드인 Redis는 그래서 테이블 두 개를 두고, 요청을 처리할 때마다 버킷 몇 개씩 옮기는 점진적 재해싱을 합니다.

해시 충돌 공격. 해시 함수가 고정돼 있으면 공격자가 같은 버킷에 모이는 키를 대량으로 보내 O(n)을 강제할 수 있습니다.

외부 입력을 키로 쓸 때를 조심하세요

2011년 여러 언어의 웹 프레임워크가 POST 파라미터 몇 MB만으로 CPU를 독점당했습니다(HashDoS).

현재의 방어

Python, Redis 등은 프로세스마다 무작위 시드를 쓰는 SipHash를 씁니다. 요청 파라미터 개수 제한도 함께 겁니다.

정리

  • Big-O는 증가율이고, 캐시 지역성은 상수입니다. 둘 다 봐야 배열이 연결 리스트를 이기는 이유가 보입니다.
  • 해시 테이블은 평균 O(1)이지만 충돌과 재해싱을 관리해야 합니다. load factor가 그 기준입니다.
  • 정렬된 모양을 유지하면 범위 검색이 됩니다. 메모리에서는 균형 트리와 Skip List, 디스크에서는 넓고 얕은 B-Tree입니다.
  • 힙은 가장 급한 것만, 트라이는 접두사만 빠르게 합니다. 필요한 연산만 싸게 만드는 것이 구조 선택입니다.
  • LRU 캐시는 해시 + 이중 연결 리스트입니다. 실제 시스템은 메모리와 스캔 내성을 위해 근사치를 씁니다.

스스로 점검

  1. 동적 배열을 두 배가 아니라 10칸씩 키우면 n개 추가의 총비용은?

    복사량이 10 + 20 + 30 + … 으로 늘어 O(n²)이 됩니다. 비율로 키워야 분할 상환 O(1)이 됩니다.

  2. 개방 주소법 테이블에서 삭제할 때 칸을 그냥 비우면 어떤 문제가 생기나요?

    그 칸을 지나 탐사해 저장된 다른 키를 찾다가 빈칸에서 멈춰 버립니다. 그래서 삭제 표시를 남깁니다.

  3. 메모리 안의 정렬 맵에는 Red-Black 트리를, DB 인덱스에는 B-Tree 계열을 쓰는 이유는?

    메모리는 노드 접근이 싸서 이진 트리로 충분하지만, 디스크는 페이지 읽기 횟수가 비용입니다. 분기 수를 키워 높이를 줄여야 합니다.

  4. LRU를 단일 연결 리스트로 만들면 어느 연산이 느려지나요?

    중간 노드를 떼어 앞으로 옮길 때 이전 노드를 찾으려면 O(n) 순회가 필요합니다.

  5. 야간 배치가 큰 테이블을 풀 스캔한 뒤 아침 응답이 느려졌습니다. 순수 LRU라면 왜일까요?

    한 번만 읽힌 페이지가 자주 쓰던 페이지를 캐시에서 밀어냈기 때문입니다. InnoDB의 중간 삽입이 이를 막습니다.

다음으로 올라갈 층

넓고 얕은 트리, 해시, 연결 리스트로 만든 캐시가 한데 모여 돌아가는 곳이 데이터베이스입니다. 데이터를 표로 나누는 관계형 모델에서 출발해 B+Tree 인덱스와 버퍼 풀을 실제 구조로 따라갑니다.
