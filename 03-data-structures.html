1부

비용을 재는 법과 기본 구조

2장에서 요청이 네트워크를 건너 서버 프로세스에 도착했습니다. 이제 서버는 답을 만들려고 메모리의 데이터를 뒤집니다. 이 부에서는 데이터가 늘수록 왜 느려지는지를 재는 방법을 먼저 세우고, 데이터를 메모리에 놓는 가장 기본적인 두 방식인 배열과 연결 리스트, 그리고 그 위에 꺼내는 순서를 약속한 스택과 큐를 봅니다.

요청 하나에도 데이터를 여러 번 찾는다

이 장은 쇼핑몰의 주문 서버 하나를 예제로 씁니다. 사용자가 "내 주문 내역"을 누르면 서버는 오른쪽 표의 일을 순식간에 해치워야 합니다. 일마다 데이터를 다루는 방식, 즉 필요한 연산이 다릅니다.

자료구조는 데이터를 메모리에 어떤 모양으로 놓고 그 위에서 어떤 연산을 허용할지에 대한 약속입니다. 알고리즘은 그 데이터로 문제를 푸는 단계적 절차입니다. 같은 데이터라도 놓는 모양에 따라 어떤 연산이 싸고 어떤 연산이 비싼지가 정해집니다.

시간 대신 연산 횟수가 늘어나는 모양을 센다

// 주문 번호 배열에 중복이 있는가
boolean hasDuplicate(long[] ids) {
  int n = ids.length;
  for (int i = 0; i < n; i++)
    for (int j = i + 1; j < n; j++)
      if (ids[i] == ids[j]) return true;
  return false;
}

이 코드는 주문 하나를 나머지 전부와 비교하므로 비교 횟수가 n(n−1)/2입니다. 주문이 1천 건이면 약 50만 번이라 눈 깜짝할 새 끝나지만, 100만 건이면 약 5천억 번이라 수 분이 걸립니다.

실행 시간은 기계마다 달라서 비교 기준이 못 됩니다. 그래서 입력 크기 n이 커질 때 연산 횟수가 어떤 모양으로 늘어나는가를 봅니다. 이것을 나타내는 표기가 다음 슬라이드의 Big-O입니다.

Big-O는 가장 빨리 자라는 항만 남긴다

Big-O 표기는 연산 횟수에서 상수 배와 작은 항을 버리고 가장 빨리 자라는 항만 남깁니다. n(n−1)/2는 O(n²)입니다. n이 크면 n²이 나머지를 압도하기 때문입니다.

O(log n)은 "n을 반으로 몇 번 나누면 1이 되는가"입니다. 2²⁰이 약 100만이므로 100만 건에서 약 20입니다. 반씩 버리는 탐색이 이 모양입니다.

보통 최악의 경우를 말하지만, 이 장의 해시 테이블처럼 평균을 말할 때는 그렇게 밝힙니다.

배열은 주소 계산 한 번으로 i번째에 닿는다

배열은 같은 크기의 원소를 메모리에 빈틈없이 이어 놓은 구조입니다. 그래서 i번째 원소의 주소는 시작 주소 + i × 원소 크기로 곱셈 한 번에 나옵니다. 주문 번호(8바이트)가 1000번지에서 시작하면 3번째는 1024번지입니다. 읽기는 n과 무관한 O(1)입니다.

대가는 중간 삽입입니다. 빈틈이 없으니 1번 자리에 새 값을 넣으려면 그 뒤의 원소를 모두 한 칸씩 밀어야 해서 O(n)입니다.

꽉 찬 배열은 더 큰 배열로 옮겨 담는다

배열은 만들 때 크기가 정해집니다. 바로 뒤의 메모리를 다른 데이터가 쓰고 있을 수 있어 제자리에서 늘릴 수 없기 때문입니다. 주문이 몇 건 들어올지 모르는 서버에는 불편합니다.

동적 배열은 칸이 차면 더 큰 배열을 새로 잡아 원소를 전부 복사하고 옛 배열을 버립니다. 그 순간의 추가는 n개를 복사하므로 O(n)입니다. 그렇다면 추가는 늘 비쌀까요? 다음 슬라이드에서 계산해 봅니다.

가끔 비싼 복사는 나눠 내면 싸다

두 배씩 키우면 n개를 넣는 동안 복사량은 1 + 2 + 4 + … 로, 마지막 항이 n보다 작으니 합이 2n을 넘지 않습니다. 추가 한 번당 평균 복사는 2칸 미만, 즉 O(1)입니다.

이렇게 연산 하나가 아니라 긴 연속 연산 전체의 비용을 횟수로 나눠 본 평균을 분할 상환 비용이라 합니다. 다만 복사가 일어나는 그 한 번은 여전히 O(n)입니다.

핵심은 고정 칸 수가 아니라 비율로 키우는 것입니다. 개수를 미리 알면 new ArrayList<>(10000)처럼 초기 용량을 줘서 복사를 아예 없앱니다.

연결 리스트는 다음 원소의 주소를 들고 있다

배열의 끼워 넣기 비용을 없애려면 원소를 붙여 놓지 않으면 됩니다. 연결 리스트는 값과 다음 원소의 주소(포인터)를 묶은 노드를 메모리 아무 곳에나 두고 주소로 잇습니다. 첫 노드를 가리키는 head, 마지막 노드를 가리키는 tail만 따로 기억합니다.

끼워 넣기는 포인터 두 개를 바꾸면 끝나 O(1)입니다. 대신 i번째를 찾으려면 head부터 따라가야 해서 O(n)입니다. 이전 노드 주소까지 갖는 이중 연결 리스트는 4부의 캐시에서 다시 씁니다.

배열과 연결 리스트는 장단점이 정반대다

두 구조를 연산별로 놓고 보면 한쪽의 강점이 다른 쪽의 약점입니다. 표의 파란 칸이 각자 잘하는 일입니다.

표만 보면 중간 삽입이 잦은 일에는 연결 리스트가 나아 보입니다. 그런데 마지막 행의 "연속이냐 흩어졌냐"가 Big-O에 잡히지 않는 큰 차이를 만듭니다.

같은 O(n)이라도 캐시 지역성이 속도를 가른다

1장에서 봤듯 CPU는 메모리를 64바이트 캐시 라인 단위로 가져옵니다. 배열을 순회하면 한 번 가져온 라인에 다음 원소 여러 개가 들어 있어 대부분 캐시에서 읽힙니다.

연결 리스트의 노드는 메모리의 힙 영역(1장, 2부의 자료구조 힙과는 이름만 같습니다) 곳곳에 흩어져 노드마다 캐시 미스, 즉 캐시에 없어 약 100ns 걸리는 메인 메모리까지 가는 일이 나기 쉽습니다. Big-O는 연산 횟수만 세고 한 번의 비용은 세지 않습니다. 끼워 넣을 자리를 찾는 순회가 먼저라 실측에서는 배열이 이기는 경우가 흔합니다.

스택은 마지막에 넣은 것을 먼저 꺼낸다

배열과 연결 리스트는 아무 데나 읽고 쓸 수 있습니다. 반대로 꺼내는 자리를 한 곳으로 묶으면 연산이 단순해지고 모두 O(1)이 됩니다. 스택은 한쪽 끝에서만 넣고(push) 꺼내는(pop) 구조로, 마지막에 넣은 것이 먼저 나옵니다(LIFO, Last In First Out).

대표 예가 호출 스택입니다. 함수를 부를 때마다 지역 변수와 돌아갈 위치를 담은 칸을 쌓고, 함수가 끝나면 맨 위 칸을 걷어 냅니다. 1장에서 본 스레드마다의 스택이 바로 이것이라, 재귀가 너무 깊으면 스택이 넘쳐 StackOverflowError가 납니다.

큐는 원형 버퍼로 앞뒤를 O(1)로 만든다

큐는 뒤로 넣고 앞에서 꺼내 먼저 온 것이 먼저 나갑니다(FIFO). 배열로 만들면 앞에서 꺼낼 때마다 전체를 당겨야 해서 O(n)이 됩니다.

원형 버퍼는 원소를 움직이지 않고 앞(head)과 뒤(tail) 번호만 옮기며, 끝에 닿으면 (번호 + 1) mod 용량, 즉 용량으로 나눈 나머지를 써서 0번으로 돌아옵니다. 양쪽 모두 O(1)이고 메모리가 연속이라 캐시에도 유리합니다. 2장의 accept 큐, 1장 스레드 풀의 작업 큐가 이런 줄입니다.

덱은 양 끝을 모두 열어 둔 큐다

덱은 앞과 뒤 양쪽에서 넣고 꺼낼 수 있는 큐입니다. 원형 버퍼로 만들면 네 연산 모두 O(1)입니다.

Java의 병렬 작업 실행기 ForkJoinPool(parallelStream()이 쓰는 공용 스레드 풀이기도 합니다)은 덱으로 작업 훔치기를 합니다. 스레드마다 자기 덱을 두고 자기 작업은 한쪽 끝에서 넣고 뺍니다. 일이 떨어진 스레드는 남의 덱 반대쪽 끝에서 훔쳐 옵니다. 두 스레드가 서로 다른 끝을 만지니 다툼이 적습니다.

세 구조 모두 "어디서 꺼내는가"만 정했습니다. 특정 주문을 찾으려면 여전히 처음부터 훑어야 하고, 이것이 2부의 질문입니다.

2부

찾기를 빠르게 만드는 구조

1부의 구조에서 특정 주문 하나를 찾으려면 처음부터 훑어야 했습니다(O(n)). 순회 없이 찾는 길은 두 갈래입니다. 키를 계산해 배열 칸 번호를 바로 얻거나(1부 배열의 O(1) 접근을 빌립니다), 데이터를 정렬된 모양으로 유지해 비교할 때마다 후보를 절반씩 버리는 것입니다.

기초 원리 여기부터는 각 구조가 내부에서 어떻게 동작하고 왜 그렇게 설계됐는지 봅니다.

해시 테이블은 키를 배열 칸 번호로 바꾼다

로그인 확인은 user:42 같은 문자열 키로 세션을 찾는 일입니다. 배열은 정수 칸 번호로만 O(1)에 닿으니, 키를 정수로 바꿀 수 있으면 됩니다.

해시 함수는 키를 정수(해시값)로 바꾸는 함수입니다. 해시값을 배열 크기로 나눈 나머지(mod)가 칸 번호이고, 이 칸을 버킷이라 합니다. 해시 계산 한 번, 나눗셈 한 번이면 위치가 나오므로 평균 O(1)입니다. 키에서 위치를 계산하는 이 표를 해시 테이블이라 합니다.

충돌은 피할 수 없고 생각보다 일찍 온다

좋은 해시 함수는 세 가지를 지킵니다. 같은 키에는 늘 같은 값을 내고, 값을 버킷 전체에 고르게 퍼뜨리고, 계산이 빠릅니다. 그래도 서로 다른 키가 같은 버킷에 떨어지는 충돌은 막을 수 없습니다.

버킷이 8개인데 키가 9개면 적어도 한 칸에는 둘이 들어갑니다(비둘기집 원리). 더 놀라운 것은 칸이 남아돌 때도 충돌이 잦다는 점입니다. 생일이 365가지인데 23명만 모여도 생일이 겹치는 쌍이 있을 확률이 50%를 넘습니다(생일 문제).

그래서 해시 테이블 설계의 절반은 충돌을 어떻게 처리하느냐입니다. 방식은 두 가지로, 같은 칸에 줄줄이 엮는 체이닝과 배열 안의 다른 빈칸을 찾는 개방 주소법입니다.

버킷 365개에 넣은 키충돌이 하나라도 있을 확률
10개약 12%
23개약 51%
50개약 97%

체이닝은 같은 칸의 키를 리스트로 엮는다

체이닝은 버킷마다 1부의 연결 리스트를 매달아 같은 칸에 떨어진 키를 줄줄이 넣습니다. 앞 슬라이드의 user:42와 cart:9는 5번 칸의 리스트에 나란히 들어갑니다.

버킷 번호만으로는 어느 키인지 모르므로, 리스트를 따라가며 저장된 키와 찾는 키가 정말 같은지 하나씩 비교합니다. 그래서 비용은 해시 계산 + 그 칸의 리스트 길이입니다. 리스트가 짧게 유지되면 O(1)이고, 한 칸에 몰리면 O(n)까지 떨어집니다.

    넣을 때는 같은 키가 없으면 리스트에 붙이고, 지울 때는 노드를 떼어 냅니다.

개방 주소법은 배열 안에서 빈칸을 찾아간다

개방 주소법은 리스트 없이 배열 하나에 모든 키를 넣습니다. 가장 단순한 선형 탐사는 칸이 차 있으면 다음 칸, 그다음 칸으로 빈칸이 나올 때까지 갑니다. 찾을 때도 같은 길을 따라가다 키를 만나면 성공, 빈칸을 만나면 "없음"입니다.

그래서 지울 때 칸을 그냥 비우면 안 됩니다. 5번을 비우면 6번에 있는 cart:9를 찾다가 5번에서 멈춰 버립니다. 대신 삭제 표시를 남겨 찾기는 지나가고 넣기는 재사용하게 합니다.

두 방식은 메모리와 혼잡에 대한 태도가 다르다

앞의 두 슬라이드에서 본 동작을 나란히 놓으면 다음과 같습니다. 개방 주소법은 1부의 캐시 지역성을 얻는 대신, 테이블이 붐비면 급격히 느려집니다.

항목체이닝개방 주소법

메모리노드마다 포인터 추가배열 하나, 캐시에 유리

Redis는 데이터를 메모리에 두는 키-값 저장소로, 이 장에서 몇 번 더 나오고 8장에서 자세히 봅니다. Java HashMap은 한 버킷의 리스트가 너무 길어지면 트리로 바꾸는데, 그 구현은 5장에서 봅니다. 어느 쪽이든 "테이블이 얼마나 찼는가"를 감시해야 O(1)이 유지되고, 그 기준이 다음 슬라이드의 load factor입니다.

load factor가 O(1)이 버티는 한계다

load factor(α)는 저장된 키 수 ÷ 버킷 수, 즉 테이블이 찬 비율입니다. 체이닝에서는 리스트의 평균 길이가 곧 α입니다.

개방 주소법은 더 민감합니다. 해시가 이상적으로 고르다고 가정해도 빈칸을 찾는 평균 탐사 횟수가 약 1 ÷ (1 − α)라서, 반쯤 찼을 때 2번이던 것이 90% 찼을 때 10번이 됩니다.

그래서 구현마다 임계값을 넘으면 버킷 배열을 키웁니다. 체이닝인 Java HashMap은 0.75, 개방 주소법인 Python dict는 약 2/3로 더 일찍 키웁니다.

버킷 수가 바뀌면 모든 키가 이사한다

버킷 배열을 키울 때 옛 배열을 그대로 복사하면 안 됩니다. 칸 번호가 해시값 mod 버킷 수였으니 버킷 수가 바뀌면 칸 번호도 바뀝니다. 해시값 13은 버킷 8개에서 5번이지만 16개에서는 13번입니다.

그래서 모든 키의 위치를 다시 계산해 옮기는 재해싱이 필요합니다. 1부의 동적 배열과 같은 논리로 분할 상환 O(1)이지만, 그 한 번은 n개를 모두 옮기는 O(n)입니다. 키가 수백만 개면 이 한 번이 서버를 멈추게 하는데, 4부에서 Redis가 이를 어떻게 피하는지 봅니다.

  1. 임계값 초과

    키 수가 버킷 수 × load factor를 넘습니다.

  2. 새 배열 할당

    보통 두 배 크기의 버킷 배열을 잡습니다.

  3. 전체 재배치

    모든 키의 칸 번호를 다시 계산해 옮깁니다. 이 순간만 O(n)입니다.

넣을 개수를 미리 알면 초기 용량을 넉넉히 줘서 재해싱을 피합니다. Java 19부터는 HashMap.newHashMap(개수)가 load factor까지 계산해 줍니다.

해시가 못 하는 일은 정렬이 한다

"11월 1일부터 15일까지의 주문"처럼 값의 구간으로 골라내는 범위 검색은 해시로 할 수 없습니다. 해시는 일부러 키를 흩뿌리므로 가까운 날짜가 가까운 칸에 있지 않습니다. 최솟값이나 정렬 순회도 마찬가지입니다.

데이터를 정렬해 두면 이분 탐색이 됩니다. 남은 구간의 가운데와 비교해 절반을 버리기를 반복하니 8개는 최대 4번, 100만 개는 약 20번이면 끝납니다. 대가는 넣기입니다. 정렬을 유지하려면 1부의 배열처럼 뒤를 밀어야 해서 O(n)입니다.

이분 탐색은 가운데를 구할 때 넘친다

int find(long[] a, long key) {
  int lo = 0, hi = a.length - 1;
  while (lo <= hi) {     // 후보가 남아 있는 동안
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == key) return mid;
    if (a[mid] < key) lo = mid + 1; // 오른쪽
    else hi = mid - 1;            // 왼쪽
  }
  return -1;                 // 없음
}

lo와 hi는 아직 후보인 구간의 양 끝입니다. 가운데 값이 작으면 왼쪽 절반을, 크면 오른쪽 절반을 버리고, 구간이 비면 없는 것입니다.

가운데를 (lo + hi) / 2로 구하면 둘이 모두 10억을 넘을 때 합이 int 최댓값(약 21억)을 넘어 음수가 됩니다. 강조한 줄처럼 차이의 절반을 더하면 안전합니다. JDK도 이 버그를 2006년에야 고쳤습니다. 커밋 기록에서 버그가 처음 생긴 지점을 찾는 git bisect도 같은 원리입니다.

이진 탐색 트리는 넣기와 찾기를 함께 빠르게 한다

정렬된 배열의 넣기 문제를 풀려면 1부의 연결 리스트처럼 포인터로 이으면서도 절반씩 버릴 수 있어야 합니다. 그 모양이 트리입니다. 맨 위 노드를 루트, 아래로 이어진 노드를 자식, 자식이 없는 노드를 리프, 루트에서 가장 깊은 리프까지의 층 수를 높이라 합니다.

이진 탐색 트리(BST)는 자식이 둘 이하이고, 왼쪽 아래에는 작은 값, 오른쪽 아래에는 큰 값만 둡니다. 5를 찾으면 4에서 오른쪽, 6에서 왼쪽으로 가 3번 비교로 닿습니다. 넣기도 같은 길을 내려가 빈자리에 붙이면 되니 아무것도 밀지 않습니다.

넣는 순서가 나쁘면 트리가 한 줄이 된다

비용이 높이라면 높이가 얼마인지가 문제입니다. 고르게 퍼진 트리의 높이는 약 log₂ n이라 100만 건에서 20입니다.

그런데 1, 2, 3… 순서로 넣으면 매번 오른쪽 끝에만 붙어 높이가 n인 편향 트리가 되고, 사실상 연결 리스트라 탐색이 O(n)입니다. 주문 번호는 늘 증가하며 들어오므로 주문 서버에서는 바로 이 최악이 기본값입니다. 트리 모양을 스스로 고치는 장치가 필요합니다.

회전은 정렬 순서를 지키며 높이를 줄인다

그 장치가 회전입니다. 1, 2, 3이 오른쪽으로만 이어졌다면 가운데 2를 위로 끌어올리고 1을 그 왼쪽 자식으로 내립니다. 높이는 3에서 2가 됩니다.

회전 뒤에도 "왼쪽은 작고 오른쪽은 크다"는 규칙이 그대로입니다. 2보다 작고 1보다 큰 값들(그림의 B)은 2의 왼쪽에서 1의 오른쪽으로 옮겨 붙으므로 순서가 지켜집니다. 바뀌는 포인터는 몇 개뿐이라 회전 한 번은 O(1)입니다.

AVL과 Red-Black은 균형의 기준이 다르다

넣거나 지울 때마다 "기울었는가"를 확인하고 회전으로 고치는 트리를 균형 트리라 합니다. 어떤 순서로 넣어도 높이가 O(log n)이라 찾기, 넣기, 지우기가 모두 O(log n)입니다. 대표적인 두 방식은 기울기의 기준이 다릅니다. AVL 트리는 모든 노드에서 좌우 높이 차를 1 이하로 엄격히 지킵니다. Red-Black 트리는 노드에 빨강, 검정 색을 칠하고 "빨강이 연달아 오지 않는다", "루트에서 어느 리프로 가든 검정 노드 수가 같다"는 규칙을 지킵니다. 그러면 가장 긴 경로가 가장 짧은 경로의 두 배를 넘지 못합니다.

항목AVL 트리Red-Black 트리
균형 기준좌우 높이 차 1 이하최장 경로 ≤ 최단 경로 × 2
찾기더 낮아서 조금 빠름약간 더 높음
넣기/지우기회전이 잦음회전이 적어 쓰기에 유리
쓰이는 곳읽기 위주 메모리 색인Java TreeMap, Linux epoll, Nginx 타이머

TreeMap은 키를 정렬된 순서로 유지하는 Java의 맵입니다. epoll은 1장에서 본, 감시할 소켓을 커널에 등록해 두는 장치로 그 목록을 Red-Black 트리로 관리하고, Nginx는 타이머를 만료 시각 순서의 Red-Black 트리에 둡니다.

힙은 가장 급한 하나만 맨 위에 둔다

쿠폰 만료를 처리하려면 수만 개의 타이머 중 가장 먼저 만료될 것만 계속 꺼내면 됩니다. 균형 트리는 전체를 정렬하느라 필요 이상으로 일합니다.

힙은 "부모가 자식보다 작다"만 지키는 트리라 맨 위가 늘 최솟값입니다(최소 힙). 형제끼리는 순서가 없습니다. 층을 왼쪽부터 빈틈없이 채우는 완전 이진 트리라서 포인터 없이 배열에 담기고, i번 노드의 자식은 2i+1, 2i+2번입니다. 이렇게 "우선순위가 가장 높은 것부터 꺼내는 큐"를 우선순위 큐라 하고, 힙이 그 표준 구현입니다.

넣을 때는 올리고 꺼낼 때는 내린다

0을 넣을 때 (앞 그림의 힙에서)

  1. 맨 끝에 붙이기

    배열 7번 칸에 0을 둡니다. 모양은 완전 이진 트리 그대로입니다.

  2. 부모와 비교해 올리기

    부모 7(3번 칸)보다 작으므로 자리를 바꿉니다. 다음 부모 3과도 바꿉니다.

  3. 루트 도착

    루트 1보다도 작아 맨 위로 갑니다. 교환은 높이만큼, 즉 O(log n)입니다.

최솟값 1을 꺼낼 때

  1. 루트를 빼고 끝을 올리기

    1을 꺼내고 마지막 칸의 9를 루트 자리로 옮깁니다.

  2. 더 작은 자식과 바꾸기

    자식 3과 2 중 작은 2와 바꿉니다. 큰 쪽과 바꾸면 부모가 자식보다 커집니다.

  3. 제자리 찾기

    다시 자식 5와 비교해 바꾸면 끝입니다. 역시 O(log n)입니다.

타이머와 예약 작업은 힙 위에서 돈다

힙이 주는 것은 정확히 두 가지입니다. 최솟값 확인은 O(1), 넣기와 꺼내기는 O(log n)입니다. 대신 특정 원소를 찾는 일은 형제 사이에 순서가 없어 O(n)입니다. 이 성질이 맞아떨어지는 곳이 타이머입니다.

Java의 PriorityQueue는 앞의 그림 그대로 배열 위의 힙입니다. "30분 뒤 결제 대기 주문 취소"처럼 예약 작업을 돌리는 ScheduledThreadPoolExecutor는 작업을 실행 시각 순서의 힙에 넣고, 작업 스레드는 루트 작업의 시각까지만 잠들었다가 깨어나 꺼냅니다.

사용자가 쿠폰을 먼저 써서 타이머를 취소하면 그 작업을 힙 한가운데서 지워야 합니다. 이 실행기는 작업마다 자기가 배열의 몇 번 칸에 있는지를 기록해 두어, 찾는 O(n)을 건너뛰고 그 자리에서 올리기나 내리기만 해 O(log n)에 지웁니다.

"100만 개 상품 중 많이 팔린 10개"를 고를 때도 힙을 씁니다. 크기 10인 최소 힙을 두고, 루트(지금까지의 10위)보다 큰 값만 루트와 바꿔 넣으면 전체를 정렬하는 O(n log n) 대신 O(n log 10)에 끝납니다.

디스크에서는 넓고 얕은 트리가 이긴다

주문이 메모리에 다 들어가지 않으면 디스크에 둡니다. 1장의 표처럼 메모리 접근은 약 100ns, SSD 읽기는 수십~100µs라 천 배 가까이 느립니다. 디스크는 정해진 크기의 블록인 페이지 단위로 읽는데, MySQL의 저장 엔진 InnoDB(4장)는 16KB입니다.

이진 트리로 1억 건을 담으면 높이가 약 27이라 찾기 한 번에 페이지를 27번 읽습니다. B-Tree는 노드 하나를 페이지 하나로 만들고 키를 수백 개 넣습니다. 한 노드에서 500갈래로 나뉘면 3층 만에 1억 2500만 건에 닿습니다.

B-Tree는 꽉 찬 노드를 둘로 쪼개며 자란다

B-Tree 노드 안의 키는 정렬되어 있고, 키 사이사이에 "이 두 키 사이의 값은 이 자식에"라는 포인터가 있습니다. 찾기는 노드 안에서 이분 탐색(메모리라 쌉니다)으로 갈 자식을 고르고 한 층 내려가는 것을 반복합니다. 디스크 읽기는 층마다 한 번입니다.

넣기는 리프에 정렬 순서대로 넣고, 리프가 넘치면 반으로 쪼개 가운데 키를 부모로 올립니다. 루트까지 넘치면 새 루트가 생겨 트리가 위로 자라므로 모든 리프의 깊이가 늘 같습니다. 회전 없이 균형이 유지됩니다. DB 인덱스가 실제로 쓰는 변형인 B+Tree는 4장에서 봅니다.

Skip List는 정렬된 리스트에 급행 차선을 얹는다

메모리 안에서 정렬을 유지하는 다른 길도 있습니다. 정렬된 연결 리스트는 넣기는 쉽지만 찾기가 O(n)입니다. Skip List는 그 위에 듬성듬성한 층을 더 얹습니다. 새 노드는 동전을 던져 앞면이 나오는 동안 한 층씩 더 올라가므로, 위층으로 갈수록 노드가 절반씩 줄어듭니다.

찾기는 맨 위층 왼쪽에서 시작해, 다음 노드가 찾는 값보다 작으면 오른쪽으로, 크면 한 층 내려갑니다. 평균 O(log n)이고, 회전 없이 확률만으로 균형이 맞습니다.

순위표는 정렬 구조와 해시를 함께 쓴다

인기 상품 순위에는 앞에서 소개한 Redis를 흔히 씁니다. 그중 Sorted Set은 멤버마다 점수를 붙여 점수 순서를 유지하는 자료형입니다.

3부

줄 세우고, 따라가고, 쪼개기

2부는 데이터를 어떤 모양으로 둘지였습니다. 3부는 그 위에서 일하는 절차입니다. 이분 탐색과 B-Tree가 전제한 "정렬된 상태"를 만드는 정렬, 1부의 스택과 큐를 다시 꺼내 쓰는 그래프 탐색, 그리고 큰 문제를 작은 문제로 쪼개는 세 가지 사고방식을 봅니다.

퀵 정렬은 피벗을 기준으로 두 편을 가른다

값을 서로 비교만 해서 정렬하면 O(n log n)보다 빠를 수 없습니다. n개를 늘어놓는 경우의 수 n!가지 중 정답 하나를, 비교 한 번에 후보를 절반씩 줄여 고르려면 log₂(n!) ≈ n log n번이 필요하기 때문입니다.

퀵 정렬은 기준값(피벗) 하나를 골라 작은 값은 왼쪽, 큰 값은 오른쪽으로 자리를 바꿔 가르고, 양쪽에 같은 일을 반복합니다. 매번 반씩 갈리면 층이 log n개, 층마다 n번 비교라 O(n log n)입니다. 그러나 피벗이 늘 최솟값이면(이미 정렬된 배열에서 첫 원소를 고를 때) 층이 n개가 되어 O(n²)입니다. 그래서 피벗을 무작위나 세 값의 중앙값으로 고릅니다.

병합 정렬은 반으로 나눈 뒤 합치며 정렬한다

병합 정렬은 배열을 길이 1이 될 때까지 반으로 나눈 뒤, 정렬된 두 묶음을 하나로 합치기를 반복합니다. 합치기는 두 묶음의 맨 앞끼리만 비교하면 되므로 O(n)이고, 층이 log n개라 피벗 운과 상관없이 항상 O(n log n)입니다. 대신 합친 결과를 담을 추가 배열이 O(n)만큼 필요합니다.

힙 정렬은 2부의 힙을 만든 뒤 최솟값을 n번 꺼냅니다. 최악에도 O(n log n)이고 추가 메모리가 없지만, i번에서 2i+1번으로 멀리 뛰며 읽어 1부의 캐시 지역성이 나빠 실측에서는 느린 편입니다.

[2, 5, 8]과 [1, 3, 9] 합치기

  1. 앞끼리 비교

    2와 1 중 작은 1을 결과에 씁니다. 오른쪽 묶음의 손가락이 3으로 갑니다.

  2. 반복

    2와 3 → 2, 5와 3 → 3, 5와 9 → 5, 8과 9 → 8을 차례로 씁니다.

  3. 남은 것 붙이기

    왼쪽이 비었으니 9를 그대로 붙입니다. 결과는 [1, 2, 3, 5, 8, 9]입니다.

안정 정렬은 같은 값의 원래 순서를 지킨다

주문 목록이 이미 주문 시각순인데 가격순으로 다시 정렬한다고 합시다. 같은 가격의 주문끼리 시각순이 유지되면 안정 정렬입니다. 병합 정렬은 합칠 때 같은 값이면 왼쪽 것을 먼저 쓰므로 안정적이고, 멀리 떨어진 원소를 맞바꾸는 퀵 정렬과 힙 정렬은 아닙니다. 실제 데이터에는 이미 정렬된 구간이 많다는 점을 노린 TimSort는 그런 구간(run)을 찾아 병합 정렬로 합치므로 안정적이고, 다 정렬된 입력이면 O(n)에 끝납니다.

정렬평균 / 최악안정특징
퀵 정렬n log n / n²아니오제자리, 실측 가장 빠른 편
병합 정렬n log n / n log n예추가 메모리 O(n)
힙 정렬n log n / n log n아니오제자리, 캐시에 불리
TimSortn log n / n log n예정렬된 구간이 많으면 O(n)에 가까움

Java는 int 같은 기본형 배열에는 피벗 두 개로 세 구간을 가르는 Dual-Pivot Quicksort를, 객체 정렬에는 TimSort를 씁니다. 같은 값의 int 둘은 구별할 수 없어 안정성이 의미가 없기 때문입니다.

그래프는 정점과 간선으로 관계를 담는다

주문 서버는 혼자 일하지 않습니다. 주문은 결제와 재고 서비스를 부르고, 둘은 다시 알림 서비스를 부릅니다. 이런 관계를 담는 구조가 그래프로, 대상을 정점(V), 관계를 간선(E)이라 합니다. 간선에 방향이 있으면 방향 그래프, 거리 같은 값이 붙으면 가중치 그래프입니다.

정점마다 이웃 목록을 두는 인접 리스트는 공간이 O(V + E)입니다. V × V 표에 연결 여부를 적는 인접 행렬은 연결 확인이 O(1)이지만 공간이 O(V²)입니다. 회원 100만 명의 친구 관계를 행렬로 두면 1조 칸이라, 간선이 드문 대부분의 그래프는 리스트로 둡니다.

DFS는 스택으로 깊게, BFS는 큐로 넓게 간다

그래프를 훑을 때는 간선이 고리를 이룰 수 있으므로 방문한 정점을 해시 집합(값 없이 키만 담은 해시 테이블)에 적어 두고 다시 가지 않습니다. 어디를 먼저 가느냐는 1부의 두 구조가 정합니다.

깊이 우선 탐색(DFS)은 스택에서 꺼내 한 길을 끝까지 파고듭니다. 재귀 호출로 쓰면 호출 스택이 그 역할을 합니다. 지금 파고드는 길 위의 정점을 다시 만나면 순환이 있다는 뜻입니다. 너비 우선 탐색(BFS)은 큐에서 꺼내 가까운 정점부터 넓혀 가므로, 간선 수 기준 최단 경로를 줍니다. 둘 다 O(V + E)입니다.

겹치는 부분 문제는 답을 적어 두고 다시 쓴다

// 그대로 재귀: fib(n-2)를 두 번씩 다시 푼다
long slow(int n) {
  return n < 2 ? n : slow(n - 1) + slow(n - 2);
}

// 메모: 한 번 푼 답은 배열에 적어 둔다
long[] memo = new long[91];
long fast(int n) {
  if (n < 2) return n;
  if (memo[n] != 0) return memo[n];
  return memo[n] = fast(n - 1) + fast(n - 2);
}

큰 문제를 작게 쪼개는 방식은 쪼갠 조각이 겹치느냐로 갈립니다. 병합 정렬의 두 절반은 서로 겹치지 않아 각자 풀고 합치면 됩니다. 이것이 분할 정복입니다.

피보나치는 다릅니다. fib(50)은 fib(49)와 fib(48)을 부르고, fib(49)도 fib(48)을 부릅니다. 같은 계산이 기하급수로 반복되어 O(2ⁿ)입니다. 강조한 줄처럼 답을 적어 두고 재사용하면 각 값을 한 번씩만 풀어 O(n)입니다. 이것이 동적 계획법(DP)입니다.

그리디는 증명이 있을 때만 믿는다

그리디(탐욕) 알고리즘은 매 순간 가장 좋아 보이는 선택을 하고 되돌아보지 않습니다. 빠르고 단순하지만, 순간의 최선이 전체의 최선이라는 보장이 있을 때만 맞습니다.

거스름돈이 좋은 예입니다. 한국 동전 500, 100, 50, 10원으로 880원을 줄 때 큰 동전부터 채우면 500 + 100×3 + 50 + 10×3, 8개로 최소입니다. 큰 동전이 늘 작은 동전의 배수라서 큰 것을 쓰는 선택이 손해가 되지 않기 때문입니다.

그런데 동전이 500, 400, 100원이고 800원을 줘야 하면 그리디는 500 + 100×3으로 4개를 내지만, 정답은 400×2의 2개입니다. 이때는 DP로 풉니다. "x원을 주는 최소 개수 = 각 동전 c에 대해 (x − c원의 최소 개수 + 1) 중 최솟값"을 1원부터 800원까지 표에 채우면 됩니다.

증명된 그리디의 대표가 다익스트라 최단 경로입니다. 아직 확정하지 않은 정점 중 지금까지 거리가 가장 짧은 것을 확정하고 이웃의 거리를 고치기를 반복합니다. "가장 짧은 것 꺼내기"에 2부의 힙을 씁니다. 간선 가중치가 음수가 아니면 정답이 보장되어, 라우터들이 서로 링크 정보를 나눠 각자 최단 경로를 계산하는 OSPF 같은 라우팅 프로토콜이 이 알고리즘을 씁니다.

4부

운영에서 만나는 자료구조

이제 부품을 조합합니다. 2부의 해시와 1부의 이중 연결 리스트를 엮으면 캐시가 됩니다. 그리고 실제 시스템이 왜 교과서 구조를 그대로 쓰지 않는지, 평균 O(1)이라던 해시 테이블이 운영에서 언제 깨지는지 봅니다.

원리 실무 LRU 캐시 구현, Redis와 InnoDB의 근사 LRU, 해시 테이블 장애 사례를 다룹니다.

LRU 캐시는 해시와 이중 연결 리스트의 조합이다

상품 정보를 매번 DB에서 읽지 않으려고 메모리에 캐시를 둡니다. 공간이 차면 무엇을 버릴지는 1장의 페이지 교체에서 본 LRU, 즉 "가장 오래 안 쓴 것부터 버린다"로 정합니다. 그러려면 찾기, 방금 쓴 것을 맨 앞으로 옮기기, 맨 뒤 버리기가 모두 O(1)이어야 합니다.

해시만으로는 순서를 모르고, 리스트만으로는 찾는 데 O(n)입니다. 그래서 해시가 노드 위치를, 이중 연결 리스트가 사용 순서를 맡습니다. 이전 포인터가 있어야 중간 노드를 O(1)에 떼어 낼 수 있습니다.

get과 put은 포인터 몇 개만 바꾼다

용량 3인 캐시에 상품 A, B, C를 차례로 넣으면 리스트는 앞에서부터 C, B, A입니다. 맨 앞이 가장 최근, 맨 뒤가 가장 오래된 항목입니다.

오른쪽 단계를 따라가면 어떤 연산도 리스트를 훑지 않습니다. 해시가 노드를 바로 가리키고, 노드를 떼고 붙이는 일은 앞뒤 노드의 포인터 몇 개를 고치는 것뿐입니다. 단일 연결 리스트라면 뗄 노드의 앞 노드를 찾으려고 처음부터 훑어야 해서 O(n)이 됩니다.

  1. get(A)

    해시로 노드 A를 찾고, 앞뒤를 서로 이어 A를 뗀 뒤 맨 앞에 붙입니다. 순서: A, C, B

  2. put(D): 용량 초과 확인

    3개가 차 있으니 하나를 버려야 합니다.

  3. 맨 뒤 제거

    tail 쪽 B를 리스트에서 떼고 해시에서도 키 B를 지웁니다.

  4. 새 노드 추가

    D를 맨 앞에 붙이고 해시에 등록합니다. 순서: D, A, C

Java에서는 LinkedHashMap 하나로 LRU가 된다

class LruCache<K,V> extends LinkedHashMap<K,V> {
  private final int capacity;

  LruCache(int capacity) {
    super(16, 0.75f, true); // 접근 순서
    this.capacity = capacity;
  }

  @Override
  protected boolean removeEldestEntry(
      Map.Entry<K, V> eldest) {
    return size() > capacity; // 넘치면 제거
  }
}

LinkedHashMap은 해시 테이블의 항목을 이중 연결 리스트로도 엮어 둔 클래스로, 앞의 그림 그대로입니다. 생성자의 16과 0.75f는 2부의 초기 버킷 수와 load factor이고, true가 순서를 "넣은 순"에서 "접근 순"으로 바꿉니다.

removeEldestEntry는 put이 끝날 때마다 불리고, true를 돌려주면 가장 오래된 항목을 지웁니다. 접근 순 모드에서는 get도 리스트를 고치는 쓰기라서, 여러 스레드가 동시에 쓰면 1장의 경쟁 상태로 리스트가 깨집니다. 운영의 로컬 캐시에는 동시성을 처리한 Caffeine 같은 라이브러리를 씁니다.

정확한 LRU는 메모리와 대량 스캔에 약하다

지금까지의 LRU는 교과서대로 정확합니다. 하지만 큰 시스템은 거의 이렇게 만들지 않습니다. 이유는 두 가지입니다.

첫째는 메모리와 쓰기 비용입니다. 키마다 이전·다음 포인터 두 개, 16바이트가 붙습니다. 키가 1억 개면 포인터만 1.6GB입니다. 게다가 읽을 때마다 노드를 맨 앞으로 옮기므로 모든 읽기가 리스트 쓰기가 되고, 여러 스레드가 그 맨 앞을 두고 다툽니다.

둘째는 한 번 훑고 지나가는 대량 접근입니다. 야간 배치가 주문 테이블 전체를 처음부터 끝까지 한 번 읽으면(풀 스캔) 그 페이지들이 모두 "가장 최근"이 되어, 낮 동안 자주 쓰던 페이지를 전부 밀어냅니다. 아침에 캐시가 텅 빈 것처럼 느려집니다.

LRU는 "얼마나 최근에"만 보고 "얼마나 자주"는 보지 않기 때문입니다. 사용 횟수를 기준으로 버리는 방식을 LFU라 합니다. 실제 시스템은 다음 슬라이드처럼 최근성과 빈도를 섞거나 정확도를 조금 버려 이 두 약점을 피합니다.

실제 시스템은 LRU를 근사하거나 고쳐 쓴다

Redis는 리스트 없이 키마다 마지막 접근 시각만 적어 두고, 메모리가 차면 키 몇 개를 무작위로 뽑아 그중 가장 오래된 것을 버립니다. 뽑는 개수 maxmemory-samples(기본 5)를 늘리면 정확한 LRU에 가까워지고 CPU를 더 씁니다. InnoDB의 버퍼 풀(디스크 페이지를 메모리에 올려 두는 캐시, 4장)은 리스트의 뒤쪽 3/8을 "오래된 구역"으로 두고 새 페이지를 그 앞머리에 넣습니다. 1초(innodb_old_blocks_time 기본 1000ms)가 지난 뒤 다시 읽혀야 앞쪽으로 승격되므로, 한 번 훑고 지나간 페이지는 앞쪽을 건드리지 못하고 빠집니다.

InnoDB 버퍼 풀새 페이지를 리스트 중간에 삽입풀 스캔이 캐시를 쓸어내는 것
CaffeineW-TinyLFU: 빈도를 함께 반영한 번 쓰고 버리는 데이터

W-TinyLFU는 새 항목을 작은 LRU 구역에 먼저 받고, 본 구역에 들어갈 때 쫓겨날 항목보다 최근 사용 빈도가 높은지 비교해 통과시킵니다.

Redis는 재해싱을 잘게 나눠 한다

2부에서 재해싱 한 번은 O(n)이라 했습니다. Redis는 한 스레드가 이벤트 루프(1장)로 모든 요청을 차례로 처리하므로, 키 수천만 개를 한 번에 옮기면 그동안 모든 클라이언트가 멈춥니다.

그래서 Redis는 점진적 재해싱을 합니다. 옛 테이블과 새 테이블을 함께 두고, 키를 건드리는 요청이 올 때마다 버킷 몇 개씩 옮깁니다. 대가는 옮기는 동안 테이블 두 개분의 메모리입니다. Redis에 허용한 메모리 상한(maxmemory) 가까이에서 재해싱이 시작되면 순간 메모리가 튈 수 있습니다.

  1. 두 테이블 준비

    두 배 크기의 새 테이블을 잡고 "몇 번 버킷까지 옮겼나" 번호를 0으로 둡니다.

  2. 요청마다 조금씩

    조회·쓰기가 올 때마다 옛 테이블의 버킷을 하나씩 새 테이블로 옮깁니다.

  3. 두 곳을 모두 본다

    찾기는 두 테이블을 모두 보고, 새 키는 새 테이블에만 넣습니다.

  4. 한가할 때 몰아서

    주기 작업이 1ms 정도씩 더 옮기고, 끝나면 옛 테이블을 버립니다.

외부 입력이 키가 되면 충돌을 공격당한다

웹 프레임워크는 요청 파라미터를 해시 테이블에 담습니다. 해시 함수가 고정되어 있고 공개되어 있으면, 공격자는 모두 같은 버킷에 떨어지는 키 수만 개를 미리 계산해 보낼 수 있습니다. 그러면 넣을 때마다 2부의 체인을 끝까지 따라가 비교하므로 n개를 넣는 데 O(n²)이 듭니다.

방어의 핵심은 공격자가 버킷을 예측하지 못하게 하는 것입니다. 프로세스가 시작될 때 무작위 비밀값(시드)을 정하고 그것을 섞어 계산하는 해시 함수를 쓰면, 같은 키라도 서버마다 버킷이 달라집니다. SipHash가 이런 용도로 만든 해시 함수입니다.

몇 MB짜리 POST 하나로 CPU가 멈췄다

2011년 말 공개된 HashDoS 공격으로 여러 언어의 웹 프레임워크가 요청 하나에 CPU 코어를 길게는 몇 시간까지 빼앗겼습니다(oCERT-2011-003 권고문).

지금의 방어는 여러 겹이다

Python과 Redis는 시드를 섞는 SipHash를 쓰고, 서버는 파라미터 개수를 제한합니다. Java HashMap은 긴 체인을 트리로 바꿔 최악을 O(log n)으로 묶습니다(5장).

자료구조는 가장 잦은 연산으로 고른다

장 첫머리의 주문 서버로 돌아가면, 일마다 가장 자주 하는 연산을 싸게 만드는 구조를 골랐다는 것이 보입니다. 대가는 그 구조가 못 하는 연산입니다.

정리

  • Big-O는 증가율이고, 캐시 지역성은 한 번의 비용입니다. 둘 다 봐야 배열이 연결 리스트를 자주 이기는 이유가 보입니다.
  • 가끔 비싼 연산은 비율로 키워 나눠 냅니다. 동적 배열의 복사와 해시 테이블의 재해싱이 모두 분할 상환 O(1)입니다.
  • 해시 테이블은 평균 O(1)이지만 충돌과 load factor를 관리해야 합니다. 운영에서는 재해싱 정지와 충돌 공격이 그 빈틈입니다.
  • 정렬된 모양을 유지하면 범위 검색이 됩니다. 메모리에서는 균형 트리와 Skip List, 디스크에서는 넓고 얕은 B-Tree입니다.
  • 힙은 가장 급한 것만, 트라이는 접두사만 빠르게 합니다. 필요한 연산만 싸게 만드는 것이 구조 선택입니다.
  • LRU 캐시는 해시 + 이중 연결 리스트입니다. 실제 시스템은 메모리와 스캔 내성을 위해 근사치를 씁니다.

스스로 점검 (1)

  1. 동적 배열을 두 배가 아니라 10칸씩 키우면 n개 추가의 총비용은?

    복사량이 10 + 20 + 30 + … 으로 늘어 O(n²)이 됩니다. 비율로 키워야 분할 상환 O(1)이 됩니다.

  2. 중간 삽입이 잦은 목록인데도 연결 리스트보다 배열이 빠른 경우가 많은 이유는?

    삽입할 자리를 찾는 순회가 먼저 필요하고, 그 순회에서 연결 리스트는 노드마다 캐시 미스가 납니다. 배열은 연속된 메모리라 원소 밀기조차 캐시 안에서 빠르게 끝납니다.

  3. 개방 주소법 테이블에서 삭제할 때 칸을 그냥 비우면 어떤 문제가 생기나요?

    그 칸을 지나 탐사해 저장된 다른 키를 찾다가 빈칸에서 "없음"으로 멈춰 버립니다. 그래서 삭제 표시를 남깁니다.

  4. 해시 테이블을 두 배로 키울 때 옛 배열을 그대로 복사하면 안 되는 이유는?

    칸 번호가 해시값 mod 버킷 수라서 버킷 수가 바뀌면 칸 번호도 바뀝니다. 그대로 두면 키를 새 규칙으로 계산한 칸에서 찾지 못합니다.

스스로 점검 (2)

  1. 증가하는 주문 번호를 일반 이진 탐색 트리에 넣으면 어떻게 되나요?

    매번 오른쪽 끝에만 붙어 높이 n인 한 줄이 되고 탐색이 O(n)이 됩니다. 회전으로 높이를 고치는 균형 트리가 필요합니다.

  2. 메모리 안의 정렬 맵에는 Red-Black 트리를, DB 인덱스에는 B-Tree 계열을 쓰는 이유는?

    메모리는 노드 접근이 싸서 이진 트리로 충분하지만, 디스크는 페이지 읽기 횟수가 비용입니다. 노드 하나에 키를 수백 개 넣어 높이를 줄여야 합니다.

  3. 힙에서 최솟값을 꺼낼 때 두 자식 중 더 작은 쪽과 바꾸는 이유는?

    큰 쪽과 바꾸면 새 부모가 다른 자식보다 커져 "부모가 자식보다 작다"는 규칙이 깨집니다.

스스로 점검 (3)

  1. 가격순으로 정렬한 뒤에도 같은 가격끼리 주문 시각순이 유지되어야 합니다. 어떤 정렬이 필요한가요?

    같은 값의 원래 순서를 지키는 안정 정렬(병합 정렬, TimSort)이 필요합니다. 퀵 정렬과 힙 정렬은 이를 보장하지 않습니다.

  2. LRU를 단일 연결 리스트로 만들면 어느 연산이 느려지나요?

    중간 노드를 떼어 앞으로 옮길 때 그 앞 노드를 찾으려면 O(n) 순회가 필요합니다.

  3. 야간 배치가 큰 테이블을 풀 스캔한 뒤 아침 응답이 느려졌습니다. 순수 LRU라면 왜일까요?

    한 번만 읽힌 페이지가 모두 "최근"이 되어 자주 쓰던 페이지를 캐시에서 밀어냈기 때문입니다. InnoDB는 새 페이지를 리스트 중간에 넣어 이를 막습니다.

다음으로 올라갈 층

넓고 얕은 트리, 해시, 연결 리스트로 만든 캐시가 한데 모여 돌아가는 곳이 데이터베이스입니다. 데이터를 표로 나누는 관계형 모델에서 출발해, 이 장의 B-Tree가 실제 인덱스인 B+Tree로, LRU가 버퍼 풀로 어떻게 쓰이는지 따라갑니다.
