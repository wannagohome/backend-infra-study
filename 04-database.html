4장 데이터베이스

데이터베이스는 어떻게 빠르고 안전하게 데이터를 지키는가

디스크 페이지 위에 쌓인 인덱스, 동시에 실행되는 트랜잭션을 갈라 놓는 MVCC와 락, 그리고 한 대를 넘어서는 복제와 샤딩까지 MySQL InnoDB를 기준으로 따라갑니다.

선수 지식
1장 디스크 I/O와 페이지, 3장 B-Tree
슬라이드
53장
예상 학습 시간
150분

아래층부터 위로 쌓아 올라가는 순서입니다. 지금은 4단계입니다.

1부

데이터를 표로 나누고 다시 잇는다

3장의 자료구조는 메모리 안의 데이터를 다뤘습니다. DBMS(Database Management System)는 여기에 세 가지를 더합니다. 전원이 꺼져도 남는 장애 복구, 동시에 읽고 쓰는 요청의 동시성 제어, 디스크에서도 빠른 검색입니다. 예시 엔진은 MySQL InnoDB이고, 크게 다른 곳에서는 PostgreSQL을 함께 봅니다.

행을 구별하는 열이 키다

관계형 모델은 데이터를 행과 열로 이루어진 테이블에 담고, 테이블 사이의 관계를 값으로 잇습니다.

키정의예 (회원 테이블)
슈퍼키행을 유일하게 구별하는 열 집합(id, email), (email, name)
후보키더 줄일 수 없는 최소 슈퍼키id, email
기본키(PK)후보키 중 대표로 고른 하나id
대체키기본키가 되지 못한 후보키email (UNIQUE 제약)
외래키(FK)다른 테이블의 PK를 가리키는 열주문.member_id
 FK 제약은 쓰기마다 부모 행을 확인하고 락을 겁니다. 쓰기가 많거나 샤딩된 DB에서는 제약 없이 FK 열과 인덱스만 두기도 합니다.

JOIN은 키 값으로 테이블을 다시 잇는다

-- 주문이 있는 회원만
SELECT m.name, o.amount
FROM member m
INNER JOIN orders o ON o.member_id = m.id;

-- 주문이 없는 회원도 (o.* 는 NULL)
SELECT m.name, o.amount
FROM member m
LEFT JOIN orders o ON o.member_id = m.id;

INNER는 양쪽에 짝이 있는 행만, LEFT/RIGHT OUTER는 한쪽을 모두 남기고 짝이 없으면 NULL로 채웁니다.

FULL OUTER는 양쪽 모두를 남기는데 MySQL에는 없어 UNION으로 흉내 냅니다. CROSS는 모든 조합, SELF는 같은 테이블끼리의 조인입니다.

중복 저장은 세 가지 이상 현상을 낳는다

수강 기록 한 테이블에 학생, 강의, 교수 연락처를 모두 담았다고 해 봅시다.

이상 현상무슨 일이 생기나원인
갱신 이상교수 연락처를 바꾸려면 수강 행 수백 개를 고쳐야 함같은 사실이 여러 행에 중복
삽입 이상수강생이 없으면 새 강의를 등록할 수 없음다른 사실 없이 기록 불가
삭제 이상마지막 수강생을 지우면 강의 정보도 사라짐두 사실이 한 행에 묶임

정규화는 "한 사실은 한 곳에만" 저장하도록 테이블을 쪼개 이 세 문제를 없애는 과정입니다.

정규형은 의존 관계를 하나씩 끊는다

  1. 1NF

    모든 칸에 원자값 하나. "전화1, 전화2"나 쉼표 목록을 행으로 분리합니다.

  2. 2NF

    복합 PK의 일부에만 의존하는 열을 떼어 냅니다(부분 함수 종속 제거).

  3. 3NF

    PK가 아닌 열을 거쳐 결정되는 열을 떼어 냅니다(이행 종속 제거).

  4. BCNF

    모든 결정자가 후보키가 되도록 남은 예외까지 정리합니다.

(학번, 강의코드) → 성적인 테이블에 강의명이 있다면, 강의명은 강의코드에만 의존하므로 2NF 위반입니다. 강의 테이블로 옮깁니다.

학번 → 학과 → 학과장처럼 열이 연쇄로 결정되면 3NF 위반입니다. 학과 테이블을 따로 만듭니다. 실무 설계는 보통 3NF까지를 목표로 합니다.

반정규화는 조인 비용을 쓰기로 옮긴다

정규화할수록 테이블이 잘게 나뉘고, 화면 하나를 그리는 데 조인이 늘어납니다. 목록 조회가 초당 수천 번 실행되는데 매번 다섯 테이블을 조인해야 한다면 읽기 비용이 커집니다.

반정규화는 일부러 중복을 들여 조회를 단순하게 만드는 것입니다. 게시글에 comment_count를 두거나, 주문에 주문 당시 상품명을 복사해 두는 식입니다.

중복의 정합성은 이제 내 책임입니다

원본이 바뀔 때 복사본을 함께 고치는 코드가 필요하고, 그 갱신이 경합을 만듭니다. 측정된 병목이 있을 때만, 캐시나 인덱스로 안 될 때 고릅니다.

트랜잭션은 전부 되거나 전혀 안 된다

계좌 이체는 "A에서 빼기"와 "B에 더하기" 두 쓰기입니다. 둘 중 하나만 반영되면 돈이 사라지거나 생깁니다.

ACID약속하는 것이체에서 보면InnoDB의 구현 (2부)
원자성(Atomicity)모두 반영 또는 모두 취소빼기만 되고 끝나지 않음Undo 로그
일관성(Consistency)제약 조건이 지켜짐잔액이 음수가 안 됨제약 조건 검사
격리성(Isolation)동시 실행이 간섭 안 함중간 상태를 남이 못 봄MVCC와 락
지속성(Durability)커밋 결과는 장애에도 남음커밋 직후 정전에도 유지Redo 로그(WAL)

2부

인덱스는 디스크 읽기 횟수를 줄인다

인덱스가 왜 빠른지, 왜 하필 B+Tree인지, 언제 쓰이지 않는지를 디스크 페이지에서부터 따라갑니다.

기초 원리 여기부터는 스토리지 엔진 내부 구조를 다룹니다.

DB는 행이 아니라 페이지를 읽는다

디스크는 바이트 하나만 읽지 못하고 블록 단위로 읽습니다. 그래서 InnoDB는 데이터를 페이지라는 고정 크기 덩어리로 저장합니다. 기본 크기는 innodb_page_size = 16KB이고, PostgreSQL은 8KB입니다.

행 하나가 필요해도 그 행이 든 페이지 전체를 읽습니다. 따라서 조회 비용은 몇 개의 페이지를 읽어야 하는가로 결정됩니다.

읽은 페이지는 메모리의 버퍼 풀에 캐시됩니다. 버퍼 풀에 있으면 수 마이크로초, 디스크에서 읽으면 SSD도 그보다 수십 배 이상 느립니다(1장 메모리 계층).

인덱스가 없으면 원하는 행을 찾기 위해 테이블의 모든 페이지를 읽는 풀 스캔을 합니다. 인덱스는 이 페이지 수를 몇 개로 줄이는 구조입니다.

B+Tree: 넓고 얕은 트리에 리프를 잇는다

3장에서 본 B-Tree처럼 B+Tree도 노드 하나가 페이지 하나입니다. 16KB 페이지에 키와 자식 페이지 번호를 수백 개 넣어 트리가 매우 넓고 얕아집니다.

높이 3~4면 수천만 행 이상을 담으므로, 어떤 행이든 페이지 3~4개만 읽으면 도착합니다. 루트와 브랜치는 대개 버퍼 풀에 있어 실제 디스크 읽기는 더 적습니다.

해시도 이진 트리도 아닌 이유

구조등치 검색범위 검색, 정렬디스크 적합성
해시 테이블O(1)불가 (순서 없음)버킷 확장 시 재배치
균형 이진 트리O(log₂ N)가능높이가 커서 페이지 읽기 많음
B-TreeO(log N), 분기 큼가능하나 트리를 오르내림노드 = 페이지
B+TreeO(log N), 분기 큼리프만 순서대로 읽음내부 노드에 키만 있어 더 넓음

이진 트리가 디스크에서 불리한 이유는 3장에서 봤습니다. B+Tree가 B-Tree에서 더 나아간 점은 두 가지입니다. 내부 노드에서 데이터를 빼고 키만 담아 분기 수를 키우고, 리프를 연결해 BETWEEN, ORDER BY, LIKE 'abc%'를 리프 순회로 처리합니다.

InnoDB 테이블 자체가 PK 인덱스다

InnoDB에서는 PK B+Tree의 리프에 행 전체가 들어 있습니다. 데이터가 PK 순서로 정렬되어 저장되므로 이를 클러스터드 인덱스라 부릅니다.

다른 열에 만든 세컨더리 인덱스의 리프에는 행 주소가 아니라 PK 값이 들어 있습니다. 그래서 세컨더리 인덱스 조회는 트리를 두 번 탑니다.

PK는 짧고 증가하는 인조키로 둔다

이메일 같은 자연키는 바뀔 수 있고 깁니다. 그래서 BIGINT AUTO_INCREMENT 인조키를 씁니다. 늘 맨 오른쪽 리프 끝에 붙으므로 페이지를 순서대로 채웁니다.

UUIDv4처럼 무작위 PK는 꽉 찬 중간 페이지에 끼어들어야 합니다. 그때 페이지 분할이 일어나 페이지가 반쯤 빈 채로 흩어집니다.

PK 크기는 모든 인덱스에 복사됩니다

세컨더리 인덱스 리프마다 PK가 들어가므로, 36자 문자열 PK는 8바이트 BIGINT보다 모든 인덱스를 크게 만듭니다.

외부 노출용 ID가 따로 필요하다면

내부 PK는 BIGINT로 두고 UUID는 별도 UNIQUE 열로 두거나, 시간순으로 증가하는 UUIDv7 같은 값을 고려합니다.

복합 인덱스는 왼쪽 열부터 정렬된다

인덱스 (a, b, c)는 전화번호부처럼 a로 정렬하고, a가 같으면 b로, b까지 같으면 c로 정렬한 B+Tree입니다.

그래서 b만 주어지면 a가 정해지지 않아 정렬 순서를 쓸 수 없습니다. 이것이 왼쪽 접두 규칙입니다. 또한 앞 열에 범위 조건이 걸리면, 그 뒤 열은 탐색 범위를 좁히는 데 쓰이지 못합니다.

조건 (인덱스 a, b, c)인덱스 활용
a = 1a 사용
a = 1 AND b = 2a, b 사용
b = 2 AND c = 3탐색에 못 씀
a = 1 AND c = 3a만 탐색, c는 걸러냄
a > 1 AND b = 2a 범위만 탐색

열 순서는 등치, 정렬, 범위 순으로

복합 인덱스의 열 순서는 "어떤 쿼리를 받칠 것인가"로 정합니다. 출발점은 다음과 같습니다.

  • 등치 조건(=) 열을 앞에. 여러 개라면 자주 함께 쓰이는 열, 선택도가 높은 열을 앞에 둡니다.
  • ORDER BY 열을 그다음에. 인덱스 순서 그대로 읽으면 정렬 작업이 사라집니다.
  • 범위 조건 열은 마지막에. 범위 뒤의 열은 탐색에 쓰이지 않기 때문입니다.

카디널리티는 열에 있는 서로 다른 값의 개수입니다. 성별처럼 값이 둘뿐인 열은 조건을 걸어도 절반이 남으므로 단독 인덱스로는 거의 쓸모가 없습니다.

다만 "카디널리티 높은 열이 무조건 앞"은 아닙니다. 그 열이 쿼리 조건에 늘 등장하는지가 먼저입니다.

인덱스만 읽고 끝내는 커버링 인덱스

-- 인덱스: (member_id, created_at)

-- 1) 커버링 아님: amount 때문에 PK로 다시 탐색
SELECT created_at, amount FROM orders
WHERE member_id = 7;

-- 2) 커버링: 필요한 열이 모두 인덱스 안에 있음
SELECT id, created_at FROM orders
WHERE member_id = 7;
-- EXPLAIN Extra: Using index

세컨더리 인덱스의 두 번째 탐색은 행마다 일어납니다. 1만 행이면 클러스터드 인덱스를 1만 번 무작위로 찾아갑니다.

쿼리가 쓰는 열이 모두 인덱스에 있으면 이 단계를 건너뜁니다. 이를 커버링 인덱스라 합니다. 리프에 PK가 들어 있으므로 id는 따로 넣지 않아도 커버됩니다.

인덱스가 있어도 못 쓰는 조건들

-- 열을 가공하면 정렬 순서를 못 씀
WHERE DATE(created_at) = '2026-11-01'
WHERE created_at >= '2026-11-01'
  AND created_at < '2026-11-02'   -- 이렇게

-- 문자열 열에 숫자 비교: 암묵적 형변환
WHERE phone = 01012345678

-- 앞부분 와일드카드
WHERE name LIKE '%민수'

-- OR 한쪽에 인덱스가 없음, 부정 조건
WHERE a = 1 OR no_idx_col = 2

인덱스는 열의 원래 값으로 정렬되어 있습니다. DATE(created_at)의 결과 순서는 트리에 없으므로 모든 행에 함수를 적용해 봐야 합니다.

문자열 열을 숫자와 비교하면 MySQL은 열 쪽을 숫자로 바꿔 비교하므로 같은 이유로 인덱스를 못 씁니다. '%민수'도 시작 위치를 알 수 없어 트리를 탈 수 없습니다.

옵티마이저는 비용으로 풀 스캔을 고른다

MySQL 옵티마이저는 통계(행 수, 값 분포)로 각 실행 방법의 비용을 추정해 가장 싼 것을 고릅니다. 세컨더리 인덱스로 테이블의 20~30% 이상을 읽어야 한다면, 행마다 무작위로 PK를 찾아가는 것보다 순서대로 전체를 읽는 편이 더 쌀 수 있습니다.

통계가 실제와 크게 어긋나면 잘못된 계획이 나옵니다. 대량 변경 뒤에는 ANALYZE TABLE로 통계를 갱신합니다.

인덱스에는 공짜가 없습니다. INSERT 한 번은 클러스터드 인덱스와 모든 세컨더리 인덱스에 각각 키를 넣고, 인덱스 열을 바꾸는 UPDATE는 삭제와 삽입을 함께 합니다.

인덱스가 늘수록 쓰기가 느려지고 버퍼 풀을 더 차지합니다. 쓰기가 많은 테이블은 실제로 쓰이는 인덱스만 남기고, 겹치는 인덱스((a)와 (a, b))를 정리합니다.

EXPLAIN으로 실행 계획을 읽는다

mysql> EXPLAIN SELECT * FROM orders
    -> WHERE member_id = 7
    -> ORDER BY created_at DESC\G
 type: ALL
  key: NULL
 rows: 982114
Extra: Using where; Using filesort

-- 인덱스 (member_id, created_at) 추가 후
 type: ref
  key: idx_member_created
 rows: 38
Extra: Backward index scan

type은 접근 방식, key는 실제로 고른 인덱스, rows는 읽을 것으로 추정한 행 수입니다.

처음 계획은 98만 행을 모두 읽고(ALL) 따로 정렬합니다(filesort). 인덱스를 만들면 38행만 읽고, 인덱스를 거꾸로 훑어 정렬도 생략합니다.

type과 Extra에서 봐야 할 값

type의미 (위가 빠름)
constPK, UNIQUE로 한 행
eq_ref조인에서 PK로 한 행씩
ref일반 인덱스 등치 검색
range인덱스 범위 검색
index인덱스 전체 스캔
ALL테이블 풀 스캔
Extra의미
Using index커버링, 테이블 안 읽음

OLTP 쿼리 대부분은 Nested Loop로 실행됩니다. 바깥 테이블에서 조건으로 걸러진 행이 적고, 안쪽 테이블의 조인 열에 인덱스가 있을 때 가장 빠릅니다. 그래서 FK 열에는 인덱스를 둡니다. 인덱스가 없으면 바깥 행마다 안쪽을 풀 스캔하게 되고, MySQL은 이때 Hash Join으로 대신합니다.

커밋은 데이터가 아니라 로그를 쓴다

  1. 변경 전 값 기록

    이전 값을 Undo 로그에 남깁니다. 롤백과 MVCC가 이것을 씁니다.

  2. 버퍼 풀 수정

    메모리의 페이지만 고칩니다. 디스크는 아직 그대로입니다.

  3. Redo 로그 기록

    "어느 페이지를 어떻게 바꿨다"를 로그 버퍼에 적습니다.

  4. COMMIT

    Redo 로그를 fsync한 뒤 응답합니다(기본값 기준).

  5. 체크포인트

    더티 페이지는 나중에 모아서 데이터 파일에 씁니다.

바뀐 페이지를 커밋마다 제자리에 쓰면 디스크 여기저기를 무작위로 써야 합니다. 대신 로그 파일 끝에 순차로 덧붙이고, 페이지는 나중에 씁니다. 이것이 WAL입니다.

장애 뒤 재시작하면 Redo로 커밋을 살리고(지속성), 미커밋 변경은 Undo로 되돌립니다(원자성).

innodb_flush_log_at_trx_commit을 기본값 1에서 0이나 2로 바꾸면 빨라지지만 장애 시 최근 약 1초의 커밋을 잃을 수 있습니다.

완벽한 격리(모두 한 줄로 실행)는 느립니다. SQL 표준은 동시성을 얻는 대신 무엇을 허용할지 네 단계로 정했습니다.

Dirty Read는 READ UNCOMMITTED에서만 생기므로 실무에서 볼 일은 거의 없습니다. Non-Repeatable Read는 문장마다 최신 커밋을 보는 READ COMMITTED에서 생기고, 같은 데이터를 여러 번 읽어 맞춰 보는 정산 같은 작업에서 문제가 됩니다.

Phantom Read: 없던 행이 나타난다

시점트랜잭션 A트랜잭션 B
t1age > 30 인 회원 수: 5
t2age = 35 회원 INSERT
t3COMMIT
t4age > 30 인 회원 수: 6

기존 행은 그대로인데 조건에 맞는 행 집합이 달라졌습니다. 행 하나에 락을 걸어서는 막을 수 없습니다. 아직 존재하지 않는 행이기 때문입니다.

그렇다면 InnoDB는 REPEATABLE READ에서 이 현상을 어떻게 다룰까요? 답은 두 장치, MVCC와 넥스트 키 락에 있습니다.

MVCC: 읽기는 과거 버전을 본다

MVCC는 행의 여러 버전을 두고, 읽는 트랜잭션에 자기 시점에 맞는 버전을 보여 주는 방식입니다.

InnoDB는 행을 제자리에서 고치고 이전 값을 Undo 로그에 체인으로 남깁니다. 읽기는 Read View를 기준으로 아직 커밋 안 된 버전을 건너뛰며 체인을 거슬러 올라갑니다. 그래서 읽기는 쓰기를 기다리지 않습니다.

스냅샷을 언제 찍느냐가 수준을 가른다

InnoDB에서 READ COMMITTED와 REPEATABLE READ의 차이는 Read View를 만드는 시점뿐입니다.

  • READ COMMITTED: SELECT 문마다 새 Read View. 그사이 커밋된 값이 보입니다.
  • REPEATABLE READ: 트랜잭션의 첫 읽기에서 만든 Read View를 끝까지 씁니다. 같은 SELECT는 같은 결과를 냅니다.

그래서 일반 SELECT에서는 Phantom도 보이지 않습니다. 나중에 들어온 행은 스냅샷에 없기 때문입니다.

PostgreSQL의 MVCC는 구조가 다릅니다

UPDATE 때 테이블 안에 새 행 버전을 통째로 쓰고 옛 버전은 VACUUM이 치웁니다. REPEATABLE READ는 스냅샷 격리라 Phantom이 없고, 동시 수정이 충돌하면 직렬화 오류로 실패시킵니다.

잠금 읽기는 갭까지 잠근다

스냅샷은 일반 SELECT에만 쓰입니다. SELECT … FOR UPDATE, UPDATE, DELETE 같은 잠금 읽기는 최신 커밋 값을 읽고 락을 겁니다.

이때 InnoDB는 레코드뿐 아니라 레코드 사이의 빈 구간에도 갭 락을 겁니다. 레코드 락과 그 앞 갭 락을 합친 것이 넥스트 키 락입니다. 갭에 INSERT가 못 들어오니 잠금 읽기에서도 Phantom이 막힙니다.

"상당 부분 막는다"의 빈틈

InnoDB REPEATABLE READ는 일반 SELECT는 스냅샷으로, 잠금 읽기는 넥스트 키 락으로 Phantom을 막습니다. 그러나 둘을 섞으면 빈틈이 생깁니다.

A가 일반 SELECT로 5행을 본 뒤 B가 행을 넣고 커밋합니다. 이어서 A가 같은 조건으로 UPDATE하면, 잠금 읽기는 최신 데이터를 보므로 B의 행까지 6행이 바뀝니다. 그다음 A의 SELECT에는 그 행이 나타납니다.

또 하나는 갱신 손실입니다. 두 트랜잭션이 재고 10을 일반 SELECT로 읽고 각자 9를 쓰면, 하나의 차감이 사라집니다. InnoDB REPEATABLE READ는 이를 오류로 막지 않습니다.

읽은 값을 근거로 쓸 때는 처음부터 잠금 읽기를 하거나 조건부 UPDATE를 써야 합니다. 이것이 다음에 볼 락의 영역입니다.

공유 락과 배타 락, 그리고 FOR UPDATE

InnoDB의 행 락은 두 종류입니다. 공유 락(S)은 "읽는 중이니 바꾸지 마라", 배타 락(X)은 "내가 바꾸니 아무도 잠그지 마라"입니다.

SELECT … FOR SHARE는 S 락, FOR UPDATE와 UPDATE, DELETE는 X 락을 겁니다. 락은 커밋이나 롤백까지 유지됩니다. 락을 기다리는 시간은 innodb_lock_wait_timeout(기본 50초)까지입니다.

보유 \ 요청S 락X 락
S 락허용대기
X 락대기대기
 락이 없는 일반 SELECT는 MVCC 스냅샷을 읽으므로 X 락이 걸린 행도 기다리지 않고 읽습니다.

낙관적 락과 비관적 락은 충돌 빈도로 고른다

-- 비관적 락: 읽을 때부터 잠금
BEGIN;
SELECT stock FROM item WHERE id = 1 FOR UPDATE;
UPDATE item SET stock = stock - 1 WHERE id = 1;
COMMIT;

-- 낙관적 락: 쓸 때 버전이 그대로인지 확인
SELECT stock, version FROM item WHERE id = 1;
UPDATE item SET stock = 9, version = 6
 WHERE id = 1 AND version = 5;
-- 영향받은 행이 0이면 누가 먼저 바꿈: 재시도

비관적 락은 충돌이 잦다고 보고 미리 잠급니다. 확실하지만 기다림이 생깁니다.

낙관적 락은 DB 락 없이 버전 열로 충돌을 감지합니다. 충돌이 드물면 빠르지만, 잦으면 재시도가 폭증합니다. JPA의 @Version이 이 방식입니다(6장).

DB 데드락은 엔진이 찾아서 끊는다

시점트랜잭션 A트랜잭션 B
t1계좌 1 X 락 획득
t2계좌 2 X 락 획득
t3계좌 2 요청: 대기
t4계좌 1 요청: 순환 대기
t5계속 진행오류 1213, 롤백

1장의 데드락 조건이 DB 행 락에서 그대로 성립합니다. A는 1→2, B는 2→1 순서로 이체하다 서로를 기다립니다.

InnoDB는 대기 그래프에서 순환을 즉시 감지하고(innodb_deadlock_detect 기본 ON) 바꾼 행이 적은 쪽을 골라 롤백시킵니다. 애플리케이션은 이 오류를 받아 재시도해야 합니다.

레플리케이션: 로그를 보내 다시 실행한다

서버 한 대의 한계를 넘는 첫 방법은 복제입니다. Primary는 변경을 binlog에 남기고, Replica는 그것을 받아 relay log에 쌓은 뒤 순서대로 다시 실행합니다. MySQL의 기본은 비동기 복제라서 Primary는 Replica를 기다리지 않고 커밋 응답을 돌려줍니다.

비동기 복제는 빠른 대신 지연과 유실이 있다

Replica를 여러 대 두고 읽기를 나눠 보내면 읽기 처리량이 늘어납니다. 쓰기는 Primary 한 곳에서만 받습니다. 이것이 읽기/쓰기 분리입니다.

대가는 두 가지입니다. Replica는 Primary보다 늦기 때문에 방금 쓴 데이터가 Replica에 없을 수 있고, Primary가 죽으면 아직 전송되지 않은 커밋은 Replica로 승격해도 없습니다.

방식커밋 응답 시점대가
비동기Primary 커밋 즉시장애 시 유실 가능
반동기Replica 하나가 수신 확인한 뒤왕복 지연 추가
동기Replica 반영 확인 뒤가장 느림, 가용성 저하
 MySQL은 반동기(semisynchronous) 복제를 플러그인으로 지원합니다.

파티셔닝은 나누고, 샤딩은 흩는다

파티셔닝은 큰 테이블을 한 서버 안에서 여러 조각으로 나누는 것입니다. 월별 파티션이면 오래된 달을 DROP PARTITION으로 한 번에 지울 수 있습니다. 열을 나누면 수직, 행을 나누면 수평 파티셔닝입니다.

샤딩은 행을 여러 DB 서버에 흩는 수평 분할입니다. 복제로는 늘릴 수 없는 쓰기 처리량과 저장 용량을 늘리는 유일한 방법입니다.

샤딩 방식장점약점
범위범위 조회가 한 샤드최신 범위에 쓰기 몰림
해시고르게 분산샤드 추가 시 대량 이동
디렉터리위치를 자유롭게 지정조회 테이블이 병목

RDBMS는 고정 스키마, 조인, 강한 트랜잭션을 주지만 쓰기를 늘리려면 샤딩이라는 큰 공사가 필요합니다. NoSQL은 대체로 조인과 다중 행 트랜잭션을 포기하고, 처음부터 여러 노드에 분산되도록 설계되었습니다. 접근 패턴이 키 중심이고 규모가 크면 NoSQL이, 관계와 정합성이 중요하면 RDBMS가 맞습니다.

CAP: 네트워크가 끊기면 둘 중 하나

분산 저장소는 세 가지를 원합니다. 모든 노드가 같은 최신 값을 보는 일관성(C), 모든 요청이 응답을 받는 가용성(A), 노드 사이 통신이 끊겨도 동작하는 분할 내성(P)입니다.

네트워크 분할은 고를 수 있는 것이 아니라 언젠가 반드시 일어납니다. 그러므로 CAP의 실제 의미는 분할이 생겼을 때 C와 A 중 무엇을 포기하느냐입니다.

분할 시 선택동작
CP반대편과 확인 못 하면 오류 반환
AP옛 값일 수 있어도 응답

CAP의 C는 ACID의 C가 아닙니다

ACID의 일관성은 제약 조건을 지키는 것이고, CAP의 일관성은 모든 노드가 최신 쓰기를 보는 것(선형성)입니다.

PACELC: 평소에는 지연과 일관성을 고른다

CAP는 장애 순간만 말합니다. 그런데 분할이 없는 평소에도 선택이 있습니다. 다른 노드의 확인을 기다리면 일관되지만 느리고, 기다리지 않으면 빠르지만 잠시 어긋납니다.

PACELC는 이를 "분할(P)이면 A와 C 중, 그 외(E)에는 지연(L)과 C 중 선택"으로 정리합니다. 앞에서 본 비동기 복제는 평소에 L을 고른 것입니다.

최종 일관성은 "새 쓰기가 없으면 결국 모든 복제본이 같아진다"는 약속입니다. 언제인지는 보장하지 않습니다.

Cassandra나 DynamoDB의 기본 설정이 PA/EL 쪽, 동기 복제를 쓰는 RDB가 PC/EC 쪽에 가깝습니다. 다만 많은 제품이 요청 단위로 일관성 수준을 고르게 해 주므로 분류는 설정에 따라 달라집니다.

3부

느린 쿼리, 데드락, 풀 고갈, 복제 지연

원리를 알면 장애가 왜 일어났는지 설명할 수 있습니다. 운영에서 실제로 자주 마주치는 다섯 가지 상황을 따라갑니다.

원리 실무 설정값, 진단 명령, 장애 사례와 대응을 다룹니다.

사례: 주문 목록 API가 2초씩 걸린다

# Query_time: 2.31  Rows_examined: 1204533
SELECT * FROM orders
WHERE member_id = 123 AND status = 'PAID'
ORDER BY created_at DESC LIMIT 20;

mysql> EXPLAIN …
 type: ref   key: idx_status
 rows: 1204533
 Extra: Using where; Using filesort

먼저 슬로 쿼리 로그로 범인을 찾습니다. long_query_time 기본값은 10초라 운영에서는 보통 1초 이하로 낮춰 둡니다.

옵티마이저는 idx_status를 골랐지만, PAID는 전체 주문의 대부분이라 120만 행을 읽고 그 결과를 다시 정렬합니다. 20행을 위해 120만 행을 읽은 셈입니다.

인덱스 하나로 120만 행을 20행으로

ALTER TABLE orders
  ADD INDEX idx_member_status_created
  (member_id, status, created_at);

mysql> EXPLAIN …
 type: ref   key: idx_member_status_created
 rows: 20
 Extra: Backward index scan

# Query_time: 0.003  Rows_examined: 20

-- 쓰이지 않게 된 idx_status는 확인 후 제거
ALTER TABLE orders
  ALTER INDEX idx_status INVISIBLE;

등치 열 두 개를 앞에, 정렬 열을 뒤에 둡니다. 인덱스 안에서 이미 created_at 순으로 정렬되어 있으므로 뒤에서부터 20개만 읽고 멈춥니다.

운영 테이블의 인덱스 추가는 InnoDB 온라인 DDL로 서비스 중에 가능하지만 I/O를 크게 씁니다. 트래픽이 적은 시간에 하고, 기존 인덱스는 먼저 INVISIBLE로 바꿔 영향을 본 뒤 지웁니다.

데드락은 없애기보다 줄이고 재시도한다

데드락이 났다면 SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK 절에서 두 트랜잭션이 어떤 락을 쥐고 무엇을 기다렸는지 봅니다. innodb_print_all_deadlocks를 켜면 모든 데드락이 에러 로그에 남습니다.

동시성이 있는 한 데드락을 0으로 만들 수는 없습니다. 그래서 목표는 빈도를 줄이고, 났을 때 안전하게 다시 하는 것입니다.

  • 락 순서 통일: 여러 행을 잠글 때 항상 PK 오름차순으로.
  • 트랜잭션은 짧게: 외부 호출이나 사용자 입력을 트랜잭션 밖으로.
  • 인덱스 확인: 조건 열에 인덱스가 없으면 스캔한 모든 행에 락이 걸립니다.
  • 재시도: 1213 오류는 백오프를 두고 트랜잭션 전체를 다시 실행.

사례: 없는 행을 잠그면 갭 데드락

시점트랜잭션 A트랜잭션 B
t1id=50 FOR UPDATE (없음)
t2id=50 FOR UPDATE (없음)
t3INSERT id=50: 대기
t4INSERT id=50: 데드락

"있으면 수정, 없으면 삽입"을 FOR UPDATE로 구현할 때 자주 터집니다. 없는 행을 잠그면 갭 락이 걸리는데, 갭 락끼리는 서로 막지 않아 둘 다 성공합니다. 그런데 INSERT는 상대의 갭 락을 기다려야 하므로 순환이 생깁니다.

UNIQUE 키를 두고 INSERT … ON DUPLICATE KEY UPDATE로 한 문장에 처리하면 피할 수 있습니다.

커넥션 풀은 비싼 연결을 재사용한다

DB 연결 하나를 새로 맺으려면 TCP 핸드셰이크(2장), 인증, 세션 초기화를 거쳐야 하고 DB 서버는 연결마다 스레드와 메모리를 씁니다. 요청마다 연결을 열고 닫으면 이 비용이 매번 듭니다.

커넥션 풀은 연결을 미리 열어 두고 빌려주었다가 돌려받습니다. Spring Boot의 기본 풀은 HikariCP입니다.

HikariCP 설정기본값의미
maximumPoolSize10최대 연결 수
minimumIdle최대와 같음고정 크기 풀 권장
connectionTimeout30초빌리기 대기 한도
maxLifetime30분DB 쪽 타임아웃보다 짧게

풀 크기는 크다고 좋지 않다

필요한 연결 수는 초당 요청 수 × 연결을 쥐고 있는 평균 시간으로 어림합니다(리틀의 법칙). 초당 1,000건, 건당 5ms면 동시에 5개면 충분합니다.

DB 서버 쪽에서 보면 실제로 동시에 일할 수 있는 수는 CPU 코어와 디스크가 정합니다. HikariCP 문서는 출발점으로 코어 수 × 2 + 유효 디스크 수를 제시합니다. 이보다 크게 잡으면 DB 안에서 컨텍스트 스위칭과 락 경합만 늘어납니다(1장).

합계는 DB 기준으로 계산합니다

서버 20대가 각각 풀 50개를 잡으면 DB에는 연결 1,000개가 붙습니다. Auto Scaling으로 인스턴스가 늘면 이 수도 함께 늘어 max_connections에 닿습니다.

사례: 트랜잭션 안의 외부 호출이 풀을 말린다

요청 스레드커넥션 풀
트랜잭션 시작 getConnection() 대여 10개 중 1개
외부 결제 API 응답 대기 3초 (연결은 쥔 채)
새 요청 getConnection()남은 연결 0개, 대기열에 줄 섬 고갈
30초 뒤 SQLTransientConnectionException

연결 10개, 건당 3초면 초당 3.3건이 한계입니다. 그 이상이 오면 Tomcat 스레드 200개가 모두 연결을 기다리며 멈춥니다.

해법은 풀을 키우는 것이 아니라 외부 호출을 트랜잭션 밖으로 빼는 것입니다. connectionTimeout은 수 초로 줄여 빨리 실패하게 합니다.

이 경계가 Spring 코드에서 어떻게 생기는지는 6장, 운영 중 로그와 덤프로 이 상황을 확정하는 법은 11장에서 다룹니다.

사례: 방금 고친 프로필이 옛날 값이다

애플리케이션DB
저장 클릭 UPDATE nickname='새이름' Primary
COMMIT OK Primary
화면 새로고침 SELECT nickname Replica
옛 값 표시 '옛이름'복제 지연 0.8초, 아직 미적용 Replica

읽기/쓰기 분리의 read-after-write 문제입니다. 평소 수 밀리초인 지연도 대량 배치 적용 중에는 수십 초로 벌어집니다.

  • 방금 쓴 사용자의 읽기는 몇 초간 Primary로
  • 저장 응답에 바뀐 값을 담아 다시 읽지 않기
  • Seconds_Behind_Source를 감시해 늦은 Replica 제외

Spring에서 읽기 전용 트랜잭션을 Replica로 보내는 구성은 6장에서 다룹니다.

샤드 키는 되돌리기 가장 어려운 결정이다

샤드 키는 행이 어느 서버에 갈지 정하는 열입니다. 고르는 기준은 세 가지입니다.

  • 분포: 값이 많고 고르게 퍼져야 합니다. 생성 시각을 범위로 쓰면 모든 쓰기가 최신 샤드 하나에 몰립니다.
  • 쿼리 지역성: 대부분의 쿼리가 키를 포함해야 한 샤드에서 끝납니다. 아니면 모든 샤드에 물어야 합니다.
  • 트랜잭션 경계: 함께 바뀌는 데이터가 같은 샤드에 있어야 합니다.

주문 서비스라면 member_id가 흔한 선택입니다. "내 주문 목록"과 주문 생성이 한 샤드에서 끝납니다. 대신 "오늘 전체 주문 집계"는 모든 샤드를 돌아야 하므로 별도 분석 저장소로 보냅니다.

hash % N은 샤드를 늘리면 거의 모든 행이 옮겨 갑니다. 이 리샤딩 비용을 줄이는 일관성 해싱은 8장에서 다룹니다.

정리

  • 조회 비용은 읽는 페이지 수입니다. B+Tree는 넓고 얕은 트리와 연결된 리프로 등치와 범위 검색을 모두 적은 페이지로 끝냅니다.
  • InnoDB 테이블은 PK 인덱스 그 자체입니다. 세컨더리 인덱스는 PK를 거쳐 행에 닿으므로 PK 설계, 복합 인덱스 순서, 커버링이 성능을 가릅니다.
  • 원자성과 지속성은 로그가, 격리성은 MVCC와 락이 만듭니다. REPEATABLE READ는 스냅샷과 넥스트 키 락으로 Phantom을 상당 부분 막습니다.
  • DB를 늘리는 순간 일관성을 일부 내줍니다. 비동기 복제의 지연, 샤드 키 선택, CAP와 PACELC가 그 대가를 설명합니다.
  • 운영 장애의 대부분은 원리로 설명됩니다. 풀 고갈은 긴 트랜잭션, 데드락은 락 순서, 옛 값은 복제 지연이 원인입니다.

스스로 점검 (1)

  1. 해시 인덱스가 등치 검색에 더 빠른데도 기본 인덱스가 B+Tree인 이유는?

    해시는 값의 순서를 잃어 범위 검색, 정렬, 접두 LIKE를 처리할 수 없습니다. B+Tree는 등치도 페이지 3~4개로 끝나면서 연결된 리프로 범위를 순서대로 읽습니다.

  2. 인덱스 (a, b)가 있을 때 WHERE b = 1 쿼리는 왜 느릴까요?

    인덱스는 a로 먼저 정렬되어 있어 b만으로는 시작 위치를 정할 수 없습니다. 왼쪽 접두 규칙에 따라 탐색에 쓰이지 못합니다.

  3. 세컨더리 인덱스로 10만 행을 읽는 쿼리가 풀 스캔보다 느릴 수 있는 이유는?

    행마다 PK로 클러스터드 인덱스를 다시 무작위 탐색하기 때문입니다. 비율이 크면 순차로 전체를 읽는 편이 싸고, 커버링 인덱스면 이 비용이 사라집니다.

  4. 커밋할 때 데이터 페이지 대신 Redo 로그만 디스크에 쓰는데도 지속성이 보장되는 이유는?

    재시작 시 Redo 로그를 다시 적용하면 버퍼 풀에만 있던 변경을 복원할 수 있기 때문입니다. 로그는 순차 쓰기라 페이지 무작위 쓰기보다 훨씬 빠릅니다.

  5. InnoDB REPEATABLE READ에서 일반 SELECT가 Phantom을 보지 않는 이유는?

    첫 읽기 때 만든 Read View를 트랜잭션 끝까지 쓰므로, 이후 커밋된 행은 스냅샷에 보이지 않습니다.

스스로 점검 (2)

  1. 재고 차감을 "SELECT로 읽고 계산해서 UPDATE"로 하면 무엇이 문제인가요?

    두 트랜잭션이 같은 값을 읽고 각자 써서 하나의 차감이 사라지는 갱신 손실이 생깁니다. FOR UPDATE, 조건부 UPDATE, 버전 열 중 하나로 막아야 합니다.

  2. DB 데드락 오류를 받은 애플리케이션은 무엇을 해야 하나요?

    롤백된 트랜잭션 전체를 짧은 백오프 뒤 다시 실행합니다. 마지막 문장만 다시 실행하면 앞의 변경이 이미 취소된 상태라 틀린 결과가 됩니다.

  3. 트래픽이 늘어 풀 고갈이 나면 maximumPoolSize를 올리면 될까요?

    대개 아닙니다. 연결을 오래 쥐는 원인(긴 트랜잭션, 외부 호출, 느린 쿼리)을 먼저 없애야 하고, 풀을 키우면 DB의 동시 실행 한계와 max_connections에 부딪힙니다.

  4. Primary가 죽어 Replica를 승격했더니 마지막 몇 건의 주문이 사라졌습니다. 왜일까요?

    비동기 복제는 Replica 전송을 기다리지 않고 커밋 응답을 주므로, 전송 전 커밋은 Replica에 없습니다. 반동기 복제로 이 위험을 줄일 수 있습니다.

  5. created_at을 범위 샤드 키로 쓰면 어떤 일이 생기나요?

    새 쓰기가 모두 가장 최신 범위의 샤드 하나에 몰려 그 샤드만 과부하가 걸립니다. 나머지 샤드는 놀게 됩니다.
