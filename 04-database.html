1부

데이터를 표로 나누고 다시 잇는다

3장에서는 메모리 안의 데이터를 빨리 찾는 구조를 봤습니다. 이 부에서는 그 데이터를 디스크에 오래, 여러 사용자가 함께 쓰도록 맡길 때 무엇이 필요한지, 그리고 데이터를 어떤 모양으로 담아야 하는지를 묻습니다.

파일에 저장하면 세 가지가 무너진다

이 장 전체에서 작은 온라인 쇼핑몰의 주문 서비스를 예로 씁니다. 회원이 상품을 고르면 재고를 하나 줄이고 주문을 기록하는 서비스입니다. 처음에는 주문을 JSON 파일에 한 줄씩 덧붙여 저장해도 될 것 같습니다. 그러나 서비스가 자라면 곧 세 가지 문제가 드러납니다.

첫째는 장애입니다. 재고를 줄이는 쓰기와 주문을 적는 쓰기 사이에 서버 전원이 꺼지면, 재고는 줄었는데 주문은 없는 상태가 디스크에 남습니다. 파일은 "둘 다 되거나 둘 다 안 되게" 해 주지 않습니다.

둘째는 동시성입니다. 남은 재고가 1개인 상품을 두 요청이 동시에 읽으면 둘 다 "1개 남음"을 보고 둘 다 판매합니다. 1장에서 본 stock--의 경쟁 상태가 디스크 위에서 일어나는 것입니다.

셋째는 검색입니다. 주문이 100만 건이 되면 "회원 7번의 주문"을 찾으려고 파일 전체를 읽어야 합니다.

이 세 가지를 대신 해결해 주는 프로그램이 DBMS입니다. 장애 복구, 동시성 제어, 빠른 검색이 DBMS가 파는 세 가지 상품이고, 이 장은 그 셋이 내부에서 어떻게 만들어지는지를 따라갑니다.

관계형 모델은 데이터를 표에 담는다

DBMS 중 가장 널리 쓰이는 것은 관계형 모델을 따르는 RDBMS입니다. 데이터를 행과 열로 이루어진 테이블에 담습니다. 행 하나가 주문 하나 같은 사실 하나이고, 열은 그 사실의 속성(금액, 상태, 시각)입니다. 테이블마다 어떤 열이 어떤 타입으로 있는지를 미리 정해 두는데, 이 정의를 스키마라 합니다.

테이블을 다루는 언어가 SQL입니다. SQL은 "회원 7번의 주문을 최신순으로 20개"처럼 무엇을 원하는지만 적는 선언형 언어입니다. 어떤 순서로 어떤 파일을 읽을지는 DBMS가 정합니다. 이 결정을 내리는 부품이 2부에서 볼 옵티마이저입니다.

이 장의 예시 DBMS는 MySQL입니다. MySQL은 SQL을 해석하는 서버 층과, 실제로 데이터를 디스크에 저장하는 스토리지 엔진 층이 나뉘어 있고, 기본 엔진이 InnoDB입니다. 인덱스 구조, 트랜잭션, 락은 모두 엔진의 일이므로 이 장의 내부 동작 설명은 InnoDB 기준입니다.

동작이 크게 다른 곳에서는 또 하나의 대표 오픈소스 RDBMS인 PostgreSQL을 함께 봅니다.

주문 서비스의 테이블을 만든다

CREATE TABLE member (
  id    BIGINT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  name  VARCHAR(50)  NOT NULL
);
CREATE TABLE orders (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  member_id  BIGINT NOT NULL,
  item_id    BIGINT NOT NULL,
  quantity   INT NOT NULL,
  amount     INT NOT NULL,
  status     VARCHAR(20) NOT NULL,
  created_at DATETIME NOT NULL,
  FOREIGN KEY (member_id) REFERENCES member(id)
);

CREATE TABLE은 스키마를 정의하는 SQL 문으로, 괄호 안에 "열 이름 타입 제약"을 한 줄씩 적습니다. 회원(member)과 주문(orders) 테이블입니다. 상품(item)은 이름, 가격, 재고 stock을 가진 비슷한 테이블입니다. ORDER는 SQL 예약어라서 테이블 이름을 orders로 지었습니다.

NOT NULL은 값이 비어 있으면 안 된다는 제약 조건이고, NULL은 "값이 없음"을 뜻하는 특별한 표시입니다. 강조한 두 줄의 키는 다음 슬라이드에서 봅니다.

키는 행 하나를 콕 집어내는 열이다

회원 테이블에 "김민수"가 두 명 있으면 이름으로는 누구인지 가릴 수 없습니다. 테이블에서 행 하나를 확실히 집어내려면 값이 절대 겹치지 않는 열(또는 열의 묶음)이 필요합니다. 이것이 키입니다.

값이 겹치지 않기만 하면 되므로 후보는 여러 개입니다. (id, name)처럼 불필요한 열이 섞여 있어도 행을 구별할 수는 있는데, 이렇게 유일성만 만족하는 열 묶음을 슈퍼키라 합니다. 여기서 열을 하나라도 빼면 유일성이 깨지는 최소 묶음이 후보키입니다. 회원 테이블에서는 id와 email이 후보키입니다.

후보키 중 대표로 하나를 골라 기본키(PK)로 정합니다. PK는 값이 겹치면 안 되고 NULL일 수도 없습니다. 고르지 않은 나머지 후보키는 대체키가 되며, 보통 UNIQUE 제약으로 유일성만 강제합니다. 앞 슬라이드의 email … UNIQUE가 그것입니다.

마지막으로 다른 테이블의 PK를 가리키는 열이 외래키(FK)입니다. orders.member_id는 member.id를 가리켜 "이 주문은 저 회원의 것"이라는 관계를 값으로 표현합니다. 관계형 모델에서 테이블 사이의 연결은 포인터가 아니라 이렇게 같은 값을 나눠 갖는 것입니다.

FK 제약은 관계를 지키는 대신 쓰기를 늦춘다

FOREIGN KEY … REFERENCES를 선언하면 DB가 참조 무결성을 지켜 줍니다. 없는 회원 번호로 주문을 넣거나, 주문이 남은 회원을 지우려 하면 오류를 냅니다.

대가도 있습니다. 주문을 INSERT할 때마다 DB는 부모인 회원 행이 있는지 확인하고, 확인하는 동안 그 회원 행이 지워지지 않도록 잠급니다(락은 2부에서 봅니다). 쓰기가 몰리면 이 확인이 경합 지점이 됩니다.

키회원 테이블의 예
슈퍼키(id, name), (email, name)
후보키id, email
기본키(PK)id
대체키email (UNIQUE)
외래키(FK)orders.member_id
 쓰기가 많거나 여러 DB로 나눈(샤딩한) 시스템은 FK 제약 없이 열과 인덱스만 두고 앱에서 관계를 지키기도 합니다.

PK에는 의미 없는 일련번호를 쓴다

회원의 PK로 이메일을 쓸 수도 있습니다. 이렇게 실제 세계에서 의미를 가진 값을 키로 쓰는 것을 자연키라 합니다. 그런데 이메일은 바뀔 수 있습니다. PK가 바뀌면 그 값을 FK로 가진 모든 주문 행을 함께 고쳐야 합니다.

그래서 보통 아무 의미 없는 번호를 PK로 따로 둡니다. 이것이 인조키입니다. MySQL에서는 BIGINT AUTO_INCREMENT로 만들며, 행을 넣을 때마다 DB가 1, 2, 3…을 자동으로 붙여 줍니다.

인조키의 장점은 셋입니다. 절대 바뀌지 않고, 8바이트로 짧으며, 늘 증가합니다. 앞의 둘은 바로 이해되지만 "늘 증가한다"가 왜 장점인지는 지금은 알 수 없습니다.

그 이유는 InnoDB가 테이블을 PK 순서로 디스크에 저장하기 때문인데, 2부에서 인덱스 구조를 본 뒤 다시 돌아와 설명합니다. 이메일은 PK 대신 UNIQUE 제약을 건 대체키로 둡니다.

JOIN은 나눠 둔 테이블을 키 값으로 다시 잇는다

-- 주문이 있는 회원만
SELECT m.name, o.amount
FROM member m
INNER JOIN orders o ON o.member_id = m.id;

-- 주문이 없는 회원도 (o.* 는 NULL)
SELECT m.name, o.amount
FROM member m
LEFT JOIN orders o ON o.member_id = m.id;

주문 화면에는 회원 이름이 필요한데 이름은 회원 테이블에 있습니다. 조인은 ON 조건이 맞는 두 테이블의 행을 짝지어 한 행으로 붙입니다.

INNER JOIN은 짝이 있는 행만 남깁니다. 주문이 없는 회원은 결과에서 빠집니다. LEFT JOIN은 왼쪽(회원)을 모두 남기고, 짝이 없으면 오른쪽 열을 NULL로 채웁니다. "주문 0건 회원 찾기"가 이 방식입니다.

나머지 조인은 남길 쪽과 짝짓는 법이 다르다

조인의 종류는 "짝이 없는 행을 어느 쪽에서 남길까"와 "무엇과 짝지을까"의 조합입니다.

조인남기는 행주문 서비스에서의 쓰임
INNER양쪽 모두 짝이 있는 행주문과 주문자 이름
LEFT / RIGHT한쪽 전부 + 짝 없으면 NULL주문 0건 회원 찾기
FULL OUTER양쪽 전부두 장부 대조(MySQL은 미지원)
CROSS가능한 모든 조합상품 × 옵션 목록 생성
SELF같은 테이블끼리추천인 회원의 이름 찾기

MySQL에는 FULL OUTER JOIN이 없어서, 두 SELECT의 결과를 위아래로 이어 붙이는 UNION으로 LEFT와 RIGHT 결과를 합쳐 흉내 냅니다. CROSS는 행 수가 곱으로 늘어나므로 큰 테이블에 실수로 쓰지 않도록 조심합니다.

한 테이블에 다 담으면 같은 사실이 반복된다

왜 처음부터 회원과 주문을 나눴을까요? 반대로 주문 한 테이블에 회원 이메일과 상품명, 가격까지 모두 담았다고 해 봅시다.

이상 현상무슨 일이 생기나원인
갱신 이상회원이 이메일을 바꾸면 그 회원의 주문 행 수백 개를 모두 고쳐야 함한 사실이 여러 행에 중복
삽입 이상아직 주문이 없는 새 상품은 기록할 자리가 없음다른 사실 없이 기록 불가
삭제 이상상품의 유일한 주문을 지우면 상품 정보도 사라짐두 사실이 한 행에 묶임

이런 문제를 이상 현상이라 부릅니다. 하나라도 고치다 빠뜨리면 같은 회원의 이메일이 행마다 다른, 서로 모순된 데이터가 남습니다. 해결책은 "한 사실은 한 곳에만" 두도록 테이블을 쪼개는 것입니다.

정규화는 함수 종속을 기준으로 테이블을 쪼갠다

"어디서 쪼갤까"를 감이 아니라 규칙으로 정하려면 열 사이의 관계를 표현할 말이 필요합니다. 열 X의 값을 알면 열 Y의 값이 하나로 정해질 때, "Y는 X에 함수 종속된다"고 하고 X → Y로 적습니다. 이때 X를 결정자라 부릅니다.

앞의 한 테이블짜리 주문에서 보면 주문번호 → 회원번호, 회원번호 → 회원 이메일, 상품번호 → 상품명이 성립합니다. 회원 이메일은 주문이 아니라 회원에 대한 사실이므로, 회원번호에 종속되어 있습니다.

정규화는 이런 종속을 하나씩 살펴, 각 열이 자기 테이블의 키에만 직접 종속되도록 테이블을 나누는 과정입니다. 회원 이메일을 회원 테이블로, 상품명을 상품 테이블로 옮기면 각 사실은 한 행에만 남고, 이메일 변경은 행 하나만 고치면 됩니다.

정규화에는 단계가 있고, 단계마다 끊어 내는 종속의 종류가 다릅니다. 이 단계를 정규형이라 하며 다음 두 슬라이드에서 1NF부터 BCNF까지 차례로 봅니다.

1NF와 2NF: 원자값, 그리고 키 전체에 종속

1NF는 모든 칸에 값이 하나씩만 들어 있어야 한다는 규칙입니다. 장바구니 주문을 지원하려고 item_ids 칸에 "3,7,12"를 넣으면 위반입니다. "상품 7이 든 주문"을 찾을 수도, 상품별 수량을 적을 수도 없습니다. 상품마다 한 행씩, order_item(order_id, item_id, quantity) 테이블로 뺍니다.

이 order_item의 PK는 (order_id, item_id) 두 열입니다. 여기에 상품명을 함께 두면 상품명은 PK의 일부인 item_id만으로 정해집니다. 이를 부분 종속이라 하고, 이것을 없앤 상태가 2NF입니다. 상품명은 상품 테이블로 옮깁니다.

이 장의 예제는 단순하게 주문 하나에 상품 하나로 둡니다.

3NF와 BCNF: 키가 아닌 열을 거친 종속

주문 테이블에 member_email을 함께 두면 주문번호 → 회원번호 → 회원 이메일처럼 키가 아닌 열을 한 번 거쳐 결정됩니다. 이것이 이행 종속이고, 없앤 상태가 3NF입니다. 앞에서 본 갱신 이상의 원인이 바로 이것이었습니다.

실무 설계는 보통 3NF까지를 목표로 합니다.

BCNF는 "모든 결정자가 후보키여야 한다"는 더 엄격한 규칙입니다. 3NF를 지켜도 드물게 위반이 남습니다. 예를 들어 (회원, 상품) → 담당 상담원이고, 상담원 한 명이 상품 하나만 맡는다면 상담원 → 상품이 성립합니다. 상담원은 후보키가 아닌데 결정자이므로 BCNF 위반이고, (상담원, 상품) 테이블을 따로 둬야 합니다.

반정규화는 조인 비용을 쓰기 쪽으로 옮긴다

정규화할수록 테이블이 잘게 나뉘고, 화면 하나를 그리는 데 필요한 조인이 늘어납니다. 상품 목록이 초당 수천 번 조회되는데 매번 리뷰 테이블을 세어 리뷰 수를 붙인다면 읽기 비용이 커집니다.

반정규화는 이럴 때 일부러 중복을 들여 조회를 단순하게 만드는 것입니다. 상품 테이블에 review_count 열을 두고 리뷰가 달릴 때마다 1씩 올리는 식입니다.

중복의 정합성은 이제 내 책임입니다

원본이 바뀔 때 복사본을 함께 고치는 코드가 필요하고, 인기 상품의 카운터 한 행에 쓰기가 몰려 경합이 생깁니다. 측정된 병목이 있고 인덱스나 캐시로 안 될 때만 고릅니다.

주문 당시 가격은 중복이 아닙니다

주문에 결제 금액을 저장하는 것은 "그때 얼마였나"라는 다른 사실입니다. 상품 가격이 바뀌어도 함께 고치면 안 됩니다.

트랜잭션은 여러 쓰기를 한 덩어리로 묶는다

START TRANSACTION;

-- 1) 재고가 남아 있을 때만 하나 줄임
UPDATE item SET stock = stock - 1
 WHERE id = 7 AND stock >= 1;

-- 2) 주문 기록
INSERT INTO orders
  (member_id, item_id, quantity,
   amount, status, created_at)
VALUES (42, 7, 1, 15000, 'PAID', NOW());

COMMIT;  -- 실패하면 ROLLBACK

주문 하나는 "재고 줄이기"와 "주문 기록" 두 쓰기입니다. 첫 슬라이드의 장애 문제를 풀려면 둘을 쪼갤 수 없는 한 단위로 묶어야 합니다. 이 단위가 트랜잭션입니다.

START TRANSACTION으로 시작한 변경은 COMMIT으로 확정되고, 도중에 ROLLBACK하거나 장애가 나면 시작 전으로 모두 되돌아갑니다. 재고가 0이면 UPDATE가 0행을 바꾸므로, 앱은 이를 보고 롤백합니다.

ACID는 트랜잭션이 지키는 네 가지 약속이다

트랜잭션의 약속은 네 성질의 머리글자를 따 ACID라 부릅니다. 오른쪽 열은 InnoDB가 이를 지키는 장치로, 2부에서 하나씩 열어 봅니다.

성질약속주문에서 보면InnoDB의 장치
원자성(Atomicity)전부 반영 또는 전부 취소재고만 줄고 끝나지 않음Undo 로그
일관성(Consistency)제약 조건이 늘 지켜짐재고가 음수가 안 됨제약 조건 검사
격리성(Isolation)동시 실행이 서로 간섭 안 함남의 중간 상태를 못 봄MVCC와 락
지속성(Durability)커밋 결과는 장애에도 남음커밋 직후 정전에도 주문 유지Redo 로그

지금은 Undo 로그를 "바꾸기 전 값을 적어 둔 기록", Redo 로그를 "무엇을 바꿨는지 적어 둔 기록", MVCC를 "행의 옛 버전을 남겨 읽기에 보여 주는 방식" 정도로 알아 두면 됩니다.

2부

약속을 엔진이 어떻게 지키는가

1부에서 DBMS가 빠른 검색, 장애 복구, 동시성 제어를 약속한다고 했습니다. 이 부는 그 순서대로 인덱스와 옵티마이저, 로그, 격리와 락을 열어 보고, 마지막으로 서버 한 대를 넘어설 때 무엇을 내주는지 봅니다.

기초 원리 여기부터는 스토리지 엔진 내부 구조를 다룹니다.

DB는 행이 아니라 페이지를 읽는다

검색이 왜 느린지부터 셉니다. 3장에서 봤듯이 디스크는 바이트 하나가 아니라 덩어리 단위로 읽습니다. 그래서 InnoDB도 데이터를 페이지라는 고정 크기 덩어리로 저장하고, 기본 크기는 16KB입니다(innodb_page_size, PostgreSQL은 8KB). 행 하나가 필요해도 그 행이 든 페이지 전체를 읽습니다.

주문 행 하나가 약 200바이트라면 페이지 하나에 80행 정도가 들어갑니다. 주문 100만 건은 약 1만 2,500페이지입니다. "회원 7번의 주문"을 찾는데 아무 단서가 없다면 이 페이지를 전부 읽어야 합니다. 이렇게 테이블 전체를 훑는 것을 풀 스캔이라 합니다.

읽은 페이지는 메모리의 버퍼 풀에 캐시됩니다. 3장에서 본 근사 LRU로 관리되는 InnoDB의 페이지 캐시입니다. 1장의 메모리 계층 표대로 메모리 접근은 약 100ns, SSD 읽기는 수십~100µs라서 버퍼 풀에 없으면 수백 배 느려집니다.

그래서 조회 비용은 몇 개의 페이지를, 그중 몇 개를 디스크에서 읽는가로 결정됩니다. 남은 질문은 하나입니다. 1만 2,500페이지 대신 몇 페이지만 읽고 원하는 행에 닿을 수는 없을까요?

인덱스는 정렬해 둔 찾아보기다

두꺼운 책에서 "B+Tree"를 찾을 때 첫 장부터 넘기지 않고 맨 뒤의 찾아보기를 봅니다. 단어가 가나다순으로 정렬되어 있어 금방 찾고, 옆에 적힌 쪽 번호로 바로 갑니다.

인덱스는 DB의 찾아보기입니다. 특정 열의 값을 정렬된 상태로 따로 모아 두고, 각 값 옆에 실제 행을 찾아갈 단서를 붙입니다. 정렬되어 있으니 3장의 이분 탐색처럼 절반씩 버리며 찾을 수 있습니다.

그런데 단순히 정렬된 배열로 두면 문제가 있습니다. 주문이 들어올 때마다 정렬 순서를 지키려고 중간에 끼워 넣어야 하는데, 배열은 뒤쪽을 전부 밀어야 합니다. 디스크 위의 수만 페이지를 매번 밀 수는 없습니다.

찾기도 빠르고 끼워 넣기도 싸야 합니다. 3장의 결론은 디스크에서는 "넓고 얕은 트리"가 이긴다는 것이었습니다. 실제 DB 인덱스가 쓰는 그 트리를 봅니다.

B+Tree는 넓고 얕은 트리에 리프를 잇는다

3장의 B-Tree처럼 B+Tree도 노드 하나가 페이지 하나입니다. 맨 위 루트와 중간 브랜치 노드에는 "이 범위는 저 자식 페이지로"라는 안내만 있고, 실제 데이터는 맨 아래 리프에만 있습니다.

B-Tree와 다른 점은 둘입니다. 안내 노드에 키만 담아 한 페이지에 자식을 더 많이 달고, 리프끼리 옆으로 이어 둡니다. 그래서 범위 검색은 시작 리프까지 한 번 내려간 뒤 옆으로 읽기만 하면 됩니다.

페이지 세 번이면 수천만 행에 닿는다

안내 노드 한 칸은 키(BIGINT 8바이트)와 자식 페이지 번호 등 십여 바이트입니다. 16KB 페이지라면 한 노드가 자식을 1,000개 넘게 가리킵니다. 3장의 이진 트리는 자식이 둘이었습니다.

루트 아래에 브랜치 약 1,000개, 그 아래 리프 약 100만 개, 리프마다 주문 수십 행이면 높이 3에서 수천만 행에 닿습니다. 어떤 주문이든 페이지 3개만 읽으면 찾습니다.

게다가 루트와 브랜치는 모든 검색이 지나가므로 늘 버퍼 풀에 머뭅니다. 실제 디스크 읽기는 리프 하나, 많아야 두 번입니다.

새 주문이 들어오면 맞는 리프에 끼워 넣고, 리프가 꽉 차면 그 페이지만 둘로 나눕니다. 배열처럼 전체를 밀 필요가 없으므로 끼워 넣기도 싸집니다. 이 "나누기"는 PK 설계에서 다시 만납니다.

해시도 이진 트리도 아닌 이유

3장에서 본 다른 탐색 구조와 나란히 놓으면 B+Tree가 기본 인덱스가 된 이유가 보입니다. 해시는 등치 검색이 빠르지만 값의 순서를 잃고, 이진 트리는 순서를 지키지만 너무 높습니다.

구조등치 검색범위 검색, 정렬디스크 적합성
해시 테이블O(1)불가 (순서 없음)버킷 확장 시 재배치
균형 이진 트리O(log₂ N)가능높이가 커서 페이지 읽기 많음
B-TreeO(log N), 분기 큼가능하나 트리를 오르내림노드 = 페이지
B+TreeO(log N), 분기 큼리프만 순서대로 읽음안내 노드에 키만 있어 더 넓음

범위 조건(BETWEEN), 정렬(ORDER BY), 앞부분 일치(LIKE 'abc%')는 모두 "정렬된 순서로 이어 읽기"라서 B+Tree의 리프 순회 한 번으로 처리됩니다.

InnoDB 테이블 자체가 PK 인덱스다

이제 B+Tree의 리프에 무엇이 들어 있는지가 중요해집니다. InnoDB에서는 PK로 만든 B+Tree의 리프에 행 전체가 들어 있습니다. 테이블과 PK 인덱스가 따로 있는 것이 아니라, 테이블이 곧 PK 순서로 정렬된 B+Tree입니다. 데이터가 인덱스 순서대로 모여(cluster) 저장된다는 뜻에서 이를 클러스터드 인덱스라 부릅니다.

그래서 InnoDB 테이블에는 클러스터드 인덱스가 반드시 하나 있어야 합니다. PK를 선언하지 않으면 NOT NULL인 첫 UNIQUE 인덱스를 대신 쓰고, 그것도 없으면 InnoDB가 6바이트짜리 숨은 행 번호를 만들어 그 순서로 저장합니다. 이 숨은 키는 쿼리에서 쓸 수 없으므로 PK는 직접 정하는 편이 낫습니다.

PK로 찾는 쿼리는 이 트리 하나만 내려가면 행 전체에 닿습니다. WHERE id = 1234가 가장 빠른 조회인 이유입니다. 또 PK 범위 조회는 이웃한 행이 같은 페이지에 모여 있어 적은 페이지로 끝납니다.

그렇다면 PK가 아닌 열, 예를 들어 member_id로 찾을 때는 어떻게 될까요? 테이블은 PK 순서로 하나만 정렬될 수 있으므로, 다른 열의 순서는 별도 트리가 필요합니다. 다음 슬라이드의 주제입니다.

세컨더리 인덱스는 PK를 거쳐 행에 닿는다

PK 이외의 열에 만든 인덱스를 세컨더리 인덱스라 합니다. 이 트리의 리프에는 인덱스 열 값과 그 행의 PK 값이 들어 있습니다. 그래서 이메일로 회원을 찾으면 트리를 두 번 탑니다.

행 주소 대신 PK를 들고 있는 이유는, 페이지가 나뉘어 행이 다른 페이지로 옮겨 가도 PK는 그대로라서 세컨더리 인덱스를 고칠 필요가 없기 때문입니다.

그래서 PK는 짧고 늘 증가하는 값이 좋다

1부에서 미뤄 둔 질문에 답할 차례입니다. AUTO_INCREMENT PK는 늘 가장 큰 값이라 새 행이 항상 맨 오른쪽 리프 끝에 붙습니다. 페이지를 앞에서부터 차곡차곡 채웁니다.

반면 UUID(128비트 무작위 식별자, 문자열로 36자)의 흔한 버전인 v4는 값이 무작위라 이미 꽉 찬 중간 리프에 끼어들어야 합니다. 그때마다 페이지 분할이 일어나 반쯤 빈 페이지가 흩어지고, 같은 데이터에 더 많은 페이지와 버퍼 풀이 필요해집니다.

PK 크기는 모든 인덱스에 복사됩니다

세컨더리 인덱스 리프마다 PK가 들어가므로, 36자 문자열 PK는 8바이트 BIGINT보다 모든 인덱스를 크게 만듭니다.

외부에 보여 줄 ID가 따로 필요하다면

내부 PK는 BIGINT로 두고 UUID는 별도 UNIQUE 열로 두거나, 앞부분이 시각이라 시간순으로 증가하는 UUIDv7을 고려합니다.

복합 인덱스는 왼쪽 열부터 정렬된다

"회원 7번의 주문을 최신순으로"처럼 조건이 둘 이상이면 열 여러 개로 인덱스 하나를 만듭니다. 이것이 복합 인덱스입니다. (a, b, c) 인덱스는 전화번호부처럼 a로 정렬하고, a가 같으면 b로, b까지 같으면 c로 정렬합니다.

그래서 b만 주어지면 a가 정해지지 않아 트리에서 시작 위치를 잡을 수 없습니다. 이것이 왼쪽 접두 규칙입니다. 앞 열에 범위 조건이 걸리면 그 범위 안에서 b는 정렬되어 있지 않으므로 뒤 열도 탐색을 좁히지 못합니다.

조건 (인덱스 a, b, c)인덱스 활용
a = 1a로 탐색
a = 1 AND b = 2a, b로 탐색
b = 2 AND c = 3탐색에 못 씀
a = 1 AND c = 3a로 탐색, c는 걸러냄
a > 1 AND b = 2a 범위만 탐색

열 순서는 등치, 정렬, 범위 순으로 놓는다

열 순서를 정하려면 두 가지 말이 필요합니다. 카디널리티는 열에 있는 서로 다른 값의 개수입니다. 선택도는 조건 하나가 전체에서 걸러 내는 비율로, 남는 행이 적을수록 "선택도가 높다"고 합니다. 회원 번호는 값이 수십만 개라 조건 하나로 몇 행만 남지만, 주문 상태는 값이 몇 개뿐이라 조건을 걸어도 대부분이 남습니다.

  • 등치(=) 조건 열을 앞에. 여러 개면 늘 함께 쓰이고 선택도가 높은 열부터.
  • ORDER BY 열을 그다음에. 인덱스 순서대로 읽으면 따로 정렬할 필요가 없습니다.
  • 범위 조건 열은 마지막에. 범위 뒤의 열은 탐색에 못 쓰이기 때문입니다.

"선택도 높은 열이 무조건 앞"은 아닙니다. 그 열이 쿼리에 늘 등장하는지가 먼저입니다.

인덱스만 읽고 끝내는 커버링 인덱스

-- 인덱스: (member_id, created_at)

-- 1) 커버링 아님: amount 때문에 PK로 재탐색
SELECT created_at, amount FROM orders
WHERE member_id = 7;

-- 2) 커버링: 필요한 열이 모두 인덱스 안
SELECT id, created_at FROM orders
WHERE member_id = 7;
-- EXPLAIN의 Extra 칸: Using index

세컨더리 인덱스의 두 번째 탐색은 찾은 행마다 일어납니다. 1만 행이면 클러스터드 인덱스를 1만 번 따로 찾아갑니다.

쿼리가 쓰는 열이 모두 인덱스 안에 있으면 이 단계를 통째로 건너뜁니다. 이를 커버링 인덱스라 합니다. 리프에 PK가 들어 있으므로 id는 넣지 않아도 커버됩니다. 마지막 줄의 EXPLAIN은 DB의 실행 계획을 보여 주는 명령으로, 곧 자세히 봅니다.

열을 가공하면 인덱스의 순서를 못 쓴다

-- 인덱스: (created_at)
-- 나쁨: 모든 행에 DATE()를 적용해 봐야 함
WHERE DATE(created_at) = '2026-11-01'

-- 좋음: 열은 그대로, 범위로 바꿔 씀
WHERE created_at >= '2026-11-01'
  AND created_at < '2026-11-02'

-- 나쁨: 문자열 열과 숫자 비교
WHERE phone = 01012345678
-- 좋음
WHERE phone = '01012345678'

인덱스는 열의 원래 값으로 정렬되어 있습니다. DATE(created_at)의 결과 순서는 트리에 없으므로 DB는 모든 행에 함수를 적용해 봐야 합니다. 같은 뜻을 열을 건드리지 않는 범위 조건으로 바꾸면 인덱스를 탑니다.

타입이 다른 값을 비교하면 DB가 한쪽을 자동으로 바꾸는 암묵적 형변환이 일어납니다. MySQL은 문자열 열과 숫자를 비교할 때 열 쪽을 숫자로 바꾸므로, 결국 열을 가공한 것과 같아집니다.

시작 위치를 모르는 조건도 트리를 못 탄다

-- 앞부분 와일드카드: 시작 위치 모름
WHERE name LIKE '%민수'
-- 앞부분이 고정되면 범위 탐색 가능
WHERE name LIKE '김민%'

-- OR 한쪽에 인덱스가 없음
WHERE member_id = 7 OR memo = '급함'

-- 부정 조건: 남는 행이 대부분
WHERE status <> 'CANCELED'

LIKE의 %는 "아무 글자나 몇 개든"을 뜻하는 와일드카드입니다. '%민수'는 첫 글자를 모르니 정렬된 트리의 어디서 시작할지 정할 수 없습니다.

OR는 한쪽만 인덱스가 있어도 나머지 쪽을 찾으려면 결국 전체를 읽어야 합니다. 부정 조건은 인덱스를 쓸 수는 있어도 대부분의 행이 남아 이득이 없습니다. 이 판단을 실제로 내리는 것이 옵티마이저입니다.

옵티마이저는 비용을 추정해 계획을 고른다

1부에서 SQL은 무엇을 원하는지만 적는다고 했습니다. 같은 쿼리를 실행하는 방법은 여럿입니다. 풀 스캔할 수도 있고, 인덱스 A나 B를 쓸 수도 있으며, 조인이면 어느 테이블부터 읽을지도 골라야 합니다. 이 중 하나를 고르는 부품이 옵티마이저입니다.

MySQL 옵티마이저는 테이블의 행 수, 열 값의 분포 같은 통계로 방법마다 읽어야 할 페이지 수를 추정하고 비용이 가장 낮은 것을 고릅니다. 통계는 표본으로 대략 계산해 두는 값이라, 대량으로 지우거나 넣은 뒤에는 실제와 어긋날 수 있습니다. 그럴 때 ANALYZE TABLE orders로 다시 계산시킵니다.

놀라운 점은 인덱스가 있어도 풀 스캔을 고를 때가 있다는 것입니다. 세컨더리 인덱스로 찾은 행마다 PK로 다시 찾아가면, 그 페이지들은 디스크 여기저기에 흩어져 있어 한 장씩 따로 읽어야 합니다(무작위 읽기). 풀 스캔은 페이지를 이어진 순서대로 크게 묶어 읽으므로(순차 읽기) 페이지당 비용이 훨씬 쌉니다.

그래서 조건에 맞는 행이 테이블의 20~30%를 넘는 정도가 되면 순서대로 전체를 읽는 편이 더 쌀 수 있습니다. 앞에서 본 "선택도 낮은 열의 인덱스는 쓸모없다"는 말의 실제 근거가 이것입니다.

인덱스는 읽기를 사고 쓰기로 값을 치른다

인덱스가 그렇게 좋다면 모든 열에 만들면 될까요? 인덱스는 테이블과 별도의 B+Tree이므로, 주문 하나를 INSERT하면 클러스터드 인덱스와 모든 세컨더리 인덱스에 각각 키를 넣어야 합니다. 인덱스 열의 값을 바꾸는 UPDATE는 옛 키 삭제와 새 키 삽입을 함께 합니다.

인덱스가 다섯 개면 쓰기 한 번이 트리 여섯 개를 건드리고, 그 페이지들이 버퍼 풀 자리도 차지합니다. 그래서 쓰기가 많은 테이블은 실제로 쓰이는 인덱스만 남깁니다.

특히 (member_id)와 (member_id, created_at)처럼 한쪽이 다른 쪽의 왼쪽 접두와 같으면, 왼쪽 접두 규칙에 따라 긴 쪽이 짧은 쪽의 일을 다 하므로 짧은 쪽을 지웁니다.

EXPLAIN은 옵티마이저가 고른 계획을 보여 준다

mysql> EXPLAIN SELECT * FROM orders
    -> WHERE member_id = 7
    -> ORDER BY created_at DESC\G

  key: NULL

Extra: Using where; Using filesort

-- 인덱스 (member_id, created_at) 추가 후
 type: ref
  key: idx_member_created

쿼리 앞에 EXPLAIN을 붙이면 실행하지 않고 계획만 보여 줍니다. 끝의 \G는 결과를 세로로 펼쳐 보이는 MySQL 클라이언트 옵션입니다. type은 접근 방식, key는 고른 인덱스, rows는 읽을 것으로 추정한 행 수입니다.

처음에는 98만 행을 모두 읽고(ALL) 메모리나 임시 파일에서 따로 정렬합니다(filesort). 인덱스를 만들면 38행만 읽고, 인덱스를 거꾸로 훑어 최신순 정렬도 생략합니다.

조인의 기본은 Nested Loop다

  1. 바깥 테이블 걸러 읽기

    조건 m.id BETWEEN 1 AND 100에 맞는 회원 100명을 읽습니다.

  2. 안쪽 테이블 찾기

    회원 한 명마다 orders에서 member_id가 같은 행을 찾습니다.

  3. 짝지어 내보내기

    찾은 주문마다 회원 열과 붙여 결과 행을 만듭니다.

  4. 반복

    바깥 행 100개에 대해 2~3을 되풀이합니다.

조인도 실행 방법이 여럿이고 옵티마이저가 고릅니다. 가장 기본인 Nested Loop는 이중 반복문 그대로입니다. 바깥 행 하나마다 안쪽 테이블을 찾습니다.

안쪽의 member_id에 인덱스가 있으면 한 번 찾는 데 페이지 몇 개면 되어 100번이어도 금방 끝납니다. 인덱스가 없으면 100번 모두 주문 테이블을 풀 스캔합니다. 그래서 FK 열에는 인덱스를 둡니다(InnoDB는 FK 제약을 선언하면 없을 때 자동으로 만듭니다).

인덱스가 없으면 해시나 정렬로 조인한다

Hash Join은 작은 쪽 테이블로 조인 열의 해시 테이블(3장)을 만든 뒤, 큰 쪽을 한 번 훑으며 해시로 짝을 찾습니다. Sort-Merge는 양쪽을 조인 열로 정렬한 뒤 지퍼처럼 나란히 맞춰 갑니다.

알고리즘비용의 모양유리한 상황지원
Nested Loop바깥 행 수 × 안쪽 탐색바깥이 적고 안쪽에 인덱스MySQL, PostgreSQL
Hash Join양쪽 한 번씩 + 해시 메모리인덱스 없는 등치 조인MySQL 8.0.18+, PostgreSQL

주문 서비스처럼 짧은 트랜잭션이 초당 수천 번 오가는 시스템을 OLTP, 큰 데이터를 모아 집계하는 시스템을 OLAP이라 합니다. OLTP 쿼리는 대부분 인덱스를 탄 Nested Loop로 실행되고, Hash Join은 인덱스가 없는 조인이나 집계에서 등장합니다.

커밋할 때마다 데이터 파일에 쓰면 느리다

검색 다음은 두 번째 약속, 장애에도 커밋이 사라지지 않는 지속성입니다. UPDATE는 먼저 버퍼 풀의 페이지를 고칩니다. 디스크와 내용이 달라진 이 페이지를 더티 페이지라 합니다. 전원이 나가면 메모리는 사라지므로, 커밋 결과를 지키려면 언젠가 디스크에 써야 합니다.

"디스크에 썼다"도 생각보다 간단하지 않습니다. 프로그램이 write()를 호출하면 OS는 데이터를 일단 커널 메모리에 받아 두고 바로 돌아옵니다. 실제 디스크 기록은 나중입니다. 지금 당장 디스크에 내려 달라고 요구하는 시스템 콜(1장)이 fsync이고, 이 호출은 저장 장치가 기록을 마칠 때까지 기다리므로 비쌉니다.

가장 단순한 방법은 커밋마다 바뀐 페이지를 fsync하는 것입니다. 그러나 주문 하나가 재고 페이지, 주문 페이지, 인덱스 페이지 여러 장을 건드리고, 그 페이지들은 파일 여기저기에 흩어져 있습니다. 커밋마다 16KB 페이지 여러 장을 무작위 위치에 써야 합니다.

필요한 것은 "커밋 순간에는 적게, 순서대로 쓰고, 페이지는 나중에 모아 쓰는" 방법입니다. 그 답이 다음 슬라이드의 로그입니다.

커밋은 데이터가 아니라 로그를 쓴다

  1. 변경 전 값 기록

    이전 값을 Undo 로그에 남깁니다. 롤백과 MVCC가 이것을 씁니다.

  2. 버퍼 풀 수정

    메모리의 페이지만 고칩니다. 디스크의 데이터 파일은 아직 그대로입니다.

  3. Redo 로그 기록

    "어느 페이지의 어디를 어떻게 바꿨다"를 메모리의 로그 버퍼에 적습니다.

  4. COMMIT

    로그 버퍼를 Redo 로그 파일 끝에 쓰고 fsync한 뒤 성공을 응답합니다.

  5. 체크포인트

    더티 페이지는 나중에 모아 데이터 파일에 씁니다.

Redo 로그에는 페이지 전체가 아니라 바뀐 내용만 적으므로 작고, 항상 파일 끝에 순차로 덧붙입니다. 커밋 때는 이것만 fsync합니다.

데이터 파일보다 로그를 먼저 디스크에 쓴다는 이 규칙을 WAL이라 합니다. 반대 방향의 기록인 Undo 로그는 바꾸기 전 값을 담아 되돌리기에 씁니다.

재시작하면 Redo로 살리고 Undo로 되돌린다

커밋 직후 전원이 나갔다고 합시다. 데이터 파일에는 아직 옛 페이지가 있지만 Redo 로그에는 변경 내용이 있습니다. 재시작한 InnoDB는 로그를 다시 적용해 커밋된 변경을 살리고(지속성), 커밋되지 않은 트랜잭션은 Undo 로그로 되돌립니다(원자성).

로그가 끝없이 길어지면 복구도 길어집니다. 체크포인트는 더티 페이지를 데이터 파일에 써서 "여기까지는 파일에 반영됨"을 표시하는 작업으로, 복구는 그 지점부터 시작합니다.

동시에 실행되면 서로의 중간 상태가 보인다

세 번째 약속인 격리성으로 넘어갑니다. 트랜잭션을 하나씩 줄 세워 실행하면 서로 간섭할 일이 없습니다. 그러나 주문 서비스에는 초당 수백 개의 트랜잭션이 들어오고, 하나가 디스크를 기다리는 동안 나머지가 모두 멈춘다면 처리량이 바닥납니다. 그래서 DB는 트랜잭션을 동시에 실행합니다.

동시에 실행하면 한 트랜잭션이 다른 트랜잭션의 작업 중간을 보게 될 수 있습니다. 이렇게 생기는 대표적인 문제가 세 가지 있고, 영어 이름 그대로 Dirty Read, Non-Repeatable Read, Phantom Read라 부릅니다. 다음 두 슬라이드에서 재고와 주문으로 하나씩 재현합니다.

모든 문제를 막으려면 결국 줄 세우기에 가까워져 느려집니다. 그래서 SQL 표준은 "얼마나 막을지"를 네 단계로 정하고 고르게 했는데, 이것이 격리 수준입니다. 격리 수준은 결국 어떤 이상 현상까지 허용할지의 목록입니다.

세 현상을 먼저 보고, 그다음 격리 수준 표를 읽습니다.

Dirty Read는 아직 커밋되지 않은 값을 읽는 것이고, 그 값은 롤백되면 존재한 적 없는 값이 됩니다. Non-Repeatable Read는 한 트랜잭션 안에서 같은 행을 두 번 읽었는데 그사이 남이 커밋해 값이 달라지는 것입니다. 같은 데이터를 여러 번 읽어 맞춰 보는 정산에서 문제가 됩니다.

t1오늘 PAID 주문 수: 5

Phantom Read는 기존 행의 값은 그대로인데, 같은 조건으로 다시 조회하니 조건에 맞는 행의 집합이 달라지는 현상입니다. 유령(phantom)처럼 없던 행이 나타납니다.

Non-Repeatable Read와 달리 행 하나에 무언가를 걸어 두는 방식으로는 막을 수 없습니다. 아직 존재하지 않는 행이기 때문입니다. 이 차이가 뒤에서 갭 락이 필요한 이유가 됩니다.

MVCC는 읽기와 쓰기가 서로 기다리지 않게 한다

격리를 만드는 가장 직관적인 방법은 1장의 뮤텍스처럼 행을 잠그는 것입니다. 쓰는 동안 아무도 못 읽게 하면 Dirty Read는 사라집니다. 하지만 그러면 인기 상품의 재고 행을 누군가 바꾸는 동안 그 상품 화면을 보는 수천 건의 조회가 모두 줄을 섭니다.

MVCC의 발상은 행의 옛 버전을 남겨 두는 것입니다. 쓰는 트랜잭션은 새 버전을 만들고, 읽는 트랜잭션은 자기에게 보여도 되는 버전을 골라 읽습니다. 그러면 읽기는 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않습니다.

InnoDB는 이를 위해 트랜잭션마다 증가하는 번호(트랜잭션 ID)를 붙이고, 모든 행에 "마지막으로 바꾼 트랜잭션 ID"와 "이전 버전이 있는 Undo 로그 위치(롤 포인터)"를 숨은 열로 둡니다. 행을 바꿀 때는 제자리에서 고치고, 이전 값은 Undo 로그에 남겨 롤 포인터로 잇습니다.

그 결과 행마다 최신 버전에서 과거로 거슬러 올라가는 버전 체인이 생깁니다. 1부에서 Undo 로그를 "되돌리기용"이라 했는데, 그 같은 기록이 읽기에도 쓰이는 것입니다.

Read View로 보일 버전을 고른다

어떤 버전이 보여도 되는지는 Read View가 정합니다. Read View는 만들어진 순간 "이미 커밋된 트랜잭션"과 "아직 진행 중인 트랜잭션"의 목록을 적어 둔 스냅샷입니다.

읽기는 최신 버전부터 보면서, 그 버전을 만든 트랜잭션이 Read View 기준으로 커밋 전이면 건너뛰고 체인을 거슬러 올라갑니다. 그래서 읽기는 쓰기를 기다리지 않습니다.

스냅샷을 언제 찍느냐가 격리 수준을 가른다

InnoDB에서 READ COMMITTED와 REPEATABLE READ의 차이는 Read View를 만드는 시점뿐입니다.

  • READ COMMITTED: SELECT 문마다 새 Read View를 만듭니다. 그사이 커밋된 값이 보이므로 Non-Repeatable Read가 생깁니다.
  • REPEATABLE READ: 트랜잭션의 첫 읽기에서 만든 Read View를 끝까지 씁니다. 같은 SELECT는 같은 결과를 냅니다.

그래서 REPEATABLE READ의 일반 SELECT에는 Phantom도 보이지 않습니다. 나중에 들어온 행은 스냅샷에 없기 때문입니다.

PostgreSQL의 MVCC는 구조가 다릅니다

UPDATE 때 테이블 안에 새 행 버전을 통째로 쓰고, 옛 버전은 VACUUM이라는 정리 작업이 나중에 치웁니다. REPEATABLE READ는 스냅샷 격리라 Phantom이 없고, 같은 행을 동시에 고치면 한쪽을 직렬화 오류로 실패시켜 앱이 재시도하게 합니다.

긴 트랜잭션은 옛 버전을 붙잡아 둔다

MVCC에는 숨은 비용이 있습니다. Undo 로그의 옛 버전은 그것을 볼 수 있는 Read View가 하나라도 남아 있는 동안 지울 수 없습니다. 아무도 필요로 하지 않게 된 버전은 InnoDB의 백그라운드 작업인 퍼지가 치웁니다.

누군가 트랜잭션을 열어 둔 채 몇 시간 방치하면, 그 시점 이후 모든 행의 옛 버전이 쌓여 Undo 로그가 커지고 읽기도 긴 체인을 거슬러 올라가야 해서 느려집니다.

트랜잭션은 짧게, 끝은 반드시 닫습니다

SHOW ENGINE INNODB STATUS의 History list length가 계속 늘면 오래 열린 트랜잭션을 의심합니다. 이 원칙은 뒤의 락과 커넥션 풀에서도 다시 나옵니다.

스냅샷 읽기만으로는 재고 차감을 못 지킨다

시점AB
t1SELECT stock: 10
t2SELECT stock: 10
t3stock = 9 로 UPDATE, COMMIT
t4stock = 9 로 UPDATE, COMMIT
 두 개가 팔렸는데 재고는 9: 하나의 차감이 사라짐

MVCC 덕분에 읽기는 편해졌지만, 읽은 값을 근거로 다시 쓰는 경우는 다릅니다. 두 트랜잭션이 같은 재고를 스냅샷으로 읽고 각자 계산해 쓰면, 나중 쓰기가 먼저 쓰기를 덮어써 차감 하나가 사라집니다. 이를 갱신 손실이라 하며, InnoDB REPEATABLE READ는 이를 오류로 막아 주지 않습니다.

막으려면 "읽고 나서 쓸 때까지 남이 못 바꾸게" 해야 합니다. 이것이 락의 역할입니다.

공유 락과 배타 락, 그리고 FOR UPDATE

InnoDB의 행 락은 두 종류입니다. 공유 락(S)은 "내가 읽는 중이니 바꾸지 마라"로, 여럿이 함께 쥘 수 있습니다. 배타 락(X)은 "내가 바꾸니 아무도 잠그지 마라"로, 혼자만 쥡니다.

SELECT … FOR SHARE는 S 락, SELECT … FOR UPDATE와 UPDATE, DELETE는 X 락을 겁니다. 락은 커밋이나 롤백까지 유지되고, 기다림은 innodb_lock_wait_timeout(기본 50초)을 넘으면 오류로 끝납니다.

쥔 락 \ 요청S 락X 락
S 락함께 허용대기
X 락대기대기

락을 거는 읽기를 잠금 읽기라 합니다. 잠금 읽기는 스냅샷이 아니라 최신 커밋 값을 읽습니다. 락이 없는 일반 SELECT는 MVCC 스냅샷을 읽으므로 X 락이 걸린 행도 기다리지 않습니다.

잠금 읽기는 행 사이의 빈틈까지 잠근다

잠금 읽기에서 Phantom은 어떻게 막을까요? 아직 없는 행에는 락을 걸 수 없으니, InnoDB는 인덱스의 레코드 사이 빈 구간에 갭 락을 겁니다. 레코드 락과 그 앞 갭 락을 합친 것이 넥스트 키 락입니다.

갭에 INSERT가 들어올 수 없으니 잠금 읽기에서도 Phantom이 막힙니다. 주문 테이블의 member_id 인덱스로 보면 오른쪽과 같습니다.

스냅샷과 잠금 읽기를 섞으면 빈틈이 생긴다

정리하면 InnoDB REPEATABLE READ는 일반 SELECT의 Phantom은 스냅샷으로, 잠금 읽기의 Phantom은 넥스트 키 락으로 막습니다. 그래서 "상당 부분 막는다"고 했습니다. 남은 빈틈은 둘을 섞을 때 생깁니다.

A가 일반 SELECT로 오늘 주문 5건을 봅니다. B가 주문을 넣고 커밋합니다. A가 같은 조건으로 UPDATE하면, UPDATE는 잠금 읽기라 최신 데이터를 보므로 B의 주문까지 6건을 바꿉니다. 그다음 A의 SELECT에는 자기가 바꾼 그 행이 나타납니다.

교훈은 앞의 갱신 손실과 같습니다. 읽은 결과를 근거로 쓸 거라면 처음부터 잠금 읽기로 읽어야 합니다.

재고 차감을 지키는 세 가지 방법

-- 1) 조건부 UPDATE: 확인과 차감을 한 문장에
UPDATE item SET stock = stock - 1
 WHERE id = 7 AND stock >= 1;

-- 2) 비관적 락: 읽을 때부터 X 락
SELECT stock FROM item WHERE id = 7 FOR UPDATE;
UPDATE item SET stock = 9 WHERE id = 7;

-- 3) 낙관적 락: 쓸 때 버전이 그대로인지 확인
SELECT stock, version FROM item WHERE id = 7;
UPDATE item SET stock = 9, version = 6
 WHERE id = 7 AND version = 5;
-- 바뀐 행이 0이면 누가 먼저 바꿈: 재시도

1은 1부의 주문 트랜잭션에서 쓴 방식입니다. UPDATE가 X 락을 걸고 최신 값으로 조건을 확인하므로 단순 차감이면 이것으로 충분합니다.

읽은 값으로 복잡한 계산을 해야 하면 2나 3을 씁니다. 비관적 락은 충돌이 일어난다고 보고 미리 잠급니다. 낙관적 락은 DB 락 없이 버전 열로 쓰는 순간에 충돌을 감지합니다.

낙관이냐 비관이냐는 충돌 빈도로 고른다

두 방식의 비용은 서로 다른 곳에서 나옵니다. 비관적 락은 충돌이 없을 때도 기다림을 만들고, 낙관적 락은 충돌이 날 때마다 작업 전체를 다시 합니다.

기준비관적 락 (FOR UPDATE)낙관적 락 (버전 열)
충돌 처리뒤에 온 쪽이 기다림뒤에 쓴 쪽이 실패, 재시도
충돌이 드물 때불필요한 락 비용거의 공짜
충돌이 잦을 때순서대로 처리됨재시도 폭증
주의할 점락 대기, 데드락재시도 로직 필수
어울리는 곳선착순 한정 판매 재고회원 정보, 게시글 수정

JPA의 @Version이 낙관적 락을 자동으로 해 줍니다(6장). 서버 여러 대와 Redis까지 놓고 동시성 문제를 푸는 법은 8장에서 다룹니다.

DB 데드락은 엔진이 찾아서 끊는다

시점A (상품 1, 2 주문)B (상품 2, 1 주문)
t1상품 1 X 락 획득
t2상품 2 X 락 획득
t3상품 2 요청: 대기
t4상품 1 요청: 순환 대기
t5계속 진행오류 1213, 롤백

락이 있으면 1장의 데드락도 따라옵니다. 1장에서 본 네 조건(상호 배제, 점유 대기, 비선점, 순환 대기)이 행 락에서 그대로 성립합니다. 장바구니에 같은 두 상품을 다른 순서로 담은 두 주문이 서로를 기다립니다.

InnoDB는 1장의 "탐지와 회복" 전략을 씁니다. 대기 그래프에서 순환을 즉시 찾아(innodb_deadlock_detect 기본 ON) 바꾼 행이 적은 쪽을 롤백시키고 오류 1213을 돌려줍니다. 앱은 이 오류를 받으면 재시도해야 합니다.

서버 한 대는 세 가지 이유로 모자라게 된다

지금까지는 DB 서버가 한 대라고 가정했습니다. 주문 서비스가 커지면 이 가정이 세 방향에서 무너집니다.

첫째, 읽기가 넘칩니다. 상품 목록과 주문 내역 조회는 쓰기보다 수십 배 많고, 한 대의 CPU와 버퍼 풀로 감당할 수 없게 됩니다. 둘째, 쓰기와 용량이 넘칩니다. 하루 주문이 수천만 건이 되면 디스크 한 대의 쓰기 속도와 용량이 한계에 닿습니다. 셋째, 장애입니다. 서버가 한 대면 그 서버가 죽는 순간 주문이 멈춥니다.

더 큰 서버로 바꾸는 것도 방법이지만 값이 급격히 비싸지고, 언젠가 살 수 있는 가장 큰 서버에 닿으며, 장애 문제는 그대로입니다. 그래서 서버를 여러 대로 늘립니다.

읽기와 장애에는 데이터를 통째로 복사해 두는 레플리케이션, 쓰기와 용량에는 데이터를 나눠 담는 샤딩으로 대응합니다. 그리고 여러 대가 되는 순간 "모든 서버가 같은 값을 보는가"라는 새 문제가 생기는데, 이 부의 마지막에 CAP로 정리합니다.

레플리케이션은 변경 로그를 보내 다시 실행한다

레플리케이션은 쓰기를 받는 Primary의 데이터를 복사본 서버인 Replica에 계속 옮기는 것입니다. Primary는 커밋된 변경을 binlog라는 파일에 순서대로 남기고, Replica는 이를 받아 자기 쪽 relay log에 쌓은 뒤 차례로 다시 실행합니다. MySQL의 기본은 비동기 복제라서 Primary는 Replica를 기다리지 않고 커밋 응답을 돌려줍니다.

비동기 복제는 빠른 대신 지연과 유실이 있다

Replica를 여러 대 두고 조회를 나눠 보내면 읽기 처리량이 늘어납니다. 쓰기는 Primary 한 곳에서만 받습니다. 이것이 읽기/쓰기 분리입니다. Primary가 죽으면 Replica 하나를 새 Primary로 올리는데, 이를 승격이라 합니다.

비동기의 대가는 둘입니다. Replica는 늘 조금 늦으므로 방금 쓴 데이터가 Replica에 없을 수 있고(복제 지연), Primary가 죽으면 아직 전송되지 않은 커밋은 승격한 Replica에 없습니다.

비동기Primary 커밋 즉시장애 시 유실 가능
반동기Replica 하나가 수신 확인한 뒤왕복 지연 추가
동기Replica 반영 확인 뒤가장 느림, Replica 장애가 쓰기를 막음
 MySQL은 반동기(semisynchronous) 복제를 플러그인으로 지원합니다. 수신만 확인하므로 유실은 막고 지연은 최소로 늘립니다.

파티셔닝은 한 서버 안에서 테이블을 나눈다

복제는 데이터를 통째로 복사하므로 쓰기와 용량 문제는 그대로입니다. 먼저 해 볼 수 있는 것은 큰 테이블을 한 서버 안에서 여러 조각으로 나누는 파티셔닝입니다. 행을 나누면 수평, 자주 안 쓰는 큰 열을 별도 테이블로 떼면 수직 파티셔닝입니다.

주문 테이블을 created_at 기준 월별로 수평 파티셔닝하면, 겉으로는 테이블 하나지만 내부는 월마다 따로 된 B+Tree입니다.

얻는 것은 둘입니다. 조건에 날짜가 있으면 해당 월의 파티션만 읽습니다(파티션 프루닝). 그리고 1년 지난 주문을 지울 때 수억 행을 DELETE하는 대신 DROP PARTITION으로 파일 하나를 지웁니다.

한계도 분명합니다. 날짜 조건이 없는 쿼리는 모든 파티션을 뒤지고, 무엇보다 서버가 여전히 한 대입니다. 쓰기와 용량을 늘리려면 서버 자체를 나눠야 합니다.

샤딩은 행을 여러 서버에 흩는다

샤딩은 행을 여러 DB 서버에 나눠 담는 수평 분할입니다. 각 서버(샤드)는 전체의 일부만 가지므로 쓰기와 용량이 서버 수만큼 늘어납니다. 복제로는 늘릴 수 없는 쓰기를 늘리는 거의 유일한 방법입니다.

행이 어느 샤드로 갈지는 샤드 키라는 열로 정합니다. 키 값을 범위로 나누거나, 해시해서 나누거나, 별도 조회 테이블에 위치를 적어 둡니다.

방식장점약점
범위범위 조회가 한 샤드에서 끝남최신 범위에 쓰기 몰림
해시고르게 분산샤드 추가 시 대량 이동
디렉터리위치를 자유롭게 지정조회 테이블이 병목

NoSQL은 관계를 덜어 내고 분산을 얻는다

RDBMS에서 쓰기를 늘리려면 샤딩이라는 큰 공사가 필요했습니다. 그렇다면 처음부터 여러 서버에 나눠 담도록 설계한 저장소는 어떨까요? 그 계열을 묶어 NoSQL이라 부르며, 데이터 모델에 따라 넷으로 나뉩니다.

Redis는 메모리에 키-값을 두는 저장소로 8장에서, DynamoDB는 AWS의 관리형 키-값 DB로 15장에서 자세히 봅니다.

무엇을 얻고 무엇을 내주는지로 고른다

NoSQL이 분산을 쉽게 얻은 비결은 RDBMS가 비싸게 제공하던 것을 덜어 낸 데 있습니다. 대부분 조인을 지원하지 않거나 제한하고, 여러 행(여러 서버)에 걸친 트랜잭션도 약하거나 없습니다. 데이터가 키 하나로 찾아갈 수 있는 단위에 모여 있으면 그 단위째 아무 서버에나 둘 수 있기 때문입니다.

그래서 설계 방식도 반대입니다. RDBMS는 데이터를 정규화해 두고 쿼리가 필요할 때 조인으로 엮습니다. NoSQL은 "어떤 화면이 어떤 키로 무엇을 읽는가"라는 접근 패턴을 먼저 정하고, 그 패턴에 맞게 데이터를 미리 묶어(반정규화해) 저장합니다. 나중에 새 조회 방식이 생기면 데이터를 다시 만들어야 할 수도 있습니다.

주문 서비스로 보면 주문, 결제, 재고처럼 여러 테이블이 함께 바뀌고 정합성이 중요한 데이터는 RDBMS가 맞습니다. 반대로 장바구니, 최근 본 상품, 세션처럼 키 하나로 읽고 쓰며 양이 많은 데이터는 키-값 저장소가 맞습니다. 실제 서비스는 둘을 함께 씁니다.

여러 서버에 나눠 담는 순간, RDBMS든 NoSQL이든 피할 수 없는 질문이 하나 생깁니다. 서버 사이 통신이 끊기면 어떻게 할 것인가입니다.

CAP: 네트워크가 끊기면 둘 중 하나를 내준다

분산 저장소가 원하는 세 성질이 있습니다. 모든 노드가 같은 최신 값을 보는 일관성(C), 모든 요청이 응답을 받는 가용성(A), 노드 사이 통신이 끊긴 네트워크 분할 중에도 동작하는 분할 내성(P)입니다.

분할은 고를 수 있는 것이 아니라 언젠가 반드시 일어납니다. 그래서 CAP의 실제 의미는 분할이 생겼을 때 C와 A 중 무엇을 포기하느냐입니다.

CAP의 C는 ACID의 C가 아니다

두 약어에 같은 "일관성"이 들어 있어 혼동하기 쉽습니다. ACID의 일관성은 트랜잭션 전후로 제약 조건(재고 ≥ 0, FK)이 지켜진다는 뜻입니다. 서버가 한 대여도 의미가 있습니다.

CAP의 일관성은 여러 복제본이 있을 때 어떤 노드에 물어도 가장 최근에 완료된 쓰기를 돌려준다는 뜻입니다. 이를 엄밀하게는 선형성이라 부릅니다. 앞의 비동기 복제 Replica는 이 성질을 만족하지 않습니다.

분할 시 선택동작어울리는 데이터
CP반대편과 확인 못 하면 오류결제, 재고
AP옛 값일 수 있어도 응답상품 조회수, 장바구니
 틀린 답이 돈 문제가 되는 데이터는 CP, 잠깐 틀려도 응답이 중요한 데이터는 AP 쪽이 맞습니다.

PACELC: 평소에는 지연과 일관성을 고른다

CAP는 장애 순간만 말합니다. 그런데 분할이 없는 평소에도 선택이 있습니다. 쓰기 때 다른 노드의 확인을 기다리면 일관되지만 느리고, 기다리지 않으면 빠르지만 잠시 어긋납니다.

PACELC는 이를 "분할(P)이면 A와 C 중, 그 외(Else)에는 지연(Latency)과 C 중 선택"으로 정리합니다. 앞에서 본 MySQL 비동기 복제는 평소에 L을 고른 것입니다.

L을 고른 시스템이 주는 약속이 최종 일관성입니다. "새 쓰기가 멈추면 결국 모든 복제본이 같아진다"는 약속이며, 언제인지는 보장하지 않습니다.

Cassandra나 DynamoDB의 기본 설정이 PA/EL 쪽, 동기 복제를 쓰는 RDB가 PC/EC 쪽에 가깝습니다. 다만 많은 제품이 요청 단위로 일관성 수준을 고르게 해 주므로 분류는 설정에 따라 달라집니다.

3부

원리로 장애를 설명하고 고친다

주문 서비스를 운영에 올리면 느린 쿼리, 데드락, 연결 고갈, 복제 지연을 만납니다. 2부의 페이지와 인덱스, 락, 복제 지식으로 각 장애가 왜 일어났는지 설명하고, 무엇을 측정해 어떻게 고치는지 따라갑니다.

원리 실무 설정값, 진단 명령, 장애 사례와 대응을 다룹니다.

느린 쿼리는 먼저 기록하게 한다

[mysqld]
slow_query_log      = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time     = 0.5
# 인덱스를 안 쓴 쿼리도 기록 (양이 많아 선택)
log_queries_not_using_indexes = OFF

"API가 느리다"는 신고가 오면 어느 쿼리가 범인인지부터 찾아야 합니다. MySQL의 슬로 쿼리 로그는 실행 시간이 기준을 넘은 쿼리를 파일에 남깁니다.

기본값은 꺼져 있고, 기준 long_query_time도 10초라 웹 서비스에는 너무 깁니다. 운영에서는 켜 두고 기준을 1초 이하로 낮춥니다. 로그의 Rows_examined(읽은 행 수)가 돌려준 행 수보다 훨씬 크면 인덱스를 의심합니다.

사례: 주문 목록 API가 2초씩 걸린다

# Query_time: 2.31  Rows_examined: 1204533
SELECT * FROM orders
WHERE member_id = 123 AND status = 'PAID'
ORDER BY created_at DESC LIMIT 20;

mysql> EXPLAIN …
 type: ref   key: idx_status
 rows: 1204533
 Extra: Using where; Using filesort

"내 주문 목록" API의 쿼리가 슬로 로그에 잡혔습니다. 20행을 돌려주려고 120만 행을 읽었습니다.

EXPLAIN을 보면 옵티마이저는 status 단독 인덱스를 골랐습니다. 그런데 PAID는 전체 주문의 대부분이라 선택도가 낮습니다. 그 결과 PAID 주문 120만 행을 PK로 재탐색하며 읽고, member_id는 읽은 뒤에 걸러 내고(Using where), 정렬도 따로 합니다(filesort).

인덱스 하나로 120만 행을 20행으로

ALTER TABLE orders
  ADD INDEX idx_member_status_created
  (member_id, status, created_at);

mysql> EXPLAIN …
 type: ref   key: idx_member_status_created
 rows: 20
 Extra: Backward index scan

# Query_time: 0.003  Rows_examined: 20

-- 쓰이지 않게 된 idx_status는 확인 후 제거
ALTER TABLE orders
  ALTER INDEX idx_status INVISIBLE;

2부의 규칙대로 등치 열 둘을 앞에, 정렬 열을 뒤에 둡니다. 인덱스 안에서 이미 created_at 순이므로 뒤에서부터 20개만 읽고 멈춥니다.

InnoDB의 온라인 DDL은 인덱스를 추가하는 동안에도 읽기와 쓰기를 막지 않지만 I/O를 크게 씁니다. 트래픽이 적은 시간에 합니다. 옛 인덱스는 바로 지우지 않고 INVISIBLE로 옵티마이저에게서만 숨겨 영향이 없는지 본 뒤 지웁니다. 다시 살리기는 즉시 됩니다.

데드락은 없애기보다 줄이고 재시도한다

데드락이 났다면 SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK 절에서 두 트랜잭션이 어떤 락을 쥐고 무엇을 기다렸는지 봅니다. 이 절은 마지막 한 건만 보여 주므로, innodb_print_all_deadlocks를 켜 모든 데드락을 에러 로그에 남겨 둡니다.

락을 쓰는 동시 실행이 있는 한 데드락을 0으로 만들 수는 없습니다. 목표는 빈도를 줄이고, 났을 때 안전하게 다시 하는 것입니다.

  • 락 순서 통일: 장바구니 상품을 잠글 때 늘 상품 id 오름차순으로. 순환 대기 조건이 깨집니다.
  • 트랜잭션은 짧게: 락을 쥔 시간이 짧을수록 겹칠 확률이 줄어듭니다.
  • 인덱스 확인: 조건 열에 인덱스가 없으면 훑은 모든 행에 락이 걸립니다.
  • 재시도: 1213은 잠깐 기다렸다(백오프) 트랜잭션 전체를 다시 실행합니다.

사례: 없는 행을 잠그면 갭 데드락이 난다

시점트랜잭션 A트랜잭션 B
t1id=50 FOR UPDATE (없음)
t2id=50 FOR UPDATE (없음)
t3INSERT id=50: 대기
t4INSERT id=50: 데드락

"장바구니 행이 있으면 수량을 늘리고, 없으면 넣는다"를 FOR UPDATE로 구현할 때 자주 터집니다. 없는 행을 잠그면 2부에서 본 갭 락이 걸리는데, 갭 락끼리는 서로 막지 않아 둘 다 성공합니다. 갭 락의 목적은 INSERT를 막는 것뿐이기 때문입니다. 그런데 둘 다 INSERT하려 하면 상대의 갭 락을 기다려야 하므로 순환이 생깁니다.

UNIQUE 키를 두고 INSERT … ON DUPLICATE KEY UPDATE로 바꿉니다. 키가 겹치면 그 자리에서 UPDATE로 바뀌는 한 문장이라 사이에 끼어들 틈이 없습니다.

커넥션 풀은 비싼 연결을 재사용한다

지금까지는 DB 안을 봤습니다. 장애의 상당수는 앱과 DB 사이의 연결에서 납니다. DB 연결 하나를 새로 맺으려면 TCP 핸드셰이크(2장), 사용자 인증, 세션 초기화를 거쳐야 하고, MySQL 서버는 연결마다 스레드와 메모리를 씁니다. 요청마다 연결을 열고 닫으면 이 비용을 매번 냅니다.

커넥션 풀은 연결을 미리 열어 두고, 요청이 오면 빌려주었다가 끝나면 돌려받습니다. 1장의 스레드 풀과 같은 발상입니다. Spring Boot의 기본 풀 구현은 HikariCP입니다.

풀의 크기는 곧 DB에 동시에 보낼 수 있는 일의 상한입니다. 그 크기와 대기 시간을 어떻게 정하느냐가 이어지는 세 슬라이드의 주제입니다.

풀 설정은 크기, 대기 한도, 수명이다

maximumPoolSize는 풀이 가질 최대 연결 수입니다. 빈 연결이 없으면 요청 스레드는 줄을 서고, connectionTimeout만큼 기다려도 못 받으면 예외로 끝납니다.

DB 서버는 오래 쉬는 연결을 스스로 끊습니다(MySQL wait_timeout, 기본 8시간). 그 사이에 방화벽이나 프록시가 먼저 끊기도 합니다. 끊긴 연결을 빌려주지 않도록 maxLifetime을 그보다 짧게 두어 연결을 주기적으로 새로 맺습니다.

HikariCP 설정기본값의미
maximumPoolSize10최대 연결 수
minimumIdle최대와 같음고정 크기 풀 권장
connectionTimeout30초빌리기 대기 한도
maxLifetime30분DB·중간 장비의 끊기 전에 교체

풀 크기는 크다고 좋지 않다

필요한 연결 수는 리틀의 법칙으로 어림합니다. 시스템 안에 동시에 있는 일의 수는 초당 도착 수 × 하나가 머무는 시간입니다. 초당 1,000건, 건당 연결을 5ms 쥔다면 동시에 5개면 충분합니다.

DB 쪽에서 실제로 동시에 일할 수 있는 수는 CPU 코어와 디스크가 정합니다. HikariCP 문서는 출발점으로 코어 수 × 2 + 유효 디스크 수를 제시합니다. 그보다 크면 DB 안에서 컨텍스트 스위칭(1장)과 락 경합만 늘어납니다.

합계는 DB 기준으로 계산합니다

앱 서버 20대가 풀 50개씩이면 DB에는 연결 1,000개가 붙습니다. MySQL이 받는 연결 상한 max_connections는 기본 151입니다. 서버 대수를 자동으로 늘리는 Auto Scaling(14장)과 함께 계산해야 합니다.

사례: 트랜잭션 안의 외부 호출이 풀을 말린다

요청 스레드커넥션 풀
트랜잭션 시작 getConnection() 대여 10개 중 1개
외부 결제 API 응답 대기 3초 (연결은 쥔 채)
새 요청 getConnection()남은 연결 0개, 대기열에 줄 섬 고갈
30초 뒤 SQLTransientConnectionException

주문 트랜잭션 안에서 결제 API를 호출했습니다. 리틀의 법칙으로 연결 10개, 건당 3초면 초당 3.3건이 한계입니다. 그 이상이 오면 요청을 처리하는 Tomcat 스레드(기본 200개, 6장)가 모두 연결을 기다리며 멈추고, 30초 뒤 연결을 못 받았다는 예외가 쏟아집니다.

해법은 풀을 키우는 것이 아니라 외부 호출을 트랜잭션 밖으로 빼는 것입니다. connectionTimeout도 수 초로 줄여 빨리 실패하게 합니다.

사례: 방금 바꾼 이름이 옛날 값으로 보인다

애플리케이션DB
저장 클릭 UPDATE name='새이름' Primary
COMMIT OK Primary
화면 새로고침 SELECT name Replica
옛 값 표시 '옛이름'복제 지연 0.8초, 아직 미적용 Replica

읽기/쓰기 분리에서 "내가 쓴 것을 내가 바로 읽는" 경우가 깨지는 문제로, read-after-write 일관성 문제라 부릅니다. 평소 수 밀리초인 지연도 Primary에 대량 배치가 돌면 Replica가 그만큼을 다시 실행해야 해서 수십 초로 벌어집니다.

Spring에서는 읽기 전용으로 표시한 트랜잭션을 Replica로 보내도록 구성하곤 하며, 그 표시(readOnly)는 6장에서 봅니다.

복제 지연은 피하거나 감추거나 걸러 낸다

복제 지연을 없앨 수는 없으므로, 지연이 문제가 되는 읽기만 골라 다르게 처리합니다.

  • 피하기: 방금 쓴 사용자의 읽기, 결제 확인처럼 정확해야 하는 조회는 몇 초간 Primary로 보냅니다.
  • 감추기: 저장 응답에 바뀐 값을 담아 돌려주면 화면이 Replica를 읽을 일이 없습니다.
  • 걸러 내기: 지연이 큰 Replica는 읽기 대상에서 잠시 뺍니다.

지연은 Replica에서 SHOW REPLICA STATUS를 실행해 Seconds_Behind_Source로 봅니다. Replica가 적용 중인 변경이 Primary에서 몇 초 전에 일어났는지를 뜻합니다(MySQL 8.0.22 이전 이름은 Seconds_Behind_Master).

이 값이 꾸준히 늘면 Replica의 적용 속도가 Primary의 쓰기를 못 따라가는 것이므로, 큰 배치를 잘게 나누거나 Replica의 사양을 올립니다.

샤드 키는 되돌리기 가장 어려운 결정이다

주문이 더 늘어 샤딩을 하기로 했다면, 샤드 키를 고르는 기준은 세 가지입니다.

  • 분포: 값이 많고 고르게 퍼져야 합니다. 생성 시각을 범위로 쓰면 모든 새 쓰기가 최신 샤드 하나에 몰립니다.
  • 쿼리 지역성: 대부분의 쿼리가 키를 포함해야 한 샤드에서 끝납니다. 아니면 모든 샤드에 물어야 합니다.
  • 트랜잭션 경계: 함께 바뀌는 데이터가 같은 샤드에 있어야 합니다.

주문 서비스라면 member_id가 흔한 선택입니다. "내 주문 목록"과 주문 생성이 한 샤드에서 끝납니다. 대신 "오늘 전체 주문 집계"는 모든 샤드를 돌아야 하므로 별도 분석 저장소로 보냅니다.

키를 나중에 바꾸려면 모든 데이터를 옮겨 담아야 합니다. 또 hash % N은 샤드 수 N이 바뀌면 거의 모든 행의 위치가 바뀝니다. 이 이동을 일부로 줄이는 일관성 해싱은 8장에서 다룹니다.

정리

  • 관계형 모델은 사실을 한 곳에 두고 키로 잇습니다. 정규화는 함수 종속을 기준으로 중복을 없애고, 반정규화는 병목이 측정될 때만 씁니다.
  • 조회 비용은 읽는 페이지 수입니다. B+Tree는 넓고 얕은 트리와 연결된 리프로 등치와 범위 검색을 페이지 몇 개로 끝냅니다.
  • InnoDB 테이블은 PK 인덱스 그 자체입니다. 세컨더리 인덱스는 PK를 거쳐 행에 닿으므로 PK 설계, 열 순서, 커버링이 성능을 가릅니다.
  • 원자성과 지속성은 로그가, 격리성은 MVCC와 락이 만듭니다. 커밋은 Redo 로그만 순차로 쓰고, 읽고 나서 쓸 때는 잠금 읽기를 씁니다.
  • DB를 여러 대로 늘리는 순간 일관성을 일부 내줍니다. 복제 지연과 CAP, PACELC가 그 대가를 설명합니다.
  • 운영 장애의 대부분은 원리로 설명됩니다. 느린 쿼리는 인덱스, 풀 고갈은 긴 트랜잭션, 옛 값은 복제 지연에서 옵니다.

스스로 점검 (1)

  1. 주문 테이블에 회원 이메일을 함께 저장하면 어떤 정규형을 어기고, 무슨 문제가 생기나요?

    주문번호 → 회원번호 → 이메일의 이행 종속이 생겨 3NF를 어깁니다. 회원이 이메일을 바꾸면 주문 행을 모두 고쳐야 하는 갱신 이상이 생깁니다.

  2. 해시 인덱스가 등치 검색에 더 빠른데도 기본 인덱스가 B+Tree인 이유는?

    해시는 값의 순서를 잃어 범위 검색, 정렬, 앞부분 LIKE를 처리할 수 없습니다. B+Tree는 등치도 페이지 3~4개로 끝나면서 연결된 리프로 범위를 순서대로 읽습니다.

  3. 인덱스 (a, b)가 있을 때 WHERE b = 1 쿼리는 왜 느릴까요?

    인덱스는 a로 먼저 정렬되어 있어 b만으로는 시작 위치를 정할 수 없습니다. 왼쪽 접두 규칙에 따라 탐색에 쓰이지 못합니다.

  4. 세컨더리 인덱스로 10만 행을 읽는 쿼리가 풀 스캔보다 느릴 수 있는 이유는?

    행마다 PK로 클러스터드 인덱스를 다시 무작위 탐색하기 때문입니다. 비율이 크면 순차로 전체를 읽는 편이 싸고, 커버링 인덱스면 이 비용이 사라집니다.

스스로 점검 (2)

  1. 커밋할 때 데이터 페이지 대신 Redo 로그만 디스크에 쓰는데도 지속성이 보장되는 이유는?

    재시작 시 Redo 로그를 다시 적용하면 버퍼 풀에만 있던 변경을 복원할 수 있기 때문입니다. 로그는 작고 순차로 쓰여 페이지를 무작위로 쓰는 것보다 훨씬 빠릅니다.

  2. InnoDB REPEATABLE READ에서 일반 SELECT가 Phantom을 보지 않는 이유는?

    첫 읽기 때 만든 Read View를 트랜잭션 끝까지 쓰므로, 이후 커밋된 행은 스냅샷에 보이지 않습니다.

  3. 재고 차감을 "SELECT로 읽고 계산해서 UPDATE"로 하면 무엇이 문제인가요?

    두 트랜잭션이 같은 값을 읽고 각자 써서 하나의 차감이 사라지는 갱신 손실이 생깁니다. 조건부 UPDATE, FOR UPDATE, 버전 열 중 하나로 막아야 합니다.

스스로 점검 (3)

  1. DB 데드락 오류를 받은 애플리케이션은 무엇을 해야 하나요?

    롤백된 트랜잭션 전체를 짧은 백오프 뒤 다시 실행합니다. 마지막 문장만 다시 실행하면 앞의 변경이 이미 취소된 상태라 틀린 결과가 됩니다.

  2. 트래픽이 늘어 풀 고갈이 나면 maximumPoolSize를 올리면 될까요?

    대개 아닙니다. 연결을 오래 쥐는 원인(긴 트랜잭션, 외부 호출, 느린 쿼리)을 먼저 없애야 하고, 풀을 키우면 DB의 동시 실행 한계와 max_connections에 부딪힙니다.

  3. Primary가 죽어 Replica를 승격했더니 마지막 몇 건의 주문이 사라졌습니다. 왜일까요?

    비동기 복제는 Replica 전송을 기다리지 않고 커밋 응답을 주므로, 전송 전 커밋은 Replica에 없습니다. 반동기 복제로 이 위험을 줄일 수 있습니다.
