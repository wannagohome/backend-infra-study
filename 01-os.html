요청 하나가 기계 안에서 겪는 일

이 부에서 풀 질문은 둘입니다. 주문 요청 하나가 서버에 도착하면 기계 안에서 누가 무엇을 하는가, 그리고 그 사이에 운영체제는 왜 끼어 있어야 하는가. 시리즈의 첫 장이므로 컴퓨터를 이루는 부품부터 차근차근 시작합니다.

이 장 내내 따라갈 주문 API 서버

이 장은 구체적인 서버 하나를 끝까지 따라갑니다. 8코어 CPU와 16GB 메모리를 가진 Linux 서버 한 대에서 Java로 만든 주문 API 서버가 돌고 있다고 합시다. 사용자가 주문 버튼을 누르면 이 서버로 "주문을 만들어 달라"는 HTTP 요청이 옵니다. HTTP는 웹에서 요청과 응답을 주고받는 약속이며 2장에서 자세히 봅니다.

서버는 요청마다 아래 다섯 단계를 거칩니다. 이 중 데이터베이스(DB) 조회와 결제 호출은 남의 컴퓨터가 답할 때까지 기다리는 일이고, 재고 차감은 CPU가 직접 하는 계산입니다. 기다림과 계산의 구분이 이 장 전체에서 계속 중요해집니다.

  1. 요청 도착네트워크 카드가 받음
  2. 재고 조회DB 응답을 기다림
  3. 재고 차감메모리에서 계산
  4. 결제 호출외부 서버를 기다림
  5. 응답 전송결과를 돌려줌

요청은 하드웨어와 커널을 거쳐 코드에 닿는다

  1. 패킷 도착

    네트워크 카드(NIC)가 전선으로 들어온 데이터 조각, 즉 패킷을 받습니다.

  2. CPU 호출

    NIC가 인터럽트라는 신호로 CPU에 "데이터가 왔다"고 알립니다.

  3. 커널이 정리

    운영체제의 핵심부인 커널이 데이터를 그 연결의 버퍼(임시 저장 공간)에 쌓습니다.

  4. 스레드 깨움

    이 연결을 기다리던 스레드를 깨우고, 스케줄러가 CPU를 내줍니다.

  5. 코드 실행

    우리 Java 코드가 돌다가 DB를 부르면 답이 올 때까지 다시 잠듭니다.

서버 코드는 요청이 "그냥 들어온다"고 느끼지만, 실제로는 하드웨어와 운영체제가 여러 단계를 대신 처리한 결과입니다. 여기 나온 인터럽트, 커널, 스레드, 스케줄러는 지금은 이름만 알아 두면 되고, 이 장에서 하나씩 정의합니다.

서버가 느려질 때 원인은 대개 이 경로에 있습니다. CPU를 못 받거나, 메모리가 모자라거나, I/O를 기다리느라 멈춰 있습니다. 그래서 이 시리즈는 가장 아래층인 운영체제에서 출발합니다. 먼저 기계를 이루는 부품부터 봅니다.

컴퓨터는 네 종류의 부품으로 이루어진다

CPU는 명령을 실제로 실행하는 부품입니다. 요즘 CPU 하나에는 독립적으로 명령을 실행하는 코어가 여러 개 들어 있어, 주문 서버의 8코어는 동시에 8개의 일을 할 수 있다는 뜻입니다.

메인 메모리(RAM)는 실행 중인 프로그램과 데이터를 담는 곳으로, 전원이 꺼지면 내용이 사라집니다. 그래서 오래 남길 데이터는 SSD나 HDD 같은 저장 장치에 둡니다. 네트워크 카드처럼 바깥과 데이터를 주고받는 부품은 입출력(I/O) 장치입니다.

CPU는 명령을 하나씩 가져와 실행한다

우리가 짠 Java 코드는 결국 CPU가 알아듣는 단순한 명령들, 즉 기계어로 바뀌어 메모리에 놓입니다. "메모리의 이 위치를 읽어라", "두 값을 더하라", "저 위치로 건너뛰어라" 같은 명령입니다.

CPU는 다음에 실행할 명령의 위치를 PC(프로그램 카운터)라는 칸에 기억하고, 계산 중인 값은 CPU 안의 아주 작고 빠른 저장 칸인 레지스터에 둡니다. PC와 레지스터의 값이 곧 "지금 어디까지 실행했는가"이고, 실행을 멈췄다 이어 갈 때 바로 이 값을 저장합니다.

  1. 가져오기

    PC가 가리키는 메모리 위치에서 명령 하나를 읽어 옵니다.

  2. 해석하기

    그 명령이 덧셈인지, 메모리 읽기인지, 건너뛰기인지 알아냅니다.

  3. 실행하기

    레지스터의 값으로 계산하거나 메모리를 읽고 씁니다.

  4. 다음으로

    PC를 다음 명령 위치로 옮기고 처음으로 돌아갑니다. 이 순환이 초당 수십억 번 일어납니다.

운영체제는 하드웨어를 나누고, 지키고, 감춘다

기계 한 대에서 주문 서버, 로그 수집기, 모니터링 프로그램이 함께 돈다고 합시다. 운영체제가 없다면 각 프로그램이 디스크 장치를 직접 조작하는 코드를 갖고, CPU를 언제 넘길지 서로 약속하고, 남의 메모리를 건드리지 않도록 스스로 조심해야 합니다. 프로그램 하나의 실수가 기계 전체를 멈추게 됩니다.

운영체제(OS)는 이 일을 대신 맡는 소프트웨어입니다. 그 핵심부, 즉 항상 메모리에 올라와 있으면서 하드웨어를 직접 다루는 부분을 커널이라고 부릅니다. 이 시리즈의 서버는 대부분 Linux 커널 위에서 돕니다.

커널이 하는 일은 세 가지로 묶을 수 있습니다. 첫째, CPU 시간과 메모리를 여러 프로그램에 나눠 줍니다. 둘째, 한 프로그램이 다른 프로그램이나 커널을 망가뜨리지 못하게 지킵니다. 셋째, 디스크의 물리적 위치나 네트워크 카드의 조작법 같은 복잡한 세부를 파일, 프로세스, 소켓 같은 단순한 개념 뒤로 감춥니다.

이 장의 나머지는 이 세 가지를 하나씩 풀어 가는 과정입니다. 1부는 겉으로 보이는 모습을, 2부는 커널이 내부에서 그 약속을 지키는 방법을, 3부는 약속의 한계가 운영 중인 서버에서 어떻게 드러나는지를 봅니다. 먼저 "나눠 줄" 자원 중 가장 기본인 CPU와 메모리의 속도 차이부터 확인합니다.

CPU는 빠르고, 나머지는 모두 느리다

 L1, L3는 CPU 안의 작은 메모리(캐시)로 다음 슬라이드에서 봅니다. 하드웨어마다 다르므로 자릿수만 기억하면 됩니다.

시간 단위부터 정리합니다. 1ms(밀리초)는 1,000분의 1초, 1µs(마이크로초)는 100만분의 1초, 1ns(나노초)는 10억분의 1초입니다. 3GHz CPU는 1초에 30억 번 박자를 치므로 한 박자가 약 0.3ns입니다.

그런데 메인 메모리에서 값을 가져오는 데 약 100ns, 즉 CPU 박자로 수백 번이 걸립니다. SSD는 그보다 1,000배, HDD는 읽는 머리를 원판 위로 옮기는 탐색 때문에 다시 수십 배 느립니다. 오른쪽 열은 이 격차를 사람의 시간으로 늘려 본 것입니다.

작고 빠른 저장소를 층층이 쌓는다

빠른 메모리는 비싸서 작게만 만들 수 있고, 크고 싼 메모리는 느립니다. 그래서 컴퓨터는 CPU 가까이에 작고 빠른 저장소를, 멀리 크고 느린 저장소를 층층이 둡니다. 이것이 메모리 계층입니다.

CPU 안의 작은 메모리인 캐시는 메인 메모리 일부의 복사본을 들고 있습니다. 찾는 값이 캐시에 있으면 캐시 히트, 없어서 아래층까지 내려가야 하면 캐시 미스입니다. 성능 튜닝의 대부분은 느린 층에 덜 내려가게 만드는 일입니다.

캐시는 지역성에 기대어 동작한다

// 행 우선: 메모리에 놓인 순서대로 읽음
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++) sum += a[i][j];

// 열 우선: 매번 한 행 크기만큼 건너뜀
for (j = 0; j < N; j++)
  for (i = 0; i < N; i++) sum += a[i][j];

캐시는 두 경향에 기댑니다. 방금 쓴 데이터는 곧 또 쓰고(시간 지역성), 어떤 데이터를 쓰면 바로 옆 데이터도 곧 씁니다(공간 지역성).

그래서 CPU는 메모리를 한 바이트씩이 아니라 대부분 64바이트 묶음으로 가져오며, 이 묶음이 캐시 라인입니다. 2차원 배열은 메모리에 행 단위로 이어 놓이므로 위쪽 루프는 가져온 라인을 끝까지 쓰고, 아래쪽 루프는 매번 새 라인을 가져옵니다. N이 크면 몇 배 차이가 납니다.

히트율 몇 %가 평균 속도를 몇 배로 바꾼다

캐시가 얼마나 중요한지 숫자로 보겠습니다. 캐시 접근에 1ns, 메인 메모리 접근에 100ns가 걸린다고 하고, 메모리 읽기 중 찾는 값이 캐시에 있는 비율을 히트율이라고 합시다.

히트율이 99%면 평균 접근 시간은 0.99×1 + 0.01×100 = 약 2ns입니다. 90%로 떨어지면 0.9×1 + 0.1×100 = 약 11ns가 됩니다. 히트율이 9%포인트 줄었을 뿐인데 평균은 다섯 배 넘게 느려집니다. 미스 한 번의 값이 히트의 100배라서, 드문 미스가 평균을 지배하기 때문입니다.

이 계산은 CPU 캐시에만 해당하지 않습니다. 4장에서 볼 DB 버퍼 풀(디스크 데이터를 메모리에 두는 영역)이나 8장의 캐시 서버도 "빠른 층에서 얼마나 자주 찾느냐"가 성능을 정하는 같은 구조입니다. 메모리 계층을 봤으니, 이제 CPU가 훨씬 느린 장치를 어떻게 기다리는지로 넘어갑니다.

장치를 기다리는 두 방법: 폴링과 인터럽트

주문 서버가 디스크에 로그를 쓰거나 네트워크로 데이터를 받을 때, 장치는 CPU보다 수천에서 수백만 배 느립니다. 그러면 CPU는 장치의 작업이 끝났는지 어떻게 알까요?

첫 번째 방법은 CPU가 장치의 상태를 계속 물어보는 폴링입니다. 단순하지만, 확인하는 동안 CPU는 다른 일을 못 하고 대부분의 확인은 "아직"이라는 답으로 끝나 시간을 버립니다.

두 번째 방법은 장치가 일을 마치면 CPU에 직접 신호를 보내는 인터럽트입니다. CPU는 평소에 다른 일을 하다가 신호가 오면 잠시 멈추고 처리한 뒤 돌아옵니다. 초인종이 울릴 때만 문으로 가는 셈입니다. 현대 컴퓨터는 주로 인터럽트를 쓰고, 패킷이 초당 매우 많이 들어올 때만 폴링을 섞어 인터럽트 처리 부담을 줄입니다.

인터럽트는 저장, 처리, 복귀 순으로 처리된다

인터럽트가 오면 CPU는 앞에서 본 PC와 레지스터를 먼저 저장합니다. 그래야 처리 후 하던 일을 정확히 그 자리에서 이어 갈 수 있습니다. 그다음 커널 안의 정해진 처리 코드인 인터럽트 핸들러로 건너뜁니다.

장치가 보내는 것이 하드웨어 인터럽트이고, 0으로 나누기 같은 실행 오류나 프로그램이 일부러 커널을 부르는 명령으로 생기는 것은 소프트웨어 인터럽트(예외, trap)입니다. 특히 하드웨어 타이머는 몇 밀리초마다 인터럽트를 걸어, 프로그램이 CPU를 붙잡고 있어도 커널이 주기적으로 제어권을 되찾게 합니다.

  1. 신호 발생

    장치나 타이머가 인터럽트 요청을 CPU에 보냅니다.

  2. 상태 저장

    CPU가 실행 중이던 프로그램의 PC와 레지스터를 저장합니다.

  3. 핸들러 실행

    커널의 인터럽트 핸들러로 건너뛰어 받은 데이터 등을 처리합니다.

  4. 복귀

    저장한 상태를 되살려 하던 일로 돌아가거나, 커널이 다른 일을 고릅니다.

유저 모드와 커널 모드로 권한을 나눈다

커널의 "지키기"는 CPU의 도움을 받습니다. 주문 서버의 버그 하나가 디스크 장치를 엉뚱하게 조작하거나 커널 메모리를 덮어쓰면 기계 전체가 멈춥니다. 그래서 CPU는 실행 권한을 두 단계로 나눕니다.

애플리케이션은 유저 모드에서 돌아 장치 조작 같은 위험한 명령을 실행할 수 없고, 커널은 모든 명령을 쓸 수 있는 커널 모드에서 돕니다. 유저 코드가 파일을 읽으려면 커널에 부탁해야 하는데, 이 정해진 부탁 창구가 시스템 콜입니다.

시스템 콜은 번호와 trap으로 커널을 부른다

시스템 콜은 함수 호출처럼 보이지만 다릅니다. 프로그램은 원하는 시스템 콜의 번호와 인자를 레지스터에 넣고 CPU의 특별한 명령(x86-64에서는 syscall)을 실행합니다. 이 명령이 소프트웨어 인터럽트, 즉 trap을 일으켜 CPU를 커널 모드로 바꾸고 커널의 처리 코드로 건너뜁니다.

커널은 인자가 올바른지, 권한이 있는지 검사한 뒤 일을 하고, 결과를 유저 메모리에 복사하고 돌아갑니다. Java의 파일 읽기나 소켓 쓰기도 내부에서는 결국 이 시스템 콜이 됩니다.

시스템 콜하는 일주문 서버에서
open파일을 열고 번호를 받음설정 파일 읽기
read, write데이터를 읽고 씀요청 받기, 응답 보내기
accept새 연결을 받아들임클라이언트 접속
close다 쓴 것을 반납연결 종료
clone새 실행 흐름을 만듦스레드 생성

시스템 콜은 공짜가 아니다

시스템 콜 한 번에는 모드 전환, 레지스터 저장과 복원, 인자 검사, 데이터 복사가 따라붙습니다. 보통 함수 호출이 몇 ns인 데 비해 시스템 콜은 그보다 수십에서 수백 배 무거운 왕복입니다. 게다가 커널 코드가 도는 동안 CPU 캐시 내용이 바뀌어, 돌아온 뒤 유저 코드도 한동안 느려집니다.

그래서 고성능 프로그램은 시스템 콜 횟수를 줄이는 쪽으로 설계됩니다. 1바이트씩 read()하지 않고 큰 덩어리를 한 번에 읽어 메모리 버퍼에 담아 두는 것이 대표적입니다. Java의 BufferedInputStream(입력을 내부 버퍼에 모아 읽는 클래스)이나 로그를 모아 한 번에 쓰는 비동기 로거가 같은 이유로 존재합니다.

연결 수천 개를 하나씩 확인하는 대신 "준비된 연결만 알려 달라"고 한 번에 묻는 epoll도 같은 발상이며 2부 끝에서 자세히 봅니다. 이제 커널이 프로그램을 어떤 단위로 관리하는지, 즉 프로세스로 넘어갑니다.

프로세스는 실행 중인 프로그램이다

$ java -jar order-api.jar &
[1] 4321
$ ps -o pid,nlwp,rss,cmd -p 4321
  PID NLWP     RSS CMD
 4321  215 2203648 java -jar order-api.jar

디스크에 있는 order-api.jar는 그저 파일, 즉 프로그램입니다. 이를 실행하면 운영체제가 코드를 메모리에 올리고 필요한 자원을 붙여 주는데, 이렇게 실행 중인 상태가 프로세스입니다. 같은 프로그램을 두 번 실행하면 프로세스가 두 개 생깁니다.

커널은 프로세스마다 번호(PID)를 붙여 구분합니다. 주문 서버는 PID 4321이고, NLWP(스레드 수)가 215, RSS(실제로 차지한 물리 메모리, KB 단위)가 약 2.1GB입니다. 스레드는 곧 봅니다.

프로세스의 메모리는 용도별 영역으로 나뉜다

커널은 프로세스마다 독립된 메모리 공간을 줍니다. 메모리는 1바이트 칸이 길게 늘어선 것이고, 각 칸의 번호를 주소라고 합니다. 프로세스의 주소 공간은 용도별 영역으로 나뉩니다.

Code에는 기계어 명령이, Data와 BSS에는 프로그램 내내 사는 전역 변수가 놓입니다(초기값이 있으면 Data, 없으면 BSS). 이 셋은 실행 전에 크기가 정해집니다. 실행 중에 크기가 변하는 두 영역, Stack과 Heap은 다음 슬라이드에서 봅니다.

스택은 호출 동안만, 힙은 쓰는 동안 계속

주문 서버의 createOrder() 메서드가 호출되면 그 지역 변수(주문 수량, 반복문 카운터)와 "끝나면 돌아갈 위치"가 한 묶음으로 스택에 쌓입니다. 이 묶음이 스택 프레임이고, 메서드가 끝나면 통째로 사라집니다. 할당과 해제가 맨 위 위치를 옮기는 것뿐이라 매우 빠르지만, 크기가 정해져 있어 재귀가 너무 깊으면 넘칩니다(Java의 StackOverflowError).

반면 메서드가 끝난 뒤에도 살아 있어야 하는 것, 예컨대 새로 만든 Order 객체는 힙에 둡니다. 힙은 크기와 수명이 실행 중에 정해지는 데이터를 담는 넓은 영역이라, 어디가 비었는지 관리하고 다 쓴 객체를 치워야 합니다. Java에서는 GC가 아무도 가리키지 않는 객체를 자동으로 치우며, 원리는 5장에서 봅니다.

이 구분은 곧 볼 스레드에서 다시 중요해집니다. 그 전에, 프로세스가 생겨나 사라지기까지 어떤 상태를 오가는지부터 봅니다.

프로세스는 다섯 가지 상태를 오간다

프로세스가 늘 CPU 위에 있지는 않습니다. 막 만들어지면 생성, CPU만 주면 돌 수 있으면 준비, 지금 CPU 위에 있으면 실행, 디스크나 네트워크의 응답을 기다려 CPU를 줘도 할 일이 없으면 대기, 끝나면 종료입니다.

준비 상태인 것들이 줄 선 목록을 준비 큐라고 합니다. 주문 서버가 DB 응답을 기다리면 대기로 가고, 응답이 도착해 인터럽트가 오면 준비로 돌아와 다시 CPU 차례를 기다립니다.

스레드는 프로세스 안의 실행 흐름이다

주문 서버에는 동시에 수백 명이 주문합니다. 요청을 하나씩만 처리하면 앞 요청이 DB를 기다리는 동안 뒤 요청은 모두 줄을 서야 합니다. 그래서 한 프로세스 안에 실행 흐름을 여러 개 둡니다. 이 흐름 하나가 스레드이고, 앞의 NLWP 215가 바로 스레드 수입니다.

같은 프로세스의 스레드들은 Code, Data, Heap, 열린 파일을 공유하지만 Stack과 레지스터(PC 포함)는 각자 가집니다. 각자 다른 메서드의 다른 줄을 실행하므로 호출 기록과 실행 위치는 공유할 수 없기 때문입니다.

멀티프로세스 대신 멀티스레드를 쓰는 이유

여러 요청을 함께 처리하려면 요청마다 프로세스를 띄우거나(멀티프로세스), 한 프로세스에 스레드를 여럿 둡니다(멀티스레드). 프로세스끼리는 메모리가 분리되어 커널이 마련한 통로인 IPC(2부에서 봄)로만 데이터를 주고받고, 스레드끼리는 같은 힙 변수를 바로 읽고 씁니다.

기준멀티프로세스멀티스레드
생성 비용메모리 공간을 새로 만듦스택만 새로 만듦
데이터 공유IPC가 필요함힙 변수를 바로 공유
장애 격리하나가 죽어도 나머지 생존한 스레드가 프로세스를 죽임
동기화공유가 적어 단순함경쟁 상태를 직접 막아야 함

공유가 훨씬 싸므로 Tomcat(Java 웹 애플리케이션을 실행하는 서버, 6장) 같은 서버는 요청을 스레드로 처리합니다. 대신 여러 스레드가 같은 데이터를 동시에 바꿔 값이 꼬이는 경쟁 상태를 막을 책임이 생기며, 이것이 2부의 주제입니다.

동시성과 병렬성은 다르다

주문 서버에는 스레드가 215개 있지만 CPU 코어는 8개뿐입니다. 한 코어는 한 순간에 한 흐름만 실행하므로, 같은 순간에 실제로 도는 스레드는 최대 8개입니다. 나머지는 준비 큐에서 차례를 기다리거나 I/O를 기다리며 대기 상태에 있습니다.

그런데도 215개가 모두 나아가는 것처럼 보이는 것은 커널이 아주 짧은 간격으로 실행 대상을 바꾸기 때문입니다. 여러 일이 번갈아 조금씩 진행되어 함께 나아가는 것을 동시성, 여러 코어에서 말 그대로 같은 순간에 실행되는 것을 병렬성이라고 합니다. 코어가 하나여도 동시성은 있지만 병렬성은 없습니다.

이 구분은 3부의 스레드 수 계산에서 핵심이 됩니다. 계산만 하는 스레드는 코어 수보다 늘려도 빨라지지 않고, 기다리는 스레드는 코어 수보다 훨씬 많아도 됩니다. 실행 대상을 바꾸는 방법은 2부 첫머리에서 보고, 그 전에 프로세스가 파일과 연결을 다루는 방식을 봅니다.

Linux에서는 모든 것이 파일이다

커널의 "감추기"가 가장 잘 드러나는 곳이 파일입니다. Linux는 디스크 파일뿐 아니라 네트워크 연결(소켓), 프로세스 사이의 통로(파이프), 터미널까지 모두 "열고, 읽고, 쓰고, 닫는" 같은 방식으로 다룹니다. 그래서 "모든 것은 파일"이라고 말합니다.

무엇을 열든 커널은 작은 정수 하나를 돌려주는데, 이것이 파일 디스크립터(fd)입니다. 프로세스는 이후 read(3, …)처럼 이 번호로 대상을 가리킵니다. 실제 대상의 정보는 커널이 쥐고, 프로세스는 번호표만 가집니다.

파일 이름은 inode를 가리키는 이정표다

디스크 파일의 내용은 디스크의 고정 크기 칸인 블록(보통 4KB)에 흩어져 담기고, 권한, 소유자, 크기, 수정 시각, 그리고 내용이 어느 블록에 있는지는 inode라는 기록에 담깁니다. inode마다 번호가 있습니다.

그러면 파일 이름은 어디 있을까요? 디렉터리도 특별한 파일이고, 그 내용은 "이름과 inode 번호"의 목록입니다. 즉 파일 이름은 inode를 가리키는 이정표일 뿐이라, 한 inode에 이름을 여러 개 붙이는 링크도 가능합니다(9장).

디스크는 블록 단위로 읽고 커널이 캐시해 둔다

주문 서버가 로그 파일에서 100바이트만 읽어도 디스크는 블록 단위로 읽고 씁니다. 장치가 바이트 단위 접근을 지원하지 않고, 한 번 다녀오는 비용이 커서 큰 덩어리를 한 번에 옮기는 편이 낫기 때문입니다.

커널은 디스크에서 읽은 블록을 메인 메모리에 남겨 두는데, 이 영역을 페이지 캐시라고 합니다. 같은 파일을 다시 읽으면 디스크까지 가지 않고 메모리에서 복사해 줍니다. 쓰기도 일단 페이지 캐시에 쓰고 나중에 디스크로 내려보내 빠릅니다. 대신 그사이 전원이 나가면 사라질 수 있어, 데이터를 확실히 남겨야 하는 DB는 fsync라는 시스템 콜로 디스크 기록을 강제합니다(4장).

Linux에서 free 명령을 치면 "buff/cache"가 크게 보이는 이유가 이것입니다. 커널은 놀고 있는 메모리를 페이지 캐시로 쓰다가 프로그램이 메모리를 원하면 내줍니다. 메모리 계층의 원리가 디스크 앞에서 한 번 더 반복되는 것입니다.

클라이언트 연결 하나가 fd 하나다

소켓은 네트워크 통신의 끝점을 나타내는 커널 객체입니다. 지금은 "다른 기계와 이어진 파일" 정도로 알아 두면 되고, 데이터가 실제로 오가는 방식은 2장에서 봅니다. 포트는 한 기계 안에서 어느 프로그램에게 갈 데이터인지 가르는 번호입니다.

서버 입장에서 중요한 사실은 클라이언트 연결 하나가 fd 하나라는 점입니다. 동시에 300명이 접속하면 주문 서버는 fd를 300개 넘게 엽니다. fd 수에는 한도가 있어서, 3부에서 이 한도가 장애로 이어지는 모습을 봅니다.

  1. socket()

    통신 끝점인 소켓을 만들고 fd를 받습니다(예: 3번).

  2. bind()

    이 소켓에 포트 번호 8080을 붙입니다.

  3. listen()

    이 포트로 오는 연결을 받겠다고 커널에 알립니다.

  4. accept()

    연결이 하나 들어올 때마다 그 연결 전용의 새 fd를 돌려줍니다.

  5. read, write, close

    그 fd로 요청을 읽고 응답을 쓰고, 끝나면 닫아 반납합니다.

2부

커널은 약속을 어떻게 지키는가

1부에서 커널은 세 가지를 약속했습니다. 8개 코어로 215개 스레드가 모두 도는 것처럼, 프로세스마다 메모리를 혼자 쓰는 것처럼, 느린 I/O를 기다려도 CPU가 놀지 않는 것처럼. 이 부는 그 약속을 지키는 장치와, 스레드가 힙을 공유하며 생기는 문제를 봅니다.

기초 원리 여기부터는 커널이 내부에서 무엇을 저장하고 바꾸는지 다룹니다.

커널은 PCB로 프로세스를 기억한다

1부에서 커널은 짧은 간격으로 실행 대상을 바꾼다고 했습니다. 멈췄던 흐름을 나중에 정확히 이어 가려면, 멈춘 순간의 PC와 레지스터, 즉 "어디까지 했는지"를 어딘가 적어 둬야 합니다.

커널은 프로세스마다 PCB라는 자료구조를 만들어 이 정보를 보관합니다. 스레드도 각자 실행 위치를 가진 실행 단위이므로 스레드마다 TCB가 있습니다. Linux는 둘을 같은 구조체(task_struct)로 다룹니다.

컨텍스트 스위칭은 이렇게 일어난다

  1. 계기 발생

    타이머 인터럽트, I/O나 락 대기, 더 급한 흐름의 등장.

  2. 현재 상태 저장

    실행 중이던 흐름의 PC와 레지스터를 PCB에 씁니다.

  3. 다음 대상 선택

    스케줄러가 준비 큐에서 다음 흐름을 고릅니다.

  4. 새 상태 복원

    다른 프로세스라면 메모리 주소 공간(페이지 테이블)도 바꿉니다.

  5. 실행 재개

    복원한 PC 위치부터 이어서 실행합니다.

실행 중인 흐름을 내리고 다른 흐름을 올리는 과정이 컨텍스트 스위칭입니다. 계기는 1부에서 본 것들입니다. 타이머 인터럽트로 할당 시간이 끝났거나, 스레드가 I/O나 락을 기다리느라 대기 상태로 갔거나, 더 급한 흐름이 준비 상태가 된 경우입니다.

저장과 복원을 하는 동안 CPU는 애플리케이션 일을 전혀 하지 않습니다. 주문 서버처럼 스레드가 DB를 기다리며 수시로 잠드는 서버에서는 초당 수천에서 수만 번 일어나는 것이 보통입니다.

스레드 전환이 프로세스 전환보다 싼 이유

레지스터를 저장하고 복원하는 직접 비용은 둘이 비슷합니다. 차이는 주소 공간에서 납니다. 다른 프로세스로 바꾸면 메모리 지도인 페이지 테이블(2부 중반에 봄)이 바뀝니다. CPU에는 주소 변환 결과를 기억하는 작은 캐시인 TLB가 있는데, 지도가 바뀌면 이 기억이 쓸모없어져 비워야 합니다. 최신 CPU는 항목마다 프로세스 표시(PCID)를 붙여 전부 비우는 일을 줄입니다.

더 큰 것은 간접 비용인 캐시 오염입니다. 새로 올라온 흐름의 데이터는 캐시에 없으므로 한동안 미스가 이어지고, 1부의 히트율 계산대로 미스가 조금만 늘어도 평균 속도는 크게 떨어집니다. 같은 프로세스의 스레드끼리는 힙을 공유해 이 손해가 덜합니다.

직접 비용은 수 마이크로초 수준이지만, 스레드가 많아 전환이 잦으면 간접 비용이 쌓여 처리량이 줄어듭니다. 3부의 "스레드를 늘렸더니 느려졌다"가 이 이야기입니다. 그러면 커널은 다음 흐름을 어떤 기준으로 고를까요?

스케줄링은 목표끼리 부딪치는 문제다

준비 큐에서 다음에 CPU를 줄 흐름을 고르는 일이 CPU 스케줄링이고, 이를 맡은 커널 부분이 스케줄러입니다. 목표는 여럿입니다. 단위 시간에 끝내는 일의 양(처리량)을 늘리고, 요청이 들어와 첫 반응이 나오기까지의 시간(응답 시간)을 줄이고, 누구도 지나치게 오래 굶기지 않아야 합니다.

이 목표들은 부딪칩니다. 처리량만 보면 전환을 줄여야 하고, 응답 시간을 보면 자주 바꿔 줘야 합니다. 또 프로그램은 CPU를 연속으로 쓰는 구간과 I/O를 기다리는 구간이 번갈아 나오는데, 주문 서버처럼 계산이 짧고 기다림이 긴 작업과 영상 변환처럼 계산만 긴 작업을 함께 공평하게 다루기는 쉽지 않습니다.

또 하나의 갈림길은 실행 중인 흐름에서 CPU를 강제로 빼앗을 수 있느냐입니다. 빼앗을 수 있으면 선점형, 스스로 내놓을 때까지 기다리면 비선점형입니다. 1부의 타이머 인터럽트가 선점을 가능하게 합니다. 이제 고전 알고리즘을 숫자로 비교합니다.

짧은 작업을 먼저 하면 평균 대기가 준다

실행 시간이 24ms, 3ms, 3ms인 작업 셋이 이 순서로 도착했다고 합시다. 도착 순서대로 처리하는 FCFS에서는 각 작업이 0, 24, 27ms를 기다려 평균 대기가 17ms입니다. 긴 작업 하나 뒤에 짧은 작업들이 줄줄이 막힌 것입니다.

짧은 작업부터 처리하는 SJF로 순서를 3, 3, 24로 바꾸면 대기는 0, 3, 6ms, 평균 3ms입니다. 평균 대기를 최소로 만드는 순서지만, 실행 시간을 미리 알아야 하고 짧은 작업이 계속 오면 긴 작업은 차례가 오지 않습니다.

방식(처리 순서)각 작업의 대기평균 대기
FCFS (24, 3, 3)0, 24, 27ms17ms
SJF (3, 3, 24)0, 3, 6ms3ms
 세 작업이 같은 시각에 도착했고 전환 비용은 없다고 가정한 계산입니다.

고전 스케줄링 알고리즘의 장단점

SJF에 선점을 더해, 새로 온 작업의 남은 시간이 더 짧으면 바로 바꾸는 것이 SRT(Shortest Remaining Time)입니다. 중요도 순으로 주는 Priority, 정해진 시간씩 돌아가며 주는 Round Robin도 있습니다. 특정 작업이 끝없이 밀리는 현상을 기아 상태라고 하며, 오래 기다린 작업의 우선순위를 서서히 올리는 에이징으로 막습니다.

알고리즘방식장점약점
FCFS먼저 온 순서, 비선점단순함긴 작업 뒤에 줄이 막힘

타임 슬라이스는 짧아도 길어도 문제다

Round Robin에서 한 번에 주는 시간을 타임 슬라이스라고 합니다. 너무 길면 앞 작업이 다 쓸 때까지 기다려야 해 FCFS처럼 응답이 늦어지고, 너무 짧으면 일하는 시간보다 전환에 쓰는 시간이 커집니다. 예컨대 전환에 0.01ms가 들 때 슬라이스가 0.1ms면 시간의 약 9%가 전환에 쓰입니다.

그래서 실제 운영체제는 고정 규칙 하나를 쓰지 않습니다. 교과서의 MLFQ는 우선순위가 다른 큐를 여러 개 두고, 받은 시간을 다 쓰는 작업은 아래 큐로 내리고, 금방 I/O로 잠드는 작업은 위 큐에 남깁니다.

실행 시간을 미리 몰라도 과거 행동으로 "짧게 쓰고 비키는 작업"을 알아내 SJF처럼 우대하는 셈입니다. 주문 서버의 스레드처럼 조금 계산하고 바로 I/O를 기다리는 흐름이 응답 빠르게 대우받는 이유입니다.

Linux는 덜 쓴 흐름에 먼저 준다

Linux는 2.6.23부터 오랫동안 CFS를 썼습니다. CFS는 흐름마다 지금까지 CPU를 쓴 시간을 우선순위로 보정한 값(vruntime)을 기록하고, 이 값이 가장 작은, 즉 가장 덜 쓴 흐름에 다음 차례를 줍니다. 모두가 비슷한 몫을 받도록 끊임없이 균형을 맞추는 방식입니다.

커널 6.6부터는 기본 스케줄러가 EEVDF로 바뀌었습니다. 공평한 몫이라는 생각은 그대로 두고, 흐름마다 가상의 마감 시각을 계산해 짧게 자주 실행되어야 하는 작업의 응답을 더 잘 챙깁니다.

서버 개발자가 스케줄러 알고리즘을 고를 일은 거의 없습니다. 기억할 것은 코어보다 실행 준비된 스레드가 많으면 누군가는 기다린다는 점입니다. 3부의 vmstat 출력에서 이 줄의 길이를 직접 봅니다. 이제 CPU를 나누는 문제에서, 스레드가 메모리를 나눠 쓸 때의 문제로 넘어갑니다.

stock-- 한 줄이 경쟁 상태를 만든다

주문 서버가 재고 수를 힙의 변수 stock에 두고 주문마다 stock--로 줄인다고 합시다. 이 한 줄은 CPU에서 "메모리에서 읽기, 레지스터에서 빼기, 메모리에 쓰기" 세 명령이 됩니다. 두 스레드의 명령이 표처럼 섞이면 주문 두 건에 재고는 하나만 줄어듭니다.

실행 순서에 따라 결과가 달라지는 이런 상황이 경쟁 상태이고, 공유 자원을 건드리는 코드 구간을 임계 구역이라고 합니다.

임계 구역 해법이 지켜야 할 세 가지

명령이 섞이는 순간은 두 가지입니다. 임계 구역 도중에 컨텍스트 스위칭이 끼어들거나, 두 코어가 같은 코드를 정말 동시에 실행할 때입니다. 해법은 표의 세 조건을 모두 지켜야 합니다. 상호 배제가 깨지면 데이터가 깨지고, 진행이 깨지면 시스템이 멈추고, 한정 대기가 깨지면 누군가 영원히 굶습니다.

코어가 하나뿐이던 시절에는 임계 구역 동안 인터럽트를 꺼서 전환을 막을 수 있었습니다. 하지만 코어가 여럿이면 다른 코어가 같은 메모리를 동시에 건드리므로 통하지 않습니다. 하드웨어의 도움이 필요합니다.

조건의미
상호 배제한 번에 하나만 들어감
진행비어 있으면 누군가는 들어감
한정 대기기다림에 끝이 있음

원자적 명령으로 가장 단순한 락을 만든다

// CAS: *addr이 expected면 new로 바꾸고
// 성공 여부를 돌려줌. 중간에 끼어들 수 없음
bool CAS(int *addr, int expected, int new);

// 스핀락: 0이면 비어 있음, 1이면 잠김
void lock(int *l) {
  while (!CAS(l, 0, 1))
    ;  // 실패하면 될 때까지 다시 시도
}
void unlock(int *l) { *l = 0; }

CPU는 "읽고, 비교하고, 쓰기"를 다른 코어가 끼어들 수 없게 한 번에 해내는 원자적 명령을 제공합니다. 대표가 CAS로, "값이 아직 0이면 1로 바꿔라"를 한 명령으로 처리합니다. 두 스레드가 동시에 시도해도 한쪽만 성공합니다.

이것만으로 락을 만들 수 있습니다. 실패한 스레드가 성공할 때까지 계속 도는 이 락이 스핀락입니다. 기다림이 아주 짧으면 빠르지만, 길어지면 기다리는 스레드가 CPU를 헛되이 태웁니다.

뮤텍스는 기다리는 스레드를 재운다

스핀락의 낭비를 없애려면 락을 못 얻은 스레드를 잠재웠다가 락이 풀릴 때 깨우면 됩니다. 이렇게 커널의 도움으로 잠들고 깨는 락이 뮤텍스(mutual exclusion에서 온 이름)입니다. 주문 서버라면 stock--를 lock과 unlock 사이에 넣어 한 번에 한 스레드만 실행하게 합니다.

뮤텍스에는 소유권이 있어 잠근 스레드만 풀 수 있습니다. Linux의 구현(futex)은 경쟁이 없으면 CAS 한 번으로 끝내고, 경쟁이 있을 때만 시스템 콜로 잠들어 비용을 아낍니다.

  1. lock() 시도

    CAS로 락 변수를 0에서 1로 바꿔 봅니다.

  2. 성공

    임계 구역에 들어가 stock--를 실행합니다.

  3. 실패

    커널의 대기 목록에 올라 대기 상태로 잠듭니다. CPU는 다른 스레드에 갑니다.

  4. unlock()

    주인이 락을 풀면서 기다리던 스레드 하나를 깨웁니다.

  5. 재시도

    깨어난 스레드는 준비 큐를 거쳐 다시 lock()을 시도합니다.

세마포어는 남은 자리 수를 센다

뮤텍스는 "한 번에 하나"만 허용합니다. 그런데 주문 서버가 결제 회사와 맺은 계약상 동시에 20건까지만 결제를 요청할 수 있다면 "한 번에 N개까지"가 필요합니다. 이때 쓰는 것이 세마포어입니다.

세마포어는 남은 자리 수를 담은 정수 카운터와 대기 목록으로 이루어집니다. 들어갈 때 wait(P라고도 함)로 카운터를 1 줄이고, 이미 0이면 잠들어 기다립니다. 나올 때 signal(V)로 카운터를 1 늘리고 기다리던 스레드를 깨웁니다.

  1. 초기값 20

    결제 호출 자리 20개로 시작합니다.

  2. wait()

    결제 전에 카운터를 1 줄입니다. 20건째까지는 바로 통과합니다.

  3. 21번째 요청

    카운터가 0이라 이 스레드는 잠들어 자리가 나기를 기다립니다.

  4. signal()

    결제를 마친 스레드가 카운터를 1 늘리고 기다리던 스레드 하나를 깨웁니다.

뮤텍스는 열쇠, 세마포어는 번호표다

기준뮤텍스(Mutex)세마포어(Semaphore)
동시 진입1개N개(카운터 값)
소유권잠근 스레드만 풀 수 있음누구나 signal 가능
주 용도공유 데이터 보호개수가 정해진 자원 제한
주문 서버 예재고 stock 갱신결제 동시 호출 20건 제한

값이 0과 1뿐인 이진 세마포어는 뮤텍스와 비슷해 보이지만 소유권이 없어, 락을 잡지 않은 스레드도 풀 수 있습니다. 또 낮은 우선순위 스레드가 락을 쥔 채 밀려나 높은 우선순위 스레드까지 기다리게 되는 우선순위 역전이 생겼을 때, 뮤텍스는 소유자를 알기에 소유자의 우선순위를 잠시 올려 풀 수 있지만 세마포어는 그럴 수 없습니다.

모니터는 락과 기다림을 언어가 묶어 준다

세마포어는 강력하지만 wait와 signal을 한 번만 빠뜨려도 데드락이나 데이터 손상이 납니다. 모니터는 공유 데이터와 그것을 다루는 연산을 한 덩어리로 묶고, 연산에 들어가고 나올 때의 잠금과 해제를 언어가 자동으로 처리하는 구조입니다.

모니터 안에서 "조건이 맞을 때까지" 기다리는 장치가 조건 변수입니다. 작업 큐가 비어 있으면 일꾼 스레드는 락을 내려놓고 잠들고, 누군가 작업을 넣으면 깨어납니다. Java의 synchronized와 wait()/notify()가 이 구조입니다. 5장에서는 synchronized가 모니터를 잡는 방식과, 조건 변수를 여러 개 둘 수 있는 ReentrantLock을 봅니다.

락 없이 안전하게 만드는 길도 있습니다

값을 바꿀 수 없게 만든 불변 객체, 스레드마다 따로 두는 변수(ThreadLocal), 앞에서 본 CAS로 직접 값을 바꾸는 방법은 락 없이 경쟁 상태를 피합니다. Java 구현은 5장에서 봅니다.

락이 둘이면 서로를 영원히 기다릴 수 있다

락이 여러 개가 되면 새 문제가 생깁니다. 주문 스레드는 재고 락을 잡은 뒤 계좌 락을 잡고, 환불 스레드는 계좌 락을 잡은 뒤 재고 락을 잡는다고 합시다. 둘이 동시에 첫 락을 잡으면 각자 상대가 쥔 락을 기다리며 영원히 멈춥니다.

이처럼 둘 이상의 흐름이 서로가 가진 자원을 기다리며 아무도 진행하지 못하는 상태가 데드락(교착 상태)입니다. 스레드가 잠들어 있으므로 CPU 사용률은 낮고, 오류도 없이 요청만 쌓입니다.

데드락은 네 조건이 모두 겹칠 때만 생긴다

데드락은 아래 네 조건이 모두 성립할 때만 생깁니다. 앞의 주문, 환불 예에 대어 보면 각 조건의 뜻이 분명해집니다.

  • 상호 배제: 락은 한 번에 한 스레드만 가집니다. 둘이 함께 가질 수 있다면 기다릴 일이 없습니다.
  • 점유 대기: 주문 스레드는 재고 락을 쥔 채 계좌 락을 더 요구합니다. 가진 것을 내려놓고 기다린다면 고리가 생기지 않습니다.
  • 비선점: 남이 쥔 락을 강제로 빼앗을 수 없습니다. 빼앗을 수 있다면 한쪽을 풀어 줄 수 있습니다.
  • 순환 대기: 주문은 환불을, 환불은 주문을 기다려 기다림이 원을 이룹니다.

따라서 네 조건 중 하나만 깨도 데드락은 원리적으로 생길 수 없습니다. 대응 전략은 결국 어느 조건을 어떻게 깨느냐, 아니면 깨지 않고 다른 방법으로 다루느냐의 선택입니다.

데드락을 다루는 네 가지 태도

예방은 조건 하나를 구조적으로 없애는 것으로, 모든 코드가 락을 같은 순서(항상 재고 락 먼저)로 잡아 순환 대기를 깨는 방법이 대표적입니다. 회피는 자원을 줄 때마다 "이걸 주고도 모두 끝까지 갈 수 있는가"를 계산해 안전할 때만 주는 것으로, 이 계산법을 은행원 알고리즘이라 합니다.

탐지와 회복은 누가 누구를 기다리는지 그래프로 그려 고리를 찾으면 하나를 강제로 끝냅니다. 무시는 드물다고 보고 개발자에게 맡기는 것입니다.

Linux 같은 범용 OS는 비용 대비 효과 때문에 무시를 택하고, DB는 데드락을 탐지해 한 트랜잭션을 되돌립니다(4장). 애플리케이션에서는 락 순서 고정이 가장 실용적입니다.

멈추지 않아도 진행이 없을 수 있다

데드락처럼 완전히 멈추지 않아도 진척이 없을 수 있습니다. 스케줄링에서 본 기아 상태는 락에서도 생깁니다. 락이 풀릴 때마다 다른 스레드가 먼저 가져가 특정 스레드만 계속 밀리는 경우로, 오래 기다린 순서대로 주는 공정 락으로 막습니다.

라이브락은 스레드들이 깨어 계속 움직이지만 서로 양보만 반복해 아무도 나아가지 못하는 상황입니다. 데드락을 피하려고 "둘째 락을 못 얻으면 첫째를 내려놓고 다시 시도"하게 만든 두 스레드가 똑같은 박자로 잡고 놓기를 되풀이하는 경우가 그렇습니다.

재시도에는 무작위 지연을 섞으세요

실패한 스레드들이 똑같은 간격으로 다시 시도하면 라이브락에 빠집니다. 재시도 간격에 무작위 값(jitter)을 더하면 박자가 엇갈려 풀립니다. 8장의 재시도 설계와 같은 원리입니다.

물리 메모리를 그대로 나눠 주면 생기는 문제

이제 커널의 두 번째 약속, "프로세스마다 메모리를 혼자 쓰는 것처럼"을 봅니다. 가장 단순한 방법은 물리 메모리를 구역으로 잘라 프로세스마다 하나씩 주는 것입니다. 주문 서버는 1GB부터 3GB까지, 로그 수집기는 3GB부터 3.5GB까지 하는 식입니다.

이 방식에는 세 가지 문제가 있습니다. 첫째, 프로그램이 주소를 잘못 계산하면 남의 구역을 그대로 덮어씁니다. 둘째, 프로그램은 자기가 몇 번지에 올라갈지 미리 알 수 없고 실행할 때마다 위치가 달라집니다. 셋째, 프로세스가 생기고 사라지며 빈 구역이 군데군데 흩어지면, 빈 공간의 합은 충분해도 큰 프로그램 하나를 올릴 연속 공간이 없어집니다.

해법은 프로세스에게 진짜 주소 대신 가짜 주소를 주고, 진짜 위치로 바꾸는 일은 하드웨어와 커널이 맡는 것입니다. 이것이 가상 메모리의 출발점입니다.

가상 메모리: 각자 전체를 가진 것처럼

각 프로세스는 0번지부터 시작하는 넓은 주소 공간을 혼자 쓰는 것처럼 동작합니다. 이 가짜 주소가 가상 주소이고, 프로세스마다 주는 이 주소 공간 전체를 가상 메모리라고 합니다.

메모리는 4KB 크기의 페이지로 쪼개고, 물리 메모리의 같은 크기 칸인 프레임에 대응시킵니다. 이 대응표가 프로세스마다 하나씩 있는 페이지 테이블입니다. 표에 없는 프레임은 건드릴 수 없으니 격리되고, 당장 안 쓰는 페이지는 디스크에 둘 수도 있습니다.

가상 주소는 페이지 번호와 오프셋으로 나뉜다

페이지가 4KB(4,096바이트)이므로, 가상 주소를 4,096으로 나눈 몫이 페이지 번호, 나머지가 페이지 안에서의 위치인 오프셋입니다. 4,096은 2의 12제곱이라 주소의 아래 12비트가 오프셋, 윗부분이 페이지 번호가 되어 나눗셈 없이 비트만 잘라 내면 됩니다.

변환은 페이지 번호만 바꾸고 오프셋은 그대로 둡니다. 페이지 안의 배치는 프레임 안에서도 똑같기 때문입니다. 표의 각 항목에는 프레임 번호 외에 "지금 메모리에 있음", "쓰기 허용" 같은 표시도 함께 들어 있습니다.

  1. 가상 주소

    주문 서버가 가상 주소 12,300번지를 읽으려 합니다.

  2. 나누기

    12,300 = 3 × 4,096 + 12. 페이지 3, 오프셋 12입니다.

  3. 표 찾기

    페이지 테이블에서 페이지 3은 프레임 7에 있다고 나옵니다.

  4. 물리 주소

    7 × 4,096 + 12 = 28,684번지를 실제로 읽습니다.

주소 변환을 빠르게 만드는 MMU와 TLB

메모리를 읽을 때마다 페이지 테이블을 먼저 읽어야 한다면 모든 접근이 두 배 이상 느려집니다. 게다가 64비트 시스템의 페이지 테이블은 크기를 줄이려고 보통 4단계로 나뉘어 있어, 변환 한 번에 메모리를 네 번 더 읽을 수도 있습니다.

그래서 앞 슬라이드의 계산은 소프트웨어가 아니라 CPU 안의 MMU라는 회로가 합니다. MMU는 최근 변환 결과를 TLB라는 작은 캐시에 두는데, 지역성 덕분에 대부분의 변환은 TLB에서 끝납니다. TLB도 캐시이므로 1부의 히트율 계산이 그대로 적용됩니다.

2부 처음에 프로세스 전환이 비싼 이유로 든 것이 이 TLB입니다. 주소 공간이 바뀌면 이전 프로세스의 변환 결과는 쓸모가 없어집니다. 이제 표에 "메모리에 없음"으로 표시된 페이지를 건드리면 어떻게 되는지 봅니다.

페이지 폴트: 없는 페이지를 건드렸을 때

  1. 접근 시도

    페이지 테이블에 해당 페이지가 메모리에 없다고 표시돼 있습니다.

  2. 페이지 폴트

    MMU가 예외를 일으켜 커널로 넘어갑니다.

  3. 빈 프레임 확보

    빈 칸이 없으면 교체 알고리즘으로 페이지 하나를 내보냅니다.

  4. 디스크에서 읽기

    그동안 이 스레드는 대기 상태로 잠들고 다른 흐름이 돕니다.

  5. 표 갱신, 재실행

    멈췄던 명령을 처음부터 다시 실행합니다.

운영체제는 프로그램을 시작할 때 모든 페이지를 메모리에 올리지 않고, 실제로 접근하는 순간 올립니다. 이를 요구 페이징이라고 합니다. 쓰지 않는 기능의 코드는 끝내 올라오지 않으니 시작이 빠르고 메모리도 아낍니다.

메모리에 없는 페이지에 접근해 MMU가 일으키는 예외가 페이지 폴트입니다. 디스크를 읽어야 하는 폴트는 메모리 접근보다 수만 배 이상 느리므로, 자주 일어나면 성능이 급격히 떨어집니다.

무엇을 내보낼지는 과거로 미래를 추정한다

빈 프레임이 없을 때 페이지 폴트가 나면, 이미 있는 페이지 하나를 내보내고 그 자리를 써야 합니다. 무엇을 내보낼지 정하는 규칙이 페이지 교체 알고리즘입니다. 잘못 고르면 방금 내보낸 페이지를 곧바로 다시 읽느라 폴트가 늘어납니다.

앞으로 가장 오래 안 쓸 페이지를 내보내는 OPT가 이론상 최선이지만, 미래를 알 수 없어 비교 기준으로만 씁니다. 가장 먼저 들어온 것을 내보내는 FIFO는 단순하지만 자주 쓰는 페이지도 오래됐다는 이유로 내보냅니다.

그래서 시간 지역성에 기대 "최근에 안 쓴 것은 앞으로도 안 쓸 것"이라고 보고, 가장 오래전에 쓴 페이지를 내보내는 LRU를 씁니다. 접근마다 정확한 순서를 기록하기는 비싸서, 실제 OS는 페이지마다 "최근 사용됨" 표시를 두고 주기적으로 지우는 방식으로 LRU를 흉내 냅니다. LRU를 빠르게 구현하는 자료구조는 3장에서 봅니다.

스왑과 스래싱: 메모리가 모자랄 때

내보낸 페이지를 담아 두는 디스크 공간을 스왑이라고 합니다. 스왑 덕분에 물리 메모리보다 많은 메모리를 쓸 수 있지만, 그 대가는 디스크 속도입니다.

프로세스가 일정 시간 동안 실제로 쓰는 페이지들을 작업 집합이라고 합니다. 작업 집합의 합이 물리 메모리보다 커지면 페이지를 들였다 내보내기만 반복하며 모든 스레드가 디스크를 기다리고 CPU는 놉니다. 이것이 스래싱이며, 이때 프로세스를 더 띄우면 더 나빠집니다.

서버가 스왑을 쓰기 시작하면 이미 늦었습니다

JVM 힙 일부가 스왑으로 밀려나면 GC가 힙을 훑으며 디스크를 읽어 수 초씩 멈춥니다. 그래서 힙을 물리 메모리보다 넉넉히 작게 잡고 스왑에 기대지 않게 운영합니다(5장, 9장).

페이징과 세그멘테이션, 그리고 단편화

메모리를 나누는 방법에는 페이징 말고 세그멘테이션도 있습니다. 코드, 데이터, 스택처럼 의미 있는 단위마다 크기가 다른 덩어리를 통째로 할당하는 방식입니다. 둘은 낭비되는 공간의 모양이 다릅니다. 빈 공간의 합은 충분한데 연속된 덩어리가 없어 못 쓰는 것이 외부 단편화(앞의 셋째 문제), 할당받은 칸 안에서 쓰지 않고 남는 것이 내부 단편화입니다.

격리된 프로세스끼리 말하는 방법, IPC

가상 메모리 덕분에 프로세스는 서로의 메모리를 볼 수 없습니다. 격리는 안전하지만, 협력하려면 1부에서 이름만 본 IPC, 즉 커널이 마련한 통로가 필요합니다.

파이프는 한쪽이 쓴 바이트를 다른 쪽이 읽는 한 방향 통로이고, 공유 메모리는 두 프로세스의 페이지 테이블이 같은 프레임을 가리키게 해 복사 없이 같은 메모리를 보게 합니다. 메시지 큐는 커널이 메시지 단위로 전달해 주고, 소켓은 다른 기계와도 통신합니다.

블로킹 I/O: 기다리는 스레드는 잠든다

  1. read() 호출

    주문 스레드가 DB 연결 소켓에서 응답을 읽으려 합니다.

  2. 데이터 없음

    커널은 아직 도착한 데이터가 없음을 확인합니다.

  3. 대기

    스레드를 대기 상태로 바꿔 소켓의 대기 목록에 올리고, CPU는 다른 스레드로 갑니다.

  4. 도착

    응답 패킷이 오면 NIC 인터럽트를 받은 커널이 버퍼에 쌓고 스레드를 준비 상태로 바꿉니다.

  5. 반환

    차례가 오면 read()가 데이터를 들고 돌아옵니다.

1부 첫머리의 요청 경로를 이제 커널 안쪽에서 볼 수 있습니다. 주문 스레드가 DB 응답을 read()할 때 데이터가 아직 없으면, 커널은 스레드를 재우고 CPU를 다른 스레드에 줍니다. 호출이 끝날 때까지 호출한 쪽이 멈춰 있는 이런 방식이 블로킹 I/O입니다.

CPU는 낭비되지 않지만 스레드는 묶여 있습니다. 동시에 기다리는 연결이 1만 개면 잠든 스레드도 1만 개가 필요하다는 뜻이고, 다른 I/O 방식들은 여기서 출발합니다.

동기/비동기와 블로킹/논블로킹은 다르다

I/O 방식에는 두 축이 섞여 쓰입니다. 블로킹과 논블로킹은 호출한 쪽이 제어권을 바로 돌려받는가의 문제로, 논블로킹 read()는 데이터가 없으면 기다리지 않고 "아직 없음"을 즉시 돌려줍니다. 동기와 비동기는 완료를 누가 챙기는가의 문제로, 동기는 호출한 쪽이 결과를 직접 확인하고 비동기는 완료되면 콜백이나 이벤트로 통보받습니다.

블로킹(끝날 때까지 멈춤)논블로킹(즉시 반환)
동기(결과를 내가 챙김)일반 read(), DB 호출준비됐는지 반복 확인(폴링)
비동기(완료를 통보받음)맡겨 놓고 곧바로 기다림콜백, 이벤트로 완료 통지

비동기+블로킹은 Java의 Future(나중에 결과가 담길 상자)를 받자마자 get()으로 결과를 기다리는 경우처럼, 비동기의 이점을 버린 조합이라 대개 실수입니다.

연결이 많으면 한꺼번에 물어야 한다

블로킹 I/O로 연결 1만 개를 다루려면 스레드도 1만 개가 필요합니다. 그렇다고 소켓을 모두 논블로킹으로 열고 스레드 하나가 1만 개를 차례로 read()해 보면, 대부분 "아직 없음"이 돌아오는 폴링이 되어 시스템 콜만 낭비합니다. 1부의 폴링 대 인터럽트 이야기가 소프트웨어 수준에서 반복되는 셈입니다.

해법은 커널에게 "이 fd들 중 읽을 준비가 된 것이 생기면 알려 달라"고 한 번에 묻는 것입니다. 스레드 하나가 여러 연결의 I/O를 한 곳에서 기다리므로 I/O 멀티플렉싱이라고 부르며, Linux에는 select, poll, epoll 세 세대가 있습니다.

select는 감시할 fd들을 fd 번호마다 1비트인 비트 묶음으로 넘기는데, 이 묶음 크기가 1024비트로 고정이라 1024번 이상의 fd는 다룰 수 없습니다. poll은 이 제한을 없앴지만, 둘 다 호출할 때마다 감시 목록 전체를 커널에 넘기고 커널이 전부 훑어야 합니다.

epoll은 활발한 연결 수만큼만 일한다

방식감시 대상 등록준비된 fd 찾기한계
select호출마다 전체를 커널에 복사전부 훑어봄 O(n)fd 1024개 제한
poll호출마다 전체 배열 전달전부 훑어봄 O(n)개수 제한은 없음
epoll한 번 등록하면 커널이 유지준비된 것만 받음Linux 전용

표의 O(n)은 감시하는 fd 수 n에 비례해 일이 늘어난다는 뜻입니다(3장). epoll은 감시 목록을 커널 안에 한 번만 등록해 두고, 준비된 fd가 생기면 커널이 따로 모아 둡니다. 그래서 호출 비용이 전체 연결 수가 아니라 실제로 활발한 연결 수에 비례합니다. 연결 수천 개 중 소수만 바쁜 웹 서버에 꼭 맞으며, macOS와 BSD에서는 kqueue가 같은 역할을 합니다.

epoll을 쓰는 코드는 세 호출로 이루어진다

int ep = epoll_create1(0);
// 연결 대기 소켓을 감시 목록에 등록
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &ev);

while (1) {
  int n = epoll_wait(ep, events, 64, -1);
  for (i = 0; i < n; i++) {
    int fd = events[i].data.fd;
    if (fd == listen_fd)
      add_client(ep, accept(fd, …));
    else
      handle(fd); // 논블로킹 read/write
  }
}

첫 줄은 커널 안에 감시 목록을 만들고 그 fd를 받습니다. epoll_ctl로 연결 대기 소켓(listen_fd)을 등록하고, 새 연결을 accept할 때마다 그 fd도 등록합니다(add_client).

강조한 epoll_wait가 핵심입니다. 준비된 fd가 없으면 스레드는 여기서 잠들고(-1은 무한 대기), 생기면 최대 64개를 담아 돌아옵니다. 루프는 그 fd들만 처리하고 다시 기다립니다.

이벤트 루프는 기다림을 커널에 맡긴다

앞 코드의 바깥 반복이 이벤트 루프입니다. 준비된 fd 목록을 받아 각 fd의 처리 함수(핸들러)를 실행하고 다시 기다리러 돌아갑니다. 소켓은 모두 논블로킹이므로 핸들러는 기다리지 않고, 읽을 수 있는 만큼 읽고 바로 돌아옵니다.

기다림은 커널이 맡고 스레드는 할 일이 있는 연결만 처리하므로 스레드 수와 컨텍스트 스위칭이 거의 늘지 않습니다. 대신 핸들러 하나가 오래 걸리면 모든 연결이 멈춥니다. 3부에서 이 약점이 실제로 어떻게 드러나는지 봅니다.

3부

원리가 장애로 드러나는 순간

2부의 원리를 주문 서버 운영에 적용합니다. 스레드를 몇 개 둘지, 늘렸는데 왜 더 느려졌는지, 결제 회사가 느려지면 왜 서버 전체가 멈추는지, fd는 왜 바닥나는지, 그리고 왜 많은 서버가 이벤트 루프를 택했는지를 차례로 봅니다.

원리 실무 스레드 풀 크기 계산, 관측 명령어, 커널 한도, 장애 사례를 다룹니다.

요청마다 스레드를 만들면 안 되는 이유

가장 단순한 서버는 요청이 올 때마다 스레드를 새로 만들고 끝나면 버립니다. 하지만 스레드 생성과 종료에는 시스템 콜과 커널 자료구조 준비가 들고, 스레드마다 스택 메모리를 예약합니다. JVM 스레드 스택은 64비트 Linux에서 기본 1MB이므로 스레드 1만 개는 스택 예약만 약 10GB입니다. 요청이 몰리면 스레드가 끝없이 늘어 메모리와 CPU를 다 먹고 서버가 통째로 쓰러집니다.

그래서 서버는 정해진 수의 스레드를 미리 만들어 두고 재사용하는 스레드 풀을 씁니다. 들어온 요청은 작업 큐에 쌓이고, 일을 마친 스레드가 큐에서 다음 작업을 꺼냅니다. 2부의 조건 변수가 바로 이 "큐가 비면 잠들고, 작업이 오면 깨는" 동작을 만듭니다.

풀의 크기는 곧 동시에 처리할 수 있는 작업 수의 상한이고, 이 상한이 과부하로부터 서버를 지키는 방어선입니다. 큐까지 가득 차면 새 요청을 거절해, 서버 전체가 쓰러지는 대신 일부 요청만 실패하게 합니다. Tomcat의 요청 스레드 풀 설정은 6장에서 봅니다.

스레드 풀 크기는 대기 비율로 정한다

// CPU 바운드: 코어 수 근처
threads ≈ cores + 1

// I/O 바운드 (Java Concurrency in Practice)
threads ≈ cores × (1 + 대기 시간 / 계산 시간)

// 주문 서버: 8코어, 계산 10ms, 대기 90ms
threads ≈ 8 × (1 + 90 / 10) = 80

암호화나 이미지 처리처럼 CPU만 쓰는 CPU 바운드 작업은 1부의 병렬성 한계 때문에 코어보다 스레드가 많아도 빨라지지 않고 전환 비용만 늡니다. 그래서 코어 수 근처로 둡니다.

DB나 외부 API를 기다리는 I/O 바운드 작업은 기다리는 동안 코어가 놀기 때문에 더 많이 필요합니다. 주문 서버 스레드는 시간의 10%만 코어를 쓰므로, 8코어를 채우려면 그 10배인 80개가 필요합니다. 공식은 위의 동시성 서적에서 널리 알려졌습니다.

공식의 숫자는 측정으로 채운다

공식은 출발점일 뿐입니다. 먼저 대기 시간과 계산 시간을 실제로 재야 합니다. 요청 처리 시간을 구간별로 기록하는 APM(애플리케이션 성능 모니터링) 도구나, 로그에 DB 호출 전후 시각을 남기는 방법으로 요청당 전체 시간과 그중 기다린 시간을 얻습니다.

다음으로 스레드 풀 바깥의 한도를 봅니다. 스레드를 80개로 늘려도 DB 커넥션 풀(미리 맺어 둔 DB 연결 묶음, 4장)이 20개라면 나머지 60개는 커넥션을 기다리며 줄을 섭니다. 결제 회사가 동시 20건만 허용하면 2부의 세마포어가 상한이 됩니다. 처리량은 경로에서 가장 좁은 곳이 정합니다.

마지막으로 부하 테스트로 확정합니다. 스레드 수를 늘려 가며 초당 처리량과 응답 시간을 재면, 어느 지점부터 처리량은 그대로인데 응답 시간만 늘어납니다. 그 직전이 적정값입니다. 이 지점을 넘으면 무슨 일이 생기는지 실제 지표로 보겠습니다.

vmstat은 CPU가 어디에 시간을 쓰는지 보여 준다

vmstat 1은 1초마다 시스템 전체의 CPU, 메모리, 전환 통계를 한 줄씩 찍는 Linux 명령입니다. 2부에서 본 개념이 각 열에 그대로 대응하므로, 열의 뜻부터 정리합니다.

CPU가 일보다 전환과 락 경합에 시간을 씁니다. 늘어난 스레드가 같은 커넥션 풀과 락을 두고 다투기 때문입니다. 풀 크기를 되돌리고 느린 구간 자체를 줄여야 합니다. pidstat -w는 전환 수를 프로세스별로 보여 줍니다.

장애 사례: 느린 결제 API가 풀을 삼킨다

  1. 평소

    결제 API 응답 50ms, 스레드 80개로 여유 있게 처리합니다.

  2. 외부 지연

    결제 회사 서버가 느려져 응답이 10초로 늘어납니다.

  3. 풀 고갈

    2초도 안 돼 80개 스레드가 모두 결제 응답을 기다리며 잠듭니다.

  4. 전면 장애

    결제와 무관한 주문 조회와 헬스 체크까지 큐에서 밀려 실패합니다.

초당 결제 요청이 50건일 때 응답이 10초 걸리면, 평균 50 × 10 = 500개 요청이 동시에 결제를 기다립니다. 스레드 80개는 순식간에 바닥납니다. 헬스 체크는 서버가 살아 있는지 주기적으로 확인하는 요청이라, 이것까지 실패하면 서버가 죽은 것으로 판정됩니다.

이때 CPU는 한가합니다. 블로킹 I/O에서는 기다리는 스레드도 풀 한 칸을 차지하기 때문입니다. CPU는 노는데 서버가 응답하지 않는다면 대개 이 패턴입니다.

타임아웃과 벌크헤드로 피해를 가둔다

첫째 방어선은 타임아웃입니다. 연결을 맺을 때 기다릴 최대 시간(연결 타임아웃)과 응답을 기다릴 최대 시간(읽기 타임아웃)을 정해, 그 시간이 지나면 기다림을 포기하고 스레드를 돌려받습니다. 결제 읽기 타임아웃을 1초로 두면 앞 사례에서 동시에 묶이는 스레드는 최대 50 × 1 = 50개 수준으로 줄어 풀 80개 안에 들어옵니다. 라이브러리 기본값이 "무한 대기"인 경우가 많으니 반드시 직접 정합니다.

둘째는 벌크헤드입니다. 배의 격벽처럼, 호출 대상별로 쓸 수 있는 스레드나 자리를 나눠 한 곳의 침수가 배 전체로 번지지 않게 합니다. 2부의 세마포어로 결제 호출을 동시 20개로 제한하면, 결제가 아무리 느려도 나머지 60개 스레드는 주문 조회와 헬스 체크를 계속 처리합니다.

이런 장애 격리 패턴은 8장에서 서비스 여러 개 규모로 다시 다룹니다. 다음은 스레드가 아니라 fd가 바닥나는 경우입니다.

상대가 끊었는데 미처리CLOSE_WAIT 누적응답 본문 소비, 연결 반납
커넥션 풀 없이 매번 연결짧은 연결이 폭증HTTP, DB 커넥션 풀 사용

셸의 ulimit는 그 셸에서 띄운 프로세스에만 적용되므로, Linux의 서비스 관리자인 systemd로 띄운 서비스는 LimitNOFILE로, 컨테이너는 컨테이너 설정에서 올립니다(9장).

연결 1만 개에서 스레드 모델이 무너졌다

2000년 전후, 서버 한 대로 동시 연결 1만 개를 다루는 문제를 C10K 문제라고 불렀습니다. 연결당 스레드 모델은 이 규모에서 스택 메모리와 컨텍스트 스위칭에 무너졌습니다. 해법은 대부분의 연결이 대부분의 시간 동안 아무것도 안 한다는 관찰에서 나왔습니다. 기다림은 epoll에 맡기고 할 일이 생긴 연결만 처리하는 이벤트 루프 서버입니다.

세 서버는 루프를 이렇게 돌린다

대표적인 이벤트 루프 서버 셋입니다. Nginx는 웹 서버이자 앞단 중계 서버로, 주문 서버 앞에서 클라이언트 연결을 받아 넘겨주는 자리에 흔히 놓입니다(2장). Node.js는 JavaScript 서버 실행 환경으로 루프를 libuv라는 C 라이브러리로 구현합니다. Netty는 Java 네트워크 라이브러리로, Spring WebFlux(6장)가 그 위에서 동작합니다.

Nginx의 worker_processes auto는 코어 수만큼 워커를 띄우고, worker_connections(기본 512)는 워커당 동시 연결 상한입니다. 이 값도 열린 파일 한도를 넘을 수 없습니다.

이벤트 루프를 막는 코드가 가장 위험하다

이벤트 루프 핸들러 안에 블로킹 DB 호출(Java 표준 DB 접속 방식인 JDBC), 큰 JSON 파싱, 동기 파일 읽기를 넣으면 그동안 같은 루프의 모든 연결이 응답을 멈춥니다. 스레드가 적어서 생긴 효율이 그대로 약점이 됩니다. 무거운 작업은 별도 스레드 풀로 넘기고, 루프는 I/O 이벤트를 나누는 일만 합니다.

반대로 주문 서버처럼 대부분이 DB 호출이고 동시 연결이 수백 개라면 스레드 풀이 더 단순하고 충분합니다. 앞단 Nginx가 수많은 연결을 루프로 받고 뒤의 주문 서버는 스레드로 일하는 구성이 흔한 이유입니다.

세 번째 길: 가벼운 스레드

Java 21의 Virtual Thread는 블로킹 코드처럼 쓰되 기다리는 동안 OS 스레드를 내놓게 해, 두 모델의 장점을 합치려는 시도입니다. 5장에서 다룹니다.

정리

  • 성능은 느린 층에 덜 내려가는 데서 나옵니다. 캐시, 페이지 캐시, 버퍼, 시스템 콜 줄이기가 모두 메모리 계층의 격차를 피하는 방법입니다.
  • 커널은 나누고, 지키고, 감춥니다. 유저/커널 모드와 시스템 콜이 지키기를, 프로세스와 fd가 감추기를 맡습니다.
  • 스레드는 힙을 공유하고 스택을 따로 가집니다. 공유는 싸지만, 그만큼 경쟁 상태를 막을 동기화 책임이 생깁니다.
  • 데드락은 네 조건이 모두 있어야 생깁니다. 실무에서는 락 순서를 고정해 순환 대기를 깨는 것이 가장 확실합니다.
  • 가상 메모리는 페이지 단위로 주소를 바꿔 줍니다. TLB와 페이지 폴트가 전환 비용과 스래싱의 정체입니다.
  • 스레드 수는 대기 비율로 정하고, 연결이 많으면 이벤트 루프를 씁니다. 스레드도 fd도 한도가 있는 자원입니다.

스스로 점검 (1) 기계와 운영체제

  1. 2차원 배열을 열 우선으로 순회하면 왜 느려지나요?

    배열은 행 단위로 연속 배치되므로 열 우선은 매번 다른 캐시 라인을 건드립니다. 공간 지역성을 못 살려 캐시 미스가 늘어납니다.

  2. 캐시 1ns, 메모리 100ns일 때 히트율 95%의 평균 접근 시간은 대략 얼마인가요?

    0.95×1 + 0.05×100 = 약 6ns입니다. 99%일 때(약 2ns)보다 세 배 느립니다.

  3. 인터럽트가 오면 CPU가 PC와 레지스터부터 저장하는 이유는 무엇인가요?

    둘이 "어디까지 실행했는가"의 전부라서, 저장해 둬야 처리 뒤 정확히 그 자리에서 이어 갈 수 있습니다.

  4. 애플리케이션이 디스크를 직접 읽지 못하고 시스템 콜을 거쳐야 하는 이유는요?

    유저 모드에선 장치 명령이 막혀 있어, 커널이 권한과 인자를 검사해 한 프로그램의 실수가 번지지 않게 합니다.

  5. 스레드마다 스택을 따로 두지 않고 공유하면 어떻게 될까요?

    스레드들이 서로 다른 함수를 실행하며 지역 변수와 돌아갈 위치를 같은 곳에 덮어써 실행 흐름이 깨집니다.

스스로 점검 (2) 커널의 원리

  1. 프로세스 전환이 스레드 전환보다 비싼 가장 큰 이유는 무엇인가요?

    주소 공간이 바뀌어 TLB 항목이 무효화되고, 캐시에 쓸모없는 데이터가 남기 때문입니다. 레지스터 저장 자체의 비용은 비슷합니다.

  2. 이진 세마포어로 뮤텍스를 완전히 대신할 수 없는 이유는 무엇인가요?

    세마포어에는 소유권이 없어 락을 잡지 않은 스레드도 풀 수 있고, 소유자를 모르니 우선순위 역전도 풀어 줄 수 없습니다.

  3. 모든 스레드가 재고 락, 계좌 락을 항상 이 순서로 잡으면 데드락이 생길 수 있나요?

    생기지 않습니다. 계좌 락을 쥔 채 재고 락을 기다리는 스레드가 없어 순환 대기가 성립하지 않습니다.

  4. 페이지 4KB에서 가상 주소 8,200이 프레임 5에 대응하면 물리 주소는요?

    8,200 = 2 × 4,096 + 8이므로 페이지 2, 오프셋 8입니다. 물리 주소는 5 × 4,096 + 8 = 20,488번지입니다.

  5. 메모리가 부족할 때 프로세스를 더 띄우면 CPU 사용률이 오히려 떨어지는 이유는요?

    작업 집합을 메모리에 다 못 올려 페이지 폴트가 폭증하고, 스레드들이 디스크를 기다리며 잠듭니다. 이것이 스래싱입니다.

스스로 점검 (3) 운영 서버

  1. epoll이 select보다 연결이 많을 때 유리한 이유는 무엇인가요?

    select는 호출마다 fd 전체를 훑지만, epoll은 한 번 등록하면 준비된 fd만 돌려줘 비용이 활성 연결 수에 비례합니다.

  2. 4코어 서버에서 요청당 계산 20ms, DB 대기 180ms라면 스레드는 대략 몇 개가 적당한가요?

    4 × (1 + 180/20) = 40개 정도가 출발점입니다. 이후 부하 테스트로 처리량이 꺾이는 지점을 확인해 조정합니다.

  3. 초당 100건 호출하는 외부 API에 읽기 타임아웃 2초를 두면, 최악일 때 묶이는 스레드는 몇 개인가요?

    100 × 2 = 약 200개입니다. 풀이 이보다 작다면 타임아웃을 줄이거나 벌크헤드로 그 호출의 자리를 따로 제한해야 합니다.

  4. ulimit를 올렸는데도 며칠 뒤 다시 Too many open files가 난다면 무엇을 의심하나요?

    fd 누수입니다. 트래픽과 무관하게 fd가 늘어나는지, CLOSE_WAIT 소켓이 쌓이는지 lsof로 확인합니다.

  5. Netty 핸들러 안에서 JDBC를 직접 호출하면 무슨 일이 생기나요?

    DB 응답을 기다리는 동안 그 EventLoop에 묶인 모든 연결이 처리되지 못합니다. 블로킹 작업은 별도 스레드 풀로 넘겨야 합니다.
