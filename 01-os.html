아래층부터 위로 쌓아 올라가는 순서입니다. 지금은 1단계, 가장 아래층입니다.

1부

기계와 프로그램 사이의 중재자

CPU, 메모리, 디스크가 어떤 속도로 움직이는지, 그리고 운영체제가 그 위에서 프로그램에게 무엇을 약속하는지부터 봅니다.

왜 백엔드 공부를 OS에서 시작하는가

  1. 패킷 도착NIC가 인터럽트를 검
  2. 커널 소켓데이터를 버퍼에 쌓음
  3. 스레드 깨어남스케줄러가 CPU를 줌
  4. 메모리 계산힙과 스택, 캐시
  5. DB, 디스크 I/O기다리는 동안 멈춤

Spring이든 Node든 요청 하나는 결국 어떤 스레드가 CPU를 얻어 메모리를 읽고, I/O를 기다리는 일로 바뀝니다. 서버가 느리거나 멈출 때 원인은 대개 이 중 한 곳에 있습니다.

그래서 이 시리즈는 가장 아래층인 운영체제에서 출발해 네트워크, 데이터베이스, 프레임워크, 클라우드로 올라갑니다.

CPU는 빠르고, 나머지는 모두 느리다

L1 캐시약 1ns1초

 하드웨어마다 다르므로 자릿수만 기억하면 충분합니다.

CPU 한 사이클은 1ns보다 짧습니다. 그런데 메모리에서 값을 가져오는 데 100ns, 디스크는 그보다 수천 배가 걸립니다.

이 격차를 메우려고 컴퓨터는 작고 빠른 저장소를 CPU 가까이에 층층이 둡니다. 이것이 메모리 계층입니다. 성능 튜닝의 대부분은 느린 층에 덜 내려가게 만드는 일입니다.

캐시는 지역성에 기대어 동작한다

// 행 우선: 메모리에 놓인 순서대로 읽음
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++) sum += a[i][j];

// 열 우선: 매번 한 행 크기만큼 건너뜀
for (j = 0; j < N; j++)
  for (i = 0; i < N; i++) sum += a[i][j];

캐시는 방금 쓴 데이터를 또 쓸 것(시간 지역성), 그 옆 데이터도 곧 쓸 것(공간 지역성)이라는 경향에 기대어 동작합니다.

CPU는 메모리를 바이트 단위가 아니라 캐시 라인(x86에서 64바이트) 단위로 가져옵니다. 그래서 연속으로 읽는 위쪽 루프가 훨씬 빠르고, N이 크면 몇 배까지 차이가 납니다.

인터럽트: CPU가 기다리지 않게 하는 장치

디스크나 네트워크 카드의 작업이 끝났는지 CPU가 계속 물어보는 방식을 폴링이라고 합니다. 확인하는 동안 CPU는 다른 일을 못 합니다.

인터럽트는 반대로 장치가 "끝났다"고 CPU에 신호를 보내는 방식입니다. CPU는 하던 일을 잠시 멈추고 처리한 뒤 돌아옵니다. 하드웨어 인터럽트 외에 시스템 콜이나 0으로 나누기 같은 예외로 생기는 소프트웨어 인터럽트도 있습니다.

  1. 신호 발생

    장치가 인터럽트 요청을 CPU에 보냅니다.

  2. 상태 저장

    CPU가 현재 PC와 레지스터를 저장합니다.

  3. 핸들러 실행

    커널의 인터럽트 처리 루틴으로 점프합니다.

  4. 복귀

    저장한 상태를 되살려 하던 일로 돌아갑니다.

유저 모드와 커널 모드로 권한을 나눈다

모든 프로그램이 디스크나 메모리를 마음대로 건드리면 버그 하나가 기계 전체를 망가뜨립니다. 그래서 CPU는 실행 권한을 두 단계로 나눕니다.

애플리케이션은 유저 모드에서 돌고, 하드웨어 접근은 커널 모드의 운영체제만 할 수 있습니다. 파일을 읽으려면 커널에 부탁해야 하는데, 이 부탁이 시스템 콜입니다.

시스템 콜은 공짜가 아니다

시스템 콜이 호출되면 CPU는 특별한 명령(trap)으로 커널 모드에 들어가 레지스터를 저장하고, 커널이 인자를 검사한 뒤 일을 하고, 결과를 유저 메모리로 복사해 돌아옵니다. 함수 호출보다 훨씬 무거운 왕복입니다.

그래서 고성능 서버는 시스템 콜 횟수를 줄이는 쪽으로 설계됩니다. 1바이트씩 read()하지 않고 버퍼에 모아 읽는 것, 여러 소켓을 하나씩 확인하지 않고 한 번의 호출로 묻는 epoll(2부에서 다룸)이 모두 같은 발상입니다.

Java의 BufferedInputStream이나 로그 라이브러리의 비동기 버퍼도 같은 이유로 존재합니다.

프로세스는 실행 중인 프로그램이다

디스크의 실행 파일은 프로그램이고, 운영체제가 이를 메모리에 올려 실행하면 프로세스가 됩니다. 프로세스마다 독립된 메모리 공간이 주어집니다.

스택은 함수 호출마다 쌓였다 사라져 할당이 포인터 이동만큼 빠르고, 힙은 크기와 수명이 실행 중에 정해지는 객체를 담아 관리 비용(GC 등)이 듭니다.

스레드는 프로세스 안의 실행 흐름이다

스레드는 한 프로세스 안에서 독립적으로 실행되는 흐름입니다. 같은 프로세스의 스레드들은 Code, Data, Heap, 열린 파일을 공유합니다.

반면 Stack과 레지스터(PC 포함)는 스레드마다 따로입니다. 각자 다른 함수를 다른 위치에서 실행하므로 호출 기록과 실행 위치는 공유할 수 없기 때문입니다.

멀티프로세스 대신 멀티스레드를 쓰는 이유

기준멀티프로세스멀티스레드
생성 비용메모리 공간을 새로 만듦스택만 새로 만듦
데이터 공유IPC가 필요함힙 변수를 바로 공유
전환 비용주소 공간까지 바뀜레지스터와 스택만 바뀜

동기화공유가 적어 단순함경쟁 상태를 직접 막아야 함

요청마다 메모리를 통째로 복제하는 것보다 공유하는 편이 훨씬 싸기 때문에 Tomcat 같은 WAS는 요청을 스레드로 처리합니다. 대신 공유한 만큼 동기화 책임이 생기고, 이것이 2부의 주제입니다.

Linux에서는 모든 것이 파일이다

Linux는 디스크 파일뿐 아니라 소켓, 파이프, 터미널까지 같은 방식으로 다룹니다. 무엇을 열든 커널은 작은 정수 하나를 돌려주는데, 이것이 파일 디스크립터이고, 줄여서 fd라고 부릅니다.

디스크 파일의 메타데이터(권한, 크기, 블록 위치)는 inode에 있습니다. 서버 입장에서 중요한 사실은 클라이언트 연결 하나가 fd 하나라는 점입니다.

2부

CPU 하나를 여럿이 나눠 쓰는 법

운영체제가 실행 흐름을 갈아 끼우는 방법, 공유 자원을 지키는 방법, 메모리를 속이는 방법, 그리고 I/O를 기다리는 방법을 차례로 봅니다.

기초 원리 여기부터는 커널이 내부에서 무엇을 저장하고 바꾸는지 다룹니다.

커널은 PCB로 프로세스를 기억한다

CPU 코어 하나는 한 순간에 한 흐름만 실행합니다. 여러 프로그램이 동시에 도는 것처럼 보이는 건 커널이 아주 짧은 간격으로 실행 대상을 바꾸기 때문입니다.

바꿨다가 다시 이어 가려면 "어디까지 했는지"를 어딘가 적어 둬야 합니다. 커널은 프로세스마다 PCB라는 자료구조에 이 정보를 보관합니다. 스레드도 실행 단위이므로 각자 TCB를 가집니다.

컨텍스트 스위칭은 이렇게 일어난다

  1. 계기 발생

    타이머 인터럽트, I/O 대기, 더 급한 작업의 등장.

  2. 현재 상태 저장

    실행 중이던 흐름의 PC와 레지스터를 PCB에 씁니다.

  3. 다음 대상 선택

    스케줄러가 준비 큐에서 다음 흐름을 고릅니다.

  4. 새 상태 복원

    다른 프로세스라면 주소 공간도 바꿉니다.

  5. 실행 재개

    복원한 PC 위치부터 이어서 실행합니다.

실행 흐름을 갈아 끼우는 이 과정을 컨텍스트 스위칭이라고 합니다. 저장과 복원을 하는 동안 CPU는 아무 애플리케이션 일도 하지 않습니다.

스레드가 read()로 디스크를 기다리거나 락을 못 얻어 잠들 때도 일어나므로, 서버에서는 초당 수만 번 일어나는 것이 보통입니다.

스레드 전환이 프로세스 전환보다 싼 이유

직접 비용인 레지스터 저장과 복원은 둘 다 비슷합니다. 차이는 주소 공간에서 납니다. 다른 프로세스로 바꾸면 페이지 테이블이 바뀌므로, 주소 변환 결과를 담아 둔 TLB(뒤에서 다룸)를 비우거나 무효화해야 합니다. 최신 CPU는 PCID 같은 태그로 이 비용을 일부 줄입니다.

더 큰 것은 간접 비용인 캐시 오염입니다. 새 흐름은 자기 데이터가 캐시에 없어 한동안 느린 메모리를 읽습니다. 같은 프로세스의 스레드끼리는 힙을 공유하므로 이 손해가 덜합니다.

직접 비용은 대략 수 마이크로초 수준이지만, 스레드가 많아 전환이 잦아지면 캐시가 식는 간접 비용이 쌓여 처리량이 눈에 띄게 떨어집니다.

실행 중인 작업을 강제로 빼앗을 수 있으면 선점형, 스스로 내놓을 때까지 기다리면 비선점형입니다. 오래 기다린 작업의 우선순위를 서서히 올려 주는 에이징으로 기아 상태를 막습니다.

타임 슬라이스는 짧아도 길어도 문제다

Round Robin에서 한 번에 주는 시간을 타임 슬라이스라고 합니다. 너무 길면 FCFS처럼 되어 응답이 늦어지고, 너무 짧으면 일하는 시간보다 컨텍스트 스위칭에 쓰는 시간이 커집니다.

그래서 실제 운영체제는 고정된 규칙 하나를 쓰지 않습니다. 교과서의 MLFQ(다단계 피드백 큐)는 I/O를 자주 하는 대화형 작업을 우대하고 CPU를 오래 쓰는 작업은 낮은 큐로 내립니다.

Linux는 오랫동안 CPU 사용 시간을 공평하게 나누는 CFS를 썼고, 커널 6.6부터 EEVDF 스케줄러로 바뀌었습니다. 공통 목표는 공평함과 응답성 사이의 균형입니다.

count++는 CPU에서 읽기, 더하기, 쓰기 세 단계로 나뉩니다. 그 사이에 컨텍스트 스위칭이 끼어들면 한 번의 증가가 사라집니다.

이처럼 실행 순서에 따라 결과가 달라지는 상황이 경쟁 상태이고, 공유 자원을 건드리는 코드 구간을 임계 구역이라고 합니다.

임계 구역 해법이 지켜야 할 세 가지

임계 구역 문제의 해법은 아래 세 조건을 모두 만족해야 합니다. 하나라도 빠지면 데이터가 깨지거나, 시스템이 멈추거나, 누군가 영원히 굶습니다.

운영체제는 이를 위해 CPU가 제공하는 원자적 명령(test-and-set, compare-and-swap)을 바탕으로 락을 만듭니다. 읽고 쓰는 동작을 쪼갤 수 없게 한 번에 처리하는 명령입니다.

값이 0과 1뿐인 이진 세마포어는 뮤텍스와 비슷해 보이지만 소유권이 없습니다. 그래서 다른 스레드가 풀어 버릴 수 있고, 우선순위 역전 방지 같은 뮤텍스 전용 기능도 없습니다.

모니터는 락 사용을 언어가 대신해 준다

세마포어는 강력하지만, wait와 signal의 순서를 한 번만 틀려도 데드락이나 데이터 손상이 납니다. 모니터는 공유 데이터와 그 데이터를 다루는 연산을 묶고, 진입과 해제를 언어가 자동으로 처리합니다.

모니터 안에서 조건이 맞을 때까지 기다리는 장치가 조건 변수입니다. Java의 synchronized와 wait()/notify()가 대표적인 모니터 구현이며 5장에서 다룹니다.

락 없이 안전하게 만드는 길도 있습니다

값을 바꾸지 않는 불변 객체, 스레드마다 따로 두는 ThreadLocal, 원자적 명령 CAS를 쓰면 락 없이도 경쟁 상태를 피할 수 있습니다. Java 구현은 5장에서 봅니다.

교착 상태(Deadlock)는 네 조건이 겹칠 때

두 스레드가 서로 상대가 가진 락을 기다리며 영원히 멈추는 상태가 데드락입니다. 네 조건이 모두 성립해야 생깁니다.

상호 배제(한 번에 하나만), 점유 대기(가진 채로 더 요구), 비선점(빼앗을 수 없음), 순환 대기(기다림이 원을 이룸). 하나만 깨도 데드락은 원리적으로 생길 수 없습니다.

데드락을 다루는 네 가지 태도

전략방법대가
예방조건 하나를 구조적으로 깸(락 순서 고정)설계 제약
회피은행원 알고리즘으로 안전할 때만 할당최대 요구량을 미리 알아야 함
탐지와 회복대기 그래프의 사이클을 찾아 하나를 중단탐지 비용, 작업 손실
무시드물다고 보고 개발자에게 맡김생기면 직접 해결

범용 OS가 대개 무시를 택하는 이유는 비용 대비 효과입니다. 반면 DB는 트랜잭션 데드락을 탐지해 하나를 롤백합니다(4장). 애플리케이션에서 가장 실용적인 것은 락을 항상 같은 순서로 잡는 예방입니다.

멈추지 않아도 진행이 없을 수 있다

기아 상태는 시스템 전체는 돌아가는데 특정 작업만 계속 자원을 못 받는 상황입니다. 우선순위 스케줄링이나 불공정한 락에서 생기며, 에이징이나 공정 락(FIFO 순서)으로 막습니다.

라이브락은 스레드들이 멈춰 있지는 않지만 서로에게 양보만 반복해 아무도 진척이 없는 상황입니다. 좁은 복도에서 두 사람이 같은 방향으로 계속 비켜 서는 모습과 같습니다.

재시도에는 무작위 지연을 섞으세요

락 획득에 실패한 스레드들이 똑같은 간격으로 다시 시도하면 라이브락에 빠집니다. 재시도 간격에 무작위 값(jitter)을 더하면 엇갈리게 되어 풀립니다. 8장의 재시도 설계와 같은 원리입니다.

가상 메모리: 각자 전체를 가진 것처럼

프로세스는 0번지부터 시작하는 넓은 주소 공간을 혼자 쓰는 것처럼 동작합니다. 실제로는 운영체제가 이 가상 메모리 주소를 물리 메모리 위치로 바꿔 줍니다.

메모리를 4KB 크기의 페이지로 쪼개고, 물리 메모리의 같은 크기 칸(프레임)에 대응시킵니다. 이 대응표가 페이지 테이블입니다. 덕분에 프로세스끼리 격리되고, 당장 안 쓰는 페이지는 디스크에 둘 수 있습니다.

주소 변환을 빠르게 만드는 MMU와 TLB

메모리를 읽을 때마다 페이지 테이블을 먼저 읽어야 한다면 모든 접근이 두 배 이상 느려집니다. 64비트 시스템의 페이지 테이블은 여러 단계로 되어 있어 변환 한 번에 메모리를 몇 번씩 읽기도 합니다.

그래서 CPU 안의 MMU가 주소 변환을 하드웨어로 처리하고, 최근 변환 결과를 TLB라는 작은 캐시에 둡니다. 지역성 덕분에 대부분의 변환은 TLB에서 끝납니다.

앞에서 프로세스 전환이 비싼 이유로 든 것이 바로 이 TLB입니다. 주소 공간이 바뀌면 이전 프로세스의 변환 결과는 쓸모가 없어집니다.

페이지 폴트: 없는 페이지를 건드렸을 때

  1. 접근 시도

    페이지 테이블에 해당 페이지가 메모리에 없다고 표시돼 있습니다.

  2. 페이지 폴트

    MMU가 예외를 일으켜 커널로 넘어갑니다.

  3. 빈 프레임 확보

    없으면 교체 알고리즘으로 하나를 내보냅니다.

  4. 디스크에서 읽기

    그동안 이 스레드는 잠들고 다른 흐름이 돕니다.

  5. 테이블 갱신, 재실행

    멈췄던 명령을 처음부터 다시 실행합니다.

운영체제는 프로그램을 시작할 때 모든 페이지를 올리지 않고, 실제로 접근할 때 비로소 올립니다. 이를 요구 페이징이라고 하며, 그 출발점이 페이지 폴트입니다.

디스크를 읽어야 하는 페이지 폴트는 메모리 접근보다 수만 배 이상 느립니다. 자주 일어나면 성능이 급격히 떨어집니다.

무엇을 내보낼까: 페이지 교체와 스래싱

메모리가 가득 차면 페이지 하나를 내보내야 합니다. 앞으로 가장 오래 안 쓸 페이지를 고르는 OPT가 이상적이지만 미래를 알 수 없어 구현이 불가능합니다. 그래서 과거로 미래를 추정하는 LRU(가장 오래전에 쓴 것부터)를 근사해 씁니다. LRU를 빠르게 구현하는 자료구조는 3장에서 봅니다.

프로세스들이 당장 필요한 페이지(작업 집합)조차 메모리에 다 못 올리면, 페이지를 들였다 내보내기만 반복하며 CPU가 놉니다. 이것이 스래싱입니다.

서버가 스왑을 쓰기 시작하면 이미 늦었습니다

JVM 힙이 스왑으로 밀려나면 GC가 디스크를 읽으며 수 초씩 멈춥니다. 서버는 메모리 여유를 두고 힙 크기를 물리 메모리보다 넉넉히 작게 잡습니다(5장).

페이징과 세그멘테이션, 그리고 단편화

기준페이징세그멘테이션
나누는 단위고정 크기 페이지의미 단위(코드, 스택 등)
외부 단편화생기지 않음빈 공간이 조각남
내부 단편화마지막 페이지에 남는 공간거의 없음
현재 쓰임대부분의 OS가 기본으로 사용보호 단위 개념으로 남음

외부 단편화는 빈 공간의 합은 충분한데 연속된 덩어리가 없어 못 쓰는 상황, 내부 단편화는 할당된 칸 안에서 남아 버려지는 공간입니다. 페이징은 크기를 고정해 외부 단편화를 없앤 대신 약간의 내부 단편화를 받아들였습니다.

격리된 프로세스끼리 말하는 방법, IPC

방식특징쓰이는 곳
파이프한 방향 바이트 흐름ps | grep 같은 셸 연결
공유 메모리복사가 없어 가장 빠름대량 데이터, 직접 동기화 필요
메시지 큐메시지 단위로 커널이 전달작업 전달
소켓다른 기계와도 통신 가능모든 네트워크 서비스

가상 메모리 덕분에 프로세스는 서로의 메모리를 볼 수 없습니다. 그래서 데이터를 주고받으려면 IPC라는 커널이 마련한 통로가 필요합니다. 이 중 소켓은 같은 fd 인터페이스로 다른 기계까지 닿으며, 2장의 출발점입니다.

동기/비동기와 블로킹/논블로킹은 다르다

블로킹(호출이 끝날 때까지 멈춤)논블로킹(즉시 반환)
동기(결과를 내가 챙김)일반 read(), JDBC 호출준비됐는지 반복해서 확인(폴링)
비동기(완료를 통보받음)비동기 호출 후 곧바로 결과를 기다림콜백, 이벤트로 완료 통지

블로킹과 논블로킹은 호출한 쪽이 제어권을 바로 돌려받는가의 문제이고, 동기와 비동기는 결과를 누가 챙기는가의 문제입니다. 축이 다르므로 네 가지 조합이 나옵니다.

비동기+블로킹은 Future.get()을 바로 호출하는 경우처럼 비동기의 이점을 버린 조합이라 대개 실수입니다.

소켓 수천 개를 스레드 하나로 지켜보기

방식감시 대상 등록준비된 fd 찾기한계
select호출마다 전체를 커널에 복사전부 훑어봄 O(n)fd 1024개 제한
poll호출마다 전체 배열 전달전부 훑어봄 O(n)개수 제한은 없음
epoll한 번 등록하면 커널이 유지준비된 것만 받음Linux 전용

연결마다 블로킹 read()를 하려면 연결 수만큼 스레드가 필요합니다. 대신 "이 fd들 중 읽을 준비가 된 것을 알려 달라"고 한 번에 묻는 것이 I/O 멀티플렉싱입니다. epoll은 연결 수천 개 중 소수만 활발한 서버에서 특히 유리합니다. macOS와 BSD에는 kqueue가 같은 역할을 합니다.

이벤트 루프는 기다림을 커널에 맡긴다

이벤트 루프는 epoll로 준비된 fd 목록을 받아 각 fd의 핸들러를 실행하고, 다시 epoll로 돌아가는 무한 반복입니다. 소켓은 모두 논블로킹으로 열어 두므로 핸들러는 절대 기다리지 않습니다.

스레드 하나가 기다리는 일은 커널에 맡기고 할 일이 있는 연결만 처리하므로, 스레드와 컨텍스트 스위칭이 거의 늘지 않습니다. 대신 핸들러 하나가 오래 걸리면 모든 연결이 멈춥니다.

3부

원리가 장애로 드러나는 순간

스레드를 몇 개 둘지, 왜 늘렸는데 더 느려지는지, fd가 왜 바닥나는지, 그리고 왜 고성능 서버가 이벤트 루프를 택했는지 봅니다.

원리 실무 스레드 풀 크기 계산, 관측 명령어, 커널 한도, 장애 사례를 다룹니다.

요청마다 스레드를 만들면 안 되는 이유

스레드는 공짜가 아닙니다. 생성과 소멸에 시스템 콜이 들고, 스레드마다 스택 메모리를 예약합니다. JVM 스레드 스택은 64비트 Linux에서 기본 1MB입니다. 요청이 몰릴 때마다 스레드를 새로 만들면 생성 비용이 쌓이고, 끝없이 늘어난 스레드가 메모리와 CPU를 잡아먹어 서버가 통째로 쓰러집니다.

그래서 서버는 미리 정해진 수의 스레드를 만들어 두고 작업을 큐로 받아 재사용하는 스레드 풀을 씁니다. 풀의 크기가 곧 동시에 처리할 수 있는 작업 수의 상한이 되고, 이 상한이 과부하로부터 서버를 지키는 방어선이 됩니다. Tomcat의 요청 스레드 풀은 6장에서 다룹니다.

스레드 풀 크기는 대기 비율로 정한다

// CPU 바운드: 코어 수 근처
threads ≈ cores + 1

// I/O 바운드 (Java Concurrency in Practice)
threads ≈ cores × (1 + 대기 시간 / 계산 시간)

// 예: 8코어, 요청당 계산 10ms, DB 대기 90ms
threads ≈ 8 × (1 + 90 / 10) = 80

암호화, 이미지 처리처럼 CPU만 쓰는 CPU 바운드 작업은 코어보다 스레드가 많아 봐야 전환 비용만 늘어납니다.

DB나 외부 API를 기다리는 I/O 바운드 작업은 스레드가 기다리는 동안 코어가 놀기 때문에 더 많은 스레드가 필요합니다. 공식은 출발점일 뿐이고, 부하 테스트로 처리량이 꺾이는 지점을 찾아 확정합니다.

스레드를 늘렸더니 더 느려졌다

$ vmstat 1
procs ------cpu------ -system-
 r  b  us sy id wa     in    cs
 6  0  71 12 17  0  9120 21034
58  0  48 41 11  0  9870 389211

$ pidstat -w -p 4321 1   # 프로세스별 전환

8코어 서버에서 풀을 500으로 키운 뒤의 모습입니다(예시 값). 실행 대기 r이 코어 수의 일곱 배, 초당 컨텍스트 스위칭 cs가 열 배 이상 늘었고, 커널 시간 sy가 41%입니다.

CPU가 일보다 전환과 락 경합에 시간을 쓰고 있습니다. 풀 크기를 되돌리고 느린 I/O 자체를 줄이는 것이 답입니다.

장애 사례: 느린 외부 API가 풀을 삼킨다

  1. 평소

    외부 API 응답 50ms, 스레드 200개로 여유롭게 처리합니다.

  2. 외부 지연

    상대 서버가 느려져 응답이 10초로 늘어납니다.

  3. 풀 고갈

    모든 스레드가 그 호출을 기다리며 블로킹됩니다.

  4. 전면 장애

    외부 API와 무관한 헬스 체크까지 큐에서 밀려 실패합니다.

CPU는 한가한데 서버가 응답하지 않는다면 대개 이 패턴입니다. 블로킹 I/O 모델에서는 기다리는 스레드도 풀 한 칸을 차지하기 때문입니다.

모든 외부 호출에 타임아웃을

연결과 읽기 타임아웃을 반드시 짧게 두고, 호출 대상별로 풀을 나눕니다(벌크헤드). 장애 격리 패턴은 8장에서 다룹니다.

Too many open files: fd 고갈

$ ulimit -n
1024
$ ls /proc/4321/fd | wc -l
1021
$ cat /proc/4321/limits | grep files
Max open files   1024   524288   files
$ lsof -p 4321 | awk '{print $5}' | sort | uniq -c
    37 REG

연결 하나가 fd 하나이므로, 프로세스별 열린 파일 한도(많은 배포판에서 기본 soft 값 1024)에 닿으면 새 연결을 accept()하지 못하고 EMFILE 오류가 납니다.

먼저 누수인지 정상 증가인지 가려야 합니다. 닫지 않은 소켓이나 파일이 계속 쌓인다면 한도를 올려도 시간만 벌 뿐입니다.

fd 고갈은 한도와 누수 둘 다 본다

원인증상대응
한도가 너무 낮음트래픽에 비례해 fd 증가systemd LimitNOFILE 상향
소켓을 닫지 않음트래픽이 줄어도 계속 증가try-with-resources, close 확인

셸의 ulimit는 그 셸에서 띄운 프로세스에만 적용되므로, systemd 서비스나 컨테이너는 각자의 설정에서 한도를 올려야 합니다(9장). 소켓 상태별 개수를 보는 방법은 2장에서 다룹니다.

Nginx, Node, Netty가 이벤트 루프인 이유

기준연결당 스레드이벤트 루프
연결 1만 개스레드 1만 개, 스택 수 GB코어 수만큼의 스레드

코드 작성위에서 아래로 쉬움콜백, 비동기로 복잡
CPU 작업다른 스레드는 영향 적음루프 전체가 멈춤

동시 연결 1만 개를 다루는 C10K 문제에서 연결당 스레드 모델은 메모리와 컨텍스트 스위칭에 무너졌습니다. 대부분의 연결이 대부분의 시간 동안 아무것도 안 한다는 점에 착안해, 기다림을 epoll에 맡긴 것이 이벤트 루프 서버입니다.

세 서버는 루프를 이렇게 돌린다

Node.jsJS 실행은 메인 루프 하나libuv 스레드 풀(기본 4개)
NettyEventLoop 여러 개, 기본 코어 수 × 2직접 별도 풀로 넘겨야 함

Nginx는 보통 worker_processes auto로 코어 수만큼 워커를 띄우고, 워커당 동시 연결은 worker_connections(기본 512)로 정합니다. 이 값도 결국 열린 파일 한도를 넘을 수 없습니다. Node는 파일 I/O와 DNS 조회를 libuv 스레드 풀로 돌리고, Spring WebFlux가 Netty 위에서 동작합니다(6장).

이벤트 루프를 막는 코드가 가장 위험하다

이벤트 루프 서버에서 핸들러 안에 블로킹 JDBC 호출, 큰 JSON 파싱, 동기 파일 읽기를 넣으면 그 시간 동안 같은 루프에 붙은 모든 연결이 응답을 멈춥니다. 스레드 수가 적어서 생기는 효율이 그대로 약점이 됩니다.

무거운 작업은 별도 워커 스레드 풀로 넘기고, 루프는 I/O 이벤트를 나누는 일만 하게 둡니다. 반대로 대부분이 DB 호출이고 동시 연결이 많지 않다면 스레드 모델이 더 단순하고 충분합니다.

세 번째 길: 가벼운 스레드

Java 21의 Virtual Thread는 블로킹 코드처럼 쓰되 기다리는 동안 OS 스레드를 내놓게 해, 두 모델의 장점을 합치려는 시도입니다. 5장에서 다룹니다.

정리

  • 성능은 느린 층에 덜 내려가는 데서 나옵니다. 캐시, 버퍼, 시스템 콜 줄이기가 모두 메모리 계층의 격차를 피하는 방법입니다.
  • 스레드는 힙을 공유하고 스택을 따로 가집니다. 공유는 싸지만, 그만큼 경쟁 상태를 막을 동기화 책임이 생깁니다.
  • 데드락은 네 조건이 모두 있어야 생깁니다. 실무에서는 락 순서를 고정해 순환 대기를 깨는 것이 가장 확실합니다.
  • 가상 메모리는 페이지 단위로 주소를 바꿔 줍니다. TLB와 페이지 폴트가 컨텍스트 스위칭과 스래싱 비용의 정체입니다.
  • 스레드 수는 대기 비율로 정하고, 연결이 많으면 이벤트 루프를 씁니다. 스레드도 fd도 무한하지 않은 자원입니다.

스스로 점검 (1)

  1. 2차원 배열을 열 우선으로 순회하면 왜 느려지나요?

    메모리는 행 단위로 연속 배치되므로 열 우선은 매번 다른 캐시 라인을 건드립니다. 공간 지역성을 못 살려 캐시 미스가 늘어납니다.

  2. 스레드마다 스택을 따로 두지 않고 공유하면 어떻게 될까요?

    스레드들이 서로 다른 함수를 실행하며 지역 변수와 복귀 주소를 같은 곳에 덮어써 실행 흐름이 깨집니다. 호출 기록은 실행 흐름마다 고유해야 합니다.

  3. 프로세스 전환이 스레드 전환보다 비싼 가장 큰 이유는 무엇인가요?

    주소 공간이 바뀌어 TLB 항목이 무효화되고 캐시에 쓸모없는 데이터가 남기 때문입니다. 레지스터 저장 자체의 비용은 비슷합니다.

  4. 이진 세마포어로 뮤텍스를 완전히 대신할 수 없는 이유는 무엇인가요?

    세마포어에는 소유권이 없어 락을 잡지 않은 스레드도 풀 수 있습니다. 실수로 다른 스레드가 해제해도 막을 장치가 없습니다.

  5. 모든 스레드가 락 A, B를 항상 A 다음 B 순서로 잡으면 데드락이 생길 수 있나요?

    생기지 않습니다. 순서가 고정되면 B를 가진 채 A를 기다리는 스레드가 없어 순환 대기가 성립하지 않습니다.

스스로 점검 (2)

  1. 메모리가 부족할 때 프로세스를 더 띄우면 CPU 사용률이 오히려 떨어지는 이유는요?

    작업 집합을 메모리에 다 못 올려 페이지 폴트가 폭증하고, 스레드들이 디스크 I/O를 기다리며 잠듭니다. 이것이 스래싱입니다.

  2. epoll이 select보다 연결이 많을 때 유리한 이유는 무엇인가요?

    select는 호출마다 전체 fd 목록을 복사하고 모두 훑지만, epoll은 한 번 등록해 두면 준비된 fd만 돌려줍니다. 비용이 전체 연결 수가 아닌 활성 연결 수에 비례합니다.

  3. 4코어 서버에서 요청당 계산 20ms, DB 대기 180ms라면 스레드는 대략 몇 개가 적당한가요?

    4 × (1 + 180/20) = 40개 정도가 출발점입니다. 이후 부하 테스트로 처리량이 꺾이는 지점을 확인해 조정합니다.

  4. ulimit를 올렸는데도 며칠 뒤 다시 Too many open files가 난다면 무엇을 의심해야 하나요?

    fd 누수입니다. 트래픽과 무관하게 fd가 늘어나는지, CLOSE_WAIT 소켓이 쌓이는지 lsof로 확인합니다.

  5. Netty 핸들러 안에서 JDBC를 직접 호출하면 무슨 일이 생기나요?

    DB 응답을 기다리는 동안 그 EventLoop에 묶인 모든 연결이 처리되지 못합니다. 블로킹 작업은 별도 스레드 풀로 넘겨야 합니다.
