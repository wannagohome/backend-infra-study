1부

서버리스: 서버 대신 이벤트를 다룬다

16장에서 요청이 엣지와 보안 계층을 지나오는 길을 봤습니다. 이제 그 요청을 받아 처리하는 쪽, 서버를 직접 띄우지 않는 컴퓨팅으로 들어갑니다.

서버리스는 용량 계획을 AWS에 넘긴다

서버리스는 서버가 없다는 뜻이 아니라, 서버의 개수와 크기, 패치, 확장을 내가 정하지 않는다는 뜻입니다. 14장의 EC2나 ECS는 "몇 대를 띄울까"를 먼저 정하고 그 용량에 요청을 맞췄습니다.

서버리스는 반대로 요청이 오는 만큼 실행 단위를 만들고, 요청이 없으면 0까지 줄입니다. 그래서 요금도 켜 둔 시간이 아니라 실제로 처리한 요청과 시간에 붙습니다.

대가도 있습니다. 실행 환경을 내가 고르지 못하니 처음 뜰 때의 지연, 실행 시간 상한, 연결 수 폭증 같은 제약이 생깁니다. 이 장은 그 제약이 어디서 오는지 따라갑니다.

서버리스는 Lambda만이 아닙니다

SQS, SNS, EventBridge, Step Functions, DynamoDB도 용량을 정하지 않고 쓴 만큼 냅니다. 이 장의 서비스 대부분이 같은 성격입니다.

핸들러는 이벤트와 컨텍스트를 받는다

public class OrderHandler
    implements RequestHandler<SQSEvent, Void> {

  // 핸들러 밖: 실행 환경당 한 번만 실행
  static final DynamoDbClient DDB =
      DynamoDbClient.create();

  public Void handleRequest(SQSEvent event,
                            Context ctx) {
    for (SQSMessage m : event.getRecords()) {
      ctx.getLogger().log(m.getMessageId());
      save(DDB, m.getBody());
    }
    return null;
  }
}

핸들러는 Lambda가 부르는 진입 함수입니다. 첫 인자 이벤트는 호출한 서비스가 보낸 JSON이고, 둘째 인자 컨텍스트는 요청 ID, 남은 실행 시간, 로거 같은 실행 정보입니다.

이벤트 모양은 트리거마다 다릅니다. SQS는 Records 배열을, API Gateway는 메서드·경로·헤더·본문을 보냅니다. 핸들러 밖 static 필드는 환경이 뜰 때 한 번만 만들어집니다.

실행 환경은 세 단계를 거친다

Init 단계에서 Lambda는 확장(extension)을 띄우고, 런타임(JVM 등)을 부팅하고, 핸들러 밖 코드를 실행합니다. 10초를 넘기면 첫 호출 때 함수 타임아웃 기준으로 다시 시도합니다. 호출이 끝나면 환경은 동결되어 CPU는 멈추고 메모리는 남습니다.

동결과 재사용이 만드는 세 가지 습관

  • SDK 클라이언트, 커넥션, 파싱한 설정처럼 만들기 비싼 객체는 핸들러 밖에 두어 실행 환경당 한 번만 만듭니다.
  • 로그 전송이나 메트릭 flush 같은 비동기 작업은 응답을 반환하기 전에 끝냅니다. 반환 뒤에는 환경이 동결되어 다음 호출까지 멈춥니다.
  • /tmp와 static 변수의 내용은 남아 있을 수도, 사라질 수도 있습니다. 캐시로는 쓰되 정답의 근거로 쓰지 않습니다.

환경 재사용은 보장이 아닙니다

동시 요청은 서로 다른 환경에서 처리되고, AWS는 언제든 환경을 회수합니다. 상태는 DynamoDB, S3, ElastiCache 같은 외부 저장소에 둡니다.

2부

콜드 스타트, 동시성, 재시도의 원리

실행 환경이 어떻게 만들어지고 늘어나는지, 실패한 호출이 어디로 가는지를 메커니즘으로 봅니다.

기초 원리 여기부터는 실행 환경과 호출 경로의 내부 동작을 다룹니다.

콜드 스타트는 환경을 처음 만드는 비용이다

  1. 환경 생성

    Firecracker microVM 하나를 배정합니다.

  2. 코드 내려받기

    zip 패키지나 컨테이너 이미지를 가져옵니다.

  3. 런타임 시작

    JVM이나 Node.js 프로세스를 띄웁니다.

  4. 초기화 코드

    핸들러 밖 코드: SDK 클라이언트, DI 컨테이너 생성.

  5. 핸들러 실행

    여기부터가 요청 처리(Invoke) 시간입니다.

1~4단계가 콜드 스타트입니다. 재사용되는 환경은 5단계만 실행합니다(웜 스타트). 전체 호출 중 비율은 작아도 p99 지연을 끌어올립니다.

Java는 JVM 기동, 클래스 로딩, Spring 컨텍스트 생성 때문에 4단계가 수 초에 이르기도 합니다. 실제 값은 로그 REPORT 줄의 Init Duration으로 확인합니다.

Java 함수라면 SnapStart부터 켭니다

수 초 걸리던 Init이 최적의 경우 1초 미만으로 줄어듭니다. Python과 .NET은 스냅샷 캐싱·복원 요금이 따로 붙습니다.

SnapStart는 Init을 배포 시점으로 옮긴다

  1. 버전 게시

    함수 버전을 게시할 때 Lambda가 Init을 미리 실행합니다.

  2. 스냅샷 저장

    초기화된 환경의 메모리와 디스크를 스냅샷으로 떠 암호화·캐시합니다.

  3. 호출 시 복원

    새 환경은 처음부터 초기화하지 않고 스냅샷에서 이어서 시작합니다.

  4. 여러 환경이 공유

    스냅샷 하나가 모든 새 환경의 출발 상태가 됩니다.

마지막 단계가 함정입니다. Init 중에 만든 난수 시드, 고유 ID, 임시 자격 증명은 모든 환경에 똑같이 복제됩니다. 고유해야 하는 값은 복원 뒤에 만듭니다.

Init 중에 맺은 네트워크 연결도 복원 뒤 살아 있다는 보장이 없습니다. AWS SDK 연결은 대부분 알아서 다시 맺지만, 직접 만든 커넥션 풀은 다시 엽니다.

Java 함수는 런타임 훅으로 미리 데운다

public class Handler implements Resource {
  public Handler() {
    Core.getGlobalContext().register(this);
  }
  @Override // 스냅샷 직전
  public void beforeCheckpoint(
      Context<? extends Resource> c) {
    warmUp();     // 자주 쓰는 경로를 미리 실행
    pool.close(); // 연결은 스냅샷에 넣지 않음
  }
  @Override // 복원 직후
  public void afterRestore(
      Context<? extends Resource> c) {
    pool = newPool(); // 연결을 새로 맺음
  }
}

SnapStart는 CRaC(org.crac) 인터페이스로 훅을 줍니다. beforeCheckpoint에서 자주 쓰는 경로를 한 번 실행해 두면 클래스 로딩과 JIT 결과까지 스냅샷에 담깁니다(priming).

그 밖의 Java 팁: 메모리는 1GB 이상에서 시작해 측정하고, 무거운 리플렉션 기반 프레임워크 대신 가벼운 DI를 고르며, Arm(Graviton)으로 단가를 낮춥니다.

동시성은 요청률과 실행 시간의 곱이다

동시성은 같은 순간 요청을 처리 중인 실행 환경 수입니다. 환경 하나가 요청 하나만 처리하므로 필요한 동시성은 초당 요청 × 평균 실행 시간입니다.

초당 500건, 평균 200ms면 100개입니다. 같은 트래픽에서 DB가 느려져 2초가 되면 1,000개가 필요합니다. 지연이 늘어도 동시성이 폭증합니다.

함수 확장 속도10초마다 환경 1,000개
동기 호출 요청률동시성 × 10 RPS
초과 시(동기)429 TooManyRequests
 새 계정은 더 낮게 시작해 사용량에 따라 자동으로 올라갑니다.

예약 동시성은 계정 풀에서 함수 몫을 떼어 다른 함수가 못 쓰게 하는 동시에, 이 함수가 그 이상 늘지 못하게 막습니다. 계정 전체로는 예약하지 않은 몫이 최소 100은 남아야 합니다. 프로비저닝된 동시성은 별칭이나 버전에 걸고, Application Auto Scaling으로 시간대별로 조절합니다.

비동기 호출은 Lambda 내부 큐를 거친다

비동기 호출에서 Lambda는 이벤트를 내부 큐에 넣고 바로 202를 돌려줍니다. 함수가 오류를 내면 기본 2번 더 시도하며 간격은 1분, 2분입니다.

스로틀이나 시스템 오류면 이벤트를 큐로 돌려 최대 6시간까지 다시 시도합니다. 큐가 최종 일관성이라 오류가 없어도 같은 이벤트가 두 번 올 수 있습니다.

SQS를 읽는 함수에는 이 설정이 듣지 않습니다

SQS 트리거는 비동기 호출이 아니라 이벤트 소스 매핑입니다. 실패 메시지는 함수가 아니라 소스 큐의 DLQ로 보냅니다.

이벤트 소스 매핑은 Lambda가 대신 읽는다

SQS, Kinesis, DynamoDB Streams, MSK처럼 메시지를 쌓아 두는 소스는 스스로 함수를 부르지 못합니다. 그래서 Lambda가 이벤트 소스 매핑(ESM)이라는 폴러를 돌려 소스를 읽고, 모은 레코드를 함수에 동기 호출로 넘깁니다.

성공하면 폴러가 SQS 메시지를 지우거나 스트림 위치를 옮깁니다. 한 번에 넘길 양은 배치 크기와 배치 창(최대 300초)이 정합니다.

스트림에서는 실패한 배치가 샤드를 막는다

SQS와 달리 Kinesis와 DynamoDB Streams는 순서가 있는 로그입니다. 배치가 실패하면 Lambda는 성공하거나 레코드가 만료될 때까지 그 배치를 다시 시도하고, 그동안 같은 샤드의 뒤쪽 레코드는 멈춥니다. 처리 지연 지표 IteratorAge가 계속 오르면 이 상황입니다.

    SQSEvent event, Context ctx) {
  List<BatchItemFailure> failed =
      new ArrayList<>();
  for (SQSMessage m : event.getRecords()) {
    try {
      process(m);
    } catch (Exception e) {
      failed.add(new BatchItemFailure(
          m.getMessageId()));
    }
  }
  return new SQSBatchResponse(failed);
}

ReportBatchItemFailures를 켜고 실패한 메시지 ID만 반환하면 나머지는 지워지고 그것만 다시 보입니다. Kinesis는 실패한 시퀀스 번호부터 다시 읽습니다.

버전은 고정되고 별칭은 가리킨다

버전은 코드와 설정을 얼린 스냅샷으로, 게시한 뒤에는 바꿀 수 없습니다. 별칭은 특정 버전을 가리키는 이름표입니다.

호출자는 별칭 ARN을 부르고, 배포는 별칭이 가리키는 버전을 바꾸는 일이 됩니다. 두 버전에 가중치를 주면 새 버전에 10%만 보내는 Canary가 됩니다(전략은 11장, AWS 배포 도구는 18장).

VPC 안의 Lambda는 NAT 없이 못 나간다

Lambda는 기본적으로 AWS가 관리하는 망에서 돌며 인터넷에 나갈 수 있습니다. Private Subnet의 RDS에 닿으려고 내 VPC에 연결하면, 서브넷과 보안 그룹 조합마다 만들어진 Hyperplane ENI를 여러 환경이 함께 씁니다.

이 ENI에는 공인 IP가 없습니다. 그래서 Private Subnet → NAT Gateway 경로가 있어야 외부 API를 부를 수 있습니다(13장).

환경마다 연결을 열면 DB가 먼저 무너진다

서버 애플리케이션은 커넥션 풀로 연결 수를 묶었습니다(4장). Lambda는 환경 하나가 프로세스 하나라 환경마다 풀이 따로 생깁니다. 풀 크기 기본값 10을 그대로 두고 동시성이 200이 되면 연결 시도는 2,000개입니다.

Lambda 안의 풀은 크기를 1~2로 줄이고, 함수와 RDS 사이에 연결을 모아 다중화하는 RDS Proxy(15장)를 둡니다.

연결 수의 상한은 동시성 상한입니다

RDS Proxy가 있어도 함수 동시성이 무한히 늘면 프록시 대기열이 막힙니다. 예약 동시성으로 DB가 견딜 상한을 함께 겁니다(6부 사례).

Lambda의 시간 한계를 넘는 새 선택지

Lambda Managed Instances는 내가 고른 EC2 인스턴스 유형 위에서 Lambda 함수를 돌립니다. 인스턴스 수명 주기와 패치는 AWS가 맡고, 환경 하나가 여러 요청을 동시에 처리하며, 비동기·ESM 호출은 최대 90분까지 돕니다. EC2 Savings Plans가 적용되어 꾸준한 고부하에 맞습니다.

durable functions는 체크포인트와 재생(replay)으로 최대 1년짜리 다단계 흐름을 함수 코드로 씁니다. 대기 중에는 컴퓨팅 요금이 붙지 않습니다. 같은 문제를 상태 머신으로 푸는 것이 3부의 Step Functions입니다.

중간에 쪼갤 수 없는 몇 시간짜리 배치라면 ECS 태스크나 AWS Batch(14장)가 더 단순합니다.

엔드포인트 유형도 고릅니다. 엣지 최적화는 AWS 관리형 CloudFront를 앞에 두고, 리전은 같은 리전 클라이언트나 내 CloudFront(16장)용, 프라이빗은 VPC 인터페이스 엔드포인트로만 열립니다.

프록시 통합은 응답 형식을 지켜야 한다

{
  "statusCode": 201,
  "headers": {
    "Content-Type": "application/json",
    "Access-Control-Allow-Origin":
      "https://app.example.com"
  },
  "isBase64Encoded": false,
  "body": "{\"orderId\":42}"
}

Lambda 프록시 통합에서 함수는 HTTP 응답 자체를 이 모양으로 돌려줘야 합니다. body는 객체가 아니라 문자열입니다.

형식이 틀리면 API Gateway는 "Malformed Lambda proxy response"와 함께 502를 냅니다. 함수가 예외로 끝나도 502, 통합 타임아웃을 넘기면 504입니다. HTTP API의 페이로드 형식 2.0은 문자열만 반환해도 200으로 감싸 줍니다.

JWT의 구조와 서명 검증 원리는 7장에서 봤습니다. 여기서의 질문은 그 검증을 어디서 하느냐입니다. 관문에서 막으면 인증에 실패한 요청은 백엔드 함수를 깨우지 않으므로 요금과 동시성을 아낍니다. HTTP API에서 Cognito 토큰은 JWT 권한 부여자로 검증합니다.

Lambda 권한 부여자는 정책을 캐시한다

  1. 요청 도착

    TOKEN 유형은 헤더 하나, REQUEST 유형은 헤더·쿼리·경로를 꺼냅니다.

  2. 캐시 확인

    같은 키의 결과가 TTL(기본 300초, 최대 3600초) 안이면 함수를 건너뜁니다.

  3. 함수 호출

    함수가 principalId와 IAM 정책(Allow 또는 Deny)을 반환합니다.

  4. 정책 평가

    정책의 Resource가 이번 메서드 ARN과 맞지 않으면 403입니다.

  5. 백엔드 호출

    함수가 넣은 context 값을 통합에 넘깁니다.

흔한 함정은 캐시와 정책 범위의 조합입니다. 첫 요청이 GET /orders/1이라서 그 메서드만 허용한 정책이 캐시되면, 같은 토큰으로 부른 POST /orders는 캐시된 정책 때문에 403을 받습니다.

캐시를 쓴다면 정책 Resource를 API 전체 와일드카드로 넓게 반환하거나, 캐시 키에 경로를 넣습니다.

스로틀링은 계정, 스테이지, 클라이언트 순

  1. 계정(리전)10,000 RPS, 버스트 5,000
  2. 스테이지·메서드경로별 상한
  3. 사용량 계획API 키별 rate, quota
  4. 통합 대상Lambda, HTTP 등

API Gateway는 8장의 Token Bucket으로 스로틀링합니다. 계정 단위 한도 아래 스테이지·메서드 한도를, 다시 그 아래 사용량 계획으로 클라이언트(API 키)별 초당 요청, 버스트, 일·월 할당량을 겁니다. 넘치면 429입니다. 일부 신규 리전은 계정 기본값이 2,500 RPS입니다.

API 키는 인증 수단이 아닙니다

키는 클라이언트를 식별해 사용량 계획을 적용하는 용도이고 쉽게 유출됩니다. 인증은 앞 슬라이드의 권한 부여로 따로 겁니다.

캐시, 검증, 매핑은 REST API의 무기다

캐시: 스테이지에 0.5~237GB 캐시를 켜면 같은 요청의 응답을 TTL(기본 300초, 최대 3600초) 동안 백엔드 없이 돌려줍니다. 캐시 키에 필요한 쿼리 문자열과 헤더를 추가하며, 캐시는 켜 둔 시간만큼 과금됩니다.

요청 검증: 모델(JSON 스키마)로 본문과 필수 파라미터를 검사하면 잘못된 요청은 400으로 끝나 백엔드에 닿지 않습니다.

매핑 템플릿: VTL 템플릿으로 요청과 응답을 변환해 AWS 서비스 통합이 원하는 모양을 만듭니다. HTTP API에는 셋 다 없고 파라미터 매핑만 있습니다.

CORS와 커스텀 도메인도 관문에서 처리

CORS(원리는 7장): HTTP API는 허용 오리진·메서드·헤더를 설정하면 preflight(OPTIONS)에 API Gateway가 직접 답합니다. REST API는 콘솔이 Mock 통합의 OPTIONS 메서드를 만들어 주지만, 프록시 통합이면 본 응답의 CORS 헤더는 함수가 넣어야 합니다. 한쪽만 하면 preflight는 통과하고 본 요청이 막힙니다.

커스텀 도메인: api.example.com에 ACM 인증서를 붙이고 API 매핑으로 여러 API와 스테이지를 경로별로 연결한 뒤, Route 53 Alias로 가리킵니다. 엣지 최적화는 us-east-1 인증서, 리전 엔드포인트는 같은 리전 인증서가 필요합니다(16장).

메시지 그룹이 순서와 병렬성의 단위다

FIFO 큐는 MessageGroupId가 같은 메시지끼리만 순서를 지킵니다. A1이 처리 중이면 A2는 A1이 삭제될 때까지 누구에게도 전달되지 않습니다.

그래서 병렬성은 그룹 수만큼이고, 계좌 ID처럼 순서가 필요한 단위로 그룹을 잘게 나눌수록 처리량이 오릅니다. 중복 제거 ID(또는 본문 해시)가 5분 안에 같으면 두 번째 송신은 성공 응답만 받고 전달되지 않습니다.

DLQ는 독이 든 메시지를 격리한다

  1. 소스 큐메시지 수신
  2. 처리 실패 반복수신 횟수 증가
  3. 임계 초과maxReceiveCount
  4. DLQ로 이동알람, 원인 조사
  5. 재처리(redrive)고친 뒤 소스로 복귀

형식이 깨진 메시지처럼 몇 번을 받아도 실패하는 메시지는 끝없이 재전달되며 컨슈머를 갉아먹습니다. 소스 큐의 재처리 정책(redrive policy)에 DLQ와 maxReceiveCount를 지정하면, 수신 횟수가 그 값을 넘은 메시지가 DLQ로 옮겨집니다.

원인을 고친 뒤에는 콘솔이나 StartMessageMoveTask API로 DLQ 메시지를 원래 큐로 되돌립니다. FIFO 큐의 DLQ는 FIFO여야 하고, Standard에서는 만료가 원래 등록 시각 기준이므로 DLQ 보존 기간을 소스보다 길게 잡습니다.

키는 SQS 메시지 ID보다 주문 ID 같은 비즈니스 키가 낫습니다. 생산자가 같은 주문을 두 번 보내면 메시지 ID는 달라지기 때문입니다. Powertools for AWS Lambda의 Idempotency 유틸리티가 이 패턴을 구현합니다.

SNS는 한 번 발행하면 구독자 모두에게 민다

SNS의 토픽은 발행 지점이고, 구독은 토픽과 엔드포인트(프로토콜과 주소)의 연결입니다. 발행자는 구독자가 누구인지 모릅니다.

SNS는 메시지를 저장하지 않고 즉시 밀어 넣으며, 구독자 하나가 느려도 다른 구독자에는 영향이 없습니다. 메시지는 기본 256KiB, 토픽 설정으로 최대 1MiB입니다.

SNS 앞, SQS 뒤: 팬아웃의 기본 형태

주문 완료 이벤트를 결제, 재고, 알림이 모두 받아야 하면 토픽에 한 번 발행하고, 구독자마다 SQS 큐를 하나씩 붙여 버퍼로 씁니다. 재고 서비스가 잠시 죽어도 메시지는 큐에 남습니다.

큐에는 토픽이 SendMessage할 수 있게 큐 정책을 두고, 원본 메시지 전달(raw message delivery)을 켜면 SNS 봉투 없이 본문만 들어갑니다.

필터 정책으로 받을 메시지를 고른다

{
  "eventType": ["order_placed"],
  "amount": [{ "numeric": [">=", 100000] }],
  "region": [{ "anything-but": ["test"] }],
  "channel": [{ "prefix": "app-" }]
}
// FilterPolicyScope: MessageAttributes(기본)
//                  또는 MessageBody

필터 정책이 없으면 구독자는 모든 메시지를 받습니다. 정책을 붙이면 SNS가 메시지 속성(기본) 또는 본문을 보고 맞는 것만 전달합니다. 키 사이는 AND, 배열 안 값은 OR입니다.

컨슈머가 받아서 버리는 대신 SNS에서 거르므로 큐 적재와 함수 호출이 줄어듭니다. 토픽당 필터 정책은 200개까지입니다.

SNS 재시도는 대상 종류에 따라 다르다

SQS나 Lambda 같은 AWS 관리형 엔드포인트로의 전달은 23일에 걸쳐 100,015번 시도합니다. HTTP/S는 기본 정책이 훨씬 짧고 전달 정책으로 바꿀 수 있지만 총 재시도 시간은 3,600초를 넘지 못합니다. 그래도 실패하면 메시지는 버려지므로, 구독마다 SQS 큐를 구독 DLQ로 붙입니다.

FIFO 토픽은 SQS 큐만 구독할 수 있고, 메시지 그룹 순서와 중복 제거를 SQS FIFO 큐까지 이어 줍니다. 그룹당 초당 300건이 상한이며, 아카이브 정책으로 메시지를 보관했다가 구독자에게 다시 재생할 수 있습니다.

모든 이벤트는 같은 봉투를 씁니다. source와 detail-type이 무슨 일인지, detail이 내용입니다.

이벤트 버스는 이벤트를 받는 라우터입니다. AWS 서비스 이벤트가 들어오는 기본 버스, 내 앱용 사용자 지정 버스, SaaS 이벤트를 받는 파트너 버스가 있습니다. SNS가 구독자 목록으로 보낸다면 EventBridge는 내용으로 보냅니다.

규칙은 패턴으로 고르고 대상에 넘긴다

{
  "source": ["com.shop.orders"],
  "detail-type": ["OrderPlaced"],
  "detail": {
    "amount": [{ "numeric": [">", 100000] }],
    "tier": ["gold", "platinum"]
  }

규칙은 패턴에 맞는 이벤트를 대상에 넘깁니다. 대상은 규칙당 최대 5개로, Lambda, SQS, SNS, Step Functions, Kinesis, 다른 버스, 외부 HTTP를 부르는 API 대상(API destination) 등입니다.

입력 변환기는 이벤트에서 필요한 값만 꺼내 대상이 원하는 모양으로 바꿉니다. 버스당 규칙은 기본 300개입니다.

재시도, DLQ, 아카이브로 이벤트를 지킨다

대상 전달이 실패하면 EventBridge는 기본 24시간 동안 최대 185번, 지수 백오프와 지터로 다시 시도합니다. 그래도 안 되면 이벤트를 버리므로 대상마다 SQS DLQ를 붙이고, 재시도 횟수와 최대 이벤트 수명은 대상별로 줄일 수 있습니다.

아카이브는 버스에 들어온 이벤트를 패턴으로 골라 보관하고, 재생은 지정한 시간 구간의 이벤트를 다시 버스에 흘립니다. 버그를 고친 뒤 놓친 이벤트를 다시 처리할 때 씁니다.

스키마 레지스트리는 버스에 흐르는 이벤트 구조를 자동으로 발견해 저장하고, Java, Python, TypeScript 코드 바인딩을 내려받게 해 줍니다.

Pipes는 점대점, Scheduler는 시간

  1. 소스SQS, Kinesis, DDB Streams
  2. 필터이벤트 패턴으로 거름
  3. 보강Lambda, API로 데이터 추가
  4. 대상Step Functions, 버스 등

EventBridge Pipes는 소스 하나와 대상 하나를 잇는 관리형 파이프입니다. ESM처럼 소스를 폴링하고, 거르고, 보강해서 넘기므로 그 사이를 잇던 Lambda 글루 코드가 사라집니다.

EventBridge Scheduler는 cron이나 rate 식, 또는 일회성 시각에 AWS API를 호출합니다. 시간대, 유연한 시간 창, 재시도와 DLQ를 지원하고 일정을 수백만 개 만들 수 있어 주문마다 "24시간 뒤 리마인드" 같은 개별 예약에 맞습니다.

5부

로그를 쌓아 두고 여러 번 읽는다

큐는 처리한 메시지를 지우지만 스트림은 보존 기간 동안 순서대로 쌓아 둡니다. Kinesis, Firehose, MSK를 보고 메시징 서비스 전체를 비교합니다.

Kinesis는 파티션 키로 샤드를 고른다

스트림은 샤드의 묶음입니다. 레코드의 파티션 키를 MD5로 해시해 그 값을 맡은 샤드에 넣고, 샤드 안에서는 시퀀스 번호 순서가 보장됩니다.

같은 키는 항상 같은 샤드로 가므로 키별 순서가 지켜지고, 키가 한쪽에 몰리면 그 샤드만 뜨거워집니다(핫 샤드). Kafka의 파티션(8장)과 같은 구조입니다.

샤드 하나는 쓰기 1MB/s, 읽기 2MB/s

항목한도의미

컨슈머 셋이 공유 읽기를 쓰면 2MB/s를 나눠 각자 약 0.67MB/s밖에 못 읽고, 초당 5회 호출 한도 때문에 지연도 늘어납니다. 같은 스트림을 읽는 컨슈머가 둘을 넘으면 향상된 팬아웃을 검토합니다.

KCL은 샤드를 임대하고 체크포인트를 남긴다

  1. 임대 테이블

    KCL이 DynamoDB 테이블에 샤드마다 임대(lease) 행을 만듭니다.

  2. 임대 획득

    워커들이 임대를 나눠 가져 샤드 하나는 워커 하나만 읽습니다.

  3. 처리와 체크포인트

    레코드를 처리하고 시퀀스 번호를 주기적으로 기록합니다.

  4. 워커 장애

    다른 워커가 임대를 가져가 마지막 체크포인트부터 읽습니다.

  5. 재샤딩

    부모 샤드를 다 읽은 뒤 자식 샤드로 넘어가 순서를 지킵니다.

체크포인트 뒤에 처리했지만 기록 전에 죽은 레코드는 다시 읽히므로 Kinesis 소비도 최소 한 번입니다.

Lambda ESM은 이 일을 대신하며, ParallelizationFactor로 샤드당 최대 10개 배치를 동시에 처리하되 같은 파티션 키의 순서는 지킵니다. 처리 지연은 IteratorAge로 봅니다.

Firehose는 버퍼에 모아 목적지에 쌓는다

  1. 입력Direct PUT, Kinesis, MSK
  2. 버퍼크기나 시간 중 먼저
  3. 변환Lambda, Parquet 변환
  4. 목적지S3, Redshift, OpenSearch

Amazon Data Firehose(옛 Kinesis Data Firehose)는 컨슈머 코드 없이 데이터를 목적지에 쌓는 적재 전용 서비스입니다. 샤드도 용량 설정도 없습니다. 버퍼가 차면 묶어서 쓰므로 실시간이 아니라 준실시간이고, 지나간 데이터를 다시 읽을 수 없습니다.

JSON을 Parquet이나 ORC로 바꾸고 S3 경로를 값에 따라 나누는 동적 파티셔닝으로 Athena 쿼리 비용을 줄입니다. Splunk, 일반 HTTP 엔드포인트, Apache Iceberg 테이블도 목적지가 됩니다.

Amazon MQ는 ActiveMQ와 RabbitMQ를 관리형으로 제공합니다. JMS, AMQP, MQTT, STOMP를 쓰는 기존 앱을 코드 변경 없이 옮길 때 고르고, 새 시스템이라면 SQS와 SNS가 운영 부담이 적습니다.

6부

서버리스와 메시징이 무너지는 방식

자동으로 늘어나는 컴퓨팅과 자동으로 재시도하는 메시징은 잘못 엮이면 장애를 키웁니다. 실제로 자주 터지는 사례와 막는 설정을 봅니다.

원리 실무 장애 사례, 방어 설정, 비용 계산, 경보 지표를 다룹니다.

급증한 이벤트가 Lambda를 거쳐 DB를 죽인다

ESM이 적체를 보고 폴러를 늘리면서 동시성이 1,000까지 오르고, 최대 연결 수가 1,000인 RDS에 연결 시도가 2,000개 몰립니다. 연결이 거부되어 함수가 실패하면 메시지가 다시 보여 재시도가 쌓이고, 같은 DB를 쓰던 웹 API까지 함께 멈춥니다.

상한, 큐 버퍼, 프록시로 막는다

  1. 큐로 받기

    동기 호출 대신 SQS에 넣어 급증을 큐에 쌓습니다.

  2. ESM 최대 동시성

    이 큐를 읽는 동시성을 DB가 버티는 값으로 묶습니다.

  3. 예약 동시성

    함수 전체 상한을 같은 값 이상으로 걸어 다른 경로도 막습니다.

  4. RDS Proxy

    남은 연결을 프록시가 다중화해 DB 연결 수를 고정합니다.

  5. 적체 감시

    가장 오래된 메시지 나이로 처리 지연을 봅니다.

상한 계산: DB가 이 작업에 내줄 연결이 50, 환경당 연결 1개면 최대 동시성은 50입니다. 처리 0.5초면 초당 100건이라 50만 건은 약 83분에 소화됩니다.

이 시간이 너무 길면 상한을 올릴 것이 아니라 배치 쓰기나 쿼리 튜닝으로 건당 처리 시간을 줄입니다.

재시도는 계층마다 곱해진다

  1. 앱 클라이언트3회 시도
  2. Lambda 비동기최대 3회 실행
  3. AWS SDK기본 3회 시도
  4. 하류 서비스최대 27배 요청

각 계층이 "세 번까지만"이라도 곱하면 하류는 요청 하나에 최대 27번 맞습니다. 막 회복하려던 서비스가 몰려든 재시도에 다시 쓰러지는 것이 재시도 폭풍입니다.

재시도는 한 계층에서만 하고, 지수 백오프와 지터를 넣고, 전체 시간 예산(데드라인)을 넘기면 포기하며, 하류가 계속 실패하면 서킷 브레이커로 끊습니다(8장). 비동기 함수는 MaximumRetryAttempts를 0~1로 줄이고 실패 Destination으로 넘기는 편이 안전합니다.

포이즌 메시지는 소스마다 막는 곳이 다르다

소스증상방어
SQS Standard계속 재전달, 동시성 소모DLQ와 부분 배치 응답
SQS FIFO같은 그룹 전체가 멈춤DLQ로 빼야 그룹이 풀림
Kinesis, DDB Streams샤드가 막혀 지연 상승Bisect, 재시도 상한, 실패 대상

공통 규칙은 둘입니다. DLQ에 메시지가 1건이라도 들어오면 경보를 울리고, 원인을 고친 뒤 재처리(redrive)합니다. DLQ를 만들고 아무도 보지 않으면 데이터 유실을 미뤄 둔 것에 불과합니다.

중복과 순서는 경계마다 다시 깨진다

$ aws dynamodb update-item \
  --table-name orders \
  --key '{"id":{"S":"42"}}' \
  --update-expression \
    "SET st = :s, ver = :v" \
  --condition-expression \
    "attribute_not_exists(ver) OR ver < :v" \
  --expression-attribute-values \
    '{":s":{"S":"SHIPPED"},":v":{"N":"7"}}'

중복은 SQS 가시성 만료, Lambda 비동기 큐, SNS와 EventBridge 재시도, Kinesis 체크포인트 이전 재처리, 생산자의 송신 재시도에서 모두 생깁니다. 그래서 "정확히 한 번"은 전달이 아니라 처리 결과로 만듭니다.

순서도 FIFO나 샤드 안에서만 지켜지고, 병렬 처리나 실패분 재처리가 끼면 결과 순서는 뒤집힙니다. 메시지에 버전을 넣고 더 새로운 버전일 때만 쓰는 조건부 쓰기로 늦게 온 옛 이벤트를 버립니다.

자주 터지는 설정 실수 다섯 가지

  • 큐 가시성 타임아웃을 함수 타임아웃보다 짧게 두면 ESM 생성이 거부되고, 직접 만든 컨슈머라면 처리 중인 메시지가 중복 전달됩니다.
  • S3 업로드 이벤트로 도는 함수가 같은 버킷에 결과를 쓰면 무한 루프가 됩니다. 입력과 출력 버킷이나 접두사를 반드시 나눕니다.
  • 함수 타임아웃을 900초로 두면 하류가 멈췄을 때 환경이 15분씩 묶여 동시성이 금방 바닥납니다. p99의 몇 배로 짧게 둡니다.
  • 예약 동시성 0은 긴급 차단 스위치로는 유용하지만, 실수로 남겨 두면 모든 호출이 스로틀되는 장애입니다.
  • 비밀 값을 환경 변수에 평문으로 넣지 않습니다. Secrets Manager(16장)에서 읽어 핸들러 밖에 캐시합니다.

Lambda 요금은 요청 수와 GB-초다

요금은 요청 100만 건당 $0.20과 GB-초당 $0.0000166667입니다(us-east-1, x86). GB-초는 메모리(GB) × 실행 시간(초)이고 1ms 단위로 올림합니다. Arm은 GB-초 단가가 20% 낮습니다.

예시를 보면 앞단 API Gateway가 함수보다 비싼 경우가 흔합니다. 로그, NAT, 프로비저닝된 동시성 요금도 따로 붙습니다.

정리

  • Lambda 환경 하나는 요청 하나를 처리합니다. 그래서 동시성은 요청률 × 실행 시간이고, 콜드 스타트와 DB 연결 폭증이 모두 여기서 나옵니다.
  • 호출 방식이 실패의 행방을 정합니다. 동기는 호출자, 비동기는 내부 큐와 Destinations, ESM은 소스의 DLQ와 실패 대상입니다.
  • API Gateway와 Step Functions는 함수 밖으로 일을 뺍니다. 인증·스로틀·검증은 관문에서, 재시도·대기·보상은 상태 머신에서 합니다.
  • 큐는 지우고 로그는 남깁니다. SQS·SNS·EventBridge는 라우팅과 완충, Kinesis·MSK는 순서 있는 재읽기에 씁니다.
  • 중복은 반드시 오고, 재시도는 곱해집니다. 멱등 처리, 동시성 상한, DLQ 경보를 처음부터 함께 설계합니다.

스스로 점검 1

  1. 초당 300건, 평균 400ms인 함수가 DB 지연으로 2초가 되면 동시성은 어떻게 되나요?

    300 × 0.4 = 120에서 300 × 2 = 600으로 다섯 배가 됩니다. 트래픽이 그대로여도 지연만으로 동시성과 DB 연결이 폭증합니다.

  2. SnapStart를 켠 Java 함수가 Init에서 UUID 생성기 시드를 만들면 어떤 문제가 생기나요?

    스냅샷 하나에서 여러 환경이 복원되므로 모든 환경이 같은 시드를 가집니다. 고유 값은 afterRestore 훅이나 핸들러 안에서 만듭니다.

  3. S3 이벤트로 도는 함수가 계속 실패합니다. 실패 이벤트는 어디로 가고, 어떻게 붙잡나요?

    S3는 비동기 호출이라 Lambda 내부 큐에서 재시도한 뒤 버려집니다. 실패 Destination이나 함수 DLQ를 설정해야 남습니다.

  4. Lambda 권한 부여자에 캐시를 켰더니 일부 경로만 403이 납니다. 왜일까요?

    첫 요청의 메서드만 허용한 정책이 토큰 기준으로 캐시되어 다른 경로에도 쓰이기 때문입니다. 정책 Resource를 넓게 반환하거나 캐시 키에 경로를 넣습니다.

  5. Lambda 함수 타임아웃이 60초입니다. 소스 SQS 큐의 가시성 타임아웃은 얼마로 두나요?

    함수 타임아웃의 6배인 360초에 배치 창을 더한 값 이상입니다. 스로틀 뒤 재시도할 시간을 남겨 중복을 막습니다.

스스로 점검 2

  1. FIFO 큐에서 메시지 그룹 ID를 전부 같은 값으로 넣으면 처리량은 어떻게 되나요?

    그룹 안에서는 한 번에 한 메시지만 처리되므로 컨슈머를 늘려도 병렬성이 1입니다. 순서가 필요한 단위(계좌, 주문)로 그룹을 나눠야 합니다.

  2. SNS에서 SQS로 팬아웃할 때 구독자마다 큐를 따로 두는 이유는 무엇인가요?

    SNS는 메시지를 저장하지 않으므로 구독자가 잠시 죽으면 버퍼가 필요하고, 큐가 따로여야 구독자마다 자기 속도로 처리하고 장애가 서로 번지지 않습니다.

  3. Kinesis 컨슈머의 IteratorAge가 계속 오르기만 합니다. 무엇부터 의심하나요?

    실패한 배치가 같은 샤드에서 무한 재시도 중인지 봅니다. Bisect, 재시도 상한, 실패 대상을 설정하고 처리량이 모자라면 ParallelizationFactor나 샤드 수를 늘립니다.

  4. Step Functions에서 결제 단계가 들어가는 흐름에 Express를 쓰면 왜 위험한가요?

    비동기 Express는 최소 한 번 실행이라 같은 실행이 두 번 돌 수 있습니다. 결제처럼 멱등하지 않은 단계는 정확히 한 번인 Standard로 둡니다.

  5. 평균 초당 2건, 낮에만 몰리는 사내 API를 Lambda와 Fargate 중 무엇으로 두나요?

    손익분기(약 15건/초)보다 훨씬 낮고 밤에 0이 되므로 Lambda가 쌉니다. 콜드 스타트가 문제면 SnapStart나 작은 프로비저닝된 동시성으로 보완합니다.
