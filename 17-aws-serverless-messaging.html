서버를 띄우지 않고 코드를 돌린다는 것

16장에서 요청이 엣지와 보안 계층을 지나 들어오는 길을 봤습니다. 이 부에서는 그 요청을 받아 처리할 코드를, 서버 대수를 정하지 않고 실행하는 방법을 봅니다. 함수는 어디서 실행되고, 누가 어떻게 부르며, 무엇을 포기하는지가 이 부의 질문입니다.

서버 대수를 정하는 일 자체가 비용이다

이 장 내내 쓸 예제는 쇼핑몰의 주문 서비스입니다. 고객이 주문 버튼을 누르면 주문 API가 요청을 받고, 뒤에서 결제·재고·배송·알림이 차례로 처리됩니다. 이 서비스의 트래픽은 점심과 저녁에 몰리고 새벽에는 거의 없으며, 마케팅 푸시를 보낸 직후에는 평소의 수십 배로 튑니다.

14장의 EC2나 ECS로 이 서비스를 돌리려면 먼저 용량 계획을 해야 합니다. 서버를 몇 대, 어떤 크기로 띄울지 정하는 일입니다. 피크에 맞추면 새벽 내내 놀고 있는 서버에 요금을 내고, 평균에 맞추면 피크에 요청이 밀립니다. Auto Scaling으로 대수를 바꿀 수는 있지만 새 서버가 뜨는 데 분 단위가 걸리고, 최소 대수만큼은 늘 켜 둬야 합니다.

용량 말고도 할 일이 있습니다. OS 패치, 런타임 업그레이드, 장애 난 서버 교체, 여러 가용 영역에 나눠 배치하기가 모두 우리 몫입니다. 주문 코드 자체와는 상관없는 일인데 운영 시간의 큰 부분을 차지합니다.

그렇다면 질문을 뒤집어 볼 수 있습니다. "서버를 몇 대 띄울까"를 아예 정하지 않고, 요청이 올 때마다 그 요청을 처리할 자리를 클라우드가 알아서 만들어 주면 어떨까요? 다음 슬라이드의 서버리스가 이 발상입니다.

서버리스는 용량 계획을 AWS에 넘긴다

서버리스는 서버가 없다는 뜻이 아니라, 서버의 개수와 크기, 패치, 확장을 내가 정하지 않는다는 뜻입니다. 앞 슬라이드에서 우리가 하던 용량 계획을 AWS가 대신합니다. 요청이 오는 만큼 실행할 자리를 만들고, 요청이 없으면 0까지 줄입니다.

그래서 요금도 켜 둔 시간이 아니라 실제로 처리한 요청 수와 처리 시간에 붙습니다. 새벽에 주문이 없으면 요금도 거의 없습니다.

대가도 있습니다. 실행 환경을 내가 고르지 못하니 처음 뜰 때의 지연, 실행 시간 상한, 데이터베이스 연결 수 폭증 같은 제약이 생깁니다. 이 장의 상당 부분은 그 제약이 어디서 오는지 따라가는 일입니다.

서버리스는 Lambda만이 아닙니다

메시지 큐(SQS), 알림(SNS), 이벤트 라우터(EventBridge), 워크플로(Step Functions)도 용량을 정하지 않고 쓴 만큼 냅니다. 모두 이 장 뒤에서 차례로 봅니다.

Lambda는 이벤트가 오면 함수를 실행한다

  1. 이벤트 발생주문 요청, 파일 업로드
  2. 트리거Lambda를 부르는 서비스
  3. 함수 실행내 코드가 이벤트 처리
  4. 결과응답 반환, DB 저장

AWS의 대표 서버리스 컴퓨팅인 Lambda에는 서버가 아니라 함수를 올립니다. 함수는 코드 묶음과 설정(메모리 크기, 최대 실행 시간, 그리고 12장에서 본 IAM 역할인 실행 역할)으로 이루어집니다. 실행 역할은 함수가 DynamoDB나 S3를 부를 때 쓰는 권한입니다.

함수는 스스로 깨어나지 않습니다. 무언가 일어났다는 사실, 즉 이벤트가 있어야 실행됩니다. 이벤트를 Lambda에 전달해 함수를 부르는 서비스를 트리거라고 합니다. 주문 서비스라면 "주문 API 요청이 왔다"(API Gateway가 트리거), "주문 메시지가 큐에 쌓였다"(SQS가 트리거)가 이벤트입니다. 다음 슬라이드에서 함수 코드가 이벤트를 어떻게 받는지 봅니다.

핸들러는 이벤트와 컨텍스트를 받는다

public class OrderHandler
    implements RequestHandler<SQSEvent, Void> {

  // 핸들러 밖: 실행 환경당 한 번만 실행
  static final DynamoDbClient DDB =
      DynamoDbClient.create();

  public Void handleRequest(SQSEvent event,
                            Context ctx) {
    for (SQSMessage m : event.getRecords()) {
      ctx.getLogger().log(m.getMessageId());
      save(DDB, m.getBody());
    }
    return null;
  }
}

핸들러는 Lambda가 부르는 진입 메서드입니다. 첫 인자 이벤트는 트리거가 보낸 JSON을 객체로 바꾼 것이고, 둘째 인자 컨텍스트는 요청 ID, 남은 실행 시간, 로거 같은 실행 정보입니다.

이 예는 주문 메시지를 담아 두는 큐(SQS, 4부)가 트리거라서 이벤트가 메시지 목록(Records)입니다. 반복문이 메시지마다 저장합니다. 위의 static 필드는 핸들러 밖이라 한 번만 만들어집니다. 왜 그런지는 다음 슬라이드의 실행 환경에서 나옵니다.

함수는 실행 환경이라는 작은 VM 안에서 돈다

Lambda는 함수를 실행 환경 안에서 실행합니다. 실행 환경은 9장에서 본 Firecracker microVM, 즉 꼭 필요한 가상 장치만 갖춰 1초 안에 뜨는 작은 VM 하나입니다. VM이므로 다른 고객의 함수와 커널까지 나뉘어 격리됩니다.

그 안에는 런타임(JVM, Node.js처럼 코드를 실행하는 프로그램), 내 코드, 그리고 /tmp라는 임시 디스크가 있습니다. 핵심 규칙은 환경 하나가 한 번에 요청 하나만 처리한다는 것입니다. 주문 100건이 동시에 오면 환경 100개가 필요합니다.

실행 환경은 생성, 실행, 회수를 거친다

Init에서 Lambda는 확장(로그 전송·모니터링 에이전트처럼 함수 옆에서 도는 동반 프로세스)을 띄우고, 런타임을 부팅하고, 핸들러 밖 코드를 실행합니다. Init에는 10초 제한이 있어, 넘기면 첫 호출 때 함수 타임아웃을 한도로 Init을 다시 시도합니다. 이어 Invoke에서 핸들러가 요청을 처리합니다.

호출이 끝나면 환경은 동결되어 CPU는 멈추고 메모리는 남습니다. 다음 요청이 오면 Init 없이 바로 Invoke합니다. Init부터 겪는 첫 요청을 콜드 스타트, 녹은 환경을 재사용하는 요청을 웜 스타트라고 합니다. 한동안 요청이 없으면 AWS가 환경을 Shutdown해 회수합니다. 콜드 스타트 비용은 2부에서 자세히 봅니다.

동결과 재사용이 만드는 세 가지 습관

앞의 생애주기에서 바로 세 가지 코딩 습관이 나옵니다.

  • SDK 클라이언트, 커넥션, 파싱한 설정처럼 만들기 비싼 객체는 핸들러 밖에 둡니다. Init에서 한 번 만들어 이후 웜 스타트가 모두 재사용합니다.
  • 로그 전송이나 지표 내보내기 같은 비동기 작업은 응답을 반환하기 전에 끝냅니다. 반환하는 순간 환경이 동결되어 그 작업도 다음 호출까지 멈추기 때문입니다.
  • /tmp와 static 변수의 내용은 다음 호출에 남아 있을 수도, 사라질 수도 있습니다. 캐시로는 쓰되 정답의 근거로는 쓰지 않습니다.

환경 재사용은 보장이 아닙니다

동시 요청은 서로 다른 환경에서 처리되고 AWS는 언제든 환경을 회수합니다. 주문 상태 같은 데이터는 DynamoDB, S3, ElastiCache 같은 외부 저장소(15장)에 둡니다.

Lambda에는 이제 세 가지 실행 모델이 있다

지금까지 본 "환경 하나에 요청 하나, 핸들러 함수" 모델이 Lambda의 원래 모습입니다. AWS는 이것을 Event Functions로 부르고, 같은 실행 환경 기술 위에 두 모델을 더했습니다. 포트를 여는 웹 서버 코드를 그대로 올리는 Web Functions와, 내 이미지를 몇 시간짜리 격리 환경으로 띄우는 MicroVMs입니다.

누가 어떻게 부르느냐로 호출 방식이 갈린다

주문 서비스에서 함수를 부르는 장면을 셋으로 나눠 보겠습니다. 첫째, 고객 앱이 주문 API를 부르면 앞단(API Gateway)은 함수 결과를 받아 고객에게 돌려줘야 합니다. 부른 쪽이 결과를 기다리는 이 방식이 동기 호출입니다.

둘째, 상품 이미지가 S3에 올라오면 썸네일 함수를 부르는데, S3는 결과를 기다릴 이유가 없습니다. 이벤트를 Lambda에 맡기고 바로 돌아서는 방식이 비동기 호출입니다. Lambda가 이벤트를 내부 큐에 넣었다가 함수에 넘깁니다.

셋째, 주문 메시지가 쌓인 큐(SQS)는 스스로 누군가를 부르는 기능이 없습니다. 그래서 Lambda가 큐를 대신 읽어 메시지를 함수에 넘겨 줍니다. 이것이 이벤트 소스 매핑(ESM)입니다. 지금은 "Lambda 안의 읽기 담당(폴러)이 소스를 당겨 온다" 정도로 알아 두고, 내부 동작은 2부에서 봅니다.

세 방식은 실패를 다루는 방법이 다릅니다. 특히 요청이 몰려 Lambda가 더 받지 못하고 거절하는 스로틀(HTTP 429, 8장의 처리율 제한과 같은 뜻)이 났을 때 누가 다시 시도하는지가 갈립니다. 다음 표가 그 차이입니다.

메모리 하나가 CPU까지 정한다

함수 설정에는 CPU 항목이 없습니다. 메모리를 128MB에서 10,240MB 사이로 고르면 CPU가 그에 비례해 붙고, 1,769MB에서 vCPU(가상 CPU, 14장) 한 개 상당이 됩니다. 메모리를 늘리면 CPU와 네트워크 몫도 함께 늘어나는 셈입니다.

요금은 메모리 × 실행 시간으로 매기므로(6부), CPU를 많이 쓰는 함수는 메모리를 올리면 실행 시간이 줄어 요금이 그대로이거나 오히려 내려가기도 합니다. 반대로 대부분의 시간을 DB 응답을 기다리며 보내는 함수는 메모리를 올려도 빨라지지 않습니다.

메모리는 측정해서 고릅니다

같은 함수를 메모리 몇 단계로 돌려 실행 시간과 요금을 비교합니다. 오픈소스 도구 AWS Lambda Power Tuning이 이 비교를 Step Functions로 자동화합니다.

코드는 zip이나 컨테이너 이미지로 올린다

함수 코드를 올리는 방법은 둘입니다. 첫째는 zip 패키지입니다. 컴파일한 코드와 라이브러리를 zip으로 묶어 올리고, 런타임은 AWS가 준비한 관리형 런타임(예: java21)을 고릅니다. 관리형 런타임은 AWS가 보안 패치를 자동으로 적용합니다. 목록에 없는 언어는 사용자 지정 런타임을 직접 만들어 올릴 수 있습니다.

여러 함수가 같은 라이브러리를 쓰면 함수마다 zip에 넣는 대신 레이어로 따로 올려 공유합니다. 레이어는 별도 zip으로, 실행 환경의 /opt 아래에 풀립니다. 주문 서비스의 공통 도메인 모델이나 모니터링 에이전트가 레이어 후보입니다.

둘째는 컨테이너 이미지입니다. 9장의 컨테이너 이미지를 ECR(14장)에 올리고 함수가 그 이미지를 쓰게 합니다. 의존성이 커서 zip 한도를 넘거나, 이미 Docker로 빌드·검사하는 파이프라인이 있을 때 고릅니다.

이미지로 배포해도 오래 떠 있는 서버가 되지는 않습니다. 실행 환경, 생애주기, 한 번에 요청 하나라는 실행 모델은 zip과 똑같고 포장만 다릅니다. 두 방식의 한도와 차이는 다음 표에 모았습니다.

zip은 가볍고, 이미지는 크고 익숙하다

가장 큰 차이는 패치 책임입니다. zip은 AWS가 런타임을 고쳐 주지만, 이미지 안의 런타임은 우리가 기반 이미지를 갱신해 다시 빌드해야 합니다. 함수 패키지가 클수록 2부에서 볼 콜드 스타트도 길어지므로, 크기는 작게 유지하는 쪽이 기본입니다.

버전은 고정되고, 별칭은 버전을 가리킨다

코드를 올리면 함수의 편집 중 사본 $LATEST가 바뀝니다. 운영 트래픽이 이것을 직접 부르면 올리는 순간 바로 반영되어 위험합니다. 그래서 버전을 게시합니다. 버전은 코드와 설정을 얼린 스냅샷으로 바꿀 수 없습니다. 별칭은 버전을 가리키는 이름표입니다.

호출자는 별칭의 ARN(12장)을 부르고, 배포는 별칭이 가리키는 버전을 바꾸는 일이 됩니다. 두 버전에 가중치를 주면 11장의 Canary가 됩니다.

2부

주문이 몰리면 Lambda 안에서 일어나는 일

1부에서 실행 환경 하나가 요청 하나를 처리한다는 규칙을 봤습니다. 주문이 몰리는 날 이 규칙은 세 질문이 됩니다. 새 환경을 만드는 데 얼마나 걸리나(콜드 스타트), 환경은 몇 개까지 늘어나나(동시성), 실패한 호출은 어디로 가나(재시도).

기초 원리 여기부터는 실행 환경과 호출 경로의 내부 동작을 다룹니다.

콜드 스타트는 환경을 처음 만드는 비용이다

  1. 환경 생성

    Firecracker microVM 하나를 배정합니다.

  2. 코드 내려받기

    zip 패키지나 컨테이너 이미지를 가져옵니다.

  3. 런타임 시작

    JVM이나 Node.js 프로세스를 띄웁니다.

  4. 초기화 코드

    핸들러 밖 코드: SDK 클라이언트, DI 컨테이너 생성.

  5. 핸들러 실행

    여기부터가 요청 처리(Invoke) 시간입니다.

1부의 Init 단계를 쪼개 보면 이렇습니다. 1~4단계가 콜드 스타트 비용이고, 재사용되는 환경은 5단계만 실행합니다.

1~3단계는 대부분 AWS 몫이고 패키지가 작을수록 짧아집니다. 우리가 가장 크게 좌우하는 곳은 4단계입니다. 핸들러 밖에서 무엇을 얼마나 만드느냐가 그대로 첫 요청의 지연이 됩니다.

콜드 스타트는 드물어도 꼬리 지연을 만든다

START RequestId: 8f2c... Version: 7
REPORT RequestId: 8f2c...
  Duration: 182.40 ms
  Billed Duration: 183 ms
  Memory Size: 1024 MB
  Max Memory Used: 214 MB

Lambda는 호출마다 로그(CloudWatch Logs)에 REPORT 줄을 남깁니다. Duration은 핸들러 실행 시간, Billed Duration은 과금 시간입니다. Init Duration은 콜드 스타트일 때만 찍히는 Init 시간입니다.

이 예는 Spring 기반 Java 함수입니다. JVM 기동, 클래스 로딩(5장), Spring 컨텍스트 생성(6장)으로 Init이 3초를 넘었습니다. 콜드 스타트가 1%만 돼도 p99(가장 느린 1% 경계의 지연)는 이 3초에 끌려 올라갑니다.

첫 번째 레버: Init 자체를 짧게 만든다

콜드 스타트를 줄이는 방법은 세 가지 레버로 정리됩니다. Init을 짧게 만들기, Init을 미리 끝내 둔 환경을 대기시키기, Init 결과를 저장해 두었다가 복원하기입니다. 첫 번째는 비용이 들지 않으므로 모든 함수의 기본입니다.

패키지를 줄입니다. 쓰지 않는 라이브러리를 빼면 2단계 내려받기와 3단계 클래스 로딩이 함께 줄어듭니다. 주문 함수가 AWS SDK 전체를 넣고 있다면 DynamoDB 모듈만 남깁니다.

무거운 프레임워크를 피합니다. 실행 중에 클래스를 훑어 객체를 만드는 리플렉션(5장) 기반 DI는 Init에서 수 초를 씁니다. 컴파일 시점에 연결을 끝내는 가벼운 DI나 프레임워크 없는 핸들러가 빠릅니다.

메모리를 올려 봅니다. Init도 CPU를 쓰므로 1부에서 본 메모리 비례 규칙이 그대로 적용됩니다. Java라면 1GB 이상에서 측정을 시작하고, 단가가 낮은 Arm(14장의 Graviton) 아키텍처도 함께 비교합니다. 그래도 남는 지연은 다음 두 레버로 다룹니다.

두 번째 레버: 데운 환경을 미리 세워 둔다

프로비저닝된 동시성은 Init까지 끝낸 실행 환경을 정한 수만큼 미리 띄워 두는 설정입니다. 요청이 오면 바로 Invoke로 들어가므로 그 수 안에서는 콜드 스타트가 없습니다.

대가는 요금과 예측입니다. 요청이 없어도 켜 둔 환경 수와 시간만큼 냅니다. 정한 수를 넘는 요청은 일반 환경으로 넘어가 다시 콜드 스타트를 겪습니다.

이 설정은 $LATEST가 아니라 1부에서 본 게시된 버전이나 별칭에 겁니다. 어떤 코드로 데워 둘지 고정돼야 하기 때문입니다.

주문 API처럼 점심 피크가 예측되면 Application Auto Scaling(EC2 밖의 자원 수를 일정이나 지표로 조절하는 AWS 기능)으로 피크 시간에만 늘리고 새벽에는 줄여 비용을 아낍니다.

세 번째 레버: SnapStart로 Init을 미리

  1. 버전 게시

    함수 버전을 게시할 때 Lambda가 Init을 미리 실행합니다.

  2. 스냅샷 저장

    초기화된 환경의 메모리와 디스크를 스냅샷으로 떠 암호화·캐시합니다.

  3. 호출 시 복원

    새 환경은 처음부터 초기화하지 않고 스냅샷에서 이어서 시작합니다.

  4. 여러 환경이 공유

    스냅샷 하나가 모든 새 환경의 출발 상태가 됩니다.

SnapStart는 Init 결과를 저장해 두었다가 복원합니다. 수 초 걸리던 Java Init이 최적의 경우 1초 미만으로 줄어듭니다.

마지막 단계가 함정입니다. Init 중에 만든 난수 시드, 고유 ID, 임시 자격 증명은 모든 환경에 똑같이 복제됩니다. Init 중에 맺은 네트워크 연결도 복원 뒤 살아 있다는 보장이 없습니다. 이 둘을 다루는 방법이 다음 슬라이드입니다.

Java 함수는 런타임 훅으로 미리 데운다

public class Handler implements Resource {
  public Handler() {
    Core.getGlobalContext().register(this);
  }
  @Override // 스냅샷 직전
  public void beforeCheckpoint(
      Context<? extends Resource> c) {
    warmUp();     // 자주 쓰는 경로를 미리 실행
    pool.close(); // 연결은 스냅샷에 넣지 않음
  }
  @Override // 복원 직후
  public void afterRestore(
      Context<? extends Resource> c) {
    pool = newPool(); // 연결을 새로 맺음
  }
}

SnapStart는 OpenJDK의 CRaC(org.crac) 인터페이스로 훅을 줍니다. 생성자에서 자신을 등록하면 스냅샷 직전에 beforeCheckpoint, 복원 직후에 afterRestore가 불립니다.

직전 훅에서 주문 처리 경로를 한 번 돌려 두면(priming) 클래스 로딩과 JIT 컴파일(5장) 결과까지 스냅샷에 담깁니다. 연결은 직전에 닫고 복원 뒤 새로 엽니다. AWS SDK 연결은 대부분 알아서 다시 맺습니다.

동시성은 요청률과 실행 시간의 곱이다

이제 두 번째 질문, 환경이 몇 개 필요한가입니다. 같은 순간 요청을 처리 중인 실행 환경 수를 동시성이라고 합니다. 환경 하나가 요청 하나만 처리하므로 필요한 동시성은 초당 요청 × 평균 실행 시간(초)입니다.

주문 함수가 초당 500건, 평균 200ms면 500 × 0.2 = 100개입니다. 트래픽은 그대로인데 DB가 느려져 2초가 되면 1,000개가 필요합니다. 지연만 늘어도 동시성이 폭증합니다.

동시성에는 계정 한도와 확장 속도가 있다

동시성은 무한히 늘지 않습니다. 리전마다 계정 전체가 나눠 쓰는 동시성 한도가 있고, 함수 하나가 늘어나는 속도에도 상한이 있습니다. 한도는 AWS 쪽 자원을 보호하는 장치이자, 버그 난 함수가 무한히 늘어 요금 폭탄을 만들지 않게 하는 안전장치입니다.

한도에 닿으면 동기 호출은 429 스로틀로 바로 실패합니다. 같은 계정의 다른 함수도 같은 풀을 쓰므로, 주문 함수 하나가 폭주하면 관리자 화면 함수까지 스로틀될 수 있습니다.

예약 동시성은 몫이자 상한이다

계정 풀을 함수끼리 다투지 않게 하는 설정이 예약 동시성입니다. 함수에 예약 동시성 200을 주면 계정 풀에서 200을 떼어 이 함수 몫으로 보장하고, 동시에 이 함수는 200을 넘지 못합니다. 보장과 상한이 한 숫자로 묶인다는 점이 핵심이며, 6부에서 DB를 지키는 데 이 상한을 씁니다. 앞에서 본 프로비저닝된 동시성과 이름이 비슷해 자주 헷갈리므로 나란히 놓습니다.

비동기 호출은 Lambda 내부 큐를 거친다

세 번째 질문, 실패한 호출은 어디로 가나입니다. 1부에서 본 비동기 호출부터 봅니다. Lambda는 이벤트를 내부 큐에 넣고 호출자에게 바로 202를 돌려줍니다. 함수가 오류를 내면 기본 2번 더 시도하며 간격은 1분, 2분입니다.

스로틀이나 시스템 오류면 이벤트를 큐로 돌려 최대 6시간까지 다시 시도합니다. 내부 큐는 여러 서버에 복제되며 최종 일관성으로 동작해서, 오류가 없어도 같은 이벤트가 두 번 올 수 있습니다.

끝내 실패한 비동기 이벤트는 Destinations로

그림 아래쪽의 두 상자가 실패와 성공의 행선지입니다. 예전에는 함수에 DLQ(SQS 큐나 SNS 토픽)를 붙여 실패 이벤트만 받았고, 지금은 성공과 실패를 따로 보낼 수 있는 Destinations를 씁니다. 새로 만든다면 Destinations가 낫습니다. 원본 이벤트와 함께 오류 내용이 담겨 왜 실패했는지 추적하기 쉽기 때문입니다.

SQS를 읽는 함수에는 이 설정이 듣지 않습니다

SQS 트리거는 비동기 호출이 아니라 이벤트 소스 매핑입니다. 실패 메시지는 함수가 아니라 소스 큐의 DLQ로 보냅니다(4부).

이벤트 소스 매핑은 Lambda가 대신 읽는다

이제 세 번째 호출 방식입니다. 메시지를 쌓아 두는 소스(SQS 큐, 그리고 5부에서 볼 순서 있는 로그인 Kinesis·DynamoDB Streams·MSK)는 스스로 함수를 부르지 못합니다. ESM은 Lambda가 관리하는 폴러로 소스를 읽어, 모은 레코드를 함수에 동기 호출로 넘깁니다.

한 번에 넘길 양은 배치 크기(최대 건수)와 배치 창(최대 300초까지 모으는 시간)이 정합니다. 성공하면 폴러가 SQS 메시지를 지우거나 스트림의 읽은 위치를 옮깁니다.

배치 하나가 실패하면 무엇이 다시 오는가

ESM은 레코드를 묶음으로 넘기므로 실패도 묶음 단위로 생각합니다. 기본 동작에서 함수가 예외를 던지면 Lambda는 배치 전체를 실패로 봅니다. 주문 메시지 10건 중 1건만 형식이 깨져도, 이미 저장한 9건까지 함께 실패 처리됩니다.

그 뒤 무슨 일이 일어나는지는 소스의 구조가 정합니다. SQS는 메시지를 지우지 않았으므로 4부에서 볼 가시성 타임아웃이 지나면 10건이 다시 큐에 보이고, 다시 배치로 묶여 옵니다. 순서가 없는 큐라서 다른 메시지 처리는 계속됩니다.

순서 있는 로그(Kinesis, DynamoDB Streams)는 다릅니다. 로그는 샤드라는 여러 줄로 나뉘고(5부), 한 샤드 안의 레코드는 순서대로 처리해야 합니다. 그래서 실패한 배치를 건너뛸 수 없고, 성공하거나 레코드가 만료될 때까지 같은 배치를 다시 시도합니다.

두 경우 모두 해법의 방향은 같습니다. 실패한 레코드만 골라내 다시 보내거나, 계속 실패하는 레코드를 다른 곳으로 치우는 것입니다. 다음 두 슬라이드가 스트림과 SQS 각각의 방법입니다.

스트림에서는 실패한 배치가 샤드를 막는다

스트림 배치가 계속 실패하면 그동안 같은 샤드의 뒤쪽 레코드는 멈춥니다. 마지막으로 읽은 레코드가 얼마나 오래됐는지를 보여 주는 지표 IteratorAge가 계속 오르면 이 상황입니다. ESM에는 이를 풀어 주는 설정이 있습니다.

코드는 메시지마다 try로 감싸 실패한 것만 failed에 모읍니다. Lambda는 목록에 없는 9건을 지우고 1건만 다시 보이게 합니다. Kinesis에서는 실패한 레코드의 시퀀스 번호를 돌려주면 그 지점부터 다시 읽습니다.

RDS에 닿으려면 Lambda를 VPC에 붙인다

지금까지 주문 함수는 DynamoDB처럼 인터넷 주소로 부르는 서비스만 썼습니다. 그런데 주문을 RDS에 저장한다면 사정이 다릅니다. 13장에서 본 대로 RDS는 보통 외부에서 닿지 않는 Private Subnet에 두기 때문입니다.

Lambda 함수는 기본적으로 내 VPC가 아니라 AWS가 관리하는 망에서 돌며, 거기서 인터넷으로 나갈 수 있습니다. 내 VPC 안의 자원에 닿으려면 함수를 VPC에 연결하고 서브넷과 보안 그룹을 지정합니다.

연결하면 Lambda는 지정한 서브넷에 ENI(13장의 가상 네트워크 카드)를 만듭니다. 예전에는 실행 환경마다 ENI를 만들어 콜드 스타트가 수십 초씩 걸렸습니다. 지금은 AWS의 네트워크 가상화 계층인 Hyperplane 위에 서브넷과 보안 그룹 조합마다 Hyperplane ENI를 하나 만들고 여러 환경이 함께 씁니다. 그래서 VPC 연결이 콜드 스타트를 크게 늘리지 않습니다.

대신 한 가지가 바뀝니다. 함수의 트래픽이 이제 내 VPC의 라우팅 규칙을 따릅니다. 다음 슬라이드에서 그 결과를 봅니다.

VPC 안의 Lambda는 NAT 없이 못 나간다

Hyperplane ENI에는 공인 IP가 없습니다. 그래서 VPC에 붙인 함수가 결제사 API 같은 외부 주소를 부르려면 Private Subnet → NAT Gateway 경로가 있어야 합니다(13장). 함수를 VPC에 붙이자마자 외부 호출이 타임아웃 나는 흔한 사고가 여기서 나옵니다.

S3와 DynamoDB로 가는 트래픽은 VPC Endpoint로 보내 NAT 처리 요금을 피합니다.

환경마다 연결을 열면 DB가 먼저 무너진다

RDS에 닿았으니 연결 수를 봐야 합니다. 4장의 커넥션 풀은 서버 한 대가 연결을 미리 열어 두고 스레드끼리 빌려 쓰는 장치였습니다. Lambda는 환경 하나가 프로세스 하나라 환경마다 풀이 따로 생깁니다. 풀 크기 기본값 10을 그대로 두고 동시성이 200이 되면 연결 시도는 2,000개입니다.

Lambda 안의 풀은 크기를 1~2로 줄이고, 15장에서 본 RDS Proxy(많은 클라이언트 연결을 적은 DB 연결에 나눠 싣는 관리형 풀)를 함수와 RDS 사이에 둡니다.

연결 수의 상한은 동시성 상한입니다

RDS Proxy가 있어도 동시성이 끝없이 늘면 프록시 대기열이 막힙니다. 예약 동시성으로 DB가 견딜 상한을 함께 겁니다. 실제 사고와 계산은 6부에서 봅니다.

함수 URL은 가장 단순한 HTTPS 입구다

3부의 API Gateway로 넘어가기 전에, 함수에 HTTP 입구를 다는 가장 단순한 방법을 봅니다. 함수 URL은 함수에 전용 HTTPS 주소를 붙입니다. 결제사가 결과를 알려 주는 웹훅 수신처럼 경로가 하나고 인증이 단순하면 충분합니다. 인증은 AWS_IAM(12장의 SigV4 서명을 요구)과 NONE(누구나 호출) 둘뿐이고, 응답을 다 만들기 전에 조금씩 흘려보내는 응답 스트리밍을 지원합니다.

15분 한계를 넘는 새 선택지 두 가지

1부의 15분 한도는 주문 처리처럼 짧은 일에는 충분하지만, 정산 배치나 몇 시간을 기다리는 흐름에는 모자랍니다. AWS는 이 틈을 메우는 두 기능을 더했습니다.

Lambda Managed Instances는 내가 고른 EC2 인스턴스 유형 위에서 Lambda 함수를 돌립니다. 인스턴스 수명 주기와 패치는 AWS가 맡고, 환경 하나가 여러 요청을 동시에 처리하며, 비동기·ESM 호출은 최대 90분까지 돕니다. 14장의 Savings Plans가 적용되어 꾸준한 고부하에 맞습니다.

durable functions는 여러 단계를 함수 코드로 쓰되, 단계가 끝날 때마다 결과를 저장(체크포인트)해 둡니다. 중간에 기다리거나 실패하면 함수를 다시 실행하면서 저장된 단계는 건너뛰고 결과만 꺼내 쓰는 재생(replay)으로 이어 갑니다. 이렇게 최대 1년짜리 흐름을 만들고, 기다리는 동안에는 컴퓨팅 요금이 붙지 않습니다.

같은 문제를 코드 대신 선언으로 푸는 것이 3부의 Step Functions입니다.

쪼갤 수 없는 긴 작업은 여전히 컨테이너로

중간에 나눌 수 없는 몇 시간짜리 배치라면 ECS 태스크나 AWS Batch(14장)가 더 단순합니다.

3부

함수 앞의 관문과 함수 사이의 지휘자

1~2부에서 주문을 처리하는 함수 하나를 깊게 봤습니다. 이 부의 질문은 둘입니다. 고객의 POST /orders를 함수 앞에서 어떻게 받고 지킬 것인가(API Gateway), 결제·재고·배송처럼 여러 함수로 나뉜 주문 처리를 실패에 강하게 어떻게 엮을 것인가(Step Functions).

API Gateway는 함수 앞에 선 관리형 관문이다

  1. 고객 앱POST /orders
  2. API Gateway인증, 제한, 검증
  3. 통합백엔드로 전달
  4. 주문 함수Lambda

7장에서 API Gateway를 "인증, TLS 종료, 라우팅, 요청 제한을 모든 요청이 지나는 입구 하나에서 처리하는 리버스 프록시"로 봤습니다. AWS API Gateway는 이것을 서버 없이 쓰는 관리형 서비스입니다. 주문 함수가 토큰 검증이나 요청 수 제한까지 하면 거절할 요청에도 함수가 깨어나 요금과 동시성을 씁니다. 관문에서 막으면 함수는 통과한 요청만 봅니다.

API Gateway가 요청을 뒤쪽 백엔드(Lambda, HTTP 서버, AWS 서비스)에 넘기는 연결을 통합이라고 합니다. 통합의 종류는 뒤에서 표로 보고, 먼저 API Gateway가 만드는 API의 종류부터 봅니다.

REST, HTTP, WebSocket: 세 종류의 API

REST API는 가장 오래되고 기능이 많은 종류입니다. 응답 캐시, 클라이언트별 사용량 제한(사용량 계획), 요청 본문 검증, 16장의 WAF 연결, VPC 안에서만 열리는 프라이빗 API를 지원합니다. 대신 요청당 요금이 셋 중 가장 비쌉니다.

HTTP API는 나중에 나온 가볍고 싼 종류입니다. REST API의 부가 기능 대부분을 빼는 대신 요금이 크게 낮고, 외부 로그인 서비스가 발급한 JWT를 바로 검증하는 기능과 자동 배포를 기본으로 줍니다. 주문 API처럼 요청을 Lambda에 넘기기만 하면 되는 경우에 먼저 고려합니다.

WebSocket API는 성격이 다릅니다. 2장의 WebSocket은 HTTP로 시작해 연결을 계속 열어 두고 양쪽이 아무 때나 메시지를 보내는 프로토콜입니다. "배송 출발" 같은 상태 변화를 서버가 먼저 고객 화면에 밀어 줄 때 씁니다.

세 종류 모두 백엔드에 넘긴 요청이 응답할 때까지 기다리는 최대 시간, 즉 통합 타임아웃이 있습니다. 이 값이 긴 작업을 설계하는 방식을 바꾸므로 뒤에서 따로 봅니다. 다음 표는 세 종류의 차이를 정리합니다.

REST API의 정의는 리소스(/orders 같은 경로)와 그 위의 메서드(GET, POST)로 이루어지고, 메서드마다 통합이 붙습니다. 정의를 고쳐도 바로 반영되지 않습니다. 배포를 만들어야 그 시점의 정의가 스냅샷으로 굳어 스테이지(dev, prod 같은 이름 붙은 실행 환경)에 올라갑니다. Lambda의 버전·별칭과 비슷한 구조입니다.

스테이지마다 스로틀, 로깅, 캐시, 스테이지 변수를 따로 두고, 카나리 설정으로 새 배포에 일부 트래픽만 보낼 수 있습니다. HTTP API는 자동 배포를 켜면 정의를 고칠 때마다 바로 반영됩니다.

엔드포인트 유형은 요청이 들어오는 길이다

REST API를 만들 때는 클라이언트가 어디서 들어오는지에 맞춰 엔드포인트 유형을 고릅니다. 같은 API라도 앞단 경로가 달라집니다.

16장에서 CloudFront와 WAF를 직접 앞에 두기로 했다면 리전 유형을 고르고 내 배포에 붙입니다. 엣지 최적화 유형의 CloudFront는 AWS가 관리해 캐시 동작을 바꿀 수 없기 때문입니다. 프라이빗 유형은 13장의 인터페이스 엔드포인트(VPC 안에 꽂는 서비스 전용 ENI)로만 접근됩니다.

통합은 요청을 백엔드에 넘기는 방식이다

스테이지에 올라간 메서드는 받은 요청을 통합으로 넘깁니다. 가장 흔한 것은 Lambda 프록시 통합입니다. 메서드, 경로, 헤더, 본문을 통째로 이벤트 JSON에 담아 함수에 넘기고, 함수가 돌려준 값을 그대로 HTTP 응답으로 바꿉니다. 변환 규칙이 없으니 설정이 단순하고, 대부분의 Lambda API가 이 방식을 씁니다.

프록시가 아닌 통합은 중간에 매핑 템플릿을 둡니다. 템플릿 언어(VTL)로 요청을 백엔드가 원하는 모양으로, 응답을 클라이언트가 원하는 모양으로 바꿉니다. 이 변환 덕분에 함수 없이 AWS 서비스 API(예: SQS에 메시지 넣기)를 바로 부르는 통합이 가능합니다.

백엔드가 VPC 안의 서버라면 VPC 링크로 Private Subnet의 ALB나 NLB(13장)에 요청을 넘깁니다. ECS나 EKS로 돌던 기존 주문 서버를 그대로 공개할 때 씁니다. HTTP API는 AWS의 서비스 이름 레지스트리인 Cloud Map에 등록된 서비스도 대상으로 삼습니다.

마지막으로 Mock 통합은 백엔드 없이 고정 응답을 돌려줍니다. 7장의 CORS 사전 요청(preflight, OPTIONS)에 답하거나, 백엔드가 준비되기 전 앞단을 시험할 때 씁니다.

받아서 큐에 넣기만 한다면 함수를 빼세요

주문 접수가 "검증 후 큐에 넣기"뿐이라면 AWS 서비스 통합으로 SQS SendMessage를 직접 부릅니다. Lambda 요금도 콜드 스타트도 없습니다.

프록시 통합은 응답 형식을 지켜야 한다

{
  "statusCode": 201,
  "headers": {
    "Content-Type": "application/json",
    "Access-Control-Allow-Origin":
      "https://app.example.com"
  },
  "isBase64Encoded": false,
  "body": "{\"orderId\":42}"
}

프록시 통합에서 함수는 HTTP 응답 자체를 이 모양으로 돌려줘야 합니다. 상태 코드, 헤더, 그리고 body인데, body는 객체가 아니라 JSON을 담은 문자열입니다.

형식이 틀리면 API Gateway는 "Malformed Lambda proxy response"와 함께 502를 냅니다(2장의 게이트웨이 오류). 함수가 예외로 끝나도 502, 통합 타임아웃을 넘기면 504입니다. HTTP API의 페이로드 형식 2.0은 문자열만 반환해도 200으로 감싸 줍니다.

권한 부여는 누가 부르는지를 관문에서 확인한다

통합 앞에서 API Gateway가 하는 첫 일은 "이 요청을 보낸 주체가 이 API를 불러도 되는가"를 확인하는 권한 부여입니다. JWT의 구조와 서명 검증 원리는 7장에서 봤으니, 여기서의 질문은 그 검증을 어디서 누가 하느냐입니다. 방식은 넷입니다.

IAM은 요청에 12장의 SigV4 서명을 요구하고 호출자의 IAM 정책으로 판단합니다. 사람보다 다른 AWS 서비스나 내부 시스템이 부를 때 맞습니다. Cognito 사용자 풀은 16장의 Cognito가 로그인 뒤 발급한 토큰을 검증합니다.

JWT 권한 부여자(HTTP API)는 Cognito를 포함한 아무 OIDC 공급자(7장)가 발급한 JWT의 서명과 iss(발급자), aud(이 토큰을 받을 대상) 값을 검사합니다. Lambda 권한 부여자는 내가 쓴 함수가 직접 판단합니다. 자체 토큰 형식이나 "VIP 고객만 대량 주문 가능" 같은 규칙에 씁니다.

어느 방식이든 관문에서 막으면 인증에 실패한 요청은 주문 함수를 깨우지 않습니다. 다음 표가 넷을 정리하고, 이어서 가장 함정이 많은 Lambda 권한 부여자를 자세히 봅니다.

"지원 API" 열을 보면 Cognito 사용자 풀 방식은 REST API에만 있습니다. HTTP API에서 Cognito 토큰을 쓰려면 Cognito를 OIDC 발급자로 보고 JWT 권한 부여자로 검증합니다. 결과는 같고 이름만 다릅니다.

Lambda 권한 부여자는 정책을 캐시한다

  1. 요청 도착

    TOKEN 유형은 헤더 하나, REQUEST 유형은 헤더·쿼리·경로를 꺼냅니다.

  2. 캐시 확인

    같은 키의 결과가 TTL(기본 300초, 최대 3600초) 안이면 함수를 건너뜁니다.

  3. 함수 호출

    함수가 principalId와 IAM 정책(Allow 또는 Deny)을 반환합니다.

  4. 정책 평가

    정책의 Resource가 이번 메서드 ARN과 맞지 않으면 403입니다.

  5. 백엔드 호출

    함수가 넣은 context 값을 통합에 넘깁니다.

권한 부여 함수는 호출자 식별자(principalId)와 12장 형식의 IAM 정책을 돌려줍니다. 정책의 Resource는 "어느 API, 스테이지, 메서드, 경로"를 ARN으로 적은 것입니다. 매 요청 함수를 부르면 느리므로 결과를 캐시합니다.

함정은 캐시와 정책 범위의 조합입니다. 첫 요청 GET /orders/1만 허용한 정책이 캐시되면, 같은 토큰의 POST /orders는 캐시된 정책 때문에 403입니다. 정책 Resource를 API 전체로 넓게 돌려주거나 캐시 키에 경로를 넣습니다.

스로틀링은 토큰 버킷 두 숫자로 정한다

권한을 통과한 요청도 너무 많으면 막아야 백엔드가 삽니다. API Gateway는 8장의 Token Bucket 알고리즘으로 처리율을 제한합니다. 버킷에 초당 일정 개수의 토큰이 채워지고, 요청 하나가 토큰 하나를 씁니다. 토큰이 없으면 429입니다.

그래서 설정 값도 둘입니다. rate는 초당 채워지는 토큰 수, 즉 꾸준히 허용하는 초당 요청이고, burst는 버킷 크기, 즉 잠깐 몰려도 한꺼번에 받아 주는 요청 수입니다.

계정 기본값은 리전당 rate 10,000 RPS, burst 5,000입니다(일부 신규 리전은 2,500 RPS). 이 한도는 계정의 모든 API가 나눠 씁니다.

주문 메서드에 rate 1,000, burst 500을 걸었다고 합시다. 푸시 직후 0.1초 사이에 3,000건이 몰리면, 쌓여 있던 토큰 500개와 그 0.1초 동안 채워진 100개, 약 600건만 통과하고 나머지는 429를 받습니다.

스로틀링은 계정, 스테이지, 클라이언트 순으로 겹친다

  1. 계정(리전)10,000 RPS, 버스트 5,000
  2. 스테이지·메서드경로별 상한
  3. 사용량 계획API 키별 rate, quota
  4. 통합 대상Lambda, HTTP 등

계정 버킷 아래에 스테이지·메서드별 버킷을 둬서 POST /orders만 따로 묶을 수 있습니다. REST API는 그 아래에 사용량 계획을 둡니다. 클라이언트에게 API 키를 발급하고 키별로 rate, burst, 일·월 할당량(quota)을 겁니다. 제휴 쇼핑몰마다 다른 요금제를 주는 식입니다. 요청은 모든 층의 버킷을 통과해야 합니다.

API 키는 인증 수단이 아닙니다

키는 클라이언트를 식별해 사용량 계획을 적용하는 용도이고 쉽게 유출됩니다. 인증은 앞의 권한 부여로 따로 겁니다.

캐시, 검증, 매핑은 REST API만의 무기다

스로틀이 요청 수를 줄인다면, REST API의 세 기능은 백엔드까지 가는 요청 자체를 줄입니다. HTTP API에는 셋 다 없고 헤더·경로를 바꾸는 파라미터 매핑만 있으므로, 이 기능이 필요하다는 것이 REST API를 고르는 주된 이유가 됩니다.

캐시: 스테이지에 0.5~237GB 크기의 캐시를 켜면 같은 요청의 응답을 TTL(기본 300초, 최대 3600초) 동안 백엔드 없이 돌려줍니다. 주문 API보다는 상품 목록처럼 모두가 같은 응답을 받는 GET에 맞습니다. 캐시 키에 필요한 쿼리 문자열과 헤더를 넣지 않으면 다른 사용자의 응답이 섞이니 주의하고, 캐시는 켜 둔 시간만큼 과금됩니다.

요청 검증: 요청 본문의 모양을 JSON 스키마로 적은 모델을 메서드에 붙이면, 필수 필드가 빠진 주문 요청은 400으로 끝나 함수에 닿지 않습니다.

매핑 템플릿: 앞에서 본 VTL 템플릿으로 요청과 응답을 변환합니다. 함수 없이 SQS나 DynamoDB를 부르는 AWS 서비스 통합은 이 변환이 있어야 가능합니다.

API가 기다리는 시간은 29초에서 시작한다

앞에서 미뤄 둔 통합 타임아웃입니다. 관문은 많은 연결을 동시에 붙잡고 있으므로, 응답이 늦는 백엔드를 끝없이 기다리면 관문 자원이 마릅니다. 그래서 상한이 있고, 넘으면 504입니다.

관문이 연결을 끊을 뿐 함수는 자기 타임아웃까지 실행됩니다. 클라이언트가 재시도하면 같은 주문이 두 번 처리될 수 있습니다.

결과는 클라이언트가 작업 ID로 상태를 조회(폴링)하거나, 뒤에서 볼 WebSocket으로 서버가 밀어 줍니다. 작업 ID가 있으므로 클라이언트 재시도도 중복으로 이어지지 않게 막을 수 있습니다.

CORS와 커스텀 도메인도 관문에서 처리한다

주문 화면이 app.example.com에서 뜨고 API가 다른 주소에 있으면 브라우저는 7장의 CORS 규칙을 적용합니다. 먼저 OPTIONS 사전 요청(preflight)으로 허락을 묻고, 서버가 허용 출처를 응답 헤더로 밝혀야 본 요청의 응답을 스크립트에 넘겨 줍니다.

HTTP API는 허용 출처·메서드·헤더를 설정하면 preflight에 API Gateway가 직접 답하고 본 응답에도 헤더를 붙입니다. REST API는 콘솔이 Mock 통합의 OPTIONS 메서드를 만들어 주지만, 프록시 통합이면 본 응답의 CORS 헤더는 함수가 넣어야 합니다(앞의 응답 JSON에 있던 Access-Control-Allow-Origin). 한쪽만 하면 preflight는 통과하고 본 요청이 막힙니다.

커스텀 도메인: 기본 주소는 길고 무작위라 api.example.com 같은 내 도메인을 붙입니다. 16장의 ACM 인증서를 연결하고, API 매핑으로 /v1은 이 API의 prod 스테이지로 하는 식으로 경로별 대상을 정한 뒤, 13장의 Route 53 Alias 레코드로 가리킵니다.

인증서 리전은 엔드포인트 유형을 따릅니다. 엣지 최적화는 CloudFront를 거치므로 us-east-1 인증서, 리전 엔드포인트는 API와 같은 리전의 인증서가 필요합니다.

WebSocket API는 연결마다 연결 ID를 줍니다. 연결 때 $connect 라우트가 실행되고, 이후 메시지는 라우트 선택 표현식(예: $request.body.action)이 고른 라우트로 갑니다.

배송 상태를 밀어 줄 때는 백엔드가 @connections API에 연결 ID로 POST합니다. 연결 ID는 DynamoDB에 두고 TTL로 지우며, 2시간 한도와 끊김 알림이 보장되지 않는 점 때문에 재연결 로직이 필수입니다.

관문을 지난 주문은 여러 단계를 거칩니다. 결제는 외부 결제 대행사(PG)를 부르고, 재고는 DB를 고치고, 배송은 물류 시스템을 부릅니다. 단계마다 함수를 나누고 앞 함수가 다음 함수를 직접 부르면 질문이 쏟아집니다. 배송에서 실패하면 어디까지 됐는지 누가 기억하나? 결제는 누가 되돌리나? 재시도는 어느 함수가 하나? 물류 응답을 몇 시간 기다려야 하면 15분 한도는 어떻게 넘나?

이 답들이 각 함수 코드에 조금씩 흩어지면 흐름 전체를 아무도 볼 수 없습니다. 게다가 앞 함수가 뒤 함수를 기다리는 동안 두 함수 모두 과금됩니다. 흐름 자체를 함수 밖으로 꺼내야 합니다.

Step Functions는 흐름을 상태 머신으로 꺼낸다

{
  "StartAt": "Validate",
  "States": {
    "Validate": {
      "Type": "Task",
      "Resource": "arn:...:validate",
      "Next": "Charge" },
    "Charge": {
      "Type": "Task",
      "Resource": "arn:...:charge",
      "Next": "Done" },
    "Done": { "Type": "Succeed" }
  }
}

Step Functions는 흐름을 상태 머신으로 정의합니다. 단계 하나하나가 상태(State)이고, 각 상태는 다음 상태를 Next로 가리킵니다. 정의는 ASL(Amazon States Language)이라는 JSON입니다.

왼쪽은 시작 상태 Validate에서 함수를 부르고 Charge로 넘어가 성공으로 끝납니다. 정의를 한 번 실행한 것을 실행이라 하며, 서비스가 실행마다 현재 상태와 입출력을 저장해 콘솔에서 단계별로 추적됩니다.

워크플로 유형은 실행 보장과 규모로 고른다

상태 머신을 만들 때 유형을 하나 고르며, 만든 뒤에는 바꿀 수 없습니다. 차이는 "실행을 얼마나 정확히 지켜 주는가"와 "얼마나 많이, 얼마나 길게 돌릴 수 있는가"의 맞교환입니다.

Standard는 상태가 바뀔 때마다 실행 기록을 내구성 있게 저장합니다. 그래서 같은 실행의 각 단계가 정확히 한 번 진행된다고 보장하고(Task가 부른 외부 시스템 안에서의 중복까지 막아 주지는 않습니다), 최대 1년까지 기다릴 수 있습니다. 기록 저장이 비싸므로 상태 전이 한 번마다 요금을 냅니다.

Express는 기록을 매번 저장하지 않고 메모리에서 빠르게 진행합니다. 초당 수천 건을 받을 수 있고 요금은 실행 수와 시간, 메모리로 매깁니다. 대신 최대 5분이고, 비동기로 시작한 실행은 장애 시 다시 돌 수 있어 최소 한 번입니다(8장의 전달 보장 용어 그대로입니다).

주문 결제처럼 두 번 실행되면 안 되고 길게 기다리는 업무 흐름은 Standard, 들어오는 클릭 이벤트를 짧게 변환하는 대량 처리는 Express입니다. Express라면 각 단계가 멱등해야 합니다.

Retry와 Catch를 상태 정의에 선언한다

"Charge": {
  "Type": "Task",
  "Resource": "arn:aws:lambda:...:charge",
  "Retry": [{
    "ErrorEquals": [
      "Lambda.TooManyRequestsException",
      "States.Timeout"],
    "IntervalSeconds": 2,
    "BackoffRate": 2,
    "MaxAttempts": 3,
    "JitterStrategy": "FULL" }],
  "Catch": [{
    "ErrorEquals": ["States.ALL"],
    "Next": "Refund" }],
  "Next": "ReserveStock"
}

앞의 Charge 상태에 실패 처리를 붙였습니다. Retry는 오류 이름별로 간격, 배수, 최대 횟수, 지터(8장의 재시도 시각 흩뜨리기)를 선언합니다. 스로틀(TooManyRequests)이나 시간 초과면 2초, 4초, 8초 간격으로 다시 시도합니다.

그래도 실패하면 Catch가 모든 오류(States.ALL)를 잡아 Refund 상태로 보냅니다. 재시도 로직이 함수 밖으로 빠지므로 결제 함수는 결제만 합니다.

Saga는 Catch마다 보상 단계를 잇는다

이제 앞에서 던진 "배송에서 실패하면 결제는 누가 되돌리나"에 답할 수 있습니다. 8장의 Saga는 큰 트랜잭션을 단계별 로컬 트랜잭션으로 나누고 실패하면 끝난 단계를 역순으로 되돌리는(보상) 패턴이었습니다. Step Functions에서는 각 Task의 Catch가 보상 경로의 입구가 됩니다. 실행 상태를 서비스가 저장하므로 진행 위치를 잃지 않고, 어디서 왜 실패했는지 기록에 남습니다. 보상까지 실패하면 사람이 볼 큐로 보냅니다.

4부

큐, 토픽, 버스로 서비스를 떼어 놓는다

3부의 Step Functions는 한 주문의 단계를 순서대로 지휘했습니다. 그런데 "주문이 완료됐다"는 사실은 결제, 재고, 알림, 분석처럼 서로 모르는 여러 서비스가 각자 알아야 합니다. 8장에서 메시지 큐가 보내는 쪽과 받는 쪽을 떼어 놓는 원리를 봤습니다. 이 부는 AWS가 그 원리를 어떤 서비스로 나눠 제공하는지 봅니다.

직접 부르면 한 서비스의 장애가 번진다

주문 함수가 주문을 저장한 뒤 결제, 재고, 알림 서비스를 차례로 HTTP로 부른다고 합시다. 알림 서비스가 3초씩 느려지면 주문 함수도 3초 늘어나고, 2부에서 본 대로 동시성이 그만큼 불어납니다. 알림이 아예 죽으면 주문 자체가 실패합니다. 주문과 상관없는 부가 기능 하나가 핵심 기능을 끌어내린 셈입니다.

새 서비스를 붙일 때도 문제입니다. 분석팀이 주문 데이터를 받고 싶어 하면 주문 함수를 고쳐 호출을 하나 더 넣어야 합니다. 주문 서비스가 모든 소비자를 알고 있어야 하는 구조입니다.

8장의 해법은 중간에 메시지 브로커를 두는 것이었습니다. 주문 서비스(생산자)는 "주문 완료"라는 메시지를 브로커에 남기고 바로 돌아섭니다. 결제나 알림(소비자)은 자기 속도로 가져가 처리합니다. 소비자가 잠시 죽어도 메시지는 브로커에 남아 있다가 회복 뒤 처리됩니다.

AWS는 이 브로커를 하나가 아니라 여럿으로 나눠 제공합니다. 메시지를 누가 몇 번, 어떤 방식으로 가져가느냐가 서비스마다 다르기 때문입니다. 다음 슬라이드에서 네 가지 모델을 정의합니다.

메시지를 나눠 주는 방식은 네 가지다

큐(점대점): 메시지 하나를 소비자 여럿 중 한 명만 가져가 처리하고 지웁니다. 일을 나눠 맡기는 모델로, 주문 메시지를 워커 10개가 나눠 처리하는 경우입니다. 8장의 RabbitMQ 큐가 이렇습니다. AWS에서는 SQS입니다.

발행-구독(Pub/Sub): 생산자가 토픽에 한 번 발행하면 구독한 소비자 모두가 복사본을 받습니다. 한 메시지를 여러 곳에 뿌리는 것을 팬아웃이라고 합니다. AWS에서는 SNS입니다.

이벤트 버스: 발행-구독과 비슷하지만, 누가 받을지를 구독자 목록이 아니라 메시지 내용을 보고 정합니다. "금액이 100만 원 넘는 주문은 심사 서비스로"처럼 규칙으로 라우팅합니다. AWS에서는 EventBridge입니다.

로그: 메시지를 처리해도 지우지 않고 순서대로 쌓아 두며, 소비자마다 자기가 어디까지 읽었는지 위치를 기억합니다. 8장의 Kafka가 이 모델이었고, 지나간 메시지를 다시 읽을 수 있다는 것이 큐와의 결정적 차이입니다. AWS에서는 Kinesis와 MSK이며 5부에서 봅니다.

AWS 메시징 서비스는 소비 방식으로 나뉜다

"소비 방식" 열의 차이가 재처리, 순서, 팬아웃 방식을 모두 가릅니다. 지우는 쪽(SQS)은 다시 읽을 수 없고, 밀어 넣는 쪽(SNS, EventBridge)은 소비자가 없으면 저장할 곳이 따로 필요하며, 쌓아 두는 쪽(Kinesis, MSK)은 다시 읽을 수 있습니다. 서비스별 내부 동작을 본 뒤 5부 끝에서 선택 기준으로 다시 비교합니다.

SQS는 소비자가 꺼내 가고 다 쓰면 지운다

  1. SendMessage

    생산자가 주문 메시지를 큐에 넣습니다.

  2. ReceiveMessage

    소비자가 큐에 메시지를 달라고 요청합니다(폴링).

  3. 처리

    주문을 DB에 저장합니다.

  4. DeleteMessage

    처리를 마친 소비자가 직접 지웁니다.

SQS(Simple Queue Service)는 밀어 주지 않습니다. 소비자가 계속 물어보는 폴링 방식입니다. Lambda가 SQS를 읽을 때도 2부의 ESM 폴러가 이 일을 대신할 뿐입니다.

기본 숏 폴링은 일부 서버만 보고 바로 답해, 메시지가 있어도 빈 응답이 올 수 있고 빈 응답에도 요금이 붙습니다. 롱 폴링은 대기 시간(최대 20초)을 주면 메시지가 올 때까지 응답을 미룹니다. 빈 응답이 줄어 요금과 지연이 함께 줄어듭니다.

중복 수신 같은 메시지 재전달다른 소비자가 받을 수도 있음 다시 보임

SQS는 메시지를 넘겨줄 때 지우지 않고 가시성 타임아웃 동안 다른 소비자에게 숨깁니다. 함께 주는 수신 핸들으로 처리를 마친 소비자가 지워야 사라지므로, 처리 중에 죽어도 메시지는 잃지 않습니다.

대가는 중복입니다. 처리 시간보다 짧게 잡으면 처리 중인 메시지가 다시 보여 두 번 처리됩니다. 긴 작업은 ChangeMessageVisibility로 중간에 숨김 시간을 연장합니다.

FIFO 큐는 순서와 중복 제거를 약속한다

SQS 큐는 만들 때 두 종류 중 하나를 고릅니다. Standard 큐는 메시지를 여러 서버에 나눠 저장해 처리량에 사실상 한도가 없습니다. 대신 가시성 타임아웃이 아니어도 드물게 같은 메시지가 두 번 전달될 수 있고(최소 한 번 전달), 넣은 순서대로 나온다는 보장이 없습니다.

주문 서비스에서 이것이 문제가 되는 경우가 있습니다. 같은 주문에 "생성", "결제", "취소" 메시지가 차례로 들어갔는데 "취소"가 "생성"보다 먼저 처리되면 상태가 엉킵니다.

FIFO(First-In-First-Out) 큐는 이 문제를 풉니다. 같은 그룹 안의 메시지는 넣은 순서대로만 나오고, 생산자가 같은 메시지를 5분 안에 다시 보내면 중복으로 보고 버립니다. 이름은 .fifo로 끝나야 합니다.

순서를 지키려면 앞 메시지가 끝나기 전에는 뒤 메시지를 내줄 수 없습니다. 그래서 FIFO는 순서를 얻는 대신 처리량을 내줍니다. 얼마나 내주는지가 다음 표이고, 그 손실을 줄이는 장치인 메시지 그룹은 그다음 슬라이드에서 봅니다.

FIFO는 순서를 얻고 처리량을 내준다

Standard 큐에 그룹 ID를 넣으면 공정 큐가 됩니다

입점 판매자 한 곳이 메시지를 쏟아내도 다른 판매자의 메시지가 뒤에 오래 밀리지 않도록 SQS가 그룹 사이를 조절합니다. 순서 보장은 없습니다.

메시지 그룹이 순서와 병렬성의 단위다

FIFO 큐는 MessageGroupId가 같은 메시지끼리만 순서를 지킵니다. A1이 처리 중이면 A2는 A1이 삭제될 때까지 누구에게도 전달되지 않습니다. 다른 그룹은 그동안 따로 진행됩니다.

그래서 병렬성은 그룹 수만큼입니다. 주문 ID를 그룹 ID로 쓰면 주문 하나의 이벤트는 순서대로, 서로 다른 주문은 동시에 처리됩니다. 중복 제거 ID(또는 본문 해시)가 5분 안에 같으면 두 번째 송신은 성공 응답만 받고 전달되지 않습니다.

DLQ는 독이 든 메시지를 격리한다

  1. 소스 큐메시지 수신
  2. 처리 실패 반복수신 횟수 증가
  3. 임계 초과maxReceiveCount
  4. DLQ로 이동알람, 원인 조사
  5. 재처리(redrive)고친 뒤 소스로 복귀

가시성 타임아웃 덕분에 실패한 메시지는 다시 보이지만, 형식이 깨진 주문처럼 몇 번을 받아도 실패하는 메시지(8장의 독이 든 메시지)는 끝없이 재전달되며 소비자를 갉아먹습니다. 소스 큐의 재처리 정책(redrive policy)에 DLQ와 maxReceiveCount를 지정하면, 수신 횟수가 그 값을 넘은 메시지가 DLQ라는 별도 큐로 옮겨집니다.

원인을 고친 뒤에는 콘솔이나 StartMessageMoveTask API로 DLQ 메시지를 원래 큐로 되돌립니다. FIFO 큐의 DLQ는 FIFO여야 하고, Standard에서는 만료가 원래 등록 시각 기준이므로 DLQ 보존 기간을 소스보다 길게 잡습니다.

가시성 타임아웃이 함수 타임아웃의 여섯 배인 이유는, 폴러가 메시지를 받았는데 함수가 스로틀되면 Lambda가 그 배치로 몇 번 더 호출을 시도하기 때문입니다. 그 사이에 메시지가 다시 보이면 안 됩니다. 같은 이유로 maxReceiveCount를 너무 작게 두면 스로틀만으로 멀쩡한 메시지가 DLQ로 갑니다. ESM의 최대 동시성과 프로비저닝 모드는 함께 쓸 수 없으며, 최대 동시성은 함수의 예약 동시성보다 작게 둡니다.

중복은 온다고 가정하고 처리에서 막는다

try {
  ddb.putItem(PutItemRequest.builder()
      .tableName("processed")
      .item(Map.of(
          "key", s(order.id()),
          "ttl", n(now() + 86_400)))
      .conditionExpression(
          "attribute_not_exists(key)")
      .build());
} catch (ConditionalCheckFailedException e) {
  return; // 이미 처리함: 건너뜀
}

}

가시성 만료, Standard 큐의 드문 중복, 생산자 재전송까지 중복은 막을 수 없으니 처리를 멱등하게 만듭니다(8장 멱등 컨슈머). 코드는 처리 전에 15장의 DynamoDB 조건부 쓰기로 "이 주문 처리함" 표시를 남깁니다. 이미 있으면 예외가 나서 건너뛰고, 처리에 실패하면 표시를 지워 재시도를 허용합니다. TTL로 하루 뒤 표시가 지워집니다.

키는 메시지 ID보다 주문 ID 같은 비즈니스 키가 낫습니다. 생산자가 같은 주문을 두 번 보내면 메시지 ID는 달라지기 때문입니다. Powertools for AWS Lambda(AWS의 Lambda용 공식 유틸리티 라이브러리)의 Idempotency 기능이 이 패턴을 구현합니다.

SNS는 한 번 발행하면 구독자 모두에게 민다

SQS는 메시지 하나를 한 소비자에게 줍니다. "주문 완료"를 결제, 재고, 알림이 모두 받으려면 발행-구독 모델인 SNS(Simple Notification Service)가 필요합니다. 구독은 토픽과 받는 곳(프로토콜과 주소)의 연결이며, 발행자는 구독자가 누구인지 모릅니다.

SNS는 메시지를 저장하지 않고 즉시 밀어 넣으며, 구독자 하나가 느려도 다른 구독자에는 영향이 없습니다. 메시지는 기본 256KiB, 토픽 설정으로 최대 1MiB입니다.

SNS 앞, SQS 뒤: 팬아웃의 기본 형태

SNS는 저장하지 않으므로, 구독자가 잠시 죽으면 받을 곳이 없습니다. 그래서 구독자마다 SQS 큐를 하나씩 붙여 버퍼로 씁니다. 재고 서비스가 잠시 죽어도 메시지는 재고 큐에 남고, 결제와 알림은 영향 없이 계속 갑니다.

각 큐에는 12장의 리소스 정책으로 이 토픽만 SendMessage하게 허용합니다. 원본 메시지 전달(raw message delivery)을 켜면 SNS의 메타데이터 봉투 없이 본문만 큐에 들어갑니다.

필터 정책으로 받을 메시지를 고른다

{
  "eventType": ["order_placed"],
  "amount": [{ "numeric": [">=", 100000] }],
  "region": [{ "anything-but": ["test"] }],
  "channel": [{ "prefix": "app-" }]
}
// FilterPolicyScope: MessageAttributes(기본)
//                  또는 MessageBody

팬아웃하면 구독자는 모든 메시지를 받습니다. 사은품 서비스가 10만 원 이상 주문만 원한다면 구독에 필터 정책을 붙입니다. SNS는 본문 밖에 붙이는 이름-값 쌍인 메시지 속성(기본) 또는 본문을 보고 맞는 것만 전달합니다.

왼쪽 정책은 앱 채널의 테스트가 아닌 10만 원 이상 주문만 받습니다. 키 사이는 AND, 배열 안 값은 OR입니다. 받아서 버리는 대신 SNS에서 거르므로 큐 적재와 함수 호출이 줄어듭니다. 토픽당 필터 정책은 200개까지입니다.

SNS 재시도는 대상 종류에 따라 다르다

SNS가 구독자에게 전달하지 못하면 다시 시도합니다. 얼마나 끈질긴지는 받는 쪽이 누구인가에 달려 있습니다. SQS나 Lambda 같은 AWS 관리형 대상은 일시적으로만 실패한다고 보고 23일에 걸쳐 100,015번 시도합니다.

HTTP/S 웹훅은 외부 서버라 오래 두드리면 상대에게 부담이므로 기본 정책이 훨씬 짧습니다. 전달 정책으로 바꿀 수 있지만 총 재시도 시간은 3,600초를 넘지 못합니다.

그래도 실패하면 메시지는 버려집니다. SNS는 저장소가 없기 때문입니다. 그래서 구독마다 SQS 큐를 구독 DLQ로 붙여, 전달에 실패한 메시지를 남깁니다. SQS의 DLQ가 "처리 실패"를 모았다면, 이것은 "전달 실패"를 모읍니다.

순서가 필요하면 FIFO 토픽을 씁니다. SQS FIFO 큐만 구독할 수 있고, 메시지 그룹 순서와 중복 제거를 큐까지 이어 줍니다. 그룹당 초당 300건이 상한이며, 아카이브 정책으로 메시지를 보관했다가 구독자에게 다시 재생할 수도 있습니다.

EventBridge는 내용을 보고 라우팅한다

{
  "version": "0",
  "id": "6a7e8feb-...",
  "detail-type": "OrderPlaced",
  "source": "com.shop.orders",
  "account": "111122223333",
  "time": "2026-11-17T09:00:00Z",
  "region": "ap-northeast-2",
  "resources": [],
  "detail": {
    "orderId": 42,
    "amount": 125000,
    "tier": "gold"
  }
}

SNS의 필터 정책이 있어도 기본은 "구독자 목록"입니다. EventBridge는 처음부터 내용으로 보냅니다. 이벤트를 받아 규칙에 따라 나눠 주는 라우터가 이벤트 버스입니다.

모든 이벤트는 같은 봉투를 씁니다. source(누가)와 detail-type(무슨 일)이 종류를, detail이 내용을 담습니다. AWS 서비스 이벤트가 들어오는 기본 버스, 내 앱용 사용자 지정 버스, Zendesk 같은 SaaS 이벤트를 받는 파트너 버스가 있습니다.

규칙은 패턴으로 고르고 대상에 넘긴다

{
  "source": ["com.shop.orders"],
  "detail-type": ["OrderPlaced"],
  "detail": {
    "amount": [{ "numeric": [">", 100000] }],
    "tier": ["gold", "platinum"]
  }
}

버스에는 규칙을 겁니다. 규칙은 이벤트 패턴과 대상 목록입니다. 왼쪽 패턴은 앞 슬라이드의 이벤트처럼 10만 원 넘는 골드·플래티넘 등급 주문만 고릅니다. 문법은 SNS 필터 정책과 거의 같습니다.

맞은 이벤트는 대상에 넘어갑니다. 규칙당 최대 5개로, Lambda, SQS, SNS, Step Functions, 다른 버스, 그리고 외부 HTTP를 부르는 API 대상 등입니다. 입력 변환기는 이벤트에서 필요한 값만 꺼내 대상이 원하는 모양으로 바꿉니다. 버스당 규칙은 기본 300개입니다.

재시도, DLQ, 아카이브로 이벤트를 지킨다

대상 전달이 실패하면 EventBridge는 기본 24시간 동안 최대 185번, 지수 백오프와 지터로 다시 시도합니다. 그래도 안 되면 SNS처럼 이벤트를 버립니다. 그래서 대상마다 SQS DLQ를 붙이고, 오래된 이벤트가 의미 없는 대상이면 재시도 횟수와 최대 이벤트 수명을 줄입니다.

버스는 이벤트를 저장하지 않지만 따로 보관할 수 있습니다. 아카이브는 버스에 들어온 이벤트를 패턴으로 골라 보관하고, 재생은 지정한 시간 구간의 이벤트를 다시 버스에 흘립니다. 사은품 서비스에 버그가 있어 어제 오후 주문을 놓쳤다면, 버그를 고친 뒤 그 구간을 재생해 다시 처리합니다.

이벤트를 받는 팀은 봉투의 detail에 어떤 필드가 오는지 알아야 합니다. 스키마 레지스트리는 버스에 흐르는 이벤트 구조를 자동으로 발견해 저장하고, 그 구조에 맞는 Java, Python, TypeScript 클래스(코드 바인딩)를 내려받게 해 줍니다.

새 버스는 보존과 순서를 더했다

지금까지 본 규칙과 대상 방식은 이제 Classic으로 불립니다. 새 Custom Event Bus는 이벤트를 버스에 보존하고, 소비하는 쪽이 자기 구독자(필터 + 대상 1개)를 만듭니다. 새 분석 서비스가 시작 위치를 30일 전으로 잡아 지난 주문부터 읽을 수 있으니, 5부에서 볼 로그 모델이 버스 안으로 들어온 셈입니다.

교차 계정 이벤트는 양쪽 허락이 필요하다

회사가 커지면 주문과 분석이 다른 AWS 계정에 삽니다. 12장의 교차 계정 원칙 그대로, 보내는 쪽 권한과 받는 쪽 허락이 모두 필요합니다. Classic 버스라면 보내는 쪽 규칙의 대상에 상대 버스 ARN과 events:PutEvents 권한이 있는 역할을 주고, 받는 쪽은 버스 리소스 정책으로 그 계정을 허용합니다.

조직 전체에 열 때는 12장의 aws:PrincipalOrgID 조건을 씁니다. Custom Event Bus는 RAM으로 공유받은 계정이 자기 구독자를 직접 붙입니다.

Pipes는 점대점 연결, Scheduler는 시간 예약

  1. 소스SQS, Kinesis, DDB Streams
  2. 필터이벤트 패턴으로 거름
  3. 보강Lambda, API로 데이터 추가
  4. 대상Step Functions, 버스 등

EventBridge에는 버스 말고도 두 도구가 있습니다. EventBridge Pipes는 소스 하나와 대상 하나를 잇는 관리형 파이프입니다. 2부의 ESM처럼 소스를 폴링하고, 패턴으로 거르고, 함수나 API로 정보를 덧붙여(보강) 대상에 넘깁니다. "주문 큐를 읽어 고객 등급을 붙인 뒤 Step Functions를 시작"하던 Lambda 글루 코드가 설정으로 바뀝니다.

EventBridge Scheduler는 정해진 시각에 AWS API를 부릅니다. 반복 일정은 cron 식(분·시·일 필드로 시각 지정)이나 rate 식(rate(5 minutes))으로, 한 번짜리는 시각으로 적습니다. 시간대, 재시도와 DLQ를 지원하고 일정을 수백만 개 만들 수 있어 주문마다 "24시간 뒤 리뷰 요청" 같은 개별 예약에 맞습니다.

5부

로그를 쌓아 두고 여러 번 읽는다

4부의 큐와 토픽은 메시지를 처리하면 잊습니다. 그런데 분석팀이 지난 일주일 주문을 새 방식으로 다시 계산하고 싶거나, 초당 수만 건의 클릭을 사용자별 순서대로 처리해야 한다면 어떻게 할까요? 이 부는 지우지 않는 로그(Kinesis, MSK)와 적재 전용 Firehose를 보고, 메시징 서비스 전체를 고르는 기준으로 마무리합니다.

큐로는 지나간 메시지를 다시 읽을 수 없다

SQS에서 메시지는 처리되는 순간 지워집니다. 주문 처리 워커에게는 그것이 맞습니다. 하지만 같은 주문 이벤트를 쓰는 분석 작업을 생각해 봅시다. 매출 집계 로직에 버그가 있었다면 지난 사흘치 이벤트를 고친 코드로 다시 돌려야 합니다. 큐에는 이미 남은 것이 없습니다.

소비자가 늘 때도 문제입니다. 추천 팀이 같은 주문 이벤트를 받고 싶으면 4부 방식으로는 SNS 구독과 큐를 하나 더 만들고, 그 시점부터의 이벤트만 받습니다. 과거 이벤트로 모델을 학습시킬 방법이 없습니다.

8장의 Kafka가 이 문제를 푸는 방식이 로그였습니다. 메시지를 끝에 덧붙이기만 하고 보존 기간 동안 지우지 않으며, 소비자마다 "어디까지 읽었나"라는 위치만 따로 기억합니다. 새 소비자는 처음부터, 버그를 고친 소비자는 사흘 전 위치부터 다시 읽으면 됩니다.

로그는 순서도 지킵니다. 다만 하나의 줄로는 처리량에 한계가 있으니 여러 줄로 나누고, 순서는 줄 하나 안에서만 지킵니다. Kafka에서는 이 줄을 파티션이라 불렀고, AWS의 관리형 로그인 Kinesis에서는 샤드라고 부릅니다.

Kinesis는 파티션 키로 샤드를 고른다

Kinesis Data Streams의 스트림은 샤드의 묶음입니다. 생산자는 레코드마다 파티션 키를 붙이고, Kinesis는 키를 MD5로 해시해 그 값 범위를 맡은 샤드에 넣습니다. 샤드 안에서는 레코드마다 시퀀스 번호가 붙고 그 순서가 지켜집니다.

사용자 ID를 키로 쓰면 한 사용자의 클릭은 늘 같은 샤드로 가서 순서가 지켜집니다. 키가 한쪽에 몰리면 그 샤드만 뜨거워집니다(핫 샤드). Kafka의 파티션(8장)과 같은 구조입니다.

KCL은 샤드를 임대하고 체크포인트를 남긴다

    부모 샤드를 다 읽은 뒤 자식 샤드로 넘어가 순서를 지킵니다.

처리했지만 체크포인트 전에 죽은 레코드는 다시 읽히므로 Kinesis 소비도 최소 한 번입니다. Lambda ESM은 이 일을 대신하며 처리 지연은 2부의 IteratorAge로 봅니다.

Firehose는 버퍼에 모아 목적지에 쌓는다

  1. 입력Direct PUT, Kinesis, MSK
  2. 버퍼크기나 시간 중 먼저
  3. 변환Lambda, Parquet 변환
  4. 목적지S3, Redshift, OpenSearch

주문 이벤트를 S3에 쌓아 나중에 분석하는 일이라면 소비자 코드를 직접 쓸 필요가 없습니다. Amazon Data Firehose(옛 Kinesis Data Firehose)는 받은 데이터를 목적지에 쌓기만 하는 적재 전용 서비스입니다. 샤드도 용량 설정도 없고, 생산자가 바로 넣거나(Direct PUT) Kinesis·MSK를 입력으로 씁니다.

버퍼가 정한 크기나 시간에 먼저 닿으면 묶어서 쓰므로 실시간이 아니라 준실시간이고, 지나간 데이터를 다시 읽을 수 없습니다. JSON을 15장에서 본 Parquet 같은 열 기반 형식으로 바꾸고, S3 경로를 날짜·국가 같은 값으로 나누는 동적 파티셔닝을 하면 S3를 SQL로 조회하는 Athena(15장)가 읽는 양이 줄어 비용이 내려갑니다. 목적지로는 데이터 웨어하우스 Redshift, 검색 엔진 OpenSearch, Splunk, HTTP 엔드포인트, S3 위 테이블 형식인 Apache Iceberg 테이블도 됩니다.

이제 4~5부의 서비스를 모두 봤으니 나란히 놓고 고를 수 있습니다. 먼저 동작 방식의 차이입니다.

주문 서비스에 모아 보면 이런 모양이다

관문(3부)이 주문을 받아 큐(4부)에 넣고 202를 돌려줍니다. 워커 함수(1~2부)가 큐를 꺼내 Saga(3부)를 시작하고 RDS Proxy를 거쳐 저장합니다. 완료 이벤트는 EventBridge가 내용에 따라 나누고, 분석용 사본은 Kinesis와 Firehose(5부)가 S3에 쌓습니다. 6부는 이 그림이 어디서 무너지는지 봅니다.

6부

자동 확장과 자동 재시도가 장애를 키울 때

1~5부의 부품은 모두 스스로 늘어나고 스스로 다시 시도합니다. 하나씩은 장점이지만, 잘못 엮이면 작은 문제를 큰 장애로 증폭합니다. 5부 끝의 주문 서비스 그림 위에서 실제로 자주 터지는 사례와 막는 설정, 비용 계산, 먼저 볼 지표를 다룹니다.

원리 실무 장애 사례, 방어 설정, 비용 계산, 경보 지표를 다룹니다.

급증한 주문이 Lambda를 거쳐 DB를 죽인다

마케팅 푸시 직후 주문 큐에 50만 건이 쌓입니다. ESM이 적체를 보고 폴러를 늘리면서 동시성이 1,000까지 오르고(2부), 환경마다 풀을 연 탓에 최대 연결 수 1,000인 RDS에 연결 시도가 2,000개 몰립니다. 연결이 거부되어 함수가 실패하면 메시지가 다시 보여 재시도가 쌓이고(4부), 같은 DB를 쓰던 주문 조회 API까지 함께 멈춥니다.

상한, 큐 버퍼, 프록시로 막는다

  1. 큐로 받기

    동기 호출 대신 SQS에 넣어 급증을 큐에 쌓습니다.

  2. ESM 최대 동시성

    이 큐를 읽는 동시성을 DB가 버티는 값으로 묶습니다.

  3. 예약 동시성

    함수 전체 상한을 같은 값 이상으로 걸어 다른 경로도 막습니다.

  4. RDS Proxy

    남은 연결을 프록시가 다중화해 DB 연결 수를 고정합니다.

  5. 적체 감시

    가장 오래된 메시지 나이로 처리 지연을 봅니다.

핵심은 확장의 상한을 DB 쪽에서 거꾸로 계산하는 것입니다. DB가 이 작업에 내줄 연결이 50, 환경당 연결 1개면 최대 동시성은 50입니다. 처리 0.5초면 초당 100건이라 50만 건은 약 83분에 소화됩니다. 큐가 급증을 흡수하는 동안 DB는 늘 견딜 만큼만 받습니다.

83분이 너무 길면 상한을 올릴 것이 아니라 배치 쓰기나 쿼리 튜닝으로 건당 처리 시간을 줄입니다.

재시도는 계층마다 곱해진다

  1. 앱 클라이언트3회 시도
  2. Lambda 비동기최대 3회 실행
  3. AWS SDK기본 3회 시도
  4. 하류 서비스최대 27배 요청

앞 사례의 고리를 일반화하면 이렇습니다. 앱이 3번, Lambda 비동기 호출이 3번(처음 + 재시도 2번), 함수 안의 AWS SDK가 3번 시도하면, 각 계층은 "세 번까지만"이어도 하류는 요청 하나에 최대 27번 맞습니다. 막 회복하려던 서비스가 몰려든 재시도에 다시 쓰러지는 것이 재시도 폭풍입니다.

막는 방법은 8장의 원칙 그대로입니다. 재시도는 한 계층에서만 하고, 지수 백오프와 지터를 넣고, 전체 시간 예산(데드라인)을 넘기면 포기하며, 하류가 계속 실패하면 서킷 브레이커로 끊습니다. 비동기 함수는 MaximumRetryAttempts를 0~1로 줄이고 실패 Destination으로 넘기는 편이 안전합니다.

포이즌 메시지는 소스마다 막는 곳이 다르다

재시도가 소용없는 메시지, 즉 8장의 독이 든(포이즌) 메시지는 소스마다 증상이 다릅니다. 지금까지 각 부에서 따로 본 방어 장치를 한 표에 모읍니다.

소스증상방어
SQS Standard계속 재전달, 동시성 소모DLQ와 부분 배치 응답
SQS FIFO같은 그룹 전체가 멈춤DLQ로 빼야 그룹이 풀림
Kinesis, DDB Streams샤드가 막혀 지연 상승Bisect, 재시도 상한, 실패 대상
Lambda 비동기재시도 후 조용히 버려짐실패 Destination
SNS, EventBridge재시도 소진 후 버려짐구독·대상별 DLQ

공통 규칙은 둘입니다. DLQ에 메시지가 1건이라도 들어오면 경보를 울리고, 원인을 고친 뒤 재처리(redrive)합니다. DLQ를 만들고 아무도 보지 않으면 데이터 유실을 미뤄 둔 것에 불과합니다.

중복과 순서는 경계마다 다시 깨진다

$ aws dynamodb update-item \
  --table-name orders \
  --key '{"id":{"S":"42"}}' \
  --update-expression \
    "SET st = :s, ver = :v" \
  --condition-expression \
    "attribute_not_exists(ver) OR ver < :v" \
  --expression-attribute-values \
    '{":s":{"S":"SHIPPED"},":v":{"N":"7"}}'

중복은 SQS 가시성 만료, Lambda 비동기 큐, SNS와 EventBridge 재시도, Kinesis 체크포인트 이전 재처리, 생산자의 송신 재시도에서 모두 생깁니다. 그래서 "정확히 한 번"은 전달이 아니라 처리 결과로 만듭니다.

순서도 FIFO나 샤드 안에서만 지켜지고, 병렬 처리나 실패분 재처리가 끼면 뒤집힙니다. 왼쪽 명령은 주문 이벤트에 버전 번호를 넣고, 저장된 버전보다 새로울 때만 쓰는 조건부 쓰기입니다. 늦게 도착한 옛 이벤트(버전 5)는 조건에 걸려 버려집니다.

자주 터지는 설정 실수 다섯 가지

사고가 아니라 설정 하나에서 시작하는 장애도 많습니다. 모두 앞에서 본 원리에서 나옵니다.

  • 큐 가시성 타임아웃을 함수 타임아웃보다 짧게 두면 ESM 생성이 거부되고, 직접 만든 소비자라면 처리 중인 메시지가 중복 전달됩니다.
  • S3 업로드 이벤트로 도는 함수가 같은 버킷에 결과를 쓰면 그 쓰기가 다시 이벤트가 되어 무한 루프가 됩니다. 입력과 출력의 버킷이나 접두사를 나눕니다.
  • 함수 타임아웃을 900초로 두면 하류가 멈췄을 때 환경이 15분씩 묶여 동시성이 금방 바닥납니다. 평소 p99의 몇 배로 짧게 둡니다.
  • 예약 동시성 0은 긴급 차단 스위치로 유용하지만, 실수로 남겨 두면 모든 호출이 스로틀되는 장애입니다.
  • 비밀 값을 환경 변수에 평문으로 넣지 않습니다. 16장의 Secrets Manager에서 Init 때 읽어 핸들러 밖에 캐시합니다.

Lambda 요금은 요청 수와 GB-초다

요금은 요청 100만 건당 $0.20과 GB-초당 $0.0000166667입니다(us-east-1, x86). GB-초는 메모리(GB) × 실행 시간(초)으로, 1부에서 메모리를 올리면 요금이 바뀌던 이유입니다. 실행 시간은 1ms 단위로 올림하고, Arm은 GB-초 단가가 20% 낮습니다.

오른쪽 계산을 보면 앞단 API Gateway가 함수보다 비싼 경우가 흔합니다. 로그, NAT, 프로비저닝된 동시성 요금도 따로 붙습니다.

계산에 없는 것도 봐야 합니다. ALB 요금, 콜드 스타트, 서버를 운영하는 사람의 시간입니다. 18장은 이 손익분기를 출발점으로 서비스의 부분마다 컴퓨팅을 고릅니다.

정리

  • Lambda 실행 환경 하나는 요청 하나를 처리합니다. 그래서 동시성은 요청률 × 실행 시간이고, 콜드 스타트와 DB 연결 폭증이 모두 여기서 나옵니다.
  • 호출 방식이 실패의 행방을 정합니다. 동기는 호출자, 비동기는 내부 큐와 Destinations, 이벤트 소스 매핑은 소스의 DLQ와 실패 대상입니다.
  • API Gateway와 Step Functions는 함수 밖으로 일을 뺍니다. 인증·스로틀·검증은 관문에서, 재시도·대기·보상은 상태 머신에서 합니다.
  • 큐는 지우고 로그는 남깁니다. SQS·SNS·EventBridge는 분산·팬아웃·라우팅과 완충에, Kinesis·MSK는 순서 있는 재읽기에 씁니다.
  • 중복은 반드시 오고, 재시도는 곱해집니다. 멱등 처리, DB에서 거꾸로 계산한 동시성 상한, DLQ 경보를 처음부터 함께 설계합니다.

스스로 점검 (1)

  1. 초당 300건, 평균 400ms인 함수가 DB 지연으로 2초가 되면 동시성은 어떻게 되나요?

    300 × 0.4 = 120에서 300 × 2 = 600으로 다섯 배가 됩니다. 트래픽이 그대로여도 지연만으로 동시성과 DB 연결이 폭증합니다.

  2. SnapStart를 켠 Java 함수가 Init에서 UUID 생성기 시드를 만들면 어떤 문제가 생기나요?

    스냅샷 하나에서 여러 환경이 복원되므로 모든 환경이 같은 시드를 가집니다. 고유 값은 afterRestore 훅이나 핸들러 안에서 만듭니다.

  3. S3 이벤트로 도는 함수가 계속 실패합니다. 실패 이벤트는 어디로 가고, 어떻게 붙잡나요?

    S3는 비동기 호출이라 Lambda 내부 큐에서 재시도한 뒤 버려집니다. 실패 Destination이나 함수 DLQ를 설정해야 남습니다.

  4. Lambda 권한 부여자에 캐시를 켰더니 일부 경로만 403이 납니다. 왜일까요?

    첫 요청의 메서드만 허용한 정책이 토큰 기준으로 캐시되어 다른 경로에도 쓰이기 때문입니다. 정책 Resource를 넓게 반환하거나 캐시 키에 경로를 넣습니다.

스스로 점검 (2)

  1. Lambda 함수 타임아웃이 60초입니다. 소스 SQS 큐의 가시성 타임아웃은 얼마로 두나요?

    함수 타임아웃의 6배인 360초에 배치 창을 더한 값 이상입니다. 스로틀 뒤 재시도할 시간을 남겨 중복을 막습니다.

  2. FIFO 큐에서 메시지 그룹 ID를 전부 같은 값으로 넣으면 처리량은 어떻게 되나요?

    그룹 안에서는 한 번에 한 메시지만 처리되므로 소비자를 늘려도 병렬성이 1입니다. 순서가 필요한 단위(계좌, 주문)로 그룹을 나눠야 합니다.

  3. SNS에서 SQS로 팬아웃할 때 구독자마다 큐를 따로 두는 이유는 무엇인가요?

    SNS는 메시지를 저장하지 않으므로 구독자가 잠시 죽으면 버퍼가 필요하고, 큐가 따로여야 구독자마다 자기 속도로 처리하고 장애가 서로 번지지 않습니다.

스스로 점검 (3)

  1. Kinesis 소비자의 IteratorAge가 계속 오르기만 합니다. 무엇부터 의심하나요?

    실패한 배치가 같은 샤드에서 무한 재시도 중인지 봅니다. Bisect, 재시도 상한, 실패 대상을 설정하고 처리량이 모자라면 ParallelizationFactor나 샤드 수를 늘립니다.

  2. Step Functions에서 결제 단계가 들어가는 흐름에 Express를 쓰면 왜 위험한가요?

    비동기 Express는 최소 한 번 실행이라 같은 실행이 두 번 돌 수 있습니다. 결제처럼 멱등하지 않은 단계는 정확히 한 번인 Standard로 둡니다.

  3. 평균 초당 2건, 낮에만 몰리는 사내 API를 Lambda와 Fargate 중 무엇으로 두나요?

    손익분기(약 15건/초)보다 훨씬 낮고 밤에 0이 되므로 Lambda가 쌉니다. 콜드 스타트가 문제면 SnapStart나 작은 프로비저닝된 동시성으로 보완합니다.

스스로 점검 (4)

  1. Lambda를 VPC에 붙였더니 RDS는 되는데 결제사 API 호출만 타임아웃이 납니다. 왜일까요?

    VPC에 붙은 함수의 Hyperplane ENI에는 공인 IP가 없어 인터넷으로 바로 나가지 못합니다. Private Subnet에서 NAT Gateway로 가는 경로를 만들어야 합니다.

  2. API Gateway가 504를 냈는데 같은 주문이 두 번 저장됐습니다. 어떻게 된 일일까요?

    통합 타임아웃으로 관문이 연결을 끊어도 함수는 계속 실행되어 첫 주문을 저장했고, 클라이언트 재시도가 두 번째를 만들었습니다. 접수 후 비동기로 넘기고 작업 ID나 멱등 키로 중복을 막습니다.

  3. 분석팀이 지난주 주문 이벤트를 고친 로직으로 다시 계산하고 싶어 합니다. SQS와 Kinesis 중 무엇이 이것을 가능하게 하나요?

    SQS는 처리한 메시지를 지우므로 불가능합니다. Kinesis는 보존 기간 동안 레코드를 남겨 두므로 그 시점 위치부터 다시 읽을 수 있습니다.
