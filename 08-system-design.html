서비스 하나가 사용자 수천에서 수백만으로 자라는 과정을 따라가며, 병목이 생길 때마다 등장하는 캐시, 큐, 분산 락, 장애 격리 패턴을 원리부터 짚습니다.

아래층부터 위로 쌓아 올라가는 순서입니다. 지금은 8단계입니다.

1부

서비스가 자라면 무엇부터 터지는가

7장에서 API를 설계하고 지켰다면, 이제 그 API를 찾는 사용자가 백 배로 늘었을 때를 생각합니다. 서버를 늘리는 두 방향과, 늘리기 위해 먼저 갖춰야 할 조건을 봅니다.

처음에는 서버 한 대로 충분하다

막 시작한 서비스는 애플리케이션과 DB를 한 서버에 올려도 잘 돌아갑니다. 단순하고, 배포도 쉽고, 비용도 적습니다.

사용자가 늘면 CPU와 메모리가 먼저 차고, 이어서 DB 커넥션과 디스크 I/O가 밀립니다. 더 근본적인 문제는 이 서버 하나가 멈추면 서비스 전체가 멈춘다는 점입니다. 이런 지점을 단일 장애점(SPOF)이라고 부릅니다.

더 큰 서버냐, 더 많은 서버냐

항목스케일 업(Scale-Up)스케일 아웃(Scale-Out)
방법CPU, 메모리를 더 큰 것으로 교체같은 서버를 여러 대로 늘림
코드 변경거의 없음무상태 설계가 전제
한계하드웨어 상한, 비용 급증이론상 수평으로 계속 확장
장애 범위여전히 한 대가 SPOF한 대가 죽어도 나머지가 처리
새 과제교체 중 중단분산, 세션, 데이터 일관성

실무에서는 둘 중 하나만 고르지 않습니다. 애플리케이션 서버는 스케일 아웃하고, 수평 확장이 어려운 DB는 먼저 스케일 업으로 버티는 조합이 흔합니다.

스케일 아웃의 전제는 무상태 서버다

서버를 세 대로 늘리고 로드 밸런서가 요청을 나눠 준다고 해 봅시다. 사용자가 1번 서버에서 로그인했는데 다음 요청이 2번 서버로 가면, 2번 서버 메모리에는 그 사용자의 세션이 없습니다. 로그인이 풀린 것처럼 보입니다. 2장에서 미뤄 둔 바로 그 문제입니다.

문제의 뿌리는 서버가 요청과 요청 사이에 기억을 들고 있다는 점입니다. 어떤 요청이 어느 서버로 가도 같은 결과를 내려면 서버 안에 사용자별 상태가 없어야 합니다. 이런 서버를 무상태 서버라고 합니다.

상태를 없앨 수는 없으니, 상태를 서버 밖의 공용 저장소로 옮깁니다. 세션, 업로드 파일, 캐시가 모두 이 대상입니다.

세션을 어디에 둘지 세 가지 선택지

대부분의 서비스는 세 번째를 고릅니다. Spring이라면 Spring Session이 세션 저장 위치만 Redis로 바꿔 주므로 코드는 거의 그대로입니다. 쿠키와 세션 ID의 동작은 2장, 토큰 방식과의 비교는 7장에서 다뤘습니다.

라운드 로빈은 요청 하나하나의 비용이 같다고 가정합니다. 어떤 요청은 10ms, 어떤 요청은 3초가 걸린다면 운 나쁜 서버에 느린 요청이 쌓이므로 최소 연결 방식이 더 고르게 나눕니다. L4와 L7의 차이는 2장에서 다뤘습니다.

헬스 체크가 죽은 서버를 빼 준다

로드 밸런서는 주기적으로 각 서버의 헬스 체크 경로(예: /health)를 호출해 봅니다. 정해진 횟수만큼 연속으로 실패하면 그 서버를 분배 대상에서 빼고, 다시 연속으로 성공하면 넣습니다.

한 번의 실패로 바로 빼지 않는 이유는 일시적인 지연 때문에 멀쩡한 서버가 들락날락하는 것을 막기 위해서입니다.

헬스 체크에 DB 확인을 넣을 때는 신중하게

DB가 잠깐 느려지면 모든 서버가 동시에 실패로 판정되어 전부 빠질 수 있습니다. "프로세스가 요청을 받을 수 있는가"와 "의존 대상이 건강한가"를 구분해야 합니다.

같은 생각이 9장에서 다시 나옵니다

Kubernetes의 liveness와 readiness probe가 바로 이 구분입니다.

이 장에서 자라날 서비스의 전체 모습

2부

DB를 덜 부르고, 한 번에 하나씩 처리하기

앱 서버를 늘려도 DB는 하나입니다. 읽기는 캐시로 덜어 내고, 몰리는 쓰기는 원자 연산과 락, 큐로 질서를 세웁니다.

기초 원리 여기부터는 캐시, 락, 큐가 내부에서 어떻게 동작하는지 다룹니다.

캐시는 읽기가 몰리는 곳에서 효과가 크다

대부분의 서비스는 쓰기보다 읽기가 훨씬 많고, 읽기도 인기 있는 일부 데이터에 몰립니다. 그 일부를 메모리에 두면 DB 왕복 수 ms를 1ms 미만으로 줄이고 DB 부하도 덜어 냅니다.

적중률이 90%면 DB로 가는 읽기가 10분의 1로 줄어듭니다. 적중률 1~2%의 차이가 DB 부하에서는 큰 차이가 됩니다.

항목로컬 캐시글로벌 캐시
위치앱 서버 메모리Redis 등 별도 서버
속도네트워크 없음네트워크 1회 왕복
서버 간 공유서버마다 값이 다를 수 있음모든 서버가 같은 값
어울리는 데이터설정, 코드표세션, 자주 바뀌는 데이터

Cache-Aside: 없으면 DB에서 읽고 채운다

앱 서버캐시 / DB

애플리케이션이 캐시와 DB를 직접 오가는 방식으로, Cache-Aside라고 합니다. 가장 흔한 기본값입니다.

캐시가 죽어도 DB로 읽으면 되므로 장애에 강합니다. 대신 처음 요청은 늘 miss이고, DB를 바꾼 뒤 캐시를 어떻게 맞출지는 직접 정해야 합니다.

쓰기 전략은 속도와 유실 위험을 맞바꾼다

전략쓰기 흐름장점위험
Read-Through캐시가 miss 시 DB를 대신 읽음앱 코드가 단순캐시 계층이 DB 접근을 알아야 함
Write-Through캐시와 DB에 동시에 기록캐시가 늘 최신쓰기마다 두 곳, 지연 증가
Write-Back캐시에만 쓰고 나중에 DB로쓰기가 매우 빠름캐시 장애 시 데이터 유실
Write-AroundDB에만 쓰고 캐시는 비움안 읽히는 데이터는 캐시 안 함쓴 직후 읽기는 miss

Write-Back(Write-Behind)은 조회수, 좋아요 수처럼 조금 잃어도 되는 카운터를 모았다가 한 번에 반영할 때 씁니다. 주문, 결제처럼 잃으면 안 되는 데이터에는 쓰지 않습니다.

TTL은 안전망이고, 무효화는 삭제로 한다

캐시는 원본의 복사본이라 언젠가 어긋납니다. TTL을 걸어 두면 아무리 잘못돼도 그 시간이 지나면 저절로 원본과 맞춰집니다. 그래서 TTL은 모든 캐시 키에 거는 마지막 안전망입니다.

데이터가 바뀌면 캐시를 새 값으로 덮어쓰기보다 지우는 편이 안전합니다. 두 요청이 동시에 갱신하면 덮어쓰기 순서가 DB 반영 순서와 뒤바뀔 수 있지만, 삭제는 몇 번을 해도 결과가 같고 다음 읽기가 DB에서 최신 값을 채웁니다.

TTL을 짧게 잡으면 정합성이 좋아지는 대신 적중률이 떨어집니다. 데이터마다 "몇 초 낡은 값까지 허용되는가"를 먼저 정하고 그 값을 TTL로 씁니다.

삭제해도 낡은 값이 다시 들어올 수 있다

  1. 요청 A 읽기

    캐시 miss라 DB에서 옛 값 v1을 읽습니다.

  2. 요청 B 쓰기

    DB를 v2로 갱신하고 캐시 키를 삭제합니다.

  3. 요청 A 채우기

    늦게 도착한 A가 v1을 캐시에 SET합니다.

  4. 결과

    DB는 v2, 캐시는 v1. TTL이 끝날 때까지 낡은 값이 남습니다.

Cache-Aside에서도 읽기와 쓰기가 엇갈리면 불일치가 생깁니다. 드물지만 트래픽이 많으면 실제로 일어납니다.

대응은 TTL을 짧게 두는 것이 기본이고, 쓰기 후 잠시 뒤 한 번 더 지우는 지연 이중 삭제나 DB 변경 로그(CDC)로 캐시를 지우는 방법이 있습니다. 강한 일관성이 꼭 필요한 데이터는 캐시하지 않는 것도 답입니다.

캐시가 한꺼번에 비면 DB가 맞는다

현상무슨 일이 일어나나대응
스탬피드인기 키 하나가 만료된 순간 수천 요청이 동시에 DB로락으로 한 요청만 재계산, 확률적 조기 갱신
관통DB에도 없는 키를 계속 조회해 매번 miss빈 결과도 짧게 캐시, Bloom Filter
눈사태많은 키가 같은 시각에 만료되거나 캐시 서버 다운TTL에 무작위 값 더하기, 캐시 이중화

스탬피드의 핵심 해법은 "재계산은 한 명만"입니다. 첫 요청만 락을 잡고 DB를 읽어 채우고, 나머지는 잠깐 기다리거나 직전 값을 받습니다. 만료 직전에 확률적으로 미리 갱신하면 만료 순간 자체를 피할 수 있습니다.

Redis는 싱글 스레드인데 왜 빠른가

Redis는 명령 실행을 스레드 하나가 순서대로 처리합니다. 모든 데이터가 메모리에 있어 명령 하나가 마이크로초 단위로 끝나므로, 병목은 CPU가 아니라 네트워크입니다.

수많은 클라이언트 연결은 1장에서 본 I/O 멀티플렉싱(epoll) 이벤트 루프로 한 스레드가 감당합니다. 락이 필요 없고 컨텍스트 스위칭도 없습니다.

느린 명령 하나가 전체를 멈춘다

KEYS *나 거대한 컬렉션 전체 조회는 그동안 다른 모든 요청을 세웁니다. 운영에서는 SCAN으로 나눠 읽습니다.

싱글 스레드라서 명령 하나는 항상 원자적으로 실행됩니다. 뒤에서 볼 재고 차감이 이 성질을 이용합니다. Redis 6.0부터는 네트워크 읽기와 쓰기만 I/O 스레드로 나눌 수 있습니다.

자료구조를 고르면 용도가 정해진다

자료구조대표 명령쓰임
StringGET, SET, INCR캐시 값, 카운터, 분산 락
HashHGET, HSET세션, 객체 필드별 저장
ListLPUSH, BRPOP간단한 작업 큐, 최근 목록
SetSADD, SISMEMBER중복 참여 방지, 태그
Sorted SetZADD, ZRANGE랭킹, 대기열 순번
StreamXADD, XREADGROUP컨슈머 그룹이 있는 로그

Sorted Set이 Skip List로 구현되는 이유는 3장에서 짚었습니다. 단순 캐시만 필요하면 Memcached도 선택지지만, 자료구조와 영속화가 필요하면 Redis를 씁니다.

메모리 저장소도 디스크에 남길 수 있다

항목RDB 스냅샷AOF
방식특정 시점 메모리 전체를 파일로쓰기 명령을 로그에 계속 추가
유실 범위마지막 스냅샷 이후 전부everysec 설정이면 약 1초
재시작 속도빠름(파일 로드)명령 재실행으로 느림
파일 크기압축된 바이너리, 작음커짐, 주기적 rewrite로 압축

RDB는 fork로 자식 프로세스를 만들어 저장하므로 메모리가 큰 인스턴스에서는 fork 순간과 Copy-on-Write로 메모리 사용이 늘어납니다. 순수 캐시라면 영속화를 끄고, 세션처럼 잃으면 곤란한 데이터라면 AOF를 켭니다.

CDN은 정적 자원을 사용자 곁에 둔다

  1. 사용자 요청이미지, JS, CSS
  2. 가까운 엣지캐시에 있으면 즉시 응답
  3. 오리진miss일 때만 원본 서버로
  4. 엣지에 저장Cache-Control 기준 TTL

CDN은 세계 곳곳의 엣지 서버에 콘텐츠를 캐시해 두는 네트워크입니다. 물리적 거리가 줄어 RTT가 짧아지고, 오리진은 같은 파일을 반복해서 보낼 필요가 없어집니다.

배포로 파일이 바뀌면 이름에 해시를 붙여(app.3f9a.js) 새 URL로 만드는 방식이 무효화 요청보다 확실합니다. AWS 구현인 CloudFront는 10장에서 다룹니다.

선착순 쿠폰 100장에 1만 명이 몰리면

  1. 요청 A 조회

    남은 수량 1을 읽습니다.

  2. 요청 B 조회

    A가 쓰기 전에 B도 남은 수량 1을 읽습니다.

  3. A 발급

    1 - 1 = 0으로 갱신하고 쿠폰을 발급합니다.

  4. B 발급

    B도 1 - 1 = 0으로 갱신하고 또 발급합니다. 101장째입니다.

"읽고, 판단하고, 쓰는" 세 단계 사이에 다른 요청이 끼어드는 경쟁 상태입니다. 1장의 임계 구역 문제가 서버 여러 대 규모로 다시 나타난 것입니다.

서버가 여러 대라 Java의 synchronized로는 막을 수 없습니다. 선택지는 네 가지입니다: DB 락, Redis 원자 연산, 분산 락, 큐로 줄 세우기.

선택지 1: DB가 직접 순서를 지키게 한다

-- 조건부 UPDATE: 확인과 차감을 한 문장으로
UPDATE coupon_stock
   SET remaining = remaining - 1
 WHERE coupon_id = 42 AND remaining > 0;
-- 영향받은 행이 0이면 소진

-- 비관적 락: 읽는 순간부터 잠금
SELECT remaining FROM coupon_stock
 WHERE coupon_id = 42 FOR UPDATE;

가장 단순하고 정확한 방법은 확인과 차감을 하나의 UPDATE로 묶는 것입니다. DB가 행 락으로 한 번에 하나씩 처리합니다. 비관적, 낙관적 락의 원리는 4장에서 다뤘습니다.

한계는 처리량입니다. 모든 요청이 같은 행 하나에 줄을 서므로 핫 로우가 되고, 대기 중인 트랜잭션이 커넥션 풀을 붙잡습니다.

선택지 2: Redis의 원자 연산에 맡긴다

local stock, users = KEYS[1], KEYS[2]
local uid = ARGV[1]
if redis.call('SISMEMBER', users, uid) == 1
then return -1 end               -- 이미 받음
local left = tonumber(redis.call('GET', stock))
if not left or left <= 0
then return 0 end                -- 소진
redis.call('DECR', stock)
redis.call('SADD', users, uid)
return 1

Redis는 명령을 하나씩 실행하므로 DECR 하나만으로도 원자적입니다. 중복 참여 확인까지 여러 명령을 묶어야 한다면 Lua 스크립트를 씁니다. 스크립트 전체가 다른 명령의 끼어듦 없이 실행됩니다.

초당 수만 건도 처리합니다. 다만 Redis의 수량과 DB의 발급 기록을 따로 맞춰야 하므로, 발급 내역은 뒤에서 볼 큐로 DB에 옮깁니다.

선택지 3: 분산 락으로 구간 전체를 잠근다

-- 획득: 없을 때만, 3초 뒤 자동 만료
SET lock:coupon:42 <uuid> NX PX 3000
-- 해제: 내 값일 때만 지운다 (Lua)
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end

// Redisson: 대기, 연장, 해제를 대신 처리
RLock lock = redisson.getLock("lock:coupon:42");
if (lock.tryLock(1, TimeUnit.SECONDS)) {
  try { issue(); } finally { lock.unlock(); }
}

여러 단계의 작업(외부 API 호출 포함)을 통째로 한 서버만 실행하게 하려면 분산 락이 필요합니다. 만료 시간은 락을 쥔 서버가 죽었을 때 영원히 잠기는 것을 막고, uuid 비교는 남의 락을 지우는 실수를 막습니다.

Redisson은 Pub/Sub로 락 해제를 기다리고, 작업이 길어지면 watchdog이 만료를 자동 연장합니다(기본 30초).

만료된 락의 주인이 돌아오면 펜싱 토큰

선택지 4: 줄을 세우고 네 방법을 비교한다

방법정확성처리량잘 맞는 경우
DB 조건부 UPDATE, 락트랜잭션으로 보장핫 로우에서 낮음경쟁이 크지 않은 재고
Redis 원자 연산, Lua명령 단위 보장매우 높음수량 차감, 선착순 판정
분산 락만료, 장애 시 허점락 대기만큼 낮음여러 단계를 묶어야 할 때
큐로 직렬화한 컨슈머가 순서대로비동기, 응답 지연즉시 결과가 필요 없는 발급

실무에서는 조합합니다. Redis로 선착순 당첨만 빠르게 판정하고, 당첨 기록은 큐에 넣어 DB 저장을 천천히 처리합니다. 큐가 무엇이고 어떻게 동작하는지가 다음 주제입니다.

메시지 큐는 보내는 쪽과 받는 쪽을 떼어 놓는다

  1. 주문 API메시지를 넣고 바로 응답
  2. 메시지 큐디스크에 보관, 순서 유지
  3. 컨슈머들각자 속도로 꺼내 처리

주문 API가 결제, 알림, 포인트 적립을 모두 동기 호출하면 응답이 가장 느린 작업만큼 늦어지고, 알림 서버가 죽으면 주문도 실패합니다. 메시지 큐를 두면 세 가지를 얻습니다.

비동기화로 응답이 빨라지고, 디커플링으로 받는 쪽이 죽거나 늘어나도 보내는 쪽은 모르며, 버퍼링으로 순간 트래픽을 큐에 쌓았다가 DB가 감당할 속도로 소화합니다.

Kafka는 파티션 단위로 쪼개고 줄 세운다

토픽은 여러 파티션으로 나뉘고, 각 파티션은 끝에 덧붙이기만 하는 로그입니다. 메시지마다 파티션 안의 위치인 오프셋이 붙습니다.

한 컨슈머 그룹 안에서 파티션 하나는 컨슈머 하나만 읽습니다. 그래서 순서는 파티션 안에서만 보장되고, 컨슈머를 파티션 수보다 늘려도 남는 컨슈머는 놉니다.

Kafka는 로그, RabbitMQ는 우체국에 가깝다

항목KafkaRabbitMQ
모델분산 로그, 컨슈머가 당겨 감(pull)브로커가 큐에서 밀어 줌(push)
읽은 메시지보존 기간 동안 남음, 재처리 가능ack 받으면 큐에서 삭제
라우팅토픽, 파티션 키 정도Exchange로 유연한 라우팅
강점대용량 이벤트 스트림, 여러 팀이 구독작업 분배, 메시지별 제어
DLQ컨슈머 쪽에서 별도 토픽으로 구현Dead Letter Exchange 내장

같은 이벤트를 여러 서비스가 각자 읽거나 과거부터 다시 읽어야 하면 Kafka, 작업을 일꾼들에게 나눠 주고 개별 메시지의 재시도와 우선순위를 다뤄야 하면 RabbitMQ가 자연스럽습니다.

전달 보장은 오프셋을 언제 커밋하느냐다

보장커밋 시점실패하면
at-most-once처리하기 전에 커밋처리 중 죽으면 그 메시지는 유실
at-least-once처리한 뒤에 커밋커밋 전 죽으면 다시 받아 중복 처리
exactly-once처리 결과와 커밋을 한 트랜잭션으로Kafka 내부끼리만 보장, 외부 DB는 별개

네트워크는 "보냈는데 응답이 안 오는" 경우를 늘 만들기 때문에, 유실을 피하려면 재전송을 하고 그 결과 중복이 생깁니다. 그래서 실무 기본값은 at-least-once + 중복을 견디는 컨슈머입니다. Kafka는 3.0부터 프로듀서의 중복 전송 방지(idempotent producer)가 기본으로 켜져 있지만, 이는 브로커에 쓰는 구간만 지킵니다.

같은 메시지를 두 번 받아도 결과는 한 번

멱등 컨슈머는 메시지마다 고유 ID를 두고, 처리한 ID를 DB에 기록합니다. 처리 결과와 ID 기록을 같은 트랜잭션에 넣고 ID에 유니크 제약을 걸면, 두 번째 메시지는 제약 위반으로 걸러집니다.

"잔액을 1000원 늘려라" 대신 "잔액을 5000원으로 만들어라"처럼 결과를 지정하는 메시지도 그 자체로 멱등입니다. 멱등성의 정의는 2장, API의 Idempotency-Key는 7장에서 다뤘습니다.

독이 든 메시지가 파티션을 막는다

형식이 깨진 메시지는 몇 번을 재시도해도 실패합니다. 순서대로 읽는 파티션에서는 그 뒤 메시지 전부가 멈춥니다.

재시도 상한 뒤에는 DLQ로

정해진 횟수만큼 실패한 메시지는 DLQ로 옮기고 다음 메시지로 넘어갑니다. DLQ에는 알람을 걸고 원인을 고친 뒤 다시 넣습니다.

3부

나누면 빨라지지만, 실패도 나뉘어 퍼진다

서비스를 쪼개면 트랜잭션도 쪼개지고, 한 서비스의 장애가 네트워크를 타고 번집니다. 그것을 견디는 패턴과, 처음부터 설계를 풀어 가는 순서를 봅니다.

원리 실무 설계 판단, 설정 수치, 장애 전파 사례와 용량 추정을 다룹니다.

MSA는 조직과 배포를 나누는 선택이다

팀이 작으면 잘 나눈 모듈형 모놀리식이 대개 더 낫습니다. 팀이 커져 배포가 서로를 막기 시작할 때, 경계가 분명한 영역부터 떼어 냅니다.

2PC는 여러 DB에 걸친 트랜잭션을 원자적으로 만듭니다. 대가는 가장 느린 참여자만큼 모두가 락을 쥐고 기다린다는 것입니다.

코디네이터가 단일 장애점이 되고, 메시지 브로커나 외부 API처럼 2PC를 지원하지 않는 참여자도 많습니다. 그래서 MSA에서는 잘 쓰지 않습니다.

Saga는 로컬 트랜잭션과 보상으로 잇는다

Saga는 큰 트랜잭션을 서비스별 로컬 트랜잭션의 연쇄로 나누고, 중간에 실패하면 이미 끝난 단계를 되돌리는 보상 트랜잭션을 거꾸로 실행합니다. 예를 들어 결제가 실패하면 "재고 복구", "주문 취소"를 실행합니다. 원자성 대신 최종 일관성을 택한 것입니다(4장 CAP 참조).

타임아웃은 모든 원격 호출에 건다

첫 번째 방어선은 타임아웃입니다. 많은 HTTP 클라이언트와 드라이버의 기본값은 무한대이거나 매우 길어서, 설정하지 않으면 느린 의존 대상에 스레드가 묶입니다.

타임아웃은 두 가지를 따로 겁니다. 연결 타임아웃은 TCP 연결 수립까지(보통 1초 안팎), 읽기 타임아웃은 응답을 기다리는 시간으로, 대상 API의 p99 응답 시간보다 조금 길게 잡습니다.

호출이 여러 단계로 이어지면 바깥 타임아웃이 안쪽보다 길어야 합니다. 바깥이 먼저 끊으면 안쪽은 아무도 기다리지 않는 일을 계속하며 자원을 씁니다.

재시도에는 지수 백오프와 지터를 섞는다

long base = 100, cap = 10_000;   // ms
for (int i = 0; i < 5; i++) {
  try {
    return call();
  } catch (RetryableException e) {
    long exp = Math.min(cap, base << i);
    sleep(rnd.nextLong(exp + 1));  // 0~exp
  }
}
throw new GiveUpException();

일시적 오류는 다시 시도하면 성공하지만, 실패한 클라이언트 수천이 같은 간격으로 재시도하면 회복 중인 서버를 다시 쓰러뜨립니다.

대기 시간을 100, 200, 400ms처럼 늘리는 지수 백오프에 무작위 지터를 섞어 재시도 시각을 흩뜨립니다. 재시도는 멱등한 요청에만, 횟수 상한을 두고 합니다.

서킷 브레이커는 실패할 호출을 미리 끊는다

계속 실패하는 대상을 계속 부르는 것은 양쪽 모두에 손해입니다. 서킷 브레이커는 최근 호출의 실패율이 임계치를 넘으면 회로를 열어, 호출하지 않고 즉시 실패를 반환합니다.

일정 시간 뒤 몇 건만 시험 삼아 보내 보고, 성공하면 닫고 실패하면 다시 엽니다. Resilience4j 기본값은 실패율 50%, 열림 대기 60초, 반열림 시험 호출 10건입니다.

격벽으로 가두고, 대체 응답으로 버틴다

벌크헤드는 배의 격벽처럼 자원을 나눕니다. 결제 호출용 스레드 풀 20개, 추천 호출용 10개처럼 의존 대상마다 풀을 따로 두면, 추천 서비스가 느려져도 그 10개만 막히고 결제는 계속 돕니다.

폴백은 실패했을 때 내보낼 대체 응답입니다. 추천 목록 대신 인기 상품, 실시간 재고 대신 캐시된 값처럼 기능을 낮춰서라도 응답합니다.

  1. 타임아웃

    느린 호출이 자원을 붙잡지 못하게 끊습니다.

  2. 재시도

    일시적 실패를 백오프와 지터로 흡수합니다.

  3. 서킷 브레이커

    지속적 실패는 호출 자체를 차단합니다.

  4. 벌크헤드

    한 의존 대상의 장애를 그 풀 안에 가둡니다.

  5. 폴백

    결국 실패하면 낮춘 기능으로라도 응답합니다.

Sliding Window Log요청 시각을 모두 기록해 최근 구간을 셈정확, 메모리 많이 씀
Sliding Window Counter이전 칸과 현재 칸을 가중 평균근사지만 가볍고 정확도 양호

Fixed Window는 0분 59초에 100건, 1분 0초에 100건이 들어오면 1초 사이에 200건이 통과합니다. 이 경계 문제를 줄인 것이 두 Sliding Window 방식입니다.

Token Bucket을 여러 서버에서 함께 쓰려면

  1. 버킷 읽기

    Redis에서 남은 토큰 수와 마지막 갱신 시각을 읽습니다.

  2. 토큰 채우기

    지난 시간 × 충전 속도만큼 더하되 용량을 넘지 않게 합니다.

  3. 판정

    토큰이 1 이상이면 하나 빼고 통과, 아니면 거절합니다.

  4. 원자적으로

    세 단계를 Lua 스크립트 하나로 묶어 실행합니다.

서버마다 따로 세면 서버가 10대일 때 한도가 10배가 됩니다. 그래서 카운터를 Redis 같은 공용 저장소에 두고, 읽기와 쓰기 사이에 끼어들지 못하게 Lua로 원자 실행합니다.

거절할 때는 429 Too Many Requests와 Retry-After 헤더로 언제 다시 오라고 알려 줍니다. API Gateway의 역할은 7장에서 다뤘고, AWS 구현은 11장에서 다룹니다.

노드가 늘어도 키 대부분은 제자리에

캐시 서버 N대에 hash(key) % N으로 키를 나누면, 서버를 한 대 늘리는 순간 N이 바뀌어 키 대부분이 다른 서버로 갑니다. 캐시가 한꺼번에 비는 눈사태가 됩니다.

일관성 해싱은 노드와 키를 같은 원 위에 놓고, 키는 시계 방향으로 처음 만나는 노드에 둡니다. 노드가 추가되면 그 노드 바로 앞 구간의 키만 옮겨 갑니다. 노드마다 가상 노드를 여러 개 두어 쏠림을 줄입니다.

설계는 요구사항과 숫자에서 시작한다

지금까지의 도구로 URL 단축기를 설계해 봅니다. 먼저 기능 요구사항(긴 URL을 짧은 코드로, 코드로 접속하면 원래 URL로 이동)과 비기능 요구사항(이동은 빨라야 하고, 링크는 5년간 유지)을 정합니다.

다음은 대략의 숫자입니다. 정확할 필요는 없고, 어느 자원이 병목인지 가리키면 충분합니다.

API, ID 생성, 확장을 차례로 정한다

API는 POST /urls로 코드를 만들고 GET /{code}가 리다이렉트합니다. 301은 브라우저가 캐시해 서버 부하가 줄지만 클릭 통계를 못 얻고, 302는 매번 서버를 거칩니다.

코드는 숫자 ID를 Base62(0-9, a-z, A-Z)로 바꿉니다. 7자리면 627, 약 3.5조 개라 183억 건을 넉넉히 담습니다. 해시를 자르면 충돌 검사가 필요하지만 ID 방식은 충돌이 없습니다.

  1. 데이터 모델

    code(PK), long_url, created_at. 조인 없는 키-값 조회.

  2. ID 발급

    서버마다 ID 구간을 미리 받아 써서 발급 경합을 없앱니다.

  3. 읽기 캐시

    Cache-Aside, 인기 링크는 소수에 몰림.

  4. 무상태 서버

    LB 뒤에서 스케일 아웃합니다.

  5. 저장소 확장

    code 기준 샤딩, 클릭 통계는 큐로 비동기 집계.

정리

  • 스케일 아웃은 무상태 서버에서 시작합니다. 세션 같은 상태를 Redis 같은 공용 저장소로 옮겨야 아무 서버나 요청을 받을 수 있습니다.
  • 캐시는 TTL로 안전망을 치고 삭제로 무효화합니다. 스탬피드, 관통, 눈사태는 "재계산은 한 명만", 빈 값 캐시, TTL 분산으로 막습니다.
  • 동시성은 원자성을 어디에 맡기느냐의 문제입니다. DB 한 문장, Redis 명령과 Lua, 분산 락과 펜싱 토큰, 큐 직렬화를 처리량과 정확성으로 고릅니다.
  • 메시지는 at-least-once로 오고, 컨슈머가 멱등해야 합니다. 서비스를 넘는 정합성은 Saga와 Transactional Outbox로 최종 일관성을 맞춥니다.
  • 느림이 실패보다 위험합니다. 타임아웃, 백오프와 지터, 서킷 브레이커, 벌크헤드, 폴백으로 장애를 가두고, 처리율 제한으로 받을 만큼만 받습니다.

스스로 점검 (1)

  1. Sticky Session만으로 세션 문제를 풀면 무엇이 남나요?

    서버 한 대가 죽으면 그 서버의 세션이 모두 사라지고, 특정 서버에 사용자가 쏠립니다. 서버를 줄이거나 배포할 때도 세션이 끊깁니다.

  2. DB를 갱신한 뒤 캐시를 새 값으로 덮어쓰지 않고 지우는 이유는?

    동시에 두 쓰기가 일어나면 캐시 덮어쓰기 순서가 DB 반영 순서와 뒤바뀌어 낡은 값이 남을 수 있습니다. 삭제는 순서와 관계없이 다음 읽기가 최신 값을 채웁니다.

  3. 모든 캐시 키에 TTL 600초를 똑같이 주면 어떤 일이 생길 수 있나요?

    한꺼번에 채운 키들이 같은 순간 만료되어 DB로 요청이 몰리는 눈사태가 납니다. TTL에 무작위 값을 더해 만료 시각을 흩뜨립니다.

  4. Redis로 분산 락을 잡을 때 만료 시간과 고유 값이 각각 필요한 이유는?

    만료 시간이 없으면 락을 쥔 서버가 죽었을 때 영원히 잠깁니다. 고유 값이 없으면 내 락이 만료된 뒤 남이 잡은 락을 내가 지울 수 있습니다.

스스로 점검 (2)

  1. 파티션이 4개인 토픽에 컨슈머 6개를 같은 그룹으로 붙이면?

    파티션 하나는 그룹 안에서 컨슈머 하나만 읽으므로 2개는 놉니다. 처리량을 늘리려면 파티션 수를 먼저 늘려야 합니다.

  2. 주문 저장 후 Kafka에 직접 발행하는 코드는 어디서 깨지나요?

    DB 커밋 후 발행 전에 서버가 죽으면 이벤트가 사라지고, 발행 후 커밋이 실패하면 없는 주문의 이벤트가 나갑니다. Outbox로 같은 트랜잭션에 묶어 해결합니다.

  3. 재시도 간격을 1초로 고정하면 장애 복구 때 무엇이 문제인가요?

    실패한 클라이언트들이 같은 박자로 동시에 재시도해 회복 중인 서버에 다시 폭주합니다. 지수 백오프와 지터로 시각을 흩뜨립니다.

  4. Fixed Window로 분당 100건을 제한할 때 최악의 경우 몇 건이 통과하나요?

    창의 경계 앞뒤 1초 사이에 이전 창 100건과 다음 창 100건, 최대 200건이 통과합니다. Sliding Window로 줄입니다.

  5. 캐시 서버를 % N 방식으로 나누다가 한 대를 늘리면 왜 위험한가요?

    N이 바뀌면서 키 대부분의 위치가 바뀌어 사실상 캐시 전체가 비고 DB로 몰립니다. 일관성 해싱은 일부 구간만 옮깁니다.
