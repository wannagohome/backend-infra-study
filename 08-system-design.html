1부

서비스가 자라면 무엇부터 터지는가

7장에서 주문 API를 설계하고 지켰습니다. 이 부에서는 그 API를 부르는 사용자가 백 배로 늘었을 때 어디가 먼저 막히는지, 서버를 늘리려면 무엇부터 갖춰야 하는지를 봅니다. 6장의 Tomcat 스레드, 4장의 커넥션 풀, 2장의 로드 밸런서가 여기서 한자리에 모입니다.

처음에는 서버 한 대로 충분하다

이 장 내내 따라갈 예제는 7장에서 만든 주문 API를 가진 작은 온라인 쇼핑몰입니다. 막 문을 열었을 때는 Spring 애플리케이션과 MySQL을 서버 한 대에 함께 올려도 잘 돌아갑니다. 구성이 단순하니 배포도 쉽고 비용도 적습니다.

사용자가 늘면 CPU와 메모리가 먼저 차고, 이어서 DB 커넥션과 디스크 I/O가 밀립니다. 더 근본적인 문제는 이 서버 하나가 멈추면 서비스 전체가 멈춘다는 점입니다. 이렇게 하나만 고장 나도 전체가 멈추는 지점을 단일 장애점(SPOF)이라고 부릅니다.

규모와 안정성은 숫자로 말한다

"트래픽이 많다", "자주 죽는다"는 말로는 설계를 할 수 없습니다. 이 장에서 계속 쓸 숫자 세 가지를 먼저 정해 둡니다.

QPS(또는 초당 트랜잭션 수인 TPS)는 초당 처리하는 요청 수, 즉 처리량입니다. 하루 860만 건이면 평균 약 100 QPS지만, 트래픽은 저녁이나 이벤트 시각에 몰리므로 설계는 평균이 아니라 최대치(피크)를 기준으로 합니다.

응답 시간은 평균으로 보면 속습니다. 요청 100개 중 99개가 50ms, 1개가 5초면 평균은 약 100ms로 멀쩡해 보이지만 그 한 명은 5초를 기다립니다. 그래서 응답 시간을 작은 순서로 줄 세웠을 때 99% 지점의 값인 p99를 함께 봅니다. "p99가 300ms"는 요청 100개 중 99개가 300ms 안에 끝났다는 뜻입니다.

가용성은 전체 시간 중 서비스가 정상이던 비율입니다. 99.9%는 한 달에 약 43분, 99.99%는 약 4분 정도만 멈춰도 된다는 뜻입니다. 9 하나를 더할 때마다 허용 중단 시간이 10분의 1로 줄어 비용이 크게 뛰므로, 서비스마다 목표치를 정합니다.

서버 한 대짜리 쇼핑몰은 배포나 OS 패치만으로도 매번 몇 분씩 멈추니 99.9%를 지키기도 어렵습니다. 처리량과 가용성을 함께 올리는 첫 번째 결정은 서버를 어떻게 늘리느냐입니다.

더 큰 서버냐, 더 많은 서버냐

서버를 키우는 방향은 두 가지입니다. 스케일 업은 같은 서버의 CPU와 메모리를 더 큰 것으로 바꾸는 수직 확장입니다. 코드를 고칠 필요가 없어 가장 쉽게 시작할 수 있습니다.

하지만 한계가 분명합니다. 한 대에 꽂을 수 있는 CPU와 메모리에는 물리적 상한이 있고, 고사양으로 갈수록 성능 대비 가격이 가파르게 오릅니다. 교체하는 동안에는 서비스가 멈추고, 아무리 커져도 여전히 한 대라서 SPOF도 그대로입니다.

스케일 아웃은 같은 서버를 여러 대로 늘리는 수평 확장입니다. 평범한 서버를 필요한 만큼 더하면 되고, 한 대가 죽어도 나머지가 요청을 받으므로 처리량과 가용성이 함께 올라갑니다.

대가는 새로운 과제들입니다. 요청을 여러 서버에 나눠 줄 장치가 필요하고, 어느 서버로 가도 같은 결과가 나오도록 서버를 설계해야 하며, 서버 사이의 데이터 일관성도 신경 써야 합니다. 이 장의 대부분이 바로 이 과제들의 해법입니다.

실무에서는 둘 중 하나만 고르지 않습니다. 애플리케이션 서버는 스케일 아웃하고, 수평 확장이 어려운 DB는 먼저 스케일 업으로 버티는 조합이 흔합니다.

여러 서버 앞에는 나눠 주는 입구가 선다

쇼핑몰 앱 서버를 세 대로 늘렸다고 합시다. 사용자는 서버 세 대의 주소를 알 수도 없고 알아서도 안 됩니다. 그래서 하나의 주소로 요청을 받아 뒤의 서버들에 나눠 주는 로드 밸런서를 앞에 둡니다. 2장에서 본 리버스 프록시, 즉 서버 편에 서서 단일 입구 역할을 하는 프록시의 한 형태입니다.

2장에서 로드 밸런서를 패킷을 어디까지 열어 보느냐로 나눴습니다. L4는 IP와 포트만 보고 TCP 연결 단위로 나누고, L7은 HTTP 메시지까지 열어 URL 경로나 헤더에 따라 보낼 곳을 고릅니다. 이 장에서는 그다음 질문, 즉 "여러 서버 중 어느 서버를 고르는가"와 "고장 난 서버를 어떻게 빼는가"를 봅니다.

로드 밸런서를 두면 서버를 한 대씩 빼고 배포한 뒤 다시 넣을 수 있어 배포 중에도 서비스가 멈추지 않습니다. 앞에서 말한 가용성 문제의 상당 부분이 여기서 풀립니다.

그런데 이제 로드 밸런서 자체가 새로운 SPOF입니다. 그래서 로드 밸런서도 두 대 이상으로 이중화하고, 한 대가 죽으면 다른 한 대가 같은 주소를 이어받게 합니다. AWS의 ALB 같은 관리형 로드 밸런서는 이 이중화를 서비스가 대신해 주며, 13장에서 다룹니다.

라운드 로빈은 요청 비용이 같다고 가정한다

로드 밸런서가 서버를 고르는 규칙을 분배 알고리즘이라고 합니다. 가장 단순한 라운드 로빈은 1번, 2번, 3번 서버에 차례로 한 건씩 돌아가며 보냅니다. 상태를 기억할 필요가 없어 빠르고 예측하기 쉽습니다.

서버 사양이 서로 다르면 가중 라운드 로빈을 씁니다. 새로 산 큰 서버에 가중치 2, 옛 서버에 1을 주면 요청이 2 대 1로 갑니다.

두 방식 모두 요청 하나하나의 처리 비용이 비슷하다고 가정합니다. 쇼핑몰에서 상품 조회는 10ms에 끝나지만 주문 내역 엑셀 다운로드는 3초가 걸린다고 해 봅시다. 순서대로 나누다 보면 운 나쁜 서버에 느린 요청이 몰려 그 서버의 스레드만 바닥나고, 다른 서버는 한가한 일이 생깁니다.

최소 연결 방식은 지금 처리 중인 연결이 가장 적은 서버를 고릅니다. 느린 요청을 붙잡고 있는 서버는 연결 수가 높게 유지되므로 새 요청이 자연스럽게 다른 서버로 갑니다. 그래서 처리 시간의 편차가 큰 서비스에 잘 맞습니다.

해시 방식은 같은 클라이언트를 같은 서버로

헬스 체크가 죽은 서버를 빼 준다

어떤 알고리즘을 쓰든, 이미 죽은 서버를 고르면 그 요청은 실패합니다. 그래서 로드 밸런서는 몇 초마다 각 서버의 헬스 체크 경로(예: /health)를 호출해 보고, 정해진 횟수(예: 연속 3회) 실패하면 분배 대상에서 뺐다가 연속으로 성공하면 다시 넣습니다.

한 번의 실패로 바로 빼지 않는 것은 일시적 지연 때문에 멀쩡한 서버가 들락날락하는 것을 막기 위해서입니다. 대신 죽은 서버를 알아채기까지 "간격 × 횟수"만큼 걸리고, 그동안 일부 요청은 실패합니다.

헬스 체크에 DB 확인을 넣을 때는 신중하게

DB가 잠깐 느려지면 모든 서버가 동시에 실패로 판정되어 전부 빠질 수 있습니다. "이 프로세스가 요청을 받을 수 있는가"와 "의존 대상이 건강한가"를 구분해야 합니다.

같은 생각이 10장에서 다시 나옵니다

Kubernetes의 liveness probe와 readiness probe가 바로 이 두 질문을 나눈 것입니다.

스케일 아웃의 전제는 무상태 서버다

로드 밸런서로 요청을 나누자 새 문제가 생깁니다. 사용자가 1번 서버에서 로그인했는데 다음 요청이 2번 서버로 가면, 2번 서버 메모리에는 그 사용자의 세션이 없어 로그인이 풀린 것처럼 보입니다. 2장에서 세션 ID 쿠키를 설명하며 "서버가 여러 대면 다른 서버는 그 세션을 모른다"고 미뤄 둔 바로 그 문제입니다.

뿌리는 서버가 요청과 요청 사이에 기억을 들고 있다는 점입니다. 어떤 요청이 어느 서버로 가도 같은 결과를 내려면 서버 안에 사용자별 상태가 없어야 합니다. 이런 서버를 무상태 서버라고 합니다.

로그인 정보 같은 상태를 아예 없앨 수는 없으니, 상태를 서버 밖으로 옮기는 것이 해법입니다. 그 방법이 세 가지 있습니다.

세션을 다루는 세 가지 방법

첫째는 Sticky Session입니다. 로드 밸런서가 첫 응답에 "이 사용자는 1번 서버"라는 쿠키를 붙이고, 이후 요청을 늘 같은 서버로 보냅니다. 코드는 그대로지만 서버 한 대가 죽으면 그 서버의 세션이 모두 사라지고, 오래 머무는 사용자가 몰린 서버만 붐빕니다. 배포로 서버를 내릴 때도 세션이 끊깁니다.

둘째는 세션 클러스터링입니다. Tomcat 같은 WAS끼리 세션이 바뀔 때마다 서로 복제해 모든 서버가 모든 세션을 갖게 합니다. 한 대가 죽어도 세션이 남지만, 서버가 늘수록 복제 트래픽과 메모리가 함께 늘어 수십 대 규모에서는 부담이 됩니다.

셋째는 세션을 외부 저장소에 두는 것입니다. 모든 서버가 같은 저장소에서 세션을 읽고 쓰므로 서버는 완전히 무상태가 됩니다. 저장소로는 주로 Redis를 씁니다. 지금은 "메모리에 키와 값을 저장하는 아주 빠른 별도 서버" 정도로 알아 두면 되고, 동작 원리는 2부에서 자세히 봅니다.

세 번째 방식의 대가는 저장소 자체가 새로운 의존 대상이 된다는 점입니다. 그래서 세션 저장소도 이중화해야 합니다. 7장의 JWT처럼 상태를 토큰에 담아 서버가 아예 저장하지 않는 방법도 있습니다.

세션 말고도 서버에 숨은 상태가 있다

세션을 Redis로 옮겼는데도 서버를 늘리자 이상한 일이 생깁니다. 상품 이미지를 올리면 가끔 "이미지를 찾을 수 없음"이 뜹니다. 업로드 요청은 1번 서버의 로컬 디스크에 파일을 저장했는데, 이미지를 보여 달라는 요청은 2번 서버로 갔기 때문입니다. 업로드 파일은 모든 서버가 HTTP로 올리고 받는 공용 객체 저장소에 둬야 합니다. AWS의 S3가 대표적이며 15장에서 다룹니다.

매일 새벽 정산을 돌리는 @Scheduled 작업도 문제입니다. 서버가 세 대면 세 대 모두에서 실행되어 정산이 세 번 됩니다. 한 대에서만 돌도록 별도 배치 서버로 빼거나, 뒤에서 볼 분산 락으로 한 서버만 실행하게 합니다.

서버 메모리에 둔 카운터나 캐시도 서버마다 값이 달라집니다. "오늘 남은 쿠폰 수"를 서버 메모리에서 세면 서버 세 대가 각자 100장씩, 모두 300장을 나눠 줍니다.

정리하면, 서버를 언제든 늘리고 죽여도 되는 상태로 만드는 것이 스케일 아웃의 전제입니다. 서버 안에 남아도 되는 것은 요청 하나를 처리하는 동안만 쓰는 값뿐입니다.

앱 서버를 늘리면 DB 연결 수가 곱해진다

앱 서버는 무상태로 만들었으니 얼마든지 늘릴 수 있습니다. 하지만 모든 서버가 여전히 같은 DB 하나를 봅니다. 4장에서 봤듯 각 서버는 커넥션 풀, 즉 미리 열어 둔 DB 연결 묶음을 갖고 있으므로 서버를 늘릴수록 DB가 받는 연결 수가 곱해집니다.

예를 들어 서버 10대가 각각 풀 크기 20이면 DB는 연결 200개를 받아야 합니다. MySQL의 max_connections 기본값은 151이라, 설정을 바꾸지 않으면 서버를 늘리는 순간 연결 오류가 납니다. 한도를 올려도 연결마다 DB 메모리를 쓰므로 무한히 올릴 수는 없습니다.

DB 자체의 처리량도 문제입니다. 4장에서 본 두 가지 확장을 상기해 봅시다. 레플리케이션은 Primary의 변경 로그를 Replica에 보내 같은 데이터를 복제해 두고 읽기를 Replica로 나누는 방식인데, 비동기 복제라 방금 쓴 값이 잠시 안 보이는 복제 지연이 있습니다. 샤딩은 데이터를 키 기준으로 여러 DB에 흩는 방식으로, 쓰기까지 나눌 수 있지만 되돌리기 어렵습니다.

두 방법 모두 비용이 큽니다. 그래서 대규모 시스템은 DB를 늘리기 전에 먼저 DB까지 오는 요청 자체를 줄입니다. 이것이 2부의 주제입니다.

이 장에서 자라날 쇼핑몰의 전체 모습

2부

DB를 덜 부르고, 몰리는 일은 줄 세운다

1부에서 앱 서버는 마음껏 늘릴 수 있게 됐지만 DB는 여전히 하나입니다. 이 부에서는 세 가지 질문을 차례로 풉니다. 반복되는 읽기는 어떻게 덜어 내나(캐시), 한 데이터에 몰리는 쓰기는 어떻게 줄 세우나(원자 연산과 락), 당장 안 해도 되는 일은 어떻게 뒤로 미루나(메시지 큐).

기초 원리 여기부터는 캐시, 락, 큐가 내부에서 어떻게 동작하는지 다룹니다.

캐시는 같은 답을 다시 계산하지 않는 것이다

쇼핑몰 트래픽을 들여다보면 대부분이 상품 상세 조회입니다. 주문 한 건이 생길 때 상세 페이지는 수십 번 열립니다. 게다가 조회는 메인에 걸린 인기 상품 몇백 개에 몰립니다. 같은 상품을 같은 내용으로 DB에서 수만 번 읽고 있는 셈입니다.

캐시는 이렇게 반복해서 읽히는 결과를 더 빠른 곳에 복사해 두고 재사용하는 것입니다. 1장에서 CPU가 자주 쓰는 데이터를 메모리보다 빠른 CPU 캐시에 두던 것과 같은 발상입니다. 그때도 "최근에 쓴 것을 곧 또 쓴다"는 지역성이 캐시를 쓸모 있게 만들었습니다.

효과는 두 가지입니다. DB가 디스크와 인덱스를 거쳐 수 ms 걸리던 조회가 메모리 조회로 1ms 미만이 되고, 그만큼 DB가 받는 요청이 줄어듭니다.

캐시에서 값을 찾으면 적중, 없으면 미스라고 하고, 전체 조회 중 적중한 비율을 적중률이라고 합니다. 적중률 90%면 DB로 가는 읽기가 10분의 1, 99%면 100분의 1입니다. 90%에서 99%로 올리면 DB 부하는 다시 10분의 1이 되므로, 적중률의 몇 %p 차이가 DB에는 큰 차이입니다.

캐시할 것과 캐시하면 안 되는 것

캐시는 원본의 복사본이므로 원본이 바뀌면 잠시 어긋난 값, 즉 낡은 값을 돌려줄 수 있습니다. 그래서 무엇을 캐시할지는 "얼마나 자주 읽히나"와 "낡은 값을 얼마나 견딜 수 있나" 두 질문으로 정합니다.

잘 맞는 대상은 읽기가 쓰기보다 훨씬 많고, 계산이나 조회 비용이 크고, 몇 초에서 몇 분 낡아도 괜찮은 데이터입니다. 상품 설명과 이미지 목록, 카테고리 트리, 메인 화면의 인기 상품 순위가 여기에 해당합니다.

맞지 않는 대상은 매 순간 정확해야 하는 데이터입니다. 남은 재고 수량을 캐시에서 읽고 "구매 가능"을 판단하면 이미 품절된 상품을 팔 수 있습니다. 결제 금액, 계좌 잔액도 마찬가지입니다. 이런 값은 화면 표시용으로만 캐시하고, 실제 판단은 원본에서 합니다.

사용자마다 다른 데이터(내 장바구니)는 키가 사용자 수만큼 늘어나 적중률이 낮으니, 캐시할 가치가 있는지 따져 봐야 합니다. 대상을 정했으면 다음 질문은 캐시를 어디에 두느냐입니다.

로컬 캐시는 빠르고, 글로벌 캐시는 하나다

로컬 캐시는 각 앱 서버의 JVM 메모리에 둡니다(Caffeine 같은 라이브러리). 네트워크를 타지 않아 가장 빠르지만, 서버 10대면 캐시도 10벌이라 한 서버에서 값을 바꿔도 나머지 9대는 옛 값을 들고 있습니다.

글로벌 캐시는 Redis 같은 별도 서버 하나를 모든 앱 서버가 함께 씁니다. 네트워크 왕복이 한 번 들지만 모두 같은 값을 보고, 지우면 한 번에 지워집니다.

Cache-Aside: 없으면 DB에서 읽고 채운다

캐시를 쓰는 가장 흔한 방식은 애플리케이션이 캐시와 DB를 직접 오가는 Cache-Aside입니다. 캐시를 먼저 보고, 미스면 DB에서 읽어 캐시에 넣어 둡니다. EX 600은 600초 뒤 저절로 지워지라는 뜻입니다.

캐시가 죽어도 DB로 읽으면 되므로 장애에 강합니다. 대신 첫 요청은 늘 미스이고, DB를 바꾼 뒤 캐시를 어떻게 맞출지는 직접 정해야 합니다.

쓰기는 DB를 먼저 바꾸고 캐시를 지운다

Product get(long id) {
  String key = "product:" + id;
  Product p = cache.get(key);       // 1
  if (p != null) return p;
  p = repository.findById(id);      // 2
  cache.set(key, p, ofSeconds(600)); // 3
  return p;
}

void update(Product p) {
  repository.save(p);               // 4
  cache.delete("product:" + p.id()); // 5
}

읽기는 앞의 그림 그대로입니다. 1에서 캐시를 보고, 있으면 바로 돌려줍니다. 없으면 2에서 DB를 읽고 3에서 600초짜리로 채웁니다.

상품 가격을 고치는 쓰기는 4에서 DB를 먼저 바꾼 뒤 5에서 캐시 키를 지웁니다. 새 값을 넣지 않고 지우는 이유, 그리고 DB가 먼저인 이유는 다음 두 슬라이드에서 봅니다.

캐시가 쓰기 경로에 끼어드는 다른 방식들

Cache-Aside는 애플리케이션이 모든 것을 직접 하는 방식입니다. 캐시 계층이 일을 더 많이 맡는 방식도 있습니다.

Read-Through는 미스가 났을 때 애플리케이션 대신 캐시 계층이 DB를 읽어 채웁니다. 앱 코드는 "캐시에서 읽는다"만 남아 단순해지지만, 캐시 라이브러리가 DB 접근 방법을 알아야 합니다.

Write-Through는 쓸 때마다 캐시와 DB에 함께 기록합니다. 캐시가 늘 최신이라 읽기 정합성이 좋지만, 쓰기마다 두 곳을 거쳐 느려지고 한 번도 안 읽힐 데이터까지 캐시에 쌓입니다.

Write-Back은 캐시에만 쓰고 바로 응답한 뒤, 모아 두었다가 나중에 DB에 반영합니다. 쓰기가 매우 빠르지만 DB에 반영되기 전에 캐시가 죽으면 그 사이의 쓰기가 사라집니다. 그래서 조회수나 좋아요 수처럼 조금 잃어도 되는 카운터를 모아 반영할 때만 쓰고, 주문이나 결제에는 쓰지 않습니다.

Write-Around는 DB에만 쓰고 캐시는 건드리지 않거나 지웁니다. 앞의 코드가 바로 이 방식이며, 쓴 직후의 첫 읽기는 미스가 됩니다.

쓰기 전략은 속도와 유실 위험을 맞바꾼다

네 방식을 나란히 놓으면, 쓰기가 빠를수록 잃을 위험이 커지는 관계가 보입니다.

전략흐름장점위험
Read-Through캐시가 미스 시 DB를 대신 읽음앱 코드가 단순캐시 계층이 DB 접근을 알아야 함
Write-Through캐시와 DB에 함께 기록캐시가 늘 최신쓰기마다 두 곳, 지연 증가
Write-Back캐시에만 쓰고 나중에 DB로쓰기가 매우 빠름캐시 장애 시 데이터 유실
Write-AroundDB에만 쓰고 캐시는 지움안 읽히는 데이터는 캐시 안 함쓴 직후 읽기는 미스

실무 기본값은 읽기 Cache-Aside + 쓰기 Write-Around(삭제) 조합입니다. 이 조합에서 남는 문제는 "캐시가 언제 원본과 어긋나는가"입니다.

TTL은 안전망이고, 무효화는 삭제로 한다

캐시는 언젠가 원본과 어긋납니다. 캐시 키에 TTL, 즉 수명을 걸어 두면 무효화 코드에 버그가 있어도 그 시간이 지나면 저절로 사라지고 원본에서 다시 채워집니다. 그래서 TTL은 모든 키에 거는 마지막 안전망입니다. 2장 DNS 레코드의 TTL과 같은 발상입니다.

데이터가 바뀌면 캐시를 새 값으로 덮어쓰기보다 지우는 편이 안전합니다. 두 요청이 동시에 가격을 바꾸면 캐시 덮어쓰기 순서가 DB 반영 순서와 뒤바뀔 수 있지만, 삭제는 순서와 상관없이 다음 읽기가 DB의 최신 값을 채웁니다. DB를 먼저 바꾸는 이유도 같습니다. 캐시를 먼저 지우면 DB가 바뀌기 전 그 틈에 다른 요청이 옛 값을 다시 채울 수 있습니다.

TTL을 짧게 잡으면 정합성은 좋아지고 적중률은 떨어집니다. 데이터마다 "몇 초 낡은 값까지 허용되는가"를 먼저 정하고 그 값을 TTL로 씁니다.

삭제해도 낡은 값이 다시 들어올 수 있다

  1. 요청 A 읽기

    캐시 미스라 DB에서 옛 가격 v1을 읽습니다.

  2. 요청 B 쓰기

    DB를 v2로 갱신하고 캐시 키를 삭제합니다.

  3. 요청 A 채우기

    늦게 도착한 A가 v1을 캐시에 SET합니다.

  4. 결과

    DB는 v2, 캐시는 v1. TTL이 끝날 때까지 낡은 값이 남습니다.

DB 먼저, 삭제 나중을 지켜도 읽기와 쓰기가 이렇게 엇갈리면 불일치가 생깁니다. 드물지만 트래픽이 많으면 실제로 일어납니다.

기본 대응은 TTL을 짧게 두는 것입니다. 쓰기 후 수백 ms 뒤 한 번 더 지우는 지연 이중 삭제, 또는 CDC로 지우는 방법도 있습니다. CDC는 4장에서 본 DB 변경 로그(binlog)를 읽어 "어떤 행이 바뀌었다"는 이벤트로 바꾸는 기법이라, DB에 실제 반영된 순서대로 캐시를 지울 수 있습니다.

인기 키 하나가 만료되면 DB가 맞는다

정합성 다음 걱정은 캐시가 비는 순간입니다. 메인에 걸린 특가 상품 키에 초당 5,000건의 조회가 온다고 해 봅시다. TTL이 끝나 키가 사라진 순간, 그 짧은 틈에 들어온 수천 요청이 모두 미스를 보고 동시에 DB로 같은 쿼리를 보냅니다. 캐시를 채우는 데 100ms가 걸리면 그사이 500건이 DB를 칩니다. 이것을 캐시 스탬피드라고 합니다.

핵심 해법은 "재계산은 한 명만"입니다. 미스를 본 요청들 중 첫 번째만 락을 잡고 DB를 읽어 캐시를 채우고, 나머지는 잠깐 기다렸다가 캐시를 다시 보거나 직전 값을 받습니다. 이 락은 서버 여러 대에 걸쳐야 하므로 Redis로 잡는데, 그 방법은 뒤의 분산 락에서 봅니다.

만료 순간 자체를 피하는 방법도 있습니다. 확률적 조기 갱신은 남은 TTL이 짧아질수록 높은 확률로 "내가 미리 갱신하겠다"고 결정하게 합니다. 대부분의 요청은 그냥 캐시 값을 받고, 운 좋은 요청 하나가 만료 전에 새 값을 채워 두므로 키가 비는 순간이 오지 않습니다.

비슷하게, 만료된 값을 일단 돌려주면서 뒤에서 한 번만 갱신하는 방식도 있습니다. 공통점은 같은 키에 대한 DB 조회가 동시에 여러 번 일어나지 않게 하는 것입니다.

없는 키를 노리거나, 한꺼번에 비거나

캐시 관통은 DB에도 없는 키(존재하지 않는 상품 ID)를 계속 조회해 매번 미스가 나는 현상입니다. "없음"도 짧게 캐시하거나, 블룸 필터(집합에 "확실히 없음"을 빠르게 알려 주는 작은 비트 배열)로 먼저 거릅니다. 캐시 눈사태는 많은 키가 같은 시각에 만료되거나 캐시 서버가 죽어 DB로 한꺼번에 몰리는 현상입니다.

현상무슨 일이 일어나나대응
스탬피드인기 키 하나가 만료된 순간 동시 미스락으로 한 요청만 재계산, 조기 갱신
관통DB에도 없는 키를 계속 조회빈 결과도 짧게 캐시, 블룸 필터
눈사태많은 키 동시 만료, 캐시 서버 다운TTL에 무작위 값 더하기, 캐시 이중화

Redis는 메모리 위의 자료구조 서버다

지금까지 세션 저장소와 글로벌 캐시로 Redis를 계속 언급했습니다. 이제 Redis가 무엇인지 제대로 봅니다. Redis는 모든 데이터를 메모리에 두는 키-값 저장소입니다. 클라이언트가 TCP로 SET, GET 같은 명령을 보내면 즉시 처리해 돌려줍니다.

단순한 키-값 캐시라면 Memcached도 오래 쓰여 온 선택지입니다. Redis가 더 널리 쓰이는 이유는 값으로 문자열뿐 아니라 리스트, 집합, 정렬된 집합 같은 자료구조를 담고 그 자료구조를 다루는 명령을 서버 안에서 실행해 주기 때문입니다. 디스크에 남기는 영속화와 복제 기능도 있습니다.

그래서 Redis는 캐시를 넘어 세션 저장소, 카운터, 랭킹, 선착순 판정, 분산 락, 간단한 큐로 쓰입니다. 이 장의 쿠폰 예제도 대부분 Redis 위에서 풀립니다.

이런 쓰임이 가능한 바탕에는 의외의 설계가 있습니다. Redis는 명령을 스레드 하나로 처리합니다. 스레드 하나로 어떻게 초당 수만 건을 감당하는지, 그리고 그 설계가 왜 오히려 장점이 되는지가 다음 주제입니다.

Redis는 싱글 스레드인데 왜 빠른가

모든 데이터가 메모리에 있어 명령 하나는 마이크로초 단위로 끝납니다. 그래서 병목은 CPU가 아니라 네트워크이고, 스레드를 늘려도 얻을 것이 적습니다.

수많은 클라이언트 연결은 1장에서 본 I/O 멀티플렉싱, 즉 epoll로 "준비된 소켓만" 골라 처리하는 이벤트 루프로 한 스레드가 감당합니다. 스레드가 하나라 락도, 컨텍스트 스위칭도 없습니다.

명령 하나는 늘 원자적이다

명령이 한 줄로 차례차례 실행되므로 명령 하나가 도는 중에 다른 명령이 끼어들 수 없습니다. 뒤의 쿠폰 차감이 이 성질에 기댑니다. Redis 6.0부터는 네트워크 읽기와 쓰기만 I/O 스레드로 나눌 수 있습니다.

느린 명령 하나가 전체를 멈춘다

KEYS *나 거대한 컬렉션 전체 조회가 도는 동안 다른 모든 요청이 섭니다. 운영에서는 SCAN으로 조금씩 나눠 읽습니다.

Redis 값은 여러 모양의 자료구조다

String은 가장 기본인 값 하나입니다. 직렬화한 상품 정보를 담는 캐시, 그리고 INCR로 원자적으로 1씩 올리는 카운터로 씁니다.

Hash는 키 하나 아래 필드-값 쌍을 여러 개 담습니다. 세션처럼 필드 몇 개만 바꾸는 객체에 맞고, Spring Session도 세션을 Hash로 저장합니다.

List는 양 끝에 넣고 빼는 순서 있는 목록입니다. "최근 본 상품 20개"나, 한쪽에서 넣고 다른 쪽에서 꺼내는 간단한 작업 큐가 됩니다. BRPOP은 비어 있으면 값이 들어올 때까지 기다리며 꺼냅니다.

Set은 중복 없는 집합입니다. "이 쿠폰을 이미 받은 사용자"를 담아 두면 SISMEMBER 한 번으로 중복 참여를 막습니다.

Sorted Set은 원소마다 점수를 붙여 점수 순으로 정렬해 두는 집합입니다. 판매량 랭킹이나 대기열 순번에 씁니다. 3장 표에서 이 구조가 Skip List 위에 있다고 했는데, Skip List는 정렬된 연결 리스트에 몇 칸씩 건너뛰는 상위 층을 얹어 삽입과 조회를 모두 O(log N)에 하는 구조입니다.

Stream은 끝에 덧붙이기만 하는 로그로, 여러 소비자가 나눠 읽는 기능이 있어 작은 메시지 큐로 쓸 수 있습니다. 같은 개념을 뒤의 Kafka에서 자세히 봅니다.

메모리 저장소도 디스크에 남길 수 있다

메모리에만 있으면 Redis를 재시작하는 순간 데이터가 모두 사라집니다. 캐시라면 다시 채우면 되지만 세션이 날아가면 모든 사용자가 로그아웃됩니다. 그래서 Redis는 두 가지 영속화 방식을 제공합니다.

RDB는 특정 시점의 메모리 전체를 파일 하나로 떠 두는 스냅샷입니다. 이때 Redis는 fork, 즉 자기 프로세스를 그대로 복제해 자식 프로세스를 만드는 시스템 콜(9장에서 자세히)을 씁니다. 자식이 파일을 쓰는 동안 부모는 계속 요청을 받습니다.

fork 직후 부모와 자식은 같은 메모리 페이지를 함께 보다가, 부모가 어떤 페이지를 고치는 순간에만 그 페이지를 복사합니다. 이를 쓰기 시 복사라고 합니다. 덕분에 fork가 빠르지만, 쓰기가 많은 동안 스냅샷을 뜨면 복사된 페이지만큼 메모리가 일시적으로 늘어납니다. 메모리의 절반 가까이를 여유로 두라는 운영 조언이 여기서 나옵니다.

AOF는 쓰기 명령을 받을 때마다 로그 파일 끝에 덧붙이고, 재시작하면 처음부터 다시 실행합니다. 파일을 디스크에 확실히 내려쓰는 주기(appendfsync)를 고를 수 있는데, 기본값 everysec는 1초마다 내려써 최대 약 1초치를 잃을 수 있습니다. 파일이 계속 커지므로 주기적으로 현재 상태만 남기는 rewrite를 합니다.

RDB는 빨리 살고, AOF는 덜 잃는다

순수 캐시라면 영속화를 끄고 재시작 후 다시 채웁니다. 세션처럼 잃으면 곤란한 데이터라면 AOF를 켜고, 백업용으로 RDB를 함께 쓰는 경우가 많습니다. 하지만 영속화는 재시작을 견디는 장치일 뿐, 서버가 통째로 죽는 상황은 따로 대비해야 합니다.

Redis가 죽으면: 복제, Sentinel, Cluster

세션과 캐시를 모두 Redis에 올리면 이번에는 Redis가 SPOF가 됩니다. 첫 단계는 4장의 DB처럼 복제입니다. Primary가 받은 쓰기를 하나 이상의 Replica에 비동기로 보내 같은 데이터를 유지합니다.

Primary가 죽었을 때 Replica를 새 Primary로 올리는 일을 자동화한 것이 Sentinel입니다. 여러 Sentinel 프로세스가 Primary를 감시하다가, 과반이 "죽었다"고 동의하면 Replica 하나를 승격하고 클라이언트에게 새 주소를 알려 줍니다.

데이터가 서버 한 대 메모리에 다 안 들어가면 Redis Cluster로 나눕니다. 키 공간을 16384개의 해시 슬롯으로 나누고, 키의 해시값으로 슬롯을, 슬롯으로 담당 노드를 정합니다. 노드마다 Replica를 두어 장애도 견딥니다.

주의할 점은 복제가 비동기라는 것입니다. Primary가 쓰기를 받고 응답한 직후, Replica에 전달하기 전에 죽으면 그 쓰기는 승격된 새 Primary에 없습니다. 캐시라면 상관없지만, 락이나 쿠폰 수량처럼 정확해야 하는 값은 장애 전환 순간에 사라질 수 있습니다. 이 사실이 뒤의 분산 락 이야기에서 다시 등장합니다.

메모리가 차면 무엇을 버릴지 정해 둔다

캐시는 넣기만 하면 언젠가 메모리가 찹니다. Redis는 maxmemory로 쓸 메모리 상한을 정하는데, 64비트 환경의 기본값은 0, 즉 상한 없음입니다. 상한 없이 두면 OS 메모리를 다 쓰고 프로세스가 죽을 수 있으므로 운영에서는 반드시 정합니다.

상한에 닿았을 때의 행동은 maxmemory-policy가 정합니다. 기본값 noeviction은 아무것도 지우지 않고 새 쓰기에 오류를 냅니다. 세션 저장소처럼 데이터를 임의로 지우면 안 되는 용도에는 이것이 맞지만, 캐시 용도라면 쓰기 오류가 곧 장애입니다.

캐시 용도라면 allkeys-lru를 씁니다. 1장에서 본 LRU, 즉 가장 오래 안 쓴 것부터 버리는 정책입니다. 다만 Redis는 정확한 LRU를 위해 모든 키를 줄 세우지 않고, 키 몇 개(기본 5개)를 무작위로 뽑아 그중 가장 오래된 것을 버리는 근사 방식을 씁니다. 메모리와 CPU를 아끼는 대신 아주 정확하지는 않습니다.

TTL이 걸린 키만 지우는 volatile-lru도 있습니다. 세션과 캐시를 한 Redis에 섞어 두었다면 세션까지 지워질 수 있으니, 용도별로 Redis를 나누는 편이 안전합니다.

CDN은 정적 파일을 사용자 곁에 둔다

Redis가 DB 앞의 캐시라면, 이미지와 JS, CSS 같은 정적 파일은 앱 서버 앞에서도 캐시할 수 있습니다. CDN은 세계 곳곳에 둔 엣지 서버에 파일을 복사해 두고 가장 가까운 엣지가 응답하게 하는 네트워크입니다. 원본을 가진 서버는 오리진이라고 부릅니다.

  1. 사용자 요청상품 이미지, JS, CSS
  2. 가까운 엣지캐시에 있으면 즉시 응답
  3. 오리진미스일 때만 원본 서버로
  4. 엣지에 저장Cache-Control 기준 TTL

물리적 거리가 줄어 2장에서 본 RTT가 짧아지고, 오리진은 같은 파일을 반복해 보내지 않아도 됩니다. 엣지가 얼마나 보관할지는 오리진이 응답에 붙이는 Cache-Control 헤더로 정합니다. max-age=86400이면 "하루 동안 다시 묻지 말고 써도 된다"는 뜻이며, 세부 설정은 16장에서 봅니다.

파일이 바뀌면 이름을 바꾼다

CDN의 어려움도 결국 무효화입니다. 배포로 app.js를 고쳤는데 엣지마다 옛 파일이 하루짜리 TTL로 남아 있으면, 사용자마다 다른 버전을 받습니다. 모든 엣지에 "이 파일 지워라"는 무효화 요청을 보낼 수 있지만 전파에 시간이 걸리고 비용이 들기도 합니다.

그래서 정적 파일은 내용의 해시를 이름에 붙여(app.3f9a.js) 내용이 바뀌면 URL 자체가 바뀌게 만듭니다. 새 HTML은 새 이름을 가리키므로 무효화가 필요 없고, 옛 파일은 아주 긴 TTL을 걸어도 안전합니다.

상품 목록 API 같은 동적 응답은 사용자마다 다르거나 자주 바뀌어 보통 CDN에 오래 두지 않습니다. AWS의 CDN인 CloudFront는 16장에서 다룹니다. 이제 읽기는 충분히 덜어 냈으니, 다음은 쓰기가 한 곳에 몰리는 문제입니다.

선착순 쿠폰 100장에 1만 명이 몰리면

  1. 요청 A 조회

    남은 수량 1을 읽습니다.

  2. 요청 B 조회

    A가 쓰기 전에 B도 남은 수량 1을 읽습니다.

  3. A 발급

    1 - 1 = 0으로 갱신하고 쿠폰을 발급합니다.

  4. B 발급

    B도 1 - 1 = 0으로 갱신하고 또 발급합니다. 101장째입니다.

쇼핑몰이 정오에 선착순 쿠폰 100장을 연다고 합시다. 정오 직후 1초에 1만 명이 버튼을 누릅니다. 발급 코드가 "남은 수량을 읽고, 0보다 크면, 1 줄여 쓴다"라면 왼쪽처럼 두 요청이 같은 값을 읽고 둘 다 발급합니다.

"읽고, 판단하고, 쓰는" 단계 사이에 다른 요청이 끼어드는 경쟁 상태입니다. 1장에서 스레드 둘이 같은 변수를 고칠 때 본 임계 구역 문제가 서버 여러 대 규모로 다시 나타난 것입니다.

서버가 여러 대면 synchronized는 막지 못한다

한 JVM 안이라면 5장의 synchronized로 발급 메서드를 감싸 한 번에 한 스레드만 들어가게 할 수 있습니다. 하지만 그 락은 JVM 프로세스 메모리 안에만 있습니다. 1부에서 서버를 세 대로 늘렸으니 각 서버는 자기 락만 보고, 서로 다른 서버의 요청은 동시에 임계 구역에 들어갑니다.

서버 여러 대의 요청을 한 줄로 세우려면 모든 서버가 함께 보는 심판이 필요합니다. 쓸 수 있는 심판은 네 가지입니다.

첫째, DB가 행 락으로 한 번에 하나씩만 고치게 합니다. 둘째, Redis의 원자 연산으로 확인과 차감을 끼어들 수 없는 한 동작으로 만듭니다. 셋째, Redis 등에 분산 락, 즉 여러 서버가 공유하는 락을 두고 이를 잡은 서버만 발급 코드를 실행합니다. 넷째, 요청을 큐에 넣고 처리기 하나가 순서대로 꺼내 처리합니다.

네 방법은 정확성, 처리량, 구현 복잡도가 서로 다릅니다. 가장 익숙한 DB부터 차례로 보고, 마지막에 표로 비교합니다.

선택지 1: DB가 직접 순서를 지키게 한다

-- 조건부 UPDATE: 확인과 차감을 한 문장으로
UPDATE coupon_stock
   SET remaining = remaining - 1
 WHERE coupon_id = 42 AND remaining > 0;
-- 영향받은 행이 0이면 소진

-- 비관적 락: 읽는 순간부터 잠금
SELECT remaining FROM coupon_stock
 WHERE coupon_id = 42 FOR UPDATE;

가장 단순하고 정확한 방법은 확인과 차감을 UPDATE 한 문장으로 묶는 것입니다. 4장에서 봤듯 UPDATE는 대상 행에 배타 락을 걸므로 두 요청이 동시에 와도 하나씩 실행되고, remaining > 0 조건은 락을 잡은 뒤의 최신 값으로 평가됩니다. 영향받은 행 수가 0이면 품절입니다.

읽은 값으로 여러 판단을 해야 하면 아래처럼 FOR UPDATE로 읽는 순간부터 잠그는 비관적 락을 씁니다.

같은 행 하나에 모두가 줄을 서면 느려진다

DB 방식은 정확하지만 처리량에 한계가 있습니다. 1만 명의 요청이 모두 coupon_id = 42라는 같은 행 하나를 고치므로, 행 락을 하나씩 넘겨받으며 한 줄로 실행됩니다. 이처럼 쓰기가 한 행에 몰리는 것을 핫 로우라고 합니다.

트랜잭션 하나가 락을 쥐는 시간이 커밋까지 5ms라면, 그 행에서는 아무리 서버를 늘려도 초당 약 200건이 상한입니다. 1만 건이면 마지막 요청은 50초를 기다립니다. 그동안 기다리는 요청마다 4장의 커넥션 풀에서 연결을 하나씩 붙잡고 있으므로 풀이 바닥나고, 쿠폰과 상관없는 주문 조회까지 연결을 못 얻어 실패합니다.

4장의 낙관적 락, 즉 버전 번호를 비교해 충돌하면 다시 시도하는 방식은 여기서 더 나쁩니다. 1만 명이 동시에 같은 버전을 읽으면 한 명만 성공하고 9,999명이 재시도하며, 그 재시도가 다시 충돌합니다. 낙관적 락은 충돌이 드문 경우를 위한 방법입니다.

그래서 경쟁이 심한 수량 차감은 DB보다 훨씬 빠른 심판, 즉 메모리에서 명령을 한 줄로 처리하는 Redis로 옮깁니다.

선택지 2: Redis의 원자 연산에 맡긴다

local stock, users = KEYS[1], KEYS[2]
local uid = ARGV[1]
if redis.call('SISMEMBER', users, uid) == 1
then return -1 end               -- 이미 받음
local left = tonumber(redis.call('GET', stock))
if not left or left <= 0
then return 0 end                -- 소진
redis.call('DECR', stock)
redis.call('SADD', users, uid)
return 1

수량만 줄이면 된다면 DECR 하나로 충분합니다. 1을 빼고 새 값을 돌려주는 명령이라, 결과가 0 이상이면 당첨입니다. 하지만 "이미 받은 사람인가"까지 함께 확인해야 하면 명령 여러 개를 묶어야 합니다.

Redis는 작은 스크립트 언어인 Lua를 내장하고 있어, EVAL로 보낸 스크립트를 명령 하나처럼 끝까지 끼어듦 없이 실행합니다. 위 스크립트는 중복 확인, 수량 확인, 차감, 참여자 기록을 한 번에 처리합니다.

Redis에서 판정하고, 기록은 DB에 옮긴다

Lua 스크립트는 메모리에서 마이크로초 단위로 끝나므로 단일 Redis로도 초당 수만 건을 판정합니다. 핫 로우 문제가 사라집니다. 하지만 이것으로 끝이 아닙니다.

Redis는 "누가 당첨됐는가"를 판정했을 뿐, 쿠폰 발급 기록의 진짜 원본은 여전히 DB에 있어야 합니다. 사용자가 결제할 때 쿠폰을 확인하는 것은 DB이기 때문입니다. 당첨 직후 DB에 INSERT하면 다시 DB가 1만 건을 받으니, 당첨 기록을 뒤에서 볼 메시지 큐에 넣고 DB가 감당할 속도로 천천히 저장합니다.

두 저장소에 나눠 담으면 어긋날 수 있습니다. 앞에서 본 대로 Redis 복제는 비동기라 장애 전환 순간 마지막 차감이 사라질 수 있고, 그러면 101번째 쿠폰이 나갑니다. 그래서 DB의 발급 테이블에 (event_id, user_id) 유니크 제약을 걸어 중복을 막고, 이벤트가 끝나면 Redis 수량과 DB 발급 건수를 대조합니다.

Redis 원자 연산은 "숫자 하나를 줄인다"처럼 한 저장소 안에서 끝나는 일에 강합니다. 외부 결제 API 호출처럼 Redis 밖의 여러 단계를 통째로 한 서버만 실행하게 하려면 다른 도구가 필요합니다.

선택지 3: 분산 락으로 구간 전체를 잠근다

-- 획득: 키가 없을 때만, 3초 뒤 자동 만료
SET lock:coupon:42 <uuid> NX PX 3000

-- 해제: 값이 내 uuid일 때만 지운다 (Lua)
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

분산 락은 여러 서버가 함께 보는 곳에 둔 락입니다. Redis에서는 SET 한 줄로 잡습니다. NX는 키가 없을 때만 저장하라는 옵션이라, 동시에 여러 서버가 시도해도 한 서버만 성공합니다. PX 3000은 3000ms 뒤 자동으로 지워지라는 뜻입니다.

만료 시간은 락을 쥔 서버가 죽었을 때 영원히 잠기는 것을 막습니다. 값에 넣은 uuid는 해제할 때 "내가 잡은 락인지" 확인해, 내 락이 만료된 뒤 남이 잡은 락을 지우는 실수를 막습니다. 확인과 삭제 사이에 끼어들지 못하게 해제도 Lua로 합니다.

Redisson은 기다림과 연장을 대신 해 준다

RLock lock = redisson.getLock("lock:coupon:42");
// 최대 1초 기다려 보고, 못 잡으면 포기
if (lock.tryLock(1, TimeUnit.SECONDS)) {
  try {
    issue();          // 여러 단계의 발급 작업
  } finally {
    lock.unlock();    // 반드시 해제
  }
} else {
  throw new TooBusyException();
}

직접 짠 락은 "못 잡았으면 어떻게 기다리나"를 해결해야 합니다. 계속 SET NX를 반복하면 Redis에 헛된 요청이 쏟아집니다. Java 클라이언트 Redisson은 Redis의 Pub/Sub(채널을 구독한 클라이언트에게 메시지를 보내는 기능)으로 "락이 풀렸다"는 알림을 받아 그때만 다시 시도합니다.

작업이 만료 시간보다 길어지는 문제는 watchdog이 맡습니다. 만료 시간을 직접 주지 않으면 기본 30초 락을 잡고, 작업이 살아 있는 동안 주기적으로 연장합니다.

락이 만료됐는데 주인이 모르면 어떻게 되나

분산 락의 만료 시간은 양날의 검입니다. 서버가 죽었을 때 락을 풀어 주지만, 서버가 죽지 않고 잠깐 멈췄을 때도 락을 풀어 버립니다.

5장에서 본 GC의 Stop-The-World를 떠올려 봅시다. 락을 쥔 서버 1이 발급 작업 도중 GC로 수 초간 멈춥니다. 그사이 락이 만료되고, 서버 2가 락을 잡아 발급을 진행합니다. 이제 서버 1이 깨어나는데, 자기는 여전히 락을 쥐고 있다고 믿고 남은 쓰기를 이어 합니다. 두 서버가 동시에 임계 구역 안에 있게 됩니다. 네트워크 지연이나 VM 일시 정지도 같은 일을 일으킵니다.

Redis 장애 전환도 같은 결과를 냅니다. 락을 잡은 직후 Primary가 죽고 그 쓰기가 Replica에 전달되지 않았다면, 새 Primary에는 락이 없으니 다른 서버가 또 잡습니다.

Redis 개발자는 여러 독립 Redis 노드의 과반에서 락을 잡는 Redlock 알고리즘을 제안했지만, 분산 시스템 연구자 Martin Kleppmann은 프로세스 정지와 시계 오차 앞에서는 이것도 안전을 보장하지 못한다고 반박했습니다. 그가 제시한 해법은 락 쪽이 아니라 데이터를 받는 저장소 쪽에서 막는 것입니다.

펜싱 토큰은 늦게 온 쓰기를 저장소가 거부한다

선택지 4: 요청을 큐에 넣고 줄 세운다

마지막 방법은 경쟁 자체를 없애는 것입니다. 발급 요청을 받으면 바로 처리하지 않고 큐에 넣은 뒤 "접수됨"만 응답합니다. 큐 뒤에서는 처리기 하나가 요청을 하나씩 꺼내 발급합니다. 처리기가 하나뿐이니 동시에 같은 수량을 고치는 일이 애초에 없습니다.

대가는 응답이 비동기가 된다는 점입니다. 사용자는 "당첨"을 바로 받지 못하고 잠시 뒤 결과를 확인하거나 알림을 받습니다. 처리기 하나의 속도가 전체 처리량이 되므로, 결과를 즉시 보여 줘야 하는 화면에는 맞지 않습니다.

비슷한 발상으로 사용자를 서비스 앞에서 줄 세우는 대기열이 있습니다. 콘서트 예매에서 "앞에 3,512명"이 뜨는 화면입니다. Redis Sorted Set에 사용자를 도착 시각을 점수로 넣고(ZADD), 순번은 ZRANK로 알려 주며, 앞에서부터 정해진 수만큼씩 실제 서비스에 들여보냅니다. 서비스가 감당할 만큼만 받으니 뒤의 모든 구성 요소가 보호됩니다.

네 가지 선택지를 모두 봤으니, 이제 나란히 놓고 언제 무엇을 고를지 정리합니다.

네 방법은 정확성과 처리량을 맞바꾼다

방법정확성처리량잘 맞는 경우
DB 조건부 UPDATE, 락트랜잭션으로 보장핫 로우에서 낮음경쟁이 크지 않은 재고
Redis 원자 연산, Lua명령 단위 보장매우 높음수량 차감, 선착순 판정
분산 락만료, 장애 시 허점락 대기만큼 낮음여러 단계를 묶어야 할 때
큐로 직렬화한 처리기가 순서대로비동기, 응답 지연즉시 결과가 필요 없는 발급

실무에서는 조합합니다. 쇼핑몰 쿠폰이라면 Redis Lua로 당첨만 빠르게 판정하고, 당첨 기록은 큐에 넣어 DB 저장을 천천히 처리하며, DB 유니크 제약을 최종 방어선으로 둡니다. 이 조합의 가운데 있는 큐가 무엇이고 어떻게 동작하는지가 다음 주제입니다.

주문 API가 모든 일을 직접 하면 생기는 일

쿠폰뿐 아니라 주문에도 같은 문제가 있습니다. 지금 쇼핑몰의 주문 API는 주문을 저장한 뒤 결제 확인, 포인트 적립, 알림 발송, 판매 통계 갱신을 차례로 직접 호출하고 나서야 응답합니다.

첫째, 응답이 느립니다. 각각 50ms, 100ms, 300ms가 걸리면 사용자는 모두를 더한 시간만큼 기다리고, 그중 가장 느린 알림 발송 때문에 주문 버튼이 무거워집니다. 둘째, 약한 고리가 전체를 끊습니다. 알림 서버가 죽으면 주문까지 실패합니다. 알림은 조금 늦어도 되는데 말입니다. 셋째, 트래픽이 출렁입니다. 이벤트 시작 순간 주문이 평소의 50배로 들어오면 뒤의 모든 서비스가 같은 순간 50배를 받습니다.

세 문제 모두 "당장 응답에 필요하지 않은 일까지 지금 바로 한다"는 데서 옵니다. 해법은 할 일을 어딘가에 적어 두고 응답부터 하는 것입니다. 그 "어딘가"가 메시지 큐입니다.

메시지 큐는 보내는 쪽과 받는 쪽을 떼어 놓는다

  1. 주문 API메시지를 넣고 바로 응답
  2. 메시지 큐디스크에 보관, 순서 유지
  3. 컨슈머들각자 속도로 꺼내 처리

메시지를 넣는 쪽을 프로듀서, 꺼내 처리하는 쪽을 컨슈머, 그 사이에서 메시지를 보관하고 전달하는 서버를 브로커라고 합니다. 주문 API는 "주문 42 생성됨" 메시지를 넣고 바로 응답합니다.

이렇게 하면 세 가지를 얻습니다. 비동기화로 응답이 빨라지고, 디커플링(결합 끊기)으로 받는 쪽이 죽거나 늘어나도 보내는 쪽은 모르며, 버퍼링으로 순간 트래픽을 큐에 쌓았다가 받는 쪽이 감당할 속도로 소화합니다.

한 명이 받느냐, 모두가 받느냐

메시지를 누가 받는지에 따라 두 가지 모델이 있습니다. 점대점 모델은 메시지 하나를 컨슈머 하나만 처리합니다. 이미지 리사이즈 작업 1,000건을 워커 10대가 나눠 처리할 때처럼, 일을 나눠 맡기는 작업 큐입니다.

발행-구독 모델은 메시지 하나를 관심 있는 구독자 모두가 각자 받습니다. "주문 생성됨" 이벤트 하나를 결제, 포인트, 알림, 통계 서비스가 각자 받아 자기 일을 합니다. 보내는 쪽은 누가 구독하는지 몰라도 되므로, 나중에 "추천 서비스"가 추가되어도 주문 API 코드는 그대로입니다.

실제 시스템은 두 모델을 섞습니다. 서비스 단위로는 모두가 받고(발행-구독), 같은 서비스의 여러 서버 사이에서는 나눠 받습니다(점대점). 포인트 서비스 서버가 세 대라면 같은 이벤트를 세 번 적립하면 안 되니까요.

이 두 모델을 대표하는 제품이 Kafka와 RabbitMQ입니다. 둘은 설계 철학이 꽤 다르므로, 각자의 구조를 먼저 보고 비교합니다.

Kafka는 파티션 단위로 쪼개고 줄 세운다

Kafka에서 메시지는 주제별 통로인 토픽에 쓰고, 토픽은 여러 파티션으로 나뉩니다. 파티션은 끝에 덧붙이기만 하는 로그이고, 메시지마다 파티션 안 위치 번호인 오프셋이 붙습니다.

프로듀서는 메시지 키(예: 주문 ID)의 해시로 파티션을 고릅니다. 같은 키는 늘 같은 파티션으로 가므로 순서는 파티션 안에서만 보장됩니다.

컨슈머 그룹과 오프셋 커밋이 진도를 기억한다

Kafka는 앞의 두 모델을 컨슈머 그룹 하나로 구현합니다. 그룹마다 토픽 전체를 따로 받으니 그룹 사이는 발행-구독이고, 그룹 안에서는 파티션 하나를 컨슈머 하나에만 배정하니 점대점입니다. 결제 서비스와 포인트 서비스는 각자의 그룹으로 같은 주문 이벤트를 모두 받습니다.

그룹 안에서 파티션 하나는 컨슈머 하나만 읽으므로 파티션 수가 곧 병렬 처리의 상한입니다. 파티션이 4개인데 컨슈머를 6대로 늘리면 2대는 놉니다. 처리량을 늘리려면 파티션부터 늘려야 하는데, 파티션을 늘리면 키와 파티션의 대응이 바뀌어 순서 보장이 잠시 깨지므로 처음에 넉넉히 잡습니다.

컨슈머는 "이 파티션은 오프셋 57까지 처리했다"를 Kafka에 기록합니다. 이를 오프셋 커밋이라 하고, 컨슈머가 재시작하거나 다른 컨슈머가 파티션을 넘겨받으면 커밋된 위치 다음부터 읽습니다. 메시지는 읽어도 지워지지 않고 보존 기간(기본 7일) 동안 남으므로, 오프셋을 되돌려 과거부터 다시 처리할 수도 있습니다.

컨슈머가 추가되거나 죽으면 그룹은 파티션 배정을 다시 나누는 리밸런싱을 합니다. 그동안 해당 파티션의 소비가 잠시 멈추므로, 배포 때 리밸런싱이 잦으면 처리 지연이 생깁니다.

RabbitMQ는 교환기가 우편함으로 분류한다

RabbitMQ는 우체국에 가깝습니다. 프로듀서는 큐에 직접 넣지 않고 익스체인지(교환기)에 메시지를 보냅니다. 익스체인지는 미리 등록된 바인딩 규칙, 예를 들어 "라우팅 키가 order.*이면 알림 큐로"에 따라 메시지를 하나 이상의 큐에 분류해 넣습니다. 그래서 메시지별로 유연하게 보낼 곳을 정할 수 있습니다.

큐에 쌓인 메시지는 브로커가 연결된 컨슈머에게 밀어 줍니다(push). 컨슈머는 처리를 마치면 ack를 보내고, 브로커는 ack를 받은 메시지를 큐에서 지웁니다. ack 없이 연결이 끊기면 그 메시지는 다른 컨슈머에게 다시 갑니다.

한 컨슈머에게 ack 없이 몇 개까지 미리 보낼지는 prefetch 값으로 정합니다. 너무 크면 한 컨슈머가 메시지를 쌓아 두고 다른 컨슈머는 놀고, 너무 작으면 왕복이 잦아 느려집니다.

Kafka와 가장 큰 차이는 처리한 메시지가 남느냐입니다. Kafka는 로그로 남겨 여러 그룹이 각자 읽고 되돌려 읽을 수 있고, RabbitMQ는 ack된 메시지를 지우는 대신 메시지 하나하나의 라우팅, 재시도, 우선순위를 세밀하게 다룹니다.

Kafka는 로그, RabbitMQ는 우체국에 가깝다

항목KafkaRabbitMQ

읽은 메시지보존 기간 동안 남음, 재처리 가능ack 받으면 큐에서 삭제

실패 메시지컨슈머 쪽에서 별도 토픽으로 구현Dead Letter Exchange 내장

"주문 생성됨"처럼 같은 이벤트를 여러 서비스가 각자 읽거나 과거부터 다시 읽어야 하면 Kafka, 작업을 워커들에게 나눠 주고 메시지별 재시도와 우선순위를 다뤄야 하면 RabbitMQ가 자연스럽습니다. 어느 쪽이든 피할 수 없는 질문이 하나 남습니다. 메시지는 정확히 한 번 도착하는가?

응답을 못 받으면 다시 보내고, 그래서 중복된다

7장에서 결제 요청의 응답을 잃어버린 클라이언트가 재시도해 결제가 두 번 되는 문제를 봤습니다. 메시지에서도 똑같은 일이 일어납니다. 네트워크는 "보냈는데 응답이 안 오는" 상황을 늘 만들고, 보낸 쪽은 메시지가 안 갔는지 응답만 사라졌는지 구분할 수 없습니다.

컨슈머 쪽에서 보면 이렇습니다. 포인트 컨슈머가 메시지를 받아 포인트를 적립하고, 오프셋을 커밋하기 직전에 서버가 죽습니다. 재시작한 컨슈머는 마지막 커밋 위치부터 다시 읽으므로 같은 메시지를 또 받고, 포인트가 두 번 쌓입니다.

순서를 바꿔 처리 전에 커밋하면 중복은 사라지지만, 커밋 직후 처리 도중 죽으면 그 메시지는 영영 처리되지 않습니다. 결국 유실을 피하면 중복이 생기고, 중복을 피하면 유실이 생깁니다. 메시지 시스템이 내세우는 "전달 보장" 수준은 이 둘 중 무엇을 택했는지를 말합니다.

전달 보장은 오프셋을 언제 커밋하느냐다

보장커밋 시점실패하면
at-most-once처리하기 전에 커밋처리 중 죽으면 그 메시지는 유실
at-least-once처리한 뒤에 커밋커밋 전 죽으면 다시 받아 중복 처리
exactly-once처리 결과와 커밋을 한 트랜잭션으로Kafka 내부끼리만 보장, 외부 DB는 별개

최대 한 번(at-most-once), 최소 한 번(at-least-once), 정확히 한 번(exactly-once)입니다. Kafka의 exactly-once는 Kafka에서 읽어 Kafka에 쓰는 구간 안에서만 성립하고, 3.0부터 기본으로 켜진 프로듀서 중복 방지(idempotent producer)도 브로커에 쓰는 구간만 지킵니다. 포인트 DB 같은 외부 시스템까지는 보장되지 않으므로 실무 기본값은 at-least-once + 중복을 견디는 컨슈머입니다.

같은 메시지를 두 번 받아도 결과는 한 번

@Transactional
void handle(OrderCreated e) {
  int n = jdbc.update(
    "INSERT IGNORE INTO processed_message"
    + " (message_id) VALUES (?)", e.id());
  if (n == 0) return;   // 이미 처리한 메시지
  pointService.add(e.userId(), e.point());
}
// message_id 열은 기본 키(PK)

2장에서 정의한 멱등성, 즉 여러 번 해도 결과가 한 번과 같은 성질을 컨슈머에 주는 것이 멱등 컨슈머입니다. 메시지마다 고유 ID를 두고, 처리한 ID를 기록하는 테이블을 둡니다.

ID 기록과 포인트 적립이 한 트랜잭션이라 함께 성공하거나 함께 실패합니다. 두 번째로 온 메시지는 기본 키 중복이라 INSERT가 0건이 되어 건너뜁니다. 7장 Idempotency-Key 저장과 같은 원리입니다.

독이 든 메시지는 DLQ로 비켜 세운다

멱등이면 재시도해도 안전하니 실패하면 다시 시도하면 됩니다. 그런데 필드가 빠져 파싱조차 안 되는 메시지는 몇 번을 재시도해도 실패합니다. 이런 메시지를 독 메시지라고 합니다.

Kafka처럼 파티션을 순서대로 읽는 구조에서는 독 메시지 하나를 넘기지 못하면 그 뒤 메시지 전부가 멈춥니다. 그래서 정해진 횟수만큼 실패한 메시지는 별도 보관 장소로 옮기고 다음으로 넘어갑니다.

재시도 상한 뒤에는 DLQ로

처리에 실패한 메시지를 모아 두는 큐를 DLQ라고 합니다. Kafka는 별도 토픽으로, RabbitMQ는 Dead Letter Exchange로 구현합니다.

DLQ는 버리는 곳이 아니다

DLQ에 메시지가 쌓이면 알람이 울리게 하고, 원인을 고친 뒤 원래 큐에 다시 넣습니다. 아무도 보지 않는 DLQ는 조용한 데이터 유실입니다.

3부

나누면 빨라지지만, 실패도 나뉘어 퍼진다

2부까지는 서비스 하나를 빠르게 만들었습니다. 쇼핑몰 팀이 커지면 주문, 재고, 결제를 별도 서비스로 나누게 되고, 그러면 트랜잭션도 나뉘고 한 서비스의 장애가 네트워크를 타고 번집니다. 이 부에서는 정합성을 맞추는 법, 장애를 가두는 법, 받을 만큼만 받는 법을 보고, 마지막에 설계 문제 하나를 처음부터 풉니다.

원리 실무 설계 판단, 설정 수치, 장애 전파 사례와 용량 추정을 다룹니다.

모놀리식에서 MSA로: 무엇을 나누는가

지금까지의 쇼핑몰은 주문, 상품, 회원, 결제 코드가 하나의 애플리케이션으로 빌드되고 함께 배포됩니다. 이런 구조를 모놀리식이라고 합니다. 기능끼리는 메서드 호출로 부르고, DB 하나에서 트랜잭션 하나로 묶을 수 있어 단순합니다.

개발자가 50명이 넘으면 문제가 달라집니다. 결제 팀의 작은 수정도 전체를 다시 빌드하고 배포해야 하고, 한 팀의 버그가 배포 전체를 막습니다. 상품 조회만 트래픽이 많아도 애플리케이션 전체를 통째로 늘려야 합니다.

MSA(마이크로서비스 아키텍처)는 업무 영역별로 작은 서비스를 따로 만들고, 각자 배포하고, 각자 DB를 갖게 하는 구조입니다. 주문 서비스와 재고 서비스는 HTTP나 7장의 gRPC 같은 네트워크 호출, 또는 2부의 메시지로 대화합니다.

이렇게 보면 MSA는 기술 선택이라기보다 팀과 배포를 나누는 선택입니다. 대가로 메서드 호출이 네트워크 호출이 되어 느려지고 실패할 수 있게 되며, DB가 나뉘어 JOIN과 트랜잭션을 서비스 경계 너머로 할 수 없습니다.

MSA는 조직이 커졌을 때의 해법이다

항목모놀리식MSA
배포전체를 한 번에서비스별 독립 배포
확장전체를 통째로 복제부하가 큰 서비스만 확장
호출메서드 호출, 실패 거의 없음네트워크 호출, 지연과 실패
데이터DB 하나, 트랜잭션 하나서비스별 DB, 분산 트랜잭션
운영 부담낮음추적, 모니터링, 배포 자동화 필수

팀이 작으면 패키지 경계를 잘 나눈 모듈형 모놀리식이 대개 더 낫습니다. 팀이 커져 배포가 서로를 막기 시작할 때 경계가 분명한 영역부터 떼어 냅니다. 떼어 내는 순간 가장 먼저 부딪히는 것이 표의 넷째 줄, 트랜잭션입니다.

서비스가 나뉘면 트랜잭션도 나뉜다

모놀리식 쇼핑몰의 주문은 4장의 트랜잭션 하나였습니다. 주문 행 저장, 재고 차감, 결제 기록이 모두 성공하거나 모두 취소됩니다.

이제 주문 서비스, 재고 서비스, 결제 서비스가 각자 DB를 갖습니다. 주문을 저장하고 재고를 줄였는데 결제가 실패하면, 이미 커밋된 주문과 재고 차감을 누가 되돌릴까요? 각 DB의 트랜잭션은 자기 DB 안에서만 원자적이라 서비스 셋을 하나로 묶어 주는 장치가 없습니다.

이 문제에는 두 갈래의 답이 있습니다. 여러 DB를 정말 하나의 트랜잭션처럼 묶는 2PC, 그리고 묶기를 포기하고 실패하면 되돌리는 Saga입니다.

2PC는 모두가 동의할 때까지 붙잡는다

코디네이터주문 DB, 재고 DB
1단계 PREPARE 커밋할 수 있나요?
YES 준비 완료, 락 유지 락 보유
여기서 코디네이터가 죽으면 참여자는 무한 대기
2단계 COMMIT 모두 커밋
ACK 락 해제

2PC(2단계 커밋)는 진행을 맡는 코디네이터가 참여 DB들에게 먼저 "커밋할 수 있나"를 묻고, 모두 YES면 커밋을, 하나라도 NO면 롤백을 지시합니다. YES라고 답한 참여자는 결정이 올 때까지 락을 쥔 채 기다립니다.

그래서 가장 느린 참여자만큼 모두가 묶이고, 코디네이터가 SPOF가 됩니다. 메시지 브로커나 외부 결제 API처럼 2PC를 지원하지 않는 참여자도 많아 MSA에서는 잘 쓰지 않습니다.

Saga는 로컬 트랜잭션을 잇고 실패하면 되돌린다

  1. T1 주문 생성

    주문 서비스가 주문을 PENDING 상태로 저장합니다.

  2. T2 재고 차감

    재고 서비스가 자기 DB에서 수량을 줄입니다.

  3. T3 결제 실패

    결제 서비스가 카드 한도 초과로 실패를 알립니다.

  4. C2 재고 복구

    T2를 되돌리는 보상 트랜잭션을 실행합니다.

  5. C1 주문 취소

    주문 상태를 CANCELLED로 바꿉니다.

Saga는 큰 트랜잭션을 서비스별 로컬 트랜잭션의 연쇄로 나눕니다. 각 단계는 자기 DB에서 바로 커밋하고, 중간에 실패하면 이미 끝난 단계를 거꾸로 되돌리는 보상 트랜잭션을 실행합니다.

DB의 롤백과 달리 보상은 "없던 일로" 만들지 않고 "반대 동작을 하나 더" 합니다. 원자성을 포기하고 4장의 최종 일관성, 즉 결국에는 맞춰진다는 약속을 택한 것입니다.

Saga의 흐름은 이벤트로 잇거나 지휘자가 잡는다

다음 단계를 누가 부르느냐로 두 방식이 나뉩니다. 코레오그래피는 각 서비스가 앞 단계의 이벤트("재고 차감됨")를 구독하다가 자기 일을 하고 다음 이벤트를 냅니다. 오케스트레이션은 오케스트레이터라는 별도 구성 요소가 "재고 줄여", "결제해"를 순서대로 지시하고 실패하면 보상도 지시합니다.

방식흐름 제어장점단점
코레오그래피각 서비스가 이벤트를 듣고 다음 단계 실행중앙 없음, 결합도 낮음전체 흐름이 코드에 흩어짐
오케스트레이션오케스트레이터가 순서대로 명령흐름과 보상이 한곳에 보임오케스트레이터에 로직 집중

단계가 서너 개를 넘고 분기가 생기면 코레오그래피는 "누가 무엇을 듣는지" 추적하기 어려워지므로 오케스트레이션이 흔히 선택됩니다.

Saga에는 격리가 없다

Saga는 각 단계가 바로 커밋되므로 중간 상태가 다른 요청에 그대로 보입니다. 4장 ACID의 I, 즉 격리성이 없는 것입니다. 앞 예에서 T2로 재고가 줄었다가 C2로 복구되기 전 사이에, 다른 고객은 "품절"을 보고 돌아갈 수 있습니다.

실무에서는 이 틈을 상태로 드러내 다룹니다. 주문을 바로 "완료"로 두지 않고 PENDING으로 시작해, 모든 단계가 끝나야 CONFIRMED로 바꿉니다. 화면과 다른 서비스는 PENDING 주문을 "처리 중"으로 다룹니다.

보상 트랜잭션은 반드시 성공해야 합니다. 재고 복구가 실패한 채 끝나면 재고가 영원히 줄어든 채 남습니다. 그래서 보상은 재시도할 수 있어야 하고, 재시도해도 두 번 복구되지 않도록 앞에서 본 멱등 컨슈머처럼 만들어야 합니다.

되돌릴 수 없는 단계도 있습니다. 이미 발송한 알림 문자는 취소할 수 없습니다. 그래서 이런 단계는 실패할 수 있는 단계들이 모두 끝난 뒤 맨 마지막에 둡니다. 그런데 Saga의 단계들을 이벤트로 잇는다면, "DB 저장"과 "이벤트 발행"은 어떻게 함께 보장할까요?

DB 저장과 메시지 발행은 함께 실패하지 않는다

주문 서비스의 코드가 "주문을 DB에 저장하고, 커밋하고, Kafka에 주문 생성 이벤트를 발행한다"라고 합시다. 이렇게 서로 다른 두 시스템에 각각 쓰는 것을 이중 쓰기라고 하며, 두 곳에 걸친 트랜잭션이 없으므로 둘 중 하나만 성공할 수 있습니다.

커밋 후 발행 전에 서버가 죽으면 주문은 있는데 이벤트가 없습니다. 재고도 결제도 그 주문을 모르니 Saga가 시작조차 안 됩니다. 순서를 바꿔 발행 후 커밋하면, 발행은 됐는데 커밋이 실패해 존재하지 않는 주문의 이벤트가 나갑니다.

발행을 트랜잭션 안에 넣어도 해결되지 않습니다. 메시지는 이미 브로커로 나갔는데 그 뒤 DB 커밋이 실패하면 되돌릴 방법이 없습니다.

핵심 발상은 두 시스템에 쓰지 말고 한 시스템, 즉 DB에만 쓰는 것입니다. 이벤트도 DB에 같이 적어 두고, 발행은 나중에 별도로 합니다.

Transactional Outbox: 이벤트를 같은 DB에 적어 둔다

이벤트 중심으로 보면 읽기와 쓰기도 나눌 수 있다

지금까지 서비스들은 "주문 생성됨", "결제 완료됨" 같은 이벤트를 주고받으며 협력했습니다. 이처럼 서비스가 서로를 직접 부르지 않고 일어난 사실(이벤트)을 발행하고 구독하며 움직이는 구조를 이벤트 기반 아키텍처(EDA)라고 합니다. 새 기능은 이벤트를 구독하기만 하면 되므로 기존 서비스를 고치지 않고 붙일 수 있습니다.

이벤트가 흐르면 읽기 전용 모델을 따로 만들 수도 있습니다. CQRS는 데이터를 바꾸는 쪽(명령)과 읽는 쪽(조회)의 모델을 분리합니다. 주문 서비스는 정규화된 테이블에 쓰고, "마이페이지 주문 목록"은 이벤트를 받아 화면에 맞게 미리 합쳐 둔 별도 테이블이나 검색 엔진에서 읽습니다. 서비스마다 DB가 나뉘어 JOIN할 수 없는 문제를 이렇게 풉니다.

한발 더 나아가 이벤트 소싱은 현재 상태 대신 상태를 바꾼 이벤트 전체를 원본으로 저장하고, 현재 상태는 이벤트를 차례로 적용해 계산합니다. 감사 기록이 완벽히 남지만 구현과 운영이 복잡해 금융 원장 같은 영역에서 주로 씁니다.

세 가지 모두 읽기 모델이 이벤트를 받기 전까지는 잠시 낡아 있다는 최종 일관성을 받아들이는 대가가 있습니다.

느린 서비스 하나가 전체를 멈춘다

실패보다 느림이 더 위험한 이유

PG가 아예 죽었다면 연결 거부가 즉시 돌아오고, 결제 서비스는 "결제 실패"를 바로 응답합니다. 사용자는 불편하지만 스레드는 바로 풀려납니다. 문제는 응답이 느리게 올 때입니다.

동시에 처리 중인 요청 수는 "초당 요청 수 × 요청 하나의 처리 시간"입니다. 이를 리틀의 법칙이라고 합니다. 6장에서 본 Tomcat의 기본 스레드 200개로 계산해 봅시다. 결제 호출이 평소처럼 0.2초 걸리면 초당 1,000건이 와도 동시 처리 수는 200, 겨우 감당합니다.

PG가 30초 걸리기 시작하면, 초당 7건만 와도 7 × 30 = 210으로 스레드 200개를 넘습니다. 1장에서 본 대로 스레드 풀이 차면 새 요청은 큐에서 기다리다 실패하고, 결제와 무관한 상품 조회까지 스레드를 못 얻습니다. 느린 의존 대상 하나가 처리 가능한 요청 수를 100분의 1 아래로 떨어뜨립니다.

그래서 장애 격리의 목표는 실패를 없애는 것이 아니라, 실패를 빨리 확정해 자원을 돌려받고 그 영향을 한 구역에 가두는 것입니다. 첫 번째 도구는 기다림에 상한을 두는 타임아웃입니다.

타임아웃은 모든 원격 호출에 건다

타임아웃은 "이 시간 안에 답이 없으면 실패로 본다"는 상한입니다. 많은 HTTP 클라이언트와 드라이버의 기본값은 무한대이거나 매우 길어서, 설정하지 않으면 느린 의존 대상에 스레드가 무기한 묶입니다.

타임아웃은 두 가지를 따로 겁니다. 연결 타임아웃은 2장의 TCP 연결 수립까지 기다리는 시간으로, 보통 1초 안팎이면 충분합니다. 읽기 타임아웃은 연결 뒤 응답을 기다리는 시간으로, 1부에서 정의한 대상 API의 p99 응답 시간보다 조금 길게 잡습니다. 평소 99%가 끝나는 시간보다 오래 걸리면 이상 상황으로 보는 것입니다.

호출이 여러 단계로 이어지면 바깥 타임아웃이 안쪽보다 길어야 합니다. 주문 서비스가 2초 만에 포기했는데 결제 서비스가 PG를 5초 기다리면, 결제 서비스는 아무도 기다리지 않는 일을 계속하며 자원을 씁니다.

재시도는 일시적 실패에만, 멱등한 요청에만

타임아웃으로 끊긴 호출 중에는 잠깐의 네트워크 끊김이나 서버 재시작처럼 다시 하면 성공할 실패가 많습니다. 그래서 몇 번 다시 시도합니다. 단, 아무 실패나 재시도하면 안 됩니다.

재시도할 것은 연결 실패, 타임아웃, 503처럼 일시적인 실패입니다. 400이나 404는 몇 번을 다시 보내도 결과가 같습니다. 그리고 요청이 멱등해야 합니다. 타임아웃이 났다고 결제가 안 된 것은 아닙니다. 응답만 늦었을 수 있습니다. 7장의 Idempotency-Key를 붙인 결제 요청만 안전하게 재시도할 수 있습니다.

재시도는 부하를 곱합니다. 주문 → 결제 → PG 세 단계가 각자 3번씩 재시도하면, 사용자 요청 하나가 PG에 최대 3 × 3 × 3 = 27번 도착합니다. 이를 재시도 증폭이라고 하며, 그래서 재시도는 한 계층(보통 가장 바깥이나 가장 안쪽)에서만 합니다.

마지막 문제는 타이밍입니다. PG가 잠깐 쓰러졌다 일어나는 순간, 실패했던 수천 클라이언트가 모두 정확히 1초 뒤에 재시도하면 회복 중인 PG를 다시 쓰러뜨립니다. 재시도 간격을 어떻게 잡을지가 다음 코드의 주제입니다.

재시도에는 지수 백오프와 지터를 섞는다

long base = 100, cap = 10_000;   // ms
for (int i = 0; i < 5; i++) {
  try {
    return call();
  } catch (RetryableException e) {
    long exp = Math.min(cap, base << i);
    sleep(rnd.nextLong(exp + 1));  // 0~exp
  }
}
throw new GiveUpException();

시도할 때마다 대기 상한을 100, 200, 400, 800ms로 두 배씩 늘리는 것이 지수 백오프입니다. base << i가 2i배를 계산하고, cap이 10초를 넘지 않게 막습니다.

강조한 줄이 핵심입니다. 상한까지를 그대로 기다리지 않고 0부터 상한 사이의 무작위 시간, 즉 지터를 기다립니다. 1장의 라이브락 해법과 같은 원리로, 클라이언트마다 재시도 시각이 흩어져 PG에 한꺼번에 몰리지 않습니다. 5번 실패하면 포기합니다.

서킷 브레이커는 실패할 호출을 미리 끊는다

PG가 몇 분째 장애라면 매번 타임아웃까지 기다렸다 재시도하는 것은 양쪽 모두에 손해입니다. 서킷 브레이커는 집의 누전 차단기처럼, 최근 호출의 실패율이 임계치를 넘으면 회로를 열어 호출 없이 즉시 실패를 돌려줍니다.

정해진 시간이 지나면 반열림으로 바꿔 몇 건만 시험 삼아 보내 보고, 성공하면 닫고 실패하면 다시 엽니다. 열린 동안 호출이 오지 않으니 PG는 회복할 시간을 벌고, 우리 스레드는 즉시 풀려납니다.

실패율은 최근 호출 창에서 계산한다

"최근 호출의 실패율"을 셀 범위를 슬라이딩 윈도라고 합니다. 최근 N건을 보는 개수 기반과 최근 N초를 보는 시간 기반이 있습니다. Java에서 흔히 쓰는 라이브러리 Resilience4j의 기본값은 최근 100건을 보고, 실패율이 50% 이상이면 엽니다.

호출이 적을 때 판단을 미루는 장치도 있습니다. 최소 호출 수(기본 100건)가 쌓이기 전에는 실패율을 계산하지 않습니다. 새벽에 호출 2건 중 1건이 실패했다고 50%로 보고 회로를 여는 것을 막기 위해서입니다.

열린 뒤에는 기본 60초를 기다린 뒤 반열림으로 가고, 반열림에서는 시험 호출 10건을 허용해 그 결과로 다시 닫을지 열지 정합니다. 오류뿐 아니라 일정 시간보다 오래 걸린 호출을 "느린 호출"로 세어 그 비율로 여는 설정도 있습니다. 앞에서 본 대로 느림이 더 위험하므로 실무에서는 이 설정을 함께 씁니다.

서킷 브레이커는 의존 대상마다 따로 둡니다. PG용 브레이커가 열려도 배송 조회 API용 브레이커는 닫힌 채로 있어야 하기 때문입니다. 같은 생각을 스레드에 적용한 것이 다음의 벌크헤드입니다.

벌크헤드는 자원을 칸막이로 나눈다

배는 선체 안을 여러 칸의 벌크헤드(격벽)로 나눠, 한 칸에 물이 들어와도 다른 칸은 멀쩡하게 둡니다. 서버에서도 같은 일을 합니다. 앞의 계산에서 Tomcat 스레드 200개를 모든 외부 호출이 함께 쓰면, PG 하나가 느려져 200개 전부가 묶였습니다.

그래서 의존 대상마다 쓸 수 있는 자원을 따로 정합니다. PG 호출은 동시에 최대 20개, 추천 서비스 호출은 10개처럼 상한을 두면, PG가 느려져도 그 20개만 막히고 나머지 180개 스레드는 상품 조회와 주문 조회를 계속 처리합니다. 구현은 의존 대상별 스레드 풀을 따로 두거나, 동시 호출 수를 세는 세마포어(1장)로 합니다.

4장에서 커넥션 풀의 크기가 DB에 동시에 보낼 수 있는 일의 상한이 되어 DB를 지켰던 것처럼, 벌크헤드는 우리 서비스를 의존 대상으로부터 지키는 방어선입니다. 상한에 막힌 호출은 기다리지 않고 바로 실패합니다. 그렇다면 막히거나 실패한 호출에는 무엇을 돌려줘야 할까요?

폴백으로 기능을 낮춰서라도 응답한다

폴백은 호출이 실패했을 때 내보낼 대체 응답입니다. 추천 서비스가 실패하면 미리 캐시해 둔 인기 상품을, 실시간 재고 조회가 실패하면 "재고 확인 중"을 보여 줍니다. 상품 페이지 전체를 오류로 만드는 대신 일부 기능만 낮추는 것입니다.

폴백이 불가능한 기능도 있습니다. 결제는 대체 응답이 없으니 "잠시 후 다시 시도해 주세요"로 빨리 실패하는 것이 최선입니다. 지금까지 본 다섯 도구는 오른쪽 순서로 겹쳐 씁니다.

  1. 타임아웃

    느린 호출이 자원을 붙잡지 못하게 끊습니다.

  2. 재시도

    일시적 실패를 백오프와 지터로 흡수합니다.

  3. 서킷 브레이커

    지속적 실패는 호출 자체를 차단합니다.

  4. 벌크헤드

    한 의존 대상의 장애를 그 칸 안에 가둡니다.

  5. 폴백

    결국 실패하면 낮춘 기능으로라도 응답합니다.

처리율 제한은 받을 만큼만 받는 장치다

장애 격리 도구들은 우리가 남을 부를 때 우리를 지킵니다. 반대로 남이 우리를 부를 때 우리를 지키는 장치가 처리율 제한입니다. 정해진 시간 동안 받을 요청 수에 상한을 두고, 넘으면 처리하지 않고 거절합니다.

이유는 셋입니다. 첫째, 쿠폰 API를 초당 수백 번 두드리는 매크로나 크롤러로부터 서버를 지킵니다. 둘째, 한 사용자나 한 파트너사가 자원을 독차지하지 못하게 해 공정하게 나눕니다. 셋째, 외부 유료 API처럼 호출마다 돈이 드는 곳에서 비용 폭주를 막습니다.

제한은 무엇을 기준으로 셀지(사용자 ID, IP, API 키)와 어디서 셀지를 정해야 합니다. 보통 7장의 API Gateway처럼 모든 요청이 지나는 입구에서 공통으로 세고, 쿠폰 발급처럼 특별한 API는 애플리케이션에서 한 번 더 셉니다.

거절할 때는 7장에서 본 429 Too Many Requests와 Retry-After 헤더로 "언제 다시 오라"고 알려 줍니다. 그래야 클라이언트가 앞의 백오프처럼 기다렸다 다시 옵니다. 이제 "몇 건까지 받았는가"를 세는 알고리즘을 봅니다.

버킷 알고리즘은 토큰과 물로 속도를 다룬다

Token Bucket은 토큰이 담기는 양동이를 상상하면 됩니다. 양동이에는 정해진 속도로 토큰이 채워지고(예: 초당 5개), 최대 용량(예: 10개)을 넘으면 넘친 토큰은 버려집니다. 요청이 오면 토큰을 하나 꺼내고, 토큰이 없으면 거절합니다.

이 구조의 장점은 평균 속도를 지키면서 순간적인 몰림, 즉 버스트를 허용한다는 것입니다. 한동안 조용했던 사용자는 토큰이 10개 모여 있으니 페이지를 열 때 요청 10개를 한꺼번에 보내도 통과합니다. 그 뒤로는 초당 5개로 제한됩니다. 사람의 실제 사용 패턴과 잘 맞아 가장 널리 쓰입니다.

Leaky Bucket은 바닥에 구멍 난 양동이입니다. 요청은 양동이(큐)에 담기고, 구멍으로 일정한 속도로만 흘러나가 처리됩니다. 양동이가 차면 새 요청은 버려집니다.

Leaky Bucket은 입력이 출렁여도 출력이 늘 고르므로, 뒤의 시스템이 정확히 일정한 속도만 감당할 때 맞습니다. 대신 버스트를 흡수하지 못하고, 큐에서 기다린 만큼 응답이 늦어집니다.

윈도 알고리즘은 시간 칸마다 개수를 센다

더 직관적인 방법은 시간을 칸으로 나눠 세는 것입니다. Fixed Window는 "12:00:00~12:00:59 칸에 100건"처럼 고정된 칸마다 카운터를 두고, 칸이 바뀌면 0으로 돌립니다. 구현이 Redis INCR과 TTL 하나로 끝날 만큼 단순합니다.

문제는 칸 경계입니다. 분당 100건 제한에서 12:00:59에 100건, 12:01:00에 100건이 오면 둘 다 통과해 1초 사이에 200건이 들어옵니다. 제한의 두 배입니다.

Sliding Window Log는 요청 시각을 모두 기록해 두고, 새 요청이 오면 "지금부터 1분 전까지" 기록만 셉니다. 경계 문제가 없고 정확하지만, 요청마다 시각을 저장하니 메모리를 많이 씁니다.

Sliding Window Counter는 둘을 절충합니다. 이전 칸과 현재 칸의 카운터만 두고, 현재 칸이 30% 지났다면 "이전 칸 개수 × 70% + 현재 칸 개수"로 최근 1분을 추정합니다. 요청이 칸 안에 고르게 있었다고 가정한 근사지만, 카운터 두 개로 경계 문제를 대부분 없앱니다.

다섯 알고리즘을 버스트와 정확도로 비교한다

어느 알고리즘이든 서버가 여러 대일 때는 같은 문제가 생깁니다. 카운터를 어디에 두어야 하는가입니다.

Token Bucket을 여러 서버에서 함께 쓰려면

  1. 버킷 읽기

    Redis에서 남은 토큰 수와 마지막 갱신 시각을 읽습니다.

  2. 토큰 채우기

    지난 시간 × 충전 속도만큼 더하되 용량을 넘지 않게 합니다.

  3. 판정

    토큰이 1 이상이면 하나 빼고 통과, 아니면 거절합니다.

  4. 원자적으로

    세 단계를 Lua 스크립트 하나로 묶어 실행합니다.

서버마다 따로 세면 서버가 10대일 때 한도가 10배가 됩니다. 1부의 "서버 메모리 속 쿠폰 카운터"와 같은 실수입니다. 그래서 카운터를 Redis 같은 공용 저장소에 둡니다.

그런데 읽고, 계산하고, 쓰는 사이에 다른 서버가 끼어들면 2부의 쿠폰처럼 경쟁 상태가 됩니다. 해법도 같습니다. 세 단계를 Lua 스크립트 하나로 묶어 원자적으로 실행합니다. AWS의 구현은 16장(웹 방화벽인 WAF)과 17장(API Gateway)에서 봅니다.

% N으로 나누면 서버 하나 늘 때 대부분이 옮겨 간다

Redis 하나로 캐시가 모자라 캐시 서버 4대에 키를 나눠 담는다고 합시다. 가장 쉬운 방법은 hash(key) % 4로 서버 번호를 정하는 것입니다. 4장에서 샤드를 고를 때 본 방식과 같습니다.

트래픽이 늘어 5대로 늘리면 식이 % 5로 바뀝니다. 해시값이 0~19인 키 20개로 세어 보면 4로 나눈 나머지와 5로 나눈 나머지가 같은 키는 0, 1, 2, 3 넷뿐입니다. 키의 80%가 다른 서버로 옮겨 갑니다.

캐시라면 옮겨 간 키는 새 서버에서 모두 미스이므로, 서버를 늘린 순간 캐시가 거의 다 빈 것과 같고 앞에서 본 캐시 눈사태가 DB로 쏟아집니다. 4장이 이 리샤딩 비용을 줄이는 방법을 이 장으로 미뤄 두었습니다.

일관성 해싱은 바뀐 구간의 키만 옮긴다

일관성 해싱은 해시값의 범위를 원(해시 링)으로 이어 붙이고, 서버와 키를 같은 해시 함수로 이 원 위에 놓습니다. 키는 자기 위치에서 시계 방향으로 처음 만나는 서버에 저장합니다.

서버 D를 추가하면 D 바로 앞 구간의 키만 D로 옮기고 나머지는 그대로입니다. 서버가 몇 개 없으면 구간 길이가 들쭉날쭉하니, 서버마다 원 위에 수백 개의 가상 노드를 흩어 놓아 고르게 나눕니다.

설계는 요구사항과 숫자에서 시작한다

이 장의 도구를 모두 모아, 쇼핑몰의 블랙프라이데이 선착순 쿠폰 이벤트를 처음부터 설계해 봅니다. 처음 보는 설계 문제는 늘 같은 순서로 풉니다. 요구사항 → 용량 추정 → API → 데이터 모델 → 확장과 장애 대비입니다. 순서를 지키는 이유는 앞 단계의 답이 뒤 단계의 선택지를 좁혀 주기 때문입니다.

기능 요구사항은 시스템이 해야 하는 일입니다. 정오에 10만 장의 쿠폰을 열고, 한 사람은 한 장만 받으며, 받은 쿠폰은 주문 때 쓸 수 있어야 합니다. 사용자는 당첨 여부를 몇 초 안에 알아야 합니다.

비기능 요구사항은 얼마나 잘 해야 하는가입니다. 10만 장을 넘겨 발급하면 안 되고(정확성), 이벤트 중에도 일반 주문과 상품 조회는 평소처럼 돌아야 하며(격리), 매크로가 쿠폰을 쓸어 가지 못해야 합니다(공정성).

이 중 가장 어려운 조건이 설계를 결정합니다. 여기서는 "정오 직후 몇 초에 몰리는 쓰기를, 정확하게, 다른 기능을 해치지 않고"입니다. 이제 "몰린다"를 숫자로 바꿉니다.

숫자는 어느 자원이 병목인지 가리킨다

용량 추정은 정확할 필요가 없습니다. 자릿수가 맞으면 어느 자원이 병목인지가 보입니다. 과거 이벤트 기록을 보니 참여자 100만 명 중 대부분이 처음 10초 안에 누르고, 새로고침으로 두세 번씩 다시 누릅니다.

초당 수십만 건은 핫 로우 DB(초당 수백 건)로는 불가능하고, 단일 Redis로도 빠듯합니다. 반대로 저장 용량은 작아 문제가 아닙니다. 병목은 오직 "순간 쓰기"입니다.

API와 데이터 모델은 중복을 막는 쪽으로

# 발급 요청: 접수만 하고 202로 응답
POST /events/7/coupons
Idempotency-Key: 9f1c...
# 결과 확인
GET  /events/7/coupons/me

CREATE TABLE coupon_issue (
  event_id   BIGINT,
  user_id    BIGINT,
  issued_at  DATETIME,
  PRIMARY KEY (event_id, user_id)
);

발급 API는 Redis 판정 결과만 알려 주고 실제 저장은 뒤로 미루므로, "요청은 받았고 처리는 나중에 한다"는 뜻의 상태 코드 202 Accepted로 응답합니다. 결과는 조회 API로 확인합니다. 새로고침으로 같은 요청이 반복되므로 7장의 Idempotency-Key를 받습니다.

테이블은 조인 없이 이벤트와 사용자로만 찾습니다. 강조한 기본 키가 "한 사람 한 장"을 DB 수준에서 보장하는 최종 방어선입니다. 메시지가 중복으로 와도 두 번째 INSERT는 실패합니다.

요청은 다섯 겹을 지나며 줄어든다

  1. CDN이벤트 페이지, 이미지
  2. 처리율 제한사용자당 초당 1건
  3. Redis Lua중복 확인, 수량 차감
  4. Kafka당첨 기록 버퍼링
  5. 컨슈머 → DB멱등 INSERT

정적인 이벤트 페이지와 이미지는 CDN이 받아 앱 서버까지 오지 않게 합니다. 발급 요청은 API Gateway의 처리율 제한(Token Bucket)이 사용자당 초당 1건으로 깎아 새로고침 폭주와 매크로를 거르고, 그래도 많으면 Sorted Set 대기열로 Redis가 감당할 만큼만 들여보냅니다.

Redis Lua 스크립트가 중복과 수량을 원자적으로 판정해 당첨자를 정확히 10만 명으로 자릅니다. 당첨 기록은 Kafka에 넣고 바로 202를 응답하며, 컨슈머가 초당 수천 건씩 DB에 멱등 INSERT합니다. 10만 건이면 1분 안쪽에 끝납니다. 각 겹이 뒤의 겹을 지키는 구조입니다.

정리

  • 스케일 아웃은 무상태 서버에서 시작합니다. 세션, 파일, 카운터를 공용 저장소로 옮겨야 아무 서버나 요청을 받을 수 있고, 늘어난 서버만큼 DB 연결 수가 곱해집니다.
  • 캐시는 적중률로 DB를, TTL과 삭제로 정합성을 지킵니다. 스탬피드, 관통, 눈사태는 "재계산은 한 명만", 빈 값 캐시, TTL 분산으로 막습니다.
  • 동시성은 원자성을 어디에 맡기느냐의 문제입니다. DB 한 문장, 싱글 스레드라 원자적인 Redis Lua, 분산 락과 펜싱 토큰, 큐를 정확성과 처리량으로 고릅니다.
  • 메시지는 at-least-once로 오고, 컨슈머가 멱등해야 합니다. 서비스를 넘는 정합성은 Saga와 Transactional Outbox로 최종 일관성을 맞춥니다.
  • 느림이 실패보다 위험합니다. 타임아웃, 백오프와 지터, 서킷 브레이커, 벌크헤드, 폴백으로 장애를 가두고 처리율 제한으로 받을 만큼만 받습니다.

스스로 점검 (1)

  1. Sticky Session만으로 세션 문제를 풀면 무엇이 남나요?

    서버 한 대가 죽거나 배포로 내려가면 그 서버의 세션이 모두 사라지고, 특정 서버에 사용자가 쏠립니다. 서버가 여전히 상태를 가지므로 마음대로 늘리고 줄일 수 없습니다.

  2. 앱 서버 20대, 풀 크기 10이면 DB 쪽에서 무엇을 확인해야 하나요?

    최대 연결이 200개이므로 DB의 max_connections(MySQL 기본 151)를 넘지 않는지 확인해야 합니다. 서버를 늘릴 계획이 있다면 풀 크기를 줄이거나 한도를 함께 조정합니다.

  3. DB를 갱신한 뒤 캐시를 새 값으로 덮어쓰지 않고 지우는 이유는?

    동시에 두 쓰기가 일어나면 캐시 덮어쓰기 순서가 DB 반영 순서와 뒤바뀌어 낡은 값이 남을 수 있습니다. 삭제는 순서와 관계없이 다음 읽기가 최신 값을 채웁니다.

  4. 모든 캐시 키에 TTL 600초를 똑같이 주면 어떤 일이 생길 수 있나요?

    한꺼번에 채운 키들이 같은 순간 만료되어 DB로 요청이 몰리는 눈사태가 납니다. TTL에 무작위 값을 더해 만료 시각을 흩뜨립니다.

스스로 점검 (2)

  1. 캐시 용도의 Redis를 maxmemory-policy 기본값으로 두면 무엇이 문제인가요?

    기본값 noeviction은 메모리가 차면 새 쓰기에 오류를 내므로 캐시 채우기가 모두 실패합니다. 캐시 용도라면 allkeys-lru처럼 오래 안 쓴 키를 버리는 정책을 씁니다.

  2. 쿠폰 차감에 낙관적 락을 쓰면 1만 명이 몰릴 때 왜 나빠지나요?

    같은 버전을 읽은 요청 중 한 명만 성공하고 나머지가 모두 충돌해 재시도합니다. 재시도가 다시 충돌하며 DB 부하만 커지므로, 충돌이 잦은 곳에는 맞지 않습니다.

  3. Redis로 분산 락을 잡을 때 만료 시간과 고유 값이 각각 필요한 이유는?

    만료 시간이 없으면 락을 쥔 서버가 죽었을 때 영원히 잠깁니다. 고유 값이 없으면 내 락이 만료된 뒤 남이 잡은 락을 내가 지울 수 있습니다.

  4. 만료 시간과 고유 값이 있어도 분산 락이 뚫리는 경우는?

    락을 쥔 서버가 GC 정지로 멈춘 사이 락이 만료되면 두 서버가 동시에 작업합니다. 펜싱 토큰으로 저장소가 오래된 쓰기를 거부하게 해 막습니다.

스스로 점검 (3)

  1. 파티션이 4개인 토픽에 컨슈머 6개를 같은 그룹으로 붙이면?

    파티션 하나는 그룹 안에서 컨슈머 하나만 읽으므로 2개는 놉니다. 처리량을 늘리려면 파티션 수를 먼저 늘려야 합니다.

  2. 오프셋을 처리 후에 커밋하는 컨슈머가 포인트를 두 번 적립하는 경우는?

    적립 후 커밋 전에 죽으면 재시작 후 같은 메시지를 다시 받습니다. 메시지 ID를 적립과 같은 트랜잭션에 기록하는 멱등 컨슈머로 막습니다.

  3. 주문 저장 후 Kafka에 직접 발행하는 코드는 어디서 깨지나요?

    DB 커밋 후 발행 전에 서버가 죽으면 이벤트가 사라지고, 발행 후 커밋이 실패하면 없는 주문의 이벤트가 나갑니다. Outbox로 같은 트랜잭션에 묶어 해결합니다.

  4. 스레드 200개 서버가 2초 걸리는 외부 API를 부르면 초당 몇 건에서 막히나요?

    리틀의 법칙으로 동시 처리 수 = 초당 요청 × 2초이므로 초당 100건에서 200개가 모두 찹니다. 타임아웃과 벌크헤드로 그 호출이 쓸 스레드를 제한합니다.

스스로 점검 (4)

  1. 재시도 간격을 1초로 고정하면 장애 복구 때 무엇이 문제인가요?

    실패한 클라이언트들이 같은 박자로 동시에 재시도해 회복 중인 서버에 다시 폭주합니다. 지수 백오프와 지터로 시각을 흩뜨립니다.

  2. Fixed Window로 분당 100건을 제한할 때 최악의 경우 몇 건이 통과하나요?

    창의 경계 앞뒤 1초 사이에 이전 창 100건과 다음 창 100건, 최대 200건이 통과합니다. Sliding Window로 줄입니다.

  3. 캐시 서버를 % N 방식으로 나누다가 한 대를 늘리면 왜 위험한가요?

    N이 바뀌면서 키 대부분의 위치가 바뀌어 사실상 캐시 전체가 비고 DB로 몰립니다. 일관성 해싱은 새 서버 앞 구간의 키만 옮깁니다.
