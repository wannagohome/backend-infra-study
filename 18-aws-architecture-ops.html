1부

무엇을 기준으로 조립하는가

17장까지 Lambda, SQS, EventBridge를 포함한 AWS 부품을 하나씩 보았습니다. 이 장은 그 부품으로 서비스를 설계하고, 배포하고, 관측하고, 장애에 대응하고, 비용을 관리하는 운영의 한 바퀴를 돕니다. 먼저 좋은 설계의 기준부터 정합니다.

Well-Architected는 설계 점검표다

Well-Architected Framework는 AWS가 수많은 고객 아키텍처를 검토하며 정리한 설계 점검 틀입니다. 아키텍처를 여섯 개의 기둥으로 나누고, 기둥마다 "이것을 어떻게 하고 있습니까?"라는 질문과 모범 사례를 제공합니다.

정답을 주는 문서가 아니라 빠뜨린 관점을 찾아 주는 문서입니다. 콘솔의 Well-Architected Tool에 워크로드를 등록하고 질문에 답하면 위험 항목이 표시됩니다.

분야별 렌즈(서버리스, 컨테이너, SaaS 등)가 추가 질문을 붙입니다. 서버리스 API라면 Serverless Lens의 질문까지 함께 봅니다.

리뷰는 한 번이 아니라 주기적으로

아키텍처는 기능이 붙으며 바뀝니다. 큰 변경 전후나 분기마다 다시 답해 보는 것이 권장 방식입니다.

오른쪽으로 갈수록 AWS가 더 많이 맡는다

첫 번째 설계 결정은 코드를 어디서 돌릴지입니다. 오른쪽으로 갈수록 OS 패치와 서버 수 관리를 AWS가 대신하지만, 실행 시간과 환경에 대한 제어권은 줄어듭니다.

실행 시간, 상태, 운영 부담이 선택을 가른다

ECS와 EKS의 세부 비교는 14장, Lambda의 한도와 동시성은 17장에서 다뤘습니다. 여기서는 워크로드 전체를 놓고 어디에 올릴지 고르는 기준만 봅니다.

트래픽 모양이 바뀌면 답도 바뀐다

  1. OS나 하드웨어 제어가 필요한가

    커널 설정, GPU 드라이버, 라이선스가 걸리면 EC2입니다.

  2. 한 번의 실행이 15분 안에 끝나나

    넘거나 장기 연결을 붙잡는 서버라면 컨테이너입니다.

  3. 트래픽이 들쭉날쭉한가

    유휴 시간이 길면 Lambda가 쌉니다.

  4. 상시 고부하인가

    꾸준히 바쁘면 Fargate나 EC2가 단가에서 유리합니다.

  5. K8s 생태계가 꼭 필요한가

    아니라면 ECS가 운영 부담이 적습니다.

17장의 손익분기 계산(1GB·100ms 함수 대 Fargate 두 대)으로는 평균 초당 15건 남짓을 넘는 꾸준한 트래픽부터 컨테이너가 Lambda보다 쌉니다. 숫자와 계산 과정은 17장 "꾸준한 트래픽이면 컨테이너가 싸진다"에 있습니다.

반대로 하루 몇천 건의 웹훅을 위해 컨테이너를 24시간 켜 두는 것은 낭비입니다. 한 서비스 안에서도 상시 API는 Fargate, 비동기 후처리는 Lambda처럼 섞습니다.

2부

장애를 흡수하는 구조와 복구 전략

레퍼런스 아키텍처 네 가지를 보고, 각 부품이 어떤 장애를 어떻게 흡수하는지, 그리고 리전 전체가 사라질 때를 위한 DR까지 따라갑니다.

기초 원리 장애가 났을 때 각 부품 안에서 일어나는 일을 다룹니다.

고가용성은 계층마다 SPOF를 없애는 일이다

단일 장애점(SPOF)은 그것 하나가 멈추면 서비스 전체가 멈추는 부품입니다. 고가용성 설계는 요청이 지나는 경로를 따라가며 모든 계층에 SPOF가 없는지 확인하는 작업입니다.

AWS에서 기본 단위는 가용 영역(AZ)입니다. AZ는 전력과 네트워크가 독립된 데이터센터 묶음이라(12장), 같은 계층을 두 개 이상의 AZ에 나눠 두면 한 곳의 정전이 전체 장애로 번지지 않습니다.

  • 중복: 모든 계층을 두 개 이상의 AZ에 둡니다.
  • 감지: 헬스 체크가 죽은 부품을 자동으로 찾아냅니다.
  • 우회와 교체: 트래픽을 건강한 쪽으로 돌리고 죽은 부품을 새로 띄웁니다.
  • 무상태: 앱 서버가 상태를 갖지 않아야 아무 서버나 죽고 떠도 됩니다(8장).

레퍼런스 1: 고가용성 3-티어

  • 요청 흐름
  • 데이터 접근
  • 복제

각 부품은 서로 다른 장애를 흡수한다

구성 요소흡수하는 장애어떻게
Route 53엔드포인트·리전 장애헬스 체크 실패 시 보조 레코드로 응답
CloudFront트래픽 폭증, 원거리 지연엣지 캐시가 오리진 요청을 줄임
ALB앱 서버 한 대의 장애헬스 체크 실패 대상을 라우팅에서 뺌
Auto Scaling인스턴스 소멸, 부하 증가원하는 용량 유지, AZ 간 균형
RDS Multi-AZDB 인스턴스·AZ 장애대기로 장애 조치, DNS 전환

정적 파일을 S3와 CloudFront로 빼면 앱 서버는 상태 없는 계산만 맡아 언제 죽고 새로 떠도 괜찮아집니다. 세션은 ElastiCache에, 업로드 파일은 S3에 둡니다. 상태를 관리형 데이터 계층으로 몰아내는 것이 3-티어 고가용성의 핵심입니다.

레퍼런스 2: 서버리스는 AZ를 AWS가 맡는다

  1. CloudFront캐시, WAF 부착
  2. API Gateway인증, 스로틀링
  3. Lambda요청마다 실행
  4. DynamoDB여러 AZ에 자동 복제

API Gateway, Lambda, DynamoDB는 모두 리전 단위 서비스라 여러 AZ에 걸친 배치를 AWS가 알아서 합니다. 3-티어에서 직접 그리던 서브넷과 Auto Scaling 그룹이 사라지고, 사용자는 코드와 한도 설정만 관리합니다.

대신 장애의 모양이 바뀝니다. 서버가 죽는 대신 동시성 한도, 스로틀링, 다운스트림 폭주가 주된 장애가 됩니다. Lambda가 VPC 안의 RDS를 부른다면 커넥션 폭증을 막을 RDS Proxy가 필요합니다(17장).

레퍼런스 3: 이벤트 기반은 장애를 큐에 가둔다

주문 서비스는 "주문 생성됨" 이벤트를 EventBridge에 던지고 바로 응답합니다. 결제, 알림, 정산은 각자의 SQS 큐에서 이벤트를 꺼내 처리합니다.

알림 서비스가 30분 동안 죽어도 주문은 계속 받습니다. 이벤트는 큐에 쌓였다가 서비스가 살아나면 처리되고, 계속 실패하는 메시지는 DLQ로 격리합니다(17장). 대가는 결과적 일관성과 멱등 컨슈머입니다(8장).

레퍼런스 4: 정적 웹과 API를 한 도메인에

React 같은 SPA는 빌드하면 정적 파일 묶음입니다. 이것을 S3에 올리고 CloudFront 하나에 오리진 두 개를 붙여 경로 패턴으로 나눕니다(16장).

기본 동작은 S3로, /api/* 동작은 ALB나 API Gateway로 보냅니다. 같은 도메인이라 CORS가 필요 없고(7장), S3 버킷은 OAC로 CloudFront만 읽게 잠급니다. 정적 파일은 엣지 캐시가 응답해 오리진 부하가 거의 없습니다.

정적 안정성: 장애 중에 새로 만들 필요가 없게

AWS 서비스는 자원을 만들고 바꾸는 컨트롤 플레인과, 이미 있는 자원이 요청을 처리하는 데이터 플레인으로 나뉩니다. 데이터 플레인이 더 단순해서 더 안정적입니다.

정적 안정성은 장애가 나도 아무것도 새로 띄우지 않고 버티는 성질입니다. AZ 장애 순간에는 모두가 인스턴스를 새로 띄우려 해 컨트롤 플레인이 느려질 수 있기 때문입니다.

설계AZ 하나를 잃으면
2 AZ × 피크의 50%새로 띄울 때까지 과부하
2 AZ × 피크의 100%남은 AZ가 그대로 피크 처리
3 AZ × 피크의 50%남은 두 AZ 합이 100%

정적 안정성은 여유 용량을 미리 사 두는 대가로 얻습니다. 3 AZ가 2 AZ보다 싼 이유는 6부 용량 계획에서 계산합니다.

셀 기반 아키텍처는 폭발 반경을 자른다

Multi-AZ는 인프라 장애를 막지만, 잘못된 배포나 독이 든 요청 하나가 모든 서버를 동시에 쓰러뜨리는 것은 막지 못합니다. 모든 서버가 같은 코드와 같은 데이터를 공유하기 때문입니다.

셀 기반 아키텍처는 전체 스택을 작고 독립된 복제본(셀) 여러 개로 나누고, 얇은 라우팅 계층이 고객 ID 같은 키로 요청을 한 셀에 보냅니다. 한 셀이 망가져도 그 셀의 고객만 영향을 받습니다.

배포도 셀 하나에 먼저 넣고 지켜본 뒤 다음 셀로 넓힙니다. 셀이 10개면 최악의 배포 사고도 고객의 약 10%에서 멈춥니다.

언제 필요한가

셀 라우팅과 셀 간 데이터 이동이라는 복잡도가 붙습니다. 장애 반경이 사업에 치명적인 대규모 서비스에서 고려합니다.

가용 영역 하나가 꺼지면 일어나는 일

  1. AZ a 정전

    AZ a의 앱 서버와 RDS 기본 인스턴스가 멈춥니다.

  2. ALB 우회

    헬스 체크에 실패한 대상을 빼고 AZ b로만 보냅니다.

  3. RDS 장애 조치

    대기가 기본으로 승격되고 엔드포인트 DNS가 바뀝니다.

  4. 캐시 승격

    ElastiCache가 AZ b의 복제본을 기본으로 올립니다.

  5. 용량 회복

    Auto Scaling이 AZ b에 인스턴스를 더 띄웁니다.

이 시나리오는 AZ가 깨끗하게 죽은 경우입니다. 헬스 체크가 분명히 실패하니 모든 부품이 알아서 넘어갑니다. AZ a가 돌아오면 Auto Scaling이 다시 두 곳에 나눠 배치합니다.

이 구조가 막지 못하는 것

리전 전체 장애, 잘못된 배포, 실수로 지운 데이터, DB 과부하는 Multi-AZ로 막을 수 없습니다. 그래서 배포 전략, 관측성, DR이 따로 필요합니다.

반쯤 죽은 AZ는 사람이 빼 줘야 한다

현실의 AZ 장애는 깔끔하지 않은 경우가 많습니다. 패킷 일부만 유실되거나 지연만 늘어나는 회색 장애에서는 헬스 체크가 간신히 통과해 트래픽이 계속 아픈 AZ로 갑니다.

이때 쓰는 것이 ARC(Application Recovery Controller)의 zonal shift입니다. ALB, NLB 같은 지원 자원에서 특정 AZ로 가는 트래픽을 한 번에 빼고, 정한 시간이 지나면 자동으로 원래대로 돌아옵니다.

zonal autoshift를 켜 두면 AWS가 AZ 이상을 감지했을 때 대신 트래픽을 뺍니다. 그래서 켜기 전에 남은 AZ만으로 피크를 버틸 용량이 있는지가 전제 조건입니다(정적 안정성).

zonal shift에는 만료 시간이 있습니다

시작할 때 최대 3일(72시간)의 만료를 정해야 하고, 연장하거나 일찍 취소할 수 있습니다. 끝나면 트래픽이 그 AZ로 돌아옵니다.

인프라가 넘어가도 앱이 따라와야 끝난다

RDS Multi-AZ 장애 조치는 엔드포인트의 DNS 레코드를 새 기본 인스턴스로 바꿔서 끝납니다. 그런데 JVM이 DNS 결과를 오래 캐시하거나, 커넥션 풀(4장)에 끊긴 연결이 남아 있으면 앱은 몇 분째 옛 IP로 갑니다.

JVM DNS 캐시 TTL(networkaddress.cache.ttl)을 60초 이하로, 풀의 최대 수명을 짧게 두는 설정은 15장에서 코드로 봤습니다. 이 장의 관심은 그 설정이 실제 장애 때 동작하는지 확인하는 일입니다.

RDS Proxy(15장)는 장애 조치 동안 앱의 연결을 붙잡고 있다가 새 기본 인스턴스로 이어 주어, 앱이 보는 중단 시간을 줄입니다.

훈련 때 확인할 것

장애 조치 훈련은 "DB가 넘어갔나"가 아니라 "앱 에러율이 몇 초 만에 0으로 돌아왔나"로 판정합니다.

DR의 두 숫자: 잃어도 되는 데이터와 시간

Multi-AZ가 막지 못하는 리전 장애와 데이터 손상에는 재해 복구(DR)로 대비합니다. 목표는 두 숫자로 정합니다.

RPO(Recovery Point Objective)는 장애 시점에서 거꾸로 얼마만큼의 데이터를 잃어도 되는가, RTO(Recovery Time Objective)는 얼마 만에 서비스를 되살려야 하는가입니다.

Multi-AZ는 DR이 아닙니다. 실수로 실행한 DELETE나 랜섬웨어 암호화는 대기 인스턴스에도 그대로 복제됩니다.

DR 전략 넷: 평소에 무엇을 켜 두는가

전략평소 DR 리전의 상태RPO / RTO비용
Backup & Restore백업 복사본만 보관시간 단위가장 낮음
Pilot Light데이터는 상시 복제, 서버는 꺼 둠수십 분낮음
Warm Standby축소된 전체 스택이 상시 가동분 단위중간

아래로 갈수록 평소에 켜 두는 것이 많아지고, 그만큼 RPO와 RTO가 줄어듭니다. 서비스마다 요구가 다르므로 전부 멀티 사이트로 만들 필요는 없습니다. 결제는 Warm Standby, 사내 도구는 Backup & Restore처럼 나눕니다.

Backup & Restore는 복사본과 IaC다

가장 단순한 전략이지만 두 가지를 빠뜨리면 동작하지 않습니다. 첫째, 백업은 다른 리전, 가능하면 다른 계정에 복사해야 리전 장애와 계정 탈취에서 살아남습니다. AWS Backup의 백업 계획으로 RDS, EBS, DynamoDB, EFS 스냅숏을 교차 리전으로 복사합니다.

둘째, 데이터만 있고 인프라가 없으면 복구에 며칠이 걸립니다. VPC부터 앱까지 IaC(11장)로 정의해 두어야 DR 리전에 같은 환경을 빠르게 다시 만들 수 있습니다.

  1. 평소

    스냅숏을 DR 리전으로 주기적으로 복사합니다.

  2. 선언

    리전 장애를 판단하고 DR을 선언합니다.

  3. 인프라 생성

    IaC로 DR 리전에 스택을 만듭니다.

  4. 데이터 복원

    스냅숏을 복원합니다. 크기에 비례해 오래 걸립니다.

  5. 전환

    DNS를 DR 리전으로 돌립니다.

Pilot Light는 끄고 Warm은 작게 켠다

Pilot Light는 가스 보일러의 불씨처럼 핵심만 켜 둡니다. DB는 교차 리전 복제로 늘 최신이지만, 앱 서버는 0대이거나 AMI와 템플릿만 있습니다. 장애 때 서버를 띄우는 시간이 RTO가 됩니다.

Warm Standby는 작은 규모의 완전한 스택이 늘 돌아갑니다. 바로 트래픽을 받을 수 있고, 장애 때는 용량만 늘리면 됩니다. 평소에도 동작하므로 DR 환경이 썩지 않았는지 계속 검증됩니다.

둘 다 장애 때 Auto Scaling으로 용량을 키우는데, 이것은 컨트롤 플레인 작업입니다. 백서는 이 의존을 없애려면 DR 리전에 전체 용량을 미리 켜 두는 hot standby를 고르라고 설명합니다.

DR 리전의 서비스 할당량

DR 리전의 EC2 vCPU 같은 할당량이 낮으면 장애 당일에 용량을 늘리지 못합니다. 미리 올려 둡니다.

Active-Active의 진짜 문제는 쓰기다

두 리전이 모두 트래픽을 받으면 장애 조치라는 절차 자체가 사라집니다. 한 리전이 죽으면 그쪽 트래픽만 다른 리전으로 보내면 됩니다. 읽기는 가까운 리전에서 처리하면 되지만, 쓰기를 어디서 받을지가 설계의 핵심입니다.

4장의 CAP에서 봤듯, 리전 사이 지연을 감수하고 강한 일관성을 얻거나, 각자 쓰고 충돌을 나중에 해결하는 길 중 하나를 골라야 합니다.

쓰기 전략방식

Write local가까운 리전에 쓰고 충돌 해결
Write partitioned사용자별 홈 리전에만 쓰기
 Aurora Global Database는 write global, DynamoDB 글로벌 테이블은 write local에 맞습니다.

장애 조치 스위치는 데이터 플레인에 둔다

리전 장애 중에는 그 리전의 콘솔이나 API가 느리거나 안 될 수 있습니다. 그래서 DR 전환 절차는 장애가 난 리전에 의존하지 않아야 합니다.

백서는 Route 53 레코드 가중치를 바꾸는 방식이 컨트롤 플레인 작업이라 덜 탄력적이라고 지적합니다. 대신 ARC의 routing control은 Route 53 헬스 체크를 사람이 켜고 끄는 스위치로 만들어, 고가용성 데이터 플레인 API로 전환합니다.

훈련하지 않은 DR은 없는 것과 같다

복원해 본 적 없는 백업은 복원된다는 보장이 없습니다. 분기마다 실제로 DR 리전에 전환해 보고 걸린 시간을 RTO와 비교합니다.

자동이냐 수동이냐

리전 전체 전환은 오판 비용이 커서 사람이 결정하고, 실행은 스크립트 한 줄로 끝나게 만드는 것이 일반적입니다.

배포 전략을 AWS 도구로 구현하기

장애의 가장 흔한 원인은 인프라가 아니라 변경입니다. Rolling, Blue-Green, Canary의 개념은 11장에서 보았으니, 여기서는 그 전략을 AWS 서비스가 실제로 어떻게 실행하는지 따라갑니다.

같은 전략도 플랫폼마다 구현이 다르다

ECS는 예전에는 Blue-Green과 Canary를 CodeDeploy에 맡겨야 했지만, 지금은 서비스의 배포 전략으로 BLUE_GREEN, LINEAR, CANARY를 직접 고를 수 있습니다. CodeDeploy 방식도 계속 지원됩니다.

CodePipeline이 단계를 잇는다

  1. 소스GitHub 연결, 푸시 감지
  2. CodeBuild테스트, 이미지 빌드
  3. ECR이미지 저장(14장)
  4. 승인수동 승인 단계(선택)
  5. 배포ECS, CodeDeploy

CodePipeline은 단계와 산출물(artifact)을 이어 주는 오케스트레이터이고, 스스로 빌드하거나 배포하지 않습니다. CodeBuild는 요청마다 깨끗한 빌드 컨테이너를 띄워 buildspec.yml을 실행하고 끝나면 버립니다. CodeDeploy는 EC2, ECS, Lambda에 새 버전을 넣고 트래픽을 옮기며, 알람이 울리면 되돌립니다.

GitHub Actions(11장)로 빌드하고 배포 단계만 AWS 도구에 맡기는 조합도 흔합니다. 어느 쪽이든 배포 단계가 IAM 역할로 인증해야 장기 키가 남지 않습니다(12장).

buildspec은 빌드 컨테이너가 따를 대본이다

version: 0.2
phases:
  pre_build:
    commands:
      - aws ecr get-login-password | docker
          login -u AWS --password-stdin $REPO
  build:
    commands:
      - ./gradlew test bootJar
      - docker build -t $REPO:$TAG .
  post_build:
    commands:
      - docker push $REPO:$TAG
      - printf '[{"name":"app","imageUri":"%s"}]'
          $REPO:$TAG > imagedefinitions.json
artifacts: { files: [imagedefinitions.json] }

단계는 install, pre_build, build, post_build 순서로 실행됩니다. 테스트가 실패하면 그 자리에서 파이프라인이 멈춥니다.

강조한 줄이 다음 단계로 넘길 산출물입니다. ECS 배포 단계는 이 파일에서 컨테이너 이름과 새 이미지 주소를 읽어 Task Definition의 새 리비전을 만듭니다. 태그에는 커밋 해시를 써서 어떤 코드가 배포됐는지 추적합니다.

ECS Blue/Green은 리스너 규칙을 바꾼다

ALB 리스너에 대상 그룹 두 개를 준비합니다. 현재 버전(blue) 태스크는 한쪽에, 새 버전(green) 태스크는 다른 쪽에 등록됩니다.

green이 뜨면 먼저 테스트 리스너 규칙(특정 헤더를 단 요청 등)으로만 검증 트래픽을 보냅니다. 통과하면 프로덕션 규칙이 green을 가리키도록 한 번에 바꿉니다. blue는 bake time 동안 살려 두어, 문제가 생기면 규칙만 되돌려 즉시 롤백합니다.

Canary와 알람 롤백은 서비스 설정 몇 줄이다

{
  "strategy": "CANARY",
  "canaryConfiguration": {
    "canaryPercent": 10.0,
    "canaryBakeTimeInMinutes": 10
  },
  "bakeTimeInMinutes": 15,
  "alarms": {
    "alarmNames": ["api-5xx-rate"],
    "enable": true,
    "rollback": true
  }
}

새 버전에 트래픽 10%를 보내고 10분간 지켜본 뒤 나머지 90%를 옮깁니다. 기본값은 5%, 10분입니다. 전부 옮긴 뒤에도 15분 동안 옛 버전을 살려 둡니다.

그동안 지정한 CloudWatch 알람이 ALARM이 되면 ECS가 자동으로 되돌립니다. 각 단계에 Lambda 함수를 거는 수명 주기 훅으로 스모크 테스트를 넣을 수도 있습니다.

Rolling은 비율 둘과 서킷 브레이커로

ROLLING 전략은 태스크를 조금씩 바꿔 끼웁니다. minimumHealthyPercent와 maximumPercent 두 비율로 빠르기와 여유 용량을 맞바꾸는 계산은 14장에서 봤습니다.

운영에서 더 중요한 질문은 잘못된 버전을 누가 멈추느냐입니다. ECS가 스스로 멈추는 장치와, 사람이 정한 지표로 멈추는 장치가 따로 있습니다.

새 이미지가 기동하자마자 죽으면 ECS는 기본적으로 끝없이 다시 띄웁니다. 배포 서킷 브레이커(14장)를 켜면 실패가 임계값에 닿을 때 배포를 실패로 끝내고, rollback을 켜 두면 마지막 성공 리비전으로 되돌립니다.

서킷 브레이커는 "뜨는가"만 봅니다

태스크는 건강한데 응답이 틀리는 버그는 못 잡습니다. 에러율 알람을 함께 걸어야 합니다.

CodeDeploy는 이동 방식을 이름으로 고른다

Canary는 작은 비율로 오래 지켜보고 한 번에 넘기며, Linear는 같은 폭으로 꾸준히 늘립니다. 어느 쪽이든 배포 그룹에 CloudWatch 알람을 연결해 두어야 사람 없이 롤백됩니다.

ALB 가중치 대상 그룹으로 직접 Canary하기

{
  "Type": "forward",
  "ForwardConfig": {
    "TargetGroups": [
      { "TargetGroupArn": "…/blue",
        "Weight": 90 },
      { "TargetGroupArn": "…/green",
        "Weight": 10 }
    ],
    "TargetGroupStickinessConfig": {
      "Enabled": true,
      "DurationSeconds": 600 }
  }
}

forward 동작에 대상 그룹 여러 개와 0~999의 가중치를 주면 ALB가 비율대로 나눕니다. 90:10에서 50:50, 0:100으로 바꿔 가는 것이 Canary입니다.

대상 그룹 고정(stickiness)을 켜야 한 사용자가 요청마다 두 버전을 오가지 않습니다. 또 한쪽 그룹이 비거나 전부 unhealthy여도 ALB는 다른 그룹으로 자동으로 넘기지 않습니다.

Route 53 가중치는 환경 통째로 나눈다

같은 이름과 타입의 레코드를 여럿 만들고 각각 0~255의 가중치를 주면, Route 53이 가중치 합 대비 비율로 응답합니다. 1과 255면 1/256만 새 쪽으로 갑니다. 0이면 보내지 않습니다.

ALB 가중치가 대상 그룹 단위라면 Route 53 가중치는 로드 밸런서나 리전 같은 환경 통째를 나눕니다. 새 VPC나 새 클러스터로 이사할 때, DB 버전을 올린 새 스택으로 옮길 때 씁니다.

DNS는 즉시 바뀌지 않습니다

클라이언트와 리졸버가 TTL 동안 옛 응답을 캐시하고, JVM처럼 더 오래 쥐는 클라이언트도 있습니다. 전환 전에 TTL을 60초 정도로 낮춰 두고, 롤백도 TTL만큼 늦다는 점을 감안합니다.

Lambda는 별칭이 두 버전에 트래픽을 나눈다

$ aws lambda publish-version \
    --function-name order-api
{ "Version": "8", … }

# live 별칭: v7에 90%, v8에 10%
$ aws lambda update-alias \
    --function-name order-api --name live \
    --function-version 7 \
    --routing-config \
    '{"AdditionalVersionWeights":{"8":0.1}}'

API Gateway나 이벤트 소스는 함수 버전이 아니라 live 같은 별칭을 가리킵니다. 별칭은 주 버전 하나와 추가 버전 하나 사이에 가중치를 줄 수 있습니다. 두 버전 모두 게시된 버전이어야 하며 $LATEST는 쓸 수 없습니다.

실무에서는 이 비율을 손으로 바꾸지 않고, SAM이나 CodeDeploy가 LambdaCanary10Percent5Minutes 같은 구성으로 옮기며 알람 시 되돌립니다.

드레이닝 시간이 배포 시간의 바닥을 정한다

옛 태스크나 인스턴스를 내릴 때 ALB는 그 대상을 draining 상태로 두고 새 요청을 보내지 않으면서, 진행 중인 요청이 끝나기를 등록 취소 지연만큼 기다립니다. 기본값은 300초입니다.

요청이 대부분 1초 안에 끝나는 API라면 300초는 배포마다 5분씩 허비하는 셈입니다. 가장 긴 정상 요청보다 조금 길게, 예를 들어 30초로 줄입니다.

너무 짧으면 502가 납니다

지연이 끝났는데도 처리 중인 요청이 있으면 ALB는 502를 돌려줍니다. 긴 업로드나 보고서 생성 API가 있다면 따로 계산합니다.

앱 쪽 종료 처리는 10·11장

SIGTERM을 받은 앱이 새 요청을 거절하고 진행 중인 요청을 끝내는 Graceful Shutdown과 짝을 이뤄야 무중단이 됩니다.

4부

보이지 않으면 운영할 수 없다

구조가 장애를 흡수하고 배포가 안전해도, 지금 무슨 일이 일어나는지 볼 수 없으면 대응할 수 없습니다. CloudWatch의 메트릭, 로그, 알람과 분산 추적, 그리고 무엇을 지켜볼지 정하는 SLO까지 다룹니다.

원리 실무 CloudWatch 설정값, 쿼리, 알람 설계 수치를 다룹니다.

CloudWatch는 차원 조합마다 별개의 메트릭으로 저장합니다. 사용자 지정 메트릭은 차원을 가로질러 합산해 주지 않으므로, 서비스 전체 값이 필요하면 그 조합으로도 따로 보내야 합니다.

AWS 서비스 메트릭은 기본이 표준 해상도(1분)입니다. 사용자 지정 메트릭은 1초 단위의 고해상도로도 보낼 수 있지만 호출 비용이 늘어납니다.

EC2는 기본 모니터링이면 5분, 세부 모니터링을 켜면 1분 주기입니다. 5분 주기로는 2분짜리 장애가 한 점으로 뭉개지므로, 운영 서버는 세부 모니터링을 켜는 편이 낫습니다.

평균은 꼬리를 숨기고 백분위는 드러낸다

CloudWatch는 한 주기 안의 값들을 통계로 요약해 돌려줍니다. Average, Sum, Minimum, Maximum, SampleCount와 함께 p50, p99 같은 백분위를 고를 수 있습니다.

요청 99건이 50ms, 1건이 5초면 평균은 약 100ms로 멀쩡해 보입니다. 그 1%의 사용자가 겪는 고통은 p99에서만 보입니다. 지연 시간은 p50, p99를 함께, 개수는 Sum으로 봅니다.

메트릭 종류맞는 통계
지연 시간p50, p90, p99
요청 수, 에러 수Sum
CPU 사용률Average, Maximum
큐 적체Maximum

샘플이 적은 주기의 p99는 값 하나에 휘둘립니다. 새벽처럼 요청이 드문 시간대의 백분위 알람은 조심해서 겁니다.

그래서 인스턴스에 CloudWatch 에이전트를 설치해 CWAgent 네임스페이스로 보냅니다. 에이전트는 로그 파일 수집과 트레이스 수집도 맡을 수 있습니다. 컨테이너는 다음에 볼 Container Insights가 같은 역할을 합니다.

EMF는 로그 한 줄을 메트릭으로 바꾼다

사용자 지정 메트릭은 PutMetricData API로 직접 보낼 수 있지만, 요청 경로에서 API를 부르면 지연과 비용이 붙습니다.

EMF는 정해진 형식의 JSON 로그를 쓰면 CloudWatch Logs가 받아서 메트릭을 뽑아 줍니다. Lambda처럼 stdout이 곧 로그인 환경에서 특히 편하고, orderId 같은 상세 필드는 로그에 남아 나중에 검색할 수 있습니다.

차원에 사용자 ID를 넣으면 청구서가 터진다

차원 조합마다 별개 메트릭이고, 사용자 지정 메트릭은 메트릭 개수로 과금됩니다. 차원에 userId를 넣으면 사용자 10만 명이 메트릭 10만 개가 됩니다. 이렇게 값의 종류가 많은 것을 카디널리티가 높다고 합니다.

차원에는 API 이름, 상태 코드 계열, 리전처럼 값이 몇십 개 이하로 정해진 것만 넣습니다.

고카디널리티 값은 로그와 트레이스로

"이 사용자의 요청이 왜 느렸나"는 메트릭이 아니라 로그 검색과 트레이스가 답할 질문입니다. EMF로 쓰면 메트릭과 상세 필드를 한 줄에 함께 남길 수 있습니다.

로그 그룹이 보존 기간과 권한의 단위다

로그는 로그 스트림(인스턴스나 컨테이너 하나가 쓰는 순서 있는 기록)에 쌓이고, 스트림들은 로그 그룹으로 묶입니다. 보존 기간, 접근 권한, 암호화, 필터는 모두 로그 그룹 단위로 정합니다.

로그 그룹의 기본 보존 기간은 무기한입니다. 정하지 않으면 저장 비용이 매달 쌓입니다. 보존 기간이 지난 로그는 보통 72시간 안에 지워집니다.

로그 클래스특징
Standard모든 기능(메트릭 필터, 실시간 보기 등)
Essentials수집 단가가 낮고 기능은 일부
 Essentials는 예전 이름이 Infrequent Access입니다. 저장과 Logs Insights 요금은 같고 수집 요금만 다릅니다.

감사 목적으로 오래 둘 로그는 S3로 내보내고 S3 수명 주기로 더 싼 클래스에 넘기는 것이 일반적입니다(15장).

Logs Insights는 로그에 묻는 질의 언어다

fields @timestamp, path, status, latency
| filter status >= 500
| stats count(*) as errors,
        pct(latency, 99) as p99
  by path, bin(5m)
| sort errors desc
| limit 20

# 특정 요청의 전 구간 로그
filter traceId = "1-6f3a…"
| sort @timestamp asc

파이프(|)로 명령을 이어 붙입니다. 위 질의는 5분 구간마다 경로별 5xx 개수와 p99 지연을 셉니다. JSON 로그는 필드가 자동으로 인식되므로, 애초에 구조화된 JSON 로그를 남기는 것이 전제입니다.

과금은 스캔한 데이터양 기준입니다. 시간 범위와 로그 그룹을 좁혀서 질의합니다.

메트릭 필터는 세고, 구독 필터는 흘려보낸다

  1. 애플리케이션JSON 로그 출력
  2. 로그 그룹CloudWatch Logs
  3. 메트릭 필터패턴이 맞으면 +1
  4. 구독 필터실시간 전달

메트릭 필터는 들어오는 로그에서 패턴({ $.level = "ERROR" } 같은)을 찾아 메트릭 값으로 만듭니다. 코드를 고치지 않고 "ERROR 로그 수" 알람을 걸 수 있습니다. 필터를 만든 뒤에 들어온 로그만 셉니다.

구독 필터는 맞는 로그를 Kinesis Data Streams, Firehose, Lambda, OpenSearch로 보통 몇 분 안에 넘깁니다. 로그 그룹당 다섯 개까지 걸 수 있고, 보안 계정이나 외부 로그 분석 도구로 모을 때 씁니다.

알람은 N개 중 M개가 넘으면 울린다

알람은 기간마다 통계 하나를 계산해 임계값과 비교합니다. 평가 기간 수(N)는 최근 몇 개를 볼지, 경보 데이터 포인트 수(M)는 그중 몇 개가 넘어야 ALARM인지입니다. 넘은 점이 연속일 필요는 없습니다.

기간 1분, 5개 중 3개로 두면 한 번 튀는 값은 무시하고, 5분 안에 3분 이상 나쁘면 울립니다. 상태는 OK, ALARM, INSUFFICIENT_DATA 셋입니다.

데이터가 없을 때의 해석도 정해 둬야 한다

설정누락된 점을맞는 경우
missing(기본)평가 범위가 전부 비면 INSUFFICIENT_DATA일반적인 경우
notBreaching정상으로 간주에러가 날 때만 찍히는 메트릭
breaching위반으로 간주끊기면 그 자체가 장애인 하트비트
ignore현재 상태 유지간헐적으로 보고되는 메트릭

5xx 개수 메트릭은 에러가 없으면 아예 점이 찍히지 않습니다. 기본값으로 두면 평온한 시간에 INSUFFICIENT_DATA로 바뀌어 헷갈리므로 notBreaching이 맞습니다. 반대로 "배치가 매시간 성공 메트릭을 보낸다"는 알람은 점이 없는 것이 곧 실패이므로 breaching입니다.

고정 임계값이 안 맞으면 띠와 조합을 쓴다

ALARM("api-5xx-rate-high")
  AND ALARM("api-p99-latency-high")
  AND NOT ALARM("maintenance-window")

트래픽이 낮과 밤에 열 배씩 차이 나면 "요청 수 1,000 미만" 같은 고정값은 밤마다 울립니다. 이상 탐지 알람은 과거 데이터에서 시간대와 요일 패턴을 학습해 기대 범위를 띠로 만들고, 그 띠를 벗어날 때 울립니다.

복합 알람은 다른 알람들의 상태를 AND, OR, NOT으로 엮습니다. 하위 알람 열 개가 동시에 울려도 사람에게는 복합 알람 하나만 알리게 해서 알람 폭풍을 막습니다.

대시보드는 장애 때 처음 여는 화면이므로 서비스마다 하나씩, 위에서부터 사용자 증상(요청 수, 에러율, p99) 다음에 원인 지표(CPU, DB 연결, 큐)를 배치합니다. Kubernetes 생태계에 익숙한 팀은 Prometheus와 Grafana의 관리형 버전(짧게만 언급)을 고르기도 합니다.

trace id 하나로 요청의 전 구간을 꿴다

요청이 들어올 때 추적 ID를 만들고, 서비스가 다른 서비스를 부를 때마다 헤더(W3C traceparent 등)로 넘깁니다. 각 구간은 시작과 끝 시각을 가진 span이 됩니다.

로그에도 같은 trace id를 찍으면 느린 span에서 바로 그 요청의 로그로 넘어갈 수 있습니다. 앞에서 본 Logs Insights 질의의 마지막 줄이 바로 그 동작입니다.

계측은 OpenTelemetry, 분석은 X-Ray

X-Ray는 AWS의 트레이스 저장·분석 서비스입니다. 앱에서 span을 만드는 계측은 예전에는 X-Ray SDK를 썼지만, AWS는 2026년 2월 25일부터 X-Ray SDK와 데몬을 보안 수정만 하는 유지 관리 모드로 돌리고 OpenTelemetry로 옮기라고 권장합니다.

ADOT는 AWS가 검증해 배포하는 OpenTelemetry 배포판입니다. Java는 에이전트 JAR를 붙이는 것만으로 HTTP, JDBC, AWS SDK 호출이 자동 계측되고, 콜렉터나 CloudWatch 에이전트가 X-Ray로 보냅니다.

모든 요청을 기록하면 비싸므로 샘플링합니다. X-Ray 기본 규칙은 매초 첫 요청 1건 + 나머지의 5%입니다. 규칙을 X-Ray 서비스에 두면 재배포 없이 바꿀 수 있습니다.

표준에 계측하면 백엔드를 바꿀 수 있다

OpenTelemetry로 계측해 두면 코드 수정 없이 수집 대상을 X-Ray에서 다른 APM으로 바꿀 수 있습니다.

자동 APM과 SLO를 한곳에서

메트릭, 로그, 트레이스를 각각 설정해 서비스 상태를 조립하는 것은 손이 많이 갑니다. Application Signals는 ADOT 기반 자동 계측으로 서비스마다 호출 수, 지연, 오류(fault/error) 같은 표준 지표를 만들고 서비스 간 의존 관계를 지도로 그립니다.

Java, Python, Node.js, .NET을 지원하며 EKS, ECS, EC2, Lambda의 앱에서 데이터를 모읍니다.

여기에 SLO를 직접 정의할 수 있다는 점이 핵심입니다. "주문 API의 p99 지연이 300ms 이하인 비율 99.9%"를 SLO로 등록하면, 남은 에러 예산과 소진 추이를 보여 주고 그 위에 알람을 겁니다.

이제 무엇을 SLO로 삼아야 하는지, 그 출발점인 골든 시그널부터 봅니다.

SLO는 얼마나 실패해도 되는지를 정한다

SLI는 측정값(성공 요청 비율), SLO는 내부 목표(30일간 99.9%), SLA는 어기면 보상하는 고객과의 계약입니다. SLO를 SLA보다 엄격하게 잡아 계약을 어기기 전에 알아챕니다.

100%에서 SLO를 뺀 나머지가 에러 예산입니다. 예산이 남으면 과감히 배포하고, 다 쓰면 기능 배포를 멈추고 안정화에 집중합니다.

에러 예산이 타는 속도에 알람을 건다

소진 속도는 지금 추세대로면 예산을 몇 배 빠르게 쓰는지입니다. 30일 SLO 99.9%에서 에러율이 0.1%면 소진 속도 1로 정확히 30일에 다 씁니다. 에러율 1.44%면 14.4배로, 1시간에 한 달 예산의 2%를 태웁니다.

"에러율 1% 넘으면 알람"은 짧은 튐에도 울리고 느린 누수는 놓칩니다. 소진 속도로 걸면 예산에 실제로 위협이 되는 것만 잡습니다.

알람은 사람을 깨울 가치가 있을 때만 울린다

  • 증상에 겁니다. 에러율, p99, SLO 소진 속도처럼 사용자가 겪는 것에 겁니다.
  • 원인 지표는 대시보드로. CPU, GC 시간은 조사할 때 봅니다.
  • 모든 알람에 런북을. 받은 사람이 할 행동을 링크로 답니다.
  • 등급을 나눕니다. 즉시 호출과 업무 시간 티켓을 구분합니다.
  • 울리고 닫기만 한 알람은 지웁니다. 주기적으로 정리합니다.

"CPU 80%" 알람이 나쁜 이유

CPU가 높아도 사용자는 멀쩡할 수 있고, 매번 확인만 하고 닫다 보면 진짜 알람도 무시하게 됩니다. 이것을 알람 피로라고 합니다. 울리면 반드시 행동하는 알람만 남깁니다.

5부

장애가 났을 때 무엇부터 하는가

알람이 울렸습니다. 사람과 절차가 움직이는 인시던트 대응, 증상에서 원인으로 좁혀 가는 플레이북, 자주 터지는 장애 유형, 그리고 장애를 일부러 일으켜 미리 대비하는 카오스 엔지니어링까지 봅니다.

인시던트 대응은 정해진 순서로 움직인다

  1. 탐지

    알람이나 사용자 신고로 이상을 알아챕니다.

  2. 선언과 분류

    인시던트를 선언하고 영향 범위로 심각도를 정합니다.

  3. 완화

    원인을 몰라도 사용자 피해부터 멈춥니다.

  4. 복구와 원인 분석

    정상으로 되돌리고 근본 원인을 찾습니다.

  5. 포스트모템

    재발을 막을 조치를 정하고 기록합니다.

장애 대응에서 가장 흔한 실수는 원인을 찾느라 완화를 미루는 것입니다. 사용자는 원인이 아니라 복구 시간을 겪습니다. 그래서 탐지까지 걸린 시간과 완화까지 걸린 시간을 따로 재서 개선합니다.

심각도(SEV1~3 등)는 미리 정의해 둡니다. "결제 불가는 SEV1, 관리자 화면 오류는 SEV3"처럼 정해져 있어야 새벽에 누구를 깨울지 고민하지 않습니다.

재시작은 증거를 지웁니다. 재시작하기 전에 스레드 덤프를 뜨고(5장), 문제 인스턴스 하나는 로드 밸런서에서만 빼서 살려 두면 나중에 원인을 볼 수 있습니다.

역할을 나누면 빨라진다

지휘자 한 명이 결정하고, 기술 담당이 조사하고, 소통 담당이 30분마다 상태 페이지와 사내 채널에 진행 상황을 올립니다.

포스트모템은 사람이 아니라 시스템을 고친다

포스트모템은 장애의 타임라인, 영향, 근본 원인, 재발 방지 조치를 기록하는 문서입니다. 비난 없는 원칙이 핵심입니다. "누가 잘못 쳤나"에서 멈추면 사람들은 실수를 숨기고, 같은 실수를 가능하게 한 시스템은 그대로 남습니다.

"운영자가 잘못된 명령을 실행했다"가 아니라 "검토 없이 운영 DB에 명령을 실행할 수 있었다"를 원인으로 적습니다.

  • 타임라인: 언제 시작, 언제 탐지, 언제 완화됐는지 분 단위로 적습니다.
  • 왜를 반복: 직접 원인에서 "왜 그게 가능했나"를 몇 번 더 묻습니다.
  • 탐지 개선: 알람이 더 일찍 울릴 수 있었는지 봅니다.
  • 조치 항목: 담당자와 기한이 있는 작업으로 남깁니다.

"서버가 느려요"에 답하는 순서

  1. 범위 좁히기

    전체인가, 특정 API나 인스턴스인가. 배포와 겹치나.

  2. 지표

    골든 시그널, CPU, 메모리, GC 시간, DB 연결 수.

  3. 로그와 트레이스

    느린 span과 그 요청의 에러 로그.

  4. 스레드·힙 덤프

    스레드가 어디서 기다리는지, 무엇이 힙을 채우는지.

  5. DB

    슬로 쿼리, 실행 계획, 락 대기.

바깥에서 안으로, 싼 정보에서 비싼 정보로 내려갑니다. 대시보드 한 화면은 몇 초면 보지만, 힙 덤프는 수 GB를 받아 분석 도구로 열어야 합니다.

각 단계의 도구는 앞 장에 있습니다. 서버 명령어는 9장, K8s 상태별 진단은 10장, 덤프 읽는 법은 5장, 슬로 쿼리와 실행 계획은 4장입니다. 여기서는 어느 순서로 그 도구를 꺼내는지를 정합니다.

5xx 급증은 누가 만든 에러인지부터 가른다

코드ALB 문서의 대표 원인먼저 볼 곳
대상이 만든 5xx앱이 직접 500을 반환HTTPCode_Target_5XX_Count, 앱 로그
502요청 중 대상이 연결을 끊음keep-alive 설정, 등록 취소 지연
503등록된 정상 대상이 없음헬스 체크, 배포 상태
504유휴 제한 시간 안에 응답 없음느린 쿼리, 외부 호출

ALB는 앱이 만든 에러(HTTPCode_Target_5XX_Count)와 ALB 자신이 만든 에러(HTTPCode_ELB_5XX_Count)를 따로 셉니다. 앞의 것이 늘면 앱 로그를, 뒤의 것이 늘면 ALB와 대상 사이의 연결을 봅니다. 그리고 첫 질문은 언제나 "방금 배포했나"입니다.

간헐적 502는 keep-alive 불일치 탓이다

# ALB 유휴 제한 시간: 기본 60초
# 앱 keep-alive는 그보다 길게
server:
  tomcat:
    keep-alive-timeout: 75s

ALB는 대상과의 연결을 재사용합니다(2장 keep-alive). 앱이 유휴 연결을 ALB보다 먼저 닫으면, ALB가 그 연결로 막 요청을 보낸 순간 끊겨 502가 납니다. 트래픽이 적은 시간에 드문드문 나는 502가 전형적인 모습입니다.

규칙은 하나입니다. 앱의 keep-alive 제한 시간을 ALB 유휴 제한 시간보다 길게 둡니다. 기본 5초인 Node.js 서버에서 특히 자주 보이는 사례입니다.

두 OOM은 흔적이 남는 곳이 다르다

JVM OutOfMemoryError(5장)와 컨테이너 OOM(9장)은 흔적이 다릅니다. 앞의 것은 앱 로그와 힙 덤프를 남기지만, 뒤의 것은 커널이 SIGKILL로 끝내 앱 로그가 조용합니다.

그래서 힙 덤프 경로는 태스크가 사라져도 남는 곳(EFS 등)에 두고, 메모리 알람은 태스크 한도 기준으로 겁니다. 종료 코드 137인데 Java 로그에 OOM이 없다면 힙 밖 메모리를 의심해 힙 비율을 낮춥니다.

주기적인 p99 튐은 GC 정지를 의심한다

p50은 평온한데 p99만 몇 분마다 톱니처럼 솟는다면, 그 시각과 GC 로그의 정지 시간을 겹쳐 봅니다. Stop-The-World 동안에는 모든 요청이 함께 멈추기 때문입니다(5장).

컨테이너에서는 원인이 하나 더 있습니다. CPU 한도를 넘으면 cgroup이 프로세스를 잠시 멈추는 스로틀링(9장)이 GC 스레드까지 멈춰 정지 시간을 늘립니다.

  • GC 로그를 켜 둡니다. 장애가 난 뒤에는 켤 수 없습니다.
  • GC 시간을 메트릭으로. Micrometer의 GC 정지 지표를 CloudWatch로 보냅니다.
  • 힙 사용률의 바닥을 봅니다. GC 직후 바닥이 계속 오르면 누수입니다.
  • CPU 여유를 둡니다. 태스크 CPU를 너무 빡빡하게 잡지 않습니다.

디스크가 차면 서버는 엉뚱한 곳에서 터진다

디스크가 가득 차면 로그 쓰기가 실패하고, DB는 쓰기를 멈추고, 앱은 임시 파일을 못 만들어 엉뚱한 예외를 냅니다. 흔한 주범은 회전되지 않는 로그 파일, 쌓인 힙 덤프, 지워졌지만 아직 열려 있는 파일(9장)입니다.

예방은 에이전트의 disk used_percent 알람(80%), 로그 회전, 로그를 파일 대신 stdout으로 보내 CloudWatch Logs에 맡기기입니다.

EBS는 볼륨을 붙인 채로 크기를 늘릴 수 있습니다(14장). 다만 그다음 OS 안에서 파티션과 파일 시스템도 늘려야 공간이 보입니다.

RDS 저장 공간도 찹니다

FreeStorageSpace 알람을 걸고, 필요하면 스토리지 자동 확장을 켭니다. 가득 찬 RDS는 쓰기를 받지 못합니다.

카오스 엔지니어링은 장애를 미리 일으켜 본다

지금까지 본 설계는 모두 "AZ가 죽으면 이렇게 넘어갈 것이다"라는 가설입니다. 가설은 실제로 일으켜 보기 전까지 검증되지 않습니다. 카오스 엔지니어링은 통제된 조건에서 장애를 주입해 시스템이 기대대로 버티는지 확인하는 실험입니다.

  1. 정상 상태 정의

    에러율, p99처럼 측정 가능한 정상 기준을 정합니다.

  2. 가설 세우기

    "태스크 절반이 죽어도 에러율 0.1% 이하"처럼.

  3. 폭발 반경 제한

    스테이징이나 일부 트래픽부터 작게 시작합니다.

  4. 주입과 관찰

    장애를 넣고 지표가 가설대로인지 봅니다.

  5. 중단 조건

    정상 기준을 넘으면 즉시 실험을 멈춥니다.

AWS FIS는 장애 주입을 관리형으로 실행합니다. 대상은 태그와 필터로 고른 자원, 행동은 인스턴스 중지, ECS 태스크 중지, 네트워크 지연, API 오류 주입 같은 장애입니다.

중단 조건은 CloudWatch 알람입니다. 실험 중 알람이 울리면 FIS가 실험을 멈춥니다. 실험은 IAM 역할로 실행되어 권한 밖 자원은 건드릴 수 없습니다.

AZ 정전을 연습하고 게임 데이로 사람도 훈련한다

FIS의 시나리오 라이브러리에는 AZ Availability: Power Interruption이 있습니다. 한 AZ의 EC2·ECS·EKS 컴퓨팅 손실, 그 AZ에서의 재확장 실패, 서브넷 연결 끊김, RDS와 ElastiCache 장애 조치 같은 증상을 한꺼번에 일으킵니다. 기본으로 30분간 정전 증상, 이어서 30분간 복구 과정의 증상을 냅니다.

2부에서 설계한 Multi-AZ와 정적 안정성이 실제로 동작하는지 확인하는 가장 직접적인 방법입니다.

게임 데이는 이런 실험을 정해진 날 팀 전체가 실제 대응하듯 진행하는 훈련입니다. 알람이 제때 울렸는지, 런북대로 움직였는지, 대시보드가 원인을 보여 줬는지를 함께 검증합니다.

6부

버틸 만큼 사고, 쓴 만큼만 낸다

고가용성과 관측성은 모두 돈이 듭니다. 장애를 버틸 용량을 계산하고, 무엇을 기준으로 늘리고 줄일지 정하고, 비용이 어디서 새는지 찾아 줄이는 방법을 봅니다.

용량은 AZ 하나를 잃어도 버티게 잡는다

  1. 피크 동시 요청

    2,000 RPS × 0.1초 = 200건(리틀의 법칙).

  2. 인스턴스당 처리량

    부하 테스트로 측정: 안정적으로 50건.

  3. 정상 시 필요 대수

    200 ÷ 50 = 4대. 여기까지는 장애가 없을 때의 숫자입니다.

  4. AZ 하나 손실 대비(N+1)

    2 AZ면 각 4대, 총 8대. 3 AZ면 각 2대, 총 6대.

AZ 하나가 사라지는 순간 남은 AZ가 피크 전체를 받아야 합니다. 2 AZ에서는 남는 비율이 1/2이라 두 배를, 3 AZ에서는 2/3라 1.5배를 사 두면 됩니다. AZ가 많을수록 여유 용량이 싸지는 이유입니다.

이것이 2부의 정적 안정성을 숫자로 옮긴 것입니다. 장애 순간 Auto Scaling에 기대지 않고 미리 사 둔 용량으로 버팁니다.

기둥 하나하나가 결국 아래층의 원리 위에 서 있습니다. 커넥션 풀 고갈을 이해하려면 4장이, 컨테이너 OOM을 이해하려면 5장과 9장이 필요했습니다. 기둥 사이의 균형을 고르는 근거가 1장부터 쌓아 온 원리입니다.

정리

  • 고가용성은 계층마다 SPOF를 없애고, 정적 안정성으로 완성합니다. AZ 하나를 잃어도 새로 띄우지 않고 버틸 용량을 미리 둡니다.
  • Multi-AZ는 DR이 아닙니다. RPO·RTO에 맞춰 Backup & Restore부터 Active-Active까지 고르고, 전환을 연습합니다.
  • 배포는 작게 넣고 알람으로 되돌립니다. ECS 배포 전략, ALB·Route 53 가중치, Lambda 별칭이 11장의 전략을 구현합니다.
  • 알람은 증상과 에러 예산에, 조사는 원인 지표로 합니다. 지표에서 트레이스, 로그, 덤프, 슬로 쿼리로 좁혀 들어갑니다.
  • 비용은 크기, 약정, 경로로 줄입니다. 태그와 예산 알람으로 비용도 지표처럼 관측합니다.

스스로 점검

  1. 2개 AZ에 피크 기준 4대가 필요한 서비스라면 최소 몇 대를 둬야 할까요?

    AZ 하나를 잃어도 버티려면 각 AZ에 4대씩 8대입니다. 3개 AZ로 나누면 각 2대씩 6대로 줄어듭니다.

  2. RDS Multi-AZ가 있는데도 교차 리전 백업이 필요한 이유는?

    Multi-AZ는 잘못된 DELETE까지 그대로 복제하고 리전 장애에는 무력합니다. 되돌아갈 시점과 다른 리전의 복사본은 백업만 줍니다.

  3. RDS 장애 조치는 끝났는데 앱이 몇 분째 DB 오류를 냅니다. 무엇을 의심하나요?

    JVM이 옛 IP를 DNS 캐시로 쥐고 있거나 풀에 끊긴 연결이 남은 경우입니다. DNS TTL을 줄이고 풀 검증을 켜거나 RDS Proxy를 씁니다.

  4. ALB 가중치로 green에 10%를 보내던 중 green이 전부 unhealthy가 되면?

    ALB는 다른 대상 그룹으로 자동으로 넘기지 않아 그 10%가 실패합니다. 에러율 알람으로 가중치를 0으로 되돌리는 롤백이 필요합니다.

  5. 배포 서킷 브레이커를 켰는데도 잘못된 응답을 내는 버전이 끝까지 배포됐습니다. 왜일까요?

    서킷 브레이커는 태스크가 정상 상태에 도달하는지만 봅니다. 응답 내용의 오류는 에러율 알람을 배포에 연결해야 잡힙니다.

스스로 점검 (계속)

  1. 5xx 개수 알람이 밤마다 INSUFFICIENT_DATA로 바뀝니다. 어떻게 고치나요?

    에러가 없으면 점이 찍히지 않는 메트릭이라 생기는 일입니다. 누락 데이터 처리를 notBreaching으로 바꿉니다.

  2. CPU는 20%인데 응답이 느립니다. 서버를 늘리면 나아질까요?

    스레드가 커넥션, 락, 외부 호출을 기다리는 경우라 늘려도 안 나아지고, DB가 원인이면 오히려 악화됩니다. 스레드 덤프로 무엇을 기다리는지 봅니다.

  3. 트래픽이 적은 새벽에만 드문드문 502가 납니다. 첫 의심 대상은?

    앱의 keep-alive 제한 시간이 ALB 유휴 제한 시간보다 짧은 경우입니다. 앱 쪽 값을 ALB보다 길게 늘립니다.

  4. SLO 99.9%(30일)에서 에러율이 1.44%로 1시간 지속되면 예산을 얼마나 쓰나요?

    소진 속도 14.4배로 1시간이면 한 달 예산의 2%를 씁니다. 즉시 호출할 수준입니다.

  5. NAT Gateway 비용이 급증했습니다. 가장 먼저 확인할 것은?

    Private Subnet에서 S3나 DynamoDB로 대량 트래픽이 NAT를 지나는지 봅니다. 게이트웨이 엔드포인트로 우회하면 처리 요금이 사라집니다.
