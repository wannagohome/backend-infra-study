5장 Java와 JVM

내 코드는 JVM 안에서 어떻게 살고 죽는가

소스 코드가 바이트코드가 되어 실행되고, 객체가 힙에서 태어나 GC로 사라지기까지를 따라갑니다. 그 위에서 언어 핵심, HashMap, 동시성, 운영 진단까지 이어 봅니다.

아래층부터 위로 쌓아 올라가는 순서입니다. 지금은 5단계입니다.

1부

Java 코드는 어떻게 실행되는가

4장까지는 OS, 네트워크, DB처럼 서버가 기대는 바닥을 봤습니다. 이제 그 위에서 우리 서버 코드가 실제로 돌아가는 런타임, JVM으로 올라갑니다.

컴파일은 한 번, 실행은 각 OS의 JVM이

C 프로그램은 OS와 CPU마다 따로 컴파일해야 합니다. Java는 소스를 특정 CPU의 기계어가 아니라 바이트코드라는 중간 명령어로 컴파일합니다.

바이트코드를 실제 기계어로 바꿔 실행하는 일은 OS마다 설치된 JVM이 맡습니다. 그래서 같은 .class 파일이 어느 OS에서든 그대로 돕니다.

Kotlin, Scala도 바이트코드로 컴파일되므로 같은 JVM 위에서 실행됩니다.

JDK는 개발 도구, JVM은 실행 엔진

구분들어 있는 것누가 필요한가
JVM클래스 로더, 메모리 영역, 실행 엔진, GC바이트코드를 실행하는 모든 곳
JREJVM + 표준 라이브러리실행만 하는 환경
JDKJRE + javac, jar, jcmd 등 도구개발과 운영 진단

JRE는 실행 환경, JDK는 여기에 개발 도구를 더한 것입니다. JDK 11부터 Oracle은 JRE를 따로 배포하지 않고, 필요한 모듈만 묶은 런타임을 jlink로 만들게 했습니다.

운영 이미지에도 진단 도구를 고려하세요

최소 런타임 이미지에는 jcmd가 없을 수 있습니다. 장애 때 힙 덤프를 뜰 방법을 미리 정해 두세요(6부에서 다룸).

소스에서 실행까지 다섯 단계를 거친다

  1. javac.java를 .class로
  2. 클래스 로더필요할 때 읽어 들임
  3. 검증과 링크바이트코드 안전성 확인
  4. 실행 엔진인터프리터 + JIT
  5. GC안 쓰는 객체 회수

javac가 만든 .class 파일은 프로그램 시작 시 한꺼번에 올라가지 않습니다. 어떤 클래스가 처음 쓰이는 순간 클래스 로더가 읽어 메모리에 올리고, 실행 엔진이 그 바이트코드를 기계어로 바꿔 실행합니다.

실행 중 만들어진 객체는 힙에 쌓이고, 더 이상 쓰이지 않으면 GC가 치웁니다. 이 장은 이 흐름을 한 칸씩 따라갑니다.

클래스 로더는 부모에게 먼저 묻는다

  1. Application 로더

    클래스패스의 우리 코드와 라이브러리를 담당. 요청을 먼저 부모에게 넘깁니다.

  2. Platform 로더

    JDK 9부터의 이름. java.sql 같은 플랫폼 모듈을 담당합니다.

  3. Bootstrap 로더

    java.lang 같은 핵심 클래스. 여기서 못 찾으면 아래로 내려옵니다.

  4. 링크와 초기화

    검증, static 필드 준비 후 static 초기화 블록을 실행합니다.

클래스 로딩은 부모 위임 모델을 따릅니다. 자식 로더는 직접 찾기 전에 부모에게 먼저 맡기고, 부모가 못 찾을 때만 스스로 찾습니다.

그래서 누군가 클래스패스에 가짜 java.lang.String을 넣어도 Bootstrap이 먼저 진짜를 올려 바꿔치기가 불가능합니다.

메모리는 공유 영역과 스레드별 영역으로 나뉜다

JVM이 쓰는 메모리를 런타임 데이터 영역이라 부릅니다. 힙과 메서드 영역은 모든 스레드가 공유하고, 스택과 PC 레지스터는 스레드마다 하나씩 생깁니다.

1장에서 본 프로세스 메모리 구조와 같은 발상입니다. 공유 영역이라서 동시성 문제가 생기고, GC가 정리하는 곳도 힙입니다.

지역 변수는 스택에, 객체는 힙에 산다

void place(long userId) {
    int qty = 3;              // 스택: 값 자체
    Order o = new Order(qty); // 스택: 참조값
    repo.save(o);              // 힙: Order 객체
}   // 메서드 종료 → 프레임 제거
    // Order는 아무도 안 가리키면
    // GC 대상

메서드를 호출할 때마다 스택에 프레임이 쌓이고, 지역 변수와 매개변수가 그 안에 놓입니다. 객체 자체는 힙에 있고, 변수에는 그 위치를 가리키는 참조값만 들어갑니다.

재귀가 너무 깊으면 StackOverflowError, 힙이 가득 차면 OutOfMemoryError가 납니다. 클래스 정보는 JDK 8부터 힙 밖 네이티브 메모리의 Metaspace에 둡니다.

인터프리터로 시작해 뜨거운 코드만 JIT으로

인터프리터는 바이트코드를 한 줄씩 해석해 바로 실행합니다. 시작은 빠르지만 같은 코드를 매번 다시 해석하므로 느립니다.

JIT 컴파일러는 자주 호출되는 뜨거운 메서드를 찾아 기계어로 컴파일해 캐시합니다. HotSpot은 빠른 C1과 최적화가 강한 C2를 단계적으로 쓰는 계층형 컴파일이 기본입니다.

배포 직후 첫 요청들은 느립니다

JIT이 아직 코드를 컴파일하지 않은 웜업 구간이라 지연이 튑니다. 트래픽을 받기 전에 주요 API를 미리 호출해 두는 이유입니다.

왜 처음부터 다 컴파일하지 않나

실행해 봐야 어떤 분기가 자주 타는지 압니다. JIT은 그 실행 정보로 인라이닝 같은 공격적 최적화를 합니다.

2부

GC는 무엇을 언제 어떻게 치우는가

Java 개발자는 free()를 호출하지 않습니다. 대신 JVM이 쓰레기를 판단하고 회수하며, 그 대가로 애플리케이션을 잠시 멈춥니다.

기초 원리 여기부터는 GC 알고리즘과 JVM 내부 동작을 다룹니다.

GC Root에서 닿지 않으면 쓰레기다

가비지 컬렉션(GC)은 GC Root에서 참조를 따라가 닿는 객체만 살아 있다고 봅니다. 이를 도달 가능성이라 합니다.

GC Root는 실행 중인 스택 프레임의 지역 변수, 클래스의 static 필드, JNI 참조 등입니다. 서로를 가리키는 순환 참조라도 Root에서 끊겼다면 함께 회수됩니다.

표시하고, 쓸고, 압축한다

  1. Mark

    GC Root부터 그래프를 따라가며 살아 있는 객체에 표시합니다.

  2. Sweep

    표시되지 않은 객체가 차지한 공간을 빈 공간으로 돌립니다.

  3. Compact

    살아남은 객체를 한쪽으로 몰아 조각난 빈 공간을 합칩니다.

Sweep만 하면 빈 공간이 여기저기 흩어집니다. 1장에서 본 외부 단편화처럼, 전체 여유는 충분한데 큰 배열 하나 놓을 연속 공간이 없게 됩니다.

Compact가 이를 해결하지만 객체를 옮기면 그 객체를 가리키던 모든 참조의 주소를 고쳐야 해 비용이 큽니다.

Stop-The-World: GC는 세상을 멈춘다

GC가 객체 그래프를 표시하는 도중에 애플리케이션이 참조를 바꾸면, 살아 있는 객체를 쓰레기로 잘못 판단할 수 있습니다. 그래서 GC는 안전한 지점에서 모든 애플리케이션 스레드를 멈춥니다. 이것이 Stop-The-World(STW)입니다.

멈춘 동안에는 요청이 처리되지 않으므로 STW 시간이 곧 응답 지연입니다. GC 튜닝의 목표는 대부분 STW를 짧고 드물게 만드는 것입니다.

현대 GC의 방향

멈추지 않을 수는 없으니, 표시 같은 무거운 일을 애플리케이션과 동시에(concurrent) 하고 STW 구간만 짧게 남깁니다.

null 대입은 즉시 회수가 아닙니다

참조를 끊어 회수 대상이 될 뿐, 실제 회수는 다음 GC 때입니다. System.gc()도 요청일 뿐 보장이 아닙니다.

대부분의 객체는 금방 죽는다

매번 힙 전체를 표시하면 힙이 클수록 STW가 길어집니다. GC 설계자들은 관찰에서 실마리를 얻었습니다. 약한 세대 가설은 두 가지입니다. 대부분의 객체는 만들어지고 곧 쓸모가 없어진다, 그리고 오래된 객체가 젊은 객체를 가리키는 경우는 드물다.

요청 하나를 처리하며 만든 DTO, 임시 문자열, 반복자는 응답이 나가면 모두 쓰레기가 됩니다. 반면 캐시나 싱글톤은 오래 삽니다.

그렇다면 힙을 나이별로 나눠 젊은 영역만 자주, 빠르게 치우면 됩니다. 젊은 영역은 대부분 죽어 있으니 살아남은 소수만 옮기면 끝납니다.

Eden에서 태어나 Survivor를 거쳐 Old로

새 객체는 Eden에 할당됩니다. Eden이 차면 Minor GC가 살아 있는 객체만 비어 있는 Survivor로 복사하고 Eden을 통째로 비웁니다.

Survivor 두 칸은 번갈아 쓰이며, 살아남을 때마다 나이가 하나씩 오릅니다. 나이가 임계값(MaxTenuringThreshold)에 닿으면 Old로 승격됩니다.

Minor, Major, Full GC는 범위가 다르다

구분대상언제정지 시간
Minor GCYoung 영역Eden이 가득 찼을 때짧음(생존자만 복사)
Major GCOld 영역 위주Old 사용률이 높을 때GC 종류에 따라 다름
Full GC힙 전체 + Metaspace회수가 할당을 못 따라갈 때가장 김(수 초도 가능)

Minor GC는 Young만 보는데, Old 객체가 Young 객체를 가리키면 그것도 Root처럼 봐야 합니다. 그래서 JVM은 Old에서 Young을 가리키는 곳을 카드 테이블에 기록해 두고 그 부분만 확인합니다. 가설 두 번째 항목 덕분에 이 기록은 작습니다.

GC는 처리량과 정지 시간 사이의 선택이다

GC방식적합한 곳버전
Serial스레드 하나로 STW작은 힙, CPU 1개초기부터
Parallel여러 스레드로 STW배치, 처리량 우선JDK 8 기본
CMSOld를 동시 표시과거 저지연용JDK 14에서 제거
G1리전 단위, 목표 정지 시간일반 서버JDK 9부터 기본
ZGC거의 모든 작업을 동시 수행큰 힙, 저지연JDK 15 정식

출처: OpenJDK JEP 248(G1 기본), JEP 363(CMS 제거), JEP 377(ZGC 정식). JDK 21 GC 튜닝 가이드 기준 G1은 서버급 머신에서 기본입니다.

G1은 힙을 리전으로 쪼개 쓰레기가 많은 곳부터

G1은 힙을 같은 크기의 리전으로 나누고, 각 리전에 Eden, Survivor, Old 역할을 그때그때 붙입니다. 세대는 물리적 구역이 아니라 리전의 꼬리표입니다.

정해진 목표 정지 시간(MaxGCPauseMillis, 기본 200ms) 안에서 쓰레기가 가장 많은 리전부터 골라 치웁니다. 이름이 Garbage-First인 이유입니다.

ZGC는 객체를 옮기는 일까지 동시에 한다

G1도 객체를 옮기는(compact) 단계는 STW 안에서 합니다. ZGC는 이 이동마저 애플리케이션과 동시에 합니다. 참조를 읽는 순간 끼어드는 로드 배리어가 옮겨진 객체의 새 주소로 참조를 고쳐 줍니다.

그 결과 정지 시간이 힙 크기와 거의 무관하게 1ms 미만으로 유지됩니다. 대신 배리어 비용만큼 CPU와 처리량을 조금 내줍니다.

  1. JDK 15

    ZGC 정식 기능(JEP 377). -XX:+UseZGC로 켭니다.

  2. JDK 21

    세대별 ZGC 추가(JEP 439). 약한 세대 가설을 ZGC에도 적용합니다.

  3. JDK 23~24

    세대별 모드가 기본(JEP 474), 24에서 비세대 모드 제거(JEP 490).

3부

JVM 위에서 객체가 동작하는 방식

JVM의 메모리 구조를 알면 언어 규칙이 왜 그렇게 정해졌는지 보입니다. 다형성, 값 전달, String 불변, equals와 hashCode를 그 관점에서 봅니다.

다형성은 실행 시점에 메서드를 고르는 것

interface Payment { void pay(int won); }
class Card implements Payment { … }
class Point implements Payment { … }

Payment p = pickByUser();  // Card? Point?
p.pay(10_000);  // 실제 객체의 pay 호출

객체지향 프로그래밍(OOP)의 4가지 특징은 캡슐화, 상속, 추상화, 다형성입니다. 다형성은 같은 호출이 객체에 따라 다르게 동작하는 성질입니다.

오버로딩은 컴파일 때 인자 타입으로 정해지고(정적), 오버라이딩은 실행 때 실제 객체의 메서드로 정해집니다(동적 디스패치).

SOLID는 바뀌는 곳을 가두는 원칙이다

원칙핵심어기면
SRP 단일 책임바뀌는 이유는 하나한 수정이 여러 기능을 깸
OCP 개방 폐쇄확장엔 열고 수정엔 닫음결제 수단마다 if 추가
LSP 리스코프 치환자식은 부모 자리에 대체 가능하위 타입에서 예외 폭발
ISP 인터페이스 분리쓰지 않는 메서드에 의존 금지빈 구현 메서드 양산
DIP 의존 역전구현 말고 추상에 의존구현 교체 시 호출부 수정

앞 슬라이드의 Payment처럼 호출부가 인터페이스에만 의존하면, 새 결제 수단을 추가해도 호출부는 그대로입니다(OCP, DIP). 그런데 구현 객체는 누가 만들어 넣어 줄까요? 그 일을 대신하는 것이 6장의 Spring DI입니다.

서로 무관한 클래스에 같은 능력을 부여할 때는 인터페이스를, 같은 계열의 클래스들이 상태와 공통 로직을 공유할 때는 추상 클래스를 씁니다. 실무에서는 인터페이스로 계약을 정하고 필요할 때만 추상 클래스로 공통 구현을 묶는 편이 유연합니다.

Java는 언제나 값을 복사해 넘긴다

메서드에 객체를 넘기면 객체가 아니라 참조값의 복사본이 넘어갑니다. 두 변수가 같은 힙 객체를 가리키므로 필드를 바꾸면 호출자도 그 변화를 봅니다.

하지만 매개변수에 새 객체를 대입하면 복사본만 바뀝니다. 호출자의 변수는 여전히 원래 객체를 가리킵니다. 그래서 Java는 Call by Reference가 아니라 Call by Value입니다.

String은 불변이라 공유할 수 있다

String a = "hello";          // String Pool
String b = "hello";          // 같은 객체 재사용
String c = new String("hello"); // 새 객체
a == b;      // true  (같은 주소)
a == c;      // false (다른 주소)
a.equals(c); // true  (같은 내용)

// 루프 안 문자열 누적은 StringBuilder로
StringBuilder sb = new StringBuilder();
for (String s : rows) sb.append(s);

String은 한 번 만들면 내용을 바꿀 수 없습니다. 그래서 같은 리터럴을 힙의 String Pool에 하나만 두고 공유해도 안전하고, 해시값을 캐시해 HashMap 키로 쓰기 좋으며, 여러 스레드가 동시에 읽어도 문제가 없습니다.

대신 +로 누적하면 매번 새 객체가 생깁니다. 반복 누적은 StringBuilder로 하고, 동기화가 붙은 StringBuffer는 거의 쓰지 않습니다.

equals를 바꾸면 hashCode도 바꿔야 한다

==는 같은 객체(주소)인지, equals()는 같은 내용인지 비교합니다. 기본 equals()는 ==와 같으므로 값 객체는 재정의합니다.

규약은 하나입니다. equals가 같으면 hashCode도 같아야 합니다. HashMap은 hashCode로 버킷을 먼저 고르고, 그 버킷 안에서만 equals로 비교하기 때문입니다.

equals만 재정의하면

내용이 같은 두 객체가 다른 버킷으로 갑니다. HashSet에 중복이 들어가고, 넣은 키로 get()을 해도 null이 나옵니다.

값 객체는 record로

Java 16의 record는 필드 기반 equals, hashCode를 자동으로 만들고 필드를 final로 묶어 불변 객체가 됩니다.

4부

컬렉션과 HashMap의 내부

3장의 해시 테이블 원리가 Java에서 어떻게 구현됐는지 봅니다. 그리고 예외, 제네릭, 람다와 Stream처럼 매일 쓰는 언어 도구를 정리합니다.

List, Set, Map은 무엇을 보장하나

인터페이스보장대표 구현조회
List순서 유지, 중복 허용ArrayList인덱스 O(1)
Set중복 금지HashSet, TreeSet평균 O(1) / O(log n)

ArrayList와 LinkedList의 차이는 3장에서 본 배열과 연결 리스트의 차이 그대로입니다. 실무에서는 캐시 지역성 때문에 대부분 ArrayList가 빠릅니다. HashSet은 내부적으로 HashMap의 키만 쓰는 구현이라, 결국 HashMap을 이해하면 둘 다 이해됩니다.

HashMap은 해시를 섞은 뒤 비트 AND로 버킷을 고른다

static final int hash(Object key) {
    int h;
    return (key == null) ? 0
        : (h = key.hashCode()) ^ (h >>> 16);
}
// 버킷 인덱스
int i = (n - 1) & hash;  // n은 2의 거듭제곱

HashMap은 배열 크기 n을 항상 2의 거듭제곱으로 유지합니다(기본 16). 그러면 나머지 연산 대신 (n-1) & hash로 빠르게 버킷을 고를 수 있습니다.

문제는 이 방식이 해시의 하위 비트만 본다는 점입니다. 그래서 상위 16비트를 하위로 XOR해 섞어, 상위 비트만 다른 키들도 고르게 퍼지게 합니다.

충돌이 쌓이면 리스트를 트리로 바꾼다

같은 버킷에 키가 몰리면 HashMap은 3장의 체이닝처럼 노드를 연결 리스트로 잇습니다. 리스트가 길어지면 조회가 O(n)으로 느려집니다.

Java 8부터는 한 버킷의 노드가 8개 이상이고 배열 크기가 64 이상이면 레드-블랙 트리로 바꿔 O(log n)을 보장합니다. 배열이 작으면 트리 대신 배열부터 키우고, 6개 이하로 줄면 다시 리스트로 돌아갑니다.

75%가 차면 배열을 두 배로 늘린다

  1. 임계값 확인

    크기가 용량 × load factor(기본 0.75)를 넘으면 리사이징합니다.

  2. 두 배 배열

    16 → 32처럼 2의 거듭제곱을 유지합니다.

  3. 노드 재배치

    hash & 기존 용량 비트 하나로 같은 자리 또는 +기존 용량 자리로 나눕니다.

3장에서 본 재해싱을 HashMap은 비트 연산으로 가볍게 만듭니다. 크기가 두 배가 되면 인덱스 계산에 비트가 하나 더 쓰입니다. 그래서 각 노드는 해시를 다시 계산하지 않고 그 비트 하나만 보고 제자리에 남을지 옮길지 정합니다.

그래도 리사이징은 모든 노드를 훑는 O(n) 작업입니다. 넣을 개수를 안다면 new HashMap<>(예상 개수 / 0.75 + 1)처럼 미리 용량을 잡습니다.

여러 스레드가 HashMap에 동시에 쓰면 갱신이 사라지거나 리사이징 중 구조가 깨집니다. Java 8의 ConcurrentHashMap은 빈 버킷은 CAS로, 차 있는 버킷은 그 첫 노드만 잠가 서로 다른 버킷 쓰기를 병렬로 처리합니다. CAS는 5부에서 다룹니다.

복구할 수 있으면 Checked, 버그면 Unchecked

Error는 OOM처럼 애플리케이션이 복구할 수 없는 문제입니다. Exception 중 RuntimeException 계열이 Unchecked 예외, 나머지가 컴파일러가 처리를 강제하는 Checked 예외입니다.

Checked는 파일 없음처럼 호출자가 대응할 수 있는 상황, Unchecked는 null 참조처럼 코드를 고쳐야 하는 상황에 씁니다.

Spring 트랜잭션은 Checked에서 롤백하지 않습니다

기본 규칙은 Unchecked와 Error에서만 롤백입니다. 원리와 rollbackFor는 6장에서 다룹니다.

예외를 삼키지 마세요

catch 후 로그도 없이 넘어가면 장애 원인이 사라집니다. 감쌀 때는 원인 예외를 cause로 넘깁니다.

제네릭은 컴파일러만 아는 타입이다

List<String> names = new ArrayList<>();
// 컴파일 후 바이트코드에서는 List
// 꺼낼 때 (String) 캐스트가 자동 삽입

// PECS: 꺼내면 extends, 넣으면 super
double sum(List<? extends Number> xs)
void fill(List<? super Integer> out)

제네릭은 컴파일 때 타입을 검사해 잘못된 대입을 막습니다. 하지만 하위 호환을 위해 바이트코드에서는 타입 정보를 지웁니다. 이를 타입 소거라 합니다.

그래서 실행 중에는 List<String>과 List<Integer>가 같은 클래스이고, new T()나 instanceof List<String>은 쓸 수 없습니다.

Stream은 최종 연산 전까지 아무것도 안 한다

List<String> vip = orders.stream()
    .filter(o -> o.amount() > 100_000) // 중간
    .map(Order::userName)             // 중간
    .distinct()                       // 중간
    .toList();                        // 최종

Optional<User> u = repo.findById(id);

               .orElse("guest");

람다는 메서드 하나짜리 함수형 인터페이스를 짧게 구현하는 문법입니다. Stream의 중간 연산은 실행 계획만 쌓고, 최종 연산이 호출될 때 요소를 하나씩 파이프라인에 흘립니다(지연 연산).

parallelStream()은 JVM 전체가 공유하는 공용 ForkJoinPool을 씁니다. 서버에서 블로킹 작업을 넣으면 다른 요청까지 막을 수 있습니다.

리플렉션과 어노테이션은 Spring의 토대다

Class<?> c = Class.forName("com.app.OrderService");
for (Field f : c.getDeclaredFields()) {
    if (f.isAnnotationPresent(Inject.class)) {
        f.setAccessible(true);
        f.set(target, findBean(f.getType()));
    }
}

리플렉션은 실행 중에 메서드 영역의 클래스 정보를 읽어 필드, 메서드, 생성자를 다루는 기능입니다. 어노테이션은 코드에 붙이는 메타데이터로, 그 자체는 아무 일도 하지 않습니다.

프레임워크는 리플렉션으로 어노테이션을 읽어 객체를 만들고 연결합니다. 실행 중 프록시 객체를 만드는 동적 프록시도 이 위에 있으며 6장에서 다룹니다.

5부

여러 스레드가 힙을 함께 쓸 때

1장에서 경쟁 상태, 뮤텍스, 모니터를 OS 관점에서 봤습니다. 이제 같은 문제를 Java가 synchronized, volatile, CAS로 어떻게 푸는지 봅니다.

synchronized는 객체마다 있는 모니터를 잡는다

class Counter {
    private int count = 0;
    synchronized void inc() {
        count++;  // 읽기, 더하기, 쓰기 3단계
    }
}
// 타임아웃, 공정성이 필요하면
lock.tryLock(1, TimeUnit.SECONDS);

Java의 모든 객체는 1장에서 본 모니터를 하나씩 가집니다. synchronized 블록에 들어가려면 그 모니터를 얻어야 하고, 같은 스레드는 다시 들어갈 수 있습니다(재진입).

더 세밀한 제어가 필요하면 ReentrantLock을 씁니다. 대기 시간 제한, 공정 모드, 여러 조건 변수를 지원하지만 finally에서 직접 풀어야 합니다.

volatile은 보이게 할 뿐 원자적이지 않다

CPU 코어는 각자 캐시를 가지므로, 한 스레드가 바꾼 값이 다른 스레드에게 바로 보이지 않을 수 있습니다. 컴파일러와 CPU가 명령 순서를 바꾸기도 합니다.

JMM은 언제 쓰기가 보이는지를 happens-before 규칙으로 정합니다. volatile 변수는 쓰기 직후 다른 스레드의 읽기에 보입니다. 하지만 count++ 같은 읽고-쓰기는 여전히 끼어들 수 있습니다.

CAS는 잠그지 않고 비교한 뒤 바꾼다

  1. 읽기

    현재 값 V를 읽어 둡니다(예: 10).

  2. 계산

    새 값 N을 만듭니다(11).

  3. 비교 후 교체

    메모리 값이 아직 V일 때만 N으로 바꿉니다. CPU 명령 하나로 원자적입니다.

  4. 실패 시 재시도

    다른 스레드가 먼저 바꿨다면 처음부터 다시 합니다.

CAS는 스레드를 재우지 않고 실패하면 다시 시도합니다. AtomicInteger.incrementAndGet()이 이 방식이라, 경합이 적으면 락보다 빠릅니다.

경합이 아주 심하면 재시도가 CPU를 태웁니다. 카운터처럼 쓰기가 몰리는 곳에는 값을 여러 칸에 나눠 더하는 LongAdder가 낫습니다.

불변 객체는 동기화가 필요 없다

public final class Money {          // 상속 금지
    private final long amount;      // final 필드
    private final List<Long> history;
    Money(long a, List<Long> h) {
        amount = a;
        history = List.copyOf(h);     // 방어적 복사
    }
    Money plus(long x) {               // 새 객체 반환
        return new Money(amount + x, history);
    }
}

동시성 버그는 공유된 가변 상태에서 생깁니다. 상태가 바뀌지 않으면 여러 스레드가 동시에 읽어도 경쟁 상태가 생길 수 없습니다.

클래스를 final로, 필드를 private final로 두고, 가변 컬렉션은 복사해서 받습니다. 바꾸고 싶으면 새 객체를 돌려줍니다. String이 바로 이런 클래스입니다.

스레드 풀에서 ThreadLocal은 지워야 한다

ThreadLocal은 스레드마다 따로 값을 두는 저장소입니다. 요청마다 스레드 하나가 처리하는 서버에서 로그인 사용자나 트랜잭션 정보를 넘기는 데 씁니다.

그런데 서버의 스레드는 풀에서 재사용됩니다. 요청이 끝나도 값을 지우지 않으면 다음 요청이 이전 사용자의 정보를 읽습니다. 큰 객체라면 스레드가 살아 있는 동안 메모리도 회수되지 않습니다.

try {
    CTX.set(user);
    chain.doFilter(req, res);
} finally {
    CTX.remove();  // 반드시
}

메모리 누수이자 보안 사고입니다

다른 사용자의 데이터가 섞여 나가는 장애로 이어질 수 있습니다.

Virtual Thread: 블로킹하면 캐리어에서 내려온다

기존 Java 스레드는 OS 스레드와 1:1이라 수천 개가 한계입니다. JDK 21의 Virtual Thread(JEP 444)는 JVM이 관리하는 가벼운 스레드로, 적은 수의 캐리어 스레드 위에 올라가 실행됩니다.

I/O로 블로킹되면 JVM이 스택을 힙에 떼어 두고 캐리어를 다른 Virtual Thread에 내줍니다. 블로킹 코드를 그대로 쓰면서 1장의 이벤트 루프 같은 효율을 얻습니다.

Virtual Thread는 I/O 대기에만 이득이다

스레드가 무제한에 가까워지면 병목은 4장의 커넥션 풀 같은 하류 자원으로 옮겨 갑니다. 스레드 수가 자연스러운 동시성 제한 역할을 하던 것이 사라지기 때문입니다.

6부

운영 서버에서 JVM 읽기

장애의 상당수는 메모리와 스레드에서 시작됩니다. 힙 크기 설정, GC 지표, 누수 패턴, 덤프를 읽는 감각을 익힙니다.

원리 실무 JVM 옵션, GC 로그, 누수 사례, 덤프 분석을 다룹니다.

컨테이너에서는 힙 기본값부터 의심한다

# 기본: 최대 힙 = 메모리의 1/4
# 2GB 컨테이너면 힙 512MB뿐
ENV JAVA_TOOL_OPTIONS="\
  -XX:MaxRAMPercentage=75 \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/dumps \
  -Xlog:gc*:file=/logs/gc.log"

JVM은 서버급 머신에서 최대 힙을 물리 메모리의 1/4로, CPU 2개 이상이고 메모리 1792MB 이상일 때만 G1을 고릅니다. CPU 1개짜리 컨테이너는 Serial GC로 뜹니다.

힙 비율은 75% 안팎으로 잡고 나머지는 Metaspace, 스레드 스택, 다이렉트 버퍼 몫으로 남깁니다.

GC는 로그와 지표 네 가지로 본다

힙 사용량은 할당과 GC로 톱니 모양을 그립니다. 꼭대기가 아니라 GC 직후의 바닥이 시간이 지나며 올라간다면 회수되지 않는 객체가 쌓이는 누수입니다. 로그는 JDK 9부터 -Xlog:gc*로 통일되었고, Spring 환경에서는 Micrometer의 jvm.gc.pause로 지표를 수집합니다.

Java 메모리 누수는 끊기지 않은 참조다

GC가 있어도 누수는 생깁니다. GC는 닿지 않는 객체만 치우므로, 더 이상 쓰지 않는데 어딘가에서 참조가 남아 있으면 영원히 살아남습니다. 자주 터지는 패턴은 다음과 같습니다.

  • static 컬렉션 캐시: 넣기만 하고 빼지 않는 Map. 크기 제한과 만료가 있는 캐시를 씁니다.
  • ThreadLocal 미삭제: 풀 스레드가 값을 계속 쥐고 있습니다.
  • 리스너, 콜백 미해제: 등록한 쪽이 사라져도 이벤트 소스가 참조를 유지합니다.
  • 닫지 않은 리소스: 커넥션, 스트림은 try-with-resources로 닫습니다.
  • hashCode가 바뀌는 키: 넣은 뒤 필드를 바꾸면 찾을 수도 지울 수도 없습니다.

OOMKilled는 JVM 예외가 아닙니다

커널이 프로세스를 강제 종료하므로 힙 덤프도 남지 않습니다. 힙은 프로세스 메모리의 일부일 뿐입니다(9장 cgroup).

힙 덤프는 그 순간 힙의 사진이다

  1. 확보

    OOM 시 자동(HeapDumpOnOutOfMemoryError) 또는 jcmd <pid> GC.heap_dump.

  2. 열기

    Eclipse MAT 같은 분석 도구로 엽니다.

  3. Retained 크기

    이 객체가 사라지면 함께 회수될 크기순으로 정렬합니다.

  4. GC Root 경로

    누가 붙잡고 있는지 Root까지 참조 사슬을 따라갑니다.

힙 덤프에는 모든 객체와 참조 관계가 담깁니다. 누수 분석은 결국 2부의 도달 가능성을 거꾸로 따라가는 일입니다. 큰 객체를 찾고, 그 객체를 살려 두는 GC Root 경로를 찾습니다.

덤프를 뜨는 동안 STW가 걸리고 파일이 힙 크기만큼 커집니다. 덤프에는 개인 정보도 들어 있으니 취급에 주의합니다.

"서버가 응답이 없다"면 스레드 덤프를 몇 초 간격으로 2~3번 뜹니다. 각 스레드의 상태(RUNNABLE, BLOCKED, WAITING)와 호출 스택이 보입니다.

요청 스레드 대부분이 같은 락에서 BLOCKED이거나 커넥션 풀 대기에서 WAITING이면 원인이 거기에 있습니다. JVM은 데드락을 감지해 직접 알려 줍니다. 전체 진단 순서는 18장에서 다룹니다.

정리

  • JVM은 바이트코드를 실행하는 OS별 엔진입니다. 클래스 로더가 필요할 때 올리고, 인터프리터로 시작해 뜨거운 코드만 JIT이 컴파일합니다.
  • GC는 GC Root에서 닿지 않는 객체를 치웁니다. 대부분 객체가 일찍 죽으므로 Young만 자주 치우고, G1과 ZGC는 STW를 줄이는 방향으로 발전했습니다.
  • equals와 hashCode는 함께 다닙니다. HashMap이 hashCode로 버킷을 고르고, 충돌이 심하면 트리로, 75%가 차면 두 배로 늘리기 때문입니다.
  • 가시성과 원자성은 다른 문제입니다. volatile은 보이게, synchronized와 CAS는 끼어들지 못하게 합니다.
  • 운영에서는 GC 직후 Old 바닥선, 덤프, 컨테이너 기본값을 봅니다. 누수는 끊기지 않은 참조입니다.

스스로 점검 (1)

  1. 스택과 PC 레지스터는 왜 스레드마다 따로 있어야 하나요?

    스레드마다 실행 중인 메서드와 위치가 다르기 때문입니다. 공유하면 서로의 호출 흐름과 지역 변수를 덮어씁니다.

  2. 서로만 참조하는 두 객체는 GC 대상인가요?

    네. Java GC는 참조 개수가 아니라 GC Root에서 닿는지로 판단하므로, Root에서 끊긴 순환 참조는 함께 회수됩니다.

  3. Young 영역을 너무 작게 잡으면 어떤 일이 생기나요?

    Minor GC가 잦아지고, 곧 죽을 객체까지 나이가 차기 전에 Old로 밀려납니다. Old가 빨리 차서 더 비싼 GC가 늘어납니다.

  4. HashMap에 넣은 키 객체의 필드를 나중에 바꾸면 어떻게 되나요?

    hashCode가 바뀌어 다른 버킷을 찾게 되므로 get도 remove도 실패합니다. 엔트리는 그대로 남아 누수가 됩니다.

스스로 점검 (2)

  1. volatile int count에 count++를 하면 안전한가요?

    아닙니다. 읽기, 더하기, 쓰기 사이에 다른 스레드가 끼어들 수 있습니다. AtomicInteger나 synchronized가 필요합니다.

  2. Tomcat 스레드 풀에서 ThreadLocal을 remove하지 않으면 무엇이 보이나요?

    재사용된 스레드에서 다음 요청이 이전 요청의 값을 읽습니다. 다른 사용자 정보가 노출될 수 있습니다.

  3. Virtual Thread로 바꿨더니 DB 커넥션 대기가 폭증했습니다. 왜일까요?

    스레드 수 제한이 사라져 동시 요청이 커넥션 풀로 한꺼번에 몰렸기 때문입니다. 하류 자원 앞에서 동시성을 따로 제한해야 합니다.

  4. 메모리 1GB, CPU 1개 컨테이너에서 옵션 없이 뜬 JVM의 GC와 최대 힙은?

    서버급 조건에 못 미쳐 Serial GC가 선택되고, 최대 힙은 메모리의 1/4인 약 256MB입니다.
