1부

코드는 어떻게 CPU 위에서 도는가

4장에서는 서버가 데이터를 맡기는 DB를 봤습니다. 이제 DB에 쿼리를 보내던 그 서버 코드가 실제로 실행되는 바닥으로 갑니다. 이 부에서 풀 질문은 하나입니다. 텍스트 파일인 .java가 어떤 단계를 거쳐 CPU 명령이 되고, 실행 중에 메모리의 어디에 자리 잡는가.

이 장은 주문 API 서버 하나를 따라간다

  1. POST /orders클라이언트의 주문 요청
  2. OrderController요청을 받아 넘김
  3. OrderService재고 확인, 주문 생성
  4. StockService재고 수량 차감
  5. Repository4장의 DB에 저장

장 전체에서 예제 하나를 계속 씁니다. Java로 만든 쇼핑몰의 주문 API 서버입니다. 사용자가 주문 버튼을 누르면 HTTP 요청(2장)이 서버에 도착하고, 서버 안에서는 위 그림처럼 클래스 몇 개가 차례로 호출되어 재고를 줄이고 주문을 DB에 저장합니다.

1부에서는 이 클래스들이 어떻게 실행 가능한 상태가 되는지, 2부에서는 요청마다 만들어지는 객체가 어떻게 치워지는지, 3~4부에서는 이 코드에 쓰인 언어 규칙과 자료구조가 안에서 어떻게 동작하는지, 5부에서는 요청 수백 개가 동시에 같은 재고를 건드릴 때, 6부에서는 이 서버가 운영 중에 느려지거나 죽을 때를 봅니다.

CPU는 자기 기계어만 알아듣는다

CPU가 직접 실행하는 것은 기계어, 즉 "이 레지스터 값을 저 값과 더하라" 같은 명령을 0과 1로 적은 것입니다. 명령의 종류와 인코딩은 CPU 계열마다 다릅니다. 인텔·AMD의 x86-64와 애플 M 시리즈·AWS Graviton의 ARM64는 같은 덧셈도 전혀 다른 비트로 씁니다.

C 같은 언어는 컴파일, 즉 소스 코드를 특정 CPU의 기계어로 미리 번역해 실행 파일을 만듭니다. 기계어는 OS가 제공하는 기능(파일 열기, 메모리 받기 같은 1장의 시스템 콜)을 부르는 방식까지 담으므로, 실행 파일은 CPU와 OS 조합마다 따로 만들어야 합니다.

서버 프로그램이라면 이것이 꽤 번거롭습니다. 개발자는 macOS 노트북에서, 운영 서버는 Linux x86-64에서, 비용을 줄이려고 옮겨 간 서버는 ARM64에서 돕니다. 1995년에 나온 Java는 이 문제를 "번역을 두 단계로 나누자"는 발상으로 풀었습니다.

컴파일은 한 번, 실행은 각 OS의 JVM이

Java 컴파일러 javac는 소스를 특정 CPU의 기계어가 아니라 바이트코드로 번역합니다. 바이트코드는 실제 CPU가 아니라 가상의 CPU를 위한 명령어이고, 결과물은 클래스마다 하나씩 생기는 .class 파일입니다.

바이트코드를 진짜 기계어로 바꿔 실행하는 일은 각 OS·CPU에 맞게 만들어진 JVM이 맡습니다. 그래서 같은 .class 파일이 어느 OS에서든 그대로 돕니다. Kotlin, Scala처럼 바이트코드를 만들어 내는 다른 언어도 같은 JVM 위에서 실행됩니다.

바이트코드는 스택 위에서 계산하는 명령어다

// 소스
static int total(int price) {
    int qty = 3;
    return qty * price;
}
// 바이트코드
0: iconst_3    // 상수 3을 스택에
1: istore_1    // 꺼내 지역 변수 1(qty)에
2: iload_1     // qty를 스택에
3: iload_0     // price를 스택에
4: imul        // 둘을 꺼내 곱하고 결과를
5: ireturn     // 스택 맨 위 값을 반환

javap -c는 .class 파일 안의 바이트코드를 사람이 읽을 수 있게 보여 주는 JDK 도구입니다. 명령 하나가 1바이트 코드로 표현되어 바이트코드라 부릅니다.

눈여겨볼 점은 레지스터가 없다는 것입니다. 값을 피연산자 스택에 쌓고, imul은 맨 위 두 값을 꺼내 곱한 뒤 결과를 다시 쌓습니다. CPU마다 레지스터 개수가 달라도 스택만 있으면 되므로, 어느 CPU로든 옮기기 쉬운 형태입니다.

JVM, JRE, JDK는 겹겹이 포함한다

바이트코드를 실행하는 엔진만으로는 프로그램이 돌지 않습니다. 우리 코드가 쓰는 String, List, 네트워크·파일 API 같은 표준 라이브러리도 있어야 합니다. JVM에 이것을 더한 실행 환경이 JRE이고, JRE에 컴파일러 javac, 압축 파일 도구 jar, 실행 중인 JVM을 진단하는 jcmd 같은 개발 도구까지 더한 것이 JDK입니다.

구분들어 있는 것누가 필요한가
JVM클래스 로더, 메모리 영역, 실행 엔진, GC바이트코드를 실행하는 모든 곳
JREJVM + 표준 라이브러리실행만 하는 환경
JDKJRE + javac, jar, jcmd 등 도구개발과 운영 진단

JDK 11부터 JRE는 따로 배포되지 않습니다

JDK 9에서 표준 라이브러리가 모듈로 쪼개졌고, 필요한 모듈만 담은 런타임을 jlink로 만듭니다. 그런 최소 이미지에는 jcmd가 없을 수 있으니 장애 때 진단할 방법을 미리 정해 두세요(6부).

소스에서 실행까지 다섯 단계를 거친다

  1. javac.java를 .class로
  2. 클래스 로더필요할 때 읽어 들임
  3. 링크와 초기화검증하고 준비
  4. 실행 엔진인터프리터 + JIT
  5. GC안 쓰는 객체 회수

첫 단계는 개발자 컴퓨터나 빌드 서버에서, 나머지는 운영 서버의 JVM 안에서 일어납니다. java -jar order-api.jar로 서버를 띄우면 JVM이 시작되고, 클래스를 하나씩 메모리에 올려 실행합니다.

실행 엔진이 바이트코드를 기계어로 바꿔 돌리는 동안 new로 만든 객체가 메모리에 쌓이고, 더 쓰이지 않는 객체는 GC가 치웁니다. 이 부는 앞의 네 단계를 차례로 보고, GC는 2부 전체를 씁니다.

클래스는 처음 쓰일 때 읽어 들인다

주문 서버를 빌드하면 수백 개의 우리 .class 파일과 수천 개의 라이브러리 .class 파일이 생깁니다. 이들은 보통 JAR, 즉 .class 파일들을 zip으로 묶은 파일에 담깁니다. JVM이 클래스를 찾을 디렉터리와 JAR 목록을 클래스패스라 부릅니다.

JVM은 시작할 때 이것을 한꺼번에 읽지 않습니다. OrderService가 코드에서 처음 쓰이는 순간, 예를 들어 첫 주문 요청이 들어와 new OrderService()가 실행될 때 클래스 로더가 클래스패스에서 OrderService.class를 찾아 메모리에 올립니다. 쓰지 않는 클래스까지 올리면 시작이 느리고 메모리가 낭비되기 때문입니다.

찾지 못하면 ClassNotFoundException이나 NoClassDefFoundError가 납니다. 빌드 때는 있던 라이브러리가 배포한 JAR에서 빠졌을 때 운영 중에야 터지는 오류입니다. 그렇다면 클래스 로더는 하나일까요? 그렇지 않습니다.

클래스 로더는 부모에게 먼저 묻는다

  1. Application 로더

    클래스패스의 우리 코드와 라이브러리 담당. 직접 찾기 전에 부모에게 넘깁니다.

  2. Platform 로더

    java.sql 같은 JDK의 나머지 표준 모듈 담당(JDK 9부터의 이름).

  3. Bootstrap 로더

    java.lang 같은 핵심 클래스 담당. JVM 자체에 내장된 최상위 로더입니다.

  4. 못 찾으면 아래로

    부모가 못 찾았을 때만 자식이 자기 담당 위치에서 찾습니다.

JVM에는 담당 범위가 다른 클래스 로더가 세 겹으로 있고, 요청은 부모 위임 모델을 따릅니다. 자식은 직접 찾기 전에 부모에게 먼저 맡깁니다.

순서를 이렇게 정한 이유는 안전입니다. 누군가 클래스패스에 가짜 java.lang.String을 넣어도 Bootstrap이 먼저 진짜를 올리므로 핵심 클래스를 바꿔치기할 수 없습니다. 같은 클래스가 두 번 올라가는 일도 막습니다.

읽은 뒤에는 검증, 준비, 초기화를 거친다

  1. 검증

    바이트코드가 스택을 넘치게 쓰거나 타입을 속이지 않는지 확인합니다.

  2. 준비

    static 필드 자리를 만들고 0, null 같은 기본값을 채웁니다.

  3. 해석

    "OrderRepository"라는 이름 참조를 실제 클래스 위치로 바꿉니다.

  4. 초기화

    static 필드 대입과 static 블록을 실행합니다. 클래스당 딱 한 번입니다.

앞의 세 단계를 묶어 링크라 합니다. 검증이 있는 이유는 .class 파일이 네트워크나 다른 회사 라이브러리에서 올 수 있기 때문입니다. 손으로 조작한 바이트코드가 JVM 메모리를 망가뜨리지 못하게 실행 전에 막습니다.

초기화는 JVM이 락을 잡고 한 스레드에서만 실행합니다. 그래서 static 필드에 객체를 만들어 두는 방식은 별도 동기화 없이도 한 번만 만들어지며, 싱글톤(객체를 하나만 두는 설계)을 안전하게 만드는 데 쓰입니다.

메모리는 공유 영역과 스레드별 영역으로 나뉜다

클래스가 올라가고 코드가 돌기 시작하면 JVM은 OS에게 받은 메모리를 용도별로 나눠 씁니다. 이것을 런타임 데이터 영역이라 합니다. 1장에서 본 대로 스레드는 힙을 공유하고 스택은 따로 가지는데, JVM도 같은 구조입니다.

힙과 메서드 영역은 모든 스레드가 공유하고, 스택, PC 레지스터, 네이티브 메서드 스택은 스레드마다 하나씩 생깁니다. 공유 영역이라서 5부의 동시성 문제가 생기고, 2부의 GC가 정리하는 곳도 힙입니다.

클래스 정보는 메서드 영역, 지금은 Metaspace에

메서드 영역에는 클래스 로더가 읽어 들인 클래스의 설계도가 놓입니다. 클래스 이름, 필드와 메서드 목록, 메서드의 바이트코드, 그리고 코드에 적힌 상수들입니다. OrderService 객체를 천 개 만들어도 이 정보는 클래스당 한 벌만 있으면 되므로 모든 스레드가 공유합니다.

JDK 7까지는 이 영역이 힙 옆의 PermGen이라는 고정 크기 공간이었습니다. 크기를 시작할 때 정해야 했기 때문에, 클래스를 많이 쓰는 프레임워크에서 PermGen space 오류가 잦았습니다. JDK 8부터는 힙 밖의 OS 메모리(네이티브 메모리)를 필요한 만큼 받아 쓰는 Metaspace로 바뀌었습니다.

기본값으로 상한이 없다는 점은 양날의 칼입니다. 실행 중에 클래스를 계속 새로 만드는 코드가 있으면 Metaspace가 끝없이 자라 컨테이너 메모리를 다 쓸 수 있습니다. 6부의 OOM 종류에서 다시 봅니다.

지역 변수는 스택에, 객체는 힙에 산다

void place(long userId) {
    int qty = 3;          // 스택: 값 자체
    Order o = new Order(qty);
                     // o는 스택: 참조값
                     // Order 객체는 힙
    repo.save(o);
}   // 종료 → 프레임 제거
    // 아무도 Order를 안 가리키면
    // GC 대상

메서드를 호출할 때마다 스레드의 스택에 프레임이 하나 쌓입니다. 앞에서 본 지역 변수 칸과 피연산자 스택이 프레임 안에 있습니다. 객체 자체는 힙에 있고, 변수 o에는 그 위치를 가리키는 참조값만 들어갑니다.

스택은 스레드당 기본 1MB 정도라, 재귀가 끝없이 깊어지면 StackOverflowError가 납니다. 힙이 꽉 차서 새 객체를 놓을 수 없으면 OutOfMemoryError(OOM)가 납니다.

인터프리터는 바로 시작하지만 반복에 약하다

메모리에 올라간 바이트코드는 결국 기계어로 바뀌어야 CPU가 실행할 수 있습니다. JVM의 실행 엔진은 이를 두 가지 방식으로 합니다.

첫째는 인터프리터입니다. 바이트코드 명령을 하나 읽고, 그에 해당하는 동작을 실행하고, 다음 명령을 읽는 일을 반복합니다. 미리 번역할 필요가 없으니 서버가 뜨자마자 실행을 시작할 수 있습니다.

약점은 반복입니다. place()가 초당 1,000번 호출되면 같은 바이트코드를 1,000번 다시 읽고 해석합니다. 해석하는 일 자체가 매번 드는 비용이라, 같은 일을 하는 기계어보다 수십 배 느릴 수 있습니다. 서버 코드는 대부분 같은 경로를 수백만 번 반복하므로, 자주 도는 부분만큼은 기계어로 한 번 번역해 두고 다시 쓰는 편이 훨씬 낫습니다.

JIT은 자주 도는 코드만 기계어로 바꾼다

  1. 세기

    메서드마다 호출 횟수와 반복문 회전 수를 셉니다.

  2. C1 컴파일

    문턱을 넘은 메서드를 빠르게, 가볍게 최적화해 기계어로 만듭니다.

  3. C2 컴파일

    계속 뜨거운 메서드는 실행 정보를 써서 강하게 최적화합니다.

  4. 코드 캐시

    만든 기계어를 보관하고, 이후 호출은 해석 없이 바로 실행합니다.

그 일을 하는 것이 JIT 컴파일러입니다. 실행 도중, 필요한 시점에 컴파일한다는 뜻입니다. 대상은 자주 호출되는 뜨거운 메서드뿐입니다. 한 번만 도는 시작 코드까지 컴파일하면 번역 비용이 실행 비용보다 커지기 때문입니다.

오늘날 표준 JVM인 HotSpot은 빠른 컴파일러 C1과 느리지만 최적화가 강한 C2를 차례로 쓰는 계층형 컴파일이 기본입니다.

JIT은 실행해 본 정보로 과감하게 최적화한다

미리 컴파일하는 C와 달리 JIT은 실제 실행을 지켜본 뒤 컴파일합니다. 예를 들어 payment.pay()가 지금까지 늘 카드 결제였다면, C2는 호출 대신 카드 결제 코드를 그 자리에 붙여 넣습니다. 이것이 인라이닝이고, 호출 비용이 사라지며 다른 최적화의 출발점이 됩니다.

가정이 깨지면, 예를 들어 처음으로 포인트 결제가 들어오면, 그 기계어를 버리고 인터프리터로 돌아갑니다. 이를 탈최적화라 하며, 덕분에 틀릴 수 있는 공격적인 가정도 안전하게 씁니다.

배포 직후 첫 요청들은 느립니다

아직 JIT이 코드를 컴파일하지 않은 웜업 구간이라 지연이 튑니다. 트래픽을 받기 전에 주요 API를 미리 호출해 두는 이유입니다.

1부를 마치며

코드는 이제 실행됩니다. 실행될 때마다 힙에는 객체가 쌓입니다. 2부는 그 객체들이 어떻게 치워지는지 봅니다.

2부

요청마다 만든 객체는 누가 언제 치우는가

주문 요청 하나를 처리하면 힙에 객체 수십 개가 생깁니다. 이 부의 질문은 세 가지입니다. 어떤 객체가 쓰레기인지 어떻게 판단하나, 어떻게 치우나, 치우는 동안 왜 주문 API의 응답이 멈추나.

기초 원리 여기부터는 GC 알고리즘과 JVM 내부 동작을 다룹니다.

메모리를 직접 돌려주던 시절의 두 가지 사고

C에서는 malloc()으로 힙 메모리를 받고, 다 쓰면 free()로 직접 돌려줘야 합니다. 이 책임이 사람에게 있으면 두 가지 사고가 반복됩니다.

하나는 돌려주는 것을 잊는 것입니다. 주문 하나마다 1KB씩 잊으면 하루 100만 건에 1GB가 사라지고, 서버는 결국 메모리가 바닥나 죽습니다. 다른 하나는 너무 일찍 돌려주는 것입니다. 아직 누군가 쓰고 있는 메모리를 해제하면 그 자리에 다른 데이터가 들어오고, 옛 위치를 가리키던 포인터(댕글링 포인터)는 엉뚱한 값을 읽거나 덮어씁니다. 이런 버그는 재현이 어렵고 보안 구멍이 되기도 합니다.

Java는 이 책임을 사람에게서 빼앗았습니다. 개발자는 new로 만들기만 하고, 언제 돌려줄지는 JVM이 판단합니다. 이 자동 회수가 가비지 컬렉션(GC)입니다. 그렇다면 JVM은 "이제 아무도 안 쓴다"를 어떻게 알아낼까요?

GC Root에서 닿지 않으면 쓰레기다

JVM은 확실히 살아 있는 출발점을 정해 둡니다. 실행 중인 스택 프레임의 지역 변수, 클래스의 static 필드, C 코드(JNI, Java와 C를 잇는 인터페이스)가 쥔 참조 등이고, 이를 GC Root라 합니다. 여기서 참조를 따라가 닿는 객체만 살아 있다고 보는 것이 도달 가능성 판정입니다.

참조 개수를 세는 방식은 서로만 가리키는 D와 E를 영영 못 치웁니다. 도달 가능성으로 보면 Root에서 끊긴 순환 참조도 함께 회수됩니다.

표시하고, 쓸고, 압축한다

  1. Mark

    GC Root부터 참조를 따라가며 살아 있는 객체에 표시합니다.

  2. Sweep

    표시되지 않은 객체가 차지한 공간을 빈 공간 목록에 돌려놓습니다.

  3. Compact

    살아남은 객체를 한쪽으로 몰아 흩어진 빈 공간을 하나로 합칩니다.

판정 방법을 알았으니 회수 방법입니다. 가장 기본은 위의 세 단계입니다. Sweep만 하면 빈 공간이 여기저기 흩어집니다. 1장의 외부 단편화, 즉 빈 공간의 합은 충분한데 연속된 덩어리가 없어 큰 배열을 못 놓는 상황이 생깁니다.

Compact가 이를 해결하지만, 객체를 옮기면 그 객체를 가리키던 모든 참조의 주소를 고쳐야 해 비용이 큽니다.

살아남은 것만 옮기는 복사 방식도 있다

Mark-Sweep-Compact의 비용은 힙 전체를 훑는 데서 옵니다. 죽은 객체가 차지한 공간까지 모두 지나가야 하기 때문입니다. 다른 발상은 공간을 두 칸으로 나누고, 한 칸에만 객체를 할당하다가 가득 차면 살아 있는 객체만 빈 칸으로 복사한 뒤 원래 칸을 통째로 비우는 것입니다. 이를 복사 수집이라 합니다.

이 방식의 비용은 죽은 객체 수가 아니라 살아 있는 객체 수에 비례합니다. 1,000개 중 990개가 죽었다면 10개만 옮기면 끝입니다. 옮기면서 자연스럽게 빈틈 없이 붙여 놓으므로 단편화도 생기지 않습니다.

대가는 공간입니다. 복사받을 칸을 늘 비워 둬야 합니다. 그래서 복사 수집은 대부분이 죽어 있는 공간에서만 이득입니다. 그런 공간이 정말 있을까요? 그 답이 조금 뒤에 볼 세대별 GC입니다. 그 전에, 어느 방식이든 피할 수 없는 비용 하나를 봅니다.

Stop-The-World: GC는 애플리케이션을 멈춘다

GC가 객체 그래프를 표시하는 도중에 주문 처리 스레드가 참조를 바꾸면, 살아 있는 객체를 쓰레기로 잘못 판단할 수 있습니다. 객체를 옮기는 중이라면 더 위험합니다. 그래서 GC는 모든 애플리케이션 스레드를 멈춥니다. 이것이 Stop-The-World(STW)입니다.

스레드는 아무 데서나 멈추지 않고, 참조 위치를 JVM이 정확히 아는 안전 지점에 도착해서 멈춥니다. 멈춘 동안에는 요청이 처리되지 않으므로 STW 시간이 곧 응답 지연입니다.

현대 GC의 방향

멈추지 않을 수는 없으니, 표시 같은 무거운 일을 애플리케이션과 동시에(concurrent) 하고 STW 구간만 짧게 남깁니다.

null 대입은 즉시 회수가 아닙니다

참조를 끊어 회수 대상이 될 뿐, 실제 회수는 다음 GC 때입니다. System.gc()도 요청일 뿐 보장이 아닙니다.

GC의 성적표는 처리량과 정지 시간이다

GC를 고르거나 설정할 때는 두 숫자를 봅니다. 처리량은 전체 실행 시간 중 애플리케이션이 실제 일을 한 비율입니다. 1분 중 GC가 3초를 썼다면 처리량은 95%입니다. 정지 시간은 STW 한 번이 얼마나 긴가입니다.

둘은 대개 맞바꿔집니다. 쓰레기를 모았다가 한 번에 몰아서 치우면 GC 작업 자체는 효율적이라 처리량이 높지만, 그 한 번이 깁니다. 반대로 애플리케이션과 번갈아 조금씩, 또는 동시에 치우면 정지는 짧아지지만 조율 비용 때문에 전체 CPU를 더 씁니다. 힙을 넉넉히 주면 둘 다 좋아지지만 메모리 비용이 듭니다.

어느 쪽이 중요한지는 서비스가 정합니다. 밤새 도는 정산 배치는 총 시간이 짧으면 그만이니 처리량이, 주문 API처럼 사용자가 기다리는 서버는 정지 시간이 중요합니다. 이 관점으로 JVM이 실제로 힙을 나누는 방식을 봅니다.

대부분의 객체는 금방 죽는다

매번 힙 전체를 표시하면 힙이 클수록 STW가 길어집니다. GC 설계자들은 실제 프로그램을 관찰해 실마리를 얻었습니다. 약한 세대 가설은 두 가지입니다. 대부분의 객체는 만들어지고 곧 쓸모가 없어진다, 그리고 오래된 객체가 새 객체를 가리키는 경우는 드물다.

주문 서버로 확인해 봅시다. 요청 하나를 처리하며 JSON을 담아 옮기는 객체(DTO), 임시 문자열, 반복문의 반복자를 만들지만, 응답이 나가는 순간 모두 쓰레기가 됩니다. 반면 상품 정보 캐시나 서버 전체에 하나뿐인 설정 객체는 서버가 꺼질 때까지 삽니다.

그렇다면 힙을 나이별로 나눠 젊은 영역만 자주 치우면 됩니다. 젊은 영역은 대부분 죽어 있으니, 앞에서 본 복사 수집이 딱 맞습니다.

Eden에서 태어나 Survivor를 거쳐 Old로

힙은 새 객체를 위한 Young 영역과 오래 산 객체를 위한 Old 영역으로 나뉩니다. Young은 다시 새 객체가 할당되는 Eden과, 복사 수집의 두 칸 역할을 하는 Survivor 두 개로 나뉩니다.

Eden이 차면 Young만 치우는 Minor GC가 일어납니다. 여러 번 살아남은 객체는 Old로 승격됩니다.

Minor GC 한 번을 따라가 보자

  1. Eden 가득 참

    주문 요청 수천 건이 만든 객체로 Eden이 찹니다. 새 할당이 실패하면 GC가 시작됩니다.

  2. 표시

    GC Root와 Old에서 Young을 가리키는 참조에서 출발해 살아 있는 Young 객체를 찾습니다.

  3. 복사

    Eden과 Survivor 0의 생존자를 빈 Survivor 1로 복사하고 나이를 1 올립니다.

  4. 승격

    나이가 임계값에 닿았거나 Survivor에 자리가 없으면 Old로 보냅니다.

  5. 비우기

    Eden과 Survivor 0을 통째로 빈 공간으로 만듭니다. 두 Survivor는 역할을 바꿉니다.

Eden에 객체 10만 개가 있어도 진행 중인 요청이 쥔 수백 개만 살아 있다면, 복사할 것은 그 수백 개뿐입니다. 그래서 Minor GC는 보통 수 밀리초 안에 끝납니다.

임계 나이는 MaxTenuringThreshold로 정하며 기본 15입니다. 객체 헤더의 나이 칸이 4비트라 15가 상한입니다. 2단계의 "Old에서 Young을 가리키는 참조"는 바로 다음 슬라이드에서 봅니다.

Old가 Young을 가리키는 곳은 따로 적어 둔다

Minor GC는 Young만 보려고 하는데 함정이 하나 있습니다. Old에 있는 상품 캐시가 방금 만든 Young 객체를 가리키고 있다면, 그 Young 객체는 살아 있어야 합니다. 그렇다고 이를 확인하려고 Old 전체를 훑으면 Young만 치우는 의미가 사라집니다.

JVM은 Old를 512바이트 단위의 칸(카드)으로 나누고, Old 객체의 참조 필드에 값이 쓰일 때마다 그 칸에 "더러움" 표시를 남깁니다. 이 표시 모음이 카드 테이블이고, 참조 필드를 쓸 때 끼어들어 표시를 남기는 짧은 코드를 쓰기 배리어라 합니다. Minor GC는 표시된 칸만 훑어 Old에서 들어오는 참조를 Root처럼 다룹니다.

약한 세대 가설의 두 번째 항목, 오래된 객체가 새 객체를 가리키는 일은 드물다는 관찰 덕분에 표시된 칸은 적고, 이 확인은 싸게 끝납니다.

Minor, Major, Full GC는 범위가 다르다

Young을 치우는 것이 Minor GC라면, Old가 차면 Old도 치워야 합니다. Old는 오래 사는 객체가 대부분이라 복사 수집이 맞지 않고, 크기도 커서 더 비쌉니다. 힙 전체와 Metaspace까지 한꺼번에 정리하는 것은 Full GC라 부릅니다.

구분대상언제정지 시간

Major GC라는 이름은 GC마다 쓰는 뜻이 조금씩 다르니, 로그에서는 무엇을 치웠는지와 STW가 얼마였는지를 보는 습관이 중요합니다. 운영에서 Full GC는 대개 "무언가 잘못됐다"는 신호입니다.

GC 구현은 처리량과 정지 시간 사이의 선택이다

세대 구분이라는 뼈대 위에서, JVM은 여러 GC 구현을 제공해 왔습니다. 각각이 앞에서 본 처리량과 정지 시간 중 무엇을 택했는지로 읽으면 쉽습니다.

Serial GC는 GC 스레드 하나로 모든 일을 STW 안에서 합니다. 단순하고 메모리를 적게 써서 CPU가 하나뿐인 작은 환경에 맞습니다. Parallel GC는 같은 일을 여러 스레드로 나눠 STW를 줄였지만 여전히 전부 멈춘 상태에서 합니다. 처리량은 가장 좋아 배치 작업에 맞고, JDK 8까지 기본이었습니다.

CMS는 Old의 표시를 애플리케이션과 동시에 하는 첫 시도였습니다. 정지는 줄었지만 압축을 하지 않아 단편화가 쌓이다 결국 긴 Full GC가 터지는 약점이 있었고, JDK 14에서 제거되었습니다.

G1은 힙을 작은 조각으로 나눠 "정해 둔 정지 시간 안에서 할 수 있는 만큼" 치우는 방식으로 균형을 잡았고, JDK 9부터 기본입니다. ZGC는 객체 이동까지 동시에 해 정지 시간을 1ms 아래로 끌어내렸습니다. 다음 표에서 정리하고, G1과 ZGC는 이어서 자세히 봅니다.

출처: OpenJDK JEP 248(G1 기본), JEP 363(CMS 제거), JEP 377(ZGC 정식). JDK 21 GC 튜닝 가이드 기준 G1은 서버급 머신에서 기본입니다.

G1은 힙을 리전으로 쪼개 쓰레기가 많은 곳부터

G1은 힙을 같은 크기의 리전 약 2,048개로 나누고(리전 크기는 1MB 이상의 2의 거듭제곱), 각 리전에 Eden, Survivor, Old 역할을 그때그때 붙입니다. 세대는 고정된 구역이 아니라 리전의 꼬리표입니다.

목표 정지 시간(MaxGCPauseMillis, 기본 200ms) 안에서 쓰레기가 가장 많은 리전부터 골라 치웁니다. 이름이 Garbage-First인 이유입니다.

G1의 한 주기: Young 수집, 동시 표시, Mixed

  1. Young 수집

    Eden 리전이 차면 STW로 생존자를 Survivor, Old 리전으로 복사합니다.

  2. 동시 표시 시작

    Old가 힙의 약 45%를 넘으면, 애플리케이션과 함께 Old의 생존 객체를 표시합니다.

  3. 리전 점수 매기기

    Old 리전마다 쓰레기 비율을 계산해 회수 효율 순으로 줄을 세웁니다.

  4. Mixed 수집

    Young과 함께 효율 좋은 Old 리전 일부를 여러 번에 나눠 복사·회수합니다.

  5. Full GC

    회수가 할당을 못 따라가면 최후 수단으로 힙 전체를 STW로 압축합니다.

G1의 핵심은 Old를 한 번에 치우지 않는다는 점입니다. 동시 표시로 "어느 리전이 쓰레기투성이인지"를 미리 알아 두고, 목표 정지 시간 안에 들어갈 만큼만 골라 Young 수집에 얹습니다.

객체를 옮기는 복사 단계는 여전히 STW 안에서 합니다. 이 마지막 정지까지 없애려는 것이 ZGC입니다.

ZGC는 객체를 옮기는 일까지 동시에 한다

애플리케이션이 돌고 있는데 객체를 옮기면, 스레드가 옛 주소로 객체를 읽으려 할 수 있습니다. ZGC는 참조를 힙에서 읽을 때마다 끼어드는 짧은 코드, 로드 배리어로 이를 해결합니다.

ZGC는 참조값 안의 몇 비트에 "이 참조가 최신 주소인가"를 적어 둡니다(색칠된 포인터). 로드 배리어는 그 비트를 보고, 옮겨진 객체라면 새 주소를 찾아 참조를 고친 뒤 넘겨줍니다. 그래서 STW에는 GC Root를 훑는 일 정도만 남고, 정지 시간이 힙 크기와 거의 무관하게 1ms 미만으로 유지됩니다.

공짜는 아닙니다

참조를 읽을 때마다 배리어가 돌고, GC가 애플리케이션과 동시에 CPU를 쓰므로 처리량을 조금 내줍니다. 앞에서 본 맞바꿈 그대로입니다.

G1과 ZGC 중 무엇을 고를까

ZGC는 빠르게 발전했습니다. 처음에는 세대 구분이 없어 매번 힙 전체를 표시했는데, JDK 21에서 약한 세대 가설을 적용한 세대별 모드가 추가되며 CPU 효율이 크게 좋아졌습니다.

선택 기준은 정지 시간 요구입니다. 주문 API가 가장 느린 요청까지 수백 ms 안에만 응답하면 된다면 G1의 수십 ms 정지는 문제가 되지 않습니다. 수십 GB 힙에 10ms 이하 응답이 필요한 서비스라면 ZGC를 시험해 볼 만합니다. 어느 쪽이든 6부의 GC 지표로 확인한 뒤 바꿉니다.

  1. JDK 15

    ZGC 정식 기능(JEP 377). -XX:+UseZGC로 켭니다.

  2. JDK 21

    세대별 ZGC 추가(JEP 439). Young만 자주 치울 수 있게 됩니다.

  3. JDK 23~24

    세대별 모드가 기본(JEP 474), 24에서 비세대 모드 제거(JEP 490).

3부

언어 규칙을 메모리 구조로 다시 읽는다

1~2부에서 객체가 힙에 살고 변수는 참조만 쥔다는 것을 봤습니다. 이 그림을 알면 Java의 언어 규칙이 왜 그렇게 정해졌는지 보입니다. 주문 서버의 코드를 설계하는 원칙(객체지향, SOLID)부터 값 전달, String, equals와 hashCode까지 봅니다.

객체는 데이터와 그 데이터의 규칙을 함께 묶는다

public class Order {
    private Status status = Status.PAID;
    private final long amount;

    public void cancel() {
        if (status == Status.SHIPPED)
            throw new IllegalStateException(
                "배송된 주문은 취소 불가");
        status = Status.CANCELED;
    }
}

객체지향 프로그래밍(OOP)은 데이터와 그 데이터를 바꾸는 규칙을 한 단위, 즉 객체로 묶는 방식입니다. class는 그 설계도이고, new로 만든 것이 힙에 사는 객체입니다.

status를 private으로 숨겼기 때문에 바깥 코드는 cancel()을 거쳐서만 상태를 바꿀 수 있고, "배송된 주문은 취소 불가" 규칙이 깨질 수 없습니다. 이것이 캡슐화입니다.

상속은 물려받기, 추상화는 핵심만 남기기

OOP의 나머지 특징 셋 중 두 가지를 먼저 봅니다. 상속은 기존 클래스의 필드와 메서드를 물려받아 새 클래스를 만드는 것입니다. class GiftOrder extends Order라고 쓰면 선물 주문은 일반 주문의 모든 것을 가지고, 선물 포장 정보만 덧붙입니다. 코드 재사용에 편하지만 부모를 고치면 모든 자식이 영향을 받으므로, 실무에서는 "정말 ~의 한 종류인가(is-a)"가 분명할 때만 씁니다.

추상화는 쓰는 쪽에 필요한 핵심만 드러내고 세부를 감추는 것입니다. 주문 서비스 입장에서 결제는 "금액을 받아 결제한다"는 능력만 중요하고, 카드사 API를 어떻게 부르는지는 몰라도 됩니다. Java에서는 이 "능력의 약속"을 interface로 표현합니다.

추상화가 만든 약속 위에서, 실제로 어떤 구현이 실행될지를 나중에 정하는 성질이 네 번째 특징인 다형성입니다.

다형성은 실행 시점에 메서드를 고르는 것

interface Payment {
    void pay(int won);
}
class Card implements Payment { … }
class Point implements Payment { … }

// 사용자가 고른 결제 수단
Payment p = pickByUser();
p.pay(10_000); // 실제 객체의 pay

다형성은 같은 호출이 실제 객체에 따라 다르게 동작하는 성질입니다. 변수 타입은 Payment지만 JVM은 실행 중에 힙의 실제 객체가 Card인지 Point인지 보고 그 클래스의 pay를 부릅니다. 이를 동적 디스패치라 합니다.

부모의 메서드를 자식이 같은 이름·인자로 다시 정의하는 오버라이딩은 이렇게 실행 때 정해집니다. 이름은 같고 인자 타입이 다른 메서드를 여러 개 두는 오버로딩은 컴파일 때 인자 타입으로 정해집니다.

SOLID는 바뀌는 곳을 가두는 다섯 원칙이다

주문 서버는 계속 바뀝니다. 결제 수단이 늘고, 할인 정책이 바뀌고, 저장소가 바뀝니다. SOLID는 이런 변경이 코드 전체로 번지지 않게 설계하는 다섯 원칙의 머리글자입니다. 앞의 세 가지부터 봅니다.

SRP(단일 책임 원칙): 클래스가 바뀌는 이유는 하나여야 합니다. OrderService가 주문 생성, 이메일 발송, 정산 계산을 다 하면 이메일 문구 수정이 주문 로직 배포가 되고, 한 수정이 다른 기능을 깨뜨립니다. 이메일은 Notifier로 떼어 냅니다.

OCP(개방 폐쇄 원칙): 확장에는 열려 있고 수정에는 닫혀 있어야 합니다. 결제 수단마다 if (type == "CARD") … else if …를 늘리면 새 수단을 넣을 때마다 기존 코드를 고칩니다. 앞의 Payment 인터페이스처럼 새 구현 클래스를 추가하는 것만으로 확장되게 합니다.

LSP(리스코프 치환 원칙): 자식 객체는 부모 자리에 넣어도 똑같이 믿고 쓸 수 있어야 합니다. Payment를 구현한 어떤 클래스가 pay()에서 "지원 안 함" 예외만 던진다면, 호출부는 다시 타입을 검사해야 하고 다형성의 이점이 사라집니다.

ISP와 DIP는 의존의 방향을 정한다

ISP(인터페이스 분리 원칙): 쓰지 않는 메서드에 의존하지 않게, 인터페이스를 쓰는 쪽 기준으로 작게 나눕니다. Payment에 결제, 환불, 정산 리포트, 카드 등록을 다 넣으면 포인트 결제는 카드 등록을 빈 메서드로 채워야 하고, 정산 리포트가 바뀔 때마다 상관없는 클래스까지 다시 컴파일됩니다.

DIP(의존 역전 원칙): 구체 구현이 아니라 추상에 의존합니다. OrderService가 new MySqlOrderRepository()를 직접 부르면 저장소를 바꿀 때 주문 로직을 고쳐야 합니다. 대신 OrderRepository 인터페이스에만 의존하면, 구현이 무엇이든 주문 로직은 그대로입니다. 의존의 화살표가 "주문 → MySQL"에서 "MySQL 구현 → 인터페이스"로 뒤집히기 때문에 역전이라 부릅니다.

그런데 DIP를 지키면 질문이 남습니다. OrderService 안에서 구현을 new하지 않는다면, 실제 구현 객체는 누가 만들어서 넣어 주는가. 이 일을 대신하는 것이 6장 Spring의 의존성 주입입니다.

다섯 원칙을 한 표로 정리한다

원칙핵심어기면
SRP 단일 책임바뀌는 이유는 하나한 수정이 여러 기능을 깸
OCP 개방 폐쇄확장엔 열고 수정엔 닫음결제 수단마다 if 추가
LSP 리스코프 치환자식은 부모 자리에 대체 가능하위 타입에서 예외 폭발
ISP 인터페이스 분리쓰지 않는 메서드에 의존 금지빈 구현 메서드 양산
DIP 의존 역전구현 말고 추상에 의존구현 교체 시 호출부 수정

다섯 원칙의 공통점은 "바뀔 곳과 안 바뀔 곳 사이에 인터페이스라는 경계를 둔다"는 것입니다. 그 경계를 만드는 도구가 인터페이스와 추상 클래스입니다. 둘은 비슷해 보이지만 쓰임이 다릅니다.

인터페이스는 역할, 추상 클래스는 공통 뼈대

추상 클래스는 일부 메서드를 구현하지 않은 채 남겨 둔 클래스로, 직접 new할 수 없고 상속해서 완성합니다. 필드와 생성자를 가질 수 있어 같은 계열 클래스의 공통 상태와 로직을 담기에 좋습니다. 인터페이스는 상태 없이 능력만 약속하며, Java 8부터는 구현을 담은 default 메서드도 둘 수 있습니다.

항목인터페이스추상 클래스
다중 상속여러 개 구현 가능하나만 상속
상태(필드)상수만인스턴스 필드 가능
구현 코드default 메서드(Java 8+)일반 메서드 자유롭게
관계할 수 있다(can-do)이다(is-a)

실무에서는 인터페이스로 계약을 정하고, 구현들 사이에 공통 코드가 많을 때만 추상 클래스로 묶는 편이 유연합니다. 클래스는 하나만 상속할 수 있어 추상 클래스를 쓰면 그 자리를 써 버리기 때문입니다.

Java는 언제나 값을 복사해 넘긴다

설계 원칙에서 다시 메모리로 돌아옵니다. 메서드에 객체를 넘기면 객체가 아니라 참조값의 복사본이 넘어갑니다. 두 변수가 같은 힙 객체를 가리키므로 필드를 바꾸면 호출자도 그 변화를 봅니다.

하지만 매개변수에 새 객체를 대입하면 복사본만 바뀝니다. 호출자의 변수는 여전히 원래 객체를 가리킵니다. 그래서 Java는 변수 자체를 넘기는 Call by Reference가 아니라 Call by Value입니다.

String은 불변이라 마음 놓고 공유한다

String a = "PAID";   // String Pool
String b = "PAID";   // 같은 객체 재사용
String c = new String("PAID"); // 새 객체
a == b;      // true  (같은 주소)
a == c;      // false (다른 주소)
a.equals(c); // true  (같은 내용)

참조를 공유하면 한쪽의 변경이 다른 쪽에 보인다는 것을 방금 봤습니다. String은 이 문제를 아예 없앴습니다. 한 번 만들면 내용을 바꿀 수 없는 불변 객체입니다.

그래서 같은 리터럴은 힙의 String Pool에 하나만 두고 공유해도 안전합니다. 해시값을 한 번 계산해 캐시해 두니 HashMap 키로 쓰기 좋고, 여러 스레드가 동시에 읽어도 문제가 없습니다.

문자열을 반복해서 붙일 때는 StringBuilder

// 나쁨: 반복마다 새 String
String csv = "";
for (Order o : orders)
    csv += o.id() + ",";

// 좋음: 내부 버퍼 하나에 덧붙임
StringBuilder sb = new StringBuilder();
for (Order o : orders)
    sb.append(o.id()).append(',');
String csv2 = sb.toString();

불변의 대가는 변경 비용입니다. 문자열을 "바꾸는" 연산은 사실 새 String을 만듭니다. 주문 1만 건을 CSV로 내보내며 +=로 이어 붙이면 반복마다 지금까지의 내용을 통째로 복사한 새 객체가 생기고, 복사량이 건수의 제곱으로 늘어납니다.

StringBuilder는 바꿀 수 있는 버퍼에 덧붙이다가 마지막에 한 번 String으로 만듭니다. 동기화가 붙은 옛 버전 StringBuffer는 요즘 거의 쓰지 않습니다.

==는 주소를, equals는 내용을 비교한다

final class OrderId {
    private final long value;
    OrderId(long v) { value = v; }
    public boolean equals(Object o) {
        return o instanceof OrderId x
            && x.value == value;
    }
    public int hashCode() {
        return Long.hashCode(value);
    }
}

앞 슬라이드의 a == c가 false였던 이유는 ==가 두 참조가 같은 힙 객체인지 보기 때문입니다. 내용이 같은지는 equals()로 비교합니다.

모든 클래스가 물려받는 기본 equals()는 ==와 같습니다. 주문 번호 12번을 뜻하는 OrderId 두 개를 같다고 보려면 위처럼 재정의해야 합니다. 그런데 왜 hashCode()까지 함께 바꿨을까요?

equals를 바꾸면 hashCode도 바꿔야 한다

규약은 equals가 같으면 hashCode도 같아야 한다입니다. 3장에서 본 해시 테이블은 키의 해시값으로 버킷(칸)을 먼저 고르고, 그 버킷 안에서만 키를 비교합니다. Java의 HashMap도 hashCode로 버킷을 고르고 버킷 안에서 equals로 비교합니다.

hashCode를 그대로 두면 기본 구현이 객체마다 다른 값을 돌려주므로, 내용이 같은 두 OrderId가 다른 버킷으로 가서 서로를 영영 만나지 못합니다.

equals만 재정의하면

HashSet에 같은 주문 번호가 중복으로 들어가고, 넣은 키와 같은 내용의 키로 get()을 해도 null이 나옵니다.

값 객체는 record로

Java 16의 record OrderId(long value) {} 한 줄이 필드 기반 equals, hashCode를 만들고 필드를 final로 묶어 불변 객체가 됩니다.

4부

매일 쓰는 도구는 안에서 어떻게 움직이나

3부 끝에서 HashMap이 hashCode와 equals에 기댄다는 것을 봤습니다. 이 부는 3장의 해시 테이블 원리가 Java HashMap에서 실제로 어떻게 구현됐는지를 중심으로, 주문 서버 코드에 늘 등장하는 예외, 제네릭, 람다와 Stream, 그리고 Spring의 토대인 리플렉션까지 봅니다.

컬렉션 프레임워크는 약속과 구현을 나눴다

주문 목록, 장바구니의 상품 집합, 상품 ID로 찾는 캐시처럼 서버 코드는 늘 여러 객체를 묶어 다룹니다. Java는 이런 묶음을 컬렉션 프레임워크로 표준화했습니다.

핵심 설계는 3부에서 본 추상화 그대로입니다. "무엇을 보장하는가"는 인터페이스(List, Set, Map, Queue)가 정하고, "어떻게 저장하는가"는 구현 클래스가 정합니다. 코드를 List<Order> orders = new ArrayList<>()처럼 인터페이스 타입으로 쓰면, 나중에 구현을 바꿔도 나머지 코드는 그대로입니다.

구현을 고를 때는 3장의 Big-O, 즉 데이터가 n개로 늘 때 연산 시간이 얼마나 빨리 느는지를 봅니다. 다음 표에서 O(1)은 개수와 무관하게 일정, O(log n)은 정렬된 트리를 타고 내려가는 시간입니다.

List, Set, Map, Queue는 무엇을 보장하나

인터페이스보장대표 구현조회
List순서 유지, 중복 허용ArrayList인덱스 O(1)
Set중복 금지HashSet, TreeSet평균 O(1) / O(log n)
Map키 중복 금지HashMap, TreeMap평균 O(1) / O(log n)

이름에 Hash가 붙은 구현은 해시 테이블, Tree가 붙은 구현은 3장의 Red-Black 트리(회전으로 높이를 log n에 묶는 균형 트리)라 키가 정렬된 순서로 나옵니다. ArrayDeque는 양 끝에서 넣고 빼는 배열 기반 큐, PriorityQueue는 늘 가장 작은 값을 먼저 꺼내는 큐입니다. HashSet은 내부적으로 HashMap의 키만 쓰는 구현이라, HashMap을 이해하면 둘 다 이해됩니다.

ArrayList가 대개 LinkedList보다 빠른 이유

3장에서 배열과 연결 리스트를 비교했습니다. 이론상 연결 리스트는 중간 삽입이 O(1)이라 유리해 보이지만, 그 위치까지 찾아가는 데 O(n)이 듭니다. 그리고 3장에서 본 캐시 지역성, 즉 CPU가 메모리를 덩어리째 캐시로 가져오므로 붙어 있는 데이터를 차례로 읽는 것이 훨씬 빠르다는 사실이 차이를 벌립니다.

ArrayList는 내부 배열에 참조를 나란히 둡니다. LinkedList는 원소마다 앞뒤 포인터를 가진 노드 객체를 힙 여기저기에 만듭니다. 원소 하나당 객체가 하나 더 생기니 메모리도 더 들고, 2부에서 본 GC가 훑을 객체도 늘어납니다.

그래서 주문 목록처럼 순서대로 쌓고 훑는 용도에는 거의 항상 ArrayList를, 양 끝에서 넣고 빼는 큐가 필요하면 ArrayDeque를 씁니다. 이제 서버 코드에서 가장 많이 쓰이는 HashMap 안으로 들어갑니다.

HashMap의 put은 네 단계로 동작한다

  1. 해시 계산

    키의 hashCode()를 받아 비트를 한 번 섞습니다.

  2. 버킷 선택

    섞은 해시로 내부 배열 table의 칸 번호를 고릅니다.

  3. 버킷 안 비교

    칸이 비면 바로 넣고, 아니면 노드들과 equals로 비교해 같은 키면 값을 덮어씁니다.

  4. 크기 확인

    원소 수가 한도를 넘으면 배열을 두 배로 키웁니다.

주문 서버가 상품 정보를 Map<Long, Product>에 캐시해 둔다고 합시다. put(42L, product)는 위 네 단계를 거칩니다. 내부 배열의 각 칸이 3장의 버킷이고, 버킷에는 키·값·해시를 담은 노드가 들어갑니다.

1, 2단계에서 왜 그냥 나머지 연산을 쓰지 않는지, 3단계에서 충돌이 쌓이면 어떻게 하는지, 4단계의 한도가 얼마인지를 차례로 봅니다.

해시를 섞은 뒤 비트 AND로 버킷을 고른다

static final int hash(Object key) {
    int h;
    return (key == null) ? 0
      : (h = key.hashCode()) ^ (h >>> 16);
}
// 버킷 번호: n은 2의 거듭제곱
int i = (n - 1) & hash;
// n=16 → n-1 = 0b1111
// hash가 ...0110_1011 이면
// i = 0b1011 = 11번 칸

HashMap은 배열 크기 n을 늘 2의 거듭제곱으로 유지합니다(기본 16). 그러면 hash % n 대신 (n-1) & hash, 즉 해시의 하위 4비트만 잘라 내는 연산으로 칸을 고를 수 있고, 나눗셈보다 훨씬 빠릅니다.

문제는 하위 비트만 본다는 점입니다. 상위 비트만 다른 키들은 모두 같은 칸에 몰립니다. 그래서 h >>> 16(부호 없이 오른쪽으로 16칸 밀기)으로 상위 16비트를 내려 XOR(두 비트가 다르면 1)로 섞어, 상위 비트의 차이도 칸 번호에 반영되게 합니다.

충돌이 쌓이면 리스트를 트리로 바꾼다

섞어도 충돌은 생깁니다. HashMap은 3장의 체이닝, 즉 같은 칸의 노드를 연결 리스트로 잇는 방식을 씁니다. 리스트가 길어지면 그 칸의 조회가 O(n)으로 느려집니다.

Java 8부터는 한 칸의 노드가 8개 이상이고 배열 크기가 64 이상이면 Red-Black 트리로 바꿔 O(log n)을 보장합니다. 배열이 작으면 트리 대신 배열부터 키우고, 6개 이하로 줄면 다시 리스트로 돌아갑니다.

75%가 차면 배열을 두 배로 늘린다

  1. 임계값 확인

    원소 수가 용량 × load factor(기본 0.75)를 넘으면 리사이징합니다.

  2. 두 배 배열

    16 → 32처럼 2의 거듭제곱을 유지합니다.

  3. 노드 재배치

    hash & 기존 용량, 비트 하나로 제자리 또는 +기존 용량 자리로 나눕니다.

3장에서 load factor(원소 수 ÷ 버킷 수)가 높아지면 충돌이 늘어 모든 키를 새 배열로 옮기는 재해싱을 한다고 했습니다. 기본 용량 16이면 13번째 원소에서 32로 늘어납니다.

HashMap은 크기가 두 배가 되면 칸 번호에 비트가 하나 더 쓰인다는 점을 이용해, 해시를 다시 계산하지 않고 그 비트 하나만 보고 옮길지 정합니다. 그래도 전체를 훑는 O(n)이라, 넣을 개수를 알면 new HashMap<>(예상 개수 / 0.75 + 1)로 미리 잡습니다.

공유하는 Map은 ConcurrentHashMap으로

주문 서버는 여러 요청을 여러 스레드로 동시에 처리합니다(5부). 상품 캐시 HashMap에 두 스레드가 동시에 쓰면 한쪽 갱신이 사라지거나 리사이징 중 구조가 깨집니다. 옛 Hashtable은 모든 메서드를 잠가 한 번에 한 스레드만 쓰게 했고, ConcurrentHashMap은 잠그는 범위를 칸 하나로 줄였습니다.

표의 volatile은 "다른 스레드가 쓴 최신 값이 보이게 하는 표시", CAS는 "잠그지 않고 값이 그대로일 때만 바꾸는 CPU 명령" 정도로 알아 두면 되고, 둘 다 5부에서 자세히 봅니다.

예외는 Throwable 아래 두 갈래로 나뉜다

재고가 부족하거나 DB 연결이 끊기면 주문 처리는 정상 흐름을 이어 갈 수 없습니다. Java는 이런 상황을 예외 객체로 만들어 던지고(throw), 호출 스택을 거슬러 올라가며 처리할 곳(catch)을 찾습니다. 아무도 잡지 않으면 그 스레드의 실행이 끝납니다.

모든 예외의 조상은 Throwable이고, 그 아래가 두 갈래입니다. Error는 OOM이나 StackOverflowError처럼 JVM 수준의 문제라 애플리케이션이 잡아서 복구하기 어렵습니다. Exception은 애플리케이션이 다룰 수 있는 문제입니다.

Exception은 다시 둘로 나뉩니다. RuntimeException과 그 자손(NullPointerException, IllegalArgumentException 등)이 한쪽, 나머지(IOException, SQLException 등)가 다른 쪽입니다. 이 구분이 컴파일러의 태도를 바꿉니다.

복구할 수 있으면 Checked, 버그면 Unchecked

RuntimeException 계열이 아닌 예외는 Checked 예외입니다. 메서드가 이를 던질 수 있으면 throws로 선언해야 하고, 호출하는 쪽은 잡거나 다시 선언해야 컴파일됩니다. 파일이 없거나 네트워크가 끊긴 것처럼 호출자가 대응할 수 있는 상황을 잊지 말라고 강제하는 것입니다.

RuntimeException 계열은 Unchecked 예외입니다. null 참조나 잘못된 인자처럼 코드를 고쳐야 하는 버그라 강제하지 않습니다.

Spring 트랜잭션은 Checked에서 롤백하지 않습니다

기본 규칙은 Unchecked와 Error에서만 롤백입니다. 원리와 rollbackFor 설정은 6장에서 다룹니다.

요즘 흐름

Checked 예외는 선언이 호출 사슬 전체로 번지는 부담이 커서, 최근 라이브러리는 Unchecked로 감싸 던지는 편입니다.

예외는 원인을 보존하고, 자원은 반드시 닫는다

try (Connection c = ds.getConnection();
     PreparedStatement ps = c.prepare(q)) {
    ps.executeQuery();
} catch (SQLException e) {
    throw new ExportFailed("주문 조회 실패",
                           e);  // cause 보존
}   // 블록을 나가면 ps, c 순서로 close()

예외를 잡을 때 가장 흔한 사고는 두 가지입니다. 하나는 catch에서 로그도 없이 넘어가 장애 원인을 지우는 것, 다른 하나는 더 의미 있는 예외로 감싸면서 원래 예외를 버리는 것입니다. 위처럼 생성자에 원래 예외를 cause로 넘기면 스택 트레이스에 원인까지 함께 찍힙니다.

try (...) 괄호 안에 연 자원은 예외가 나든 안 나든 블록을 나갈 때 자동으로 닫힙니다. 이것이 try-with-resources이고, 4장의 커넥션 풀에서 빌린 연결을 돌려주지 않아 풀이 서서히 마르는 누수를 막습니다.

제네릭은 컴파일러만 아는 타입이다

// Java 5 이전: 무엇이든 담기는 List
List raw = new ArrayList();
raw.add("oops");
Order o = (Order) raw.get(0); // 실행 중 폭발

// 제네릭: 컴파일 때 막힘
List<Order> orders = new ArrayList<>();
orders.add("oops"); // 컴파일 오류
Order first = orders.get(0); // 캐스트 불필요

제네릭이 없던 시절 컬렉션은 모든 것을 Object로 담았고, 꺼낼 때마다 직접 형변환(캐스트)해야 했습니다. 잘못 넣은 값은 꺼내는 순간 ClassCastException으로 운영 중에 터졌습니다.

제네릭은 List<Order>처럼 담을 타입을 적게 해, 잘못된 대입을 컴파일 때 막습니다. 다만 Java 5 이전 코드와 호환하려고 바이트코드에서는 이 타입 정보를 지우고 꺼낼 때 캐스트를 자동으로 넣습니다. 이를 타입 소거라 하며, 그래서 실행 중에는 new T()를 쓸 수 없습니다.

꺼내기만 하면 extends, 넣기만 하면 super

// List<Integer>는 List<Number>가 아니다

// 꺼내서 읽기만: Producer → extends
long sum(List<? extends Number> xs) {
    long s = 0;
    for (Number n : xs) s += n.longValue();
    return s;
}
// 넣기만: Consumer → super
void fill(List<? super Integer> out) {
    out.add(1);
}

Integer는 Number의 자식이지만 List<Integer>는 List<Number>의 자식이 아닙니다. 그렇지 않으면 정수 목록에 실수를 넣을 수 있게 되기 때문입니다. 그래서 여러 타입을 받으려면 와일드카드 ?를 씁니다.

규칙은 PECS(Producer Extends, Consumer Super)로 외웁니다. 값을 꺼내 주는 쪽은 ? extends, 값을 받아 담는 쪽은 ? super입니다.

람다는 메서드 하나짜리 객체를 짧게 쓴다

// 함수형 인터페이스: 추상 메서드 1개
interface Predicate<T> {
    boolean test(T t);
}
// 익명 클래스(Java 7까지)
Predicate<Order> big = new Predicate<>() {
    public boolean test(Order o) {
        return o.amount() > 100_000;
    }
};
// 람다(Java 8+)
Predicate<Order> big2 =
    o -> o.amount() > 100_000;
// 메서드 참조
Function<Order, String> f = Order::userName;

"10만 원 넘는 주문인가" 같은 조건을 다른 메서드에 넘기려면, 예전에는 그 조건을 담은 클래스를 만들어 객체로 넘겨야 했습니다. 추상 메서드가 딱 하나인 인터페이스를 함수형 인터페이스라 하는데, 람다는 이 구현을 매개변수 -> 식으로 짧게 쓰는 문법입니다.

기존 메서드를 그대로 넘길 때는 Order::userName 같은 메서드 참조로 더 줄입니다.

Stream은 최종 연산 전까지 아무것도 안 한다

List<String> vip = orders.stream()
    .filter(o -> o.amount() > 100_000)
    .map(Order::userName)
    .distinct()
    .toList();   // 최종 연산: 여기서 실행

람다가 생기자 컬렉션 처리를 "무엇을 할지"의 연결로 쓰는 Stream이 가능해졌습니다. 위 코드는 10만 원 넘는 주문의 사용자 이름을 중복 없이 모읍니다.

filter, map, distinct는 중간 연산으로, 호출해도 처리 계획만 쌓습니다. toList 같은 최종 연산이 불릴 때 비로소 원소를 하나씩 파이프라인에 흘립니다(지연 연산). 덕분에 findFirst처럼 앞에서 답이 나오면 나머지 원소는 처리하지 않습니다.

Optional은 없을 수 있음을 타입으로 알린다

Optional<User> u = repo.findById(id);
String name = u.map(User::name)
               .orElse("guest");

// 주의: 공용 풀을 함께 씀
orders.parallelStream()
      .forEach(o -> callPg(o)); // 블로킹

조회 결과가 없을 때 null을 돌려주면 호출자가 확인을 잊어 NullPointerException이 납니다. Optional은 "값이 있을 수도 없을 수도 있다"를 반환 타입으로 드러내는 상자로, 값이 있을 때만 map을 적용하고 없으면 orElse의 기본값을 씁니다. 반환 타입에만 쓰고 필드나 매개변수에는 쓰지 않는 것이 관례입니다.

parallelStream()은 JVM 전체가 공유하는 공용 스레드 풀(ForkJoinPool)로 원소를 나눠 처리합니다. 여기서 외부 결제 API처럼 기다리는 작업을 하면 그 풀을 쓰는 다른 코드까지 멈춥니다.

어노테이션은 스스로 아무 일도 하지 않는 꼬리표다

Spring으로 만든 주문 서버에는 @RestController, @Transactional, @Autowired 같은 @ 표시가 가득합니다. 이것이 어노테이션, 즉 클래스·메서드·필드에 붙이는 메타데이터입니다.

중요한 점은 어노테이션이 그 자체로는 아무 동작도 하지 않는다는 것입니다. @Transactional을 붙였다고 메서드 바이트코드에 트랜잭션 코드가 생기지 않습니다. 정의할 때 @Retention(RUNTIME)으로 지정하면 꼬리표가 .class 파일에 남아 실행 중에도 읽을 수 있을 뿐입니다.

그렇다면 누군가 실행 중에 "이 메서드에 @Transactional이 붙어 있나?"를 확인하고 그에 맞게 행동해야 합니다. 1부에서 본 메서드 영역의 클래스 정보를 실행 중에 들여다보는 기능, 리플렉션이 그 일을 합니다.

리플렉션과 어노테이션은 Spring의 토대다

Class<?> c = Class.forName(
    "com.shop.OrderService");
Object target = c.getDeclaredConstructor()
                 .newInstance();
for (Field f : c.getDeclaredFields()) {
  if (f.isAnnotationPresent(Inject.class)) {
    f.setAccessible(true);
    f.set(target, findBean(f.getType()));
  }
}

리플렉션은 실행 중에 클래스 이름 문자열로 클래스를 찾고(Class.forName), 생성자로 객체를 만들고, 필드와 메서드 목록을 읽고 호출하는 기능입니다. 위 코드는 @Inject가 붙은 필드를 찾아 private이라도 접근을 열고(setAccessible) 알맞은 객체를 넣습니다.

3부 DIP에서 남긴 질문, "구현 객체는 누가 넣어 주나"의 답이 이 코드의 확장판입니다. 메서드 호출 앞뒤에 코드를 끼우는 동적 프록시도 리플렉션 위에 있으며 6장에서 다룹니다.

5부

스레드 수백 개가 같은 재고를 건드리면

1장에서 경쟁 상태, 뮤텍스, 모니터를 OS 관점에서 봤고, 4장에서는 DB가 락으로 동시 수정을 막는 법을 봤습니다. 이 부의 질문은 같은 문제가 JVM 힙 안에서 생길 때 Java가 무엇으로 막느냐입니다. synchronized, volatile, CAS, 불변 객체, ThreadLocal, 그리고 Virtual Thread까지 봅니다.

count++ 한 줄도 세 단계라 끼어들 수 있다

  1. 읽기

    스레드 A와 B가 거의 동시에 남은 재고 10을 읽습니다.

  2. 계산

    둘 다 각자 10 - 1 = 9를 계산합니다.

  3. 쓰기

    A가 9를 쓰고, B도 9를 씁니다. 주문은 두 건인데 재고는 하나만 줄었습니다.

Spring Boot의 내장 웹 서버 Tomcat은 1장에서 본 스레드 풀을 두고(기본 최대 200개) 요청 하나를 스레드 하나에 맡깁니다. 주문 요청 두 개가 동시에 오면 두 스레드가 동시에 StockService를 실행하고, 둘 다 힙의 같은 재고 객체를 봅니다.

stock--는 한 줄이지만 바이트코드로는 읽기, 계산, 쓰기입니다. 그 사이에 다른 스레드가 끼어들면 위처럼 갱신이 사라집니다. 1장의 경쟁 상태(Race Condition)입니다.

synchronized는 객체마다 있는 모니터를 잡는다

class Stock {
    private int count = 10;
    synchronized boolean decrease() {
        if (count == 0) return false;
        count--;     // 한 번에 한 스레드만
        return true;
    }
}

1장에서 본 모니터는 공유 데이터와 그 연산을 묶고 진입·해제를 언어가 처리해 주는 동기화 장치였습니다. Java의 모든 객체는 모니터를 하나씩 가집니다. synchronized 메서드나 블록에 들어가려면 그 객체의 모니터를 얻어야 하고, 이미 다른 스레드가 쥐고 있으면 풀릴 때까지 기다립니다(BLOCKED 상태).

같은 스레드는 이미 쥔 모니터에 다시 들어갈 수 있는데, 이를 재진입이라 합니다. 메서드를 빠져나가면 예외가 나도 자동으로 풀립니다.

더 세밀한 제어가 필요하면 ReentrantLock

private final ReentrantLock lock =
    new ReentrantLock();

boolean decrease() throws InterruptedException {
    if (!lock.tryLock(1, TimeUnit.SECONDS))
        return false;   // 1초 안에 못 잡으면 포기
    try {
        return stock.decrease();
    } finally {
        lock.unlock();   // 직접 풀어야 함
    }
}

synchronized는 간단하지만 한계가 있습니다. 한번 기다리기 시작하면 포기할 수 없어서, 락을 쥔 스레드가 느려지면 요청 스레드 200개가 모두 줄을 서 서버 전체가 멈출 수 있습니다.

ReentrantLock은 대기 시간 제한(tryLock), 오래 기다린 순서대로 주는 공정 모드, 여러 조건 변수를 지원합니다. 대신 해제를 언어가 해 주지 않으므로 finally에서 반드시 직접 풉니다.

한 스레드가 쓴 값이 다른 스레드에 안 보일 수 있다

락은 끼어들기를 막습니다. 그런데 동시성에는 다른 종류의 문제도 있습니다. 서버 종료 시 running = false로 작업 스레드를 멈추려 하는데, 작업 스레드가 영영 멈추지 않는 경우입니다.

CPU 코어는 각자 캐시를 가지고, JIT과 CPU는 성능을 위해 명령 순서를 바꾸거나 반복문 안의 읽기를 밖으로 빼기도 합니다. 그래서 한 스레드의 쓰기가 다른 스레드에 언제 보일지 보장되지 않습니다. 이를 가시성 문제라 합니다.

JMM의 happens-before가 보이는 시점을 정한다

CPU마다 캐시 동작이 다르니, Java는 "어떤 조건이면 앞의 쓰기가 뒤의 읽기에 반드시 보이는가"를 언어 수준에서 약속합니다. 이것이 JMM이고, 그 약속의 형식이 happens-before 관계입니다. A가 B보다 happens-before이면, A까지의 모든 쓰기가 B에서 보입니다.

대표 규칙은 세 가지입니다. 같은 모니터를 푸는 것은 다음에 그 모니터를 잡는 것보다 앞섭니다(그래서 synchronized 안의 값은 서로 보입니다). volatile 변수에 쓰는 것은 그 변수를 다음에 읽는 것보다 앞섭니다. 스레드 시작은 그 스레드의 모든 동작보다 앞섭니다.

그래서 앞의 running 플래그는 volatile boolean으로 선언하면 해결됩니다. 하지만 volatile은 보이게 할 뿐 원자적이지 않습니다. volatile int stock에 stock--를 해도 읽기와 쓰기 사이에 다른 스레드가 끼어드는 문제는 그대로입니다. 끼어들기를 락 없이 막는 방법이 CAS입니다.

CAS는 잠그지 않고 비교한 뒤 바꾼다

  1. 읽기

    현재 값 V를 읽어 둡니다(예: 재고 10).

  2. 계산

    새 값 N을 만듭니다(9).

  3. 비교 후 교체

    메모리 값이 아직 V일 때만 N으로 바꿉니다. CPU 명령 하나라 중간에 끼어들 수 없습니다.

  4. 실패 시 재시도

    다른 스레드가 먼저 바꿨다면 새 값을 읽어 처음부터 다시 합니다.

CAS는 "내가 읽은 값이 그대로라면 바꾸고, 아니면 실패를 알려 줘"라는 원자적 CPU 명령입니다. 락처럼 다른 스레드를 재우지 않고, 실패한 쪽이 스스로 다시 시도합니다.

앞의 재고 예에서 A와 B가 둘 다 10을 읽어도, 먼저 바꾼 A만 성공합니다. B의 CAS는 값이 이미 9라 실패하고, B는 9를 다시 읽어 8로 바꿉니다. 갱신이 사라지지 않습니다.

Atomic 클래스는 CAS를 감싼 것이다

AtomicInteger stock = new AtomicInteger(10);
stock.decrementAndGet();  // CAS 반복

// 쓰기가 몰리는 카운터
LongAdder orderCount = new LongAdder();
orderCount.increment();   // 칸을 나눠 더함
long total = orderCount.sum();

AtomicInteger, AtomicLong, AtomicReference는 값 하나를 CAS로 바꾸는 메서드를 제공합니다. 경합이 적으면 락보다 빠릅니다. 4부의 ConcurrentHashMap이 빈 칸에 쓸 때 쓰는 것도 이 CAS입니다.

경합이 아주 심하면 실패와 재시도가 반복되며 CPU를 태웁니다. "오늘 주문 수"처럼 모든 요청이 더하기만 하는 카운터는 값을 여러 칸에 나눠 더하고 읽을 때 합치는 LongAdder가 낫습니다.

불변 객체는 동기화가 필요 없다

public final class Money {   // 상속 금지
    private final long amount;
    private final List<Long> history;
    Money(long a, List<Long> h) {
        amount = a;
        history = List.copyOf(h); // 방어적 복사
    }
    Money plus(long x) {        // 새 객체 반환
        return new Money(amount + x, history);
    }
}

지금까지는 공유된 값을 안전하게 바꾸는 방법이었습니다. 더 근본적인 해법은 바꾸지 않는 것입니다. 동시성 버그는 공유된 가변 상태에서만 생기므로, 상태가 바뀌지 않는 객체는 여러 스레드가 동시에 읽어도 안전합니다. String이 바로 이런 클래스였습니다.

클래스를 final로, 필드를 private final로 둡니다. 밖에서 받은 리스트는 복사해 두는 방어적 복사로, 넘겨준 쪽이 나중에 원본을 바꿔도 영향이 없게 합니다. 바꾸고 싶으면 새 객체를 돌려줍니다.

ThreadLocal은 스레드마다 따로 쓰는 칸이다

공유하지 않는 또 다른 방법은 스레드마다 자기 몫을 따로 갖게 하는 것입니다. ThreadLocal은 같은 변수처럼 보이지만 실제 값은 스레드마다 따로 저장되는 칸입니다. 스레드 A가 넣은 값은 A만 꺼낼 수 있습니다.

요청 하나를 스레드 하나가 끝까지 처리하는 서버에서 특히 유용합니다. 주문 서버는 요청 맨 앞에서 로그인 사용자를 확인한 뒤, 그 정보를 OrderService, StockService, 로그 코드까지 매개변수로 일일이 넘기지 않고 ThreadLocal에 넣어 둡니다. 같은 스레드에서 실행되는 코드는 어디서든 꺼낼 수 있습니다. 6장에서 볼 Spring의 트랜잭션도 같은 방식으로 DB 커넥션을 스레드에 묶어 둡니다.

문제는 서버의 스레드가 요청이 끝나도 죽지 않는다는 데 있습니다.

스레드 풀에서 ThreadLocal은 반드시 지운다

Tomcat의 스레드는 풀에서 재사용됩니다. 요청이 끝나도 값을 지우지 않으면 같은 스레드가 다음 요청을 처리할 때 이전 사용자의 정보를 읽습니다. 큰 객체를 넣었다면 스레드가 살아 있는 동안 GC도 회수하지 못합니다.

그래서 값을 넣는 곳에서 finally로 지웁니다. 아래 코드는 요청 처리 앞뒤에 끼어드는 필터(6장에서 자세히 봄)에서 사용자를 넣고 빼는 모습입니다.

try {
    CURRENT_USER.set(user);
    chain.doFilter(req, res);
} finally {
    CURRENT_USER.remove();  // 반드시
}

메모리 누수이자 보안 사고입니다

다른 사용자의 주문 내역이 섞여 나가는 장애로 이어질 수 있습니다.

OS 스레드는 비싸서 수천 개가 한계다

지금까지 본 Java 스레드는 OS 스레드와 1:1입니다. new Thread() 하나가 커널 스레드 하나이고, 스택으로 기본 약 1MB를 잡으며, 전환할 때마다 1장의 컨텍스트 스위칭 비용이 듭니다. 그래서 한 서버에 수천 개가 현실적인 한계입니다.

그런데 주문 요청을 처리하는 스레드는 대부분의 시간을 기다리며 보냅니다. DB 응답에 20ms, 결제 대행사 API 응답에 200ms를 기다리는 동안 스레드는 아무 일도 하지 않으면서 자리만 차지합니다. 동시 요청이 스레드 수를 넘으면 나머지는 줄을 섭니다.

1장에서 본 이벤트 루프는 기다림을 커널에 맡겨 적은 스레드로 수만 연결을 다뤘지만, 모든 코드를 논블로킹 콜백 방식으로 다시 써야 했습니다. JDK 21은 다른 길을 냈습니다. 코드는 지금처럼 기다리는 방식으로 쓰되, 기다리는 동안에는 OS 스레드를 내놓게 하자는 것입니다.

Virtual Thread는 기다릴 때 캐리어에서 내려온다

JDK 21의 Virtual Thread(JEP 444)는 JVM이 관리하는 가벼운 스레드입니다. 스택을 힙에 필요한 만큼만 두므로 수십만 개를 만들 수 있고, 실행할 때만 코어 수만큼의 OS 스레드, 즉 캐리어 스레드에 올라탑니다.

DB 응답처럼 I/O를 기다리게 되면 JVM이 스택을 힙에 떼어 두고 캐리어를 다른 Virtual Thread에 내줍니다. 응답이 오면 빈 캐리어에 다시 올라탑니다.

Virtual Thread는 I/O 대기에만 이득이다

Virtual Thread는 기다림을 싸게 만들 뿐, 계산을 빠르게 하지는 않습니다. 그리고 지금까지 스레드 수가 몰래 해 주던 일을 없앤다는 점을 기억해야 합니다.

주의점이유대응
CPU 바운드 작업코어 수 이상 빨라지지 않음기존 스레드 풀 유지
풀링 금지만들기가 매우 싸서 풀이 무의미작업마다 새로 생성
synchronized 고정JDK 21~23은 캐리어를 붙잡음JDK 24(JEP 491)에서 해소
하류 자원 고갈동시 요청이 DB로 몰림세마포어로 동시성 제한
ThreadLocal수십만 개면 메모리 급증큰 값 넣지 않기

Tomcat 스레드 200개는 동시에 DB로 가는 요청도 200개로 묶어 주던 제한이었습니다. 그 제한이 사라지면 병목은 4장의 커넥션 풀로 옮겨 가므로, 1장의 세마포어(동시에 들어갈 수 있는 수를 세는 장치)로 따로 막습니다.

6부

주문 서버가 느려지거나 죽을 때

1~5부의 원리가 실제로 문제가 되는 곳은 운영 서버입니다. 주문 서버를 컨테이너로 띄웠다고 가정하고, 힙 크기를 어떻게 정하는지, GC가 괜찮은지 무엇으로 판단하는지, 메모리가 새거나 서버가 멈췄을 때 무엇을 떠서 어떻게 읽는지 봅니다.

원리 실무 JVM 옵션, GC 로그와 지표, 누수 사례, 힙·스레드 덤프를 다룹니다.

JVM 옵션은 모양을 보면 종류를 안다

JVM의 동작은 java 명령 뒤에 붙이는 옵션으로 바꿉니다. 모양으로 종류를 구별할 수 있습니다. -Xmx2g처럼 -X로 시작하는 것은 자주 쓰는 비표준 옵션으로, -Xms와 -Xmx는 힙의 시작 크기와 최대 크기입니다.

-XX:로 시작하는 것은 HotSpot 내부 설정입니다. 켜고 끄는 옵션은 -XX:+UseZGC(켜기), -XX:-UseZGC(끄기)처럼 +와 -로, 값을 주는 옵션은 -XX:MaxGCPauseMillis=100처럼 등호로 씁니다. -Dkey=value는 JVM 설정이 아니라 애플리케이션이 읽을 시스템 속성입니다.

컨테이너에서는 실행 명령을 고치기 번거로우므로 환경 변수 JAVA_TOOL_OPTIONS에 옵션을 넣는 경우가 많습니다. JVM이 시작할 때 이 변수를 읽어 명령줄 옵션처럼 적용합니다. 실제로 적용된 값은 java -XX:+PrintFlagsFinal -version으로 확인합니다.

컨테이너에서는 힙 기본값부터 의심한다

# 기본: 최대 힙 = 메모리 상한의 1/4
# 2GB 컨테이너면 힙 512MB뿐
ENV JAVA_TOOL_OPTIONS="\
  -XX:MaxRAMPercentage=75 \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/dumps \
  -Xlog:gc*:file=/logs/gc.log"

옵션 없이 뜬 JVM은 메모리 상한을 보고 기본값을 정합니다. 컨테이너라면 상한은 9장에서 볼 cgroup, 즉 커널이 그 컨테이너에 허락한 메모리입니다. 최대 힙은 그 1/4이고, CPU 2개 이상·메모리 1792MB 이상인 서버급 머신일 때만 G1을 고릅니다. CPU 1개짜리 컨테이너는 Serial GC로 뜹니다.

그래서 비율을 직접 정하고, OOM 때 힙 덤프를 남기며, GC 로그를 파일로 쓰게 해 둡니다.

힙은 JVM 프로세스 메모리의 일부일 뿐이다

왜 100%가 아니라 75% 안팎일까요? JVM 프로세스가 쓰는 메모리는 힙만이 아니기 때문입니다. 1부의 Metaspace(클래스 정보), 스레드마다 약 1MB인 스택(스레드 200개면 200MB), JIT이 만든 기계어를 담는 코드 캐시, GC가 쓰는 카드 테이블 같은 관리 구조, 그리고 네트워크 라이브러리가 쓰는 힙 밖의 다이렉트 버퍼가 모두 힙 바깥에 있습니다.

2GB 컨테이너에서 힙을 1.9GB로 잡으면, 힙은 여유가 있어도 프로세스 전체가 2GB를 넘는 순간 커널이 프로세스를 강제로 죽입니다. 반대로 너무 작게 잡으면 GC가 잦아지고 남는 메모리를 버립니다.

그래서 보통 70~75%에서 시작해, 실제 프로세스 메모리 사용량과 GC 지표를 보며 조정합니다. 그 GC 지표의 원천이 GC 로그입니다.

GC 로그 한 줄에 무엇을 치웠고 얼마나 멈췄는지 있다

[12.345s][info][gc] GC(41)
  Pause Young (Normal)
  (G1 Evacuation Pause)
  612M->148M(1536M) 7.912ms
[98.102s][info][gc] GC(57)

JDK 9부터 GC 로그는 -Xlog:gc* 형식으로 통일되었습니다. 원래 한 줄인 로그를 읽기 쉽게 나눠 적었습니다. 첫 기록은 41번째 GC가 Young 수집이었고, 힙 사용량이 612MB에서 148MB로 줄었으며(괄호는 현재 힙 크기), 7.9ms 멈췄다는 뜻입니다. 정상적인 모습입니다.

두 번째는 위험 신호입니다. 2.3초짜리 Full GC를 했는데 1490MB가 1402MB로 거의 줄지 않았습니다. 살아 있는 객체가 힙을 거의 채웠다는 뜻이고, 누수나 힙 부족을 의심합니다.

GC 상태는 지표 네 가지로 판단한다

로그를 매번 읽을 수는 없으니 지표로 모아 봅니다. 기준이 되는 것은 서비스의 응답 목표입니다. SLO는 "주문 API는 p99 응답 300ms 이내" 같은 목표이고, p99는 요청 100개를 빠른 순으로 세웠을 때 99번째 값, 즉 가장 느린 1%의 경계입니다.

지표무엇을 보나위험 신호
GC 정지 시간p99 STW 길이응답 SLO에 근접
GC 시간 비율전체 시간 중 GC 비중수 % 이상 지속
GC 후 Old 사용량살아남는 데이터 크기바닥선이 계속 상승
Full GC 횟수G1에서 최후 수단 발생0이 아니면 조사

힙 사용량은 할당과 GC로 톱니 모양을 그립니다. 꼭대기가 아니라 GC 직후의 바닥이 시간이 갈수록 올라가면 회수되지 않는 객체가 쌓이는 누수입니다. Spring 환경에서는 지표 수집 라이브러리 Micrometer가 jvm.gc.pause 같은 이름으로 이 값들을 내보냅니다.

Java의 메모리 누수는 끊기지 않은 참조다

GC가 있는데 왜 누수가 생길까요? 2부에서 본 대로 GC는 Root에서 닿지 않는 객체만 치웁니다. 더는 쓰지 않는데 어딘가에서 참조가 남아 있으면 GC 입장에서는 살아 있는 객체입니다. 주문 서버에서 자주 터지는 패턴은 다음과 같습니다.

  • static 컬렉션 캐시: 상품 캐시 Map에 넣기만 하고 빼지 않으면 static 필드(GC Root)에서 영원히 닿습니다. 크기 제한과 만료가 있는 캐시 라이브러리를 씁니다.
  • ThreadLocal 미삭제: 5부에서 본 대로 풀 스레드가 값을 계속 쥐고 있습니다.
  • 리스너, 콜백 미해제: 등록한 쪽이 사라져도 이벤트를 보내는 쪽이 참조를 유지합니다.
  • 닫지 않은 리소스: 커넥션과 스트림은 4부의 try-with-resources로 닫습니다.
  • hashCode가 바뀌는 키: Map에 넣은 뒤 키의 필드를 바꾸면 다른 칸을 찾게 되어 꺼낼 수도 지울 수도 없습니다.

OOM 메시지가 어느 영역인지 알려 준다

누수가 쌓이든 일시적으로 큰 데이터를 올리든, 결국 어떤 영역이 바닥나면 OutOfMemoryError가 납니다. 메시지 뒷부분이 바닥난 영역을 알려 주므로 거기서 조사를 시작합니다.

메시지 / 증상바닥난 곳먼저 의심할 것

Metaspace클래스 정보동적 클래스 생성 누적
unable to create native threadOS 스레드스레드 무한 생성
Direct buffer memory힙 밖 버퍼네트워크 라이브러리 버퍼

OOMKilled는 JVM 예외가 아닙니다

커널이 프로세스를 강제 종료한 것이라 Java 로그도 힙 덤프도 남지 않습니다. 앞에서 본 힙 밖 메모리를 의심합니다.

힙 덤프는 그 순간 힙의 사진이다

  1. 확보

    OOM 때 자동(HeapDumpOnOutOfMemoryError) 또는 jcmd <pid> GC.heap_dump 파일.

  2. 열기

    Eclipse MAT 같은 덤프 분석 도구로 엽니다.

  3. Retained 크기순

    그 객체가 사라지면 함께 회수될 크기가 큰 순서로 봅니다.

  4. GC Root 경로

    누가 붙잡고 있는지 Root까지 참조 사슬을 거꾸로 따라갑니다.

힙 덤프는 모든 객체와 참조 관계를 파일로 쏟아 낸 것입니다. 객체 자체의 크기(Shallow)보다, 그 객체를 통해서만 닿는 객체까지 합친 Retained 크기가 중요합니다. 작은 Map 하나가 주문 객체 수백만 개를 붙잡고 있을 수 있기 때문입니다.

덤프를 뜨는 동안 STW가 걸리고 파일은 힙 크기만큼 큽니다. 주문자 정보 같은 개인 정보가 그대로 들어 있으니 취급에 주의합니다.

스레드는 여섯 가지 상태 중 하나에 있다

메모리가 아니라 "서버가 살아는 있는데 응답이 없다"면 스레드를 봐야 합니다. 그러려면 Java 스레드의 상태를 알아야 합니다.

상태뜻주문 서버의 예
NEW / TERMINATED시작 전 / 끝남덤프에서는 드묾
RUNNABLE실행 중이거나 실행 가능계산 중, 소켓 읽기 중
BLOCKED모니터를 기다림synchronized 재고 차감 대기
WAITING깨워 줄 때까지 대기커넥션 풀 반납 대기

주의할 점은 소켓에서 DB 응답을 기다리는 스레드도 RUNNABLE로 보인다는 것입니다. JVM 입장에서는 OS 호출 안에 있을 뿐이라, 상태만이 아니라 호출 스택을 함께 봐야 합니다.

jcmd <pid> Thread.print는 모든 스레드의 상태와 호출 스택을 찍습니다. 한 장은 한순간이라, 몇 초 간격으로 2~3번 떠서 비교합니다. 계속 같은 곳에 있는 스레드가 범인입니다.

요청 스레드(http-nio-…-exec-N) 대부분이 같은 락에서 BLOCKED이거나 커넥션 풀에서 WAITING이면 원인이 거기 있습니다. 두 스레드가 서로의 락을 기다리는 데드락은 JVM이 직접 찾아 알려 줍니다. 장애 전체의 진단 순서는 18장에서 다룹니다.

정리

  • JVM은 바이트코드를 실행하는 OS별 엔진입니다. 클래스는 처음 쓰일 때 부모 위임으로 로딩되고, 인터프리터로 시작해 뜨거운 코드만 JIT이 기계어로 바꿉니다.
  • GC는 GC Root에서 닿지 않는 객체를 치웁니다. 대부분 객체가 일찍 죽으므로 Young만 복사 방식으로 자주 치우고, G1과 ZGC는 STW를 줄이는 방향으로 발전했습니다.
  • SOLID는 인터페이스로 바뀌는 곳을 가둡니다. 구현 객체를 넣어 주는 일은 리플렉션과 어노테이션 위에서 Spring이 맡습니다.
  • equals와 hashCode는 함께 다닙니다. HashMap이 hashCode로 칸을 고르고, 충돌이 심하면 트리로, 75%가 차면 두 배로 늘리기 때문입니다.
  • 가시성과 원자성은 다른 문제입니다. volatile은 보이게, synchronized와 CAS는 끼어들지 못하게 하고, 불변 객체는 둘 다 필요 없게 합니다.
  • 운영에서는 힙 밖 메모리, GC 직후 바닥선, 덤프를 봅니다. Java의 누수는 끊기지 않은 참조입니다.

스스로 점검 (1)

  1. 스택과 PC 레지스터는 왜 스레드마다 따로 있어야 하나요?

    스레드마다 실행 중인 메서드와 위치가 다르기 때문입니다. 공유하면 서로의 호출 흐름과 지역 변수를 덮어씁니다.

  2. 배포 직후 몇 분간만 주문 API 응답이 느립니다. 무엇을 의심하나요?

    JIT이 아직 뜨거운 메서드를 컴파일하지 않은 웜업 구간입니다. 트래픽을 받기 전에 주요 API를 미리 호출해 둡니다.

  3. 서로만 참조하는 두 객체는 GC 대상인가요?

    네. Java GC는 참조 개수가 아니라 GC Root에서 닿는지로 판단하므로, Root에서 끊긴 순환 참조는 함께 회수됩니다.

  4. Young 영역을 너무 작게 잡으면 어떤 일이 생기나요?

    Minor GC가 잦아지고, 곧 죽을 객체까지 나이가 차기 전에 Old로 밀려납니다. Old가 빨리 차서 더 비싼 GC가 늘어납니다.

스스로 점검 (2)

  1. 결제 수단을 추가할 때마다 OrderService를 고쳐야 합니다. 어떤 원칙이 깨졌나요?

    OCP와 DIP입니다. 호출부가 Payment 인터페이스에만 의존하게 하고 새 구현 클래스를 추가하는 것으로 확장되게 합니다.

  2. HashMap에 넣은 키 객체의 필드를 나중에 바꾸면 어떻게 되나요?

    hashCode가 바뀌어 다른 칸을 찾게 되므로 get도 remove도 실패합니다. 엔트리는 그대로 남아 누수가 됩니다.

  3. volatile int stock에 stock--를 하면 안전한가요?

    아닙니다. 읽기, 계산, 쓰기 사이에 다른 스레드가 끼어들 수 있습니다. AtomicInteger나 synchronized가 필요합니다.

  4. Tomcat 스레드 풀에서 ThreadLocal을 remove하지 않으면 무엇이 보이나요?

    재사용된 스레드에서 다음 요청이 이전 요청의 값을 읽습니다. 다른 사용자 정보가 노출될 수 있습니다.

스스로 점검 (3)

  1. Virtual Thread로 바꿨더니 DB 커넥션 대기가 폭증했습니다. 왜일까요?

    스레드 수가 해 주던 동시성 제한이 사라져 동시 요청이 커넥션 풀로 한꺼번에 몰렸기 때문입니다. 하류 자원 앞에서 세마포어 등으로 따로 제한해야 합니다.

  2. 메모리 1GB, CPU 1개 컨테이너에서 옵션 없이 뜬 JVM의 GC와 최대 힙은?

    서버급 조건에 못 미쳐 Serial GC가 선택되고, 최대 힙은 메모리의 1/4인 약 256MB입니다.

  3. 힙을 컨테이너 메모리의 95%로 잡았더니 OOMKilled가 납니다. 힙 사용량은 여유가 있었습니다. 왜일까요?

    Metaspace, 스레드 스택, 코드 캐시, 다이렉트 버퍼 같은 힙 밖 메모리를 더하면 프로세스가 상한을 넘기 때문입니다. 힙 비율을 70~75%로 낮춥니다.

  4. GC 직후 Old 사용량이 매일 조금씩 올라갑니다. 다음에 할 일은?

    누수를 의심하고 힙 덤프를 떠서 Retained 크기가 큰 객체와 그것을 붙잡는 GC Root 경로를 찾습니다.
