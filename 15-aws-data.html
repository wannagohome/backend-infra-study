1부

데이터는 모양에 따라 사는 집이 다르다

14장에서 EC2와 컨테이너를 언제든 갈아 끼울 수 있는 소모품으로 만들었습니다. 그렇다면 갈아 끼워도 사라지면 안 되는 데이터는 어디에 두어야 할까요? 이 부에서는 저장소의 세 가지 기본 모양을 구별하고, 여러 서버가 함께 쓰는 파일을 어디에 둘지부터 답합니다.

쇼핑몰 하나가 남기는 데이터는 성질이 제각각이다

이 장은 14장에서 ECS 위에 띄운 쇼핑몰 주문 API를 끝까지 예제로 씁니다. 이 서비스가 남기는 데이터를 늘어놓고 크기, 바뀌는 방식, 찾는 방식을 적어 보면 저장소 하나로 전부 받기 어렵다는 것이 보입니다.

서버 안의 디스크는 데이터의 집이 될 수 없다

가장 쉬운 답은 서버의 디스크에 그냥 쓰는 것입니다. 하지만 14장에서 본 대로 인스턴스 스토어는 인스턴스를 멈추면 지워지고, EBS 볼륨은 AZ 하나에 묶여 보통 인스턴스 한 대에만 붙습니다. Auto Scaling이 서버를 줄이거나 ECS가 태스크를 교체하면 그 디스크도 함께 사라지거나 고아가 됩니다.

더 근본적인 문제는 공유입니다. 서버가 세 대면 사용자가 올린 이미지는 그중 한 대의 디스크에만 있습니다. 다음 요청이 다른 서버로 가면 이미지를 찾지 못합니다. 9장에서 "남겨야 할 데이터는 컨테이너 밖에 둔다"고 했던 원칙이 서버 단위로 다시 나타나는 것입니다.

그래서 데이터는 서버 밖에, 여러 서버가 동시에 닿을 수 있는 곳에 둡니다. 남는 질문은 서버가 그 저장소에 무엇을 요청하느냐입니다. 디스크 칸을 달라고 하는지, 파일 경로를 여는지, 이름 붙은 덩어리를 통째로 주고받는지에 따라 저장소의 모양이 셋으로 갈립니다.

디스크는 번호 붙은 칸이고, 이름은 파일 시스템이 붙인다

세 모양을 구별하려면 먼저 디스크와 파일 시스템의 관계를 알아야 합니다. 디스크는 운영체제에게 블록 장치로 보입니다. 블록 장치는 고정 크기(보통 4KB) 칸에 0번부터 번호를 붙여 놓고 "123번 칸을 읽어라, 456번 칸에 써라"라는 명령만 받습니다. 이 장치는 파일 이름도, 폴더도 모릅니다.

이름을 붙이는 일은 커널 안의 파일 시스템(ext4, XFS 등)이 합니다. 파일 시스템은 1장에서 본 inode, 즉 파일의 크기·권한과 데이터가 놓인 블록 번호를 적은 기록표를 디스크에 함께 저장하고, /data/report.csv 같은 경로를 블록 번호 목록으로 바꿔 줍니다.

여기서 중요한 사실이 하나 나옵니다. 파일 시스템은 성능을 위해 inode와 빈 칸 목록을 자기 메모리에 캐시해 둡니다. 같은 블록 장치를 서버 두 대가 각자의 파일 시스템으로 동시에 열면, 서로 상대가 바꾼 기록표를 모른 채 같은 칸에 다른 파일을 써서 데이터가 깨집니다.

그래서 블록 장치는 원칙적으로 서버 한 대가 독점합니다. 여러 서버가 같은 파일을 보려면 파일 시스템을 한곳에만 두고 다른 서버들은 그곳에 요청을 보내야 합니다. 파일 시스템을 누가 들고 있느냐, 이것이 다음 슬라이드의 세 모양을 가르는 기준입니다.

블록, 파일, 객체는 파일 시스템의 위치가 다르다

블록 스토리지는 블록 장치를 네트워크 너머에서 빌려줍니다(EBS). 파일 시스템은 내 서버 안에 있고, 4KB 한 칸만 골라 고쳐 쓸 수 있습니다.

파일 스토리지는 파일 시스템을 저장소 쪽이 들고, 서버들은 NFS라는 프로토콜로 원격 경로를 내 디렉터리처럼 엽니다(EFS).

객체 스토리지는 파일 시스템이 아예 없습니다. 키와 데이터 덩어리를 HTTP로 주고받고, 객체는 통째로 교체됩니다(S3).

객체 스토리지는 부분 수정을 버리고 규모를 얻는다

객체 스토리지가 부분 수정을 지원하지 않는 것은 결함이 아니라 설계입니다. 파일 시스템은 디렉터리 트리, 파일 잠금, 바이트 단위 덮어쓰기를 지켜야 하므로 여러 서버에 흩어 놓기 어렵습니다. 객체는 키 하나와 바이트 덩어리, 약간의 메타데이터뿐이라 서로 독립적이고, 그래서 저장소는 객체를 수많은 서버와 AZ에 마음대로 흩어 복제할 수 있습니다.

그 결과 용량은 사실상 무제한이 되고 사본이 여러 곳에 있어 잘 잃지 않습니다. 대가도 분명합니다. 1바이트를 고쳐도 객체 전체를 다시 올려야 하고, 요청마다 HTTP 왕복과 인증을 거치니 지연이 수십 밀리초 단위이며, 폴더 이름 바꾸기 같은 연산도 없습니다.

쇼핑몰의 상품 이미지는 한 번 올리고 통째로 읽기만 하니 이 대가를 거의 치르지 않습니다. 반대로 주문 행처럼 작게 자주 고치는 데이터에 객체 스토리지는 맞지 않습니다.

EBS, EFS, S3는 붙는 범위와 지연이 다르다

세 모양을 AWS 서비스로 옮기면 아래 표가 됩니다. 지연 차이는 요청이 지나는 길의 길이에서 옵니다. EBS는 블록 I/O 하나가 같은 AZ의 스토리지로 바로 가고, EFS는 NFS 요청이 파일 서버의 처리를 거치며, S3는 HTTP 요청마다 서명 검증과 객체 조회를 거칩니다.

EFS는 여러 AZ의 서버가 같은 폴더를 연다

쇼핑몰의 정산 작업은 서버 여러 대가 같은 작업 폴더에 중간 파일을 쓰고 읽습니다. 이런 곳에 EFS, 즉 AWS가 운영하는 NFS 파일 시스템을 씁니다.

EFS는 AZ마다 마운트 대상을 하나씩 둡니다. 마운트 대상은 13장의 ENI, 즉 서브넷에 꽂힌 가상 네트워크 카드이고 IP 주소를 가집니다. 서버는 자기 AZ의 마운트 대상으로 NFS 연결을 맺습니다. 데이터는 여러 AZ에 중복 저장(Regional 유형)되어 AZ 하나가 죽어도 남은 서버는 계속 씁니다.

EFS 성능은 지연과 처리량을 따로 고른다

저장소의 성능은 두 숫자로 말합니다. 지연은 작업 하나(파일 열기, 4KB 읽기)가 끝나기까지 걸리는 시간이고, 처리량은 초당 옮기는 바이트의 양입니다. 작은 파일을 자주 여는 일은 지연이, 큰 파일을 길게 읽는 일은 처리량이 좌우합니다.

EFS는 이 둘을 별도의 설정으로 정합니다. 성능 모드는 작업당 지연을, 처리량 모드는 초당 바이트 상한과 과금 방식을 정합니다.

처리량 모드 중 Bursting은 14장의 T 계열 CPU 크레딧과 같은 발상입니다. 저장한 용량에 비례해 기본 처리량이 정해지고, 덜 쓴 만큼 크레딧이 쌓였다가 몰릴 때 꺼내 씁니다. 그래서 파일은 적은데 읽기가 많으면 크레딧이 바닥나 갑자기 느려집니다.

EFS는 안 쓰는 파일을 싼 클래스로 옮긴다

성능을 정했으면 다음은 비용입니다. EFS에는 자주 쓰는 데이터용 Standard, 가끔 쓰는 Infrequent Access(IA), 거의 안 쓰는 Archive 클래스가 있습니다. IA와 Archive는 저장 단가가 낮은 대신 첫 바이트 지연, 즉 읽기를 요청하고 첫 데이터가 오기까지의 시간이 수십 밀리초로 늘고 읽을 때 요금이 붙습니다.

수명 주기 관리를 켜면 "30일 동안 안 열린 파일은 IA로"처럼 자동으로 옮기고, 다시 열리면 Standard로 되돌릴 수 있습니다.

작은 파일 수십만 개는 EFS가 약하다

파일 하나를 열 때마다 네트워크 왕복이 생깁니다. 작은 파일 수만 개로 된 node_modules나 빌드 캐시를 EFS에 두면 로컬 디스크보다 수십 배 느려집니다.

One Zone 유형도 있다

한 AZ에만 저장해 더 싸지만 그 AZ가 죽으면 접근할 수 없습니다. 다시 만들 수 있는 데이터에만 씁니다.

특정 파일 시스템이 꼭 필요하면 FSx를 쓴다

EFS는 리눅스 서버끼리 NFS로 공유하는 일반적인 경우를 위한 것입니다. 그런데 기존 시스템이 특정 파일 시스템의 기능에 기대고 있다면 EFS로는 대신할 수 없습니다. 이럴 때 쓰는 것이 FSx로, 잘 알려진 파일 시스템 네 가지를 AWS가 대신 운영해 줍니다.

FSx for Windows File Server는 Windows의 파일 공유 프로토콜인 SMB와, 사내 사용자·권한을 관리하는 Windows 디렉터리 서비스인 Active Directory를 그대로 씁니다. Windows 서버들이 공유 드라이브를 쓰던 환경을 옮길 때 고릅니다.

FSx for Lustre는 파일을 여러 스토리지 서버에 쪼개 두고 수천 대가 병렬로 읽게 만든 고성능 파일 시스템입니다. 대규모 과학 계산(HPC)이나 ML 학습처럼 거대한 데이터를 한꺼번에 읽는 작업에 쓰고, S3 버킷과 연결해 데이터를 끌어올 수 있습니다.

FSx for NetApp ONTAP은 기업용 스토리지 장비인 NetApp의 운영체제를, FSx for OpenZFS는 스냅샷과 압축 기능이 풍부한 오픈소스 파일 시스템 ZFS를 제공합니다. 온프레미스에서 그 장비와 기능에 맞춰 운영하던 것을 그대로 옮기는 용도입니다. 쇼핑몰 정산 폴더처럼 리눅스끼리 공유하는 경우라면 EFS로 충분합니다.

백업은 AWS Backup이 한곳에서 모아 맡는다

지금까지 본 저장소와 앞으로 볼 DB는 저마다 백업 방법이 다릅니다. EBS는 스냅샷, RDS는 자동 백업, DynamoDB는 따로 켜는 백업이 있습니다. 서비스가 늘수록 "무엇을, 얼마나 자주, 얼마나 오래" 백업하는지가 흩어져 아무도 전체를 모르게 됩니다.

AWS Backup은 이 일정을 백업 계획 하나에 모읍니다. 태그로 대상을 고르면(backup=daily가 붙은 모든 리소스) EBS, RDS, DynamoDB, EFS, S3 등을 같은 규칙으로 백업하고, 결과물을 백업 볼트라는 별도 금고에 담아 다른 리전이나 계정으로 복사합니다. Vault Lock을 걸면 정한 기간 동안 관리자도 백업을 지우지 못해, 랜섬웨어나 실수로 백업까지 사라지는 일을 막습니다.

얼마나 자주 백업할지는 두 목표에서 나옵니다. RPO는 장애 때 잃어도 되는 최대 데이터의 시간 폭, RTO는 복구까지 허용되는 시간입니다. 이 두 숫자로 백업과 DR을 설계하는 법은 18장에서 봅니다.

온프레미스 데이터는 연결 방식에 맞춰 옮긴다

회사가 직접 운영하는 데이터센터, 즉 온프레미스에 쌓인 파일을 AWS로 옮기거나 함께 쓰는 일도 흔합니다. 네트워크로 계속 이어 쓸지, 한 번에 옮기고 끝낼지, 네트워크로는 너무 많은지에 따라 도구가 다릅니다.

서비스하는 일고르는 상황
Storage Gateway사내에 S3를 파일·볼륨·테이프로 보여 줌사내 앱을 고치지 않고 클라우드에 저장
DataSyncNFS·SMB·다른 클라우드에서 온라인 전송검증, 증분, 일정 실행이 필요할 때
Snowball Edge장비를 배송해 오프라인 전송신규 고객에게는 더 이상 제공 안 함

Storage Gateway는 사내에 설치한 게이트웨이가 자주 쓰는 데이터를 로컬에 캐시하고 원본은 S3에 둡니다. 이제 이 표 곳곳에 등장한 S3를 본격적으로 열어 봅니다.

2부

S3는 끝없는 키-값 창고다

1부에서 이미지와 로그처럼 한 번 쓰고 통째로 읽는 데이터는 객체 스토리지가 맞다고 했습니다. 이 부는 AWS의 객체 스토리지인 S3가 데이터를 어떻게 이름 붙여 담는지, 쓴 값이 언제 보이고 얼마나 안전한지, 그리고 요금이 어떻게 매겨지는지를 봅니다.

S3는 버킷 안의 객체를 키로 찾는다

S3의 저장 단위는 세 가지입니다. 버킷은 객체를 담는 최상위 그릇이고 리전 하나에 속해, 따로 복제하지 않는 한 데이터가 그 리전을 벗어나지 않습니다. 객체는 데이터 덩어리와 메타데이터(콘텐츠 형식, 사용자 정의 태그 등)의 묶음이고, 키는 버킷 안에서 객체를 가리키는 이름입니다.

버킷 이름은 전 세계에서 하나뿐이어야 합니다. 버킷 이름이 shop-uploads.s3.ap-northeast-2.amazonaws.com처럼 DNS 이름의 일부가 되기 때문입니다.

S3의 모든 동작은 HTTP API입니다. 객체를 올리면 PUT, 읽으면 GET, 지우면 DELETE, 목록은 LIST 요청이 되고, 콘솔·CLI·SDK 모두 12장에서 본 SigV4 서명을 붙여 이 API를 부릅니다. 쇼핑몰의 상품 이미지는 shop-uploads 버킷에 둡니다.

S3의 폴더는 키 문자열의 일부일 뿐이다

images/2026/a.png의 슬래시는 폴더가 아닙니다. S3의 키 공간은 평평하고, 콘솔은 키 앞부분인 접두사를 폴더처럼 보여 줄 뿐입니다.

첫 명령은 키 하나에 파일을 올립니다. 둘째 명령은 접두사가 images/2026/인 키만 나열하고, --delimiter /로 그다음 슬래시까지를 묶어 하위 "폴더"처럼 돌려줍니다. 그래서 "폴더 이름 바꾸기"는 그 아래 모든 객체를 복사하고 지우는 일이 됩니다.

$ aws s3api put-object \
    --bucket shop-uploads \
    --key images/2026/a.png \
    --body a.png
$ aws s3api list-objects-v2 \
    --bucket shop-uploads \
    --prefix images/2026/ \
    --delimiter /
# prefix와 delimiter로 폴더처럼 나열할 뿐

사본이 여럿이면 방금 쓴 값이 안 보일 수 있다

S3는 객체를 여러 서버와 AZ에 사본으로 저장합니다. 사본이 여럿이면 피할 수 없는 질문이 생깁니다. 한 사본에 새 값을 쓰는 사이 다른 사본에서 읽으면 무엇이 보일까요?

쓰기가 모든 사본에 퍼지기 전에 옛 값이 보일 수 있고, 시간이 지나면 결국 같아지는 성질을 최종 일관성이라고 합니다. 4장의 PACELC로 말하면, 장애가 없을 때도 지연을 줄이려고 일관성을 조금 양보하는 쪽입니다. 반대로 쓰기가 끝난 순간부터 어느 읽기든 새 값을 보장하는 성질을 강한 일관성이라고 합니다.

S3는 오랫동안 덮어쓰기와 삭제가 최종 일관성이었습니다. 그래서 "이미지를 올리고 바로 썸네일 작업이 읽었더니 옛 파일이 나왔다"는 버그를 막으려고 앱마다 재확인 코드를 넣어야 했습니다.

지금의 S3는 쓰고 바로 읽으면 새 값이 보인다

S3는 2020년 12월부터 모든 PUT, DELETE, 목록 조회에 강한 읽기-쓰기 일관성(strong read-after-write)을 보장합니다. 덮어쓴 직후 GET을 해도 옛 값이 나오지 않고, 지운 직후 목록에도 나타나지 않습니다. 추가 요금이나 성능 저하도 없습니다.

그래서 앞 슬라이드의 재확인 코드는 이제 필요 없습니다. 업로드가 성공 응답을 받은 뒤 시작한 읽기는 반드시 그 객체를 봅니다.

일관성은 락이 아니다

두 클라이언트가 같은 키에 동시에 쓰면 마지막 쓰기가 이기고 앞의 쓰기는 조용히 사라집니다. 덮어쓰기 경쟁을 막으려면 3부에서 볼 조건부 쓰기를 씁니다.

내구성은 잃지 않는 것, 가용성은 읽히는 것이다

일관성 다음으로 물을 것은 "안전한가"인데, 이 말에는 두 가지 뜻이 섞여 있습니다. 내구성은 저장한 데이터가 사라지지 않을 확률입니다. S3는 모든 스토리지 클래스가 99.999999999%(9가 11개)를 목표로 설계되었습니다. 객체 1,000만 개를 저장하면 평균 1만 년에 하나를 잃는 수준입니다.

가용성은 요청했을 때 실제로 응답받을 확률입니다. S3 Standard는 99.99%로 설계되어, 1년에 약 53분은 요청이 실패할 수 있습니다. 데이터는 안전하지만 잠깐 못 읽을 수 있다는 뜻입니다.

그래서 S3를 부르는 코드에는 503이나 타임아웃에 대한 재시도가 있어야 합니다. AWS SDK는 8장에서 본 지수 백오프, 즉 실패할 때마다 기다리는 시간을 두 배씩 늘리고 무작위 지터를 섞는 재시도를 기본으로 합니다.

S3 요금은 저장, 요청, 꺼내기로 나뉜다

S3에는 저장 방식과 가격이 다른 여러 스토리지 클래스가 있습니다. 클래스를 비교하기 전에, 요금이 어떤 항목으로 매겨지는지부터 알아야 표가 읽힙니다.

저장 요금은 GB를 한 달 동안 보관하는 값입니다. 요청 요금은 API 호출 1,000건 단위로 붙는데, 쓰기와 목록(PUT, COPY, LIST)이 읽기(GET)보다 훨씬 비쌉니다. 조회 요금(retrieval)은 싼 클래스에서 데이터를 꺼낼 때 GB당 붙는 값입니다.

싼 클래스에는 조건이 두 개 더 붙습니다. 최소 보관 기간은 그 기간이 지나기 전에 지우거나 옮기면 남은 기간의 저장 요금을 한꺼번에 청구하는 규칙이고, 최소 과금 크기는 그보다 작은 객체도 그 크기로 계산하는 규칙입니다.

여기서 S3 비용의 기본 법칙이 나옵니다. 저장이 싼 클래스일수록 꺼낼 때 비쌉니다. 그래서 클래스는 데이터를 얼마나 자주 꺼내느냐로 고릅니다. 여기에 인터넷으로 나가는 데이터 전송 요금(12장)이 따로 붙습니다.

스토리지 클래스는 꺼내는 빈도로 고른다

클래스접근 패턴설계 가용성최소 보관 / 최소 과금 크기
Standard월 1회 이상, 기본값99.99%없음 / 없음
Intelligent-Tiering모르거나 자주 바뀜99.9%없음, 조회 요금 없음
Standard-IA월 1회 정도99.9%30일 / 128KB
One Zone-IA다시 만들 수 있는 데이터99.5%30일 / 128KB
Express One Zone지연에 민감한 고성능99.95%없음 / 없음

IA(Infrequent Access) 계열은 저장 단가가 싼 대신 GB당 조회 요금이 붙습니다. 쇼핑몰이라면 오늘 올라온 상품 이미지는 Standard, 몇 달 지난 주문의 영수증 PDF는 Standard-IA가 어울립니다. 이 밖에 꺼내는 일이 훨씬 드문 데이터를 위한 Glacier 클래스가 따로 있습니다.

One Zone 클래스는 AZ 하나에 데이터를 건다

표의 대부분은 데이터를 3개 이상의 AZ에 나눠 저장합니다. 이름에 One Zone이 붙은 두 클래스만 AZ 하나에 저장하고, 그만큼 싸거나 빠릅니다. 대신 그 AZ가 물리적으로 망가지면 데이터를 잃을 수 있습니다.

One Zone-IA는 다른 곳에 원본이 있거나 다시 만들 수 있는 데이터, 예를 들어 원본 이미지에서 만든 썸네일에 씁니다. 썸네일은 잃어도 다시 생성하면 됩니다.

Express One Zone은 성능을 위한 클래스입니다. 특정 AZ에 만드는 디렉터리 버킷이라는 전용 버킷에 저장되는데, 일반 버킷의 평평한 키 공간과 달리 데이터를 실제 디렉터리 계층으로 정리해 요청을 빠르게 처리합니다. Standard보다 최대 10배 빠르고 같은 AZ의 컴퓨팅이 쓰는 작업용 사본, 예를 들어 ML 학습 데이터나 분석 중간 결과에 맞습니다.

Glacier 세 클래스는 꺼내는 속도가 다르다

Glacier 클래스는 분기나 연 단위로 꺼낼까 말까 한 보관용 데이터를 위한 것입니다. 저장 단가가 가장 싸고, 대신 꺼내는 속도와 최소 보관 기간으로 값을 치릅니다.

클래스접근 패턴꺼내는 방법최소 보관
Glacier Instant Retrieval분기 1회밀리초, 바로 GET90일
Glacier Flexible Retrieval연 1회복원 요청 후 분~시간90일
Glacier Deep Archive연 1회 미만복원 요청 후 12~48시간180일

Instant Retrieval은 조회 요금만 비쌀 뿐 Standard처럼 바로 읽힙니다. 나머지 둘은 "복원"이라는 단계를 거쳐야 하는데, 그 과정을 다음 슬라이드에서 봅니다.

보관된 객체는 복원을 거쳐야 읽힌다

  1. GET은 실패한다

    Flexible·Deep Archive 객체는 보관 상태라 바로 읽으면 오류가 납니다.

  2. RestoreObject 요청

    복원 등급과 임시 사본을 둘 일수를 정해 요청합니다.

  3. 복원 대기

    등급에 따라 몇 분에서 수십 시간이 걸리고, 끝나면 이벤트로 알 수 있습니다.

  4. 임시 사본 읽기

    정한 일수가 지나면 임시 사본은 사라지고 원본은 보관 상태로 남습니다.

복원 등급은 Expedited(1~5분), Standard, Bulk가 있고 빠를수록 비쌉니다. Deep Archive는 Expedited가 없습니다.

Glacier에 넣는 객체에는 S3가 색인용 메타데이터 40KB를 함께 과금합니다. 그래서 작은 파일 수백만 개는 tar 등으로 묶어서 넣어야 메타데이터 비용이 데이터 비용을 넘지 않습니다.

Intelligent-Tiering은 알아서 계층을 옮긴다

  1. Frequent Access

    올리거나 옮겨 온 객체는 모두 여기서 시작합니다.

  2. Infrequent Access

    30일 연속 접근이 없으면 자동으로 내려갑니다.

  3. Archive Instant Access

    90일 연속 접근이 없으면 한 단계 더 내려갑니다.

  4. 다시 접근하면

    즉시 Frequent Access로 돌아옵니다. 조회 요금은 없습니다.

지금까지는 사람이 데이터의 접근 빈도를 알고 클래스를 고른다고 가정했습니다. 리뷰 사진처럼 어떤 것은 몇 년 뒤에도 자주 보이고 어떤 것은 바로 잊히면 그 가정이 깨집니다. Intelligent-Tiering은 객체마다 접근을 지켜보고 알아서 옮깁니다.

대신 객체마다 소액의 월 모니터링 요금이 붙고, 128KB보다 작은 객체는 모니터링하지 않아 항상 Frequent Access 요금을 냅니다.

수명 주기 규칙이 객체를 옮기고 지운다

{ "Rules": [{
  "ID": "logs", "Status": "Enabled",
  "Filter": { "Prefix": "logs/" },
  "Transitions": [
    { "Days": 30,  "StorageClass": "STANDARD_IA" },
    { "Days": 180, "StorageClass": "DEEP_ARCHIVE" }
  ],
  "Expiration": { "Days": 730 }
}]}

쇼핑몰 접근 로그는 처음 한 달만 자주 보고, 반년 뒤에는 감사 때나 꺼냅니다. 이런 시간표를 수명 주기 규칙으로 적습니다.

Filter는 logs/ 접두사의 객체만 대상으로 고릅니다. Transitions는 만든 지 30일에 Standard-IA로, 180일에 Deep Archive로 전환하고, Expiration은 730일에 만료시켜 지웁니다.

같은 문서에 이전 버전과 미완료 업로드를 치우는 규칙도 넣는데, 그 둘이 무엇인지 3부에서 보고 8부에서 완성합니다.

전환에도 비용이 들고, 최소 기간이 걸린다

수명 주기 규칙은 공짜 자동화처럼 보이지만, 앞에서 본 요금 항목이 그대로 적용됩니다. 규칙을 만들기 전에 세 가지를 확인합니다.

  • 전환은 객체당 요청 요금입니다. 그래서 2024년 9월부터 수명 주기는 기본적으로 128KB보다 작은 객체를 옮기지 않습니다. 작은 객체는 옮기는 비용이 아끼는 저장 비용보다 큽니다.
  • 최소 보관 기간 전에 옮기거나 지우면 남은 기간만큼 청구됩니다. 그래서 Glacier IR(90일)에 4일째 넣고 20일째 Deep Archive로 옮기는 규칙은 아예 만들 수 없습니다.
  • Glacier 전환은 비동기입니다. 실제 이동이 늦어져도 과금은 규칙 조건이 충족된 날부터 대상 클래스 요금으로 바뀝니다.

3부

지우지 못하게, 엿보지 못하게

2부에서는 S3에 데이터를 넣고 싸게 보관하는 법을 봤습니다. 이 부는 그 데이터를 지키는 법과 빠르게 넣고 빼는 법을 봅니다. 실수로 지우면 되살릴 수 있나, 권한을 가진 공격자도 못 지우게 할 수 있나, 누가 읽을 수 있는지는 무엇이 정하나, 그리고 큰 파일은 어떻게 올리나를 차례로 답합니다.

기초 원리 여기부터는 S3가 요청을 판정하고 데이터를 보호하는 내부 규칙을 다룹니다.

버전 관리를 켜면 삭제는 표시만 남긴다

운영자가 aws s3 rm으로 상품 이미지 폴더를 잘못 지웠다고 해 봅시다. 버전 관리가 없으면 끝입니다. 버전 관리를 켠 버킷은 같은 키에 쓸 때마다 새 버전 ID를 붙여 쌓으므로, 덮어써도 이전 버전이 남습니다.

버전을 지정하지 않은 DELETE는 아무것도 지우지 않고 맨 위에 삭제 마커만 얹습니다. GET은 404를 받지만 삭제 마커를 지우면 객체가 되살아납니다. 버전 ID를 지정해 지워야 진짜로 사라집니다.

버전 관리는 켜면 끌 수 없고, 버전마다 돈을 낸다

버킷은 처음에 버전 관리가 꺼진 상태입니다. 한 번 켜면(Enabled) 다시 끌 수 없고 일시 중지(Suspended)만 할 수 있습니다. 중지해도 이미 쌓인 버전은 그대로 남고, 이후 쓰기만 버전 없이 덮어씁니다.

버전 관리의 대가는 저장 용량입니다. 이전 버전도 모두 저장 요금을 냅니다. 매일 덮어쓰는 catalog.json이 있다면 콘솔에 보이는 크기는 그대로인데 청구 용량은 날마다 하루치씩 늘어납니다.

그래서 버전 관리는 수명 주기 규칙의 NoncurrentVersionExpiration, 즉 "현재 버전이 아니게 된 지 N일 지난 버전은 지운다"는 규칙과 짝으로 켭니다. 실수를 되돌릴 시간(예: 30일)만큼만 이전 버전을 남기는 것입니다. 이 규칙은 8부에서 전체 수명 주기 문서로 완성합니다.

Object Lock은 권한이 있어도 못 지우게 한다

버전 관리는 실수는 막지만 악의는 막지 못합니다. 관리자 자격 증명을 훔친 공격자는 버전 ID를 지정해 모든 버전을 지울 수 있습니다. 데이터를 지우거나 암호화한 뒤 몸값을 요구하는 랜섬웨어가 노리는 것이 이것입니다. 또 금융 거래 기록처럼 규정상 "몇 년간 변경 불가"를 증명해야 하는 데이터도 있습니다.

Object Lock은 한 번 쓰면 정한 기간 동안 고치거나 지울 수 없는 WORM(write once, read many) 저장을 제공합니다. 버전 관리가 켜진 버킷에서만 동작하고, 객체 버전 단위로 보존 기간을 겁니다.

보존 모드는 둘입니다. Governance 모드는 특별 권한(s3:BypassGovernanceRetention)을 가진 주체만 풀 수 있어 실수 방지와 시험에 씁니다. Compliance 모드는 루트 사용자도 기간 전에는 지우지 못합니다. 기간과 상관없이 해제할 때까지 묶어 두는 법적 보존(legal hold)도 따로 걸 수 있습니다.

비슷한 목적의 오래된 장치로 MFA Delete가 있습니다. 버전을 영구 삭제하거나 버전 관리 상태를 바꿀 때 12장에서 본 MFA 코드를 요구하며, 루트 사용자만 CLI나 API로 켤 수 있습니다. 자동화와 함께 쓰기 어려워 요즘은 Object Lock과 12장의 SCP 같은 정책 가드레일을 더 많이 씁니다.

복제는 새로 쓰는 객체를 다른 버킷으로 보낸다

리전 하나가 통째로 문제를 겪을 때를 대비하거나, 다른 계정의 감사용 버킷에 사본을 두려면 복제를 씁니다. S3 복제는 원본 버킷에 새로 쓰인 객체를 비동기로 다른 버킷에 복사합니다. 다른 리전이면 CRR(Cross-Region Replication), 같은 리전이면 SRR(Same-Region Replication)입니다.

복제는 객체 버전 단위로 동작하므로 양쪽 버킷 모두 버전 관리가 켜져 있어야 합니다. 규칙을 켜기 전에 있던 객체는 복제되지 않아, Batch Replication 작업으로 따로 보냅니다.

시간 보장이 필요하면 RTC

Replication Time Control은 대부분을 몇 초 안에, 99.9%를 15분 안에 복제하고 지연을 지표와 이벤트로 알려 줍니다.

복제는 백업이 아니다

잘못된 덮어쓰기도 그대로 복제됩니다. 실수 복구는 버전 관리, 변조 방지는 Object Lock이 맡습니다.

암호화는 데이터 키로 하고, 그 키를 다시 잠근다

지우지 못하게 하는 장치를 봤으니 이제 엿보지 못하게 하는 장치입니다. 먼저 저장 시 암호화가 무엇을 막는지 분명히 해야 합니다. 이것은 디스크가 도난당하거나 폐기된 매체에서 데이터가 새는 것을 막습니다. S3 API로 정당하게 읽을 권한이 있는 사람은 그대로 평문을 받습니다. 누가 읽느냐는 권한이 정합니다.

S3는 7장에서 본 대칭키 암호로 객체를 암호화합니다. 객체마다 새 데이터 키를 만들어 암호화하고, 그 데이터 키를 다시 상위 키로 암호화해 객체 옆에 함께 저장합니다. 이렇게 키를 키로 감싸는 방식을 봉투 암호화라고 합니다. 상위 키 하나만 안전하면 객체가 수십억 개여도 키 관리는 하나로 끝납니다.

그 상위 키를 누가 쥐느냐가 선택지를 가릅니다. S3가 직접 쥘 수도 있고, KMS에 맡길 수도 있습니다. KMS는 AWS의 키 보관 서비스로, 키 원본을 밖으로 내보내지 않은 채 "이 데이터 키를 풀어 달라" 같은 API만 제공하고, 누가 그 키를 쓸 수 있는지는 키 정책으로 정합니다.

KMS의 키 정책과 키 교체, 사용 기록은 16장에서 자세히 봅니다. 여기서는 KMS 키는 권한이 따로 걸린 열쇠 정도로 알아 두면 다음 표가 읽힙니다.

서버 측 암호화는 키를 누가 쥐느냐로 갈린다

SSE-S3S3가 전부 관리2023년 1월부터 모든 새 객체에 기본 적용, 무료

SSE는 server-side encryption, 즉 S3가 저장하기 직전에 암호화한다는 뜻입니다. SSE-KMS의 진짜 가치는 암호화 자체보다 두 번째 권한 검사입니다. S3 읽기 권한이 있어도 KMS 키를 풀 권한(Decrypt)이 없으면 객체를 읽지 못하므로, 버킷 권한 실수 하나로 데이터가 새는 일을 한 겹 더 막습니다.

SSE-KMS는 버킷 키로 KMS 호출을 줄인다

두 번째 권한 검사에는 대가가 있습니다. SSE-KMS는 원래 객체를 쓰고 읽을 때마다 KMS에 데이터 키를 요청합니다. KMS에도 12장에서 본 할당량, 즉 초당 요청 수 상한이 있어서, 이미지 GET이 초당 수천 건 몰리면 S3 요청이 KMS 쓰로틀링으로 실패하고 KMS 요청 요금도 늘어납니다.

버킷 키를 켜면 S3가 KMS에서 짧게 쓰는 버킷 단위 키를 받아 두고, 그 키로 객체별 데이터 키를 만듭니다. AWS 문서는 KMS 요청 비용을 최대 99% 줄인다고 설명합니다.

기본 암호화는 새 객체에만

버킷 기본 암호화를 바꿔도 이미 있는 객체는 그대로입니다. 기존 객체를 다시 암호화하려면 객체 수백만 개에 같은 작업을 일괄로 거는 S3 Batch Operations로 제자리 복사합니다.

S3 권한은 주체 쪽과 버킷 쪽에서 함께 정한다

이제 누가 읽고 쓸 수 있는지를 정하는 장치들입니다. 가장 기본은 12장에서 본 두 종류의 정책입니다. IAM 정책은 자격 증명 기반 정책으로, 역할이나 사용자 쪽에 "이 주체는 무엇을 할 수 있나"를 적습니다. 버킷 정책은 리소스 기반 정책으로, 버킷 쪽에 "누가 이 버킷에 무엇을 할 수 있나"를 적습니다.

쇼핑몰 주문 API의 ECS 작업 역할(14장)에는 IAM 정책으로 shop-uploads/images/*에 대한 s3:PutObject를 줍니다. 같은 계정 안에서는 IAM 정책과 버킷 정책 중 한쪽만 허용해도 됩니다.

다른 계정의 분석 팀이 로그를 읽어야 한다면 사정이 다릅니다. 12장의 규칙대로 계정을 넘는 요청은 양쪽 모두 허용해야 하므로, 분석 팀 역할의 IAM 정책과 우리 버킷 정책 둘 다에 허용을 적습니다.

버킷 정책으로 지켜야 할 조건을 강제한다

{ "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyInsecureTransport",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": [
      "arn:aws:s3:::shop-uploads",
      "arn:aws:s3:::shop-uploads/*" ],
    "Condition": { "Bool":
      { "aws:SecureTransport": "false" } }
  }]
}

버킷 정책은 허용보다 Deny로 조건을 강제할 때 특히 쓸모 있습니다. 이 정책은 누구든(Principal: *) 버킷과 그 안의 객체(Resource 두 줄)에 대해, HTTPS가 아닌 요청이면(aws:SecureTransport가 false) 거부합니다.

같은 방식으로 aws:SourceVpce 조건을 걸어 13장의 VPC 엔드포인트를 거친 요청만 받거나, 특정 KMS 키로 암호화하지 않은 업로드를 막습니다.

ACL은 끄고 객체 소유권은 버킷에 둔다

정책보다 먼저 있던 권한 장치가 ACL입니다. 12장의 정책 유형 표에서 JSON이 아닌 고정 형식의 "옛 방식"으로 봤던 그것으로, 버킷과 객체 하나하나에 "이 계정에 읽기 허용" 같은 목록을 붙입니다.

ACL의 가장 큰 혼란은 소유권이었습니다. 다른 계정이 우리 버킷에 올린 객체는 업로더가 소유자가 되어, 버킷 주인인 우리가 그 객체를 읽지 못하는 일이 생겼습니다. 정책과 ACL이 섞이면 실제 권한을 추적하기도 어렵습니다.

객체 소유권 설정을 BucketOwnerEnforced로 두면 ACL이 꺼지고 모든 객체를 버킷 소유자가 가집니다. 권한은 정책만 보면 되게 됩니다. 새 버킷은 이것이 기본값이고, 기존 버킷도 이 값으로 바꾸는 것이 권장입니다.

퍼블릭 액세스 차단은 공개 실수를 덮어쓴다

12장에서 봤듯 클라우드 사고의 대부분은 고객 쪽 설정에서 나고, S3에서는 "버킷 정책 한 줄 실수로 전체 공개"가 대표적입니다. 퍼블릭 액세스 차단은 정책이나 ACL이 공개를 허용해도 그것을 무효로 만드는 안전장치입니다.

새 버킷은 네 설정이 모두 켜져 있습니다. 계정 수준에서도 켜 두면 누군가 실수로 버킷을 열어도 막힙니다. 공개가 필요한 정적 파일은 버킷을 닫은 채 CloudFront 뒤에 둡니다(16장).

요청 하나를 네 겹의 장치가 함께 판정한다

지금까지 본 장치를 한 줄로 세우면, S3 요청 하나가 받는 판정은 아래와 같습니다. 어느 단계에서든 거부되면 403이고, 마지막 단계까지 통과해야 데이터를 받습니다.

  1. 명시적 Deny어디에 있든 즉시 거부
  2. 퍼블릭 액세스 차단공개 허용을 무효화
  3. IAM + 버킷 정책같은 계정은 한쪽 Allow
  4. KMS 키 정책SSE-KMS면 Decrypt 권한

12장의 평가 규칙 그대로, Deny는 어느 정책에 있든 Allow보다 먼저 이깁니다. 그래서 앞 슬라이드의 HTTPS 강제 정책은 관리자 역할에게도 예외 없이 적용됩니다. 마지막 KMS 단계 때문에 S3 권한은 있는데 403이라면 키 정책을 먼저 의심합니다.

Access Point는 사용처마다 문을 따로 낸다

버킷 하나를 여러 팀과 앱이 쓰면 버킷 정책 하나에 규칙이 수십 개 쌓여 고치기 무서운 문서가 됩니다. Access Point는 버킷에 이름 붙은 출입구를 여러 개 만들고, 출입구마다 자기 정책을 붙입니다.

예를 들어 analytics-ap는 logs/ 읽기만, ingest-ap는 쓰기만 허용합니다. 출입구를 특정 VPC에서만 열리게 제한할 수도 있습니다. 팀마다 자기 출입구 정책만 고치면 되니 서로의 규칙을 건드릴 일이 없습니다.

버킷 정책에 위임을 적는다

버킷 정책에 "Access Point를 거친 요청은 Access Point 정책에 맡긴다"는 조건(s3:DataAccessPointAccount)을 두면 권한 관리가 출입구 쪽으로 옮겨 갑니다.

권한 이야기의 실전 응용입니다. 사용자가 리뷰 사진을 올릴 때 파일이 앱 서버를 거치면 큰 파일이 서버 메모리와 대역폭을 차지합니다. 그렇다고 브라우저에 AWS 자격 증명을 줄 수는 없습니다.

Presigned URL은 서버가 자기 자격 증명으로 특정 객체, 특정 동작, 만료 시각을 12장의 SigV4 방식으로 미리 서명해 둔 URL입니다. 받은 사람은 자격 증명 없이 그 일 하나만 할 수 있습니다.

URL은 서명한 자격 증명보다 오래 살지 못한다

Presigned URL은 서명한 주체의 권한을 넘지 못합니다. 그 주체에게 s3:PutObject가 없으면 URL도 403입니다.

만료는 설정한 시각과 자격 증명이 끝나는 시각 중 빠른 쪽입니다. SigV4 서명은 최대 7일이지만, 역할로 서명했다면 12장에서 본 역할 세션이 끝날 때 함께 만료됩니다. AssumeRole 세션은 기본 1시간이고, EC2 인스턴스 프로파일 자격 증명은 최대 약 6시간마다 바뀝니다.

"7일짜리 링크가 몇 시간 만에 죽어요"

ECS 태스크나 EC2 역할로 서명한 링크입니다. 오래 가야 하는 공유 링크는 CDN 쪽에서 별도 키로 서명하는 CloudFront Signed URL(16장)로 만듭니다.

큰 파일은 조각으로 나눠 병렬로 올린다

  1. CreateMultipartUpload

    업로드 ID를 받습니다.

  2. UploadPart × N

    조각마다 번호를 붙여 병렬로 올리고, 실패한 조각만 다시 보냅니다.

  3. CompleteMultipartUpload

    조각 목록을 보내면 S3가 하나의 객체로 합칩니다.

  4. 완료하지 않으면

    조각은 목록에 보이지 않게 남아 계속 과금됩니다.

상품 소개 영상처럼 큰 파일을 PUT 한 번으로 올리다 99%에서 끊기면 처음부터 다시 보내야 합니다. 멀티파트 업로드는 파일을 조각으로 나눠 실패한 조각만 재전송하고, 여러 조각을 동시에 보내 대역폭을 다 씁니다.

PUT 한 번은 5GB까지이고, 멀티파트는 조각 5MiB~5GiB, 최대 10,000개로 객체 하나를 최대 48.8TiB까지 만듭니다. AWS는 100MB부터 권장하며, SDK의 전송 관리자(TransferManager 등)가 이 과정을 대신합니다.

ETag는 객체 내용의 지문이다

2부에서 S3는 같은 키에 동시에 쓰면 마지막 쓰기가 이긴다고 했습니다. 이를 막으려면 "내가 읽은 그 버전일 때만 덮어써라"라고 말할 수단이 필요합니다. 그 수단이 ETag와 조건부 요청입니다.

ETag는 S3가 객체마다 붙여 돌려주는 식별 문자열입니다. 내용이 바뀌면 ETag도 바뀌므로 객체 내용의 지문처럼 쓸 수 있습니다. 한 번에 올린 객체는 대개 내용의 MD5 해시이고, 멀티파트로 올린 객체는 조각 해시들로 만든 다른 형식이라 내용 검증용 해시로 믿지는 않습니다.

HTTP에는 2장에서 본 304 응답을 만드는 조건부 요청 헤더가 있습니다. If-Match는 "ETag가 이 값일 때만", If-None-Match는 "이 값이 아닐 때만" 요청을 실행하라는 뜻입니다. S3는 이 헤더를 쓰기에도 받아 줍니다.

조건부 쓰기는 S3에서 덮어쓰기 경쟁을 막는다

# 같은 키가 없을 때만 생성
$ aws s3api put-object --bucket b \
    --key locks/job-42 --body owner.txt \
    --if-none-match "*"
An error occurred (PreconditionFailed)

# 내가 읽은 버전일 때만 덮어쓰기
$ aws s3api put-object --bucket b \
    --key state.json --body new.json \
    --if-match '"9b2cf535f27731c9"'

If-None-Match: *는 "어떤 ETag든 이미 있으면 실패"이므로, 키가 없을 때만 만들어집니다. 정산 작업자 여럿이 같은 작업을 집으려 할 때 하나만 이기게 하는 선점 장치가 됩니다. 진 쪽은 412(PreconditionFailed)를 받습니다.

If-Match는 읽을 때 받은 ETag가 그대로일 때만 씁니다. 4장의 낙관적 락, 즉 버전을 확인하며 쓰고 충돌하면 재시도하는 방식을 객체 저장소에서 하는 셈입니다. 동시 요청이 겹치면 409가 올 수 있으니 재시도합니다.

요청 성능은 접두사마다 따로 늘어난다

S3는 내부적으로 키를 정렬된 범위로 나눠 여러 서버에 맡기고, 부하가 몰리는 범위를 더 잘게 쪼갭니다. 그래서 처리 한도가 접두사 단위로 매겨집니다. 분할된 접두사 하나당 초당 최소 3,500건의 쓰기(PUT/COPY/POST/DELETE)와 5,500건의 읽기(GET/HEAD)를 처리하고, 읽기를 접두사 10개로 나누면 초당 55,000건까지 늘어납니다.

쪼개기는 트래픽을 보고 점진적으로 일어납니다. 그 사이에는 503 Slow Down이 나올 수 있고, 확장이 끝나면 사라집니다.

그래서 키 설계가 중요하다

모든 쓰기가 logs/2026-11-17/ 하나로 몰리면 그 접두사가 병목입니다. 해시나 테넌트 ID를 앞에 두어 접두사를 흩고, 503에는 백오프로 재시도합니다.

멀리서 올리기와 올린 뒤 처리하기

서울 사용자가 버지니아 리전 버킷에 큰 파일을 올리면 인터넷 구간이 길어 느리고 자주 끊깁니다. Transfer Acceleration은 사용자가 12장에서 본 엣지 로케이션, 즉 리전 밖 도시 곳곳에 있는 AWS 거점 중 가까운 곳으로 올리게 하고, 거기서부터는 AWS 전용 백본망으로 버킷까지 보냅니다. 전용 엔드포인트 bucket.s3-accelerate.amazonaws.com을 쓰며, 거리가 멀수록 효과가 큽니다.

업로드가 끝나면 보통 후속 작업이 따라옵니다. 쇼핑몰은 리뷰 사진이 올라오면 썸네일을 만들어야 합니다. 이벤트 알림은 객체 생성, 삭제, 복원 완료 같은 일이 생기면 다른 서비스에 알려 줍니다.

받는 쪽은 넷입니다. SNS는 여러 구독자에게 한꺼번에 뿌리는 알림 서비스, SQS는 메시지를 쌓아 두고 작업자가 꺼내 가는 큐, Lambda는 이벤트가 오면 함수 하나를 실행하는 서버리스 컴퓨팅, EventBridge는 규칙으로 이벤트를 골라 여러 대상에 보내는 이벤트 버스입니다. 지금은 이 정도로 알아 두면 되고 자세한 동작은 17장에서 봅니다.

알림은 적어도 한 번 전달이라 같은 알림이 두 번 올 수 있습니다. 그래서 받는 쪽은 8장에서 본 멱등 처리, 즉 같은 메시지를 두 번 받아도 결과가 한 번인 것처럼 만들어야 합니다.

정적 호스팅과 질의는 다른 서비스와 함께 쓴다

S3에 쌓인 데이터를 밖으로 내보내거나 분석하는 두 가지 기능으로 S3 이야기를 마칩니다. S3 정적 웹 사이트 호스팅을 켜면 버킷이 index.html과 오류 문서를 돌려주는 웹 서버가 됩니다. 하지만 웹 사이트 엔드포인트는 HTTPS를 지원하지 않고 버킷을 공개해야 합니다.

그래서 운영에서는 버킷을 닫아 두고 CloudFront(16장의 CDN)가 OAC(Origin Access Control)라는 서명된 접근으로만 버킷을 읽게 합니다. 사용자는 CloudFront로만 들어오고 버킷은 공개되지 않습니다.

S3에 쌓인 CSV, JSON 로그를 SQL로 조회하려면 Athena를 씁니다. 서버 없이 쿼리할 때 스캔한 데이터 양만큼 과금되므로, 읽는 양을 줄이는 것이 곧 비용 절감입니다. 날짜별 접두사(logs/dt=2026-11-17/)로 나눠 두면 필요한 날짜만 읽습니다.

또 Parquet 같은 열 형식, 즉 행이 아니라 열끼리 모아 압축해 저장하는 파일 형식을 쓰면 쿼리에 필요한 열만 읽습니다. 객체 하나 안을 SQL로 거르던 S3 Select는 신규 고객에게 더 이상 제공되지 않습니다.

4부

RDS는 4장의 DB 운영을 대신 맡는다

S3는 통째로 읽고 쓰는 데이터의 집이었습니다. 하지만 주문, 결제, 재고처럼 여럿이 동시에 고치고 조인과 트랜잭션으로 묻는 데이터는 4장의 관계형 DB가 맡아야 합니다. 이 부는 4장에서 본 복제와 커넥션 관리, 그리고 백업처럼 DB 서버를 직접 운영할 때 하던 일 중 무엇을 AWS에 맡길 수 있고, 장애 조치가 실제로 어떻게 일어나는지 봅니다.

DB를 EC2에 직접 띄우면 할 일이 쏟아진다

주문 DB를 EC2에 MySQL을 설치해 운영한다고 해 봅시다. 4장에서 배운 것을 전부 직접 해야 합니다.

  • 설치와 패치: OS와 DB 엔진의 보안 패치를 챙기고, 재시작 시간을 잡아야 합니다.
  • 백업과 복원: 매일 백업을 뜨고 로그를 보관하며, 실제로 복원되는지 주기적으로 시험해야 합니다.
  • 복제와 장애 조치: 다른 AZ에 복제본을 구성하고, 주 DB가 죽으면 이를 감지해 복제본을 승격하고 앱이 새 주소를 보게 해야 합니다.
  • 용량과 관측: 디스크가 차기 전에 늘리고, 느린 쿼리와 OS 지표를 모을 도구를 갖춰야 합니다.

이 일들을 서비스가 맡아 주는 DB를 관리형 DB라고 하고, AWS의 관리형 관계형 DB가 RDS입니다.

RDS가 맡는 일과 여전히 우리 몫인 일

영역RDS가 대신 함여전히 우리 몫

오른쪽 열이 비어 있지 않다는 점이 중요합니다. RDS는 서버를 관리해 줄 뿐 느린 쿼리와 앱의 재연결은 여전히 우리 문제입니다. 엔진은 MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2 중에서 고르고, OS에 직접 들어가야 하는 특수한 경우에는 RDS Custom이나 EC2 직접 운영을 고려합니다.

인스턴스 클래스는 CPU와 메모리, 스토리지는 IOPS

RDS를 만들 때 처음 고르는 것은 서버 크기와 디스크입니다. DB 인스턴스 클래스는 14장의 EC2 이름 규칙을 그대로 씁니다. db.r7g.large는 메모리 최적화(r), 7세대, Graviton(g)입니다. 4장에서 본 버퍼 풀, 즉 디스크 페이지를 메모리에 올려 두는 캐시가 클수록 디스크를 덜 읽으므로 DB는 보통 메모리가 넉넉한 r 계열이 기본입니다.

스토리지는 14장의 EBS 볼륨과 같은 gp3가 기본입니다. RDS의 gp3는 3,000 IOPS·125MiB/s를 기본으로 주는데, MySQL·PostgreSQL·MariaDB는 400GiB부터 데이터를 볼륨 4개에 나눠 쓰는 스트라이핑을 해서 12,000 IOPS·500MiB/s가 기본이 됩니다. 볼륨 넷이 동시에 일하니 성능도 네 배가 되는 것입니다.

짧은 트랜잭션이 끊임없이 들어오는 주문 처리 같은 작업을 OLTP라고 합니다. 규모가 큰 OLTP에서 지연이 늘 일정해야 하면 io2 Block Express(Provisioned IOPS)로 IOPS를 따로 삽니다.

어떤 스토리지를 골라도 인스턴스 클래스마다 EBS 대역폭 한도가 있습니다. 14장에서 봤듯 스토리지 IOPS를 아무리 올려도 작은 인스턴스는 그 한도에서 막힙니다.

스토리지 자동 확장은 여유 10%에서 움직인다

주문이 쌓이면 디스크는 언젠가 찹니다. 스토리지 자동 확장을 켜면 남은 공간이 할당량의 10% 이하로 5분 이상 유지될 때 RDS가 스토리지를 늘립니다.

한 번 늘린 뒤에는 14장의 Elastic Volumes에서 본 볼륨 최적화가 끝나야 다시 늘릴 수 있어, 몇 시간 동안은 추가 확장이 막힐 수 있습니다. 상한(최대 스토리지 임곗값)은 현재 크기보다 최소 10% 크게, 권장은 26% 이상입니다.

스토리지는 줄일 수 없다

RDS 스토리지는 늘리기만 됩니다. 대량 로그 테이블 때문에 한 번 커지면, 줄이려면 새 인스턴스로 데이터를 옮겨야 합니다.

설정은 파라미터 그룹으로 모아 바꾼다

RDS는 OS 접속을 막으므로 my.cnf 같은 설정 파일을 직접 고칠 수 없습니다. 대신 파라미터 그룹이라는 설정 묶음을 만들어 인스턴스에 연결합니다. 기본 그룹은 수정할 수 없으니 처음부터 사용자 그룹을 만들어 둡니다.

파라미터는 즉시 반영되는 dynamic과 재부팅해야 반영되는 static으로 나뉩니다. static을 바꾸면 상태가 pending-reboot로 남아, 다음 재부팅까지 실제로는 옛 값으로 돕니다.

옵션 그룹은 엔진의 추가 기능을 켜는 장치입니다. MariaDB의 감사 플러그인, Oracle의 TDE(Transparent Data Encryption: DB 엔진이 데이터 파일을 스스로 암호화하는 기능), SQL Server의 네이티브 백업·복원 같은 것이 여기 있습니다.

자주 만지는 값은 max_connections, 슬로 쿼리 로그, 타임존, 문자셋입니다.

복제는 커밋을 언제 돌려주느냐로 세 가지다

이제 가용성입니다. 4장에서 본 복제 방식을 한 줄씩 떠올려 봅시다. 비동기 복제는 주 DB가 커밋하자마자 응답하고 사본에는 나중에 보내므로 빠르지만, 주 DB가 죽으면 아직 안 간 커밋을 잃습니다. 반동기는 사본 하나가 변경을 받았다고 확인한 뒤 응답하고, 동기는 사본에 반영까지 확인한 뒤 응답해 가장 안전하고 가장 느립니다.

주 DB가 죽었을 때 사본 하나를 새 주 DB로 올리고 클라이언트가 그쪽으로 가게 하는 일을 장애 조치라고 합니다. 복제 방식이 안전할수록 장애 조치 때 잃는 데이터가 적습니다.

RDS는 이 선택을 세 가지 배치로 제공합니다. 장애 조치만을 위한 동기 대기, 장애 조치와 읽기를 함께 맡는 반동기 클러스터, 읽기 확장을 위한 비동기 복제본입니다. 하나씩 봅니다.

Multi-AZ 인스턴스는 커밋마다 다른 AZ를 기다린다

Multi-AZ 인스턴스 배포는 다른 AZ에 대기 인스턴스를 두고 스토리지 수준에서 동기 복제합니다. 기본 인스턴스의 쓰기는 대기 쪽 디스크에도 써졌다는 확인을 받아야 커밋됩니다.

그래서 커밋된 데이터는 장애가 나도 잃지 않지만, AZ 사이 왕복만큼 쓰기 지연이 늘어납니다. 대기는 연결을 받지 않으므로 이것은 읽기 확장 수단이 아니라 순수한 보험입니다.

Multi-AZ DB 클러스터는 대기도 읽기를 받는다

보험으로 놀고 있는 대기가 아깝다면 Multi-AZ DB 클러스터를 씁니다. 서로 다른 세 AZ에 쓰기를 받는 writer 하나와 읽기만 받는 reader 둘을 둡니다.

엔진 수준의 반동기 복제라서 reader 중 하나만 변경을 받았다고 확인하면 커밋됩니다. 둘을 모두 기다리지 않으니 Multi-AZ 인스턴스보다 쓰기 지연이 짧고, reader는 읽기 트래픽도 받습니다. 장애 시에는 가장 최근 변경을 가진 reader가 승격됩니다.

확인은 "받았다"이지 "반영했다"가 아니다

reader가 아직 적용하지 못한 변경이 쌓이면 복제 지연이 생기고, 장애 조치는 그 지연을 다 적용한 뒤에야 끝납니다. MySQL은 흐름 제어로 지연이 커지면 writer의 쓰기를 늦춥니다.

읽기 전용 복제본은 비동기라 늦게 따라온다

상품 목록처럼 읽기가 쓰기보다 훨씬 많으면 읽기를 나눌 사본이 필요합니다. 읽기 전용 복제본은 4장의 비동기 레플리케이션을 관리형으로 만든 것입니다. 원본의 변경 로그(MySQL의 binlog, PostgreSQL의 WAL)를 받아 다시 실행하므로 복제 지연이 생기고, 원본이 갑자기 죽으면 아직 오지 않은 커밋은 잃습니다.

복제본은 자기 엔드포인트가 따로 있고, 다른 리전에도 둘 수 있습니다. 만들려면 원본의 자동 백업이 켜져 있어야 합니다.

승격하면 복제본이 복제를 끊고 독립 DB가 됩니다. 다른 리전 복제본을 승격하는 것이 가장 단순한 리전 단위 재해 복구 방법입니다(18장).

RDS는 복제본 개수를 자동으로 늘리지 않습니다. 읽기 부하에 맞춰 스스로 늘고 줄어야 한다면 5부에서 볼 Aurora의 복제본 Auto Scaling을 씁니다.

쇼핑몰 주문 DB라면 Multi-AZ 인스턴스 배포로 장애에 대비하고, 상품 목록 조회용 읽기 전용 복제본을 붙이는 구성이 가장 흔한 출발점입니다. 그럼 표의 "장애 조치 60~120초" 동안 실제로 무슨 일이 일어나는지 봅니다.

장애 조치는 DNS를 바꿔서 끝난다

  1. 장애 감지

    기본 인스턴스, 스토리지, 네트워크, AZ의 이상을 RDS가 감지합니다.

  2. 대기 승격

    동기 복제본이라 커밋된 데이터는 이미 대기에 있습니다.

  3. DNS 전환

    엔드포인트 레코드가 새 기본 인스턴스를 가리킵니다.

  4. 재연결

    기존 커넥션은 끊깁니다. 앱이 다시 연결해야 합니다.

RDS의 엔드포인트는 DB 인스턴스의 IP가 아니라 DNS 이름입니다. 장애 조치는 이 이름이 가리키는 IP를 바꿔 끝나고, 보통 60~120초, 큰 트랜잭션을 복구하는 중이면 더 걸립니다.

이름이 그대로라 설정은 바꿀 필요가 없지만, 13장에서 봤듯 앱이 옛 IP를 캐시하거나 죽은 커넥션을 붙잡으면 장애가 길어집니다. 같은 절차가 패치나 인스턴스 유형 변경 때도 쓰이며, 앱 쪽 대응은 8부에서 봅니다.

자동 백업은 스냅샷과 로그로 시점 복원을 만든다

장애 조치는 서버가 죽는 사고를 막지만, 누군가 DELETE를 잘못 실행한 사고는 사본에도 그대로 복제됩니다. 이때 필요한 것이 백업입니다.

RDS는 매일 백업 창에 스토리지 스냅샷을 찍고(첫 번째 이후는 바뀐 블록만 저장하는 증분), 그 사이 트랜잭션 로그를 S3에 계속 올립니다. 스냅샷에 로그를 재생하면 보관 기간 안의 원하는 시각으로 되돌리는 특정 시점 복원(PITR)이 됩니다. 4장에서 커밋은 로그를 쓰는 일이고 로그를 다시 실행하면 데이터가 복원된다고 했던 원리 그대로이며, 보통 5분 전 시점까지 됩니다.

복원하면 새 인스턴스가 생긴다

기존 DB를 되돌리지 않습니다. 새 엔드포인트로 앱을 돌리고, 보안 그룹과 파라미터 그룹도 다시 확인합니다.

보관 기간은 0~35일이고, 0이면 자동 백업과 읽기 전용 복제본이 모두 꺼집니다. 수동 스냅샷은 DB를 지워도 남으니 큰 변경 전에 찍어 둡니다.

패치와 업그레이드는 유지 관리 기간에 온다

RDS가 패치를 대신 해 준다는 것은, 그 패치가 언제 적용될지도 RDS가 정한다는 뜻입니다. 인스턴스마다 매주 30분짜리 유지 관리 기간이 있고, 지정하지 않으면 리전별 8시간 블록 안에서 무작위로 정해지므로 트래픽이 가장 적은 시간으로 직접 지정합니다.

자동 마이너 버전 업그레이드를 켜 두면 버그·보안 수정인 마이너 패치(8.0.39 → 8.0.40)가 이 기간에 적용됩니다. Multi-AZ라면 대기를 먼저 패치하고 장애 조치한 뒤 옛 기본을 패치해 중단을 줄입니다.

메이저 버전 업그레이드(MySQL 8.0 → 8.4 등)는 동작이 바뀔 수 있어 자동으로 하지 않습니다. 호환되지 않는 문법과 파라미터가 있을 수 있으니 직접 계획하고 시험합니다.

엔진 버전에도 표준 지원 종료일이 있고, 지나면 유료 연장 지원으로 넘어갑니다. 업그레이드를 미루는 것도 비용입니다. 그 업그레이드를 안전하게 하는 장치가 다음 슬라이드입니다.

Blue/Green으로 업그레이드를 1분 안에 바꿔 탄다

  1. Green 생성

    운영(Blue)을 복사하고 논리 복제로 계속 따라오게 합니다.

  2. Green 변경

    메이저 업그레이드, 파라미터 변경을 Green에만 적용하고 시험합니다.

  3. 전환(switchover)

    쓰기를 막고 복제를 따라잡은 뒤 이름을 바꿔 Green을 운영으로 만듭니다.

RDS Blue/Green Deployments는 11장의 Blue-Green 배포를 DB에 적용한 기능입니다. 핵심은 논리 복제로, 디스크 블록이 아니라 "이 행을 이렇게 바꿨다"는 변경 내용을 보내므로 버전이 다른 엔진 사이에서도 복제가 됩니다.

전환은 보통 1분 안에 데이터 손실 없이 끝나고, 엔드포인트 이름이 그대로라 앱 설정을 바꾸지 않습니다. RDS for MySQL, MariaDB, PostgreSQL과 Aurora에서 씁니다.

RDS Proxy는 많은 클라이언트를 적은 연결에 싣는다

4장에서 봤듯 DB 연결은 만들기 비싸고 max_connections로 상한이 있습니다. 그런데 Lambda(요청마다 짧게 떴다 사라지는 함수 실행 환경, 17장)처럼 연결을 마구 여는 클라이언트가 몰리면 DB가 연결 처리만으로 쓰러집니다.

RDS Proxy는 앱과 DB 사이의 관리형 커넥션 풀입니다. 트랜잭션이 끝나면 DB 연결을 다른 클라이언트에게 넘기는 멀티플렉싱으로 연결 수를 줄이고, 장애 조치 동안 클라이언트 연결을 붙잡았다가 새 기본으로 이어 줍니다.

세션 상태를 쓰면 프록시가 연결을 고정한다

멀티플렉싱은 "다음 트랜잭션이 이전 상태에 기대지 않는다"는 전제에서만 안전합니다. 클라이언트가 SET으로 세션 변수를 바꾸거나 임시 테이블을 만들면, 그 상태는 특정 DB 연결에만 남습니다. 그래서 프록시는 그 클라이언트를 DB 연결 하나에 붙박는 피닝을 합니다.

피닝된 연결은 다른 클라이언트와 나눠 쓰지 못하므로 피닝이 많으면 프록시를 둔 효과가 사라집니다. 16KB가 넘는 문장도 피닝을 일으킵니다.

피닝을 숫자로 본다

CloudWatch의 DatabaseConnectionsCurrentlySessionPinned 지표를 봅니다. 드라이버가 연결마다 보내는 초기 SET 문은 프록시의 초기화 쿼리 설정으로 옮겨 피닝을 피합니다.

느린 원인은 DB가 무엇을 기다리는지로 찾는다

4장에서는 쿼리 하나를 EXPLAIN으로 분석했습니다. 운영 중인 DB 전체가 느릴 때는 "지금 DB가 무엇 때문에 바쁜가"를 먼저 알아야 합니다. 그 답을 주는 것이 Performance Insights이고, 지금은 CloudWatch Database Insights로 통합되었습니다.

핵심 지표는 평균 활성 세션(AAS), 즉 특정 순간에 일하고 있거나 무언가를 기다리는 세션 수의 평균입니다. AAS가 vCPU 수보다 크면 일이 처리 능력보다 많이 밀려 있다는 뜻입니다.

이 부하를 대기 이벤트, 즉 세션이 멈춰 서서 기다리는 대상(CPU, 행 락, 디스크 읽기, 로그 쓰기 등)별로 쪼개 보여 주고, SQL·호스트·사용자별로도 나눕니다. "CPU 대기인가, 락 대기인가, I/O 대기인가"를 바로 알 수 있으니 처방의 방향이 정해집니다.

DB 바깥의 OS 상태는 따로 봅니다. 기본 CloudWatch 지표는 하이퍼바이저 쪽에서 1분 단위로 잽니다. Enhanced Monitoring은 인스턴스 안 에이전트가 최대 1초 간격으로 프로세스별 CPU, 메모리, 디스크를 보내 주어 순간적인 급증을 잡습니다.

암호화는 만들 때 정하고, 비밀번호 대신 IAM도 된다

RDS 저장 데이터 암호화는 3부에서 본 KMS 키로 하며, 인스턴스를 만들 때만 켤 수 있습니다. 이미 운영 중인 암호화되지 않은 DB는 스냅샷을 암호화하며 복사한 뒤 복원하거나, Blue/Green으로 암호화된 Green을 만들어 옮깁니다. 복제본과 스냅샷은 원본의 암호화를 따라갑니다.

IAM DB 인증을 켜면 앱은 비밀번호 대신 IAM 역할로 서명한 15분짜리 인증 토큰으로 접속합니다. DB 비밀번호를 어디에도 저장하지 않아도 되지만, 토큰 생성이 연결마다 필요하니 커넥션 풀과 함께 씁니다.

비밀번호를 쓴다면 비밀 값을 보관하고 주기적으로 자동 교체해 주는 Secrets Manager에 맡깁니다(16장).

5부

Aurora는 DB의 아래 절반을 다시 만들었다

4부의 RDS에는 분명한 한계가 남았습니다. 복제본은 늦게 따라오고, 장애 조치는 1~2분 걸리며, 스토리지는 줄일 수 없습니다. RDS가 기존 엔진을 그대로 관리해 준다면, Aurora는 엔진 밑의 스토리지 계층을 분산 시스템으로 바꿔 이 한계를 풉니다. 이 부는 그 구조가 숫자를 어떻게 바꾸는지 봅니다.

RDS의 한계는 인스턴스마다 디스크가 따로라는 데서 온다

4부의 구성을 다시 보면 DB 인스턴스마다 자기 EBS 디스크가 있고, 복제는 그 디스크들의 내용을 맞추는 일입니다. 여기서 세 가지 비용이 생깁니다.

  • 같은 일을 두 번 합니다. 복제본은 원본의 변경을 다시 실행해 자기 디스크에 씁니다. 원본에서 1분 걸린 대량 UPDATE는 복제본에서도 1분 걸리고, 그동안 복제 지연이 쌓입니다.
  • 쓰기가 부풀어 오릅니다. 엔진은 같은 변경을 로그와 데이터 페이지로 여러 번 쓰고, Multi-AZ면 그 쓰기가 전부 다른 AZ로 한 번 더 건너갑니다.
  • 사본을 늘리는 데 복사가 듭니다. 복제본 하나를 추가하려면 수 TB의 데이터를 통째로 복사해야 합니다.

Aurora의 발상은 단순합니다. 디스크를 인스턴스에서 떼어 내 모두가 함께 쓰게 하자는 것입니다.

모든 인스턴스가 하나의 클러스터 볼륨을 공유한다

Aurora는 MySQL·PostgreSQL과 호환되는 AWS의 관계형 DB입니다. writer와 reader가 3개 AZ에 걸친 하나의 클러스터 볼륨을 함께 쓰고, 볼륨은 데이터를 AZ마다 2개씩 6개 스토리지 노드에 둡니다.

컴퓨팅과 스토리지가 분리되어 있으니 reader를 추가해도 데이터를 복사하지 않습니다. reader는 최대 15개, 볼륨은 쓰는 만큼 자동으로 커지며 일부 엔진 버전은 256TiB까지 늘어납니다.

쿼럼은 과반이 아니라 겹침으로 최신을 보장한다

그림 아래의 "6개 중 4개", "6개 중 3개"를 이해하려면 쿼럼이라는 개념이 필요합니다. 사본이 6개일 때 쓰기마다 6개 전부의 확인을 기다리면, 노드 하나만 느려도 모든 쓰기가 느려지고 하나만 죽어도 쓰기가 멈춥니다. 그렇다고 하나만 확인하고 끝내면 그 노드가 죽을 때 데이터를 잃습니다.

쿼럼은 그 사이의 규칙입니다. 사본 V개 중 쓰기는 W개가 확인하면 성공, 읽기는 R개가 응답하면 성공으로 칩니다. 이때 W + R > V이면 어떤 읽기 집합도 직전 쓰기 집합과 최소 한 노드가 겹치므로, 읽은 것 중에 반드시 최신 값이 들어 있습니다.

Aurora는 V=6, W=4, R=3입니다. 4+3=7로 6보다 크니 읽기와 쓰기가 겹치고, 4+4=8도 6보다 커서 서로 다른 두 쓰기가 동시에 성공하는 일도 없습니다. 느린 노드 둘은 기다리지 않아도 되니 꼬리 지연도 줄어듭니다.

덧붙여, 평소 읽기는 쿼럼을 쓰지 않습니다. DB 인스턴스가 스토리지 노드마다 어느 로그까지 받았는지 추적하고 있어서, 읽으려는 시점까지 다 받은 노드 하나만 골라 읽습니다. 3개 읽기 쿼럼은 인스턴스가 재시작해 그 추적 상태를 잃었을 때, 복구 과정에서 다시 세우는 데 쓰입니다. 이 설계는 Aurora 설계 논문(SIGMOD 2017)에 정리되어 있습니다.

4/6 쿼럼은 AZ 하나를 잃어도 쓰게 해 준다

숫자를 장애에 대입해 봅시다. AZ 하나가 통째로 죽으면 그 AZ의 사본 2개를 잃어도 4개가 남아 쓰기가 계속됩니다. AZ 하나에 더해 다른 노드 하나까지 잃어도 3개가 남아 읽기가 가능하고, 남은 사본으로 잃은 사본을 다시 채우는 복구가 진행됩니다.

쓰기를 가볍게 만드는 장치가 하나 더 있습니다. writer는 데이터 페이지를 보내지 않고 4장에서 본 redo 로그 레코드만, 즉 "이 페이지의 이 위치를 이렇게 바꿨다"는 짧은 기록만 스토리지로 보냅니다. 로그를 페이지에 적용하는 일은 스토리지 노드가 뒤에서 합니다.

앞에서 본 "쓰기가 부풀어 오르는" 문제가 여기서 풀립니다. 네트워크로 오가는 것이 작은 로그뿐이라 같은 하드웨어에서 쓰기 처리량이 크게 늘어납니다.

같은 볼륨을 읽으니 복제 지연이 짧다

RDS 복제본은 원본의 변경을 다시 실행해 자기 디스크에 써야 했습니다. Aurora reader는 데이터를 다시 쓰지 않습니다. 같은 볼륨을 읽고, writer가 보내는 로그로 자기 메모리 캐시에 올라 있는 페이지만 갱신합니다.

할 일이 "디스크 쓰기"에서 "메모리의 몇 페이지 갱신"으로 줄었으니, 복제 지연이 보통 100밀리초보다 훨씬 짧습니다.

짧아도 0은 아니다

쓰기가 몰리면 지연이 늘어납니다. 4장의 복제 지연(방금 쓴 값이 복제본에 아직 없는 문제) 때문에, 쓴 직후 본인이 다시 읽는 화면은 여전히 writer로 보내야 합니다.

인스턴스가 여럿이니 앱은 어디로 연결할지 골라야 합니다. Aurora는 목적별로 DNS 이름 네 종류를 줍니다.

리더 엔드포인트는 DNS 수준에서, 연결 단위로 나눕니다. 커넥션 풀이 연결을 오래 붙잡으면 새로 추가한 reader에 트래픽이 가지 않으므로, 풀의 최대 연결 수명을 짧게 둡니다.

Aurora 장애 조치는 대개 30초 안팎에 끝난다

writer가 죽으면 reader 하나가 승격되고 클러스터 엔드포인트가 그쪽을 가리킵니다. 데이터는 이미 공유 볼륨에 있으니 따라잡을 복제가 없고, 서비스는 보통 60초 안에, 많은 경우 30초 안에 돌아옵니다.

reader가 하나도 없으면 writer를 새로 만들어야 해서 보통 10분 가까이 걸립니다. 그래서 운영 클러스터에는 다른 AZ에 reader를 최소 하나 둡니다.

어느 reader를 승격할지는 승격 우선순위(tier 0~15)로 정합니다. 숫자가 작을수록 먼저이고, 같으면 큰 인스턴스가 먼저입니다.

writer와 같은 크기의 reader를 tier 0에 두세요. 작은 분석용 reader가 승격되면 장애 조치는 성공했는데 곧바로 과부하로 다시 쓰러집니다.

Serverless v2는 ACU 단위로 초마다 늘고 준다

쇼핑몰은 낮과 밤, 평일과 할인 행사 때 부하가 몇 배씩 다릅니다. 고정 크기 인스턴스는 최대 부하에 맞춰 사야 합니다. Aurora Serverless v2는 인스턴스 크기 대신 용량 범위를 정하고, 그 안에서 부하에 맞춰 늘고 줍니다.

단위는 ACU로, 1 ACU는 약 2GiB 메모리와 그에 맞는 CPU·네트워크입니다. 용량은 초 단위로 측정되어 쓴 만큼 과금되고, 범위는 0 ACU부터 Aurora MySQL 256, PostgreSQL 384 ACU까지입니다. 최소를 0으로 두면 부하가 없을 때 자동으로 멈춥니다.

프로비저닝과 섞어 쓸 수 있다

writer는 고정 크기 인스턴스로, reader만 Serverless v2로 두어 낮과 밤의 읽기 부하 차이를 흡수하는 구성이 흔합니다.

최소 ACU가 너무 낮으면

버퍼 풀도 함께 작아져 트래픽이 갑자기 몰릴 때 캐시가 비어 느립니다. 운영 writer의 최소값은 평소 부하 기준으로 잡습니다.

Global Database는 1초 안에 리전을 넘는다

지금까지는 리전 하나 안의 이야기였습니다. Global Database는 쓰기를 받는 기본 리전 하나와 읽기 전용 보조 리전을 최대 10개 둡니다. 복제는 엔진이 아니라 스토리지 계층의 전용 인프라가 맡아 보통 1초 안에 도착합니다.

보조 리전 사용자는 가까운 곳에서 읽습니다. 보조 리전의 앱이 쓰기를 해야 하면 write forwarding을 켜서, 보조 클러스터가 받은 쓰기를 기본 리전으로 대신 넘기게 할 수 있습니다.

기본 리전을 옮기는 방법은 둘입니다. 계획된 이동은 switchover로 복제를 다 따라잡은 뒤 데이터 손실 없이, 기본 리전 장애는 failover로 아직 복제되지 않은 몇 초의 쓰기를 포기하고 보조 리전을 승격합니다.

Global Database 쓰기 엔드포인트는 전환 뒤에도 기본 클러스터를 따라갑니다. 멀티 리전 재해 복구 설계는 18장에서 봅니다.

Backtrack은 되감고, Cloning은 싸게 복사한다

공유 볼륨 구조는 두 가지 편의 기능도 가능하게 합니다. Backtrack은 Aurora MySQL 클러스터를 새 클러스터 없이 과거 시점으로 되감습니다. 실수로 테이블을 지웠을 때 4부의 PITR은 새 클러스터를 만드느라 몇 시간이 걸리지만, Backtrack은 몇 분이면 됩니다. 되감을 수 있는 창은 최대 72시간이고 Aurora PostgreSQL은 지원하지 않습니다.

Cloning은 9장의 컨테이너 쓰기 레이어에서 본 복사 후 쓰기(copy-on-write)로 클러스터를 복제합니다. 처음에는 같은 스토리지 페이지를 함께 가리키다가, 어느 한쪽이 바꾼 페이지만 새로 저장합니다.

그래서 운영 데이터 그대로 마이그레이션을 리허설하거나 분석 쿼리를 돌릴 사본을 수 분 만에, 바뀐 만큼의 비용으로 만듭니다.

Aurora 요금은 I/O를 따로 내느냐로 갈린다

Aurora를 고르기 전에 요금 구조를 알아야 합니다. RDS는 미리 할당한 스토리지 크기에 돈을 내지만, Aurora는 실제로 쓴 볼륨 크기에 돈을 내고 데이터를 지우면 청구도 줄어듭니다.

여기에 I/O, 즉 스토리지 읽기·쓰기 요청을 어떻게 셀지 두 모델이 있습니다. Standard는 I/O 요청 수만큼 따로 과금합니다. I/O-Optimized는 I/O 요금이 없는 대신 인스턴스와 스토리지 단가가 높습니다.

읽기·쓰기가 많아 청구서에서 I/O 비중이 크면 I/O-Optimized가 유리합니다. AWS는 I/O 비용이 Aurora 전체 비용의 25% 이상이면 I/O-Optimized를 권장합니다. 비용 탐색기에서 지난 몇 달의 비중을 확인하고 바꾸면 됩니다.

6부

질의를 버리고 규모를 얻는 저장소

장바구니와 조회수는 사용자 ID나 글 ID 같은 키 하나로만 읽고 쓰지만, 트래픽이 주문보다 몇십 배 많습니다. 4장에서 NoSQL은 조인과 자유로운 질의를 포기하고 수평 확장을 얻는다고 했습니다. 이 부는 AWS가 그 거래를 DynamoDB로 어떻게 구현했는지, 그래서 키를 어떻게 설계해야 하는지 봅니다.

관계형 DB는 키 하나로 몰리는 대량 트래픽에 약하다

장바구니를 주문 DB에 넣으면 어떻게 될까요? 장바구니는 상품을 담고 뺄 때마다 쓰기가 일어나 할인 행사 때는 초당 수만 건이 됩니다. 그런데 4~5부의 RDS와 Aurora는 writer 하나가 모든 쓰기를 받습니다. 읽기는 복제본으로 나눌 수 있어도, 쓰기는 더 큰 인스턴스를 사는 것 말고는 늘릴 방법이 없습니다.

4장의 답은 샤딩, 즉 데이터를 키로 나눠 여러 DB에 흩는 것이었지만, 샤드 라우팅과 재분배를 직접 만들고 운영해야 했습니다. 장바구니는 조인도 복잡한 질의도 필요 없으니 그 수고를 들일 이유가 더 적습니다.

DynamoDB는 이 샤딩을 AWS가 대신 해 주는 키-값·문서형 DB입니다. 서버나 인스턴스 크기를 고르지 않고, 요청한 만큼 과금되며, 데이터가 늘어도 키로 찾는 지연이 한 자릿수 밀리초로 일정합니다. 대가는 키로만 찾을 수 있다는 제약입니다.

DynamoDB는 키로만 찾는 거대한 해시 테이블이다

DynamoDB는 테이블에 아이템(행)을 넣고, 아이템은 속성(열)을 자유롭게 가집니다. 스키마로 정하는 것은 기본 키뿐이라, 오른쪽의 items처럼 목록이나 중첩 객체도 그대로 담습니다.

기본 키는 파티션 키 하나이거나, 파티션 키 + 정렬 키입니다. 같은 파티션 키를 가진 아이템들은 정렬 키 순서로 모여 저장됩니다. 예제에서는 사용자 42의 주문들이 PK=USER#42 아래 날짜순으로 놓입니다.

{
  "PK": "USER#42",       // 파티션 키
  "SK": "ORDER#2026-11-17", // 정렬 키
  "total": 32000,
  "status": "PAID",
  "items": [ { "sku": "A1", "qty": 2 } ]
}

파티션 키의 해시가 저장 위치를 정한다

DynamoDB는 파티션 키 값을 해시해서 아이템이 갈 내부 파티션을 정합니다. 3장의 해시 테이블이 키를 해시해 칸을 고르던 것을 서버 여러 대로 넓힌 발상입니다. 파티션은 데이터나 처리량이 늘면 자동으로 쪼개집니다.

파티션 하나가 처리할 수 있는 양에는 상한이 있습니다. 읽기 용량 단위(RCU)와 쓰기 용량 단위(WCU)는 요청 크기를 표준화한 단위로, 계산법은 뒤에서 봅니다. 파티션당 초당 3,000 RCU, 1,000 WCU가 상한이라서 값이 고르게 퍼지는 파티션 키가 성능의 전부입니다.

Query는 파티션 하나를, Scan은 전체를 읽는다

# 사용자 42의 11월 주문: 파티션 하나만 읽음
$ aws dynamodb query --table-name shop \
  --key-condition-expression \
    "PK = :u AND begins_with(SK, :p)" \
  --expression-attribute-values '{
    ":u": {"S": "USER#42"},
    ":p": {"S": "ORDER#2026-11"} }'

# 상태가 PAID인 모든 주문: 전체를 읽고 거름
$ aws dynamodb scan --table-name shop \
  --filter-expression "#s = :paid" ...

키로 찾는다는 제약이 실제로 어떤 모습인지 봅니다. Query는 파티션 키를 반드시 지정하고, 정렬 키 조건(여기서는 ORDER#2026-11로 시작)으로 범위를 좁힙니다. 읽은 양만큼만 비용이 듭니다.

파티션 키를 모르면 Scan밖에 없습니다. Scan은 테이블 전체를 1MB씩 읽고, 필터는 읽은 뒤에 거르는 것이라 비용은 전부 냅니다.

다른 키로 찾으려면 그 키로 정렬된 사본을 만든다

쇼핑몰 관리자 화면은 "결제 대기 중인 주문 전부"를 봐야 합니다. 테이블의 파티션 키는 사용자 ID라서 이 질문은 Scan이 됩니다. 4장에서 인덱스가 원하는 열로 정렬된 별도 구조였던 것처럼, DynamoDB도 다른 키로 정렬된 사본을 하나 더 두는 것으로 답합니다. 이것을 보조 인덱스라고 합니다.

GSI(전역 보조 인덱스)는 파티션 키부터 새로 정합니다. 예를 들어 파티션 키를 status, 정렬 키를 주문 시각으로 두면 "PAID 상태를 시간순으로"가 Query 한 번이 됩니다. 테이블 전체를 가로지르므로 "전역"입니다.

LSI(로컬 보조 인덱스)는 파티션 키는 그대로 두고 정렬 키만 바꿉니다. "사용자 42의 주문을 금액순으로"처럼 한 파티션 안에서 다른 순서가 필요할 때 씁니다.

GSI는 내부적으로 별도 테이블에 비동기로 복사됩니다. 그래서 읽기가 최종 일관성뿐이고, 쓰기 비용이 인덱스 수만큼 늘며, GSI 처리량이 모자라면 원본 테이블 쓰기까지 쓰로틀링됩니다. 생성 후 추가할 수 있다는 유연성 때문에 대부분은 GSI를 씁니다. 표의 "최종 일관성"과 "강력 일관성"이 무슨 차이인지 다음에 봅니다.

기본 읽기는 최종 일관성이고 비용은 절반이다

DynamoDB는 데이터를 여러 AZ에 복제합니다. 2부의 S3에서 본 것과 같은 질문이 생기는데, DynamoDB는 답을 요청마다 고르게 합니다. 기본 읽기는 최종 일관성이라 방금 끝난 쓰기가 반영되지 않았을 수 있고, 잠시 뒤 다시 읽으면 최신값이 나옵니다.

ConsistentRead=true를 주면 강력 일관성 읽기로 최신값을 보장받는 대신 비용이 두 배입니다. 테이블과 LSI에서만 되고, GSI와 Streams는 항상 최종 일관성입니다.

4장의 PACELC로 보면

평소에는 지연(L)과 일관성(C) 중 하나를 요청마다 고르게 한 설계입니다. 기본값은 지연과 비용 쪽입니다. 장바구니 표시는 최종 일관성으로, 결제 직전 재고 확인은 강력 일관성으로 읽습니다.

용량은 요청마다 사거나 미리 사 둔다

앞에서 "비용이 두 배"라고 했는데, DynamoDB의 비용과 처리 한도는 모두 요청 단위로 계산됩니다. 그 요청을 어떻게 살지 두 가지 용량 모드가 있습니다.

온디맨드는 미리 정하는 것 없이 실제 요청 수만큼 냅니다. 트래픽이 예측되지 않거나 들쭉날쭉한 서비스에 맞고, 지금은 이것이 기본이자 권장값입니다.

프로비저닝은 초당 읽기·쓰기 용량을 미리 정해 사 둡니다. 14장의 EC2 Auto Scaling처럼 사용률을 보고 용량을 자동 조정하게 할 수 있습니다. 트래픽이 꾸준하고 예측 가능하면 온디맨드보다 쌀 수 있지만, 정한 용량을 넘는 요청은 거절됩니다. 어느 모드든 요청의 크기를 세는 단위는 같고, 그것이 다음 슬라이드의 RCU와 WCU입니다.

RCU와 WCU는 크기를 올림해서 센다

1 RCU는 4KB 이하 아이템의 강력 일관성 읽기 1회/초, 또는 최종 일관성 읽기 2회/초입니다. 1 WCU는 1KB 이하 쓰기 1회/초입니다. 트랜잭션 읽기·쓰기는 두 배를 씁니다.

크기는 단위 크기로 올림합니다. 3KB 읽기도 4KB로, 1.5KB 쓰기는 2KB, 즉 2 WCU로 셉니다. 그래서 아이템을 작게 유지하는 것이 곧 비용 절감입니다.

요구계산용량
3KB 강력 읽기 80회/초3/4 → 1 × 8080 RCU
3KB 최종 읽기 80회/초80 ÷ 240 RCU
6KB 강력 읽기 80회/초6/4 → 2 × 80160 RCU
1.5KB 쓰기 100회/초1.5/1 → 2 × 100200 WCU

쓰로틀링은 대개 키 하나가 뜨거워서 생긴다

이제 앞에서 미뤄 둔 파티션 상한의 의미가 보입니다. 테이블 전체 용량이 남아도 핫 파티션 하나가 3,000 RCU / 1,000 WCU를 넘으면 그 키의 요청은 ProvisionedThroughputExceededException으로 거절됩니다. 이렇게 한도를 넘는 요청을 거절하는 것을 쓰로틀링이라고 합니다. 인기 상품 ID나 오늘 날짜를 파티션 키로 쓰면 생깁니다.

DynamoDB는 쓰지 않은 용량을 최대 5분치 모아 두는 버스트와, 뜨거운 아이템을 따로 떼어 내는 적응형 용량으로 완화하지만 키 하나의 상한은 넘지 못합니다.

온디맨드도 무한하지 않습니다. 이전 최고치의 2배까지는 즉시 받지만, 30분 안에 그 이상으로 뛰면 쓰로틀링될 수 있습니다. 새 온디맨드 테이블은 초당 쓰기 4,000, 읽기 12,000에서 시작합니다.

그래서 대형 할인 행사 전에는 테이블이 즉시 받을 수 있는 처리량인 웜 처리량(warm throughput)을 미리 올려 둡니다.

조건식과 트랜잭션으로 정합성을 지킨다

# 재고가 남아 있을 때만 1 차감
$ aws dynamodb update-item --table-name stock \
  --key '{"PK": {"S": "SKU#A1"}}' \
  --update-expression "SET qty = qty - :one" \
  --condition-expression "qty >= :one" \
  --expression-attribute-values \
    '{":one": {"N": "1"}}'
ConditionalCheckFailedException  # 품절

조인과 SQL이 없어도 정합성은 지킬 수 있습니다. 조건식은 쓰기 직전에 서버에서 조건을 검사하고, 맞을 때만 원자적으로 씁니다. 이 명령은 qty가 1 이상일 때만 1을 빼고, 아니면 실패합니다. 8장 선착순 쿠폰에서 본 "DB가 직접 순서를 지키게" 하는 방법입니다.

여러 아이템을 함께 바꾸려면 TransactWriteItems로 최대 100개 작업을 전부 되거나 전혀 안 되게 묶습니다(합계 4MB).

TTL은 무료로 지우고, Streams는 변경을 흘려보낸다

장바구니는 몇 주 지나면 버려도 되는 데이터입니다. TTL은 아이템의 특정 속성에 만료 시각(Unix 초)을 넣어 두면 DynamoDB가 쓰기 용량을 쓰지 않고 지워 줍니다. 세션, 인증 코드, 임시 데이터에 씁니다.

단, 만료 직후가 아니라 보통 며칠 안에 지웁니다. 만료된 아이템이 아직 조회될 수 있으니 읽을 때 필터로 거릅니다.

DynamoDB Streams는 아이템 단위 변경(바뀌기 전후의 값)을 시간 순서대로 24시간 보관하는 로그입니다. Lambda가 이를 읽어 검색 인덱스 갱신, 집계, 다른 시스템 알림을 처리합니다.

8장의 Outbox 패턴, 즉 DB 저장과 이벤트 발행을 한 트랜잭션으로 묶으려고 별도 테이블에 이벤트를 적던 일을 DB 기능으로 대신하는 셈입니다. 더 길게 보관하려면 대용량 스트림 서비스인 Kinesis Data Streams로 보냅니다(17장).

DAX는 캐시를, Global Tables는 리전을 더한다

밀리초도 길다면 캐시를 둡니다. DAX는 DynamoDB 전용 인메모리 캐시입니다. API가 같아 클라이언트만 바꾸면 되고, 읽기 지연이 밀리초에서 마이크로초로 줄어듭니다.

DAX는 최종 일관성 읽기만 캐시합니다. 강력 일관성 읽기는 DynamoDB로 그대로 넘기고, 노드 간 복제도 최종 일관성이라 노드마다 잠시 다른 값을 볼 수 있습니다.

Global Tables는 여러 리전에 복제본을 두고 어느 리전에서나 쓰게 합니다. 기본 모드인 MREC(Multi-Region Eventual Consistency)는 보통 1초 안에 비동기 복제하고, 같은 아이템을 두 리전에서 동시에 고치면 마지막 쓰기가 이깁니다.

리전 간에도 최신 값을 보장하는 MRSC(Multi-Region Strong Consistency) 모드도 있지만, 만들 때 정하고 나중에 바꿀 수 없습니다.

DynamoDB는 질문 목록부터 쓰고 키를 짠다

지금까지 본 제약을 모으면 설계 순서가 정해집니다. RDB는 정규화한 뒤 어떤 질의든 나중에 조인으로 풉니다. DynamoDB는 조인이 없으므로 접근 패턴을 먼저 전부 적고 각 패턴이 Query 한 번으로 끝나도록 키와 GSI를 설계합니다.

단일 테이블 설계는 사용자, 주문, 배송처럼 함께 읽히는 엔터티를 한 테이블에 넣고 PK=USER#42, SK=ORDER#…처럼 접두사로 구분합니다. 그러면 Query 한 번으로 사용자 정보와 주문 목록을 함께 가져옵니다.

한도값
아이템 크기최대 400KB
Query/Scan 1회 응답1MB
트랜잭션100개 작업, 4MB
LSI가 있는 파티션 키 묶음10GB

상품 상세 설명이나 이미지처럼 큰 본문은 S3에 두고 아이템에는 키만 저장합니다.

7부

캐시를 맡기고, 데이터 모양마다 DB를 고른다

쇼핑몰의 세션과 인기 상품 목록은 잃어도 다시 만들 수 있지만 1밀리초 안에 읽혀야 합니다. 8장에서 본 Redis 캐시가 이 자리에 들어갑니다. 이 부는 그 Redis를 관리형으로 띄울 때 무엇을 고르고 장애 때 무슨 일이 생기는지 보고, 지금까지 다루지 않은 데이터 모양을 위한 DB들을 훑습니다.

ElastiCache는 8장의 Redis를 관리형으로 준다

ElastiCache는 AWS가 운영하는 인메모리 캐시입니다. 엔진은 세 가지이고, 그중 Valkey는 Redis의 라이선스가 바뀐 뒤 Linux Foundation이 이어 가는 오픈소스 포크로 명령과 동작이 Redis OSS와 같으며 ElastiCache에서 더 싸게 제공됩니다.

항목Valkey / Redis OSSMemcached
자료구조문자열, 해시, 리스트, Sorted Set 등문자열 키-값만
복제·장애 조치복제본, Multi-AZ 자동 장애 조치없음, 노드가 죽으면 데이터 소실
백업스냅샷을 S3에 저장노드 기반은 없음
스레드명령 처리는 싱글 스레드멀티 스레드
쓰는 곳세션, 랭킹, 락, 대부분의 캐시단순하고 큰 휘발성 캐시

Cache-Aside, 스탬피드, Redis 자료구조와 영속화(RDB/AOF)의 원리는 8장에서 다뤘습니다. 여기서는 관리형으로 띄울 때의 구성만 봅니다.

샤드는 primary 하나와 복제본의 묶음이다

ElastiCache의 구성을 읽으려면 단어 세 개가 필요합니다. 노드는 캐시 서버 하나, 즉 정해진 크기의 메모리를 가진 인스턴스입니다. 샤드는 쓰기를 받는 primary 노드 하나와 그 데이터를 비동기로 받아 읽기를 나눠 맡는 복제본 0~5개의 묶음입니다. 클러스터는 이 샤드들 전체입니다.

샤드가 하나뿐이면 데이터 전체가 primary 한 대의 메모리에 들어가야 하고, 쓰기도 그 한 대가 다 받습니다. 복제본을 늘려도 늘어나는 것은 읽기뿐입니다. 4장의 RDB에서 writer 하나가 쓰기의 천장이었던 것과 같은 구조입니다.

메모리나 쓰기 처리량이 노드 한 대를 넘으면 데이터를 여러 샤드에 나눠야 합니다. 이 선택이 다음 슬라이드의 클러스터 모드입니다.

클러스터 모드를 켜면 데이터를 샤드로 나눈다

클러스터 모드 비활성은 샤드 하나에 primary 1개와 복제본 최대 5개입니다.

클러스터 모드 활성은 키를 CRC16 해시로 16,384개의 해시 슬롯 중 하나에 배정하고, 슬롯 범위를 최대 500개 샤드에 나눠 맡깁니다. 샤드를 늘릴 때는 슬롯 일부만 옮기므로 8장의 일관성 해싱처럼 키 대부분이 제자리에 남습니다. 대신 클러스터를 지원하는 클라이언트가 필요하고 여러 키 명령은 같은 슬롯 안에서만 됩니다.

엔드포인트를 맞게 쓰면 장애 조치가 투명하다

RDS처럼 ElastiCache도 노드 IP 대신 DNS 이름인 엔드포인트로 접속합니다. 클러스터 모드 비활성에서는 쓰기를 기본 엔드포인트로, 읽기를 리더 엔드포인트로 보냅니다. 활성에서는 구성 엔드포인트 하나로 "어느 슬롯이 어느 샤드에 있나"라는 클러스터 지도를 받아 클라이언트가 샤드를 직접 찾아갑니다.

Multi-AZ를 켜면 복제본을 여러 AZ에 두고, primary가 죽으면 복제 지연이 가장 작은 복제본을 승격한 뒤 기본 엔드포인트 DNS를 그쪽으로 돌립니다.

노드 엔드포인트를 하드코딩하지 않는다

특정 노드 주소로 쓰면 승격 뒤에도 옛 primary(이제 복제본)로 쓰기를 보내 READONLY 오류가 납니다. 복제가 비동기라 승격 직전의 쓰기 일부는 잃을 수 있습니다.

노드를 고를지, 서버리스로 맡길지, 영속 DB로 쓸지

노드 크기와 샤드 수를 고르는 일조차 맡기고 싶다면 ElastiCache Serverless를 씁니다. 데이터를 3개 AZ에 저장하고 부하에 맞춰 늘고 줄며, 저장량(GB-시간)과 처리량에 돈을 냅니다. 처리량 단위인 ECPU(ElastiCache Processing Unit)는 요청이 쓴 CPU 시간과 주고받은 데이터 양을 합쳐 센 값입니다. 1분 안에 만들어지고 99.99% SLA를 제공합니다.

트래픽이 일정하면 단가가 낮은 노드 기반, 예측이 어려우면 Serverless가 유리합니다.

ElastiCache는 어디까지나 캐시라 장애 조치 때 일부 쓰기를 잃을 수 있습니다. Redis 자료구조를 그대로 쓰는 주 데이터베이스가 필요하면 MemoryDB를 씁니다.

MemoryDB는 모든 쓰기를 여러 AZ에 걸친 트랜잭션 로그에 남긴 뒤 응답해 커밋된 데이터를 잃지 않습니다. 읽기는 마이크로초, 쓰기는 한 자릿수 밀리초로 캐시보다 조금 느립니다.

관계형과 키-값 밖에도 데이터의 모양이 있다

쇼핑몰이 자라면 지금까지의 저장소로 다루기 어색한 질문이 생깁니다. "이 상품을 산 사람이 함께 산 상품은?", "'무선 이어폰'이 들어간 리뷰를 관련도순으로", "지난 1년 카테고리별 매출 합계는?" 같은 것들입니다. 각 질문은 데이터를 다른 모양으로 저장해야 빨라집니다.

문서형은 JSON 문서를 통째로 저장하고 문서 안 필드로 질의합니다. 와이드 컬럼은 행마다 열이 수천 개까지 달라질 수 있는 표로, 대량 쓰기에 강합니다. 그래프는 데이터를 점(사람, 상품)과 선(구매함, 친구임)으로 저장해 "몇 단계 건너 이어진 것"을 빠르게 찾습니다.

시계열은 시각이 붙은 측정값을 시간 범위로 모으고 줄이는 데 맞춥니다. 역색인은 책 뒤의 찾아보기처럼 단어마다 그 단어가 나오는 문서 목록을 들고 있어 전문 검색을 빠르게 합니다.

마지막으로 집계 분석을 OLAP이라고 하는데, 4부의 OLTP와 달리 행 몇 개가 아니라 수억 행의 몇 개 열을 훑습니다. 그래서 2부의 Parquet처럼 열 지향으로 저장한 데이터 웨어하우스가 맞습니다.

데이터 계층은 조용히 쌓이다 한꺼번에 터진다

1~7부에서 쇼핑몰의 데이터마다 집을 정했습니다. 이 부는 그 집들이 운영에서 문제를 일으키는 지점을 봅니다. 저장소를 고르는 기준을 정리한 뒤, 장애 조치 뒤 붙지 않는 앱, 배포 한 번에 폭증하는 연결, 가득 찬 스토리지, 뜨거운 키, 그리고 청구서를 보고서야 아는 S3 비용을 차례로 다룹니다.

원리 실무 DB 선택 기준, 설정값, 지표, 장애 사례와 대응을 다룹니다.

장애 조치 뒤에 앱이 다시 붙지 않는 이유

# $JAVA_HOME/conf/security/java.security
networkaddress.cache.ttl=30

# application.yml (HikariCP)
spring.datasource.hikari:
  max-lifetime: 300000     # 5분
  connection-timeout: 3000
  keepalive-time: 60000
spring.datasource.url: "jdbc:mysql://\
  prod.cluster-xxxx.rds.amazonaws.com/shop"

4·5부에서 장애 조치는 DNS를 바꿔 끝난다고 했습니다. 13장에서 봤듯 JVM이 DNS 결과를 오래 캐시하면 앱은 옛 IP로 계속 갑니다. 첫 줄은 그 캐시를 30초로 묶습니다. AWS는 60초 이하를 권장합니다.

풀에 남은 죽은 연결은 max-lifetime(연결 최대 수명)과 keepalive-time(빈 연결 점검 주기)으로 빨리 버리고, connection-timeout으로 연결 대기를 3초에서 끊습니다. 주소는 인스턴스가 아니라 클러스터 엔드포인트를 씁니다.

복제 지연은 라우팅으로 피하고 지표로 지킨다

4장의 복제 지연, 즉 방금 쓴 값이 복제본에 아직 없는 문제는 RDS 읽기 전용 복제본과 Aurora reader에서도 그대로 생깁니다. 쓴 직후 본인이 다시 읽는 화면, 결제처럼 정확해야 하는 조회는 writer로 보냅니다.

Spring이라면 라우팅 데이터 소스를 두고, 6장에서 본 @Transactional(readOnly = true) 메서드만 reader로 보내는 방식이 흔합니다. 지연 자체를 줄여야 하면 Aurora로 옮기는 것이 가장 큰 레버입니다.

분석 쿼리가 서비스 복제본을 늦춘다

복제본에서 긴 분석 쿼리가 돌면 ReplicaLag(Aurora는 AuroraReplicaLag)가 몇 분까지 늘어납니다. 알람을 걸고, 분석용 reader는 Aurora 사용자 지정 엔드포인트로 분리합니다.

사례: 배포 한 번에 DB 연결이 바닥났다

쇼핑몰은 평소 ECS 태스크 20개가 HikariCP 풀 20개씩, 연결 400개를 씁니다. 할인 행사로 Auto Scaling이 태스크를 50개로 늘렸고, 롤링 배포까지 겹쳐 옛 태스크와 새 태스크가 잠시 100개 떠 있었습니다. 100 × 20 = 2,000개가 연결을 시도했고, max_connections를 넘은 태스크는 Too many connections로 헬스 체크에 실패해 재시작을 반복했습니다.

대응은 세 단계입니다. 먼저 풀 크기를 줄입니다(4장: 풀은 클수록 좋지 않다). 다음으로 "최대 태스크 수 × 풀 크기 < max_connections"를 Auto Scaling 최대값과, 14장에서 본 롤링 배포의 maximumPercent(배포 중 잠시 띄울 수 있는 태스크 비율)에 함께 반영합니다.

그래도 클라이언트 수가 예측되지 않으면 RDS Proxy를 앞에 둡니다. Lambda에서 RDS를 부른다면 사실상 필수입니다(17장).

사례: 스토리지가 가득 차 DB가 멈췄다

남은 공간이 0이 되면 인스턴스는 storage-full 상태가 되어 쓰기가 멈추고 자동 백업도 돌지 않습니다. 원인은 대개 주문 데이터 자체보다 보이지 않는 것입니다. 길게 잡은 binlog 보관 기간, 거대한 정렬이 만든 임시 파일, PostgreSQL에서 옛 행 버전을 치우는 VACUUM(4장)이 따라가지 못해 죽은 행이 쌓여 부풀어 오른 테이블, 켜 둔 채 잊은 슬로 쿼리 로그 테이블입니다.

미리 막는 설정

FreeStorageSpace에 20% 알람을 걸고, 스토리지 자동 확장을 켜되 상한을 둡니다. 확장 뒤 몇 시간은 다시 늘지 않으니 알람이 먼저입니다.

메모리 부족도 같이 본다

FreeableMemory가 바닥나 스왑을 쓰기 시작하면 디스크가 남아도 느려집니다. 연결 수가 많을수록 연결당 메모리가 쌓입니다.

사례: 조회수 카운터 하나가 테이블을 막았다

# 문제: 모든 조회가 한 아이템에 쓰기
PK = "VIEWS#post-777"   # 1,000 WCU 상한

# 해결: 접미사로 10개 아이템에 나눠 쓰기
PK = "VIEWS#post-777#" + rand(0, 9)

# 읽기: 10개를 BatchGetItem으로 모아 합산
total = sum(get("VIEWS#post-777#" + i)
            for i in range(10))

인기 리뷰 글 하나에 초당 3,000번 조회가 몰리자, 그 글의 카운터 아이템이 6부에서 본 파티션 하나의 쓰기 상한을 넘어 쓰로틀링되었습니다. 테이블 용량은 충분했습니다.

키에 무작위 접미사를 붙여 쓰기를 여러 파티션에 흩는 쓰기 샤딩으로 풉니다. 읽을 때는 여러 키를 한 번에 가져오는 BatchGetItem으로 모아 더합니다. 어떤 키가 뜨거운지는 키별 요청 수를 순위로 보여 주는 CloudWatch Contributor Insights로 찾습니다.

S3 청구서는 저장량보다 숨은 항목에서 커진다

{ "Rules": [{
  "ID": "cleanup", "Status": "Enabled",
  "Filter": {},
  "NoncurrentVersionExpiration":
    { "NoncurrentDays": 30 },
  "AbortIncompleteMultipartUpload":
    { "DaysAfterInitiation": 7 }
}]}

2부에서 미뤄 둔 두 규칙입니다. 빈 Filter는 버킷 전체가 대상입니다. 첫 규칙은 현재 버전이 아니게 된 지 30일 지난 이전 버전(3부)을, 둘째 규칙은 시작한 지 7일이 지나도 완료되지 않은 멀티파트 조각(3부)을 지웁니다. 둘 다 콘솔 목록에 안 보이면서 과금됩니다.

또 1KB짜리 객체 수억 개를 PUT·LIST하면 저장 요금보다 요청 요금이 커집니다. 버킷별 이전 버전 비율과 미완료 업로드 용량은 S3 사용 현황을 계정 전체에서 모아 보여 주는 S3 Storage Lens로 찾습니다.

정리

  • 저장소는 데이터를 어떻게 찾느냐로 고릅니다. 한 서버의 디스크는 EBS, 공유 파일은 EFS, 파일 원본은 S3입니다.
  • S3는 강하게 일관되지만 락은 아닙니다. 버전 관리·Object Lock으로 지키고, 동시 쓰기는 조건부 쓰기로 막습니다.
  • RDS의 Multi-AZ는 가용성, 복제본은 읽기 확장입니다. 장애 조치는 DNS 전환이라 앱의 DNS 캐시와 풀이 복구 시간을 정합니다.
  • Aurora는 스토리지를 6개 사본의 쿼럼으로 바꿨습니다. reader가 같은 볼륨을 읽어 복제 지연과 장애 조치가 짧습니다.
  • DynamoDB는 키 설계가 성능의 전부입니다. 접근 패턴부터 적고 뜨거운 키를 만들지 않습니다.
  • ElastiCache는 관리형 캐시이지 주 저장소가 아닙니다. 잃으면 안 되는 데이터는 MemoryDB나 DB에 둡니다.

스스로 점검 (1)

  1. Auto Scaling 그룹의 여러 EC2가 같은 업로드 디렉터리를 봐야 한다면 EBS, EFS, S3 중 무엇을 고르고 왜일까요?

    EBS는 블록 장치라 파일 시스템을 서버 한 대가 독점하므로 맞지 않습니다. 파일 시스템 의미가 꼭 필요하면 EFS, 앱을 고칠 수 있다면 S3에 Presigned URL로 올리는 편이 확장과 비용에서 낫습니다.

  2. 파일은 몇 GB뿐인데 읽기가 많은 EFS가 어느 날부터 느려졌습니다. 처리량 모드가 Bursting이라면 원인은?

    Bursting은 저장 용량에 비례해 기본 처리량과 크레딧이 정해지므로, 용량이 작으면 크레딧이 금방 바닥납니다. Elastic 모드로 바꾸면 쓰는 만큼 처리량이 늘어납니다.

  3. 버전 관리를 켠 버킷에서 aws s3 rm으로 지운 파일을 되살릴 수 있을까요?

    네. 버전을 지정하지 않은 삭제는 삭제 마커만 얹으므로, 그 마커를 지우면 직전 버전이 다시 현재 버전이 됩니다.

스스로 점검 (2)

  1. 작은 로그 파일 수천만 개를 Deep Archive로 옮기는 수명 주기 규칙이 오히려 비용을 늘리는 이유는?

    객체마다 전환 요청 요금과 40KB 메타데이터 과금이 붙기 때문입니다. 묶어서 큰 객체로 만든 뒤 옮겨야 합니다.

  2. 역할로 서명한 7일짜리 Presigned URL이 몇 시간 만에 403이 되는 이유는?

    URL은 서명한 임시 자격 증명이 만료되면 함께 무효가 됩니다. 역할 세션은 기본 1시간, 인스턴스 프로파일은 최대 약 6시간입니다.

  3. S3 읽기 권한이 분명히 있는 역할이 SSE-KMS로 암호화된 객체를 읽을 때 403을 받습니다. 어디를 먼저 볼까요?

    KMS 키 정책과 역할의 kms:Decrypt 권한입니다. SSE-KMS 객체는 S3 권한과 별개로 키를 풀 권한이 있어야 읽힙니다.

  4. Multi-AZ 인스턴스 배포의 대기 인스턴스로 읽기 부하를 나눌 수 있을까요?

    나눌 수 없습니다. 대기는 동기 복제로 장애 조치만 준비하며 연결을 받지 않습니다. 읽기 확장은 복제본이나 Multi-AZ DB 클러스터로 합니다.

스스로 점검 (3)

  1. 장애 조치는 30초에 끝났는데 앱은 10분 동안 DB 오류를 냈습니다. 무엇부터 의심할까요?

    JVM의 DNS 캐시 TTL과 커넥션 풀의 죽은 연결입니다. TTL을 60초 이하로, 풀의 최대 수명과 keepalive를 짧게 둡니다.

  2. RDS Proxy를 붙였는데 DB 연결 수가 줄지 않습니다. 가장 흔한 원인은?

    세션 변수 SET, 임시 테이블 등으로 생기는 피닝입니다. 피닝 지표를 확인하고 초기 SET을 프록시의 초기화 쿼리로 옮깁니다.

  3. Aurora가 AZ 하나를 통째로 잃어도 쓰기를 계속할 수 있는 이유를 숫자로 설명하면?

    사본 6개 중 AZ 하나에 2개가 있으므로 4개가 남고, 쓰기 쿼럼이 4이기 때문입니다. 읽기 쿼럼 3과 합치면 7로 6보다 커서 최신 쓰기와 반드시 겹칩니다.

  4. Aurora의 쓰기 쿼럼을 3으로 줄이면(읽기 3 유지) 어떤 문제가 생길까요?

    쓰기 3과 읽기 3의 합이 6이라 V를 넘지 못하므로, 읽기 집합이 최신 쓰기와 하나도 겹치지 않을 수 있습니다. 쓰기끼리도 3+3=6이라 서로 다른 두 쓰기가 사본 절반씩에서 동시에 성공할 수 있습니다.

스스로 점검 (4)

  1. 날짜(YYYY-MM-DD)를 DynamoDB 파티션 키로 쓴 로그 테이블이 쓰로틀링되는 이유는?

    그날의 모든 쓰기가 파티션 키 하나, 즉 파티션 하나로 몰려 1,000 WCU 상한에 걸립니다. 접미사로 쓰기를 샤딩하거나 고르게 퍼지는 키를 씁니다.

  2. 운영 중인 DynamoDB 테이블에 "사용자별 주문을 금액순으로" 조회를 추가하려고 LSI를 만들려 합니다. 무엇이 걸릴까요?

    LSI는 테이블을 만들 때만 정의할 수 있습니다. 운영 중에는 같은 키 구조의 GSI를 추가하고, 그 대신 최종 일관성 읽기와 별도 처리량을 감수합니다.

  3. ElastiCache 클러스터 모드를 켰더니 MGET이 CROSSSLOT 오류를 냅니다. 왜일까요?
