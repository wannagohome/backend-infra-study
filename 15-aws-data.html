1부

데이터는 모양에 따라 사는 집이 다르다

14장에서 EC2와 컨테이너를 언제든 갈아 끼울 수 있는 소모품으로 만들었습니다. 그렇다면 갈아 끼워도 사라지면 안 되는 데이터는 어디에 두어야 할까요?

블록, 파일, 객체는 읽는 단위가 다르다

블록 스토리지는 번호 붙은 고정 크기 칸의 나열입니다. OS가 그 위에 파일 시스템을 직접 만들고, 4KB 한 칸만 골라 고쳐 쓸 수 있습니다.

파일 스토리지는 파일 시스템을 서버 쪽이 들고 있고, 클라이언트는 NFS 같은 프로토콜로 경로를 엽니다.

객체 스토리지는 키와 데이터 덩어리를 HTTP로 주고받습니다. 부분 수정이 없고 객체는 통째로 교체됩니다.

EBS 볼륨 유형, 스냅샷, IOPS 모델은 14장에서 다뤘습니다. 이 장은 EFS와 S3부터 이어 갑니다.

EFS는 여러 AZ의 서버가 같은 폴더를 연다

EFS는 관리형 NFS 파일 시스템입니다. 파일 시스템 하나에 AZ마다 마운트 대상이라는 ENI를 하나씩 만들고, 각 서버는 자기 AZ의 마운트 대상으로 붙습니다.

데이터는 여러 AZ에 중복 저장되므로(Regional 유형) AZ 하나가 죽어도 다른 AZ의 서버는 계속 읽고 씁니다. EC2, ECS, EKS, Lambda, Fargate에서 모두 마운트할 수 있습니다.

EFS 성능은 두 가지 모드로 정한다

설정선택지의미와 권장
성능 모드General Purpose기본값, 작업당 지연이 가장 낮음. 항상 권장
Max I/O지연이 더 높은 레거시 모드
처리량 모드Elastic기본값, 쓰는 만큼 자동 확장·과금

Bursting은 EBS gp2처럼 저장한 용량이 클수록 기본 처리량이 커지는 모델이라, 파일은 적은데 읽기가 많으면 크레딧이 바닥납니다. 요즘은 트래픽 예측이 어려우면 Elastic이 기본 선택입니다.

EFS는 스토리지 클래스로 비용을 줄인다

EFS에는 자주 쓰는 데이터용 Standard, 가끔 쓰는 데이터용 Infrequent Access(IA), 거의 안 쓰는 데이터용 Archive 클래스가 있습니다. IA와 Archive는 첫 바이트 지연이 수십 밀리초로 늘어나는 대신 저장 단가가 낮습니다.

수명 주기 관리를 켜면 "30일 동안 안 열린 파일은 IA로"처럼 자동으로 옮기고, 다시 접근하면 Standard로 되돌리게 할 수 있습니다.

작은 파일 수십만 개는 EFS가 약하다

파일 하나를 열 때마다 네트워크 왕복이 생깁니다. node_modules나 빌드 캐시를 EFS에 두면 로컬 디스크보다 수십 배 느려집니다.

One Zone 유형도 있다

한 AZ에만 저장해 더 싸지만 그 AZ가 죽으면 접근할 수 없습니다. 다시 만들 수 있는 데이터에만 씁니다.

AWS Backup은 백업 볼트를 Vault Lock으로 잠가 랜섬웨어나 실수로 백업이 지워지는 것을 막습니다. 백업을 어떤 RPO/RTO로 설계할지는 18장 DR에서 다룹니다.

2부

S3는 끝없는 키-값 창고다

AWS에서 가장 많이 쓰는 저장소인 S3를 구조, 일관성, 내구성부터 스토리지 클래스와 수명 주기까지 차례로 봅니다.

S3의 폴더는 키 문자열의 일부일 뿐이다

S3는 버킷 안에 객체를 저장하고, 객체는 키로 찾습니다. 버킷 이름은 전 세계에서 유일하고, 버킷은 리전 하나에 속합니다.

images/2026/a.png의 슬래시는 폴더가 아닙니다. 키 앞부분인 접두사를 콘솔이 폴더처럼 보여 줄 뿐입니다. 그래서 "폴더 이름 바꾸기"는 그 아래 모든 객체를 복사하고 지우는 일이 됩니다.

$ aws s3api put-object \
    --bucket shop-uploads \
    --key images/2026/a.png \
    --body a.png
$ aws s3api list-objects-v2 \
    --bucket shop-uploads \
    --prefix images/2026/ \
    --delimiter /
# prefix와 delimiter로 폴더처럼 나열할 뿐

쓰고 바로 읽으면 방금 쓴 값이 보인다

S3는 2020년 12월부터 모든 PUT, DELETE, 목록 조회에 강한 읽기-쓰기 일관성(strong read-after-write)을 보장합니다. 덮어쓴 직후 GET을 해도 옛 값이 나오지 않고, 지운 직후 목록에도 나타나지 않습니다.

예전에는 덮어쓰기와 삭제가 최종 일관성이라 "올리고 바로 읽었더니 없다"는 버그가 있었지만, 이제는 그런 방어 코드가 필요 없습니다.

일관성은 락이 아니다

두 클라이언트가 같은 키에 동시에 쓰면 마지막 쓰기가 이깁니다. 덮어쓰기 경쟁을 막으려면 이 부의 뒤에서 볼 조건부 쓰기를 씁니다.

내구성은 잃지 않는 것, 가용성은 읽히는 것이다

내구성은 저장한 데이터가 사라지지 않을 확률입니다. S3는 모든 스토리지 클래스가 99.999999999%(9가 11개)를 목표로 설계되었습니다. 객체 1,000만 개를 저장하면 평균 1만 년에 하나를 잃는 수준입니다.

가용성은 요청했을 때 실제로 응답받을 확률입니다. S3 Standard는 99.99%로 설계되어, 1년에 약 53분은 요청이 실패할 수 있습니다. 데이터는 안전하지만 잠깐 못 읽을 수 있다는 뜻입니다.

그래서 S3를 부르는 코드에는 503이나 타임아웃에 대한 재시도가 반드시 있어야 합니다. AWS SDK는 기본으로 지수 백오프 재시도를 합니다.

스토리지 클래스는 꺼내는 빈도로 고른다

클래스접근 패턴설계 가용성최소 보관 / 최소 과금 크기
Standard월 1회 이상, 기본값99.99%없음 / 없음
Intelligent-Tiering모르거나 자주 바뀜99.9%없음, 조회 요금 없음
Standard-IA월 1회 정도99.9%30일 / 128KB
One Zone-IA다시 만들 수 있는 데이터99.5%30일 / 128KB
Express One Zone지연에 민감한 고성능99.95%없음 / 없음

IA 계열은 저장 단가가 싸지만 GB당 조회 요금이 붙습니다. One Zone-IA와 Express One Zone만 AZ 하나에 저장되고 나머지는 3개 이상의 AZ에 저장됩니다. Express One Zone은 특정 AZ에 만드는 디렉터리 버킷에 저장해 Standard보다 최대 10배 빠르지만, AZ 장애에 대비되지 않으므로 원본이 아니라 같은 AZ 컴퓨팅이 쓰는 작업용 사본을 둡니다.

Glacier 세 클래스는 꺼내는 속도가 다르다

클래스접근 패턴꺼내는 방법최소 보관
Glacier Instant Retrieval분기 1회밀리초, 바로 GET90일
Glacier Flexible Retrieval연 1회복원 요청 후 분~시간90일
Glacier Deep Archive연 1회 미만복원 요청 후 12~48시간180일

Flexible과 Deep Archive는 보관(archive) 상태라 바로 GET할 수 없습니다. RestoreObject로 복원 등급(Expedited 1~5분, Standard, Bulk)을 골라 요청하면, 정한 일수 동안만 쓸 수 있는 임시 사본이 생깁니다.

객체마다 메타데이터 40KB가 추가로 과금되므로, 작은 파일 수백만 개는 묶어서(tar) 넣습니다.

Intelligent-Tiering은 객체마다 계층을 옮긴다

  1. Frequent Access

    올리거나 옮겨 온 객체는 모두 여기서 시작합니다.

  2. Infrequent Access

    30일 연속 접근이 없으면 자동으로 내려갑니다.

  3. Archive Instant Access

    90일 연속 접근이 없으면 한 단계 더 내려갑니다.

  4. 다시 접근하면

    즉시 Frequent Access로 돌아옵니다. 조회 요금은 없습니다.

사람이 "이 데이터는 언제부터 덜 쓰일까"를 맞힐 필요가 없다는 것이 장점입니다. 대신 객체마다 소액의 월 모니터링 요금이 붙습니다.

128KB보다 작은 객체는 모니터링하지 않고 항상 Frequent Access 요금을 냅니다. 비동기 접근이 가능한 데이터라면 Archive Access 계층을 선택해서 켤 수도 있습니다.

수명 주기 규칙이 객체를 옮기고 지운다

{ "Rules": [{
  "ID": "logs", "Status": "Enabled",
  "Filter": { "Prefix": "logs/" },
  "Transitions": [
    { "Days": 30,  "StorageClass": "STANDARD_IA" },
    { "Days": 180, "StorageClass": "DEEP_ARCHIVE" }
  ],
  "Expiration": { "Days": 730 },
  "NoncurrentVersionExpiration":
    { "NoncurrentDays": 30 },
  "AbortIncompleteMultipartUpload":
    { "DaysAfterInitiation": 7 }
}]}

수명 주기 규칙은 접두사나 태그로 대상을 고르고, 나이에 따라 전환(Transition)과 만료(Expiration)를 지정합니다.

강조한 두 줄은 비용 사고를 막는 안전장치입니다. 이전 버전과 끝나지 않은 멀티파트 업로드 조각은 눈에 안 보이게 쌓이며 과금됩니다.

전환에도 비용이 들고, 최소 기간이 걸린다

  • 전환은 객체당 요청 요금입니다. 그래서 2024년 9월부터 수명 주기는 기본적으로 128KB보다 작은 객체를 옮기지 않습니다. 작은 객체는 옮기는 비용이 아끼는 저장 비용보다 큽니다.
  • 최소 보관 기간 전에 옮기거나 지우면 남은 기간만큼 청구됩니다. Glacier IR(90일)에 4일째 넣고 20일째 Deep Archive로 옮기는 규칙은 만들 수 없습니다.
  • Glacier 전환은 비동기입니다. 실제 이동이 늦어져도 과금은 규칙 조건이 충족된 날부터 대상 클래스 요금으로 바뀝니다.

3부

지우지 못하게, 엿보지 못하게

버전 관리와 Object Lock으로 실수와 악의를 막고, 복제와 암호화, 여러 겹의 접근 제어가 요청 하나를 어떻게 판정하는지 봅니다.

기초 원리 여기부터는 S3가 요청을 판정하고 데이터를 보호하는 내부 규칙을 다룹니다.

버전 관리를 켜면 삭제는 표시만 남긴다

버전 관리를 켠 버킷은 같은 키에 쓸 때마다 새 버전 ID를 붙여 쌓습니다. 덮어써도 이전 버전이 남습니다.

버전을 지정하지 않은 DELETE는 아무것도 지우지 않고 맨 위에 삭제 마커만 얹습니다. 그래서 GET은 404를 받지만, 삭제 마커를 지우면 객체가 되살아납니다. 특정 버전 ID를 지정해 지워야 진짜로 사라집니다.

Object Lock은 정해진 기간 동안 지울 수 없게 한다

Object Lock은 한 번 쓰면 기간 동안 못 고치는 WORM(write once, read many) 저장을 제공합니다. 버전 관리가 켜진 버킷에서만 동작하고, 객체 버전 단위로 걸립니다.

Governance 모드는 특별 권한(s3:BypassGovernanceRetention)이 있으면 풀 수 있습니다. Compliance 모드는 루트 사용자도 기간 전에는 지우지 못합니다. 기한 없는 법적 보존(legal hold)도 따로 걸 수 있습니다.

MFA Delete는 버전을 영구 삭제하거나 버전 관리 상태를 바꿀 때 MFA 코드를 함께 요구합니다. 버킷 소유 계정의 루트 사용자만 켤 수 있고, 콘솔이 아니라 CLI나 API로만 켭니다.

운영에서는 MFA Delete보다 Object Lock과 SCP 같은 정책 가드레일을 더 많이 씁니다. 자동화와 함께 쓰기 쉽기 때문입니다.

복제는 새로 쓰는 객체를 다른 버킷으로 보낸다

S3 복제는 원본 버킷에 새로 쓰인 객체를 비동기로 다른 버킷에 복사합니다. 다른 리전이면 CRR(Cross-Region Replication), 같은 리전이면 SRR(Same-Region Replication)입니다. 양쪽 버킷 모두 버전 관리가 켜져 있어야 합니다.

규칙을 켜기 전에 있던 객체는 복제되지 않습니다. 기존 객체는 Batch Replication 작업으로 따로 보냅니다.

시간 보장이 필요하면 RTC

Replication Time Control은 대부분을 몇 초 안에, 99.9%를 15분 안에 복제하고 지연을 지표와 이벤트로 알려 줍니다.

복제는 백업이 아니다

잘못된 덮어쓰기도 그대로 복제됩니다. 실수 복구는 버전 관리, 변조 방지는 Object Lock이 맡습니다.

SSE-KMS의 진짜 가치는 암호화 자체보다 두 번째 권한 검사입니다. S3 읽기 권한이 있어도 KMS 키의 Decrypt 권한이 없으면 객체를 읽지 못합니다. KMS 키 정책은 16장에서 다룹니다.

SSE-KMS는 버킷 키로 KMS 호출을 줄인다

SSE-KMS는 원래 객체를 쓰고 읽을 때마다 KMS에 데이터 키를 요청합니다. 초당 수천 건의 GET이 오면 KMS 요청 할당량에 걸려 S3 요청이 KMS 쓰로틀링으로 실패하고, KMS 요청 요금도 늘어납니다.

버킷 키를 켜면 S3가 KMS에서 짧게 쓰는 버킷 단위 키를 받아 두고, 그 키로 객체별 데이터 키를 만듭니다. AWS 문서는 KMS 요청 비용을 최대 99% 줄인다고 설명합니다.

기본 암호화는 새 객체에만

버킷 기본 암호화를 바꿔도 이미 있는 객체는 그대로입니다. 기존 객체를 다시 암호화하려면 S3 Batch Operations로 복사합니다.

요청 하나를 네 겹의 장치가 함께 판정한다

  1. 명시적 Deny어디에 있든 즉시 거부
  2. 퍼블릭 액세스 차단공개 허용을 무효화
  3. IAM + 버킷 정책같은 계정은 한쪽 Allow
  4. KMS 키 정책SSE-KMS면 Decrypt 권한

IAM 정책은 주체 쪽에서 "이 역할이 무엇을 할 수 있나"를, 버킷 정책은 리소스 쪽에서 "누가 이 버킷에 접근하나"를 적습니다. 평가는 12장의 규칙 그대로입니다. 같은 계정이면 둘 중 하나만 허용해도 되고, 다른 계정이면 양쪽 모두 허용해야 합니다.

버킷 정책으로 지켜야 할 조건을 강제한다

{ "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyInsecureTransport",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": [
      "arn:aws:s3:::shop-uploads",
      "arn:aws:s3:::shop-uploads/*" ],
    "Condition": { "Bool":
      { "aws:SecureTransport": "false" } }
  }]
}

버킷 정책은 Allow보다 Deny로 조건을 강제할 때 특히 쓸모 있습니다. 이 정책은 HTTPS가 아닌 요청을 누가 보내든 거부합니다.

같은 방식으로 aws:SourceVpce 조건을 걸어 특정 VPC 엔드포인트(13장)를 거친 요청만 받게 하거나, 특정 KMS 키로 암호화하지 않은 업로드를 막습니다.

ACL은 끄고 퍼블릭 차단은 켜 둔다

ACL은 정책이 생기기 전부터 있던 객체 단위 권한 장치입니다. 다른 계정이 올린 객체의 소유자가 업로더가 되는 등 혼란이 컸습니다. Object Ownership을 BucketOwnerEnforced로 두면 ACL이 꺼지고 모든 객체를 버킷 소유자가 가집니다. 새 버킷은 이것이 기본값입니다.

퍼블릭 액세스 차단은 정책이나 ACL이 공개를 허용해도 그것을 덮어쓰는 안전장치입니다. 공개 ACL 차단·무시, 공개 정책 차단·제한의 네 설정이 있고, 새 버킷은 모두 켜져 있습니다.

계정 수준에서도 켜 두면 누군가 실수로 버킷을 열어도 막힙니다. 공개가 필요한 정적 파일은 CloudFront 뒤에 둡니다(16장).

Access Point는 사용처마다 문을 따로 낸다

버킷 하나를 여러 팀과 앱이 쓰면 버킷 정책 하나에 규칙이 수십 개 쌓여 고치기 무서운 문서가 됩니다. Access Point는 버킷에 이름 붙은 출입구를 여러 개 만들고, 출입구마다 자기 정책을 붙입니다.

예를 들어 analytics-ap는 logs/ 읽기만, ingest-ap는 쓰기만 허용합니다. 출입구를 특정 VPC에서만 열리게 제한할 수도 있습니다.

버킷 정책에 위임을 적는다

버킷 정책에 "Access Point를 거친 요청은 Access Point 정책에 맡긴다"는 조건(s3:DataAccessPointAccount)을 두면 권한 관리가 출입구 쪽으로 옮겨 갑니다.

Presigned URL은 서버가 자기 자격 증명으로 특정 객체, 특정 동작, 만료 시각에 서명해 준 URL입니다. 받은 사람은 자격 증명 없이 그 일 하나만 할 수 있습니다.

큰 파일이 앱 서버의 메모리와 대역폭을 지나가지 않으니 서버 수를 늘리지 않아도 됩니다.

URL은 서명한 자격 증명보다 오래 살지 못한다

Presigned URL은 서명한 주체의 권한을 넘지 못합니다. 그 주체에게 s3:PutObject가 없으면 URL도 403입니다.

만료는 설정한 시각과 자격 증명이 끝나는 시각 중 빠른 쪽입니다. SigV4 서명은 최대 7일이지만, 역할로 서명했다면 역할 세션이 끝날 때 함께 만료됩니다. AssumeRole 세션은 기본 1시간, EC2 인스턴스 프로파일 자격 증명은 최대 약 6시간마다 바뀝니다.

"7일짜리 링크가 몇 시간 만에 죽어요"

ECS 태스크나 EC2 역할로 서명한 링크입니다. 오래 가야 하는 공유 링크는 CloudFront Signed URL(16장)로 만듭니다.

큰 파일은 조각으로 나눠 병렬로 올린다

  1. CreateMultipartUpload

    업로드 ID를 받습니다.

  2. UploadPart × N

    조각마다 번호를 붙여 병렬로 올리고, 실패한 조각만 다시 보냅니다.

  3. CompleteMultipartUpload

    조각 목록을 보내면 S3가 하나의 객체로 합칩니다.

  4. 완료하지 않으면

    조각은 보이지 않게 남아 계속 과금됩니다.

한 번의 PUT은 5GB까지입니다. 멀티파트 업로드는 조각 5MiB~5GiB, 최대 10,000개로 객체 하나를 최대 48.8TiB까지 만듭니다. AWS는 100MB부터 멀티파트를 권장합니다.

SDK의 전송 관리자(TransferManager 등)가 이 과정을 자동으로 해 줍니다.

조건부 쓰기는 S3에서 덮어쓰기 경쟁을 막는다

# 같은 키가 없을 때만 생성
$ aws s3api put-object --bucket b \
    --key locks/job-42 --body owner.txt \
    --if-none-match "*"
An error occurred (PreconditionFailed)

# 내가 읽은 버전일 때만 덮어쓰기
$ aws s3api put-object --bucket b \
    --key state.json --body new.json \
    --if-match '"9b2cf535f27731c9"'

If-None-Match: *는 키가 이미 있으면 412로 실패합니다. 여러 작업자 중 하나만 이기게 하는 간단한 선점 장치가 됩니다.

If-Match는 ETag가 같을 때만 씁니다. 4장의 낙관적 락을 객체 저장소에서 하는 셈입니다. 동시 요청이 겹치면 409가 올 수 있으니 재시도합니다.

요청 성능은 접두사마다 따로 늘어난다

S3는 분할된 접두사 하나당 초당 최소 3,500건의 쓰기(PUT/COPY/POST/DELETE)와 5,500건의 읽기(GET/HEAD)를 처리합니다. 접두사 수에는 제한이 없어, 읽기를 접두사 10개로 나누면 초당 55,000건까지 늘어납니다.

확장은 트래픽을 보고 점진적으로 일어납니다. 그 사이에는 503 Slow Down이 나올 수 있고, 확장이 끝나면 사라집니다.

그래서 키 설계가 중요하다

모든 쓰기가 logs/2026-11-17/ 하나로 몰리면 그 접두사가 병목입니다. 해시나 테넌트 ID를 앞에 두어 접두사를 흩고, 503에는 백오프로 재시도합니다.

멀리서 올리기와 올린 뒤 처리하기

Transfer Acceleration은 사용자가 가까운 CloudFront 엣지 로케이션으로 올리면, 거기서부터 AWS 백본망을 타고 버킷까지 가게 합니다. 서울 사용자가 버지니아 버킷에 대용량 파일을 올릴 때처럼 거리가 멀수록 효과가 큽니다. 전용 엔드포인트 bucket.s3-accelerate.amazonaws.com을 씁니다.

이벤트 알림은 객체 생성, 삭제, 복원 완료 같은 일이 생기면 SNS, SQS, Lambda, EventBridge로 알려 줍니다. 업로드되면 썸네일을 만드는 흐름이 대표적입니다.

알림은 적어도 한 번 전달이라 중복이 올 수 있으니 처리 쪽을 멱등하게 만듭니다(17장).

정적 호스팅과 질의는 다른 서비스와 함께 쓴다

S3 정적 웹 사이트 호스팅을 켜면 버킷이 index.html과 오류 문서를 돌려주는 웹 서버가 됩니다. 하지만 웹 사이트 엔드포인트는 HTTPS를 지원하지 않고 버킷을 공개해야 합니다. 운영에서는 버킷을 닫고 CloudFront와 OAC로 내보냅니다(16장).

S3에 쌓인 CSV, JSON, Parquet을 SQL로 조회하려면 Athena를 씁니다. 서버 없이 스캔한 데이터 양만큼 과금되므로, 날짜별 파티션과 Parquet 같은 열 형식이 비용을 크게 줄입니다.

객체 하나 안을 SQL로 거르던 S3 Select는 신규 고객에게 더 이상 제공되지 않습니다.

4장에서 본 복제, 백업, 커넥션 풀을 AWS가 어떤 부품으로 제공하는지, 장애 조치가 실제로 어떻게 일어나는지 봅니다.

인스턴스 클래스는 CPU와 메모리, 스토리지는 IOPS

DB 인스턴스 클래스는 EC2와 같은 명명 규칙을 씁니다(db.r7g.large: 메모리 최적화, 7세대, Graviton). DB는 버퍼 풀에 데이터를 많이 올릴수록 빨라지므로 보통 r 계열이 기본입니다.

스토리지는 gp3가 기본입니다. RDS의 gp3는 3,000 IOPS·125MiB/s를 기본으로 주고, MySQL·PostgreSQL·MariaDB는 400GiB부터 볼륨 4개로 나눠 12,000 IOPS·500MiB/s가 기본이 됩니다.

지연이 일정해야 하는 큰 OLTP는 io2 Block Express(Provisioned IOPS)로 IOPS를 따로 삽니다.

어떤 스토리지를 골라도 인스턴스 클래스마다 EBS 대역폭 한도가 있습니다. 스토리지 IOPS를 아무리 올려도 작은 인스턴스는 그 한도에서 막힙니다(14장).

스토리지 자동 확장은 여유 10%에서 움직인다

스토리지 자동 확장을 켜면 남은 공간이 할당량의 10% 이하로 5분 이상 유지될 때 RDS가 스토리지를 늘립니다. 한 번 늘린 뒤에는 볼륨 최적화가 끝나야 다시 늘릴 수 있어, 몇 시간 동안은 추가 확장이 막힐 수 있습니다.

상한(최대 스토리지 임곗값)은 현재 크기보다 최소 10% 크게, 권장은 26% 이상입니다.

스토리지는 줄일 수 없다

RDS 스토리지는 늘리기만 됩니다. 대량 로그 테이블 때문에 한 번 커지면, 줄이려면 새 인스턴스로 옮겨야 합니다.

설정은 파라미터 그룹으로 모아 바꾼다

RDS는 my.cnf를 직접 고칠 수 없습니다. 대신 파라미터 그룹이라는 설정 묶음을 만들고 인스턴스에 연결합니다. 기본 그룹은 수정할 수 없으니 처음부터 사용자 그룹을 만들어 둡니다.

파라미터는 즉시 반영되는 dynamic과 재부팅해야 반영되는 static으로 나뉩니다. static을 바꾸면 상태가 pending-reboot로 남습니다.

옵션 그룹은 엔진의 추가 기능을 켜는 장치입니다. MariaDB의 감사 플러그인, Oracle의 TDE, SQL Server의 네이티브 백업·복원 같은 것이 여기 있습니다.

자주 만지는 값은 max_connections, 슬로 쿼리 로그, 타임존, 문자셋입니다.

Multi-AZ 인스턴스는 커밋마다 다른 AZ를 기다린다

Multi-AZ 인스턴스 배포는 다른 AZ에 대기 인스턴스를 두고 스토리지 수준에서 동기 복제합니다. 기본 인스턴스의 쓰기는 대기 쪽 디스크에도 써졌다는 확인을 받아야 커밋됩니다.

그래서 커밋된 데이터는 장애가 나도 잃지 않지만, AZ 사이 왕복만큼 쓰기 지연이 늘어납니다. 대기는 읽기를 받지 않으므로 이것은 확장 수단이 아닙니다.

Multi-AZ DB 클러스터는 대기도 읽기를 받는다

Multi-AZ DB 클러스터는 서로 다른 세 AZ에 writer 하나와 reader 둘을 둡니다. 엔진 수준의 반동기 복제라서 reader 중 하나만 변경을 받았다고 확인하면 커밋됩니다. 두 대기를 모두 기다리지 않으니 Multi-AZ 인스턴스보다 쓰기 지연이 짧습니다.

reader는 읽기 트래픽도 받고, 장애 시 가장 최근 변경을 가진 reader가 승격됩니다.

확인은 "받았다"이지 "반영했다"가 아니다

reader가 아직 적용하지 못한 변경이 쌓이면 복제 지연이 생기고, 장애 조치는 그 지연을 다 적용한 뒤에야 끝납니다. MySQL은 흐름 제어로 지연이 커지면 writer의 쓰기를 늦춥니다.

읽기 전용 복제본은 비동기라 늦게 따라온다

읽기 전용 복제본은 4장의 비동기 레플리케이션을 그대로 관리형으로 만든 것입니다. 원본의 binlog나 WAL을 받아 다시 실행하므로 복제 지연이 생기고, 원본이 갑자기 죽으면 아직 오지 않은 커밋은 잃습니다.

복제본은 자기 엔드포인트가 따로 있고, 다른 리전에도 둘 수 있습니다. 만들려면 원본의 자동 백업이 켜져 있어야 합니다.

승격하면 복제본이 복제를 끊고 독립 DB가 됩니다. 다른 리전 복제본을 승격하는 것이 가장 단순한 리전 DR 방법입니다(18장).

RDS는 복제본 개수를 자동으로 늘리지 않습니다. 읽기 부하에 맞춰 스스로 늘리고 줄여야 한다면 Aurora 복제본 Auto Scaling을 씁니다.

장애 조치는 DNS를 바꿔서 끝난다

  1. 장애 감지

    기본 인스턴스, 스토리지, 네트워크, AZ의 이상을 RDS가 감지합니다.

  2. 대기 승격

    동기 복제본이라 커밋된 데이터는 이미 대기에 있습니다.

  3. DNS 전환

    엔드포인트 레코드가 새 기본 인스턴스를 가리킵니다.

  4. 재연결

    기존 커넥션은 끊깁니다. 앱이 다시 연결해야 합니다.

보통 60~120초가 걸리고, 큰 트랜잭션을 복구하는 중이면 더 길어집니다. 엔드포인트 이름은 그대로라 설정을 바꿀 필요는 없지만, 앱이 옛 IP를 캐시하거나 죽은 커넥션을 붙잡으면 장애가 길어집니다.

같은 절차가 패치나 인스턴스 유형 변경 때도 쓰입니다. 앱 쪽 대응은 7부에서 봅니다.

자동 백업은 스냅샷과 로그로 PITR을 만든다

RDS는 매일 백업 창에 스토리지 스냅샷을 찍고(첫 번째 이후는 증분), 그 사이 트랜잭션 로그를 S3에 계속 올립니다. 스냅샷에 로그를 재생하면 보관 기간 안의 특정 시점으로 복원합니다. 4장의 WAL 재생과 같은 원리이고, 보통 5분 전 시점까지 됩니다.

보관 기간은 0~35일입니다. 0이면 자동 백업이 꺼지고, 그러면 읽기 전용 복제본도 만들 수 없습니다.

복원하면 새 인스턴스가 생긴다

기존 DB를 되돌리지 않습니다. 새 엔드포인트로 앱을 돌리고, 보안 그룹과 파라미터 그룹도 다시 확인합니다.

수동 스냅샷은 보관 기간과 상관없이, DB를 지워도 남습니다. 큰 변경 전에는 수동 스냅샷을 찍어 둡니다.

패치와 업그레이드는 유지 관리 기간에 온다

인스턴스마다 매주 30분짜리 유지 관리 기간이 있습니다. 지정하지 않으면 리전별 8시간 블록 안에서 무작위로 정해지므로, 트래픽이 가장 적은 시간으로 직접 지정합니다.

자동 마이너 버전 업그레이드를 켜 두면 마이너 패치가 이 기간에 적용됩니다. Multi-AZ라면 대기를 먼저 패치하고 장애 조치한 뒤 옛 기본을 패치해 중단을 줄입니다.

메이저 버전 업그레이드(MySQL 8.0 → 8.4 등)는 자동으로 하지 않습니다. 호환되지 않는 문법과 파라미터가 있을 수 있어 직접 계획합니다.

엔진 버전에도 표준 지원 종료일이 있고, 지나면 유료 연장 지원으로 넘어갑니다. 업그레이드를 미루는 것도 비용입니다.

Blue/Green으로 업그레이드를 1분 안에 바꿔 탄다

  1. Green 생성

    운영(Blue)을 복사하고 논리 복제로 계속 따라오게 합니다.

  2. Green 변경

    메이저 업그레이드, 파라미터 변경을 Green에만 적용하고 시험합니다.

  3. 전환(switchover)

    쓰기를 막고 복제를 따라잡은 뒤 이름을 바꿔 Green을 운영으로 만듭니다.

RDS Blue/Green Deployments는 11장의 Blue-Green 전략을 DB에 적용한 기능입니다. 전환은 보통 1분 안에 데이터 손실 없이 끝나고, 엔드포인트 이름이 그대로라 앱 설정을 바꾸지 않습니다.

RDS for MySQL, MariaDB, PostgreSQL과 Aurora에서 씁니다. 암호화되지 않은 DB를 암호화된 Green으로 옮길 때도 씁니다.

RDS Proxy는 많은 클라이언트를 적은 연결에 싣는다

DB 연결은 비싸고 max_connections로 상한이 있습니다(4장). Lambda처럼 짧게 살아 연결을 마구 여는 클라이언트가 몰리면 DB가 연결 처리만으로 쓰러집니다.

RDS Proxy는 앱과 DB 사이의 관리형 커넥션 풀입니다. 트랜잭션이 끝나면 DB 연결을 다른 클라이언트에게 넘겨 주는 멀티플렉싱으로 연결 수를 줄이고, 장애 조치 동안 클라이언트 연결을 붙잡았다가 새 기본으로 이어 줍니다.

세션 상태를 쓰면 프록시가 연결을 고정한다

멀티플렉싱은 "다음 트랜잭션이 이전 상태에 기대지 않는다"는 전제에서만 안전합니다. 클라이언트가 SET으로 세션 변수를 바꾸거나 임시 테이블을 만들면, 프록시는 그 클라이언트를 DB 연결 하나에 붙박는 피닝을 합니다.

피닝된 연결은 다른 클라이언트와 나눠 쓰지 못하므로 피닝이 많으면 프록시를 둔 효과가 사라집니다. 16KB가 넘는 문장도 피닝을 일으킵니다.

피닝을 숫자로 본다

CloudWatch의 DatabaseConnectionsCurrentlySessionPinned 지표를 봅니다. 드라이버가 연결마다 보내는 초기 SET 문은 프록시의 초기화 쿼리 설정으로 옮겨 피닝을 피합니다.

느린 쿼리는 대기 이벤트로, OS는 초 단위로 본다

Performance Insights는 DB 부하를 평균 활성 세션(AAS)으로 보여 주고, 그 부하를 대기 이벤트, SQL, 호스트, 사용자별로 쪼갭니다. "CPU 대기인가, 락 대기인가, I/O 대기인가"를 바로 알 수 있습니다. 지금은 CloudWatch Database Insights로 통합되었습니다.

기본 CloudWatch 지표는 하이퍼바이저에서 1분 단위로 봅니다. Enhanced Monitoring은 인스턴스 안 에이전트가 최대 1초 간격으로 프로세스별 CPU, 메모리, 디스크를 보내 줍니다.

4장에서 EXPLAIN으로 하던 분석을, 운영 중인 DB 전체를 상대로 하는 도구라고 보면 됩니다.

암호화는 만들 때 정하고, 비밀번호 대신 IAM도 된다

RDS 저장 데이터 암호화는 KMS 키로 하며, 인스턴스를 만들 때만 켤 수 있습니다. 이미 운영 중인 암호화되지 않은 DB는 스냅샷을 암호화하며 복사한 뒤 복원하거나, Blue/Green으로 암호화된 Green을 만들어 옮깁니다. 복제본과 스냅샷은 원본의 암호화를 따라갑니다.

IAM DB 인증을 켜면 앱은 비밀번호 대신 IAM 역할로 서명한 15분짜리 인증 토큰으로 접속합니다. DB에 비밀번호를 저장하지 않아도 되지만, 토큰 생성이 연결마다 필요하니 커넥션 풀과 함께 씁니다.

비밀번호를 쓴다면 Secrets Manager의 자동 교체를 씁니다(16장).

5부

Aurora는 DB의 아래 절반을 다시 만들었다

RDS가 기존 엔진을 그대로 관리해 준다면, Aurora는 엔진 밑의 스토리지 계층을 분산 시스템으로 바꿨습니다. 그 구조가 복제 지연과 장애 조치 시간을 어떻게 바꾸는지 봅니다.

모든 인스턴스가 하나의 클러스터 볼륨을 공유한다

RDS는 인스턴스마다 자기 디스크가 있고 복제로 내용을 맞춥니다. Aurora는 writer와 reader가 3개 AZ에 걸친 하나의 클러스터 볼륨을 함께 쓰고, 볼륨은 데이터를 AZ마다 2개씩 6개 스토리지 노드에 둡니다.

컴퓨팅과 스토리지가 분리되어 있으니 reader를 추가해도 데이터를 복사하지 않습니다. reader는 최대 15개, 볼륨은 쓰는 만큼 자동으로 커지며 일부 엔진 버전은 256TiB까지 늘어납니다.

4/6 쿼럼은 AZ 하나를 잃어도 쓰게 해 준다

Aurora 설계 논문(SIGMOD 2017)에 따르면 쓰기는 6개 중 4개, 읽기는 3개가 응답하면 성립합니다. 4+3이 6보다 크므로 읽기 집합과 쓰기 집합은 반드시 한 노드 이상 겹쳐, 최신 쓰기를 놓치지 않습니다.

AZ 하나가 통째로 죽으면 사본 2개를 잃어도 4개가 남아 쓰기가 계속됩니다. AZ 하나에 더해 다른 노드 하나까지 잃어도 3개가 남아 읽기와 복구가 가능합니다.

또 writer는 데이터 페이지가 아니라 redo 로그 레코드만 스토리지로 보내고, 페이지 적용은 스토리지 노드가 합니다. 네트워크로 오가는 양이 크게 줄어 쓰기 처리량이 늘어납니다.

같은 볼륨을 읽으니 복제 지연이 짧다

RDS 복제본은 원본의 변경을 다시 실행해 자기 디스크에 써야 합니다. 원본에서 1분 걸린 대량 UPDATE는 복제본에서도 1분 걸립니다.

Aurora reader는 데이터를 다시 쓰지 않습니다. 같은 볼륨을 읽고, writer가 보내는 로그로 자기 메모리 캐시의 페이지만 갱신합니다. 그래서 복제 지연이 보통 100밀리초보다 훨씬 짧습니다.

짧아도 0은 아니다

쓰기가 몰리면 지연이 늘어납니다. 쓴 직후 본인이 다시 읽는 화면은 여전히 writer로 보내야 합니다(4장 read-after-write).

엔드포인트로 연결의 목적지를 고른다

리더 엔드포인트는 DNS 수준에서 연결을 나눕니다. 쿼리 단위가 아니라 연결 단위라서, 커넥션 풀이 연결을 오래 붙잡으면 새로 추가한 reader에 트래픽이 가지 않습니다. 풀의 최대 연결 수명을 짧게 두는 이유입니다.

Aurora 장애 조치는 대개 30초 안팎에 끝난다

writer가 죽으면 reader 하나가 승격됩니다. 데이터는 이미 공유 볼륨에 있으니 따라잡을 복제가 없고, 서비스는 보통 60초 안에, 많은 경우 30초 안에 돌아옵니다.

reader가 하나도 없으면 같은 AZ에 writer를 새로 만들어야 해서 보통 10분 가까이 걸립니다. 그래서 운영 클러스터에는 다른 AZ에 reader를 최소 하나 둡니다.

어느 reader를 승격할지는 승격 우선순위(tier 0~15)로 정합니다. 숫자가 작을수록 먼저이고, 같으면 큰 인스턴스가 먼저입니다.

writer와 같은 크기의 reader를 tier 0에 두세요. 작은 분석용 reader가 승격되면 장애 조치는 성공했는데 곧바로 과부하로 다시 쓰러집니다.

Serverless v2는 ACU 단위로 초마다 늘고 준다

Aurora Serverless v2는 인스턴스 크기 대신 용량 범위를 정합니다. 단위는 ACU로, 1 ACU는 약 2GiB 메모리와 그에 맞는 CPU·네트워크입니다. 용량은 초 단위로 측정되고 쓴 만큼 과금됩니다.

범위는 0 ACU부터 Aurora MySQL 256, PostgreSQL 384 ACU까지입니다. 최소를 0으로 두면 부하가 없을 때 자동으로 멈춥니다.

프로비저닝과 섞어 쓸 수 있다

writer는 고정 크기 인스턴스로, reader만 Serverless v2로 두어 낮과 밤의 읽기 부하 차이를 흡수하는 구성이 흔합니다.

최소 ACU가 너무 낮으면

버퍼 풀도 함께 작아져 트래픽이 갑자기 몰릴 때 캐시가 비어 느립니다. 운영 writer의 최소값은 평소 부하 기준으로 잡습니다.

Global Database는 리전 너머로 1초 안에 복제한다

Global Database는 쓰기를 받는 기본 리전 하나와 읽기 전용 보조 리전을 최대 10개 둡니다. 복제는 엔진이 아니라 스토리지 계층의 전용 인프라가 맡아 보통 1초 안에 도착합니다.

보조 리전 사용자는 가까운 곳에서 읽고, 쓰기는 write forwarding으로 기본 리전에 넘길 수 있습니다.

리전을 옮기는 방법은 둘입니다. 계획된 이동은 switchover로 데이터 손실 없이, 기본 리전 장애는 failover로 아직 복제되지 않은 몇 초의 쓰기를 포기하고 보조 리전을 승격합니다.

Global Database 쓰기 엔드포인트는 전환 뒤에도 기본 클러스터를 따라갑니다. 멀티 리전 DR 설계는 18장에서 봅니다.

Backtrack은 되감고, Cloning은 공짜로 복사한다

Backtrack은 Aurora MySQL 클러스터를 새 클러스터 없이 과거 시점으로 되감습니다. 실수로 테이블을 지웠을 때 PITR은 새 클러스터를 만드느라 몇 시간이 걸리지만, Backtrack은 몇 분이면 됩니다. 창은 최대 72시간이고 Aurora PostgreSQL은 지원하지 않습니다.

Cloning은 copy-on-write로 클러스터를 복제합니다. 처음에는 같은 스토리지 페이지를 함께 가리키다가, 어느 한쪽이 바꾼 페이지만 새로 저장합니다.

운영 데이터 그대로 마이그레이션을 리허설하거나 분석 쿼리를 돌릴 때 수 분 만에 복사본을 만들 수 있습니다.

엔진 자유도버전·확장 선택이 넓음호환 엔진, 일부 차이

Aurora 스토리지 요금은 두 가지입니다. Standard는 I/O 요청마다 과금하고, I/O-Optimized는 I/O 요금 없이 인스턴스와 스토리지 단가가 높습니다. AWS는 I/O 비용이 Aurora 전체 비용의 25% 이상이면 I/O-Optimized를 권장합니다.

6부

질의를 버리고 규모를 얻는 저장소

4장에서 본 NoSQL의 거래(조인과 자유로운 질의를 포기하고 수평 확장을 얻는 것)를 AWS가 어떻게 구현했는지, DynamoDB와 ElastiCache로 봅니다.

DynamoDB는 키로만 찾는 거대한 해시 테이블이다

DynamoDB는 서버를 고르지 않는 키-값·문서형 DB입니다. 테이블에 아이템(행)을 넣고, 아이템은 속성(열)을 자유롭게 가집니다. 스키마는 기본 키만 정합니다.

기본 키는 파티션 키 하나이거나, 파티션 키 + 정렬 키입니다. 같은 파티션 키를 가진 아이템들은 정렬 키 순서로 모여 저장됩니다.

{
  "PK": "USER#42",       // 파티션 키
  "SK": "ORDER#2026-11-17", // 정렬 키
  "total": 32000,
  "status": "PAID",
  "items": [ { "sku": "A1", "qty": 2 } ]
}

파티션 키의 해시가 저장 위치를 정한다

DynamoDB는 파티션 키 값을 해시해서 아이템이 갈 내부 파티션을 정합니다. 파티션은 여러 서버에 흩어진 저장 단위이고, 데이터나 처리량이 늘면 자동으로 쪼개집니다.

파티션 하나는 초당 최대 3,000 RCU, 1,000 WCU를 처리합니다. 그래서 값이 고르게 퍼지는 파티션 키가 성능의 전부입니다. 키를 해시해 칸을 고르는 3장 해시 테이블을 서버 여러 대로 넓힌 발상입니다.

Query는 파티션 하나를, Scan은 테이블 전체를 읽는다

# 사용자 42의 11월 주문: 파티션 하나만 읽음
$ aws dynamodb query --table-name shop \
  --key-condition-expression \
    "PK = :u AND begins_with(SK, :p)" \
  --expression-attribute-values '{
    ":u": {"S": "USER#42"},
    ":p": {"S": "ORDER#2026-11"} }'

# 상태가 PAID인 모든 주문: 전체를 읽고 거름
$ aws dynamodb scan --table-name shop \
  --filter-expression "#s = :paid" ...

Query는 파티션 키를 반드시 지정하고, 정렬 키로 범위를 좁힙니다. 읽는 양만큼만 비용이 듭니다.

Scan은 테이블 전체를 읽습니다. 필터는 읽은 뒤에 거르는 것이라 비용은 전부 냅니다. 한 번에 1MB씩 페이지로 읽습니다.

다른 키로 찾으려면 보조 인덱스를 만든다

항목GSI(전역 보조 인덱스)LSI(로컬 보조 인덱스)
키파티션 키부터 새로 정함같은 파티션 키, 다른 정렬 키
만드는 시점언제든 추가·삭제테이블 생성 때만
읽기 일관성최종 일관성만강력 일관성 가능

기본 한도테이블당 20개테이블당 5개

GSI는 내부적으로 별도 테이블에 비동기로 복사됩니다. 그래서 쓰기 비용이 인덱스 수만큼 늘고, GSI 처리량이 모자라면 원본 테이블 쓰기까지 쓰로틀링됩니다. 대부분은 GSI를 씁니다.

기본 읽기는 최종 일관성이고 비용은 절반이다

DynamoDB는 데이터를 여러 AZ에 복제합니다. 기본 읽기는 최종 일관성이라 방금 끝난 쓰기가 반영되지 않았을 수 있고, 잠시 뒤 다시 읽으면 최신값이 나옵니다.

ConsistentRead=true를 주면 강력 일관성 읽기로 최신값을 보장받는 대신 비용이 두 배입니다. 테이블과 LSI에서만 되고, GSI와 Streams는 항상 최종 일관성입니다.

4장의 PACELC로 보면

평소에는 지연(L)과 일관성(C) 중 하나를 요청마다 고르게 한 설계입니다. 기본값은 지연과 비용 쪽입니다.

RCU와 WCU는 크기를 올림해서 센다

1 RCU는 4KB 이하 아이템의 강력 일관성 읽기 1회/초, 또는 최종 일관성 읽기 2회/초입니다. 1 WCU는 1KB 이하 쓰기 1회/초입니다. 트랜잭션 읽기·쓰기는 두 배를 씁니다.

온디맨드는 요청한 만큼 내고, 프로비저닝은 초당 용량을 미리 정합니다(Auto Scaling 가능). 지금은 온디맨드가 기본이자 권장값입니다.

요구계산용량
3KB 강력 읽기 80회/초3/4 → 1 × 8080 RCU
3KB 최종 읽기 80회/초80 ÷ 240 RCU
6KB 강력 읽기 80회/초6/4 → 2 × 80160 RCU
1.5KB 쓰기 100회/초1.5/1 → 2 × 100200 WCU

쓰로틀링은 대개 키 하나가 뜨거워서 생긴다

테이블 전체 용량이 남아도 핫 파티션 하나가 3,000 RCU / 1,000 WCU 상한을 넘으면 그 키의 요청은 ProvisionedThroughputExceededException으로 거절됩니다. 인기 상품 ID나 오늘 날짜를 파티션 키로 쓰면 생깁니다.

DynamoDB는 쓰지 않은 용량을 최대 5분치 모아 두는 버스트와, 뜨거운 아이템을 따로 떼어 내는 적응형 용량으로 완화하지만 키 하나의 상한은 넘지 못합니다.

온디맨드도 무한하지 않습니다. 이전 최고치의 2배까지는 즉시 받지만, 30분 안에 그 이상으로 뛰면 쓰로틀링될 수 있습니다. 새 온디맨드 테이블은 초당 쓰기 4,000, 읽기 12,000에서 시작합니다.

대형 이벤트 전에는 웜 처리량(warm throughput)을 미리 올려 둡니다.

조건식과 트랜잭션으로 정합성을 지킨다

# 재고가 남아 있을 때만 1 차감
$ aws dynamodb update-item --table-name stock \
  --key '{"PK": {"S": "SKU#A1"}}' \
  --update-expression "SET qty = qty - :one" \
  --condition-expression "qty >= :one" \
  --expression-attribute-values \
    '{":one": {"N": "1"}}'
ConditionalCheckFailedException  # 품절

조건식은 쓰기 직전에 서버에서 조건을 검사하고, 맞을 때만 원자적으로 씁니다. 8장 선착순 쿠폰의 "DB가 직접 순서를 지키게" 하는 방법이 이것입니다.

여러 아이템을 함께 바꾸려면 TransactWriteItems로 최대 100개 작업을 전부 되거나 전혀 안 되게 묶습니다(합계 4MB).

TTL은 무료로 지우고, Streams는 변경을 흘려보낸다

TTL은 아이템의 특정 속성에 만료 시각(Unix 초)을 넣어 두면 DynamoDB가 쓰기 용량을 쓰지 않고 지워 줍니다. 세션, 인증 코드, 임시 데이터에 씁니다.

단, 만료 직후가 아니라 보통 며칠 안에 지웁니다. 만료된 아이템이 아직 조회될 수 있으니 읽을 때 필터로 거릅니다.

DynamoDB Streams는 아이템 단위 변경(전/후 이미지)을 시간 순서대로 24시간 보관하는 로그입니다. Lambda가 이를 읽어 검색 인덱스 갱신, 집계, 다른 시스템 알림을 처리합니다.

8장의 아웃박스 패턴을 DB 기능으로 대신하는 셈입니다. 더 긴 보관이 필요하면 Kinesis Data Streams로 보냅니다(17장).

DAX는 앞에 캐시를, Global Tables는 리전을 더한다

DAX는 DynamoDB 전용 인메모리 캐시입니다. API가 같아 클라이언트만 바꾸면 되고, 읽기 지연이 밀리초에서 마이크로초로 줄어듭니다.

DAX는 최종 일관성 읽기만 캐시합니다. 강력 일관성 읽기는 DynamoDB로 그대로 넘기고, 노드 간 복제도 최종 일관성이라 노드마다 다른 값을 볼 수 있습니다.

Global Tables는 여러 리전에 복제본을 두고 어느 리전에서나 쓰게 합니다. 기본 모드(MREC)는 보통 1초 안에 비동기 복제하고, 같은 아이템을 동시에 고치면 마지막 쓰기가 이깁니다.

리전 간 강한 일관성(MRSC) 모드도 있지만 만들 때 정하고 바꿀 수 없습니다.

DynamoDB는 질문 목록부터 쓰고 키를 짠다

RDB는 정규화한 뒤 어떤 질의든 나중에 조인으로 풉니다. DynamoDB는 조인이 없으므로 접근 패턴을 먼저 전부 적고 그 패턴이 Query 한 번으로 끝나도록 키를 설계합니다.

단일 테이블 설계는 사용자, 주문, 배송처럼 함께 읽히는 엔터티를 한 테이블에 넣고 PK=USER#42, SK=ORDER#…처럼 접두사로 구분합니다. 한 번의 Query로 사용자와 주문을 함께 가져옵니다.

한도값

Query/Scan 1회 응답1MB
트랜잭션100개 작업, 4MB

큰 본문은 S3에 두고 키만 저장합니다.

클러스터 모드를 켜면 데이터를 샤드로 나눈다

클러스터 모드 비활성은 샤드 하나에 primary 1개와 복제본 최대 5개입니다. 데이터 전체가 primary 메모리 하나에 들어가야 하고, 쓰기는 노드 하나가 다 받습니다.

클러스터 모드 활성은 키 공간을 16,384개 해시 슬롯으로 나눠 최대 500개 샤드에 흩습니다. 메모리와 쓰기 처리량이 샤드 수만큼 늘지만, 클러스터를 지원하는 클라이언트가 필요하고 여러 키 명령은 같은 슬롯 안에서만 됩니다.

엔드포인트를 맞게 쓰면 장애 조치가 투명하다

클러스터 모드 비활성에서는 쓰기를 기본 엔드포인트로, 읽기를 리더 엔드포인트로 보냅니다. 활성에서는 구성 엔드포인트 하나로 클러스터 지도를 받아 클라이언트가 샤드를 직접 찾아갑니다.

Multi-AZ를 켜면 복제본을 여러 AZ에 두고, primary가 죽으면 복제 지연이 가장 작은 복제본을 승격한 뒤 기본 엔드포인트 DNS를 그쪽으로 돌립니다.

노드 엔드포인트를 하드코딩하지 않는다

특정 노드 주소로 쓰면 승격 뒤에도 옛 primary(이제 복제본)로 쓰기를 보내 READONLY 오류가 납니다. 복제가 비동기라 승격 직전의 쓰기 일부는 잃을 수 있습니다.

노드를 고를지, 서버리스로 맡길지, 영속 DB로 쓸지

ElastiCache Serverless는 노드 유형과 샤드 수를 정하지 않습니다. 데이터를 3개 AZ에 저장하고 부하에 맞춰 늘고 줄며, 저장량(GB-시간)과 처리량(ECPU)만큼 냅니다. 1분 안에 만들어지고 99.99% SLA를 제공합니다.

노드 기반 클러스터는 단가가 낮고 세밀한 조정이 됩니다. 트래픽이 일정하면 노드 기반, 예측이 어려우면 Serverless가 유리합니다.

ElastiCache는 어디까지나 캐시라 장애 조치 때 일부 쓰기를 잃을 수 있습니다. Redis 자료구조를 그대로 쓰는 주 데이터베이스가 필요하면 MemoryDB를 씁니다.

MemoryDB는 모든 쓰기를 Multi-AZ 트랜잭션 로그에 남겨 커밋된 데이터를 잃지 않습니다. 읽기는 마이크로초, 쓰기는 한 자릿수 밀리초로 캐시보다 조금 느립니다.

S3 위의 파일을 서버 없이 SQL로 조회하는 Athena(3부)까지 더하면, "하나의 DB로 모든 것을"이 아니라 접근 패턴마다 맞는 저장소를 고르는 것이 AWS의 기본 방향입니다.

데이터 계층은 조용히 쌓이다 한꺼번에 터진다

장애 조치 뒤 붙지 않는 앱, 배포 한 번에 폭증하는 연결, 가득 찬 스토리지, 뜨거운 키, 그리고 청구서를 보고서야 아는 S3 비용까지 차례로 봅니다.

원리 실무 DB 선택 기준, 설정값, 지표, 장애 사례와 대응을 다룹니다.

spring.datasource.url: "jdbc:mysql://\
  prod.cluster-xxxx.rds.amazonaws.com/shop"

장애 조치는 DNS를 바꿔 끝나는데, JVM이 DNS 결과를 오래 캐시하면 앱은 옛 IP로 계속 갑니다. AWS는 JVM의 DNS TTL을 60초 이하로 두라고 권장합니다.

풀에 남은 죽은 연결은 최대 수명과 keepalive로 빨리 버리게 합니다. 엔드포인트는 인스턴스 주소가 아니라 클러스터 주소를 씁니다.

복제 지연은 지표로 보고 구조로 줄인다

4장의 read-after-write 문제는 RDS 읽기 전용 복제본에서도 그대로 생깁니다. 쓴 직후 본인이 다시 읽는 화면, 결제처럼 정확해야 하는 조회는 writer로 보냅니다. Spring이라면 @Transactional(readOnly = true)만 reader로 라우팅하는 방식이 흔합니다.

지연 자체를 줄여야 하면 Aurora로 옮기는 것이 가장 큰 레버입니다.

분석 쿼리가 서비스 복제본을 늦춘다

복제본에서 긴 분석 쿼리가 돌면 ReplicaLag(Aurora는 AuroraReplicaLag)가 몇 분까지 늘어납니다. 알람을 걸고, 분석용 복제본은 Aurora 사용자 지정 엔드포인트로 분리합니다.

사례: 배포 한 번에 DB 연결이 바닥났다

평소 ECS 태스크 20개가 HikariCP 풀 20개씩, 연결 400개를 씁니다. 대형 이벤트로 Auto Scaling이 태스크를 50개로 늘렸고, Rolling 배포까지 겹쳐 잠시 100개가 떠 있었습니다. 100 × 20 = 2,000개가 연결을 시도했고, max_connections를 넘은 태스크는 Too many connections로 헬스 체크에 실패해 재시작을 반복했습니다.

대응은 세 단계입니다. 먼저 풀 크기를 줄입니다(4장: 풀은 클수록 좋지 않다). 다음으로 "최대 태스크 수 × 풀 크기 < max_connections"를 Auto Scaling 최대값과 배포 설정(maximumPercent)에 함께 반영합니다.

그래도 클라이언트 수가 예측되지 않으면 RDS Proxy를 앞에 둡니다. Lambda에서 RDS를 부른다면 사실상 필수입니다(17장).

사례: 스토리지가 가득 차 DB가 멈췄다

남은 공간이 0이 되면 인스턴스는 storage-full 상태가 되어 쓰기가 멈추고 자동 백업도 돌지 않습니다. 원인은 대개 데이터 자체보다 보이지 않는 것입니다. 길게 잡은 binlog 보관 기간, 거대한 정렬이 만든 임시 파일, PostgreSQL에서 VACUUM이 따라가지 못한 테이블 팽창, 열어 둔 슬로 쿼리 로그 테이블입니다.

미리 막는 설정

FreeStorageSpace에 20% 알람을 걸고, 스토리지 자동 확장을 켜되 상한을 둡니다. 확장 뒤 몇 시간은 다시 늘지 않으니 알람이 먼저입니다.

메모리 부족도 같이 본다

FreeableMemory가 바닥나 스왑을 쓰기 시작하면 디스크가 남아도 느려집니다. 연결 수가 많을수록 연결당 메모리가 쌓입니다.

사례: 조회수 카운터 하나가 테이블을 막았다

# 문제: 모든 조회가 한 아이템에 쓰기
PK = "VIEWS#post-777"   # 1,000 WCU 상한

# 해결: 접미사로 10개 아이템에 나눠 쓰기
PK = "VIEWS#post-777#" + rand(0, 9)

# 읽기: 10개를 BatchGetItem으로 모아 합산
total = sum(get("VIEWS#post-777#" + i)
            for i in range(10))

인기 글 하나에 초당 3,000번 조회가 몰리자, 그 글의 카운터 아이템이 파티션 하나의 쓰기 상한을 넘어 쓰로틀링되었습니다. 테이블 용량은 충분했습니다.

키에 무작위 접미사를 붙여 쓰기를 여러 파티션에 흩는 쓰기 샤딩으로 풉니다. 어떤 키가 뜨거운지는 CloudWatch Contributor Insights로 찾습니다.

S3 청구서는 저장량보다 숨은 항목에서 커진다

  • 요청 수: 1KB짜리 객체 수억 개를 PUT하고 LIST하면 저장 요금보다 요청 요금이 큽니다. 작은 데이터는 묶어서 쓰고, 객체 단위로 매번 LIST하지 않습니다.
  • 이전 버전 누적: 버전 관리를 켠 버킷에서 같은 키를 매일 덮어쓰면 보이는 용량은 그대로인데 청구 용량은 계속 늘어납니다. NoncurrentVersionExpiration을 겁니다.
  • 미완료 멀티파트: 실패한 대용량 업로드 조각은 목록에 안 보이지만 과금됩니다. AbortIncompleteMultipartUpload를 겁니다.
  • 찾는 법: S3 Storage Lens에서 버킷별 이전 버전 비율과 미완료 업로드 용량을 봅니다.

정리

  • 저장소는 데이터의 모양과 접근 방식으로 고릅니다. 한 서버의 디스크는 EBS, 여러 서버의 공유 파일은 EFS, 파일 원본과 정적 자산은 S3입니다.
  • S3는 일관되지만 락은 아닙니다. 버전 관리와 Object Lock으로 지키고, 동시 쓰기는 조건부 쓰기로, 비용은 수명 주기로 다스립니다.
  • RDS의 Multi-AZ는 가용성, 복제본은 확장입니다. 장애 조치는 DNS를 바꿔 끝나므로 앱의 DNS 캐시와 커넥션 풀이 복구 시간을 정합니다.
  • Aurora는 스토리지를 6개 사본의 쿼럼으로 바꿨습니다. 그래서 복제 지연과 장애 조치가 짧고, reader 추가에 복사가 없습니다.
  • DynamoDB는 키 설계가 성능의 전부입니다. 접근 패턴부터 정하고, 파티션 하나의 상한을 넘는 뜨거운 키를 만들지 않습니다.

스스로 점검 (1)

  1. Auto Scaling 그룹의 여러 EC2가 같은 업로드 디렉터리를 봐야 한다면 EBS, EFS, S3 중 무엇을 고르고 왜일까요?

    EBS는 AZ 하나의 인스턴스에 붙으므로 맞지 않습니다. 파일 시스템 의미가 꼭 필요하면 EFS, 앱을 고칠 수 있다면 S3에 Presigned URL로 올리는 편이 확장과 비용에서 낫습니다.

  2. 버전 관리를 켠 버킷에서 aws s3 rm으로 지운 파일을 되살릴 수 있을까요?

    네. 버전을 지정하지 않은 삭제는 삭제 마커만 얹으므로, 그 마커를 지우면 직전 버전이 다시 현재 버전이 됩니다.

  3. 작은 로그 파일 수천만 개를 Deep Archive로 옮기는 수명 주기 규칙이 오히려 비용을 늘리는 이유는?

    객체마다 전환 요청 요금과 40KB 메타데이터 과금이 붙기 때문입니다. 묶어서 큰 객체로 만든 뒤 옮겨야 합니다.

  4. 역할로 서명한 7일짜리 Presigned URL이 몇 시간 만에 403이 되는 이유는?

    URL은 서명한 임시 자격 증명이 만료되면 함께 무효가 됩니다. 역할 세션은 기본 1시간, 인스턴스 프로파일은 최대 약 6시간입니다.

  5. Multi-AZ 인스턴스 배포의 대기 인스턴스로 읽기 부하를 나눌 수 있을까요?

    나눌 수 없습니다. 대기는 동기 복제로 장애 조치만 준비하며 연결을 받지 않습니다. 읽기 확장은 복제본이나 Multi-AZ DB 클러스터로 합니다.

스스로 점검 (2)

  1. Aurora가 AZ 하나를 통째로 잃어도 쓰기를 계속할 수 있는 이유를 숫자로 설명하면?

    사본 6개 중 AZ 하나에 2개가 있으므로 4개가 남고, 쓰기 쿼럼이 4이기 때문입니다. 읽기 쿼럼 3과 합치면 7로 6보다 커서 최신 쓰기와 반드시 겹칩니다.

  2. 장애 조치는 30초에 끝났는데 앱은 10분 동안 DB 오류를 냈습니다. 무엇부터 의심할까요?

    JVM의 DNS 캐시 TTL과 커넥션 풀의 죽은 연결입니다. TTL을 60초 이하로, 풀의 최대 수명과 keepalive를 짧게 둡니다.

  3. RDS Proxy를 붙였는데 DB 연결 수가 줄지 않습니다. 가장 흔한 원인은?

    세션 변수 SET, 임시 테이블 등으로 생기는 피닝입니다. 피닝 지표를 확인하고 초기 SET을 프록시의 초기화 쿼리로 옮깁니다.

  4. 날짜(YYYY-MM-DD)를 DynamoDB 파티션 키로 쓴 로그 테이블이 쓰로틀링되는 이유는?

    그날의 모든 쓰기가 파티션 키 하나, 즉 파티션 하나로 몰려 1,000 WCU 상한에 걸립니다. 접미사로 쓰기를 샤딩하거나 고르게 퍼지는 키를 씁니다.

  5. ElastiCache 클러스터 모드를 켰더니 MGET이 CROSSSLOT 오류를 냅니다. 왜일까요?

    여러 키 명령은 같은 해시 슬롯의 키끼리만 됩니다. 키에 {user42} 같은 해시 태그를 넣어 같은 슬롯에 모읍니다.
